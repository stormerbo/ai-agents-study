# P5 offline synthetic evaluation

This package exercises deterministic scoring and report control flow with Python's standard library plus the pinned RFC 8785 JCS helper. Its cases and outputs are fictional, contain no personal data, and are marked `fixture`; this command makes no model or network calls. A green report is not evidence of real provider quality and is never publishable without human review.

Run the development fixture repeatedly:

```bash
python examples/p5-agent-delivery/evaluation/run_fixture.py --split dev --run-id dev-check-1
```

The release manifest pins the datasets, fixture outputs, scorer contract and implementation, prompt/tool schema, lockfile, evaluator and runner by SHA-256. Any material edit invalidates evaluation until a new release freeze is deliberately created. The task is the independent unit; multiple attempts for a case remain grouped under one task and the task succeeds only if all attempts pass.

The `holdout` split in this package is an offline replay fixture, not an official or blind holdout: both `holdout.json` and its expected `holdout-results.json` are checked into this repository. The evaluator reads those saved outputs; it does not run the Agent against hidden cases. Its single-use marker is named `fixture-consumed-*`, and its report explicitly says `blind_holdout: false` and `official_holdout_consumed: false`. Use this only to exercise the scorer and local guard:

```bash
python examples/p5-agent-delivery/evaluation/run_fixture.py --split holdout --fixture-only --run-id fixture-holdout-1 --state-root /path/to/persistent/p5-evaluation-state
```

To additionally exercise candidate provenance checks against the same offline fixture, pass an append-only candidate manifest:

```bash
python examples/p5-agent-delivery/evaluation/run_fixture.py --split holdout --candidate-manifest verify-output/stage5-release/candidate.json --run-id candidate-fixture-check-1 --state-root /path/to/persistent/p5-fixture-state
```

This mode verifies the candidate manifest self-hash, current clean commit, every tracked release material hash, frozen evaluation identity, and the six same-commit drill artifacts. It still scores only the checked-in synthetic outputs and does not execute the candidate. The persistent local fixture guard permits one replay per frozen evaluation release and records which candidate manifest was checked; it does not reserve or consume any official holdout allowance. Keep its state directory separate from any real evaluation registry.

`official_holdout.py` now defines a repository-side orchestration boundary for one authorized run: it checks the candidate image/source, scorer hash, and a frozen executor bundle hash before reserving. `executor_bundle_sha256()` length-prefix hashes `official_holdout.py`, `subprocess_candidate.py`, and the directly imported `canonicalization.py`; changing any of them invalidates the previously authorized spec before reservation. The release manifest also pins each source separately. The dependency lock and evaluator runtime image are recorded independently in the handoff record. The runner requires the registry reservation to bind the full spec hash. `HoldoutReservation` contains no cases and carries a one-time capability in an immutable opaque wrapper: repr is redacted, `dataclasses.asdict()` produces only `<redacted>`, pickle is rejected, and the runner may reveal it to the data plane once. This reduces accidental disclosure/replay but does not prevent same-process introspection. The runner unwraps it only at the call to `HoldoutDataPlane`, presenting it with the frozen runtime identity, which streams one public attempt at a time. The candidate receives only its opaque attempt id, public input, deadline, and exact remaining budget; the capability is never passed to `CandidateRuntime`. The runner records each output, closes and seals the session, verifies the sealed attempt list, output hash, and run/reservation/spec/candidate/image/dataset/scorer identity bindings, records the custodian-issued `output_seal_id` in the completed runner result, and only then calls the separately injected scorer with the sealed output set. The scorer returns one boolean result per opaque attempt id; no label enters the runner report. Scoring is idempotent by `(seal_id, scorer_sha256, output_sha256)`: after a lost response, the runner reconciles that exact key and may replay the identical request once only after the service confirms no result was committed; unknown status leaves the registry reserved. If the close response is lost, `reconcile_seal(reservation_id, runtime_identity, spec)` must return the same durable seal or authoritatively confirm that no seal exists; an unavailable/unknown reconciliation leaves registry state `reserved`. The runner never reruns the candidate. If a run fails before sealing, the data plane must confirm revocation by reservation id before the registry may record `aborted`; an unknown revocation leaves the reservation open for reconciliation. Its report binds the authorization, reservation, and deterministic terminal event IDs, so a lost write response can be reconciled and retried idempotently using the same event identity and payload. Budget and reported-cost inputs must be exact decimal strings (numeric JSON values, including integers and binary floats, are rejected); totals preserve small nonzero values. Missing usage remains unknown. The runtime adapter must enforce provider-side per-call limits against the supplied remaining budget; the orchestration layer can only detect an overrun after a call returns. It is also responsible for forcefully enforcing the wall-clock deadline; this in-process interface can only validate it before and after a call.

The orchestration layer's `max_output_bytes` check remains a second structural guard. Before reserving a run, `execute_official_holdout` also requires the candidate runtime's streaming output limit to equal the frozen run spec; a mismatch stops before consuming the reservation. The POSIX reference adapter in `subprocess_candidate.py` reads child stdout in bounded chunks, stops after `max_output_bytes + 1`, kills the child process group on overflow or deadline, suppresses stderr, defaults to an empty child environment, and parses exactly one strict JSON object (duplicate keys and non-JSON numeric constants are rejected). Eight focused tests cover these behaviors, including that a parent-process credential is not inherited; contract tests also cover spec-to-adapter limit binding and a full adapter/orchestrator run. This adapter is a process-management example only: it does not provide a container/OS security sandbox, provider-side cost enforcement, network restrictions or trusted identity isolation. A formal runner must place it inside an independently configured OCI or equivalent sandbox and retain the outer structural check.

The runner output uses `official-blind-holdout-run-result-v4`; the capstone acceptance gate consumes `official-blind-holdout-evidence-envelope-v6`, which packages the runner result with the separately retrieved registry event chain and gate metadata. Both carry `hash_profile: jcs-rfc8785-v1`. Every `aborted` result must bind runtime-stop and capability-revocation evidence. A recovered terminal event may be authored by the frozen recovery operator rather than the executor, but the evidence envelope must bind the runtime shutdown audit; a recovered completed score must also bind the durable usage ledger. Missing runtime or ledger evidence cannot turn an interrupted run into a passed result. `acceptance.decide` now supports both `single-authority-v1` and `dual-witness-v1`: the latter fetches a latest witness-chain snapshot from an independently configured source, checks source/scope/freshness, verifies each witness signature and chain link, and compares the terminal receipt digest with the separately pinned handoff value. These checks exercise the local verifier contract only; they do not authenticate or prove operational independence of an external witness service. The artifacts are different: a runner JSON file alone cannot satisfy the acceptance gate, and the external evidence assembler has not yet been implemented in this repository. Python producer/verifier and the Node.js `canonicalize@5.1.0` reference adapter both pass the shared RFC/project vectors (`pnpm test:jcs:interop`); the adapter also enforces the project's safe-integer limit. No actual registry implementation, strict service parser, or registry API has been tested.

The terminal registry event must also bind the canonical result-body hash. The runner places `report_sha256` in the result before calling `append_terminal`; the external registry independently recomputes it and records it on the terminal event. The evidence envelope may attach the event snapshot afterward, but that envelope and event snapshot are excluded from the result-body hash to avoid a self-referential digest. The acceptance gate recomputes the result-body hash and checks that the terminal event carries the same value. This detects report edits that preserve a valid-looking event id or output hash; it still does not authenticate the registry itself.

This is not yet a formal blind-holdout executor. The repository does not supply a trusted external append-only registry, hidden dataset custodian, isolated OCI candidate runtime, or independently operated scorer. The injected adapters are trusted interfaces and are not secured by this module; in particular, the candidate adapter must enforce process/container isolation, wall-clock deadlines, provider-side cost accounting, and no access to labels. Real holdout inputs and labels must stay outside this checkout. Contract tests use in-memory fixtures only and make no model or network calls, so they provide no candidate-quality evidence.

Reports use schema `p5-evaluation-report-v3` and bind `hash_profile`, synthetic provider/model labels, release identity, hashes, run id and timestamp. Candidate manifests use schema `p5-release-candidate-v2`. `null` means the metric has no observations. The small synthetic sample's Wilson interval is illustrative and must not be interpreted as a claim about an online model.
