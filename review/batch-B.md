**逐节评估**

- **01-context-is-finite.mdx**：讲什么 —— 用 5 次设计（最高 22.8k token）重测 Lost in the Middle 与 context rot，全部未复现，并把它落回「即使没复现，克制使用上下文的理由一条没少」。覆盖：**强**。缺失子主题：**多文档综合类任务**（论文的真正设定）。作者自己把这条差异列进了对照表（01:92-97）并明确说「我的结论只能说这么远」（01:86），这是本章最诚实的一段；但它仍然是「读者会误以为已推翻论文」的风险点。问题：表格设计①「12k 字符 / 3 位置全遵守」（01:22）是第 0 章的数据，**本节没有复跑**，放在「五次设计」表里会让人以为是本节实测 —— 属于口径混装，低severity。另 `01:34` 列出「134 个风险为高干扰项、266 个预算超 200 万干扰项」，可与 400 段、复合条件自洽（134+266=400，两组互斥），数字没矛盾。`01:215` 如实标注脚本未在官方端点验证 —— 这一节的实测纪律是本章样板。

- **02-system-prompt-altitude.mdx**：讲什么 —— 三种具体度的同一组输入对照，重点是 18 条规则里埋一对矛盾后同一个 prompt 跑 12 次出现 8:4 分裂；再给出「让模型自己审规则集」这条低成本 CI 探针（02:198-202）。覆盖：**强**。缺失子主题：**规则冲突的自动化检测**只给了「问模型」一条，没有提「把规则写成可测断言 / 结构化 YAML + 冲突规则引擎」这条根本解 —— 但 02:202 明确标注了「判断辅助，不是证明」的边界，属可接受的取舍。问题：`02:18-24` 表格和 `02:44-58` 表格的样本量不统一（3 个典型+1+2 = 每配置 5 次，但单条规则那行是 /4，其它行 /4 与 /5 混排），读者无法反推出到底每个配置跑了几次；`02:54-57`「只留 7+12 → 2/4」「7+12+18 → 1/4」「同一配置再跑 → 4/4」三行并列时，第三行是**同一配置的第二次运行**，但表里没有「第几次运行」这一列，只有正文一句提示（02:61）。这是真实分裂的证据，但表格形态会让快速浏览者误读为不同配置。

- **03-just-in-time.mdx**：讲什么 —— 两组实测把「按需取一定更省」翻转为「交叉点 ≈ 需要的占全部 20%」；再补两段工程化内容：取不到时的错误回填（03:216-234）与索引过期（03:236-242）。覆盖：**强**。缺失子主题：**按需取的检索质量本身**（索引怎么写才找得到）完全没提，全部推给第 6 章 —— 衔接合理，但这一节标题承诺的是「即时检索」，读者会预期至少有「目录粒度」的讨论。问题三处：(a) `03:25` 说「token 为**全部轮次的三项之和**」，而 `03:144-155` 的函数 docstring 写「必须用四项之和」、实现只有三项、且**没有 output_tokens** —— 正文与代码自相矛盾，且代码实现与它自己的注释矛盾；(b) `03:133-141` 的 `read_doc` 工具用 `{"id": ...}`，而 `03:178-201` 的循环里对每个块取 `b.input.get("id")`，一致，无 bug；(c) `03:224-228` 的「取不到」对照表只有一行（做了正确回填的 4/4），**没有对照组的实测数据**，只是引用第 4 章的结论 —— 作为「实测」证据链偏薄，好在作者没有把它包装成独立实验。

- **04-compaction.mdx**：讲什么 —— 两组实测（压缩比不压缩贵；摘要 7/8 而结构化笔记 8/8，丢的是硬约束），加一段「丢掉之后模型会不会承认自己不知道」（04:175-189，含 5/5 vs 0/5 的对照）。覆盖：**强**，尤其 `04:185` 那段「推理来源是假的」是本章最值钱的一段。**问题（P0）**：本节正文与本章 meta.ts 的实测数字**互相打架** —— 正文 `04:20-23` 表是「A 完整历史 1952 / B 摘要 2272 / C 结构化笔记 4246，三条路线全部 3/3」，`04:45-49` 第二组表是「摘要 138 字 812 token / 结构化笔记 880 字 2776 token」；而 meta.ts:141 的 checkpoint 答案是「摘要保住 7 条…摘要比不压缩更贵（实测 2272 vs 1952 token）」，meta.ts:149 又写「产物更长、更贵（880 字 / 2776 token vs 摘要 138 字 / 812 token）」。正文里 **4246 这个数字在 meta 中完全不存在**，meta 也没有 `3/3`。读者按 checkpoint 自测会对不上正文。这不是措辞差异，是同一节两套数字。

- **05-subagent-isolation.mdx**：讲什么 —— 两个方向相反的实测（隔离更省 1/5 上下文、总 token 9182 vs 25913；共享背景重复装载时贵 8.1 倍），统一成「成本 = 内容 × 装载次数」，再加失败模式三种（05:186-194）。覆盖：**强**。这是本章论证结构最完整的一节：先给反例、再给统一规律、再给失败模式。问题：`05:61-62` 说「实测一里 20 篇原文在 A 路线上被装了 4 次」，与 `05:26` 的「4 轮 × 约 4600 token」一致，可复核；`05:119-120` 的注释「本次写作里踩过三次」与 01:82 的「已经在本站出现过两次」、05:51 的「第三次」构成一条跨节计数，**前后自洽**（两次在第 1、4 节实例 + 本节 = 三次），这是好的内部纪律。**唯一实质问题**：`05:129-136` 的 `total_tokens` 含 output_tokens 且注释写「四项之和」，而它是「实测一/二」的口径 —— 与 03 节（三项）不一致，读者照抄两个脚本会得到不可比的数字。

- **06-chat-template.mdx**：讲什么 —— 把「消息数组 → token 串」的渲染层讲清楚：同样内容拆 10 轮多 60 token（25%）、位置/角色影响渲染、缓存哈希是对渲染后 token 串做的、由此得出「能用一轮别拆多轮」「结构变化不免费」「不要手写估算公式」三条推论。覆盖：**中**。缺失子主题（P1）：**Chat Template 的可实现层** —— 这一节讲的是 API 厂商黑盒里的那一层，但完全没有提「本地模型（vLLM / llama.cpp / HF）的 chat template 是 Jinja 模板，你可以自己看、自己改，而且改错会让模型行为崩掉」这条对「工具地图」（第 21 章）直接可用的内容；也没有提 Chat Template 与 **tool 定义如何渲染**（tools 渲染成什么角色块）的关系，而这正是上一节与下一章的交点。问题：(a) **缺 `实跑状态` 标注**（本节是本批 3 节无标注之一，另两节是 07、08）—— 它有实测表格（06:16-20、06:34-40）和一段代码，按 AGENTS.md §3.4「跑不了的标注实跑状态」，这里是缺的；(b) `06:17-20` 表格的 token 数与 meta.ts:205 一致（238 / 298 / 60 / 25%），内部自洽；(c) `06:67-68`「OpenAI 把 system 当成 messages 里的第一条」表述不严谨：OpenAI Chat Completions 里 `system` 是 messages 数组内的一种 role，但 LiteLLM/OpenAI Responses API 用的是 `instructions` 顶层参数 —— 把它说成「第一条消息」在 Chat Completions 语境下勉强成立，但「本质是这一层的差别」这个结论在 Responses API 下不成立。**确信度：中**。

- **07-kv-cache.mdx**：讲什么 —— 从 KV Cache 按位置累积推出「前缀稳定是架构约束」，四条约束（稳定前/变后、工具定义顺序固定、压缩有缓存代价、渲染参数不可中途改），外加一段钱账。覆盖：**强**（机制层这一节的价值最高，07:52-56 的三层表是本章最有信息量的一张图）。**P0 风险**：`07:111-114` 写「按第 1 章那条记账口径（`input + cache_read + cache_creation`），两者**总 token 数是一样的**（都是 20 × 1024 的输入量级），但**计费口径完全不同**」。这句话在同一个「token 数」和「计费」之间来回，且与本节自己的数据冲突：`07:16-21` 实测恰恰显示命中缓存时 `input_tokens` 从 1205 掉到 181 —— 也就是说**未命中与命中的输入 token 数不同**（总 token 数含 cache_read 才相等，但「20 × 1024」对两种结构都不成立：命中侧是 181 + 1024 cache_read）。读者如果只读这一句，会得出「缓存只省钱不省 token」这个与 07:172 自相矛盾的结论。改成「两者覆盖的 token 总量可以相同，但你付的是不同的单价」才准确。另两处：(a) **缺 `实跑状态` 标注**（有 07:16-21 实测表与 07:127-148 代码）；(b) `07:155` 引用「第 18 章（成本与延迟）做那个『工具定义占 62%』的实测」—— 已核实存在：`cost-and-latency/01-cost-model.mdx:107,126`，引用成立；`07:94` 引用「第 1 章第 2 节记过：同一个会话里改变顶层的 `effort`」—— 第 1 章第 2 节确实是 sampling-params，可信。

**逐节评估**

- **01-what-really-happens.mdx**：讲什么 —— 抓一次完整往返的原始结构（stop_reason=tool_use、thinking 块、input 已是对象），三个必须由你补的环节，两种 400 硬错误（缺 tool_result / tool_use_id 写错），再补两段未复现（模型不会硬编参数；工具返回值格式差异测不出）。覆盖：**强**。缺失子主题：**流式下的工具调用**只有一句带过（01:34「参数是一段段拼出来的」，引用第 1 章的 18 分片），没有讲按 index 累积拼装 —— 这是实际写代码时最容易错的地方，而 `claude-streaming` 资源就在库里（resources.ts:148-162）。问题：(a) `01:234` 说「缓存层级是 tools → system → messages」并称「第 1 章讲过」——第 1 章 `prompt-caching` 节确实讲前缀顺序，但**第 1 章从未给出「三层」这个顺序**（resources.ts:163-166 那条也只讲前缀），这是把 externals 的知识安到了第 1 章头上，属**归属不实**，确信度中高；(b) `01:240`「只挑文本会让下一轮缺少 tool_use 块，tool_result 就配不上对了 —— 直接 400」**归因不准**：真实报错（01 节自己在 04 节引到的那条）是 `The content[].thinking in the thinking mode must be passed back to the API`，即缺的是 thinking 块而非 tool_use 配对；`tool-calling/04-parallel-and-errors.mdx:103-116` 给了正确的报错原文，两节对同一现象的归因不同。**确信度：高**（有 04 节的原始报文对照）。

- **02-schema-design.mdx**：讲什么 —— 一句描述同时修正参数格式与误用（02:24-35）；enum 把校验从运行时提前到生成时（02:59-66）；一份 5 项自检清单；三类 schema 写法错误（两个会 400，一个 200 不报错）。覆盖：**强**。缺失子主题：**工具的 description 与 input_schema 之间的一致性**没有讲（例如 description 说「按城市名查」而参数名是 `q`）；也**完全没有提工具命名对模型选择的影响**（`search_orders` vs `find_order` 的动词差异在 05 节才被当作变量测，02 节没建立这个维度）。问题：(a) `02:194-206` 的第三条「`required` 写了不存在的字段 → HTTP 200」结论可信，但**没有给原始响应**（前两条有报文原文，第三条只有一行描述），四块里的「错误案例」这一条在本节偏弱；(b) `02:130-145` 的 `TOOL` 定义里 `required: ["level"]` 与 `properties` 一致，脚本本身没问题；(c) `02:98` 自检清单第 5 条「描述里有给人看的话吗」判据是「对模型决策无用」，方向对但**不可机判**，与本节开头「判据全部可机判」（02:113）冲突 —— 清单与脚本的口径不一致。

- **03-poka-yoke.mdx**：讲什么 —— 两个危险动作实验：按路径删 vs 先列编号再删（都不删，但后者能自己定位）、互斥可选参数的三级修法（①不修 3/3 冲突 → ②写描述 0/3 → ③拆工具 0/3 且结构上不可能）；改造清单 5 条；由「required 不一致不报错」推出「结构能消除的错误才叫结构性防护」。覆盖：**中**（论证清晰但结论弱）。**核心张力（P1）**：节标题与 meta.ts:91-92 都主张「让错误在结构上不可能」是「本章最值钱的一节」，而本节自己的实测是 `03:33`「两个变体都没有真的去删」、`03:211`「模型一次都没有鲁莽下手」—— 也就是说这一节**没有测到 poka-yoke 防住了任何一次真实错误**，所有收益都是「模型能自己把问题查清楚」这种体验层收益。作者在 03:35-37、03:211 已经明确写了这一点（诚实），但**没有回答「那我为什么还需要 ③ 而不是 ②」的定量问题**：在 ② 已经 0/3 的情况下，③ 的增量价值完全建立在「换模型/换场景之后约定会被稀释」这个**未实测**的假设上（03:68、03:215）。这不是错误，是**该节的中心论断缺一个实测支撑**。问题：(a) `03:19-22` 表格 A/B 两种接口，「B」定义里 `delete_file(file_id)` 的 `file_id` 只在描述里说「只能原样取自 list_files 的返回结果」（03:127），但**代码层没有校验 file_id 的来源**（只在 `delete_file` 里校验存在性，03:145-149）—— 一个模型完全可以传 `file_id="f_002"` 而跳过 `list_files`（只要它猜到了编号），所以题面宣称的「想删一个没看过的文件，连表达都表达不出来」（03:37）**在实现上不成立**：表达得出来，只是需要猜中。这是一处**说法强于实现**，确信度高（代码在 03:145-149，无 provenance 校验）；(b) `03:51` 表注写「三个请求各跑一遍」，但同一表里写 `3/3`、`0/3` —— 一边说 3 次请求、一边用 /3 的比例，口径又绕了；(c) `03:171` 用 `IMPL[block.name]`（会 KeyError）而 01:207 用 `IMPL.get(block.name)` + 未知工具分支 —— 两节的健壮性处理不一致，照抄 03 的版本遇到未知工具会崩。

## 批次总结

**最严重的 3 个问题（跨章）**

1. **P0 — 实测数字在正文与 meta.ts 之间分成两套**（`context-engineering/04-compaction.mdx:20-23` vs `meta.ts:141,149`）。这是全批唯一一处「读者照着 checkpoint 自测会对不上正文」的问题，也是最容易被外传的错误（正文 4246 / meta 2272，正文 3/3 / meta 7-8/8）。其余数字问题都是口径与措辞级，只有这一处是两套数据并存。
2. **P0 — KV Cache 节的收支结论与自己的实测相反**（`context-engineering/07-kv-cache.mdx:111-114`）。「两者总 token 数是一样的」与 07:16-21 的 1205→181 实测、07:172 的「`input_tokens` 命中时会变小」冲突。这一节是全书讲缓存机制的核心，读者据此建立的心智模型会错。
3. **P1 — 记账口径「三项 / 四项」在全批至少 6 处不一致，且其中一处是代码注释与实现不符**（`context-engineering/03-just-in-time.mdx:145-155`、`05-subagent-isolation.mdx:130-136`、`07-kv-cache.mdx:36,111`、`tool-calling/05-tool-count.mdx:22,144`）。两章的实测表格都建立在这个口径上，不一致意味着**表格之间不可比**，而「可比性」正是这一章全部论证的基础。

**本批次最有价值的 2 节**

1. `context-engineering/07-kv-cache.mdx` —— 把 KV Cache / Prompt Cache / 客户端缓存三层分清（07:52-56），并给出「哪些上下文结构在架构上不可用」的四条约束。**前提是先修掉 07:111-114 那句收支结论**；修掉之后它是全站机制层最有价值的一节。
2. `tool-calling/05-tool-count.mdx` —— 全批唯一一节把「我测不出这个流传很广的结论」写成了正面教学内容的节，并且把测量缺陷（对照组缺答案）下沉进了可运行脚本的注释与输出里（05:130-135、05:179-180）。

**对「是否成体系」的总体判断**

这两章**成体系，而且是全站体系性最强的一段**：章 3 内部有「策略（01-05）→ 机制（06-08）」的清楚分层，且 07 节明确回收了 04 节的结论（07:91-92 把「压缩更贵」归因到缓存断点）；章 4 内部有「机制 → 软约束 → 硬约束 → 并发失败 → 规模」的递进，01→02→03→04 的引用链在正文里显式标注且**全部指向真实存在的节**。跨章引用也基本可靠：核实了「第 18 章 62%」（`cost-and-latency/01-cost-model.mdx:107,126`）、「第 5 章 `maximum`/`pattern`/`format` 不生效」（`structured-output/02-json-schema-strict.mdx:38,216`）、「第 16 章沙箱」等引用均成立；`tool-calling/03-poka-yoke.mdx:217` 把「不可逆动作要一步确认」指向第 16 章，内容上更贴第 19 章，但第 16 章确实讲权限与执行策略，属可接受。

真正削弱体系性的不是缺内容，而是**同一批实测数据在不同位置被写成不同的数或不同的口径**：读者无法判断哪张表能和哪张表相加、哪个 checkpoint 答案与正文对应。就「目标读者是后端工程师」而言，这两章的适配度是全批最好的 —— 每节都在用接口契约、枚举类型、幂等键、缓存前缀、资源调度这些后端既有概念做锚，几乎没有把读者当小白，也没有预设 ML 知识。**结论：可发布水平之上，但上面 3 条中最少要先修 2 条 P0，否则「实测站」这个核心卖点会在最懂行的读者那里先破功。**
