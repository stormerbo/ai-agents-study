## 批次总结

**最严重的 3 个问题（跨章）**
1. **可运行代码与声明的"实跑输出"不一致**（P0）：continuous-evolution/01-from-traces.mdx:120-128 的 `classify` 对"什么样的回答算得体"实际返回"指令"，正文 01:148 却印着"参数"；抽出来跑一遍即可复现。这不是笔误，而是分类体系里 PARAMETER 档被自己的分支顺序屏蔽了 —— 而这一档正是本节的核心论点。对整个站点来说，"实跑"是立身之本，此处等于自证不成立。
2. **实测数字的机制解释错误**（P0）：coding-agent/03-file-editing.mdx:60-63 把一个 83 行文件里"匹配 1879 次"解释成"一段很长的通用字符串"，而复算表明 `count("")=1879`（len+1），长串只会匹配更少；真正的成因是空 old_string，正文给出的因果是反的。
3. **章号/条目引用在系统层面陈旧且互相打架**（P1 群）："第 9 章那五个零件"（应为 11）会被 UI 自动链接到错误的章；"第 20 节"（应为第 20 章）；"全书二十二章/前面二十一章"（应为 26 章/前 25 章）；capstone 的加固清单在"明确不做"与"待办"之间自我否定；meta 里把自跑实验标成 `documented`。这些都不影响单节阅读，但**恰好把这本书最引以为傲的"准确性机制"（basis 标注、章号引用、清单可核对）在元数据层削弱了**。

**本批次最有价值的 2 节**
1. **continuous-evolution/02-distill-and-test**：把"从失败里学习"的结构性矛盾（规则来自罕见情况，而验证需要大量同类任务，偏偏那些任务模型本来就会做）讲透了，并用两个真实的 max_tokens 假发现演示"先怀疑测量方法"——全批洞察密度与诚实度最高的一节。
2. **coding-agent/02-search-strategy**：三种上下文组织方式有脚本、有日志、有 token 数，结论（grep 省约一半且不掉点、符号索引答不了"谁调用它"）可直接用于工程决策；"基础设施坏了但表现得像查无此物"是本批最好的失败模式命名。

**对"是否成体系"的总体判断**
四章的宏观结构是成体系的：源码研读（方法）→ Coding Agent（最成熟的形态）→ 持续进化（上线之后）→ 综合项目（组装），且每章的引用大多能落到具体章号与具体数字，跨章"结论回写"（第 22 章→第 13 章）是真实发生的。但体系化的代价是把章号写死了：本书经过一次章序调整（coding-agent/continuous-evolution 插入、capstone 顺延），大量"第 N 章/第 N 节/前面 N 章"没有跟着改，而 UI 又会对"第 N 章"自动生成链接，于是**陈旧引用从"读起来别扭"升级成"点过去是错的"**。更实质的缺口是两个：Coding Agent 章完全没有版本控制维度（改文件却不谈提交/分支/回滚），持续进化章完全没有轨迹治理维度（用真实轨迹却不谈脱敏/留存/采样）。这两块不补齐，两章都停在"机制讲解"而没有覆盖工程师真正要做的动作。建议下一轮优先做三件事：① 用脚本重跑并修正连续进化与 capstone 的三处数字；② 用"概念→章号"白名单扫一遍所有"第 N 章"；③ 给 coding-agent 补 git 工作流、给 continuous-evolution 补轨迹治理。
