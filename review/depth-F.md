### 章：MCP（协议）的两处最薄弱内容（要详细）

1. **第 3 节「MRTR：服务端不再主动发请求」——回程报文缺失，且代码自造字段**
   原文：「客户端补上输入后，**再调一次**。」（03 第 88 行）；而实现里是 `if not params.get("_confirmed"):`（03 第 239 行）。
   为什么读者在这里会卡住：这是本次协议修订第二重要的变化（第 66 行自称），读者要落地的正是"回程"。正文只给出 `resultType: input_required` 的**响应**，没有第二次请求的完整报文——补的输入放哪个字段、`inputRequests[].id` 如何与回答对应、客户端拒绝或超时返回什么、`id` 不匹配怎么处理，全无交代。而代码里的 `_confirmed` 是本节自造字段，文档却声称"按规范描述的形态实现"（第 58 行）；读者照抄后接第三方 server 会对不上协议。
   要补成什么样：
   - ① 第一次 `tools/call` 请求原文（含 `_meta.protocolVersion` + `clientCapabilities`）与 `input_required` 响应原文；
   - ② 第二次**完整请求报文**：明确"回答放在 params 的哪个键、必须原样带回 `id`"；
   - ③ `input_required` 被拒绝、超时、部分满足三种返回形态；
   - ④ 一行醒目标注区分"本节约定字段 `_confirmed`"与"规范定义的字段"。

2. **第 2 节「三类能力：谁决定用它」——核心决策没有产物支撑**
   原文：「优先用它的 resources，谨慎使用它的 tools。」（02 第 50 行）与第 113-121 行的三步接入顺序。
   为什么读者在这里会卡住：这一节的价值全在"从控制权最强的能力开始用"这条决策上，但读者手上没有 resources 与 prompts 的任何形态——全文没有 `resources/list`、`resources/read`、`prompts/list` 的报文，配的「完整可运行代码」只声明了 `capabilities: {"tools": {"listChanged": True}}` 和 tools（02 第 184-189 行）。于是"优先用 resources"停留在口号：不知道它长什么样、怎么读进上下文、读进来放哪个位置、与 tools 在消息层的区别是什么。第 30 行"host 可以把来自不同 server 的工具放在不同的权限桶里"同样无落点。
   要补成什么样：
   - ① 一份 `resources/list` 返回（`uri`/`name`/`mimeType` 三字段，体现"可读数据"与工具的区别）；
   - ② 一次 `resources/read` 往返，并写明读到的内容被拼进 system 还是 user 消息；
   - ③ 一份 `prompts/list`（含 `arguments` 定义）与用户选择后的填充结果；
   - ④ 一句权限桶的可执行说明（例如"按 server 维度维护一份 allowlist，调用前查表"）。
