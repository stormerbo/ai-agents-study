## 深度批次 A：读源码（reading-source，第 22 章）

### 逐节

- **为什么读到一定阶段必须读源码** ｜等级 A ｜最缺的一样：全节赖以成立的两个核心名词（JSON schema、enum）零解释。
  - 未解释名词：`schema`（首现于「那个参数只有 {"type": "string"}，没有 enum」前一段）、`enum`（首现于「没有 enum」）、`docstring`（首现于「convert.py 里五处重载」段之前）。正文对 enum 只给了数值形态的对照（`"enum": ["明天", "后天"]`），从未说明它和 `description` 在模型侧的作用差异 —— 而这正是本节结论「把约束从散文搬进类型标注」的全部理由。
  - 无示例的产物/跳过的步骤：产物不缺（三组对照 + inspect 脚本 + 真实输出齐全）。跳过的是从「schema 里有 enum」到「模型因此不能乱填」这一步 —— 读者不知道 enum 是给解码器用的硬约束，还是只是又一段提示。
  - 最该补的：在第一个代码块前加 4 行，说明「schema 是发给模型的工具说明书；description 是建议，模型可以不听；enum 是解码时被强制过滤的取值集合」，并配一句「模型想输出『大后天』时会发生什么」。
- **挑项目：按理由，不按热度** ｜等级 A ｜最缺的一样：两个核心工具名词只点名不解释。
  - 未解释名词：`tree-sitter（就是 Aider 那个 repo-map 用的东西）`（首现于「Python 用 ast，JS/TS 用 tree-sitter」）—— 括号里给的是另一个未解释名词；`AST`（首现于「这类问题需要 AST 级别的分析」）。reader 知道 Python 的 `ast`，但不知道 JS/TS 侧该装什么、AST 分析比 grep 多做什么。
  - 无示例的产物/跳过的步骤：量法示例完整（文件数/行数代码 + langchain_core ~200 文件 ~50000 行、langchain ~50 文件 ~10000 行的真实输出）。跳过的是「定位那条调用链」本身的可操作步骤 —— 正文说「先定位那条调用链，再量它经过的模块」，但没有给一个「怎么定位」的动作。
  - 最该补的：把 tree-sitter 换成一句可执行的替代（「JS/TS 用 `npx tree-sitter parse` 或退化成 grep `^function `」），并给一句定位调用链的最小命令。
- **沿着一次任务读到底** ｜等级 B ｜最缺的一样：本节「完整可运行代码」复制出来跑不了，而它正是本节强调的产出形式。
  - 未解释名词：`重载 / @typing.overload`（首现于「那是 @typing.overload 的写法」）—— 只说了「给不同调用方式提供类型提示」，没说清为什么会有五个同名定义、为什么真正跑的是最后一个；`properties`（首现于 _get_filtered_args 注释）未解释。
  - 无示例的产物/跳过的步骤：产物有（链路图 + 三组 schema 对照 + 真实输出）。**可执行性欠缺（实读确认）**：脚本正文里 `def summary(t): return t.args_schema...` 在**本节缺失**，只在本章第 5 节的同名脚本里才定义（第 5 节脚本有 `def summary`），读者从本节复制脚本会在 `summary(t)` 处 NameError。此外正文自相矛盾两处：一处写 `base.py:95 附近`、同段的代码注释与结论写 `base.py:103`；第一步给读者的命令 `grep -n "^def tool" convert.py` 与它随后声称的「五个定义」也对不上（若那五处定义带 `@typing.overload` 装饰器，该模式按行首匹配，读者复制这条命令得到的行数与原文不一致，正是本节自己说的「第一跳」）。
  - 最该补的：把 `summary` 函数补进本节脚本（或改成内联一行），并把 `base.py` 那一处的 95/103 统一。
- **横向对比：同一个能力的不同实现** ｜等级 A ｜最缺的一样：一个判断结论与自己的示例互相打架。
  - 未解释名词：`inputSchema` / `tools/list`（首现于「MCP 的 tools/list 规范只要求 server 提供 inputSchema」）—— 没有说明这两个是 MCP 协议里的什么东西（请求方法名？响应字段？），reader 只能靠上下文猜。
  - 无示例的产物/跳过的步骤：产物完整（三种实现并排 + 三个读数 + 三问框架）。跳过的是「我怎么自己跑出 C 那一组」——C 的数据形态在代码里是手写的字面量，读者拿不到一个真 MCP server 去对照，无法验证「协议不要求 required」。
  - 最该补的：明确标注 C 是「第 14 章实测抓到的真实响应删减而成」，并补一句「自己复现需要什么」（一个 MCP server + 一次 tools/list 调用），否则这一节的核心证据只能信、不能验。
- **读完要产出什么** ｜等级 A ｜最缺的一样：与第 1 节共用同一份脚本，读者会以为「四种产出」各有实现。
  - 未解释名词：`site-packages`（首现于 `inspect.getsourcefile(target).split("site-packages/")[-1]`）未解释；`site-packages` 对 Java/Go 背景读者不是常识。
  - 无示例的产物/跳过的步骤：四行模板与位置校验脚本完整（含反例「手写位置无法自动校验」）。跳过的是「归档到哪里、用什么命名」——正文说「放进仓库脚本」，但没给目录约定或文件名约定，读者仍要自己发明一套。
  - 最该补的：`inspect.getsourcefile` 那行加一句「如果不含 site-packages（比如项目内代码），split 的结果就是完整路径」；并对四行模板补一句文件命名建议。

### 章 22：读源码 的两处最薄弱内容（要详细）

1. **第 3 节的「完整可运行代码」不可运行，且与本节「可复现才是最强产出」的主张冲突**
   - 原文片段：脚本内 `print("  %-32s %s" % (label, json.dumps(summary(t), ensure_ascii=False)))`；以及 `def summary(t): return t.args_schema.model_json_schema()["properties"]["day"]`（后者只存在于第 5 节的脚本 `verify-output/read-source-tool.py:52`）。
   - 为什么读者在这里会卡住：这一节从头到尾在讲「怎么得到一手证据」，最后一屏给出代码，读者的第一个动作就是复制执行。执行到 `json.dumps(summary(t))` 直接 `NameError: name 'summary' is not defined`。对一个「以可验证性为卖点」的章节，第一个交互动作就失败，后面所有「预测—验证」的说服力都会被折价。同一节的 `base.py:95` 与 `base.py:103` 不一致会加剧这一点：读者去翻源码对不上。
   - 建议补成什么样（骨架）：
     ```python
     def summary(t):
         """取参数 schema —— 本节 §3 的对照全部依赖它。"""
         return t.args_schema.model_json_schema()["properties"]["day"]
     ```
     并统一行号；同时在脚本输出里加一行自检：`assert summary(a_default) == {"title":"Day","type":"string"}`，让「行号会变、断言不变」（第 5 节的主张）在本节就兑现。
2. **enum / JSON schema 的机制缺席，导致「约束要写进类型标注」这条唯一产出无法被真正理解**
   - 原文片段：`{"description": "只能是「明天」或「后天」", "title": "Day", "type": "string"}` 对 `{"enum": ["明天", "后天"], ...}`，正文结论是「散文只能生成 description，生成不了约束」。
   - 为什么读者在这里会卡住：一个有后端经验的人会立刻问第二个问题 ——「description 给模型、enum 给谁？如果模型就是生成器，两者不都是提示吗？」原文从头到尾没有出现「解码」「约束解码」「取值集合」这类词，也没有一句话说明 enum 被谁、在哪个环节强制执行。所以读者能背下结论「写进类型标注」，但不知道它在哪一层生效、什么时候会失效（例如 enum 之外的字符串真的会被拦住吗）。
   - 建议补成什么样（骨架）：
     1. 一句机制：「schema 是随请求发给模型的工具定义；description 进的是自然语言提示，enum 进的是 api 侧的取值校验/约束解码 —— 前者模型可违反，后者在协议层被过滤。」
     2. 一个可验证判据：「让模型对 day 传 `"大后天"`，看请求是 400 还是模型自己改口」——这是后端读者熟悉的「校验在哪一层」的问题。
     3. 一句话边界：「enum 只约束取值，不约束必填；必填由 required 表达」（正好接第 4 节）。

### 本批次总结（读源码）

- 最严重的 3 个「读到一半读不下去」的点：
  1. 第 3 节脚本用未定义的 `summary(t)`（「json.dumps(summary(t), ...)」）——复制即报错，直接否定了本节的产出主张。
  2. 第 1、3 节反复出现 `enum` / `schema` 却零机制解释（「那个参数只有 {"type": "string"}，没有 enum」）——结论可背、不可懂。
  3. 第 3 节同一函数位置既写 `base.py:95` 又写 `base.py:103`，且 `grep -n "^def tool"` 与「五个定义」对不上（「五个定义，都不是重复实现」）——读者按原文操作会得到相反结果。
- 做得最透的 2 节：
  1. **第 3 节沿着一次任务读到底**：五跳链路每跳都标 file:line，三组对照给真实输出，最值钱的是一条「预测之外」的发现（整段 docstring 漏进工具描述）——「机制 + 产物 + 反例」三件齐备，是本章的方法范本。
  2. **第 4 节横向对比**：把同一能力在语言层/应用层/协议层各写一遍并排输出，产出「谁负责保证正确」这张边界表，并给了可照抄的三问（层次/责任方/能否发现）。这是全批次里唯一把「抽象概念」转成「可执行检查表」的写法。

## 深度批次 B：Coding Agent（coding-agent，第 23 章）

### 逐节

- **为什么 Coding Agent 是一个分水岭** ｜等级 B ｜最缺的一样：全节的方法论核心（agent 循环）只有主张，没有可运行的循环骨架。
  - 未解释名词：`agent 循环`（首现于「这就是第 11 章那个 agent 循环的最自然形态」）——本节只作为一个已完成的概念引用，读者若跳读第 11 章则无法继续；`世界图景`（首现于「它必须先从上下文里重建出足够准确的世界图景」）未解释。
  - 无示例的产物/跳过的步骤：有 5 个 fixture 的实测表与 `truncate` 反例全文。跳过的是「这个循环长什么样」——读者知道「要循环」，但不知道每轮把什么喂回去、怎么判定收敛、代码挂在哪儿。
  - 最该补的：本节末尾补一个 20 行的最小修复循环（跑测试 → 把原始报错拼进下一轮提示 → 再跑），让第 2 节「一次成型不现实」有一个可运行的对应物；本节目前只有反例、没有正例。
- **搜索：在大仓库里找到那一处** ｜等级 A- ｜最缺的一样：真仓库里「命中 200 行怎么排序截断」只有一句话，没有示例。
  - 未解释名词：`tree-sitter / repo-map`（首现于「JS/TS 用 tree-sitter（就是 Aider 那个 repo-map 用的东西）」）；`符号索引`（首现于「C. 只给符号索引」）虽由前文代码定义，但「索引和代码不同步」这个它在 Mermaid 里自己点名的风险没有任何处置办法。
  - 无示例的产物/跳过的步骤：skip 的步骤很具体 ——「两级检索」（先 grep 出所有命中的文件，再按命中次数或是否含 def/class 排序，只把前几个文件的命中行塞进去）只有一句话，没有一段做这件事的代码，也没有一次真实输出（截断前后各多少 token）。读者能读懂策略，写不出这个策略。
  - 最该补的：给一段 `rank_and_truncate(hits, top_k=5)` 的实现 + 一次真实输出（命中 312 行 → 截到 8 行、token 从 X 降到 Y），并让它在 fixture 上可复现。
- **文件编辑：为什么模型总改错** ｜等级 A- ｜最缺的一样：正文里的示例代码自身有语法错误，而本节还要求读者「注意报错文案是功能的一部分」。
  - 未解释名词：无严重（`old_string`/`new_string` 由上下文定义清楚；`幂等`/`AST` 对目标读者是已知或已解释）。
  - 无示例的产物/跳过的步骤：A/B 两组对照 + 三个真实失败形态（「匹配 0 次」「匹配 1879 次」「JSON 解析失败」）都齐全。跳过的是失败**原始形态**：读者看不到模型那次「JSON 外面加了说明或代码块围栏」的原始输出长什么样，也就无法设计自己的容错解析。
  - 最该补的：贴一段真实的裸模型输出（带围栏、带解释），再贴正确的解析方式；并把「JSON 解析失败」两次失败的原始文本一并列出 —— 本节的 `apply_edit` 两版代码本身是合法的（实查引号均为半角），但读者看不到失败在解析器的哪一步，也就写不出容错分支。
- **验证与恢复：报错之后该给它什么** ｜等级 A ｜最缺的一样：三块「该给什么」的规则没有对应的提示词文本。
  - 未解释名词：`断言`（首现于「同一个断言连续失败 2 次」）对后端读者是已知词，可接受；`Pass^k` 未在本章出现。
  - 无示例的产物/跳过的步骤：`fix_loop` 完整（含 SAME_FAILURE_LIMIT、tried、模型未改动检测）与计数器重置 bug 都很好。跳过的是本节标题的那个问题「报错之后该给它什么」的**最终产物**：`ask_model(code, err, hint, tried)` 内部的提示词长什么样、原始报错用什么包裹、已试方案怎么列，全部留白。而正文断言「加上一句『你已经试过 A、B 两种做法，都失败了』会让它更换方向」——这一句就是最有价值的产物，却没有给出。
  - 最该补的：给出一个完整的下一轮提示模板（系统段 + 原始报错原文 + 已试方向列表 + 本轮要求），并配一次真实对话截断（第 2 轮 vs 第 4 轮的 hint 差异）。
- **安全边界：能执行代码意味着什么** ｜等级 A ｜最缺的一样：最强的一层防护（网络白名单）在代码里被写成了形同虚设的形态，且安全语境的免责缺席。
  - 未解释名词：`bubblewrap`（首现于「一个受限的进程（容器、bubblewrap、或者至少一个专用的低权限用户）」）——只给了名字，没有一句它做什么、在 Linux 上怎么用、能不能在 macOS 上跑（本文其他地方的实跑环境是 macOS 路径）；`typosquatting`（首现于「一个拼错的包名（typosquatting）」）括号里给的是现象不是机制。
  - 无示例的产物/跳过的步骤：`Sandbox` 与 `build_policy` 完整，三档表可照抄。跳过的是「按域名放行 pypi.org 到底能防住什么」——同样的代码可以 `POST` 到 pypi.org 的任意路径，白名单只约束了目标域名，不约束动作。正文没有写出这条边界，读者会以为开了 `allow_network_hosts` 就安全了。
  - 最该补的：在「网络边界」那一段补一句「域名白名单防的是『把数据发到自己家服务器』，不防『往白名单域名发任意请求』；要防后者需要出网代理 + 内容检查」，并给 bubblewrap 一句可执行说明或换成通用表述。

### 章 23：Coding Agent 的两处最薄弱内容（要详细）

1. **第 4 节标题问题「报错之后该给它什么」，恰恰是全章唯一没有给出产物的地方**
   - 原文片段：正文写「加上一句『你已经试过 A、B 两种做法，都失败了』会让它更换方向」，以及代码里 `new_code = ask_model(code, err, hint, tried)`。
   - 为什么读者在这里会卡住：这一节的实测（4/5 修好、2 轮收敛、1 个 5 轮不收敛）全部指向一个结论 —— 决定成败的是「喂回去什么」。但 `ask_model` 只有一个签名，没有提示词正文；`hint` 的两种分支也没有展开成完整文本。读者读完会认同「要给已试方案」，但打开编辑器时写不出第一条。这是典型的「只讲要注意、不讲怎么注意」：规则有了（给原始报错、给已试方案、别塞整个文件），形态没有。
   - 建议补成什么样（骨架）：
     1. 一个完整提示模板，三段结构：`【原始报错】`（逐字贴，含 AssertionError 的期望/实际值）、`【已试方向】`（编号列表，每条一句）、`【本轮要求】`（正常轮：修好它；降级轮：放弃当前实现，给一个结构上不同的写法）。
     2. 一次前后对照：同一个 `truncate` 案例，第 2 轮 hint 与第 4 轮 hint 并排，说明后者为什么要显式写「你已经卡了 2 次」。
     3. 一条可断言的判据：「提示里必须出现报错的最后一行原文」——写成 `assert err.strip().splitlines()[-1] in prompt`。
2. **第 2 节的四级搜索流程里，第二步与第三步的「读多少」永远停在形容词**
   - 原文片段：`按行号窗口读（比如命中行前后各 40 行）` / `只读窗口能省掉 90% 以上的上下文` / 而第三步又说 `「读窗口」够用来理解，但不够用来生成 old_string`。
   - 为什么读者在这里会卡住：读者要写的是一个搜索工具，需要一个能落地的策略切换 ——「什么时候从窗口读升级到全文件读？」原文给的是两句话和一个 90% 的估计，但没有：窗口读失败时的检测条件（比如 `old_string` 匹配数 != 1 就升级）、升级的代码位置、以及升级后上下文预算怎么变化。而且「省 90%」是估计，与本章第 3 节「匹配 1879 次」的真实失败模式接不上 —— 后者的根因恰恰是窗口读，读者需要一条把两者连起来的判据。
   - 建议补成什么样（骨架）：
     1. 一段状态机：`读窗口 → 生成 old_string → count != 1 → 升级为整文件读 → 重试（最多 1 次）→ 仍失败则降级为整文件重写`，并给出对应代码骨架。
     2. 把第 3 节的失败率指标接进来：「编辑失败率上升 = 窗口太小」的诊断规则，配一个阈值示例。
     3. 把「90%」换成一次可复现的测量（在 fixture 与一个真实仓库各量一次窗口读 vs 全文读的输入 token）。

### 本批次总结（Coding Agent）

- 最严重的 3 个「读到一半读不下去」的点：
  1. 第 4 节 `ask_model(code, err, hint, tried)`：全节主题是「喂什么」，却没有任何提示词产物（「加上一句『你已经试过 A、B 两种做法，都失败了』会让它更换方向」）。

- 做得最透的 2 节：
