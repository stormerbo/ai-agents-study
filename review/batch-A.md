### 章 2 Prompt 工程（prompt-engineering，5 节）

**一句话判词**：实验设计是全批次最务实的（每节一个可复现对照脚本），但"可运行的代码"和"结论一致性"这两条底线都有破口：一节代码缺 import 跑不起来，两处"常见坑"与正文结论直接相反，且 meta 有一条 outcome 无人兑现。

**定位与目标对齐**（meta.outcomes，prompt-engineering/meta.ts:11-15）
- "能写出让模型稳定按格式输出的 prompt" → 01/03/05 合力兑现（正面+否定+具体例子、边界示例、三层校验）。

## 批次总结

- **最严重的 3 个跨章问题**
  1. **章号引用体系整体失配。** ch0 的 04 节含 4 处错误章号 + 总章数写错（what-is-an-agent/04:11,41-43），ch0 其余节与 ch1/ch2 另有 8 处指向错误的"第 N 章"（循环→ch11、评估→ch15、适配层→ch8、缓存/成本→ch18）。根因是 verify-output/check-refs.mjs:16-19 只校验"章号是否存在"，指向错位测不出来，所以"悬空引用 0"这个结论不成立。
  2. **代码块可信度不齐。** prompt-engineering/05:170 自称"完整可运行"却缺 import os（P0）；ch1/03 的流式解析用了未定义的 json/handle_tool_call；ch0/02、03 的代码是无实跑标注的示意片段。全站"代码示例必须跑过或标注"的机制在批次 A 有至少 4 处漏标。
  3. **元数据与正文/产品状态脱节。** ch0/04:108 说进度功能未实现（实际已实现）；ch2 有一条 outcome（资料位置）无人兑现；ch1 有一条 outcome（超时/重试）无代码。三章都有 meta 承诺大于正文的情况。
- **本批次最有价值的 2 节**：llm-api-basics/01-tokens-and-context（把 token 这个计费/容量/延迟的共同单位讲到底，有数据、有脚本、有原始报错）；prompt-engineering/05-reliability（把"可靠性=可校验性"落成三层可执行校验，并用作者自己的两次错误证明"自查同源"的边界）。次选 what-is-an-agent/03-mindset-shift 的未复现诚实报告。
- **是否成体系的总体判断**：三章作为"阶段 0 → 阶段 1 地基"在依赖顺序上成立——章 0 给判断力、章 1 给 API 与成本机制、章 2 给 prompt 与可靠性，章内顺序也基本是依赖序而非难度序，且章 1 的 token/成本线索被章 2 的示例成本账接住。但"成体系"目前止于内容层面：**导航层的章号引用、元数据层的 outcomes、以及代码层的可运行标注这三层都没有跟内容一起更新**，导致读者按最短路径读会走错门、按 outcome 自检会发现承诺没兑现。修掉章号引用与三处代码/元数据破口后，这一批可以算扎实的教材；在这之前，它的"体系"只对通读全文的人成立，对按目录跳读的人不成立。
