# 深度审计：零基础可理解度（第二份评审标准，与 RUBRIC.md 不同）

## 读者设定（必须严格遵守）

读者画像：**做了 8 年后端（Java/Python/Go）、做过分布式与数据库、但从未做过任何 AI Agent 开发、没调过任何大模型 API**。
他能读懂 Python、Redis、Kafka、幂等、连接池、状态机 —— 读不懂任何未解释的 AI 概念。
判断标准只有一条：**这一节读完之后，他能不能自己动手做出来？还是只知道"有这么回事"？**

## 你要审计什么（只审内容深度，不审结构／不审引用／不审章节衔接）

对每一节回答四个问题，每个都要**引用原文片段**（≤60 字）作为证据：

1. **必须懂但没解释的名词**。列出这一节里出现、但读者若不知道就无法继续的概念名词（例：system prompt、token、embedding、tool schema、few-shot、prefill、ReAct、checkpoint、trace、harness、compaction、skill、MCP、handoff…）。对每个写：原文第一次出现的位置 + 它在正文里有没有被解释（引原文说明"解释了"或"没解释"）。
   ⚠️ 注意：**"换个说法"不算解释**。例如"把上下文压成摘要"没有解释什么是摘要、摘要为什么按重要性取舍。真正算解释的是：给机制（为什么会这样）、给可验证的判据、给一个具体的产物/例子。

2. **抽象但没有示例的产物**。这一节如果引入了某种"东西"（一段笔记、一份 schema、一条轨迹、一个计划、一个 skill、一份评测集、一个工具定义…），正文有没有给出**一份真实的、完整的示例**让人看到它到底长什么样？没有就点名，并写出"缺的到底是什么"（哪个字段、格式、长度、放在哪里）。

3. **被跳过的中间步骤**。从"我知道这个概念"到"我能写出来"之间，正文跳过了哪些步骤？（例：字段怎么设计？谁在什么时机写？写进去之后放在哪？下一轮怎么读回来？失败了怎么发现？）逐条列，不要合并且不要泛泛而谈。

4. **判定等级**（三选一，必须给）：
   - **A 能照着做**：有机制解释 + 有产物示例 + 步骤完整，读完可以动手。
   - **B 知道有这么回事**：讲了是什么、为什么，但缺少产物示例或关键步骤，读完只能"知道"。
   - **C 读不懂**：名词未解释、前提缺失、或推理跳跃到无法跟随。

## 额外要抓的两类问题

- **结论没有机制**：正文只给了结论（"X 更好/更可靠"），没给"为什么"或给了听起来对但无法验证的理由。
- **只讲"要注意"不讲"怎么注意"**：这类句子（"要小心 Y"、"Y 很危险"、"应该考虑 Z"）如果后面没有可执行动作，单独列出来。
- **同一件事被当成两件事**：读者容易混淆的相邻概念之间有没有交代边界（例：结构化笔记 vs 记忆 vs RAG；工具 vs skill vs MCP；轨迹 vs 审计日志；评测集 vs 测试用例）。

## 输出格式

**只输出下面这个结构，不要写客套话、不要复述我的要求。**

```
## 深度批次 <X>：<章名>

### 逐节（每节 2-4 行，务必精简）
- <节名> ｜等级 <A/B/C> ｜最缺的一样：<一句话>
  - 未解释名词：<名词>(<原文首现行>) ；…
  - 无示例的产物/跳过的步骤：<…>
  - 最该补的（具体到加什么）：<一句话，例：补一份真实笔记 JSON + 字段设计的三条判据>

### 章 <N>：<章名> 的两处最薄弱内容（要详细）
1. <小节/段落名>：<原文片段> → 为什么读者在这里会卡住 → 要补成什么样（写出你建议补的内容骨架）
2. …（同上）

### 本批次总结（≤300 字）
- 最严重的 3 个"读者读到一半读不下去"的点（含原文片段）
- 这批里**做得最透**的 2 节（说明它做对了什么，可复用）
```

## 纪律

- **不要评结构、不要评章号引用、不要评字数** —— 那些已经有人评过了。
- 每一条都要能指到原文；引不到原文的判断不要写。
- 宁可只写 3 条真正致命的，也不要列 20 条泛泛的"不够深入"。
- 判断"够不够深"时问自己：**我能不能用这一节的文字，教会一个后端同事做出这个功能？** 不能就说清差在哪。
