## 一、章 3 上下文工程（8 节）

### 3.1 上下文不是越多越好：两个实证 ｜ 等级 **B**

1. **未解释名词**
   - `Lost in the Middle`（首现 L9）：「模型对长上下文各位置的利用率是 U 形的，中间最容易被忽略」——**只给结论，没有机制**（为什么中间会被忽略、注意力是什么，全节未讲）。
   - `context rot`（首现 L10）：「塞进去的内容越多，模型对其中每一部分的关注度越低」——同义改写，未解释「关注度」是什么、怎么观测。
   - `语义 needle`（首现 L24）：全节没有定义 needle，读者无法知道「只在全文一段埋答案」与「机械标记」的区别。
   - `max_tokens` / `stop_reason`：**解释了**（L68「思考过程就把输出预算吃光了」、L81-82 给出两个对照输出），这是本节最好的一段。
   - `prompt caching`（首现 L109）：本体未解释，只给「能省一部分，但缓存有失效条件」。
2. **无示例的产物**：本节真正的产物是「一份能跑的位置效应测试」，脚本给了（L127-213），但表里 5 种设计的**输入文档长什么样**（400 段项目条目、两跳 lookup 的设备/规格表）没有任何一份片段，读者无法照着重造「句式不同、含 134/266 个干扰项」的语料。
3. **被跳过的中间步骤**：怎么判定一个问题「真的需要读懂文档」而不是照抄标记（只说了「不是照抄一个标记」）；怎么造干扰项；`DOCS`、`NEEDLE_INDEX`、`QUESTION`、`ANSWER` 四个变量全用 `...` 占位，读者得自己发明任务。
4. **结论没有机制**：L86「我的结论只能说这么远」态度诚实，但 L97「论文测的是『读完之后能不能**用**这些信息』…对注意力的要求不同」——「注意力」本身未定义，这条解释无法验证。
5. **最该补的**：补一段**真实的 400 段语料片段**（含正确条目 + 两类干扰项各一条）+ 一句判定「什么叫读懂」的判据（如答案必须由两个字段联合推出）。

### 3.2 system prompt 的高度 ｜ 等级 **B**

1. **未解释名词**
   - `system prompt`（首现 L7）：先修章已定义，本节不再赘述——可接受。
   - `原则式 / 逐条式`（L21-22）：逐条式给了两条规则原文（L33-34），原则式**只给了「4 条判断原则 + 2 个示例」这个数量描述**，从未给出那 4 条原则长什么样。
2. **无示例的产物（本节最致命）**：结论是「原则式最好」，但**表现最好的那份 prompt 全文从未出现**。读者拿到的是「3~6 条，覆盖主要判断维度」这条建议，以及一张「判断原则 vs 输出形态」的对照表，却看不到任何一份真的原则式客服 prompt。这等于告诉读者「答案是最好的，但答案不给你看」。
3. **被跳过的中间步骤**：怎么把业务需求拆成 3~6 条原则（分类维度是什么）；原则怎么排序/是否要写优先级；示例怎么选（选正例还是反例）；「输出形态约束尽量少」具体留哪几条。
4. **只讲「要注意」不讲「怎么注意」**：L200「把它做成一条 CI 检查（每次改 system prompt 就跑一遍）」——本节给了跑 12 次看方差的脚本，但**没有给 CI 里那句自检的提示词**，读者只能自己拼。
5. **最该补的**：补一份真实的「原则式」system prompt 全文（4 条原则 + 2 个示例），并与逐条式 18 条并列展示，标出哪几条是「判断原则」、哪几条是「输出形态」。

### 3.3 即时检索：不要预先塞入所有可能用到的资料 ｜ 等级 **B**

1. **未解释名词**
   - `预加载 / 按需取`：**解释了**（L9-10 各给一句话定义）。
   - `is_error`（首现 L226）：本节正文第一次出现，未解释是什么、为什么加它能改变行为（章 4 才讲），读者在此处只能照抄。
   - `checkpoint`（首现 L98「两个 checkpoint 里那个「文件路径模式」」）：站点内部概念，正文未解释。
   - `prompt caching`（首现 L83）：同上，只给一句「每轮重复的前缀是可以命中缓存的」。
2. **无示例的产物**：本节的落地建议是「中间形态：只给目录」，但**没有给出一份真实索引**。「索引（标题、路径、一句话摘要）」只是名词罗列，没有 20 行示例，也没说「一句话摘要」该由谁写、写多长。更严重的是代码与建议不一致：L102 说索引含「标题、路径、一句话摘要」，L169 的 `catalogue` 只拼了 `id + title`——**给出的代码没有实现正文推荐的那种索引**。
3. **被跳过的中间步骤**：目录怎么生成（离线还是让模型写）；摘要粒度；模型看到目录后「选择」的提示词长什么样；「取不到」时三种错误（不存在/暂不可用/无权限）**分别对应模型该做什么**（L234 只列了三种，没有给动作映射）。
4. **最该补的**：补一份真实的 20 条索引样例 + 三种「取不到」错误的回填 JSON 各一份 + 从目录到选中的那轮提示词。

### 3.4 压缩与结构化笔记 ｜ 等级 **B**

1. **未解释名词**
   - `压缩（compaction）`：以「把之前的对话总结一下」引入，读者能懂操作含义。
   - `结构化笔记`（首现 L22「让模型抽成结构化 JSON」）：**字段名给了**（L142-143 的 identifiers/amounts/dates/rejected_proposals/constraints/error_codes/contacts），但**产物形态从未展示**。
   - `checkpoint`（首现 L58「这正好印证了 checkpoint 里那条判断」）：未解释。
2. **无示例的产物（本节最致命）**：全节的核心处方是「把状态从历史里挪出来」，但**没有一份填好的结构化笔记**——只有 7 个字段名。读者看不到：字段是数组还是字符串？`constraints` 存原文还是改写？时间戳/来源轮次要不要？产物多大？摘要（138 字、812 token）与笔记（880 字、2776 token）也都没有原文。
3. **被跳过的中间步骤**（本节跳得最多）：
   - 笔记**放在哪里**：单独一条 message？塞进 system？还是外置存储？正文只说「挪出来」，没说挪到哪。
   - **下一轮怎么读回来**：谁来把笔记重新拼进请求、拼在第几个位置（这直接决定缓存，见 3.7）。
   - **怎么更新**：多轮之后是覆盖、追加还是去重？同一订单号再次出现怎么处理？
   - **运行期怎么发现丢了字段**：脚本（L155-163）是事后核对，没讲在线检测。
4. **结论没有机制**：L58「摘要天然按『重要性』排序，而『结论』和『主线』看起来总比『约束』重要」——只有一条实测支撑（丢 1 条），机制是断言；读者无法据此预测「哪类还会丢」。
5. **最该补的**：一份真实的笔记 JSON（8 条信息全填）+ 它在消息数组中的位置 + 读回与更新的三段伪码。

### 3.5 子智能体：它首先是个上下文技巧 ｜ 等级 **B**（偏 C 的边缘）

1. **未解释名词**
   - `子智能体（subagent）`（标题 / 首现 L7）：本节是全书第一次引入该词，却**没有定义**它是一次独立的模型调用、有独立上下文、有自己的 tool loop；读者只能从「只回传结论」反推。
   - `主 agent`（L26）：同上定义未给。
   - `prompt caching`（L80）：「命中成本远低于首次写入」——只说结论，未讲怎么触发。
   - `主上下文峰值`（表头）：正文未解释「峰值」如何测量。
2. **无示例的产物**：结尾要求子 agent 返回「**结构化**结果（至少含『做了什么 / 失败什么 / 哪些没查到』三项）」，但**没有任何一份这样的结果 schema**，也没有子 agent 的 system prompt。
3. **被跳过的中间步骤**：怎么**派出**一个子 agent（再起一个模型循环？给它哪些工具？它自己的 `max_rounds` 设多少）；它的最终答复怎么被主 agent 取用（只取 text 还是结构化）；「把共享背景收窄」具体怎么裁；子 agent 内部的失败怎么上报。
4. **产物与标题不符（最致命）**：`## 完整可运行代码` 里的 `with_subagents()`（L157-168）只是**对同一个 client 顺序发 N 次请求**，注释却写「每个子任务一个子 agent」——这不是子智能体，没有独立循环、没有结果回传协议。读者抄完会以为自己做成了子智能体。这一节可用来「判断该不该用」，但**不足以照着搭一个**。
5. **最该补的**：一段真正的最小 subagent 实现（子循环 + 只回传 JSON 的收尾）+ 一份返回 schema。

### 3.6 Chat Template：你写的消息，模型看到的 token ｜ 等级 **B**

1. **未解释名词**
   - `Chat Template`：**解释了**（L9「把『role + content』的结构渲染成模型能吃的标记序列」），本节名词处理最好的一处。
   - `前缀哈希`（L71）：**解释了**（对渲染后的 token 串做哈希）。
   - `适配层`（L68、L141）：前向引用第 8 章，本节未解释。
2. **无示例的产物**：本节推荐「实测两个版本对比」，但**没有给出任何一份真实的 messages 数组**——L158-167 的「写法一/写法二」是文字示意图，不是 JSON。读者无法知道 system 与 user 在数组里到底怎么写。
3. **被跳过的中间步骤（含自相矛盾）**：
   - `compare_structures(render_and_count, variants)` 的 `render_and_count` 是一个**从未实现的形参**，正文却说「这是唯一可靠的判断方法」——读者被要求测，却没有测量函数。
   - 更矛盾的是 L84 推论三「**不要手写 token 估算公式**」，而 L91-95 恰好给了一个含魔法数「每条消息约 3~5 token」的估算函数。读者会困惑该用还是不该用。
4. **最该补的**：一份真实 messages JSON（同一内容合并版 / 拆 10 轮版）+ 一段真正能跑的 `render_and_count`（直接发请求读 `usage.input_tokens`），并删掉或明确定位那个估算函数为「只做量级直觉」。

### 3.7 KV Cache：为什么前缀一改，成本就翻倍 ｜ 等级 **B**

1. **未解释名词**
   - `KV Cache`：**给了机制**（L42-43「每一层注意力都会为每个 token 算一对 Key/Value 向量并缓存起来」），但机制的**前提「注意力」与「Key/Value 向量」本身从未解释**——对零 AI 读者，这是用一个未解释的概念去解释另一个。
   - `自回归生成`（L54 表格）：未解释。
   - `effort`（首现 L94）：「同一会话里改变顶层的 effort，之前的缓存会失效」——`effort` 是什么、在哪一层，未解释。
   - `cache_control`（L19）：只说「带与不带标记没有区别」，没说它是干什么的。
   - 三层缓存表（L52-56 KV/Prompt/客户端缓存）：**这是本批概念边界做得最好的一处**，直接区分了三者。
2. **无示例的产物**：`diagnose_prefix` 的 `render_prefix`（L143-147）用 `json.dumps(tools) + system` 拼接来**冒充「渲染后的前缀」**——而本节自己的论点是「缓存哈希是对渲染后的 token 串做的」。这个工具会把「字面相同但渲染不同」与「字面不同但 token 相同」都判错，作为产物不可信。
3. **被跳过的中间步骤**：怎么从 API 侧**确认**缓存断在哪；怎么在开发期持续监控命中率；发现前缀不稳后怎么改（只说「先检查前缀结构」）。
4. **结论没有机制/无法验证**：L113「**缓存读取的单价通常只有基础输入价的一成左右**」——这是一个价格数字，既无来源也无核实日期，且与项目自身「不写价格、只教估算」的规范冲突。
5. **最该补的**：补一句「注意力是什么」的白话机制（或明确标注为可跳过的前置知识）+ 把「一成单价」改成教读者自己去账单里算占比。

### 3.8 Agent Skills：可组合的上下文单元 ｜ 等级 **B**

1. **未解释名词**
   - `skill`：**给了定义**（L14「一份自包含的指令包」，L16-17 元数据/正文）——但只到概念层，没有落地形态。
   - `工具（tool）`（L84 表）：本节用一整张表把它和 skill 区分开（**本批边界做得最好的一处之一**），但工具本身的定义要等章 4。
   - `两层索引`（L126）：只提名字，未给形态。
   - `key（amount-norm）`：**解释了**（L137 用真实报错讲清中英文不匹配）。
2. **无示例的产物（本节最致命）**：本节测了 6 个 skill（PDF 表格提取、日期归一化…），却**一个 skill 的正文都没有展示**——没有元数据那「一句话描述」的原文，没有 80~120 字的正文示例。「写一个 skill 的四个要点」全是判据，没有范例；真实世界 skill 的**存放形态**（文件？frontmatter？配置项？）也完全缺失。读者读完说不出 first skill 该长什么样。
3. **被跳过的中间步骤**：skill 物理上是什么、放哪；模型「选中」是走一次工具调用还是文本输出（4 步流程是叙述，没有请求/响应示例）；加载进来的正文拼在哪个位置（决定缓存）；`amount-norm` 这类 key 与描述如何一一对应；skill 多了之后冲突怎么发现。
4. **结论没有机制**：L118「100 个 skill 就是 2000 token」——每个描述约 20 token 是拍的，未给测量方式（对比 3.5 节测工具时是实测的）。
5. **最该补的**：补一个完整的真实 skill（元数据 + 全文正文）+ 两阶段选择那轮的提示词与返回示例。

### 4.3 poka-yoke：让错误在结构上不可能 ｜ 等级 **B**

1. **未解释名词**
   - `poka-yoke`：**解释了**（L11 USB 形状的类比）。
   - `轨迹`（首现 L26 表头「轨迹」）：**本节第一次出现且从未定义**（指模型这一轮的调用序列？完整对话？），读者要靠上下文猜。审计标准点名的一类词。
   - `干跑`（L80）、`联合类型`（L78）：后端读者熟。
2. **无示例的产物**：给了两种接口设计（A 按路径 / B 先列后删）、三种互斥参数修法、可跑脚本。产物不差。
3. **机制不成立（本节最致命）**：L37 断言「`file_id` 只能从 `list_files` 拿到：**你想删一个没看过的文件，连表达都表达不出来**」。但实现（L145-149）只做 `if file_id not in FILES`——**存在性校验，不是「必须调用过 list_files」的校验**。编号是 `f_001/f_002/f_003` 这样可枚举的，模型完全可以直接输出 `f_002` 而跳过 `list_files`（或沿用上一轮上下文里的编号）。「结构上不可能」并未成立，真正需要的是**会话绑定、不可猜的凭证**。对做过分布式的读者，这个问题恰恰是最想搞清楚的地方，而正文给了一个会让人误以为已经防住的实现。
4. **被跳过的中间步骤**：跨请求/跨服务时怎么让编号不可伪造；「先确认/干跑」的双阶段怎么写（只指向第 16 章）。
5. **最该补的**：把「结构上不可能」的条件说透——**编号必须不可枚举、且与本次会话绑定**，并给一段最小实现（`list_files` 写入 session cache，`delete_file` 校验编号属于本 session）。

### 4.4 并行调用、错误处理与幂等 ｜ 等级 **A**

1. **未解释名词**

### 1. 「那该怎么做：把状态从历史里挪出来」（3.4，L72-93）

## 四、章 4 的两处最薄弱内容（详细）

### 1. 「poka-yoke 的机制」段（4.3，L35-38）
- **原文**：「`delete_file(file_id)` 之所以安全，是因为 `file_id` 只能从 `list_files` 拿到：**你想删一个没看过的文件，连表达都表达不出来。**」（L37）／实现只有 `if file_id not in FILES`（L147）

## 五、本批次总结

### 最严重的 3 个「读到一半读不下去」的点
1. **3.4 结构化笔记：处方给了，产物和生命周期全缺。** 原文「结构化笔记：你定义有哪些字段 → 模型只负责填 → 缺字段是可检测的」，但全节没有一份填好的 JSON，也没说笔记放哪、下一轮谁读回来、怎么 merge。读者停在「知道该这么做」。
2. **3.5 子智能体：标题承诺的「完整可运行代码」不是子智能体。** 原文 `def with_subagents(): """每个子任务一个子 agent"""`，实现只是顺序直调 N 次；且「子智能体」本身未被定义。读者抄完会误以为搭成了。
3. **4.3 poka-yoke：「结构上不可能」在给出的实现里并不成立。** 原文「你想删一个没看过的文件，连表达都表达不出来」，而实现只做 `file_id not in FILES` 的存在性校验，可枚举编号可直接传。核心机制被夸大，照着做会得到一个假防护。

（紧随其后：3.8 从未展示任何一个 skill 的正文/元数据；4.5 的唯一处方「分组加载」零实现。）

### 这批里做得最透的 2 节（可复用）
1. **4.1 工具调用到底发生了什么**：真实 HTTP 报文 + 两个真实 400 错误 + 60 行最小循环，且每一步都标注了「哪一环必须由你的代码补上」。**可复用做法：先用原始报文展示机制，再给最小的、不含框架的完整实现，最后用真实报错证明协议会拦住你。**
2. **4.2 工具描述即 prompt**：把「模糊描述 vs 精确描述」两版**原文并列**，先用三个问题跑出行为差异，再落到 enum 与一张可逐条过的自检清单，还附了三类 schema 写法的真实结果（两个 400、一个静默 200）。**可复用做法：把「好/坏」两份产物原文端出来，让差异自己说话，而不是描述差异。**

> 两章的共同短板是一致的：**凡是真的要读者动手「造一个东西」的地方，产物就消失**（笔记、索引、skill、子智能体返回、分组加载、幂等注入）；凡是「展示一次调用/一次对照」的地方，都做得很好（工具往返、描述对照、错误回填）。建议按这条线补产物。
