### 章 11：两处最薄弱内容

1. **01 节：从假模型到真 API 的整段路被省略，循环只能"理解"不能"接上"。**
   原文：01:29 `resp = call_model(messages, tools=registry.specs())` ／ 01:85「这三样都是协议层的概念，与你的业务无关」。
   为什么卡住：读者画像里写死了"没调过任何大模型 API"。本节把 `call_model` 换成 `FakeModel`（01:149）后，所有协议细节（tools 参数怎么传、响应里 content 是块数组、`stop_reason` 取值、`tool_use` 块的 `id`/`name`/`input`、`tool_result` 必须回填且 id 对齐）都只以"函数名"或"自造字典"出现。读者读完能背出十七行骨架，但把 `call_model` 换成真的那一刻，四个字段全靠猜——而这一节恰好是"零基础动手"的入口。更糟的是"协议层的事实"（01:85）被当作判断依据反复引用，却没解释协议是什么。
   建议补成什么样：① 一段最小真实调用（只依赖标准库 `urllib`），打印出完整响应 JSON；② 把这段响应的三个块（text / tool_use / end_turn）逐字贴出，旁注字段含义；③ 一张"假模型字段 ↔ 真实字段"对照表；④ 明确一句话："`tool_result` 的 `tool_use_id` 必须等于请求里 `tool_use.id`，否则 API 报 400"，并给一次报错原文。

2. **03 节：token 预算这条闸门只有"要设"，没有"怎么设"，三个停止条件里最贵的一个无法落地。**
   原文：03:129-137 `def check_step(self, tokens_used): ... self.tokens += tokens_used`；03:156「`ok, why = g.check_step(500)`」。
   为什么卡住：后端读者对"限额+熔断"很熟，会自然地问"计量单位从哪来"。本节所有演示都把 token 当外部给定的常数（500、1000），而真实系统里这个数来自模型的 `usage`（还分 input / output / cache_read / cache_creation 四项）。不写这一层，读者写出的 `check_step` 永远拿不到实参；而 03:216 那条"正常路径用掉上限三分之一"的建议也就无从计算（分母是什么都不知道）。
   建议补成什么样：① 一段 10 行代码，从响应 `usage` 累加 `input_tokens + output_tokens`（并注明缓存字段是否计入）；② 给一个"8 步任务实际 token 曲线"的打印（配合第 1 节循环），让读者看到步数上限与 token 上限在什么时候分别先触发；③ 把 03:18 的"996 token"与"工具返回值可能上千"换算成同一个任务上的具体数字。

## 本批次（E）总结

最严重的三个"读到一半读不下去"的点：

1. **agent-loop/01:29 `resp = call_model(messages, tools=registry.specs())`**——全章入口把真 API 换成 `FakeModel`，而 `stop_reason`、`tool_use` 块、`tool_use_id`、`system 提示` 全部未解释，"零基础动手"在这一节断掉。

这批里做得最透的两节（可复用）：
