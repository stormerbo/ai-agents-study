### 章 what-is-an-agent：两处最薄弱内容
1. **01-why-now 的 token 未定义**：原文 L63「而同一模型处理一句纯文本请求（不带工具定义），输入只有 **33 token**」，紧接 L65「多出来的 270 多个 token，全是工具相关的开销」。这是本站第一节，读者在此之前没有任何 token 概念，却被要求接受「33 → 306」的成本论证，并记住 L122「『模型能调用工具了』这个能力是免费的，但你让它知道有哪些工具可用，是要花钱的」。**卡点**：token 同时是计费单位和长度单位（L66 才点明「既是计费单位，也是容量单位」），读者无法判断「300 token」是多是少、贵不贵，后面每一节的成本数字都会变成无意义的字符串。**补法骨架**：① 一句定义（「模型不能按字读写，先把文本切成词表里的片段，每个片段是一个 token」）；② 用本节数据做一次拆解（「什么是幂等性？」7 字 → 35 token = 内容约 5 + 请求结构约 30）；③ 一句量级锚（1 个 token 大约是什么、1000 token 大约多少字），再进入成本表。

  - 最该补的：给「加示例验证」的最小方法（固定测试集 + 只统计边界题的 N 次结果 + 一个可接受的提升阈值）。
- 思维链与 prefill（04-chain-of-thought） ｜等级 **B** ｜最缺的一样：**prefill 只有伪代码，且已发现「拼起来会得到两个对象」却没给修复动作**。

### 章 prompt-engineering：两处最薄弱内容
1. **02-structure-and-separation 的 `is_supported_by` 黑盒**：原文 L134-136 `for claim in extract_claims(text): if not is_supported_by(claim, doc): raise SuspiciousOutput(...)`，紧接 L140「第 3 条是关键 —— 它直接对应第 ⑤ 行那个实验」。实测 L26 显示内容操纵「有 XML 标签边界」时仍然 **6/6 得逞**，也就是说第 1 层完全挡不住它，第 3 条校验是唯一防线 —— 但正文把它写成一行未定义函数。**卡点**：读者读完能复述「不要相信模型输出，要用代码检查」，却写不出「检查结论是否由文档支持」这件事，而这恰恰是提示注入防御里最难、最值钱的一步；读者很可能以为「等第 4 章工具调用就好了」，但工具层并不会替他做事实核对。**补法骨架**：给出 2-3 种可实现的方案并对比漏报/误杀：① 抽取 claim 里的数字、专名、日期，逐一检查是否出现在 `doc`（精确 + 模糊匹配）；② 句级相似度阈值（claim 与 doc 句子的最长公共子串/向量余弦），并给阈值与实测命中；③ 反向提问（「doc 里有没有支持这句话的原文？」）再做一致性比对；附一段能跑在 L179-191 那份伪造报告上的最小实现与结果。
2. **04-chain-of-thought 的 prefill 不闭环**：原文 L90「# 伪代码示意（不同厂商的 prefill 支持方式不同）」给出的只有 messages 数组，没有 SDK 调用；L187「HTTP 200，预填被接受了」，紧接着 L189「模型**重新输出了一整个对象**，而不是只续写缺的那半截……如果你把预填和续写直接拼起来，会得到两个对象糊在一起的字符串」，而解决办法只有 L191「用之前先确认它的实际边界」。**卡点**：prefill 是标题级技能，读者按正文抄会得到一个必然 JSON 解析失败的字符串；既然作者已经实测到这一点，却没沉淀成一条规则 —— 读者只能自己踩坑。**补法骨架**：① 完整可运行调用（含某家 SDK 的 prefill 写法）；② 处理续写的三种策略与推荐（a. 解析时丢弃重复的开头；b. 用响应里模型自带的完整对象、忽略预填；c. 用 stop 序列限制），并说明哪种在实测里可靠；③ 一张厂商支持差异表（Anthropic 支持 messages 末尾 assistant；OpenAI 无等价机制 → 用格式示例近似）；④ 一个断言「拼接后仍是合法 JSON」的测试。
