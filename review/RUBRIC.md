# 逐章深度评审 · 评分标准与输出格式（RUBRIC）

你在评审一个中文 AI Agent 学习站的内容质量。目标读者：有 Java/Python/Go 背景、正在转 AI Agent 开发的后端工程师。

## 项目方自定的验收标准（用来对照，不是用来复述）

每节必须四块齐全：**实测数据（有反直觉点）+ Mermaid 图 + 完整可运行代码 + 真实错误案例**；
且中文 ≥1500 字、说明文字 ≥3000 字（`node scripts/content-stats.mjs` 已算出 134/134 达标 —— 你不必复核字数，**要复核的是「数字达标是否等于内容真的讲透了」**）。

章的元数据在 `src/content/chapters/<章>/meta.ts`：`outcomes`（学完能做到什么）、每个 lesson 的 `checkpoints`（带 `basis` = documented/inferred/unverified 和 `answer`）。正文在 `<章>/<节>.mdx`。

## 你要回答的核心问题

1. **这一章是否把该讲的东西讲清了？** 以你自己的领域知识列出「这个主题下工程师必须知道的子主题」，逐条对照正文，明确指出**缺失或只提了一句就没展开**的。
2. **四块内容是否真的成立，还是形式上有、实质上空？**
   - 「实测数据」：数字是否有来源、日期、可复现的脚本痕迹？还是编造/含糊（"据测试大约..."）？
   - 「代码」：是否真的可运行？导入、API 调用、参数是否自相一致、是否与正文其他部分矛盾？是否有明显 bug（变量未定义、缩进错、API 名写错、异步没 await、文件路径不存在）？是否标注了实跑状态？
   - 「错误案例」：是真实报错的形态（有原始报错文本、有排查过程），还是编的「某天我遇到一个错误」？
   - 「Mermaid 图」：图是否在讲机制（有信息量），还是把正文标题重排一遍？
3. **章内体系**：节的顺序是否是依赖顺序？有无重复、跳跃、前后矛盾（同一概念两节说法不一致）？
4. **章间体系**：本章的定位是否清楚？与相邻章的衔接（前后引用）是否成立？是否和别的章内容大量重复？
5. **准确性风险**：逐条列出你**有理由怀疑**的事实性错误或不严谨表述（含 API 名、协议名、日期、参数默认值、论文结论、安全建议）。标出你的确信度（高/中/低），不要编造你没把握的「错误」。
6. **对目标读者的适配**：是否真的照顾了「有后端经验、非 AI 新手」？还是把后端工程师当小白教？或者反过来默认了太多 ML 知识？

## 纪律

- **必须给证据**：每条结论后面跟 `文件路径:行号`，并引用最多 1 行原文（≤80 字）。
- **禁止客套**。不要写「整体质量很高」「内容详实」这类没有信息量的话。如果某节确实做得好，用一句话说清好在哪（例如「把 X 与 Y 的对照做成了可复现脚本」）。
- 不要把「字数达标」当成「讲透了」。反过来，也不要因为字数少就判差 —— 判据是覆盖与深度。
- 不确定就写「不确定」，不要为了凑数编问题。宁少而准。
- 不要修改任何 `src/` 下的文件。你只读。

## 输出格式（严格照抄结构，写进 `review/batch-<字母>.md`，并把同样的内容作为最终答复返回）

```
## 批次 <字母>：<章名列表>
（元信息：节数、读完的文件数、用时感受）

### 章 <章号> <章名>（<id>，N 节）
**一句话判词**：<这一章到底成不成立>

**定位与目标对齐**：meta.outcomes 承诺了什么 → 正文是否兑现（逐条）

**逐节评估**（每节 3-6 行）
- <节文件名>：<讲了什么>；覆盖：<强/中/弱>；缺失子主题：<...>；问题：<... 证据 file:line>

**四块核验**（表格：节 × 实测/图/代码/错误案例，写「实/空/无」+ 一句依据）

**体系性**：<章内顺序、章间衔接、重复、矛盾，附证据>

**问题清单**（严重度 P0/P1/P2 × 证据 × 一句话修法）

**亮点**（最多 3 条，各一句）

### 章 <下一章> ...
（同上）

## 批次总结
- 最严重的 3 个问题（跨章）
- 本批次最有价值的 2 节
- 对「是否成体系」的总体判断（3-5 句）
```

严重度定义：**P0** = 事实错误或会误导读者做错工程决策；**P1** = 关键子主题缺失/深度不足，读者学完仍有盲区；**P2** = 表达、结构、打磨问题。
