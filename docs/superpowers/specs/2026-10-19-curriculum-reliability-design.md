## 1 设计决策与边界

### 1.1 三种方案比较

| 方案                                 | 收益                                   | 代价和局限                                                      | 结论                           |
| ------------------------------------ | -------------------------------------- | --------------------------------------------------------------- | ------------------------------ |
| 只修已发现错误                       | 快速降低当前误导风险                   | 缺少完整项目，后续仍容易出现正文与实验脱节                      | 作为第一批工作，不作为最终方案 |
| 保留章节，补证据、纵向项目和能力验收 | 复用现有内容，同时解决准确性与教学闭环 | 需要维护 Python 示例、实验资料与内容之间的关联                  | 采用                           |
| 全书重排重写，统一为框架教程         | 叙事容易统一                           | URL、学习进度、交叉引用和已有实测大面积受影响，削弱框架无关能力 | 不采用                         |

### 1.2 保留的约束

- 读者有 Java、Python 或 Go 后端经验，不重复讲 HTTP、数据库和基础语法。
- Next.js 内容站的定位、六阶段、26 个现有 chapter id 与全部既有 lesson id、slug 保持稳定。
- 正文继续使用 `meta.ts + body.ts + MDX`；不引入新的 MDX 组件或 frontmatter 字段。
- 保留四块内容、五要素深度和中文 1500／说明文字 3000 的门槛，不以扩充字数作为完成标准。
- Python 是教学项目主实现；TypeScript 只承担已有站点和必要的 MCP 互操作示例，不同时维护四种语言的完整运行时。
- 不给学习站增加账号、数据库或后台任务。教学服务独立放在 `examples/`，其数据库不属于站点架构。
- 现有未复现实验继续保留；历史数据不被新数据覆盖。

### 1.3 本轮不做的内容

不建设新课程平台，不重做 UI，不引入 Kubernetes、消息中间件集群或复杂多 Agent 调度作为必修基础设施。不补齐模型训练、机器人和语音实时系统的完整开发课程；在总览中交代适用范围与后续路线即可。已有持续进化章聚焦可回归验证的规则、Prompt 与工具改进。

### 1.4 完成的定义

本轮完成必须同时满足：已确认的高优先级问题有回归验证；全部 144 节完成内容准确性复审并有逐节可核验记录；五个阶段都有明确交付物；最终项目真实调用模型并完成跨进程审批恢复；关键实验具有可追溯证据；未验证项继续可见，不能用离线 fixture 的通过率代替在线能力结论。截至 2026-10-22，W6 全节复核为 144/144（100%）；逐节具体审计依据另覆盖 144/144。两种覆盖数字衡量范围不同，W6 范围已完成，但历史付费实验、生产行为和外部副作用未因此全部验证。W6 覆盖不代表历史付费实验已复跑，也不替代 Stage 4 人工审阅或 Stage 5 live/holdout/独立交接与发布回滚门禁。历史付费实验未全量复跑。Stage 4 首次人工审阅、Stage 5 live/holdout/独立交接和发布/回滚仍按独立条件跟踪。

### 2.1 历史证据的处理

将“原始观测”“评分结果”“解释”“教学建议”分别处理。原始观测不变不代表解释不能纠正。旧代码、旧结果与旧解释如有冲突，以勘误记录保存其关系，在正文主路径给出修正后的可执行版本，旧数字不能继续被标作当前代码输出。

实施前在 `CONTENT_GUIDE.md` 与 `docs/CONTENT-DEPTH.md` 明确纠错规则：允许有依据地修正错误代码、评分与解释；不得静默替换历史实测；每次纠错要有编号、旧结论、原因、新证据与影响小节。该规则用于解决现有“不得删改实测”与准确性修复之间的冲突，不意味着放弃内容保护。

`pnpm verify:depth` 继续运行，但当前实现依赖本地 `verify-output/baseline/`，不能当作可复现的 Git HEAD 比较。后续改为显式 Git base ref；比较时基线缺失直接失败。对纠错的字数下降只能用逐条文件、基线内容 hash、原因与补充教学内容清单审核，不以全局关闭门禁或增加无关文字通过。

## 3 学习路径与阶段作品

### 3.1 目录稳定，增加两条阅读路径

完整路径继续按现有六阶段学习。另在第 0 章提供第一轮动手路径：第 1 章 API 关键节 → 第 2 章指令与数据边界 → 第 4 章工具调用 → 第 11 章第 1 节最小循环。

## 5 最终项目架构

### 5.1 业务范围与运行模式

售后订单助手完成：识别诉求、读取有权限的订单、检索当前政策、生成带来源的答复草稿、请求审批，以及在批准后投递到本地消息接收服务。

必修项目不退款、不改真实订单、不向真实客户发邮件。消息接收服务是真 HTTP 边界、可持久化并支持故障注入，用于观察外部副作用；不能用函数返回 `sent=True` 冒充投递。真模型模式必须实际调用一个已验证的模型端点。离线模式使用固定响应序列，测试控制流与故障恢复，两种结果分开报告。

实现使用 Python 服务、PostgreSQL、官方模型 SDK 和官方 MCP SDK；FastAPI 作为 HTTP 层，`httpx` 作为项目业务 HTTP 客户端。正式实现时核对当时官方文档并锁定具体版本。任务表也承担小规模队列，初版不引入 Redis。浏览器或 CLI 访问服务，不改学习站运行模式。

### 5.2 模块与边界

```text
CLI / API client
    │ authenticated principal + request id
    ▼
HTTP API ── task / approval / event queries ── PostgreSQL
    │                                              ▲
    └── create durable task ──► worker claims task ─┘
                                  │
                              Agent runtime
                       ┌──────────┼──────────┐
                    LLM adapter  retrieval  tool gateway
                                            │ policy + argument validation
                                            │ approval + action ledger
                                            ▼
                                  read-only MCP / outbox
                                                     │
                                                dispatcher
                                                     ▼
                                          local delivery sink
```

| 单元         | 输入与输出                                  | 责任                                                         |
| ------------ | ------------------------------------------- | ------------------------------------------------------------ |
| `domain`     | 任务、动作、审批和身份的类型与状态转换      | 不依赖 SDK、Web 框架或模型输出文本                           |
| `runtime`    | 规范化模型响应 → 下一条状态转换和持久化事件 | 决定继续、等待、终止、重试；不直接调用外部动作               |
| `providers`  | 模型请求、完整响应、usage 与错误            | 保留厂商原始结束原因并提供适配后的结果，禁止编造不支持的能力 |
| `tools`      | principal、工具名、参数、业务操作 id → 结果 | 工具 schema 校验、资源授权、策略判断与动作记录的唯一入口     |
| `retrieval`  | principal、查询、索引版本 → 可访问证据      | 过滤、融合、重排、出处与版本；不让模型提供可信身份           |
| `storage`    | 状态转换、事件、租约与幂等写入              | 事务、唯一约束、乐观版本与迁移                               |

| `delivery`   | 已授权 outbox 操作 → 投递回执或未知状态     | 使用稳定外部幂等键；失败对账；不调用模型作最终授权           |
| `evaluation` | 数据集、发布单与轨迹 → 分层指标和失败案例   | 评分独立于执行，不把模型自评直接当成功标签                   |

### 5.4 模型适配契约

每个端点声明协议、模型标识、已验证能力、SDK 版本、验证时间与证据 id。能力至少覆盖 streaming、tools、parallel tools、strict schema、thinking、vision、usage 与 cache 字段语义。

规范化响应区分 final、tool_calls、refusal、truncated 与 transport_error，并保留原始 stop_reason。`end_turn` 只是模型回合完成，业务任务还需通过输出、证据和未完成动作检查。未知响应类型明确报错，不静默降级成 final。

至少一个端点完成完整真模型验收；第二端点用于能力契约与迁移对照。没有访问权限的能力标记 unavailable 或 unverified，不声称已验证，也不要求读者同时购买所有厂商服务。

### 5.5 任务状态与恢复

任务状态：`queued / running / waiting_approval / reconciling / completed / failed / cancelled`。

- 提交请求在一个事务里建立 queued 任务与首条事件，随后由 worker 领取。短请求可以等待该任务完成，等待超时只返回任务 id，不重新入队。
- worker 领取时获得 execution_epoch 与有限租约；续约、检查点、审批记录和 outbox 写入都带 epoch 条件。旧 worker 失去租约后不能继续提交状态或调度副作用。
- 模型可以一次提出多个工具调用，但 runtime 保持独立的 pending action 清单。一旦有待审批动作，暂停后续执行；其他待处理工具调用不被丢弃，也不凭空写入成功 tool_result。
- 审批恢复时从冻结动作与检查点继续，执行并补齐全部对应结果后，才再次请求模型。不能重放整段历史作为恢复策略。
- 只读工具调用在结果持久化前按 at-least-once 处理：若远端读取已返回但 worker 失去租约、尚未能把结果写入检查点，后继 worker 可以重试该只读调用；已持久化的结果必须复用。不得把“读取操作完成”与“结果已可靠保存”混为一谈，也不得对只读 MCP 调用宣称 exactly-once。
- 授权通过的动作在执行前仍重新检查资源权限、policy_version 和资源版本。资源条件变化则原审批失效，不自动把旧批准移用到新参数。
- 外部请求超时不等于失败；动作进入 unknown，任务进入 reconciling。支持按幂等键查询或安全重试时由代码处理；否则要求人工核实。
- completed 必须没有 pending、unknown、denied 等未解决动作，并通过任务输出校验。拒绝动作若允许替代方案继续，轨迹必须记录策略分支；不能吞掉错误后无条件成功。

租约保证数据库内状态与动作调度的所有权，不保证已发出的远程请求能撤回。外部恰好一次效果只在接收方具有对应幂等保证时成立，不能由本地 fencing token 单独推出。

### 5.6 审批与授权

权限判定以 `(principal, action, resource, context)` 为输入；用户传来的 tenant_id、模型工具参数和第三方工具描述都不是可信身份。

审批绑定：租户、审批者资格、动作 id、规范化参数 hash、资源版本、策略版本和有效期。可信工具注册表定义风险信息；参数规模和资源敏感度参与判定。模型不能通过自己填写 `approved=true`、`reversible=true` 或权限字段提升能力。

审批不是只向人展示一个 approval id 和“批准”按钮。指定审批者的详情查询必须展示由可信工具登记表生成的动作摘要、明确允许展示的规范化参数、资源/ACL/策略版本、请求者、审批者与失效时间，并核对摘要参数 hash 与冻结动作一致；陌生身份、跨租户身份或快照不一致时 fail closed。拒绝、过期、撤权或参数/资源策略变化后，审批不能触发副作用。当前 P4 教学 API 已提供只面向指定审批者的详情查询，但展示投影只覆盖合成 `send_notice`；没有生产 UI、PII 脱敏规则或责任流程，部署时必须针对实际工具重新定义和审查可见字段。

跨租户读取、过期审批、重复审批、参数替换、批准后权限撤回、并发点击均有负向测试。额度许可有授权主体和期限，不能把“小金额”写成天然无需授权。

### 5.7 外部动作与取消

审批通过后，在同一数据库事务更新动作为 authorized 并写 outbox。dispatcher 使用 action_id 派生的稳定 external_key 发送；接收方持久化去重与回执。失败恢复先查询回执，再按端点契约决定是否重试。

取消停止新的模型调用和尚未被投递器领取的动作，排队 outbox 标记 cancelled。已经被领取或已发出的动作等待回执或对账，不向用户承诺已撤回。任务有正在处理的副作用时先进入 reconciling，确认结果后记录取消的实际边界。

投递与撤权、取消的竞争以数据库内从 queued 到 dispatching 的原子转换为界：dispatcher 在该事务中重查任务取消状态、审批、权限与参数版本。撤权或取消先提交则不能领取投递；dispatching 先提交后，对外只承诺“已交给投递器，结果需确认”，不能承诺撤回。数据库提交与网络发送之间仍可能崩溃，该状态按未知动作对账；测试覆盖领取前、领取后但网络发送前、发送后三个时点。这里定义的是授权判定时点，不声称数据库与远程发送具备原子性。

### 5.8 检索数据生命周期

摄取流程固定为：可信资源归属 → 文档版本与 hash → 切块 → embedding → 带 ACL 的候选查询 → 重排 → 带出处的上下文。过滤条件由服务端 principal 构造。

正文解释三种变化：文档内容更新、权限变化、embedding/切分版本变化。新索引完成验证后通过 index_version 切换；删除和权限撤回首先在查询层立即拒绝旧记录，再清理索引、结果缓存与相关记忆。仅清理向量库而继续返回缓存也算失败。

最终答案中引用可定位到 resource_id、doc_version 和片段；引用存在不等于结论被证据支持，评分仍要检查蕴含关系。不得先把无权限候选交给模型，再只过滤最终答案。

### 5.9 并发与成本

队列有长度上限，任务和供应商各有并发限制。429 按可验证的端点信号退避并带抖动；deadline 内无法继续则明确失败或保留可查询状态。模型 token 预算在发送前预留输出上限和已知输入估计，收到 usage 后核销；预估与实计分开记录。

工具本身的外部费用单独纳入动作预算。并发调用、重试和多 Agent 子任务不能各自看到一份未扣减的共享余额。接收方拒绝重复动作不等于上游模型调用免费。

模型请求发出后若连接中断且没有 usage，该次预留保留为 unknown，不能因本地报错立刻退还。新重试占用另一笔预留；只有可靠用量记录或对账结果才能核销，无法核实则保守保留并停止超预算调度。未发出的请求可以释放预留。预算报告分别展示已核实消耗、未知预留与可用余额，不把客户端估算上限宣称为厂商最终账单的绝对上限。

### 6.2 实验登记契约

每条登记至少包含：id、受影响 lesson id、验证问题、类型、代码入口及 hash、依赖锁文件 hash、数据集版本、评分器版本、运行方式、预期不变量、结果位置、最后状态。

在线结果额外记录 provider、协议、去除凭据与敏感参数后的 endpoint、请求与响应模型标识、采样/思考/截断参数、usage 分项、结束原因、运行时间和重复次数。若返回的只是滚动模型别名，明确不能追溯到权重快照。

结果类型使用五类：本地确定性执行、真实在线实验、原始数据回放、合成 fixture、官方资料核对。回放或合成数据不计入真实模型能力验证。官方支持与本环境实测分两列，不用单一“已验证”覆盖两者。

密钥通过环境或安全存储读取，不进入命令参数、URL、stdout 或持久化结果。结果入库前执行字段白名单与敏感值扫描；扫描通过不代替首次人工检查。

`kind/status/locator` 的自我声明不是 evidence。acceptance gate 必须在受控 evidence root 下解析实际 artifact，校验其 schema、hash、run id、release/commit、依赖、prompt、工具 schema、数据集和评分器版本，并根据 gate 限定的来源类型拒绝 fixture 冒充 live、离线测试冒充 integration、作者自填字段冒充 manual review。证据齐全只能得到 `ready-for-human-acceptance`，不能由脚本自动变为发布批准。当前 `examples/capstone-acceptance/acceptance.py` 已做 root/hash/provenance 与类型门禁；v2 将 `official_blind_holdout` 设为必需 gate，并检查候选/image/holdout/scorer 身份、费用/sample-size 字段以及授权、reservation、consumption 事件结构和非递减时间顺序。它仍是本地结构校验，不能验证外部 registry 签名或真实性；没有实际 holdout artifact 时应保持 `incomplete`。`build_acceptance_matrix()` 将 19 个 gate 的结构状态逐项输出，并保留 `authenticated: false`；缺失项不会被其他 gate 的失败遮蔽。其合成 contract tests 构造的 holdout payload 仅证明输入形状能被接受，不能充当真实证据。

证据源码绑定要区分“当前文件没漂移”和“当时执行了什么”。registry 中的 `scriptSha256` 会与当前 checkout 比较，只能完成前者；结果文件新加 `sourceBindings`，把运行入口、被测实现、相关依赖和测试逐项绑定到运行前采集的 SHA-256。结果测试要验证这些源码仍可取回且 hash 一致。旧结果没有该字段时保留原观测，但不得把后补的当前 hash 当作历史执行证明；需要重建可复现结论时新增一次带源码绑定的运行，不覆盖历史结果。

### 6.3 正文代码与输出同步

全量 MDX 只做静态登记与格式检查，绝不自动执行任意围栏。显式登记的可执行示例才进入执行清单，并在临时目录、超时和受限环境中运行。

每个登记片段用文件路径、围栏序号、内容 hash 和片段角色定位，不新增 frontmatter。片段角色区分完整脚本、代码片段、伪代码、故意错误示例和协议报文；故意错误代码不能被“修复到全部可运行”。

教学短例在正文保留完整可复制代码；测试对正文片段本身执行或核对其与规范示例的 hash。综合项目按章节完整展示当节单元，并明确来自哪个阶段目录；整仓运行步骤在项目入口交代，不能要求 import 作者本地文件。

确定性结果自动生成并与登记的输出围栏核对。动态时间、UUID 等只允许在登记的字段上规范化，不得抹掉统计值、动作次序、状态和错误信息。随机示例固定算法、种子、Python 版本与输入；模型结果不做固定文本快照，而校验结构、评分规则与结果证据是否对应。

### 6.4 论断与勘误

现有 Checkpoint.basis 三种值保持不变。新增 `experiments/claims.json` 只关联正文中高风险论断，先覆盖协议字段、厂商能力、统计公式、安全保证、成本倍数和跨模型泛化，不要求每句话都登记。

每条论断记录 lesson id、文本 hash、适用条件、既有资源 sourceIds、实验 id、依据类型和复核状态。sourceIds 仍只能引用 `resources.ts`。外部资料的核对版本与内容 hash 独立保存；链接可用不等于内容仍支持该论断。

勘误与历史结果关联，保留原结果、失效原因和新证据。正文代码或结论变化后，相关记录先转为需复核，不能只更新 verifiedAt 维持“已验证”。全章 verifiedAt 仅在该章复核范围满足后更新，部分复核记录在 tracker。

### 6.5 统计与在线评测规范

- 按问题先定义估计对象：单次成功、Pass@k、Pass^k、任务成本或延迟；声明其分母与独立单位。
- Pass@k 组合估计校验 k 与 n；同一任务多次运行作为任务内重复，不把相关样本展开后当独立任务。
- 区间估计与比较实验分开；比较实验声明基线、目标差、显著性、power、配对方式。用固定输入和独立实现交叉核对统计函数，包含全对、全错和边界样本。
- task 层重采样与任务内随机性分开解释；饱和回归用例用于防回归，另加挑战集测改进，不因全绿就删除旧测试。
- 训练/规则提炼集、开发集和 holdout 分离；公开 toy 数据只用于教学，正式结论报告是否存在污染风险。
- 在线评测先跑可行性试验，按预算执行预先确定的设计。样本不足就报告区间与限制，不写预设准确率或“必然提高”。
- 质量、成本、延迟分别报告；缓存命中输入量乘相应价格才可比较费用。没有固定计价来源时只报 token 分项与计费方法。

## 7 验证与毕业验收

### 7.1 三条验证通道

| 通道         | 何时运行                        | 能证明什么                                            | 不能证明什么                     |
| ------------ | ------------------------------- | ----------------------------------------------------- | -------------------------------- |
| 离线必跑     | 每次相关变更                    | 代码行为、状态转换、统计计算、登记和输出一致          | 真模型工具选择质量、真实厂商特性 |
| 本地集成必跑 | 项目服务或协议变化              | PostgreSQL、MCP peer、worker 与投递服务的真实进程边界 | 公网模型可用性与客户环境性能     |
| 在线显式运行 | 模型/端点迁移，或需要新实测结论 | 实际请求、能力支持、质量与 usage                      | 未来模型别名的行为不变           |

离线或构建任务没有 Key 也应执行。显式要求在线验证却缺凭据时，该项为 blocked/unverified 并返回非成功状态；不能把 skip 写成 pass。普通站点构建不暗中发 API 请求。

仓库现已提供 `pnpm verify:examples` 与 `pnpm verify:evidence`，用于执行显式登记的离线合同测试及 evidence registry/schema 检查；它们不会运行 Docker/PostgreSQL integration，也不会调用在线模型。Python 项目使用各自锁文件执行 `uv run pytest`。阶段 4 集成需在 `examples/p4-durable-support/` 执行 `uv run pytest -m integration -q`，缺 Docker 或 PostgreSQL 时失败而不 skip。阶段 5 的本地 evidence artifact/hash/provenance classifier、仓库内可见的 synthetic dev/holdout fixture scorer、provider 驱动与 v2 live 报告生成已实现并登记在 `examples/manifest.json`；`holdout-results.json` 与输入一起入库，不是盲测，也不运行候选 Agent。live gate 只在持久终态、有效输出 hash 与逐轮完整 usage 齐备时通过。`pnpm verify:examples` 覆盖离线 evidence gate、evaluator、P5 host、runner 与 drill contracts；这些检查不运行真实模型，也不证明线上质量。真实隐藏集执行、独立评分和外部消费 registry 尚未实现；首次 live smoke、人工 review 与独立 handoff gate 也未完成，见专项计划。**术语边界：**普通学习和开发迭代只需本地 CSV/JSON 或笔记，不需要盲测后台；“正式 blind holdout”专指最终候选发布验收时由独立角色执行的一次隐藏题集测试，需外部服务记录一次性授权、预约和终态。模板[正式盲测运行登记表](../templates/official-holdout-run-record.md)只供该发布验收流程使用，不是读者需要实现的课程功能；当前外部服务未接通，不能按模板直接运行。面向读者的白话定义与角色时序图见 [Stage 5 正式盲测说明](../plans/2026-10-20-stage5-capstone.md#用白话看正式盲测)。Stage 5 还需单独验收 executor 进程崩溃恢复：provider send intent、封存、评分持久化和终态提交各边界崩溃时，不得重跑候选；runtime usage ledger 只接受 workload identity 认证的可信 supervisor 写入。任何 `aborted` 终态都必须绑定可信 runtime stop 与 capability-revocation 证据；registry 必须从可信 runtime audit/ledger 源端核验引用，不能只信 URI/hash 外形。candidate 未启动时使用 `recover_abort`；candidate 已启动但执行已确认停止时由独立 recovery operator 使用 `recover_finalize`，恢复的完整结果还须绑定 usage-ledger；缺失 usage/cost 以 `unknown` 记入 `aborted`；执行状态未知时保留 `reserved`，不能伪造为零或通过.

### 7.2 项目验收矩阵

| 场景                     | 可观察到的通过条件                                                         |
| ------------------------ | -------------------------------------------------------------------------- |
| 真模型正常任务           | 至少一次真实模型工具往返，有完整事件、usage、出处和最终结果                |
| 工具参数不合法           | 执行前拒绝，错误可追踪，不产生动作记录中的成功副作用                       |
| 审批在流程中途           | task=waiting_approval，后续动作未执行，待执行列表可恢复                    |
| 审批后服务重启           | 从数据库读回同一动作和参数，继续而非重新规划整个任务                       |
| 重复或并发批准           | 同一业务动作仅有一个 outbox 操作和一个接收方副作用                         |
| 权限撤回或参数变化       | 已有审批失效，无越权读取或发送                                             |
| 投递与撤权、取消竞争     | 领取前提交撤权或取消则不投递；领取后状态准确反映待确认结果，无虚假撤回保证 |
| 跨租户读取与检索         | 无权资料不进入模型上下文，事件与结果查询也被拒绝                           |
| HTTP 等待超时            | 返回原任务 id，后台只有同一任务的有效执行者                                |
| worker 租约过期          | 新 worker 接管，旧 epoch 无法写检查点、审批或 outbox                       |
| 外部调用完成后丢失响应   | 进入 unknown/reconciling，经回执查询恢复，不直接重复动作                   |
| Stage 5 executor 进程崩溃 | 由无候选执行权限的恢复身份查回原 seal、评分与 runtime usage ledger；状态未知时不重跑并保持 reserved；已停止但 usage/cost 缺失时记 aborted/unknown |
| 外部端点无幂等也无查询   | 明确暂停并需人工核实，不宣称能够保证不重复                                 |
| 取消发生在投递领取前后   | 领取前取消无副作用；领取后明确展示已发生或待核实的状态                     |
| 429 与预算不足           | 退避受 deadline 和预算限制；不无限重试或超额并发                           |
| 模型请求断流且缺 usage   | unknown 预留不被提前释放，重试另行预留，报告区分已核实用量与未知消耗       |
| 文档删除和 ACL 撤回      | 旧索引与缓存不会继续向无权用户提供资料                                     |
| 拒绝、截断与部分工具失败 | 不被合并成 completed；失败分类与策略分支明确                               |
| 升级模型或端点           | 完成能力契约与质量回归，差异和不支持项形成迁移记录                         |

以上测试中的“无副作用”依据数据库和独立接收服务状态，不只看 Agent 自己的日志。幂等保证注明作用域：该业务操作、该接收方契约以及该幂等保留期限。

### 7.3 内容与视觉验收

每章先修正文、示例、Checkpoint 参考答案和资源依据，再更新完成状态。术语首次出现、五要素与后端失效直觉由人工逐节检查，机器门禁只作辅助。

每批修改执行现有 test、depth-check、content-stats 和有显式 base 的 verify:depth；涉及课程登记执行 typecheck。整章收口执行 lint、build、build-search 与受影响页面链接核对，构建页面数按派生结果确认，不继续写死 225。

正文变化遵循现有视觉要求：每个修改或新增小节在深浅主题分别截图，主题通过 next-themes 的存储加 reload 切换。确认运行的是本批构建，检查 Mermaid、长表格、代码溢出与字面 Markdown 残留；截图记录放本地忽略目录，问题和验收结论进入 tracker。不得通过会回显参数的浏览器 CLI 输入密钥。

### 7.4 能力答辩

最终交付除测试外，还要求读者回答并用轨迹或代码证明：为何用 Agent；哪些步骤固定为 workflow；模型无法越过哪个授权入口；审批批准了哪一组参数；状态未知时为什么不重试；如何判断检索失败还是生成失败；如何证明模型迁移没有破坏关键契约。

不设置凭空制定的“在线准确率必须 95%”。质量目标从项目任务、错误代价和初始基线制定；安全与状态不变量则是必须全部满足的交付条件。

## 11 教程完备性与准确性的总评估设计

本节定义如何判断“这本教程是否教全、是否说对”，避免把章节数量、字数、测试绿灯或单次模型演示当作质量结论。适用对象是有后端工程经验、缺少 Agent 工程经验的读者；结论只针对本教程声明的范围，不宣称覆盖所有 Agent 产品形态。

### 11.1 两条互相独立的质量轴

**完备性**回答读者能否完成目标工作；**准确性**回答教材中的事实、代码、实验和结论是否可信。两轴分别验收，不能互相抵消：一个事实准确但缺少实施路径的章节仍不完备；一个项目能跑但关键保证描述错误仍不准确。

| 质量轴     | 检查对象                                  | 合格证据                                                  | 不足以单独证明合格                                    |
| ---------- | ----------------------------------------- | --------------------------------------------------------- | ----------------------------------------------------- |
| 能力完备性 | 目标能力是否被讲解、练习、集成并验收      | 能力矩阵中的学习结果有先修、练习、反馈及阶段作品证据      | 有同名章节、术语出现、正文达字数                      |
| 技术准确性 | API/协议/安全/统计/运行时断言的适用范围   | 固定来源或可复算实验；版本、端点、时间、边界均清楚        | 链接可访问、构建通过、模型回答看似合理                |
| 可执行性   | 读者是否能从干净环境复现关键步骤          | 锁定依赖、命令、输入、预期输出、失败路径和清理步骤        | 作者机器上的一次成功或未登记脚本                      |
| 迁移性     | 读者是否能把原后端直觉迁移到 Agent 控制流 | 对照表、负例、任务级项目与故障演练                        | 只讲新术语，不指出旧经验何时失效                      |
| 证据完整性 | 结论能否追溯到来源、运行与评分口径        | claim、source/experiment、artifact、hash、review 状态关联 | fixture 被称作 live、报告自填状态、无原始记录的旧数字 |

逐章审计改为“能力结果 → 教学节 → 练习 → 阶段作品 → 验收证据”的追踪。每项结果只允许以下等级：`0 缺失`、`1 能解释`、`2 能在受限练习实现`、`3 能在项目中集成并处理失败`。等级描述学习表现，不是对产品成熟度的认证。

逐项映射见[教程能力追踪矩阵](../../CURRICULUM-CAPABILITY-MATRIX.md)：前 10 行对应本节定义的核心毕业能力，另 6 行覆盖 Agent 适用边界、MCP、多智能体、多模态/计算机使用、人机协作、Coding Agent 与源码研读等专题，使全部 26 个注册章节都有明确的能力追踪入口。矩阵连接实际 lesson/lab/project/rubric ID，并标出目前只能证明离线行为或尚无评分项的部分。该矩阵是课程设计追踪，不代表读者已达到相应级别；当前 Stage 5 外部 holdout 与独立交接仍开放，因此毕业判定不能通过。新增或改名课程 ID 时须同步矩阵，并验证所有引用仍存在。

阶段 3 的失败轨迹验收必须把 provider 传输失败、MCP 发现/客户端异常、工具业务错误、协议错误、拒绝、截断和预算停止分开；调用已发出但未收到工具响应时记录 `execution_outcome=unknown`，不能写成工具未执行，也不能无条件重放。共享 `run_agent()` 现对 MCP 发现与调用异常生成脱敏终态/轨迹；离线合同测试只证明错误分类和 unknown 保留，真实端点、SDK 与业务工具仍需单独核对。

多智能体属于专题练习，不提高共同毕业门槛。阶段 3 项目增加受限对照：单 Agent 与多 Agent 使用同一冻结任务集、模型版本和生成参数；报告分角色轨迹、交接、调用数、usage、耗时及失败。离线替身用于固定输出并注入超时、无效结果、拒答和重复 JSON key，只能验编排和错误处理，不可据此宣称模型质量提升。现已提供独立可运行的参考练习 `examples/multi-agent-comparison/`，其中模拟时延明示为 fixture 值。rubric 必须奖励可复查对照与诚实边界，不因多 Agent 调用更多而默认得分更高。若要宣称质量差异，仍需配对真实模型评测和预先定义的评分标准。

多模态文档路径是阶段 2 的专题选修，不与版本化文本检索作品合并验收。选择者在固定输入上记录原生 PDF、页图或文本抽取路线，逐字段对照原始来源并分类转换/模型错误和不确定性；无真实模型运行则标为未验证。新增的 P2 `p2-4` rubric 评估实验记录质量，不宣称视觉能力普遍成立。computer-use 现在提供本地合成页面练习 `examples/computer-use-safety/`，并在 P5 以专题选修 rubric `p5-5` 验收任务范围、对页面不可信内容的处理、动作记录与审批停止；它不接模型或真实业务系统。真实 GUI Agent 的工具权限、隔离 runtime、视觉识别和动作日志仍须单独验证。

Coding Agent 与源码研读也是专题能力，不提高共同毕业线。选择该方向时，阶段 5 增加一次隔离副本中的范围受限任务，评分看权限边界、最终 diff、测试、对仓库不可信文本的处理和人工复核；真实凭据与客户数据不得进入练习环境，范围外改动需撤销后重新验收。不选择该方向时 `p5-4` 标为不适用，不计入共同毕业判定。现有 `examples/coding-agent-safety/` 提供故意有缺陷的 starter、合成攻击文本、验收测试和参考实现，展示目标程序如何把数据中的指令误当作优先级信号。测试不能自动审计 Coding Agent 的工具调用或沙箱设置，因此该专题验收仍需人工核对运行隔离、工具记录和完整 diff，不能把项目通过描述为跨工具的普遍安全证明。

### 11.3 Claim 级准确性分级与处置

每个重要论断按错误影响与可变性分级，而不是平均用力审所有句子：

- **A 级：安全、授权、协议兼容、数据隔离、统计推断、重试/幂等/恢复保证。** 必须有直接一手来源或可重复故障实验、明确适用版本与负例；不能验证则标 `in-review`/`unverified`，相关项目 gate 不得通过。
- **B 级：模型能力、SDK 行为、价格/usage、性能与 benchmark 数字。** 必须有端点/model/SDK/日期/参数/样本口径；动态数字应优先教查询或测量方法，过期时撤下正文结论并保留 errata。
- **C 级：工程建议、架构取舍、经验法则。** 标明是推断，写出前提、替代方案和反例；不把局部实验提升为普遍规律。

一条 claim 的闭环记录至少包含 `claim_id`、正文位置、风险级别、原始表述、来源/experiment、适用范围、修订理由、回归方式、复核者和状态。来源只能证明其明确覆盖的事实；SDK 接受参数不能证明模型支持能力，单端点观测不能证明所有兼容端点，模拟服务不能证明生产部署。修改错误结论时保留旧观测并修订其解释；若无原始材料能复核旧数字，标记未验证并停止将其用于新结论。

### 11.4 完备性审查流程

1. **锁定目标画像和边界**：明确读者既有经验、终点能力、明确不教的领域；范围变化必须说明新增先修和维护成本。
2. **建能力图**：逐项记录能力结果、依赖、lesson id、练习、项目阶段和验收；先查缺失与错误依赖，再查章节数量。
3. **走读关键路径**：由未参与编写的审阅者只看教程材料，按 clean checkout 完成阶段作品，记录每次需要作者口头补充的知识、命令和隐含前提。
4. **按风险复核 claims**：A 级全审；B 级检查仍在使用的动态结论和所有正文数字；C 级抽查绝对措辞及跨章泛化。未复核结果不能自动提升状态。
5. **验证垂直闭环**：至少从第一次模型调用、只读工具回合、检索引用、审批暂停/恢复，到外部动作对账各走一条可观察路径；fixture、集成与 live 证据分别记账。
6. **发布差距而不是隐藏差距**：报告按能力域给出等级、失败案例、证据链接和阻塞条件；“全部课程完成”只表示内容交付完成，不表示能力毕业或事实全部更新。

W6 首轮审计记录（2026-10-20；当时 144 节为 46 corrected / 15 in-review / 83 reviewed-ok）只代表 lesson 覆盖，不等价于 A/B/C claim 全量通过；该次巡检为 0 个 URL 返回 404/410，另有 16 个访问受限与 24 个网络错误/超时待复核，历史付费实验未全量重跑，Stage 4 证据待首次人工复核、Stage 5 端到端与 live/holdout/交接缺口仍需单列。该历史段落记录的逐节计数已被后续增量取代；当前数量见顶部状态与逐节台账；本段链接扫描数字仍是 2026-10-20 的历史快照。本轮修复了 5 个确认失效的链接：三个项目页的徽章锚点改到可访问的仓库主页，LangGraph 旧部署文档改到 LangSmith 官方部署文档，已更名的 GitHub 作者账号改为当前主页。修复后全量巡检未发现 404/410；24 个网络错误/超时仍待核实，16 个受限也不代表失效。

### 11.5 完成报告的标准格式

每次课程审查的结论固定包含：

1. **范围与基线**：commit、章节/lesson 数、端点及文档版本、实际执行的检查。
2. **能力完备性**：逐域等级、未映射的能力、依赖断层、阶段项目能否独立完成。
3. **准确性**：已确认错误、范围过宽的论断、动态过期项、`in-review` 与缺少原始证据项。
4. **验证边界**：offline、integration、live、人工审阅分别证明什么，以及没有证明什么。
5. **最高优先级风险**：按用户/数据伤害、错误传播面、读者卡点和修复成本排序；给出文件/小节定位与可判定的验收条件。
6. **关闭判据**：标明哪些属于课程缺口、实现缺口、外部证据缺口或人工发布决定，避免用修改正文掩盖系统未实现。
