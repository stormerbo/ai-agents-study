# 内容深度标准（CONTENT-DEPTH.md）

> 这份标准与 AGENTS.md §3.2 的「四块」**并行**，不是替代。
> 四块（实测数据 / Mermaid / 可运行代码 / 真实错误案例）保证**可信**；这份标准保证**能读懂、能照着做**。
> 背景：四块标准下 134/134 节全部达标，但一个「有后端经验、零 AI Agent 经验」的读者会在大量小节卡住 ——
> 因为它测的是证据密度，不是可教学性。

## 一、一节必须有的五样

| # | 要素 | 判据（自问） | 常见缺失 |
|---|---|---|---|
| 1 | **定义** | 本节新出现的概念，读者在**第一次遇到它的那一句**就能知道它是什么吗？用他已知的东西（HTTP / 缓存 / 状态机 / 接口签名）类比了吗？ | 名词直接使用（token、embedding、stop_reason、few-shot、Jaccard、水合） |
| 2 | **产物** | 本节让读者「造」的东西（笔记、记录、schema、报文、清单、轨迹、配置），有没有一份**真实、完整、可复制**的示例？ | 只有描述与字段名，没有 JSON / 报文 / 记录 |
| 3 | **判据** | 为什么这样设计？换一个场景怎么改？ | 只说「字段固定」，不说字段怎么定 |
| 4 | **步骤** | 谁、在什么时机、写到哪里、下一轮怎么读回来、怎么更新？ | 只有「应该做 X」，没有「在哪做、做完放哪」 |
| 5 | **失败形态** | 它会怎么坏？坏了怎么发现？ | 只讲正面路径 |

**五样里 1 / 2 / 4 是重灾区。** 判断方法只有一句话：**我能不能用这一节的文字，教会一个后端同事做出这个功能？**

## 二、术语首现规则

1. **首次出现即解释**（一句即可，但要给机制或类比，不能换一个说法糊过去）。
   例： 例：token 不是字符也不是单词，而是词表切分后的片段 —— 它是模型的计费单位、容量单位与延迟来源。
2. **英文缩写首次出现必须展开**：RAG、CoT、MRTR、DPR、SSE、TTFT…（全站目前 RAG 只出现 1 次且从未解释）。
3. **同一词两义必须显式提示**。已有的坑：checkpoint 在第 3 章指「本节自检题」，在第 11 / 15 章指「框架的持久化检查点」。
4. 不要依赖术语表（glossary.ts 全站 0 处使用、也没有术语页面）—— 解释写在正文里。

## 三、禁止清单（硬性）

- ❌ **不许新造实测数字**。新增数字只有两个合法来源：站内已有实测、或本次真实跑出来的输出。
- ❌ **不许把未实跑的示例写成实测**。构造出来的产物必须就地标注：`（示例：构造数据，未实跑）`（示例：构造数据，未实跑）。
- ❌ 不许删改已有实测数据、口径与日期。
- ❌ 不许引入新的 MDX 组件或新的 frontmatter 字段（只用标准 Markdown、``` 围栏、表格、`<Mermaid chart={...} />` 组件）。
- ❌ 正文里不允许出现 `CODE`、@@CODE@@、TODO、待补 这类占位符。
- ❌ 代码块必须标语言；代码必须自包含（不许 importlib 去读读者拿不到的文件）。
- ❌ 用 os.environ 必须同时 import os，并在正文交代需要哪几个环境变量、怎么拿到。
- ❌ 不许把「要注意 X / X 很危险」当终点，后面必须跟一句「所以怎么做」。

## 四、写法样板：以「压缩与结构化笔记」（ch3/04）为例

它原本缺的：一份填好的笔记、字段怎么设计、谁在什么时机写 / 写到哪里 / 怎么读回、笔记自己怎么坏、笔记与记忆 / RAG 的边界。

补法（可直接照抄这个结构）：

1. **产物** —— 给一份完整笔记，标注为示例或实测：
   ```json
   {
     "identifiers": {"order_id": "ORD-88213", "report_id": "RE-4471"},
     "amounts":     [{"value": 4820, "unit": "CNY", "what": "退款金额"}],
     "constraints": [{"text": "不要动生产库", "source": "客户", "turn": 31}],
     "rejected":    [{"proposal": "改用批量接口", "reason": "不支持幂等", "turn": 3}],
     "errors":      ["ERR_POOL_EXHAUSTED"]
   }
   ```
2. **判据** —— 三条：会被**程序**比较 / 拼接的（id、金额、日期）必须结构化；丢了会**重复执行**的（副作用）必须记；丢了会**越界**的（约束 / 禁止项 / 否决理由）必须记。
3. **步骤** —— 触发（检测到新事实时写，不是每轮、也不是结束时）→ 存放（独立 notes，序列化后放固定 system 段或首条 user 块，理由是不破坏前缀稳定）→ 读回（先 notes 再最近 N 轮）→ 更新（按 (category, value) 去重，冲突记 superseded_by）。
4. **失败形态** —— 字段空着不填（等于第 5 章的「必填逼幻觉」）；推断被当事实（每条必须带 source）；笔记自己膨胀（按字段合并，而不是按重要性摘要）。
5. **边界** —— 笔记 = 本任务状态（任务结束作废）；记忆 = 跨会话（第 7 章三条标准）；RAG = 外部只读知识（第 6 章）。

## 五、验收

```bash
node scripts/depth-check.mjs          # 机器可判的部分（占位符 / 语言 / 自包含 / 术语 / 产物）
node scripts/content-stats.mjs        # 字数与四块（不应下降）
pnpm test                             # 内容完整性 + 渲染契约 + 深度门禁
pnpm typecheck && pnpm lint
```

> 机器能查的只是子集。每一节的「能不能读懂」最终由人判断 —— 判据就是第一节那张五要素表。
