## 4. 踩过的坑（务必避免重犯）

### 4.1 代码高亮配色 ×2 —— 同一个根因

**症状**：浅色模式下代码块「深色文字 + 深色背景」，几乎不可读。

**根因**：`next.config.ts` 里设了 `keepBackground: false`，注释还写着「背景交给 Tailwind」—— **但从没真正设置过那个背景**。注释描述了一个不存在的实现。于是代码块落到 Tailwind typography 的 `pre` 默认样式上（那是为深色背景配的浅色文字）。

**两次的具体触发条件不同**：

| 次数   | 触发场景           | 原因                                                                                             |
| ------ | ------------------ | ------------------------------------------------------------------------------------------------ |
| 第一次 | 浅色模式全部代码块 | 没给 `pre` 设背景与前景                                                                          |
| 第二次 | ````text` 纯文本块 | Shiki 对**无语法高亮**的内容不输出内联 CSS 变量，导致 `color: var(--shiki-light)` 取不到值而失效 |

**修复**（见 `globals.css`）：给 `.prose pre` 显式设置 `background-color: var(--color-muted)` 和 `color: var(--color-foreground)` 兜底。

**教训**：**关掉某个默认值时必须补上自己的**。而且这类问题构建通过、内容完整、肉眼才看得出 —— 见 §5.2 的验证流程。

### 4.2 长行溢出

代码示例的某些行超出正文栏被裁掉。已加 `overflow-x: auto` 兜底，同时**把示例代码拆行** —— 教程代码不该逼读者横向滚动。

2026-10-08 做过一次全库扫描：阈值定在 86 字符，把 `api_key=os.environ.get(A) or os.environ.get(B)` 这类惯用长行拆成多行。

**阈值适用于「可以改写的代码」。** 逐字的 API 报错是例外 —— 拆行会让「原文」失真，而它本身就可能有 100+ 字符。处理方式是：**保留开头的关键片段，用 `…（下略）` 明确标注截断**，让它从 200 字符降到 110 左右。读者需要的是这条报错的**形状与信息量**，不是逐字全文。见章 4 第 1 节的两条 400 报文。

### 4.3 我（AI）在同一个 bug 上猜错三次

记录这个过程，因为它是本项目准确性标准的**现实依据**：

| 猜测                                  | 实际情况                                   |
| ------------------------------------- | ------------------------------------------ |
| 「内联样式优先级高，加 `!important`」 | 错。span 上根本没有内联 `color`            |
| 「`.dark` 类没加上」                  | 错。类加上了，规则也生效了                 |
| 真实根因                              | `keepBackground: false` 没有配套的背景设置 |

**教训**：**不要猜运行时状态，去读它。** 装 playwright 之后可以直接截图与读计算样式（见 §5.2）。

### 4.4 统计指标陷阱

用「中文字符数」衡量篇幅会误导 —— `messages-api.mdx` 因为含大量 JSON 与事件序列，中文字符只有 1366，但实际内容量远超。**要同时看「说明文字总量」与「代码块数」。**

### 4.5 实验数据被 prompt caching 污染

做「工具定义成本」实验时，数据出现 `1 个工具 306 token，3 个工具 174 token` 的矛盾结果 —— 表面上像是「工具越多越便宜」。

**真相**：DeepSeek 自动做了 prompt caching，而 `input_tokens` 的语义是「**未命中缓存的**输入」。必须用三项之和：

```
总输入 = input_tokens + cache_read_input_tokens + cache_creation_input_tokens
```

**教训**：数据自相矛盾时，先怀疑测量方法，不要急着解释或丢弃。

### 4.7 localStorage 导致的 hydration mismatch（**重犯**）

**症状**：

```
Hydration failed because the server rendered HTML didn't match the client
...
+ className="border-b border-amber-500/40 bg-amber-500/5 px-4 py-3 text-xs"   ← 客户端
- className="border-border border-b px-4 py-2"                               ← 服务端
```

**根因**：`useState(() => loadByok())` —— `loadByok()` 读 localStorage，
而**服务端没有 localStorage**，返回空状态；客户端返回实际状态。两端首次渲染必然不一致。

**讽刺之处**：这个项目在 `theme-toggle.tsx` 里**已经用 `useSyncExternalStore` 正确
解决过同样的问题**，但写 Playground 时忘了。所以这条要单独记。

**修复**：

```ts
const subscribeNothing = () => () => {};
const mounted = useSyncExternalStore(
  subscribeNothing,
  () => true,
  () => false,
);
```

所有依赖 localStorage 的渲染都加 `mounted &&` 门控。

**规则**：**任何读 localStorage / sessionStorage 的状态，首次渲染必须与服务端一致。**
用 `useSyncExternalStore` 的 `getServerSnapshot` 区分，或用 `mounted` 门控。
不要用 `useEffect + setState` —— React 19 的 lint 规则会直接报错。

### 4.8 `meta.ts` 的纯文本字段不解析 Markdown（静默失效）

**症状**：章节摘要、自检项、资源推荐理由、实验目标里写的 `**强调**`，页面上**原样显示成星号**。全站一度有 8 个页面中招。

**根因**：这些字段是 `meta.ts` 里的普通字符串，通过 `{field}` 直接插进 JSX —— **不走 MDX 管线**。内容是按 Markdown 写的，渲染层却当纯文本。

同一个文件里还有第二种表现：MDX 正文里的 `**` 若**紧贴 CJK 标点**，CommonMark 的 flanking 规则会让它失效：

| 写法                          | 为什么失效                                                 |
| ----------------------------- | ---------------------------------------------------------- |
| `而**「独立」是关键词**`      | 开头 `**` 后紧跟 `「`，且前面是普通字 → 不构成左闭合分隔符 |
| `采用**子词（subword）**方案` | 结尾 `**` 前紧贴 `）`，后面又是普通字 → 不构成右闭合分隔符 |

**修复**：

1. 新增 `src/components/ui/inline-md.tsx` —— `<InlineMd>` 渲染 `**粗体**` 与 `` `代码` ``，`plainText()` 用于不能放 JSX 的位置（`<meta description>`、SVG `<title>`）。所有渲染这些字段的组件都已接入。
2. 修掉 MDX 里两处紧贴标点的写法（把标点移到标记**外面**）。
3. `tests/curriculum.test.ts` 加两组断言：纯文本字段的标记必须成对；MDX 正文的粗体两端必须构成合法分隔符（按奇偶位置认开/闭标记，再套 flanking 规则）。

**验证方式**：`curl` 每个页面，剔掉 `<pre>`/`<code>` 后 grep 字面 `**`。**这条比读源码可靠** —— 靠肉眼看源码发现不了，靠构建也发现不了。

**教训**：和 §4.1 是同一类 —— **内容按一种格式写、渲染层按另一种处理，且失败是静默的**。凡是「塞进 JSX 的字符串字段」，都要问一句：作者会不会在里面写标记？

### 4.9 一节正文要登记四处，漏一处静默失效

**症状**：`.mdx` 写好了、`meta.ts` 也标了 `hasBody: true`，但页面就是显示「这一节的正文还在撰写中」。

**根因**：正文要真正渲染，需要**四处**同时写对 —— 而它们之间没有任何编译期联系：

| #   | 位置                                                          | 作用                      |
| --- | ------------------------------------------------------------- | ------------------------- |
| 1   | `meta.ts` 的 `hasBody: true`                                  | 页面据此决定去不去取正文  |
| 2   | 该章 `body.ts` 的 `'<slug>': () => import('./NN-<slug>.mdx')` | 把 MDX 接进编译图         |
| 3   | 磁盘上的 `.mdx` 文件                                          | 实际内容                  |
| 4   | `src/lib/content/body.ts` 的 `REGISTRY`                       | 按章 id 找到该章的 loader |

`getLessonBody` 查不到时**返回 `undefined`**（这是设计使然 —— 正文没写时章节页要能展示大纲），页面于是静默退回占位。构建通过、测试曾经也全绿 —— 又一个 §4.1 / §4.8 家族的成员。

**修复**：`tests/curriculum.test.ts` 新增「正文登记一致性」组（2 条断言），校验四方互相一致：body.ts 的 key 集合 = 标了 `hasBody` 的 slug 集合、每个 import 指向的文件真实存在、`.mdx` 文件名符合 `<编号>-<slug>.mdx` 且每节恰好一个、有正文的章必须在 `REGISTRY` 里注册（没有正文的章则不许注册）。

> 这条守卫本身就是它要防的 bug 的变体：第一版正则只认带引号的 key，而 `prompt-engineering/body.ts` 与 `context-engineering/body.ts` 里有两处写成了不带引号的 `reliability:` / `compaction:` —— 守卫当场误报。已把两处统一成带引号，并让正则两种都接受。**守卫也要能被证伪**：写完要故意摘掉一处登记，确认它真的会红。

**教训**：凡是「同一个事实写在两个以上地方」的结构，都要问一句 —— **不一致时会报错，还是会静默降级？** 这里是降级，所以只能靠测试。

### 4.10 两类命名空间长得很像：章节 id 被误填成资源 id

**症状**：新增章节时，`lesson.resourceIds` 里填了 `'tool-calling'`、`'agent-loop'` 这类值。测试报错，但报的是「引用了不存在的资源」，而不是「你填错了类型」。

**根因**：`ChapterId` 与 `ResourceId` 在 schema 里**都是 `string`**（第 21-25 行），所以编译器不会拦。而两者的命名风格高度相似（都是 kebab-case 名词短语），写的时候很容易顺手写成章节名 —— 尤其是当你要表达「这一节与第 4 章相关」时。

**修复**：只能靠测试。已有断言 `节 X 引用了不存在的资源 Y` 会抓住它。补充一条更省时的自查脚本：

```bash
node -e "…扫描所有 resourceIds 与资源库 id 求差集…"   # 见本次新增的临时脚本做法
```

**教训**：**类型别名一律用 `string` 会丢失一整类检查。** 这里用模板字面量类型（把资源 id 约束成「res- 前缀」的模板字面量类型）不现实（资源太多），但至少要知道这个洞在哪 —— 它在「新增章节」这个高频动作上一定会被踩到。本次 10 个新章里有 13 处踩中。

### 4.11 编辑工具的 old_string 是子串匹配，不是整行匹配

**症状**：想在某行前插入一行，用 2 个空格缩进的那行做锚点，结果报 `old_string matched 2 times`。

**根因**：匹配是**子串**匹配。锚点 `  resourceIds: [` 同时也出现在 `      resourceIds: [` 里面（后者的尾部就是它）。缩进越浅，越容易成为更深缩进行的子串。

**修复**：需要行精确时，不要用编辑工具 —— 用脚本按 `split('\n')` 找 `startsWith` 的行号再 splice。本次给 4 个章插入 `labIds` 就是这么做的。

**教训**：和 §4.9 同一类 —— **工具的语义与你的直觉不一致，而失败信息不会告诉你这一点**。报错说「匹配到 2 次」，而不是「你的锚点太短了」。

### 4.12 两个臂用不同的判分口径 —— 结论从 4/10 变成 7/10

**症状**：做「宽召回 + 模型重排」的对照实验时，我算了两个数字：重排前命中率、重排后命中率。前者用**章节区间**判命中（候选段落必须与金标小节重叠），后者图省事写成了**文件判等**（只要来自同一个文件就算对）。

结果跑出来是「重排前 0/10，重排后 7/10」，看起来像重排把效果翻了七倍。

**根因**：7/10 里有几条的正确答案**压根不在候选集里** —— 重排只能重排候选，它们不可能被救回来。是文件级判等把「同文件的另一小节」也算成了命中。

**修复**：把两个臂统一成章节级判定，同时把**天花板**也显式算出来（正确答案在候选集内的条数）。修正后的数字是：重排前 0/10、天花板 4/10、重排后 4/10 —— **正好打满上限**，故事比原来更干净，也更有教学价值。

**教训**：这一条比前几条更隐蔽，因为**两个数字单独看都合理**。只有当它们放在一起（重排后 > 天花板）时才自相矛盾。所以对照实验里要养成两个习惯：

1. **判分函数只写一份**，两个臂共用。分开写就一定会漂。
2. **把理论上限一起算出来**。任何「A 比 B 好多少」的结论，先问一句：B 的最好情况能到多少？超过了就说明测量错了。

### 4.13 用占位符写正文时忘了执行替换 —— 页面上出现字面 @@

**症状**：为了让正文模板里的反引号不干扰外层字符串，我用 `@@` 作占位符，写完再统一替换成反引号。章 7 第 2 节那次**我漏掉了这一步** —— 页面上出现了字面的 `@@deepseek-flash@@`。

**根因**：替换是我手工执行的一步，它与「写文件」之间没有任何强制关系。更麻烦的是**构建通过、测试通过、内容体量达标** —— 三样都没红。

**修复**：加了一个全库扫描脚本（`verify-output/scan-markers.mjs`）：逐行判断是否在代码围栏内，围栏外出现 `@@` 就报错。它随即又抓出章 6 第 5 节的一处（那处是我后来用 edit 追加段落时带的标记，同样漏了替换）。

**教训**：凡是「写进去之后再处理一遍」的流程，都要问一句 —— **这一步漏掉会报错，还是会静默留下痕迹？** 这次是后者，而且当时的三套守卫全都没覆盖它。可靠的替代做法是**根本不用占位符**：直接用 `String.fromCharCode(96)` 拼出反引号，让「替换」这一步从流程里消失。

### 4.14 脚本把 label 写在了数组外面 —— 文档被静默改坏

**症状**：用脚本批量更新本文档时，我写了几处 `reps.push([a, b], '标签')` —— **标签落在了数组外面**。于是 `reps` 里多出一个独立的字符串元素，而循环里的 `const [a, b, label] of reps` 会把它解构成三个字符。

结果是执行了这些「替换规则」：`'章' → '列'`、`'待' → '办'`、`'工' → '具'`、`'未' → '复'`、`'进' → '度'` —— 每个都替换了**全文第一处出现**。

文档里因此出现了「办验证清单」「后端具程师」「每一列都有」「复命中缓存」「办办清单」这类字。

**为什么没被发现**：脚本退出码 0、没有任何报错；`pnpm test` 全绿；`pnpm build` 通过；内容体量统计也不看这个文件。**所有守卫都不覆盖它。**

**修复**：`git checkout -- AGENTS.md` 恢复，然后用一个 `add(a, b, label)` 函数收口（参数位置固定，从语法上就不可能写错），并在脚本开头加一条断言：`reps.every(r => r.length === 3)`。

**教训**：这和第 4.12 是同一类 —— **错误发生在「我的工具脚本」里，而不是在产品代码里，所以所有面向产品的检查都看不见它**。两个可操作的习惯：

1. **批量改文档的脚本必须自带校验**：改完之后 grep 几个已知正确的串，确认它们还在、且没有出现可疑的近似串。
2. **用函数收口参数**，而不是裸数组 —— 数组靠位置，位置靠人记。

### 4.15 组件返回 Fragment，父容器是 flex —— 一句话被拆成三列

**症状**（用户截图发现）：章节日「会失效的直觉」里有一条被拆成**三列并排**，文字完全交错：

```
把上下文窗口当成内   放进去不等于读   ，中间部分最容易被
存：              得到            忽略
```

原文是一句话：「把上下文窗口当成内存：**放进去不等于读得到**，中间部分最容易被忽略」。

**根因**：`InlineMd` 返回的是 **Fragment**，而调用方的 `<li>` 是 `flex` 容器：

```jsx
<li className="flex gap-2 text-sm leading-relaxed">
  {' '}
  {/* 父容器是 flex */}
  <span aria-hidden>!</span>
  <InlineMd text={item} /> {/* 返回 Fragment → 3 个 flex item */}
</li>
```

Fragment 的子节点**直接成为 flex item**，于是「文本 / 粗体 / 文本」各占一列并排排开。

**为什么长期没被发现**：触发需要三个条件同时成立 —— ①该字段里写了 `**` 或反引号；②渲染它的父容器是 flex/grid；③有人真的去看那一屏。构建、测试、内容完整性统计**三样全绿**。

同一个组件还有一处**潜伏**的调用点：`checkpoint-list.tsx` 里 `<span className="flex ...">` 包着 `<InlineMd text={cp.question} />`。当前没有任何自检项含 `**`，所以它还看不出来 —— 一旦有人给自检项加粗，同样的错位就会在那里出现。

**修复**：让 `InlineMd` 返回**单个** `<span>`。这是根因修法 —— 它有 15 处调用点，逐个加包装层既啰嗦又一定会漏。

**守卫**：`tests/inline-md.test.ts`（5 条）用 `renderToStaticMarkup` 断言输出以单个 `<span>` 开头结尾。已按 §4.9 的规矩**证伪过**：把实现改回 Fragment，2 条立刻变红。

**教训**：**一个返回「多个并列节点」的组件，它的安全性取决于调用方的 CSS。** 这类组件要么返回单根，要么必须在文档里写明「只能放在块级容器里」—— 而后者是靠人记的约束，迟早会被忘。

这条和 §4.8 / §4.13 是同一个家族：**内容与渲染层的契约不一致，且失败是静默的**。这次撞在一起的两个契约是「行内 Markdown」与「flex 布局」。

### 4.16 解析器贪婪匹配，把「解析失败」当成了「模型全错」

**症状**：测「同一张图跑三次、比对差异能不能抓出错误」时，第一版给出了一组完美数字：**召回 100%、精确 100%**。

但明细里有一行：`第 2 次：标准答案 360 格，实际错 360 格`。

一次提取 360 格**全错**是不可能的 —— 那等于说模型一个字都没读对。那是解析失败，而我的代码把「解析不出来」记成了「每一格都错」。

**根因**：解析器用的是贪婪正则 `re.search(r"[.*]", text, re.S)` 的写法（`.*` 加 `re.S` 跨行），它会从第一个 `[` 一直匹配到**最后一个** `]`，把数组后面的说明文字也吃进来，`json.loads` 必然失败。

**修复**：改用 `json.JSONDecoder().raw_decode(text[text.find("[") :])` —— 从第一个 `[` 起按 JSON 语法解析，结构一结束就停。同时加断言：解析出的行数必须等于期望行数，否则重试并把尾部 90 个字符打出来。

**修正后的真实数字**：三次各自错 6 / 9 / 8 格，并集 12/360；一致性校验**召回 67%、精确 100%**。

**教训**：这和 §9 里那条「解析器只认对象不认顶层数组」是同一类 —— **解析器的失败被记成了被测对象的失败**。两个可操作的习惯：

1. **解析失败必须是一个独立状态**，不能和「解析成功但结果为空或全错」混在一起。
2. **对解析结果的形状写断言**（行数、字段数），而不是只检查「有没有解析出东西」。
