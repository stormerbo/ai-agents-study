## 6. 当前进度 · 实测数据

### 6.3 已采集的实测数据（可复用）

全部标注了模型与日期，写正文时直接引用：

- **token 密度**：短中文 7 字符→35 tok、长英文 1050 字符→381 tok，推出约 30 token 固定开销
- **工具成本**：tools 数组入场费约 200 token，每个工具约 60 token（**注意缓存污染**，见 §4.5）
- **温度对比**：`temperature=0` 三次里一次不同（「三味咖啡/三味咖啡/三咖小馆」）
- **三种实现成本**：单次调用 365 / workflow 619 / agent 1625 token
- **多轮成本**：每轮输入 +32 token，累计 `57N + 16N(N-1)`，是 O(N²)
- **缓存行为**：命中使未缓存输入从 2688 降到 256、耗时快 3.4 倍；**改一个字全部失效**
- **流式事件**：63 个事件的完整序列，工具参数 18 个分片拼成完整 JSON
- **enum 约束**：模型正确拒绝不在枚举内的城市，**未编造参数**
- **否定式 vs 正面指令**：否定式越界 0 次（完美达成约束），但平均只写 74 字（要求 200 字）—— 抑制约束的同时把合法内容一起压掉了
- **提示注入 6 种形式**：脚本式/伪装式 0/6（完全失败）；格式操纵 6/6 → 加 XML 标签 2/6；内容操纵 6/6 → 加标签**仍 6/6**（标签只挡一半）
- **少样本**：10 个典型示例 = 零样本（都是 9/10，且错同一条）；3 个边界示例 = 10/10；边界+典型 = 10/10（典型纯属陪跑）
- **CoT**：多步推理题准确率 15/15 → 15/15，成本 +85%；简单题 6/9 → 6/9，成本 +125%
- **self-consistency**：唯一答案题 5 次采样**零分歧**（temperature 1 与 0 都一样）；创作题 6/6 各不相同 → 投票无事可做，成本 5.4x
- **self-eval**：喂入构造的错答 8/8 捉住、0/8 误报 —— 但那是**独立重算**，不是审阅推理
- **位置 / 容量效应**（章 3 第 1 节）：5 种设计、最高 22.8k token，位置扫描与容量扫描全部 15/15，**未复现**；唯一一次 0/3 是 `max_tokens` 被思考吃光造成的空输出
- **system prompt 具体度**（章 3 第 2 节）：矛盾规则下同一 prompt 跑 12 次 → 8 承诺 / 4 不承诺；单条规则时确定（7 → 4/4、12 → 0/4）。输出长度：抽象 311 字 / 原则式 334 字 / 逐条式 81 字
- **预加载 vs 按需取**（章 3 第 3 节）：20 篇省 12%、60 篇省 47%；固定 40 篇、需要 2/8/20/40 篇时按需取分别是 0.64x / 0.95x / 2.47x / 3.60x —— **交叉点约在「需要的占 20%」**
- **压缩**（章 3 第 4 节）：一次性任务里摘要 2272 token > 不压缩 1952 token；细节保存率摘要 7/8（丢的是「不要动生产库」这条硬约束）、结构化笔记 8/8（但贵 3.4 倍）
- **子智能体**（章 3 第 5 节）：20 篇检索任务里主上下文峰值 1258 vs 6816、总 token 9182 vs 25913；而 8 个子 agent 各装一次共享背景 → 68548 vs 8430 token（**8.1 倍**）
- **工具调用的往返结构**（章 4 第 1 节）：`stop_reason=tool_use`、content = [thinking, tool_use]；漏 `tool_result` 与 `tool_use_id` 不匹配都是 **400**，报文指出具体位置
- **工具描述精确度**（章 4 第 2 节）：模糊描述 3/3 发起调用（含 1 次误用、参数传中文）→ 精确描述正确调用且不误用
- **enum vs 自由字符串**（章 4 第 2 节）：自由字符串 0/3 合法（"最高"/"低"/"紧急"），enum 3/3 合法
- **互斥可选参数**（章 4 第 3 节）：两个普通可选字段 3/3 同时传 → 描述写明二选一 0/3 → 拆成两个工具 0/3 且结构上不可能
- **失败结果的回传形态**（章 4 第 4 节）：不标 `is_error` → 3/3 把错误当数据写进表格；只标不给原因 → 3 次中 2 次原地重试；标 + 说明原因 → 正确
- **写操作的重复执行**（章 4 第 4 节）：返回「状态未知」时模型**主动不重试**并说明理由 —— 重复风险主要在你的代码层
- **工具定义成本**（章 4 第 5 节）：约 60 token/工具，8 → 86 个是 678 → 4945 token，**每轮都要付**
- **工具数量与准确率**（章 4 第 5 节）：8/20/44/86 个工具选对率均为 8/8；5 个语义重叠工具连问 5 次也稳定
- **提示式 JSON 的稳定性**（章 5 第 1 节）：两个任务三方案各 8 次全部格式成功；记录数 5/10/20/30/60 各 3 次、三种方案共 45 次运行，**一条不漏、一次不坏**
- **强制工具调用必须关闭思考**（章 5 第 1 节）：带思考时 400 `Thinking mode does not support this tool_choice`；关掉后可用，output_tokens 中位从 1591 降到 223
- **schema 关键字的实际约束力**（章 5 第 2 节）：`maximum`/`pattern`/`format`/`minItems` **均不强制**（150 / 吞掉连字符 / 输出「下周三」/ 只给 2 项）；`required` 反而逼出假值（`""` / `"未提及"`）；`strict: true` 被接受但静默无效
- **description 才是有效约束**（章 5 第 2 节）：`必须用英文` → 5/5 输出英文；`必须是 11 位手机号` → 遵守了「纯数字」但做不到「11 位」
- **enum 的双刃剑**（章 5 第 2 节）：无正确答案时 `[refund, repair]` 6/6 静默选错；补上 `other` 后 6/6 正确
- **重试策略**（章 5 第 3 节，隐藏业务规则，各 6 次）：首轮全部不合格；原样重发 0/6、空洞重试 0/6、**带错误信息 6/6**；拆开测：只给上次输出 0/6、只给错误原因 6/6
- **幻觉**（章 5 第 4 节）：对话里从未出现订单状态，schema 强制要一个 → 5/5 输出「处理中」；改成「代码查库后注入事实」→ 5/5 原样采用
- **跨字段规则**（章 5 第 4 节）：输入自相矛盾（end < start），不提示 → 5/5 照抄；提示归一化 → 5/5 修正

- **图像 token 阶梯**（章 8 第 1 节）：≤512px 都是固定下限 186 token；1280 / 1568 / 2048 / 3000 都是同一个上限 996 token（服务端会缩）；中间段约每 1600 像素 1 token
- **URL 图像会被服务端下载**（章 8 第 1 节）：给不存在的地址返回 400 `Failed to download image from ...`，说明是**服务端**去取 —— 地址来自用户即构成 SSRF 面
- **PDF 三条路线**（章 8 第 2 节）：直接发 document 块 **HTTP 200 但只有 59 token、内容被静默丢弃**（模型答「文档不受支持」）；渲染成图 337 token ✅；自己抽文本 123 token ✅
- **视觉提取的分辨率阶梯**（章 8 第 3 节）：480 宽 290 token 到 2000 宽 1061 token，**准确率全是 36/36** —— 多花 3.7 倍买不到准确率
- **视觉错误的真实形态**（章 8 第 4 节）：120 行密集表 352/360，8 处错误**全部是单字符替换**（838→836、359→389、88.38→98.38），item 编号列**零错误**；格式/类型/范围三重校验全过
- **一致性校验的效果**（章 8 第 5 节）：同一张图跑 3 次，错误并集 12/360；「三次不一致」标出 8 格且全对 → **召回 67%、精确 100%**；漏掉的 4 格是「每次都错成同一个值」

- **界面 agent 的循环成本**（章 9 第 2 节）：合成表单任务 5 步完成、3/3 成功；每步输入 token 473 → 758 → 1053 → 1356 → 1661，**每步约 +300（就是一张截图的价钱）**；5 步合计 5,301
- **点击精度**（章 9 第 2 节）：每次点击到最近元素中心的平均距离 **1.3 / 2.1 / 2.6 px**，落空 0 次
- **小目标的失败形态**（章 9 第 3 节）：按钮从 180×52 缩到 44×26，12 次里 3 次失败（75%）；失败时**反复点同一个错位置**（落空 39-45 px，最后跳到 323 px），成本 19,209 与 26,568 token —— 是成功案例的 **3.8 到 5.3 倍**
- **点击无效**（章 9 第 3 节）：让点 Create 完全无反应（界面不变、无报错），模型**察觉到了**并连点 4 次，但它**没有「报告卡住」的出口**，撞到 8 步上限才停；12,269 token（成功的 2.4 倍）
- **API vs 界面**（章 9 第 5 节）：同一件事**创建用户**，走 API 工具调用 **384 token / 1 次往返**，走界面循环 **5,528 token / 5 次往返** —— **14.4 倍 token、5 倍往返**
- **三种范式的代价**（章 10 第 1 节，线性任务）：Plan-Execute **506** / ReAct 1,203 / Reflection 2,568 token —— 都对，最贵比最省贵 **5.1 倍**
- **静态计划在条件分支任务上失效**（章 10 第 3 节，各 3 次）：ReAct **3/3**、1,971 token；Plan-Execute **0/3**、3,087 token（**贵 57% 且全错**）。三次失败签名是把「待定决策」写进工具参数：`"北京或上海中明天最高温更高的城市"`、`"${北京明天最高温 > 上海明天最高温 ? '北京' : '上海'}"` —— **模型试图用三元表达式构造一个条件**，因为计划格式里没有条件结构
- **反思的成本**（章 10 第 4 节）：ReAct 1,203 → ReAct+Reflection 2,568（**+113%**），结果相同。7 次里 2 次把正确改错，其中一次的理由是「我没有联网数据，无法核实」—— 因为只给了结论没给证据；后来 3 次对照（只给答案 vs 答案+证据）**全部通过，未复现**
- **断点恢复会重复副作用**（章 11 第 4 节）：在「工具已执行、状态未落盘」之间注入崩溃，恢复后朴素版写入 `u1, u2, u2, u3`（**4 条，重复 1**），幂等版 `u1, u2, u3`（3 条）。**注意：第一版用去重 id 集合计数，两版都显示「3 条」—— 测量方法把重复藏起来了，改成数行数才暴露**
- **多智能体的成本倍数**（章 12 第 2 节）：单 agent 4,270 vs 主管+3 工人 8,161 = **1.91×**（小背景）；9,734 vs 19,380 = **1.99×**（3,489 字大背景）。**倍数没有随背景变大而升高** —— 机制是「输入乘份数、输出不乘」，输出占比高时倍数被摊平。对照第 3 章那个 8.1 倍（8 个子 agent、输出很短）是同一模型的另一段
- **抽象泄漏的现场**（章 13 第 3 节，真 LangChain 0.3.7）：`@tool` 装饰器生成的 schema 里 `day` 只有 `{"type": "string"}`，**没有 enum** —— 尽管文档字符串写了「只支持明天或后天」。而第 4 章实测 enum 与自由字符串是 **3/3 对 0/3**。改用 `Literal["明天","后天"]` 后 schema 变成 `{"enum": ["明天","后天"], ...}`
- **MCP 无状态化的机制验证**（章 14 第 3、4 节，自实现 stdio server）：不带 `_meta` → `UnsupportedProtocolVersionError(-32001)`，`requested: null`；带错版本同样；带对版本 → result。**版本校验发生在每个请求上**，没有握手。MRTR：`transfer_money` 首次调用返回 `{"resultType": "input_required", ...}`，客户端补输入后重调才有 `complete` —— **server 不主动发请求，发起权始终在客户端**
- **第三方 server 的可见边界**（章 14 第 5 节）：`tools/list` 只给出 name / description / inputSchema 三样。实现、有无副作用、参数怎么处理 —— **全都看不到**。`transfer_money` 恰好把危险写在名字上，而 `optimize_storage` 可以是 `DROP DATABASE`

- **评测集大小**（章 15 第 2 节）：20 道可判定题答对 19（**95%，天花板效应**）。bootstrap 4000 次：5 题 ±20.0 个百分点、10 题 ±20.0、15 题 ±13.3、20 题 ±15.0 —— **不单调，因为 p=95% 时区间被 1.0 截断**。二项模型（纯计算）：让单次测量误差 ≤10 个百分点需 **98 题**；A/B 分辨 10 个百分点需**每组约 195 题**；分辨 5 个百分点需每组约 780 题。区分度由 p(1-p) 决定：p=50% 时 0.25，p=95% 时只有 0.0475 —— **全对的评测集测不出改进**
- **LLM-as-judge 的位置偏见**（章 15 第 3 节）：悬殊对 4 组各判两次（好的放 A / 放 B）→ **0/4 偏见，与人工标注 8/8 一致**；接近对 4 组各判三次 → **重复一致性 4/4、位置偏见 0/4**。合计 **位置偏见 0/12**
- **judge 的冗长偏见**（章 15 第 3 节）：第一轮注意到"4/4 都选了更长更详细的答案"，但我停下来问了一句「在我的对照里长度和完整度是不是同一件事」—— 是。于是第三轮让**长答案注水**（绕、重复、答非所问地扩写）→ **6 次全部选了短的，冗长偏见 0/6**。**这一轮反过来解释了上一轮**：它偏好的不是长度，是完整度
- **轨迹的定位价值**（章 15 第 4 节）：同一份最终答案（`预计送达: 1288.50` 与金额相同），只看答案时四种猜测指向四份不同的代码；有轨迹时对照第 2 步返回值 `{"carrier":"顺丰","eta":1288.50}` → **根因是字段名 `eta` 被当成了可直接展示的字段**，且值是同一个所以伪装成脏数据而非类型错误
- **回归的噪声底线**（章 15 第 5 节）：30 题、基线通过 26（86.7%）→ 噪声底线 **±20.0 个百分点**。改动 A（修好 1 题、碰坏 1 题）**净变化 +0.0 但退步 1 条** —— 只看总分完全看不到。三个候选改动**全部落在噪声内**（±3.3 点对 ±20 点）
- **朴素路径检查被绕过**（章 16 第 3 节）：沙箱外放一个含密钥的文件，6 种攻击手法对照 —— 朴素 `startswith` 前缀检查**放过 4 种**（`../secret.env`、`sub/../../secret.env`、符号链接、`./.././secret.env`），真实路径检查**全部拦住**。根因：`SANDBOX/../secret.env` 这个**字符串确实以 SANDBOX 开头**，但文件系统会先解析 `..`
- **隔离层级的实际差别**（章 16 第 2 节）：L0 进程内 / L1 禁内建黑名单**都能算出正确答案且耗时相同（0.039s）** —— 从输出上完全看不出差别；L2 子进程 + `RLIMIT_CPU` 1 秒 → **SIGXCPU（返回码 -24）在 1.014s 生效**；L2b 墙钟超时 1.005s。**CPU 限制与墙钟超时不能互相替代**（一个 sleep 不花 CPU 但会挂住请求）
- **策略层的同一个漏洞**（章 16 第 5 节）：我实现的策略 R1 是「path 以 `/workspace/` 开头则允许」，而 `/workspace/../../../etc/passwd` **被放行** —— 与第 3 节那个前缀检查是**同一个漏洞，只是发生在策略层**。**把策略抽成数据不会自动让它变安全**
- **7 次注入尝试全部未复现**（章 17 第 1 节）：第一轮「宣布自己是系统指令」（藏在工具返回值 / 藏在工具描述 / 控制组）→ **0/3**，模型明确识破并主动报告；第二轮「伪装成业务流程」（去掉了指令、忽略、系统这类词）→ **0/3**，模型**连提都没提**，正常总结；第三轮「动作合法只改目标」（任务是总结并发给同事，注入只把收件人换成攻击者）→ **0/2**。**合计 0/7**。我用的注入都有同一个破绽：**要求的动作与任务完全无关**（任务是总结，却要求删库）
- **外泄三要素**（章 17 第 4 节）：访问 / 通道 / 触发逐个拿掉 → 缺任何一个都不会外泄，三要素齐全则成功。**砍触发最不可靠（取决于攻击手法，第 2 章实测 6/6 到 0/6 都有）；砍访问和砍通道都是确定性的**
- **延迟由输出主导**（章 18 第 2 节）：四种组合实测 —— 短入短出（36→80）首 token 0.64s / 生成 0.59s；短入长出（42→710）1.22s / 3.80s；**长入短出（1238→80）0.88s / 0.36s**；长入长出（1245→1200）0.68s / 6.78s。**输入涨 34 倍，首 token 只从 0.64 涨到 0.88 秒，而且不单调**（1245 输入的 0.68s 比 42 输入的 1.22s 还低）。decode 速率约 **180 token/秒**，基本是常数
- **成本模型的四个比例**（章 18 第 1 节，本地计算）：8 个工具、每轮输出 300 token —— 单轮 1,257 / 单轮含工具 1,737 / 10 轮 18,090 / 30 轮 59,070。**30 轮比单轮轮数涨 30 倍，但输入侧成本涨 405 倍**；30 轮里**工具定义累计占输入侧 62%**；4 个 agent 共享背景时输入侧再乘 4、输出不乘
- **前缀缓存的收益与位置**（章 18 第 3 节，本地模拟）：分段（系统提示 400 / 工具定义 480 / 历史 3000 / 本轮 200）—— 改第 1 段命中率 **0.0%**，改第 2 段 9.8%，改第 3 段 21.6%，改第 4 段 **95.1%**。**同样是「改一处」，差别 95 个百分点**。最常见的坑（系统提示开头拼时间戳）代价最大
- **分级路由的成本对比**（章 18 第 4 节，本地计算）：1000 请求、20% 难题、强模型输入 5 倍 / 输出 20 倍 —— 全用强模型 18,000,000；规则路由 5,520,000（**省 69%**）；级联升级率 20% 反而 6,300,000（**比规则路由更贵**，因为每个请求都加了判定开销）；级联升级率 60% 是 13,500,000；并行 20,400,000。规则路由的收益上限 = 难题占比（5% 时省 82%，90% 时只省 9%）
- **审批点应该按可逆性设，不是按危险程度**（章 19 第 2 节）：7 步任务（5 步可逆、`send_email` 不可逆、`update_crm` 不可逆且高危）—— A 每个动作都问 **7 次打断 / 0 漏网**；B 只问不可逆动作 **2 次打断 / 0 漏网**；C 只问高危动作 **1 次打断 / 1 漏网（放过了 send_email）**；D 只在最后确认一次 **0 次打断 / 2 漏网**。**B 用 A 的 29% 打断次数达到同样的安全效果**
- **灰度能测出什么**（章 20 第 2 节，本地计算）：基线错误率 2% —— 要发现 **+5 个百分点**的退步需每组约 **170** 个请求；+2 点需 1,061；**+1 点需 4,243**；+0.5 点需 16,971。**所以「灰度 100 个请求没发现问题」几乎不说明任何事**。分工：灾难性故障在线上 1% 灰度看（信噪比高，样本少就够），统计退化在离线回归集看
- **上下文窗口实测**（章 7 第 1 节）：填充到 104 万 token 仍返回 200，无任何报错；停在 104 万是因为探测成本线性增长，不是到了头
- **海捞针**（章 7 第 1 节）：约 13 万 token 上下文，针放在 10% / 50% / 90% 三处，**3/3 全中**，位置效应未复现（把章 3 的否定结论边界从 2.2 万推到 13 万）
- **多轮成本曲线**（章 7 第 1 节）：12 轮对话累计输入 57,822 token，是末轮单次（8,907）的 **6.5 倍**；按模型外推 50 轮是 24.2 倍
- **写入策略对照**（章 7 第 2 节）：无差别记录 5 条，含 3 项一次性信息 + 2 项推断（把「我可能对价格敏感」写成了确凿事实）；按规则筛选 3 条，全为稳定事实
- **误召回的静默代价**（章 7 第 3 节）：注入一条不相关的「脚本必须用 Python 2.7」记忆，部署脚本输出从 npm 流程变成 python2.7 流程，**输出格式完全正常**
- **冲突裁决**（章 7 第 4 节，各跑 3 次）：两条矛盾记忆不带时间戳时结果是「中文、英文、英文」**不稳定**；带时间戳后 3/3 稳定遵循「取最新」
