**一句话结论**：流式不是一个「优化项」，它是**让长输出变得可用**的机制 —— 但它的代价是你要处理一整类「分片边界」问题。

## 为什么流式是必须的

本站第 1 章与第 18 章都实测过同一件事：**首 token 延迟远小于总时长**。所以对一个要几十秒才能输出完的响应，流式把「等待」变成了「阅读」。

对一个 agent 来说，流式还有第二个作用更重要：**你能在生成过程中看到工具调用的参数正在成形** —— 这在调试时非常有用（第 1 章第 3 节讲过 `input_json_delta` 的机制）。

## 事件序列

本站按 `VERIFY.md` 实跑时（2026-10-09）抓到的完整序列：

```
message_start → content_block_start → (ping) → content_block_delta
  → content_block_stop → message_delta → message_stop
```

几处值得注意的：

- **`ping` 事件会出现**（保持连接）—— 解析器要对未知事件类型容错，不能只处理白名单
- **`content_block_start` / `stop` 是成对的** —— 一次响应里可能有多组（文本块、工具调用块各一组）
- **`message_start` 里通常带 `usage`**；**`message_delta` 里的 usage 是累积终值**

## 一个实测确认的坑

本站实跑确认了第 1 章第 3 节那条说法：**`input_json_delta` 只带 `index`，不带 `id`。**

实测数据：9 个 delta，事件顶层的键只有 `delta` / `index` / `type` —— **没有 `id`**。而 `id` 只在 `content_block_start` 里出现一次。

**所以流式工具调用的解析必须「先记住 id，再按 index 累积参数」。** 如果你假设每个 delta 都自带 id，代码会崩或者静默拼错 —— 而那类 bug 在小输入下测不出来。

顺带一提：这条结论**在非 Anthropic 的实现上也成立了**（本站用兼容端点实测，行为一致）。这说明它是**协议形状**，不是某家的实现细节 —— 这类结论可以放心依赖。
