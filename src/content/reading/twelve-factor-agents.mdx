**一句话结论**：把 agent 当成**普通软件**来工程化 —— 大多数「AI Agent 产品」其实主要是确定性代码，只有少数地方用 LLM。

## 它为什么值得读

作者开篇的观察很直接：**「我试过所有 agent 框架」**，而**生产环境里面向客户的 agent 很少用框架** —— 大多数团队自己搭栈。他还说了一句容易被忽略的话：**很多自称「AI Agent」的产品其实没那么 agentic**，主要是确定性代码加少量 LLM 调用。

这条观察和本站第 13 章那张「后端视角对照」表是同一个判断：**别把 agent 当成新物种，它是你熟悉的软件加上一层不确定的决策点。**

## 十二条

| # | 主张 | 一句话理解 |
|---|---|---|
| 1 | Natural Language to Tool Calls | 把自然语言转成结构化工具调用，是 agent 的基本动作 |
| 2 | Own your prompts | 提示词是你的资产，不要藏在框架里 |
| 3 | Own your context window | 上下文组装要自己控制（本站第 3 章的骨架） |
| 4 | Tools are just structured outputs | 工具调用就是结构化输出，不是魔法（第 5 章） |
| 5 | Unify execution state and business state | 别把「执行到哪了」和「业务数据」拆成两套状态 |
| 6 | Launch/Pause/Resume | 用简单的 API 支持启动、暂停、恢复（第 19 章） |
| 7 | Contact humans with tool calls | 需要人时，用工具调用去联系，而不是另造一套机制 |
| 8 | Own your control flow | 控制流自己写（第 11 章的循环） |
| 9 | Compact Errors into Context | 错误要压缩后再放进上下文（第 4 章） |
| 10 | Small, Focused Agents | 小、专注的 agent 优于一个大而全的 |
| 11 | Trigger from anywhere | 从任何地方触发，去用户所在的地方 |
| 12 | Stateless reducer | agent 最好是无状态的归约器 |

## 三条最值得单独说的

**第 5 条（统一执行状态与业务状态）。** 这一条最容易被忽略，但它是分布式系统里的老问题：如果你的 agent 把「走到第几步」存在一处、把「用户数据」存在另一处，那么崩溃恢复时两者会不一致。**统一到一个状态里，恢复语义就简单了。** 本站第 11 章实测的「重复副作用」问题，根子就在这两套状态之间的窗口。

**第 7 条（用工具调用联系人类）。** 这条建议很实用：审批、澄清、确认都**走同一套工具调用机制**，而不是在 agent 循环外另接一套通知系统。好处是它们自动获得了同样的轨迹、重试、幂等语义 —— 本站第 19 章与第 22 章 capstone 都是这么做的。

**第 12 条（无状态归约器）。** 这条和第 6 条是一对：agent 的状态放在外部存储里，每次执行是「读状态 → 处理 → 写状态」。这样它才能水平扩展、才能在任意点恢复。**代价是你要设计状态结构** —— 那正是第 5 条的收益。

## 建议怎么读

不用按顺序读十二条。**建议先读第 5、7、12 条**（它们改变架构），其余按需查。每条都短，适合当检查表用 —— 写完一个 agent 之后逐条对照。

> 本篇导读覆盖原文的主张与取舍，不是逐句翻译。每条 factor 的原文都有更长的论证与代码示例。
