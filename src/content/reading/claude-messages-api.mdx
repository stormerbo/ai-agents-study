**一句话结论**：这是**最核心的一页 API 参考** —— 一次调用长什么样、有哪些字段、错误码是什么。

## 为什么它排在必读第一位

本站第 1 章第 3 节整节都在讲 Messages API 的调用形状，而那一节的依据就是这一页。原因是：**后面所有章节的代码，最终都落到这一个接口上**。

- 流式 → 同一个接口加 `stream: true`（第 1 章第 3 节）
- 工具调用 → 同一个接口加 `tools`，响应的 `content` 里多一种块（第 4 章）
- 结构化输出 → 同一套工具机制（第 5 章）
- 缓存 → 同一套 `system` 结构上加标记（第 1 章第 5 节）
- 图像/文档 → `content` 数组里换块类型（第 8 章）

**理解这一个接口，等于理解后面所有章节的公共底座。**

## 值得注意的几处结构设计

**一、`system` 是顶层字段，不是一条 message。** 这不是随手的设计 —— 它反映了「系统指令」与「对话」在语义上不同：前者是配置，后者是历史。本站第 3 章讲上下文分块时，这个区分是关键。

**二、`content` 是块（block）的数组。** 文本、图像、工具调用、工具结果都是「块」，各有 type。**这个设计让多模态与工具调用不需要另开接口。** 第 8 章讲多模态时，本质就是在换块类型。

**三、`usage` 里的三个 token 字段要一起看。** `input_tokens`、`cache_creation_input_tokens`、`cache_read_input_tokens` —— **只加第一个会低估或高估真实消耗**。本站所有 token 统计都按三者之和算。

## 一个实测提醒

本站按 `VERIFY.md` 实跑时（2026-10-09）确认了一处**跨厂商差异**：在兼容端点上，**缺 `max_tokens` 返回 200，传 `temperature` 也返回 200**；而官方端点要求 `max_tokens`、新模型会对 `temperature` 报 400。

**照这一页写的代码，在兼容端点上可能跑得「太顺」而掩盖问题。** 这是第 1 章「兼容不等于一致」那句话的具体证据。
