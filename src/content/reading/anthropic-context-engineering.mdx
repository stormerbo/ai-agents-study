**一句话结论**：上下文是**有限资源**，工程问题是「用哪些 token 换到想要的行为」——而不是「怎么把提示词写得更好」。

## 先把两个词分开

这篇文章最重要的贡献是一个区分：

| | 关心什么 |
|---|---|
| **prompt engineering** | 指令怎么写、system prompt 怎么组织 |
| **context engineering** | **整个上下文状态**：system 指令、工具定义、示例、外部数据、消息历史，以及推理过程中动态加进来的东西 |

两者的关系不是替代 —— **context engineering 是把 prompt engineering 当子集**。作者的说法是「自然演进」：单轮分类/生成任务里 prompt 确实是最大头，但 agent 是多轮、长时程的，那时你要管的是整个状态。

## 上下文由哪几块组成

文章把它拆成四块，每块都有自己的取舍：

1. **System prompt** —— 追求「**最小充分集**」。注意 minimal 不等于 short：信息要给够，但不要重复、不要自相矛盾。做法是先用最好的模型跑一个最小提示，再按实际失败的形态往上加。

2. **Tools** —— 工具定义的是「agent 能看到的动作空间」，所以工具要在**信息效率**和**行为引导**两方面都合格。作者点名了一个最常见的失败模式：**工具集臃肿** —— 覆盖太多功能、导致「该用哪个」变得模糊。判断标准很干脆：**如果一个人工程师都说不清该用哪个工具，模型更不可能说得清。**

3. **Examples** —— few-shot 仍然强烈推荐，但**不要堆边界情况**。团队常犯的错是把「所有可能的规则」都塞进去；作者建议的是**一组多样且有代表性的典型例子**。他们的比喻是：例子对模型来说就是「一图胜千言」。

4. **Message history** —— 会随轮次增长，是长任务里最先失控的一块（本站第 3 章实测过：30 轮后输入侧涨到单轮的 405 倍）。

## 一个关键的转向：从「预先塞」到「按需取」

文章描述了一个正在发生的迁移：

- **过去**：预先用 embedding 检索，把相关内容在推理前塞进上下文
- **现在**：越来越多人转向 **just-in-time** —— agent 只保留**轻量标识符**（文件路径、查询语句、链接），在需要时用工具把数据动态拉进来

**这个转向对本站读者很实用**，因为它和第 6 章那条「先量召回再加重排」是同一个思路的两面：与其猜「哪些内容将来有用」，不如让 agent 带着引用、需要时再取。作者举的例子是 Claude Code 处理大数据库 —— 它可以写针对性的查询、用 `head` / `tail` 之类命令看局部，**从不把整份数据读进上下文**。

## 长任务的三条路

文章最后一节讲长时程任务，给了三种策略（本站第 3 章第 5 节做过对照实验）：

| 策略 | 做法 | 代价 |
|---|---|---|
| **Compaction** | 把历史总结掉，用摘要继续 | 细节有损，需要设计「总结什么」 |
| **结构化笔记** | 让 agent 把关键结论写成外部文件，需要时读回 | 需要 agent 自己判断「什么值得记」 |
| **子智能体** | 把探索放在子上下文里，只把结论带回主上下文 | 多一次调用，且要设计「带回什么」 |

三者的共同点：**都不是「把上下文窗口做大」，而是「决定什么值得留在里面」。**
