### 多 agent 系统的优势

研究工作涉及开放式问题，很难提前预测所需的步骤。你无法为探索复杂主题硬编码一条固定路径，因为这一过程本质上是动态且依赖于路径的。当人们开展研究时，他们往往会基于发现不断更新自己的方法，沿着调查过程中出现的线索前行。
这种不可预测性使 AI agent 特别适合研究任务。研究要求具备随着调查展开而转向或探索周边关联的灵活性。模型必须自主运行多个轮次，基于中间发现决定要追寻哪些方向。线性的、一次性的流水线无法处理这些任务。
搜索的本质是压缩：从庞大的语料库中提炼洞见。Subagents 通过并行运行并拥有自己的 context windows 来促进压缩，同时探索问题的不同方面，然后再为 lead research agent 压缩最重要的 tokens。每个 subagent 还提供了关注点分离——不同的 tools、prompts 和探索轨迹——这减少了路径依赖，并支持彻底、独立的调查。
一旦智能达到某个阈值，multi-agent 系统就成为扩展性能的关键方式。例如，尽管在过去 100,000 年里个体人类变得更智能，但在信息时代，人类社会已经变得
指数级
更有能力，因为我们的
集体
智能和协调能力。即使是通用智能的 agents，在作为个体运行时也面临限制；agents 群体可以完成的事情要多得多。
我们的内部评估显示，multi-agent 研究系统尤其擅长涉及同时追求多个独立方向的广度优先查询。我们发现，一个以 Claude Opus 4 作为 lead agent、Claude Sonnet 4 作为 subagents 的 multi-agent 系统，在我们的内部研究评估上比单 agent Claude Opus 4 高出 90.2%。例如，当被要求找出 Information Technology S&P 500 中所有公司的董事会成员时，multi-agent 系统通过将其分解为 subagents 的任务找到了正确答案，而单 agent 系统则因缓慢、顺序的搜索而未能找到答案。
Multi-agent 系统之所以有效，主要是因为它们有助于消耗足够的 tokens 来解决问题。在我们的分析中，三个因素解释了
BrowseComp 中 95% 的性能方差
评估（测试浏览 agent 定位难以找到的信息的能力）。我们发现，token 使用量本身就能解释 80% 的方差，而工具调用次数和模型选择是另外两个解释因素。这一发现验证了我们的架构，即通过具有独立 context window 的多个 agent 来分配工作，从而为并行推理增加更多容量。最新的 Claude 模型在 token 使用上充当了巨大的效率倍增器，因为升级到 Claude Sonnet 4 所带来的性能提升，比在 Claude Sonnet 3.7 上将 token 预算翻倍还要大。多 agent 架构有效地扩展了 token 使用量，以应对超出单个 agent 能力上限的任务。
这也有一个缺点：在实践中，这些架构会快速消耗 token。在我们的数据中，agent 通常使用的 token 约为 chat 交互的 4 倍，而 multi-agent 系统使用的 token 约为 chat 的 15 倍。就经济可行性而言，multi-agent 系统需要任务的价值足够高，才能支付其性能提升带来的成本。此外，一些要求所有 agent 共享相同 context 或涉及 agent 之间大量依赖关系的领域，目前并不适合 multi-agent 系统。例如，大多数 coding 任务中真正可并行的任务比 research 更少，而且 LLM agent 目前还不擅长实时协调和委派给其他 agent。我们发现，multi-agent 系统最擅长处理涉及高度并行化、信息量超出单个 context window，以及与众多复杂工具交互的有价值任务。

### Research 的架构概览

我们的 Research 系统采用 multi-agent 架构，使用 orchestrator-worker 模式，其中 lead agent 协调整个过程，同时委派给并行运行的专门 subagent。
multi-agent 架构的实际运行方式：用户查询流经一个 lead agent，该 lead agent 创建专门的 subagent 来并行搜索不同方面。
当用户提交一个 query 时，lead agent 会对其进行分析，制定策略，并派生 subagents 来同时探索不同方面。如上图所示，subagents 通过迭代使用搜索工具来收集信息（在本例中是 2025 年 AI agent 公司），充当智能过滤器，然后向 lead agent 返回一份公司列表，以便其汇总出最终答案。
使用 Retrieval Augmented Generation (RAG) 的传统方法采用静态检索。也就是说，它们会获取一组与输入 query 最相似的 chunks，并使用这些 chunks 来生成响应。相比之下，我们的架构使用多步搜索，能够动态查找相关信息、适应新发现，并分析结果以形成高质量答案。
展示我们多 agent Research 系统完整工作流程的过程图。当用户提交一个 query 时，系统会创建一个 LeadResearcher agent，它会进入一个迭代式研究过程。LeadResearcher 首先会思考方法，并将其计划保存到 Memory 中以持久保存上下文，因为如果上下文窗口超过 200,000 tokens，它就会被截断，因此保留该计划非常重要。然后它会创建带有特定研究任务的专门 Subagents（这里展示了两个，但数量可以是任意多个）。每个 Subagent 都会独立执行 web searches，使用
interleaved thinking 来评估工具结果
，并将发现结果返回给 LeadResearcher。LeadResearcher 综合这些结果，并决定是否需要更多研究——如果需要，它可以创建额外的子 agent 或优化其策略。一旦收集到足够的信息，系统就退出研究循环，并将所有发现结果传递给 CitationAgent，后者处理文档和研究报告，以确定引用的具体位置。这确保所有主张都正确地归属于其来源。最终的研究结果连同引用一起返回给用户。

### 研究型 agent 的 prompt engineering 与评估

多 agent 系统与单 agent 系统存在关键差异，包括协调复杂性的快速增长。早期的 agent 会犯错误，比如为简单查询生成 50 个子 agent，为不存在的来源无休止地搜索网络，以及用过量的更新相互干扰。由于每个 agent 都由 prompt 引导，prompt engineering 是我们改进这些行为的主要杠杆。以下是我们学到的关于 prompting agent 的一些原则：
像你的 agent 一样思考。
要迭代 prompt，你必须理解它们的效果。为了帮助我们做到这一点，我们使用我们的
Console
以及来自我们系统的确切 prompt 和工具构建了模拟，然后逐步观察 agent 工作。这立即揭示了失败模式：agent 在已经拥有足够结果时仍继续，使用过于冗长的搜索查询，或选择错误的工具。有效的 prompting 依赖于建立对 agent 的准确心智模型，这可以让最有影响的更改变得显而易见。
教 orchestrator 如何委派。
在我们的系统中，lead agent 将查询分解为子任务，并向 subagent 描述这些子任务。每个 subagent 都需要一个目标、一种输出格式、关于所用工具和来源的指导，以及清晰的任务边界。没有详细的任务描述，agent 就会重复工作、留下缺口，或找不到必要的信息。我们最初允许 lead agent 给出简单、简短的指令，例如“研究半导体短缺”，但发现这些指令往往过于模糊，以至于 subagent 误解了任务，或执行了与其他 agent 完全相同的搜索。例如，一个 subagent 探究了 2021 年汽车芯片危机，而另外 2 个则重复工作，调查当前的 2025 年供应链，缺乏有效的分工。

让投入与查询复杂度相匹配。

Agent 难以判断不同任务所需的适当投入，因此我们在 prompt 中嵌入了伸缩规则。简单的事实查找只需 1 个 agent 和 3-10 次工具调用，直接比较可能需要 2-4 个 subagent，每个进行 10-15 次调用，而复杂研究可能使用 10 个以上职责明确划分的 subagent。这些明确的准则帮助 lead agent 高效分配资源，并防止对简单查询过度投入——这是我们早期版本中一种常见的失败模式。

工具的设计与选择至关重要。

Agent 与工具的接口，其重要性不亚于人机接口。使用正确的工具是高效的——通常，它是绝对必要的。例如，一个 agent 在网上搜索只存在于 Slack 中的上下文，从一开始就注定失败。借助
MCP servers
当赋予模型访问外部工具的能力时，这个问题会更加复杂，因为 agent 会遇到描述质量参差不齐的未见过的工具。我们给 agent 提供了明确的启发式规则：例如，先检查所有可用工具，将工具使用与用户意图匹配，使用网络搜索进行广泛的外部探索，或优先选择专用工具而非通用工具。糟糕的工具描述可能会让 agent 走上完全错误的道路，因此每个工具都需要有明确的用途和清晰的描述。
让 agent 自我改进
。我们发现 Claude 4 模型可以成为出色的 prompt 工程师。当给定一个 prompt 和一种失败模式时，它们能够诊断 agent 失败的原因并提出改进建议。我们甚至创建了一个工具测试 agent——当给定一个有缺陷的 MCP 工具时，它会尝试使用该工具，然后重写工具描述以避免失败。通过对该工具进行数十次测试，这个 agent 发现了关键的细微差别和 bug。这一改进工具易用性的流程使未来使用新描述的 agent 的任务完成时间减少了 40%，因为它们能够避免大多数错误。
先宽后窄。
搜索策略应当模仿专家级的人类研究：在深入细节之前先探索整体格局。Agent 通常默认使用过长、过于具体的查询，导致返回结果很少。我们通过提示 agent 从简短、宽泛的查询开始，评估可用的内容，然后逐步缩小范围来抵消这一倾向。
引导思考过程。
Extended thinking mode
会让 Claude 输出额外的 token，形成可见的思考过程，它可以作为一个可控的暂存器。Lead agent 使用思考来规划其方法，评估哪些工具适合任务，确定查询复杂度和 subagent 数量，并定义每个 subagent 的角色。我们的测试表明，extended thinking 改善了指令遵循、推理和效率。Subagent 也会进行规划，然后使用
interleaved thinking
在工具结果之后评估质量、识别差距并优化其下一个 query。这使 subagent 能更有效地适应任何任务。
并行工具调用改变了速度与性能。
复杂的研究任务自然会涉及探索许多来源。我们早期的 agent 执行顺序搜索，速度慢得令人痛苦。为了提升速度，我们引入了两种并行化方式：(1) lead agent 并行启动 3-5 个 subagent，而不是串行启动；(2) subagent 并行使用 3+ 个工具。这些改动将复杂查询的研究时间最多缩短了 90%，使 Research 能在几分钟而不是几小时内完成更多工作，同时覆盖的信息比其他系统更多。
我们的 prompting 策略侧重于灌输良好的启发式方法，而不是僵化的规则。我们研究了熟练的人类如何开展研究任务，并将这些策略编码进我们的 prompt 中——例如将困难问题分解为更小的任务、仔细评估来源质量、根据新信息调整搜索方法，以及识别何时应专注于深度（详细调查一个主题）与广度（并行探索许多主题）。我们还通过设置明确的 guardrail 来主动减轻意外副作用，以防止 agent 失控。最后，我们专注于一个带有可观测性和测试用例的快速迭代循环。

### agent 的有效评估

好的评估对于构建可靠的 AI 应用至关重要，agent 也不例外。然而，评估 multi-agent 系统带来了独特的挑战。传统评估往往假设 AI 每次都遵循相同的步骤：给定输入 X，系统应沿着路径 Y 生成输出 Z。但 multi-agent 系统并非如此运作。即使起点完全相同，agent 也可能沿着完全不同的有效路径达成目标。一个 agent 可能搜索三个来源，而另一个搜索十个，或者它们可能使用不同的工具找到同一个答案。由于我们并不总是知道正确的步骤是什么，通常就不能仅仅检查 agent 是否遵循了我们事先规定的“正确”步骤。相反，我们需要灵活的评估方法，判断 agent 是否在遵循合理过程的同时达成了正确的结果。
立即用小样本开始评估
。在 agent 开发的早期，变更往往会产生巨大的影响，因为有大量容易摘取的果实。一次 prompt 微调可能将成功率从 30% 提升到 80%。在效应量如此之大的情况下，只需几个测试用例就能发现变化。我们从一组约 20 个代表真实使用模式的查询开始。测试这些查询常常让我们能够清楚地看到变更的影响。我们经常听说 AI 开发团队推迟创建 eval，因为他们认为只有包含数百个测试用例的大规模 eval 才有用。然而，最好立即用几个例子开始小规模测试，而不是推迟到能够构建更全面的 eval 时再开始。
LLM-as-judge 评估如果做得好，就能规模化。
研究输出很难通过程序化方式评估，因为它们是自由形式的文本，且很少只有一个正确答案。LLM 天然适合为输出评分。我们使用了一个 LLM judge，根据 rubric 中的标准对每个输出进行评估：事实准确性（claim 是否与来源匹配？）、引用准确性（引用的来源是否与 claim 匹配？）、完整性（是否涵盖了所有要求的方面？）、来源质量（是否使用了 primary sources 而非质量较低的 secondary sources？）以及工具效率（是否以合理的次数使用了正确的工具？）。我们尝试了多个 judge 来评估每个组成部分，但发现使用单个 prompt 进行一次 LLM 调用，输出 0.0-1.0 的分数和 pass-fail 等级，是最一致的，并且与人类判断最为吻合。当 eval test cases
确实
有明确答案时，这种方法尤其有效，我们可以使用 LLM judge 简单地检查答案是否正确（即，它是否准确列出了研发预算最高的前 3 大制药公司？）。使用 LLM 作为 judge 使我们能够可扩展地评估数百个输出。
人工评估能捕捉到自动化遗漏的问题。
测试 agent 的人会发现 eval 遗漏的 edge cases。这些包括对不寻常查询的幻觉答案、系统故障或微妙的来源选择偏差。在我们的案例中，人工测试者注意到，我们早期的 agent 一直选择 SEO 优化的内容农场，而不是权威但排名较低的来源，如学术 PDF 或个人博客。将来源质量启发式规则添加到我们的 prompt 中有助于解决这个问题。即使在自动化评估的世界中，手动测试仍然至关重要。
Multi-agent 系统具有涌现行为，这些行为并非由特定编程产生。例如，对 lead agent 的小改动可能会以不可预测的方式改变 subagents 的行为。成功需要理解交互模式，而不仅仅是单个 agent 的行为。因此，这些 agent 的最佳 prompts 不只是严格的指令，而是协作框架，用于定义分工、问题解决方法和工作量预算。要做到这一点，依赖于精心的 prompt 设计和 tool 设计、扎实的启发式方法、可观测性以及紧密的反馈循环。

### 生产可靠性与工程挑战

在传统软件中，一个 bug 可能会破坏某个功能、降低性能或导致服务中断。在 agentic systems 中，微小的改动会级联成巨大的行为变化，这使得为必须在长时间运行的进程中维护状态的复杂 agent 编写代码变得异常困难。
Agents 是有状态的，错误会累积。
Agents 可以长时间运行，在多次 tool calls 之间维护状态。这意味着我们需要持久地执行代码，并在此过程中处理错误。如果没有有效的缓解措施，微小的系统故障对 agents 来说可能是灾难性的。当错误发生时，我们不能只是从头重启：重启代价高昂，并且会让用户感到沮丧。相反，我们构建的系统可以从 agent 发生错误时所处的位置恢复。我们还利用模型的智能来优雅地处理问题：例如，让 agent 知道某个 tool 正在失败，并让它进行调整，效果出奇地好。我们将基于 Claude 构建的 AI agents 的适应性与确定性保障措施结合起来，例如重试逻辑和定期检查点。
调试受益于新的方法。
Agent 会做出动态决策，并且即使 prompt 完全相同，在多次运行之间也是非确定性的。这使调试变得更加困难。例如，用户会报告 agent “找不到明显的信息”，但我们无法看出原因。是 agent 使用了糟糕的搜索查询？选择了劣质来源？遇到了工具故障？添加完整的生产环境 tracing 使我们能够诊断 agent 失败的原因，并系统地修复问题。除了标准的 observability 之外，我们还监控 agent 的决策模式和交互结构——所有这些都不监控单个对话的内容，以维护用户隐私。这种高层次的 observability 帮助我们诊断根本原因、发现意外行为，并修复常见故障。
部署需要仔细协调。
Agent 系统是由 prompt、工具和执行逻辑组成的高度有状态的网络，几乎持续运行。这意味着每当我们部署更新时，agent 可能处于其流程的任何位置。因此，我们需要防止我们善意的代码更改破坏现有的 agent。我们无法同时将每个 agent 更新到新版本。相反，我们使用
rainbow deployments
来避免中断正在运行的 agent，通过逐渐将流量从旧版本转移到新版本，同时保持两者同时运行。
同步执行会造成瓶颈。
目前，我们的 lead agents 同步执行 subagents，等待每组 subagents 完成后再继续。这简化了协调，但在 agents 之间的信息流中造成了瓶颈。例如，lead agent 无法引导 subagents，subagents 无法协调，并且整个系统可能因等待单个 subagent 完成搜索而阻塞。异步执行将支持额外的并行性：agents 并发工作，并在需要时创建新的 subagents。但这种异步性在结果协调、状态一致性以及跨 subagents 的错误传播方面增加了挑战。随着模型能够处理更长、更复杂的研究任务，我们预期性能收益将证明这种复杂性是合理的。

### 结论

在构建 AI agents 时，最后一英里往往变成旅程的大部分。能在开发者机器上运行的代码库需要大量工程工作才能成为可靠的生产系统。agentic 系统中错误的复合性质意味着，对传统软件而言很小的问题可能完全使 agents 脱轨。一个步骤失败可能导致 agents 探索完全不同的轨迹，从而导致不可预测的结果。出于本文所述的所有原因，原型与生产之间的差距往往比预期更大。
尽管存在这些挑战，多 agent 系统已被证明对开放式研究任务很有价值。用户表示，Claude 帮助他们发现了未曾考虑过的商业机会、梳理了复杂的医疗保健选择、解决了棘手的技术 bug，并通过发现他们独自无法找到的研究关联，节省了长达数天的工作时间。经过精心工程化、全面测试、注重细节的 prompt 与工具设计、稳健的运营实践，以及研究、产品和工程团队之间在对当前 agent 能力有深刻理解基础上的紧密协作，多 agent 研究系统能够可靠地大规模运行。我们已经看到这些系统正在改变人们解决复杂问题的方式。

## 附录

以下是一些关于多 agent 系统的额外杂项提示。
对在多轮中改变状态的 agent 进行最终状态评估。
评估那些在多轮对话中修改持久状态的 agent 会带来独特的挑战。与只读研究任务不同，每个动作都可能改变后续步骤的环境，从而产生传统评估方法难以处理的依赖关系。我们发现，聚焦于最终状态评估而非逐轮分析是有效的做法。与其判断 agent 是否遵循了特定流程，不如评估它是否达成了正确的最终状态。这种方法承认 agent 可能会找到通往同一目标的替代路径，同时仍能确保它们交付预期的结果。对于复杂的工作流，应把评估拆分为离散的检查点，在这些检查点上应当已经发生了特定的状态变化，而不是试图验证每一个中间步骤。
长时程对话管理。
生产环境中的 agent 常常参与跨越数百轮的对话，这要求谨慎的上下文管理策略。随着对话延长，标准上下文窗口变得不够用，因此需要智能压缩和记忆机制。我们实现了一些模式：agent 会总结已完成的工作阶段，并在继续处理新任务之前将关键信息存入外部记忆。当接近上下文限制时，agent 可以生成具有干净上下文的全新 subagent，同时通过谨慎的交接保持连续性。此外，它们可以从记忆中检索已存储的上下文，比如研究计划，而不是在达到上下文限制时丢失先前的工作。这种分布式方法可防止上下文溢出，同时在扩展交互中保持对话连贯性。
Subagent 输出到文件系统，以尽量减少“传话游戏”。
Direct subagent 输出在某些类型的结果上可以绕过 main coordinator，从而同时提升 fidelity 和 performance。与其要求 subagents 将所有内容都通过 lead agent 来传递，不如实现 artifact systems，让 specialized agents 能够创建独立持久化的输出。Subagents 调用 tools 将其工作存储到外部系统中，然后把轻量级的 references 传回 coordinator。这可以防止多阶段处理过程中的信息丢失，并减少因在 conversation history 中复制大型输出而产生的 token 开销。对于代码、报告或数据可视化等结构化输出，这种模式效果尤其好，因为此时 subagent 的 specialized prompt 产生的结果要优于经由通用 coordinator 过滤后的结果。
