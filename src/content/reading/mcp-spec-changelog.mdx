**一句话结论**：MCP 的**破坏性修订**都记在这一页 —— 接 MCP 之前先看它，能省掉一整类「看起来能跑但行为不对」的排查。

## 为什么这一页比规范正文更该先读

MCP 是一个**跨进程协议**（本站第 14 章讲过：工具定义在不同进程之间传递，双方的假设必须对齐）。协议一旦修订，**「兼容」与「不兼容」的差别通常不会在编译期暴露** —— 它表现为运行时的行为差异。

而这一页就是所有这类差异的清单。它的结构本身就说明了问题：

- **Major changes** —— 破坏性，你的服务端或客户端必须改
- **Minor changes** —— 向后兼容的新增
- **Deprecated** —— 还能用但会消失
- **Other schema changes / Governance** —— 结构性的小改动与流程变更

**养成习惯：升级 MCP 相关依赖前，先翻 Major changes。**

## 2026-07-28 这一版的意义

本站第 14 章复核时记录过：**MCP 文档已进入 2026-07-28 版本，且该版本是破坏性修订。** 这正是「链接还在不代表内容还对」的一个实例 —— 当时链接是可达的，但内容已经变了。

这条经验值得单独记住：**协议类文档的「可达性」与「适用性」是两回事。** 版本号写在 URL 里，一旦你不注意路径里的日期，就会照着旧版本写代码。

## 建议怎么读

**不要通读。** 它的用法是查表：

1. 接入或升级 MCP 前，扫一遍 **Major changes**
2. 遇到「行为和我预期不一致」时，回来查 **Deprecated** 与 **Other schema changes**
3. **顺手核对 URL 里的版本日期**是不是你以为的那一版
