在过去一年中，我们与数十个跨行业构建大语言模型（LLM）agents 的团队合作过。始终如一的是，最成功的实现没有使用复杂的框架或专门的库。相反，他们使用简单、可组合的模式进行构建。

在本文中，我们分享从与客户合作以及自己构建 agents 中学到的经验，并为开发者提供关于构建有效 agents 的实用建议。

## 什么是 agents？

“Agent”可以有多种定义方式。一些客户将 agents 定义为完全自主的系统，能够在较长时间内独立运行，使用各种工具来完成复杂任务。其他人用这个词来描述更规范化的实现，即遵循预定义 workflows 的实现。在 Anthropic，我们将所有这些变体归类为 agentic systems，但会在 workflows 和 agents 之间划出重要的架构区分：

Workflows 是 LLMs 和工具通过预定义代码路径进行编排的系统。

另一方面，Agents 是 LLMs 动态指导自己的过程和工具使用，并保持对如何完成任务的控制权的系统。

下面，我们将详细探讨这两种类型的 agentic systems。在附录 1（“实践中的 Agents”）中，我们描述了客户在使用这类系统时发现特别有价值的两个领域。

## 何时（以及何时不）使用 agents

在使用 LLM 构建应用程序时，我们建议尽可能寻找最简单的解决方案，只在需要时才增加复杂度。这可能意味着根本不构建 agentic 系统。Agentic 系统通常以延迟和成本换取更好的任务表现，你应该考虑这种权衡何时合理。
当确实需要更高复杂度时，workflows 为定义明确的任务提供可预测性和一致性，而当需要大规模灵活性和模型驱动的决策时，agents 则是更好的选择。然而，对许多应用程序而言，用 retrieval 和 in-context examples 优化单个 LLM 调用通常就足够了。

## 构建块、workflows 和 agents

在本节中，我们将探讨我们在生产环境中见过的 agentic 系统的常见模式。我们将从我们的基础构建块——augmented LLM——开始，并逐步增加复杂度，从简单的组合式 workflows 到自主 agents。

### 构建块：Augmented LLM

agentic 系统的基本构建块是一个 LLM，并辅以 retrieval、tools 和 memory 等增强功能。我们当前的模型可以主动使用这些能力——生成自己的搜索查询、选择合适的 tools，并确定要保留哪些信息。
增强后的 LLM
我们建议重点关注实现中的两个关键方面：根据你的具体用例定制这些能力，并确保它们为你的 LLM 提供一个易于使用且文档完善的 interface。虽然实现这些增强功能有很多方式，但一种途径是通过我们最近发布的
Model Context Protocol
，它允许开发者通过简单的
client implementation
接入不断增长的第三方 tools 生态。
在本文余下部分，我们将假设每次 LLM 调用都可以访问这些增强能力。

### 工作流：Prompt chaining

Prompt chaining 将任务分解为一系列步骤，其中每次 LLM 调用都会处理上一次调用的输出。你可以在任何中间步骤上添加程序化检查（见下图中的 “gate”），以确保流程仍在正轨上。
Prompt chaining 工作流
何时使用此工作流：
此工作流非常适合任务可以轻松且清晰地分解为固定子任务的情况。其主要目标是通过让每次 LLM 调用成为更简单的任务，以延迟换取更高的准确性。
Prompt chaining 有用的示例：
生成营销文案，然后将其翻译成另一种语言。
编写文档大纲，检查大纲是否满足某些标准，然后基于大纲编写文档。

### 工作流：Routing

Routing 会对输入进行分类，并将其导向专门的后续任务。此工作流允许关注点分离，并构建更专门的 prompts。如果没有此工作流，针对一种输入进行优化可能会损害其他输入的性能。
Routing 工作流
何时使用此工作流：
Routing 适用于复杂任务，其中存在更适合单独处理的不同类别，并且分类可以由 LLM 或更传统的分类模型/算法准确处理。
Routing 有用的示例：
将不同类型的客户服务查询（一般问题、退款请求、技术支持）引导到不同的下游流程、prompts 和工具中。
将简单/常见问题路由到更小、成本高效的模型（如 Claude Haiku 4.5），将困难/不寻常问题路由到能力更强的模型（如 Claude Sonnet 4.5），以优化最佳性能。

### 工作流：Parallelization

LLM 有时可以同时处理一个任务，并以编程方式聚合它们的输出。这种工作流，即 parallelization，表现为两种关键变体：
Sectioning
：将任务分解为并行运行的独立子任务。
Voting：
多次运行同一任务以获得多样化的输出。
parallelization 工作流
何时使用此工作流：
当划分的子任务可以并行化以提高速度，或者需要多个视角或尝试以获得更高置信度的结果时，parallelization 是有效的。对于具有多个考虑因素的复杂任务，当每个考虑因素都由单独的 LLM 调用处理时，LLM 通常表现更好，从而能够将注意力集中在每个特定方面。
Parallelization 有用的示例：
Sectioning
：
实现 guardrails，其中一个模型实例处理用户查询，而另一个筛选它们是否存在不当内容或请求。这往往比让同一个 LLM 调用同时处理 guardrails 和核心响应表现得更好。
自动化 evals 以评估 LLM 性能，其中每个 LLM 调用评估模型在给定 prompt 上性能的不同方面。
Voting
：
审查一段代码的漏洞，其中几个不同的 prompts 审查代码，并在发现问题时标记代码。
评估给定内容是否不当，使用多个 prompt 评估不同方面，或要求不同的投票阈值以平衡假阳性和假阴性。

### 工作流：Orchestrator-workers

在 orchestrator-workers 工作流中，一个中央 LLM 动态分解任务，将其委派给 worker LLM，并综合它们的结果。
Orchestrator-workers 工作流
何时使用此工作流：
此工作流非常适合无法预测所需子任务的复杂任务（例如在编码中，需要更改的文件数量以及每个文件中更改的性质很可能取决于任务）。虽然它在拓扑上相似，但与并行化的关键区别在于其灵活性——子任务不是预定义的，而是由 orchestrator 根据具体输入确定的。
orchestrator-workers 有用的示例：
每次对多个文件进行复杂更改的编码产品。
涉及从多个来源收集和分析信息以寻找可能相关信息的研究任务。

### 工作流：Evaluator-optimizer

在 evaluator-optimizer 工作流中，一个 LLM 调用生成响应，而另一个在循环中提供评估和反馈。
Evaluator-optimizer 工作流
何时使用此工作流：
当我们有明确的评估标准，并且迭代改进能提供可衡量的价值时，此工作流特别有效。良好契合的两个标志是：第一，当人类阐明其反馈时，LLM 响应能够明显改进；第二，LLM 能够提供此类反馈。这类似于人类作者在制作精炼文档时可能经历的迭代写作过程。
evaluator-optimizer 有用的示例：
文学翻译，其中存在翻译 LLM 最初可能无法捕捉的细微差别，但 evaluator LLM 可以提供有用的批评。
需要多轮搜索和分析以收集全面信息的复杂搜索任务，由评估者判断是否有必要进行进一步搜索。

### Agents

随着 LLM 在关键能力上的成熟——理解复杂输入、进行推理和规划、可靠地使用工具以及从错误中恢复——agents 正在生产环境中出现。Agents 的工作始于人类用户的命令或与之进行的交互式讨论。一旦任务明确，agents 就会独立进行规划和操作，并可能返回人类处获取更多信息或判断。在执行过程中，agents 在每一步从环境获取“ground truth”（例如工具调用结果或代码执行）以评估其进展至关重要。Agents 随后可以在检查点或遇到阻塞时暂停以获取人类反馈。任务通常在完成后终止，但包含停止条件（例如最大迭代次数）以保持控制也很常见。
Agents 可以处理复杂任务，但其实现通常很直接。它们通常只是 LLM 在循环中基于环境反馈使用工具。因此，清晰且深思熟虑地设计 toolsets 及其文档至关重要。我们在附录 2（“Prompt Engineering your Tools”）中进一步阐述了工具开发的最佳实践。
Autonomous agent
何时使用 agents：
Agents 可用于开放式问题，这些问题难以或无法预测所需步骤数，且无法硬编码固定路径。LLM 可能会运行许多轮次，你必须对其决策有一定程度的信任。Agents 的自主性使其非常适合在可信环境中扩展任务。
Agents 的自主性意味着更高的成本，以及错误累积的可能性。我们建议在沙盒环境中进行大量测试，并配备适当的 guardrails。

## 组合并定制这些模式

这些构建块并非规定性的。它们是常见模式，开发者可以根据不同用例对其进行塑造和组合。与任何 LLM 功能一样，成功的关键在于衡量性能并迭代实现。再重复一次：只有当复杂性能够被证明可以改善结果时，你才应该考虑添加它。

## 总结

在 LLM 领域取得成功，并不在于构建最复杂的系统。而在于构建适合你需求的
正确
系统。从简单 prompt 开始，通过全面评估对其进行优化，并且只有当更简单的解决方案不足时，才添加多步骤 agentic 系统。
在实现 agent 时，我们尽量遵循三个核心原则：
在 agent 的设计中保持
简单性
。
通过明确展示 agent 的规划步骤来优先保证
透明性
。
通过完善的工具
文档和测试
，精心设计你的 agent-computer interface（ACI）。
框架可以帮助你快速开始，但在进入生产环境时，不要犹豫，减少抽象层并使用基础组件进行构建。通过遵循这些原则，你可以创建不仅强大，而且可靠、可维护，并受用户信任的 agent。

## 附录 1：实践中的 Agent

我们与客户的合作揭示了 AI agents 的两个特别有前景的应用，它们展示了上文讨论的模式的实践价值。这两个应用都说明，对于既需要对话又需要行动、具有明确成功标准、支持反馈循环并整合有意义的人类监督的任务，agents 如何创造最大价值。

### A. 客户支持

客户支持将熟悉的聊天机器人界面与通过工具集成增强的能力结合起来。这天然适合更开放式的 agents，因为：
客户支持交互自然遵循对话流程，同时需要访问外部信息和执行动作；
可以集成工具来拉取客户数据、订单历史和知识库文章；
诸如发放退款或更新工单之类的动作可以通过编程方式处理；以及
成功可以通过用户定义的解决结果清晰衡量。
几家公司已经通过基于用量的定价模型证明了这种方法的可行性，这些模型只对成功解决收费，显示出对其 agents 有效性的信心。

### B. 编码 agents

软件开发领域已经展现出 LLM 功能的显著潜力，能力从代码补全演进到自主问题解决。agents 特别有效，因为：
代码解决方案可以通过自动化测试验证；
agents 可以利用测试结果作为反馈来迭代解决方案；
问题空间定义明确且结构化；以及
输出质量可以客观衡量。
在我们自己的实现中，agents 现在可以在
SWE-bench Verified
benchmark 中仅根据 pull request 描述解决真实的 GitHub issues。然而，尽管自动化测试有助于验证功能，人工审查对于确保解决方案符合更广泛的系统需求仍然至关重要。

## 附录 2：Prompt engineering 你的工具

无论你在构建哪种 agentic system，tools 都很可能是你的 agent 的重要组成部分。
Tools
使 Claude 能够与外部服务和 API 交互，方法是在我们的 API 中指定它们的确切结构和定义。当 Claude 响应时，如果它打算调用某个 tool，就会在 API 响应中包含一个
tool use block
。Tool 定义和规格应当获得与你的整体 prompts 同等的 prompt engineering 关注度。在这篇简短的附录中，我们描述如何对你的 tools 进行 prompt engineering。
指定同一个动作往往有多种方式。例如，你可以通过写一个 diff 来指定文件编辑，也可以通过重写整个文件来指定。对于结构化输出，你可以把代码放在 markdown 里返回，也可以放在 JSON 里返回。在软件工程中，这类差异只是形式上的，可以无损地从一种转换到另一种。然而，有些格式对 LLM 来说比其他格式难写得多。写 diff 需要在新代码写出来之前就知道 chunk header 中有多少行在变化。把代码放在 JSON 里（与 markdown 相比）需要对换行和引号做额外的转义。
我们关于如何选择 tool 格式的建议如下：
给模型足够的 tokens 去“思考”，以免它把自己写进死胡同。
让格式尽量接近模型在互联网文本中自然见过的样子。
确保没有格式上的“开销”，例如必须准确统计数千行代码，或者对它写出的任何代码做字符串转义。
一条经验法则是：想一想在 human-computer interfaces（HCI）上投入了多少精力，并计划在创建良好的
agent
-computer interfaces（ACI）上投入同样多的精力。以下是一些关于如何做到这一点的思考：
设身处地为模型着想。根据描述和参数，使用这个工具的方式是否显而易见，还是说你需要仔细思考一番？如果是后者，那么对模型来说很可能也是如此。一个好的工具定义通常包含示例用法、边界情况、输入格式要求，以及与其他工具的明确界限。
你如何更改参数名称或描述，让事情变得更加显而易见？把这想象成在为你团队中的初级开发者写一份出色的 docstring。当使用许多相似工具时，这一点尤其重要。
测试模型如何使用你的工具：在我们的
workbench
中运行许多示例输入，看看模型会犯哪些错误，并迭代改进。
对你的工具进行
Poka-yoke
。更改参数，让犯错变得更难。
在为
SWE-bench
构建我们的 agent 时，我们实际上花在优化工具上的时间比花在整个 prompt 上的时间还多。例如，我们发现，当 agent 移出根目录后，模型会在使用相对文件路径的工具上犯错。为了解决这个问题，我们更改了工具，使其始终要求绝对文件路径——结果我们发现模型完美地使用了这种方法。
