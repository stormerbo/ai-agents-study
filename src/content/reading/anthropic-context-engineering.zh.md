Context 是 AI agent 的关键但有限的资源。在这篇文章中，我们探讨有效策展和管理驱动它们的 context 的策略。
在 prompt engineering 成为应用 AI 关注焦点几年之后，一个新术语开始崭露头角：
context engineering
。使用语言模型进行构建，正越来越多地从为 prompt 寻找合适的词语和短语，转向回答一个更广泛的问题：“什么样的 context 配置最有可能生成我们模型期望的行为？”
Context
指的是从大型语言模型（LLM）采样时所包含的 token 集合。这里的
engineering
问题是在 LLM 固有限制下优化这些 token 的效用，以持续实现期望的结果。有效驾驭 LLM 通常需要
在 context 中思考
——换句话说：考虑 LLM 在任意给定时刻可用的整体状态，以及该状态可能产生哪些潜在行为。
在这篇文章中，我们将探讨正在兴起的 context engineering 艺术，并为构建可引导、有效的 agent 提供一个更精炼的心智模型。

## Context engineering 与 prompt engineering

在 Anthropic，我们将 context engineering 视为 prompt engineering 的自然演进。Prompt engineering 指的是编写和组织 LLM 指令以获得最佳结果的方法（参见
我们的文档
以了解概览和有用的 prompt engineering 策略）。
Context engineering
指的是在 LLM 推理期间策展和维护最佳 token（信息）集合的策略，包括除 prompt 之外可能进入其中的所有其他信息。
在早期使用 LLM 进行工程的阶段，prompting 是 AI 工程工作中最大的组成部分，因为在日常聊天交互之外，大多数用例都需要针对一次性分类或文本生成任务优化的 prompt。正如这个术语所暗示的，prompt engineering 的主要关注点是如何编写有效的 prompt，尤其是 system prompt。然而，随着我们朝着工程化更强大的 agent 迈进，这些 agent 需要在多轮推理和更长的时间跨度上运行，我们需要管理整个上下文状态（system instructions、tools、
Model Context Protocol
（MCP）、external data、message history 等）的策略。
一个在循环中运行的 agent 会生成越来越多
可能
与下一轮推理相关的数据，而这些信息必须被循环式地精炼。Context engineering 是
艺术与科学
的结合，它负责从那个不断演化的可能信息宇宙中，策划哪些内容将进入有限的上下文窗口。
与编写 prompt 这种离散任务相比，context engineering 是迭代式的，每当我们决定要向模型传递什么时，策划阶段都会发生。

## 为什么 context engineering 对构建强大的 agent 很重要

尽管 LLM 速度很快，并且能够管理越来越大量的数据，但我们观察到，LLM 和人类一样，会在某个时刻失去专注或陷入混乱。关于 needle-in-a-haystack
式基准测试的研究揭示了
context rot
这一概念：随着上下文窗口中的 token 数量增加，模型从该上下文中准确召回信息的能力会下降。
虽然有些模型表现出的退化比另一些更平缓，但这一特征会在所有模型中出现。因此，必须将上下文视为一种有限资源，其边际回报递减。就像人类一样，人类的
working memory 容量有限
, LLM 拥有一个“注意力预算”，在解析大量上下文时会动用这一预算。每引入一个新的 token 都会以某种程度消耗这一预算，从而增加了精心策划可供 LLM 使用的 token 的必要性。
这种注意力稀缺源于 LLM 的架构约束。LLM 基于
transformer 架构
，该架构使每个 token 都能
关注到整个上下文中的每一个其他 token
。对于 n 个 token，这会产生 n² 个成对关系。
随着上下文长度的增加，模型捕捉这些成对关系的能力会被拉伸到极限，从而在上下文大小和注意力焦点之间形成一种天然的张力。此外，模型从训练数据分布中发展出它们的注意力模式，而在这些分布中，较短的序列通常比较长的序列更常见。这意味着模型对上下文范围的依赖关系经验更少，专门用于处理这类依赖关系的参数也更少。
像
位置编码插值
这样的技术，通过将更长的序列适配到最初训练的较小上下文，使模型能够处理更长的序列，不过在 token 位置理解上会有一定退化。这些因素造成的是一种性能梯度，而不是一道硬性悬崖：模型在较长的上下文中仍然具有很强能力，但与在较短上下文中的表现相比，在信息检索和长距离推理方面可能会表现出精度下降。
这些现实意味着，深思熟虑的上下文工程对于构建有能力的 agent 至关重要。

## 有效上下文的解剖结构

鉴于 LLM 受限于有限的注意力预算，
好的
上下文工程意味着找到
尽可能小
的一组高信号 token，以最大化某种期望结果的可能性。实施这一实践说起来容易做起来难，但在下一节中，我们将概述这一指导原则在上下文的不同组成部分中在实践中意味着什么。
系统提示
应当极其清晰，并使用简单、直接的语言，把想法呈现在对 agent 来说恰当的
altitude
上。恰当的 altitude 是两种常见失败模式之间的 Goldilocks zone。在一个极端，我们看到工程师在 prompt 中硬编码复杂、脆弱的逻辑，以引出精确的 agentic 行为。这种做法会造成脆弱性，并随着时间推移增加维护复杂度。在另一个极端，工程师有时提供含糊、高层次的指导，未能给 LLM 提供关于期望输出的具体信号，或者错误地假设存在共享上下文。最佳 altitude 取得一种平衡：既足够具体以有效引导行为，又足够灵活以向模型提供强有力的启发式方法来引导行为。
在光谱的一端，我们看到脆弱的 if-else 硬编码 prompt；在另一端，我们看到过度泛化或错误假设共享上下文的 prompt。
我们建议将 prompt 组织成不同的部分（例如
<background_information>
、
<instructions>
、

## Tool guidance

、

## Output description

等），并使用 XML tagging 或 Markdown headers 等技术来划分这些部分，尽管随着模型能力增强，prompt 的确切格式可能变得不那么重要。
无论你决定如何组织 system prompt，你都应当力求提供最小信息集，以完整概述你期望的行为。（注意，minimal 并不一定意味着短；你仍然需要预先给 agent 足够的信息，以确保它遵循期望的行为。）最好先用可用的最佳模型测试一个 minimal prompt，看看它在你的任务上表现如何，然后根据初始测试中发现的失败模式，添加清晰的 instructions 和 examples 来提升性能。
Tools
允许 agent 在其环境中运行，并在工作时引入新的、额外的上下文。由于 tool 定义了 agent 与其信息/行动空间之间的契约，因此 tool 必须提升效率，这一点极其重要——既要通过返回 token 高效的信息，也要鼓励高效的 agent 行为。
在
Writing tools for AI agents – with AI agents
中，我们讨论了如何构建被 LLM 良好理解、且功能重叠最少的 tool。类似于设计良好的代码库中的函数，tool 应当是自包含的、对错误健壮的，并且就其预期用途而言极其清晰。输入参数同样应当具有描述性、无歧义，并发挥模型的固有优势。
我们看到的最常见失败模式之一，是臃肿的 tool 集合覆盖了过多功能，或导致关于该使用哪个 tool 的模糊决策点。如果人类工程师都无法明确说出在给定情境下应当使用哪个 tool，就不能指望 AI agent 做得更好。正如我们稍后将讨论的，为 agent 精心策划一套最小可行 tool 集合，也可以带来更可靠的维护，以及在长交互中对上下文的修剪。
提供示例，也称为 few-shot prompting，是一种众所周知的最佳实践，我们继续强烈建议这样做。然而，团队常常会把一长串边缘情况塞进 prompt，试图阐明 LLM 在特定任务中应当遵循的每一条可能规则。我们不推荐这样做。相反，我们建议努力精心策划一组多样化的、典型的示例，以有效展现 agent 的预期行为。对于 LLM 而言，示例就是“一图胜千言”中的“图”。
我们针对上下文不同组成部分（system prompts
、
tools
、
examples
、
message history 等）的总体指导是：要深思熟虑，让你的上下文既有信息量，又保持紧凑。现在让我们深入探讨在运行时动态检索上下文。

## 上下文检索与 agentic 搜索

在《Building effective AI agents》一文中，我们强调了基于 LLM 的 workflow 与 agent 之间的差异。自那篇文章发表以来，我们逐渐倾向于一个关于 agent 的简单定义：LLM 在循环中自主地使用工具。

在与客户合作的过程中，我们看到该领域正逐渐收敛于这一简单范式。随着底层模型能力不断增强，agent 的自主程度也可以随之扩展：更智能的模型让 agent 能够独立应对微妙复杂的问题空间，并从错误中恢复。

我们现在看到工程师对如何为 agent 设计上下文的思考方式正在发生转变。如今，许多 AI 原生应用采用某种形式的基于 embedding 的推理前检索，来为 agent 呈现重要的上下文以供其推理。随着该领域转向更具 agentic 特性的方法，我们越来越多地看到团队用“just in time”的上下文策略来增强这些检索系统。

采用“just in time”方法构建的 agent，不再预先处理所有相关数据，而是维护轻量级标识符（文件路径、存储的查询、网页链接等），并在运行时使用工具通过这些引用来动态加载数据到上下文中。Anthropic 的 agentic 编码方案 Claude Code 就使用这种方法在大型数据库上执行复杂的数据分析。模型可以编写有针对性的查询、存储结果，并利用 `head` 和 `tail` 之类的 Bash 命令来分析大量数据，而无需将完整的数据对象加载到上下文中。这种方法与人类认知相仿：我们通常不会记住全部信息语料，而是引入诸如文件系统、收件箱和书签之类的外部组织与索引系统，按需检索相关信息。

除了存储效率之外，这些引用的元数据还提供了一种高效地细化行为的机制，无论这些元数据是显式提供的还是直觉性的。对于在文件系统中运行的 agent 来说，一个名为
test_utils.py
位于
tests
文件夹中，与位于
src/core_logic/
中的同名文件相比，意味着不同的用途。
文件夹层级、命名约定和时间戳都提供了重要信号，帮助人类和 agent 理解如何以及何时使用信息。
让 agent 自主导航和检索数据也实现了渐进式披露——换句话说，允许 agent 通过探索逐步发现相关上下文。每次交互都会产生为下一次决策提供信息的上下文：文件大小暗示复杂度；命名约定提示用途；时间戳可以作为相关性的代理指标。Agent 可以逐层组装理解，只在工作记忆中保留必要内容，并利用笔记策略实现额外的持久化。这种自我管理的上下文窗口使 agent 专注于相关子集，而不是淹没在详尽但可能无关的信息中。
当然，这里存在权衡：运行时探索比检索预计算数据更慢。不仅如此，还需要有主见且深思熟虑的工程，以确保 LLM 拥有正确的工具和启发式方法，从而有效地导航其信息景观。如果没有适当的指导，agent 可能会因误用工具、追逐死胡同或未能识别关键信息而浪费上下文。
在某些场景中，最有效的 agent 可能会采用混合策略，预先检索一些数据以提高速度，并根据自身判断进行进一步的自主探索。“正确”自治程度的决策边界取决于任务。Claude Code 就是一个采用这种混合模型的 agent：
CLAUDE.md
文件会被直接放入上下文中，而像 glob 和 grep 这样的原语允许它导航其环境并按需检索文件，从而有效绕过陈旧索引和复杂语法树的问题。
混合策略可能更适合动态内容较少的场景，例如法律或金融工作。随着模型能力的提升，agentic 设计将趋向于让智能模型智能地行动，并逐步减少人工策展。鉴于该领域进展迅速，“做能起作用的最简单的事”很可能仍是我们对在 Claude 之上构建 agent 的团队的最佳建议。

### 面向长时任务的上下文工程

长时任务要求 agent 在一系列动作中保持连贯性、上下文和目标导向行为，而这些动作的 token 数量会超过 LLM 的上下文窗口。对于持续数十分钟到数小时连续工作的任务，例如大型代码库迁移或综合性研究项目，agent 需要专门技术来绕开上下文窗口大小的限制。
等待更大的上下文窗口似乎是一种显而易见的策略。但在可预见的未来，各种规模的上下文窗口都可能面临上下文污染和信息相关性问题——至少在需要最强 agent 表现的情况下是如此。为了让 agent 能够在更长的时间跨度内有效工作，我们开发了一些直接应对这些上下文污染限制的技术：compaction、结构化笔记和多 agent 架构。
Compaction
Compaction 是指将一段接近上下文窗口限制的对话取出，对其内容进行摘要，并用该摘要重新开启一个新的上下文窗口的做法。Compaction 通常是上下文工程中的第一个杠杆，用于推动更好的长期连贯性。其核心在于，compaction 以高保真方式提炼上下文窗口的内容，使 agent 能够在性能下降最小的情况下继续工作。
例如在 Claude Code 中，我们通过将消息历史传给模型来总结并压缩最关键细节，从而实现这一点。模型保留架构决策、未解决的 bug 和实现细节，同时丢弃冗余的工具输出或消息。然后，agent 可以基于这个压缩后的上下文以及最近访问的五个文件继续工作。用户获得连续性，而无需担心上下文窗口限制。
压缩的艺术在于选择保留什么与丢弃什么，因为过度激进的压缩可能导致丢失那些微妙但关键的上下文，而这些上下文的重要性往往要到之后才显现。对于实现压缩系统的工程师，我们建议在复杂 agent 轨迹上仔细调优你的 prompt。先从最大化 recall 开始，确保你的压缩 prompt 捕获轨迹中每一条相关信息，然后再迭代提升 precision，通过消除多余内容来实现。
一个最容易处理的多余内容示例是清理 tool calls 和 results——一旦某个工具已在消息历史深处被调用过，agent 为什么还需要再次看到原始结果？最安全、侵入性最小的压缩形式之一是 tool result clearing，最近已作为一项功能在
Claude Developer Platform
上推出。
结构化笔记
结构化笔记，或称 agentic memory，是一种技术，其中 agent 会定期将笔记写入持久化到上下文窗口之外的 memory。这些笔记之后会被重新拉回上下文窗口。
这种策略以极小的开销提供持久 memory。就像 Claude Code 创建 to-do list，或你的 custom agent 维护一个 NOTES.md 文件一样，这种简单模式允许 agent 在复杂任务中跟踪进度，维护那些否则会在数十次 tool calls 中丢失的关键上下文和依赖关系。
Claude 在玩 Pokémon
……展示了记忆如何在非编码领域改变 agent 的能力。该 agent 在数千个游戏步骤中保持着精确的记录——追踪诸如“在过去的 1,234 步中，我一直在 Route 1 训练我的 Pokémon，Pikachu 已经升了 8 级，目标是 10 级”这样的目标。在没有任何关于记忆结构的 prompt 的情况下，它绘制出已探索区域的地图，记住自己解锁了哪些关键成就，并维护战斗策略的战略笔记，这帮助它了解哪些攻击对不同对手最有效。
在 context 重置之后，该 agent 读取自己的笔记，继续长达数小时的训练序列或地下城探索。这种跨摘要步骤的一致性使得长时程策略成为可能，而如果仅把所有信息保留在 LLM 的 context window 中，这些策略是不可能实现的。
作为我们
Sonnet 4.5 launch
的一部分，我们在 Claude Developer Platform 上以公开 beta 形式发布了一个 memory tool，它通过基于文件的系统，让在 context window 之外存储和查阅信息变得更容易。这使得 agent 能够随时间积累知识库、跨会话维护项目状态，并引用先前的工作，而无需把所有内容都保留在 context 中。
Sub-agent 架构
Sub-agent 架构提供了另一种绕过 context 限制的方法。与其让一个 agent 试图在整个项目中维护状态，专门化的 sub-agent 可以用干净的 context window 处理聚焦的任务。主 agent 依据高层计划进行协调，而 subagent 执行深度技术工作或使用工具查找相关信息。每个 subagent 可能会进行广泛探索，使用数万或更多 token，但只返回其工作的凝练、提炼后的摘要（通常为 1,000-2,000 token）。
这种方法实现了清晰的关注点分离——详细的搜索 context 保持隔离在 sub-agent 内部，而主导 agent 专注于综合和分析结果。这种模式，在
我们如何构建我们的多 agent 研究系统
，在复杂研究任务上相较于单 agent 系统展现出了显著改进。
这些方法之间的选择取决于任务特征。例如：
Compaction 为需要大量来回交互的任务维持对话流；
Note-taking 在具有明确里程碑的迭代开发中表现出色；
Multi-agent 架构处理并行探索能带来收益的复杂研究和分析。
即便模型持续改进，在扩展交互中保持连贯性这一挑战仍将是构建更有效 agent 的核心。

## 结论

Context engineering 代表了我们在使用 LLM 构建系统方式上的一次根本转变。随着模型能力越来越强，挑战不仅仅在于编写完美的 prompt——而在于在每一步都深思熟虑地策划哪些信息进入模型有限的注意力预算。无论你是在为长时程任务实施 compaction、设计 token 高效的工具，还是让 agent 即时探索其环境，指导原则始终相同：找到最小的、高信号的 token 集合，以最大化你期望结果的可能性。
我们概述的这些技术将随着模型改进而持续演进。我们已经看到，更智能的模型需要更少的规定性工程，使 agent 能够以更多自主性运行。但即便能力不断扩展，将 context 视为一种宝贵且有限的资源仍将是构建可靠、有效 agent 的核心。
今天就在 Claude Developer Platform 中开始使用 context engineering，并通过我们的
memory and context management
cookbook 获取实用技巧和最佳实践。
