**一句话结论**：读它的**信息架构** —— 按 Build / Test / Deploy / Monitor 四个动词组织，而不是按模块罗列。

## 为什么这个组织方式值得注意

大多数框架文档是**按模块**排的：这个类、那个类、这个组件。你得先知道框架里有什么，才能找到需要的东西。

而这份文档是**按动词**排的：**构建 / 测试 / 部署 / 监控** —— 也就是「一个 agent 项目要经历哪几个环节」。

**这个视角对工程判断很有帮助**：它把技术栈映射成了项目阶段。你会发现「构建」只是一小部分，而**测试与监控占了两个环节** —— 这正是本站阶段 4 那六章在讲的事。

## 什么时候细看

`resources.ts` 的建议是**第 11 章选型时再细看**。理由：在没手写过循环、没被上下文与预算问题咬过之前，看框架文档很容易把它的抽象当成问题的本质（本站第 13 章）。

## 和本站的关系

- **第 11 章「agent 循环」** —— 手写一遍作为基准
- **第 13 章「框架选型」** —— 抽象模型与「能让路」的检查项
