第 2 节说"从入口往下追"。这一节把它走完整：**一次真实的追踪，从装饰器到 JSON schema。**

任务很具体：**搞清楚 `@tool` 是怎么把 Python 函数变成模型看到的 schema 的。** 问题来自第 13 章那个实测。

## 第一步：定位入口

先在源码目录里找 `tool` 的定义：

```text
$ grep -n "^def tool" langchain_core/tools/convert.py
16:def tool(
29:def tool(
44:def tool(
58:def tool(
71:def tool(
```

**五个定义，都不是重复实现。** 那是 `@typing.overload` 的写法 —— 为了给不同的调用方式提供类型提示。真正跑的是最后一个（第 71 行）。

这条本身就是源码阅读的一个小教训：**看到多个同名定义时，先确认是不是 overload。** 直接读第一个会读到只用于类型检查的桩。

## 第二步：读签名，找线索

第 71 行的签名里有一个参数值得注意：

```python
def tool(
    name_or_callable=None, runnable=None, *args,
    description=None, return_direct=False, args_schema=None,
    infer_schema: bool = True,
    response_format: Literal["content", "content_and_artifact"] = "content",
    parse_docstring: bool = False,      # ← 这个
    error_on_invalid_docstring: bool = True,
) -> ...:
```

**`parse_docstring: bool = False`。** 这就是答案的一半 —— 参数说明的解析**默认是关的**。

而我在第 13 章写下那个结论时，完全不知道有这个开关。这也是为什么"读源码"这件事不能靠猜：**一个默认值就能决定行为，而它不在文档的显著位置。**

## 第三步：往下追调用链

继续在 `convert.py` 里找它把工作交给了谁：

```text
$ grep -n "StructuredTool\|infer_schema" langchain_core/tools/convert.py
219:    def _create_tool_factory(
263:            if infer_schema or args_schema is not None:
264:                return StructuredTool.from_function(
271:                    infer_schema=infer_schema,
```

第 264 行交给了 `StructuredTool.from_function`。跟到 `structured.py`，再往下就进到 `base.py` 的 `create_schema_from_function`。**而 schema 真正被取出来的地方在这里：**

```python
# langchain_core/tools/base.py:95 附近
def _get_filtered_args(inferred_model, func, *, filter_args, include_injected=True):
    """Get the arguments from a function's signature."""
    schema = inferred_model.model_json_schema()["properties"]   # ← 就是这一行
```

**`model_json_schema()` 是 pydantic 的方法。** 到这里链路清楚了：

```text
@tool（convert.py:71，parse_docstring 默认 False）
  → _create_tool_factory（convert.py:219）
      → StructuredTool.from_function（structured.py）
          → create_schema_from_function（base.py:214）
              → _get_filtered_args（base.py:95）
                  → pydantic 的 model_json_schema()   ← 约束在这里定下来
```

**关键结论：LangChain 只是一个"搬运工"。** 它把函数的类型标注交给 pydantic，再把 pydantic 生成的 schema 原样拿走。所以约束（enum、range、pattern）**只能来自类型标注** —— 那一层不产生它们，下一层就不会有。

## 第四步：写一个可验证的预测，然后跑

到这里我有两个预测：

- 打开 `parse_docstring=True` 之后，那句「只能是明天或后天」会进 `description`
- 但它**仍然不会**变成 `enum`

跑了一次（三种写法对照）：

```text
写法                                参数 schema
A day: str，默认                     {"title": "Day", "type": "string"}
B day: str，parse_docstring=True     {"description": "只能是「明天」或「后天」",
                                      "title": "Day", "type": "string"}
C day: Literal[...]，True            {"description": "查询的日期",
                                      "enum": ["明天", "后天"],
                                      "title": "Day", "type": "string"}
```

（实跑数据，2026-10-09。langchain_core 0.3.63。）

**两个预测都对了。** 但有一个我**没预测到**的现象：看 A 组的工具级 description：

```text
A 组工具级 description：
    查天气。 /  /     Args: /         day: 只能是「明天」或「后天」
```

**A 组把整段文档字符串（含 `Args:` 这个标题）原样当成了工具描述。** 也就是说：默认配置下，那段"Args:"不仅是没被解析，它还被**当成正文漏了出去** —— 模型会看到一段带着格式残骸的描述。

这个发现是我预测之外的，而它比预测对的那两条更有用：**它说明默认值不只是"少做了一件事"，而是"把该做的事做错了"。**

## 第五步：把结论收敛成一句可执行的话

整个追踪的产出应该是一句能指导改代码的话，而不是"LangChain 有个 parse_docstring 参数"。

收敛过程：

- "它默认不解析文档字符串" → 描述现象
- "所以参数说明丢了" → 描述后果
- **"所以约束要写在类型标注里，说明写在文档字符串里，并且打开 parse_docstring"** → 可执行

**最后那句才是产出。** 前两句都对，但它们不能让你写出更好的代码 —— 而第 5 节会讲"产出什么"这件事。

## 三个可以复用的动作

把这次追踪里可复用的部分抽出来：

**一，先确认重载。** 看到多个同名定义时，先看是不是 `@overload`。否则会读到类型桩。

**二，用 grep 追调用，不要用眼睛翻。** 每一跳都是 `grep -n "下一个函数名" 当前文件`。这样每一跳都有 file:line，而且不会漏。

**三，写下预测再跑。** 这次追踪里最有价值的信息来自"我预测之外的"那一条。**预测错了的地方，就是你和作者思路不同步的地方** —— 而那正是你要学的东西。


## 一个容易忽略的细节：追踪时要带着问题走

第 3 节那条链有五跳。但**五跳不是目标** —— 目标是在链上找到"约束是在哪一层定下来的"。

这个区别很实际：如果不带着问题走，你会在每一跳都想"这个函数还调用了什么"，然后扩散开去。带着问题走，每一跳只问一句：**"这里还能产生我要找的东西吗？"**

用第 3 节那个例子看：

```text
问题：约束（enum）是从哪一层产生的？

第 1 跳 convert.py:71   工具包装层 —— 不产生约束
第 2 跳 convert.py:219  建工具 —— 不产生约束
第 3 跳 structured.py  组装 —— 不产生约束
第 4 跳 base.py:214    建 schema —— 交给 pydantic
第 5 跳 base.py:95     取 properties —— 从 pydantic 的 model_json_schema() 拿
                        ← 约束在"pydantic 从类型标注生成"这一步定下来
```

**前四跳都只是透传，第五跳才见到机制。** 而这个判断只有在带着问题时才能做出来 —— 否则你不知道第 2 跳算不算"找到了"。

## 一个反过来的情况：追不到底怎么办

有时候链路会追出你熟悉的语言之外 —— 比如追到 `model_json_schema()` 时，那是 pydantic 的方法。这时候有三个选择：

**一、继续追进 pydantic。** 适合"这个行为对我是关键"的情况。代价是可能很深（pydantic 用 Rust 实现核心）。

**二、在这里停，用实验代替。** 上面三组对照做的就是这个 —— 不读 pydantic 内部，而是输入几种类型看输出。**对"行为边界"类的问题，这往往比读实现更快。**

**三、接受"这是它的约定"并记录下来。** 适合"我不需要改它，只需要知道边界在哪"的情况。

第 3 节选的是第二种，理由是：**我的问题是"约束从哪来"，而这个问题用三组输入就能回答。** 追进 pydantic 会得到更精确的机制描述，但那对"我该怎么写代码"没有额外帮助。

**这是一个可以省很多时间的判断：问一句"知道到这个程度够不够我做出决定"。** 够了就停 —— 读源码不是越深越好。
## 完整可运行代码

下面这段代码把这次追踪做成了可复现的脚本：用 `inspect` 取真实 file:line，并跑三种写法对照 schema。

```python
"""沿一次任务读到底：@tool 是怎么把函数变成 JSON schema 的。

第 13 章测出一个现象：@tool 生成的 schema 里 day 只有 {"type": "string"}，没有 enum ——
尽管文档字符串写了「只支持明天或后天」。当时我把它记成了「抽象泄漏」。

读了源码之后，结论要**修正**，而且比原来更具体。下面这组对照是这次读源码的产出。

环境：langchain_core 0.3.63 / langchain 0.3.7。实跑状态：2026-10-09。
"""
import inspect, json
from typing import Literal

from langchain_core.tools import tool

DOC = """查天气。

Args:
    day: 只能是「明天」或「后天」
"""


@tool
def a_default(day: str) -> str:
    """查天气。

    Args:
        day: 只能是「明天」或「后天」
    """
    return day


@tool(parse_docstring=True)
def b_parsed(day: str) -> str:
    """查天气。

    Args:
        day: 只能是「明天」或「后天」
    """
    return day


@tool(parse_docstring=True)
def c_literal(day: Literal["明天", "后天"]) -> str:
    """查天气。

    Args:
        day: 查询的日期
    """
    return day


def summary(t):
    return t.args_schema.model_json_schema()["properties"]["day"]


if __name__ == "__main__":
    print("=== 一、调用链（file:line 由 inspect 取真实位置）===")
    from langchain_core.tools import base as base_mod, convert as convert_mod
    for label, fn in [("装饰器入口", convert_mod.tool),
                      ("建 schema", base_mod.create_schema_from_function),
                      ("取 properties", base_mod._get_filtered_args)]:
        src = inspect.getsourcefile(fn).split("site-packages/")[-1]
        print("  %-14s %s:%d" % (label, src, inspect.getsourcelines(fn)[1]))
    print()

    print("=== 二、参数 schema 对照 ===")
    rows = [
        ("A day: str，默认", a_default),
        ("B day: str，parse_docstring=True", b_parsed),
        ("C day: Literal[...]，True", c_literal),
    ]
    for label, t in rows:
        print("  %-32s %s" % (label, json.dumps(summary(t), ensure_ascii=False)))
    print()

    print("=== 三、工具级 description（前 30 字）===")
    for label, t in rows:
        d = (t.description or "（空）").replace(chr(10), " / ")[:34]
        print("  %-32s %s" % (label, d))
    print()

    print("=== 结论 ===")
    print("  1. parse_docstring 默认是 False（convert.py:23/38/52/66/80 五处重载）")
    print("     → 写在 Args: 段里的参数说明**被静默丢弃**，而且原文还漏进了工具级 description。")
    print("  2. 打开 parse_docstring 之后，那句「只能是明天或后天」进了 description ——")
    print("     但**仍然没有变成 enum**。散文只能生成 description，生成不了约束。")
    print("  3. 只有类型标注（Literal）能生成 enum。LangChain 在 base.py:103 用")
    print("     pydantic 的 model_json_schema() 取 schema，约束完全由类型决定。")
    print()
    print("  所以第 13 章那个现象更准确的解释是：")
    print("    **约束写在散文里，就等于把它从「机器可校验」降级成了「模型可以忽略的提示」。**")
    print("    这不是框架丢了信息 —— 是 prose 和 type 承载的东西不同：")
    print("      description ← 文档字符串    enum/range/pattern ← 类型标注")
```

## 常见坑

- **读到 overload 的桩就停下。** 先确认同名定义是不是 `@typing.overload`。
- **用眼睛翻代码追调用。** 用 `grep -n`，每一跳都有 file:line，而且不会漏。
- **凭记忆写行号。** 一定用 `inspect.getsourcefile` / `getsourcelines` 取。
- **不写预测就开始读。** 预测之外的发现最有价值 —— 那是你和作者思路不同步的地方。
- **追到"它调了 X"就停。** 要追到"约束是在哪一层定下来的"—— 这次是 base.py:95 那行 `model_json_schema()`。
- **产出停在描述现象。** "它默认不解析"是现象，"所以约束要写进类型标注"才是可执行的产出。
