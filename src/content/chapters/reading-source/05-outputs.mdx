前四节讲了怎么读。这一节讲一个更容易被忽略的问题：**读完留下什么。**

因为源码阅读有一个特点：**不产出时，读过的源码很容易只剩模糊印象。** 三个月后你只会记得"我看过 LangChain 的 tool 模块"，而那时你连 `parse_docstring` 这个参数都不记得了。

## 四种可能的产出

| 产出 | 例子 | 三个月后还有用吗 |
|---|---|---|
| **笔记** | 摘抄代码片段 | 取决于有没有问题、来源和适用范围；孤立片段难复用 |
| **调用链图** | 第 3 节那张 file:line 链 | 结构可能有复用价值；文件位置会随版本变化 |
| **可执行的判据** | "把需要的约束写进最终工具 schema（可由类型推断，也可显式提供 args_schema）" | **有** —— 它指导写代码 |
| **可复现的实验** | 第 3 节那个三种写法对照脚本 | 适合检查特定版本行为 —— 需固定依赖并断言目标行为 |

这四类产出的复用价值取决于你要解决的问题：定位线上问题时调用链图可能最有用；要把发现变成团队习惯时，可执行判据更直接；要核对版本变化时，带断言和固定环境的复现脚本更合适。脚本可以把结论变成可重跑的检查，但它不会因为“能运行”就自动证明结论。

源码会变。第 3 节的行号（`convert.py:71`、`base.py:95`）随版本变化，不能当成稳定标识。脚本也可能因 API、依赖或运行环境变化而报错；即使运行成功，若没有断言关键行为，它也不能自动判断结论是否仍成立。要复核时，应记录包版本和环境、让断言覆盖具体结论，并把输出与限制一起保存。

在能固定环境并写出明确断言时，一种有用的产出是“脚本 + 一句结论”：脚本重跑已声明的检查，结论说明证据支持到哪里。本站 `verify-output/` 是本地验证产物目录，已被 Git 忽略；其中的脚本不会随仓库交付。可复用的课程示例应放在受版本控制的 `experiments/` 或 `examples/` 中，并记录依赖快照。

## 这份产出要放在哪

四种产出的位置不同，而放错位置会让它失效：

| 产出 | 该放哪 | 为什么 |
|---|---|---|
| 可执行判据 | **代码注释 / 团队规范** | 写代码时能看到 |
| 可复现实验 | **仓库里的脚本** | 换版本时能重跑 |
| 调用链图 | **设计文档** | 讲结构时用 |
| 笔记 | 自己的地方 | 只对你有用 |

第一行最容易被忽略。**一条"约束要进入最终工具 schema"的结论，如果只写在笔记里，那它三个月后不会影响任何人**；写进团队的代码规范或者工具定义模板里，它才会。

本项目自己做了一次这件事：第 3 节那个发现（`parse_docstring` 默认关、文档说明不会变成 enum）在**第 13 章的正文里补了一条修正**。因为那一章正是当时写下"抽象泄漏"这个说法的地方 —— **结论要回到它该更新的位置**，而不是只留在新写的那一章。固定在 langchain-core 0.3.63 的源代码中，[`@tool` 的 parse_docstring 默认值](https://github.com/langchain-ai/langchain/blob/langchain-core%3D%3D0.3.63/libs/core/langchain_core/tools/convert.py)为 `False`；[schema 生成与字段提取](https://github.com/langchain-ai/langchain/blob/langchain-core%3D%3D0.3.63/libs/core/langchain_core/tools/base.py)说明自然语言说明与类型约束由不同机制处理。可复现断言见 `experiments/scripts/verify_reading_source_tool_063.py`，依赖锁见 `experiments/locks/reading-source-compare-py314-macos-arm64-20261021.txt`。该脚本在 `langchain-core==0.3.63` 下用六项断言核对参数说明、`Literal` schema 与 inspect 位置；输出不代表其他版本。

## 一个具体的模板

给一个可以照着用的产出模板。每条源码阅读的产出包含四行：

```text
问题      我想搞清楚什么（一句话）
位置      file:line（用 inspect 取的，不是背的）
结论      可执行的一句话
复现      一个能重跑的脚本路径
```

四行里，**第二行和第四行是"可验证性"** —— 它们让别人（包括三个月后的你）能回到证据上。

第三行是价值。而第一行是**筛选器**：如果你写不出这个"问题"那一行，那说明这次阅读没有目标 —— 按第 2 节那条，它可能根本就不该发生。

**归档到哪里、叫什么名字**取决于团队现有目录约定。可复用的验证脚本应放在版本控制内、文件名能说明检查对象，并与依赖快照、运行命令和结果相互关联。四行笔记中的“位置”应由函数对象经 `inspect` 生成文件路径与起始行，不要手抄；若要跨版本追踪，还要记录包版本、模块和符号名，因为行号会移动。对 C 扩展、动态生成或源码不可用的对象，`inspect` 可能无法给出位置，需改用官方文档、仓库版本和符号引用。

## 一个反过来的判断：什么时候不该产出

最后说一个反面。**不是每次读源码都值得留产出。**

三种情况可以只读不写：

- **你只是在查一个 API 的确切签名** —— 那是查文档，不是读源码
- **你在调试一个具体 bug** —— 产出是那个 fix，不是一份笔记
- **你在确认一个你已经知道的结论** —— 确认过了就够，不必留档

区分标准是：**这次阅读有没有让你"改变一个判断"。** 如果读完发现"原来是我想的那样"，那没有新的东西需要留；如果发现"和我原来想的不一样"（第 3 节那个 `parse_docstring` 就是），那就值得写下来 —— 尤其是**那个被推翻的旧判断**。

## 一个具体的例子：这个项目自己怎么做的

上面说"把发现回到它该更新的位置"。这里给一个这个项目里真实发生的例子，因为它是这套做法的完整演示。

**起因**：第 13 章测出 `@tool` 生成的 schema 里没有 enum，当时的解释是"抽象泄漏"。

**触发**：写第 22 章时读了源码，发现真实机制不同 —— `parse_docstring` 默认关，而且散文永远变不成 enum。

**处理**：回头去第 13 章补了一条修正说明，指向第 22 章。

三步里，第三步最容易被跳过 —— 因为新写的章节已经把事情讲清楚了，"旧章节有点不准确"看起来不重要。

但它有一个具体的代价：**读者是按顺序读的。** 他先在第 13 章看到"抽象泄漏"这个说法，然后形成印象；到第 22 章才发现要修正。而如果第 13 章那处不改，那两章之间就留着一个矛盾 —— 读者不知道该信哪个。

**所以"读完要产出什么"这件事，最后一条是：产出一个"该更新哪里"的清单。** 而它往往指向的不是新文件，是旧文件。

## 一个可以自动化的检查

最后给一个低成本的做法：**如果你在写新章节时修正了旧章节的结论，把那条修正也写进旧章节。** 具体形式可以很短：

```text
> 修正（2026-10-09）：这里当时记成了「抽象泄漏」。读源码后的准确说法见第 22 章第 3 节 ——
> 机制是 parse_docstring 默认关闭；infer schema 会读取类型标注，而显式 args_schema 也能提供字段约束。
```

两行字，但它解决了三个问题：读者知道该信哪个、知道去哪看细节、而且能看到"结论是被修正过的"—— 后者本身就是一种可信度信号。

**一份从不修正的文档，通常不是因为它没错，而是因为没人回去看。** 而源码阅读恰好是发现旧错误最有效的途径之一 —— 所以它是"修正"这件事的主要来源。

## 一个反过来的成本：产出也会过期

最后说一个容易忽略的点。上面讲的都是「要留产出」，但**产出本身也会过期** —— 而且比源码过期得更快。

两种过期形态：

**一、行号变了。** 下一版本 base.py:95 可能变成 base.py:120。这是为什么第 3 节强调「用 inspect 取」，也是为什么最强的产出形式是**脚本**可以在固定依赖版本中重复同一检查；若要判断新版本是否仍符合结论，需要在目标版本环境中更新依赖快照并重跑断言。原封不动地重跑固定在旧版本的脚本，只能复现旧环境，不能自动发现上游行为变化。

**二、结论变了。** 更麻烦的一种。比如「parse_docstring 默认关闭」这条 —— 如果某个版本改成默认开启，那你的产出就从「正确」直接变成「错误」，而且**没有任何提示**。

对治第二种的办法是**给产出一条可检验的断言**。落到脚本里就是一句 assert：

```text
# 如果这个断言在某天失败了，说明结论需要更新
assert summary(a) == {"title": "Day", "type": "string"}, "parse_docstring 默认值可能变了"
```

这条断言可以充当一个有限的“过期检测器”：当断言覆盖目标行为且测试仍运行在记录的环境中，它能发现部分变化；它不能证明未测试的行为，也不能代替重新核对来源与适用范围。

## 完整可运行代码

下面这段代码生成上面那个四行模板：给定问题、位置、结论，输出一份可存档的产出，并检查"位置"是不是用 inspect 取的（而不是手写的）。

脚本里 `split("site-packages/")[-1]` 的用意第 1 节解释过：把冗长的安装路径截短；**如果函数来自你自己的项目（路径里没有 `site-packages`），`split` 找不到分隔符就原样返回完整路径**，这正是下面第 3 条"手写位置"反例要对照的情形。

```python
"""读完要产出什么：四行模板 + 位置校验。纯本地。
实跑状态：2026-10-21。langchain-core 0.3.63；见依赖快照。"""
import inspect


def make_note(question, target, conclusion, script):
    """生成一份产出。target 传函数对象时自动取 file:line。"""
    if callable(target):
        try:
            source_file = inspect.getsourcefile(target)
            line = inspect.getsourcelines(target)[1]
        except (OSError, TypeError) as exc:
            raise ValueError("inspect 无法定位这个对象的源码") from exc
        if source_file is None:
            raise ValueError("inspect 没有返回源码文件")
        src = source_file.split("site-packages/")[-1]
        loc = "%s:%d" % (src, line)
        loc_verified = True
    else:
        loc = str(target)
        loc_verified = False
    return {
        "问题": question,
        "位置": loc,
        "结论": conclusion,
        "复现": script,
        "位置由 inspect 取得": loc_verified,
    }


def render(note):
    out = []
    for k in ("问题", "位置", "结论", "复现"):
        out.append("%-6s%s" % (k, note[k]))
    if not note["位置由 inspect 取得"]:
        out.append("      ⚠️ 位置是手写的 —— 应该传函数对象让 inspect 取")
    return chr(10).join(out)


if __name__ == "__main__":
    from langchain_core.tools import base as base_mod
    from langchain_core.tools import convert as convert_mod

    script = "experiments/scripts/verify_reading_source_tool_063.py"
    notes = [
        make_note("约束是从哪一层产生的？",
                  base_mod._get_filtered_args,
                  (
                      "schema 来自 pydantic 的 model_json_schema()；"
                      "约束可来自类型推断，也可由 args_schema 提供。"
                  ),
                  script),
        make_note("参数说明为什么没进 schema？",
                  convert_mod.tool,
                  (
                      "parse_docstring 默认 False；开启后进入 description，"
                      "但仍不会变成 enum"
                  ),
                  script),
        make_note("手写行号会怎样？",
                  "langchain_core/tools/base.py:999",
                  # 虚构行号：展示手写位置不会被自动校验
                  "反面示例：手写的位置无法自动校验",
                  "-"),
    ]
    for i, n in enumerate(notes, 1):
        print("=== 产出 %d ===" % i)
        print(render(n))
        print()
    print("四行里，位置与复现是「可验证性」，结论是价值，问题是筛选器。")
    print("写不出「问题」那一行，说明这次阅读没有目标 —— 按第 2 节，它可能不该发生。")
```

## 常见坑

- **读完不留产出。** 三个月后你只记得"看过"，而那是零。
- **只留笔记和代码片段。** 片段脱离上下文没意义；可执行的判据和可复现的实验才有长期价值。
- **手写行号。** 用 `inspect` 取 —— 手写的行号会错，而错了之后读者去翻会发现对不上。
- **产出只放在自己的笔记里。** 一条判据要写进代码规范或模板注释，才会影响以后写的代码。
- **不回头更新旧结论。** 第 3 节的发现就该回到第 13 章去修正 —— 结论要回到它该更新的位置。
- **每次都强行留产出。** 只是查签名或修 bug 时不必 —— 判据是"这次有没有改变一个判断"。
