前四节讲了怎么读。这一节讲一个更容易被忽略的问题：**读完留下什么。**

因为源码阅读有一个特点：**不产出就等于没读。** 三个月后你只会记得"我看过 LangChain 的 tool 模块"，而那时你连 `parse_docstring` 这个参数都不记得了。

## 四种产出，价值递增

| 产出 | 例子 | 三个月后还有用吗 |
|---|---|---|
| **笔记** | 摘抄代码片段 | 很少 —— 片段脱离上下文没意义 |
| **调用链图** | 第 3 节那张 file:line 链 | 有一点 —— 位置会变，但结构还在 |
| **可执行的判据** | "约束要写进类型标注" | **有** —— 它指导写代码 |
| **可复现的实验** | 第 3 节那个三种写法对照脚本 | **最有** —— 换版本后重跑就能验证结论还成不成立 |

最后一行的价值值得展开：**它把一个"结论"变成了一个"可以重新验证的过程"。**

源码是会变的。第 3 节那些行号（`convert.py:71`、`base.py:95`）在下一个版本里可能全变了。但那个脚本不会失效 —— 它会在新版本上重新跑一遍，然后告诉你"结论还成立"或者"变了"。

**所以最强的一种产出是：一个脚本 + 一句结论。** 脚本负责可复现，结论负责可执行。而这个项目自己的做法就是这个 —— `verify-output/` 目录里每一个实测脚本对应的正是这个模式。

## 这份产出要放在哪

四种产出的位置不同，而放错位置会让它失效：

| 产出 | 该放哪 | 为什么 |
|---|---|---|
| 可执行判据 | **代码注释 / 团队规范** | 写代码时能看到 |
| 可复现实验 | **仓库里的脚本** | 换版本时能重跑 |
| 调用链图 | **设计文档** | 讲结构时用 |
| 笔记 | 自己的地方 | 只对你有用 |

第一行最容易被忽略。**一条"约束要写进类型标注"的结论，如果只写在笔记里，那它三个月后不会影响任何人**；写进团队的代码规范或者工具定义的模板注释里，它才会。

本项目自己做了一次这件事：第 3 节那个发现（`parse_docstring` 默认关、散文变不成 enum）在**第 13 章的正文里补了一条修正**。因为那一章正是当时写下"抽象泄漏"这个说法的地方 —— **结论要回到它该更新的位置**，而不是只留在新写的那一章。

## 一个具体的模板

给一个可以照着用的产出模板。每条源码阅读的产出包含四行：

```text
问题      我想搞清楚什么（一句话）
位置      file:line（用 inspect 取的，不是背的）
结论      可执行的一句话
复现      一个能重跑的脚本路径
```

四行里，**第二行和第四行是"可验证性"** —— 它们让别人（包括三个月后的你）能回到证据上。

第三行是价值。而第一行是**筛选器**：如果你写不出这个"问题"那一行，那说明这次阅读没有目标 —— 按第 2 节那条，它可能根本就不该发生。

## 一个反过来的判断：什么时候不该产出

最后说一个反面。**不是每次读源码都值得留产出。**

三种情况可以只读不写：

- **你只是在查一个 API 的确切签名** —— 那是查文档，不是读源码
- **你在调试一个具体 bug** —— 产出是那个 fix，不是一份笔记
- **你在确认一个你已经知道的结论** —— 确认过了就够，不必留档

区分标准是：**这次阅读有没有让你"改变一个判断"。** 如果读完发现"原来是我想的那样"，那没有新的东西需要留；如果发现"和我原来想的不一样"（第 3 节那个 `parse_docstring` 就是），那就值得写下来 —— 尤其是**那个被推翻的旧判断**。

## 一个具体的例子：这个项目自己怎么做的

上面说"把发现回到它该更新的位置"。这里给一个这个项目里真实发生的例子，因为它是这套做法的完整演示。

**起因**：第 13 章测出 `@tool` 生成的 schema 里没有 enum，当时的解释是"抽象泄漏"。

**触发**：写第 22 章时读了源码，发现真实机制不同 —— `parse_docstring` 默认关，而且散文永远变不成 enum。

**处理**：回头去第 13 章补了一条修正说明，指向第 22 章。

三步里，第三步最容易被跳过 —— 因为新写的章节已经把事情讲清楚了，"旧章节有点不准确"看起来不重要。

但它有一个具体的代价：**读者是按顺序读的。** 他先在第 13 章看到"抽象泄漏"这个说法，然后形成印象；到第 22 章才发现要修正。而如果第 13 章那处不改，那两章之间就留着一个矛盾 —— 读者不知道该信哪个。

**所以"读完要产出什么"这件事，最后一条是：产出一个"该更新哪里"的清单。** 而它往往指向的不是新文件，是旧文件。

## 一个可以自动化的检查

最后给一个低成本的做法：**如果你在写新章节时修正了旧章节的结论，把那条修正也写进旧章节。** 具体形式可以很短：

```text
> 修正（2026-10-09）：这里当时记成了「抽象泄漏」。读源码后的准确说法见第 22 章第 3 节 ——
> 机制是 parse_docstring 默认关闭，且约束只能由类型标注产生。
```

两行字，但它解决了三个问题：读者知道该信哪个、知道去哪看细节、而且能看到"结论是被修正过的"—— 后者本身就是一种可信度信号。

**一份从不修正的文档，通常不是因为它没错，而是因为没人回去看。** 而源码阅读恰好是发现旧错误最有效的途径之一 —— 所以它是"修正"这件事的主要来源。

## 一个反过来的成本：产出也会过期

最后说一个容易忽略的点。上面讲的都是「要留产出」，但**产出本身也会过期** —— 而且比源码过期得更快。

两种过期形态：

**一、行号变了。** 下一版本 base.py:95 可能变成 base.py:120。这是为什么第 3 节强调「用 inspect 取」，也是为什么最强的产出形式是**脚本**（它会在新版本上重新跑，自动发现结论是否还成立）。

**二、结论变了。** 更麻烦的一种。比如「parse_docstring 默认关闭」这条 —— 如果某个版本改成默认开启，那你的产出就从「正确」直接变成「错误」，而且**没有任何提示**。

对治第二种的办法是**给产出一条可检验的断言**。落到脚本里就是一句 assert：

```text
# 如果这个断言在某天失败了，说明结论需要更新
assert summary(a) == {"title": "Day", "type": "string"}, "parse_docstring 默认值可能变了"
```

**这条断言就是你的「过期检测器」。** 它不需要你记得回来检查 —— 脚本重跑时会自己告诉你。而这也回到了本节开头那个判断：**最强产出 = 脚本 + 一句结论**，因为脚本负责的可复现性，恰好也是防过期的那一层。## 完整可运行代码

下面这段代码生成上面那个四行模板：给定问题、位置、结论，输出一份可存档的产出，并检查"位置"是不是用 inspect 取的（而不是手写的）。

```python
"""读完要产出什么：四行模板 + 位置校验。纯本地。实跑状态：2026-10-09。"""
import inspect


def make_note(question, target, conclusion, script):
    """生成一份产出。target 传函数对象时自动取 file:line。"""
    if callable(target):
        src = inspect.getsourcefile(target).split("site-packages/")[-1]
        line = inspect.getsourcelines(target)[1]
        loc = "%s:%d" % (src, line)
        loc_verified = True
    else:
        loc = str(target)
        loc_verified = False
    return {"问题": question, "位置": loc, "结论": conclusion, "复现": script,
            "位置已校验": loc_verified}


def render(note):
    out = []
    for k in ("问题", "位置", "结论", "复现"):
        out.append("%-6s%s" % (k, note[k]))
    if not note["位置已校验"]:
        out.append("      ⚠️ 位置是手写的 —— 应该传函数对象让 inspect 取")
    return chr(10).join(out)


if __name__ == "__main__":
    from langchain_core.tools import base as base_mod
    from langchain_core.tools import convert as convert_mod

    notes = [
        make_note("约束是从哪一层产生的？",
                  base_mod._get_filtered_args,
                  "schema 来自 pydantic 的 model_json_schema()，约束只能由类型标注产生",
                  "verify-output/read-source-tool.py"),
        make_note("参数说明为什么没进 schema？",
                  convert_mod.tool,
                  "parse_docstring 默认 False；开启后进 description，但仍不会变成 enum",
                  "verify-output/read-source-tool.py"),
        make_note("手写行号会怎样？",
                  "langchain_core/tools/base.py:95",
                  "反面示例：手写的位置无法自动校验",
                  "-"),
    ]
    for i, n in enumerate(notes, 1):
        print("=== 产出 %d ===" % i)
        print(render(n))
        print()
    print("四行里，位置与复现是「可验证性」，结论是价值，问题是筛选器。")
    print("写不出「问题」那一行，说明这次阅读没有目标 —— 按第 2 节，它可能不该发生。")
```

## 常见坑

- **读完不留产出。** 三个月后你只记得"看过"，而那是零。
- **只留笔记和代码片段。** 片段脱离上下文没意义；可执行的判据和可复现的实验才有长期价值。
- **手写行号。** 用 `inspect` 取 —— 手写的行号会错，而错了之后读者去翻会发现对不上。
- **产出只放在自己的笔记里。** 一条判据要写进代码规范或模板注释，才会影响以后写的代码。
- **不回头更新旧结论。** 第 3 节的发现就该回到第 13 章去修正 —— 结论要回到它该更新的位置。
- **每次都强行留产出。** 只是查签名或修 bug 时不必 —— 判据是"这次有没有改变一个判断"。
