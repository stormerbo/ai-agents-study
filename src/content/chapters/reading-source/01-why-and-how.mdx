前面二十章讲的都是「怎么用」。这一章讲一个不同的技能：**怎么读它的实现。**

## 一个具体的例子

先说一个真实发生的修正。

第 13 章我测过一件事：用 LangChain 的 `@tool` 装饰器定义一个函数，参数类型是 `str`、文档字符串里写着「只能支持明天或后天」。结果生成的 schema 里，那个参数**只有 `{"type": "string"}`，没有 enum**。

当时的解释是「抽象泄漏」—— 框架丢掉了我写在文档里的约束。这个解释听起来合理，而且和流传的说法一致。

这一章我去读了源码，结论要改：

```text
@tool 默认 parse_docstring=False（convert.py 里五处重载都是这个默认值）
  → 写在 Args: 段里的参数说明**根本没被读**
  → 更糟的是，那段原文还漏进了工具级 description

打开 parse_docstring=True 之后，说明被读到了，进了 description
  → 但它**仍然没有变成 enum**
  → 因为 schema 来自 pydantic 的 model_json_schema()（base.py:103）
     而 pydantic 只能从**类型标注**生成 enum，无法从散文里推断约束
```

所以真实情况比「抽象泄漏」更具体、也更有用：

- **框架没有丢信息** —— 它提供了解析文档字符串的开关，只是**默认关着**

- **散文和类型承载的东西不同**：description 来自文档字符串，enum 来自类型标注

- **把约束写进散文，等于把它从「机器可校验」降级成了「模型可以忽略的提示」**

三种说法里，只有第三种能指导你改代码：**把约束从散文搬进类型标注。** 前两种都停在"框架不好"这个层面。

## 什么时候该读源码

读源码不是越早越好。它有一个明确的门槛，而门槛由**你能问出什么问题**决定。

**不该读的时候**：你还在学"怎么用"，而文档已经覆盖了你的问题。这时读源码是浪费时间 —— 你会被大量与你无关的细节淹没。

**该读的时候**：有三类问题文档回答不了：

| 问题类型 | 例子 |
|---|---|
| **行为的确切边界** | "这个参数默认值是什么？" "出错时返回什么？" |
| **为什么是这样** | "为什么要这样设计？有没有别的选择？" |
| **能不能改** | "我想让它支持 X，从哪里入手？" |

第一类最常见，而且最容易验证 —— 本节开头那个例子就属于这一类。

## 三个可以立刻用的方法

**方法一：用 inspect 拿真实位置，不要凭记忆。** Python 里一行代码就能得到函数定义在哪个文件第几行：

```python
import inspect
inspect.getsourcefile(func)     # 文件路径
inspect.getsourcelines(func)[1]  # 起始行号
```

这个习惯很重要，因为**我上面那些行号（convert.py:23/38/52/66/80、base.py:103）全是用它取出来的，不是背的**。凭记忆写行号一定会错，而错了之后读者去翻会发现对不上，整段论述的可信度就没了。

**方法二：从入口往下追，别从目录开始读。** 沿着一次真实的调用往下走（第 3 节会完整演示），每一步只读你需要的那个函数。

**方法三：读之前先写下一个可验证的预测。** 比如「我猜它默认会解析文档字符串」。然后跑一次看结果 —— **预测错了的地方，就是你真正学到东西的地方。** 本节开头那个 `parse_docstring=False` 就是这么发现的：我预测「说明会进 description」，结果它连读都没读。

## 一个反过来的收益

读源码还有一个不常被提到的收益：**它让你能判断"哪些说法不可信"。**

第 2 章那个提示注入的实验里，我测出脚本式注入 0/6、内容操纵 6/6 —— 而流传的说法往往是"加个 XML 标签就安全了"。两者的差别不在细节，在**有没有实测**。

读源码提供的正是同一类东西：**一手证据**。一段被广泛转载的"某某框架内部会做 X"，读一遍源码通常只要十几分钟，而它的结论可能和你看到的完全不同（就像本节开头那个例子）。

## 一个诚实的提醒

最后说一个反面：**读源码也有明确的成本，而且它不总是值得。**

三个不值得的情况：

- **你只是想用这个库。** 文档够了就读文档 —— 源码是给你"要改它"或"要判断它的边界"时用的

- **你还在选型阶段。** 第 13 章给过选型判据，那不需要读实现（架构和抽象模型更重要）

- **这个库不打算长期用。** 读源码的回报是长期的（你能改、能判断、能给上游提 issue），一次性使用不值得

所以这一章的定位是：**它是一项按需使用的技能，不是一个"想成为高手就必须做"的美德。** 而判断依据是本节前面那张表 —— 你手里有没有一个文档答不上来的具体问题。


## 一个具体的门槛：什么问题文档答不了

上面那张表列了三类问题。这里各给一个真实例子，因为"该不该读源码"的判断完全取决于你能不能问出它们。

| 问题 | 为什么文档答不了 | 读源码花多久 |
|---|---|---|
| `parse_docstring` 的默认值是啥 | 它在签名里，而文档通常只讲"怎么用" | 1 分钟 |
| 出错时抛什么异常 | 文档常写"可能抛异常"而不列全 | 5 到 10 分钟 |
| 这个参数能不能传负数 | 取决于实现里的校验逻辑 | 5 分钟 |
| 缓存是怎么失效的 | 属于内部机制 | 半小时 |
| 我该从哪里改 | 文档不写扩展点 | 视情况 |

前三行是**低成本高回报**的一类 —— 通常几分钟就能确认，而不确认就只能靠猜。第四、五行成本高一些，但它们回答的是"为什么"和"怎么改"，价值也更高。

**一个实用的起步方式：把你最近一次"猜错"的地方记下来。** 那些地方就是该去读源码的点 —— 因为猜错说明文档没覆盖，而你已经付过一次代价了。

## 一个具体的收益：读源码让你能判断"哪些说法不可信"

前面说过读源码提供一手证据。举一个具体的：流传的 LangChain 用法里，很多人写：

```python
@tool
def f(x: str) -> str:
    """说明。

    Args:
        x: 参数的详细说明
    """
```

**这段代码里的 `Args:` 段，在默认配置下是被丢掉的。** 而写它的人以为自己在给模型提供参数说明 —— 因为他读到的大部分示例都这么写。

这个例子说明一件事：**广泛流传的写法不一定是有效的写法。** 而验证它只要十几分钟（读一眼签名，或者跑一次看 schema）。

这也解释了为什么这一章放在最后 —— 它不是新知识，而是一个**验证前面二十章所有说法的方法**。前二十章我尽量标了实测数据，但总有一些地方是引用二手资料的；读源码是补最后那一层的方法。

## 一句可以带走的判据

前面讲了「什么时候该读源码」的三类问题。如果只记一句，记这句：

**当你发现自己在猜某个行为的确切表现时，去读源码。**

「猜」的信号很具体：你写了「应该」「大概」「一般来说」这类词；或者你去搜了别人的博客、论坛、issue。这些都不算证据 —— 而读一次签名或跑一次实验，通常只要几分钟。

**反过来，如果你没有在猜（文档已经说清楚了），那就不必读。** 这一章讲的是按需使用的技能，不是必须完成的美德。## 完整可运行代码

下面这段代码演示三个方法里的第一个：用 inspect 从任意函数取真实文件与行号，并沿着 LangChain 的 `@tool` 追出三层调用链。

```python
"""沿一次任务读到底：@tool 是怎么把函数变成 JSON schema 的。

第 13 章测出一个现象：@tool 生成的 schema 里 day 只有 {"type": "string"}，没有 enum ——
尽管文档字符串写了「只支持明天或后天」。当时我把它记成了「抽象泄漏」。

读了源码之后，结论要**修正**，而且比原来更具体。下面这组对照是这次读源码的产出。

环境：langchain_core 0.3.63 / langchain 0.3.7。实跑状态：2026-10-09。
"""
import inspect, json
from typing import Literal

from langchain_core.tools import tool

DOC = """查天气。

Args:
    day: 只能是「明天」或「后天」
"""


@tool
def a_default(day: str) -> str:
    """查天气。

    Args:
        day: 只能是「明天」或「后天」
    """
    return day


@tool(parse_docstring=True)
def b_parsed(day: str) -> str:
    """查天气。

    Args:
        day: 只能是「明天」或「后天」
    """
    return day


@tool(parse_docstring=True)
def c_literal(day: Literal["明天", "后天"]) -> str:
    """查天气。

    Args:
        day: 查询的日期
    """
    return day


def summary(t):
    return t.args_schema.model_json_schema()["properties"]["day"]


if __name__ == "__main__":
    print("=== 一、调用链（file:line 由 inspect 取真实位置）===")
    from langchain_core.tools import base as base_mod, convert as convert_mod
    for label, fn in [("装饰器入口", convert_mod.tool),
                      ("建 schema", base_mod.create_schema_from_function),
                      ("取 properties", base_mod._get_filtered_args)]:
        src = inspect.getsourcefile(fn).split("site-packages/")[-1]
        print("  %-14s %s:%d" % (label, src, inspect.getsourcelines(fn)[1]))
    print()

    print("=== 二、参数 schema 对照 ===")
    rows = [
        ("A day: str，默认", a_default),
        ("B day: str，parse_docstring=True", b_parsed),
        ("C day: Literal[...]，True", c_literal),
    ]
    for label, t in rows:
        print("  %-32s %s" % (label, json.dumps(summary(t), ensure_ascii=False)))
    print()

    print("=== 三、工具级 description（前 30 字）===")
    for label, t in rows:
        d = (t.description or "（空）").replace(chr(10), " / ")[:34]
        print("  %-32s %s" % (label, d))
    print()

    print("=== 结论 ===")
    print("  1. parse_docstring 默认是 False（convert.py:23/38/52/66/80 五处重载）")
    print("     → 写在 Args: 段里的参数说明**被静默丢弃**，而且原文还漏进了工具级 description。")
    print("  2. 打开 parse_docstring 之后，那句「只能是明天或后天」进了 description ——")
    print("     但**仍然没有变成 enum**。散文只能生成 description，生成不了约束。")
    print("  3. 只有类型标注（Literal）能生成 enum。LangChain 在 base.py:103 用")
    print("     pydantic 的 model_json_schema() 取 schema，约束完全由类型决定。")
    print()
    print("  所以第 13 章那个现象更准确的解释是：")
    print("    **约束写在散文里，就等于把它从「机器可校验」降级成了「模型可以忽略的提示」。**")
    print("    这不是框架丢了信息 —— 是 prose 和 type 承载的东西不同：")
    print("      description ← 文档字符串    enum/range/pattern ← 类型标注")
```

## 常见坑

- **还在学"怎么用"就去读源码。** 文档能回答的问题不该读源码 —— 你会被无关细节淹没。
- **凭记忆写行号。** 一定要用 `inspect.getsourcefile` / `getsourcelines` 取，错了会让整段论述失去可信度。
- **从目录开始读。** 应该从一次真实调用的入口往下追。
- **不写预测就开始读。** 先写下你会怎么猜，跑一遍再对照 —— 预测错的地方最有价值。
- **把"抽象泄漏"当结论。** 那是描述现象，不是解释；要读到"它的机制是什么、怎么改才对"。
- **把读源码当成必须做的美德。** 它按需使用：只在文档答不上来、且你要改或判断边界时。
