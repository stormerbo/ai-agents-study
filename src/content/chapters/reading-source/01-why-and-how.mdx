前面的章节讲的是「怎么用」。这一章讲一个不同的技能：**什么时候需要读实现，以及怎样把问题查清楚。**

## 一个具体的例子

本节用 LangChain Core 0.3.63 的固定示例说明：文档说明、字段 schema 与运行时校验是不同层次。相关源码与完整复现见本节代码和第 3 节的追踪。

先说四个词，因为这一节的结论全部建立在它们的区别上：

- **JSON Schema**（本节简称 schema）：描述工具参数形状的一份机器可读定义。某个 provider/endpoint 是否接受相应的 schema 子集、是否在生成阶段约束输出，要以该接口契约为准。后端类比：接口的 IDL / OpenAPI 定义；应用侧仍需在执行工具前校验参数。
- **文档字符串（docstring）**：写在 Python 函数下面的那段说明文字（三引号包起来），运行时能用 `func.__doc__` 读到。
- **字段 description**：参数 schema 里的自然语言说明，常由函数文档字符串解析得到。工具自身也可以有单独的工具级 description；两者都能帮助模型理解意图，但不等于模型或宿主已经执行了校验。
- **enum**：schema 里声明的**取值集合**，例如 `"enum": ["明天", "后天"]`。它比自然语言更便于机器读取；只有在目标端点支持并执行对应约束时，才会影响生成。宿主仍应在工具执行前按业务规则校验。

落到本节：如果字段只有 description、没有可执行约束，模型仍可能返回「大后天」。若接口没有其它规则，模型输出不会因这条业务要求自动报错；工具宿主必须在副作用发生前校验并拒绝非法值。声明 enum 能让接口以机器可读方式表达范围，但生成期执行与否取决于 endpoint；应用校验仍是本地安全边界。**失败形态是约束遗漏时，问题可能延迟到工具执行才暴露，也可能变成静默业务错误。**

一条边界要记住：**enum 只约束取值，不约束必填** —— 必填由 `required` 表达（第 3、4 节会用到这条）。

第 13 章我测过一件事：用 LangChain 的 `@tool` 装饰器定义一个函数，参数类型是 `str`、文档字符串里写着「只能支持明天或后天」。结果生成的 schema 里，那个参数**只有 `{"type": "string"}`，没有 enum**。

当时的解释是「抽象泄漏」—— 框架丢掉了我写在文档里的约束。这个解释听起来合理，但它把“没有成为字段 schema”与“文本彻底消失”混成一件事。

这一章我去读了源码，结论要改：

```text
@tool 默认 parse_docstring=False
  → 该固定示例里，参数说明没有进入字段 schema 的 description
  → 完整 docstring（包括 Args: 段）出现在工具级 description

打开 parse_docstring=True 之后，参数说明进入字段 description
  → 但它**不会自动变成 enum**
  → Literal 等类型标注或显式 args_schema 可构造字段约束
  → model_json_schema() 导出已构造的 Pydantic schema，不是约束的来源
```

这里的实现细节固定在 `langchain-core==0.3.63`：[convert.py](https://github.com/langchain-ai/langchain/blob/langchain-core%3D%3D0.3.63/libs/core/langchain_core/tools/convert.py)、[structured.py](https://github.com/langchain-ai/langchain/blob/langchain-core%3D%3D0.3.63/libs/core/langchain_core/tools/structured.py) 与 [base.py](https://github.com/langchain-ai/langchain/blob/langchain-core%3D%3D0.3.63/libs/core/langchain_core/tools/base.py)。`StructuredTool.from_function` 将默认推断分支交给 `create_schema_from_function`，显式 `args_schema` 则复用调用方模型；`tool_call_schema` 形成模型可见字段，`model_json_schema()` 导出已有 schema。固定示例的源码定位由完整复现打印，不能将 `_get_filtered_args` 的定义误当作此处的调用节点。本地四组断言只验证该版本下构造出的 schema 与 description，不测试 endpoint 如何生成或执行约束。

所以真实情况比「抽象泄漏」更具体、也更有用：

- **这个示例并非文本完全消失**：默认路径没有把 Args 参数说明解析为字段 description；这段文本仍出现在本例的工具级 description 中。

- **说明与约束承担不同职责**：description 传达意图；类型推断或显式 schema 可表达结构化字段约束。

- **自然语言说明本身不等于机器校验**：是否在生成阶段执行 enum 约束由目标 endpoint 决定，工具宿主应按业务规则校验最终参数。

可执行做法是：用 `Literal` 等类型或显式 `args_schema` 表达机器约束，按需要配置 `parse_docstring` 提取参数说明，对最终 schema 写断言，并在工具执行前验证业务条件。

## 什么时候该读源码

读源码不是越早越好。它有一个明确的门槛，而门槛由**你能问出什么问题**决定。

**不该读的时候**：你还在学"怎么用"，而文档已经覆盖了你的问题。这时读源码是浪费时间 —— 你会被大量与你无关的细节淹没。

**该读的时候**：有三类问题文档回答不了：

| 问题类型 | 例子 |
|---|---|
| **行为的确切边界** | "这个参数默认值是什么？" "出错时返回什么？" |
| **为什么是这样** | "为什么要这样设计？有没有别的选择？" |
| **能不能改** | "我想让它支持 X，从哪里入手？" |

第一类最常见，而且通常能通过固定版本的签名、源码和针对性测试缩小问题范围 —— 本节开头的例子就属于这一类。

## 三个可以立刻用的方法

**方法一：用 inspect 拿真实位置，不要凭记忆。** Python 里一行代码就能得到函数定义在哪个文件第几行：

```python
import inspect
inspect.getsourcefile(func)     # 文件路径
inspect.getsourcelines(func)[1]  # 起始行号
```

这个习惯很重要，因为源码行号会随版本变化。应在目标环境中用 `inspect` 定位，随后阅读相邻上下文并验证调用路径；单独一个 file:line 不能证明结论正确。本节固定版本的行号和对应调用链见第 3 节。

**方法二：从入口往下追，别从目录开始读。** 沿着一次真实的调用往下走（第 3 节会完整演示），每一步只读你需要的那个函数。

**方法三：读之前先写下一个可验证的预测。** 比如「我猜它默认会解析文档字符串」。然后跑一次看结果 —— **预测错了的地方，就是你真正学到东西的地方。** 本节开头那个 `parse_docstring=False` 就是这么发现的：我预测「说明会进 description」，结果它没有把参数说明解析成字段 description；在这个固定示例里，原文仍出现在工具级 description。

## 一个反过来的收益

读源码还有一个不常被提到的收益：**它让你能判断"哪些说法不可信"。**

第 2 章曾记录一个小规模提示注入对照。它至多说明该 fixture 下的观察，不能证明某种标签普遍安全；读源码与做实验都要把结论限定在它们实际覆盖的范围。

源码能提供关于特定版本实现的**一手材料**，但读到代码本身不等于运行时行为已验证。对关键路径，应结合固定依赖、断言和目标环境测试；被广泛转载的“框架内部会做 X”仍需按具体版本核实。

## 一个诚实的提醒

最后说一个反面：**读源码也有明确的成本，而且它不总是值得。**

三个不值得的情况：

- **你只是想用这个库。** 文档够了就读文档 —— 源码是给你"要改它"或"要判断它的边界"时用的

- **你还在选型阶段。** 第 13 章给过选型判据，那不需要读实现（架构和抽象模型更重要）

- **这个库不打算长期用。** 读源码的回报是长期的（你能改、能判断、能给上游提 issue），一次性使用不值得

所以这一章的定位是：**它是一项按需使用的技能，不是一个"想成为高手就必须做"的美德。** 而判断依据是本节前面那张表 —— 你手里有没有一个文档答不上来的具体问题。


## 一个具体的门槛：什么问题文档答不了

上面那张表列了三类问题。这里各给一个真实例子，因为"该不该读源码"的判断完全取决于你能不能问出它们。

| 问题 | 为什么文档答不了 | 读源码花多久 |
|---|---|---|
| `parse_docstring` 的默认值是啥 | 源码签名与目标版本测试可核对 | 几分钟（视环境而定） |
| 出错时抛什么异常 | 文档常写“可能抛异常”；需追调用路径或运行测试 | 依赖具体代码路径 |
| 这个参数能不能传负数 | 查找实现中的输入校验并覆盖边界值 | 依赖验证路径 |
| 缓存是怎么失效的 | 属于内部机制，需追踪写入/读取/失效路径 | 通常需要更多上下文 |
| 我该从哪里改 | 文档不写扩展点 | 视情况 |

前三行通常比追完整架构便宜，但具体耗时取决于依赖安装、入口定位和测试条件；第四、五行需要更多上下文。不要把表里的时间当作验收承诺。

**一个实用的起步方式：把你最近一次"猜错"的地方记下来。** 那些地方就是该去读源码的点 —— 因为猜错说明文档没覆盖，而你已经付过一次代价了。

## 一个具体的收益：读源码让你能判断"哪些说法不可信"

前面说过读源码提供一手证据。举一个具体的：流传的 LangChain 用法里，很多人写：

```python
@tool
def f(x: str) -> str:
    """说明。

    Args:
        x: 参数的详细说明
    """
```

**在 `langchain-core==0.3.63` 的这个默认示例中，`Args:` 没有解析到字段 schema。** 由于没有显式提供工具级 description，原文仍可出现在工具 description 中；这不等于字段约束或参数 description 已建立。

这个例子说明一件事：**广泛流传的写法不一定满足它看上去要表达的契约。** 应检查最终字段 schema 和工具级 description，并验证工具执行前的业务校验。

这也是把源码阅读安排在已有工程经验之后的原因 —— 它不是新知识，而是一个**按需核实实现细节的方法**。它不能替代运行测试、官方契约、线上可观测数据或独立复核。

## 一句可以带走的判据

前面讲了「什么时候该读源码」的三类问题。如果只记一句，记这句：

**当你发现自己在猜某个行为的确切表现时，先明确问题，再选择文档、源码、测试或运行观测来核实。**

「猜」的信号很具体：你写了「应该」「大概」「一般来说」这类词；或者你去搜了别人的博客、论坛、issue。这些都只是线索 —— 接下来要按问题选择证据：查版本文档、读关联实现、写固定断言，或在目标环境跑实验。它们通常比无边界地读完整代码目录更聚焦。

**反过来，如果你没有在猜（文档已经说清楚了），那就不必读。** 这一章讲的是按需使用的技能，不是必须完成的美德。

## 完整可运行代码

下面脚本复核四种 schema 构造方式，并用 `inspect` 定位当前安装版本的入口。它固定检查 `langchain-core==0.3.63`；换版本时应先更新断言，再重新审阅相应源码。**实跑状态：** 2026-10-22，在固定 Python 3.14.7 环境执行通过。

```python
"""Compare LangChain tool descriptions and JSON Schema fields."""
import inspect
import json
from importlib.metadata import version
from typing import Literal

from pydantic import BaseModel, Field
from langchain_core.tools import tool

assert version("langchain-core") == "0.3.63", version("langchain-core")


@tool
def a_default(day: str) -> str:
    """查天气。

    Args:
        day: 只能是「明天」或「后天」
    """
    return day


@tool(parse_docstring=True)
def b_parsed(day: str) -> str:
    """查天气。

    Args:
        day: 只能是「明天」或「后天」
    """
    return day


@tool(parse_docstring=True)
def c_literal(day: Literal["明天", "后天"]) -> str:
    """查天气。

    Args:
        day: 查询的日期
    """
    return day


class ExplicitDay(BaseModel):
    day: Literal["明天", "后天"] = Field(description="显式 schema 的日期")


@tool(args_schema=ExplicitDay)
def d_explicit(day: str) -> str:
    """查天气。"""
    return day


def field_schema(tool_):
    return tool_.tool_call_schema.model_json_schema()["properties"]["day"]


assert "description" not in field_schema(a_default)
assert "Args:" in (a_default.description or "")
assert "只能是「明天」或「后天」" in (a_default.description or "")
assert field_schema(b_parsed).get("description") == "只能是「明天」或「后天」"
assert "enum" not in field_schema(b_parsed)
assert field_schema(c_literal)["enum"] == ["明天", "后天"]
assert field_schema(d_explicit)["enum"] == ["明天", "后天"]
assert field_schema(d_explicit)["description"] == "显式 schema 的日期"

from langchain_core.tools import base as base_mod, convert as convert_mod
from langchain_core.tools import structured as structured_mod
for label, fn in [
    ("@tool", convert_mod.tool),
    ("StructuredTool.from_function", structured_mod.StructuredTool.from_function),
    ("create_schema_from_function", base_mod.create_schema_from_function),
    ("get_input_schema", base_mod.BaseTool.get_input_schema),
    ("tool_call_schema", base_mod.BaseTool.tool_call_schema.fget),
]:
    print(label, inspect.getsourcefile(fn), inspect.getsourcelines(fn)[1])
for label, registered_tool in [("A default", a_default), ("B parsed", b_parsed),
                               ("C Literal", c_literal), ("D args_schema", d_explicit)]:
    print(label, json.dumps(field_schema(registered_tool), ensure_ascii=False))
print(
    "default tool description contains Args:",
    "Args:" in (a_default.description or ""),
)
```

固定版本源码：[convert.py](https://github.com/langchain-ai/langchain/blob/langchain-core%3D%3D0.3.63/libs/core/langchain_core/tools/convert.py) 说明 `parse_docstring` 默认值和入口；[structured.py](https://github.com/langchain-ai/langchain/blob/langchain-core%3D%3D0.3.63/libs/core/langchain_core/tools/structured.py) 与 [base.py](https://github.com/langchain-ai/langchain/blob/langchain-core%3D%3D0.3.63/libs/core/langchain_core/tools/base.py) 展示默认推断、显式 schema、`tool_call_schema` 路径；[Pydantic 文档](https://docs.pydantic.dev/latest/concepts/json_schema/) 说明 `model_json_schema()` 用于导出模型 schema。四组实测的跟踪记录和依赖锁见 `experiments/scripts/verify_reading_source_trace_one_task_review_20261021.py` 与 `experiments/locks/reading-source-compare-py314-macos-arm64-20261021.txt`。

## 常见坑

- **还在学"怎么用"就去读源码。** 文档能回答的问题不该读源码 —— 你会被无关细节淹没。
- **凭记忆写行号。** 一定要用 `inspect.getsourcefile` / `getsourcelines` 取，错了会让整段论述失去可信度。
- **从目录开始读。** 应该从一次真实调用的入口往下追。
- **不写预测就开始读。** 先写下你会怎么猜，跑一遍再对照 —— 预测错的地方最有价值。
- **把"抽象泄漏"当结论。** 那是描述现象，不是解释；要读到"它的机制是什么、怎么改才对"。
- **把读源码当成必须做的美德。** 它按需使用：只在文档答不上来、且你要改或判断边界时。
