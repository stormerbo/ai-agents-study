假设你从一份 2024 年的教程里抄了一段代码，把 `temperature` 从 `0.7` 调到 `0.2` 想让输出更稳定。参数看起来合理，当年也确实管用。

现在它返回 **400**。

不是你的代码写错了。是这三个参数被移除了。

## 先看这三个参数本来做什么

要理解「为什么被移除」，得先知道它们解决的是什么问题。

模型生成下一个 token 时，不是直接给出一个词，而是给**整个词表**上每个 token 打分（称为 logits）。然后从这些分数转成的概率分布里**采样**出一个。

<Mermaid
  chart={`
flowchart LR
    A["输入上下文"] --> B["模型前向计算"]
    B --> C["词表中每个 token 的<br/>原始分数 logits"]
    C --> D{"采样策略"}
    D -->|"temperature"| E["缩放分布的平坦度"]
    D -->|"top_p"| F["截断到累积概率 p"]
    D -->|"top_k"| G["截断到前 k 个"]
    E --> H["最终概率分布"]
    F --> H
    G --> H
    H --> I["采样出一个 token"]
`}
/>

三个参数各自作用在采样的不同环节：

| 参数 | 作用 | 典型效应 |
|---|---|---|
| `temperature` | 把所有 logits 除以温度值后再转概率 | 低 → 分布更尖（倾向最高分）；高 → 分布更平（低分 token 也有机会） |
| `top_p`（核采样） | 只保留累积概率达到 p 的最小 token 集合 | 0.9 意味着只从「最可能的那 90% 概率质量」里采样 |
| `top_k` | 只保留概率最高的 k 个 token | 硬性截断，与概率分布形状无关 |

**为什么当初需要它们？** 因为早期模型的能力不够稳。同一个提示，有时输出太死板（需要调高温度增加多样性），有时又跑偏（需要调低）。这些参数是给使用者的一根**补偿用的旋钮**。

**为什么现在被移除？** 官方的迁移建议很直接：

> 删掉这些参数，改用 prompting 来引导模型行为。

背后的逻辑是：这些旋钮的调节是**盲目**的 —— 你在调一个你不了解内部机制的分布，效果无法预测，而且不同模型上的最优值各不相同。模型能力提升之后，用一两句明确的指令来控制输出风格（「只输出 JSON，不要解释」「用一句话回答」），比调温度更直接、更可预测，也更能跨模型迁移。

理解这三点之后，「被移除」这件事就不再意外了：**它移除的是一根不再需要的补偿旋钮，而不是一种控制能力。**

## 发生了什么

对 Claude Opus 4.6 之后发布的模型，`temperature`、`top_p`、`top_k` 不再被接受（[模型迁移指南](https://platform.claude.com/docs/en/about-claude/models/migration-guide)、[Messages API 参考](https://platform.claude.com/docs/en/api/messages)）：

| 你传的值 | 结果 |
|---|---|
| `temperature` 非 1.0 | 400 错误 |
| `top_p` 小于 0.99 | 400 错误 |
| `top_k` 任意值 | 400 错误 |
| `temperature: 1.0`、`top_p >= 0.99` | 为向后兼容被接受，但**不产生任何效果** |

仍然接受这些参数的只有旧模型。SDK 层面也有变化：Python SDK 从 1.0 起不再定义这些参数，传了会抛 `TypeError`。

### 一个容易被误判的失败模式

**不同平台对同一件事的处理方式不一样**：

- **直连 API** → 返回 400，你会立刻发现
- **通过聚合层（如 OpenRouter）** → 参数被**静默忽略**。请求成功，但你调了半天温度，什么都没发生

后者难排查得多。你会在「为什么调参数没效果」上浪费几个小时，而真相是这个参数根本不存在。**排查这类问题时，第一步永远是打原始响应看状态码** —— 只看 SDK 返回的对象，你甚至不知道服务端接收了什么。

## 但"被移除"不等于"这个概念不存在了"

这是本节最需要建立的认识。

我实测了同一份请求在两个不同端点的行为：

| 实验 | Anthropic 官方 | DeepSeek 兼容端点（实测） |
|---|---|---|
| 传 `temperature: 0.2` | **400 错误**（已移除） | **200 成功**，参数生效 |
| 不传 `max_tokens` | **报错**（必填） | **200 成功**，有默认值 |

（DeepSeek 数据来源：`api.deepseek.com/anthropic`，模型 `deepseek-flash`，2026-09-24 实测。）

同一个参数名，一边报错、一边正常；另一个参数，一边必填、一边可选。**「兼容 Anthropic API」兼容的是接口形状，不是行为语义。**

这有两层意义：

**实践层面** —— 你的代码如果只在 DeepSeek 上测过，迁到 Claude 时会在 `max_tokens` 上撞墙；反过来，代码里传了 `temperature`，在 DeepSeek 上跑得好好的，换到 Claude 新模型就 400。

**架构层面** —— 这正是需要适配层的原因。如果业务代码里散落着 `if provider == 'deepseek'` 这样的分支，每接一家厂商都要改一遍业务逻辑。正确做法是把差异收拢到一处（见第 8 章）。

## 实测：temperature 到底控制了什么

既然 DeepSeek 支持它，我们用真实数据看清这个参数的作用。

同一个提示，分别在两个温度下各跑三次：

```
提示：给一家只卖三种咖啡的小店起个名字，只回名字，不要解释。

temperature = 0:
   #1  三味咖啡
   #2  三味咖啡
   #3  三咖小馆          ← 注意这一次

temperature = 1:
   #1  三咖小铺
   #2  三豆咖啡
   #3  三杯就好
```

（实测数据，模型 `deepseek-flash`，2026-09-24。）

这张表里藏着三个结论。

### 结论一：温度确实在控制输出的发散程度

`temperature=1` 三次全不同，`temperature=0` 三次里两次相同。趋势符合预期。

### 结论二：`temperature=0` **不保证**可复现

这是最容易被误解的一点，也是很多人写测试时踩的坑。

如果温度 0 意味着「确定性」，那三次结果应该完全一致。但实测结果里**第三次不同** —— 前两次是「三味咖啡」，第三次是「三咖小馆」。

原因不止一个：

- **浮点运算的非确定性**：模型的推理涉及大量矩阵运算，在 GPU 上的执行顺序可能因批次大小、并行策略而变化，导致极小的数值差异被放大
- **批处理的影响**：服务端会把多个并发请求打包处理，同一请求在不同批次里的计算结果可能有细微差别
- **服务端版本更新**：模型权重或推理实现可能在你不知情时变化

实践结论：**不要写依赖逐字节相等的测试**。要验证 LLM 输出的正确性，断言应该落在结构性属性上（能否通过 schema 校验、关键字段是否被提取到、是否调用了预期工具），并用一组样本统计成功率。

> 顺带说一句：现在这个坑对你来说已经不是「温度调零够不够」的问题了 —— 在新一代 Claude 模型上 **`temperature` 根本无法设置**。但理解「为什么温度 0 也不可复现」仍然重要，因为同一个误解会以其他形式出现：以为固定了 prompt 就能复现、以为固定了模型版本就能复现。

### 结论三：三次样本不足以得出任何结论

我上面只跑了三次。严格来说，这个样本量**不足以**估计概率分布 —— 三次里两次相同，可能是 67%，也可能是 90%，你无法区分。

这一点值得单独强调，因为它是 AI 应用评估里最常见的统计学错误：**拿三五个样本的对比结果当作结论**。

如果你要判断「方案 A 是否比方案 B 稳定」，需要的样本量取决于你想检测的差异大小。粗略的经验法则：想可靠地发现 10% 的差异，至少需要上百次；发现 5% 的差异，需要上千次。第 13 章会讲完整的评估方法。

## 现在用什么控制：effort

采样参数在 Claude 上走了，但「控制模型花多少力气」这件事没有消失，只是换了杠杆 —— **effort**。

它设置在 `output_config.effort`，有五个级别（[effort 文档](https://platform.claude.com/docs/en/build-with-claude/effort)）：

```python
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=4096,
    messages=[{"role": "user", "content": "分析微服务与单体架构的取舍"}],
    output_config={"effort": "medium"},
)
```

| 级别 | 定位 |
|---|---|
| `max` | 不限制 token 消耗的绝对最强能力 |
| `xhigh` | 长周期任务（30 分钟以上的 agentic / coding），token 预算以百万计 |
| `high` | 按任务需要花费 token，追求最佳结果 |
| `medium` | 平衡速度、成本与性能 |
| `low` | 最省，适合简单任务与子智能体 |

几个必须知道的细节：

**默认值因模型而异，而且变过。** 除 Opus 5.5 外的支持模型默认都是 `high`，**Opus 5.5 的默认是 `medium`**。这意味着从 Opus 5 迁到 Opus 5.5 时，如果你没显式设 effort，请求实际会在**低一档**的强度上运行 —— 这是个很隐蔽的行为变化。

**把 effort 设成默认值，等于没设。** 官方明确说明两者行为完全一致，所以不要为了让代码"看起来更明确"而重复默认值。

**它影响的是全部输出 token**，不只是思考部分：文本、工具调用及其参数、思考都在内。降低 effort 会让工具调用更少、更简短 —— 如果任务依赖多次工具调用来探索，这会直接影响效果。

**Haiku 4.5 不支持 effort。**

> 再澄清一个易混点：`adaptive` 是 **thinking 的模式**，不是 effort 的取值。别把它写进 `output_config.effort`。

## 一个容易踩的坑：effort 会让缓存失效

这是本节最实用的一条。

**顶层的 `output_config.effort` 参与 prompt 的渲染。** 因此如果你在同一个会话的不同请求之间改变它，**之前缓存的 prefix 会失效**（[effort 文档](https://platform.claude.com/docs/en/build-with-claude/effort)）。

也就是说：为了省钱降低 effort，反而可能因为缓存失效而花更多钱。这个反直觉的后果在长会话里尤其明显。

官方的建议：

- 依赖 prompt caching 的长会话，**在开头就定好 effort 并保持不变**
- 需要中途改变的话，用 **per-message effort**（beta 特性，需要 beta header `mid-conversation-output-config-2026-07-01`），它的设计目标正是保留缓存。支持它的模型包括 Fable 5.1、Mythos 5.1、Opus 5.5、Opus 5

另一个相关行为：**在 Opus 5.5 上，adaptive thinking 始终开启、无法关闭**。传 `thinking: {"type": "disabled"}` 会返回 400。所以在这些模型上，effort 是控制「模型思考多少」的唯一杠杆。

## 一次完整的迁移：从旧代码到能跑

把前面的内容串起来，看一个真实的迁移过程。

### 起点：一份当年能跑的代码

从 2024 年的教程里抄来的：

```python
response = client.messages.create(
    model="claude-3-5-sonnet-20241022",
    max_tokens=1024,
    temperature=0.3,      # 想让它稳定
    top_p=0.9,
    system="你是一个严谨的技术助手。",
    messages=[{"role": "user", "content": question}],
)
```

当年它工作得很好。现在你换成了新模型。

### 第一步：报错（或者不报错）

直连 API 的话，你会看到：

```
HTTP 400
{"error":{"message":"temperature: Extra inputs are not permitted", ...}}
```

错误指向很明确：`temperature` 不被允许。

**但如果走的是聚合层，你可能什么错误都看不到** —— 请求成功，温度被静默丢弃。那时你会开始怀疑自己的 prompt 写得不好，在完全错误的方向上排查。

### 第二步：查文档确认

搜「temperature deprecated」，找到官方的[模型迁移指南](https://platform.claude.com/docs/en/about-claude/models/migration-guide)：

> 对 Opus 4.6 之后发布的模型，传 `temperature`（非 1.0）、`top_p`（小于 0.99）、`top_k`（任意值）会返回 400 错误。

删掉那两行。

### 第三步：删完之后仍然不稳

代码能跑了，但输出**仍然不稳定** —— 同一段输入，两次调用可能给出不同措辞。

**这时才意识到：「低温度换稳定」这条路本来就不成立。** 本节的实测已经证明了：`temperature=0` 三次里也有一次不同。

参数从来不是稳定性的来源，它只是一个你无法预测效果的补偿旋钮。

### 第四步：正确的做法

```python
# 1. 删掉采样参数，改用 prompt 明确约束
SYSTEM = """你是一个严谨的技术助手。

输出要求：
- 只输出 JSON，不要任何解释文字
- 字段：{"answer": string, "confidence": number}
"""

response = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=2048,
    output_config={"effort": "medium"},   # 用 effort 控制投入深度
    system=SYSTEM,
    messages=[{"role": "user", "content": question}],
)

# 2. 稳定性靠校验 + 重试，而不是靠参数
data = validate_schema(response.content[0].text)   # 结构不符就重试
```

### 迁移对照表

| 旧做法 | 新做法 |
|---|---|
| `temperature=0.3` 求稳定 | prompt 明确约束 + schema 校验 |
| `top_p=0.9` 控制多样性 | 用 prompt 描述风格 |
| 相信「温度 0 = 可复现」 | 接受不确定性，改用统计指标衡量 |
| 不显式设 effort | 显式设置（默认值已经变过一次） |
| 写精确匹配的测试 | 断言结构属性 + 成功率阈值 |

## 从旧代码迁移的检查清单

1. 搜索代码里的 `temperature` / `top_p` / `top_k`，**全部删掉**
2. 如果原本靠低温度追求稳定性，改为在 prompt 里明确约束输出格式，并加上结构化校验（第 5 章）
3. **检查你对"确定性"的所有假设**。如果你写了依赖输出一致的测试，改成结构性断言 + 成功率统计
4. 显式设置 `output_config.effort`，不要依赖默认值 —— 默认值已经变过一次了
5. 检查有没有把 `thinking` 配置为手动模式（`type: "enabled"` + `budget_tokens`）：这套在 Opus 4.6 / Sonnet 4.6 上已废弃，之后的模型不接受
6. 如果你在用 prompt caching，确认 effort 在整个会话里保持不变

## 常见坑

**以为「参数被忽略」和「参数报错」是一回事。** 直连 API 报错，聚合层静默忽略。排查时先确认请求到底到了哪里、状态码是什么。

**把 effort 当成"输出长度控制"。** 它控制的是投入的总工作量。在部分模型上，改变 effort 并不会可靠地缩短可见回复的长度 —— 那要用 prompt 控制。想控制长度就明说「用三句话回答」。

**在缓存会话里动态调 effort。** 见上文，这会抵消缓存带来的节省。

**拿几次样本的对比就下结论。** 三次里两次相同不能说明「稳定」，只能说明你跑的次数太少。

**为 LLM 输出写精确匹配的测试。** 实测已经证明温度 0 也会变。断言要落在结构上。
