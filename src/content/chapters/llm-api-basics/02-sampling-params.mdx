假设你从一份旧教程抄了 `temperature=0.2`，准备把模型输出变得更稳定。请求返回 400，或者 Python SDK 在本地直接抛 `TypeError`。先别把这两种错误当成同一原因：前者来自目标 API / 模型的请求契约，后者可能来自 SDK 方法签名。

本节讲的不是“采样参数在所有接口里都已消失”，而是**同名参数在 API 版本、SDK 版本、模型和兼容端点上有不同契约**。迁移时要分别核对调用层与服务端，再用目标任务评测参数是否有帮助。

## 采样参数是什么

自回归模型每一步会为候选 token 计算 logits，再经 softmax 形成概率分布。采样参数是在这条过程中改写候选或分布的控制项。以下是常见实现的概念说明；具体应用顺序、默认值、取值范围及模型支持由 provider 定义。

/>

| 参数 | 常见概念 | 需要避免的误解 |
|---|---|---|
| `temperature` | 缩放 logits 后再形成概率分布；低值通常更集中，高值通常更分散 | 低温不等于可复现，也不直接保证正确 |
| `top_p` | 按概率排序，保留累计概率达到阈值所需的候选集合 | `p=0.9` 不是固定 90% 的 token 数，也不是跨 provider 一致的实现细节 |
| `top_k` | 将候选限制在概率最高的 k 项 | 结果仍依赖该请求的概率排序；不是与分布无关的硬编码词表 |

采样参数和 prompting 解决的问题不同。Prompt 描述目标、约束和风格；采样参数改变生成时如何选择候选。结构化输出、校验器与评测负责约束或衡量结果。Anthropic 的迁移文档在部分模型上建议省略已弃用参数并用 prompting 引导，但这不代表 prompt 是温度的等价替代，也不表示其他 provider 已取消采样参数。

## 先分清 SDK 与 API 的契约

截至 **2026-10-22**，Anthropic 的[参数弃用说明](https://platform.claude.com/docs/en/about-claude/model-deprecations)与 [2026-10-21 API 迁移指南](https://platform.claude.com/docs/en/api/migration-2026-10-21)给出了两层边界：使用 API version `2026-10-21` 时，Messages 请求只要携带 `temperature`、`top_p` 或 `top_k` 中任意字段，即使值为默认值也会返回 400；较早 API version 仍允许省略字段，对 Claude 4.7 及之后的模型与 Mythos Preview 则会拒绝非默认值。不要把新 API version 的统一移除规则误写成所有历史 API version 的行为，也不要只按模型发布日期判断。

Anthropic **Python SDK 1.0 及之后版本**也从 Messages 方法签名中移除了这三个参数。直接向 `client.messages.create(..., temperature=...)` 传参会在 SDK 本地抛 `TypeError`，还没发出 HTTP 请求。SDK 官方[迁移指南](https://github.com/anthropics/anthropic-sdk-python/blob/main/MIGRATION.md)说明 `extra_body` 可以把字段直接并入请求 JSON，但它只绕过 SDK 的类型签名，不绕过 API version / model 的服务端校验。SDK 2.0.0 默认切换到 API version `2026-10-21`；在该版本下，改用 `extra_body` 仍会得到 400。只有确实固定在较早 API version、旧模型仍支持非默认采样值且评测证明业务需要时，才考虑保留该字段；并把 SDK 版本、API version、model ID 一并锁定和测试。

| 场景 | 可能发生什么 | 应查哪里 |
|---|---|---|
| 旧 Python SDK，方法签名仍有该参数 | 请求可能被发出，服务端按模型处理 | SDK 锁定版本与模型 API 文档 |
| Anthropic Python SDK 1.0+ | 方法不接受这些关键字，调用前即 `TypeError` | SDK 迁移指南 |
| API version `2026-10-21` 携带任一采样字段（任何模型、包括默认值） | API 返回 400 | API version 迁移指南与当前 SDK 默认版本 |
| 更早 API version 上，Claude 4.7+ / Mythos Preview 的非默认采样值 | API 返回 400 | 模型弃用说明与模型迁移文档 |
| DeepSeek Anthropic-compatible endpoint | 当前兼容表中 `temperature` 支持、`top_k` 忽略，`top_p` 随模型/模式变化 | [DeepSeek 当前兼容说明](https://api-docs.deepseek.com/guides/anthropic_api/) |
| 其他聚合或自托管网关 | 可能转发、拒绝、忽略或改写字段 | 该网关的文档与端到端契约测试 |

所以不要写“Claude 已移除采样参数”或“兼容 Anthropic 就有相同语义”这种无范围的结论。记录 SDK 版本、provider、endpoint、model ID 与请求参数，再测试实际响应；成功返回也不证明参数产生了预期效果。

## 历史样本能说明什么

项目的历史记录保存了一组 DeepSeek `deepseek-flash` 温度对比摘要：提示是为咖啡店起名，`temperature=0` 三次返回两种文本，`temperature=1` 三次返回三种文本，记录日期为 2026-09-24。这个观察与“温度会影响输出分布”相容，但它没有完整请求/响应、固定模型快照或可复核评分器，也只有每个设置三次；因此它**不能证明温度造成了这组差异、不能估计多样性概率，更不能推出温度 0 的跨时间可复现性**。原始数据与撤回范围见项目中的 `docs/DATA.md`。

相同输入得到不同输出并不罕见，但不能用这三次记录归因于 GPU 浮点顺序、批处理、权重更新或其他具体原因。没有服务端 trace、模型版本和重复受控实验，这些都只是待验证假设。教学时应把“结果不保证逐字节复现”作为需要按 provider 合约和重复测试处理的工程边界，而不是把旧样本当作其原因的证明。

如果需要评估参数是否有用，先固定任务集、模型快照（若 provider 能固定）、prompt、解码参数、工具/环境版本与成功判据；随机化调用顺序，记录每次完整配置、终止状态、usage 与原始响应的受控哈希或脱敏记录。按题目或任务分层比较质量、格式错误率、延迟和费用，使用评估章节的方法确定样本量和不确定性。旧文曾给出“检测 10% 差异需上百次”这类无依据的固定样本数建议；样本量应按评估设计推导。

## `effort` 是另一类控制，不是温度的替代品

Anthropic 的 `output_config.effort` 影响一次响应整体投入：文本、工具调用参数，以及启用 thinking 时的 thinking token 都会受影响。低 effort 往往产生更精简的响应和工具调用，但它是**行为信号**，不是输出 token 硬上限，也不是“确定性开关”。`max_tokens` 才是请求级生成上限；质量、延迟和费用变化要在目标任务上评测。

```python
import os

import anthropic

client = anthropic.Anthropic()
model = os.environ["VERIFY_MODEL"]  # 设为目标 endpoint 当前支持的 model ID
response = client.messages.create(
    model=model,
    max_tokens=4096,
    messages=[{"role": "user", "content": "分析微服务与单体架构的取舍"}],
    output_config={"effort": "medium"},
)

print("stop_reason:", response.stop_reason)
for block in response.content:
    if block.type == "text":
        print(block.text)
```

> **实跑状态**：代码结构按 Anthropic Python SDK 示例编写并做语法检查；本轮没有使用 provider 凭据发请求。运行前需安装并锁定 SDK 版本，设置 `VERIFY_MODEL`，并确认目标 endpoint / model 支持 `output_config.effort`。

Effort 当前有 `low`、`medium`、`high`、`xhigh`、`max` 五个命名级别，但**不是每个模型都支持全部级别**。截至 2026-10-21，官方说明大多数支持 effort 的模型默认 `high`，Opus 5.5 与 Haiku 5.5 默认 `medium`；支持模型和能力持续变化，具体矩阵应以[官方 Effort 文档](https://platform.claude.com/docs/en/build-with-claude/effort)为准。显式值等于目标模型默认值时，行为与省略字段相同。

不要把 `effort` 与 thinking mode 混为一谈：thinking 配置说明是否以及如何输出 thinking block；在 adaptive thinking 下，effort 影响模型思考的频率和深度。不同模型默认模式不同，有的不能关闭 thinking，有的旧模式已弃用。迁移时应按当前[Thinking 文档](https://platform.claude.com/docs/en/build-with-claude/thinking)逐模型确认，不能照抄旧的 `thinking: {"type": "enabled", "budget_tokens": ...}` 示例。`adaptive` 是 thinking mode，不是 effort 值。

### 旧 thinking 摘要：只能作为待复核线索

本项目留有一组 2026-10-12 DeepSeek `deepseek-flash` 旧摘要：同一道注水算术题，在未显式设置 thinking 与 `thinking=disabled` 两种配置下各运行三次；摘要记录的 output token 数分别为 `63/83/75` 与 `3/3/2`，六次都显示答案“24小时”。摘要另记两种配置的 input usage 为 70 与 44。

这些数字没有完整逐次请求/响应、模型快照、SDK 版本、终止原因和可复核 scorer。我们无法确认 `thinking` 的实际生效语义，也不能把 input 差异归因于 thinking 字段、把 output 差异归因于 reasoning 内容，或据此声称“准确率没变化”与“关闭思考节省成本”。这里保留它们作为历史记录审计案例，不用作效果证据；在该 endpoint/model 上重新测量前，结论是**未知**。

如果要做这个对照，应先确认模型对 thinking 配置的当前支持情况，再保存匿名化配置与响应摘要，检查完整 `stop_reason`、内容块类型、usage 字段和答案判据；重复多个任务而不是对一个题做三次，并区分模型的 thinking token、可见文本、工具调用和账单字段。对不支持的配置要记录明确的 400/忽略行为，不能把“请求成功”当成参数生效。

## Effort 与 prompt caching 的交互

Anthropic 当前缓存文档说明，**改变 `output_config.effort` 会使 message cache 失效**；改变顶层 effort 时，tool/system cache 是否同时失效取决于模型。显式设置为模型默认值等同于省略，不会造成失效；支持 per-message effort 的模型可通过 `messages` 中的 system message 改变轮次 effort 并保留缓存前缀，但这项能力仍是 beta，需逐模型、逐平台核实。如果会话依赖 prompt caching，先确认目标模型支持的方式，再测量缓存读写；不要只比较 effort 改变前后的总费用，因为输入、输出、模型和缓存状态都会影响账单。此规则属于 Anthropic API，不能外推到兼容端点或其他 provider。

截至 2026-10-22，Anthropic 将 per-message effort 标为 beta：它要求指定 beta header，并且可用模型、云平台及 thinking 模式都有额外限制；官方称这种方式可保留缓存前缀。用之前请读当前 [Effort 文档](https://platform.claude.com/docs/en/build-with-claude/effort)的支持表和限制，不要把 beta 能力当成稳定的通用替代方案。

## 一次完整的迁移：从旧调用到可验证调用

旧代码常把模型名称、SDK 版本和采样参数写在同一个调用里：

```python
# 历史调用形状示意：旧 SDK + API version 2023-06-01；不要在当前 SDK/API version 原样运行。
response = client.messages.create(
    model="claude-sonnet-4-6",  # 演示旧 API version 下的旧式调用形状
    max_tokens=1024,
    temperature=0.3,
    top_p=0.9,
    system="你是一个严谨的技术助手。",
    messages=[{"role": "user", "content": "解释幂等性"}],
)
```

迁移第一步不是盲目删参数，而是把环境具体化：记录 `anthropic` 包的锁定版本、base URL / provider、实际模型 ID，以及传入的所有采样和 thinking 字段。再区分错误发生在哪层：

| 现象 | 可能原因 | 怎么确认 |
|---|---|---|
| Python 调用立刻 `TypeError`，没有 HTTP 请求 | 新版 SDK 方法签名不再接受 `temperature` / `top_p` / `top_k` | 检查锁文件与 SDK 迁移说明；查看客户端的 exception stack，而非猜服务端 400 |
| 服务端返回 HTTP 400 | 该 model/API 拒绝请求中的非默认参数或 thinking 组合 | 记录目标 model ID、API 错误类型和 request ID；对照当前 model-specific 文档 |
| 返回 2xx，改变参数却看不出差异 | 参数可能被忽略、固定、模型不支持，或当前任务无法测出效应 | 做可重复的能力探针与离线 eval；不要把 HTTP 成功当作参数生效 |
| 改 effort 后缓存读数下降 | 顶层 effort 改变可能改变 Anthropic prompt-cache 前缀 | 在固定模型、提示和请求顺序下核对 cache usage；勿用单次总价推断因果 |

对于 Claude API 与 Python SDK 1.x，**两层变更要分别处理**。若调用最新模型，移除该模型拒绝的采样参数，并查看模型迁移文档；若确实固定在仍支持采样参数的旧模型，且实验表明业务需要该设置，Anthropic SDK v1 迁移指南给出的方式是通过 `extra_body` 传递。该方式绕过 SDK 类型签名，不绕过服务端模型校验，不能把旧字段带到新模型上碰运气。

```python
# 迁移后的请求骨架：使用可配置的目标模型，默认不携带采样参数
import json
import os

import anthropic

client = anthropic.Anthropic()
model = os.environ["VERIFY_MODEL"]
system = "你是一个严谨的技术助手。只返回包含 answer 字段的 JSON 对象。"
response = client.messages.create(
    model=model,
    max_tokens=2048,
    system=system,
    messages=[{"role": "user", "content": "用一句话解释幂等性"}],
    output_config={"effort": "medium"},
)

if response.stop_reason != "end_turn":
    raise RuntimeError(f"incomplete response: {response.stop_reason}")
text = "".join(block.text for block in response.content if block.type == "text")
value = json.loads(text)
if not isinstance(value, dict) or not isinstance(value.get("answer"), str):
    raise ValueError("response does not match the expected object shape")
print(value["answer"])
```

> **实跑状态**：本例展示 Anthropic Messages SDK 的调用形状；本轮没有使用 provider 凭据发送请求。语法与本地错误分支可离线检查，但 SDK 集成、目标模型对 effort 的支持和 JSON 输出都需在实际锁定版本及 endpoint 上验证。Prompt 要求 JSON 不等于结构化输出保证，正式应用应按第 5 章使用可用的 schema 能力并验证业务条件。

代码中故意将 `VERIFY_MODEL` 作为环境配置，避免教材把短期 model alias 写死。运行前在 `.env.local` 或当前 shell 设置目标环境变量；不要把密钥硬编码进教程或终端回显。确认 SDK 参数兼容后，再发最小探针请求并检查 response 的 `stop_reason`、内容块和 usage。

迁移验收不应以“请求不报错”为终点。至少建立一份按模型/endpoint 区分的契约检查：旧 SDK 接受的字段是否被 1.x 本地拒绝；目标 API 接受哪些参数和值；2xx 响应中的设置是否真实影响了行为；输出通过什么结构和任务判据；变化是否影响缓存、延迟与费用。若 provider 不支持固定模型快照，就把后端可能变化列为限制，记录请求日期与返回的 model 字段。

## 把参数实验做成可复核的验收

一次迁移实验应留下可供他人复跑和审查的产物，而不只是一句“体感更稳定”。最小记录包括：数据集版本与每题输入、完整请求配置、SDK/provider/endpoint/model 标识、请求时间、响应正文或受控脱敏副本、`stop_reason`、usage、解析结果与逐题判分。凭据不得进入记录；如响应含用户数据，应先定义访问权限和保留期限。若服务端只返回浮动别名，记录响应中的 model 字段和日期，并把无法固定权重版本写进限制。

比较时以同一批题目作为配对样本，对每道题分别运行基线与候选配置，并随机化两者的调用顺序，减少题目难度和时间顺序带来的混杂。先定义主指标，例如任务通过率或格式错误率，再把延迟、token usage 与账单字段作为成本指标；失败、拒答、截断和服务端错误必须各自分类，不能从均值里消失。若目标是判断“是否改善”，应事先定义最小有意义差异及置信区间；若区间仍同时覆盖有意义的正负效果，结果应报告为不确定，而不是挑较好的一次。

一个可审查的结果表至少按题目列出基线/候选的判分、失败类别和成本，并汇总配对差值、样本范围、置信区间、排除规则及其理由。遇到 provider 限流、版本漂移或模型响应异常，保存原始事件并标记该次无效原因；不要只重跑失败组。这样的验收能回答“这个设置在这组任务上是否值得”，但不能自动推出其他模型、提示或生产流量也会得到同样结果。

## 迁移检查清单

1. 锁定并记录 SDK 版本、provider、base URL 和完整模型 ID，不把“兼容 Anthropic”当作行为等价。
2. 根据目标模型文档逐项检查 `temperature`、`top_p`、`top_k` 及 thinking 配置。不要机械地全删，也不要跨模型复制。
3. 若 Python SDK 1.0+ 因签名抛 `TypeError`，先判断目标旧模型和 API version 是否仍接受该参数；只有确有需要并已验证服务端支持时，才按 SDK 指南使用 `extra_body`，并将 SDK 与 API version 一起锁定。
4. 用一组代表性任务评测变更前后质量、格式、失败率、延迟和账单字段。固定样本量应按期望检测的差异和评估设计推导，不使用“三次”“上百次”等通用门槛。
5. 输出稳定性依靠明确判据、schema/业务校验和有版本的 eval；低温或固定 prompt 都不保证相同文本。
6. 若使用 Anthropic prompt caching，评测 effort 或 thinking 配置变更对 cache prefix 的影响；beta 能力必须逐模型、逐平台核验。

## 常见坑

- **把 SDK 错误和 API 错误混为一谈。** `TypeError` 可能在请求发出前发生；服务端 400 则需要看错误体与 request ID。
- **把一个发布时间当作全模型分界。** 参数支持随模型代际和接口版本变化，按具体目标模型查表。
- **把 2xx 当作参数生效证据。** 兼容端点可能忽略字段，部分字段还会依模型或模式变化。
- **把 `effort` 当成 temperature 的替代品。** 它控制的是响应投入行为，不提供采样多样性开关，也不是 token 上限。
- **把 prompt 当作稳定性或格式保证。** Prompt 只能传达指令；用 schema、业务校验和按任务构建的评估判定结果。
- **用几次样本声称因果或普遍规律。** 本节留下的温度与 thinking 数字都是无法独立复核的历史摘要；它们不能支撑模型行为结论。
