## 先把第一次调用跑通

这一节后面全是数字，但数字只有跑起来才有意义。所以先花五分钟把环境搭好 —— 后面每一节的脚本都复用这四个东西。

```bash
pip install anthropic
```

**四个环境变量，脚本只读它们：**

| 环境变量 | 填什么 | 说明 |
|---|---|---|
| `ANTHROPIC_AUTH_TOKEN` | 你的 API Key | 在厂商控制台建一把**专用的、限额的** Key（拿 Key 的四步见第 0 章第 4 节） |
| `ANTHROPIC_API_KEY` | 同上，二选一 | 脚本的写法是「先看 `ANTHROPIC_API_KEY`，没有再用 `ANTHROPIC_AUTH_TOKEN`」—— 官方端点习惯用前者，兼容端点习惯用后者，填一个就行 |
| `ANTHROPIC_BASE_URL` | 端点地址 | **留空则用 Anthropic 官方端点**；用兼容端点则填它给的地址，如 `https://api.deepseek.com/anthropic` |
| `VERIFY_MODEL` | 模型名 | 必须是该端点真的支持的名字。写错时 DeepSeek 的错误信息会把可用模型名列出来 |

设好之后先跑这个最小示例（6 行逻辑，不用建文件）：

```python
# hello.py —— 第一次调用：只关心 usage 与 stop_reason
import os

import anthropic

client = anthropic.Anthropic(
    api_key=os.environ.get("ANTHROPIC_API_KEY")
    or os.environ.get("ANTHROPIC_AUTH_TOKEN"),
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),   # 留空用官方端点
)

resp = client.messages.create(
    model=os.environ["VERIFY_MODEL"],
    max_tokens=600,
    # 输出长度上限：达到后可能拿到不完整文本/工具参数，必须检查 stop_reason
    messages=[{"role": "user", "content": "只回复两个字：收到"}],
)

print("stop_reason:", resp.stop_reason)
print("input/output:", resp.usage.input_tokens, resp.usage.output_tokens)
print("blocks:", [b.type for b in resp.content])
```

它在 DeepSeek 的兼容端点上输出（**本次实跑，2026-10-12**）：

```text
stop_reason: end_turn
input/output: 35 16
blocks: ['thinking', 'text']
```

**三个数字先把后面的内容锚住：**

1. `input_tokens = 35`，而这句提示只有 7 个字符 —— 这是该 endpoint 对这次完整请求的 usage 记录；不能仅凭差值把 token 归因给消息封装。

> 顺带把第一个字段定义掉：`max_tokens` 是**单次响应允许生成的输出 token 上限**，不是输入长度或整个会话的上限。达到它时，结果可能不完整；如何确认要看该 API 的停止原因和任务级校验。
2. `blocks = ['thinking', 'text']`：这次特定 DeepSeek 响应包含 `thinking` 与 `text` 两种内容块。内容块类型不能推出 CoT 提示的效果，也不应把 thinking 当成面向用户的正文。
3. `stop_reason` 用来解释协议层为什么结束，不是任务成功的唯一判据。把这次请求的 `max_tokens` 降到 64 后，历史记录出现了下面的结果：

（本地历史响应记录，`deepseek-flash`，小 `max_tokens` 探测：HTTP 200、`stop_reason=max_tokens`、`output_tokens=5`，内容只有非文本 block，没有 text block。原始报告包含 provider 返回的内部 reasoning 字段；这里不展示其内容。它只说明这次探测没有可见答案，不能推广到其他模型/provider。）

处理时至少分两步：先按 provider 协议处理 `stop_reason`（如截断、工具交接、拒绝或正常结束），再用业务判据校验期望产物。即使是 `end_turn`，也只说明该 API 的生成轮次自然结束，不证明答案正确或动作成功。

现在看一组实测数据。这是我用同一个端点、同一个模型，对不同文本做 token 计数得到的结果：

| 文本 | 字符数 | token 数 | 每字符消耗 |
|---|---:|---:|---:|
| `什么是幂等性？` | 7 | **35** | 5.0 |
| `What is idempotency?` | 20 | **37** | 1.85 |
| `什么是幂等性？` × 50 | 350 | **280** | 0.80 |
| `What is idempotency? ` × 50 | 1050 | **381** | 0.36 |
| `func main() { fmt.Println("hello") }` | 36 | **40** | 1.11 |

（数据来源：DeepSeek 的 Anthropic 兼容端点，模型 `deepseek-flash`，2026-09-24 实测。完整脚本见本章附录。）

这张表是 **2026-09-24 在一个 DeepSeek Anthropic-compatible endpoint 上得到的五条历史单次记录**。它展示同一个端点里，几个不同字符串的计数可以差很多；它不是对语言、模型或 tokenizer 的受控比较。

这组数里有三个直观观察：

**第一，7 个字符的短句要 35 个 token。** 如果 token 和字符是简单比例关系，这个数字应该是 5 左右。

**第二，短英文样本（20 字符）比短中文样本（7 字符）多 2 个 token。** 两个句子字符数、内容和分词边界都不同，不能据此得出中英文谁更省。

**第三，长样本的 token/字符比不同**（0.80 vs 0.36），但文本是重复短语，仍不足以代表一般中文、英文或业务文本。

这几条记录**不能单独识别固定请求开销**。不同 tokenizer 切分、消息封装、服务端自动加入内容、输入数据和 endpoint 计量口径都可能影响 `input_tokens`；要确认结构开销，需要受控的成对请求、完整请求参数与原始 usage。

算一下：短句 35 token 减去 7 个字符的「真实内容」（约 5 token），剩下约 30。英文短句同理：37 减去约 5，还是约 30。

下面的方程只演示一种**假设下的拟合**，不是由这两行观测证明了固定开销：

```text
7   字符 → 35 token        （短句）
350 字符 → 280 token        （同一个短句 × 50）

假设每个字符的成本线性且有一个固定项：
   7a + b = 35
 350a + b = 280
相减： 343a = 245  →  a ≈ 0.714
代入： b = 35 - 7×0.714 ≈ 30.0
这只是两参数模型对两条数据的精确拟合；它没有检验线性假设，也没有证明 b 来自消息结构
```

（数据来自本地留存的 2026-09-24 历史报告；请求快照、服务端模型指纹与可重复试验未归档。`a` 和 `b` 是人为选定线性形式后算出的参数，不是 API 字段或已确认的机制。重复 50 次同一短语也不能证明字符成本恒定。）

不要把拟合出的 `b` 直接解释成 `role`、`content` 等字段的 token 费用，更不要把它当作每次调用都固定发生的账单。若要估算生产成本，应记录目标 endpoint 的响应 usage，并对照该 endpoint 当前的计费字段与规则。

一旦理解这一点，前面三个现象就都通了：

- 仅凭字符数不能推算 token；应使用目标模型/tokenizer 的计数方式
- 真实工作负载应按相同 endpoint、模型、请求结构和任务采样，报告计数与 usage 的口径
- 模型间迁移时，不复用未经核验的历史 token/char 比率

> 历史观测和拟合本身不能确定开销来源。若你关心输入计数，使用对应 provider 的计数端点或实际响应 usage，并在版本变化后重测。

这一节要讲的就是这个单位：它怎么来的、怎么算、以及为什么它是后面所有成本与容量问题的根源。

## 为什么需要 token 这个东西

最直接的问题是：模型为什么不直接处理字符？

模型以离散 token ID 序列作为输入。tokenizer 的一个重要作用，是在词表规模与序列长度之间做工程折中：更大的子词单元可缩短某些常见文本的序列，但也增大词表/embedding 与输出层等成本；具体取舍由模型设计决定。

计算成本也不能简化成“token 数翻倍就总成本四倍”。以**标准 dense self-attention 的 prompt prefill**为例，注意力计算随序列长度呈二次增长；使用 KV cache 的自回归解码中，每个新 token 的注意力仍需读取已有上下文，整体成本还取决于输入长度、输出长度、模型结构与实现。工程上用 token 作为容量和成本核算的重要指标，但实际开销以目标模型/API 的规格、usage 与测量为准。

字符与 UTF-8 字节数也不等于模型位置数。模型处理的是 tokenizer 编出的 token 序列，所以本地 `len(text)` 只能用于展示样本长度，不能用来推断模型上下文占用。

## token 是怎么切出来的

tokenizer 把输入文本编码成模型使用的 token ID 序列。BPE、Unigram 等子词方案很常见，但不同模型可能使用不同词表、预分词规则和编码细节，不能仅凭一套通俗算法解释所有 tokenizer。

以 BPE 的一种典型训练思路为例：

1. 从单个字符（或字节）开始，每个都是独立单元
2. 统计语料里哪两个相邻单元出现最频繁，把它们合并成一个新单元
3. 重复第 2 步，直到词汇表达到预设大小

这类训练过程会让某些常见片段容易成为 token，但具体编码结果仍由目标 tokenizer 决定：

| 内容 | 典型切法 | 原因 |
|---|---|---|
| 常见英文词 | 某些 tokenizer 可能编码成少量 token | 取决于词表、大小写和边界规则 |
| 生僻术语 | 可能被拆成多个子词或字节 token | 取决于模型训练的 tokenizer |
| 代码标识符 | 可能按常见片段、标点或字节拆分 | 代码格式和 tokenizer 都会影响结果 |
| 随机字符串 | 可能需要较多 token | 具体数量须用目标 tokenizer 测量 |

**关键推论**：token 是 tokenizer 对表面输入的编码单位，不是可靠的语义边界。语义相近的词可能切法不同，语义无关的字符串也可能有相同切法；同长度的 `1234567` 和 `7654321` 也不保证 token 数相同。不要用数字长度或语言类别代替实际计数。

历史表格中的代码样本为 36 字符、40 token，但它只是一个字符串的一次记录。不能据此断言代码通常比英文贵三倍；要比较应对目标仓库/提示做成组采样，并保持模型和请求结构一致。

## token/字符比为什么不能跨文本外推

历史记录中，一条重复中文短语为 350 字符 / 280 input tokens，一条重复英文短语为 1,050 字符 / 381 input tokens。

这两个样本不是语义等价的中英对照，长度也不同，因此**不能证明中文普遍更贵**。token/字符比会受 tokenizer、具体文本、标点、代码、空白与模型版本影响。对业务容量规划，选取代表性文本并用目标模型测量；不要套用本节两个比率。

要比较语言差异，可构造意义相同的句子对，控制长度与领域，覆盖多条样本，再记录模型名、tokenizer/API、输入结构与测量日期。即便如此，结论也只适用于该样本集合；上下文容量不要按“字符数”换算。

## 新分词器：一次约 30% 的 token 计数变化

这里说明一项可能影响容量与费用估算的变化。

Anthropic 当前 token-counting 文档明确列出的共享该 tokenizer 的型号是 Claude Fable 5.1、Mythos 5.1、Fable 5 与 Mythos 5；文档称它由 Opus 4.7 引入，并说明同一提示在这四个型号上的计数一致，且相较 Opus 4.7 之前的模型约高 30%，具体增幅取决于内容。不要把这句话扩展为“所有 4.7 及之后的 Claude 型号”或 Mythos Preview；需要比较其他型号时，按目标型号重新计数。[Token counting 文档](https://platform.claude.com/docs/en/build-with-claude/token-counting)（核对日期：2026-10-22）。

这不是小事。它意味着：

1. **从旧模型迁移时不要直接复用计数。** 对官方所述同一输入，token 数平均变化约 30%，具体工作负载要单独核实；官方建议用目标模型重新数。
2. **旧教程里的经验法则会失效。** 「一份文档大概多少 token」这类直觉是绑定在某个分词器上的，换个模型就可能不准。
3. **成本和容量都要重新核算。** 如果某个输入计数恰好增加 30%、单价不变且没有阶梯或缓存等因素，该输入部分的 token 费用会随计数增加 30%；在固定 token 窗口里，同类内容能装入量的理想化比例是 `1 / 1.3 ≈ 76.9%`（约少 23.1%），实际还取决于内容分布、窗口和计价规则。

> 以上 30% 是官方对其特定模型 tokenizer 的近似说明，不是本项目的新旧模型实测。迁移前应按目标模型对同一组请求重计数，并检查费率、缓存与长上下文阈值。

## 上下文窗口：一个有上限的工作台

理解了 token，上下文窗口就很好定义了。

**上下文窗口是模型处理一次请求时的容量约束；具体哪些输入、输出及内部推理 token 计入约束，要按所用模型和 API 文档确认。** 许多模型的规划可以先用「输入占用 + 预留输出」检查是否放得下，但这只是理解容量的简化模型，不能当成跨供应商通用公式。

以 Anthropic Messages API 的 Claude 为例，[上下文窗口文档](https://platform.claude.com/docs/en/build-with-claude/context-windows)说明请求消息（包括工具结果、图像和工具定义）以及生成输出都计入窗口；在这个语义下可用下面的近似不等式做容量规划。OpenAI 也说明其窗口定义会涵盖输入、输出及部分模型的 reasoning tokens，具体规则仍需按模型文档确认：

```text
本轮输入占用 + 预留的生成空间 ≤ 该模型的上下文窗口
```

它回答的是「请求能否装入上下文」，不是「账单会如何计量」。上下文占用和 billable usage 是两种口径：缓存读写、图像/音频等模态、reasoning tokens、工具调用的独立费用或运行时费用，可能以供应商特定字段或 SKU 计量。例如 Anthropic 的 usage 会分别列出 cache read / write tokens，OpenAI Responses API 会提供 input、output 及 reasoning-token 明细；它们的价格规则也不同（见 [Anthropic 定价文档](https://platform.claude.com/docs/en/about-claude/pricing) 和 [OpenAI Responses API usage 字段](https://developers.openai.com/api/docs/api-reference/responses/object#responses/object-usage)）。核算成本时按端点返回的 usage 字段与当前价格规则逐项计算，不要把 `input_tokens + output_tokens` 当作通用账单公式；设置运行预算时也应明确它约束的是上下文容量、可计费 token、金额还是其他运行资源。

上下文窗口属于模型规格，型号升级后可能变化，不能从模型家族名或旧章节表格推断。以 2026-10-21 查阅的 [Anthropic Context Windows](https://platform.claude.com/docs/en/build-with-claude/context-windows) 和[模型总览](https://platform.claude.com/docs/en/models/overview)为例，当前列出的 Opus 5.5、Sonnet 5.5、Haiku 5.5 为 1M token；Haiku 4.5 为 200K。要用于容量规划，先按部署平台与精确 model ID 核对官方模型页或 Models API。

**不要把 1M token 换算成固定的中英文字符数或书本页数。** 同一个窗口能容纳多少自然语言、代码、工具定义、图像内容或历史消息，取决于实际 tokenizer 和输入结构。按代表性请求做 token count，再为输出、工具结果、系统消息和安全余量留容量。

1M token 是很大的名义窗口，但这会带来一种危险的错觉：能装下不代表适合全部塞进去。

## 危险之处：「能装下」不等于「能用好」

既然窗口这么大，把整个代码库、全部文档、所有历史对话都塞进去不就行了？

不行。有两个独立的机制在阻碍你。

### 机制一：上下文变长后，任务表现可能下降

上下文窗口能容纳多少 token，只说明接口允许输入的上限，不能保证模型在所有任务中都能同样有效地利用这些信息。长上下文下的表现会受到任务、模型、信息位置、干扰项和提示结构等因素影响；不能简单解释成「有限注意力平均摊到每个 token 上」。工程上应把它当作需要针对目标任务测量的风险，而不是一个适用于所有模型的固定定律。

### 机制二：部分长上下文任务存在位置效应

论文 *Lost in the Middle* 在特定模型和检索任务设置中改变关键信息的位置，发现一些设置下模型对位于上下文中间的信息利用率较低，曲线呈 **U 形**；不同模型、任务和上下文长度的结果并不必然相同：

论文 *Lost in the Middle*（[arXiv:2307.03172](https://arxiv.org/abs/2307.03172)，TACL 2024）报告了这些受测设置的结果。它支持的结论是：长上下文中的信息位置可能影响特定任务表现，不是所有模型、任务都必然呈现同样的曲线。

> 在论文的一些测试设置中，把答案线索放在长上下文中部，表现可能低于放在开头或结尾；这不能外推为「一定比只给这一句话还差」，也不能据此断言原因必然是周围内容造成干扰。

可用于工程实践的假设（需在目标模型与任务上验证）：

- 通过位置对照实验，检查关键约束放在不同位置是否影响目标任务表现
- 长参考资料可先评估检索、压缩或分段方案，比较质量、延迟和成本后再决定
- 若观察到位置效应，再依据实测结果调整提示结构；不存在适用于所有模型与任务的固定放置规则

### 这些现象意味着什么

把窗口上限与上述实证结果合起来看：

```text
上下文窗口的标称容量  ≠  模型实际能用好的容量
```

**「窗口还有空间」不能作为继续塞内容的理由。** 这是第 3 章「上下文工程」要解决的核心问题 —— 那一章会讲具体的压缩、检索与隔离策略。

## 完整项目：一个输入 token 估算器

前面所有概念，落到工程上就是一个工具：**在发请求之前，估算目标模型会收到多少输入 token。** 计数结果不是账单金额，也不能单独预估未知长度的生成输出。

这类工具的价值在批量任务上尤其明显。等你跑完一万次调用再看账单，已经晚了。

下面的脚本调用 Anthropic 官方 Messages token-counting endpoint；它不是跨 provider 通用实现。运行前安装 Anthropic Python SDK，并提供官方 API key 和当前有效的 model ID。Python 3.10 或更高版本可直接运行：

```python
# input_token_estimator.py
"""用 Anthropic 官方 endpoint 估算请求的输入 token；不估金额或生成输出。"""

import os

import anthropic

# 凭据从环境变量读取，不要硬编码在代码里
api_key = os.environ.get("ANTHROPIC_API_KEY") or os.environ.get(
    "ANTHROPIC_AUTH_TOKEN"
)

if not api_key:
    raise RuntimeError("请设置 ANTHROPIC_API_KEY 或 ANTHROPIC_AUTH_TOKEN")

client = anthropic.Anthropic(api_key=api_key)  # 本脚本面向 Anthropic 官方 endpoint

MODEL = os.environ["VERIFY_MODEL"]  # 填当前官方 Models API 支持的 ID/alias


def count_input(messages: list[dict], system: str | None = None,
                tools: list[dict] | None = None) -> int:
    """估算给定 Anthropic Messages 输入的 input_tokens。"""
    kwargs = {"model": MODEL, "messages": messages}
    if system is not None:
        kwargs["system"] = system
    if tools is not None:
        kwargs["tools"] = tools
    result = client.messages.count_tokens(**kwargs)
    return result.input_tokens


def main() -> None:
    samples = {
        "短中文": "什么是幂等性？",
        "短英文": "What is idempotency?",
        "长中文": "什么是幂等性？" * 50,
        "长英文": "What is idempotency? " * 50,
        "代码": 'func main() { fmt.Println("hello") }',
    }

    print(f"模型: {MODEL}\n")
    print(f"{'样本':<10}{'字符数':>8}{'token':>8}{'每字符':>9}")
    print("-" * 36)

    for label, text in samples.items():
        messages = [{"role": "user", "content": text}]
        tokens = count_input(messages)
        print(f"{label:<10}{len(text):>8}{tokens:>8}{tokens / len(text):>9.2f}")


if __name__ == "__main__":
    main()
```

运行它（还需在本节开头的环境变量中设置 Anthropic 官方 key 与一个当前有效的官方模型 ID；本脚本不设置 `ANTHROPIC_BASE_URL`）：

```bash
export ANTHROPIC_API_KEY="..."
export VERIFY_MODEL="<当前支持的 Anthropic model ID>"
python3 input_token_estimator.py
```

DeepSeek 的 Anthropic-compatible 文档没有承诺与 Anthropic 官方相同的 `/v1/messages/count_tokens` 能力。若改用兼容端点，应先独立验证计数请求与版本；也可以在真实 Messages 响应中记录 DeepSeek 返回的 `usage`，但这发生在创建消息之后，不能称为免费预估。

输出是每条输入的 token-count estimate，不保证与实际 message usage 完全相同。你可以改 `samples`，加入与线上一致的系统提示、客户端工具定义和历史消息；若要计数图像或 PDF，按 Anthropic 文档要求使用 base64 source。注意该 endpoint 不接受部分 server tools、MCP connector，以及 URL/file source 的 image/document block；这些请求应以实际 Messages 响应中的 usage 为准，不能把示例扩写成“支持所有多模态输入”。即便计数准确，它仍只覆盖输入，金额估算还要使用对应模型的当前输入/输出/缓存费率，并为输出量建立独立假设。

> **实跑状态**：上方 token 数来自 DeepSeek Anthropic-compatible endpoint 的 2026-09-24 历史记录；原始本地报告保存在被 git 忽略的 `verify-output/report.json`，未作为可复现数据集提交。代码示例在本轮未对 provider 发请求；应先在干净环境按目标 SDK 版本运行，再标记该环境实跑。历史 SDK 0.39.0 / 1.12.1 的调用路径观察只适用于当时版本，不再作为当前 SDK 接口保证。

## 历史错误探测

以下状态码来自 2026-09-24 的 DeepSeek 兼容端点历史报告。除错误响应摘录外，正文只列出能从归档中核实的字段；不要把这组记录视为当前 provider 契约。

### 案例一：模型名写错

```json
{
  "error": {
    "message": "The supported API model names are deepseek-flash, deepseek-v4-pro, but you passed .",
    "type": "invalid_request_error",
    "param": null,
    "code": "invalid_request_error"
  }
}
```

HTTP 状态码 400。

这个错误信息**本身就值得学习**：它不只说了「模型名无效」，还直接把当前可用的模型名列了出来。对比一下常见的 `{"error": "invalid model"}` —— 后者会让你去翻文档，前者让你当场就能改对。

**给你自己的 API 设计的启示**：错误信息应该包含「调用方能据此采取行动」的信息。这条能做到，很多 API 做不到。

### 案例二：小 `max_tokens` 后没有可见文本

2026-09-24 的 DeepSeek `deepseek-flash` 历史探测中，`max_tokens=64` 的请求返回 HTTP 200，`stop_reason=max_tokens`、`output_tokens=5`，响应里没有可见文本块。原始归档没有记录 JSON 解析过程，因此不能把它写成真实发生过的 `JSONDecodeError`，也不能仅凭这次响应断言模型内部为何没有生成文本。

可复用的工程结论更窄：对 Anthropic Messages API，`stop_reason=max_tokens` 表示生成达到请求上限；它是需要由调用方处理的完成状态之一。不要把“HTTP 200”当作业务输出完整的证明，也不要假设每种截断都必然形成半截 JSON。先按目标 API 的返回结构收集文本与停止原因，再决定重试、降级或报错。

下面是一个最小的 Anthropic Messages API 检查示例：

```python
import os

import anthropic

client = anthropic.Anthropic()
MODEL = os.environ["VERIFY_MODEL"]
prompt = "只回复两个字：收到"

response = client.messages.create(
    model=MODEL,
    max_tokens=2048,                      # 1. 留足余量，别卡着预期长度设
    messages=[{"role": "user", "content": prompt}],
)

# 检查停止原因，并显式提取文本 block
if response.stop_reason == "max_tokens":
    raise RuntimeError("生成达到 max_tokens；按应用策略重试或降级")

text_blocks = [block.text for block in response.content if block.type == "text"]
if not text_blocks:
    raise RuntimeError(f"响应没有文本内容，stop_reason={response.stop_reason!r}")
text = "".join(text_blocks)
# 只有在应用明确要求 JSON、且 API 返回了可解析文本时，才调用 json.loads(text)
```

> **实跑状态**：代码可通过语法检查；本轮未使用 Anthropic 凭据调用 provider。接入应用前，应按当前 SDK 和目标模型执行集成验证。

**关键点**：检查 `stop_reason` 是协议状态处理的一部分，但需结合 API 的内容块与其他终止状态解释；不同 provider 的字段语义必须查各自文档。

### 案例三：跨厂商的意外行为

这是最有意思的一个，因为它演示了「兼容」的真实含义。

我用同一个端点做了三组对照实验：

| 实验 | Anthropic 官方行为 | DeepSeek 兼容端点实测 |
|---|---|---|
| 不传 `max_tokens` | Anthropic Messages API reference 将其列为必需参数 | 2026-09-24 历史探测：HTTP 200；不能推广为当前默认行为 |
| 传 `temperature: 0.2` | Claude 4.7+ / Mythos Preview：非默认值返回 400 | 2026-09-24 历史探测：HTTP 200；不能由状态码判断参数是否生效 |
| 空模型名 | 由目标模型和 API 校验规则决定 | 2026-09-24 历史探测：HTTP 400，并回报支持的模型名 |

这两次观测提醒我们：兼容端点需要按版本重新验证；它们只是 2026-09-24 的 HTTP 响应记录，不足以证明语义完全相反或参数生效。

这个结果有两层意义：

**第一层，实践层面。** 你的代码如果只在某一兼容端点上测过，迁移到 Anthropic 或另一版本时仍需核对必填参数、参数约束和终止状态。HTTP 200 只证明该次请求被接受，不能证明参数按预期生效。**「兼容 Anthropic API」不代表行为一致** —— 兼容的是接口形状，不自动保证语义。

**第二层，架构层面。** 这正是为什么需要适配层。如果业务代码里直接散落着 `if provider == 'deepseek'` 这样的判断，每接一家厂商就要改一遍业务逻辑。正确做法是把差异**收拢到一处**（见本章第 6 节「Provider Contracts」），让上层只面对有明确能力边界的接口。

## 常见坑

**按字符数估算 token。** 本节五个 2026-09-24 历史样本的 token/字符比在 0.36 到 5.0 之间；它们不是受控对照，也不能代表其他文本或模型。容量规划应使用目标 provider 的 tokenizer/计数接口，或以目标请求的实际 usage 校准。

**把样本差异当成固定开销。** 历史短句样本不能证明每次调用都有固定约 30 token 的结构开销。若关心具体请求形状，应计入 system、tools、消息结构与多模态内容，并在目标 provider 上实测。

**把上下文窗口当「输入预算」。** 输出也占额度。要求结构化输出时要留出充足空间。

**把 `max_tokens` 卡在预期长度附近。** 输出的长度是概率性的，卡得太紧就会间歇性截断，表现为「偶尔报 JSON 解析错误」这种极难定位的 bug。

**不检查 `stop_reason`。** 对本节使用的 API，按其协议状态判断输出是否正常完成、被截断或需其他处理；不能只凭文本内容推断完整性。不同 API 的字段和值应由适配层分别解释。

**假设跨厂商行为一致。** 一次兼容端点探测只能提供日期明确的局部证据；凡是跨厂商的部分，都要对目标模型与 API 版本单独验证。

**以为「窗口够大」就不用做取舍。** 容量充足不保证任务表现；检索、位置、干扰项、模型和任务都会影响结果，应针对目标场景测量，而不是把问题简化成单一的「注意力瓶颈」。

## 附录：数据采集脚本

本节开头的历史样本与错误探测汇总来自一次 2026-09-24 DeepSeek 兼容端点记录。下面的简化脚本展示如何记录 Messages API 原始响应；它不是当时原始采集脚本的逐字复现，也未在本轮对 provider 实跑。

它直接请求 Messages API 并显示响应摘要，适合观察该次 HTTP 结果；它不是比 SDK 更可靠的通用方案，认证、重试、超时和响应解析仍需应用明确处理。

```python
# collect_token_stats.py
"""采集 token 消耗数据与原始错误响应。

用法（Anthropic 官方端点）：
    export ANTHROPIC_API_KEY="..."
    export VERIFY_MODEL="<当前支持的 Anthropic model ID>"
    python3 collect_token_stats.py
"""

import json
import os

import anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])

MODEL = os.environ["VERIFY_MODEL"]

# 刻意覆盖不同语言与文本类型 —— 单一类型的样本测不出语言差异
SAMPLES = {
    "短中文": "什么是幂等性？",
    "短英文": "What is idempotency?",
    "长中文": "什么是幂等性？" * 50,
    "长英文": "What is idempotency? " * 50,
    "代码": 'func main() { fmt.Println("hello") }',
}


def count_tokens(text: str) -> int:
    # Anthropic 官方 token counting endpoint；结果是估算值，不代表账单金额。
    result = client.messages.count_tokens(
        model=MODEL,
        messages=[{"role": "user", "content": text}],
    )
    return result.input_tokens


def report_samples() -> None:
    print(f"模型: {MODEL}\n")
    print(f"{'样本':<8}{'字符数':>8}{'token':>8}{'每字符':>10}")
    print("-" * 36)
    for label, text in SAMPLES.items():
        tokens = count_tokens(text)
        print(f"{label:<8}{len(text):>8}{tokens:>8}{tokens / len(text):>10.2f}")


def probe_errors() -> None:
    """打原始响应，而不是只看解析后的结果。

    有些行为差异（比如「缺 max_tokens 会不会报错」）
    只有看 HTTP 状态码才能发现。
    """
    probes = {
        "空模型名": {
            "model": "", "max_tokens": 16,
            "messages": [{"role": "user", "content": "hi"}],
        },
        "缺 max_tokens": {
            "model": MODEL,
            "messages": [{"role": "user", "content": "hi"}],
        },
        "传 temperature": {
            "model": MODEL,
            "max_tokens": 16,
            "temperature": 0.2,
            "messages": [{"role": "user", "content": "hi"}],
        },
    }

    # 用单独的 httpx 客户端观察 HTTP 状态；不把 SDK 私有 client 当作稳定接口。
    import httpx

    headers = {
        "x-api-key": os.environ.get("ANTHROPIC_AUTH_TOKEN")
        or os.environ.get("ANTHROPIC_API_KEY", ""),
        "anthropic-version": "2023-06-01",
        "content-type": "application/json",
    }
    print("\n错误行为探查：\n")
    with httpx.Client(
        base_url="https://api.anthropic.com", headers=headers, timeout=60
    ) as raw:
        for label, body in probes.items():
            resp = raw.post("/v1/messages", json=body)
            print(f"[{label}] HTTP {resp.status_code}")
            print(f"  {resp.text[:200]}")
            print()


if __name__ == "__main__":
    report_samples()
    probe_errors()
```

> **实跑状态**：历史结果来自 2026-09-24、anthropic SDK 0.39.0 与 DeepSeek `deepseek-flash` Anthropic-compatible endpoint。正文中的脚本已按 Anthropic 当前公开接口重写，代码在本轮未执行；请在部署前用当前 SDK 版本运行。历史记录只保留该次 HTTP 状态与 usage 数值，不将它们视作当前行为保证。

### 怎么用这个脚本建立自己的成本直觉

把 `SAMPLES` 换成**你自己业务里的真实文本**，然后跑一遍。这一步比读任何文章都有用，因为：

- 你的文本的 token 特性（中英比例、代码密度、结构重复度）是独一无二的
- 你能观察同类请求在目标 provider 的 input usage 如何随 prompt 变化；要估计金额，还需分别核对当前输入、输出与缓存费率

Anthropic 官方 token-counting endpoint 当前说明为免费但受速率限制；这一点不能推广到其他 provider。可在 CI 中对固定请求样本做 token 回归测试，并将其与实际账单/usage 监控分开。
