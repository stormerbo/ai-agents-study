先看一组实测数据。这是我用同一个端点、同一个模型，对不同文本做 token 计数得到的结果：

| 文本 | 字符数 | token 数 | 每字符消耗 |
|---|---:|---:|---:|
| `什么是幂等性？` | 7 | **35** | 5.0 |
| `What is idempotency?` | 20 | **37** | 1.85 |
| `什么是幂等性？` × 50 | 350 | **280** | 0.80 |
| `What is idempotency? ` × 50 | 1050 | **381** | 0.36 |
| `func main() { fmt.Println("hello") }` | 36 | **40** | 1.11 |

（数据来源：DeepSeek 的 Anthropic 兼容端点，模型 `deepseek-flash`，2026-09-24 实测。完整脚本见本章附录。）

这张表里有三件违反直觉的事：

**第一，7 个字符的短句要 35 个 token。** 如果 token 和字符是简单比例关系，这个数字应该是 5 左右。

**第二，10 个英文单词（20 字符）比 7 个汉字（7 字符）消耗的 token 还多。** 按照「英文更省」的常识，这说不通。

**第三，中英文的每字符消耗差了两倍多**（0.80 vs 0.36），但短句上的差距却被抹平了。

这三个现象指向同一个解释：**存在一个约 30 token 的固定开销，它与你的文本长度无关。**

算一下：短句 35 token 减去 7 个字符的「真实内容」（约 5 token），剩下约 30。英文短句同理：37 减去约 5，还是约 30。

这个固定开销来自请求的结构本身 —— `role`、`content` 这些包装字段，以及服务端在消息前后自动附加的内容。它不随你的文本变化，但**每一次调用都要付**。

一旦理解这一点，前面三个现象就都通了：

- 短句之所以「不划算」，是因为 30 token 的固定成本摊在了 5 token 的内容上
- 长文本的每字符消耗之所以更低，是因为固定成本被摊薄了
- 中英文之所以在短句上看不出差距，是因为固定开销盖过了字符差异
- 只有把文本拉长（350 字符 vs 1050 字符），真实的语言差异才显现出来：**中文的 token 密度约是英文的两倍**

> 这个固定开销是我实测出来的推论，不是官方文档里写明的数字。不同模型、不同服务端的开销可能不同，你应该用本章附录的脚本对自己的场景测一遍。

这一节要讲的就是这个单位：它怎么来的、怎么算、以及为什么它是后面所有成本与容量问题的根源。

## 为什么需要 token 这个东西

最直接的问题是：模型为什么不直接处理字符？

因为**序列长度是模型最昂贵的资源**。注意力机制的计算量随序列长度呈平方增长 —— 序列翻倍，计算量变四倍。如果按字符处理，一段 350 字的中文就是 350 个位置；而按 token 处理后（实测 280），差别还不算大。但如果按**字节**处理，同样的文本是 1050 个字节，位置数变成三倍。

所以需要一个折中：**词汇表不能太大**（否则输出层的矩阵会爆炸），**序列也不能太长**（否则注意力计算扛不住）。

分词器就是这两者之间的权衡产物。

## token 是怎么切出来的

现代分词器普遍采用**子词**（subword）方案，主流是 BPE（Byte Pair Encoding）及其变体。

思路很朴素：

1. 从单个字符（或字节）开始，每个都是独立单元
2. 统计语料里哪两个相邻单元出现最频繁，把它们合并成一个新单元
3. 重复第 2 步，直到词汇表达到预设大小

结果是：**高频片段被合并成一个 token，低频内容保持碎片状态**。这解释了你在实践中看到的几乎所有现象：

| 内容 | 典型切法 | 原因 |
|---|---|---|
| `the`、`什么` | 1 个 token | 语料里出现极频繁 |
| `idempotency` | 可能 3~4 个 token | 生僻词，被切成常见子串 |
| `fmt.Println` | 可能是 3 个以上 | 代码标识符不在自然语料的高频表里 |
| 一串随机字符 | 几乎逐字符 | 没有任何可复用的片段 |

**关键推论**：token 的切法与语义无关，只与频率有关。`1234567` 和 `7654321` 消耗的 token 数相同，哪怕前者在你的业务里是个有意义的订单号。

这也直接解释了实测数据里代码样本的表现：36 个字符消耗 40 个 token（每字符 1.11），效率比英文长文本差三倍 —— 代码里的符号、驼峰命名、标点密度都远高于自然语言。

## 中文为什么更贵

回到实测数据：长中文每字符 0.80 token，长英文每字符 0.36 token。

原因在于**训练语料中的语言分布**。主流大模型的语料以英文为主，BPE 合并出的高频片段大多是英文单词。于是：

- 英文的常见词（`the`、`and`、`is`）几乎都是 1 个 token
- 中文的一个常用词可能是 1 个 token，但一个汉字平均要 0.8 个 token 左右
- 换句话说，表达同样信息量时，中文的序列长度通常更长

这有个很实际的后果：**如果你的应用面向中文用户，你和面向英文用户的应用，在同样的上下文窗口下能装的内容量是不一样的。** 官方文档给出的「100 万 token ≈ 55.5 万英文单词」这个换算，对中文并不成立，中文要按更保守的数字估。

## 新分词器：一次约 30% 的成本变化

这里要插入一个正在发生的变化，因为它会让很多现成的成本估算失效。

Claude 4.7 及之后的模型引入了**新的分词器**。据官方文档（[Token counting](https://platform.claude.com/docs/en/build-with-claude/token-counting)、[模型总览](https://platform.claude.com/docs/en/about-claude/models/overview)）：**同样的输入文本，在新分词器下产生的 token 数比之前大约多 30%**。

这不是小事。它意味着：

1. **从旧模型迁移时不能复用旧的 token 计数。** 拿旧数字估算新模型的成本与容量占用，会系统性低估 30%。官方给的做法是用你打算用的那个 `model` 重新数一遍。
2. **旧教程里的经验法则会失效。** 「一份文档大概多少 token」这类直觉是绑定在某个分词器上的，换个模型就可能不准。
3. **它同时影响成本和容量。** 30% 更多的 token，意味着同样的钱能处理的内容少了 30%，同样的窗口能装的内容也少了 30%。

> 这个数字（约 30%）来自官方文档，但我**没有在新旧模型上实测验证**（本机可用的端点是 DeepSeek，不涉及这次分词器变更）。你在做容量规划前，值得用两个模型各测一遍自己的典型输入。

## 上下文窗口：一个有上限的工作台

理解了 token，上下文窗口就很好定义了。

**它是单次请求中模型能「看到」的 token 总量上限，输入与输出共用这个额度。**

不是「输入预算」—— 这一点很关键。如果你给一次生成分配了 20 万 token 的输入，而模型的最大输出是 12.8 万 token，那么在 20 万窗口的模型上你根本放不下两者之和。真实约束是：

```
输入 token + 输出 token ≤ 上下文窗口
```

当前 Claude 主力模型的窗口是 100 万 token，Haiku 4.5 是 20 万（[模型总览](https://platform.claude.com/docs/en/about-claude/models/overview)）。用官方给的换算：

| | 100 万 token 约等于 |
|---|---|
| 英文单词 | 约 55.5 万个 |
| Unicode 字符 | 约 250 万个 |

按前面实测的中文 token 密度（每字符约 0.8 token）反推，**100 万 token 大约能装 125 万个中文字符** —— 比英文的字符数少一半。这些换算都是量级估算，别当精确值用。

100 万 token 是什么概念？大约是一本中等厚度技术书的体量。这确实很大，大到足以产生一种危险的错觉。

## 危险之处：「能装下」不等于「能用好」

既然窗口这么大，把整个代码库、全部文档、所有历史对话都塞进去不就行了？

不行。有两个独立的机制在阻碍你。

### 机制一：注意力被稀释

上下文里内容越多，模型对其中**每一部分**的关注度就越低。注意力的总量是有限的，摊到更多 token 上，每个 token 分到的就少了。

这不是容量问题（你可能只用了窗口的 10%），而是分配问题。业界称之为 **context rot**（上下文腐化）。

### 机制二：中间位置最容易被忽略

这个现象有一个明确的实证来源。研究者在长上下文里放置关键信息，然后改变信息的位置，测量模型能否找到它 —— 结果呈现明显的 **U 形曲线**：

论文 *Lost in the Middle*（[arXiv:2307.03172](https://arxiv.org/abs/2307.03172)，TACL 2024）给出了这个结果。它有一个非常反直觉的推论：

> 把关键信息埋在长上下文的中部，效果可能**比只给它这一句话还差** —— 因为模型不仅没用好这条信息，还被周围的内容干扰了。

实践上的直接指导：

- **指令放开头或结尾**，不要埋在参考资料中间
- 长参考资料要**检索后再放**，而不是整段塞入
- 如果参考资料不可避免很长，把它放在中间，而不是把指令放在中间

### 这两个机制意味着什么

把两件事合起来看：

```
上下文窗口的标称容量  ≠  模型实际能用好的容量
```

**「窗口还有空间」不能作为继续塞内容的理由。** 这是第 3 章「上下文工程」要解决的核心问题 —— 那一章会讲具体的压缩、检索与隔离策略。

## 完整项目：一个 token 成本估算器

前面所有概念，落到工程上就是一个工具：**在发请求之前，算出这次调用要花多少 token。**

这类工具的价值在批量任务上尤其明显。等你跑完一万次调用再看账单，已经晚了。

下面是本章的完整示例，可以直接运行：

```python
# token_estimator.py
"""在发请求前估算 token 消耗与成本。"""

import os

import anthropic

# 凭据从环境变量读取，不要硬编码在代码里
api_key = os.environ.get("ANTHROPIC_API_KEY") or os.environ.get(
    "ANTHROPIC_AUTH_TOKEN"
)

client = anthropic.Anthropic(
    api_key=api_key,
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),  # 留空用官方端点
)

MODEL = os.environ.get("VERIFY_MODEL", "claude-sonnet-5")


def count(text: str, system: str | None = None) -> int:
    """返回这次调用会消耗的输入 token 数。

    count_tokens 端点接受与创建消息相同的参数结构，
    所以 system、tools、图片都能算进去。
    """
    kwargs = {"model": MODEL, "messages": [{"role": "user", "content": text}]}
    if system:
        kwargs["system"] = system
    result = client.messages.count_tokens(**kwargs)
    # 不同 SDK 版本的返回类型不同，用 getattr 兼容
    return getattr(result, "input_tokens", None) or result.json()["input_tokens"]


def main() -> None:
    samples = {
        "短中文": "什么是幂等性？",
        "短英文": "What is idempotency?",
        "长中文": "什么是幂等性？" * 50,
        "长英文": "What is idempotency? " * 50,
        "代码": 'func main() { fmt.Println("hello") }',
    }

    print(f"模型: {MODEL}\n")
    print(f"{'样本':<10}{'字符数':>8}{'token':>8}{'每字符':>9}")
    print("-" * 36)

    for label, text in samples.items():
        tokens = count(text)
        print(f"{label:<10}{len(text):>8}{tokens:>8}{tokens / len(text):>9.2f}")


if __name__ == "__main__":
    main()
```

运行它（把凭据放进环境变量）：

```bash
export ANTHROPIC_API_KEY="..."
python3 token_estimator.py
```

输出就是本节开头那张表。你可以直接改 `samples` 里的文本，换成你自己的真实输入 —— 这是最有价值的一步，因为**你的业务文本的 token 特性，只有测了才知道。**

> **实跑状态**：本节开头的**数据表来自实测**（DeepSeek 的 Anthropic 兼容端点）。但上面的脚本是针对通用 Anthropic 接口写的，**脚本本身未在官方端点上实跑验证**；不同 SDK 版本的返回类型有差异，代码里用 `getattr` 做了兼容处理。

## 三个真实的错误案例

下面三段错误响应都来自实测，不是编造的。

### 案例一：模型名写错

```json
{
  "error": {
    "message": "The supported API model names are deepseek-flash, deepseek-v4-pro, but you passed .",
    "type": "invalid_request_error",
    "param": null,
    "code": "invalid_request_error"
  }
}
```

HTTP 状态码 400。

这个错误信息**本身就值得学习**：它不只说了「模型名无效」，还直接把当前可用的模型名列了出来。对比一下常见的 `{"error": "invalid model"}` —— 后者会让你去翻文档，前者让你当场就能改对。

**给你自己的 API 设计的启示**：错误信息应该包含「调用方能据此采取行动」的信息。这条能做到，很多 API 做不到。

### 案例二：`max_tokens` 导致的静默截断

现象：请求返回 200，但解析结果时报 `JSONDecodeError`。

排查过程（这正是真实排查的样子）：

1. **先看原始响应**，而不是只看解析后的结果 —— 发现输出被腰斩在半截 JSON 上
2. **再查 `stop_reason`** —— 值是 `max_tokens`，而不是 `end_turn`
3. 确认了是长度截断，不是模型能力问题

根因：`max_tokens` 是**硬截断**。达到上限就停，不会给你一个完整结构。你要求输出 JSON，但额度不够，拿到的就是半截字符串。

修复要同时做两件事：

```python
response = client.messages.create(
    model=MODEL,
    max_tokens=2048,                      # 1. 留足余量，别卡着预期长度设
    messages=[{"role": "user", "content": prompt}],
)

# 2. 检查停止原因，而不是盲目解析
if response.stop_reason == "max_tokens":
    # 走重试（提高上限）或降级路径，不要直接 json.loads
    raise TruncatedOutputError("输出被截断，请提高 max_tokens 或拆分任务")

data = json.loads(extract_json(response.content[0].text))
```

**关键点**：`stop_reason` 字段就是为这个场景存在的。不检查它，你就只能靠解析失败来发现截断 —— 而那时已经浪费了一次调用。

### 案例三：跨厂商的意外行为

这是最有意思的一个，因为它演示了「兼容」的真实含义。

我用同一个端点做了三组对照实验：

| 实验 | Anthropic 官方行为 | DeepSeek 兼容端点实测 |
|---|---|---|
| 不传 `max_tokens` | **报错**（必填参数） | **返回 200**，有默认值 |
| 传 `temperature: 0.2` | **报错 400**（新模型已移除该参数） | **返回 200**，参数生效 |
| 模型名写错 | 报错 | 报错，且列出可用模型名 |

两项的**行为完全相反**。

这个结果有两层意义：

**第一层，实践层面。** 你的代码如果只在 DeepSeek 上测过，迁移到 Claude 时会在 `max_tokens` 上撞墙；反过来，如果代码里传了 `temperature`，在 DeepSeek 上跑得好好的，换到 Claude 新模型就 400。**「兼容 Anthropic API」不代表行为一致** —— 兼容的是接口形状，不是语义。

**第二层，架构层面。** 这正是为什么需要适配层。如果业务代码里直接散落着 `if provider == 'deepseek'` 这样的判断，每接一家厂商就要改一遍业务逻辑。正确做法是把差异**收拢到一处**（本站的做法见第 8 章），让上层只面对统一接口。

## 常见坑

**按字符数估算 token。** 实测数据显示每字符消耗在 0.36 到 5.0 之间浮动，取决于文本类型和长度。任何固定的换算系数都是错的，用 `count_tokens`。

**忽略固定开销。** 每次调用都有约 30 token 的结构开销。做小请求的成本估算时如果不算上它，会低估得离谱 —— 短句场景下它可能占总额的 85%。

**把上下文窗口当「输入预算」。** 输出也占额度。要求结构化输出时要留出充足空间。

**把 `max_tokens` 卡在预期长度附近。** 输出的长度是概率性的，卡得太紧就会间歇性截断，表现为「偶尔报 JSON 解析错误」这种极难定位的 bug。

**不检查 `stop_reason`。** 它是你判断「这次输出是否完整」的唯一可靠依据。

**假设跨厂商行为一致。** 案例三实测证明了两家可以在同一个参数上行为相反。凡是跨厂商的部分，都要单独验证。

**以为「窗口够大」就不用做取舍。** 容量不是瓶颈，注意力是。

```python
def count_tokens(text: str) -> int:
    result = client.messages.count_tokens(
        model=MODEL,
        messages=[{"role": "user", "content": text}],
    )
    # SDK 版本不同，返回类型可能是对象也可能是可 json() 的包装
    return getattr(result, "input_tokens", None) or result.json()["input_tokens"]


def report_samples() -> None:
    print(f"模型: {MODEL}\n")
    print(f"{'样本':<8}{'字符数':>8}{'token':>8}{'每字符':>10}")
    print("-" * 36)
    for label, text in SAMPLES.items():
        tokens = count_tokens(text)
        print(f"{label:<8}{len(text):>8}{tokens:>8}{tokens / len(text):>10.2f}")


def probe_errors() -> None:
    """打原始响应，而不是只看解析后的结果。

    有些行为差异（比如「缺 max_tokens 会不会报错」）
    只有看 HTTP 状态码才能发现。
    """
    probes = {
        "空模型名": {
            "model": "", "max_tokens": 16,
            "messages": [{"role": "user", "content": "hi"}],
        },
        "缺 max_tokens": {
            "model": MODEL,
            "messages": [{"role": "user", "content": "hi"}],
        },
        "传 temperature": {
            "model": MODEL,
            "max_tokens": 16,
            "temperature": 0.2,
            "messages": [{"role": "user", "content": "hi"}],
        },
    }

    print("\n错误行为探查：\n")
    for label, body in probes.items():
        # 注意：这里用 client._client 是有意为之 —— 我们要看原始 HTTP 层
        resp = client._client.post("/v1/messages", json=body)
        print(f"[{label}] HTTP {resp.status_code}")
        print(f"  {resp.text[:200]}")
        print()


if __name__ == "__main__":
    report_samples()
    probe_errors()
```

> **实跑状态**：本脚本产出的**数据**是实测的（正文表格与错误案例都来自它的真实输出）；但脚本本身是用 SDK 调用写的，而我的数据采集用的是直接 HTTP 请求。两者的字段名一致，`probe_errors` 里访问 `client._client` 的写法**未经验证** —— 如果你用的 SDK 版本没有这个属性，改成直接用 `httpx` / `requests` 发请求即可。

### 怎么用这个脚本建立自己的成本直觉

把 `SAMPLES` 换成**你自己业务里的真实文本**，然后跑一遍。这一步比读任何文章都有用，因为：

- 你的文本的 token 特性（中英比例、代码密度、结构重复度）是独一无二的
- 你能直接看到固定开销占总额的比例 —— 如果占比很高，说明你的请求太小，**合并请求**可能比优化 prompt 更有效
- 你能算出「每万次调用要多少 token」，再乘官方定价，就是个量级正确的预算

最后一个提醒：这个脚本用的是 `count_tokens`，它**免费**。你可以在 CI 里跑它，把每次发布前的 token 预算做成一个回归测试 —— 当某次改动让 prompt 膨胀了 40% 时，你会立刻知道。
