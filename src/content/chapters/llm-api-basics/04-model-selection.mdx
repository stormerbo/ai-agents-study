第一次收到账单时，多数人会做同一件事：把所有调用都换成便宜模型。然后质量掉了，又全部换回来。

这两个决定都太粗。模型选型的本质是**按任务分层**，而分层的前提是你知道成本是怎么产生的 —— 不只是单价，还有**结构**。

## 先弄清 usage 与费用口径

成本不能只按“输入、输出、缓存”三个互斥桶相加。对每次调用，应按 endpoint 的账单字段与费率逐项计算：

```text
token 费用 = Σ(各类 billable usage × 对应单价)
总费用 = token 费用 + 服务器工具 / 托管运行时等其他适用费用
```

缓存读取与写入可能是 input usage 的不同子类；若计数器已经包含它们，再把“缓存相关费用”整项额外叠加会重复计费。不同 provider、模型、平台、缓存时长和请求模式的字段及费率可能不同，须读目标端点的账单说明。可以先用[Anthropic 定价页](https://platform.claude.com/docs/en/about-claude/pricing)学习一套具体契约，但不要把它套给别家。

本站不在正文固定价格或输入/输出倍率：价格和平台选项会变化，也可能包含地区、长上下文、缓存和批处理修饰项。优化方向同样不能仅凭输入/输出单价推断；要用实际 usage、质量、延迟和每个成功任务成本验证。

## 条件模型：客户端完整重发时的多轮 input 增长

多轮 token 总量取决于调用协议与状态管理。下面的历史摘要不完整，因此只用它演示一个带前提的增长公式，不将其称为可复现的账单实测：

```text
（2026-09-24 的 DeepSeek `deepseek-flash` 历史摘要：每轮问「N 加 N 等于几」，要求只回数字。原始请求、响应与 usage 字段语义未完整归档。下表累计列的口径无法从现有材料确认；后文只用本轮 input 列进行条件算术，不用累计列推导账单。）

轮次 | 本轮 input 记录 | 历史累计字段（口径未核实）
  1  |      57        |   151
  2  |      89        |   298
  3  |     121        |   469
  4  |     153        |   698
  5  |     185        |   935
  6  |     217        |  1182
```

### 只对可核实的 input 列作条件算术

历史摘要中的 input 列每轮增加 32：57 → 89 → 121 → 153 → 185 → 217。这组模式与客户端逐轮重发累积历史相容，但由于原始请求和字段未归档，不能确认这 32 token 全部来自上一轮问答，也不能推广到其他 API。只有在每轮都把完整对话历史重新放进请求、且消息持续增长时，累计 input 才会呈二次增长；使用服务端会话、裁剪、摘要或缓存时，实际传输、usage 与费用曲线会不同。

把六轮 input 数字相加，得到 `57 + 89 + 121 + 153 + 185 + 217 = 822`。这是对表内 input 字段的算术求和，不是核实过的账单总额。由于没有逐轮请求体，无法把 822 拆成“新内容”和“重发历史”，此前的 `342 token / 58%` 归因已撤回。

在该线性增长假设下，第 N 轮 input 为 `57 + 32(N-1)`，累计 input 才是：

```text
累计 = 57N + 16N(N-1)     ← 这是一个 O(N²) 的函数
```

按这个式子作情景外推，50 轮累计 input 为 42,050，而第 50 轮单轮 input 为 1,625；这个比例只属于该组参数和“每轮重发完整历史”的假设，不能当作实测或所有会话 API 的通用倍率。

### 成本结构取决于请求形状

在这种客户端显式提交历史的调用形状中，服务端不必替客户端维护对话状态，但重复提交会增加该请求的 input。其他 API 也可能提供服务端会话或托管状态；缓存能改变计费字段，却不必然减少请求上下文长度。选用哪种状态管理方式，应分别核对请求形状、保留/删除语义与 usage 计费口径。

三个对策，按代价排序：

| 对策 | 做法 | 代价 |
|---|---|---|
| **截断历史** | 只保留最近 N 轮 | 丢失早期上下文，模型可能"忘记"关键信息 |
| **压缩历史** | 把早期对话摘要化 | 摘要会丢细节，且本身要花一次调用 |
| **缓存前缀** | 用 prompt caching 降低重复部分的费用 | 有门槛与前提条件（见下一节） |

第 3 章会详细讲这三种策略的取舍。

## 一个被忽略的成本来源：工具定义

第 4 章保存过一组 8/20/44/86 个工具的 DeepSeek 兼容端点历史请求总 input（678/1326/2623/4945）；两端差约 55 token/新增工具，但原始请求与缓存字段未归档，不能称作固定开销或普遍价格。评估当前方案时应按目标 endpoint 的 usage 与缓存口径重测。

如果目标 endpoint 每轮都需要提交完整工具定义，请求输入可能随工具数与调用轮次增加。实际未缓存输入和费用取决于缓存、服务端会话与工具加载机制；应从当前 endpoint 的完整 usage 计算。比如，若你的测量显示每轮约多 600 个未缓存 input token，20 轮的未缓存输入增量约为 12000 token；这是带前提的估算，不应套用第 4 章旧样本的斜率。

## 分层路由：按两个维度切

不该所有请求都走最强模型。判断标准是两个维度。

**维度一：候选模型是否满足任务要求。**

分类、抽取、改写、格式转换可以作为轻量模型的候选任务，多步推理、代码生成、复杂规划可以作为高能力模型的候选任务；这只是初始假设。相同标签下，数据分布、prompt、工具、模型版本与验收标准都会改变结果，所以应通过代表性任务评测检查能力、质量、成本和延迟，再选出通过门槛的候选。

**维度二：错误的后果与验收门槛。**

同一任务难度下，错误后果会改变你能接受的质量门槛、复核方式和行动权限；它不自动证明更强模型就足够安全。对外发送、生产写入、付款或不可逆操作，必须由独立于模型输出的服务端授权、业务校验和必要的人审来控制。模型档位只影响候选生成质量与成本，不能授予权限，也不能替代审批。

路由是否省钱、是否达到质量门槛，要用代表性任务集按目标模型实测。轻模型的候选比例、漏升级率、误升级率、成功任务成本和尾延迟都取决于你的请求分布；没有本地评测时，不应预设“大部分流量简单”或“质量下降更慢”。

### 把分类判据写下来，别留在脑子里

上面两个维度的问题是：它们都是**判断**，而判断不能进代码。要落地，两条判据必须各有一个可执行的代理指标：

| 维度 | 留在脑子里的版本 | 可执行的版本 |
|---|---|---|
| 工作负载 | 「这题难不难」 | 记录任务类别、输入分布、工具/上下文需求与失败类型；它们是候选路由信号，要由代表性 eval 验证，不是模型能力的保证 |
| 错误后果 | 「错了要紧吗」 | 记录错误影响、可检测性、可逆性与业务验收门槛；这些信息用来决定复核和授权策略，不直接等同于模型能力档位 |

任务特征可以作为路由信号，但关键词、来源数或“是否用工具”都只是 proxy，可能漏判或误判。先在历史样本上检查规则覆盖率与错误类型，再决定是否使用分类模型；所有路径都要保留可观测的路由原因与兜底状态。对外部副作用的授权判断应读取宿主可信上下文和业务策略，不能从用户 prompt 或模型分类推断。

### 最小路由实现

下面的 Python 片段是一个路由决策骨架，需要替换占位模型名，并对照锁定的 SDK 与 endpoint 验证。流程是**先规则、再分类、异常时转人工复核**；分类只选择候选模型，不授权副作用。

```python
# router.py
"""把一个请求分到 cheap / mid / strong 三档。"""

import logging
import os

import anthropic

client = anthropic.Anthropic(
    api_key=os.environ.get("ANTHROPIC_API_KEY")
    or os.environ.get("ANTHROPIC_AUTH_TOKEN"),
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)
CLASSIFIER_MODEL = os.environ["VERIFY_MODEL"]
logger = logging.getLogger(__name__)

# 每档一个模型名 —— 换成你端点里真的存在的名字
MODELS = {"cheap": "cheap-model", "mid": "mid-model", "strong": "strong-model"}

# ③ 兜底：分类失败、或分数落在灰区时走哪档
MANUAL_REVIEW = "manual_review_required"  # 分类异常时不伪装成模型档位，也不触发副作用

# ① 规则：一眼能判的先判掉，不花一次调用
RULE_TIERS = [
    ("strong", ("对账 SQL", "迁移方案", "重构", "多步规划")),   # 示例启发式，必须用已标注请求评估误差
    ("cheap",  ("分类", "打标签", "抽取", "翻译", "格式化")),  # 仅作为候选信号，须用本地数据评估
]

# ② 分类：规则判不出时才调用。要求只输出一个词，便于程序解析
CLASSIFIER_PROMPT = """判断这个请求属于哪一档，只输出 cheap / mid / strong 中的一个词。

cheap  —— 一个经评测达到当前任务质量门槛的轻量候选。
mid    —— 一个经评测达到门槛、在质量/延迟/成本间折中的候选。
strong —— 对当前评测集有必要的高能力候选；这不代表答案正确、操作获授权或高影响动作可自动执行。

请求："""


def classify_by_rule(request: str) -> str | None:
    for tier, keywords in RULE_TIERS:
        if any(k in request for k in keywords):
            return tier
    return None


def classify_by_model(request: str) -> str | None:
    try:
        resp = client.messages.create(
            model=CLASSIFIER_MODEL,
            max_tokens=10,
            system=CLASSIFIER_PROMPT,
            messages=[{"role": "user", "content": request}],
        )
    except Exception as exc:
        logger.warning("classifier request failed: %s", type(exc).__name__)
        return None  # API/网络/SDK 错误：交给人工复核路径，不降级成默认模型
    if resp.stop_reason != "end_turn":
        logger.warning("classifier response incomplete: %s", resp.stop_reason)
        return None  # 截断或非正常终止不能当作有效分类
    text = "".join(b.text for b in resp.content if b.type == "text").strip().lower()
    if text not in MODELS:
        logger.warning("classifier returned an invalid tier")
        return None
    return text


def route(request: str) -> str:
    """返回模型名或人工复核哨兵；这不是授权或执行决策。"""
    tier = classify_by_rule(request)
    source = "rule"
    if tier is None:
        source = "classifier"
        tier = classify_by_model(request)
    if tier is None:
        logger.warning("model route requires manual review: source=%s", source)
        return MANUAL_REVIEW  # 调用方必须识别该哨兵；本函数不执行任何业务动作
    logger.info("model route selected: source=%s tier=%s", source, tier)
    return MODELS[tier]


if __name__ == "__main__":
    for q in ["把这条评论分类为正面/负面", "帮我生成对账 SQL", "总结这段话"]:
        print(f"{q}  ->  {route(q)}")
```

**三个设计决定，以及它们的理由：**

1. **规则放在分类模型前面。** 规则是确定性的、可单测、零成本；能一眼判掉的那部分不该花一次调用。分类调用只处理灰区。
2. **分类失败要能被发现。** `classify_by_model` 用一个白名单校验返回值（`text in MODELS`）—— 模型多吐一句解释、或吐了 `medium` 这种不在枚举内的词，都会被判为 None 而不是当成合法档位。若不校验返回值，非法档位可能导致错误的模型 ID 或后续请求失败；此示例通过白名单将该情况送入人工复核。
3. **分类不确定时必须显式处理。** 分类 API 报错、输出截断或返回白名单外的值时，示例返回 `manual_review_required`，不是悄悄挑一个模型继续。这个哨兵必须由调用方识别并阻断自动执行；不能直接把字符串当模型 ID。**使用强模型仍不代表答案正确或操作获授权**。高影响动作还需要独立的授权、业务规则与人审策略。

> 模型更强不自动等于任务成功率更高，也不能确保越过业务验收门槛。比较候选时，应使用同一批代表性输入和有版本的判分标准，记录模型、prompt、参数、失败与重试、质量分布、端到端延迟和完整 usage；若样本不足以区分效果，就把结论标为不确定。高影响动作仍须单独经过宿主授权与审批。

> 第 7 章的路由数字是按声明的 token 和费率假设做的情景算术，不是实测价格、任务质量或生产收益。路由节省取决于候选模型、任务分布、升级策略、分类器/评估器成本、失败重试以及成功标准；请使用那一节的公式和你的实际输入重算，不要把一个演算百分比当成收益预测。

## effort：同一模型内的一个可评估旋钮

如果目标模型支持 effort，可以将其与换模型作为不同的候选配置进行评估；不要预设简单任务一定该用 `low`、复杂任务一定该用 `high`。支持级别、默认值与对质量、延迟、费用的影响均因模型和请求而异，见第 2 节及当前 provider 文档。

但注意两个约束：

截至 2026-10-21，Claude Haiku 4.5 不支持 Anthropic `effort`；其他模型与版本的支持及默认值会变化，应查看当前模型能力页。

Anthropic 文档提示，跨请求改变顶层 `output_config.effort` 可能使可缓存前缀不再匹配；这不是所有 provider 的通用规则，也不意味着每个 cache entry 都必然整体失效。是否复用、缓存边界与费用变化要按当前 endpoint 文档和 usage 实测。若业务依赖缓存，可以固定该字段作为一种可测试的请求配置策略。

## 怎么读定价页

定价页上除了单价，还要看三样东西（[定价页](https://platform.claude.com/docs/en/about-claude/pricing)）：

**1. 缓存写入与读取的费率。** 读写费率由 provider、模型、缓存时长和平台决定；先查目标定价表，再把实际 cache read/write usage 分开计价。缓存命中不必然让总成本下降，还要把写入费用、最小长度、TTL 与命中率一起纳入估算。

**2. 批处理折扣。** Batch API 有折扣，适合离线任务。代价是延迟。

**3. 长上下文定价与限制。** 某些模型/平台会按 prompt 长度采用不同费率或限制；另一些在给定窗口内采用相同费率。以目标模型当前定价与上下文文档为准。

## 成本估算的最小可行做法

在写代码之前先做一次算术，比上线后看账单便宜。

```python
import os
import anthropic

client = anthropic.Anthropic(
    api_key=os.environ.get("ANTHROPIC_API_KEY")
    or os.environ.get("ANTHROPIC_AUTH_TOKEN"),
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)

MODEL = os.environ["VERIFY_MODEL"]

# 一次「典型请求」的两部分 —— 换成你自己线上的提示词与对话即可。
# （这两个变量原先在正文里没定义，脚本因此跑不起来；2026-10-09 实跑时补上）
MY_SYSTEM_PROMPT = (
    "你是一个订单查询助手。用户会问订单状态，你只能依据工具返回的数据回答，"
    "不确定时明确说不确定。回答控制在三句话以内。"
)
MY_TYPICAL_MESSAGES = [
    {"role": "user", "content": "帮我看看订单 A-1001 现在到哪了？"},
]

# 第一步：数清楚一次典型请求要多少输入 token
# 方法挂在哪个对象上随 SDK 版本变（0.3x 在 beta 下）—— 详见第 1 章第 1 节
_count = getattr(client.messages, "count_tokens", None) or client.beta.messages.count_tokens
count = _count(
    model=MODEL,
    system=MY_SYSTEM_PROMPT,
    messages=MY_TYPICAL_MESSAGES,
)
input_tokens = count.input_tokens

# 第二步：使用逐次 usage 测得的 input 增量做情景估算。
# 该值来自与目标端点、prompt、模型和工具配置相符的多轮记录，
# 不是把首轮完整 input 误当成每轮新增内容。
CONTEXT_GROWTH_PER_TURN = int(os.environ["CONTEXT_GROWTH_PER_TURN"])


def cumulative_input(base_input: int, growth_per_turn: int, turns: int) -> int:
    """客户端每轮完整提交历史时的条件估算；不等于账单。"""
    if min(base_input, growth_per_turn, turns) < 0 or turns == 0:
        raise ValueError("token counts must be non-negative and turns must be positive")
    return base_input * turns + growth_per_turn * turns * (turns - 1) // 2


DAILY_CONVERSATIONS = 500
TURNS_PER_CONVERSATION = 10
per_conversation = cumulative_input(input_tokens, CONTEXT_GROWTH_PER_TURN, TURNS_PER_CONVERSATION)

print(f"首轮 input 估算: {input_tokens} token")
print(f"假设每轮历史增长: {CONTEXT_GROWTH_PER_TURN} token")
print(f"单次对话（{TURNS_PER_CONVERSATION} 轮）情景 input: {per_conversation:,} token")
print(f"日情景 input: {per_conversation * DAILY_CONVERSATIONS:,} token")
print("完成请求后，再用 endpoint 返回的 usage 与账单费率核对估算。")
```

> **实跑状态**：2026-10-09 的旧版本曾报告首轮 75 token、10 轮 4,125 token；该公式把首轮完整 input 当成每轮增长量，没有区分固定 prompt 与新增历史，因此该对话/日成本外推已撤回。本次未调用 provider。当前公式要求显式提供 `CONTEXT_GROWTH_PER_TURN`，仅作完整历史重发场景估算；`count_tokens` 是 Anthropic 请求形状的 input 估算，最终应以目标 endpoint 的响应 usage 和账单字段核对。代码中的环境变量与 endpoint 需按使用环境配置。

估算结果是用于容量规划的情景值，不是账单预测。请求文本、工具、历史状态、缓存与供应商 tokenizer 会影响实际 usage；运行后应逐次记录响应 usage，再按目标定价表核对。

## 一个多轮成本估算示例（假设数据）

下面是条件算术，不是 provider 账单或历史实测结论。假设客户端每轮都把完整对话历史放进请求，初始 input 为 `B=57`，每增加一轮，历史与新消息合计令下一次 input 增加 `g=32`，那么第 `i` 轮 input 是：

```text
input_i = B + (i - 1)g
N 轮累计 input = NB + gN(N - 1)/2
```

取 `N=6`，每轮 input 为 `57、89、121、153、185、217`，求和为 `822`。若误把每一轮都当成固定 `57`，会算成 `57×6=342`。差额 `480` 只是两种假设算法的差值；只有当 `B` 与 `g` 分别代表已确认的新内容和重发历史时，才可将它解释为重复发送量。历史摘要没有请求快照，因此本节不作这种归因。

在相同的假设下，`N=50` 时累计为 `50×57 + 32×50×49/2 = 42,050`，第 50 轮 input 为 `57 + 49×32 = 1,625`。这是展示增长机制的演算；真实 API 是否重复收取这些 token、缓存读写怎样计价、使用 server-side state 后 usage 如何变化，都必须查目标 provider 的文档与逐次 usage。

工具 schema 也可能随请求计入 input，但不能从工具数量直接推导固定 token 开销。若某个**假设场景**测得每轮 5 个工具 schema 共增加 500 个未缓存 input token，那么 50 轮会多提交 25,000 个这类 token；实际账单仍须检查 schema 是否计入请求 usage、是否命中缓存以及各类费率，不能与已经包含 schema 的 usage 再重复相加。

### 怎么避免

1. 用目标 endpoint 的实际请求形状和 usage 字段计算逐次成本；先确认服务端状态、缓存和工具调用语义。
2. 将 input、output、缓存读写及其他费用按 endpoint 定义分别计价，避免把计数器子集当成完整总量。
3. 用脱敏、可重放的代表性多轮样本测量轮数、消息长度、工具 schema 和 cache 状态；把模型、SDK、prompt、请求顺序与响应终态一并记录。
4. 对成本优化同时检查任务质量、失败率和延迟，并以“每个通过验收的任务成本”比较候选。没达到统计把握时报告不确定，不宣称通用节省比例。

## 常见坑

**把「最强模型」或轻量模型当成默认正确答案。** 候选模型的成本、质量、延迟和工具能力要结合目标任务实测；厂商 benchmark 不能直接预测你的负载。

**只看单价，不看消耗结构。** 不同模型的输出长度、失败重试、缓存命中及工具使用会改变每个成功任务的总费用；按实际 usage 和账单费率计算。

**把多轮增长说成所有 API 都是平方级。** 只有在客户端每轮完整重发并增长历史等条件下，累计 input 才可能呈二次增长；使用对应请求形状和 usage 验证。

**忽略工具定义带来的请求输入变化。** 工具定义可能占用输入上下文，但计费与缓存行为取决于 endpoint；用目标配置的 usage 字段和缓存读写口径测量，不要沿用历史样本的每工具均价。

**为了省钱调整 effort，却假设缓存一定命中或必然失效。** 检查目标 provider 的缓存边界与 usage，再通过对照测量影响。

**只看单一 `input_tokens` 字段算成本。** 不同 provider 对缓存 token 的字段和计价定义不同；读取完整请求 usage 文档，按 billable 类别映射到定价。
