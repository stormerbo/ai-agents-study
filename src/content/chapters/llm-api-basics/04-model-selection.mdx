第一次收到账单时，多数人会做同一件事：把所有调用都换成便宜模型。然后质量掉了，又全部换回来。

这两个决定都太粗。模型选型的本质是**按任务分层**，而分层的前提是你知道成本是怎么产生的 —— 不只是单价，还有**结构**。

## 成本的三项构成

一次调用的成本是三项之和：

```
输入 token × 输入单价  +  输出 token × 输出单价  +  缓存相关费用
```

输出单价通常远高于输入单价（在多数厂商的定价表上，差距在 3~5 倍）。这个差价决定了优化的方向：**减少输出通常比减少输入更划算。**

关于具体单价：本站不写。原因是它以周为单位变动，写死的数字会在你读到它的时候就已经是错的。请到[定价页](https://platform.claude.com/docs/en/about-claude/pricing)现查 —— 要记住的是**计算方式**，不是数字。

## 实测：多轮对话的成本是平方级增长

这是最容易被低估的一项。下面是对同一个模型做的一次多轮对话实测，每轮问一个极短的问题：

```
（实测数据，deepseek-flash，2026-09-24。每轮问「N 加 N 等于几」，要求只回数字。）

轮次 | 本轮输入 token | 累计消耗
  1  |      57        |   151
  2  |      89        |   298
  3  |     121        |   469
  4  |     153        |   698
  5  |     185        |   935
  6  |     217        |  1182
```

### 看两列，得出两个不同结论

**第一列（本轮输入）是线性的**：57 → 89 → 121 → 153 → 185 → 217，**每轮稳定增加 32**。

这 32 个 token 就是上一轮的问答内容。因为 API 是无状态的，每一轮都必须把完整历史重新发一遍。

**第二列（累计）是平方的**：

```
累计输入 = 57 + 89 + 121 + 153 + 185 + 217 = 822
```

而这 6 轮里，**真正的新增内容只有 6 × 57 = 342 token**。也就是说：

```
822 - 342 = 480 token  (58%) 是在重复发送历史
```

对话越长，这个比例越高。用公式表示，第 N 轮的输入是 `57 + 32(N-1)`，累计输入是：

```
累计 = 57N + 16N(N-1)     ← 这是一个 O(N²) 的函数
```

按这个式子外推：**50 轮对话的累计输入约 42000 token**，而单轮只有约 1625 token —— 差了 26 倍。

### 这不是缺陷，但你必须知道

无状态是有意为之的设计（它让服务端不必保存会话），但它在成本上意味着什么，是使用者自己的责任。

三个对策，按代价排序：

| 对策 | 做法 | 代价 |
|---|---|---|
| **截断历史** | 只保留最近 N 轮 | 丢失早期上下文，模型可能"忘记"关键信息 |
| **压缩历史** | 把早期对话摘要化 | 摘要会丢细节，且本身要花一次调用 |
| **缓存前缀** | 用 prompt caching 降低重复部分的费用 | 有门槛与前提条件（见下一节） |

第 3 章会详细讲这三种策略的取舍。

## 一个被忽略的成本来源：工具定义

第 0 章用实测数据算过：**启用工具调用有约 200 token 的固定开销，每个工具再约 60 token**。

关键在于，这部分成本**每一轮都要付**。一个有 20 轮工具调用的 agent 任务，光工具定义就要花掉：

```
20 轮 × (200 + 10个工具 × 60) = 20 × 800 = 16000 token
```

**这还没算模型实际输出的任何内容。** 所以「给模型更多工具」不是免费的扩展，它有持续成本。

## 分层路由：按两个维度切

不该所有请求都走最强模型。判断标准是两个维度。

**维度一：任务需要多少推理深度。**

分类、抽取、改写、格式转换 —— 这些任务的正确答案是确定的，弱模型就能做好。多步推理、代码生成、复杂规划才需要强模型。

**维度二：错了的代价有多大。**

这是容易被忽略的那个。一个把商品分类标错的请求，和一个生成对账 SQL 的请求，即使难度相近，也不该用同一个模型。**错误代价高的任务值得用更强的模型，哪怕它很简单** —— 因为你买的是可靠性，不是难度。

按这两个维度切完之后，通常会发现大部分流量落在便宜模型上，而成本下降得比质量下降快得多。

## effort：模型内部的第二个旋钮

即使选定了模型，还有 effort 可以调（见第 2 节）。这带来比「换模型」更细的控制粒度：同一个模型，简单任务用 `low`、复杂任务用 `high`。

但注意两个约束：

**Haiku 4.5 不支持 effort。**

**改变顶层的 effort 会让 prompt cache 失效。** 如果你的请求依赖缓存，effort 必须在整个会话里保持一致 —— 否则你为了省钱降 effort，反而会因为缓存失效而花更多钱。这个反直觉的后果在长会话里尤其明显。

## 怎么读定价页

定价页上除了单价，还要看三样东西（[定价页](https://platform.claude.com/docs/en/about-claude/pricing)）：

**1. 缓存写入与读取的费率。** 缓存读取通常是基础输入价的 10%（部分新模型更低），写入则比基础价略高。缓存只有在**同一前缀被反复使用**时才划算。

**2. 批处理折扣。** Batch API 有折扣，适合离线任务。代价是延迟。

**3. 长上下文的加价规则。** 部分平台对超长上下文有额外计费方式。

## 成本估算的最小可行做法

在写代码之前先做一次算术，比上线后看账单便宜。

```python
import os
import anthropic

client = anthropic.Anthropic(
    api_key=os.environ.get("ANTHROPIC_API_KEY")
    or os.environ.get("ANTHROPIC_AUTH_TOKEN"),
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)

MODEL = os.environ["VERIFY_MODEL"]

# 第一步：数清楚一次典型请求要多少输入 token
count = client.messages.count_tokens(
    model=MODEL,
    system=MY_SYSTEM_PROMPT,
    messages=MY_TYPICAL_MESSAGES,
)
input_tokens = count.input_tokens

# 第二步：按对话轮数推算累计消耗（注意是平方级，不是线性）
def cumulative_input(per_turn: int, turns: int) -> int:
    """每轮多出 per_turn 个 token 时的累计输入量。

    第 i 轮的输入是 per_turn * i，所以累计是 per_turn * N(N+1)/2。
    这是 O(N²) —— 千万别按 per_turn * N 估算。
    """
    return per_turn * turns * (turns + 1) // 2

DAILY_CONVERSATIONS = 500
TURNS_PER_CONVERSATION = 10
PER_TURN_GROWTH = input_tokens   # 简化假设：每轮新增约等于一次典型请求

per_conversation = cumulative_input(PER_TURN_GROWTH, TURNS_PER_CONVERSATION)

print(f"单次请求输入: {input_tokens} token")
print(f"单次对话（{TURNS_PER_CONVERSATION} 轮）累计输入: "
      f"{per_conversation:,} token")
print(f"日输入总量: {per_conversation * DAILY_CONVERSATIONS:,} token")
print("再乘定价页上的单价，得到一个量级正确的估算")
```

> **实跑状态**：上面的**数据是实测的**（多轮对话的 token 增长表来自真实调用）；但这段 Python 脚本用的是 SDK 写法，我的采集用的是直接 HTTP 请求，脚本本身未在官方端点验证。

要点是**量级正确**就够了。精确到小数点后两位的估算没有意义，因为输出的 token 数是概率性的。

## 一个真实的成本误判

上面的公式看起来简单，但**按它算错的人非常多**。看一个具体的误判过程。

假设你在做一个客服助手，用前面那组实测数据推算：

```
单轮输入：57 token（一次典型请求）
预计对话轮数：6 轮
→ 估算输入总量：57 × 6 = 342 token
```

看起来合理。但实测的累计输入是 **822 token** —— 低估了 **2.4 倍**。

差别在哪？因为每一轮都要**重发完整历史**：

```
第 1 轮发 57 token
第 2 轮发 57 + 32 token（含第 1 轮内容）
第 3 轮发 57 + 64 token（含前两轮）
...
```

用 `57 × 轮数` 是把「线性增长」当成了「常量」。正确式子是 `57N + 16N(N-1)`，O(N²)。

**这个误判在长对话里会被放大得多。** 50 轮时：

```
线性估算：57 × 50 = 2,850 token
正确算法：57×50 + 16×50×49 = 42,050 token
差了 15 倍
```

如果再加上工具定义（每轮都要付）：

```
50 轮 × (200 入场费 + 5 个工具 × 60) = 50 × 500 = 25,000 token
```

**光是「让模型知道有哪些工具」，就比线性估算出来的整个对话成本还高。**

### 怎么避免

三个习惯：

1. **用累加公式，不用乘法。** `N(N+1)/2` 而不是 `N`。
2. **把工具定义单列一项。** 它不随对话内容变化，但每轮都付。
3. **上线前跑一次真实的多轮对话，记录每轮的 usage。** 实测曲线比任何估算公式都可靠 —— 而且能发现你预料之外的开销（自动缓存、系统提示的实际消耗、模型输出比预期啰嗦）。

第 3 条最重要。我在本章所有数据都是这么来的 —— **先跑，再算**。凭直觉估算在 LLM 成本上几乎总是错的，因为这里存在太多「你以为不会计费但其实计费」的东西。

## 常见坑

**把「最强模型」当成默认值。** 它会让成本和延迟都高出数倍，而多数流量并不需要它。

**只看单价，不看消耗结构。** 一个便宜模型如果输出啰嗦，总成本可能更高 —— 输出 token 通常更贵。

**按线性估算多轮对话的成本。** 实测已经证明是平方级。用 `N(N+1)/2` 而不是 `N`。

**忽略工具定义的持续成本。** 每个工具约 60 token，**每一轮都要付**。

**为了省钱降 effort，却破坏了 prompt cache。** 见上文。

**只看 `input_tokens` 算成本。** 缓存命中的部分走的是 `cache_read`，漏掉它会系统性低估（第 0 章有实测案例）。
