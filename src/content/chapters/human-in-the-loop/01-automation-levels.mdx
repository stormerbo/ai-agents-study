前面几章一直在讲"让 agent 自己做完"。这一章讲反面：**在哪里停下来问人。**

而这个问题有一个前提要先说清楚：**停下来问人是有成本的**，不只是用户的时间，还有系统复杂度。所以目标不是"尽量多问"，而是**在最值得的地方问**。

## 五个档位

把"人在哪"排成一个谱系，实际上只有五档：

| 档位 | 人做什么 | 适合什么 |
|---|---|---|
| **全自动** | 什么都不做 | 低风险、可回滚、量大 |
| **事后复核** | 做完之后看结果 | 可回滚，但错了有代价 |
| **关键点确认** | 只在不可逆的动作前停 | 大部分生产任务 |
| **逐步确认** | 每一步都确认 | 学习阶段、高风险探索期 |
| **人做主** | agent 只给建议 | 决策类任务 |

这个谱系的两个端点都很清楚，难的是**中间该停在哪**。

## 一个判断顺序

选档位时，按顺序问四个问题。**任一个问出"是"，档位就往上一档。**

**一、这个动作可逆吗？** 不可逆 → 至少"关键点确认"。这一条最重要，下一节会用数据说明为什么。

**二、错误的代价谁承担？** 如果代价落在别人身上（发邮件给客户、改别人的数据），档位要更高 —— 因为受影响的人没有机会阻止。

**三、量大吗？** 如果一天几十万次，"逐步确认"实际上不可行（没人看得过来）。这时应该**降低单次的风险**（收窄权限、拆小动作），而不是硬加审批。

**四、现在是什么阶段？** 新上线、新模型、新工具时都应该上移一档，稳定之后再往下移。**档位不是一次性决定，它应该随系统的成熟度变化。**

第四条在实践中经常被忽略。一个常见的形态是：上线时设了"逐步确认"，运行三个月没问题，但没人去把它往下调 —— 于是用户一直在为已经验证过的稳定性付审批成本。

## 为什么"全自动"也是一个正当选择

有一种反应是"涉及钱和数据当然要人工确认"。但**全自动是很多场景的正确选择**，理由有三个：

**一、审批不是免费的。** 下一节会给数据：一个 7 步任务如果每步都问，是 7 次打断。而审批疲劳会让用户开始盲点同意 —— 那时审批反而制造了**虚假的安全感**。

**二、有些任务的风险本来就低。** 读文档、检索、生成草稿 —— 这些错了可以直接重来。

**三、可以用别的机制替代审批。** 收窄权限（第 16 章）、设额度、加回滚能力 —— 这些都不需要用户参与，而且它们是**确定性的**（审批是人做的，而人会疲劳）。

第三条值得展开：**审批和权限是两种不同的控制手段，而它们可以互相替代。** 一个"能删任意数据但每次都要确认"的工具，和一个"只能删自己创建的数据、不需要确认"的工具，后者往往更好 —— 因为它把安全性放在了不依赖人的地方。

## 和前面几章的关系

这一章不是推翻前面，而是补上最后一块。完整的控制体系有四层：

| 层 | 章节 | 人的参与 |
|---|---|---|
| 权限 | 第 9、11 章 | 无（设计时决定） |
| 隔离 | 第 16 章 | 无 |
| 审批 | 本章 | **有（运行时）** |
| 审计 | 第 15、16 章 | 无（事后看） |

**审批是唯一一个需要人在运行中介入的机制** —— 这就是它特殊的地方：它最灵活（能处理没预料到的情况），但也最脆弱（依赖人的注意力）。

所以本章的核心问题可以重新表述为：**怎么用最少的人的注意力，覆盖最多的真实风险。** 下一节给出一个具体的答案。

## 一个常被忽略的成本：学习曲线也是成本

评估框架时，「上手快」经常被当成主要优点。但它只在**短期**成立。

一个抽象越省事，它在泄漏时需要你了解的东西就越多 —— 而泄漏是迟早会遇到的。到那时你要读它的源码、查它的 issue、理解它的内部模型。**这部分成本在选型时几乎总是被低估**，因为它不会出现在「三天跑通 demo」的体验里。

一个更实际的评估办法：**问「三个月后我遇到一个它不支持的场景，我该怎么办」**。答案决定了两件事：

- 如果是「绕开它，自己写那一小段」 → 成本可控，前提是它**允许你绕**
- 如果是「等它支持」或者「换框架」 → 这笔成本要在选型时就算进去

第 3 节那个 enum 的例子就是第一种：改一行注解就能绕开，成本很低。但有些框架把抽象做得很严密，你根本绕不开 —— 那时「省事」就变成了「受制」。

## 一份可以逐条过的清单

| 问题 | 为什么问 |
|---|---|
| 它能用在哪一类上？ | 工具接入是标配，差别在控制流和可观测性 |
| 我最复杂的分支它能表达吗？ | 表达不了就是选错了抽象 |
| 它允许我绕开吗？ | 不允许绕 = 泄漏时会卡死 |
| 出问题时我能看到中间状态吗？ | 没有可观测性，故障排查只能猜 |
| 我能不能说出它替换了哪几行？ | 说不出 = 不了解自己在依赖什么 |

五条里，**第三条最容易被忽略**。多数框架在用得顺的时候都很好；差别出现在你需要绕开它的时候 —— 而那一天一定会来。

## 五个档位在真实项目里的分布

最后给一个经验观察，它可以帮助判断自己是不是选错了档位。

大多数生产系统的档位分布长这样：

- **全自动**：占绝大多数调用。读、检索、生成草稿、格式化 —— 这些不该有任何人工环节。
- **关键点确认**：占少数，但覆盖了几乎全部不可逆动作。
- **事后复核**：用于那些"做完之后要留痕"的场景（合规要求、对外输出）。
- **逐步确认**：只在新上线、新模型、或者专门的调试模式里。
- **人做主**：只在决策类任务上（比如"要不要批这笔预算"）。

**如果"逐步确认"占了很大比例，那通常是一个信号** —— 要么权限设计得太宽（所以什么都要问），要么还没建立对系统的信任（所以什么都想看一眼）。前者改权限，后者要靠时间和数据积累。

反过来，如果"全自动"占 100% 而且没有任何审计，那也是一个信号 —— 不是"系统很成熟"，而是"没人看过它出什么错"。
## 完整可运行代码

下面这段代码把一个 7 步任务的三种审批策略跑一遍，统计中断次数与放行的不可逆动作数。

```python
"""审批点的粒度：一个任务会被打断几次。

同一份任务流程，三种审批策略下统计中断次数与"拦住的危险动作数"。
纯本地，实跑状态：2026-10-09。
"""

# 一个真实形态的任务：每步有 (名称, 是否可逆, 是否高危)
TASK = [
    ("read_doc",        True,  False),
    ("search_kb",       True,  False),
    ("summarize",       True,  False),
    ("draft_email",     True,  False),
    ("send_email",      False, False),   # 不可逆：发出去了收不回
    ("update_crm",      False, True),    # 不可逆 + 高危：改客户数据
    ("log_result",      True,  False),
]

POLICIES = {
    "A 每个动作都问":      lambda s: True,
    "B 只问不可逆动作":    lambda s: not s[1],
    "C 只问高危动作":      lambda s: s[2],
    "D 只在最后确认一次":  lambda s: False,
}


def run(policy):
    asked = []
    risky_executed = 0
    for i, step in enumerate(TASK, 1):
        if policy(step):
            asked.append((i, step[0]))
        else:
            if not step[1] or step[2]:
                risky_executed += 1
    return asked, risky_executed


if __name__ == "__main__":
    total_risky = sum(1 for s in TASK if (not s[1]) or s[2])
    print("任务共 %d 步，其中不可逆或高危的有 %d 步：" % (len(TASK), total_risky))
    for i, s in enumerate(TASK, 1):
        tag = []
        if not s[1]:
            tag.append("不可逆")
        if s[2]:
            tag.append("高危")
        print("    %d. %-14s %s" % (i, s[0], "、".join(tag) or "可逆且低危"))
    print()
    print("  %-20s %-10s %-12s %s" % ("策略", "中断次数", "未审批执行", "说明"))
    for name, pol in POLICIES.items():
        asked, risky = run(pol)
        note = {
            "A 每个动作都问": "打断 7 次 —— 审批疲劳，用户会开始盲点同意",
            "B 只问不可逆动作": "打断 2 次，全在真正不可逆的步骤上",
            "C 只问高危动作": "打断 1 次，但 send_email 无审批就发了",
            "D 只在最后确认一次": "0 次打断，两个不可逆动作全部裸奔",
        }[name]
        print("  %-20s %-10d %-12d %s" % (name, len(asked), risky, note))
    print()
    print("=== 关键点 ===")
    print("  A 看着最安全，代价是 7 次打断。而审批疲劳是真实存在的：")
    print("  用户在第 3 次之后就会开始不看内容直接点同意 —— 那时审批就失效了。")
    print()
    print("  C 看着「克制」，但它放过了 send_email（不可逆但不算高危）——")
    print("  而「发出去就收不回」正是最该问的那一类。")
    print()
    print("  正确的判据是 B：**按可逆性，不按危险程度**。")
    print("  理由：可逆的动作错了可以回滚；不可逆的错了只能补救。")
```

## 常见坑

- **"涉及数据就要确认"。** 全自动是很多场景的正确选择 —— 收窄权限、设额度、加回滚都不需要人参与。
- **忘了审批也有成本。** 每个动作都问会带来审批疲劳，而疲劳制造的是虚假的安全感。
- **档位一次定死。** 新上线该上移，稳定之后该下移 —— 没人往下调是最常见的浪费。
- **用审批替代权限设计。** "能删任意数据但每次确认"通常不如"只能删自己创建的、不需要确认"。
- **在量大时硬加逐步确认。** 应该降低单次风险（拆小动作、收窄权限），而不是假设有人看得过来。
- **不考虑代价落在谁身上。** 影响第三方的动作（发邮件、改别人的数据）档位要更高。
