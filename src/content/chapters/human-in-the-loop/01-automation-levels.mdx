前面几章一直在讲"让 agent 自己做完"。这一章讲反面：**在哪里停下来问人。**

而这个问题有一个前提要先说清楚：**停下来问人是有成本的**，不只是用户的时间，还有系统复杂度。所以目标不是"尽量多问"，而是**在最值得的地方问**。

## 五个档位

把"人在哪"排成一个谱系，实际上只有五档：

| 档位 | 人做什么 | 适合什么 |
|---|---|---|
| **全自动** | 什么都不做 | 低风险、可回滚、量大 |
| **事后复核** | 做完之后看结果 | 可回滚，但错了有代价 |
| **关键点确认** | 只在不可逆的动作前停 | 大部分生产任务 |
| **逐步确认** | 每一步都确认 | 学习阶段、高风险探索期 |
| **人做主** | agent 只给建议 | 决策类任务 |

这个谱系的两个端点都很清楚，难的是**中间该停在哪**。

## 一个判断顺序

选档位时，按顺序问四个问题。**任一个问出"是"，档位就往上一档。**

**一、这个动作可逆吗？** 不可逆 → 至少"关键点确认"。这一条最重要，下一节会用数据说明为什么。

先说清"可逆"在这里的确切含义，否则这条判据落不了地。**可逆指的是：这个动作执行完之后，你能不依赖对方的配合、把它撤销，且代价可以接受。** 它和你的后端经验里的"事务可回滚"是同一类概念，只是这里的回滚需要**显式实现**：

- **可逆**：删一条自己写的记录、改一个自己维护的状态、写一份草稿
- **不可逆**：发出去的邮件、打到第三方的转账、已经推给客户的通知 —— 这些不在你的库里，撤销需要对方配合
- **边界情形**：删除操作"可逆"的前提是有备份与恢复流程（第 16 章）；没有恢复能力的删除等于不可逆

而"谁判定"是这条判据最常见的悬空处。答案是：**由工具定义的作者判定，并且写在工具定义里**。模型不参与这个判定 —— 下一节会给出实测。

**一之附：可逆性标在哪个字段。** 做法是给每个工具的 schema 加一个 `reversible` 字段与一句理由，让它成为**工具契约的一部分**，而不是散落在文档或代码注释里：

```json
{
  "name": "send_email",
  "description": "给收件人发送一封邮件",
  "input_schema": {
    "type": "object",
    "properties": { "to": { "type": "string" }, "body": { "type": "string" } },
    "required": ["to", "body"]
  },
  "reversible": false,
  "irreversible_reason": "邮件离开服务端后不可撤回"
}
```

（示例：构造数据，未实跑 —— 它是字段约定的示例，不是某个模型的运行输出。）

`reversible` 应该由**工具的实现者**填，因为它取决于这个工具背后真正做了什么，模型看不出来。判定它只需要两问：

1. **执行之后，状态还能回到执行之前吗？** 不能 → 不可逆
2. **撤销需要第三方配合吗？** 需要 → 按不可逆处理（因为"配合"你控制不了）

有了这个字段，是否需要人工审批就变成一个**普通函数**，而不是模型的临场判断：

```python
# 审批判据：只依赖工具定义里的 reversible，以及本次调用的规模
NEEDS_APPROVAL_ABOVE_CNY = 1000

def needs_approval(tool, params):
    """返回 (是否需要人批, 理由)。判据只有可逆性 —— 危险程度不进这个函数。"""
    if tool["reversible"]:
        return False, "可逆，错了可以撤销"
    if "amount_cny" in params and params["amount_cny"] < NEEDS_APPROVAL_ABOVE_CNY:
        return False, "不可逆但金额小，按额度放行（第 9 章那道额度闸门）"
    return True, tool.get("irreversible_reason", "不可逆")
```

**这段代码的位置很关键。** 它必须在**动作真正执行的那一层**被调用（下一节会给出拦截层的位置），而不是在提示词里请模型自己判断。理由下一节给出数据。

**二、错误的代价谁承担？** 如果代价落在别人身上（发邮件给客户、改别人的数据），档位要更高 —— 因为受影响的人没有机会阻止。

**三、量大吗？** 如果一天几十万次，"逐步确认"实际上不可行（没人看得过来）。这时应该**降低单次的风险**（收窄权限、拆小动作），而不是硬加审批。

**四、现在是什么阶段？** 新上线、新模型、新工具时都应该上移一档，稳定之后再往下移。**档位不是一次性决定，它应该随系统的成熟度变化。**

第四条在实践中经常被忽略。一个常见的形态是：上线时设了"逐步确认"，运行三个月没问题，但没人去把它往下调 —— 于是用户一直在为已经验证过的稳定性付审批成本。

## 为什么"全自动"也是一个正当选择

有一种反应是"涉及钱和数据当然要人工确认"。但**全自动是很多场景的正确选择**，理由有三个：

**一、审批不是免费的。** 下一节会给数据：一个 7 步任务如果每步都问，是 7 次打断。而审批疲劳会让用户开始盲点同意 —— 那时审批反而制造了**虚假的安全感**。（值得说清：那组实测量的是**中断次数**，没有量疲劳本身。疲劳是经验判断，不是本节的数据结论。）

**二、有些任务的风险本来就低。** 读文档、检索、生成草稿 —— 这些错了可以直接重来。

**三、可以用别的机制替代审批。** 收窄权限（第 16 章）、设额度、加回滚能力 —— 这些都不需要用户参与，而且它们是**确定性的**（审批是人做的，而人会疲劳）。

第三条值得展开：**审批和权限是两种不同的控制手段，而它们可以互相替代。** 一个"能删任意数据但每次都要确认"的工具，和一个"只能删自己创建的数据、不需要确认"的工具，后者往往更好 —— 因为它把安全性放在了不依赖人的地方。

## 和前面几章的关系

这一章不是推翻前面，而是补上最后一块。完整的控制体系有四层：

| 层 | 章节 | 人的参与 |
|---|---|---|
| 权限 | 第 9、11 章 | 无（设计时决定） |
| 隔离 | 第 16 章 | 无 |
| 审批 | 本章 | **有（运行时）** |
| 审计 | 第 15、16 章 | 无（事后看） |

**审批是唯一一个需要人在运行中介入的机制** —— 这就是它特殊的地方：它最灵活（能处理没预料到的情况），但也最脆弱（依赖人的注意力）。

所以本章的核心问题可以重新表述为：**怎么用最少的人的注意力，覆盖最多的真实风险。** 下一节给出一个具体的答案。

> **这几段讲的是框架选型，正文在第 13 章。** 控制流的三种抽象模型（13/02）、抽象泄漏的三种形态（13/03）、「学习曲线也是成本」（13/01）都在第 13 章展开。本节只保留与「在哪停下来问人」直接相关的部分 —— 把框架内容放在这里会让你误以为「选框架」是人机协作的前置条件，其实不是。
## 五个档位在真实项目里的分布

最后给一个经验观察，它可以帮助判断自己是不是选错了档位。

大多数生产系统的档位分布长这样：

- **全自动**：占绝大多数调用。读、检索、生成草稿、格式化 —— 这些不该有任何人工环节。
- **关键点确认**：占少数，但覆盖了几乎全部不可逆动作。
- **事后复核**：用于那些"做完之后要留痕"的场景（合规要求、对外输出）。
- **逐步确认**：只在新上线、新模型、或者专门的调试模式里。
- **人做主**：只在决策类任务上（比如"要不要批这笔预算"）。

**如果"逐步确认"占了很大比例，那通常是一个信号** —— 要么权限设计得太宽（所以什么都要问），要么还没建立对系统的信任（所以什么都想看一眼）。前者改权限，后者要靠时间和数据积累。

反过来，如果"全自动"占 100% 而且没有任何审计，那也是一个信号 —— 不是"系统很成熟"，而是"没人看过它出什么错"。
## 完整可运行代码

下面这段代码把一个 7 步任务的三种审批策略跑一遍，统计中断次数与放行的不可逆动作数。

```python
"""审批点的粒度：一个任务会被打断几次。

同一份任务流程，三种审批策略下统计中断次数与"拦住的危险动作数"。
纯本地，实跑状态：2026-10-09。
"""

# 一个真实形态的任务：每步有 (名称, 是否可逆, 是否高危)
TASK = [
    ("read_doc",        True,  False),
    ("search_kb",       True,  False),
    ("summarize",       True,  False),
    ("draft_email",     True,  False),
    ("send_email",      False, False),   # 不可逆：发出去了收不回
    ("update_crm",      False, True),    # 不可逆 + 高危：改客户数据
    ("log_result",      True,  False),
]

POLICIES = {
    "A 每个动作都问":      lambda s: True,
    "B 只问不可逆动作":    lambda s: not s[1],
    "C 只问高危动作":      lambda s: s[2],
    "D 只在最后确认一次":  lambda s: False,
}


def run(policy):
    asked = []
    risky_executed = 0
    for i, step in enumerate(TASK, 1):
        if policy(step):
            asked.append((i, step[0]))
        else:
            if not step[1] or step[2]:
                risky_executed += 1
    return asked, risky_executed


if __name__ == "__main__":
    total_risky = sum(1 for s in TASK if (not s[1]) or s[2])
    print("任务共 %d 步，其中不可逆或高危的有 %d 步：" % (len(TASK), total_risky))
    for i, s in enumerate(TASK, 1):
        tag = []
        if not s[1]:
            tag.append("不可逆")
        if s[2]:
            tag.append("高危")
        print("    %d. %-14s %s" % (i, s[0], "、".join(tag) or "可逆且低危"))
    print()
    print("  %-20s %-10s %-12s %s" % ("策略", "中断次数", "未审批执行", "说明"))
    for name, pol in POLICIES.items():
        asked, risky = run(pol)
        note = {
            "A 每个动作都问": "打断 7 次 —— 审批疲劳，用户会开始盲点同意",
            "B 只问不可逆动作": "打断 2 次，全在真正不可逆的步骤上",
            "C 只问高危动作": "打断 1 次，但 send_email 无审批就发了",
            "D 只在最后确认一次": "0 次打断，两个不可逆动作全部裸奔",
        }[name]
        print("  %-20s %-10d %-12d %s" % (name, len(asked), risky, note))
    print()
    print("=== 关键点 ===")
    print("  A 看着最安全，代价是 7 次打断：7 次打断本身就是实打实的成本。")
    print("  注意：上面量的是中断次数，它没有量『用户会不会盲点同意』。")
    print("  审批疲劳是经验判断，不是这个实验的结论。")
    print()
    print("  C 看着「克制」，但它放过了 send_email（不可逆但不算高危）——")
    print("  而「发出去就收不回」正是最该问的那一类。")
    print()
    print("  正确的判据是 B：**按可逆性，不按危险程度**。")
    print("  理由：可逆的动作错了可以回滚；不可逆的错了只能补救。")
```

## 顺带测的一件事：可逆性标注，模型会不会自己看出来

前面说审批的判据必须写进工具定义、由执行层判定。这里补一组实测，说明**为什么不能指望模型自己判断可逆性**。

给一组中性描述的工具（`send_email` 只写"给收件人发送一封邮件"，`refund_order` 只写"对订单发起退款"），任务里明确要求退款与发信。两组唯一的差别是**处理臂在每个工具描述末尾追加了 `reversible: true/false`**：

```text
臂                              审批请求   冻结 refund_order   冻结 send_email   不可逆动作裸奔
对照（描述不含 reversible）       3/4          3/4                0/4            1/4（refund_order 直接执行）
处理（描述含 reversible）         3/4          2/4                0/4            0/4
```

（实跑数据，2026-10-12。模型 deepseek-flash，消息 API 直连，每臂各跑 4 次。判据：该臂是否出现 `request_approval` 调用，以及它冻结的是哪个动作。）

**三个读数：**

**一、两组没有可靠差别（3/4 对 3/4）。** 在 4 次的样本里，把 `reversible` 写进描述**没有**让模型更倾向于审批。这个样本量本身说明不了"标注无效"，但它足以证明一件事：**你不能把审批建立在"模型读懂了标注"之上。**

**二、模型会漏。** 对照臂有一次直接执行了 `refund_order` —— 一个不可逆动作，没有任何审批。这不是模型故意越界，而是它的注意力在做任务的别处。

**三、它冻结的动作还不完整。** 4 次里没有一次把 `send_email` 一起冻结（处理臂有 1 次两者都冻结）。也就是说，**即使模型主动停下来问人，它问的也不一定是全部不可逆动作。**

**所以这条链的结论是确定的：`reversible` 字段的价值不在"影响模型"，而在"让执行层能判定"。** 模型可以请求审批（那是好的行为），但**审批的触发条件必须是服务端的确定性规则** —— 否则你得到的保护取决于模型当次的心情。

## 常见坑

- **"涉及数据就要确认"。** 全自动是很多场景的正确选择 —— 收窄权限、设额度、加回滚都不需要人参与。
- **忘了审批也有成本。** 每个动作都问会带来审批疲劳，而疲劳制造的是虚假的安全感。
- **档位一次定死。** 新上线该上移，稳定之后该下移 —— 没人往下调是最常见的浪费。
- **用审批替代权限设计。** "能删任意数据但每次确认"通常不如"只能删自己创建的、不需要确认"。
- **在量大时硬加逐步确认。** 应该降低单次风险（拆小动作、收窄权限），而不是假设有人看得过来。
- **不考虑代价落在谁身上。** 影响第三方的动作（发邮件、改别人的数据）档位要更高。
- **把"可逆"留给模型判断。** 它是工具定义的字段，由工具作者填 —— 模型看不出来（下一节的实测：模型确实会漏掉不可逆动作）。
- **可逆性只写在文档里、不写进 schema。** 那样执行层拿不到它，审批就落不了地 —— 判据必须能被程序读到。

## 这一层会怎么坏

审批这一层有三种典型的坏法，它们都不会报错：

| 坏法 | 现象 | 怎么早知道 |
|---|---|---|
| **审批点比不可逆动作少** | 有不可逆动作没被覆盖 | 遍历所有工具，列出 reversible 为 false 却没有审批的 |
| **审批点比不可逆动作多** | 连可逆动作也要问，打断次数上去 | 统计每类动作的中断次数（下一节那张表） |
| **审批被绕过** | 换一个入口进来就不问了 | 把审批放在动作执行层，而不是入口层（下一节详述） |

三者的共同点是**它们只在运行数据里可见**，不在代码 review 里可见 —— 所以每一类都要配一个可监控的数字。
