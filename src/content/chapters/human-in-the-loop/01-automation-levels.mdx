前面几章一直在讲"让 agent 自己做完"。这一章讲反面：**在哪里停下来问人。**

而这个问题有一个前提要先说清楚：**停下来问人是有成本的**，不只是用户的时间，还有系统复杂度。所以目标不是"尽量多问"，而是**在最值得的地方问**。

## 五个档位（本节的决策框架）

为了讨论方便，本节把人的介入方式归为五档。这是一个工程决策框架，不是标准规定的唯一分类；实际系统可以组合多个控制：

| 档位 | 人做什么 | 适合什么 |
|---|---|---|
| **全自动** | 什么都不做 | 在主体授权和自动额度内，影响小且结果可观察 |
| **事后复核** | 做完之后看结果 | 可回滚，但错了有代价 |
| **关键点确认** | 超出自动执行策略时暂停 | 高影响、敏感、超额度或未预授权动作 |
| **逐步确认** | 每一步都确认 | 初期受控试运行或有明确监管要求的流程 |
| **人做主** | agent 只给建议 | 决策类任务 |

这个谱系的两个端点都很清楚，难的是**中间该停在哪**。

## 一个判断顺序

选档位时，结合动作影响、主体与对象授权、影响范围、可恢复性、任务频率和人工复核容量，再按组织策略决定自动执行、人工复核或拒绝。**某一项风险信号不自动等于审批；没有权限的动作应拒绝，不能靠用户点一次确认来补齐授权。**

**一、这个动作可逆吗？** 不可逆会提高风险，但若动作已在明确的主体、资源和额度范围内预授权，可以按策略自动执行；没有明确预授权时，应暂停或拒绝。这一项不能单独决定档位。

先说清"可逆"在这里的工程含义，否则这条判据落不了地。**可逆是指系统能否在可接受的时间和代价内，把业务状态可靠地恢复到等价状态。** 它与数据库事务回滚相关，但不是同一个保证：事务回滚只覆盖事务边界内的写入，邮件、通知或第三方状态可能已经被观察或产生后续影响；补偿操作也未必能撤销这些影响。

- **较容易恢复**：未发送的草稿、可在同一事务中撤销的状态变更；仍要评估范围、并发和下游观察
- **难以恢复**：已送达的邮件、外部转账、客户已收到的通知；即使能发起退款或更正，也不等于原影响已撤销
- **边界情形**：删除只有在恢复流程经过验证且满足时限/完整性要求时，才可按可恢复动作评估；备份存在本身不证明恢复可行

而"谁判定"是这条判据最常见的悬空处。工具作者描述动作属性；服务端策略根据已认证主体和当前资源决定 allow、review 或 deny。模型不负责授权判定 —— 下一节会给出实测。

**一之附：可逆性标在哪。** 把可逆性与理由记录在宿主侧可信的工具注册表/策略元数据中，并与模型可见的输入 schema 分开。它描述的是实现和副作用边界，不能让模型决定策略。下面把两者并排展示以便说明，`reversible` 并不是发给模型的参数字段：

```json
{
  "name": "send_email",
  "description": "给收件人发送一封邮件",
  "input_schema": {
    "type": "object",
    "properties": { "to": { "type": "string" }, "body": { "type": "string" } },
    "required": ["to", "body"]
  },
  "reversible": false,
  "irreversible_reason": "邮件离开服务端后不可撤回"
}
```

（示例：构造数据，未实跑 —— 它是字段约定的示例，不是某个模型的运行输出。）

`reversible` 应由**工具实现者**基于实际副作用填，并由宿主策略维护，因为它描述撤销能力，不是完整风险分数：

1. **执行之后，状态还能回到执行之前吗？** 不能 → 不可逆
2. **撤销需要第三方配合吗？** 需要 → 按不可逆处理（因为"配合"你控制不了）

审批策略还要结合影响范围、金额、数据敏感度、动作目标和调用者授权。可逆但影响全租户的批量操作仍可能要求审批；不可逆但金额低的动作，也只有在明确授权范围内才能自动执行。下面的函数是一个小型策略示例：

```python
# 示意策略函数；principal、tool 元数据与 policy 必须由服务端可信来源提供。
# 它不代替对象级授权、完整参数校验或受保护执行入口。
def needs_approval(tool, params, principal, policy):
    """Minimal policy fixture: malformed trusted inputs fail closed."""
    if not all(isinstance(value, dict) for value in (tool, params, principal, policy)):
        return "deny", "策略输入结构无效"

    name = tool.get("name")
    allowed_tools = principal.get("allowed_tools")
    if not isinstance(name, str) or not name.strip():
        return "deny", "工具元数据缺少有效名称"
    if not isinstance(allowed_tools, (set, frozenset, list, tuple)) or any(
        not isinstance(item, str) for item in allowed_tools
    ):
        return "deny", "主体授权元数据无效"
    if name not in allowed_tools:
        return "deny", "主体无权调用此工具"

    # 比较阈值与风险标签必须来自可信、完整的策略元数据。
    numeric_fields = (
        (tool, "impact_scope"),
        (tool, "data_sensitivity"),
        (policy, "max_auto_scope"),
        (policy, "max_auto_amount_fen"),
        (policy, "max_auto_sensitivity"),
    )
    for source, field in numeric_fields:
        value = source.get(field)
        if isinstance(value, bool) or not isinstance(value, int) or value < 0:
            return "deny", f"策略元数据无效：{field}"

    reversible = tool.get("reversible")
    amount_required = tool.get("amount_required", False)
    if not isinstance(reversible, bool) or not isinstance(amount_required, bool):
        return "deny", "工具风险元数据无效"

    preapproved = policy.get("preapproved_irreversible_tools")
    if not isinstance(preapproved, (set, frozenset, list, tuple)) or any(
        not isinstance(item, str) for item in preapproved
    ):
        return "deny", "不可逆动作预授权策略无效"
    reason = tool.get("irreversible_reason", "动作不可逆且未预授权")
    if not isinstance(reason, str):
        return "deny", "不可逆原因元数据无效"

    if amount_required and "amount_fen" not in params:
        return "deny", "缺少必需的金额参数"
    amount_fen = params.get("amount_fen", 0)
    if isinstance(amount_fen, bool) or not isinstance(amount_fen, int) or amount_fen < 0:
        return "deny", "金额参数无效"

    reasons = []
    if tool["impact_scope"] > policy["max_auto_scope"]:
        reasons.append("影响范围超出自动执行额度")
    if amount_fen > policy["max_auto_amount_fen"]:
        reasons.append("金额超出自动执行额度")
    if tool["data_sensitivity"] > policy["max_auto_sensitivity"]:
        reasons.append("数据敏感度超出自动执行范围")
    if not reversible and name not in preapproved:
        reasons.append(reason)
    if reasons:
        return "review", "；".join(reasons)
    return "allow", "在主体授权与自动执行策略范围内"

# 可逆但影响全租户：仍需审批；低金额且明确预授权的动作：可自动执行。
assert needs_approval(
    {"name": "bulk_update", "amount_required": False, "reversible": True, "impact_scope": 3, "data_sensitivity": 1},
    {}, {"allowed_tools": {"bulk_update"}},
    {"max_auto_scope": 1, "max_auto_amount_fen": 100000, "max_auto_sensitivity": 1,
     "preapproved_irreversible_tools": set()},
)[0] == "review"

assert needs_approval(
    {"name": "small_refund", "amount_required": True, "reversible": False, "impact_scope": 1, "data_sensitivity": 0},
    {"amount_fen": 5000}, {"allowed_tools": {"small_refund"}},
    {"max_auto_scope": 1, "max_auto_amount_fen": 100000, "max_auto_sensitivity": 1,
     "preapproved_irreversible_tools": {"small_refund"}},
)[0] == "allow"

assert needs_approval(
    {"name": "small_refund", "amount_required": True, "reversible": False, "impact_scope": 1, "data_sensitivity": 0},
    {"amount_fen": True}, {"allowed_tools": {"small_refund"}},
    {"max_auto_scope": 1, "max_auto_amount_fen": 100000, "max_auto_sensitivity": 1,
     "preapproved_irreversible_tools": {"small_refund"}},
)[0] == "deny"
```

该演示要求 `amount_required` 为真的工具显式提供金额；缺失金额不会被当成 0。缺少或类型错误的主体授权、风险标签、阈值和预授权元数据都会拒绝。它仍未实现完整参数 schema、多租户对象授权、精确资金类型、策略版本/变更竞争或执行时重验；生产系统应使用业务域精确数值类型与受保护服务端门禁，不要复制此函数作为完整授权方案。

**这段代码只是策略判定函数，不是执行保护本身。** 它必须由宿主在受保护动作执行路径中调用；所有同步、批量、重试和异步入口都要验证覆盖。模型不应成为授权或审批判定点。

**二、错误的代价落在谁身上？** 第三方影响是风险输入之一，但不自动决定审批档位；还要看影响程度、授权范围、可恢复性和业务策略。

**三、人工复核量是否可承受？** 在高频场景，逐步确认可能形成队列和操作负担。应按任务风险分层、收窄每次授权范围，并验证复核容量与漏检风险；单纯因为调用量大而取消必要控制也不合理。

**四、当前有哪些变化和证据？** 新模型、新工具或策略变更可以触发额外验证、分阶段发布或临时收紧，但不意味着一律“上移一档”。是否放宽控制，要看预先约定的评测结果、运行监控、影响范围和回滚能力；一段时间未出事故本身不是充分证据。

档位需要定期复核，但不能仅按运行时长或“最近没出事”降低控制；调整应有明确证据、责任人和回滚路径。

## 为什么"全自动"也是一个正当选择

有一种反应是"涉及钱和数据当然要人工确认"。但**全自动是很多场景的正确选择**，理由有三个：

**一、审批有成本，也不保证有效。** 下一节的合成任务统计了 7 次逐步确认；它没有测真实用户负担、盲批或疲劳。是否需要某个人工关口，应由风险、授权与评估证据决定。

**二、有些任务的风险本来就低。** 读文档、检索、生成草稿 —— 这些错了可以直接重来。

**三、审批应与其他控制共同设计。** 收窄权限、设额度、执行前校验和恢复能力可以减少风险或缩小影响，但各自覆盖不同失效形态，通常不能相互替代。人工审批也不能补足缺失的权限；它自身的有效性仍需验证。

例如，限制删除工具只能操作当前主体拥有的记录，可以降低错误或越权调用的影响；对超出该范围的动作应拒绝或进入另一个明确的授权流程。这个权限边界不能因用户在审批页点击“同意”而消失。

## 和前面几章的关系

这一章不是推翻前面，而是补上最后一块。完整的控制体系有四层：

| 层 | 章节 | 人的参与 |
|---|---|---|
| 权限 | 第 9、11 章 | 无（设计时决定） |
| 隔离 | 第 16 章 | 无 |
| 审批 | 本章 | **有（运行时）** |
| 审计 | 第 15、16 章 | 无（事后看） |

**审批是唯一一个需要人在运行中介入的机制** —— 这就是它特殊的地方：它最灵活（能处理没预料到的情况），但也最脆弱（依赖人的注意力）。

所以本章的核心问题可以重新表述为：**怎么用最少的人的注意力，覆盖最多的真实风险。** 下一节给出一个具体的答案。

> **这几段讲的是框架选型，正文在第 13 章。** 控制流的三种抽象模型（13/02）、抽象泄漏的三种形态（13/03）、「学习曲线也是成本」（13/01）都在第 13 章展开。本节只保留与「在哪停下来问人」直接相关的部分 —— 把框架内容放在这里会让你误以为「选框架」是人机协作的前置条件，其实不是。
## 用场景选档，不预设项目分布

五档是讨论控制方式的词汇，不代表真实系统应有固定比例。可以用以下场景检查策略是否覆盖了不同目标：

- 只读检索、草稿生成：在主体授权、数据边界和额度内自动执行，并按风险保留必要观测。
- 已授权的小额动作：按服务端策略自动执行；影响范围或额度越界时拒绝或进入执行前审批。
- 已发生且不可撤销的对外动作：执行前风险控制与事后抽样复核承担不同职责，不能把复核当作预防。
- 新工具或策略变更：可先采用受控流量、人工复核或逐步确认；是否放宽由预先定义的评测和运行证据决定。
- 价值判断或责任决策：系统整理材料与选项，由有权主体作决定。

观察到某档比例偏高时，应先按任务类型、风险、权限和失败结果分层，再检查复核容量与策略目标；总比例本身既不能诊断原因，也不能证明成熟度或信任程度。
## 完整可运行代码

下面这段代码把一个 7 步合成任务的四种策略跑一遍，分别统计执行前审批、事后复核与未审批执行的风险动作数。

```python
"""审批点的粒度：一个任务会被打断几次。

同一份任务流程，四种策略下统计执行前审批、事后复核与未审批执行的风险动作数。D 是任务结束后复核；这不是执行前审批，无法阻止已经发生的副作用。
纯本地，实跑状态：2026-10-09。
"""

# 一个真实形态的任务：每步有 (名称, 是否可逆, 是否高危)
TASK = [
    ("read_doc",        True,  False),
    ("search_kb",       True,  False),
    ("summarize",       True,  False),
    ("draft_email",     True,  False),
    ("send_email",      False, False),   # 不可逆：发出去了收不回
    ("update_crm",      False, True),    # 不可逆 + 高危：改客户数据
    ("log_result",      True,  False),
]

POLICIES = {
    "A 每个动作都问":      lambda s: True,
    "B 只问不可逆动作":    lambda s: not s[1],
    "C 只问高危动作":      lambda s: s[2],
    "D 任务结束后复核一次":  lambda s: False,
}


def run(policy, review_after=False):
    asked = []
    risky_executed = 0
    for i, step in enumerate(TASK, 1):
        if policy(step):
            asked.append((i, step[0]))
        else:
            if not step[1] or step[2]:
                risky_executed += 1
    return asked, risky_executed, int(review_after)


if __name__ == "__main__":
    total_risky = sum(1 for s in TASK if (not s[1]) or s[2])
    print("任务共 %d 步，其中不可逆或高危的有 %d 步：" % (len(TASK), total_risky))
    for i, s in enumerate(TASK, 1):
        tag = []
        if not s[1]:
            tag.append("不可逆")
        if s[2]:
            tag.append("高危")
        print("    %d. %-14s %s" % (i, s[0], "、".join(tag) or "可逆且低危"))
    print()
    print("  %-20s %-10s %-10s %-12s" % ("策略", "执行前审批", "事后复核", "未审批风险动作"))
    for name, pol in POLICIES.items():
        asked, risky, reviewed_after = run(pol, review_after=name == "D 任务结束后复核一次")
        print("  %-20s %-10d %-10d %-12d" % (name, len(asked), reviewed_after, risky))
    print()
    print("=== 关键点 ===")
    print("  A 有 7 次审批；这里统计次数，不测真实用户负担或疲劳。")
    print()
    print("  C 未审批执行 send_email；不可逆/高危属性是作者给定的标签。")
    print()
    print("  仅就这个合成任务的审批次数和未审批风险动作数，B 优于 C。")
    print("  这不是通用审批公式：生产策略还要结合影响范围、敏感度、金额与主体授权。")
```

## 历史小样本记录：模型能否根据工具说明识别可逆性

前面说审批的判据必须由执行层判定。这里保留一组历史记录，作为待复核线索；由于缺少逐次原始材料，它不能说明模型通常能否识别可逆性。

旧记录称，实验使用中性工具描述（`send_email` 写"给收件人发送一封邮件"，`refund_order` 写"对订单发起退款"），任务要求退款与发信；处理臂在工具描述末尾追加了 `reversible: true/false`。下表仅保留当时记录的摘要：

> **证据限制：** 当前仓库没有逐次原始请求/响应、完整模型与参数指纹、题目映射或 scorer，无法独立重算这些分数。`deepseek-flash` 仅是旧记录中的模型标签，不足以确定具体 API model ID 或版本。不要将这组数字当作已复现结果或普遍行为证据。

```text
臂                              审批请求   冻结 refund_order   冻结 send_email   不可逆动作裸奔
对照（描述不含 reversible）       3/4          3/4                0/4            1/4（refund_order 直接执行）
处理（描述含 reversible）         3/4          2/4                0/4            0/4
```

（旧记录标注日期为 2026-10-12、模型标签为 `deepseek-flash`，并称消息 API 直连、每臂各 4 次。以上信息也没有原始运行记录佐证；判据仅按旧摘要转述为是否出现 `request_approval` 以及冻结了哪个动作。）

**三个读数：**

**一、旧摘要记录两臂均为 3/4。** 由于原始样本不可复核，不能判断差异是否真实，更不能从四次试验估计整体效果。架构上仍应把授权和审批策略放在宿主执行路径中，不能把模型对说明文字的响应当成强制控制。

**二、旧摘要称对照臂有一次 `refund_order` 未经审批执行。** 在原始轨迹缺失时，这只是未经独立复核的报告，不能推断模型为什么如此响应或该行为是否稳定。

**三、旧摘要称 `send_email` 的审批请求数为 0/4，处理臂有 1/4 次同时冻结两项动作。** 若该摘要准确，它提示需检查一次审批是否覆盖同一任务中的所有副作用；当前证据不能验证其计数。

**稳妥的工程结论不依赖这组小样本：** 工具描述和模型返回都不是授权边界。服务端必须根据认证主体、目标资源、动作参数与当前策略作决定；需要复核时，审批提案须覆盖将要执行的具体动作，并在副作用执行点再次验证。该历史摘要不能证明模型总体上是否能识别可逆性。

## 常见坑

- **"涉及数据就要确认"。** 全自动是很多场景的正确选择 —— 收窄权限、设额度、加回滚都不需要人参与。
- **把审批次数直接当成审批质量。** 本节的合成计数没有测用户疲劳或审核质量。
- **档位一次定死或按时间自动放宽。** 策略变更应由评测和运行证据支持，并能回滚；“稳定一段时间”本身不足以降低控制。
- **用审批替代权限设计。** "能删任意数据但每次确认"通常不如"只能删自己创建的、不需要确认"。
- **在量大时硬加逐步确认。** 应该降低单次风险（拆小动作、收窄权限），而不是假设有人看得过来。
- **不考虑影响对象。** 第三方影响是风险因素之一，仍须结合授权、影响规模、补救路径和业务策略判断。
- **让模型决定动作是否需要审批。** 风险属性由宿主侧可信元数据与策略处理，模型提议不能代替服务端授权；下一节的小样本摘要不可独立复核，不作为这一设计原则的证据。
- **把可逆性当作完整审批策略。** 它只说明动作能否撤销，不能表达影响范围、敏感度和主体授权；策略必须由服务端综合判定。

## 这一层会怎么坏

审批这一层有三种典型的坏法，它们都不会报错：

| 坏法 | 现象 | 怎么早知道 |
|---|---|---|
| **高风险/未预授权动作没有被策略覆盖** | 需要复核的动作在没有适用批准时仍执行 | 清点写操作及入口，按主体、对象、参数和策略检查 allow/review/deny 路径 |
| **审批点比不可逆动作多** | 连可逆动作也要问，打断次数上去 | 统计每类动作的中断次数（下一节那张表） |
| **审批被绕过** | 换一个入口进来就不问了 | 把审批放在动作执行层，而不是入口层（下一节详述） |

这些问题可在代码审查、针对性测试和运行观测中分别发现；仅凭单一计数或日志都不能证明覆盖完整。
