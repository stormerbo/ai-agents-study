审批的本质是**把一次执行切成两段**：跑到要问的地方停下，人回答之后继续。这一节讲这个「停下再继续」在实现上要注意什么。

## 中断不是暂停

一个常见的误解是把中断当成「暂停一个正在跑的东西」。更准确地说：**等待人的期间不应占着同步请求、worker、数据库事务或锁**；运行时可以保留一个被挂起的逻辑任务，但要能跨进程恢复时，状态不能只活在该进程的内存里。

一种常见模型是：**把执行状态持久化下来，结束这次请求，等人回答后由新的请求或 worker 恢复**；队列编排或 durable workflow 也可以实现同一生命周期。

这个区别带来三个实际后果：

- **等待可以超过一次请求/worker 的生命周期**；是否采用 durable execution 取决于任务和运行时
- **不能依赖进程内存**，状态必须在存储里
- **要能跨进程恢复**，因为回答可能来自另一个实例

第 11 章讲断点恢复时给过一条结论：**在「副作用已发生、状态未落盘」之间崩溃会重复执行。** 审批场景的断点恰好落在这个危险区间附近 —— 因为**你停下时，前一个动作可能已经执行了**。

## 恢复时最容易出的两个错

**错误一：重复提交或重复副作用。** 用户双击、浏览器重试、服务重启都可能让相同的请求再次到达；它们本身不必然产生重复副作用，是否重复取决于服务端状态转换、动作幂等键和接收端去重。

第 11 章的历史实测记录是：朴素版写入 `u1, u2, u2, u3`（4 条，重复 1），幂等版 `u1, u2, u3`（3 条）。这组结果仅描述该章的本地故障注入，不代表所有审批服务的重复率。审批等待会带来较长的状态有效期和更多重放机会；不能据此断言它的重复概率高于崩溃。

审批记录 ID、工作流动作 ID、外部接收端幂等键承担不同职责。服务端生成稳定的动作 ID 并持久化；执行时以原子状态转换防止重复领取。若效果在外部系统发生，还需接收端按同一键去重，或在结果未知时对账；本地“检查过未执行”不等于外部副作用只发生一次。

**错误二：审批结果与上下文不匹配。** 用户同意的是「发给 zhangsan 的那封邮件」，但恢复时提案参数、目标对象版本、主体授权或策略已经变了；若仍按旧批准执行，可能产生过期或越权效果。

修法：**把足以界定本次动作的最小必要提案内容冻结下来**，或引用不可变的业务对象版本；恢复时除核对审批绑定内容，还要重新验证当前授权、期限和业务前置条件。敏感字段应受保护并设置保留策略。

## 恢复之后要不要重新规划

一个设计问题：人回答之后，是继续原计划，还是让模型重新规划一次？两种都要，取决于人的回答内容：

| 人的回答 | 接下来做什么 |
|---|---|
| **同意** | 仅在身份、权限、审批状态、期限、策略和冻结提案都通过服务端复核后，执行同一版本 |
| **提出修改** | 生成新版本、重新展示并要求对该版本作出新决定；旧批准不能沿用 |
| **拒绝** | 遵守拒绝；若这是授权/策略拒绝或用户要求停止，就终止该动作/任务。只有策略允许且不会绕过拒绝时，才可提出替代方案重新审核 |
| **主动改用其他方式** | 将人的约束纳入新计划，再对新计划中的受保护动作重新做权限与风险判断 |

将修改后的内容直接执行同样危险：原批准绑定的是旧提案。必须把修改作为新提案，重新校验授权并取得针对新版本的批准；不能让模型在批准后悄悄改写参数。

拒绝不能一概解释为“只拒绝了这一步”。拒绝原因可能是用户停止、权限不足、政策禁止或信息不足；尝试另一条路线之前必须判断拒绝范围，不能把重新规划变成绕过否决。

## 状态里要存什么

第 11 章讲过断点恢复要存什么。审批场景要额外存三样：

```text
1. 待审批的动作（完整冻结，含参数）
2. 这个动作的唯一 id（用于幂等）
3. 为什么需要审批（可逆性、影响范围）—— 因为界面要展示它
4. 已经执行过的动作列表（恢复时不能重做）
```

第 4 条是第 11 章故障注入场景的应用：恢复前要核对每一步的持久化状态和外部结果；工作流 checkpoint/动作账本可以记录已确认步骤，但单独保存“已执行列表”不足以消除“外部成功、本地未记账”的未知窗口。

但"完整冻结"到底长什么样、这条记录写到哪、下一次请求怎么把它读回来 —— 这三步缺任何一步就做不出来。下面把它们补齐。

## 落盘：恢复状态与外部效果分开建模

等待期间必须释放 worker/请求资源，但“把数据写到外部存储”还不足以构成安全恢复。先定义谁拥有什么状态，以及恢复后如何证明审批仍有效。

一条持久化提案可包含以下字段；按数据最小化原则保存执行所需的最少内容，敏感参数应设置访问控制、加密与保留期限：

```text
approval_id       服务端生成的不可猜引用；本身不是授权凭据
tenant_id         所属租户/账户
subject_id        发起任务的主体
approver_policy   允许审批的角色/策略版本（仍需恢复时重新校验）
action_id         稳定的动作标识，与 approval_id 区分
proposal_version  每次编辑递增；批准绑定一个确定版本
proposal_digest   服务端对规范化提案内容计算的摘要，含动作、目标与参数
status            pending / approved / executing / succeeded / rejected / expired / unknown
expires_at        过期时间；过期审批不能被重新激活执行
checkpoint_ref    工作流检查点；恢复位置与已完成步骤的版本
```

摘要用于发现内容变化，不取代服务端授权，也不应信任浏览器传回的摘要。摘要必须由服务端对同一规范化提案计算；跨租户、动作类型或目标对象的差异必须进入绑定内容。审批记录 ID 只用于定位记录，服务端仍要验证当前调用者是否可查看、审批和执行该对象。

```text
收到决定 → 校验身份/租户/审批角色、期限和当前授权策略
         → 按 approval_id 锁定当前记录并校验 proposal_version 与服务端摘要
         → 同意：pending → approved（记录人的决定，尚未执行副作用）
         → 拒绝：pending → rejected
         → 修改：创建新版本并回到 pending，旧批准不迁移
         → 过期/权限撤销/参数变化：标记 expired 或 invalidated，不执行
```

**人的“同意”与副作用执行前的一次性授权消费是两个状态。** 执行组件应在紧邻受保护动作前，通过服务端原子状态转换验证该决定属于当前 actor 和精确的冻结提案、仍在有效期内、权限/策略仍允许，并原子消费本次 approval、把唯一一次执行权从 `approved` 消费为 `executing`（或等价状态）；只有成功消费的那一个 worker 才能发起动作。OWASP 的 [AI Agent Security 指引](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html)也要求校验并原子消费 approval，避免并发/重放复用。批准记录或浏览器里的 `user_confirmed` 标记本身都不够。

若通过 outbox 异步执行，审批过期语义必须落到明确的边界。本节把 `expires_at` 定义为**执行 claim 的截止时间**：worker 真正领取动作时要重新核对，过期的待投递动作不得启动。若产品采用“决定在期限内即可排队”的其他语义，应显式命名并说明其风险边界。动作一旦启动后结果变为 `unknown`，过期不能证明外部效果没发生；只能先按稳定 action key 对账，不能因过期而重新消费审批并盲目重发。还要覆盖一个常被漏掉的崩溃窗口：接收端已经提交，但调用方在写入回执或 `unknown` 状态前崩溃，本地记录仍显示 `approved`。恢复时应先查询接收端的权威幂等账本；若找到同键同指纹的结果，就对账并补写成功状态，不得因本地状态陈旧或审批已过期而再次发送。接收端若不提供权威查询/幂等契约，查不到记录不能证明动作未发生。

PostgreSQL 的 `SELECT ... FOR UPDATE` 会锁住返回行，阻塞对同一行的竞争更新/锁定直到当前事务结束；锁定读与事务隔离级别也会影响并发行为。它不替代状态条件、权限检查、过期检查，也不把数据库事务延伸到外部服务。应在短事务内重新验证记录并执行条件状态更新，检查恰好影响一行；不要在等待人工输入期间持有事务或行锁。[PostgreSQL 18 行锁文档](https://www.postgresql.org/docs/18/explicit-locking.html) 还提醒，长时间持有锁会阻塞其他事务。

下面是**事务边界示意，不是可直接运行的完整 SQL**。应用在锁内校验当前用户/角色、租户策略和冻结提案；`UPDATE` 的条件再防止重复决定与审批过期竞态。只有检查确实返回一行才提交：

```sql
BEGIN;
SELECT approval_id, proposal_version, proposal_digest, status, expires_at,
       action_id, frozen_action
  FROM approvals
 WHERE approval_id = :approval_id AND tenant_id = :authenticated_tenant
 FOR UPDATE;
-- 服务端检查当前 approver 权限、策略、proposal_digest 与对象版本。
UPDATE approvals
   SET status = 'approved', decided_by = :authenticated_actor,
       decided_at = clock_timestamp()
 WHERE approval_id = :approval_id
   AND tenant_id = :authenticated_tenant
   AND status = 'pending'
   AND proposal_version = :version_displayed_to_approver
   AND expires_at > clock_timestamp()
RETURNING action_id, frozen_action;
-- 必须恰好返回一行；否则 ROLLBACK，不能执行。
-- 外部效果：在此事务内 INSERT outbox(action_id, frozen_action, 'pending')。
-- 同库效果：在此事务内写业务表，并将动作/审批状态记为 succeeded。
COMMIT;
```

对外部效果，这个事务记录的是人的决定与待投递任务；它还没有许可 dispatcher 忽略后续状态。worker 应在真正发起副作用前，以条件更新/行锁原子地将 `approved` 消费为 `executing`，并复查 `expires_at`、冻结版本和当前权限；只有成功 claim 的 worker 才能发送。若 claim 后进程崩溃，必须根据接收端幂等键和 `unknown` 状态对账，不得重新把已消费的批准当作新的发送许可。示例将 `expires_at` 定义为 worker claim 截止时间；若系统将其定义为用户决定截止时间，应使用另一个明确字段描述执行期限。

`clock_timestamp()` 用于在语句实际执行时检查期限；PostgreSQL 的事务时间函数 `now()` 固定为事务开始时间，锁等待较久时二者语义不同。[PostgreSQL 18 日期/时间函数文档](https://www.postgresql.org/docs/18/functions-datetime.html) 说明了这些时间函数的差异。生产实现还需定义冲突/死锁/重试处理，并用真实数据库测试条件更新及过期竞态。

若受保护效果完全在同一数据库内，状态 claim、业务写入与成功标记可在一个数据库事务中完成。若效果在邮件、支付等外部系统，事务 outbox 可以原子保存“已授权待投递”的本地状态和投递任务，但 dispatcher 通常可能重复投递。接收方必须以稳定幂等键去重并对同键异参作出冲突处理；否则超时后应记录 `unknown`，查询有权威性的结果或人工对账，不能把“查不到”默认等同“没有发生”。本地数据库事务本身不提供跨服务 exactly-once。不同接收方对幂等键的保存和清理策略不同；例如 [Stripe API v1 会在至少 24 小时后清理幂等记录](https://docs.stripe.com/api/idempotent_requests)，过期后重用同一键仍可能变成新请求，因此重试期限必须符合具体下游契约。

审批等待期间，任务上下文、账户授权、对象状态和策略都可能变化。恢复时应从持久化 checkpoint 载入，并对剩余动作按当前策略重新校验；对已经授权的某个冻结动作，不得让模型重写动作参数后沿用旧批准。

## 一个具体的失败形态

第 11 章的教学 fixture 在本地注入“效果写入后、checkpoint 落盘前”中断，历史输出为朴素版 4 条（含 1 条重复）、去重版 3 条。它说明该 fixture 的恢复路径会重放动作；不代表每种数据库、队列或接收端都有相同结果。

## 审批等待与故障窗口怎么观察

可以按动作类型、风险级别和主体统计等待时长、批准/拒绝/修改/过期比例、队列积压和后续结果。它们是调查线索，不是单独的诊断：等待长可能来自通知、时区、排班或信息不足；频繁修改可能源于提案质量，也可能源于界面、策略或用户偏好。对日志做数据最小化，不默认长期保存完整 prompt、邮件正文或敏感参数。


> **「抽象泄漏」的完整定义与三种形态在第 13 章第 3 节**（agent-frameworks/03-leaky-abstractions）。本节只需要它的一条推论：当错误语义被压平时，恢复逻辑会把「不知道」误判成「已完成」，所以恢复前必须先核对副作用记录。
## 将等待期和副作用不确定窗口分开

崩溃窗口没有固定的“微秒级”长度：它取决于实现、存储、网络和故障位置。审批等待则是一个可能较长的业务状态期，期间权限、对象版本、策略和提案时效都可能变化。它们不是同一个窗口，也不能仅按时长比较重复概率。

恢复流程至少要区分三件事：审批决定是否仍对当前提案有效；动作是否已被本地 worker claim；外部服务是否已产生效果。每一项都需要自己的持久状态和重试规则。刷新、重复提交或服务重启应返回同一审批/动作的既有状态；它们不能成为再次绕过状态门禁的路径。
## 完整可运行代码

下面的本地模型演示几个必须分开的状态：审批绑定提案摘要；编辑后产生新版本并使旧提案失效；执行前验证审批主体、租户和期限；外部接收端按稳定 `action_id` 去重。它**不是持久化、并发或跨服务事务的证明**，内存字典和模拟接收端不具备这些生产保证。

```python
"""本地状态机示例：批准绑定版本；外部收件端模拟幂等去重。

实跑状态：纯 Python 标准库离线运行。此 fixture 不证明数据库持久性、
并发安全、真实身份认证或外部服务的幂等能力。
"""
import hashlib
import json


def digest(tenant_id, action, params):
    canonical = json.dumps(
        {"tenant_id": tenant_id, "action": action, "params": params},
        sort_keys=True, separators=(",", ":"), ensure_ascii=False,
    ).encode("utf-8")
    return hashlib.sha256(canonical).hexdigest()


class Fixture:
    def __init__(self):
        self.approvals = {}
        self.effects = {}  # fake receiver's persisted idempotency ledger
        self.next_id = 0

    def create(self, tenant_id, action, params, now, ttl=60, version=1):
        self.next_id += 1
        approval_id = f"approval-{self.next_id}"
        action_id = f"action-{self.next_id}"
        self.approvals[approval_id] = {
            "tenant_id": tenant_id, "action": action, "params": dict(params),
            "digest": digest(tenant_id, action, params), "version": version,
            "action_id": action_id, "expires_at": now + ttl, "status": "pending",
        }
        return approval_id

    def decide(self, approval_id, actor_tenant, actor_id, expected_digest, now):
        rec = self.approvals.get(approval_id)
        if rec is None or rec["tenant_id"] != actor_tenant:
            return "not_found_or_forbidden"
        approvers_by_tenant = {"tenant-1": {"alice"}}
        if actor_id not in approvers_by_tenant.get(actor_tenant, set()):
            return "forbidden"
        if now >= rec["expires_at"]:
            rec["status"] = "expired"
            return "expired"
        if rec["status"] != "pending" or rec["digest"] != expected_digest:
            return "stale_or_already_decided"
        rec["status"] = "approved"
        return "approved"

    def edit_as_new_proposal(self, approval_id, new_params, now):
        old = self.approvals[approval_id]
        if old["status"] not in {"pending", "approved"}:
            raise ValueError("only an unexecuted proposal can be edited")
        old["status"] = "invalidated"
        return self.create(
            old["tenant_id"], old["action"], new_params, now,
            ttl=max(1, old["expires_at"] - now), version=old["version"] + 1,
        )

    def deliver(self, approval_id, now, lose_receipt=False):
        rec = self.approvals[approval_id]
        if rec["status"] not in {"approved", "unknown"}:
            return rec["status"]
        key = rec["action_id"]
        fingerprint = rec["digest"]
        prior = self.effects.get(key)
        if prior and prior["fingerprint"] != fingerprint:
            return "idempotency_key_conflict"
        if prior is not None:
            # Any authoritative receiver record wins, even if the caller crashed
            # while the local approval still says approved.
            rec["status"] = "succeeded"
            return prior["result"]
        if rec["status"] == "unknown":
            return "unknown"  # absence is not proof unless receiver lookup is authoritative
        if now >= rec["expires_at"]:
            rec["status"] = "expired"
```

## 常见坑

- **把中断当暂停。** 应该持久化状态、结束请求 —— 因为等待可能持续几小时。
- **恢复时只看审批记录，不核对动作结果。** 重复提交应返回已有决定；副作用是否发生还要检查本地动作状态和接收端回执。
- **审批通过后重新生成动作。** 用户同意的是那个具体动作，必须完整冻结，不能恢复时再生成。
- **修改后沿用旧批准，或批准后让模型改写参数。** 修改应创建新提案版本并重新授权/审批；批准必须绑定将要执行的内容。
- **把拒绝当成自动改道信号。** 先判断拒绝的主体与范围；授权/政策拒绝不能通过另一工具或新计划绕过。
- **把等待时长或修改率当作根因。** 它们是需分层调查的信号，不能单独证明界面信息不足或模型参数有偏差。
- **把审批 ID 当幂等键。** 对外部副作用使用稳定动作键，并由接收端按键去重；持久 ledger 应对同键异参冲突拒绝。时间戳或 ID 难猜本身不能替代此机制。
- **只存审批状态，不存 workflow checkpoint/动作结果。** 那样恢复时无法区分已完成步骤与结果未知步骤。
- **把本地锁当成外部幂等。** 同一数据库可用短事务/条件更新防止并发 claim；外部效果仍要靠接收端去重或对账，二者不可互换。

## 这一层会怎么坏

三种坏法，都不会报错：

| 坏法 | 现象 | 怎么发现 |
|---|---|---|
| **状态在进程内存里** | 单实例测试全过，扩容或重启后"找不到待审批动作" | 部署两个实例后跑一遍审批流程 |
| **幂等键不唯一或被异参复用** | 不同动作被误合并，或重放时参数不一致 | 并发创建键、同键异参和超出保留期的重试测试；用唯一约束和接收端契约验证 |
| **本地状态与本地副作用未原子提交** | 重启后可能重复本地业务写入 | 在事务提交前后注入故障，核对数据库状态与动作次数 |

三者的共同点是**在单实例、低并发、不崩溃的开发环境里完全看不到** —— 所以它们必须靠**故意制造的坏条件**（多实例、并发、注入崩溃）来验证，而不是靠正常跑一遍。外部副作用另需分别注入“调用前失败”“远端成功但回执未落库”“超时但远端结果未知”，并检查 outbox、幂等查询与对账分支；数据库事务不能替代这些验证。
