前两节讲「什么时候停下来问人」。这一节讲另一个和信任有关的问题：**跑的时候让用户看到什么。**

## 一个反直觉的起点

先说一个容易被误解的事实：**用户对 agent 的信任，主要不是来自它做对了，而是来自他能预测它在做什么。**

第 9 章的实测支持这一点：让界面 agent 反复点同一个错位置时，它**察觉到了**（连点 4 次）但没有「报告卡住」的出口 —— 于是撞到 8 步上限才停，花了 12,269 token。如果它有一个「我卡住了」的出口，用户至少知道发生了什么。

所以在设计上，有两件事比「提高准确率」更早该做：

1. **让过程中可见** —— 用户知道它在干什么
2. **让异常有出口** —— 卡住时它能说出来

## 过程可见的三种做法

| 做法 | 展示什么 | 代价 |
|---|---|---|
| **结果只有** | 什么都不展示，等结果 | 等待期间一片空白，长任务体验最差 |
| **状态可见** | 「正在检索…」「正在生成…」 | 简单，但信息量低 |
| **动作可见** | 「正在读取订单 A-1001」「准备发送邮件给…」 | 需要结构化输出，但信息量高 |

第三种是目标。它的实现依赖第 15 节那套追踪 —— 因为你得先「记录了每一步」，才能「展示每一步」。**追踪（trace）在这里就是这次任务的逐步记录**：每一步调了什么工具、原始参数、原始返回值、花了多少 token 与时间（第 15 章那四个字段）。**它的用途不只是排查，还有展示** —— 同一个记录，展示给用户的是加工过的文案，留给运维的是原始字段。

一个具体的判据：**如果用户离开 3 分钟回来，他能不能从界面上判断出「进行到哪了、大概还要多久」。** 不能的话，可见性不够。

## 三类必须暴露的异常

异常不展示是最常见的问题。有三类必须说出来：

**一、卡住了。** 同一个动作重复、或者长时间没有进展。第 9 章那个实测就是这个形态：模型反复点同一个位置，而界面上一片安静。

**二、降级了。** 比如熔断触发了、换成了便宜模型（第 18 章）、或者某个工具不可用。**用户有权知道他在用哪个版本。**

（"熔断"就是你已经见过的那个模式：某个依赖连续失败若干次之后，停止继续调用它、直接走降级路径，而不是每次都等一遍超时。它保护的是调用方 —— 在 agent 里被熔断的通常是某个工具或上游模型。第 18 章那三层预算闸门里的第三层就是它，判定代码见第 20 章第 3 节。）

**三、不确定。** 模型自己没把握时应该说出来，而不是给一个看起来很确定的答案。第 5 章那条「幻觉」的实验里，模型对不存在的事实 5/5 编出了「处理中」—— 而它本可以说「我不知道」。

第三类最难做，因为它需要模型**主动承认不确定**。做法是在 schema 或提示里明确给它这个出口：允许输出 unknown 或 need_confirmation，而不是强制它填一个值。

**没有出口会怎样，第 5 章量得很清楚：** 那个实验强制模型为一个对话里从未出现过的字段填值，它 5/5 填出了"处理中"—— 看起来像正常结果，实际是编的。**"不确定"这个状态在 schema 里不存在，模型就只能选一个"看起来对"的值。**

## 那个出口的 schema 长什么样

下面是一份完整的响应 schema。"出口"就是 `status` 的三个取值，以及当它取 `unknown` / `need_confirmation` 时**必须填**的解释字段：

```json
{
  "type": "object",
  "required": ["status", "answer", "evidence"],
  "properties": {
    "status": {
      "type": "string",
      "enum": ["ok", "unknown", "need_confirmation"]
    },
    "answer": { "type": ["string", "null"] },
    "evidence": {
      "type": "array",
      "items": { "type": "string" },
      "description": "answer 里每个具体事实的依据：来自哪一步、哪个工具返回值"
    },
    "unknown_reason": {
      "type": ["string", "null"],
      "description": "status=unknown 时必填：缺什么信息、去哪里能拿到"
    },
    "confirmation": {
      "type": ["object", "null"],
      "properties": {
        "proposed_action": { "type": "string" },
        "frozen_params": { "type": "object" },
        "why": { "type": "string" }
      },
      "description": "status=need_confirmation 时必填：冻结的待审批动作"
    }
  }
}
```

（示例：构造数据，未实跑 —— 它是 schema 形状的示例。）

**一次 unknowns 的填充实例：**

```json
{
  "status": "unknown",
  "answer": null,
  "evidence": ["订单表里没有 A-1001 的记录（第 2 步，query_order 返回 []）"],
  "unknown_reason": "查不到这个订单号，需要客户提供下单时使用的手机号后才能继续",
  "confirmation": null
}
```

（示例：构造数据，未实跑。）

**三条判据，决定这个 schema 能不能真的挡住幻觉：**

1. **`status` 是必填，而且 `answer` 允许为 null。** 如果 `answer` 是必填的字符串，"不知道"就只能被编码成某个听起来像答案的字符串 —— 出口等于没有。
2. **`unknown_reason` 要求写"缺什么、去哪拿"。** 只说"我不知道"没有可操作性；说"需要手机号"才让下一步有方向。这也是让"找人"变成正常路径（第 1 节）的具体形态。
3. **`evidence` 把每个事实指回来源步骤。** 它是"审阅"这个动作可执行的前提：人能顺着它去核对，而不是只能在两个都是空口的答案之间选。代价是输出变长，所以只对**关键结论**要求填，不要对每一句话都要求。

## 内部轨迹 → 用户可见文案：一张映射表

"动作可见"（上一节第三种做法）在实现上是一次**字段映射**：把轨迹里的原始字段翻译成用户能读的一句话。而这一步有一个必须同时决定的事 —— **哪些字段可以给用户看**。

| 轨迹里的字段 | 用户看到的 | 为什么不直接给原文 |
|---|---|---|
| `tool` + `params`（如 `{"to": "zhangsan@example.com"}`） | 「准备发送邮件给 zhangsan@example.com」 | 原始 JSON 对人不可读；但**目标对象必须原样出现**，不能转述 |
| `result`（工具返回值） | 「已查到 3 条订单」 | 返回值可能很长，也可能含内部字段名（第 15 章那个 `eta` 被当成"预计送达"的例子） |
| `status` / 重试计数 | 「同一个动作已重试 3 次，没有进展」 | 这是"卡住了"的判据，见下 |
| **API Key、DB 连接串、内部主机名** | **绝不展示** | 它们会出现在工具参数与返回里，而"把原始参数给用户看"就是泄露 |
| **其他用户的标识 / 全量数据** | **只展示与本次任务相关的切片** | 展示范围应按"这个用户有没有权限看"过滤，而不是按"它有没有出现在轨迹里" |
| 模型的思考过程 | 默认折叠或不展示 | 它可能很长，也可能包含对用户的评价 |

**这张表最值钱的是最后三行。** 前两行是体验问题，后三行是安全问题：**轨迹是给运维看的内部数据，界面是给当事人看的外部数据，两者不是同一个集合。** 常见的错误是"轨迹里有什么就往界面上放"，于是内部主机名、别人的订单、密钥前缀都漏出去了。

**判据可以简化成一句：这条信息，如果这个用户自己来问你，你会告诉他吗？** 答案是否，它就不该出现在界面上。

## 进度条的一个常见错误

很多实现用「步数」做进度条：5 步里的第 3 步就是 60%。

这个做法在 agent 里**不成立**，因为**步数不可预知**。第 10 章实测过：Plan-Execute 在分支任务上 0/3 —— 计划本身就不可靠，更别说用它来算进度。

更诚实的做法有三种：

- **不显示百分比**，只显示「当前在做什么」（信息量等同于百分比，但没有虚假精度）
- **按阶段**显示（「已找到资料」→「正在整理」→「准备发送」），这些阶段通常可预知
- **按已完成的具体动作**列出来，让用户自己判断

第一种最省事也最诚实。**「正在读取第 3 份文档」比「60%」更有用** —— 因为它具体，而且不会在步数变化时跳来跳去。

## 一个和「信任」有关的反直觉结论

最后说一个容易被忽略的点：**展示过程会降低短期满意度，但提高长期信任。**

具体说，一个什么都不显示然后给出结果的界面，在成功时感觉更「神奇」；而一个把每一步都亮出来的界面，用户会看到中间的错误尝试、绕路、重试 —— 短期体感更差。

但长期看，第二种建立的是**可校准的信任**：用户知道它什么时候可靠、什么时候不可靠。而第一种建立的是**盲信** —— 它会在第一次重大失败时崩塌，因为没有中间信号让用户建立预期。

这个取舍没有标准答案，但应该**有意识地做** —— 具体做法是三个决定，而不是一个原则：

1. **默认显示到哪一层。** 建议默认"动作可见"（正在读哪份文档、准备发给谁），把"思考过程"默认折叠 —— 前者是用户在意的，后者往往只是噪声。
2. **成功后要不要保留过程。** 长任务保留（用户会回来看它做了什么），秒级任务可以收起。
3. **失败时显示多少。** 至少要给出"卡在哪一步 + 已完成的产出"，而不是一个"失败了"。

而这里最常见的失败形态是**默认什么都不显示** —— 它不是设计决定，而是没做。判断方法很直接：把界面交给一个没参与开发的人看 30 秒，问他"它现在在干什么"。

## 一个可以量化的信任指标

「信任」听起来很抽象，但有几个能监控的数字：

| 指标 | 变差的含义 |
|---|---|
| 用户取消任务的比率 | 他不再相信它能做完 |
| 用户重复提问同一件事的比率 | 上一次的回答没让他放心 |
| 审批的响应时间 | 缩短说明在盲点（第 2 节） |
| 任务完成后用户手动修改的比率 | 结果不可直接用 |

四个里最值得看的是第二个。**用户重复问同一件事，是一个很强的信号** —— 它说明上一次的回答形式上完成了任务，但没有让他放心。


## 那份清单的另一面

上一节讲了反方立场，这里补一句它没说透的话：**12-Factor Agents 描述的是「理想形态」，不是「最低成本路径」。**

它的十二条如果全部自己实现，你会得到一个完全可控、也完全由你维护的系统。对长期运行的核心系统，这个交易可能划算。但对一个验证性项目、或者一个季度内要上线的功能，它可能过于昂贵。

所以真正的判断依据是**这个 agent 要活多久**：

- **一次性 / 验证性** → 用框架快，之后大概率会重写
- **中长期（一年以上）** → 控制和可观测性的价值会超过维护成本
- **核心链路** → 控制流和提示词必须在你自己手里

这条判据比「该不该用框架」更好用，因为它把问题从「哪个更好」变成了「这个东西要活多久」。

## 一个具体的边界：什么绝对不该交给框架

有三样东西，无论项目多短，都不该完全交给框架：

**一是提示词。** 它是第 2 章的工程对象，要能 diff、能回滚、能做 A/B。如果它藏在框架的模板参数里，你就失去了迭代它的能力 —— 而这恰恰是效果提升最大的地方。

**二是状态定义。** 你的业务状态是什么形状，应该由你定义。框架的内部状态对象是它的实现细节，不该成为你的数据模型。第 11 章第 4 节那条「存可重建的输入，不存内存快照」讲的就是这个。

**三是权限边界。** 第 9 章那四道闸门 —— 活动范围、预算、熔断、不可逆确认。这些是你的安全边界，交给框架等于把安全建立在你不了解的代码上。

三样之外的，交给框架没问题。

## 一个具体的设计：让"卡住"可检测

第 9 章那个实测里，模型连点 4 次同一个错位置而界面上一片安静。要暴露它，需要一个可检测的判据。

三个可用的信号：

- **同一个动作重复**：连续两次调用同一个工具、参数相同
- **没有状态变化**：执行了动作，但观测到的状态和之前一样
- **时间超限**：单步耗时超过它的 P99 的若干倍

三个里最可靠的是第二个，因为它直接观测"有没有进展"，而不是猜测。而它要求你能**观测状态** —— 这又回到第 15 节那套追踪：你得记录了状态，才能比较状态。

第二和第三个信号可以自动化。第一个的误报率稍高（有些任务确实需要重复调用同一个工具，比如翻页），所以它的判据应该是"相同参数重复且无状态变化"。

**这三个信号的价值在于它们不需要模型配合。** 第 4 节讲过：模型察觉不到自己卡住了，所以"报告卡住"这件事应该由你的代码从外部判断。
## 完整可运行代码

下面这段代码把一个 agent 的执行过程转成面向用户的进度事件，并演示「动作可见」和「按阶段」两种展示方式。

```python
"""把内部执行转成面向用户的进度事件。纯本地。实跑状态：2026-10-09。"""
TASK = [
    ("read_doc", "读取订单 A-1001"),
    ("search_kb", "检索退款政策"),
    ("summarize", "整理要点"),
    ("draft_email", "起草回复"),
    ("send_email", "发送回复给 zhangsan@example.com"),
]


def as_percent(total):
    """做法一：用步数算百分比。"""
    out = []
    for i in range(1, total + 1):
        out.append("%d%%" % round(i / total * 100))
    return out


def as_action():
    """做法二：只显示当前动作（不显示百分比）。"""
    return ["正在%s…" % desc for _, desc in TASK]


def as_phases():
    """做法三：按可预知的阶段显示。"""
    phases = [(1, 2, "正在查找资料"), (3, 4, "正在起草回复"), (5, 5, "等待确认发送")]
    seq = []
    for i, (_, desc) in enumerate(TASK, 1):
        for lo, hi, name in phases:
            if lo <= i <= hi:
                seq.append(name)
                break
    return seq


if __name__ == "__main__":
    print("任务共 %d 步" % len(TASK))
    print()
    print("做法一：用步数算百分比")
    for p in as_percent(len(TASK)):
        print("    %s" % p)
    print("  ⚠️ 问题：步数不可预知（第 10 章实测 Plan-Execute 在分支任务上 0/3），")
    print("     所以总步数是个猜测 —— 真实步数变化时百分比会跳来跳去。")
    print()
    print("做法二：只显示当前动作")
    for a in as_action():
        print("    %s" % a)
    print("  ✅ 具体、不会跳；信息量等同于百分比，但没有虚假精度。")
    print()
    print("做法三：按可预知的阶段显示")
    for p in as_phases():
        print("    %s" % p)
    print("  ✅ 阶段通常可预知，比百分比诚实；适合对外展示给非技术用户。")
```

## 常见坑

- **只展示结果。** 长任务期间一片空白，用户无法判断进展。
- **用步数算百分比。** 步数在 agent 里不可预知（第 10 章：计划本身 0/3）—— 那会给出虚假精度。
- **不暴露「卡住了」。** 第 9 章实测过模型连点 4 次同一个错位置而没有出口。
- **不告诉用户降级了。** 换模型、熔断触发时用户有权知道他在用哪个版本。
- **强制模型填值，不给「不知道」的出口。** 第 5 章实测：不存在的事实被 5/5 编了出来。
- **以为展示过程会降低满意度就不做。** 长期看它建立的是可校准的信任，而不是盲信。
- **给"不确定"留了 schema 出口，但 answer 还是必填。** 那样"不知道"只能被编码成一个听起来像答案的字符串 —— 出口等于没有。
- **把轨迹原样当界面文案。** 轨迹里有 API Key、内部主机名、别人的数据 —— 它和"用户可见"不是同一个集合。

## 这一层会怎么坏

三类坏法，它们都不会报错：

| 坏法 | 现象 | 怎么发现 |
|---|---|---|
| **有一条"不确定"的路径没有出口** | 模型编一个看起来正常的答案（第 5 章 5/5） | 故意问一个数据里不存在的字段，看它是否敢说不知道 |
| **动作可见映射漏了脱敏** | 界面上出现内部字段名、密钥前缀、别人的数据 | 用一个含敏感参数的工具跑一遍，直接读渲染结果（不要只看代码） |
| **进度用步数算百分比** | 数字跳来跳去，卡住时给出稳定感 | 跑一个会绕路的任务，看百分比有没有倒退 |

第一条的验证成本最低：**给它一个答案不存在的问题。** 如果它每次都能编出一个"合理"的值，那你的出口没有生效。
