前两节讲「什么时候停下来问人」。这一节讲另一个和信任有关的问题：**跑的时候让用户看到什么。**

## 一个反直觉的起点

自动化研究通常把信任、依赖行为与系统能力/情境联系起来；把「理解、预测、纠正」当作设计目标是可检验的产品假设，不是对所有用户都成立的定律。可见性可以提供判断依据，但信息是否有用取决于准确性、任务风险、呈现方式和用户预期。[Lee 与 See 对自动化信任的综述](https://journals.sagepub.com/doi/10.1518/hfes.46.1.50_30392)

第 9 章留存的 noop 变体摘要记录了 4 次提交动作、最终触及 8 步上限并使用 11,827 token；逐次模型响应没有保存，所以不能说模型「察觉到了」，也不能把它当作一般任务的成本或失败率。它只说明这个本地样例的界面没有展示有用的执行状态（详见 `docs/DATA.md` 的点击无效记录）。

因此，产品设计要分别处理两类问题：系统是否可靠，以及用户是否能理解当前状态并作出监督决策。可见性不能替代准确性、安全控制或任务评测：

1. **让有用状态可见** —— 用户知道任务处于什么状态，以及是否需要自己行动
2. **为异常保留路径** —— 宿主检测到超时或降级时，能解释影响并提供恢复/升级选项

## 过程可见的三种做法

| 做法 | 展示什么 | 代价 |
|---|---|---|
| **仅展示结果** | 等待期间不展示中间状态 | 可能让用户难以判断任务是否仍在运行；是否影响体验需按任务验证 |
| **状态可见** | 「正在检索…」「正在生成…」 | 简单，但信息量低 |
| **动作可见** | 「正在读取订单 A-1001」「准备发送邮件给…」 | 需要结构化输出，但信息量高 |

动作级状态是可选的呈现方案，不是所有产品的目标。运行轨迹可能被采样、脱敏、裁剪或因故缺失，也不保证包含每次内部步骤；追踪字段应按诊断目的和隐私政策采集。用户界面要经过授权和字段白名单投影，不能直接复用运维轨迹；原始参数、返回值、token 用量和耗时也不应默认展示。

一个形成性可用性测试：让目标用户离开一段时间再回来，观察他能否判断「已发生什么、当前状态是什么、是否需要我采取行动」。不要把「还要多久」设成普遍要求；只有在有校准数据的工作流里才展示 ETA，并说明不确定性。测试任务、样本和判据应记录下来，单次测试不能证明整体可用性。

## 三类值得评估是否呈现的状态

优先展示会改变用户决策或预期的状态，而不是把内部每次重试都暴露出来。下面是三类常见候选状态，是否展示、何时升级应由产品风险和用户任务决定：

**一、可能没有进展。** 重复动作或超出任务特定的等待目标可以触发检查，但不等于 agent 已卡住；分页、轮询和只读查询可能合理地重复。结合工具语义、预期状态变化和可取消性判断，并把无法确认的状态表述为「仍在处理」或「需要检查」，而非伪造诊断。

**二、影响用户结果的降级。** 例如某项能力不可用、结果范围因此缩小，或用户需要改用另一条路径。内部重试、路由细节是否披露取决于是否影响结果、合同承诺或用户选择；避免暴露可能增加攻击面的内部细节。

（"熔断"就是你已经见过的那个模式：某个依赖连续失败若干次之后，停止继续调用它、直接走降级路径，而不是每次都等一遍超时。它保护的是调用方 —— 在 agent 里被熔断的通常是某个工具或上游模型。第 18 章那三层预算闸门里的第三层就是它，判定代码见第 20 章第 3 节。）

**三、答案缺少足够依据。** 模型自报信心不是事实核验；应区分缺少数据、工具失败、被拒绝和策略要求确认。第 5 章的 5/5 记录只能描述该特定提示、模型和小样本，不能说明所有 schema 都会消除不确定性（实验边界见 `docs/DATA.md`）。

可以在输出协议中为 unknown、工具错误或 need_confirmation 保留明确分支；宿主仍须校验事实来源、权限与业务状态。schema 只约束输出形状，不能证明结论真实，也不能授权动作。

第 5 章的有限样例展示了风险：在特定提示下，模型 5 次都为缺失字段返回「处理中」。这支持为缺数据设计错误/未知状态分支，但不能推出「没有 unknown schema 就只能编造」这一普遍因果结论。

## 那个出口的 schema 长什么样

下面是一份 Draft 2020-12 示例 schema，使用 `anyOf` 和互斥的 `status.const` 让三种状态各自约束字段。Claude structured outputs 当前文档支持 `anyOf` 与 `const`，但不支持 `minLength` 等字符串长度约束；因此下方 provider-facing schema 不含这些约束，宿主还须在解析后拒绝空白的 `unknown_reason`、`proposed_action` 和 `why`。其他模型/provider 的支持范围也不同，接入前须按实际 API 约束调整并用宿主 validator 校验。schema 约束结构，不验证 `evidence` 是否真实，也不构成审批或授权。[Claude Structured Outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "anyOf": [
    {
      "type": "object",
      "required": ["status", "answer", "evidence"],
      "properties": {
        "status": { "const": "ok" },
        "answer": { "type": "string" },
        "evidence": { "type": "array", "items": { "type": "string" } }
      },
      "additionalProperties": false
    },
    {
      "type": "object",
      "required": ["status", "answer", "evidence", "unknown_reason"],
      "properties": {
        "status": { "const": "unknown" },
        "answer": { "type": "null" },
        "evidence": { "type": "array", "items": { "type": "string" } },
        "unknown_reason": { "type": "string" }
      },
      "additionalProperties": false
    },
    {
      "type": "object",
      "required": ["status", "answer", "evidence", "confirmation"],
      "properties": {
        "status": { "const": "need_confirmation" },
        "answer": { "type": "null" },
        "evidence": { "type": "array", "items": { "type": "string" } },
        "confirmation": {
          "type": "object",
          "required": ["proposed_action", "why"],
          "properties": {
            "proposed_action": { "type": "string" },
            "why": { "type": "string" }
          },
          "additionalProperties": false
        }
      },
      "additionalProperties": false
    }
  ]
}
```

（示例：构造数据，未实跑 —— 它是 schema 形状的示例。）

**一次 unknown 的填充实例**（`evt-order-lookup-0002` 是构造的事件 ID；实际 UI 仍须由宿主解析并授权后展示）：

```json
{
  "status": "unknown",
  "answer": null,
  "evidence": ["evt-order-lookup-0002"],
  "unknown_reason": "查不到这个订单号，需要客户提供下单时使用的手机号后才能继续"
}
```

（示例：构造数据，未实跑。）

**结构校验只能保证协议形状，不能「挡住幻觉」。** 宿主应进一步校验引用的 trace/event ID 是否存在、调用者是否有权查看相应数据，以及答案是否被可信来源支持；对高影响动作，另走冻结提案、身份/授权和审批流程。Draft 2020-12 的条件 schema 语义见 [JSON Schema Core](https://json-schema.org/draft/2020-12/json-schema-core)；模型供应商支持范围需单独核对。

1. 分支结构和必填字段由 validator 检查，未知状态不能误报为成功。
2. `unknown_reason` 可以说明缺少什么，以及用户可选的下一步；不能暗示系统一定能获得该数据。
3. `evidence` 应引用宿主可解析的来源 ID，而不是让模型自由编写「第几步」；宿主解析、授权并展示来源。

## 内部轨迹 → 用户可见文案：一张映射表

"动作可见"（上一节第三种做法）在实现上是一次**字段映射**：把轨迹里的原始字段翻译成用户能读的一句话。而这一步有一个必须同时决定的事 —— **哪些字段可以给用户看**。

| 轨迹里的字段 | 用户看到的 | 为什么不直接给原文 |
|---|---|---|
| `tool` + `params` | 经白名单和授权检查后的「准备发送邮件」或经确认可展示的收件人摘要 | 目标可能是个人数据；按用户权限、任务相关性和产品策略投影，必要时掩码 |
| `result`（工具返回值） | 「已查到 3 条订单」 | 返回值可能很长，也可能含内部字段名（第 15 章那个 `eta` 被当成"预计送达"的例子） |
| `status` / 重试计数 | 「同一个动作已重试 3 次，没有进展」 | 这是"卡住了"的判据，见下 |
| **API Key、DB 连接串、内部主机名** | **绝不展示** | 它们会出现在工具参数与返回里，而"把原始参数给用户看"就是泄露 |
| **其他用户的标识 / 全量数据** | **只展示与本次任务相关的切片** | 展示范围应按"这个用户有没有权限看"过滤，而不是按"它有没有出现在轨迹里" |
| 模型的思考过程 | 默认折叠或不展示 | 它可能很长，也可能包含对用户的评价 |

**这张表最值钱的是最后三行。** 前两行是体验问题，后三行是安全问题：**轨迹是给运维看的内部数据，界面是给当事人看的外部数据，两者不是同一个集合。** 常见的错误是"轨迹里有什么就往界面上放"，于是内部主机名、别人的订单、密钥前缀都漏出去了。

字段展示判据至少包括：当前用户是否有权看、信息是否为完成当前监督决策所必需、是否会泄露凭据/第三方数据，以及展示是否可能误导。采用字段白名单和服务端权限过滤；敏感字段默认隐藏或掩码。

## 进度条的一个常见错误

很多实现用「步数」做进度条：5 步里的第 3 步就是 60%。

对于动态 agent，计划步数可能变化，不能把「已完成步数 / 初始计划步数」当作真实完成度；第 10 章的 0/3 是特定任务和旧评分器下的历史记录，不能证明所有计划都不可靠（见 `docs/DATA.md`）。若流程总量确定且可测量，例如上传字节或固定批次处理，可以显示确定性百分比；动态工作流宜用不确定进度或当前阶段。

更诚实的做法有三种：

- **不确定进度**，显示「当前在做什么」并说明阻塞/等待状态
- **按阶段**显示（「已找到资料」→「正在整理」→「准备发送」），前提是阶段语义明确、阶段转移可验证
- **按已完成的具体动作**列出来，让用户自己判断

屏幕阅读器也要获得有意义的状态更新。WAI-ARIA 允许不确定进度条省略 `aria-valuenow`；`progressbar` 的数值更新本身不是 live region，辅助技术不会因此自动播报每次变化。应按更新频率提供合适的状态消息，避免每个 token 都打断用户。[WAI-ARIA range properties](https://www.w3.org/WAI/ARIA/apg/practices/range-related-properties/)；[W3C ARIA25](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA25)；[WCAG status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)。

## 一个和「信任」有关的反直觉结论

过程可见性可能改善用户理解，也可能增加认知负担或泄露敏感内容。它对信任、依赖行为或任务绩效的影响，需要在目标任务和人群中评估；「展示得更多」本身不意味着更好。

具体而言，过多的低价值状态更新可能让用户忽略真正需要关注的事件；只展示结果也可能让长任务缺少状态线索。两种呈现方式的效果都是待验证的产品假设，不应当作普遍的用户心理规律。

过程信息可以帮助用户理解进度、发现异常并调整预期；信息过载、暴露敏感内容或显示误导性轨迹也可能损害体验。仅隐藏过程不必然产生盲信，展示过程也不自动建立信任；应通过用户研究和运行指标验证目标用户是否能据此做出更好的监督决策。

这个取舍没有标准答案，但应该**有意识地做** —— 具体做法是三个决定，而不是一个原则：

1. **默认显示到哪一层。** 显示足够支持用户决策的阶段和安全动作摘要；避免把原始思维链、凭据或未经授权的原始结果作为进度信息。
2. **成功后要不要保留过程。** 长任务保留（用户会回来看它做了什么），秒级任务可以收起。
3. **失败时显示多少。** 至少要给出"卡在哪一步 + 已完成的产出"，而不是一个"失败了"。

可用性检查可让目标用户执行具体监督任务，例如判断是否在运行、是否等待输入、如何停止；记录任务完成情况和误解点。单次「30 秒看懂」测试是形成性检查，不是通用验收阈值。

## 可量化的信任相关信号

「信任」听起来很抽象，但有几个能监控的数字：

| 信号 | 可能提示什么 |
|---|---|
| 用户取消任务的比率 | 可能与信任相关，也可能是任务变更、误触、时间成本或取消流程设计 |
| 用户重复提问同一件事的比率 | 可能反映回答不清楚/不完整，也可能是补充信息、状态变化或重复提交 |
| 审批响应时间与决定分布 | 描述审批行为；需结合动作风险、审批内容、拒绝/修改与抽样复核解释，不能单独诊断盲批 |
| 任务完成后的用户修改率 | 描述人工修订行为；修改可能是风格偏好，也可能是错误修复，应结合修改类型和任务结果 |

四个指标都只是信任相关体验的间接信号。重复提问可能表示回答不清楚或不可信，也可能是用户补充信息、任务状态变化或界面重复提交；需要结合任务类型、完成质量、取消原因和用户反馈解释，不能单独当成信任的测量值。


## 信任校准与授权是两条独立的轴

用户是否理解系统状态，不会自动扩大系统权限；一次评测准确率较高，也不足以证明某主体对某对象的每种动作都获得了授权。把 UI 的可理解性、任务效果评测和安全授权分别设计：授权由可信身份、对象范围、动作策略和执行时检查决定；逐步上线可用受限范围、显式审批、监控与回滚，但适用条件由风险和策略确定。模型自报置信度、最近没出事故、总体准确率都不能单独作为放权依据。

## 一个具体的设计：让"卡住"可检测

第 9 章保留的 noop 样例能提示一个设计问题：如果状态不变化且用户看不到有意义的信息，界面应提供可检查、可取消或可升级的路径；该样例不能证明模型是否察觉错误。

三个可用的信号：

- **同一个动作重复**：在特定任务中，相同工具/参数重复且预期状态未变化
- **没有状态变化**：只对预期应改变状态的动作有诊断价值；只读动作的状态不变可能完全正常
- **等待超出目标**：超过该业务步骤的超时/SLO 时触发检查，不自动断言模型卡住；P99 是特定流量分布下的延迟统计，不能直接当通用阈值

没有一个信号普遍最可靠。状态变化需定义业务上的预期，并考虑异步完成、最终一致性、无副作用查询和不可观测外部系统；超时应结合任务 SLA、历史分布与用户影响设定。

宿主可自动检测重试次数、心跳、工具结果和期限，并依据任务状态机选择提示、取消或转人工。检测规则必须按工具语义校验，分页、轮询、幂等读取和重试都可能合法。

这些信号来自宿主可观测数据，但它们只能标记「需要检查」的候选状态，不能单独推断模型内部是否察觉或任务必然卡死。
## 完整可运行代码

下面这段代码区分「固定总量工作」与「后续步骤未确定的 agent 任务」：只有前者在总量和计量口径可信时才计算百分比。

```python
"""把内部执行转成面向用户的进度事件。纯本地。实跑状态：2026-10-09。"""
FIXED_BATCH_TOTAL = 5


def fixed_batch_percent(completed, total):
    """仅对总量固定且计量口径明确的工作显示百分比。"""
    if isinstance(completed, bool) or not isinstance(completed, int):
        raise ValueError("completed must be an integer")
    if isinstance(total, bool) or not isinstance(total, int) or total <= 0:
        raise ValueError("total must be a positive integer")
    if not 0 <= completed <= total:
        raise ValueError("completed must be within the known total")
    return round(completed / total * 100)


def dynamic_agent_status(completed_actions, current_action, next_step_known):
    """动态任务报告观察到的状态，不猜测总步数或 ETA。"""
    if isinstance(completed_actions, bool) or not isinstance(completed_actions, int) or completed_actions < 0:
        raise ValueError("completed_actions must be a non-negative integer")
    if not isinstance(current_action, str) or not current_action.strip():
        raise ValueError("current_action must be a non-empty string")
    if not isinstance(next_step_known, bool):
        raise ValueError("next_step_known must be a boolean")
    suffix = "后续步骤尚未确定" if not next_step_known else ""
    return f"已完成 {completed_actions} 个动作；当前：{current_action}；{suffix}".strip("；")


def local_checks():
    invalid_inputs = ((6, 5), (-1, 5), (True, 5), (1.5, 5), (1, 0), (1, True), (1, "5"))
    for completed, total in invalid_inputs:
        try:
            fixed_batch_percent(completed, total)
        except ValueError:
            continue
        raise AssertionError(f"invalid progress accepted: {completed!r}/{total!r}")

    for args in ((-1, "检索", False), (True, "检索", False), (0, "  ", False), (0, "检索", 1)):
        try:
            dynamic_agent_status(*args)
        except ValueError:
            continue
        raise AssertionError(f"invalid dynamic status accepted: {args!r}")


if __name__ == "__main__":
    local_checks()
    print("固定批次：已处理 3 / 5 个文件，进度 %d%%" % fixed_batch_percent(3, FIXED_BATCH_TOTAL))
    print("动态 Agent：" + dynamic_agent_status(3, "检索退款政策", next_step_known=False))
    try:
        fixed_batch_percent(6, FIXED_BATCH_TOTAL)
    except ValueError as exc:
        print("越界进度被拒绝：%s" % exc)
```

## 常见坑

- **只展示结果。** 长任务期间一片空白，用户无法判断进展。
- **把动态计划步数当真实百分比。** 若计划可变，不要声称其代表完成度；已知总量的工作仍可显示有依据的进度。
- **把重复动作直接诊断为卡住。** 先检查操作语义、状态变化预期和业务期限，再决定是否通知用户。
- **隐瞒影响结果的降级。** 应说明能力变化及用户可选动作；是否披露内部实现细节按安全和产品需要决定。
- **强制模型填值，不给「不知道」的出口。** 第 5 章实测：不存在的事实被 5/5 编了出来。
- **因为担心展示过程降低满意度就不提供任何进度。** 先明确用户需要做出的监督决策，再测试最小且可理解的进度信息是否改善可见性、异常发现或用户体验。
- **以为 schema 能验证事实。** schema 只能约束输出形状；事实依据、权限、业务状态和审批必须由宿主验证。
- **把轨迹原样当界面文案。** 轨迹里有 API Key、内部主机名、别人的数据 —— 它和"用户可见"不是同一个集合。

## 这一层会怎么坏

三类坏法，它们都不会报错：

| 坏法 | 现象 | 怎么发现 |
|---|---|---|
| **有一条"不确定"的路径没有出口** | 模型编一个看起来正常的答案（第 5 章 5/5） | 故意问一个数据里不存在的字段，看它是否敢说不知道 |
| **动作可见映射漏了脱敏** | 界面上出现内部字段名、密钥前缀、别人的数据 | 用一个含敏感参数的工具跑一遍，直接读渲染结果（不要只看代码） |
| **动态步数被冒充为完成百分比** | 计划变化后数字失真 | 用可变长度任务对比 UI 声称与真实已完成工作；固定总量任务单独评估 |

第一条的验证方式之一是给模型一个来源中不存在的问题，并检查系统是否进入 unknown/拒绝/工具失败等正确状态；一次成功不能证明机制稳定，需用多样化数据集、可信评分器和任务级验收验证。
