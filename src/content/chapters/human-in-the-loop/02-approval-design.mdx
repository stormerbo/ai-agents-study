上一节说"不可逆就停下来问"。这一节讲**怎么问** —— 因为审批的设计细节决定了它是否有效。

## 先看一个数据

我拿一个 7 步的任务流程，测了四种审批策略：

```text
步骤                性质
1. read_doc         可逆且低危
2. search_kb        可逆且低危
3. summarize        可逆且低危
4. draft_email      可逆且低危
5. send_email       不可逆
6. update_crm       不可逆、高危
7. log_result       可逆且低危
```

四种策略下统计"中断次数"和"未经审批就执行的不可逆动作数"：

```text
策略                 中断次数   未审批执行   说明
A 每个动作都问           7          0        打断 7 次
B 只问不可逆动作          2          0        全在真正不可逆的步骤上
C 只问高危动作           1          1        send_email 无审批就发了
D 只在最后确认一次        0          2        两个不可逆动作全部裸奔
```

（实跑数据，2026-10-09。纯本地模拟。）

## 三个读数

**A 看着最安全，但它有 7 次打断。** 而审批疲劳是真实存在的：**用户在第 3 次之后就会开始不看内容直接点同意。** 那时审批就从"一道闸门"退化成了"一个点击动作"—— 而它还会让人以为已经检查过了。**这是审批设计里最危险的状态：有成本，没效果。**

**C 看着"克制"，但它放过了 send_email。** 因为发邮件**不可逆但不高危** —— 它不改数据、不删东西，只是送出去一份内容。然而"送出去就收不回"正是最该问的那一类。

**B 是正确答案，而且它的判据只有一个：按可逆性。** 2 次中断、0 个漏网 —— 用 A 的 29% 的打断次数，达到了同样的安全效果。

**所以审批点的判据应该是"可逆吗"，不是"危险吗"。** 理由很直接：可逆的动作错了可以回滚；不可逆的错了只能补救。而"危险程度"是一个模糊的主观判断，它在实现时必然会有分歧。

## 审批要展示什么

判据解决了"在哪停"，下一个问题是"停下来之后给用户看什么"。三种常见的失败：

**失败一：只显示工具名。** "agent 想调用 send_email，是否同意？" —— 用户不知道发给谁、发了什么，只能盲点。

**失败二：显示原始 JSON 参数。** 技术上完整，但对人来说不可读。用户会跳过。

**失败三：把整个上下文倒出来。** 信息过载，用户同样会跳过。

有效的信息是**这次动作会改变什么**，具体三样：

```text
1. 动作 + 目标：要发给 zhangsan@example.com（不是「调用 send_email」）
2. 影响范围：这封邮件会被 1 个外部收件人看到
3. 可逆性：发出后无法撤回
```

第 3 条尤其重要 —— 它把"为什么需要你确认"直接说出来。用户理解了这个理由，才会真的看内容。

## 审批的四种响应选项

很多实现只给"同意 / 拒绝"两个按钮。但用户的实际意图通常比这丰富，而**缺选项会导致错误的动作**：

| 选项 | 什么时候用 |
|---|---|
| **同意** | 就是这么办 |
| **拒绝** | 不要做这件事 |
| **修改后同意** | 方向对，但参数要改（收件人、金额、范围） |
| **换个方式** | 目标对，但做法不对（比如"用这个工具，不是那个"） |

第三种和第四种最容易被漏，而它们恰恰是最常见的真实需求。如果只给"同意/拒绝"，用户的反应通常是**拒绝然后重说一遍** —— 那等于浪费了 agent 已经做好的部分。

## 一个反过来的检查

审批也可能做错方向。三种需要警惕的形态：

**一、审批点比不可逆动作少。** 说明有不可逆的动作没被覆盖 —— 那是最严重的漏洞。

**二、用户对审批的响应时间在缩短。** 从平均 8 秒降到 1 秒，说明他在盲点。这是一个**可监控的指标**，而它是审批失效的早期信号。

**三、审批被频繁"修改后同意"。** 说明 agent 的参数选择经常有偏差 —— 那是提示词或工具设计的问题，不该靠审批来兜。

第二条特别值得做：**它把"审批是否还有效"变成一个有数字的问题。** 而如果没有这个指标，你不会知道审批已经在第 3 次之后失效了。

## 和"不可逆确认"的区别

第 9 章给过一道闸门叫"不可逆确认"。本节讲的是它的设计细节，但有一处不同值得说清：

第 9 章的重点是**要有这道闸门**；本节的重点是**闸门要设在正确的位置，并且要给出正确的信息**。前者是"有没有"，后者是"有没有用"。

一个具体例子：把闸门设在"调用 write_file 之前"（每个写操作都问）和设在"覆盖已有文件之前"（只在真正不可逆时问）—— 后者打断次数少得多，而安全性相同。**闸门的位置应该由"可逆性"决定，而不是由"工具名"决定。**


## 三种抽象对应的代码形态

把三种抽象写成代码，形状的差别会一目了然。

**链**：控制流是一串管道，读起来就是「先做这个、再做那个」。

**图**：控制流是一张声明式的表，节点和边分开写。它更像配置，不像代码。

**自主 agent**：控制流是隐藏的 —— 你只写了「给它一个目标」，循环在框架内部。

**这个差别带来一个实际问题：可调试性。** 链和图里，你能在读代码时说出「接下来会发生什么」；自主 agent 里你不能，你只能看运行时的轨迹。所以第 11 章讲的轨迹记录，在自主 agent 上是必需品，在链上则是可选。

## 选择时的两个常见误判

**误判一：把链当成「不够强」的选项。** 实际上在流程固定的任务上，链是最优选 —— 它最便宜、最可测、最不容易出意外。第 10 章第 5 节量过这个方向：静态计划在线性任务上 506 token，比 ReAct 的 1,203 便宜一半多。

**误判二：以为图能解决所有复杂流程。** 图的表达力上限是「你能否枚举出所有分支条件」。如果分支条件本身需要模型来判断，那这个判断仍然要交给一个自主 agent 节点 —— 图只是把它的位置固定下来，没有替代它。

## 一个反过来的问题：审批能不能被绕过

设计完审批之后要问一个检验问题：**有没有一条路径能绕过它？**

常见的三条：

**一、批量和单条走不同的代码路径。** 单条发送会弹审批，但批量导入接口直接调了同一个底层函数。这是最经典的一种 —— 因为批量入口往往是后加的。

**二、重试逻辑绕过审批。** 第一次执行失败，重试时"反正已经批过了"就直接执行 —— 但那次失败可能发生在副作用已经产生之后（第 11 节那个窗口）。

**三、内部调用不走审批。** 别的服务通过内部 API 调这个动作，而审批只在面向用户的入口上做了。

三条的共同点是：**审批加在了"入口"上，而不是"动作"上。** 正确的做法是把审批放在**动作真正执行的那一层**（和第 16 节讲执行层是唯一安全边界是同一个道理）—— 那样无论从哪个入口进来，都绕不过去。

这也是一个可以自动化检查的东西：**遍历所有能触发不可逆动作的代码路径，确认每一条都经过了审批。** 而这种检查在没有审计日志的情况下做不了。
## 完整可运行代码

下面这段代码就是上面那张对照表的实现：三种审批策略，统计中断次数与漏网的不可逆动作。

```python
"""审批点的粒度：一个任务会被打断几次。

同一份任务流程，三种审批策略下统计中断次数与"拦住的危险动作数"。
纯本地，实跑状态：2026-10-09。
"""

# 一个真实形态的任务：每步有 (名称, 是否可逆, 是否高危)
TASK = [
    ("read_doc",        True,  False),
    ("search_kb",       True,  False),
    ("summarize",       True,  False),
    ("draft_email",     True,  False),
    ("send_email",      False, False),   # 不可逆：发出去了收不回
    ("update_crm",      False, True),    # 不可逆 + 高危：改客户数据
    ("log_result",      True,  False),
]

POLICIES = {
    "A 每个动作都问":      lambda s: True,
    "B 只问不可逆动作":    lambda s: not s[1],
    "C 只问高危动作":      lambda s: s[2],
    "D 只在最后确认一次":  lambda s: False,
}


def run(policy):
    asked = []
    risky_executed = 0
    for i, step in enumerate(TASK, 1):
        if policy(step):
            asked.append((i, step[0]))
        else:
            if not step[1] or step[2]:
                risky_executed += 1
    return asked, risky_executed


if __name__ == "__main__":
    total_risky = sum(1 for s in TASK if (not s[1]) or s[2])
    print("任务共 %d 步，其中不可逆或高危的有 %d 步：" % (len(TASK), total_risky))
    for i, s in enumerate(TASK, 1):
        tag = []
        if not s[1]:
            tag.append("不可逆")
        if s[2]:
            tag.append("高危")
        print("    %d. %-14s %s" % (i, s[0], "、".join(tag) or "可逆且低危"))
    print()
    print("  %-20s %-10s %-12s %s" % ("策略", "中断次数", "未审批执行", "说明"))
    for name, pol in POLICIES.items():
        asked, risky = run(pol)
        note = {
            "A 每个动作都问": "打断 7 次 —— 审批疲劳，用户会开始盲点同意",
            "B 只问不可逆动作": "打断 2 次，全在真正不可逆的步骤上",
            "C 只问高危动作": "打断 1 次，但 send_email 无审批就发了",
            "D 只在最后确认一次": "0 次打断，两个不可逆动作全部裸奔",
        }[name]
        print("  %-20s %-10d %-12d %s" % (name, len(asked), risky, note))
    print()
    print("=== 关键点 ===")
    print("  A 看着最安全，代价是 7 次打断。而审批疲劳是真实存在的：")
    print("  用户在第 3 次之后就会开始不看内容直接点同意 —— 那时审批就失效了。")
    print()
    print("  C 看着「克制」，但它放过了 send_email（不可逆但不算高危）——")
    print("  而「发出去就收不回」正是最该问的那一类。")
    print()
    print("  正确的判据是 B：**按可逆性，不按危险程度**。")
    print("  理由：可逆的动作错了可以回滚；不可逆的错了只能补救。")
```

## 常见坑

- **按"危险程度"设审批点。** 实测：那会放过 send_email（不可逆但不高危）。判据应该是**可逆性**。
- **每个动作都问。** 7 次打断会让用户在第 3 次之后开始盲点 —— 有成本，没效果。
- **只显示工具名。** 用户不知道发给谁、发了什么，只能盲点同意。
- **只给"同意/拒绝"。** 缺"修改后同意"和"换个方式"，用户会拒绝然后重说一遍。
- **不监控审批响应时间。** 它是审批失效的早期信号，而且是一个有数字的指标。
- **用审批掩盖参数设计问题。** 频繁"修改后同意"说明提示词或工具出了问题，该去修那里。
