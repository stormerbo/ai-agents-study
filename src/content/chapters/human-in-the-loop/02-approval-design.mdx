上一节说"不可逆就停下来问"。这一节讲**怎么问** —— 因为审批的设计细节决定了它是否有效。

## 先看一个数据

我拿一个 7 步的任务流程，测了四种审批策略：

```text
步骤                性质
1. read_doc         可逆且低危
2. search_kb        可逆且低危
3. summarize        可逆且低危
4. draft_email      可逆且低危
5. send_email       不可逆
6. update_crm       不可逆、高危
7. log_result       可逆且低危
```

四种策略下统计"中断次数"和"未经审批就执行的不可逆动作数"：

```text
策略                 中断次数   未审批执行   说明
A 每个动作都问           7          0        打断 7 次
B 只问不可逆动作          2          0        全在真正不可逆的步骤上
C 只问高危动作           1          1        send_email 无审批就发了
D 只在最后确认一次        0          2        两个不可逆动作全部裸奔
```

（实跑数据，2026-10-09。纯本地模拟。）

## 三个读数

**A 看着最安全，但它有 7 次打断。** 而 7 次打断本身就是成本 —— 它会招来审批疲劳：人会开始不看内容直接点同意。那时审批就从"一道闸门"退化成了"一个点击动作"，而它还会让人以为已经检查过了。**这是审批设计里最危险的状态：有成本，没效果。**

> **口径说明（重要）：** 上面那张表量的是**中断次数**，它没有量疲劳。审批疲劳是一个经验判断，不是本节的实验结论 —— 不要在引用时把它说成实测。真要把疲劳变成数据，得测"响应时间随第几次审批的变化"，本节末尾给出这个指标怎么做。

**C 看着"克制"，但它放过了 send_email。** 因为发邮件**不可逆但不高危** —— 它不改数据、不删东西，只是送出去一份内容。然而"送出去就收不回"正是最该问的那一类。

**B 是正确答案，而且它的判据只有一个：按可逆性。** 2 次中断、0 个漏网 —— 用 A 的 29% 的打断次数，达到了同样的安全效果。

**所以审批点的判据应该是"可逆吗"，不是"危险吗"。** 理由很直接：可逆的动作错了可以回滚；不可逆的错了只能补救。而"危险程度"是一个模糊的主观判断，它在实现时必然会有分歧。

## 审批要展示什么

判据解决了"在哪停"，下一个问题是"停下来之后给用户看什么"。三种常见的失败：

**失败一：只显示工具名。** "agent 想调用 send_email，是否同意？" —— 用户不知道发给谁、发了什么，只能盲点。

**失败二：显示原始 JSON 参数。** 技术上完整，但对人来说不可读。用户会跳过。

**失败三：把整个上下文倒出来。** 信息过载，用户同样会跳过。

有效的信息是**这次动作会改变什么**，具体三样：

```text
1. 动作 + 目标：要发给 zhangsan@example.com（不是「调用 send_email」）
2. 影响范围：这封邮件会被 1 个外部收件人看到
3. 可逆性：发出后无法撤回
```

第 3 条尤其重要 —— 它把"为什么需要你确认"直接说出来。用户理解了这个理由，才会真的看内容。

## 那三样信息落成什么结构

上面那三行是"要展示什么"，它还需要一个**能被程序读写**的载体。这个载体就是待审批记录 —— 它同时喂给三个地方：界面（展示那三样）、执行层（批准后照着执行）、存储（下一节的恢复要靠它查回来）。

一份完整的记录长这样：

```json
{
  "approval_id": "ap_8f3c21",
  "action": "send_email",
  "target": "zhangsan@example.com",
  "target_kind": "外部地址",
  "scope": "1 个外部收件人可见",
  "reversible": false,
  "why": "邮件离开服务端后不可撤回",
  "frozen_params": {
    "to": "zhangsan@example.com",
    "body": "订单 A-1001 已发货，物流显示派送中。"
  },
  "params_hash": "sha256:9f2a…",
  "status": "pending",
  "created_at": "2026-10-12T10:31:02+08:00",
  "expires_at": "2026-10-13T10:31:02+08:00"
}
```

（示例：构造数据，未实跑 —— 它是记录结构的示例；第 3 节会给这个结构的持久化形态。）

**字段不是随便定的，每一个都对应一个失败形态。** 这张表是这一节的判据部分 —— 换一个场景时，改的是这里的**取舍**，不是字段名：

| 字段 | 为什么必须有 | 少了它会怎么坏 |
|---|---|---|
| `action` + `target` + `target_kind` | 人要知道"发给谁"，`target_kind` 标出它是不是外部对象 | 用户只看工具名就盲点 |
| `scope` | 影响范围是"1 个外部收件人"还是"全体客户"，决定要不要更谨慎 | 用户无法估计爆炸半径 |
| `reversible` + `why` | 上一节那个字段；`why` 是给人看的理由 | 用户不理解为什么被打断，于是不看内容 |
| **`frozen_params`** | **用户批准的是这一组具体参数，不是"以后会生成的"动作** | 恢复时重新生成 → 执行的可能不是用户批准的那件事（第 3 节详述） |
| `params_hash` | 给冻结参数留一个可比较的指纹 | 无法判断"要执行的是不是当初批准的那份" |
| `status` | 记录自己要走完 pending → approved → executed / rejected | 无法区分"等审批"和"已批准待执行" |
| `expires_at` | 审批是有时效的，几小时前的批准不该永久有效 | 用户一周前批过的动作，今天被恢复执行 |

**其中 `frozen_params` 和 `reversible` 是这张表里最容易漏的两个** —— 它们恰好对应两个不同的坏法：一个导致"执行了没批过的东西"，一个导致"批了不该批的东西"。

## 拦截层放在哪：一个会真的被调用的地方

上面说判据要有载体，载体要有位置。位置选错的典型症状是"审批加了，但有个入口绕过它"（本节最后一节会展开三种绕过路径）。所以先把这个位置写清楚。

**正确的位置是"动作真正执行的那一层"，形态是一个 wrapper/decorator，而不是散落在各个入口里的 if。** 下面这段代码是它的骨架：

```python
# 审批拦截层：所有不可逆动作都必须穿过这个 wrapper。
# 关键：调用方永远拿不到 tool["impl"]，只能拿到 guarded。
PENDING = {}          # approval_id -> 待审批记录（真实实现里换成存储，见第 3 节）

def guard(tool, params, actor):
    """执行入口。返回三种结果之一：已执行 / 待审批 / 拒绝。"""
    if tool["reversible"]:
        return {"status": "executed", "result": tool["impl"](**params)}

    record = build_record(tool, params, actor)   # 上一节那份 JSON 结构
    PENDING[record["approval_id"]] = record
    return {"status": "pending_approval", "approval_id": record["approval_id"],
            "show": {"action": record["action"], "target": record["target"],
                     "scope": record["scope"], "reversible": record["reversible"],
                     "why": record["why"]}}
```

**为什么必须在这一层。** 因为这一层的入参只有"做什么"和"对谁做"，没有"从哪个入口来的"。于是无论调用来自普通对话、批量导入接口、还是别的服务的内部调用，都会撞上这个判断 —— **它把关的是动作本身，不是路径。**

反过来，如果审批写在面向用户的 handler 里，那么后加的批量接口、内部 API、重试逻辑都天然绕开它。这是本节最后要检查的那件事。

## 批准之后怎么续跑：一句话的指针

上面那个 `pending_approval` 结果里最重要的字段是 `approval_id`。它是**唯一的指针**：界面把四个选项各自带上这个 id 发出去，服务端用 id 找回记录、核对冻结参数、然后执行。

所以"续跑"不是一个内存里的回调，而是**一次新的请求**：

```text
界面 → POST /approval/ap_8f3c21/approve
服务端 → 读回 PENDING["ap_8f3c21"] → 核对 params_hash → 执行 frozen_params → status=executed
```

这条链路能成立的前提是**记录在存储里、不在进程内存里** —— 因为用户可能几分钟后才回答，而那时最早处理这个请求的实例可能已经没了。这一点是下一节的主题。

## 审批的四种响应选项

很多实现只给"同意 / 拒绝"两个按钮。但用户的实际意图通常比这丰富，而**缺选项会导致错误的动作**：

| 选项 | 什么时候用 |
|---|---|
| **同意** | 就是这么办 |
| **拒绝** | 不要做这件事 |
| **修改后同意** | 方向对，但参数要改（收件人、金额、范围） |
| **换个方式** | 目标对，但做法不对（比如"用这个工具，不是那个"） |

第三种和第四种最容易被漏，而它们恰恰是最常见的真实需求。如果只给"同意/拒绝"，用户的反应通常是**拒绝然后重说一遍** —— 那等于浪费了 agent 已经做好的部分。

## 一个反过来的检查

审批也可能做错方向。三种需要警惕的形态：

**一、审批点比不可逆动作少。** 说明有不可逆的动作没被覆盖 —— 那是最严重的漏洞。

**二、用户对审批的响应时间在缩短。** 从平均 8 秒降到 1 秒，说明他在盲点。这是一个**可监控的指标**，而它是审批失效的早期信号。

**三、审批被频繁"修改后同意"。** 说明 agent 的参数选择经常有偏差 —— 那是提示词或工具设计的问题，不该靠审批来兜。

第二条特别值得做：**它把"审批是否还有效"变成一个有数字的问题。** 它是上面那个经验判断的验证手段 —— 与其相信"第 3 次之后就没人看了"，不如直接看响应时间曲线：从平均 8 秒降到 1 秒，就是盲点开始的信号。

## 和"不可逆确认"的区别

第 9 章给过一道闸门叫"不可逆确认"。本节讲的是它的设计细节，但有一处不同值得说清：

第 9 章的重点是**要有这道闸门**；本节的重点是**闸门要设在正确的位置，并且要给出正确的信息**。前者是"有没有"，后者是"有没有用"。

一个具体例子：把闸门设在"调用 write_file 之前"（每个写操作都问）和设在"覆盖已有文件之前"（只在真正不可逆时问）—— 后者打断次数少得多，而安全性相同。**闸门的位置应该由"可逆性"决定，而不是由"工具名"决定。**


> **三种抽象对应的代码形态与两个常见误判，正文在第 13 章第 2 节**（agent-frameworks/02-abstraction-models）。审批设计只需要用到其中一件事：链的下一步在代码里写死、ReAct 的下一步由模型当次推理决定 —— 这决定了审批点该放在装配层还是执行层。
## 一个反过来的问题：审批能不能被绕过

设计完审批之后要问一个检验问题：**有没有一条路径能绕过它？**

常见的三条：

**一、批量和单条走不同的代码路径。** 单条发送会弹审批，但批量导入接口直接调了同一个底层函数。这是最经典的一种 —— 因为批量入口往往是后加的。

**二、重试逻辑绕过审批。** 第一次执行失败，重试时"反正已经批过了"就直接执行 —— 但那次失败可能发生在副作用已经产生之后（第 11 节那个窗口）。

**三、内部调用不走审批。** 别的服务通过内部 API 调这个动作，而审批只在面向用户的入口上做了。

三条的共同点是：**审批加在了"入口"上，而不是"动作"上。** 正确的做法是把审批放在**动作真正执行的那一层**（和第 16 节讲执行层是唯一安全边界是同一个道理）—— 那样无论从哪个入口进来，都绕不过去。

**"那一层"具体是哪一层？** 就是前面那个 `guard`：它包着工具的**真实实现**，并且不把真实实现暴露给调用方。形状是这样的：

```python
# 装配层（唯一能碰 impl 的地方）：把真实实现包进 guard
TOOLS = [
    {"name": "send_email",  "reversible": False, "impl": _send_email_impl,
     "irreversible_reason": "邮件离开服务端后不可撤回"},
    {"name": "read_doc",    "reversible": True,  "impl": _read_doc_impl},
]

# 其余所有代码路径（对话循环、批量导入、内部 API、重试）都只能这样调用：
#   guard(tool, params, actor)
# 它们拿不到 _send_email_impl —— 所以不存在"忘了加审批"的那条路。
```

**这个形状和后端里的那些"绕不过去的拦截点"是同一个模式**：数据库的权限检查在引擎里、网关的鉴权在网关里、审计在写入路径上 —— 都不依赖调用方自觉。审批要放在同一类位置。

这也是一个可以自动化检查的东西：**遍历所有能触发不可逆动作的代码路径，确认每一条都经过了审批。** 而这种检查在没有审计日志的情况下做不了。

**"轨迹"在这里指什么。** 它是这次任务按顺序留下的每一步记录 —— 每一步调了什么工具、参数是什么、返回了什么、花了多少 token。第 15 章定的四个字段就是它：步骤序号、原始参数、原始返回值、token 与耗时。它是排查的原料（第 15 章），也是本节的兜底：**审批记录回答"人批了什么"，轨迹回答"系统实际做了什么"，两者对不上就是要出事的信号。**
## 完整可运行代码

下面这段代码就是上面那张对照表的实现：三种审批策略，统计中断次数与漏网的不可逆动作。

```python
"""审批点的粒度：一个任务会被打断几次。

同一份任务流程，三种审批策略下统计中断次数与"拦住的危险动作数"。
纯本地，实跑状态：2026-10-09。
"""

# 一个真实形态的任务：每步有 (名称, 是否可逆, 是否高危)
TASK = [
    ("read_doc",        True,  False),
    ("search_kb",       True,  False),
    ("summarize",       True,  False),
    ("draft_email",     True,  False),
    ("send_email",      False, False),   # 不可逆：发出去了收不回
    ("update_crm",      False, True),    # 不可逆 + 高危：改客户数据
    ("log_result",      True,  False),
]

POLICIES = {
    "A 每个动作都问":      lambda s: True,
    "B 只问不可逆动作":    lambda s: not s[1],
    "C 只问高危动作":      lambda s: s[2],
    "D 只在最后确认一次":  lambda s: False,
}


def run(policy):
    asked = []
    risky_executed = 0
    for i, step in enumerate(TASK, 1):
        if policy(step):
            asked.append((i, step[0]))
        else:
            if not step[1] or step[2]:
                risky_executed += 1
    return asked, risky_executed


if __name__ == "__main__":
    total_risky = sum(1 for s in TASK if (not s[1]) or s[2])
    print("任务共 %d 步，其中不可逆或高危的有 %d 步：" % (len(TASK), total_risky))
    for i, s in enumerate(TASK, 1):
        tag = []
        if not s[1]:
            tag.append("不可逆")
        if s[2]:
            tag.append("高危")
        print("    %d. %-14s %s" % (i, s[0], "、".join(tag) or "可逆且低危"))
    print()
    print("  %-20s %-10s %-12s %s" % ("策略", "中断次数", "未审批执行", "说明"))
    for name, pol in POLICIES.items():
        asked, risky = run(pol)
        note = {
            "A 每个动作都问": "打断 7 次 —— 审批疲劳，用户会开始盲点同意",
            "B 只问不可逆动作": "打断 2 次，全在真正不可逆的步骤上",
            "C 只问高危动作": "打断 1 次，但 send_email 无审批就发了",
            "D 只在最后确认一次": "0 次打断，两个不可逆动作全部裸奔",
        }[name]
        print("  %-20s %-10d %-12d %s" % (name, len(asked), risky, note))
    print()
    print("=== 关键点 ===")
    print("  A 看着最安全，代价是 7 次打断 —— 注意这里量的是中断次数。")
    print("  疲劳（用户会不会盲点同意）是经验判断，不是这个实验测出来的。")
    print()
    print("  C 看着「克制」，但它放过了 send_email（不可逆但不算高危）——")
    print("  而「发出去就收不回」正是最该问的那一类。")
    print()
    print("  正确的判据是 B：**按可逆性，不按危险程度**。")
    print("  理由：可逆的动作错了可以回滚；不可逆的错了只能补救。")
```

## 常见坑

- **按"危险程度"设审批点。** 实测：那会放过 send_email（不可逆但不高危）。判据应该是**可逆性**。
- **每个动作都问。** 7 次打断（实测）本身就会招来审批疲劳 —— 有成本，没效果。疲劳是经验判断，别当成实测引用。
- **只显示工具名。** 用户不知道发给谁、发了什么，只能盲点同意。
- **只给"同意/拒绝"。** 缺"修改后同意"和"换个方式"，用户会拒绝然后重说一遍。
- **不监控审批响应时间。** 它是审批失效的早期信号，而且是一个有数字的指标。
- **用审批掩盖参数设计问题。** 频繁"修改后同意"说明提示词或工具出了问题，该去修那里。
