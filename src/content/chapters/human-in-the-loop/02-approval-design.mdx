上一节讨论了自动化档位。这一节讲**何时要求复核，以及怎样让复核有信息可核对**。可逆性只是风险判断的一项输入；权限检查和业务策略不能被人工确认替代。

## 先看一个数据

我拿一个 7 步的任务流程，测了四种审批策略：

```text
步骤                性质
1. read_doc         可逆且低危
2. search_kb        可逆且低危
3. summarize        可逆且低危
4. draft_email      可逆且低危
5. send_email       不可逆
6. update_crm       不可逆、高危
7. log_result       可逆且低危
```

四种策略下分别统计执行前审批、事后复核和未经预先审批执行的风险动作数：

```text
策略                 执行前审批   事后复核   未审批风险动作
A 每个动作都问              7          0             0
B 只问不可逆动作             2          0             0
C 只问高危动作              1          0             1
D 任务结束后复核一次         0          1             2
```

（实跑数据，2026-10-09。纯本地模拟。）

## 三个读数

**A 看着最谨慎，但它有 7 次打断。** 打断次数是本地模拟的直接计数；审批疲劳及其对决策质量的影响没有在这个实验里测量。频率过高可能增加审查负担，但是否导致盲批，需要结合审批内容、任务类型和人的行为另行评估。

> **口径说明：** 上表只统计这个合成任务中的审批次数和未审批执行的风险动作数，不测真实用户行为、疲劳、正确率或业务风险。可把响应时间作为待验证的运营信号之一，但它会受任务复杂度、界面和用户习惯影响，单凭变快不能判断用户在盲批。

**C 看着"克制"，但按本实验的标签它放过了 send_email。** 本实验把发邮件标成"不可逆、非高危"，这只是人为设定的标签；真实邮件可能包含敏感信息、欺诈风险或重大业务影响，不能普遍归为低危。

**在这组任务中，B 在这两个计数上优于 A、C、D。** 这只是由本地代码对预设动作与标签算出的结果；它没有衡量漏报风险的严重度、审批质量或真实用户负担，不能推出通用最优策略。

**可逆性是重要输入，但不足以单独决定审批。** 生产策略还要检查主体是否有权限、目标资源与影响范围、敏感度、金额或规模，以及是否存在可接受的撤销路径。无权限的动作应拒绝，不能通过让用户确认来补权；有权限但影响很大的可逆动作也可能需要复核。

## 审批要展示什么

判据解决了"在哪停"，下一个问题是"停下来之后给用户看什么"。以下是设计时需要检查的失败形态：

**失败一：只显示工具名。** "agent 想调用 send_email，是否同意？" —— 用户不知道发给谁、发了什么，只能盲点。

**失败二：显示原始 JSON 参数。** 技术上完整，但对人来说不可读。用户会跳过。

**失败三：把整个上下文倒出来。** 信息过载，用户同样会跳过。

界面应让审批者看清**这次具体动作会改变什么**。展示内容取决于动作，但至少让人核对动作、目标和重要影响；例如：

```text
1. 动作 + 目标：要发给 zhangsan@example.com（不是「调用 send_email」）
2. 影响范围：这封邮件会被 1 个外部收件人看到
3. 影响与撤销边界：外部收件人会看到正文；发出后通常无法由本系统撤回
```

这能帮助用户理解复核原因，但不能保证他已理解或认真核对。敏感字段应按最小必要原则展示，避免审批页面本身扩大数据暴露。

## 那三样信息落成什么结构

上面那三行是"要展示什么"，它还需要一个**能被程序读写**的载体。这个载体就是待审批记录 —— 它同时喂给三个地方：界面（展示那三样）、执行层（批准后照着执行）、存储（下一节的恢复要靠它查回来）。

一份完整的记录长这样：

```json
{
  "approval_id": "ap_example",
  "tenant_id": "tenant_example",
  "requested_by": "user_example",
  "approver_policy": "当前策略版本或决策引用",
  "action": "send_email",
  "target": "zhangsan@example.com",
  "target_kind": "外部地址",
  "scope": "1 个外部收件人可见",
  "reversible": false,
  "why": "邮件离开服务端后不可撤回",
  "frozen_params": {
    "to": "zhangsan@example.com",
    "body": "订单 A-1001 已发货，物流显示派送中。"
  },
  "params_hash": "sha256:<完整摘要值>",
  "status": "pending",
  "created_at": "2026-10-12T10:31:02+08:00",
  "expires_at": "2026-10-13T10:31:02+08:00"
}
```

（示例：构造数据，未实跑 —— 它是记录结构的示例；第 3 节会给这个结构的持久化形态。）

**字段不是随便定的，每一个都对应一个失败形态。** 这张表是这一节的判据部分 —— 换一个场景时，改的是这里的**取舍**，不是字段名：

| 字段 | 为什么必须有 | 少了它会怎么坏 |
|---|---|---|
| `action` + `target` + `target_kind` | 人要知道"发给谁"，`target_kind` 标出它是不是外部对象 | 用户只看工具名就盲点 |
| `scope` | 影响范围是"1 个外部收件人"还是"全体客户"，决定要不要更谨慎 | 用户无法估计爆炸半径 |
| `reversible` + `why` | 上一节那个字段；`why` 是给人看的理由 | 用户不理解为什么被打断，于是不看内容 |
| **`frozen_params`** | **用户批准的是这一组具体参数，不是"以后会生成的"动作** | 恢复时重新生成 → 执行的可能不是用户批准的那件事（第 3 节详述） |
| `params_hash` | 给冻结参数留一个可比较的指纹 | 无法判断"要执行的是不是当初批准的那份" |
| `status` | 记录 pending、approved、executing、executed、rejected、expired、unknown/reconciling 等状态 | 无法区分"等审批"、"已批准待执行"与"外部效果未知" |
| `expires_at` | 审批是有时效的，几小时前的批准不该永久有效 | 用户一周前批过的动作，今天被恢复执行 |

**其中 `frozen_params` 是避免批准内容与执行内容漂移的关键字段。** `reversible` 只是风险属性，不能回答调用者是否有权执行。`params_hash` 只能在同一规范化规则下帮助比较提案与待执行参数；普通 SHA-256 不能保护冻结记录本身：若攻击者能同时改参数和摘要，就能重新计算。服务端应从可信、受保护的记录读取提案，并在执行前再次核对；若威胁模型包含存储记录被篡改，还需要适用的访问控制、不可变存储或带密钥的完整性机制。示意中的占位符不是可直接使用的摘要。

审批 ID 只是查找记录的引用，不能当作授权凭据。读取或批准记录时，服务端仍须验证登录身份、租户/对象范围、审批者权限和当前策略；批准后执行前也要重新检查授权、有效期、目标版本及一次性状态。若参数、目标或权限发生变化，应使旧批准失效并重新提交审批。`修改后同意` 和 `换个方式` 都会形成新提案，不能沿用旧提案的批准。

## 拦截层放在哪：一个会真的被调用的地方

上面说判据要有载体，载体要有位置。位置选错的典型症状是"审批加了，但有个入口绕过它"（本节最后一节会展开三种绕过路径）。所以先把这个位置写清楚。

**关键控制应由服务端在受保护动作附近强制执行**，不能只依赖某个 UI handler 自觉调用审批。工程上可以用统一的工具执行器或服务端策略执行点；每个可达入口仍需纳入授权和绕过测试。下面是教学用伪代码骨架，不是安全实现：

```python
# 教学伪代码：持久化、原子状态转换、身份与策略检查由省略的服务端组件负责。

def guard(tool, params, actor):
    """执行入口。返回三种结果之一：已执行 / 待审批 / 拒绝。"""
    decision = authorize(actor, tool, params)  # 每次请求都检查主体/目标/动作
    if not decision.allowed:
        return {"status": "denied"}

    if policy_requires_review(actor, tool, params, decision):
        # 持久化冻结后的提案；UI 不持有 impl，也不能改写已批准参数
        record = persist_pending(tool, params, actor, decision.policy_version)
        return {"status": "pending_approval", "approval_id": record.id}

    return execute_with_idempotency(tool, params, actor)
```

服务端执行点能保护到达该点的调用，但它不能自动覆盖绕开该服务的其他写路径。应枚举单条、批量、内部 API、重试和异步 worker 等入口，并证明它们都经过身份/对象授权与适用的审批策略。OWASP 的事务授权建议也要求服务端执行授权、绑定用户实际看到并确认的重要交易数据；不能把此处的伪代码当成完整安全保证。

反过来，如果审批写在面向用户的 handler 里，那么后加的批量接口、内部 API、重试逻辑都天然绕开它。这是本节最后要检查的那件事。

## 批准之后怎么续跑：一句话的指针

上面那个 `pending_approval` 结果里有一个 `approval_id`，供服务端定位待审记录。它只是引用：界面提交响应时携带该 id，服务端仍要核验调用者权限、记录状态、冻结参数和当前策略后才能继续。

所以"续跑"不是一个内存里的回调，而是**一次新的请求**：

```text
界面 → POST /approval/ap_8f3c21/approve
服务端 → 按租户/审批者权限读取记录 → 原子 claim 并复核冻结参数/授权/期限 → 执行 → 记录结果或转 unknown/reconciling
```

这条链路能成立的前提是记录持久化，并使用原子状态转换防止并发重复批准。外部副作用如果执行后响应丢失，状态可能未知；不能简单把记录标成失败并重放，应由下一节讨论的幂等与对账机制处理。记录持久化是必要条件，但不等于副作用 exactly-once。

## 审批的四种响应选项

除了"同意 / 拒绝"，界面也可以提供修改参数或提出替代方案的路径，但这些选项是否合适取决于任务和产品设计：

| 选项 | 什么时候用 |
|---|---|
| **同意** | 就是这么办 |
| **拒绝** | 不要做这件事 |
| **修改后同意** | 方向对，但参数要改（收件人、金额、范围） |
| **换个方式** | 目标对，但做法不对（比如"用这个工具，不是那个"） |

如果用户修改目标、参数或方案，服务端应生成新的冻结提案并要求重新审批；不得把旧批准自动迁移到新动作。也不能假设拒绝后用户一定会重述，应该明确展示拒绝、编辑和重新规划各自的结果。

## 一个反过来的检查

审批也可能做错方向。三种需要警惕的形态：

**一、审批点比不可逆动作少。** 说明有不可逆的动作没被覆盖 —— 那是最严重的漏洞。

**二、审批响应行为发生变化。** 响应时间可以作为调查线索之一，但需要按动作类型、风险、用户和界面版本分层；变快本身不证明盲批，也不能单独作为审批失效判据。

**三、审批被频繁"修改后同意"。** 说明 agent 的参数选择经常有偏差 —— 那是提示词或工具设计的问题，不该靠审批来兜。

如需评估审批是否仍有效，应把响应时间与抽样复核、审批后撤销/更正、不同风险层级的误批率及用户研究结合，并预先说明判据。单个时间阈值无法证明人的注意力或判断质量。

## 和"不可逆确认"的区别

第 9 章给过一道闸门叫"不可逆确认"。本节讲的是它的设计细节，但有一处不同值得说清：

第 9 章的重点是**要有这道闸门**；本节的重点是**闸门要设在正确的位置，并且要给出正确的信息**。前者是"有没有"，后者是"有没有用"。

一个具体例子：把闸门设在"调用 write_file 之前"（每个写操作都问）和设在"覆盖已有文件之前"（按资源影响、授权和恢复能力判断是否复核）—— 后者可以减少不必要的打断，同时保留高影响操作的保护。**闸门的位置应该由动作风险与授权策略决定，而不是由"工具名"决定。**


> **三种抽象对应的代码形态与两个常见误判，正文在第 13 章第 2 节**（agent-frameworks/02-abstraction-models）。审批设计只需要用到其中一件事：链的下一步在代码里写死、ReAct 的下一步由模型当次推理决定 —— 这决定了审批点该放在装配层还是执行层。
## 一个反过来的问题：审批能不能被绕过

设计完审批之后要问一个检验问题：**有没有一条路径能绕过它？**

常见的三条：

**一、批量和单条走不同的代码路径。** 单条发送会弹审批，但批量导入接口直接调了同一个底层函数。这是最经典的一种 —— 因为批量入口往往是后加的。

**二、重试逻辑绕过审批。** 第一次执行失败，重试时"反正已经批过了"就直接执行 —— 但那次失败可能发生在副作用已经产生之后（第 11 节那个窗口）。

**三、内部调用不走审批。** 别的服务通过内部 API 调这个动作，而审批只在面向用户的入口上做了。

三条的共同风险是：审批只覆盖了部分入口。应尽量让策略在受保护动作附近统一执行，同时逐个盘点其他写路径；单个 wrapper 本身不证明所有入口都无法绕过。

**"那一层"具体是哪一层？** 可以是由服务端统一执行策略的工具执行器或受保护业务服务。它应避免把可绕过的真实实现暴露给不可信调用方；示意如下，实际系统还要在各服务/数据边界检查权限：

```python
# 示意：受保护的服务端装配层提供统一调用接口
TOOLS = [
    {"name": "send_email",  "reversible": False, "impl": _send_email_impl,
     "irreversible_reason": "邮件离开服务端后不可撤回"},
    {"name": "read_doc",    "reversible": True,  "impl": _read_doc_impl},
]

# 其余所有代码路径（对话循环、批量导入、内部 API、重试）都只能这样调用：
#   guard(tool, params, actor)
# 仍须验证其他入口、worker 和重试路径是否都使用该受保护接口。
```

**这个形状和后端里的那些"绕不过去的拦截点"是同一个模式**：数据库的权限检查在引擎里、网关的鉴权在网关里、审计在写入路径上 —— 都不依赖调用方自觉。审批要放在同一类位置。

可以通过代码搜索、路由/工具清单、集成测试和审计事件检查所有可达路径是否经过控制；日志有助于发现运行时调用，但单靠日志不能证明没有未覆盖路径。

**"轨迹"在这里指什么。** 它是按顺序保留的执行证据：步骤序号、动作、经过校验与筛选/脱敏的参数字段、安全摘要或受控结果引用，以及与对应模型调用关联的 usage 和耗时。不要默认把完整参数、返回值或上下文写入普通日志；字段白名单、访问权限和保留期限应按数据敏感度确定。可参考[评估与追踪](/chapters/evaluation/traces)中的字段建议。轨迹帮助排查，但不能单独证明根因或代替业务判据：**审批记录说明人确认了哪份冻结提案，轨迹帮助核对系统执行了什么，两者的差异是需要调查的信号。**
## 完整可运行代码

下面这段代码实现上面这张对照表的四种策略，统计审批次数与未审批执行的风险动作数。

```python
"""审批点的粒度：一个任务会被打断几次。

同一份任务流程，四种审批策略下统计审批次数与未审批执行的风险动作数。
纯本地，实跑状态：2026-10-09。
"""

# 一个真实形态的任务：每步有 (名称, 是否可逆, 是否高危)
TASK = [
    ("read_doc",        True,  False),
    ("search_kb",       True,  False),
    ("summarize",       True,  False),
    ("draft_email",     True,  False),
    ("send_email",      False, False),   # 不可逆：发出去了收不回
    ("update_crm",      False, True),    # 不可逆 + 高危：改客户数据
    ("log_result",      True,  False),
]

POLICIES = {
    "A 每个动作都问":      lambda s: True,
    "B 只问不可逆动作":    lambda s: not s[1],
    "C 只问高危动作":      lambda s: s[2],
    "D 任务结束后复核一次":  lambda s: False,
}


def run(policy, review_after=False):
    asked = []
    risky_executed = 0
    for i, step in enumerate(TASK, 1):
        if policy(step):
            asked.append((i, step[0]))
        else:
            if not step[1] or step[2]:
                risky_executed += 1
    return asked, risky_executed, int(review_after)


if __name__ == "__main__":
    total_risky = sum(1 for s in TASK if (not s[1]) or s[2])
    print("任务共 %d 步，其中不可逆或高危的有 %d 步：" % (len(TASK), total_risky))
    for i, s in enumerate(TASK, 1):
        tag = []
        if not s[1]:
            tag.append("不可逆")
        if s[2]:
            tag.append("高危")
        print("    %d. %-14s %s" % (i, s[0], "、".join(tag) or "可逆且低危"))
    print()
    print("  %-20s %-10s %-10s %-12s" % ("策略", "执行前审批", "事后复核", "未审批风险动作"))
    for name, pol in POLICIES.items():
        asked, risky, reviewed_after = run(pol, review_after=name == "D 任务结束后复核一次")
        print("  %-20s %-10d %-10d %-12d" % (name, len(asked), reviewed_after, risky))
    print()
    print("=== 关键点 ===")
    print("  A 有 7 次打断；这里量的是次数，不是实际用户负担或疲劳。")
    print()
    print("  C 未审批执行 send_email；本模拟的风险标签由作者设定。")
    print()
    print("  仅就本任务的审批次数和未审批风险动作计数，B 优于 C。")
    print("  这不是通用审批公式：生产策略还要结合影响范围、敏感度、金额与主体授权。")
```

## 常见坑

- **只按"危险程度"或只按可逆性设审批点。** 本任务实测显示只看高危标签会放过 send_email；生产判定还需结合影响范围、敏感度、金额与主体授权。
- **每个动作都问。** 本模拟里有 7 次打断；真实用户负担与审批疲劳需要单独验证，不能由这个计数推出。
- **只显示工具名。** 用户不知道发给谁、发了什么，只能盲点同意。
- **把选项设计成批准后仍能悄悄修改动作。** 参数或目标一旦改变，就应形成新提案并重新审批。
- **把响应时间当成审批有效性的单一判据。** 它只能作为需要分层解释的线索，不能证明用户是否认真审核。
- **用审批掩盖参数设计问题。** 频繁"修改后同意"说明提示词或工具出了问题，该去修那里。
