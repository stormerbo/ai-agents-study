第 18 章测过一个数字：一个输出 1200 token 的回答要 6.78 秒，而首 token 只要 0.68 秒。这一节讲怎么用这个差别改善体验 —— 以及流式带来的新问题。

## 流式解决的是「感知延迟」，不是延迟

先把这件事说清楚，因为混淆它会导致错误的优化方向：

**流式不减少总时间。** 6.78 秒还是 6.78 秒。它做的是把「0.68 秒后开始出现内容」这件事变成可能，而不是「7.5 秒后一次性出现」。

从第 18 章的数据看，这个差别很具体：


```text
非流式：0 → 6.78 秒：一片空白
流式：  0.68 秒开始逐字出现，6.78 秒结束
```

**用户对「正在发生」和「什么都没发生」的耐心差别极大。** 第 18 章那条「总延迟 ≈ 0.8s + 输出/180」可以用来设置预期：如果输出大概 1200 token，界面应该在 0.8 秒内出现第一个字，否则就该有一个「正在处理」的提示。

## 一个容易做错的地方：流式 + 结构化的冲突

流式对纯文本很自然，但和第 5 章的结构化输出有冲突：**JSON 在流式过程中是无效的。**

用户看到的是：

```text
{"order": "A-1001", "status": "已发
```

这段内容既不能被解析，展示出来也很奇怪。三种处理方式：

| 做法 | 什么时候用 |
|---|---|
| **不流式结构化部分** | 结构固定、字段少：等完整 JSON 再一次性展示 |
| **流式但解析缓冲** | 边收边解析，字段完整一个就渲染一个 |
| **分离字段与文本** | 让模型把自然语言部分和结构化部分分开输出 |

第三种在 agent 里最实用：**大部分 agent 的输出是「一段说明 + 一个动作」**，把说明流式出来、动作等完整 JSON 再执行。这样用户能提前看到它在想什么，而工具调用仍然是原子的。

## 停止：控制感的核心

流式带来的最有价值的交互是**停止按钮** —— 但它经常被做错。

三种错误：

**错误一：停止只是断开前端连接。** 后端还在跑、还在计费。用户以为停了，账单还在涨。

**错误二：停止之后已生成的内容被丢弃。** 用户等了 3 秒看到了一半内容，点停止，然后什么都没了 —— 那他为什么要等那 3 秒？

**错误三：停止的粒度太粗。** 整个任务被终止，而用户可能只是不想要某一句话。

正确的做法：**停止要真的终止后端、保留已生成的内容、并且明确告知「已停止，这是已完成的部分」。** 这三条合起来才是「控制感」—— 用户知道他的操作真的生效了。

## 服务端取消到底要做什么

上面三条里最难的是第一条，因为它**跨越了三个层次**，而每一层都要各自处理：

```text
层          要做的动作                              不做会怎样
HTTP 连接   检测到客户端断开（或收到 /stop 请求）      前端断了，后端不知道
模型调用     把取消信号传给正在进行的流式请求          连接断了，服务端仍在生成并计费
工具执行     停止"还没开始"的调用；已经在跑的等它结束   半途中断的副作用没人管
```

**第一条的实测在这里。** 我用一个故意写长的请求（要求约 1200 字），在收到第一段内容后就断开 socket：

```text
客户端收到第一段：455 字节，用时 0.09s，随后断开
同一提示词完整跑完：20.38s，输出 2951 token
```

（实跑数据，2026-10-12。模型 deepseek-flash，消息 API 直连，流式。）

**断开的时候，客户端只用了 0.09 秒就"停"了 —— 而服务端还会继续生成到大约 20 秒。** 这组数字就是"停止只是断开前端连接"的代价：界面上一秒内就安静了，而账单按完整生成结。它和"流式不减少总时间"是同一个机制的两面 —— **生成是服务端驱动的，客户端断开不会通知它。**

**所以取消要显式传下去，而不是等连接断。** 形态是一个取消令牌（cancellation token），在三个地方被检查。下面这段代码是它的骨架，可以直接跑：

```python
"""服务端取消：取消令牌要传到模型调用与工具执行。

可运行 —— 它用一个本地的 FakeProvider 产生分片，所以不需要任何凭据。
换成真实端点时的接线见文末注释。

实跑状态：2026-10-12。
"""
import asyncio
import os
import time


class Cancelled(Exception):
    pass


class Token:
    """取消令牌：一个事件 + 一个理由。所有层都持有它。"""

    def __init__(self):
        self.event = asyncio.Event()
        self.reason = None

    def cancel(self, reason="用户点击停止"):
        if not self.event.is_set():
            self.reason = reason
            self.event.set()

    def check(self):
        if self.event.is_set():
            raise Cancelled(self.reason)


class FakeProvider:
    """本地假模型：按分片吐出，每片 5ms。真实实现换成你的 SDK 流式调用。"""

    FRAMES = 1200

    async def stream(self, token):
        for text in ("这是个很长的回答，", "它会被分成很多片，", "每一片都要检查取消令牌。"):
            for _ in range(self.FRAMES // 3):
                token.check()                       # ← 每收一片检查一次
                await asyncio.sleep(0.005)
                yield text


class FakeTool:
    """有副作用的工具。它**不可取消** —— 开始之后只能等它结束。"""

    async def run(self, token):
        if token.event.is_set():
            return None                              # 还没开始 → 直接不执行
        await asyncio.sleep(0.05)                    # 已经开始了
        return "mail_sent"


async def run_turn(provider, token, stop_after_ms):
    """跑一轮：到点取消，统计取消前实际生成了多少片。"""
    stats = {"frames": 0, "cancelled": False}

    async def stop_later():
        await asyncio.sleep(stop_after_ms / 1000)
        token.cancel()

    async def consume():
        try:
            async for _ in provider.stream(token):
                stats["frames"] += 1
        except Cancelled:
            stats["cancelled"] = True

    await asyncio.gather(stop_later(), consume())
    tool = await FakeTool().run(token)
    return stats, tool


async def main():
    provider = FakeProvider()
    token = Token()
    stats, tool = await run_turn(provider, token, stop_after_ms=100)
    print("  提示词要求的总分片数：%d" % provider.FRAMES)
    print("  客户端实际收到的分片：%d" % stats["frames"])
    print("  是否收到取消异常：%s" % ("是" if stats["cancelled"] else "否"))
    print("  取消理由：%s" % token.reason)
    print("  取消之后模型这一层：%s"
          % ("停了 —— 这就是省下账单的那一行" if stats["frames"] < provider.FRAMES
             else "没停，把整个输出跑完了"))
    print("  工具这一层：%s"
          % ("没有执行（取消时它还没开始）" if tool is None else "已执行 " + str(tool)))


# 换成真实端点时，Provider 里的 stream 大概长这样：
#   key = os.environ["ANTHROPIC_AUTH_TOKEN"]        # 需要一个 API Key
#   async with client.messages.stream(...) as s:
#       async for chunk in s:
#           token.check()          # ← 取消信号在这里生效，连接被关闭
#           yield chunk.text
#   密钥的拿法见项目约定：本地放在 .env.local，或由部署平台注入环境变量。


if __name__ == "__main__":
    asyncio.run(main())
```

**这段代码里有两个要带走的东西。**

**一、取消令牌必须一路传到底。** `token.check()` 出现在模型流的分片循环里 —— 这是让"停止"真正省钱的那一行。如果只在入口检查一次，取消之后服务端照样会跑完。

**二、工具层只能做"尽力而为"的取消。** 上面的 `FakeTool` 演示了两条分支：

- **还没开始的动作** → 不执行（这是"停止"能拦住的）
- **已经开始的副作用** → 等它结束，然后按第 3 节那套恢复逻辑决定要不要补偿（这是拦不住的）

**这个区别必须在接口上写清楚**，因为它是"用户以为停了"的来源：停止能取消模型生成与排队中的工具，**不能撤销已经在跑的副作用**。所以界面上的文案应该是"已停止生成"或者"正在完成当前动作，稍后确认结果"，而不是笼统的"已取消"。

## 流式里到底有哪些事件

上面说"分片循环里检查取消"，前提是你知道流里有哪些事件。协议层至少有四类（第 1 章记录过完整的 63 个事件序列）：

| 事件 | 带什么 | 该做什么 |
|---|---|---|
| **消息开始** | 模型名、初始用量 | 建流、准备渲染 |
| **内容块增量** | 文本片段、或工具参数的分片 | 追加到缓冲；`token.check()` 在这里 |
| **消息增量** | `stop_reason`、累计用量 | 判结束原因（见下） |
| **消息结束** | 完整消息 | 收尾、落库 |

**`stop_reason` 是这次生成"为什么停下"的字段** —— 它是模型的结束原因，不是你的业务状态。而 **`max_tokens` 指的是那次调用允许生成的最大 token 数** —— 你在请求里设的输出预算，不是模型的能力上限。两者是一对。最常见的两个取值：`end_turn`（正常说完了）与 `max_tokens`（输出预算用完，回答被截断）。后者是本站踩过三次的坑（第 3、7、18 章）：预算不够时返回的是**空文本 + 停止原因是 max_tokens**，看起来像"模型做不到"。**判据：没确认 `stop_reason` 之前，不要解释任何"没答出来"的结果。**

**SSE 指的是 Server-Sent Events，一种承载这套事件的传输格式**：一个长连接，服务端按 `data: {...}` 的文本行往下推，客户端逐行解析。它和 WebSocket 的差别是单向（服务端 → 客户端），而这恰好够用 —— 用户要发的东西（停止、审批）走另一个普通请求。**恢复连接与断线重连是它的弱点**：SSE 断了之后要靠客户端重连并带上"我收到哪里了"（第 3 节那套状态），否则会重复或漏掉片段。

## 一个反直觉的取舍：越流畅，越难打断

最后说一个和前面几节冲突的点。

第 3 节讲审批时要「停下来问人」，而流式的目标是「尽量流畅地输出」。这两件事在同一个界面里会冲突：

- 流式输出到一半，突然弹出一个审批框 —— 用户的第一反应是「我刚才在看的内容呢」
- 审批通过之后继续流式，但用户已经失去了上下文

处理方式有两种，按任务类型选：

**一、把审批放在流式之前。** 适合「动作型」任务（要调工具）：先规划、审批、再执行并流式输出结果。用户看到的是一条干净的流。

**二、流式输出中遇到审批就明确分段。** 适合「探索型」任务：界面显示「已生成前半部分，需要你确认后才能继续」，并保留已生成内容。

第二种的关键是**明确分段** —— 让用户理解「暂停」是流程的一部分，不是卡住了（第 4 节那条「异常要有出口」的反面）。

## 两个在前文出现过的词

**装饰器（decorator）。** 就是 Python 里那个 `@something` 语法 —— 它把一个函数包一层，返回一个新的可调用对象。框架常用它来"自动收集工具定义"：你在函数上写一个 `@tool`，框架在启动时扫描它、生成 schema。**本节那个 `guard` wrapper 其实就是手写的装饰器**，区别只是框架帮你做、你要知道它做了什么。

**enum（在框架语境里）。** 指"这个参数只能取给定几个值"的约束。第 13 章第 3 节实测过：LangChain 0.3.7 的 `@tool` 装饰器生成的 schema 里 `day` 只有 `{"type": "string"}`，**没有 enum** —— 尽管注释里写了"只支持明天或后天"。改用 `Literal["明天","后天"]` 之后才出现。所以"装饰器给不给 enum"是一个可验证的边界问题，而不是一个感觉。

## 一个具体的交互细节：停止之后怎么办

点了停止之后，界面上该显示什么？三种做法，体验差别很大。

**做法一：清空。** 界面回到初始状态，什么都没留下。
问题是用户等了 3 秒看到的内容也没了。

**做法二：保留内容，但显示"已停止"。** 用户能看到已经生成的部分，并且知道它不完整。
这是最实用的做法 —— 而且它往往已经够用了（很多场景下前半段就是用户要的）。

**做法三：保留内容，并给出"继续"入口。** 用户能从中断处继续。
功能最强，但实现上要处理"继续时的上下文"问题（第 3 节那套状态持久化），复杂度最高。

**从做法二开始是对的。** 它用很小的成本解决了 90% 的需求，而且它不需要持久化执行状态 —— 只需要把已经推给前端的内容留在那里。

做法三只在特定场景值得做：长任务（跑了几分钟）、且中间结果不能单独使用。

## 一个和"控制感"有关的心理学细节

最后补一个观察，它影响停止按钮的设计：**用户点停止，通常不是因为他不要这个结果，而是因为他不确定它还要多久。**

这个区别很重要，因为它指向完全不同的两种改进：

- 如果真的是不要结果 → 优化停止（当前话题）
- 如果不确定要多久 → **优化进度提示**（第 4 节）

判别方法是看数据：**如果加了准确的进度预估之后，停止率明显下降**，那说明之前的问题在可见性，不在控制。这个测试值得做一次 —— 因为它可能用一行进度文案，替代掉一整套"继续执行"的实现。
## 完整可运行代码

下面这段代码实现流式输出的分片处理，并演示「说明流式 + 动作等完整 JSON」的分离策略。

```python
"""流式 + 结构化：分离「说明」和「动作」。纯本地。实跑状态：2026-10-09。"""
import json

# 模型输出形态：一段自然语言说明 + 一个结构化动作
FULL = '{"say": "我查到订单 A-1001 已发货，物流显示派送中。", "action": {"tool": "reply", "to": "zhangsan@example.com"}}'


def naive_stream(full, chunk=18):
    """做法一：对流式分片直接展示。用户会看到半截 JSON。"""
    frames = []
    for i in range(0, len(full), chunk):
        frames.append(full[i:i + chunk])
    return frames


def split_stream(full):
    """做法二：说明部分逐字流出，动作等完整 JSON 再解析。"""
    obj = json.loads(full)
    say = obj["say"]
    frames = [say[i:i + 8] for i in range(0, len(say), 8)]
    action = obj["action"]
    return frames, action


if __name__ == "__main__":
    print("模型输出（%d 字符）：" % len(FULL))
    print("  %s" % FULL[:60] + "…")
    print()
    print("做法一：直接流式展示 —— 用户看到的中间状态：")
    for f in naive_stream(FULL)[:4]:
        print("    %s" % f)
    print("  ⚠️ 这些片段无法解析，展示出来也很奇怪。")
    print()
    print("做法二：分离说明与动作")
    frames, action = split_stream(FULL)
    print("  说明部分逐字流出（前 4 帧）：")
    for f in frames[:4]:
        print("    %s" % f)
    print("  说明流完之后，动作已完整：%s" % json.dumps(action, ensure_ascii=False))
    print("  ✅ 用户提前看到它在想什么，而工具调用仍然是原子的。")
```

## 常见坑

- **以为流式减少总时间。** 它只改善感知延迟 —— 6.78 秒还是 6.78 秒。
- **对结构化输出直接流式。** JSON 在流式中无效，用户会看到半截无法解析的内容。
- **停止只断开前端。** 后端还在跑、还在计费 —— 用户以为停了，账单还在涨。
- **停止后丢弃已生成内容。** 那用户为什么要等那几秒？已生成的部分应该保留。
- **审批框打断流式却不解释。** 用户会以为卡住了 —— 要明确说是「等待确认」。
- **不给「还有多久」的提示。** 用第 18 章那个估算式：总延迟 ≈ 0.8s + 输出/180。
- **在入口检查一次取消就以为停了。** 取消信号必须传到模型流的分片循环与工具执行里，否则服务端照样跑完（本节那组 0.09s 对 20.38s 的数据就是这个）。
- **把"已停止"和"已撤销"混为一谈。** 停止能拦住生成与排队中的工具，**拦不住已经在跑的副作用** —— 文案要说清是哪一种。
- **SSE 断线后从头重推。** 客户端重连要带上"我收到哪里了"，否则会重复渲染或漏掉片段。

## 这一层会怎么坏

三类坏法，前两类不会报错，第三类会在账单上出现：

| 坏法 | 现象 | 怎么发现 |
|---|---|---|
| **取消没传到底** | 界面一秒内安静了，账单按完整输出结 | 断开之后看服务端日志：那条请求是什么时候真正结束的 |
| **停止后丢弃已生成内容** | 用户等了 3 秒点停止，界面空了 | 手动点一次停止，看已生成的部分还在不在 |
| **审批框打断流式却不解释** | 用户以为卡住了，于是点停止或刷新 | 让一个任务在中途需要审批，走一遍完整交互 |

第一条的判据最直接：**断开连接之后，服务端还在工作多久。** 本节那组实测（客户端 0.09 秒退出、完整生成 20.38 秒）就是它的量纲 —— 如果这个差值很大，你需要的不是优化文案，而是把取消信号接下去。
