第 18 章保留的一条历史摘要记录了 1,200 输出 token：首事件 0.68 秒、「生成」6.78 秒、总计 7.46 秒。它只有单次记录，原始 trace 未归档；首事件不一定是首个可见文本，「生成」列也不能确认是纯解码时间。这一节用它说明指标口径，而不把它当成基准或 ETA。

## 流式解决的是「感知延迟」，不是延迟

先把这件事说清楚，因为混淆它会导致错误的优化方向：

**流式的目标通常是更早交付可呈现的部分内容；它不保证端到端总时长变短。** 分片本身、缓冲、代理与客户端渲染都会影响实际时间。第 18 章的这条摘要报告总计 7.46 秒，但没有可配对的非流式对照，不能据此声称非流式必定要等同样时间。

从第 18 章的数据看，这个差别很具体：


```text
本次历史流式摘要：0.68 秒首事件 / 7.46 秒记录总计
说明：首事件不等同首个可见文本；该记录没有配对的非流式对照
```

首事件与首个可见文本要分开测；如果状态迟迟没有变化，界面可以展示「正在连接/等待首个内容」等真实状态。不要用这四条单次记录拟合通用的首 token 期限、token/s 或 ETA；进度预估应由具体工作流的重复数据校准，并报告不确定性。

## 一个容易做错的地方：流式 + 结构化的冲突

流式结构化输出需要区分「当前片段」与「完整、可校验的对象」。JSON 的中间片段经常是不完整的，不能直接 `json.loads` 或据此执行动作；部分协议/解析器可以增量识别已完成字段，但最终对象仍需等内容块结束、解析成功并通过 schema、权限与业务校验。

用户看到的是：

```text
{"order": "A-1001", "status": "已发
```

这段内容既不能被解析，展示出来也很奇怪。三种处理方式：

| 做法 | 什么时候用 |
|---|---|
| **不流式结构化部分** | 结构固定、字段少：等完整 JSON 再一次性展示 |
| **流式但解析缓冲** | 边收边解析，字段完整一个就渲染一个 |
| **分离字段与文本** | 让模型把自然语言部分和结构化部分分开输出 |

若产品协议把面向用户的文本块与工具调用块分开，可以分别处理：只流式呈现获准展示的文本；将工具参数按块索引累积，等块完整后解析和校验，再交由宿主授权执行。不要把模型内部 reasoning/thinking 当成用户说明；协议形状与逐步解析能力因 provider 而异。[Claude 的流式规范](https://platform.claude.com/docs/en/build-with-claude/streaming)说明 `tool_use` 的 JSON delta 可能只是部分字符串，需累计到 `content_block_stop` 再解析。

## 停止：控制感的核心

流式界面常需要停止、暂停或改方向的入口，但这些操作不是同一个语义，也不能仅凭按钮点击就宣称任务已终止。

三种错误：

**错误一：停止只是断开前端连接。** 这只能证明浏览器不再接收数据，不能证明应用任务、上游模型生成或计费已经结束。

**错误二：已生成内容被静默丢弃。** 用户等了 3 秒看到了一半内容，点停止后界面什么都没留下，却没有说明这些内容被丢弃了；即使产品因隐私或安全策略选择不保留，也应明确告知。

**错误三：停止的粒度太粗。** 整个任务被终止，而用户可能只是不想要某一句话。

更可靠的做法是定义清楚状态：收到请求后显示「正在停止」；只有宿主确认该运行已结束，才显示「已停止」。已生成文本是否保留由产品决定，但应标注它是部分结果。若无法确认上游是否停止，应显示「客户端已停止接收；上游状态待确认」，不能把连接关闭等同于取消成功。

把四个动作区分开：**停止生成**尝试结束当前模型调用；**取消任务**请求终止整个运行；**暂停**需要可持久化的检查点与恢复语义；**撤销副作用**则是另一个业务补偿流程。对已发出的邮件、付款或写入，取消任务不能承诺回滚。控制项应依据任务能力与风险呈现，并说明它实际能做到什么。

## 服务端取消到底要做什么

取消请求最容易被误判，因为它**跨越多个层次**，而每一层都要各自处理：

```text
层          要做的动作                                  能证明什么
HTTP 连接   发现断开，或收到经鉴权的取消请求            客户端连接状态
运行宿主     将取消传给任务、队列与当前步骤              应用运行是否结束
模型适配器   调用 SDK/HTTP 客户端的取消或关闭接口         本地响应是否关闭；上游效果需另核实
工具执行     阻止未派发动作；追踪已派发动作结果            副作用是否完成、未知或已补偿
```

**历史取消探测的证据边界。** 2026-10-12 的一次原始探测记录：原始 TCP 客户端第一次读取到 455 字节（其中可能包含 HTTP 头和响应片段），用时 0.09 秒后关闭 socket；另一次单独的完整请求耗时 20.38 秒、输出 2,951 token：

```text
客户端第一次读取：455 字节，用时 0.09s，随后关闭 socket
另一次完整请求：20.38s，输出 2,951 token
```

（历史记录，模型标识为 deepseek-flash，消息 API 直连，流式。没有可验证的 request id、原始响应 trace 或重复试验。）

**这两条记录不能证明原请求在断开后仍生成了 20 秒，也不能证明账单按完整输出结算。** 完整请求是另一轮运行，不是原请求的对照。探测只说明客户端较快关闭了本地 socket；上游是否停止、服务端继续多久、产生多少用量都未知。它因此是一个未能回答取消语义的探测，不是「断开后仍计费」的实测结论。

**所以取消要从宿主显式传下去，而不是把连接断开当作取消。** 取消令牌可协调本地任务，但每个阻塞调用还需要适配器调用真实的取消/关闭接口。下面代码演示本地协作式取消；它不验证远端生成或计费：

```python
"""服务端取消：取消令牌要传到模型调用与工具执行。

可运行 —— 它用一个本地的 FakeProvider 产生分片，所以不需要任何凭据。
换成真实端点时的接线见文末注释。

实跑状态：2026-10-12。
"""
import asyncio
import os
import time


class Cancelled(Exception):
    pass


class Token:
    """取消令牌：一个事件 + 一个理由。所有层都持有它。"""

    def __init__(self):
        self.event = asyncio.Event()
        self.reason = None

    def cancel(self, reason="用户点击停止"):
        if not self.event.is_set():
            self.reason = reason
            self.event.set()

    def check(self):
        if self.event.is_set():
            raise Cancelled(self.reason)


class FakeProvider:
    """本地假模型：按分片吐出，每片 5ms。真实实现换成你的 SDK 流式调用。"""

    FRAMES = 1200

    async def stream(self, token):
        for text in ("这是个很长的回答，", "它会被分成很多片，", "每一片都要检查取消令牌。"):
            for _ in range(self.FRAMES // 3):
                token.check()                       # ← 每收一片检查一次
                await asyncio.sleep(0.005)
                yield text


class FakeTool:
    """有副作用的工具。它**不可取消** —— 开始之后只能等它结束。"""

    async def run(self, token):
        if token.event.is_set():
            return None                              # 还没开始 → 直接不执行
        await asyncio.sleep(0.05)                    # 已经开始了
        return "mail_sent"


async def run_turn(provider, token, stop_after_ms):
    """跑一轮：到点取消，统计取消前实际生成了多少片。"""
    stats = {"frames": 0, "cancelled": False}

    async def stop_later():
        await asyncio.sleep(stop_after_ms / 1000)
        token.cancel()

    async def consume():
        try:
            async for _ in provider.stream(token):
                stats["frames"] += 1
        except Cancelled:
            stats["cancelled"] = True

    await asyncio.gather(stop_later(), consume())
    tool = await FakeTool().run(token)
    return stats, tool


async def main():
    provider = FakeProvider()
    token = Token()
    stats, tool = await run_turn(provider, token, stop_after_ms=100)
    print("  提示词要求的总分片数：%d" % provider.FRAMES)
    print("  客户端实际收到的分片：%d" % stats["frames"])
    print("  是否收到取消异常：%s" % ("是" if stats["cancelled"] else "否"))
    print("  取消理由：%s" % token.reason)
    print("  取消之后本地生成循环：%s"
          % ("已停止；此模拟器没有供应商账单" if stats["frames"] < provider.FRAMES
             else "仍在运行，把整个输出跑完了"))
    print("  工具这一层：%s"
          % ("没有执行（取消时它还没开始）" if tool is None else "已执行 " + str(tool)))

    # 再模拟一次：工具已越过派发边界后才收到取消。
    dispatched_token = Token()
    dispatched_task = asyncio.create_task(FakeTool().run(dispatched_token))
    await asyncio.sleep(0)  # 让工具先通过执行前检查并开始不可取消的副作用
    dispatched_token.cancel("副作用已派发后用户点击停止")
    dispatched_result = await dispatched_task
    print("  副作用已派发后收到取消：%s"
          % ("动作仍完成：" + str(dispatched_result) if dispatched_result else "没有成功结果"))


# 换成真实 Anthropic Python SDK 时，Provider 的异步文本流可以这样写：
#   async with client.messages.stream(...) as stream:
#       async for text in stream.text_stream:
#           yield text
# 宿主取消时还必须取消消费任务并退出 async with，让 SDK 关闭本地响应。
# token.check() 只有在控制流再次运行时才会执行，无法打断卡在网络读取中的 await。
# 具体 SDK/版本的取消接口与上游计费结果须单独验证；当前只实跑上面的 FakeProvider。
# 密钥的拿法见项目约定：本地放在 .env.local，或由部署平台注入环境变量。


if __name__ == "__main__":
    asyncio.run(main())
```

**这段代码里有两个要带走的东西。**

**一、取消信号必须一路传到底。** 在本地协作代码里，`token.check()` 能在循环重新获得控制权时停止后续步骤；若代码正等待网络 I/O，仅检查令牌不够，必须中断/关闭该调用。SDK 关闭本地响应不等于已证实供应商端生成和账单停止。

**二、工具层只能做"尽力而为"的取消。** 上面的 `FakeTool` 演示了两条分支：

- **还没开始的动作** → 不执行（这是"停止"能拦住的）
- **已经派发的副作用** → 结果可能成功、失败或未知；按第 3 节的恢复逻辑查询、幂等重试或人工对账（不能假定一定等它结束或可撤销）

**这个区别必须在接口与界面上写清楚**：排队动作可在执行前拦截；已派发动作须读取其真实状态，可能需要补偿或对账。界面文案应对应已确认的状态，例如「生成已结束」「取消请求已提交」或「动作结果待确认」，而不是笼统地说「已取消」。

## 流式里到底有哪些事件

上面提到按事件处理取消，先要确认协议边界。以下是 Claude Messages API 文档描述的事件形态；其他厂商协议与版本可能不同，客户端应容忍未知事件：

| 事件 | 带什么 | 该做什么 |
|---|---|---|
| `message_start` | 消息初始信息与用量 | 建立本次消息状态 |
| `content_block_start` / `content_block_delta` / `content_block_stop` | 内容块类型与增量；工具 JSON 可能是不完整片段 | 按 block index 累积；块结束后再完成解析与校验 |
| `message_delta` | 结束原因及累计用量增量 | 记录用量、解释协议结束原因 |
| `message_stop` | 消息流结束 | 收尾本次消息，不代表业务动作成功 |
| `ping` / `error` / 未知事件 | 心跳、流错误或未来扩展 | 按协议处理错误，对未知类型安全忽略或记录 |

Claude Messages API 的 `stop_reason` 是协议级结束原因，不是业务成功状态；例如 `end_turn`、`max_tokens` 与工具交接原因各有含义，具体枚举以所用 API 版本文档为准。`max_tokens` 表示达到本次输出预算，结果可能不完整；不应推断它必定为空。应用还要校验任务产物是否完整，并按供应商对应字段处理，不能把 Anthropic 字段名当成通用协议。

**SSE（Server-Sent Events）是事件流的一种传输方式**：服务端沿连接发送文本事件。标准 EventSource 支持重连，并可在事件带 `id` 时发送 `Last-Event-ID`；这不自动保证服务端保留或重放事件。要做到无重复、无遗漏，应用需定义稳定事件 ID、持久化/保留事件日志，并实现按游标补发与客户端去重。若使用 POST `fetch` 读取流，则重连行为通常由应用自行实现。停止或审批走何种控制通道取决于应用协议，不是 SSE 自动提供的能力。

## 一个反直觉的取舍：越流畅，越难打断

最后说一个和前面几节冲突的点。

第 3 节讲审批时要「停下来问人」，而流式的目标是「尽量流畅地输出」。这两件事在同一个界面里会冲突：

- 流式输出到一半，突然弹出一个审批框 —— 用户的第一反应是「我刚才在看的内容呢」
- 审批通过之后继续流式，但用户已经失去了上下文

处理方式取决于当前运行状态与授权边界：

**一、动作尚未派发时先审批。** 展示冻结的动作摘要与影响范围，用户批准后由宿主重新校验授权并执行。可以继续展示此前已生成且获准展示的内容，但不能让流式文本暗示动作已执行。

**二、执行中遇到审批或等待时明确分段。** 显示「已生成的内容」和「等待你确认的动作」两个状态；批准、拒绝或修改后由宿主决定能否继续。保留前文与否按产品需求处理，并明确部分结果可能不完整。

关键是**明确状态与授权边界** —— 让用户知道系统正在等什么、批准会触发什么，以及取消请求是否已确认生效。

## 如何验证控制面真的有效

先把状态机写出来，再测每个转移。一个可复用的最小模型如下：

```text
running --stop requested--> stopping --host confirms--> stopped
    |                           |                         |
    |                           +--timeout--------------> outcome_unknown
    +--tool dispatched----------------------------------> reconciling
paused --resume + policy check--------------------------> running
```

每条边都要有可观察事件：`stop_requested_at`、运行宿主确认的 `terminal_at`、供应商响应关闭状态、工具派发/结果与对账结论。敏感信息应脱敏；这些记录用于诊断状态转换，不代表已经获得供应商的计费事实。

故障注入至少验证三个不变量：

1. 客户端断开但宿主仍运行时，运行状态不能被误标成 `stopped`。
2. 收到取消时，如果读取正阻塞在网络 I/O，适配器取消路径应中断或关闭本地请求；测试结果只描述实际 SDK 与版本。
3. 工具请求已发送但响应丢失时，状态应为未知并进入幂等查询或人工对账，不得盲目重发高风险动作。

用户体验假设也要单独验证。若想知道进度信息是否减少用户取消，可做有对照的可用性测试或实验，并预先定义取消率、任务完成率、错误取消率与样本分层。单看停止率变化不能证明原因，更不能据此移除停止能力。

## 一个具体的交互细节：停止之后怎么办

点了停止之后，界面上该显示什么？三种做法，体验差别很大。

**做法一：清空。** 界面回到初始状态，什么都没留下。
问题是用户等了 3 秒看到的内容也没了。

**做法二：保留内容，但显示真实运行状态。** 若宿主已确认结束，可标注「生成已停止，以下为部分结果」；若只是断开客户端，应标注「停止请求已提交」或「上游状态待确认」。

**做法三：保留内容，并给出"继续"入口。** 用户能从中断处继续。
功能最强，但实现上要处理"继续时的上下文"问题（第 3 节那套状态持久化），复杂度最高。

是否保存部分结果取决于任务、隐私与恢复要求；这个体验选择不等同于持久化任务恢复。若要「继续」，还要定义检查点、上下文、权限复核与幂等边界。

做法三只在特定场景值得做：长任务（跑了几分钟）、且中间结果不能单独使用。

## 验证停止原因的产品假设

一种待验证的假设是：部分用户停止，是因为无法判断还需等待多久；也有人确实不再需要结果、发现方向错误或担心动作风险。仅凭点击事件无法区分这些原因。

这个区别很重要，因为它指向完全不同的两种改进：

- 如果真的是不要结果 → 优化停止（当前话题）
- 如果不确定要多久 → **优化进度提示**（第 4 节）

可以通过非诱导式的可选反馈、任务完成率与错误取消率，结合有对照的进度提示实验来检验。即使停止率下降，也只能说明该实验条件下出现关联；不能据此移除停止能力或推断所有用户的动机。
## 完整可运行代码

下面代码用本地合成事件展示两种处理路径：获准显示的 `text_delta` 到达后即可呈现；工具参数分片按索引累计，直到块结束才解析，并在基础字段检查后交给宿主做权限校验。它不展示模型 thinking，也不代表供应商原始事件的完整实现。

```python
"""合成事件流：文本增量即时呈现，工具 JSON 完整后才校验和执行。纯本地演示。"""
import json
from collections import defaultdict

EVENTS = [
    {"type": "text_delta", "text": "我先核对订单状态。"},
    {"type": "tool_json_delta", "index": 0, "text": '{"tool":"lookup",'},
    {"type": "tool_json_delta", "index": 0, "text": '"order_id":"A-1001"}'},
    {"type": "tool_block_stop", "index": 0},
]


def consume(events):
    visible_text = []
    tool_buffers = defaultdict(str)
    ready_tools = []
    for event in events:
        if event["type"] == "text_delta":
            visible_text.append(event["text"])
            print("展示获准文本：%s" % event["text"])
        elif event["type"] == "tool_json_delta":
            tool_buffers[event["index"]] += event["text"]
        elif event["type"] == "tool_block_stop":
            index = event["index"]
            args = json.loads(tool_buffers[index])
            if args.get("tool") != "lookup" or not args.get("order_id"):
                raise ValueError("工具参数校验失败")
            # 生产系统还需由宿主检查身份、授权、对象范围与业务状态。
            ready_tools.append(args)
    return "".join(visible_text), ready_tools


if __name__ == "__main__":
    text, tools = consume(EVENTS)
    print("最终可见文本：%s" % text)
    print("完整并通过基础字段检查的工具参数：%s" % json.dumps(tools, ensure_ascii=False))
    print("注意：基础字段检查不是授权；工具执行由宿主策略决定。")
```

## 常见坑

- **以为流式必然减少总时间。** 本节的历史记录没有配对非流式对照，不能从它推断总时长差异。
- **把结构化输出的每个流式分片都当成完整 JSON。** 中间片段通常尚未构成完整 JSON；应先缓冲到对应内容块结束，再解析、校验与授权。
- **把断开连接当成停止成功。** 它不能证明后端任务、上游生成或计费状态。
- **静默丢弃已生成内容。** 按任务、隐私与安全策略决定是否保留；若丢弃，应说明原因；若保留，应标明这是部分结果。
- **审批框打断流式却不解释。** 用户会以为卡住了 —— 要明确说是「等待确认」。
- **在入口检查一次取消就以为停了。** 对阻塞中的网络调用还需调用客户端取消/关闭接口；本地检查不能证明供应商端停止。
- **把"已停止"和"已撤销"混为一谈。** 已派发副作用可能成功、失败或未知，应对账或补偿。
- **认为 SSE 自动重放。** 标准支持游标机制，但应用仍需保存事件并实现重放与去重。

## 这一层会怎么坏

三类故障都可能不直接抛程序错误，但影响与发现方式不同；取消未传到底还可能带来额外生成或费用，需用宿主和上游证据确认：

| 坏法 | 现象 | 怎么发现 |
|---|---|---|
| **取消没传到底** | 界面一秒内安静了，账单按完整输出结 | 断开之后看服务端日志：那条请求是什么时候真正结束的 |
| **静默丢弃已生成内容** | 用户等了 3 秒点停止，界面空了且没有说明 | 按产品保留策略检查停止后的内容与提示是否一致 |
| **审批框打断流式却不解释** | 用户以为卡住了，于是点停止或刷新 | 让一个任务在中途需要审批，走一遍完整交互 |

第一条的判据是宿主状态与上游适配器证据，而不是浏览器何时停止显示。要测取消效果，应为同一原始请求关联 request ID，采集取消时间、宿主终态、SDK 关闭结果、供应商可提供的终态/用量，并以重复试验报告限制。当前历史探测缺少这些证据，因此结论仍是未知。
