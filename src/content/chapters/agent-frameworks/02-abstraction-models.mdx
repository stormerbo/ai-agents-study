第 11 章末尾提到过三种抽象模型。这一节把它们讲清楚，因为**选框架本质上就是选一种抽象模型** —— 而抽象模型决定了你能表达什么、不能表达什么。

## 模型一：链（chain）

把调用串成一条线，上一步的输出是下一步的输入。

```python
chain = prompt | model | parser
result = chain.invoke({"question": "..."})
```

它表达的是**线性流程**。控制流完全由你写的顺序决定，模型不参与决定下一步。

优点非常明确：**可预测、可测试、可在编译期检查。** 你知道它一定会按这个顺序执行，而且每一步的类型是确定的。

缺点是它表达不了循环和分支 —— 因为它就是一条线。而这正是第 10 章讲的 workflow：流程固定时它最省、最可靠。

## 模型二：图（graph）

节点是步骤，边是转移。条件边（路由器）让你表达分支和循环。

```python
graph.add_node("search", search_fn)
graph.add_node("summarize", summarize_fn)
graph.add_conditional_edges("search", should_continue,
                            {"yes": "search", "no": "summarize"})
```

它比链多两个关键能力：

**一是循环和分支。** 上面那个 `should_continue` 就是一个路由器 —— 它让图可以「继续 search 直到满足条件」。

**二是执行位置是一个值。** 「现在在哪个节点」是可以序列化的，所以断点恢复变得自然：存下节点名和状态，下次从那里继续。第 11 章第 4 节讲的状态持久化，在图抽象里是内建的。

而第 11 章的实测也揭示了它的真相：**要表达循环，图的边必须是一个函数。** 静态的 `next` 字符串做不到 —— 所以抽象并没有消除条件判断，只是把它从 `while` 挪到了路由函数里。

## 模型三：自主 agent（autonomous）

你给一个目标和一组工具，模型自己决定走多少步、调什么工具。第 10 章讲的 ReAct 就是它。

```python
agent = create_react_agent(model, tools)
result = agent.invoke({"messages": [("user", task)]})
```

它的控制流在模型手里，所以**最灵活、也最不可预测**。你需要为它补上第 11 章那些闸门（预算、熔断、幂等），因为它自己不会停。

## 三者的关系不是「逐级进化」

一个常见的误解是：链到图再到自主 agent，越来越强。实际上它们是**控制权逐步从你手里转移到模型手里**：

| 模型 | 谁决定下一步 | 适合 | 表达不了 |
|---|---|---|---|
| 链 | 你（写死的顺序） | 流程固定 | 分支、循环 |
| 图 | 你（路由器函数） | 流程会变，但分支条件可枚举 | 模型自主决策 |
| 自主 agent | 模型 | 任务形状事先不知道 | 你可控的成本上限 |

**注意最后一列。** 越往下，你越难给行为下保证 —— 这不是缺点，是那个抽象的定义。选它就意味着接受这一点，并用手写的那一层（闸门）把保证补回来。

## 一个混合的实际做法

真实系统里很少只用一种。一个常见且有效的组合是：

**外层用图，节点内部用链，只有需要判断的那个节点用自主 agent。**

这样做的收益可以直接算：图的节点边界是可序列化的（断点恢复、可观测），链是可预测的（成本固定），而自主只在真正需要它的地方出现（一次判断）。第 10 章第 5 节那条「把分支留在代码里、线性段交给便宜的执行方式」，说的就是这件事的另一种表述。

## 一个判断抽象是否合适的测试

拿你最复杂的那条业务分支，试着用目标抽象表达出来。三个结果：

- **能直接表达** → 抽象合适
- **需要绕开抽象**（比如在节点内部塞一个 if、或者用回调钩子） → 这就是第 3 节要讲的泄漏
- **完全表达不了** → 抽象选错了

这个测试要**在选框架之前做**，因为它只需要你在纸上画一遍，而代价是选错之后的一次重写。

## 完整可运行代码

下面这段代码用真框架演示「装饰器生成的 schema 里有什么、没有什么」—— 那是判断一个抽象边界最直接的方式：**把它生成的东西原样打印出来看。**

```python
"""真框架对照：同一个任务，手写循环 vs LangChain。

不是性能对比 —— 比的是三件事：
  1. 代码量
  2. 你能看见什么、看不见什么
  3. 想加一个需求时，需要在哪里「逃出抽象」

实跑状态：2026-10-09，langchain 0.3.7 + deepseek-flash（Anthropic 兼容端点）。
"""
import os, json, time

print("langchain 版本：", end="")
import langchain
print(langchain.__version__)

from langchain_core.tools import tool as lc_tool
from langchain_anthropic import ChatAnthropic

TEMP = {("北京", "明天"): 31, ("上海", "明天"): 27, ("广州", "明天"): 34}

# ---- 手写版的工具定义：schema 与实现分开写 ----
HAND_TOOLS = [{
    "name": "get_weather",
    "description": "查询某个城市某一天的最高气温（摄氏度）。",
    "input_schema": {"type": "object",
                     "properties": {"city": {"type": "string"},
                                    "day": {"type": "string", "enum": ["明天", "后天"]}},
                     "required": ["city", "day"]},
}]


def hand_get_weather(city, day):
    return TEMP.get((city, day), {"error": "没有数据"})


# ---- 框架版的工具定义：一个装饰器，schema 从类型注解推断 ----
@lc_tool
def get_weather(city: str, day: str) -> dict:
    """查询某个城市某一天的最高气温（摄氏度）。

    Args:
        city: 城市名
        day: 只支持「明天」或「后天」
    """
    return TEMP.get((city, day), {"error": "没有数据"})


if __name__ == "__main__":
    print()
    print("=== 1. 代码量 ===")
    print("手写版工具定义：%d 行（schema 手写）" % len(json.dumps(HAND_TOOLS, ensure_ascii=False).split(chr(10))))
    print("框架版工具定义：6 行（一个装饰器 + 文档字符串）")
    print("→ 框架在「schema 生成」这一层确实省事")
    print()

    print("=== 2. schema 长什么样（框架替你生成了什么）===")
    print(json.dumps(get_weather.args_schema.model_json_schema(), ensure_ascii=False, indent=1)[:600])
    print()

    print("=== 3. 一个抽象泄漏的现场 ===")
    print("题目：它的 input_schema 里有没有 enum 约束？")
    schema = get_weather.args_schema.model_json_schema()
    print("day 的定义：", json.dumps(schema["properties"].get("day"), ensure_ascii=False))
    if "enum" not in json.dumps(schema["properties"].get("day", {})):
        print("→ ❌ 没有 enum。文档字符串里写了「只支持明天或后天」，")
        print("   但生成的 schema 只有 type: string。")
        print("   而第 4 章实测过：enum 约束下模型 3/3 合法，自由字符串 0/3。")
        print("   要拿到 enum，必须逃出装饰器，改用 pydantic 的 Literal 或手动写 schema。")
    print()
    print("结论：抽象替你生成了「能用的」schema，但没有生成「最好的」schema。")
    print("      而第 4 章的实测说明这两者的差别是 0/3 和 3/3。")


# ==== 4. 逃出抽象：用 Literal 把 enum 找回来 ====
print()
print("=== 4. 逃出抽象之后 ===")
from typing import Literal


@lc_tool
def get_weather_v2(city: str, day: Literal["明天", "后天"]) -> dict:
    """查询某个城市某一天的最高气温（摄氏度）。

    Args:
        city: 城市名
        day: 明天或后天
    """
    return TEMP.get((city, day), {"error": "没有数据"})


schema2 = get_weather_v2.args_schema.model_json_schema()
print("day 的定义：", json.dumps(schema2["properties"].get("day"), ensure_ascii=False))
has_enum = "enum" in json.dumps(schema2["properties"].get("day", {}))
print("现在有 enum 了：%s" % ("✅ 是" if has_enum else "❌ 否"))
print()
print("代价：这已经不是在写「普通的 Python 函数」了 —— 类型注解从 str 变成了 Literal，")
print("      而 Literal 是为「生成 schema」这个目的服务的。这就是**抽象泄漏**：")
print("      为了拿到想要的效果，你必须了解抽象内部是怎么把注解翻译成 schema 的。")
```


## 三种抽象对应的代码形态

把三种抽象写成代码，形状的差别会一目了然。

**链**：控制流是一串管道，读起来就是「先做这个、再做那个」。

**图**：控制流是一张声明式的表，节点和边分开写。它更像配置，不像代码。

**自主 agent**：控制流是隐藏的 —— 你只写了「给它一个目标」，循环在框架内部。

**这个差别带来一个实际问题：可调试性。** 链和图里，你能在读代码时说出「接下来会发生什么」；自主 agent 里你不能，你只能看运行时的轨迹。所以第 11 章讲的轨迹记录，在自主 agent 上是必需品，在链上则是可选。

## 选择时的两个常见误判

**误判一：把链当成「不够强」的选项。** 实际上在流程固定的任务上，链是最优选 —— 它最便宜、最可测、最不容易出意外。第 10 章第 5 节量过这个方向：静态计划在线性任务上 506 token，比 ReAct 的 1,203 便宜一半多。

**误判二：以为图能解决所有复杂流程。** 图的表达力上限是「你能否枚举出所有分支条件」。如果分支条件本身需要模型来判断，那这个判断仍然要交给一个自主 agent 节点 —— 图只是把它的位置固定下来，没有替代它。

## 抽象模型和成本的关系

选抽象还直接影响成本结构，这一点容易被忽略。

**链的成本是确定的。** 因为调用次数固定，你可以精确算出每次运行花多少 token。这对需要预算控制的生产系统很重要 —— 你能给出一个准确的单次成本上界。

**图的成本是半确定的。** 节点数固定，但循环的次数不确定（取决于路由器什么时候返回「结束」）。所以成本有上界吗？有 —— 只要你给循环加一个次数上限（第 11 章第 3 节那道闸门）。**图的成本可控，前提是你主动加那个上限。**

**自主 agent 的成本是不确定的。** 步数由模型决定，所以没有天然的界。第 9 章实测过这种不确定性的代价：同一个任务，成功时 5,000 token，卡住时 27,000 —— 5 倍以上。

所以从成本可控性看：链 > 图 > 自主 agent，和前面那张表达力的表正好相反。**这又回到同一个结论：越灵活的抽象，越需要你自己把保证补回来。**


## 一个抽象模型的选择顺序

最后给一个可执行的顺序。不要先看框架，先看你的流程：

**第一步，把流程画出来。** 如果画出来是一条直线，那就是链 —— 而且这时候你多半不需要框架，两个函数就够了。

**第二步，看有没有回到前面的箭头。** 有循环或分支，就需要图（或自己写的状态机）。这时候路由器函数是你要写的东西。

**第三步，看分支条件能不能枚举。** 如果不能（比如「判断这段代码有没有安全问题」），那这个节点必须是自主 agent。

三步走完，你的架构就是「链/图/自主」的一个组合，而不是「选一个框架」。**框架只是实现这个组合的工具** —— 而这个组合，你在纸上就定下来了。
## 常见坑

- **把三种抽象当成「逐级进化」。** 它们是控制权的分配方式，各有表达不了的东西。
- **以为图抽象消除了条件判断。** 第 11 章实测过：表达循环必须靠路由器函数，条件只是换了位置。
- **用链去表达需要循环的流程。** 它表达不了 —— 你会被迫写一个假的循环，而那比直接用图更糟。
- **用自主 agent 却指望确定性。** 那是抽象本身的定义，不是实现缺陷。
- **在选框架之前不做表达测试。** 拿最复杂的分支先画一遍，只需要十分钟，能省一次重写。
