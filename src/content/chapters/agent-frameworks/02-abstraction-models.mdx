第 11 章末尾提到过几种控制流形状。本节用线性序列、图和 agent loop 三个教学模型帮助比较；**选框架不只是在选抽象**，还要看持久化、权限、可观测性、部署和团队维护等取舍。

## 模型一：链（chain）

这里的「链」特指**线性序列**：上一步输出作为下一步输入，顺序预先写定。不同框架会把多个组合原语都叫 chain；不要把这个教学分类当成所有框架的完整能力清单。

```python
# 形状示意：说明线性组合，不是可独立运行的程序
chain = prompt | model | parser
result = chain.invoke({"question": "..."})
```

线性序列让执行顺序直观、便于逐步测试。它本身不会替你做动态路由；但这不代表框架中的所有 Runnable 都不能分支。以 LangChain 为例，`RunnableSequence` 表示顺序组合，另有 `RunnableBranch` 进行条件路由。Python 运行时也不会因为使用管道符就自动完成通用的编译期类型检查；仍需验证输入输出契约和运行结果。

如果流程固定，线性序列往往比引入更复杂的编排更容易理解。是否更可靠或更便宜，取决于具体调用路径、实现和约束，不能仅由「链」这个名字推出。

## 模型二：图（graph）

图用节点表示工作步骤，用边表示后继关系。固定边表示固定转移，条件边则根据当前状态或计算结果选择后继；条件判断可以是普通代码，也可以使用模型的输出。

```python
# LangGraph 形状示意：展示条件边；缺少 StateGraph 定义与编译步骤
graph.add_node("search", search_fn)
graph.add_node("summarize", summarize_fn)
graph.add_conditional_edges(
    "search",
    should_continue,
    {"yes": "search", "no": "summarize"},
)
```

图能显式表达分支与循环，但路由条件仍由应用提供。LangGraph 的图需要定义 state、nodes 和 edges 并调用 `compile()`；编译会检查部分图结构问题，不等于一般意义上的静态类型证明。

LangGraph 还支持检查点恢复，但前提是运行图时配置适当的 checkpointer，并以稳定的 `thread_id` 标识线程。跨线程保存的应用数据属于 store 的用途。内存 checkpointer 不会跨进程重启保留数据；检查点也不为外部副作用提供 exactly-once。节点可能重放，幂等和业务状态仍需应用设计与测试。

## 模型三：自主 agent（autonomous）

在这里，「自主 agent」指一种运行方式：模型输出会参与下一步行动的选择，host/runtime 负责解释这些输出并执行被允许的工具调用。具体循环、handoff、停止条件和安全边界取决于所用 SDK 与应用，不是所有 agent 都以同一种方式运行。

```python
# 形状示意：具体工厂函数、消息格式与停止语义取决于 SDK 版本
agent = create_react_agent(model, tools)
result = agent.invoke({"messages": [("user", task)]})
```

模型参与决策会增加运行路径的不确定性，但不等于「模型拥有执行权」或「系统不会停」。实际执行仍由 host/runtime 控制；turn、工具、token、时间和费用上限需要分别确认并按应用需求配置。

## 三者的关系不是「逐级进化」

一个常见的误解是：链到图再到自主 agent，越来越强。本文用这些术语讨论控制流如何组织，以及模型决策放在哪里；它们不是互斥的实现类别，也不是能力等级：

| 教学模型 | 主要由谁表达转移 | 典型用途 | 需要留意 |
|---|---|---|---|
| 线性序列 | 应用预先写定顺序 | 步骤固定的流程 | 动态路由应显式交给分支/图等原语 |
| 图 / 状态机 | 应用定义节点与路由；节点内部也可调用模型 | 可见分支、循环、暂停与状态管理 | 需要设计状态、路由、持久化和恢复 |
| agent loop | 模型输出参与选择下一步，host/runtime 执行与约束 | 任务路径不能完全预先列举 | 需评估模型决策、循环限制、工具权限与失败恢复 |

这是一种便于讨论控制流的分类，不是能力等级。框架可以组合这些做法；例如图节点中可以调用 agent loop，agent loop 也可以被固定流程包围。

## 一个混合的实际做法

系统可以组合多种控制流形状；一种可评估的组合方式是：

**可以考虑外层显式编排、节点内部执行线性步骤，只在部分节点调用模型决策。**

组合让每层承担不同职责，但效果取决于具体实现：图状态能否序列化和恢复取决于框架支持、状态设计与持久化配置；这不会自动让任意节点边界都可恢复。成本和可观测性也要按目标运行时与部署验证。

## 一个判断抽象是否合适的测试

选型前可以拿一条有代表性的业务路径做表达测试：把步骤、状态、分支判断、失败恢复和人工介入点画出来，再用候选抽象尝试实现关键路径。

- **核心路径能直接表达**：记录实现与测试成本，继续检查边界条件。
- **需要回调或在节点里补分支**：确认这是有意的组合，还是框架抽象正在妨碍需求。
- **无法表达或恢复语义不清**：对照文档和最小原型，评估其他抽象或自建控制层。

这只是选型证据之一。还要核对可观测性、持久化、权限、团队维护成本和部署约束；一次纸面练习不能证明未来不会迁移。

## 三种抽象的可运行对照

下面的离线 fixture 用同一组纯函数，分别表达固定线性序列、LangGraph 条件路由，以及一个由脚本策略控制的循环骨架。三者打印相同轨迹，只验证这组 fixture 的状态转移与代码执行；第三种**不是模型驱动的 agent，也不验证模型自主决策**。版本与实跑结果仅覆盖标注的本地环境（2026-10-12）。

```python
"""三个执行形状的离线 fixture：线性序列 / 图 / 脚本策略循环。

本例只比较控制流写在哪里；第三种不是自主 agent 实验，也不调用模型。
安装：`python -m pip install 'langgraph==1.2.14' 'langchain-core==1.6.12'`。
实跑状态：本轮验证（2026-10-21）；原记录日期：2026-10-12；Python 3.10.9、langgraph 1.2.14、langchain-core 1.6.12；仅离线 fixture。
"""
from typing import TypedDict

from langchain_core.runnables import RunnableLambda
from langgraph.graph import StateGraph, START, END


class State(TypedDict):
    pending: list
    trace: list


def search(state):
    return {"pending": [1, 2], "trace": state["trace"] + ["search"]}


def fetch(state):
    return {"pending": state["pending"][1:], "trace": state["trace"] + ["fetch"]}


def summarize(state):
    return {"trace": state["trace"] + ["summarize"]}


# ---- 线性序列：本例的顺序固定 ----
def chain():
    return (RunnableLambda(search)
            | RunnableLambda(fetch)
            | RunnableLambda(fetch)
            | RunnableLambda(summarize))


# ---- 图：控制流是节点表 + 路由函数 ----
def after_fetch(state):
    return "fetch" if state["pending"] else "summarize"


def graph():
    b = StateGraph(State)
    b.add_node("search", search)
    b.add_node("fetch", fetch)
    b.add_node("summarize", summarize)
    b.add_edge(START, "search")
    b.add_edge("search", "fetch")
    b.add_conditional_edges("fetch", after_fetch, {"fetch": "fetch", "summarize": "summarize"})
    b.add_edge("summarize", END)
    return b.compile()


# ---- agent-like 控制骨架：脚本化策略替身，不调用模型 ----
def scripted_policy(state):
    return "fetch" if state["pending"] else "summarize"


def autonomous_control_fixture():
    state = search({"pending": [], "trace": []})
    while True:
        action = scripted_policy(state)
        if action == "fetch":
            state = fetch(state)
        elif action == "summarize":
            return summarize(state)
        else:
            raise ValueError("unknown scripted action")


if __name__ == "__main__":
    print("链：  ", chain().invoke({"pending": [], "trace": []})["trace"])
    print("图：  ", graph().invoke({"pending": [], "trace": []})["trace"])
    print("脚本策略骨架：", autonomous_control_fixture()["trace"])
```

实跑输出：

```text
链：   ['search', 'fetch', 'fetch', 'summarize']
图：   ['search', 'fetch', 'fetch', 'summarize']
脚本策略骨架： ['search', 'fetch', 'fetch', 'summarize']
```

三份实现和它们的控制流位置：

| 示例 | 控制流在哪 | 本例能说明什么 |
|---|---|---|
| 线性序列 | 管道里的固定顺序 | 顺序由代码预先写定 |
| 图 | `after_fetch` 路由函数 | 路由条件由程序根据状态计算 |
| 脚本策略骨架 | `scripted_policy` 与循环 | 控制决策可以放在循环中；本例没有模型调用 |

**和第 11 章手写循环的关系：** 线性序列把下一步写在管道顺序里；图由 `after_fetch` 返回节点名；循环骨架则从 scripted policy 读取动作。这些是状态转移形状的对照，不等同于 LangGraph 的所有执行语义，也不代表策略来自模型。

在这个固定任务里，线性序列需要重复写两次 `RunnableLambda(fetch)`。如果次数运行时才确定，应选择能表达运行时路由/循环的控制结构；LangChain 的线性 `RunnableSequence` 不是其全部原语。

## 一个需要单独验证的边界

本节讨论控制流抽象，不评估框架生成的工具 schema 是否符合业务约束。装饰器如何生成 schema、类型注解的限制与本地校验示例，见[结构化输出：为什么“请在 prompt 里写清楚要 JSON”不够](/chapters/structured-output/why-not-prompt-only)；两类证据不要混为一谈。

## 三种抽象对应的代码形态

线性序列把执行顺序写在组合表达式中；图把节点和边分开声明；agent loop 则允许模型输出参与运行时的下一步选择。具体可见性、调试能力与轨迹内容因框架和配置而异，需检查实际运行时，不宜用「必需」或「可选」一概而论。

## 选择时的两个常见误判

**误判一：把链当成「不够强」的选项。** 固定流程可以用简单线性组合表达；是否选框架应看维护、测试、运行与部署要求，不存在对所有任务都最优的抽象。

旧版曾引用第 10 章的 506 与 1,203 token 对照，原始逐次轨迹、模型快照和评分器不在当前仓库，无法独立复核。它只能作为未验证的历史记录，不能证明线性计划普遍更便宜或更好。

**误判二：以为图只能包含枚举好的非模型分支。** 图节点本身可以调用模型，路由也可以根据节点结果选择后继；要评估的是决策在哪一层作出、如何约束和测试，而不是把「图」和「模型决策」视为互斥选项。

## 抽象模型和成本的关系

抽象会影响调用路径，但**抽象名称本身不能决定实际费用**。若线性流程中的模型调用次数固定，通常更容易估算请求次数；每次输入与输出 token 仍会变化，工具、重试、缓存和 endpoint 计费也会改变总成本，因此固定调用次数不等于准确的费用上界。

图中的循环和 fan-out 应有明确限制。LangGraph 的递归步数限制约束图执行步数；OpenAI Agents SDK 的 `max_turns` 约束 runner 的 agent turn。它们不是美元上限，也不自动限制工具内部计算、单次输出 token 或外部副作用。若需要硬预算，应在应用层分别计量并限制模型调用、输入/输出 token、工具资源、重试和墙钟时间，并为拒绝继续的路径定义行为。

自主 agent 也可以加 turn、token、时间和费用限制；这些限制是否覆盖嵌套 agent、工具调用、并行工作和重试，需要核对目标 SDK 与应用实现。不能只凭「步数由模型选择」判断它没有成本上界。

本节旧版引用的「成功 5,000 token、卡住 27,000 token」缺少逐次 trace、准确运行条件与评分器，当前无法独立复算；这是不可复核的历史摘要，不是自主 agent 的一般成本规律。比较抽象时，应在同一任务集、质量门槛、模型/provider、工具与重试策略下，记录实际 usage、费用和完成状态。

## 一个抽象模型的选择顺序

先问系统需要什么控制与恢复语义，再选实现方式；不要把流程形状机械映射成某一种框架：

1. **标出决策点和执行者。** 哪些转移是确定规则，哪些依赖模型判断？模型可以在图节点内参与决策；host/runtime 才负责执行和授权。
2. **标出状态与恢复要求。** 需要跨请求或进程恢复什么？谁提供持久化存储？节点重放时怎样避免重复副作用？
3. **写出端到端预算。** 分别约束模型调用、token、工具工作、重试、并行度、时间和费用，并确定超限后的安全行为。
4. **用目标版本做最小原型。** 验证关键路径、失败路径、trace 可见性、持久化和权限边界；再把维护与迁移成本纳入选择。

最终架构可以由多种抽象组合。选择标准是它是否清晰表达了所需控制流，并且能在目标运行环境中满足状态、失败、安全和预算要求；不由「直线/分支/未知任务」单一特征决定。

## 常见坑

- **把三种抽象当成逐级进化。** 它们是控制流与决策职责的不同组织方式，可以组合。
- **把线性序列等同于框架的全部表达能力。** LangChain 有 `RunnableBranch` 等其他原语；本节的「链」只指线性序列。
- **以为图自动提供持久化或 exactly-once。** 检查点需要配置；外部副作用的幂等、事务和恢复仍需应用负责。
- **把自主 agent 等同于没有上限。** SDK/runtime 与应用可以施加不同限制，但必须逐一确认限制范围。
- **把单个历史 token 数字当成抽象的普遍排序。** 没有原始 trace 与可重算 scorer 的数据只能保留为不可复核的历史观察。
- **把示意代码或脚本策略 fixture 当成真实 agent 实验。** 先说明测试对象，再解释输出能支持什么结论。
