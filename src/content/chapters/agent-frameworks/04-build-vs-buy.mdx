前面三节都在讲框架的边界。这一节把反方的立场完整讲一遍 —— 不是因为它一定对，而是因为**你需要听过最强的反对意见，才能做出真的选择。**

这个立场的代表作是一份叫「12-Factor Agents」的清单，它的核心主张可以用一句话概括：

**好的 agent 应该是你可以自己写出来的普通软件，而不是一个藏在框架里的黑箱。**

## 那份清单说了什么

它的十二条里有几条直接针对框架抽象：

**「拥有你自己的控制流」。** 不要让框架决定循环怎么走。你写的循环就是一个 while，你可以加断点、加日志、加任意判断 —— 而在框架里，这些东西要么没有，要么要绕开它。

**「拥有你自己的提示词」。** 提示词是第 2 章讲的工程对象，它应该在你的代码里、可以被版本管理、可以被 diff。如果它藏在框架的模板里，你就没法迭代它。

**「把 agent 当作普通软件」。** 状态、错误处理、重试、可观测性 —— 这些在普通服务里已经有一套成熟做法。agent 不该因为「有模型参与」就放弃这些，或者把它们交给第三方。

**「小步、可组合、无隐藏状态」。** 每个步骤应该是可单独测试的纯函数。这一点和第 11 章讲「骨架层用假模型测」是同一个思路。

## 这个立场的实证支持

这一章和第 11 章的实测，其实都在给这个立场提供证据：

**证据一：需求清单不长。** 第 11 章把「一个能用的循环」拆成了四块（消息搬运、工具注册表、停止判据、状态持久化），加起来两三百行。**这不是一个需要框架才能完成的规模。**

**证据二：关键的东西框架往往不提供。** 循环检测、幂等、错误分层、断点恢复的语义 —— 第 3 节列的三类泄漏，恰好都在这些地方。也就是说：**框架替你省下的（schema 生成），和你真正需要的（可靠的边界），重合度不高。**

**证据三：抽象会在你最需要精确的地方变粗。** 那个 enum 的例子很典型：框架生成「能用」的 schema，但你想要「最好」的 schema 时得绕开它。而第 4 章实测过，这两者的差距是 0/3 对 3/3。

## 但这个立场也有它的问题

诚实地说，反方立场有三个薄弱处：

**第一，它低估了维护成本。** 自己写意味着自己维护：模型 API 变了要跟、新的工具协议（比如第 14 章的 MCP）要接、并发和重试的坑要自己趟。框架把这些的跟进成本摊到了社区上。

**第二，它假设你有能力判断。** 「拥有自己的控制流」的前提是你知道好的控制流长什么样。第 11 章之所以先手写一遍，就是在补这个能力 —— 但并不是每个团队都有这个时间。

**第三，它在工具很多时成本上升。** 3 个工具时手写 schema 很轻松；30 个工具时，手写 schema 会变成一件容易出错、很难维护的事，而框架的装饰器在这里优势明显。

## 一个折中的实际做法

两边各取一半，落到具体做法上是：

**自己拥有控制流、提示词、状态和闸门；框架只用来做工具接入和可观测性。**

这个划分的理由是：**控制流和状态是你系统的核心逻辑，也是泄漏最集中的地方；而工具接入和可观测性是通用问题，框架做得比你好，且不涉及你的业务判断。**

具体到代码上，就是第 11 章那个手写循环，加上框架的工具装饰器和追踪回调。这样你既有第 11 章那些闸门，又不用手写 30 份 schema。

## 怎么用这一节

不要把它当成「该不该用框架」的答案 —— 它是一套**评估的框架**（这个词在这里有点双关）。

实际用法是：把这十二条里的每一条，对照你正在考虑的方案问一遍：

- 「控制流在谁手里？」→ 如果答案不是你，再问「这要紧吗」
- 「提示词在哪？」→ 如果不在你的代码库里，再问「我以后怎么迭代它」
- 「状态是什么形状？」→ 如果是框架的内部对象，再问「我以后怎么迁移」

三个问题的答案会告诉你：**这份依赖是有意识的取舍，还是默认接受了。** 前者没问题，后者是这一章要防的。

## 完整可运行代码

下面这段代码用真实框架演示「它生成的东西长什么样」—— 这是执行 12-Factor 里「不要有隐藏状态」那条的最低成本做法：把隐藏的东西打印出来。

```python
"""真框架对照：同一个任务，手写循环 vs LangChain。

不是性能对比 —— 比的是三件事：
  1. 代码量
  2. 你能看见什么、看不见什么
  3. 想加一个需求时，需要在哪里「逃出抽象」

实跑状态：2026-10-09，langchain 0.3.7 + deepseek-flash（Anthropic 兼容端点）。
"""
import os, json, time

print("langchain 版本：", end="")
import langchain
print(langchain.__version__)

from langchain_core.tools import tool as lc_tool
from langchain_anthropic import ChatAnthropic

TEMP = {("北京", "明天"): 31, ("上海", "明天"): 27, ("广州", "明天"): 34}

# ---- 手写版的工具定义：schema 与实现分开写 ----
HAND_TOOLS = [{
    "name": "get_weather",
    "description": "查询某个城市某一天的最高气温（摄氏度）。",
    "input_schema": {"type": "object",
                     "properties": {"city": {"type": "string"},
                                    "day": {"type": "string", "enum": ["明天", "后天"]}},
                     "required": ["city", "day"]},
}]


def hand_get_weather(city, day):
    return TEMP.get((city, day), {"error": "没有数据"})


# ---- 框架版的工具定义：一个装饰器，schema 从类型注解推断 ----
@lc_tool
def get_weather(city: str, day: str) -> dict:
    """查询某个城市某一天的最高气温（摄氏度）。

    Args:
        city: 城市名
        day: 只支持「明天」或「后天」
    """
    return TEMP.get((city, day), {"error": "没有数据"})


if __name__ == "__main__":
    print()
    print("=== 1. 代码量 ===")
    print("手写版工具定义：%d 行（schema 手写）" % len(json.dumps(HAND_TOOLS, ensure_ascii=False).split(chr(10))))
    print("框架版工具定义：6 行（一个装饰器 + 文档字符串）")
    print("→ 框架在「schema 生成」这一层确实省事")
    print()

    print("=== 2. schema 长什么样（框架替你生成了什么）===")
    print(json.dumps(get_weather.args_schema.model_json_schema(), ensure_ascii=False, indent=1)[:600])
    print()

    print("=== 3. 一个抽象泄漏的现场 ===")
    print("题目：它的 input_schema 里有没有 enum 约束？")
    schema = get_weather.args_schema.model_json_schema()
    print("day 的定义：", json.dumps(schema["properties"].get("day"), ensure_ascii=False))
    if "enum" not in json.dumps(schema["properties"].get("day", {})):
        print("→ ❌ 没有 enum。文档字符串里写了「只支持明天或后天」，")
        print("   但生成的 schema 只有 type: string。")
        print("   而第 4 章实测过：enum 约束下模型 3/3 合法，自由字符串 0/3。")
        print("   要拿到 enum，必须逃出装饰器，改用 pydantic 的 Literal 或手动写 schema。")
    print()
    print("结论：抽象替你生成了「能用的」schema，但没有生成「最好的」schema。")
    print("      而第 4 章的实测说明这两者的差别是 0/3 和 3/3。")


# ==== 4. 逃出抽象：用 Literal 把 enum 找回来 ====
print()
print("=== 4. 逃出抽象之后 ===")
from typing import Literal


@lc_tool
def get_weather_v2(city: str, day: Literal["明天", "后天"]) -> dict:
    """查询某个城市某一天的最高气温（摄氏度）。

    Args:
        city: 城市名
        day: 明天或后天
    """
    return TEMP.get((city, day), {"error": "没有数据"})


schema2 = get_weather_v2.args_schema.model_json_schema()
print("day 的定义：", json.dumps(schema2["properties"].get("day"), ensure_ascii=False))
has_enum = "enum" in json.dumps(schema2["properties"].get("day", {}))
print("现在有 enum 了：%s" % ("✅ 是" if has_enum else "❌ 否"))
print()
print("代价：这已经不是在写「普通的 Python 函数」了 —— 类型注解从 str 变成了 Literal，")
print("      而 Literal 是为「生成 schema」这个目的服务的。这就是**抽象泄漏**：")
print("      为了拿到想要的效果，你必须了解抽象内部是怎么把注解翻译成 schema 的。")
```


## 那份清单的另一面

上一节讲了反方立场，这里补一句它没说透的话：**12-Factor Agents 描述的是「理想形态」，不是「最低成本路径」。**

它的十二条如果全部自己实现，你会得到一个完全可控、也完全由你维护的系统。对长期运行的核心系统，这个交易可能划算。但对一个验证性项目、或者一个季度内要上线的功能，它可能过于昂贵。

所以真正的判断依据是**这个 agent 要活多久**：

- **一次性 / 验证性** → 用框架快，之后大概率会重写
- **中长期（一年以上）** → 控制和可观测性的价值会超过维护成本
- **核心链路** → 控制流和提示词必须在你自己手里

这条判据比「该不该用框架」更好用，因为它把问题从「哪个更好」变成了「这个东西要活多久」。

## 一个具体的边界：什么绝对不该交给框架

有三样东西，无论项目多短，都不该完全交给框架：

**一是提示词。** 它是第 2 章的工程对象，要能 diff、能回滚、能做 A/B。如果它藏在框架的模板参数里，你就失去了迭代它的能力 —— 而这恰恰是效果提升最大的地方。

**二是状态定义。** 你的业务状态是什么形状，应该由你定义。框架的内部状态对象是它的实现细节，不该成为你的数据模型。第 11 章第 4 节那条「存可重建的输入，不存内存快照」讲的就是这个。

**三是权限边界。** 第 9 章那四道闸门 —— 活动范围、预算、熔断、不可逆确认。这些是你的安全边界，交给框架等于把安全建立在你不了解的代码上。

三样之外的，交给框架没问题。

## 怎么判断你的团队属于哪一类

前面那条「看这个 agent 要活多久」的判据，可以再具体化一点。三个信号：

**信号一，你的提示词改动频率。** 如果每周都要调提示词，那么提示词必须在你自己的代码库里 —— 它需要 diff、需要回滚。藏在框架模板里的提示词会让这个迭代循环变得很慢。

**信号二，你的失败恢复要求。** 如果任务是「重跑一次就行」，那不需要严格的状态管理；如果是「跑了一半不能重来」（比如涉及支付、发货），那第 11 章第 4 节那些问题就是你的核心问题，必须自己掌控。

**信号三，你有没有专职的人跟这些基础设施。** 12-Factor 那套东西是要人维护的。如果没人跟，框架帮你摊掉的那部分跟进成本会变成你的负担。

三个信号指向「自己掌控」时，就从第 11 章那两三百行开始；指向「用框架」时，就按第 5 节的矩阵挑，并把框架限制在一个薄层里。
## 常见坑

- **把「自己写」当成道德立场。** 它是一个取舍：你换来了控制力，付出了维护成本。
- **低估框架的跟进成本。** API 变更、新协议适配、并发坑 —— 这些框架替你摊掉了，自己写要自己跟。
- **假设自己有判断力。** 「拥有自己的控制流」的前提是知道好控制流长什么样，第 11 章的手写就是补这个。
- **在工具很多时坚持手写 schema。** 30 个工具时手写会变成负担，这时框架的优势是真的。
- **不做折中。** 最常见的错误是二选一 —— 实际上「控制流自己写、工具接入用框架」往往是最优解。
