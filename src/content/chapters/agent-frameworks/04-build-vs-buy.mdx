前面三节讨论了框架抽象的覆盖面和边界。这一节补上常见的反方观点：**把控制流、提示词、上下文和状态保持在应用可检查的范围内，能降低对不透明默认行为的依赖。** 这是作者的工程立场与一组设计原则，不是对所有框架的实证判决，也不要求团队把每个通用组件都从头实现。

这组原则的代表材料是 HumanLayer 作者维护的「12-Factor Agents」。它试图回答：怎样用软件工程方法把 LLM 功能做成可维护的产品。作者明确说这些想法不等于批评框架，并提出可以把小而模块化的 agent 概念融入现有产品。读者应把它当作**审查问题清单**，再按具体需求决定自行实现、采用框架或混合使用。

## 那份清单说了什么

十二条里有几项与框架抽象的责任边界关系较大。这里概述作者主张，不把它们改写成所有框架都缺少相应能力的事实：

**「拥有自己的控制流」。** 作者倾向让应用代码拥有关键决策与转移逻辑。实际评估时，问清哪些决策由模型、SDK 默认值、框架配置和应用代码分别负责；若框架暴露足够清晰的扩展点，也可能满足这一原则。

**「拥有自己的提示词与上下文」。** 提示词和最终发送的上下文应能被团队检查、版本化和测试。它们可以来自代码、受控配置或数据库；重要的是来源可追踪、变化可审查、最终请求可验证，而不是必须采用某种存储形式。

**「把 agent 当作普通软件」。** 把重试、错误恢复、授权、预算和业务状态当作明确的软件契约。框架可以提供实现机制，但采用者仍需确认其语义满足自己的业务与故障模型。

**「小步、可组合、无隐藏状态」。** 将任务拆成可观察和可测试的步骤，避免无法恢复或审查的隐式状态。这是可维护性目标，不表示每一步都必须是纯函数；I/O 和副作用仍需明确隔离与对账。

### 十二条完整清单

上面那四条只是和框架抽象直接冲突的部分。12 条要能当自评工具用，得列全（原文 https://github.com/humanlayer/12-factor-agents ，资源库里也收录了）。每条附一个「你现在的做法符合吗」的自测问题：

| # | 主张 | 自测问题 |
|---|---|---|
| 1 | 自然语言到工具调用 | 用户的一句话，是被解析成结构化调用，还是整段塞给模型？ |
| 2 | 拥有你的提示词 | 你的提示词在代码库里能 diff、能回滚吗？ |
| 3 | 拥有你的上下文窗口 | 发给模型的每条消息，是你拼的还是框架拼的？ |
| 4 | 工具只是结构化输出 | 工具调用对你来说是不是一段可校验的 JSON？ |
| 5 | 统一执行状态与业务状态 | 「走到哪一步」和业务数据是两份，还是同一份？ |
| 6 | 用简单 API 启动 / 暂停 / 恢复 | 能一句话暂停一个跑到一半的任务再恢复吗？ |
| 7 | 通过工具调用联系人工 | 人工审批如何进入流程，并留下可恢复、可审计的记录？ |
| 8 | 拥有你的控制流 | 循环、分支、重试写在你自己的代码里吗？ |
| 9 | 把错误压缩进上下文 | 工具报错时，进上下文的是堆栈还是一句可行动的说明？ |
| 10 | 小而专注的 agent | 你的 agent 是一件事，还是一堆事的集合？ |
| 11 | 从任何地方触发 | 换一个入口（CLI / HTTP / 定时任务）要改核心逻辑吗？ |
| 12 | 把 agent 做成无状态 reducer | `(state, event) -> new_state` 这个形状，你的系统符合吗？ |

12 条不需要全打勾才叫合格 —— 它的用法是**找出你没做到的那几条，并确认那是取舍还是疏忽**。

## 这组原则提供什么判断

12-Factor Agents 是**作者提出的设计原则，不是框架能力的对照实验**。它能帮助我们把“框架是不是黑箱”拆成可以核验的问题，但不能单独证明手写系统更可靠、更便宜或更容易维护。

**一、明确谁掌握关键决策。** 列出终止条件、工具授权、重试、恢复和拒绝分别由哪一层控制，再用目标任务测试一个关键故障路径。这样做能发现责任空档；是否要改成自研，仍要比较实现和运维成本。

**二、查看最终请求与可恢复状态。** 不只看提示词模板或状态类型的名字，还要验证运行时发出的完整消息、外部写入后的状态和重启行为。版本化与可观测有助于审查，但也需要访问控制、保留期限和敏感字段治理。

**三、把生成物和验收契约分开。** 上一节的固定版本 LangChain 示例展示了普通 `str` 与 `Literal` 生成不同 schema；这验证的是本地 schema 形状，不是模型遵循率。第 4 章曾记录 `0/3` 对 `3/3` 的小样本摘要，但逐次响应、固定模型快照和 scorer 缺失，不能独立复核，不能据此声称 enum 会普遍提高成功率。

这些原则更适合作为**选型前的核对清单**，而不是“自研胜过框架”的实证结论。

## 应该同时评估的成本

采用 12-Factor Agents 的立场并不会让维护成本消失；采用框架也不会自动移交所有责任。两边都要按系统要求和团队能力评估。

**一、实现和跟进成本需要算在一起。** 手写循环让团队直接控制协议细节，但也要跟踪 provider API 变化、错误语义和认证机制。框架可能替你维护部分适配，也会带来版本升级、依赖行为和扩展接口的核对工作。比较时列出实际依赖的组件和维护责任，不用“框架把成本摊给社区”作为未经验证的结论。

**二、控制力需要对应足够的工程判断。** 自己拥有循环不自动意味着设计正确；需要定义终止判据、预算、并发、重试和副作用恢复。团队如果暂时缺少经验，可以采用文档清晰且可测试的框架构件，同时用离线测试和故障演练补齐判断依据。

**三、工具数量会影响维护方式，但不构成固定分界线。** 工具变多时，手写重复 schema 和逐个维护契约可能增加工作；函数注解、集中 schema 或生成器也能减少重复。不要把“30 个工具”当作通用阈值；盘点字段变化频率、授权差异、校验测试和升级影响，再比较两种方案。

## 一个折中的实际做法

混合方案不是固定的“手写循环 + 框架工具装饰器 + tracing”，而是把责任拆清楚，再让每一层采用适合的实现：

**应用拥有业务不变量和策略选择**，例如谁可以调用工具、任务何时需要人工批准、费用上限如何核算，以及结果未知时是否允许重放。**框架可以承接通用运行机制**，例如消息适配、schema 生成、checkpoint 或 tracing，但要验证具体版本、配置和故障语义。**provider 与外部服务仍有各自的契约**，例如 stop reason、限流、请求幂等和数据保留，不应由框架名义替代核验。

选型时先挑一条代表性的成功路径和一条有副作用的失败路径，验证完整请求、工具授权、错误分类、取消/恢复、观察字段和成本记录。再把每项能力标成“已验证、需配置、应用负责、暂不支持”。这个清单能支撑“买”“自研”或混合选择，也指出还缺哪些证据。

## 怎么用这一节

不要把它当成「该不该用框架」的答案 —— 它是一套**评估的框架**（这个词在这里有点双关）。

实际用法是：选一个具体方案，把十二条当成讨论目录，再挑与你的风险和目标相关的条目做验证。至少说清：

- **哪层拥有决策权？** 对终止、工具授权、审批和恢复等关键行为，能看到实际配置并覆盖默认策略吗？
- **关键数据是否可追踪？** 能否定位某次运行使用的 prompt、上下文来源、schema、策略版本和工具结果？日志是否有脱敏、保留和访问规则？
- **失败后会发生什么？** 任务可恢复到哪个状态，外部写入如何去重或对账，未知结果如何处理？

记录选择、验证证据、未验证项和退出方案。这样能区分有意识的依赖与未检查的默认值，不会把 12 个原则简化成某一边必胜。

## 完整可运行代码

下面用一个**本地、确定性的 reducer fixture**说明第 12 条的核心形状：函数接收当前状态和规范化事件，返回新状态。它不包含 LLM、provider、数据库或真实工具执行，也不是一套可直接用于生产的 agent runtime；`tool_call` 和 `tool_result` 是本地教学事件，不是某个 provider 的 wire format。

Reducer 只负责状态转移。实际应用需要由外围执行器验证授权、调用外部工具、持久化事件并处理崩溃窗口；状态 reducer 本身不能保证 exactly-once。

```python
"""纯状态转移示例：用不可变状态处理规范化事件，不调用模型或工具。"""

from dataclasses import dataclass


@dataclass(frozen=True)
class State:
    phase: str = "idle"
    events: tuple[str, ...] = ()
    pending_call_id: str | None = None
    answer: str | None = None


def transition(state: State, event: dict[str, str]) -> State:
    kind = event.get("type")

    if kind == "user_message":
        content = event.get("content", "")
        if state.phase != "idle" or not content.strip():
            raise ValueError("invalid user_message")
        return State("running", state.events + (f"user:{content}",))

    if kind == "tool_call":
        call_id = event.get("id", "")
        name = event.get("name", "")
        if state.phase != "running" or not call_id or not name:
            raise ValueError("invalid tool_call")
        return State(
            "waiting_tool",
            state.events + (f"tool_call:{call_id}:{name}",),
            pending_call_id=call_id,
        )

    if kind == "tool_result":
        call_id = event.get("id", "")
        content = event.get("content", "")
        if state.phase != "waiting_tool" or call_id != state.pending_call_id:
            raise ValueError("tool_result does not match pending call")
        return State(
            "running",
            state.events + (f"tool_result:{call_id}:{content}",),
        )

    if kind == "final_answer":
        content = event.get("content", "")
        if state.phase != "running" or not content.strip():
            raise ValueError("invalid final_answer")
        return State(
            "done",
            state.events + (f"assistant:{content}",),
            answer=content,
        )

    raise ValueError(f"unknown event type: {kind}")


if __name__ == "__main__":
    initial = State()
    after_user = transition(initial, {"type": "user_message", "content": "查天气"})
    waiting = transition(after_user, {"type": "tool_call", "id": "call-1", "name": "get_weather"})

    try:
        transition(waiting, {"type": "tool_result", "id": "wrong-id", "content": "20C"})
    except ValueError:
        mismatch = "rejected"
    else:
        mismatch = "accepted"

    after_tool = transition(waiting, {"type": "tool_result", "id": "call-1", "content": "20C"})
    done = transition(after_tool, {"type": "final_answer", "content": "20C"})

    print(f"initial_unchanged={initial.phase == 'idle' and not initial.events}")
    print(f"phase={done.phase} event_count={len(done.events)} pending={done.pending_call_id}")
    print(f"wrong_tool_result={mismatch}")
    print(f"answer={done.answer}")
```

**实跑状态**：Python 3.10+ 标准库；下方 fixture 在本地运行，无 provider 或网络调用。输出检查 reducer 不修改旧状态，并拒绝与待处理调用 ID 不匹配的结果。

```text
initial_unchanged=True
phase=done event_count=4 pending=None
wrong_tool_result=rejected
answer=20C
```

这里的状态转移是可确定重放的，因为 reducer 只计算规范化事件；数据库写入、工具副作用和模型调用必须由外层编排处理，并另行定义持久化、幂等、授权与错误恢复。


## 那份清单的另一面

12 条适合用来提出问题，不应被当作每个项目都必须逐条照做的目标。完全自己控制会增加实现和持续维护责任；借用成熟组件也可能降低重复工作，但需要确认 API、数据流和运行语义仍足够透明。

判断时可查看下面这些**项目属性**，它们比单看预计生命周期更有区分力：

- **变更是否可审查。** Prompt、上下文组装和策略可以放在不同受控存储中；要求有版本、变更记录、回滚与测试，来源和实际发送内容可追踪。
- **失败恢复要求是什么。** 对无副作用的请求，有限重试可能足够；对支付、发货、写库等操作，要验证幂等键、结果查询、对账和人工处置路径。未知状态不应直接重放。
- **抽象能否通过验证。** 若框架能满足要求的测试、运维和审计契约，使用它不等于放弃控制；若关键路径无法观察或扩展，才比较替代实现的实际成本。
- **谁维护它。** 把升级、故障响应、依赖安全和 schema/策略维护列入团队工作，不论代码来自应用还是第三方。

这组属性没有通用权重。按风险和目标给出理由，保留未验证项，等集成证据而不是按“一年”或“核心链路”标签直接下结论。

## 应用必须保留哪些责任

无论采用什么框架，应用团队都要明确并验收责任边界：

**一是策略与授权。** 应用应确定允许谁在什么任务、租户和资源范围内调用工具，以及哪些操作需要审批。框架可能提供 guardrail、策略钩子或授权构件，但需要验证它们真实覆盖的路径，尤其是失败、并发和旁路路径。

**二是业务状态与恢复契约。** 可以使用框架内部状态或 checkpoint，只要定义迁移、持久化、并发和恢复语义，并能在升级时兼容。数据库模型不必与框架状态完全分离，但业务记录的所有权和外部副作用必须明确。

**三是可审查的请求与结果。** Prompt 可以由模板引擎、配置服务或代码生成；团队应能定位某次请求使用的版本，限制敏感数据访问，并有测试或审计记录。可观测性组件可以由框架提供，不表示默认隐私和留存设置天然满足要求。

因此，不能把“交给框架”简单等同于“交出安全”；要问框架承接了哪段实现、应用如何配置和验证，以及失败时谁负责决策。

## 怎么判断你的团队属于哪一类

前面的属性可以转成三组团队问题：

**信号一，Prompt 与上下文的变化能否审查？** 如果频繁变化，重要的是每次修改可追踪、可回滚且能回归测试。可以通过代码仓库实现，也可以使用具备版本管理和审计能力的受控配置系统；不要把“必须放在代码里”当作唯一答案。

**信号二，失败后要恢复到什么状态？** 先定义用户可见的结果、外部副作用和未知状态处理，再分别测试框架和自研实现。若业务要求“不能重复扣款”，应验证交易幂等、结果查询和人工对账，而不是只验证进程重启后代码能继续运行。

**信号三，团队能否长期维护这些边界？** 盘点谁负责依赖升级、prompt/schema 回归、工具权限、trace 脱敏、故障演练和版本兼容。人手不足可以成为选择托管或框架能力的理由，也意味着要审查其服务边界和可退出方案。

三组问题的结果决定哪些组件适合自建、采用或暂缓；没有一个预设的生命周期、团队规模或工具数量阈值可以替代这个判断。

## 常见坑

- **把「自己写」当成道德立场。** 它是一个取舍：你换来一部分实现控制力，也接下实现、升级和运行责任。
- **低估框架或自研的维护成本。** 两种方案都要计入版本升级、故障响应和兼容性验证；先列明谁负责、哪些证据证明能力满足要求。
- **假设控制流属于一个固定组件。** 决策、终止、重试、恢复和权限可能跨模型、SDK、应用与外部服务；逐条标出责任。
- **用工具数量或系统寿命设通用阈值。** 比较真实的 schema 维护、变更频率、恢复要求、团队能力和退出成本。
- **把审查要求误当实现位置要求。** Prompt 或业务状态不一定要保存在应用代码里，但应能审查版本、来源和变化，并有测试、权限和回滚方案。
- **把“混合方案”当作最优解。** 先用目标路径和失败演练证明混合边界可工作，再决定工具接入、循环、追踪等具体组件由谁提供。
