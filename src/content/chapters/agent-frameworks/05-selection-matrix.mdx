前面四节讲了框架给你什么、抽象有哪些、会在哪里泄漏、以及反方的立场。这一节把它们收成一张可以用的表。

## 一张评估矩阵

按维度打分，不要按框架名排序。五个维度，权重按你的实际情况调：

| 维度 | 要问的问题 | 怎么验 |
|---|---|---|
| **表达力** | 我最复杂的分支它能表达吗 | 拿流程图在纸上对它一遍 |
| **可绕性** | 需要绕开时，我绕得出去吗 | 找它的 escape hatch（逃生舱：框架留的「用你自己的实现覆盖某一层」的正规入口，比如自定义回调、替换掉某个内置组件），或读源码看有没有 |
| **可观测性** | 出故障时我能看到中间状态吗 | 跑一个失败的任务，看它能给出什么 |
| **状态模型** | 状态是什么形状、能不能序列化 | 尝试把状态存成 JSON 再读回来 |
| **迁移成本** | 换掉它要动多少代码 | 数一数你的代码里有多少处直接依赖它的类型 |

**最后一行最容易被忽略，也最重要。** 它就是你为「第 3 节那些泄漏」付的总账：每处绕开抽象的地方，都是一处迁移时要改的地方。

## 迁移成本怎么估

一个可操作的办法：**数你的代码里出现了多少个框架的类型。**

比如：

```python
from framework import AgentExecutor, Tool, BaseCallbackHandler

def build() -> AgentExecutor:              # ← 1 处
    tools: list[Tool] = [...]              # ← 2 处
    handler = MyHandler(BaseCallbackHandler)  # ← 3 处
    return AgentExecutor(tools=tools, ...)
```

这里框架的类型出现在三个地方。如果换成手写循环，这三处要改；而如果你的业务函数签名里也带着框架类型（比如工具函数接收框架的 context 对象），那数字会迅速上升。

**判据：如果一个框架类型出现在你的业务逻辑签名里，那它就不是一个可替换的依赖。** 它会渗透进你的每一层。

一个好习惯是把框架的使用**限制在一个薄层里**：业务代码只认你自己定义的类型，框架类型只在外层转换。这样迁移成本是可估的 —— 就是那一层。

## 按场景选

把前面几节的内容收成几个典型场景：

| 你的场景 | 建议 | 理由 |
|---|---|---|
| 流程固定，就是几步调用 | **不用框架**，写两个函数 | 链抽象在这里没有额外价值 |
| 流程会变，分支可枚举 | **用图的抽象**，或自己写状态机 | 图的可序列化位置对断点恢复有用（第 11 章第 4 节） |
| 工具很多（20+），schema 手写成负担 | **用框架的工具接入** | 这是框架最成熟的优势区 |
| 需要精确控制 schema 约束 | **框架 + 手写 schema 覆盖** | 装饰器给不出 enum（第 3 节实测） |
| 需要严格的预算/熔断/幂等 | **自己写闸门** | 第 9 章和第 11 章的那四道闸门，多数框架不提供 |
| 任务形状事先不知道 | **自主 agent + 自己补闸门** | 灵活性来自模型，保证要来自你的代码 |

注意这张表里**没有一行的建议是「全都用框架」或「全都自己写」**。这正是第 4 节那个折中做法的具体形态。

## 一个反直觉的建议：先不用

如果你现在还没有选框架，这一节的建议是**先用自己写的那两三百行跑一个真实任务**。

理由和这一章的结构一样：**只有跑过一个真实任务，你才知道自己的泄漏区在哪。** 在那之前，你对「需要什么抽象」的判断都是猜测 —— 而框架选型的错误代价是重写。

而跑过之后，你会带着一份具体的问题清单去看框架：

- 我遇到的这个分支，它怎么表达？
- 我需要保留的这个约束，它的装饰器给得出吗？
- 我这次崩溃恢复踩的坑，它替我做对了吗？

**带着真实问题去评估，和拿着功能列表去比较，是两件完全不同的事。**

## 完整可运行代码

下面这段代码是这一章所有判断的起点：**把框架生成的东西原样打印出来。** 无论你最后选哪个，这一步都该做。

```python
"""真框架对照：同一个任务，手写循环 vs LangChain。

不是性能对比 —— 比的是三件事：
  1. 代码量
  2. 你能看见什么、看不见什么
  3. 想加一个需求时，需要在哪里「逃出抽象」

实跑状态：2026-10-09，langchain 0.3.7 + deepseek-flash（Anthropic 兼容端点）。
"""
import os, json, time

print("langchain 版本：", end="")
import langchain
print(langchain.__version__)

from langchain_core.tools import tool as lc_tool
from langchain_anthropic import ChatAnthropic

TEMP = {("北京", "明天"): 31, ("上海", "明天"): 27, ("广州", "明天"): 34}

# ---- 手写版的工具定义：schema 与实现分开写 ----
HAND_TOOLS = [{
    "name": "get_weather",
    "description": "查询某个城市某一天的最高气温（摄氏度）。",
    "input_schema": {"type": "object",
                     "properties": {"city": {"type": "string"},
                                    "day": {"type": "string", "enum": ["明天", "后天"]}},
                     "required": ["city", "day"]},
}]


def hand_get_weather(city, day):
    return TEMP.get((city, day), {"error": "没有数据"})


# ---- 框架版的工具定义：一个装饰器，schema 从类型注解推断 ----
@lc_tool
def get_weather(city: str, day: str) -> dict:
    """查询某个城市某一天的最高气温（摄氏度）。

    Args:
        city: 城市名
        day: 只支持「明天」或「后天」
    """
    return TEMP.get((city, day), {"error": "没有数据"})


if __name__ == "__main__":
    print()
    print("=== 1. 代码量 ===")
    print("手写版工具定义：%d 行（schema 手写）" % len(json.dumps(HAND_TOOLS, ensure_ascii=False).split(chr(10))))
    print("框架版工具定义：6 行（一个装饰器 + 文档字符串）")
    print("→ 框架在「schema 生成」这一层确实省事")
    print()

    print("=== 2. schema 长什么样（框架替你生成了什么）===")
    print(json.dumps(get_weather.args_schema.model_json_schema(), ensure_ascii=False, indent=1)[:600])
    print()

    print("=== 3. 一个抽象泄漏的现场 ===")
    print("题目：它的 input_schema 里有没有 enum 约束？")
    schema = get_weather.args_schema.model_json_schema()
    print("day 的定义：", json.dumps(schema["properties"].get("day"), ensure_ascii=False))
    if "enum" not in json.dumps(schema["properties"].get("day", {})):
        print("→ ❌ 没有 enum。文档字符串里写了「只支持明天或后天」，")
        print("   但生成的 schema 只有 type: string。")
        print("   而第 4 章实测过：enum 约束下模型 3/3 合法，自由字符串 0/3。")
        print("   要拿到 enum，必须逃出装饰器，改用 pydantic 的 Literal 或手动写 schema。")
    print()
    print("结论：抽象替你生成了「能用的」schema，但没有生成「最好的」schema。")
    print("      而第 4 章的实测说明这两者的差别是 0/3 和 3/3。")


# ==== 4. 逃出抽象：用 Literal 把 enum 找回来 ====
print()
print("=== 4. 逃出抽象之后 ===")
from typing import Literal


@lc_tool
def get_weather_v2(city: str, day: Literal["明天", "后天"]) -> dict:
    """查询某个城市某一天的最高气温（摄氏度）。

    Args:
        city: 城市名
        day: 明天或后天
    """
    return TEMP.get((city, day), {"error": "没有数据"})


schema2 = get_weather_v2.args_schema.model_json_schema()
print("day 的定义：", json.dumps(schema2["properties"].get("day"), ensure_ascii=False))
has_enum = "enum" in json.dumps(schema2["properties"].get("day", {}))
print("现在有 enum 了：%s" % ("✅ 是" if has_enum else "❌ 否"))
print()
print("代价：这已经不是在写「普通的 Python 函数」了 —— 类型注解从 str 变成了 Literal，")
print("      而 Literal 是为「生成 schema」这个目的服务的。这就是**抽象泄漏**：")
print("      为了拿到想要的效果，你必须了解抽象内部是怎么把注解翻译成 schema 的。")
```


## 一个可以现在就做的动作

看完这一章，最有用的一件事不是选型，而是**把当前代码里框架类型的出现位置列出来**：

```bash
# 粗略但有效：数一数有多少文件直接 import 了框架
grep -rl "from langchain" --include=*.py . | wc -l
```

然后看这些文件里，有多少是**业务逻辑**，多少是**装配代码**。

- 如果框架只出现在装配层（构建 agent、注册工具的那几个文件）→ 迁移成本可控，你换掉它只要改那一层
- 如果它出现在业务函数签名里（工具函数接收框架的 context、业务逻辑返回框架的 Message 对象）→ 它已经渗透进去了

这个动作的价值在于：**它把「我对框架的依赖有多深」从一个感觉变成了一个数字。** 而这个数字，比任何框架对比文章都更能告诉你该怎么做。

## 把「渗透进签名」变成一条能跑的检查

上面那个 `grep` 数的是**文件数**，它分不出「这个文件只是装配」和「框架类型已经进了业务签名」。要区分得看每个函数的签名，那就得解析 Python —— 标准库 `ast` 就够了：

```python
"""检查「框架类型有没有渗透进业务函数签名」。

自包含：示例源码写在字符串里，不需要额外文件。
实跑状态：2026-10-12。
"""
import ast

SAMPLE = '''
from langchain_core.messages import HumanMessage
from langchain.agents import AgentExecutor
from myapp.models import Order


def make_agent(model, tools):                     # 装配层：出现框架类型是正常的
    return AgentExecutor(model=model, tools=tools)


def handle_payment(order: Order, message: HumanMessage) -> dict:   # 业务签名：渗进来了
    return {"id": order.id}


def total(orders: list[Order]) -> int:            # 干净的
    return sum(o.amount for o in orders)
'''

FRAMEWORKS = ("langchain", "langgraph", "llama_index", "haystack", "autogen", "crewai")


def is_framework_module(module):
    return any(module == fw or module.startswith(fw + ".") or module.startswith(fw + "_")
               for fw in FRAMEWORKS)


def framework_symbols(tree):
    """收集从框架包 import 进来的那些名字。"""
    names = set()
    for node in ast.walk(tree):
        if isinstance(node, ast.ImportFrom) and node.module and is_framework_module(node.module):
            for a in node.names:
                names.add(a.asname or a.name)
        if isinstance(node, ast.Import):
            for a in node.names:
                if is_framework_module(a.name):
                    names.add((a.asname or a.name).split(".")[0])
    return names


def _annotations(fn):
    args = fn.args
    out = []
    for a in list(args.args) + list(args.posonlyargs) + list(args.kwonlyargs):
        if a.annotation is not None:
            out.append(ast.unparse(a.annotation))
    if args.vararg and args.vararg.annotation is not None:
        out.append(ast.unparse(args.vararg.annotation))
    if args.kwarg and args.kwarg.annotation is not None:
        out.append(ast.unparse(args.kwarg.annotation))
    if fn.returns is not None:
        out.append(ast.unparse(fn.returns))
    return out


def leaks(source, filename="<sample>"):
    tree = ast.parse(source, filename)
    fw = framework_symbols(tree)
    found = []
    for node in ast.walk(tree):
        if not isinstance(node, ast.FunctionDef):
            continue
        for ann in _annotations(node):
            for name in fw:
                if name in ann:
                    found.append((filename, node.name, node.lineno, ann, name))
    return found


if __name__ == "__main__":
    print("框架符号（从框架包 import 进来的）：%s" % sorted(framework_symbols(ast.parse(SAMPLE))))
    rows = leaks(SAMPLE)
    print("签名里出现框架类型的函数：")
    for f, fn, line, ann, name in rows:
        print("  %s:%d  def %s(...)  注解 %r 引用了 %s" % (f, line, fn, ann, name))
    print("合计：%d 处，涉及 %d 个函数" % (len(rows), len({r[1] for r in rows})))
```

实跑输出（2026-10-12；示例：构造数据，未实跑 —— 解析的源码字符串是构造的，脚本本身本次已跑通）：

```text
框架符号（从框架包 import 进来的）：['AgentExecutor', 'HumanMessage']
签名里出现框架类型的函数：
  <sample>:11  def handle_payment(...)  注解 'HumanMessage' 引用了 HumanMessage
合计：1 处，涉及 1 个函数
```

把它套到你自己的包上（对每个 `.py` 跑 `ast.parse(open(path).read())` 即可），输出的就是迁移成本四层里**业务逻辑**那一层（第三层）的数字：

- **0 处** → 框架只在装配层与工具定义层，迁移成本就是前两层，可控
- **有若干处** → 每一处都是换框架时要改的业务代码。数量乘以改一处的成本，就是这一层的账

注意它只统计**函数签名**（参数与返回注解）里的框架类型，不统计函数体 —— 函数体里用框架类型（比如构造对象）属于装配，签名里出现才叫渗透。这个区分就是那句话的可执行版本：**「如果一个框架类型出现在你的业务逻辑签名里，那它就不是一个可替换的依赖。」**

## 最后：这一章没有推荐任何框架

这是刻意的。原因有两个。

**第一，框架的迭代速度远快于这本书。** 具体的 API、具体的包名，半年后可能就变了。写进正文只会让它快速过期 —— 而这一章用的 langchain 0.3.7 的实测结论（装饰器不给 enum）在写下来的那一刻就标注了版本号，正是为了这个原因。

**第二，更重要的是：这一章教的是一套判断方法，而判断方法不会过期。** 「把生成的 schema 打印出来」「数框架类型出现在哪」「拿最复杂的分支做表达测试」—— 这三件事在任何框架上都能做，而且十分钟就能做完。

所以这一章的产出不是「用哪个」，是三件可以立刻做的事。

## 迁移成本的一个具体估算

上面说的是「数框架类型的出现处数」。这里给一个更细的算法：

**第一层，装配代码。** 构建 agent、注册工具、配置回调 —— 这部分换框架时一定要重写，但它本来就是一次性的，工作量按小时算。

**第二层，工具定义。** 每个工具的定义跟着框架走。如果有 30 个工具，换框架就是 30 处改动。这一层的成本随工具数线性增长，是容易低估的一块。

**第三层，业务逻辑。** 如果业务函数直接接收框架的上下文对象（比如工具函数的第一个参数是框架的 ToolRuntime），那改动会渗透进实现内部。这一层最贵，也最该避免。

**第四层，状态与持久化。** 如果你的状态是框架的内部对象，迁移时要重新做一遍序列化设计。第 11 章第 4 节那条「存可重建的输入而不是内存快照」，在这里就是一个可迁移性的选择。

四层里，**前两层是可控的固定成本，后两层取决于你当初有没有留边界。** 所以「把框架限制在一个薄层里」这句话的具体含义就是：让它只出现在前两层，不要进入第三、四层。


## 一个提醒：别把矩阵变成打分表

这张矩阵的用法不是给每个框架打分然后选最高分。那样做有两个问题。

**第一，维度的权重完全取决于你的场景。** 对一个内部工具，可观测性可能最重要；对一个延迟敏感的产品，表达力和延迟才要紧。同一个框架在不同场景下的得分是相反的。

**第二，有些维度是「门槛」而不是「分数」。** 「最复杂的分支能不能表达」不是加分项 —— 表达不了就是不能用。把它和「文档好不好」放在一起算总分，会让你选出一个表达不了你需求的框架。

所以正确的用法是：**先用门槛维度筛掉不能用的，再用权重维度在剩下的里面选，最后用迁移成本做一次压力测试。** 三步的顺序不能反。
## 常见坑

- **按框架名排序，而不是按维度打分。** 「哪个更流行」和「哪个适合我的分支」是两个问题。
- **不估迁移成本。** 数一数框架类型出现在你代码里的处数，那就是你换掉它的代价。
- **让框架类型进入业务签名。** 一旦渗透进业务层，它就不再是可替换的依赖。
- **在没跑过真实任务之前选型。** 你那时对「需要什么抽象」的判断是猜测，而选错的代价是重写。
- **以为必须二选一。** 控制流自己写、工具接入用框架，往往是最优解。
