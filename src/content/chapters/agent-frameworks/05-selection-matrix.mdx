前面四节讲了框架给你什么、抽象有哪些、会在哪里泄漏、以及反方的立场。这一节把它们收成一张可以用的表。

## 一张评估矩阵

不要从“哪个框架功能最多”开始。先把**硬性门槛**和**可权衡的偏好**分开：有一项硬门槛不满足，综合分再高也不能抵消。下面是起始清单，具体项目可按风险补充，不是完整标准。

| 评估面 | 要问的问题 | 怎么取证 |
|---|---|---|
| **能力与协议门槛** | 目标模型/provider、工具协议、schema、流式输出和多模态要求是否被支持？ | 用目标 endpoint 和版本跑边界样例；分别检查本地 schema 与 provider 实际接受行为 |
| **控制流与故障语义** | 谁决定继续、停止、交接、重试和取消？部分失败、超时或进程重启后状态如何？ | 跑一条成功路径和有副作用的失败路径，确认事件、恢复点、幂等与人工介入 |
| **权限与数据边界** | 工具授权由谁执行？提示、状态和 trace 会流向哪里，谁能访问、保留多久？ | 检查授权代码、存储/导出配置、敏感字段处理和租户边界；不能只看产品功能表 |
| **运行与可观测性** | 能否记录诊断所需状态？超时、并发、费用和调用限制各由哪层负责？ | 验证 trace 字段与数据去向；将调用数、token、并发、时间和货币预算分开测试 |
| **集成与扩展** | 现有 provider、存储、部署和测试设施能否接入？遇到缺口能否覆盖默认行为？ | 做一个有代表性的适配，并验证文档支持的扩展点与升级后测试 |
| **团队与生命周期** | 谁负责升级、告警、兼容、漏洞响应和迁移？离开服务或框架时如何取回状态？ | 明确责任人；检查状态格式、导出能力、依赖与退出步骤；估算一次切换演练 |

硬性门槛应有“满足 / 有条件满足 / 不满足”的证据；通过门槛后，再按当前项目给偏好维度赋权。权重是团队的决策记录，不是框架的客观排名。对可能导致数据泄漏、重复副作用或无法恢复的缺口，不能靠其它维度的高分抵消。

官方产品自己的选型说明也会保留多条路径。例如 [OpenAI Agents SDK 官方文档](https://openai.github.io/openai-agents-python/)把“直接调用 Responses API、由应用控制 loop/tool dispatch/state”与“让 SDK runtime 管理 turns、tools、guardrails、handoffs 或 sessions”分别列为适用方向，并说明两种方式可以在一个应用中并用。这只能说明该产品提供这些路径；其它 SDK/provider 的能力与责任仍须按目标版本和配置验证。

## 迁移成本怎么估

不要把框架类型或 import 出现次数直接当成迁移工时。它们是**定位耦合点的线索**；真正的成本来自这些耦合点承载的行为、状态与兼容责任。至少盘点：

1. **接口与适配**：模型请求、工具 schema、事件流、错误和取消如何映射。
2. **业务行为**：哪些策略写进 framework callback/node/context；替换后是否能保持授权、终止、重试和人工审批语义。
3. **持久化数据**：数据库行、checkpoint、对话历史和工具结果是否使用框架私有格式，能否导出、迁移或重建。
4. **可观测与测试**：trace、评测、告警和回归夹具有多少依赖框架的字段或服务。
5. **运行与团队责任**：升级兼容、凭据/数据治理、故障响应、部署和退出方案由谁承担。

做一个切换演练比数类型更有用：选关键工作流，在隔离分支把一个模型适配、一个工具和一个失败恢复路径切到候选实现；记录改动文件、语义差异、数据转换、测试缺口和验证耗时。它仍是该工作流的样本，不能直接外推为全系统工时。

薄适配层可能降低某些接口替换的修改面，却不会自动消除状态迁移、行为差异、存储格式或运行责任。把这些边界分别记录，才能讨论“迁移是否可控”。

## 按场景选

下面是形成候选方案的起点，不是“满足某个场景就必须选某种框架”的规则：

| 需求形状 | 候选方向 | 必须验证 |
|---|---|---|
| 几步固定调用，状态短暂 | 直接用 provider SDK、已有应用代码或轻量封装 | 错误分类、超时/重试、校验与可测试性；“不用 agent 框架”不等于跳过可靠性工程 |
| 分支已知，执行需要暂停/恢复 | 显式状态机、图运行时或应用持久化工作流 | 分支语义、持久化位置、恢复/并发行为；有图 API 不代表默认就能跨重启恢复 |
| 工具 schema 与接入需要集中管理 | 框架工具层、生成器或自有 registry 都可比较 | 最终 schema、授权绑定、参数校验、版本兼容和本地执行语义 |
| 输出受严格契约约束 | provider 约束输出、工具 schema 或显式 schema + 本地校验 | 目标 provider 的实际约束范围、拒绝/截断路径、schema 与业务规则；历史 0/3 对 3/3 结果不可独立复核，不能当模型成功率证据（见[工具 schema 泄漏示例](/chapters/agent-frameworks/leaky-abstractions)） |
| 成本、并发或副作用风险高 | 应用侧预算/授权门禁，可组合框架能力 | token/费用、并发、时限、幂等、取消、恢复逐项测；SDK 的 turn/step 限制不一定是你的金额或业务预算 |
| 路径需要模型动态选择 | 受约束的 agent runtime 或自有 loop | 能力范围、停止条件、权限、人工审批、重试和总预算；“自主”不能取代宿主验证 |

具体方案通常是分层组合。比如可以让 SDK 管理 agent loop，同时由业务应用负责用户授权与持久化副作用；也可以自己实现短循环而复用 framework 的 tool/schema、trace 或 session 组件。边界以测试验证为准，不能先假设“混合”一定最优。

## 先选一条路径做验证

如果还没有选型，不要先用固定的自研代码规模当目标，也不要先装功能最多的框架。挑一条业务代表性工作流，把候选方案放到同一个验收契约里比较：

- 完成一次正常请求，记录最终输入、工具参数和业务结果。
- 注入一次工具失败或超时，检查授权、重试、去重和恢复路径。
- 检查状态是否可持久化/导出，部署重启后谁负责恢复。
- 检查 trace、提示与工具输入输出的数据去向。
- 记录实现、升级、运维和退出所需的代码与责任；没有实际测量的工时不要写成精确结论。

先筛掉不满足硬门槛的候选，再讨论其余方案的便利性和维护代价。单条工作流的结果是原型证据，不等于全系统 benchmark。

## 生成的 schema 是一条独立验收线

旧稿在这里放过一段 LangChain 0.3.7 / Pydantic 示例，并把 `str`、参数说明与 `Literal` 的本地 schema 差异，连接到缺少原始逐次请求、响应和 scorer 的历史 `0/3` 与 `3/3` 模型摘要。后者不能证明某种 annotation 会提升模型成功率；这段框架生成规则已有版本锁定的说明和可执行比较，见[抽象泄漏：框架文档与类型约束](/chapters/agent-frameworks/leaky-abstractions)。

选型时把三类验证分开记录：

- **本地生成结果**：固定框架与依赖版本，打印完整 schema，断言字段、必填项、枚举和额外属性策略。
- **Provider 接受性**：用目标 endpoint 和请求格式发送代表性的边界 schema，记录成功、拒绝和不支持的部分。
- **模型任务表现**：使用固定数据集、模型快照、任务级答案键和 scorer，报告分母与失败类型；没有这些材料，就不要把零散历史数字写成结论。

工具装饰器、类型注解或框架名本身，都不能替代这三条验收线。

## 一个可以现在就做的动作

先为候选方案画一张依赖图：哪些模块初始化 SDK/runtime，哪些业务函数调用框架类型，哪些数据被写入框架状态或持久化存储，哪些测试和运营工具读取其事件。可以用源码搜索定位直接 import，再逐处确认调用方向；搜索结果是待检查清单，不是迁移成本数字。

如果依赖只集中在装配和适配层，接口替换通常更容易限定修改范围；但这仍不能证明状态格式、运行语义和生产恢复也可替换。若框架对象进入业务函数签名，说明模块接口和框架 API 已耦合，应评估是否值得引入自己的业务类型作为边界。

## 把「签名耦合」变成一条可运行的静态检查

下面的 Python AST（抽象语法树）脚本只查一个窄问题：同一文件直接从已列出的框架模块导入的名字，是否出现在 `def` / `async def` 的参数或返回注解里。它识别 import alias，并精确比较注解中的标识符；不导入框架，也不访问网络。

它是定位审查对象的启发式，不是完整类型分析：不会解析间接 re-export、框架符号的本地赋值、字符串形式的前向引用或其它语言，也不会检查函数体和运行时状态。先按项目扩展包名，再人工确认每个命中及漏检风险。

```python
"""检查「框架类型有没有渗透进业务函数签名」。

自包含：示例源码写在字符串里，不需要额外文件。
实跑状态：Python 3.10.9，本地构造样例，无依赖安装与网络调用。
"""
import ast

SAMPLE = '''
from langchain_core.messages import HumanMessage as ChatMessage
from langchain.agents import AgentExecutor
from myapp.models import Order


def make_agent(model, tools):                     # 装配层：出现框架类型是正常的
    return AgentExecutor(model=model, tools=tools)


async def handle_payment(order: Order, message: ChatMessage) -> dict:  # 业务签名：渗进来了
    return {"id": order.id}


def total(orders: list[Order]) -> int:            # 干净的
    return sum(o.amount for o in orders)
'''

FRAMEWORKS = ("langchain", "langgraph", "llama_index", "haystack", "autogen", "crewai")


def is_framework_module(module):
    return any(module == fw or module.startswith(fw + ".") or module.startswith(fw + "_")
               for fw in FRAMEWORKS)


def framework_symbols(tree):
    """收集从框架包 import 进来的那些名字。"""
    names = set()
    for node in ast.walk(tree):
        if isinstance(node, ast.ImportFrom) and node.module and is_framework_module(node.module):
            for a in node.names:
                names.add(a.asname or a.name)
        if isinstance(node, ast.Import):
            for a in node.names:
                if is_framework_module(a.name):
                    names.add((a.asname or a.name).split(".")[0])
    return names


def _annotations(fn):
    args = fn.args
    out = []
    for a in list(args.args) + list(args.posonlyargs) + list(args.kwonlyargs):
        if a.annotation is not None:
            out.append(a.annotation)
    if args.vararg and args.vararg.annotation is not None:
        out.append(args.vararg.annotation)
    if args.kwarg and args.kwarg.annotation is not None:
        out.append(args.kwarg.annotation)
    if fn.returns is not None:
        out.append(fn.returns)
    return out


def leaks(source, filename="<sample>"):
    tree = ast.parse(source, filename)
    fw = framework_symbols(tree)
    found = []
    for node in ast.walk(tree):
        if not isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef)):
            continue
        for ann in _annotations(node):
            names = {item.id for item in ast.walk(ann) if isinstance(item, ast.Name)}
            for name in fw & names:
                found.append((filename, node.name, node.lineno, ast.unparse(ann), name))
    return found


if __name__ == "__main__":
    print("框架符号（从框架包 import 进来的）：%s" % sorted(framework_symbols(ast.parse(SAMPLE))))
    rows = leaks(SAMPLE)
    print("签名里出现框架类型的函数：")
    for f, fn, line, ann, name in rows:
        print("  %s:%d  def %s(...)  注解 %r 引用了 %s" % (f, line, fn, ann, name))
    print("合计：%d 处，涉及 %d 个函数" % (len(rows), len({r[1] for r in rows})))
```

实跑输出（Python 3.10.9；输入源码为本地构造的 fixture，脚本不导入 LangChain）：

```text
框架符号（从框架包 import 进来的）：['AgentExecutor', 'ChatMessage']
签名里出现框架类型的函数：
  <sample>:11  def handle_payment(...)  注解 'ChatMessage' 引用了 ChatMessage
合计：1 处，涉及 1 个函数
```

怎样把扫描结果用于迁移评估：

1. 确认命中是否真的是框架类型，而不是同名业务类型。
2. 检查它影响的业务行为、序列化数据、测试和运行路径。
3. 在代表工作流的试点中替换一个边界，记录实际的代码变化与行为差异。
4. 把未测的工作流、持久化数据和外部集成列为剩余风险。

扫描命中数只能帮助找位置；不能按命中数量直接乘“每处成本”，也不能推出零命中就容易迁移。真正的评估要看改动所触及的语义和数据兼容。

## 用试点估迁移成本

把迁移任务拆成可验证的工作项，而不是使用“框架 API 引用处数 × 单处工时”的公式：

| 工作项 | 需要记录的证据 |
|---|---|
| 模型/provider 适配 | 请求/响应、流式事件、错误与取消如何映射；目标 endpoint 运行结果 |
| 工具和业务策略 | schema、授权、拒绝、重试、幂等与人工审批的行为差异 |
| 对话与运行状态 | 持久化格式、导入/导出、恢复位置以及旧数据迁移策略 |
| 可观测和测试 | trace 字段、评测夹具、告警、隐私配置与回归覆盖的替换工作 |
| 部署和团队运维 | 依赖升级、故障响应、密钥管理、服务责任和退出步骤 |

以一条关键工作流做小型切换演练，先得到实际改动与验证清单。再由熟悉项目的人逐项估时、记录假设和置信度，并把未试验的服务路径单列。不要把这个样本外推成精确的全系统迁移工期。

## 门槛先于加权比较

有些维度应作否决门槛：目标 provider/schema 不兼容、无法满足授权边界、不能恢复关键状态，或数据无法按要求保留/删除。只有通过门槛的候选才适合按团队赋予的权重比较便利性、集成成本、可观测性和维护负担。

权重和结论都要记录情境、依赖版本、配置、测试数据与复查日期。框架功能、provider 接口和合规选项都会变化；重做评估时，以当前文档和可复现试验为准。

## 常见坑

- **把功能清单当作项目能力证明。** 文档说明“有 session/trace/guardrail”，不等于当前配置满足你对隔离、留存、审计或恢复的要求。
- **把一个维度的高分抵消硬性缺口。** 关键权限、数据、故障恢复或协议要求必须单独通过。
- **把搜索命中数当作迁移工时。** 引用位置的行为与数据含义不同，须做试点并检查状态格式和兼容责任。
- **把框架抽象或薄适配层当成可替换保证。** 适配层帮助限定接口修改面，但不自动迁移持久数据、重现执行语义或保留测试/trace。
- **因为流程固定就认为不需要可靠性设计。** 不用 agent framework 也要处理超时、错误、预算、权限和副作用恢复。
- **因为已经选了某框架就停止复核。** 版本升级、provider 变化、团队与业务风险变化，都可能改变取舍；记录重新评估的触发条件。
