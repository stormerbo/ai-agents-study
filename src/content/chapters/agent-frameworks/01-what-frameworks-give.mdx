第 11 章从零写了一个循环。这一章要回答的是：**当你决定用一个现成的框架时，你换来了什么、付出了什么。**

先给结论，后面几节展开：**框架把一批常见决策封装成可复用构件和默认行为，减少部分胶水代码；代价是你需要理解这些默认行为的适用范围，并在关键路径上保留检查与覆盖能力。** 默认值是否适合你的任务，要靠具体配置和验收来判断。

## 选型时可检查的四类能力

下面四类是**便于检查的视角，不是穷尽分类**；不同框架会合并、拆分或用不同名字描述它们。它们也会重叠：一次 tool call 既涉及工具 schema，也涉及控制流、状态和 tracing。不要只凭类别名判断功能，应该核对你使用的具体 SDK、版本和配置。

**一、工具接入。** 框架可能提供函数包装器、schema 推断、工具调用分发和结果适配。有的从类型注解推断 schema，有的要求显式声明，也可能允许两者混用。以 [LangChain 当前工具文档](https://docs.langchain.com/oss/python/langchain/tools) 为例，工具类型注解定义输入 schema，也可提供 Pydantic 或 JSON Schema。生成之后仍应检查必填字段、枚举和值域是否符合任务契约；后面的固定旧版示例不代表当前所有版本。

**二、控制流。** 框架可能提供顺序执行、图或路由、handoff、重试等构件。要确认它们的终态、异常、取消和恢复语义，而不只看流程图能否画出来。

**三、状态与持久化。** 对话历史、运行状态、检查点和长期记忆不是同一个东西。框架可能只提供进程内状态，也可能有持久化接口；崩溃恢复、版本迁移和并发语义要按实际 backend 与配置核对。

**四、可观测性。** Tracing、日志、指标和供应商 dashboard 都可能帮助定位问题。框架自带 trace 的字段覆盖、导出目标、采样和保留策略各不相同；它不能单独证明根因，也不保证涵盖业务事件。发送输入、输出或工具参数前，还要确定脱敏、访问和保留策略。

下文关于四类能力的优先级是**作者的选型经验，不是跨框架对照实验**。哪类收益更大取决于任务、团队和部署要求；框架与版本更新后，应重新核对功能和默认值。

把四类展开成选型清单（示例：构造数据，未实跑）：

| 检查视角 | 要核实的具体能力 | 本例需求 |
|---|---|---|
| 工具接入 | 生成 schema 后是否含所需 required、enum 与约束 | 检查 30 个工具是否需要集中维护；数量本身不决定选择 |
| 控制流 | 重试、分支、取消和恢复由谁负责 | 只有两个分支时，比较框架方案与显式代码的维护成本 |
| 状态与持久化 | 状态存储、进程重启和版本迁移语义 | 若要求崩溃恢复，验证具体 backend 的恢复路径 |
| 可观测性 | trace/span 中可见哪些事件与字段，数据如何保留 | 只记录排障所需字段，并验证敏感数据处理 |

这张表的作用不是把框架打分，而是把“好用”拆成可以查文档、跑小实验和审查配置的主张。

## 框架不会替团队承担的责任

框架能提供构件与默认行为，但最终责任仍在集成它的应用：

- **基础模型能力不会因此自动提升。** 框架可能改变请求格式、提示模板、重试或模型路由，所以端到端表现需要在实际配置下评估。
- **提示与上下文仍需设计。** 框架可以提供模板和消息管理，但不会自动知道你的任务需要哪些事实、边界和验收条件。
- **业务架构仍需由团队决定。** 框架的默认组织方式不一定适合你的恢复、权限或审计要求。
- **运行时限制不等于业务保证。** 最大轮数、重试、guardrails 或并发限制的语义各异；例如 [OpenAI Agents SDK 的 `max_turns`](https://openai.github.io/openai-agents-python/running_agents/) 限制 runner 轮数，并不等于总 token/金额预算、外部写入幂等或跨重试恢复保证。选型时逐项核对文档，并在目标任务上测试。

因此，“用了框架，agent 还是不好用”不能直接归因于框架。先把请求构造、模型行为、工具实现、业务规则和运行边界分开观察，再定位哪一层需要改变。

## 决定之前该问的三个问题

**问题一：你要用它的哪项能力？** 用工具接入为例，比较手写 schema 与框架生成 schema 的内容、校验行为和维护方式。不要假设代码行数能代表维护成本；重点是生成产物是否满足接口契约，以及升级时能否重新验证。第 4 章曾记录一个 enum 对照的历史小样本，证据边界见下文；不能把它当成所有框架或模型的普遍效果。

**问题二：它的控制流抽象能不能表达你的分支？** 拿实际流程中的失败、人工审批、取消或动态路由路径核对。若要绕开抽象，记录绕行的位置、恢复语义和测试责任，再判断这种代价是否可接受。

**问题三：发生故障时能取得哪些证据？** 先确认框架 trace、应用日志、指标和 provider dashboard 各自覆盖什么，再注入一个无害的工具异常，检查你能否关联运行、步骤、错误类别和耗时。注意不要为了排障默认记录敏感 prompt 或完整工具参数；例如 [OpenAI Agents SDK tracing 文档](https://openai.github.io/openai-agents-python/tracing/) 说明 span 可能捕获输入/输出，默认配置与脱敏方式需要审查。缺少某种 trace 时，日志、指标或可控重现仍可能提供线索；可观测性不足通常让定位更困难，但不意味着只能猜。

三个问题的答案应落到可检查的证据：官方文档、生成的 schema、一个本地分支测试，以及异常路径可见字段。先做多大规模的 PoC 取决于集成成本；这里不把完成时间设成固定验收标准。

下面的两条记录是构造示例，未实跑：它们只说明不同可见字段可能怎样影响排查，不能证明任一框架真实输出这些内容。

```text
无步骤关联的错误记录： ToolException: boom

带步骤关联的诊断记录：
  run=... step=3 tool=get_weather outcome=error category=timeout duration_ms=...
  run=... step=4 model_call input_tokens=... output_tokens=...
```

后者包含更多定位线索；上线前仍需核对字段定义、隐私策略与数据保留。

## 一个判断方法：列清楚框架接管了哪些责任

第 11 章末尾给过一条判据，这里把它改成可核验的清单：

**对每条关键路径，写出框架负责的步骤、应用仍负责的步骤，以及失败后如何恢复。** 例如标明请求构造、schema 校验、工具授权、重试、持久化和外部副作用分别由哪一层负责。

这张清单不能单独证明框架适合你，但能发现责任空档与重复实现。再用目标版本的文档和失败路径测试逐项核对，才有选型依据。


## 一个具体的对照：省下的和失去的

比较工具定义时，把“手写”和“框架生成”的**最终 schema**放在一起，而不是只比较源码行数：手写方式让 schema 显式可见；函数包装器可以减少重复声明，并从函数签名推断输入字段。最终产物仍需检查，因为注解、文档字符串和框架配置分别影响 schema 的哪些部分，要以该版本文档和实际生成结果为准。

下面的可运行示例固定了 LangChain 与 Pydantic 版本，只在本地构造工具 schema；它不调用模型或 provider。结果显示：在这一组版本与这个函数定义中，普通 `str` 没生成 enum，而 `Literal` 生成了 enum。它说明要检查生成产物，不能推出其他版本、其他装饰器或其他框架也有相同结果。

第 4 章曾留下 enum 约束与自由字符串的 3/3 对 0/3 历史摘要。原始逐次响应、完整请求和评分器未归档，本轮无法独立复核；这个小样本不能作为通用成功率或因果结论。

**这笔交易不是简单的“框架更短”**：框架可能省去重复 schema 声明，但 schema 的生成规则和版本变化也成为你必须检查的依赖。需要精确约束时，可显式提供 schema，或采用该版本支持的类型标注，再验证最终结果。

## 完整可运行代码

环境：Python 3.10、`langchain==0.3.7`、`langchain-core==0.3.63`、`pydantic==2.9.2`。可在干净虚拟环境中安装这些固定版本；示例只创建本地工具定义并读取 schema，不需要 API Key，也不会调用模型。

```bash
python -m pip install "langchain==0.3.7" "langchain-core==0.3.63" "pydantic==2.9.2"
```

```python
"""比较 LangChain 工具注解生成的本地 JSON Schema；不发起 provider 请求。"""

import json
from typing import Literal

import langchain
import langchain_core
import pydantic
from langchain_core.tools import tool


@tool
def plain_weather(city: str, day: str) -> str:
    """查询天气。

    Args:
        city: 城市名
        day: 只支持明天或后天
    """
    return f"{city} {day}: fixture"


@tool
def literal_weather(city: str, day: Literal["明天", "后天"]) -> str:
    """查询天气。

    Args:
        city: 城市名
        day: 查询日期
    """
    return f"{city} {day}: fixture"


if __name__ == "__main__":
    plain_day = plain_weather.args_schema.model_json_schema()["properties"]["day"]
    literal_day = literal_weather.args_schema.model_json_schema()["properties"]["day"]
    print(f"langchain={langchain.__version__}")
    print(f"langchain-core={langchain_core.__version__}")
    print(f"pydantic={pydantic.__version__}")
    print("plain.day=" + json.dumps(plain_day, ensure_ascii=False, sort_keys=True))
    print("literal.day=" + json.dumps(literal_day, ensure_ascii=False, sort_keys=True))
    print("provider request: none (local schema construction only)")
```

**实跑状态（仅本地 schema 构造，不调用 provider）**：Python 3.10 环境中运行下例，输出如下：

```text
langchain=0.3.7
langchain-core=0.3.63
pydantic=2.9.2
plain.day={"title": "Day", "type": "string"}
literal.day={"enum": ["明天", "后天"], "title": "Day", "type": "string"}
provider request: none (local schema construction only)
```

此输出只描述上面固定版本的本地 schema 生成结果。它不评测工具调用成功率、模型行为、框架性能或生产可观测性。

## 一个容易被忽略的成本：学习曲线也是成本

评估框架时，「上手快」是一个维度，长期维护和扩展成本是另一个维度。短期 demo 的体验不能代表遇到边界场景后的成本；抽象泄漏也不是必然事件，但需要检查扩展点、逃生口和迁移路径。

一个实际的评估办法是：对照一个明确的需求，问“如果当前抽象不能直接表达它，我可以怎样扩展或绕开？”答案会影响你的后续维护成本：

- 如果你的答案是「绕开它，自己写那一小段」 → 评估框架是否允许，以及升级后是否仍可维护
- 如果答案是「等它支持」或者「换框架」 → 这笔成本要在选型时就算进去

本节的 enum 例子展示了一种扩展方式：把 `str` 改为 `Literal`。其他扩展点是否足够，应以具体框架和版本测试；若无法绕开，还要比较替代实现和迁移成本。

## 一个判断清单

把这一节的内容压成一份可以在选型会上逐条过的清单：

| 问题 | 为什么问 |
|---|---|
| 它解决哪一项具体需求？ | 避免只按功能数量或宣传语选型 |
| 我的关键失败分支能表达吗？ | 检查重试、取消、审批和恢复语义 |
| 不满足需求时能否扩展或绕开？ | 评估维护成本与迁移路径 |
| 出问题时我能看到中间状态吗？ | 没有可观测性，故障排查只能猜 |
| 框架与应用各自负责什么？ | 避免授权、校验、预算或恢复责任留空 |

五条可以作为审查起点，不是覆盖所有框架风险的完整清单。框架在常见路径上可能省事；当默认行为不满足需求时，再核对配置、扩展点和实现边界。

## 常见坑

- **把框架能力等同于模型能力。** 框架可能改变请求与运行方式，但应在目标配置上评估端到端效果。
- **只看工具 schema 是否自动生成。** 还要检查最终字段、值域、运行校验和版本变化。
- **把 tracing 当作唯一排障手段。** 按需组合 trace、日志、指标和可控重现，并执行脱敏与访问控制。
- **把“能编排”当成充分理由。** 还要核对异常、取消、重试、授权和恢复语义。
- **没有写清责任边界。** 标明框架、应用与 provider 各自负责的校验和副作用，避免默认值被误当成业务保证。
