第 11 章从零写了一个循环。这一章要回答的是：**当你决定用一个现成的框架时，你换来了什么、付出了什么。**

先给结论，后面几节展开：**框架换来的是「一批常见决定被默认做对了」，付出的是「你不再知道那些决定的具体内容」。** 前者省时间，后者在出问题时要命。

## 框架提供的四类东西

把市面上这些框架的功能拆开，大体是四类。

**一、工具接入。** 一个装饰器把普通函数变成模型能调用的工具，schema 从类型注解和文档字符串推断。这是各家都做得最成熟的一块，也是省事最明显的一块。

**二、控制流编排。** 把多个调用串起来：顺序链、状态图、路由分支。它决定了你能表达多复杂的流程，以及流程能不能被序列化和恢复。

**三、状态与记忆。** 会话历史怎么存、存到哪、怎么在崩溃后恢复。这一块各家的差异极大 —— 有的只给你一个内存里的对话数组，有的提供可插拔的持久化。

**四、可观测性。** 调用链追踪、每一步的输入输出、token 统计。这一块在调试时价值很高，而在生产里往往是你判断「哪一步慢、哪一步贵」的唯一依据。

四类里，**第一类最成熟、第四类最实用、第三类差异最大。** 而第二类是最容易让人误判的 —— 因为「能编排」听起来是核心能力，实际用起来最常撞到抽象泄漏（第 3 节）。

把四类展开成一张表，就是选型会上能直接用的能力清单（示例：构造数据，未实跑）：

| 类别 | 框架实际提供什么 | 我需要它吗 |
|---|---|---|
| 工具接入 | 装饰器从类型注解生成 schema | 工具 30 个，需要 |
| 控制流编排 | 链 / 图 / 条件边 | 分支只有 2 个，不需要 |
| 状态与记忆 | 内存里的对话数组 | 要求崩溃恢复，不够 |
| 可观测性 | 回调 + trace | 最需要 |

**右列必须逐条回答** —— 它逼你把「这个框架挺好用」拆成「它具体替我做哪一件事」。

## 框架不提供的东西

同样重要的是它**不**提供的：

- **不提供模型能力**。它调的还是同一个 API、同一个模型。
- **不提供提示词质量**。第 2 章讲的那些东西，框架替不了你写。
- **不提供正确的架构决定**。第 10 章那五种范式该选哪个，框架不会告诉你。
- **不提供成本控制**。预算、熔断、幂等这些，第 9 章和第 11 章讲的闸门，大多数框架要么没有，要么只给一半。

所以一个常见的失望是：「用了框架，agent 还是不好用。」那是因为不好用的原因本来就不在框架覆盖的那一层。

## 决定之前该问的三个问题

**问题一：你要用它的哪一类能力？** 如果只是第一类（工具接入），那收益有限 —— 手写 schema 也就几十行，而且你能精确控制 `enum`、取值范围、字段描述这些真正影响模型行为的东西（第 4 章实测过它们的差别是 3/3 对 0/3）。

**问题二：它的控制流抽象能不能表达你的分支？** 把你的流程图拿给它对一遍。如果一个常见需求（重试、人工审批、动态分支）需要绕开它的抽象才能实现，那就是第 3 节讲的那种泄漏。

**问题三：出问题时你能不能看到中间状态？** 这是第四类能力。**没有可观测性的框架，出故障时你只能猜。** 而猜在这里的代价很大 —— 第 10 章那条「先确认停止原因，再解释结果」的教训就是这个意思。

三个问题的答案决定了框架值不值。而它们的答案都不是「这个框架好不好」，是「你的任务和它的形状合不合」。

### 三个问题各自的验收动作

三个问题都容易答成「感觉」。给每个问题配一个半小时内能做完的动作：

| 问题 | 验收动作 | 期望看到的证据 |
|---|---|---|
| 用它的哪一类能力？ | 列出你打算交给它的能力，逐条标「有它更好 / 没它也行」 | 至少有一条「没它也行」，说明没被锁死 |
| 控制流表达得了吗？ | 拿最复杂的分支，只用它的抽象写一遍（先不接模型） | 能跑通，或能明确指出卡在哪一步 |
| 出故障看得到吗？ | 故意让一个工具抛异常，看它输出了什么 | 能看到「哪一步、什么错」，而不只是一个异常类型 |

三个动作里第三个最值得先做：通常只要十几分钟，却能直接暴露可观测性上的缺口 —— 而这一项在出故障那天是救命的。

具体差别长什么样（示例：构造数据，未实跑）—— 同一次工具异常，两种输出的信息量完全不同：

```text
无可观测性：  ToolException: boom

有可观测性：
  第 3 步 tool=get_weather 输入 {"city":"北京"} 耗时 1.2s 结果=error("下游超时")
  第 4 步 model 调用 输入 812 token 输出 96 token
```

前者只告诉你「它挂了」；后者能让你定位到「第 3 步的工具超时，模型在第 4 步收到了它」。**排查方向的差别就在这里。**

## 一个判断方法：能不能说出它替换掉了哪几行

第 11 章末尾给过一条判据，这里值得重复，因为它最实用：

**如果你能说清楚框架在你的循环里替换掉了哪几行代码，你就有能力判断它值不值得。**

反过来，如果你说不出它做了什么，那么它出问题时你也说不出该从哪查。

这条判据有一个具体的好处：它把选型从「感觉哪个更先进」变成了「我能列出它的作用清单」。而清单是可以逐条核对的。


## 一个具体的对照：省下的和失去的

把「框架版」和「手写版」的工具定义并排放一次，能看清这笔交易的具体内容。

框架版：

```python
@tool
def get_weather(city: str, day: str) -> dict:
    """查询某个城市某一天的最高气温（摄氏度）。

    Args:
        city: 城市名
        day: 只支持「明天」或「后天」
    """
    return TEMP.get((city, day), {"error": "没有数据"})
```

手写版是一个字典：

```python
{"name": "get_weather",
 "description": "查询某个城市某一天的最高气温（摄氏度）。",
 "input_schema": {"type": "object",
                  "properties": {"city": {"type": "string"},
                                 "day": {"type": "string", "enum": ["明天", "后天"]}},
                  "required": ["city", "day"]}}
```

**框架版更短、更好读、文档和实现放在一起。** 这些是真实的收益，不该低估 —— 尤其在工具很多的时候，手写 schema 会变成一件很容易写错、很难维护的事。

但第 3 节会看到：框架版生成出来的 schema **少了那个 enum**。而第 4 章实测过，enum 与自由字符串的差别是 3/3 对 0/3。

**这就是这笔交易的本质：你省下了写 schema 的功夫，代价是 schema 的最终形态不由你决定。** 想要拿回来，你得了解它内部怎么翻译类型注解 —— 那就进入了第 3 节讲的泄漏。
## 完整可运行代码

下面这段代码用真实的 LangChain（0.3.7）定义工具，并把生成的 schema 原样打印出来 —— 你会看到框架替你生成了什么，以及它漏掉了什么。

```python
"""真框架对照：同一个任务，手写循环 vs LangChain。

不是性能对比 —— 比的是三件事：
  1. 代码量
  2. 你能看见什么、看不见什么
  3. 想加一个需求时，需要在哪里「逃出抽象」

实跑状态：2026-10-09，langchain 0.3.7 + deepseek-flash（Anthropic 兼容端点）。
"""
import os, json, time

print("langchain 版本：", end="")
import langchain
print(langchain.__version__)

from langchain_core.tools import tool as lc_tool
from langchain_anthropic import ChatAnthropic

TEMP = {("北京", "明天"): 31, ("上海", "明天"): 27, ("广州", "明天"): 34}

# ---- 手写版的工具定义：schema 与实现分开写 ----
HAND_TOOLS = [{
    "name": "get_weather",
    "description": "查询某个城市某一天的最高气温（摄氏度）。",
    "input_schema": {"type": "object",
                     "properties": {"city": {"type": "string"},
                                    "day": {"type": "string", "enum": ["明天", "后天"]}},
                     "required": ["city", "day"]},
}]


def hand_get_weather(city, day):
    return TEMP.get((city, day), {"error": "没有数据"})


# ---- 框架版的工具定义：一个装饰器，schema 从类型注解推断 ----
@lc_tool
def get_weather(city: str, day: str) -> dict:
    """查询某个城市某一天的最高气温（摄氏度）。

    Args:
        city: 城市名
        day: 只支持「明天」或「后天」
    """
    return TEMP.get((city, day), {"error": "没有数据"})


if __name__ == "__main__":
    print()
    print("=== 1. 代码量 ===")
    print("手写版工具定义：%d 行（schema 手写）" % len(json.dumps(HAND_TOOLS, ensure_ascii=False).split(chr(10))))
    print("框架版工具定义：6 行（一个装饰器 + 文档字符串）")
    print("→ 框架在「schema 生成」这一层确实省事")
    print()

    print("=== 2. schema 长什么样（框架替你生成了什么）===")
    print(json.dumps(get_weather.args_schema.model_json_schema(), ensure_ascii=False, indent=1)[:600])
    print()

    print("=== 3. 一个抽象泄漏的现场 ===")
    print("题目：它的 input_schema 里有没有 enum 约束？")
    schema = get_weather.args_schema.model_json_schema()
    print("day 的定义：", json.dumps(schema["properties"].get("day"), ensure_ascii=False))
    if "enum" not in json.dumps(schema["properties"].get("day", {})):
        print("→ ❌ 没有 enum。文档字符串里写了「只支持明天或后天」，")
        print("   但生成的 schema 只有 type: string。")
        print("   而第 4 章实测过：enum 约束下模型 3/3 合法，自由字符串 0/3。")
        print("   要拿到 enum，必须逃出装饰器，改用 pydantic 的 Literal 或手动写 schema。")
    print()
    print("结论：抽象替你生成了「能用的」schema，但没有生成「最好的」schema。")
    print("      而第 4 章的实测说明这两者的差别是 0/3 和 3/3。")


# ==== 4. 逃出抽象：用 Literal 把 enum 找回来 ====
print()
print("=== 4. 逃出抽象之后 ===")
from typing import Literal


@lc_tool
def get_weather_v2(city: str, day: Literal["明天", "后天"]) -> dict:
    """查询某个城市某一天的最高气温（摄氏度）。

    Args:
        city: 城市名
        day: 明天或后天
    """
    return TEMP.get((city, day), {"error": "没有数据"})


schema2 = get_weather_v2.args_schema.model_json_schema()
print("day 的定义：", json.dumps(schema2["properties"].get("day"), ensure_ascii=False))
has_enum = "enum" in json.dumps(schema2["properties"].get("day", {}))
print("现在有 enum 了：%s" % ("✅ 是" if has_enum else "❌ 否"))
print()
print("代价：这已经不是在写「普通的 Python 函数」了 —— 类型注解从 str 变成了 Literal，")
print("      而 Literal 是为「生成 schema」这个目的服务的。这就是**抽象泄漏**：")
print("      为了拿到想要的效果，你必须了解抽象内部是怎么把注解翻译成 schema 的。")
```

实跑输出（2026-10-09，langchain 0.3.7）：

```text
=== schema 长什么样（框架替你生成了什么）===
{
 "description": "查询某个城市某一天的最高气温（摄氏度）。…",
 "properties": {
  "city": { "title": "City", "type": "string" },
  "day":  { "title": "Day",  "type": "string" }
 },
 "required": ["city", "day"],
 "type": "object"
}
```

注意 `day` 只有 `type: string` —— 详情见第 3 节。

代码里那个 `args_schema` 是装饰器注入的属性：`@lc_tool` 会把你的函数签名编译成一个 pydantic 模型，`args_schema` 就是它，`.model_json_schema()` 是把它转成 JSON Schema 的方法。另外，代码里 `from langchain_anthropic import ChatAnthropic` 这一行只是演示「模型接入也走这个包」，本例没有发请求，所以导入后没用到它。


## 一个容易被忽略的成本：学习曲线也是成本

评估框架时，「上手快」经常被当成主要优点。但它只在**短期**成立。

一个抽象越省事，它在泄漏时需要你了解的东西就越多 —— 而泄漏是迟早会遇到的。到那时你要读它的源码、查它的 issue、理解它的内部模型。**这部分成本在选型时几乎总是被低估**，因为它不会出现在「三天跑通 demo」的体验里。

一个更实际的评估办法：**问「三个月后我遇到一个它不支持的场景，我该怎么办」**。答案决定了两件事：

- 如果你的答案是「绕开它，自己写那一小段」 → 成本可控，前提是它允许你绕（不是所有框架都允许）
- 如果答案是「等它支持」或者「换框架」 → 这笔成本要在选型时就算进去

第 3 节那个 enum 的例子就是第一种：改一行注解就能绕开，成本很低。但有些框架把抽象做得很严密，你根本绕不开 —— 那时「省事」就变成了「受制」。

## 一个判断清单

把这一节的内容压成一份可以在选型会上逐条过的清单：

| 问题 | 为什么问 |
|---|---|
| 它能用在哪一类上？ | 工具接入是标配，差别在控制流和可观测性 |
| 我的最复杂分支它能表达吗？ | 表达不了就是选错了抽象 |
| 它允许我绕开吗？ | 不允许绕 = 泄漏时会卡死 |
| 出问题时我能看到中间状态吗？ | 没有可观测性，故障排查只能猜 |
| 我能不能说出它替换了哪几行？ | 说不出 = 不了解自己在依赖什么 |

五条里，**第三条最容易被忽略**。多数框架在用得顺的时候都很好；差别出现在你需要绕开它的时候 —— 而那一天一定会来。

## 常见坑

- **以为框架提供模型能力。** 它调的是同一个 API。agent 不好用，原因通常不在这层。
- **只评估第一类能力（工具接入）。** 那一类各家都成熟，差别不大；真正的差别在控制流和可观测性上。
- **不问「出问题时能不能看到中间状态」。** 没有可观测性的框架，故障排查只能靠猜。
- **把「能编排」当成核心卖点。** 编排是最容易撞到抽象泄漏的一块，见第 3 节。
- **说不出框架替换了哪几行。** 说不出就等于把关键路径交给了你不了解的东西。
