「抽象泄漏」是一个有明确含义的说法：**当一个抽象宣称替你处理了某个细节，但你在某些情况下不得不了解那个细节时，它就泄漏了。**

这一节不给理论，直接用真框架跑出一个泄漏现场。用的是 LangChain 0.3.7。

## 泄漏现场：装饰器生成的 schema 缺了 enum

先看它生成的完整 schema：

```text
{
 "description": "查询某个城市某一天的最高气温（摄氏度）。\n\nArgs:\n    city: 城市名\n    day: 只支持「明天」或「后天」",
 "properties": {
  "city": { "title": "City", "type": "string" },
  "day":  { "title": "Day",  "type": "string" }
 },
 "required": ["city", "day"],
 "title": "get_weather",
 "type": "object"
}
```

问题在 `day` 上：它只有 `type: string`。

而**文档字符串里明确写了「只支持『明天』或『后天』」** —— 这句话进了 `description`（在函数级描述里），却没有变成字段级的 `enum` 约束。

这个差别的代价有多大？第 4 章第 2 节实测过：**自由字符串 0/3 给出合法值，enum 3/3 合法。** 也就是说，装饰器生成的 schema 是一个「能用」的 schema，但它落在第 4 章那个 0/3 的档位上。

## 抽象泄漏的定义在这里怎么体现

按定义检查：

- **抽象宣称**：你写普通的 Python 函数，我用类型注解和文档字符串自动生成 schema。
- **实际情况**：它能生成 object / string / integer / required，但生成不了 enum。
- **结果**：要拿到 enum，你必须知道「它内部是把注解翻译成 JSON Schema 的」—— 然后改写注解。

改法是用 `Literal`：

```python
from typing import Literal

@tool
def get_weather_v2(city: str, day: Literal["明天", "后天"]) -> dict:
    ...
```

再打印一次，schema 里就有了：

```text
day 的定义： {"enum": ["明天", "后天"], "title": "Day", "type": "string"}
```

**问题解决了，但注意代价：这已经不是在写「普通的 Python 函数」了。** `str` 变成 `Literal["明天", "后天"]` 这个改动的唯一目的，是让框架生成出你想要的东西。你为了用一个抽象，不得不了解它内部的翻译规则。

这就是泄漏：**抽象没有消失，它只是从「你不需要知道」变成了「你必须在某些时候知道」。**

## 三类常见的泄漏

按出现频率排，框架类的抽象有三处最容易漏。

**第一类：schema 与约束。** 就是上面这个例子。凡是「从类型注解推断 schema」的抽象，都会在枚举、范围、格式、条件必填这些约束上泄漏 —— 因为 Python 的类型系统表达不了它们（这正是第 5 章讲 JSON Schema 那一节的内容）。

**第二类：错误处理。** 抽象通常定义一个「错误」的概念，但真实的错误有层次：可以重试的、不能重试的、状态未知的。第 4 章实测过「状态未知」这个特殊情形 —— 模型面对它会主动不重试。而框架的错误类型里往往没有这个区分，你要么自己包一层，要么把语义丢掉。

**第三类：控制流的边角。** 重试与退避、超时、并发限制、人工审批中断 —— 这些在流程图上是小方块，在抽象里往往需要特殊的钩子。第 11 章第 4 节那个断点恢复就是个例子：状态持久化和「副作用不重复」是两件事，而多数框架只提供前者。

## 怎么面对泄漏

三步，都不复杂：

**第一步，把抽象生成的东西打印出来看。** 这是本节做的事 —— 它不需要读源码，只要把 schema、把发出去的消息、把错误对象打出来。**用真框架跑一次，比读十页文档有用。**

**第二步，测试边界而不是测试正路。** 正路框架都替你测过了。该测的是：参数越界时它怎么处理？工具抛异常时错误长什么样？中断之后能不能恢复？这些正是泄漏发生的地方。

**第三步，为每个泄漏记一笔。** 记下「哪个需求需要绕开抽象、怎么绕」。这份清单就是你的迁移成本 —— 第 5 节会用到它。

## 一个反过来的视角

泄漏不全是坏事。**一个从不泄漏的抽象，通常意味着它能表达的东西很少。**

链（chain）抽象就很少泄漏 —— 因为它只做一件事：按顺序调用。你几乎不会遇到「需要绕开它」的情况，因为你能想到的需求它都表达不了，你也不会拿它做那些事。

所以判断标准不是「有没有泄漏」，而是：**泄漏的地方，是不是你真正需要的地方。**

- 如果你的任务不需要 enum（比如参数本来就是自由文本），那这个泄漏对你没有影响
- 如果你需要精确的 schema 约束，那它每一天都在影响你

这也是为什么「哪个框架好」没有通用答案 —— 答案取决于你的需求落在它的泄漏区还是覆盖区。

## 完整可运行代码

下面这段代码用真实的 LangChain 跑一遍上面的对照：先打印装饰器生成的 schema，再用 Literal 拿回 enum。

```python
"""真框架对照：同一个任务，手写循环 vs LangChain。

不是性能对比 —— 比的是三件事：
  1. 代码量
  2. 你能看见什么、看不见什么
  3. 想加一个需求时，需要在哪里「逃出抽象」

实跑状态：2026-10-09，langchain 0.3.7 + deepseek-flash（Anthropic 兼容端点）。
"""
import os, json, time

print("langchain 版本：", end="")
import langchain
print(langchain.__version__)

from langchain_core.tools import tool as lc_tool
from langchain_anthropic import ChatAnthropic

TEMP = {("北京", "明天"): 31, ("上海", "明天"): 27, ("广州", "明天"): 34}

# ---- 手写版的工具定义：schema 与实现分开写 ----
HAND_TOOLS = [{
    "name": "get_weather",
    "description": "查询某个城市某一天的最高气温（摄氏度）。",
    "input_schema": {"type": "object",
                     "properties": {"city": {"type": "string"},
                                    "day": {"type": "string", "enum": ["明天", "后天"]}},
                     "required": ["city", "day"]},
}]


def hand_get_weather(city, day):
    return TEMP.get((city, day), {"error": "没有数据"})


# ---- 框架版的工具定义：一个装饰器，schema 从类型注解推断 ----
@lc_tool
def get_weather(city: str, day: str) -> dict:
    """查询某个城市某一天的最高气温（摄氏度）。

    Args:
        city: 城市名
        day: 只支持「明天」或「后天」
    """
    return TEMP.get((city, day), {"error": "没有数据"})


if __name__ == "__main__":
    print()
    print("=== 1. 代码量 ===")
    print("手写版工具定义：%d 行（schema 手写）" % len(json.dumps(HAND_TOOLS, ensure_ascii=False).split(chr(10))))
    print("框架版工具定义：6 行（一个装饰器 + 文档字符串）")
    print("→ 框架在「schema 生成」这一层确实省事")
    print()

    print("=== 2. schema 长什么样（框架替你生成了什么）===")
    print(json.dumps(get_weather.args_schema.model_json_schema(), ensure_ascii=False, indent=1)[:600])
    print()

    print("=== 3. 一个抽象泄漏的现场 ===")
    print("题目：它的 input_schema 里有没有 enum 约束？")
    schema = get_weather.args_schema.model_json_schema()
    print("day 的定义：", json.dumps(schema["properties"].get("day"), ensure_ascii=False))
    if "enum" not in json.dumps(schema["properties"].get("day", {})):
        print("→ ❌ 没有 enum。文档字符串里写了「只支持明天或后天」，")
        print("   但生成的 schema 只有 type: string。")
        print("   而第 4 章实测过：enum 约束下模型 3/3 合法，自由字符串 0/3。")
        print("   要拿到 enum，必须逃出装饰器，改用 pydantic 的 Literal 或手动写 schema。")
    print()
    print("结论：抽象替你生成了「能用的」schema，但没有生成「最好的」schema。")
    print("      而第 4 章的实测说明这两者的差别是 0/3 和 3/3。")


# ==== 4. 逃出抽象：用 Literal 把 enum 找回来 ====
print()
print("=== 4. 逃出抽象之后 ===")
from typing import Literal


@lc_tool
def get_weather_v2(city: str, day: Literal["明天", "后天"]) -> dict:
    """查询某个城市某一天的最高气温（摄氏度）。

    Args:
        city: 城市名
        day: 明天或后天
    """
    return TEMP.get((city, day), {"error": "没有数据"})


schema2 = get_weather_v2.args_schema.model_json_schema()
print("day 的定义：", json.dumps(schema2["properties"].get("day"), ensure_ascii=False))
has_enum = "enum" in json.dumps(schema2["properties"].get("day", {}))
print("现在有 enum 了：%s" % ("✅ 是" if has_enum else "❌ 否"))
print()
print("代价：这已经不是在写「普通的 Python 函数」了 —— 类型注解从 str 变成了 Literal，")
print("      而 Literal 是为「生成 schema」这个目的服务的。这就是**抽象泄漏**：")
print("      为了拿到想要的效果，你必须了解抽象内部是怎么把注解翻译成 schema 的。")
```

## 泄漏的第三种形态：错误语义被压平

第三类泄漏（控制流的边角）值得单独展开，因为它最不容易被发现。

真实的工具失败有三层语义，第 4 章实测过它们的区别：

- **可以重试的失败**（网络抖动、限流）→ 应该重试
- **不能重试的失败**（参数错误、权限不足）→ 应该修正或放弃
- **状态未知的失败**（超时后不知道操作是否生效）→ **不应该重试**，因为可能有副作用

而框架通常只有一个「错误」的概念。当你把一个「状态未知」包装成框架的普通异常时，框架的重试机制会**帮你重试** —— 于是副作用执行了两次。

这和第 11 章第 4 节那个 `u1, u2, u2, u3` 是同一个问题，只是触发路径不同：那次是进程崩溃，这次是框架的重试。**两者的根因都是「错误语义被压平」。**

所以在评估框架时，有一个具体的问题值得问：**它的重试机制能不能区分「可以重试」和「状态未知」？** 如果答案是不能，那你至少要知道这一点，并在工具层自己处理幂等。

## 泄漏区往往就是价值区

最后补一个反过来的观察：**框架替你处理得越好的地方，通常越不是你的差异化所在；而它泄漏的地方，往往正好是你业务里最有价值的部分。**

schema 生成是很标准的活，框架做得好、泄漏也少（除了 enum 这种边界）。而预算、熔断、幂等、错误分层这些 —— 恰恰和第 9 章那四道闸门一样 —— 是需要按业务定制的地方。

所以「框架省下的 ≠ 你需要的」这句话，可以更准确地表述为：**框架省下的是通用问题，泄漏的是定制问题。** 而你的系统值不值钱，取决于定制问题解决得怎么样。

## 一个判断泄漏严重程度的方法

不是所有泄漏都一样严重。有三个维度可以用来分级：

**一、绕开它需要改多少地方。** 那个 enum 的例子只需要改一个类型注解 —— 影响面是一处。而如果某个泄漏需要你在每个工具上包一层，那就是系统性成本。

**二、绕开之后会不会破坏抽象的其他部分。** 有些绕法会连带失效（比如你手写了 schema，装饰器的自动校验就不生效了）。这种泄漏的代价是双份的。

**三、泄漏区是不是你的高频需求。** 如果你的工具参数基本都是自由文本，那 enum 这个泄漏你一辈子碰不到几次；如果每个工具都有枚举字段，它每天都在影响你。

三个维度合起来给出一个判断：**频次 × 影响面 × 连带代价**。低的可以忽略，高的要在选型时就算进成本。
## 常见坑

- **只看文档，不打印生成物。** 把 schema、发出的消息、错误对象打出来看，比读十页文档有用。
- **只测正路。** 正路框架已经测过了。泄漏发生在参数越界、工具异常、中断恢复这些边界上。
- **把泄漏当成「框架的 bug」。** 它多半是类型系统的表达力边界，不是实现缺陷 —— 换成任何一家都一样。
- **追求零泄漏的抽象。** 从不泄漏通常意味着表达力很低。该问的是「泄漏的地方是不是我需要的地方」。
- **不记录绕开抽象的地方。** 那些绕法就是你的迁移成本，不记下来，下次换框架还得重新发现一遍。
