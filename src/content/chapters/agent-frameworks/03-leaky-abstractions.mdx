「抽象泄漏」指一个抽象隐藏了实现细节，但在某些需求或故障路径上，使用者仍必须理解、配置或绕过该细节。它不是框架质量差的同义词；关键是明确**哪项需求触发下探、谁负责保证行为、绕行会带来什么维护成本**。

下面用一个固定版本的 LangChain 工具 schema 例子说明：类型注解可以生成字段约束，散文描述则不会自动变成机器可校验的枚举。示例只看本地生成的 JSON Schema，不请求模型。

## 泄漏现场：字段说明不是字段约束

在 LangChain `0.3.7` / `langchain-core 0.3.63` 中，`@tool` 默认根据函数签名推断参数 schema；`parse_docstring` 默认关闭。普通 `str` 参数生成 `type: string`，不会因为文档字符串里写了「只支持明天或后天」就自动生成 enum。`Literal["明天", "后天"]` 则能在该版本的本地 schema 中表达枚举。参数说明解析与 schema 约束是两件事；即使打开 docstring 解析，说明文本也不能代替类型约束。

早期章节曾把这一现象描述成装饰器无法生成 enum，并引用 2026-10-08 记录的自由字符串 `0/3`、enum `3/3` 结果。前半句过度概括：这个固定版本支持 `Literal`。后半句缺少逐次响应、完整请求、模型快照与评分器，当前无法独立复核，因此只保留为历史摘要，不用于证明 enum 导致成功率提高。下面的可运行例子只验证本地 schema，不验证模型行为。

## 抽象泄漏的定义在这里怎么体现

按定义检查：

- **抽象提供的便利**：从函数签名推断参数 schema，避免手工重复声明字段。
- **触发下探的需求**：调用方需要机器可校验的枚举，而普通 `str` 只表达了字符串类型。
- **可用的扩展点**：在本节固定版本中可以使用 `Literal`、显式 Pydantic `args_schema`，或经验证的 JSON Schema。具体方案取决于校验、维护和目标 provider 的兼容要求。
- **仍由应用负责的事**：检查最终生成的 schema，并在工具执行边界校验业务规则。schema 描述输入契约，不自动保证授权、数据库状态或业务副作用安全。

要拿到 enum，不需要猜内部实现：查看生成物，并核对框架版本文档与支持的输入类型。这里的下探只需改一处注解；其他框架、版本或复杂约束可能需要不同做法。

## 常见的泄漏检查面

下面三类是审查时常见的检查面，**不是按实测频率排序的结论，也不是完整分类**。

**第一类：schema 与约束。** 从函数签名推断 schema 时，检查必填字段、枚举、格式、范围和嵌套对象是否出现在最终产物中。注解或显式 schema 能表达哪些约束，要按具体版本验证。模型输出即使符合 schema，也仍需应用校验权限与业务条件。

**第二类：错误与重试策略。** 错误可按来源区分，例如本地输入校验失败、provider 返回的终态错误、网络/API 失败、工具执行失败，以及结果状态未知。并非每个框架都把这些类别映射成同一种异常，也不能笼统断言框架会自动重试。核对具体 SDK 的默认行为、错误类型和可配置策略。对于可能产生副作用的工具，超时只说明调用方未及时收到结果，不能单独证明远端操作没有发生；只有应用层具备幂等保障，或状态查询/对账确认操作尚未生效时，才有依据重放该工具操作。provider 对模型请求的 replay-safety 提示只适用于该 provider 请求，不能证明工具副作用安全。否则应暂停并进入查询、人工处理或补偿流程。

**第三类：控制流与恢复边界。** 重试与退避、超时、并发限制、人工审批中断等，在不同框架里可能由内建配置、钩子或应用代码实现。第 11 章第 4 节的断点恢复也应按 runtime 与副作用边界理解：持久化工作流状态不等于外部写入 exactly-once；是否能恢复、何时重放、如何去重，都要针对具体执行路径验证。

## 怎么面对泄漏

可以用三步把抽象边界变成可检查的工程问题：

**第一步，检查实际产物。** 打印工具 schema、规范化后的请求、错误类型或恢复状态，并与目标 SDK 版本的文档对照。不要仅凭函数注解或配置文件推断运行时行为。离线 schema 检查能验证生成物，但无法替代一次目标 endpoint 的协议兼容测试。

**第二步，测试你负责的边界。** 覆盖缺字段、非法值、权限拒绝、超时、重复请求、中断恢复等与你的任务相关的条件。为每个测试写明预期责任层：SDK、应用、provider 或外部系统。边界集合由真实需求决定，所谓“正常路径都被框架测过”并不能替你的集成测试作保证。

**第三步，记录扩展和后果。** 写下绕过抽象的方法、升级时要复核的接口、附加的测试责任，以及绕行是否跳过原有校验或观测。清单可以帮助第 5 节比较迁移成本，但频次和影响面要来自你的项目数据，不能从一个例子外推。

### 泄漏登记表长什么样

「记一笔」要有固定字段，否则三个月后自己都看不懂。用这六个（示例：构造数据，未实跑）：

```json
{
  "need": "工具参数需要枚举约束",
  "workaround": "把 str 换成 Literal[\"明天\", \"后天\"]",
  "scope": "本仓库示例 1 个；真实项目数量待盘点",
  "breaks_other": "若改用显式 schema，需单独验证框架运行时是否仍应用预期的参数校验",
  "repro": "python3.10 experiments/scripts/verify_agent_frameworks_leaky_abstractions_w6.py",
  "cleanup": "改注解并更新 schema 回归检查；实际工时待测"
}
```

字段的判据：

- `need` 写**需求**，不是「哪里烦」。需求决定这条泄漏会不会反复出现。
- `workaround` 要具体到能照做 —— 只写「改注解」，三个月后等于没写。
- `scope` 给处数。这就是第 5 节估迁移成本的分母。
- `breaks_other` 记绕开后需要重新验证的其他保证，例如运行时解析、自动校验或观测；是否确实失效要实测。它对应本节末尾启发式中的「连带代价」。
- `repro` 是一条能重跑的命令或脚本名。**判据：照着它跑一遍能不能看到同一个现象。**
- `cleanup` 是换框架时每个点要动的工作量。

这份表是活的：每遇到一次泄漏就加一行，第 5 节的迁移成本估算直接从它求和。

## 一个反过来的视角

泄漏不全是坏事，也不能从“抽象没有泄漏”推出它表达力不足。抽象的目标、使用场景与边界各不相同；真正有用的判断是：**当前抽象覆盖了哪些需求，未覆盖时有哪些可维护的扩展方式？**

- 如果任务参数本来就是自由文本，就不需要枚举约束；但要确认下游是否接受任意字符串。
- 如果业务契约限定了值域，schema 可以描述这个约束；应用仍应按权限和业务状态做校验。
- 如果扩展点需要 fork 或复制大量内部实现，把这项成本与显式实现、其他框架的方案一起比较，不要直接推断抽象“安全”或“迟早成为负债”。

早期版本曾用「零泄漏意味着表达力很少」作为反向观察。它没有可检验的范围或证据，现改为需求驱动的检查方法。

> **历史说明（2026-10-09）**：当时写作曾把散文说明未形成 enum 的现象说成装饰器不能生成 enum。LangChain `langchain-core 0.3.63` 的官方 API 将 `parse_docstring` 默认值列为 `False`，该选项的作用是解析 Google Style 文档字符串中的参数说明；它不把说明文字转换为类型约束。函数注解或显式 schema 定义参数结构。当前章节用固定版本的本地示例核对普通 `str` 与 `Literal` 生成物；该例不代表其他版本或其他框架。

## 完整可运行代码

下面的代码固定 LangChain 与 Pydantic 版本，只在本地构造工具 schema。它分别检查普通 `str`、开启 `parse_docstring` 的参数说明，以及 `Literal` 枚举。示例不发送模型请求；它验证 schema 生成行为，不测模型是否遵守 schema。

```bash
python -m pip install "langchain==0.3.7" "langchain-core==0.3.63" "pydantic==2.9.2"
```

```python
"""比较函数类型、docstring 参数说明和 Literal 对本地 schema 的影响。"""

import json
from typing import Literal

import langchain
import langchain_core
import pydantic
from langchain_core.tools import tool


@tool
def plain_weather(city: str, day: str) -> str:
    """查询天气。

    Args:
        city: 城市名
        day: 只支持明天或后天
    """
    return f"{city} {day}: fixture"


@tool(parse_docstring=True)
def described_weather(city: str, day: str) -> str:
    """查询天气。

    Args:
        city: 城市名
        day: 只支持明天或后天
    """
    return f"{city} {day}: fixture"


@tool
def literal_weather(city: str, day: Literal["明天", "后天"]) -> str:
    """查询天气。"""
    return f"{city} {day}: fixture"


if __name__ == "__main__":
    plain_day = plain_weather.args_schema.model_json_schema()["properties"]["day"]
    described_day = described_weather.args_schema.model_json_schema()["properties"]["day"]
    literal_day = literal_weather.args_schema.model_json_schema()["properties"]["day"]
    print(f"langchain={langchain.__version__}")
    print(f"langchain-core={langchain_core.__version__}")
    print(f"pydantic={pydantic.__version__}")
    print("plain.day=" + json.dumps(plain_day, ensure_ascii=False, sort_keys=True))
    print("described.day=" + json.dumps(described_day, ensure_ascii=False, sort_keys=True))
    print("literal.day=" + json.dumps(literal_day, ensure_ascii=False, sort_keys=True))
    print("provider request: none (local schema construction only)")
```

**实跑状态（仅本地 schema 构造，不调用 provider）**：下方输出只适用于上列固定版本。实跑同时检查了 `parse_docstring=True`：参数说明可出现在字段描述中，但不会替代枚举约束。

```text
langchain=0.3.7
langchain-core=0.3.63
pydantic=2.9.2
plain.day={"title": "Day", "type": "string"}
described.day={"description": "只支持明天或后天", "title": "Day", "type": "string"}
literal.day={"enum": ["明天", "后天"], "title": "Day", "type": "string"}
provider request: none (local schema construction only)
```

这组结果把两种信息分开了：`description` 是给读者或模型看的说明，`enum` 才是 schema 中机器可检验的值域约束。不同 provider 对 schema 子集的接受行为仍要单独核实；接收方约束也不替代服务端业务校验。

## 错误语义与重放安全

第三类泄漏（控制流的边角）值得单独展开，因为它最不容易被发现。

工具或模型调用失败可从结果上区分，但不能仅凭异常名字得出统一重试规则：

- **明确未执行且暂时失败**（例如 provider 表示请求未接收）可能适合重试，仍需遵循服务端建议、预算和退避策略。
- **明确不可恢复的输入或授权错误**通常应修正请求、拒绝执行或交由业务流程处理。
- **状态未知**（例如调用方等待超时，但远端可能已经提交）不代表“一定不能重试”，而是**不能盲目重放有副作用的操作**。先用幂等键、状态查询或对账确认结果；如果无法判断，应暂停自动重试并转人工或补偿。

框架对模型请求和工具副作用的重试可能是不同机制。比如 [OpenAI Agents SDK 的模型文档](https://openai.github.io/openai-agents-python/models/) 将 runner 管理的模型重试设为 opt-in，并在策略上下文中提供 replay-safety 信息；这不能推出所有 SDK 的默认行为，也不意味着框架会替应用保证工具操作幂等。选型时应分别检查 provider 请求重试、工具执行重试和业务操作重放。

这与第 11 章第 4 节的崩溃恢复案例有相同的工程关注点：**恢复逻辑必须考虑外部系统是否已提交副作用**。故障时序相似，但不能仅凭一个案例断言根因一定是“错误语义被压平”。

## 泄漏区与业务价值

评估时可分别列出框架已经提供的通用能力，以及仍由应用决定的策略。预算、熔断、幂等、授权和错误恢复经常需要结合业务要求，但各框架与 SDK 覆盖范围不同，应逐项查看文档和配置，不能一概归为“泄漏”或“价值区”。

## 一个判断泄漏严重程度的方法

不是所有未覆盖的需求都一样。可以用三个维度记录**本项目中的**影响，而不是假设通用频率：

**一、绕开它需要改多少地方。** `Literal` 的例子在一个函数里只改一项注解；若相同需求散落在多个工具中，先盘点实际数量，再估算集中 schema 或公共校验能否减少重复维护。

**二、绕开之后会不会破坏其他保证。** 使用显式 schema 时，要验证工具构造、运行时解析和业务校验分别由谁负责；不要未经测试就假定自动校验一定保留或一定失效。

**三、该需求在自己的任务里出现多频繁。** 从 issue、调用数据或需求清单统计分母与时间窗口。没有数据时标成待盘点，不能把单例示例说成每天发生。

可以用「频次 × 影响面 × 连带代价」作为**项目内部的排序启发式**，但要先定义计数单位、观察窗口与影响等级。该乘积不是通用风险公式；当数据稀疏时，保留原始计数和不确定性，不要输出伪精确分数。

## 常见坑

- **只看文档，不打印生成物。** 对照 schema、规范化请求或错误对象，确认目标版本实际产生了什么。
- **把说明文本当成机器约束。** 分清 `description`、schema 关键字和应用侧校验；不要把其中一层当成另一层的保证。
- **把一个 SDK 的行为推广到所有框架。** 版本、配置、endpoint 和工具执行 runtime 都会改变责任边界。
- **把所有超时当成同一种失败。** 区分明确拒绝、可重试传输错误与结果状态未知；副作用调用先查询或去重，再决定是否重放。
- **把“逃逸测试”当成框架安全证明。** 它只能验证选定版本、配置、需求和失败路径；还要检查升级兼容性、权限、隐私与部署边界。
- **不记录绕开抽象的地方。** 记录需求、复现步骤、适用版本、验证结果和剩余责任；没有盘点的数据明确标成未知。
