前四节解决的是「怎么让模型这次答对」。这一节解决另一个问题：**怎么让它一直答对。**

多数 prompt 教程在结尾会给出两个「可靠性技巧」：**self-consistency**（同一问题问多次，取多数结果）和 **self-eval**（让模型检查自己的输出）。它们听起来都很合理 —— 都是我这一节要实测的东西。

这两组样本的历史记录是：算术/计数题上的多数投票没有增加观察到的正确率，但平均 token 更多；自查实验也只覆盖了构造的可独立重算错答。它们不能单独确定这两种方法在其他任务上的收益。

## 历史记录一：多数投票在这组样本中没有提升

以下数字来自 2026-10-08 的实验摘要。逐次请求/响应、精确模型版本、样本映射与评分器未归档，不能独立复算；将它们作为待复核观察，而不是可重复的实测结论。

任务：程序生成的算术与计数题（答案由代码算出，这一点很重要，后面会解释）。每题的配置是「单次采样」与「5 次采样取多数」。

| 写法 | 报告的正确数 | 报告的平均 token | token 体积比 |
|---|---:|---:|---:|
| 单次采样 | **10/10** | 237 | 1.0x |
| 5 次采样取多数 | **10/10** | **1281** | **5.4x** |

（实测数据，`deepseek-flash`，2026-10-08。）

self-consistency 是有论文研究的解码策略；原论文在其评测的算术与常识基准上报告了收益，但不能据此推断每个任务或端点都会改善。这里的历史样本缺少原始响应，无法与论文结果做可比复核。参见 [Self-Consistency Improves Chain of Thought Reasoning in Language Models](https://arxiv.org/abs/2203.11171)。

在这 10 道题的记录中，观察到的正确率相同；5 次采样的平均 token 约为单次的 5.4 倍。token 比值不是账单比值，后者还取决于输入/输出类别、缓存和当时的端点价格。

但这个结果本身不说明问题 —— 如果模型本来 10/10，那投票当然没有提升空间。真正值得注意的是另一列数据：

> **5 次采样出现分歧的题目：0/10。**

历史摘要称每道题的 5 个答案**一模一样**。若该摘要准确，这组样本里投票没有利用到候选差异；但由于逐次输出不可用，这一结果不能独立复核。

### 温度探测的另一组历史记录

这是一项不同于上面 self-consistency 采样的温度探测，同样缺少逐次响应与准确 endpoint/model 指纹，不能复算或证明参数生效：

你可能会说：「投票本来就要配高温，这样才能产生多样性。」我一开始也这么想，于是补了一组温度对照。

同时跑两个任务：一个有唯一正确答案（「北京是中国的首都吗」），一个有多个合理答案（「给一家手冲咖啡店起名」）。每个温度各采样 6 次：

| 温度 | 唯一答案的题 | 多答案的题 |
|---|---|---|
| `temperature=1` | **1/6 个不同答案** | **6/6 个不同答案** |
| `temperature=0` | **1/6 个不同答案** | **6/6 个不同答案** |

（实测数据，`deepseek-flash`，2026-10-08。由于没有请求/响应归档或端点追踪，这组输出不能确认 `temperature` 是否被端点透传。）

这张表仅描述该模型、端点、提示和这组题目的观察结果，不能推出普遍的「模型分布」规律。它展示了 self-consistency 的两个必要条件：

**这道唯一答案题：观察到输出收敛。** 温度开到 1，6 次仍然给同一个答案。这个小样本可能反映该问题在该模型/端点上的高概率答案，但不足以说明模型分布只有一个峰；温度也不保证不同采样一定产生不同答案。

**有多个合理答案的任务：确实发散，但发散的不是对错。** 「一注咖啡」「漉光手冲」「慢滤小馆」—— 6 个名字各不相同，可它们**都对**。这类任务没有「多数答案」可以投。

**多数投票可能有用的条件**是：存在可判定的目标答案、采样能产生有意义的候选差异，并且聚合器能利用这些差异提升正确率。不同任务、模型、采样参数会改变这些条件；本节样本显示的是当前实验没有收益，不是证明 self-consistency 普遍无效。

> 补一句关于可复现性的观察：上表里 `temperature=0` 在**本次创作题样本**上仍然 6/6 各不相同。**本次端点下的 `temperature=0` 没有带来逐字一致，不应被当作这条端点的可复现性保证。** 其他 API 可能有不同采样与 seed 契约；评估时需记录模型版本、端点与配置。

## 历史记录二：自查的构造错答样本

第二个技巧是 self-eval：让模型检查自己的输出。这一轮我做了两组测试。

**第一组**：把**已知错误的答案**喂给模型，看它能否发现。8 道题，每道题分别喂入一个错答和一个正确答案：

| 指标 | 结果 |
|---|---|
| 捉错率（喂错答，判「错误」） | **8/8** |
| 误报率（喂正答，判「错误」） | **0/8** |

（实测数据，`deepseek-flash`，2026-10-08。）

模型**全部捉住**了 8 个错答，而且对正确答案一次都没误判。看起来自查很有效，甚至比它的名声好得多。

但这里有个陷阱，必须点出来：

> **那些错答是我手工构造的。模型只要独立把题重算一遍，就能发现。**

我构造的错法（比如把 `37 × 43` 答成 1581）都有一个共同点：**正确答案可以由模型自己独立算出来**。这种「可自校验」的错误，自查当然抓得住 —— 因为自查实际做的不是「审阅」，而是**重做一遍**。

真正的难题是：**模型自己犯的错，它能不能抓住？** 这需要先找到它真的会答错的题。我拿 10 道字符级/精确索引题去测（这类题是公认的薄弱环节），结果它 **10/10 全对** —— 样本里根本没有可供自查的错误。

于是这一组没能测出想测的东西。但测试过程中发生的事，比实验本身更有价值。

## 我的答案键错了两次

在准备上面这些题目时，我（人）手工写了两道题的答案，**两道都写错了**：

| 题目 | 我写的答案 | 实际答案 | 我错在哪 |
|---|---|---|---|
| 从 1 数到 20，其中**包含数字 1 的数**有几个？ | 12 | **11** | 把「数字 1 出现的次数」当成了「包含 1 的数的个数」 |
| 单词 `encapsulation` 里**第 5 个字母**是什么？ | a | **p** | 数位时把第 4 位当成了第 5 位 |

两次我都在写下答案后**做过「自查」**，而且都确信自己是对的。

**这跟模型自查失效是同一个机制：用同一套直觉去检查同一套直觉，查不出错。** 我数错了，然后我用同样会数错的直觉去复核，复核自然通过。

这个错误直接改变了我的实验方法。你回头看本节第一个实验，题目是这样来的：

```javascript
const a = 1000 + Math.floor(Math.random() * 9000);
// ... 题目由代码生成
tasks.push({ q: `计算 ${a} × ${b} + ${c} 的结果。`, a: String(a * b + c) });
//                                                        ↑ 答案由代码算出，不经过我的直觉
```

**答案由代码算，不给我出错的机会。** 这不是为了严谨好看 —— 是因为我在同一个任务上已经错过两次了。

> **这是本节最重要的一条经验**：可靠性的瓶颈通常不在「模型会不会错」，而在「错了之后，谁能独立地发现它」。而关键词是「**独立**」 —— 一个用同样假设的复核者（无论是人还是模型），查不出同源的错误。

## 结论：可靠性的上限是「可校验性」

把两个实验合起来看，得到一张分类表：

| 任务类型 | 模型出错率 | 多数投票 | 自查 | 为什么 |
|---|---|---|---|---|
| 有唯一答案，且**可程序验证**<br/>（算术、计数、格式） | 视模型与任务而定 | 本次样本无效；其他设置需评估 | 有效，但没什么可查 | 答案可独立重算；是否有可投票的分歧需实测 |
| 有唯一答案，**不可程序验证**<br/>（事实真伪、外部世界） | 不定 | 需有可靠判分器与候选差异 | 有限 | 若无独立证据，同源盲区仍可能存在 |
| **缺少可判定的目标**（写作、风格等） | 取决于标准 | 未定义或需先归一化 | 只能判断「像不像」 | 没有可操作的判分标准时，多数结果不等于更好 |

**决定可靠性的不是模型的聪明程度，而是这个任务的正确答案能不能被独立验证。** 而这个「能不能」，是你可以设计的。

## 可校验性的三个层次

按「校验有多可靠」把输出分成三层，这是本节真正要交付的东西：

| 层次 | 校验手段 | 可靠性 | 例子 |
|---|---|---|---|
| **① 结构可校验** | JSON Schema、类型检查、正则 | **对已校验的结构属性可确定判断** | 输出是不是合法 JSON、字段齐不齐、类型对不对；不代表字段内容或任务答案正确 |
| **② 语义可校验** | 用程序算（不是用模型算） | **高** | 金额合计是否等于明细之和、引用的文档是否真的在知识库里、日期是否在合理区间 |
| **③ 仅模型可判** | LLM-as-judge | **概率性** | 摘要写得好不好、语气合不合适、意图理解对不对 |

关键动作是**把校验从第 ③ 层往第 ① ② 层挪**：

<Mermaid

箭头方向说明了本节的边界：**能写成代码的确定性不变量，应在可信执行路径里校验。** 模型侧自查（虚线）不能替代它；代码校验只对被检查且实际强制执行的不变量提供保证，不会自动证明语义正确或覆盖未纳入规则的风险。两类方法的成本也要按系统和任务测量，不能假定代码校验总是免费。

### 为什么「带回具体错误重新生成」比「再问一次」有效

注意图上那条回边：校验失败时不是简单重试，而是**把具体的失败原因拼回 prompt**。这比 self-consistency 那种「投币式重试」有效得多 —— 因为重试传递了**新信息**（哪个字段错了、哪个约束违反了），而多数投票只是在重复同一个盲区。

## 完整可运行代码

```python
# validation_layer.py
"""把校验从模型侧挪到代码侧：一个三层校验的完整例子。

场景：从自由文本里抽取发票信息。这类任务模型做得不错，
但"做得不错"和"能上生产"之间，隔着的就是下面这层校验。
"""

import json
import os
import re
from collections import Counter
from dataclasses import dataclass
from datetime import date
from decimal import Decimal, InvalidOperation

import anthropic
from pydantic import BaseModel, ConfigDict, Field, ValidationError

# 示例按 anthropic SDK 2.0+ 的凭证参数区分 API key 与 auth token。
client_options = {}
api_key = os.environ.get("ANTHROPIC_API_KEY")
auth_token = os.environ.get("ANTHROPIC_AUTH_TOKEN")
if api_key:
    client_options["api_key"] = api_key
elif auth_token:
    client_options["auth_token"] = auth_token
base_url = os.environ.get("ANTHROPIC_BASE_URL")
if base_url:
    client_options["base_url"] = base_url
client = anthropic.Anthropic(**client_options)
MODEL = os.environ["VERIFY_MODEL"]


# ── 第 ① 层：结构 ────────────────────────────────────────────
class InvoiceItem(BaseModel):
    model_config = ConfigDict(extra="forbid")

    name: str
    amount: Decimal = Field(gt=0)        # 用十进制保存货币


class Invoice(BaseModel):
    model_config = ConfigDict(extra="forbid")

    invoice_no: str
    issue_date: str
    items: list[InvoiceItem] = Field(min_length=1)
    total: Decimal


# ── 第 ② 层：语义（用程序算，不用模型算） ────────────────────
class ValidationFailed(Exception):
    """携带脱敏后的原因 —— 重新生成时要把这个原因带回 prompt."""


def reject_duplicate_keys(pairs: list[tuple[str, object]]) -> dict:
    result = {}
    for key, value in pairs:
        if key in result:
            raise ValueError("JSON 对象包含重复字段")
        result[key] = value
    return result


def safe_feedback(error: Exception) -> str:
    if isinstance(error, ValidationError):
        details = error.errors(include_input=False, include_url=False)
        return "; ".join(
            f"{'.'.join(map(str, item['loc']))}: {item['msg']}"
            for item in details
        )
    return str(error)


def check_semantics(inv: Invoice) -> None:
    # 规则 1：拒绝超过两位小数，再精确比较明细与合计。
    cent = Decimal("0.01")
    try:
        amounts = [item.amount.quantize(cent) for item in inv.items]
        total = inv.total.quantize(cent)
    except InvalidOperation as exc:
        raise ValidationFailed("金额超出可处理范围") from exc
    if any(item.amount != amount for item, amount in zip(inv.items, amounts)):
        raise ValidationFailed("行项目金额最多保留两位小数")
    if inv.total != total:
        raise ValidationFailed("发票合计最多保留两位小数")
    computed = sum(amounts, Decimal("0.00"))
    if computed != total:
        raise ValidationFailed("发票合计与行项目金额之和不符")

    # 规则 2：发票号格式。错误信息不回显用户提供的字段值。
    if not re.fullmatch(r"INV-\d{8}", inv.invoice_no):
        raise ValidationFailed("发票号必须符合 INV- 加 8 位数字的格式")
    # 规则 3：日期不能是未来。
    try:
        issue_date = date.fromisoformat(inv.issue_date)
    except ValueError as exc:
        raise ValidationFailed("开票日期必须使用 YYYY-MM-DD 格式") from exc
    if issue_date > date.today():
        raise ValidationFailed("开票日期不能晚于今天")


# ── 编排：校验失败就把原因带回，重试有限次 ──────────────────
SCHEMA_HINT = """
输出 JSON，字段：
  invoice_no: str（格式 INV- 加 8 位数字）
  issue_date: str（YYYY-MM-DD）
  items: [{name: str, amount: number（最多两位小数）}]
  total: number（最多两位小数，必须等于 items 各 amount 之和）
只输出 JSON，不要其他文字。
"""


def extract(text: str, max_attempts: int = 3) -> Invoice:
    feedback = ""
    for attempt in range(1, max_attempts + 1):
        msg = (
            "从下面这段文字里抽取发票信息。\\n\\n"
            f"{SCHEMA_HINT}\\n{feedback}\\n"
            f"<text>\\n{text}\\n</text>"
        )
        resp = client.messages.create(
            model=MODEL,
            max_tokens=1500,
            messages=[{"role": "user", "content": msg}],
        )
        if resp.stop_reason != "end_turn":
            raise RuntimeError(
                f"模型响应未正常结束：stop_reason={resp.stop_reason}"
            )
        raw = "".join(
            block.text for block in resp.content if block.type == "text"
        ).strip()
        if not raw:
            raise RuntimeError("模型正常结束但没有返回可解析的文本")
        try:
            data = json.loads(
                raw,
                parse_float=Decimal,
                parse_int=Decimal,
                object_pairs_hook=reject_duplicate_keys,
            )
            inv = Invoice.model_validate(data, strict=True)
            check_semantics(inv)
            return inv
        except (
            ValidationError, ValidationFailed, ValueError, InvalidOperation
        ) as exc:
            feedback = safe_feedback(exc)
            feedback = f"\\n上一次输出不合格：{feedback}\\n请修正后重新输出。"
            print(f"  第 {attempt} 次校验未通过：{feedback}")

    raise RuntimeError(f"{max_attempts} 次尝试后仍未通过校验")


if __name__ == "__main__":
    doc = """
    发票号 INV-20261008，开票日期 2026-10-08。
    明细：咨询费 1200.00，差旅费 356.50。
    合计 1556.50 元。
    """
    print(extract(doc))
```

> **版本边界**：此 Anthropic Python 客户端初始化按 SDK 2.0+ 编写；它分别使用 `api_key` 与 `auth_token` 参数，若同时设置两个环境变量则示例优先选 API key。SDK/API 版本会影响认证头等行为；兼容端点必须按其文档验证。
>
> **边界**：`<text>` 只是提示词里的分隔标记，不是安全边界；若原文可能包含指令、诱导内容或敏感数据，应按不可信输入处理，并用权限隔离、输出校验及数据最小化保护系统。本文表格里的**数据是历史实测摘要**；上面这份 Python 脚本用的是 SDK 与 Pydantic 的标准写法，**脚本本身未在官方端点验证**。

这份代码里没有一行 self-eval。**校验全部由代码完成** —— 这不是巧合，而是结论本身。

## 主观项怎么挪到代码层

上面那个发票例子是「客观项」—— 合计对不对，程序一算就知道。但真实的验收清单里总有一半是主观项：「摘要写得好不好」「语气合不合适」「有没有跑题」。这些**没法直接程序验证**，于是很多人就此放弃，把它们留在第 ③ 层让模型自评。

**正确的做法不是「能不能验」，而是「找一个能替代它的可计算指标」** —— 也就是**代理指标**（proxy）。思路是把「好」这个形容词拆成几条**可数**的性质，每条都能用字符串/结构算出数来：

| 主观项 | 不可计算的写法 | 可计算的代理指标 |
|---|---|---|
| 摘要写得好 | 「是否忠实、完整、简洁」 | 可将数字 token 是否在原文出现、摘要长度比作为候选代理；每条 claim 是否有出处仍需单独对齐/复核。本节示例只实现数字、长度、禁词和主题词初筛，不实现专名抽取或 claim 对齐。 |
| 语气合适 | 「要专业、友好」 | 禁词表命中数 = 0（如「哈哈」「随便」）；疑问句数量或第一人称计数可作为其他待校准代理，但示例代码未实现 |
| 没跑题 | 「是否围绕主题」 | 检查预先选定的主题词是否出现，或在校准集上评估覆盖率；向量相似度只提供相似线索，不证明事实忠实或任务完成 |

 > 上表提到的向量余弦相似度需要嵌入表示：语义相近的文本在向量空间里可能更近，但相似不等于忠实。若已有向量可复用，未必每次请求都新增模型调用；计算、存储、延迟和费用取决于部署与缓存方式。

把其中几项规则落进代码，可以得到有限的自动初筛；它们不会把主观质量变成完整、可靠的自动判定：

```python
# proxy_metrics.py
"""把「摘要写得好不好」换成四条可计算的代理指标。"""

import re

# ① 数字 token 是否出现在原文
NUM_RE = re.compile(r"\d+(?:\.\d+)?%?")

# ② 长度区间
MIN_RATIO, MAX_RATIO = 0.10, 0.30

# ③ 语气类禁词
FORBIDDEN = ["哈哈", "随便", "无所谓", "算了"]

# ④ 跑题：主题词在摘要里的覆盖率
TOPIC_WORDS = ["营收", "增长", "客户"]


def proxy_score(summary: str, doc: str) -> dict:
    if not summary.strip() or not doc.strip():
        raise ValueError("summary and doc must both contain text")

    # ① 仅比较数字的原样出现次数；这仍不证明数字被正确归因。
    summary_numbers = Counter(NUM_RE.findall(summary))
    document_numbers = Counter(NUM_RE.findall(doc))
    numbers_present = not (summary_numbers - document_numbers)

    # ② 长度比
    ratio = len(summary) / max(len(doc), 1)

    # ③ 语气
    hits = [w for w in FORBIDDEN if w in summary]

    # ④ 主题覆盖：至少覆盖一半主题词
    topic_hit = [w for w in TOPIC_WORDS if w in summary]

    return {
        "numbers_present": numbers_present,
        "length_ratio": round(ratio, 3),
        "tone_clean": not hits,
        "topic_covered": len(topic_hit) >= (len(TOPIC_WORDS) + 1) // 2,
    }


def accept(score: dict) -> bool:
    """四条全过才放行 —— 这就是原来交给模型自评的那个判断。"""
    return (
        score["numbers_present"]
        and MIN_RATIO <= score["length_ratio"] <= MAX_RATIO
        and score["tone_clean"]
        and score["topic_covered"]
    )


if __name__ == "__main__":
    doc = "第三季度营收同比增长 12%，主要来自企业客户。"
    for s in [
        "营收增长 12%，来自企业客户。",                    # 正常
        "营收增长 15%，来自企业客户。",                    # 数字被改 → ① 不过
        "哈哈，营收还行吧。",                              # 语气 → ③ 不过
    ]:
        score = proxy_score(s, doc)
        print(f"{s!r} -> {score} -> {'采用' if accept(score) else '打回'}")
```

> （**示例：构造数据，未实跑。** 它不调用模型，纯本地字符串检查 —— 可以直接跑，但上面三条输入是我手写的。）

**代理指标的三条使用规则：**

1. **代理指标不等于原指标。** 数字出现、长度、禁词或关键词覆盖都可能误报或漏报；通过不代表质量达标，失败也只有在目标任务上校准过后才能作为拒绝条件。它们适合做分层信号，不应直接当整体质量分数。
2. **阈值来自你的统计，不是别人的经验。** 上面那个 `0.10~0.30` 是示例值；正确做法是拿一批「人工判定为合格」的样本来反推区间（这和本节前面「阈值取基线减噪声」是同一件事）。
3. **每加一条代理指标，都要先量它的误杀率。** 用一批已知合格的输出跑一遍，看它误判了几条 —— 误杀率高的指标不如不要，因为它会把好输出也打回，触发无意义的重试成本。

> **和 self-eval 的关系**：本地规则通常不需要额外的模型调用，但仍有实现、计算和维护成本；远程 embedding 或 judge 还会增加调用、延迟与费用。先用经校准的确定性规则处理可验证的不变量，再评估剩余主观项是否需要模型或人工复核。换一个模型可能带来不同盲区，但收益仍需在目标任务上测量。

## 那 self-eval 还剩什么用途

并不是说 self-eval 完全没用。它能做的是**在程序算不出来的地方，提供一层粗糙的过滤**，前提是你要接受它的两个局限：

**① 它只有在检查所需信息充分时才有机会做有根据的判断。** 给它一段文本和一句「判断这个摘要是否忠实于原文」，**原文就在上下文里**，它可以逐项对照；这比让它靠记忆核对引用更有依据，但是否可靠仍要在目标任务上评测。一旦要检查的东西不在上下文里（「这个引用是真的吗」），它就只能靠记忆猜。

**② 它不能用来检查推理链。** 让模型审阅自己的推理过程，通常等于让它**重跑一遍**同一个推理 —— 同样的前提错误会同样地滑过去。实践上更有效的是换一个视角：**只给答案、不给推理过程**，让它独立算出结果再比对（这也是本节第二组实验里，模型能 8/8 捉住我构造的错答的原因 —— 它是重算，不是审阅）。

**③ 用另一个模型评审，可能带来不同盲区，但不能预设它更有价值。** 是否改善错误发现率，要在目标任务上和同模型自评、规则校验及人工基线比较。这是第 13 章 LLM-as-judge 的内容。

## 常见坑

**无脑上多数投票。** 本节特定算术/计数题实验里 5 次采样零分歧，成本 5.4 倍、该样本没有收益。**先测分歧率** —— 如果 5 次答案一样，投票没有意义。

**把 `temperature=0` 当成跨端点的可复现保证。** 本次创作类样本仍然 6/6 各不相同；应查目标 API 的确定性契约，并记录模型版本、端点和配置。

**把「自查」当成「审阅」。** 自查的实际机制是「重做一遍」，所以它只能抓住**可独立重算**的错误。推理链里的错误抓不住。

**用模型的记忆去核对模型的事实。** 这等于用同一把尺子量自己 —— 同源盲区必然漏网。事实类的校验需要**外部依据**（检索命中、数据库查询）。

**自己写答案键，然后自己复核。** 我在本节错了两次，两次都复核通过。**能由程序算出来的答案，就让程序算** —— 人工写答案键只用在程序确实算不出来的地方。

**把校验当成「加一层保险」。** 校验层的价值不只在拦截错误，更在于它**能不能给出可执行的具体原因**。一句「输出不合格」的校验是浪费，一条「合计 1556.50 与明细之和 1556.5 不符」的校验才能驱动修复。
