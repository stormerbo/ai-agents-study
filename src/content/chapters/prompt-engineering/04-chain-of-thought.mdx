2022 年的 CoT 论文在特定大模型和多步推理基准上报告了带推理示例的 few-shot CoT 收益（[arXiv:2201.11903](https://arxiv.org/abs/2201.11903)）。这是一项有范围的实验发现，不表示任何模型、任务或提示都能得到同样收益。本站历史摘要中的处理则是零样本地要求“先一步步推理”，两者并非同一实验。

本站保留了一组 DeepSeek 兼容端点的历史摘要；它的样本规模、评分器和 usage 口径不足以检验论文结论，也不能说明当前模型普遍不需要 CoT。本节把论文结论、历史观察和可复验的方法分开讲。

## 一组有限的历史观察

**多步推理题**（5 道 × 3 轮 = 15 次）：

| 写法 | 历史记录的正确数 | 历史平均 token 摘要¹ |
|---|---:|---:|
| 无 CoT：「只给出最终答案」 | **15/15** | **130** |
| 加 CoT：「先一步步推理，最后给出答案」 | **15/15** | **241** |

两组多步题都记录为 15/15，答案率在这组小题上已到 ceiling，无法检验 CoT 是否对更难题目有帮助。130 与 241 是历史 token 汇总值，不是费用；历史计算只记录 input + output，未纳入或留存 endpoint 的完整 usage 口径。数值与原始逐次响应、模型快照和可复算记录均未归档，因此保留为不可独立复核的观察，不据此得出“CoT 没提升”或成本结论。

**简单题**（3 道 × 3 轮，不需要推理的常识题）：

| 写法 | 历史记录的正确数 | 历史平均 token 摘要¹ |
|---|---:|---:|
| 无 CoT | 6/9 | **88** |
| 加 CoT | 6/9 | **198** |

这一组也不能作准确率差异结论：历史记录承认至少一个“七天”答案被只识别字符串 `7` 的判据误判，且没有逐题响应可供重评分。88 与 198 同样只是历史 token 汇总值，不是费用；不从中计算通用成本增幅。

（历史摘要标注 `deepseek-flash`、2026-10-08；逐次请求/响应、完整 usage、模型指纹、任务集与 scorer 未归档。下文代码是供读者重新评估的示例，不是这组历史数据的复现。）

¹ 原脚本只把 `input_tokens + output_tokens` 相加；未保留缓存字段、逐次 usage 或原始响应。这里的数值只作为历史摘要，不表示完整 token 用量或账单。

## 一条历史响应不能解释实验结果

看一个前面章节出现过的细节。这是第 1 章在当时选定的模型、端点与请求配置下采集的真实响应结构：

```text
content_block_start   index=0  type=thinking      ← 模型自己的思考
  thinking_delta     × 36
content_block_stop    index=0
content_block_start   index=1  type=text          ← 给用户的回答
  text_delta         × N
```

**这次历史响应摘要返回了两个块** —— 一个 thinking 块和一个 text 块。这只能说明当时那次配置返回过 thinking 内容；它不能解释前一组 CoT 的结果，也不能推出所有模型会默认思考或返回可见的 thinking 块。

部分当前模型/API 提供显式或自适应 thinking，参数、默认行为和可见内容都依赖模型版本与端点。Anthropic 当前文档分别说明模型对应的 thinking 配置、默认值和迁移方式；这些是 Claude 的 provider/model-specific 行为，不能套用到其他模型。**不要把内部 thinking 与用户可见的推理文本等同起来**，也不要假定再加一句 CoT 必然只是重复输出。

## 那 CoT 这个技巧还有用吗

CoT 是否有用取决于目标模型和任务。要求生成可见步骤会改变输出契约并可能增加输出量；它不等同于启用模型的内部 reasoning，也不保证答案正确或解释忠实。以下场景可以考虑要求可检查的中间产物，但应分别评估：

**① 你需要一个可检查的解释产物。**

步骤文本可能帮助读者发现明显的算式或前提错误，但它是模型生成的说明，不保证忠实呈现内部计算，也不能单独作为审计证据。对金额仍应由独立程序重算；涉及安全或合规监控时，也不要把可见步骤当作唯一信号。

**② 任务复杂到需要显式的中间结果。**

如果一个任务有多个步骤，而中间结果本身有价值（例如要展示给用户、或要落库），那就值得让模型输出出来。但这时你需要的其实是**结构化的中间产物**，而不只是"思维链"这个概念。

**③ 目标模型的对照评测表明确有收益时。**

不同模型与任务的提示收益不同；不能仅凭模型大小或年代推断。用目标模型、真实任务和预先定义的评分规则对照评测，再决定是否保留该提示。

> 换个角度看：2022 年 CoT 论文报告了特定模型与任务上的提示收益；它不是「所有当前模型都有内置推理」的证据。今天模型能力、API thinking 模式和提示最佳实践按模型版本变化。查阅[Anthropic 当前提示工程文档](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)中按模型区分的 thinking 指南，再对目标场景做评估。

## prefill：旧模型/API 上的兼容性技巧

另一个需要按版本判断的技巧是 **prefill**（在对话末尾放入一条不完整的 assistant 消息）。它只适用于明确支持的 API/model 组合；请求被接受不等于输出一定只补全剩余部分，更不保证输出满足 JSON schema。

两个用途：

**① 影响输出起始形态。** 一些支持 prefill 的旧接口允许提供 assistant 前缀，但这不是结构约束，也不能替代 JSON 解析、schema 校验或结构化输出功能。

Prefill 请求的核心 `messages` 数组如下（这是请求片段，不是完整 SDK 调用）：

```python
messages = [
    {
        "role": "user",
        "content": (
            "用 JSON 给出北京的气温，形如 {\"city\":...,\"temp_c\":...}。"
            "只输出 JSON。"
        ),
    },
    {"role": "assistant", "content": "{\"city\": \"北京\", \"temp_c\":"},   # ← prefill
]
```

**历史记录存在互相冲突的续写摘要，无法作为实测结论：**

```text
同一节先记录 `temp_c:20`，后文又记录 `temp_c:null`；逐次原始请求/响应未归档，无法判断哪一条准确，
也不能确认 usage 与返回块的对应关系。
```

因此本文撤回“本次端点已经证明模型会重写整个对象”的说法。若某个受支持端点返回与前缀重复的完整对象，直接把前缀和响应拼接会产生无效 JSON，例如：

```text
预填： {"city": "北京", "temp_c":
续写： {"city":"北京","temp_c":20}
拼起来： {"city": "北京", "temp_c":{"city":"北京","temp_c":20}    ← JSON 解析必失败
```

该例说明拼接策略必须依据目标 endpoint 的真实响应契约。不要预设返回的是完整对象，也不要预设它是前缀的后半段；解析后仍须校验必需字段与类型。

| 处理方式 | 适用前提 | 必须验证 |
|---|---|---|
| 按完整响应解析 | endpoint 返回完整 JSON 文本 | JSON 结构、必需字段、字段类型与业务规则 |
| 将响应接到前缀后解析 | endpoint 返回严格的后缀续写 | 前缀边界、编码与最终 JSON schema |
| 使用 structured output | 目标模型/API 提供该能力 | 结构约束仍不保证事实或业务语义正确 |

下面示例仅展示对构造响应的两种解析形态做 fail-closed 校验；它不推断某个 provider 的 prefill 语义：

```python
# prefill_parse_fixture.py
"""仅用构造响应演示完整对象/后缀两种解析路径；不调用模型。"""
import json
import math

PREFILL = '{"city": "北京", "temp_c":'


def reject_duplicate_keys(pairs: list[tuple[str, object]]) -> dict:
    result = {}
    for key, value in pairs:
        if key in result:
            raise ValueError(f"duplicate JSON key: {key}")
        result[key] = value
    return result


def parse_response(response: str, *, mode: str) -> dict:
    if mode == "full":
        candidate = response.strip()
    elif mode == "suffix":
        candidate = PREFILL + response.strip()
    else:
        raise ValueError("mode 必须显式为 full 或 suffix")

    value = json.loads(candidate, object_pairs_hook=reject_duplicate_keys)
    if not isinstance(value, dict):
        raise ValueError("响应必须是 JSON object")
    if set(value) != {"city", "temp_c"}:
        raise ValueError("字段集合不符合契约")
    if not isinstance(value["city"], str) or not value["city"].strip():
        raise ValueError("city 必须是非空字符串")
    temp_c = value["temp_c"]
    if isinstance(temp_c, bool) or not isinstance(temp_c, (int, float)):
        raise ValueError("temp_c 必须是数值")
    if isinstance(temp_c, float) and not math.isfinite(temp_c):
        raise ValueError("temp_c 必须是有限数值")
    return value


full = parse_response('{"city":"北京","temp_c":20}', mode="full")
suffix = parse_response('20}', mode="suffix")
assert full == suffix == {"city": "北京", "temp_c": 20}
print(full)
```

> **实跑状态**：历史 provider 响应无法从归档中恢复；上方 parser 只针对两种构造 fixture 离线执行，不调用 provider，也不证明任何端点的兼容性。

**厂商支持差异**：

| 厂商 | 是否支持 messages 末尾放 assistant | 说明 |
|---|---|---|
| Anthropic Messages API | 依模型版本 | 旧模型支持；Claude 4.6 起最后一条 assistant prefill 不再支持，请求会返回 400，见[迁移文档](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#migrating-away-from-prefilled-responses) |
| DeepSeek 兼容端点 | 需按目标接口确认 | 本节只有互相冲突、无法复核的历史摘要，不能支持当前兼容性结论 |
| OpenAI Chat Completions | 需按 API 与目标模型确认 | 本节未验证 OpenAI API，不作跨 API 能力比较；使用结构化输出时也仍需验证语义 |

> 表格不构成完整厂商能力矩阵；跨厂商、模型或 API 前，先查当前官方文档并对目标请求做兼容性测试。

**② 兼容既有调用契约。** 若历史系统依赖 prefill，应先确认目标 endpoint 仍接受该请求，并验证返回结构；不要把它当作绕过安全拒答的技巧。

**注意**：prefill 的支持方式与限制**因厂商、模型版本和 API 而异**。上表的 Anthropic 结论已按当前文档限定到旧模型；Claude 4.6 及后续模型应使用清晰指令或支持的结构化输出能力。不要把早期兼容端点的成功请求当成当前官方模型的通用行为。

## 完整可运行代码

下方代码只面向 Anthropic Messages API。按该 API 的 usage 契约，input token 总量是 `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`，`output_tokens` 单独记录；其他 API 的字段名、终态和计量口径必须另外核对。[Anthropic Messages API](https://platform.claude.com/docs/en/api/messages)

```python
# cot_experiment.py
"""在自己的任务集上比较两种输出契约；描述统计，不自动判定普遍优劣。

只针对 Anthropic Messages API。结果需结合任务质量、完整 usage 和延迟解释，
不能把 token 数直接当作费用，也不能把少量重复当作统计显著性证据。
"""
import os
import random
import re
from decimal import Decimal

import anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = os.environ["VERIFY_MODEL"]

PROBLEMS = [
    ("一个班有 40 人，其中 60% 是女生，女生中又有 25% 戴眼镜。戴眼镜的女生有多少人？", "6"),
    ("商品原价 200 元，先涨价 10%，再打 8 折，最终价格是多少元？", "176"),
    ("甲乙两地相距 300 公里。A 车时速 60，B 车时速 40，相向而行，几小时相遇？", "3"),
    ("一个数加 5 后乘以 2，再减 10 得到 20。这个数是多少？", "10"),
    ("3 个工人 3 小时做 3 个零件，那么 9 个工人 9 小时做多少个？", "27"),
]
VARIANTS = {
    "final_only": "回答问题，只输出一行，格式严格为：答案：<数值>。不要解释。",
    "visible_steps": "回答问题，先写简短步骤，最后一行严格为：答案：<数值>。",
}
RUNS = 3
USAGE_FIELDS = (
    "input_tokens", "output_tokens",
    "cache_creation_input_tokens", "cache_read_input_tokens",
)


def ask(system: str, question: str) -> tuple[str, dict[str, int]]:
    response = client.messages.create(
        model=MODEL,
        max_tokens=2000,
        system=system,
        messages=[{"role": "user", "content": question}],
    )
    if response.stop_reason != "end_turn":
        raise RuntimeError(f"样本未完整结束：stop_reason={response.stop_reason!r}")
    text_blocks = [block.text for block in response.content if block.type == "text"]
    text = "".join(text_blocks).strip()
    if not text:
        raise RuntimeError("响应没有可评分的 text 内容")

    usage = response.usage
    counts: dict[str, int] = {}
    for field in USAGE_FIELDS:
        value = getattr(usage, field, None)
        # Anthropic 文档允许无缓存 token 时省略缓存字段；不接受未知/非法计数。
        if value is None and field.startswith("cache_"):
            value = 0
        if isinstance(value, bool) or not isinstance(value, int) or value < 0:
            raise RuntimeError(f"usage.{field} 缺失或非法")
        counts[field] = value
    return text, counts


def extract_answer(text: str) -> Decimal:
    matches = re.findall(r"(?m)^答案[：:]\s*(-?\d+(?:\.\d+)?)\s*$", text)
    if not matches:
        raise ValueError("没有符合契约的答案行")
    return Decimal(matches[-1])


if __name__ == "__main__":
    rng = random.Random(2026)
    totals = {name: {field: 0 for field in USAGE_FIELDS} for name in VARIANTS}
    scores = {name: [0, 0] for name in VARIANTS}

    for _ in range(RUNS):
        for question, expected in PROBLEMS:
            order = list(VARIANTS)
            rng.shuffle(order)
            for name in order:
                text, usage = ask(VARIANTS[name], question)
                scores[name][0] += extract_answer(text) == Decimal(expected)
                scores[name][1] += 1
                for field, value in usage.items():
                    totals[name][field] += value

    for name in VARIANTS:
        correct, count = scores[name]
        means = {field: totals[name][field] / count for field in USAGE_FIELDS}
        print(f"{name}: {correct}/{count}; 平均 usage 字段={means}")
```

> **实跑状态**：这份评估脚本仅做过 mock 验证，未在官方端点运行。Anthropic usage 字段有 provider 专属语义；迁移到其他 API 前必须重写并核对其终态、缓存和 token 计量契约。

## 那这一节到底留下了什么

把三件事放在一起看会更清楚：

| 技巧 | 本节结论 | 现在该怎么做 |
|---|---|---|
| 自由形式的 CoT（「让我们一步步思考」） | 一组小样本历史摘要；题目有 ceiling，无法推出一般效果 | 在目标工作负载上比较任务质量、完整 usage、延迟与风险 |
| 可见的步骤说明 | 不能据此声称得到忠实思维轨迹 | 只作为一种可检查的说明产物，并配独立校验 |
| prefill | 依模型/API 版本；Claude 4.6 起不支持最后一条 assistant prefill | 在仍支持的端点上可控制起始前缀；新端点优先用指令或结构化输出 |

这几种机制的价值与边界不同：CoT 提示可能改变任务表现和输出；可见解释可供检查但不是忠实性证明；prefill 是受 endpoint 支持范围约束的输入形式。是否采用要按任务评估，并优先使用可验证的输出契约。

> 适用边界：本站 2026-10-08 的 DeepSeek 历史摘要不能证明模型内部 thinking 导致了观察结果，也不能代表其他模型或任务。下方脚本仅是重新评估的起点，需补充经过验证的评分器、任务样本、完整 usage 与响应终态记录。

## 常见坑

**把一次小样本当成普遍结论。** CoT 的收益依模型、任务和提示而变；小样本或 ceiling 结果不能证明有效或无效。

**把 CoT 当成万能药。** 不要假定它一定提升复杂题准确率，也不要断言它在分类、抽取、改写上必然净亏损；在目标分布上做对照评估。

**把 token 数直接叫作费用。** 成本需按目标 provider 的 input/output/cache 计量和费率分别计算；历史 token 汇总不含足够信息支持账单结论。

**以为 prefill 是通用能力。** 它依厂商、模型版本和 API 支持；Anthropic 已对 Claude 4.6 及之后的模型移除最后一条 assistant prefill。使用前查该模型的迁移文档并做兼容测试。

**把用户可见的解释当成验证过的内部轨迹。** 接口可能返回经过整理的解释或摘要，而非原始内部推理。[OpenAI 对 o1 的说明](https://openai.com/index/learning-to-reason-with-llms/)明确区分隐藏的 chain of thought 与面向用户展示的模型生成摘要；这个例子仅适用于该产品系列，但说明了解释文本不能替代独立校验。
