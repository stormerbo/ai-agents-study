少样本提示（**few-shot** prompting）是在请求中放入若干输入/期望输出示例，让模型按示例完成新输入。示例能传递任务约定、标签边界和输出形状；它们不是训练数据，也不能替代验证集。数量没有通用最佳值，应由目标任务上的评测决定。

Anthropic 当前指南建议用相关且多样的示例覆盖边界，并把 3–5 条作为起步建议；OpenAI 指南同样强调不同模型快照可能表现不同，建议用评测验证提示变更。这些都是厂商的实践建议，不证明某个固定数量或挑选规则对所有任务都有效。

## 旧实验记录：有观察，不足以证明因果

|---|---|---:|---|
| 零样本 | 无示例 | 9/10 | 一条反讽被判成中性 |
| 10 个典型示例 | 如“很好用，推荐购买” | 9/10 | 同一条 |
| 3 个边界示例 | 如混合评价、委婉否定 | 10/10 | 无 |
| 10 个典型 + 3 个边界 | 合计 13 条 | 10/10 | 无 |

旧记录标注 DeepSeek deepseek-flash、2026-10-08。逐题请求与响应、精确模型快照、采样配置、评分器和数据版本都没有归档，因此表格只能保留为**未独立验证的历史摘要**。每组只运行一次，10 题也不足以估计稳定性；9/10 与 10/10 不能推出“边界示例带来了提升”。

还有一个会直接影响解释的问题：旧主表的 3 条边界示例，与 10 条测试文本有 **1 条完全相同**（“总算没搞砸，但也就那样”）。这属于训练示例与测试题重叠，不能用于证明模型把规则泛化到了新样本。另一个曾附上的、标为未实跑的消融脚本，把 3 条边界文本全部同时放进示例和测试；如果运行，其分数也不能证明泛化。主表即使数字准确，边界组的 10/10 仍受一条泄漏样本影响。评测前必须检查精确重复，并人工审查近似改写。

## 怎样挑选示例

先写清任务和标签的业务定义。以情感分类为例，“中性”可以表示总体评价均衡、没有明确情绪，还是信息不足？不同团队的标注规则可能不同。没有先定义标签，示例就会把作者的临时判断伪装成标准答案。

然后按下面步骤设计：

1. **建立独立数据分区**：用开发集查看常见错误并设计示例；留出集不参与示例挑选、提示修改或阈值调整。相同文本不能同时出现在示例和留出集。相似改写也要人工检查是否泄漏了目标答案。
2. **覆盖决策边界**：优先包含容易混淆、但标签依据明确的案例，例如总体评价与局部优点相反、委婉否定、信息不足。每条示例都要能说明“为什么是这个标签”。
3. **检查示例质量**：确认标签符合已写明的规则；覆盖标签、写法和边界；避免少数示例形成与规则冲突的模式。格式一致有利于审阅与定位问题，但其收益仍应通过目标任务测量。
4. **做消融与对照**：比较零样本、基线示例、边界示例及组合；一次只改变一类因素。对同一批留出题配对比较，保存每题结果与模型版本。
5. **根据任务决定是否保留**：除了总体准确率，也检查每类召回、混淆矩阵、错误严重性、输入 token 与延迟。示例可能不改变平均准确率，却修复了关键类别；也可能提高一类同时损害另一类。

“删除一条示例后分数没变”不自动代表它没有价值：留出集可能太小、基线可能已经接近满分、收益可能只出现在某个子群，或结果只是采样噪声。反过来，增加示例后的单次提升也不能证明因果。需要先定义业务关心的最小改进、独立评测单位和比较方法，再决定样本量；不能把固定的 5 次或 10 题当作通用充分标准。

## 可运行的评测样例

下面脚本提供一套本地示例数据与四种配置，在 Anthropic Messages API 上运行配对评测。样例文字与上面的历史数据不同；脚本启动时会拒绝训练/测试的精确文本重叠，但语义近似泄漏仍需人工审查。默认每个配置重复 5 轮，共 240 次请求；实际调用可能产生费用。运行前安装 anthropic SDK，设置 ANTHROPIC_API_KEY 与有权限访问的 ANTHROPIC_MODEL，然后执行 `python few_shot_experiment.py`。默认将逐次记录写到 `few-shot-results.jsonl`；可用 `FEWSHOT_OUTPUT` 改路径，目标文件已存在时脚本会拒绝覆盖。

```python
# few_shot_experiment.py
"""Compare few-shot variants on a held-out fixture set; this is not the 2026 history."""
import json
import os
import random
from pathlib import Path

import anthropic

MODEL = os.environ["ANTHROPIC_MODEL"]
RUNS = int(os.environ.get("RUNS", "5"))
OUTPUT = Path(os.environ.get("FEWSHOT_OUTPUT", "few-shot-results.jsonl"))
SEED = 20261021
LABELS = {"正面", "负面", "中性"}

# Mixed/balanced or insufficient evidence is neutral.
TEST = [
    ("t01", "说明书看着复杂，实际十分钟就装好了", "正面"),
    ("t02", "客服当天就解决了换货问题", "正面"),
    ("t03", "用了两天，按键就卡住了", "负面"),
    ("t04", "外壳不错，但充电时总会断开", "负面"),
    ("t05", "包装完整，暂时还没拆开使用", "中性"),
    ("t06", "功能和旧款差不多，没有特别感受", "中性"),
    ("t07", "本来担心很难上手，结果第一次就成功", "正面"),
    ("t08", "客服态度客气，可问题一直没有解决", "负面"),
    ("t09", "说不上好坏，先用一阵再评价", "中性"),
    ("t10", "看着普通，用起来比预期顺手", "正面"),
    ("t11", "宣传说全金属，实际只有背板是金属", "负面"),
    ("t12", "东西收到了，具体效果还不知道", "中性"),
]

TYPICAL = [
    ("手感很好，愿意推荐", "正面"),
    ("做工很差，不会再买", "负面"),
    ("今天刚下单，还没收到", "中性"),
    ("操作简单，体验不错", "正面"),
    ("用了就坏，质量堪忧", "负面"),
    ("暂时没有使用", "中性"),
]
BOUNDARY = [
    ("安装过程比预期麻烦，完成后使用很顺", "正面"),
    ("小问题不多，但核心功能一直失灵", "负面"),
    ("有优点也有缺点，整体说不上满意或失望", "中性"),
    ("评价里说很安静，我这台运行时声音明显", "负面"),
]

VARIANTS = {
    "zero": [],
    "typical": TYPICAL,
    "boundary": BOUNDARY,
    "combined": TYPICAL + BOUNDARY,
}
BASE = (
    "按评论的总体情绪分类，只回复正面、负面或中性。"
    "总体褒扬为正面，总体批评为负面；评价均衡或证据不足为中性。"
)


def normalize(text: str) -> str:
    return " ".join(text.casefold().split())


def assert_no_exact_overlap(examples, tests) -> None:
    train_texts = [normalize(text) for text, _ in examples]
    test_texts = [normalize(text) for _, text, _ in tests]
    if len(set(train_texts)) != len(train_texts):
        raise ValueError("duplicate demonstration text")
    overlap = set(train_texts) & set(test_texts)
    if overlap:
        raise ValueError(f"demonstration/test leakage: {sorted(overlap)!r}")


def build_system(examples) -> str:
    if not examples:
        return BASE
    lines = "\n".join(f"评论：{text}\n标签：{label}" for text, label in examples)
    return f"{BASE}\n\n示例：\n{lines}"


def parse_label(text: str):
    candidate = text.strip()
    return candidate if candidate in LABELS else None


def usage_fields(response) -> dict[str, int]:
    usage = response.usage
    values = {
        "input_tokens": getattr(usage, "input_tokens", None),
        "output_tokens": getattr(usage, "output_tokens", None),
    }
    for field in ("cache_creation_input_tokens", "cache_read_input_tokens"):
        value = getattr(usage, field, None)
        values[field] = 0 if value is None else value
    if any(type(value) is not int or value < 0 for value in values.values()):
        raise RuntimeError(f"missing or invalid usage: {values!r}")
    return values


def response_text(response) -> str:
    return "".join(
        getattr(block, "text", "")
        for block in response.content
        if getattr(block, "type", None) == "text"
    ).strip()


def extract_text(response) -> str:
    if response.stop_reason != "end_turn":
        raise RuntimeError(f"incomplete response: {response.stop_reason!r}")
    text = response_text(response)
    if not text:
        raise RuntimeError("response has no text")
    return text


def main() -> None:
    if RUNS < 1:
        raise ValueError("RUNS must be at least 1")
    for examples in VARIANTS.values():
        assert_no_exact_overlap(examples, TEST)

    client = anthropic.Anthropic()  # Reads ANTHROPIC_API_KEY from the environment.
    rng = random.Random(SEED)
    rows = []
    jobs = [
        (condition, case)
        for condition in VARIANTS
        for case in TEST
    ]
    with OUTPUT.open("x", encoding="utf-8") as archive:
        for run in range(1, RUNS + 1):
            run_jobs = list(jobs)
            rng.shuffle(run_jobs)
            for condition, (case_id, text, expected) in run_jobs:
                try:
                    response = client.messages.create(
                        model=MODEL,
                        max_tokens=16,
                        system=build_system(VARIANTS[condition]),
                        messages=[{"role": "user", "content": text}],
                    )
                except Exception as error:
                    row = {
                        "run": run,
                        "condition": condition,
                        "case_id": case_id,
                        "requested_model": MODEL,
                        "response_model": None,
                        "stop_reason": None,
                        "raw_output": "",
                        "predicted": None,
                        "usage": None,
                        "status": "request_error",
                        "error_type": type(error).__name__,
                        "correct": False,
                    }
                else:
                    raw = response_text(response)
                    predicted = parse_label(raw)
                    try:
                        usage = usage_fields(response)
                        usage_error = False
                    except RuntimeError:
                        usage = None
                        usage_error = True
                    stop_reason = getattr(response, "stop_reason", None)
                    if stop_reason == "refusal":
                        status = "refusal"
                    elif stop_reason != "end_turn":
                        status = "incomplete"
                    elif not raw:
                        status = "missing_text"
                    elif predicted is None:
                        status = "invalid_label"
                    elif usage_error:
                        status = "invalid_usage"
                    else:
                        status = "scored"
                    row = {
                        "run": run,
                        "condition": condition,
                        "case_id": case_id,
                        "requested_model": MODEL,
                        "response_model": getattr(response, "model", None),
                        "stop_reason": stop_reason,
                        "raw_output": raw,
                        "predicted": predicted,
                        "usage": usage,
                        "status": status,
                        "correct": status == "scored" and predicted == expected,
                    }
                row["expected"] = expected
                rows.append(row)
                archive.write(json.dumps(row, ensure_ascii=False) + "\n")
                archive.flush()
                print(
                    f"archived run={run} condition={condition} "
                    f"case={case_id} status={row['status']}"
                )
    print("\n本批留出集结果；失败请求计入尝试数但不算正确")
    for condition in VARIANTS:
        group = [row for row in rows if row["condition"] == condition]
        correct = sum(row["correct"] for row in group)
        invalid = sum(
            row["status"] in {"missing_text", "invalid_label"} for row in group
        )
        failed = sum(row["status"] != "scored" for row in group)
        summary = (
            f"{condition}: {correct}/{len(group)} attempts, invalid={invalid}, "
            f"failed={failed}"
        )
        print(summary)

if __name__ == "__main__":
    main()
```

> **实跑状态**：2026-10-22，离线 verifier 15/15；正文 Python fence 编译，通过 fake SDK 执行 240 次构造调用，覆盖重叠拒绝、缓存 usage 类型、严格标签、refusal、截断、空文本、请求超时记录和 JSONL 不覆盖。没有调用 provider，Anthropic SDK/endpoint 与模型质量未实跑。每次尝试都会写入 JSONL；请求错误、refusal、截断、无效标签和 usage 错误保留为失败记录并计入尝试分母，不会算作正确。终端只显示样本 ID 与状态，不打印原文或模型回答。归档包含输入与原始输出，正式使用时按数据政策选择资料并保护文件。

## 评测交付物：把示例集当成版本化测试资产

对后端工程师来说，可以把 few-shot 示例看成一组随请求发送的输入/期望输出 fixture。它们既定义模型要模仿的格式，也可能隐式定义业务标签；因此示例变更应像 API schema 或规则配置一样做版本管理、代码审查和回归测试。仅保存一段 prompt 文本，不足以重建一次评测。

一份可复核的示例评测至少应留下三类产物：

- **任务契约**：目标、标签定义、边界决策、输入输出结构、无法判断时的行为。若两个标注者按契约仍无法独立判断，先修任务定义，而不是要求模型从含糊示例中猜。
- **数据清单**：开发集和留出集的版本、来源、标签依据、去重结果、每类覆盖情况。留出集在本轮提示迭代结束前不用于挑选示例；查看失败后再改提示，就应另建确认集。
- **运行报告**：提示版本、请求模型与响应模型、关键参数、每条原始输出、解析结果、usage、错误类别和评测日期。记录失效输出、截断、拒答和超时，不要把它们默默丢出分母。

| 失败形态 | 观测信号 | 排查动作 |
|---|---|---|
| 示例或近似改写进入留出集 | 演示文本与测试相同，或仅换标点/同义词 | 精确去重后再做人审近似样本；重新划分未触碰的留出集 |
| 标签规则没有定义清楚 | 人工也对“中性/负面”分歧，模型错误集中在边界 | 写出优先规则与不确定时的标签；对样本独立复核 |
| 输出格式被评分器误读 | 一个答案里出现多个标签，正则只取第一个 | 解析器只接受精确允许值；把 invalid 单独计数并检查原始文本 |
| 总体准确率掩盖类别退步 | 少数类样本很少或混淆方向改变 | 看混淆矩阵、每类 precision/recall 与错误严重度；按任务目标选择主指标 |
| 结果随请求变化 | 同一题在重复调用中预测不同 | 固定模型快照和参数、随机交错条件，保留每次输出并估计区间 |
| 示例成本上升但收益不明 | input usage 或延迟增加，关键错误未改善 | 将额外资源与目标错误修复量一起比较；必要时测缓存后的真实请求口径 |

验收不要写成“示例数量至少为 N”或“所有样本必须全对”。先明确任务风险，再预先约定目标指标、允许的退步、最小有意义差异和样本量依据。离线静态检查可以保证 fixture 不重复、schema 有效、版本已记录；只有在真实目标数据上运行的评测才能说明它对模型输出有什么影响。到了发布阶段，还要在模型升级后运行同一套回归集，并查看是否出现新增失败类别。

## 如何解释结果

本节旧表能提出“哪些示例可能值得测试”的假设，不能证明“边界示例导致 10/10”或“典型示例完全无用”。2 条文本重复使边界结果存在泄漏；测试集小、每组只运行一次、模型快照和评分器缺失，又进一步限制结论。

实用的决定方式是看留出案例的逐项差异：某示例是否修复了目标错误？它是否影响其他标签？差异在重复运行、合理的输入变化和目标模型版本上是否仍存在？新增输入 token、延迟与维护成本是否值得？在回答这些问题前，不要把“例子越少越好”或“例子越多越稳”写成默认规则。

错误标签也要严肃处理。旧记录的 5 次测试只用了一个明显正面句子，无法说明边界案例会不会被错标签影响。示例标签应由规则和独立标注检查；对模糊业务定义，先修订标签手册，再扩展示例。把无效输出、拒答、截断和错标签分别记录，避免把解析失败误记成分类错误。

## 检查清单

- 标签定义先于示例，边界情况也有可复核理由。
- 开发集用于找错误；留出集与示例集没有重复或近似泄漏。
- 同一模型版本、请求参数、题目和评分规则比较各配置，并保存逐题记录。
- 使用总体指标和按类指标检查 trade-off；样本量根据希望检测的差异确定。
- 格式一致作为数据质量习惯；它是否改变模型表现仍要在任务上验证。
- 每次请求的 usage 与结果一起记录；只在示例确实改善目标质量时承担其 token 与维护成本。
