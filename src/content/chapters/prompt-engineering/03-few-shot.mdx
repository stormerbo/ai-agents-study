「示例不够多，再加几个」——这是 prompting 里最常见的直觉，也是最容易白费力气的地方。

本节用一组对照实验说明：**决定效果的不是示例数量，而是示例覆盖了什么。**

## 实测：10 个典型示例 ≈ 零样本

任务：把用户评论分类为「正面 / 负面 / 中性」。

测试集 10 条，其中 **4 条是容易误判的边界情况**（反讽、混合评价、委婉否定）。四组配置各跑一遍：

| 配置 | 示例内容 | 准确率 | 错在哪 |
|---|---|---:|---|
| ① 零样本 | 无示例 | **9/10** | 反讽那条判成中性 |
| ② 10 个典型示例 | 「很好用，推荐购买」→ 正面 … | **9/10** | **同一条** |
| ③ 3 个边界示例 | 「东西是好东西，就是太贵」→ 中性 … | **10/10** | 全对 |
| ④ 10 典型 + 3 边界 | 上面两组相加，共 13 条 | **10/10** | 全对 |

（实测数据，`deepseek-flash`，2026-10-08。）

这张表里有两个值得反复看的地方。

### 第一处：第 ② 行和第 ① 行完全一样

我加了 **10 个示例**，准确率**一点没变**（9/10），而且错的是同一条。

原因不难理解：那 10 个示例都是**显而易见的** —— 「很好用，推荐购买」当然是正面，「质量太差了」当然是负面。**模型不用看示例也知道这些。** 这些示例消耗了 token，却没有传递任何新信息。

### 第二处：第 ③ 行和第 ④ 行完全一样

第 ③ 行只有 **3 个示例**，准确率 10/10。

第 ④ 行把 10 个典型示例加上去，**准确率还是 10/10**。

也就是说：**起作用的只有那 3 条边界示例，另外 10 条纯属陪跑。**

而且第 ④ 行还更贵 —— 多出的 10 条示例，每次请求都要重发一遍。

## 怎么挑选示例

既然决定效果的是覆盖度，挑选方法就很具体了：

### 第一步：列出模型已经在错的类型

不要凭想象挑示例。**先去跑一遍零样本，看模型错在哪**。

我上面的实验就是这样做的：零样本跑完，发现反讽那条稳定出错，于是构造了针对性的示例。**示例是用来修补具体缺陷的，不是用来"教模型说话"的。**

### 第二步：按「容易混淆」挑选，不按「典型」挑选

| 该选 | 不该选 |
|---|---|
| 「东西是好东西，就是太贵」→ 中性 | 「这个产品很好用」→ 正面 |
| 「不是不好用，只是不适合我」→ 中性 | 「质量太差了」→ 负面 |
| 「总算没搞砸，但也就那样」→ 负面 | 「再也不会买了」→ 负面 |

**判据很简单：如果去掉这条示例，模型大概率也能做对，那它就不该占名额。**

反过来，那些「看起来像 A 其实该归到 B」的例子，才是真正传递信息的。

### 第三步：格式尽量一致（但别当成铁律）

「模型会忠实地复制你示例里的不一致」——这是一句流传很广的说法。我测了一遍，**没能复现**：

| 示例格式 | 守约定次数 |
|---|---|
| 三条示例结构完全一致 | 12/12 |
| 其中一条多带一个额外字段 | **12/12** |

（实测数据，`deepseek-flash`，2026-10-08。判据：输出是否恰好是两个约定字段、类型正确。）

**轻微的不一致没有造成影响。** 但这不等于可以随便写：

- 我的测试里不一致的程度很轻（只是一条示例多了个可选字段）
- 结构性的差异（一半 JSON、一半 YAML）大概率会有影响，**我只是没测**
- 格式一致是**零成本**的，没有理由不做

所以这条经验的价值不在于「必须严格一致」，而在于：**遇到输出「时好时坏」时，格式不一致是应该排查的方向之一 —— 但别把它当成必然原因。**

> 这是本项目第三个「未复现」的常见说法（前两个是「否定式指令更不稳」与「中间位置被忽略」）。
> 它们共同说明一件事：**这个领域里流传的很多经验之谈没有实测支撑**，包括我写的这一条。

### 「加了示例有没有提升」怎么判断

本节开头那张表是每个配置**跑一遍**得到的结果。要把它变成判据，还差三样东西：**测试集、重复次数、阈值。**

| 要素 | 这里怎么定 | 理由 |
|---|---|---|
| 测试集 | 固定那 10 条，其中 **4 条是边界题** | 10 条总数偏少，够发现「明显提升」，不够发现小提升 —— 想分辨 10 个百分点按第 1 章的算法要上百条 |
| 重复次数 | **5 遍**，看每遍是否一致 | 单次差异可能来自采样噪声，不是示例的作用。注意：第 2 节实测过 `temperature=0` 也不保证可复现 |
| 阈值 | **边界题全对**（4/4），且**5 遍都全对** | 边界题才是示例要修的东西；典型题本来就会做，它们全对不构成「提升」 |

**判据一句话**：只有当你删掉某条示例后，`边界题从全对变成有错`（且在 5 遍里稳定复现），那条示例才算真的在起作用。否则它就是每轮都在付 token 的陪跑项。

```python
# ablate_examples.py
"""验证一条示例到底有没有用：删掉它，边界题还全对吗？"""

import os
import re

import anthropic

client = anthropic.Anthropic(
    api_key=os.environ.get("ANTHROPIC_API_KEY")
    or os.environ.get("ANTHROPIC_AUTH_TOKEN"),
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)
MODEL = os.environ["VERIFY_MODEL"]

# 边界题：模型在零样本下会判错的那类（这里是反讽 / 委婉否定 / 混合评价）
BOUNDARY_TESTS = [
    ("东西是好东西，就是太贵", "中性"),
    ("不是不好用，只是不适合我", "中性"),
    ("总算没搞砸，但也就那样", "负面"),
]

EXAMPLES = [
    ("东西是好东西，就是太贵", "中性"),        # 与测试集同型
    ("总算没搞砸，但也就那样", "负面"),
    ("不是不好用，只是不适合我", "中性"),
]

BASE = "把用户评论分类为『正面』『负面』或『中性』，只回复类别名。"
RUNS = 5


def classify(system: str, text: str) -> str:
    resp = client.messages.create(
        model=MODEL, max_tokens=800, system=system,
        messages=[{"role": "user", "content": text}],
    )
    out = "".join(b.text for b in resp.content if b.type == "text").strip()
    m = re.search(r"正面|负面|中性", out)
    return m.group(0) if m else out[:6]


def score(examples: list[tuple[str, str]]) -> int:
    """返回边界题在 RUNS 遍里的总对数（满分 = 题数 × RUNS）。"""
    system = BASE if not examples else BASE + "\n\n示例：\n" + "\n".join(
        f"「{t}」→ {c}" for t, c in examples
    )
    return sum(
        classify(system, text) == expect
        for _ in range(RUNS)
        for text, expect in BOUNDARY_TESTS
    )


if __name__ == "__main__":
    full = score(EXAMPLES)
    total = len(BOUNDARY_TESTS) * RUNS
    print(f"全部 {len(EXAMPLES)} 条示例: {full}/{total}")

    # 逐条消融：一次删一条，看分数掉不掉
    for i in range(len(EXAMPLES)):
        ablated = EXAMPLES[:i] + EXAMPLES[i + 1:]
        s = score(ablated)
        verdict = "这条在起作用" if s < full else "删掉没差别 → 陪跑"
        print(f"删掉第 {i + 1} 条: {s}/{total}   {verdict}")
```

> **实跑状态：未实跑。** 这个脚本是本次新写的（消融式验证），**没在这台机器上跑过**。它的测试题与示例取自本节上面那份实测脚本，但**分数是你自己跑出来的才对**。

> 跑之前注意一件事：如果全部示例的分数已经是满分，删一条仍可能不掉分 —— **那正说明这条示例在陪跑**，而不是说明实验失败。

## 完整可运行代码

```python
# few_shot_experiment.py
"""对比示例数量与示例质量对准确率的影响。

把 TEST / TYPICAL / BOUNDARY 换成你自己的任务就能跑。
关键在 BOUNDARY —— 那些「容易混淆」的例子需要你自己从失败案例里挖出来。
"""

import os
import re

import anthropic

client = anthropic.Anthropic(
    api_key=os.environ.get("ANTHROPIC_API_KEY")
    or os.environ.get("ANTHROPIC_AUTH_TOKEN"),
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)
MODEL = os.environ["VERIFY_MODEL"]

# 测试集：含 4 条容易误判的边界情况
TEST = [
    ("这个产品很好用", "正面"),
    ("完全是个灾难", "负面"),
    ("东西收到了", "中性"),
    ("总算没搞砸，但也就那样", "负面"),
    ("还行吧，没什么特别的", "中性"),
    ("客服态度不错，问题解决了", "正面"),
    ("用了三天就坏了", "负面"),
    ("请问什么时候发货", "中性"),
    ("比我想象的好太多了", "正面"),
    ("下次不会再买了", "负面"),
]

# 典型示例：数量多，但都是显而易见的 —— 模型不看也会
TYPICAL = [
    ("很好用，推荐购买", "正面"), ("质量太差了", "负面"), ("今天下的单", "中性"),
    ("非常满意", "正面"), ("再也不会买了", "负面"), ("刚收到货", "中性"),
    ("性价比很高", "正面"), ("有质量问题", "负面"), ("想问下保修期", "中性"),
    ("五星好评", "正面"),
]

# 边界示例：数量少，但每条都在教「怎么区分容易混的情况」
BOUNDARY = [
    ("东西是好东西，就是太贵", "中性"),
    ("总算没搞砸，但也就那样", "负面"),
    ("不是不好用，只是不适合我", "中性"),
]

BASE = "把用户评论分类为『正面』『负面』或『中性』，只回复类别名。"


def build_system(examples: list[tuple[str, str]]) -> str:
    if not examples:
        return BASE
    lines = "\n".join(f"「{t}」→ {c}" for t, c in examples)
    return f"{BASE}\n\n示例（共 {len(examples)} 条）：\n{lines}"


def classify(system: str, text: str) -> str:
    response = client.messages.create(
        model=MODEL, max_tokens=800, system=system,
        messages=[{"role": "user", "content": text}],
    )
    out = "".join(b.text for b in response.content if b.type == "text").strip()
    match = re.search(r"正面|负面|中性", out)
    return match.group(0) if match else out[:6]


if __name__ == "__main__":
    groups = [
        ("零样本", []),
        (f"{len(TYPICAL)} 个典型示例", TYPICAL),
        (f"{len(BOUNDARY)} 个边界示例", BOUNDARY),
        ("典型 + 边界", TYPICAL + BOUNDARY),
    ]

    print(f"{'配置':<18} 准确率  示例的 token 成本")
    print("-" * 48)
    for label, examples in groups:
        system = build_system(examples)
        ok = sum(classify(system, text) == expect for text, expect in TEST)
        # 示例占的篇幅，粗略反映每次请求的额外成本
        cost = len(system)
        print(f"{label:<18} {ok}/{len(TEST)}    system 长度 {cost}")
```

> **实跑状态**：本文表格里的**数据是实测的**；上面这份 Python 脚本用的 SDK 写法，字段一致但**脚本本身未在官方端点验证**。

## 一个反直觉的推论

上面的实验导出一个实用结论：

> **如果加了示例之后效果没提升，那多半不是示例太少，而是示例没覆盖到模型真正在错的地方。**

这时正确的动作是**回去看错误案例**，而不是继续加示例。

这也解释了为什么「堆示例」是条死路：如果新加的示例都是模型本来就会做的，那它对准确率没有任何贡献，只是在推高每次请求的成本。

## 示例里写错一个标签，会怎样

示例是「教」模型的，那如果**教错了**呢？这是 few-shot 最被担心的问题，也是本节开头结论的直接推论 —— 如果示例真能决定行为，一个写反的标签就该被学走。

我测了一次最小对照：情感分类，三个示例，其中一个把明显的正面话标成了 negative。

| 示例集 | 5 次分类「东西很棒，我很喜欢」 |
|---|---|
| 三个都正确 | positive ×5 |
| 第 3 个标签写反了 | **positive ×5** |

**没有被带偏。** 这与本节开头的结论一致：示例对这个模型的影响力比想象中小 —— 10 个典型示例等于零样本，一个写错的标签也没能动摇它的判断。

但这条结论有必须说清的边界：**我用的判断句情感太明确了**，模型完全可以绕过示例、靠常识作答。真正危险的是**语义模糊、必须靠约定才能分类**的输入 —— 比如内部工单的标签体系，那里的「正确答案」只存在于你的示例里。那种情况下示例的权重完全不同。

所以可操作的结论是：

- **示例主要用来传递「约定」，不是用来传递「常识」。** 常识类任务上它可能纯属陪跑（本节开头的实测）。
- **模糊输入才需要示例，而那里写错标签的代价最高。** 两件事叠在一起，意味着示例的正确性检查值得当成一次数据质量工作，而不是随手写几条。
- 顺带一笔成本账：示例是 prompt 的一部分，**每一轮都要重发**。10 个示例按每个 40 token 算，20 轮就是 8000 token —— 而本节的实测说，它们可能一个都没起作用。

再补一个挑选示例的实用判据。既然示例的价值在于传递约定，那么**判断一个示例有没有用，标准就是「去掉它之后模型还会不会给出同样的答案」**。会，它就是陪跑；不会，才说明它真的携带了信息。本节那 10 个典型示例属于前一种 —— 成本每轮都付，收益是零。

顺带说一句示例的顺序。本节没有单独测它，但「错误标签没被学走」这个结果至少说明：**在常识足够明确的任务上，示例的排列顺序不会成为主要变量**。而在约定类任务上顺序是否重要，值得你自己验一遍 —— 本节那个脚本改一改就能回答。

## 常见坑

**以为示例越多越稳。** 实测显示 10 个典型示例的效果等于零样本。

**挑「典型」示例。** 典型情况模型本来就会。该挑的是「容易混」的。

**示例格式不一致。** 模型会忠实复制你的不一致，表现为「时好时坏」，而你会误判成模型不稳定。

**加完示例不看效果就上线。** 加示例是有成本的（每次请求都重发）。**没用就该删掉**，而不是留着「以防万一」。

**一次加太多示例，无法归因。** 一次只加一条（或一组同类），跑一遍看有没有提升。否则你不知道是哪条起了作用。
