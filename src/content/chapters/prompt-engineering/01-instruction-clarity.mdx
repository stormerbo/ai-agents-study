先看一组实测数据。同一个任务，**只改约束的写法**，各跑 8 次：

> 任务：写一段 200 字左右的公司介绍。这是一家做企业级数据分析的公司，目标客户是中型制造企业。

| 约束写法 | 越界次数 | 字数达标 | 平均字数 |
|---|---:|---:|---:|
| ① **纯否定**：「不要提到价格、费用或任何具体数字」 | 0/8 | 3/8 | **74 字** |
| ② **纯正面**：「内容限定在技术能力与适用场景两个方面」 | 3/8 | 5/8 | **108 字** |
| ③ **组合式**：否定划边界 + 正面给方向 | 0/8 | 4/8 | **113 字** |

（实测数据，`deepseek-flash`，2026-10-08。要求 200 字，这里把「≥150 字」算作达标。）

看这张表之前先交代我的预判：**我以为正面指令会更稳**。很多教程也这么说 —— 「告诉模型你要什么，而不是你不要什么」。

**实测结果是：两种写法各有代价，但代价的形式和我想的不一样。**

## 否定式的代价不是「失效」，是「过度保守」

先看第 ① 行。纯否定式 —— 「不要提到价格」—— **越界 0 次**。它完美地达成了目标。

但它同时**平均只写了 74 字**，而要求是 200 字。8 次里只有 3 次达到 150 字。

对比第 ② 行：纯正面式平均写 108 字，但越界 3 次（提到了「成本」）。

所以否定式的问题**不是「模型不听」** —— 它听了，而且听得很彻底。问题是它在阻止目标行为的同时，**把大量合法内容也一起抑制了**。模型不确定哪些内容「可能沾边」，于是选择少说。

这个现象值得单独记住：

> **否定式指令的实际效果，往往不是「精准排除某个东西」，而是「整体收缩输出空间」。**

## 那为什么不能只用正面？

第 ② 行给出了答案：正面式确实展开了（108 字），但越界 3 次。

原因不难理解。「内容限定在技术能力与适用场景」这句话划的范围**不够紧**。什么是「技术能力」？写「降低了客户的**成本**」算不算在讲技术能力带来的价值？在模型看来算 —— 所以它写了，然后越界了。

**正面式的问题在于：你给出的正向描述，未必能覆盖你想排除的情况。**

## 组合式为什么最好

第 ③ 行是我把两者拼起来：

```
不要提到价格、费用或任何具体数字。
内容聚焦在技术能力（如数据处理规模、集成方式）与适用场景（如产线质检、设备预测性维护）上。
```

结果：**越界 0 次，平均 113 字**。

两句话各司其职：

- **否定句划出禁区** —— 精确定义「不能做什么」。这是正面描述难以替代的
- **正面句给出方向** —— 告诉模型「该往哪走」，避免它因为不确定而过度收缩

注意我在正面句里加了**具体的例子**（数据处理规模、集成方式、产线质检、设备预测性维护）。这不是修饰 —— 它把「技术能力」这个抽象概念落成了具体方向，模型因此知道自己**能**写什么。

## 完整可运行代码：复现这组实验

下面这段脚本可以直接运行。把 `TASK` 与 `VIOLATION_RE` 换成你自己的场景，就能测你自己的 prompt：

```python
# compare_instruction_styles.py
"""对比三种约束写法的效果。

改 TASK 与 VIOLATION_RE 就能套到你自己的场景上 —— 这是本节的真正交付物：
不是「应该这样写」的结论，而是一个能验证你自己写法的工具。
"""

import os
import re

import anthropic

client = anthropic.Anthropic(
    api_key=os.environ.get("ANTHROPIC_API_KEY")
    or os.environ.get("ANTHROPIC_AUTH_TOKEN"),
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)
MODEL = os.environ["VERIFY_MODEL"]

TASK = (
    "写一段 200 字左右的公司介绍。"
    "这是一家做企业级数据分析的公司，目标客户是中型制造企业。"
)

VARIANTS = {
    "纯否定": TASK + "\n\n不要提到价格、费用或任何具体数字。",
    "纯正面": TASK + "\n\n内容限定在技术能力与适用场景这两个方面。",
    "组合式": (
        TASK
        + "\n\n不要提到价格、费用或任何具体数字。"
        + "内容聚焦在技术能力（如数据处理规模、集成方式）"
        + "与适用场景（如产线质检、设备预测性维护）上。"
    ),
}

# 判据一：越界（出现价格类词或具体数字）
VIOLATION_RE = re.compile(r"价格|费用|成本|定价|收费|\d+\s*(元|万|美元|%)")
# 判据二：达标（中文字数下限）
MIN_CHARS = 150
RUNS = 8


def once(system: str) -> tuple[bool, int]:
    """跑一次，返回（是否越界, 中文字数）。"""
    response = client.messages.create(
        model=MODEL,
        max_tokens=1500,
        messages=[{"role": "user", "content": system}],
    )
    text = "".join(b.text for b in response.content if b.type == "text").strip()
    violated = bool(VIOLATION_RE.search(text))
    chars = len(re.findall(r"[一-龥]", text))
    return violated, chars


if __name__ == "__main__":
    print(f"{'写法':<10} 越界   达标(≥{MIN_CHARS}字)  平均字数")
    print("-" * 46)

    for label, system in VARIANTS.items():
        bad = good = total = 0
        for _ in range(RUNS):
            violated, chars = once(system)
            bad += violated
            good += chars >= MIN_CHARS
            total += chars
        print(f"{label:<10} {bad}/{RUNS}   {good}/{RUNS}          {total // RUNS}")
```

> **实跑状态**：本文表格里的**数据是实测的**（用直接 HTTP 请求采集）。上面这份 Python 脚本用的是 SDK 写法，字段与采集脚本一致，但**脚本本身未在官方端点验证**。

**为什么这个脚本比结论更重要**：约束写法的最优解**依赖你的具体任务**。我做出来的结论（组合式最好）只在这个任务上成立。你该做的是把这套脚本套到自己的场景上，得到你自己的数字。

## 所以「清晰直接」的真正含义

回到本节标题。多数人理解的「清晰」是**把话说得漂亮、完整**。但实测显示，真正起作用的是另外三件事：

**第一，正反两面都要说。** 只说不该做什么，模型会过度收缩；只说该做什么，边界又会松。

**第二，把抽象概念落到具体。** 「技术能力」不如「数据处理规模、集成方式」；「简洁回答」不如「控制在三句话以内」。抽象描述留下解释空间，而模型的解释未必是你想的那种。

**第三，约束要可判断。** 「写得专业一点」不可判断；「不使用第一人称」可判断。可判断的约束才能被稳定执行 —— 这也是第 5 节要讲的「让输出稳定」的基础。

## 冲突发生时，模型听谁的

写 prompt 时最常撞上的不是「怎么写清楚」，而是**两条规则打架时怎么办** —— 用户在对话里说「用中文回答」，而你的 system 写着「一律用英文」。

我做了对称测试来排除语种偏好（两边都不用英文，用中文对法文）：

| 规则摆放 | 3 次的结果 |
|---|---|
| system 要法文 / user 要中文 | 法文 ×3 |
| system 要中文 / user 要法文 | 中文 ×3 |

**system 层稳定压过 user 层** —— 两个方向都赢在 system，所以不是碰巧偏向某个语种。

那两条规则都在 user 里呢？

| 规则摆放 | 3 次的结果 |
|---|---|
| 先法文、后中文 | 中文 ×3（听了后一条） |
| 先中文、后法文 | 法文 ×1、中文 ×2（**不稳定**） |

**同层冲突时行为不稳定。** 两次的方向都不一致，所以别把「后出现的指令会覆盖先出现的」当成规则来用。

工程含义三条：

1. **不可协商的约束放 system**，它压得住 user 层。
2. **别指望在 user 层写「不要做 X」去挡住另一条指令** —— 同层之间没有可靠优先级。
3. **同层冲突应该被消除，而不是被排序。** 出现两条互相拉扯的指令时，正确做法是删掉一条、或合并成带条件的一条。第 3 章那组实测可以佐证：矛盾规则会让同一份 prompt 跑出 8/12 的分裂。

还有一个附带发现值得记：这个测试里最长的一次用了 **3153 个 output token**，而它最终只输出了一句「你好！」。规则冲突会让模型反复权衡 —— **冲突的代价不只是行为不稳定，还有实打实的 token。**

最后补一条操作建议：**把 system 与 user 的职责分开。** system 放不可协商的约束（语言、格式、安全边界、角色）；user 放这一次任务的参数（对象、范围、语气）。当你在 user 里写下「不要……」时，先问一句：这难道不是一条该上移到 system 的约束？同理，凡是「必须始终成立」的规则都属于 system，而不是某一轮任务的描述。

## 一个诊断清单

prompt 效果不好时，先判断症状属于哪一类，**因为修法方向是相反的**：

| 现象 | 大概率原因 | 怎么改 |
|---|---|---|
| 输出太短、内容单薄 | **否定式用多了**，模型不确定能说什么 | 补正面描述 + 具体例子 |
| 输出越界、夹带不该有的内容 | 只有正面描述，范围划得不够紧 | 补一句否定式划边界 |
| 时好时坏、不稳定 | 约束本身模糊，不可判断 | 把抽象要求落成可判断的条件 |
| 输出很长但没重点 | 没给长度或结构约束 | 明确字数、段数或输出格式 |

**别在没判断清楚症状前就盲目加长 prompt。** 「输出太短」和「输出越界」需要的是相反的修改 —— 加错方向只会让问题更严重。
