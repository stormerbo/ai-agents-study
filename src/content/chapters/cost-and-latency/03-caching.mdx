第 1 节说「不变的内容是好的复用候选」，但哪些输入被缓存、怎样命中和如何计价，必须按 provider、model 与 endpoint 的契约判断。缓存复用的是模型处理过的前缀状态；它不是应用数据缓存，也不保证后续请求一定命中。

## 第 1 章的实测

第 1 章的历史记录摘要写着：`deepseek-flash` Anthropic 兼容端点于 2026-09-24 有一组请求，记录了以下现象：

```text
命中缓存：未缓存输入从 2688 降到 256，耗时快 3.4 倍
改一个词：该次请求未报告缓存读取
```

原始逐次响应没有归档，因此这些数字无法独立复算。3.4 倍延迟差只是两次历史请求的对照，不能单独证明因果。即使记录无误，也只描述该 endpoint 当时的观测，不证明其缓存键或失效规则适用于其他接口。

## 前缀与缓存键：先看具体接口契约

支持前缀缓存的接口可能按缓存断点或其他 provider 定义的键复用输入。以下「前缀」示意适用于有前缀缓存语义的接口；具体纳入缓存的字段、序列化方式、缓存键和断点规则，应以目标 provider 与 endpoint 文档为准。Anthropic 的 `tools → system → messages` 顺序和显式断点规则是该 API 的契约，不是所有兼容端点的通用协议。

在按累计前缀匹配的契约下，较早位置改变会使从该处开始的候选前缀不同；后续是否仍能复用某个更短的已缓存前缀，由具体接口的缓存单元、断点查找和路由规则决定。不能把“前缀不同”直接推成“全部缓存必然失效”。

```text
[按目标 API 定义的缓存输入顺序]
     ↑ 改这里       → 对应断点/键可能不再匹配
                    ↑ 改这里   → 影响范围依断点与 API 规则而定
```

因此，对于按前缀复用且已确认其键/断点规则的接口，可以把稳定内容放在易变内容之前，减少动态字段改变可复用前缀的机会。不要在未核实缓存契约时，把这个顺序直接当作 provider 无关的保证。

当目标 endpoint 按前缀缓存且文档确认以下序列化/匹配关系时，这类顺序建议在 agent 里尤其有用：

```text
❌ 把用户上传的文档放在系统提示之前
❌ 把当前时间戳拼在系统提示的最前面
❌ 把工具定义放在历史消息之后
✅ 系统提示 → 工具定义 → 历史 → 本轮输入（本轮输入里，稳定的在前）
```

第二行是个常见的风险：**在缓存键覆盖的稳定区域开头拼一个时间戳**。在按前缀匹配的契约下，这可能导致较长的缓存前缀无法复用；实际命中范围须结合目标接口的键、断点和查找规则确认。

## 怎么把缓存打开：请求体里的断点

前面讲了前缀复用的思路，但显式缓存断点只适用于支持该功能和语法的接口。下面是 Anthropic Messages API 的 `cache_control` 请求形态；不能将它当作 DeepSeek Anthropic 兼容 API 或其他 provider 的缓存开关：

```json
{
  "model": "claude-opus-5-5",
  "max_tokens": 64,
  "system": [
    {"type": "text",
     "text": "<长且逐字固定的系统提示 + 参考资料>",
     "cache_control": {"type": "ephemeral"}},
    {"type": "text", "text": "<易变内容，比如当前时间>"}
  ],
  "messages": [{"role": "user", "content": "用一句话概括上面资料的主题。"}]
}
```

这段 JSON 是 Anthropic API 的请求形状示例。这里的短占位符不是实际可缓存内容；按示例字面发送，不能期待达到当前模型和平台的最小缓存长度。`cache_control` 只标记候选断点，是否实际写入或读取缓存要以响应 usage 为准；请替换成真实上下文，并按当前模型与平台文档核对门槛。它不是可跨 provider 复制的缓存开关。三个要点：

1. **断点位置由接口契约定义。** Anthropic API 的缓存层级和断点按 Anthropic 文档解释；兼容端点的字段被接受或忽略，都不能仅凭 SDK 类型推断。
2. **DeepSeek 不能直接套用这个显式断点示例。** 当前 DeepSeek Anthropic API 文档明确把 `cache_control` 列为 ignored；其官方 Context Caching 说明的是自动磁盘缓存与完整缓存前缀单元匹配。该当前文档不能证明 2026-10-12 历史响应里的具体缓存实现。
3. **缓存门槛、断点数、TTL、自动缓存、计量与费率都可能按 provider/model/endpoint 不同。** 不要把一个接口的前缀长度观测当作其他接口的缓存门槛。

### 历史 usage 表（原始响应缺失，无法独立复算）

条件：固定前缀约 8250 字符（约 2.4k token），断点打在第一个 system 块上；请求体就是上面那段。实跑数据 2026-10-12，`deepseek-flash`。

```text
组别                           input_tokens   cache_read   cache_creation   说明
1 冷启动（带断点）                    4693            0              0   本次未报告缓存读取

4-b 无断点第二次                      185         4352              0   本次读取 4352 cache tokens
5-a 短前缀第一次                      221            0              0   约 110 token 的前缀
5-b 短前缀第二次                      221            0              0   本次未报告缓存读取
```

**这组历史表记录的输入项从 4693 降到 213、`cache_read` 记为 4480。** 但原始响应不可用，字段映射与计量口径无法独立确认；不能据此报告通用的“缓存节省量”。第 3 组也不能证明其他接口上“断点之后随便变”都能命中。

两个必须如实说明的观测：

- **第 4 组：历史表记载该次无断点请求也有缓存读取。** 这与自动缓存解释相符，但因为原始请求/响应未保存，不能确认它是如何触发的，也不能推断 `cache_control` 是必要或有效条件。
- **历史表把 `cache_creation` 记为 0。** 这只是该表的记录；由于原始响应没有归档，无法确认它对应 provider 的正式字段，或能否与 `input_tokens` / `cache_read` 相加。不要把下方 Anthropic 的三字段公式套给 DeepSeek、OpenAI 或其他 endpoint。

**失败形态：** 在支持显式断点的接口上，断点位置或输入稳定性与预期不符，可能导致缓存读取低于预期；表现和诊断方式由接口定义。检查时先核对目标 endpoint 的缓存开关、输入字段、断点/缓存键规则、TTL 与 usage，再用重复请求验证。不要只凭「断点后还有动态内容」就认定配置错误，也不要把未命中单独归因于长度或前缀变化。


## 在 agent 循环里，缓存为什么更重要

在常见的 stateless Chat Completions 用法里，客户端会把当前需要的消息历史放进下一次请求；但托管会话、server-side conversation state、摘要/裁剪策略可能改变实际传输方式。不要把“每一轮都重发全部历史”当作所有 agent runtime 的定律。

这意味着：每轮请求仍包含当时需要的上下文；前缀缓存命中时，服务端可以复用已有前缀计算，usage 中缓存读取量仍按 provider 规则计费。命中与否会改变计算与计价类别，不会把历史 token 从请求和 usage 中删除。

仅在第 1 节那个 stateless、每轮增长历史并完整重发的简化模型中，未缓存的累计输入按 `57N + 8N(N-1)` 增长。缓存可以复用服务端已算过的前缀状态，却不会消除应用需要保留的逻辑上下文，也不会跳过新输入的处理。能否减少网络传输、如何报告 usage、缓存读取/写入怎样收费，都因接口而异；应分别测量传输量、端到端时延和总费用。

**缓存可能对共享稳定前缀的多轮工作流更有价值。** 这是优化候选，不是固定收益：上下文是否复用、每轮请求是否携带完整消息、cache read/write 的费率及 TTL 都按具体系统验证。

## 缓存的三个排查方向

**方向一：时间戳、随机 id、请求 id 拼进缓存覆盖的输入。** 在按前缀匹配的接口上，这可能降低后续前缀的复用。先按目标 API 的契约确认哪些字段参与缓存，再考虑把动态信息放到不影响目标复用段的位置。

**方向二：工具定义的顺序不稳定。** 若目标 API 将工具定义纳入缓存键，序列化顺序变化可能导致该部分无法复用。需要按接口的序列化与键规则验证；若适用，固定工具顺序有助于保持请求稳定。

**方向三：系统提示里塞了动态内容。** 比如把用户画像、权限列表拼进系统提示。这些内容每轮都可能变；如果目标接口的缓存规则将它们纳入稳定前缀，复用可能受影响。

三个陷阱的共同点是：它们可能改变目标接口参与缓存匹配的请求表示。语义相同不保证缓存键相同；应根据接口文档和 usage 观测，而不是假定存在统一的「差别是 100%」规则。

## 复用：不能缓存的那部分

缓存解决的是「同样的输入重复发送」。还有一类复用是「同样的结果不用重算」：

- **工具结果缓存**：查同一个订单两次，第二次直接用上次的结果（要注意时效性）
- **检索结果缓存**：第 6 章的检索，同样的查询加同样的语料可以直接返回
- **确定性计算的缓存**：任何由代码算出来的中间结果

这类缓存的判据和上面不同：它要求**输入相同且结果未过期**。过期策略取决于数据的变化频率 —— 订单状态可能几分钟就变，而文档内容可能几周不变。

## 一个反过来的代价

缓存不是免费的，代价有三条：

**一、实现复杂度。** 什么时候失效、怎么验证生效，都是要维护的逻辑。

**二、可能读到旧结果或越权数据。** 工具结果缓存如果过期策略设错，用户会看到过时数据；如果缓存键漏掉租户/对象范围，或读取时未重新检查授权，还可能把其他主体的数据返回给当前用户。缓存键不是授权凭证，服务端应在每次读取时按可信身份验证租户与对象权限。

**三、测量变难。** 第 4 节那个陷阱：缓存读取可能以单独字段出现在 usage 中；只看一个输入字段可能误判成本。要先按 provider 文档核对字段，再按账单费率计算。

第三条是本节和前面章节的连接点：**缓存让成本数据变得难以直接比较。** 任何时候看到「成本突然降了一半」，先问一句是不是缓存生效了。


## 一个简化模型：改动位置可能影响多少复用

在累计前缀匹配的简化模型里，较早位置的变化会影响更长的候选前缀。下面按一份示例上下文计算四种改动位置；这是模型演算，不是任何 provider 的实测命中率或通用缓存契约：

```text
改在哪一段              候选可复用比例   候选前缀 token   模型未计入 token
第 1 段：系统提示                0.0%              0             4,080
第 2 段：工具定义                9.8%            400             3,680
第 3 段：历史消息               21.6%            880             3,200
第 4 段：本轮输入               95.1%          3,880               200
```

（本地模拟，2026-10-09。分段：系统提示 400、工具定义 480、历史消息 3000、本轮输入 200。）

这些值只是被模型假设为可复用的前缀 token 占分段总量的比例，不是 cache hit 率或概率。在这个简化模型中，同样是「改一处」，候选可复用比例从 0.0% 到 95.1%。

这份**简化累计前缀模型**中，最前一段变化会令模型假设的可复用前缀归零。真实 endpoint 是否如此，取决于它的缓存键和断点规则；时间戳的例子只是说明为什么要检查动态字段是否进入目标接口的缓存覆盖区域。

如果确实需要时间信息，可以评估是否放入不影响目标接口可复用范围的请求部分，或在需要时通过工具查询；具体放置位置要根据该接口的缓存规则与任务要求决定。

## 什么时候缓存会让成本数据变得无法解释

第 3 节提过一个测量问题，值得展开，因为它是实际操作中最容易误判的地方。缓存相关 usage 字段并没有跨 provider 的统一名称或含义，先按目标 endpoint 文档解读，再把字段映射到费用。

下面是 Anthropic Messages API 的示意口径：`input_tokens` 表示未缓存输入，缓存读取和写入分列报告。相同上下文可能出现如下 usage 差异；数字仅为示意，不是历史实测：

```text
冷启动（示意）：input_tokens = 4080, cache_read_input_tokens = 0
缓存读取（示意）：input_tokens = 0,    cache_read_input_tokens = 4080
```

仅看 `input_tokens` 会漏掉缓存读取输入；但也不能据此断言它免费或所有请求费用等价，实际计价还取决于 provider 对缓存读取、写入和其他 token 的费率。

Anthropic Messages API 的总输入可按其 usage 字段相加：

```text
Anthropic total input = input_tokens + cache_read_input_tokens + cache_creation_input_tokens
```

这不是通用公式：DeepSeek Chat API 使用 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 等字段；OpenAI 在输入 token details 下报告 cached tokens。Anthropic Messages API 的 total input 可由 `input_tokens`、`cache_read_input_tokens` 与 `cache_creation_input_tokens` 相加；DeepSeek Chat API 与 OpenAI 的缓存 usage 字段结构不同，因此该公式不能跨 provider 套用。按各自文档与账单口径计算，不能跨 provider 直接相加字段。

这个陷阱在本项目里**实际发生过一次**（第 4 节记录的）：当时测「工具定义成本」，数据出现「1 个工具 306 token、3 个工具 174 token」的矛盾结果，看起来像「工具越多越便宜」。一种可能解释是缓存状态不同，而当时只读取了 `input_tokens`；但该历史记录缺少原始逐次响应，不能把这个解释当成已独立确认的因果结论。

**教训是通用的：成本异常下降时，应先检查缓存状态、usage 口径、请求范围与费率，再归因。**

## 一个反过来的用法：缓存命中率是一个指标

除了省钱，缓存命中率也是一个可调查的运行信号。它是否能被 API 直接观测、按什么分母计算，取决于 provider 的 usage 与 dashboard：

- **命中率突然下降** → 可调查模板、动态字段、缓存配置或 endpoint 行为是否变化
- **命中率长期为 0** → 核对目标接口是否支持/启用缓存、请求是否满足条件及 usage 口径
- **某个工具上线后命中率下降** → 检查工具定义/序列化以及目标 endpoint 的缓存键规则

这些变化可能不触发错误，却会影响复用与账单；命中率是可调查的信号之一，需要结合接口契约和 usage 解读。

## 一个反过来的检查：缓存是不是在帮倒忙

缓存也会做错事，有两种形态值得知道。

**形态一：缓存让问题变得更隐蔽。** 一份上下文被缓存了，但它里面含有一个**已经过期的事实**（比如某个订单的状态）。缓存让「同样的输入」得到「同样的输出」—— 而那个输出基于的是一小时前的数据。这类问题不会报错，只会让用户看到旧结果。

所以缓存之前要先分清：**这段内容是"不变的事实"还是"某个时刻的快照"？** 系统提示和工具定义属于前者，而工具返回值属于后者 —— 后者缓存要带过期时间（本节前面那个「复用」部分讲的就是这种情况）。

**形态二：缓存减少前缀处理，但端到端延迟变化不明显。** 对小输入或网络固定开销主导的场景，prefill 改进可能被其他耗时盖住；缓存也可能降低首 token 延迟。应测目标工作负载的 TTFT 与端到端耗时，不要从一次小样本观测推导缓存永远不省时。

这两件事要分开看：**省钱看 token，省时间看 decode。** 而很多"性能优化"的讨论把两者混在一起，于是得不出能落地的结论。
## 完整可运行代码

下面这段代码模拟一种**简化累计前缀缓存模型**：假设改变某段后，只有它之前的前缀可复用。它用于解释该模型下改动位置的影响，不模拟任何 provider 的缓存键、断点回退或自动缓存行为。

```python
"""简化前缀缓存演示：改动位置影响模型假定的可复用范围。纯本地。实跑状态：2026-10-09。"""
SEGMENTS = [("系统提示", 400), ("工具定义", 480), ("历史消息", 3000), ("本轮输入", 200)]


def candidate_reuse_ratio(changed_index):
    """简化模型：第 changed_index 段变化，返回此前前缀占比。"""
    total = sum(n for _, n in SEGMENTS)
    candidate_prefix = sum(n for _, n in SEGMENTS[:changed_index])
    # 仅按本演示的模型计算：变化段之前的 token 作为候选可复用前缀
    return candidate_prefix / total, candidate_prefix, total


if __name__ == "__main__":
    print("上下文分段：")
    for i, (name, n) in enumerate(SEGMENTS):
        print("  第 %d 段 %-10s %5d token" % (i + 1, name, n))
    print()
    print("  %-34s %8s %10s %12s" % ("改在哪一段", "候选比例", "候选前缀 token", "模型未计入 token"))
    for i, (name, n) in enumerate(SEGMENTS):
        ratio, candidate_prefix, total = candidate_reuse_ratio(i)
        print("  %-34s %7.1f%% %10d %9d" % ("第 %d 段：" % (i + 1) + name, ratio * 100, candidate_prefix, total - candidate_prefix))
    print()
    print("=== 关键点 ===")
    r1 = candidate_reuse_ratio(0)[0]
    r3 = candidate_reuse_ratio(2)[0]
    print("  改第 1 段（系统提示）：模型假设下的候选可复用前缀占 %.1f%%。" % (r1 * 100))
    print("  改第 3 段（历史）：模型假设下候选可复用前缀占 %.1f%%。" % (r3 * 100))
    print("  同样的「改一处」，候选可复用比例从 %.1f%% 到 %.1f%% —— 差了 %.1f 个百分点。" % (r1 * 100, r3 * 100, (r3 - r1) * 100))
    print()
    print("  因此，动态值若进入缓存覆盖区域，可能影响复用；实际 endpoint 请按其契约验证。")
```

## 常见坑

- **以为缓存「见过这段内容就命中」。** 缓存键和命中方式由 provider/endpoint 定义；先核对其契约与 usage。
- **在缓存覆盖区域开头拼时间戳或随机 id。** 对采用累计前缀键的接口，这可能降低后续前缀复用；按目标 API 验证影响范围。
- **工具定义顺序不稳定。** 若工具定义参与目标接口缓存键，序列化顺序变化可能影响复用；按其请求序列化规则检查。
- **把动态内容放进缓存覆盖区域。** 用户画像、权限列表每轮可能变化；核对其在目标接口缓存键中的位置与影响。
- **只看一个 usage 字段判断成本。** 先核对 provider 对 total input、cache read/write 和计费的定义；Anthropic、OpenAI、DeepSeek 的字段口径不同。
- **给工具结果缓存设错过期时间或跨租户复用。** freshness 之外，每次读取仍要验证租户/对象授权；缓存键不能代替访问控制。
