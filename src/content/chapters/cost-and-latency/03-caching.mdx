第 1 节说「不变的内容是好的复用候选」，而工具定义和系统提示通常较稳定。这一节讲缓存的实际行为；具体缓存键、复用边界、自动缓存与计价均由 provider、模型和 endpoint 定义。

## 第 1 章的实测

第 1 章记录了 `deepseek-flash` 的 Anthropic 兼容端点在 2026-09-24 的一组对照。它观察到两件事：

```text
命中缓存：未缓存输入从 2688 降到 256，耗时快 3.4 倍
改一个词：该次请求未报告缓存读取
```

这只是该 endpoint 当时的一次观测，不能据此断言缓存键或失效规则适用于其他 provider、endpoint 或缓存层。缓存能否复用以及如何匹配，取决于具体接口的缓存契约。

## 前缀与缓存键：先看具体接口契约

支持前缀缓存的接口可能按缓存断点或其他 provider 定义的键复用输入。以下「前缀」示意适用于有前缀缓存语义的接口；具体纳入缓存的字段、序列化方式、缓存键和断点规则，应以目标 provider 与 endpoint 文档为准。Anthropic 的 `tools → system → messages` 顺序和显式断点规则是该 API 的契约，不是所有兼容端点的通用协议。

在按累计前缀匹配的契约下，较早位置发生变化可能使对应断点的前缀键不再匹配；具体哪些缓存段仍可复用、是否回退到较早断点，由接口规则决定。

```text
[按目标 API 定义的缓存输入顺序]
     ↑ 改这里       → 对应断点/键可能不再匹配
                    ↑ 改这里   → 影响范围依断点与 API 规则而定
```

因此，对于按前缀复用且已确认其键/断点规则的接口，可以把稳定内容放在易变内容之前，减少动态字段改变可复用前缀的机会。不要在未核实缓存契约时，把这个顺序直接当作 provider 无关的保证。

当目标 endpoint 按前缀缓存且文档确认以下序列化/匹配关系时，这类顺序建议在 agent 里尤其有用：

```text
❌ 把用户上传的文档放在系统提示之前
❌ 把当前时间戳拼在系统提示的最前面
❌ 把工具定义放在历史消息之后
✅ 系统提示 → 工具定义 → 历史 → 本轮输入（本轮输入里，稳定的在前）
```

第二行是个常见的风险：**在缓存键覆盖的稳定区域开头拼一个时间戳**。在按前缀匹配的契约下，这可能导致较长的缓存前缀无法复用；实际命中范围须结合目标接口的键、断点和查找规则确认。

## 怎么把缓存打开：请求体里的断点

前面讲了前缀复用的思路，但显式缓存断点只适用于支持该功能和语法的接口。下面的 `cache_control` 请求形态用于演示兼容接口上的配置；具体字段、缓存键和行为必须查目标 endpoint 文档：

```json
{
  "model": "deepseek-flash",
  "max_tokens": 64,
  "system": [
    {"type": "text",
     "text": "<长且逐字固定的系统提示 + 参考资料>",
     "cache_control": {"type": "ephemeral"}},
    {"type": "text", "text": "<易变内容，比如当前时间>"}
  ],
  "messages": [{"role": "user", "content": "用一句话概括上面资料的主题。"}]
}
```

三个要点：

1. **断点位置由接口契约定义。** Anthropic API 的断点与 `tools → system → messages` 层级按该 API 文档解释；不能假定兼容 endpoint 暴露相同字段就必然实现完全相同的缓存键或边界。
2. **断点之后是否影响命中取决于该接口。** 本项目 2026-10-12 在 `deepseek-flash` 兼容 endpoint 的一次测试中，修改所标断点之后的动态段仍观测到 cache read；这是该次 endpoint 观测，不构成所有缓存实现的保证。
3. **门槛、断点数量、TTL、自动缓存与计价均由 provider/model/endpoint 定义。** 本项目同一 endpoint 在该次测试中约 2.4k token 前缀报告缓存读取，约 110 token 的短前缀两次均未报告读取；这不是可推广的门槛结论。

### 打开前后的 usage 对照（本次实跑）

条件：固定前缀约 8250 字符（约 2.4k token），断点打在第一个 system 块上；请求体就是上面那段。实跑数据 2026-10-12，`deepseek-flash`。

```text
组别                           input_tokens   cache_read   cache_creation   说明
1 冷启动（带断点）                    4693            0              0   本次未报告缓存读取
2 完全相同（带断点）                   213         4480              0   本次读取 4480 cache tokens
3 只改断点之后的部分                   213         4480              0   本次仍读取 4480 cache tokens
4-a 无断点第一次                     4537            0              0   本次未报告缓存读取
4-b 无断点第二次                      185         4352              0   本次读取 4352 cache tokens
5-a 短前缀第一次                      221            0              0   约 110 token 的前缀
5-b 短前缀第二次                      221            0              0   本次未报告缓存读取
另：预热后改前缀里的一个空格         4837            0              0   本次请求未报告缓存读取
```

**这次冷启动 → 全部命中的观测：未缓存输入从 4693 降到 213**（其中 4480 变成 `cache_read`）。第 3 组仅表明，在这次 endpoint、请求和断点配置下，修改该动态段后仍报告了缓存读取；它不证明其他接口上「断点之后随便变」都能命中。

两个必须如实说明的观测：

- **第 4 组：这个端点上不打断点也报告了缓存读取。** 这与该次请求存在自动缓存行为相符，但单次对照不能确定其完整缓存策略。不能推断 `cache_control` 对其他模型/endpoint 都非必要；也不能仅凭添加它就假设能控制缓存边界。
- **`cache_creation_input_tokens` 在这个端点上始终是 0。** 冷启动的那次全部计入 `input_tokens`（4693），并不单独报「写入量」。所以「三项之和」的口径在这里等于「全量输入」，但**换一个端点读数可能不同** —— 做成本对比时永远用三项之和，别假设某个字段一定是 0。

**失败形态：** 在支持显式断点的接口上，断点位置或输入稳定性与预期不符，可能导致缓存读取低于预期；表现和诊断方式由接口定义。检查时先核对目标 endpoint 的缓存开关、输入字段、断点/缓存键规则、TTL 与 usage，再用重复请求验证。不要只凭「断点后还有动态内容」就认定配置错误，也不要把未命中单独归因于长度或前缀变化。


## 在 agent 循环里，缓存为什么更重要

普通 API 调用是一次性的，缓存收益有限。而 agent 是多轮的，**每一轮都要重发全部历史**（第 1 节）。

这意味着：每轮请求仍包含当时需要的上下文；前缀缓存命中时，服务端可以复用已有前缀计算，usage 中缓存读取量仍按 provider 规则计费。命中与否会改变计算与计价类别，不会把历史 token 从请求和 usage 中删除。

按第 1 节的简化模型，未缓存的累计输入为 `57N + 8N(N-1)`：每轮仍会发送完整上下文。前缀缓存可以复用服务端已计算的前缀状态，降低重复 prefill 工作；它**不会让平方级的上下文 token 量或请求内容消失**。被缓存读取的 token 仍会计入 usage，并通常按 provider 专属的 cache-read 单价计费；创建/写入缓存也可能有独立价格或门槛。具体省多少要按厂商、模型和缓存命中 usage 逐项算。

**缓存的价值在多轮 agent 中可能更明显，因为固定前缀会反复出现；收益来自复用计算和 provider 对缓存 token 的差异化计价，而不是免除这些 token。**

## 缓存的三个排查方向

**方向一：时间戳、随机 id、请求 id 拼进缓存覆盖的输入。** 在按前缀匹配的接口上，这可能降低后续前缀的复用。先按目标 API 的契约确认哪些字段参与缓存，再考虑把动态信息放到不影响目标复用段的位置。

**方向二：工具定义的顺序不稳定。** 若目标 API 将工具定义纳入缓存键，序列化顺序变化可能导致该部分无法复用。需要按接口的序列化与键规则验证；若适用，固定工具顺序有助于保持请求稳定。

**方向三：系统提示里塞了动态内容。** 比如把用户画像、权限列表拼进系统提示。这些内容每轮都可能变；如果目标接口的缓存规则将它们纳入稳定前缀，复用可能受影响。

三个陷阱的共同点是：它们可能改变目标接口参与缓存匹配的请求表示。语义相同不保证缓存键相同；应根据接口文档和 usage 观测，而不是假定存在统一的「差别是 100%」规则。

## 复用：不能缓存的那部分

缓存解决的是「同样的输入重复发送」。还有一类复用是「同样的结果不用重算」：

- **工具结果缓存**：查同一个订单两次，第二次直接用上次的结果（要注意时效性）
- **检索结果缓存**：第 6 章的检索，同样的查询加同样的语料可以直接返回
- **确定性计算的缓存**：任何由代码算出来的中间结果

这类缓存的判据和上面不同：它要求**输入相同且结果未过期**。过期策略取决于数据的变化频率 —— 订单状态可能几分钟就变，而文档内容可能几周不变。

## 一个反过来的代价

缓存不是免费的，代价有三条：

**一、实现复杂度。** 什么时候失效、怎么验证生效，都是要维护的逻辑。

**二、可能读到旧结果。** 工具结果缓存如果过期策略设错，用户会看到过时数据。

**三、测量变难。** 第 4 节那个陷阱：`input_tokens` 只算未命中部分，如果不加上 cache_read，你会以为成本突然降了。

第三条是本节和前面章节的连接点：**缓存让成本数据变得难以直接比较。** 任何时候看到「成本突然降了一半」，先问一句是不是缓存生效了。


## 一个简化模型：改动位置可能影响多少复用

在累计前缀匹配的简化模型里，较早位置的变化会影响更长的候选前缀。下面按一份示例上下文计算四种改动位置；这是模型演算，不是任何 provider 的实测命中率或通用缓存契约：

```text
改在哪一段                命中率    命中 token   失效 token
第 1 段：系统提示           0.0%           0        4,080
第 2 段：工具定义           9.8%         400        3,680
第 3 段：历史消息          21.6%         880        3,200
第 4 段：本轮输入          95.1%       3,880          200
```

（本地模拟，2026-10-09。分段：系统提示 400、工具定义 480、历史消息 3000、本轮输入 200。）

在这个简化模型中，同样是「改一处」，候选可复用比例从 0.0% 到 95.1%。

这份**简化累计前缀模型**中，最前一段变化会令模型假设的可复用前缀归零。真实 endpoint 是否如此，取决于它的缓存键和断点规则；时间戳的例子只是说明为什么要检查动态字段是否进入目标接口的缓存覆盖区域。

如果确实需要时间信息，可以评估是否放入不影响目标接口可复用范围的请求部分，或在需要时通过工具查询；具体放置位置要根据该接口的缓存规则与任务要求决定。

## 什么时候缓存会让成本数据变得无法解释

第 3 节提过一个测量问题，值得展开，因为它是实际操作中最容易误判的地方。

缓存生效时，input_tokens 只统计**未命中**的部分。所以同一份上下文、同样的调用，会因为缓存状态不同而报出完全不同的数字：

```text
冷启动（全部未命中）：input_tokens = 4080, cache_read = 0
     第二次（全部命中）：input_tokens = 0,    cache_read = 4080
```

如果只读第一个字段，你会以为第二次「免费」；如果只读第二个字段，你会以为第一次「没用缓存」。**两者都是错的** —— 实际计费口径要看厂商，但成本比较必须用三项之和：

```text
总输入 = input_tokens + cache_read_input_tokens + cache_creation_input_tokens
```

这个陷阱在本项目里**实际发生过一次**（第 4 节记录的）：当时测「工具定义成本」，数据出现「1 个工具 306 token、3 个工具 174 token」的矛盾结果，看起来像「工具越多越便宜」。真相是缓存命中状态不同，而我只读了 input_tokens。

**教训是通用的：任何「成本异常下降」都要先排除缓存，再下结论。**

## 一个反过来的用法：缓存命中率是一个指标

除了省钱，缓存命中率本身就是一个值得监控的运行指标。它的变化能告诉你一些别处看不到的事：

- **命中率突然下降** → 可调查模板、动态字段、缓存配置或 endpoint 行为是否变化
- **命中率长期为 0** → 核对目标接口是否支持/启用缓存、请求是否满足条件及 usage 口径
- **某个工具上线后命中率下降** → 检查工具定义/序列化以及目标 endpoint 的缓存键规则

这些变化可能不触发错误，却会影响复用与账单；命中率是可调查的信号之一，需要结合接口契约和 usage 解读。

## 一个反过来的检查：缓存是不是在帮倒忙

缓存也会做错事，有两种形态值得知道。

**形态一：缓存让问题变得更隐蔽。** 一份上下文被缓存了，但它里面含有一个**已经过期的事实**（比如某个订单的状态）。缓存让「同样的输入」得到「同样的输出」—— 而那个输出基于的是一小时前的数据。这类问题不会报错，只会让用户看到旧结果。

所以缓存之前要先分清：**这段内容是"不变的事实"还是"某个时刻的快照"？** 系统提示和工具定义属于前者，而工具返回值属于后者 —— 后者缓存要带过期时间（本节前面那个「复用」部分讲的就是这种情况）。

**形态二：缓存让成本下降但延迟不变。** 缓存省的是 prefill 的成本，而第 2 节实测过：在小输入量级下，prefill 本来就被固定开销盖住了。所以**缓存省钱，但不一定省时间**。

这两件事要分开看：**省钱看 token，省时间看 decode。** 而很多"性能优化"的讨论把两者混在一起，于是得不出能落地的结论。
## 完整可运行代码

下面这段代码模拟一种**简化累计前缀缓存模型**：假设改变某段后，只有它之前的前缀可复用。它用于解释该模型下改动位置的影响，不模拟任何 provider 的缓存键、断点回退或自动缓存行为。

```python
"""简化前缀缓存演示：改动位置影响模型假定的可复用范围。纯本地。实跑状态：2026-10-09。"""
SEGMENTS = [("系统提示", 400), ("工具定义", 480), ("历史消息", 3000), ("本轮输入", 200)]


def hit_ratio(changed_index):
    """简化模型：第 changed_index 段变化，返回此前前缀占比。"""
    total = sum(n for _, n in SEGMENTS)
    prefix = sum(n for _, n in SEGMENTS[:changed_index])
    # 仅按本演示的模型计算：变化段之前的 token 可复用
    return prefix / total, prefix, total


if __name__ == "__main__":
    print("上下文分段：")
    for i, (name, n) in enumerate(SEGMENTS):
        print("  第 %d 段 %-10s %5d token" % (i + 1, name, n))
    print()
    print("  %-34s %8s %10s %9s" % ("改在哪一段", "命中率", "命中 token", "失效 token"))
    for i, (name, n) in enumerate(SEGMENTS):
        ratio, hit, total = hit_ratio(i)
        print("  %-34s %7.1f%% %10d %9d" % ("第 %d 段：" % (i + 1) + name, ratio * 100, hit, total - hit))
    print()
    print("=== 关键点 ===")
    r1 = hit_ratio(0)[0]
    r3 = hit_ratio(2)[0]
    print("  改第 1 段（系统提示）：简化模型中此前前缀为 %.1f%%。" % (r1 * 100))
    print("  改第 3 段（历史）：   仍有 %.1f%% 命中。" % (r3 * 100))
    print("  同样的「改一处」，命中率从 %.1f%% 到 %.1f%% —— 差了 %.1f 个百分点。" % (r1 * 100, r3 * 100, (r3 - r1) * 100))
    print()
    print("  因此，动态值若进入缓存覆盖区域，可能影响复用；实际 endpoint 请按其契约验证。")
```

## 常见坑

- **以为缓存「见过这段内容就命中」。** 缓存键和命中方式由 provider/endpoint 定义；先核对其契约与 usage。
- **在缓存覆盖区域开头拼时间戳或随机 id。** 对采用累计前缀键的接口，这可能降低后续前缀复用；按目标 API 验证影响范围。
- **工具定义顺序不稳定。** 若工具定义参与目标接口缓存键，序列化顺序变化可能影响复用；按其请求序列化规则检查。
- **把动态内容放进缓存覆盖区域。** 用户画像、权限列表每轮可能变化；核对其在目标接口缓存键中的位置与影响。
- **只看 `input_tokens` 判断成本。** 必须加 cache_read 和 cache_creation，否则会误判。
- **给工具结果缓存设错过期时间。** 订单状态几分钟就变，文档几周不变 —— 过期策略要按数据定。
