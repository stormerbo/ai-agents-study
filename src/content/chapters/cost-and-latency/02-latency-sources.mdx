用户感受到的延迟和账单上的 token 是两件事。这一节把一次调用拆开，看延迟到底花在哪。

## 两个阶段

一次 LLM 调用在延迟上分两段：

- **首 token 时间（TTFT，time to first token）**：TTFT 指的是从发出请求到第一个字到达的那段等待；这一段主要是 **prefill**（预填充：模型把整段输入一次性读进去、算出每个位置的内部表示）。
- **生成时间（decode）**：从第一个字到最后一个字。这一段是**逐 token 生成**，每个 token 都要等上一次的**前向计算**（把当前全部输入送进网络、算出下一个字概率的那一次完整计算）。

这里说的**注意力状态**，粗略理解就是模型读完输入后留下的「笔记」：生成每个字时，它都会按相关性去翻这份笔记。prefill 就是**做笔记**的过程，decode 才是**照着笔记写字**。

两段的性质完全不同：prefill 可以并行（输入的所有 token 一起处理），decode 只能串行（第 N 个 token 依赖前 N-1 个）。**这个差别决定了它们对输入/输出长度的敏感度完全不同。**

## 实测

我用流式接口记下第一个 token 到达的时刻和结束时刻，跑了四种组合：

```text
场景              输入    输出    首token   生成     总计
短输入 + 短输出      36     80     0.64s   0.59s   1.24s
短输入 + 长输出      42    710     1.22s   3.80s   5.01s
长输入 + 短输出    1238     80     0.88s   0.36s   1.23s
长输入 + 长输出    1245   1200     0.68s   6.78s   7.46s
```

（实跑数据，2026-10-09，`deepseek-flash`。长输入用约 2400 字的背景资料填充。）

## 两个结论 —— 第二个和直觉相反

**结论一：生成时间完全由输出长度决定。**

把输出长度除以生成时间，得到四组的速率：

```text
80   / 0.59s = 136 token/秒
710  / 3.80s = 187 token/秒
80   / 0.36s = 222 token/秒
1200 / 6.78s = 177 token/秒
```

**大约 180 token/秒，基本上是个常数。** 注意它和输入长度几乎无关 —— 1238 token 输入那组（222）甚至比 36 token 输入那组（136）还快，那只是噪声。

这条结论很有用：**如果你能估出输出长度，你就能估出生成时间。**

```text
生成时间 ≈ 输出 token 数 / 180   （本模型实测，换模型要重测）
```

**结论二：首 token 时间对输入长度不敏感。**

这一条和我预期的不一样。输入从 **36 涨到 1238（34 倍）**，首 token 时间只从 **0.64s 涨到 0.88s** —— 而且**不单调**：长输入 + 长输出那组（1245 token 输入）是 **0.68s**，比短输入 + 长输出那组（42 token 输入）的 **1.22s** 还低。

**四组的首 token 时间落在 0.64 到 1.22 秒之间，看不出和输入长度的关系。**

合理的解释是：在这个规模上，**首 token 时间被一个固定的网络与启动开销主导**（大约 0.6 到 0.9 秒），而 1238 token 的 prefill 成本还没有大到能在这个固定开销之上显现出来。那些波动更像是网络抖动，不是输入长度的影响。

## 这两个结论意味着什么

它们推翻了一条很常见的建议：**"压缩 prompt 能降延迟"。**

在这个规模上，**它几乎不降。** 你把 1238 token 压到 600，省下的是几百 token 的 prefill —— 而按上面的数据，那点 prefill 本来就被固定开销盖住了。

而**缩短输出能降得很明显**：1200 token 输出要 6.78 秒，压到 300 token 大约 1.7 秒。**降了 5 秒，而压缩输入降不到 0.2 秒。**

所以优化的优先级是：

| 想降延迟 | 做什么 | 预期效果 |
|---|---|---|
| **先看输出** | 让它少说、结构化输出、限制 `max_tokens` | 每减 180 token 省 1 秒 |
| 再看固定开销 | 流式输出（首字更快到）、连接复用 | 改善"感知延迟" |
| 最后才看输入 | 压缩上下文、加缓存 | 小输入量级下几乎无感 |

**注意第二行的"感知延迟"。** 流式输出不减少总时间，但它把首字提前到 0.6 秒 —— 而用户对"已经开始出来了"和"转圈 5 秒"的体感差别很大。这一条在第 19 章讲人机协作时还会用到。

## 一个边界：什么时候输入会主导

上面那条结论有边界，必须说清楚，否则它会被误用。

**prefill 的成本是随输入长度增长的，只是在本节这个规模下被固定开销掩盖了。** 当输入到几万、十几万 token 时，它会成为主导项 —— 第 7 章那组实验里上下文填到 104 万 token，那种规模下 prefill 显然是主要成本。

所以更准确的表述是：

```text
输入 ≤ 几千 token   → 首 token 由固定开销主导，压缩输入收益很小
输入 几万 token 以上  → prefill 成为主导，压缩输入收益显著
```

**而 agent 场景通常落在哪一边？** 第 11 章实测过每轮输入几百到几千 token，第 3 章那组到 22.8k。所以**长会话的后期**会逐渐滑向"输入主导"那一侧 —— 这也是为什么缓存（第 3 节）在长会话里价值很高。

## 怎么用这两个数字

两个可以直接用的估算式：

```text
生成时间 ≈ 输出 token 数 / 180
总延迟 ≈ 0.8s（固定开销）+ 输出 token 数 / 180
```

第二个式子可以用来**设置用户预期**：一个要输出 500 token 的回答大约 3.6 秒；1200 token 大约 7.5 秒。如果 UI 上没有任何提示，用户会以为卡住了 —— 而这不是性能问题，是交互问题（第 19 章）。

它也可以用来**判断"慢"的归因**：如果一个请求花了 12 秒，那么按这个式子，它大概输出了一两千 token。去查那次的输出长度，比去查输入更可能有收获。


## 为什么 prefill 可以并行而 decode 不能

上面两个结论的根源是两种计算的并行性不同，值得讲清楚 —— 因为它决定了这两条结论会不会随规模变化。

**prefill 阶段**：输入的 N 个 token 一起进入模型，计算注意力时它们可以**互相看到**，所以整段可以并行处理。硬件吃得满，吞吐高。这意味着**单位 token 的 prefill 成本很低** —— 低到在本节的规模上被网络开销盖住。

**decode 阶段**：第 k 个 token 的计算依赖前 k-1 个的结果（自回归），所以**只能串行**。每生成一个 token 要走一次完整的前向计算，而 GPU 在这一次计算里远没有吃满（batch size 为 1 时算力利用率很低）。这就是为什么 decode 的速率是一个固定的常数（约 180 token/秒），以及为什么它成为总延迟的主导项。

这个差别还解释了一个现象：**为什么流式输出对体感帮助很大。** 因为 decode 是逐步产出，所以你可以把第一个 token 立刻推给用户，而不是等全部生成完。总时间没变，但用户从 0.8 秒就开始看到内容了。

它同时也解释了另一个现象：**为什么「换个更强的模型」不一定更慢。** 强模型的 decode 速率可能更低（每 token 更慢），但它可能用更少的 token 说完同样的事（更简洁）。两者相乘才是总时间 —— 这也是第 4 节要对比的。
## 完整可运行代码

下面这段代码用流式接口把延迟拆成两段，并跑上面那四种组合。

```python
"""延迟被什么主导 —— 把一次流式调用拆开测。

两个问题：
  1. 首 token 时间（TTFT，主要是 prefill）和生成时间（decode）各占多少？
  2. 输入变长影响谁？输出变长影响谁？

做法：用流式接口记下第一个 token 到达的时刻，以及结束时刻。
实跑状态：2026-10-09，deepseek-flash。
"""
import os
import json, os, time, urllib.request


def stream_call(prompt, max_tokens, label):
    body = json.dumps({"model": os.environ["VERIFY_MODEL"], "max_tokens": max_tokens,
                       "stream": True,
                       "messages": [{"role": "user", "content": prompt}]}).encode()
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages", data=body,
        headers={"content-type": "application/json",
                 "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
                 "anthropic-version": "2023-06-01"})
    t0 = time.time()
    ttft = None
    out_tokens = 0
    in_tokens = 0
    with urllib.request.urlopen(req, timeout=300) as resp:
        for raw in resp:
            line = raw.decode("utf-8", "ignore").strip()
            if not line.startswith("data:"):
                continue
            payload = line[5:].strip()
            if payload == "[DONE]":
                break
            try:
                ev = json.loads(payload)
            except Exception:
                continue
            t = ev.get("type")
            if t == "message_start":
                u = ev.get("message", {}).get("usage", {})
                in_tokens = (u.get("input_tokens", 0) + u.get("cache_read_input_tokens", 0)
                             + u.get("cache_creation_input_tokens", 0))
            elif t == "content_block_delta":
                if ttft is None:
                    ttft = time.time() - t0
            elif t == "message_delta":
                out_tokens = ev.get("usage", {}).get("output_tokens", 0)
    total = time.time() - t0
    return {"label": label, "in": in_tokens, "out": out_tokens,
            "ttft": ttft or 0, "total": total, "decode": total - (ttft or 0)}


FILLER = "以下是背景资料，仅供参考。" * 200   # 约 2400 字

CASES = [
    ("短输入 + 短输出", "用一句话说明什么是缓存。", 80),
    ("短输入 + 长输出", "详细解释什么是缓存，写 500 字左右。", 1200),
    ("长输入 + 短输出", FILLER + "\n\n请用一句话概括上面资料的主题。", 80),
    ("长输入 + 长输出", FILLER + "\n\n请详细复述上面资料的内容，写 500 字左右。", 1200),
]

if __name__ == "__main__":
    rows = []
    for label, prompt, mt in CASES:
        r = stream_call(prompt, mt, label)
        rows.append(r)
        print("  %-16s 输入 %-6d 输出 %-5d 首token %5.2fs  生成 %5.2fs  总计 %5.2fs"
              % (label, r["in"], r["out"], r["ttft"], r["decode"], r["total"]))
    print()
    print("=== 读法 ===")
    print("  对比第 1、2 行（输入相同、输出不同）：输出变长主要拉长**生成时间**。")
    print("  对比第 1、3 行（输出相同、输入不同）：输入变长主要拉长**首 token 时间**。")
    print()
    print("  这两个数字指导的优化方向完全不同：")
    print("    · 首 token 慢 → 压缩输入、加缓存（第 3 节）")
    print("    · 生成慢   → 缩短输出、换更快的模型（第 4 节）")
```

## 输出长度怎么估：把那个 180 用起来

L50 给了式子「生成时间 ≈ 输出 token 数 / 180」，但没说请求之前怎么拿到输出 token 数。方法是用**同一任务的历史调用**估：

1. 从第 1 节那套调用记录里，取出同一个 `step_kind` 的输出 token（`output_tokens` 字段）。
2. 算它的中位数（P50）—— 用中位数而不是平均，因为一次失控的长输出会把平均值拉飞。
3. 生成时间 ≈ P50 / 180；总延迟再加固定开销。

下面这段跑的正是本次实跑那 4 轮记录（2026-10-12）：

```python
# 用同一任务的历史输出长度估下一次的生成时间（历史来自本次实跑的 4 轮记录）
HISTORY_OUTPUT_TOKENS = [129, 57, 56, 22]   # 实跑数据 2026-10-12
DECODE_RATE = 180                            # 第 2 节实测：约 180 token/秒（换模型要重测）
FIXED_OVERHEAD = 0.8                         # 第 2 节实测：固定开销约 0.6-0.9s

def percentile(xs, p):
    xs = sorted(xs)
    if not xs: return 0
    k = max(0, min(len(xs) - 1, int(round((p / 100) * (len(xs) - 1)))))
    return xs[k]

if __name__ == "__main__":
    p50, p90 = percentile(HISTORY_OUTPUT_TOKENS, 50), percentile(HISTORY_OUTPUT_TOKENS, 90)
    for name, out in [("P50", p50), ("P90", p90)]:
        gen = out / DECODE_RATE
        print("  %s 输出 %3d token -> 生成 ≈ %.2fs，总延迟 ≈ %.2fs" % (name, out, gen, FIXED_OVERHEAD + gen))
    print()
    for out in (300, 500, 1200):
        print("  若输出 %4d token -> 生成 ≈ %4.1fs，总延迟 ≈ %4.1fs"
              % (out, out / DECODE_RATE, FIXED_OVERHEAD + out / DECODE_RATE))
```

实跑输出：

```text
  P50 输出  57 token -> 生成 ≈ 0.32s，总延迟 ≈ 1.12s
  P90 输出 129 token -> 生成 ≈ 0.72s，总延迟 ≈ 1.52s

  若输出  300 token -> 生成 ≈  1.7s，总延迟 ≈  2.5s
  若输出  500 token -> 生成 ≈  2.8s，总延迟 ≈  3.6s
  若输出 1200 token -> 生成 ≈  6.7s，总延迟 ≈  7.5s
```

**判据与边界：** 这个估法在「同类任务、同一模型」内有效 —— 换模型要重测 180，换任务类型要重取历史。它估不了第一次遇到的任务（没有历史），那种情况退回用 `max_tokens` 设一个上限、按上限估最坏情况。

## 判断输入是否进入主导区：一个两步测量

L89 那条边界（「几万 token 以上」）不是让你背的数字，而是可以用两次调用测出来的。做法：

**第一步：把输出固定住。** 两次请求用**完全相同**的输出要求（同一句「用一句话回答」，`max_tokens` 也相同），只有输入长度不同。

**第二步：输入加倍，看 TTFT 变不变。** 记录两次的 TTFT：

| 测量 | 输入 token | 输出要求 | TTFT | 判读 |
|---|---|---|---|---|
| A | 短（比如几千） | 同一句 | t1 | 基准 |
| B | 翻倍（同一内容重复两遍） | 同一句 | t2 | `t2 ≈ t1` → 输入还没进入主导区；`t2 ≫ t1` 且接近翻倍 → 已进入 |

**为什么这么判：** 小输入量级下 TTFT 由固定开销（网络 + 启动，约 0.6-0.9s）主导，输入翻倍只挪动被盖住的那一小部分，看似不变。等 prefill 成本超过固定开销，它就变成 TTFT 里的主要项，翻倍效应才会显现。**本项目实测过这个「看不出关系」的现象**：输入 36 → 1238（34 倍），TTFT 只从 0.64s 到 0.88s 且不单调 —— 也就是说，本节这个规模还在固定开销区内。

**失败形态：** 用「输入长 = 慢」做优化决策，却不做这次对照 —— 把预算花在压缩一个本来就被固定开销盖住的输入上。第二个失败形态是**只测一次**：TTFT 受网络抖动影响大（上面四组里 0.64-1.22s 的波动就是抖动），每组至少跑 3 次取中位数，再比较。

## 把估算式接到 UI 与超时阈值

「设置用户预期」落到代码上是两个数，都由上面的估算式推出来：

- **单轮超时阈值**：取该任务生成时间的 **P99 再加余量**（而不是拍一个整数）。低于它，你会把正常的长回答掐断；远高于它，一次卡死会白等很久。
- **进度提示**：显示「已生成 N 字 / 预计 M 秒」。M 用本节估算式算；N 用流式事件累加。做法上是把两个数都暴露给前端 —— 只给一个转圈动画等于没有预期管理。

**判据：** 超时阈值应该是**有依据的数**（来自历史 P99），不是「拍脑袋的 30 秒」。如果它和实际分布对不上，先改数据采集，别改阈值。

## 常见坑

- **以为压缩 prompt 能显著降延迟。** 实测：输入涨 34 倍，首 token 只涨 0.24 秒（且不单调）。
- **忽略固定开销。** 约 0.6 到 0.9 秒是网络与启动成本，短请求的总延迟一半在它身上。
- **想当然地按输入长度估总延迟。** 生成时间才是主导项，约 180 token/秒。
- **忘了流式输出的价值。** 它不减少总时间，但把首字提前 —— 体感差别很大。
- **把这组数字外推到别的模型。** 180 token/秒是本站这台模型的实测，换模型必须重测。
- **忽略边界。** 输入到几万 token 以上时，prefill 会成为主导项，那时的结论反过来。
