用户感受到的延迟和账单上的 token 是两件事。做 agent 时，还要把**模型服务时间**和**整项任务的端到端时间**分开：一次模型请求快，不代表多轮工具任务快；第一个事件很早到，也不代表用户已经看到有意义的进展。

本节的目标不是给所有模型背一个固定的 token/秒常数，而是建立可测量的延迟模型：定义起止点、记录每个阶段、画出任务关键路径，再用可重复的对照实验决定优化方向。

## 先把指标说清楚

| 指标 | 起止点 | 能回答什么 | 不能直接说明什么 |
|---|---|---|---|
| 请求延迟 | 客户端发出请求，到完整响应可用 | 这次 provider 请求花了多久 | 是排队、网络、prefill、decode 还是重试造成 |
| TTFT（time to first token） | 按服务端或客户端约定的请求开始，到第一个输出 token/事件 | 流式响应何时开始 | 第一个事件是否是用户可见文本；也不等于纯 prefill 时间 |
| 首个可见文本时间 | 用户动作到界面首次呈现有意义文本 | 用户何时看到文字反馈 | 任务何时完成；事件可能先是 thinking、工具调用或状态 |
| TPOT（time per output token） | 首 token 之后的输出阶段按 token 计时 | 输出阶段的平均节奏 | 任意模型/上下文下的稳定生成速率 |
| 任务端到端延迟 | 用户提交任务，到最终结果满足任务契约 | 用户真正等待多久 | 不能只用单次模型请求代替 |

不同供应商对 TTFT 的计时点、事件定义与 usage 字段可能不同。做横向比较前先统一计时口径；若供应商只暴露流事件，客户端测到的是“请求发送至某事件到达”的观测值，包含客户端、网络和服务端路径，不应标成纯 prefill 时长。Anthropic 流式事件里可能有文本、思考、工具输入等不同 block；把第一个 `content_block_delta` 当作首个可见文本，会把非文本事件误算成用户已看到回答。

## 一次模型请求里发生什么

自回归模型通常可以从计算阶段理解：prefill 处理输入上下文，decode 逐步产生输出 token；生成中的 KV cache 可复用此前 token 的 key/value 状态，避免每步从头重算全部历史。这个机制有助于解释输入与输出对服务时间的不同影响，但**客户端实际请求延迟还包括排队、网络、调度、批处理、限流、序列化和流式传输**。因此 TTFT 不等于 prefill，TPOT 也不是脱离硬件、模型、并发和上下文长度的常数。

把一次客户端请求记为：

```text
request_latency = client_setup + network_up + provider_queue + prefill
                + output_decode + network_stream + client_parse
```

这只是分解观测路径的账本，不是所有 API 都能直接分别测出每项。若服务端没有暴露排队或计算阶段的 trace，就把未知部分保留为未知，不能从总时间反推一个“固定网络开销”。

## 一组历史数据：保留观察，不越界推断

下表保留 2026-10-09 的四条历史摘要。它记录了当时 DeepSeek 兼容端点的输入/输出 token、首事件和剩余用时，但原始逐次请求与响应、request ID、精确模型快照、endpoint 配置、逐事件时间戳、重复样本及判分脚本没有归档。**这组数据无法独立复现**，并且每种条件只有一个样本，输出上限、提示内容、调用顺序和服务端负载也未充分控制。

```text
历史摘要（单次/条件；单位秒；不是当前服务基准）
场景              输入    输出    记录首事件    记录“生成”    记录总计
短输入 + 短输出      36      80       0.64          0.59         1.24
短输入 + 长输出      42     710       1.22          3.80         5.01
长输入 + 短输出    1238      80       0.88          0.36         1.23
长输入 + 长输出    1245    1200       0.68          6.78         7.46
```

“生成”列按旧摘要原样保留；因逐次时间戳与原始 trace 缺失，无法核对它是否等于总计减首事件。表格只保留两位小数，首事件 + 记录生成与记录总计之间还出现 0.01 秒差异，可能涉及独立舍入或原记录口径，现有证据无法裁定。若只对展示值做相减，得到的是**展示值残差**，不能冒充原“生成”列，更不能确认是纯 decode；如果第一事件是 thinking 或工具输入，它也不等于从首个可见文本开始的时间。输入 token 只从 36 到 1245 的这四个点，首事件时间不单调；这既不能证明输入无影响，也不能证明变化来自网络开销。输出长度与记录生成时间在这组摘要里同向变化，**不能推断**普遍固定的 180 token/秒，也不能据此承诺“每少 180 token 就省 1 秒”。

下面这段可运行脚本只重算已保留摘要的差值和范围；它不发 API 请求、不读取密钥，也不伪装成历史实验复现。它让读者能检查我们从记录中实际知道什么，以及哪些信息缺失。

实跑状态：本节两段 Python 代码均已在本地 Python 3 下执行。它们只覆盖离线算术与事件分类示意，不包含 provider 调用或线上测量。

```python
"""对已归档的四行延迟摘要做纯离线算术，不访问 provider。"""
from statistics import median

historical_summary = [
    {"label": "短输入短输出", "input": 36, "output": 80, "first_event": 0.64, "recorded_generation": 0.59, "total": 1.24},
    {"label": "短输入长输出", "input": 42, "output": 710, "first_event": 1.22, "recorded_generation": 3.80, "total": 5.01},
    {"label": "长输入短输出", "input": 1238, "output": 80, "first_event": 0.88, "recorded_generation": 0.36, "total": 1.23},
    {"label": "长输入长输出", "input": 1245, "output": 1200, "first_event": 0.68, "recorded_generation": 6.78, "total": 7.46},
]

displayed_residual = [row["total"] - row["first_event"] for row in historical_summary]
print("n=", len(historical_summary), "；这是历史摘要的复算，不是重新测量")
print("首事件时间范围：%.2f–%.2fs" % (
    min(row["first_event"] for row in historical_summary),
    max(row["first_event"] for row in historical_summary),
))
print("展示值相减所得残差中位数：%.2fs；范围：%.2f–%.2fs" % (
    median(displayed_residual), min(displayed_residual), max(displayed_residual)
))
print("残差不等于已核实的‘生成’字段；小样本也不能估计稳定 token/s 或 SLA。")
for row, residual in zip(historical_summary, displayed_residual):
    print("%s: 记录生成=%.2fs；记录总计-首事件=%.2fs" % (
        row["label"], row["recorded_generation"], residual
    ))
```

## agent 的延迟是关键路径，不是请求数乘常数

一个 agent 任务可能先调用模型，再查询两个互不依赖的服务，随后把结果交给模型整合。每一阶段包含自身排队、网络、工具耗时、执行、解析、重试与调度时间。**串行阶段求和**；真正并行且没有额外依赖的**并行分支取最长**，并还要计入并发启动/汇合开销。任何串行依赖、限流等待、重试或人工审批都会延长关键路径。

```text
提交任务
   │
   ▼
模型规划 ──► 工具 A ──┐
   │                  ├─► 模型整合 ─► 校验 ─► 最终结果
   └──────► 工具 B ───┘

总时长 ≈ 规划 + max(A 分支, B 分支) + 整合 + 校验
```

并行仅在语义上独立且资源允许时成立：两个工具若共享限流额度、数据库锁、同一外部副作用或有先后依赖，就不能简单按 `max(A, B)` 估算。一个可操作的 trace 至少记录 `task_id`、`run_id`、`step_id`、父子关系、阶段名称、开始/结束时间、队列等待、尝试次数、结果状态、模型/endpoint、输入输出 usage；敏感 prompt 与工具结果按最小必要原则脱敏。记录单调时钟的 duration，避免系统时钟校准导致负耗时。

后端工程的一个常见误区，是只看模型请求平均耗时。任务由多轮串行调用组成时，单次尾延迟会累计；若有并发分支，整体由关键路径和共享资源决定。失败重试也有双重效果：提高成功机会，却会增加失败任务的尾延迟和成本。因此同时看任务 P50/P95、首个可见文本、成功率、重试次数和任务完成率，并按任务类型分组；只报平均值会掩盖尾部等待。

一个具体的归因顺序是：先从用户提交到任务结束算出 wall-clock duration；再按 `run_id` 找到所有模型与工具 span；依赖关系明确后标出最长路径；最后比较慢 span 的自身耗时和等待耗时。若关键路径是“模型请求 → 工具 → 模型请求”，模型调用减少一轮可能直接缩短串行路径；若两项工具已并行但都在等同一个下游限流，继续提高并发只会加剧排队。若 UI 很快显示状态而任务总时间仍长，改善的是反馈，不是吞吐或完成时间；这两类优化要分开验收。

生产观测要把 trace 传播到 provider adapter 和工具客户端。为每次尝试分配独立 span，同时保留稳定的逻辑步骤 ID，才能区分“一步重试两次”和“任务设计上有三步”。时间戳使用同一进程的 monotonic clock 计算 duration；跨机器只比较带时钟同步假设的绝对时间，不能把各机绝对时间直接相减当成精确的网络耗时。日志与指标应通过 trace ID 关联，但不能把完整 prompt、工具返回值、用户数据或密钥当作方便的标签写入高基数指标。

预算也应落到任务级 deadline。开始新模型请求或工具调用前先检查剩余时间；请求超时不代表 provider 一定没处理，是否重试要结合幂等与取消语义。把每一步的 timeout 设成固定长值，可能导致前序步骤耗尽了总 deadline 后，后续步骤还继续等待；把总 deadline 传播到子调用，才能让系统及时停止无价值工作。deadline 保护的是用户等待上限，不能代替成本上限、调用次数预算或副作用恢复机制。

## 从流事件测“首个可见文本”

测量边界应与产品问题一致。下面的示意代码判断 Anthropic Messages 流中第一个文本增量；thinking、工具输入和其他 delta 不会被误当成文本。若 UI 还要经过缓冲、Markdown 渲染或审核，真实首屏时间应在浏览器呈现层另打时间戳。该片段只演示事件分类，不含网络读取、重试或供应商通用适配器；字段形状以链接的官方流式文档为准。

```python
# event 是已由 SSE 解码器解析成 dict 的 Anthropic Messages 事件。
def is_first_visible_text(event, first_visible_text_seen):
    if event.get("type") != "content_block_delta":
        return False
    delta = event.get("delta", {})
    is_text_delta = delta.get("type") == "text_delta"
    if not is_text_delta:
        return False
    if not delta.get("text", "") or first_visible_text_seen:
        return False
    return True

examples = [
    {"type": "content_block_delta", "delta": {"type": "thinking_delta", "thinking": "先分析"}},
    {"type": "content_block_delta", "delta": {"type": "input_json_delta", "partial_json": "{}"}},
    {"type": "content_block_delta", "delta": {"type": "text_delta", "text": "结果"}},
]
first_visible = None
for index, event in enumerate(examples):
    if is_first_visible_text(event, first_visible is not None):
        first_visible = index
print("首个可见文本事件序号：", first_visible)
```

**构造的解析错误案例（不是一次真实线上事故）**：旧式解析器把第一个 `content_block_delta` 记成 TTFT。若 stream 先发 `thinking_delta`，服务端日志会显示“0.3 秒已出首 token”，但用户界面还没有文字；若接着是 `input_json_delta`，则把工具参数当成回答首字。对照官方事件类型和 UI 呈现时间后，应分别记录 provider 首事件、首个 `text_delta` 与浏览器首屏，避免把测量口径错误当成性能改善。

## 如何做能支持决策的对照

若要判断输入长度是否影响延迟，不能拿两个不同提示各请求一次就下结论。准备语义一致、只改变填充上下文长度的输入组；固定模型快照、endpoint、输出约束、区域、缓存条件与客户端；明确排除或记录排队、重试、限流和错误。短/长输入交错执行，避免总是先跑短输入；同一配置重复足够多次，保存逐次原始时间戳、usage、请求 ID 和响应状态，再报告分布与置信范围。输出长度也要用任务设计与输出上限控制，而不是只看请求参数 `max_tokens`（它是上限，不保证实际输出长度）。

至少区分以下时间：请求提交、首个 provider 事件、首个可见文本、每个文本增量、工具开始/结束、最终响应、浏览器呈现。若服务商提供 server-side timing header 或 request ID，连同原始值保存；若没有，就标注服务端阶段不可观测。对于输入长度对照，可报告每档 TTFT 的中位数与高分位数、差值分布和失败/超时比例；对输出阶段可按实际输出 token 计算 TPOT 分布。样本规模应根据业务所需精度、波动和尾延迟目标预先确定，而不是把四个点当作性能基准。

## 从观测到优化

先画 trace 找出任务关键路径，再按证据做优化。输出特别长时，收紧任务范围、限制无用重复或要求紧凑格式，通常值得测；输入特别长时，裁剪无关上下文、检索必要片段或使用服务商支持的前缀缓存可能值得测。不要为了降低模型时间删掉完成任务所需证据，也不要把缓存复用自动等同于更低端到端延迟：缓存规则、命中率、计价和后续 decode 行为都需要单独核实。

若模型步骤可以减少，先确认是否会降低质量、审计能力或安全控制；若工具调用互相独立，可评估并行，但检查外部依赖的限流和副作用。流式输出通常能改善用户更早看到进展的体验，**并不保证缩短最终任务时间**。如果长任务中间没有可展示的文本，也可以呈现有根据的状态事件（例如“正在查询订单”）；不能把内部思考内容暴露为进度，也不能在工作仍运行时误报完成。

把优化假设写成可证伪的实验：目标指标、对照组、固定条件、样本数、停止条件、质量护栏和回滚条件。比较版本时同时报告任务延迟分布、成功率、成本与质量。若输入缩短后 TTFT 没变化，可能是变化小于噪声，也可能是排队、缓存或别的阶段主导；需要更好的控制与更大样本，而不是得出“prompt 压缩无效”的通则。若 token/s 改变，也先检查输出 token 口径、事件边界、服务负载、并发和错误样本。
