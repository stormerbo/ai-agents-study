前面章节里散落着一些历史成本记录：单次调用 365 token、agent 1625、12 轮累计输入 57,822、以及某组子 agent 的 8.1 倍 token 比值。它们来自不同任务和记录口径，部分缺少逐次原始请求/响应，不能直接拼成一组可比较的质量或账单证据。本节把**成本归因方法**收拢起来，并将历史数字与可计算的情景模型分开。

## 四种成本观察角度

一次 agent 运行可以从四种角度看成本；这些分析视角会交叉，**不是四个互斥的账单项目**：输入和输出是 API usage 中通常需要分别核算的 token 类别；工具定义是输入的一部分；“重复”是多个调用/执行者反复提交内容的放大机制。

| 观察角度 | 什么时候出现 | 如何计量 |
|---|---|---|
| **输入** | 按调用协议发送上下文；Stateless 客户端常在下一次请求中带上当前需要的消息历史 | 按完整调用轨迹和目标 provider usage 汇总；只有当每轮提交完整且上下文逐轮增长时，简化模型才呈二次增长 |
| **输出** | 模型每次响应生成内容 | 按每次调用的实际 output usage 汇总；单价由 provider、model 与 token 类别决定 |
| **工具定义** | 请求中包含工具 schema 时 | 它已包含在输入里；可单独归因分析，但不得把已含在 usage 的工具定义再加一遍 |
| **重复** | 多轮、多 agent 或重试再次提交上下文/工具定义时 | 不是额外 token 字段；从调用轨迹看哪些输入被重复以及重复了几次 |

**先区分请求形态、归因维度与账单口径。** Hosted conversation state、缓存或延迟加载会改变请求与 usage；不要把“每轮必定重发完整历史”当成所有 agent runtime 的事实。工具 schema 也不是独立于输入的第二份账单：把它标记出来是为了知道输入成本从哪里来，汇总账单时不能重复计算。

## 第一、二块：输入与输出

第 1 章保留过一组历史 token 摘要：单次调用 365 token、workflow 619 token、agent 1625 token。这些记录缺少可独立核验的逐次原始响应、完整任务轨迹与质量评分；它们不能证明各方案任务质量等价，也不能把 4.5 倍 token 比值当成费用或质量差异。

第 7 章另有 12 轮累计输入 57,822、末轮 8,907，以及按原模型外推的 50 轮 24.2 倍记录。它们仍是历史摘要，缺少足以重建 endpoint、逐轮请求和用量口径的原始证据；保留作复核线索，不作通用增长实测。

累计输入的二次项只出现在下面这些假设同时成立时：每轮都提交完整的、随轮数增加的上下文，且新上下文按固定增量增长。这不是所有 agent 或 server-side conversation state 的公式：

```text
简化模型：累计输入 = Σ[57 + 16(n-1)]（n=1..N）= 57N + 8N(N-1)
假设：stateless、每轮重发完整历史、每轮新增 16 token
```

这里的二次项是 `8N(N-1)`：在该假设中，每轮输入按 16 token 增长，再对 0 到 N-1 累加。二次项占主导时，“轮数翻倍约增至四倍”才是近似，**不是每个 N 都精确成立**。实际任务应按调用轨迹中的每轮输入量求和；若使用 server-side state、裁剪或摘要，增长形状会不同。

第 11 章讲预算闸门时会讨论任务步数限制。步数是一个控制旋钮，但不能仅凭轮数推断账单；还要统计每轮 input/output usage、工具定义以及重试与失败调用。

输出 token rate 因 provider 与 model 而异，有些模型的输出费率高于输入；不能只看 token 数比较成本。确认当前 price sheet 后，用该 workload 的实际输入/输出构成分别估算。输入是否占主要成本，也应由 usage 和费率计算得出。

## 第三种观察：工具定义

第 4 章保留的 DeepSeek 兼容端点历史摘要显示，8/20/44/86 个工具时请求总 input 为 678/1326/2623/4945，两端差约 55 token/新增工具。它没有隔离 schema token，也缺少原始请求和逐次缓存 usage，所以不是隔离测得的 schema token，更不能当成固定“每个工具的价格”。

如果 endpoint 每次请求都携带完整工具 schema，那么 schema 会增加输入量；如果有工具延迟加载或 prompt cache，具体未缓存/缓存读取/写入的字段与费率要按该 endpoint 文档解读。实测时用相同模型、system、messages 和其余请求参数做有/无工具对照，同时记录 provider 返回的完整 usage。**工具 token 已经包含在输入 usage 时，只能作为输入的归因子集，不能再次加到总输入上。**

## 第四种机制：重复

历史记录曾报告多智能体场景：单 agent 4,270 token，主管加 3 个工人 8,161 token（1.91 倍）；另一个背景更大的配置为 1.99 倍。第 3 章还记录 8.1 倍（8 个子 agent 的记录摘要 68,548 vs 8,430）。这些任务的原始逐次轨迹、统一评分与账单资料不完整，**不能据此确认各拓扑质量等价、普遍成本倍数，或把 token 比值当作费用倍数**。

只在一个受控的敏感性模型里，可以假设被复制的输入乘以 `m`，而输出量固定不变：

```text
token-volume multiplier = (input × m + output) / (input + output)
```

这个算式只说明：在这些假设下，输出占比越高，复制输入造成的总 token 增幅越小。真实多 agent 系统还可能重复工具 schema、生成更多输出、增加失败/重试或改变任务质量；应从所有 agent 的实际调用轨迹分别汇总 usage 和 provider 费率。它可以帮助提出评估问题，**不能单独决定是否采用多智能体**。

## 一个可操作的估算方法

**第一步，使用各次调用实际 usage 与元数据。** 记录 endpoint/provider、返回的实际 model、request/trace id、任务 id、轮次、step kind、输入/输出 usage、结束状态和延迟；不要把日志中的字段名直接当作跨 provider 的标准。

以当前官方接口文档为例，Anthropic Messages API 的 `input_tokens`、`cache_read_input_tokens`、`cache_creation_input_tokens` 是三个不重叠的输入类别，官方总输入算法为三者相加；DeepSeek Chat API 同时报告 `prompt_tokens`、`prompt_cache_hit_tokens`、`prompt_cache_miss_tokens` 与相关 cached-token details；OpenAI usage 有 `input_tokens`，并可能在 `input_tokens_details` 下报告 `cached_tokens` 与 `cache_write_tokens`。字段关系和费用算法因 provider/model/endpoint 而异：**只能按对应接口定义把 usage 映射到不重叠的计费类别，不能把总量和它的明细再次相加，也不得把 Anthropic 的字段公式套给其他 provider。**

**第二步，按任务类型看调用数与成本分布。** 记录每个完整任务的调用轮数和总费用，按 workload/cohort 查看 P50、P90、P99；样本太少时只描述样本，不把分位数当稳定总体估计。若任务确实按轮次增长上下文，单独画出每轮 token 和成本，但不要假设所有接口都在每轮完整重发。

**第三步，做同条件对照来归因工具定义。** 在相同 model、system、messages 和采样设置下，比较有/无工具的完整调用 usage；按 provider 契约核对缓存读写计量，并检查工具是否每次都实际提交、是否延迟加载。工具 schema 已在总输入 usage 中时，它只是可归因的子集。不要直接用“工具数 × 60 token × 轮数”，除非这是你明确标出的、经过本地验证的情景假设。

**第四步，按 provider 的当前费率逐次折算，再汇总任务账单。** 可把计算过程写成概念模板：

```text
call_cost = provider_pricing(model, usage_categories, current_rate_card)
task_cost = Σ(call_cost for every request, including retries and failed requests when billed)
```

按账单费率分别计算未缓存、缓存读取、缓存写入与输出，再对任务内请求求和；费率卡也可能包含图片、音频或服务调用等类别，实际计算以当前 provider 计费文档和账单为准。工具定义不是另一个 token 账单字段，不得在 usage 已含 schema 后再加一次。

四步里，最容易跳过的是逐次归因：只看平均轮数或总 token 会隐藏长任务、重试和缓存状态的差异。最后的成本结论应由完整调用轨迹、provider usage 与当前费率共同决定，而不是从一个简化公式推断。

## 一个需要用任务级数据回答的问题

减少重复输入，和更换更低单价的模型，哪项节省更多？不能从不同章节的 token 摘要直接比较：每个模型的输入/输出构成、缓存读写、任务完成质量和实际费率都可能不同。

第 1 章历史摘要中的 365 与 1,625 token 缺少可复核的完整请求和评分；把差额换算成“省 78% 成本”，或据此断言它超过“模型单价减半”的收益，都没有充分依据。正确做法是对同一目标 workload 设立可接受的质量/完成判据，分别测试减少上下文重复与模型替换，按每次调用的 provider usage 和当前费率核算总成本，并同时比较延迟、失败率和重试。

分级路由仍是候选优化（第 4 节），但路由自身也可能增加判定调用或升级重试。先收集基线，再用固定评测集和在线灰度检验质量与成本，最后决定优先级。


## 固定假设场景：工具定义约占情景输入量的 62%

以下是本地算术演示，不是 provider 实测或账单。假设每轮上下文从 57 token 起、之后每轮增加 16 token；每个工具 schema 按 60 token 计；每轮输出 300 token；输出的情景单位按普通输入的 4 倍计。表中工具 schema 与上下文假设分开列示，只为归因；真实 provider usage 通常已将 schema 纳入输入，账单不得重复相加。

```text
场景                                      上下文   输出   schema估算   情景成本单位
单轮，无工具                                  57    300          0          1,257
单轮，8 个工具                                57    300        480          1,737
10 轮，8 个工具                            1,290  3,000      4,800         18,090
30 轮，8 个工具                            8,670  9,000     14,400         59,070
30 轮，上下文复制 4 份（输出/schema 不变）  34,680  9,000     14,400         85,080
```

（本地计算，2026-10-09。`4×` 输出权重、`60 token/schema` 与上下文复制次数都是情景参数，不是当日或当前价格。）

**第一**，在这组假设里，30 轮的上下文+schema token 为 23,070，是单轮无工具的上下文 57 的约 405 倍。它体现“固定小输入逐轮增长”的数学结果，不代表一般任务的 token 或费用倍率。

**第二**，30 轮 schema 估算量为 14,400，占该情景上下文+schema token 的 62.4%（14,400 / (8,670 + 14,400)）。这是指定参数下的归因示例，不是分离测得的 schema 用量、账单占比或可复用的工具单价。

**第三**，在该敏感性模型里，输出和工具定义保持不变，只把上下文复制 4 份，用来隔离“重复上下文”这一变量；它不是多 agent 工作流的完整总成本。真实 agent 的工具 schema、输出、重试都要从各自实际请求轨迹取数。

这组假设可提示你检查重复传输；是否缓存、延迟加载或缩短输入，应按目标 endpoint 的 usage、当前费率、延迟和质量评估。不能只凭 62.4% 情景占比断定缓存优先于换模型。

## 把成本归因落到调用轨迹

上面的角度是**分析框架**。实际系统应逐次记录调用并归属到完整任务；三个标签是起点，还要保留 provider usage 与计费所需信息。

```text
task_id      串起一个完整任务的所有请求
request_id   对应 provider 返回的 request/response id（如可用）
provider     实际 endpoint 与 provider
model        响应返回的 model id
step_kind    planning | execution | summarization | retrieval
turn_index   这是任务中的第几轮
usage        原始 provider usage 与版本化后的非重叠归一化字段
outcome      stop reason / error / retry / latency
```

三个标签分别对应三个不同的问题：

- **task_id / request_id** —— 把所有调用串成任务并与账单或日志核对；敏感标识应按数据策略做脱敏或短期化。
- **provider / model** —— 区分实际 endpoint 和返回模型，以当前费率归算；只看请求时填写的别名可能会归错价格。
- **step_kind / turn_index / outcome** —— 用于比较工作阶段、轮次成本和失败/重试；只有特定任务分布才会呈现“后期更贵”，要用逐次 usage 检验。

仅有三个标签仍不足以对账：需要 provider usage、模型费率版本、时间戳、结束状态及重试关联。比如“一开始每轮 500、后期每轮 8,000”可以作为假想轨迹，具体系统是否如此要由采样数据回答。

**把成本与现有 tracing 关联**，但不要为了成本长期保存 prompt 原文或敏感业务载荷；通常先记录 usage、模型、调用阶段、状态和必要的版本/哈希元数据。
## 完整可运行代码

下面的 Python 程序按明确列出的本地情景参数计算示例表；schema token 从上下文输入中拆开只为归因，真实 API 的 usage 通常会把它计入输入。程序输出是 `scenario_cost_units` 情景成本单位，不是 provider 账单。实跑状态：Python 标准库本地情景计算；结果是构造情景，不是 provider 请求或账单。

```python
"""成本情景代理：演示输入、工具 schema 与输出的算术关系，不是 provider 账单。纯本地计算。"""
TOOL_TOKENS_PER_TOOL = 60   # 情景参数；不是实测的通用 schema 单价
FIXED_INPUT = 57            # 简化上下文模型的起点
PER_TURN_INPUT = 16         # 每轮上下文增量


def estimate(turns, tools, output_per_turn, output_rate=4.0, context_copies=1):
    """复制上下文但固定工具/schema与总输出的敏感性演示。"""
    if turns < 1 or tools < 0 or context_copies < 1:
        raise ValueError("turns/context_copies must be >= 1 and tools >= 0")
    context_total = 0
    schema_total = 0
    output_total = 0
    for n in range(1, turns + 1):
        context_total += (FIXED_INPUT + PER_TURN_INPUT * (n - 1)) * context_copies
        schema_total += TOOL_TOKENS_PER_TOOL * tools
        output_total += output_per_turn
    scenario_cost_units = context_total + schema_total + output_total * output_rate
    return {
        "context": context_total,
        "output": output_total,
        "schema_estimate": schema_total,
        "scenario_cost_units": scenario_cost_units,
        "turns": turns,
    }


if __name__ == "__main__":
    print("本地情景成本代理（输出权重按上下文的 4 倍）")
    print()
    print("  %-42s %9s %9s %10s %12s" % ("场景", "上下文", "输出", "schema估算", "情景成本单位"))
    cases = [
        ("单轮，无工具", 1, 0, 300, 1),
        ("单轮，8 个工具", 1, 8, 300, 1),
        ("10 轮，8 个工具", 10, 8, 300, 1),
        ("30 轮，8 个工具", 30, 8, 300, 1),
        ("30 轮，上下文复制 4 份（其他不变）", 30, 8, 300, 4),
    ]
    for label, turns, tool_count, output, copies in cases:
        result = estimate(turns, tool_count, output, context_copies=copies)
        print("  %-42s %9d %9d %10d %12d" % (
            label, result["context"], result["output"],
            result["schema_estimate"], result["scenario_cost_units"]))

    one = estimate(1, 0, 300)
    many = estimate(30, 8, 300)
    input_side = many["context"] + many["schema_estimate"]
    print()
    print("30 轮情景的上下文+schema量是单轮无工具上下文的 %.0f 倍。" %
          (input_side / one["context"]))
    print("工具schema假设占该情景上下文+schema量的 %.1f%%。" %
          (many["schema_estimate"] / input_side * 100))
    print("上下文复制 4 份的敏感性场景固定输出和工具定义，仅用于隔离上下文重复。")
```

## 一条可归因记录需要包含什么

`stop_reason`、`finish_reason` 等结束状态字段的名称和语义由 provider API 定义；日志可保存 provider 原字段并在版本化 adapter 中归一化。`max_tokens` 一类请求参数限制输出或计算行为，但不等于完整任务成本预算。

以下四行是从历史记录整理出的**规范化的历史记录摘要**，不是保存下来的原始逐次请求/响应；原始逐次请求/响应未归档，确切 endpoint、字段映射和 usage 分解无法独立复核。`input_tokens`、`cache_read`、`cache_create` 是该样例内部的规范化列名，不保证等同任何 provider 字段或原始响应：

```json
{"trace_id":"tr_a1","turn_index":1,"step_kind":"planning","model":"deepseek-flash","input_tokens":341,"cache_read":0,"cache_create":0,"output_tokens":129,"stop_reason":"tool_use","latency_ms":1460}
{"trace_id":"tr_a1","turn_index":2,"step_kind":"execution","model":"deepseek-flash","input_tokens":227,"cache_read":256,"cache_create":0,"output_tokens":57,"stop_reason":"tool_use","latency_ms":900}
{"trace_id":"tr_a1","turn_index":3,"step_kind":"execution","model":"deepseek-flash","input_tokens":169,"cache_read":384,"cache_create":0,"output_tokens":56,"stop_reason":"tool_use","latency_ms":760}
{"trace_id":"tr_a1","turn_index":4,"step_kind":"summarization","model":"deepseek-flash","input_tokens":238,"cache_read":384,"cache_create":0,"output_tokens":22,"stop_reason":"end_turn","latency_ms":930}
```

字段从哪里取、类型与取值：

| 字段 | 从哪来 | 类型 / 取值 |
|---|---|---|
| task_id / trace_id | 由应用生成，关联一次完整任务的所有请求 | 脱敏标识 |
| request_id | provider 返回的 id（如有） | string |
| turn_index / step_kind | 应用记录轮次与阶段 | int / 受控枚举 |
| provider / endpoint / requested_model / returned_model | 记录实际路由与模型别名/返回值 | string |
| usage_raw | 原始 provider usage（遵循数据保留策略） | 结构化字段或短期留存 |
| usage_normalized | 版本化 adapter 生成、明确非重叠的分类 | int 与 adapter 版本 |
| outcome / stop field / retry | 用 provider 原字段并保留重试关系 | 受控枚举 / int |
| latency_ms / timestamp | 应用本地时钟测时及事件时间 | int / timestamp |

**判据：** 只有当原始字段和归一化规则足以把请求放进正确账单类别，才可用于费用核对。任务 id、provider/model、usage、费率版本和重试关联缺一项，都可能让“总 token”无法解释为实际成本；可按敏感数据策略对 request id 做哈希/缩短，并避免记录 prompt 原文。

## 从归一化样例计算分位数与 schema 情景占比

下面代码跑的是上方四条规范化历史摘要，仅演示分位数与归因算法；字段映射不可独立复核，不能把其输出当作 provider usage 或成本结论。

```python
"""对本地归一化 usage 样例计算分位数与工具 schema 情景占比。"""
import math

# 这些列是示例 adapter 的规范化类别，不是 provider 的统一原始字段。
RECORDS = [
    {"turn_index": 1, "step_kind": "planning", "input_tokens": 341, "cache_read": 0, "cache_create": 0, "output_tokens": 129},
    {"turn_index": 2, "step_kind": "execution", "input_tokens": 227, "cache_read": 256, "cache_create": 0, "output_tokens": 57},
    {"turn_index": 3, "step_kind": "execution", "input_tokens": 169, "cache_read": 384, "cache_create": 0, "output_tokens": 56},
    {"turn_index": 4, "step_kind": "summarization", "input_tokens": 238, "cache_read": 384, "cache_create": 0, "output_tokens": 22},
]
TOOL_TOKEN_PER_TOOL = 60   # 假设参数；不是该 usage 中分离测得的工具 token
TOOLS_PER_REQUEST = 1


def normalized_input(record):
    """仅在 adapter 已确认三类不重叠时，汇总本例的输入 token。"""
    return record["input_tokens"] + record["cache_read"] + record["cache_create"]


def percentile_nearest_rank(values, p):
    """最近秩法：升序后取 ceil(p*n)-1；用于说明口径，不代表稳定总体估计。"""
    if not values:
        raise ValueError("values must not be empty")
    if not 0 <= p <= 100:
        raise ValueError("p must be between 0 and 100")
    ordered = sorted(values)
    rank = max(1, math.ceil(p / 100 * len(ordered)))
    return ordered[rank - 1]


if __name__ == "__main__":
    inputs = [normalized_input(record) for record in RECORDS]
    for record in RECORDS:
        total = normalized_input(record)
        print("  第 %d 轮 %-14s 总输入 %5d（input %d + cache_read %d + create %d）"
              % (record["turn_index"], record["step_kind"], total,
                 record["input_tokens"], record["cache_read"], record["cache_create"]))
    print()
    print("P50=%d  P90=%d  P99=%d  （最近秩法；样例仅 4 条）"
          % (percentile_nearest_rank(inputs, 50),
             percentile_nearest_rank(inputs, 90),
             percentile_nearest_rank(inputs, 99)))
    by_step = {}
    for record in RECORDS:
        by_step[record["step_kind"]] = by_step.get(record["step_kind"], 0) + normalized_input(record)
    total_input = sum(by_step.values())
    for step, value in sorted(by_step.items(), key=lambda item: -item[1]):
        print("  %-14s %5d token  %4.1f%%" % (step, value, 100 * value / total_input))

    schema_estimate = TOOL_TOKEN_PER_TOOL * TOOLS_PER_REQUEST * len(RECORDS)
    print("工具定义情景估算 ≈ %d token，占输入侧 %d 的 %.1f%%。"
          % (schema_estimate, total_input, 100 * schema_estimate / total_input))
```

程序输出摘录（关键结果）：

```text
  第 1 轮 planning       总输入   341（input 341 + cache_read 0 + create 0）
  第 2 轮 execution      总输入   483（input 227 + cache_read 256 + create 0）
  第 3 轮 execution      总输入   553（input 169 + cache_read 384 + create 0）
  第 4 轮 summarization  总输入   622（input 238 + cache_read 384 + create 0）

P50=483  P90=622  P99=622  （最近秩法；样例仅 4 条）
  execution       1036 token  51.8%
  summarization    622 token  31.1%
  planning         341 token  17.1%
工具定义情景估算 ≈ 240 token，占输入侧 1999 的 12.0%。
```

**读法：** 在这四行规范化摘要中，execution 占示例归一化输入的 51.8%；这不证明实际历史任务后期变贵，因为摘要本身不能独立复核。12.0% 是把假设 `60 token/工具` 乘以 4 次请求后的 schema 情景量，占样例归一化输入的比例；**不是独立测得的工具定义 usage 或账单费用**。四条样本不足以支持稳定的 P50/P90/P99 推断；这里仅演示最近秩法，真实系统应按目标 workload 采集更多完整调用。

**失败形态：** 把归一化样例里的 `input_tokens` 当成 provider 总输入，或没有查清它与缓存明细是否互斥；本例第 2 行只看该列得到 227，三个已声明为不重叠的本地类别相加才是 483。面对真实响应，先按具体 API 文档检查总量与明细关系，避免漏计或重复计数。本项目旧记录曾出现此类解读，但因原始逐次响应缺失，具体因果仍无法独立复核。

## 常见坑

- **只按平均轮数估算。** 长会话可能贡献不成比例，要查看 P90/P99 和实际逐轮 usage。
- **把某个 provider 的 usage 算法当通用公式。** 按 endpoint 文档区分总输入、缓存读取/写入明细和费用，确认字段是否重叠后再归一化。
- **预设输入或输出一定是主要成本。** 按当前费率和完整调用轨迹计算两者实际贡献。
- **忽略工具定义带来的请求输入变化。** 某些 endpoint 每轮会提交工具 schema；历史请求总量不能直接当成 schema 单价。记录缓存读写和完整 usage，再估算目标 endpoint 的边际费用。
- **把简化模型推广成所有 agent 的增长律。** 二次项要求 stateless 全量重发且上下文按轮增长；其他状态协议、摘要、裁剪与缓存行为要从实际 trace 测量。
- **把情景比例当成普遍优化收益。** 60 token/schema、输出 4×、上下文复制 4 份都只是参数；真实 workload 必须按目标任务的质量判据、provider usage、当前费率、延迟和失败/重试成本一起对照。
