前面十七章里散落着很多成本数字：单次调用 365 token、agent 1625、12 轮对话累计 57822、8 个子 agent 是 8430 的 8.1 倍。这一节把它们收成一个模型。

## 四块来源

一次 agent 运行的成本由四块组成，而它们的增长方式完全不同：

| 来源 | 什么时候付 | 增长方式 |
|---|---|---|
| **输入** | 每一轮都要重发全部上下文 | 随轮数**平方**增长 |
| **输出** | 只有新增的部分 | 线性，但单价通常是输入的几倍 |
| **工具定义** | 每一轮都随输入重发 | 线性（工具数 × 轮数） |
| **重复** | 多 agent / 子 agent 各装一份 | 乘份数 |

**第二列是这一节最重要的东西："每一轮都要重发"。** 这是 agent 成本区别于普通 API 调用的根本原因。

## 第一块和第二块：输入与输出

第 1 章测过一组对照：单次调用 365 token、workflow 619、agent 1625 —— 同样是完成任务，agent 的 token 是单次调用的 4.5 倍。差别不在输出了多少，而在**输入被重发了多少次**。

第 7 章测过多轮：12 轮对话累计输入 57822 token，是末轮单次（8907）的 **6.5 倍**。按模型外推 50 轮是 **24.2 倍**。

这个增长是**平方级**的，公式在第 1 章已经推过：

```text
累计输入 ≈ 57N + 16N(N-1)      （N 为轮数）
```

那个 `16N(N-1)` 就是平方项。它说明一件事：**轮数翻倍，累计输入翻四倍。**

所以「让 agent 多跑几轮」这个决定的成本不是线性的。第 11 章讲预算闸门时说"设一个最大步数"，成本上的理由就在这里。

**输出的单价通常是输入的几倍**（各厂商不同，本站不写具体价格 —— 第 3 节讲怎么估算）。但输出量小得多，所以在多轮场景里**输入往往才是主要成本**。这一点和直觉相反，值得用数据确认一次再下结论。

## 第三块：工具定义

第 4 章实测：约 60 token 一个工具，8 个工具 678 token，86 个工具 **4945 token**。

关键在于**这个成本每一轮都要付一次**。8 个工具跑 10 轮 = 6780 token 的工具定义开销 —— 而这部分内容**从头到尾没变过**。

这引出第 3 节要讲的缓存：**不变的内容是最好的缓存对象，而工具定义恰好是最典型的不变内容。**

## 第四块：重复

第 12 章测过多智能体：单 agent 4270 token，主管加 3 个工人 8161 token，**1.91 倍**。而背景更大时（3489 字）是 1.99 倍。

第 3 章那个 8.1 倍（8 个子 agent 各装一份共享背景，68548 vs 8430）是同一个模型取不同参数的结果：**输入乘以份数，输出不乘。** 所以输出占比高时倍数被摊平，背景占比高时倍数放大。

用公式表达：

```text
倍数 = (输入 × 份数 + 输出) / (输入 + 输出)
```

这个公式可以直接用来判断"该不该上多智能体"：**如果你的任务里输出占比高（比如生成长文本），多智能体的成本惩罚比你想的小；如果背景占比高（比如多份材料分析），惩罚会显著放大。**

## 一个可操作的估算方法

看上面的数字会有一个自然的问题：**我怎么估我自己的系统？** 步骤只有四步。

**第一步，量一次单轮的实际 token。** 别用估算 —— 跑一次真的调用，读回 usage。注意要看三项之和（第 4 节的缓存陷阱）：

```text
输入 = input_tokens + cache_read_input_tokens + cache_creation_input_tokens
```

**第二步，量轮数分布。** 不是平均轮数，是分布 —— 因为成本是平方的，**长尾的那几次才是账单的主体**。看 P50、P90、P99。

**第三步，算工具定义的固定开销。** 工具数 × 60 token × 平均轮数。如果这个数占总成本的比例超过 20%，缓存是第一个该做的事。

**第四步，把上面三项加起来乘调用量。** 得到的是**输入侧**成本，输出侧单独算。

四步里，第二步最容易被跳过 —— 很多人用平均轮数去估，而那会显著低估。因为平方关系决定了几次 30 轮的会话，比三百次 3 轮的会话还贵。

## 一个反直觉的结论

把这一节的数据合起来，得到一条和直觉相反的结论：

**在 agent 里，省钱的关键通常不是"用更便宜的模型"，而是"少发一点重复内容"。**

理由：第 1 章那组对照里，agent 是单次调用的 4.5 倍 —— 而那个 4.5 倍**完全来自重复**，不是来自模型的单价。换一个便宜一半的模型，你省 50%；把重复消掉，你省 78%。

这不是说模型选择不重要（第 4 节会讲分级路由），而是说**优化的顺序应该是：先消重复，再换模型**。而这个顺序经常被倒过来 —— 因为换模型看起来更像一个"技术决策"，而"少发点重复内容"听起来像小打小闹。


## 一个真实的比例：工具定义占了 62%

上面的公式可以代进具体数字。我用一个常见的形态算了一遍：8 个工具、每轮输出 300 token、跑 30 轮。

```text
场景                                    输入      输出     工具定义      折算计费
单轮，无工具                              57      300          0        1,257
单轮，8 个工具                            57      300        480        1,737
10 轮，8 个工具                        1,290    3,000      4,800       18,090
30 轮，8 个工具                        8,670    9,000     14,400       59,070
30 轮，8 工具，4 个 agent 共享背景      34,680    9,000     14,400       85,080
```

（本地计算，2026-10-09。输出单价按输入的 4 倍计。）

三个数字值得单独看：

**第一，30 轮比单轮，轮数是 30 倍，但输入侧成本增长 405 倍。** 那不是笔误 —— 平方项就长这样。

**第二，30 轮里工具定义累计占了输入侧的 62%。** 工具定义从头到尾没变过一个字，却成了最大的一块。

**第三，4 个 agent 共享背景时，输入侧再乘 4，输出不乘。**

第二条直接给出了优化顺序：**如果你的 agent 跑很多轮、工具很多，第一个该做的是缓存（第 3 节），而不是换模型。** 因为那 62% 是完全不变的重复内容。

## 一个把它落地的方法：先给成本打上标签

上面四块来源是**分析框架**。要在真实系统里用起来，还得先把成本拆到能归属的粒度上。做法是：**每一次调用都打上三个标签。**

```text
step_kind    planning | execution | summarization | retrieval
model        实际用的模型名
turn_index   这是第几轮
```

三个标签分别对应三个不同的问题：

- **step_kind** —— 回答「钱花在哪种工作上」。如果发现 60% 花在 summarization 上，那第一个该优化的是摘要，不是工具调用。
- **model** —— 回答「换模型能省多少」。同时它也是验证分级路由生效的方式（第 4 节）。
- **turn_index** —— 回答「是前期贵还是后期贵」。这个维度最容易被忽略，而它的信息量最大 —— 因为成本是平方的，**后期那几轮才是账单主体**。

没有第三个标签，你会看到「平均每轮 3000 token」这样一个没用的数字；有了它，你会看到「第 1 轮 500、第 20 轮 8000」，然后立刻明白该优化什么。

**这三个标签是第 15 节那套追踪的扩展。** 追踪本来就是逐步记录的，加上成本字段几乎是零边际成本 —— 而它让成本从「一个总数」变成了「可归因的结构」。
## 完整可运行代码

下面这段代码按上面的公式算一遍：给定轮数、每轮输入输出、工具数，算出总成本以及四块各自的占比。

```python
"""成本模型：四块来源各自占多少。纯本地计算。实跑状态：2026-10-09。"""
TOOL_TOKENS = 60          # 第 4 章实测：约 60 token/工具
FIXED_INPUT = 57          # 第 1 章公式的常数项
PER_TURN_INPUT = 16       # 第 1 章公式的每轮增量


def estimate(turns, tools, output_per_turn, out_price_ratio=4.0, share_context=1):
    """share_context>1 表示多 agent，每个 agent 各装一份背景。"""
    input_total = 0
    output_total = 0
    tool_total = 0
    for n in range(1, turns + 1):
        ctx = FIXED_INPUT + PER_TURN_INPUT * (n - 1)      # 历史累积
        tool_total += TOOL_TOKENS * tools                  # 每轮重发工具定义
        input_total += (ctx * share_context)
        output_total += output_per_turn
    billed = input_total + output_total * out_price_ratio
    return {"input": input_total, "output": output_total, "tools": tool_total,
            "billed": billed, "turns": turns}


if __name__ == "__main__":
    print("四块来源的占比（输出单价按输入的 4 倍计）")
    print()
    print("  %-34s %9s %9s %9s %11s" % ("场景", "输入", "输出", "工具定义", "折算计费"))
    cases = [
        ("单轮，无工具", 1, 0, 300, 1),
        ("单轮，8 个工具", 1, 8, 300, 1),
        ("10 轮，8 个工具", 10, 8, 300, 1),
        ("30 轮，8 个工具", 30, 8, 300, 1),
        ("30 轮，8 工具，4 个 agent 共享背景", 30, 8, 300, 4),
    ]
    for label, t, tl, o, sc in cases:
        e = estimate(t, tl, o, share_context=sc)
        total = e["input"] + e["tools"] + e["output"] * 4
        print("  %-34s %9d %9d %9d %11d" % (label, e["input"], e["output"], e["tools"] & 0xFFFFFFFF, total))
    print()
    e1 = estimate(1, 0, 300); e2 = estimate(30, 8, 300)
    print("=== 关键对比 ===")
    print("  单轮到 30 轮，轮数 30 倍，但输入侧成本增长 %.0f 倍 —— 因为它是平方的。" %
          ((e2["input"] + e2["tools"]) / e1["input"]))
    print("  30 轮里，工具定义累计占了输入侧的 %.0f%%。" %
          (e2["tools"] / (e2["input"] + e2["tools"]) * 100))
    print("  4 个 agent 共享背景时，输入侧再乘 %.0f 倍（输出不乘）。" %
          (estimate(30, 8, 300, share_context=4)["input"] / estimate(30, 8, 300)["input"]))
```

## 常见坑

- **按平均轮数估算。** 成本是平方的，长尾那几次才是账单主体，要用 P90/P99。
- **只看 `input_tokens`。** 必须加上 cache_read 和 cache_creation 两项（第 4 节的实测陷阱）。
- **以为输出是主要成本。** 多轮场景里输入通常才是，而且它每轮重发。
- **忽略工具定义的固定开销。** 60 token/工具 × 轮数，86 个工具时每轮就近 5000 token。
- **把「一亿 token」当成线性。** 轮数翻倍，累计输入翻四倍。
- **优化顺序倒过来。** 先消重复（省 78%）再换模型（省 50%），不是反过来。
