第 9 章给过四道闸门（活动范围、预算、熔断、不可逆确认）。这一节把「预算」和「熔断」这两道讲透 —— 因为它们的失效方式是**静默的**：超支之后你不会收到错误，只会收到账单。

## 三个层次

预算闸门要分三层设，因为它们的**作用范围**和**响应动作**不同：

| 层次 | 计量单位 | 超限时做什么 |
|---|---|---|
| **单次调用** | 该次请求的 token / 耗时 | 截断（`max_tokens`）、超时 |
| **单次任务** | 整个 agent 循环累计 | 停止循环、返回当前结果 |
| **账户 / 每日** | 全部调用累计 | 熔断（拒绝新请求） |

三层里最容易漏的是中间那层。第一层有现成的参数（`max_tokens`、超时），第三层有云厂商的预算告警，而**单次任务的累计限制要自己实现** —— 而它恰好是 agent 特有的那一层。

一个 30 轮的 agent 循环，如果每轮 3000 token 输入，累计就是 9 万 token。**单看每一轮都很正常，加起来是 30 倍。** 这正是第 1 节那个平方项的表现。

## 为什么必须在循环里检查，而不是事后统计

事后统计能告诉你花了多少，但它**拦不住第三次**。

闸门必须在循环里，而且判据要是**确定性的**（第 16 节那条）。具体说，每一轮开始前检查：

```text
累计 token > 预算上限     → 停止，返回已有结果
累计步数 > 最大步数       → 停止
单轮耗时 > 单轮超时       → 中断该轮
连续失败 > N 次           → 熔断（第 11 章）
```

注意第一行的动作是**返回已有结果，而不是报错**。这是一个交互设计问题（第 19 章会展开）：agent 跑到一半被预算截断时，把已经完成的部分交出去，比抛一个异常有用得多 —— 因为那部分往往已经能用了。

## 熔断：和预算不同的一个机制

预算管的是「花太多」，熔断管的是「坏太多次」。两者容易混，但触发条件和动作都不同：

| | 预算 | 熔断 |
|---|---|---|
| 触发 | 累计 token / 步数超限 | 连续失败 / 异常响应比例 |
| 保护的 | 成本 | **上游服务和你自己** |
| 动作 | 停止本次任务 | 拒绝**后续所有**请求一段时间 |
| 恢复 | 下一个任务重新开始 | 半开状态试探后恢复 |

熔断的必要性来自第 11 章那条结论：**模型察觉不到自己卡住了**（第 9 章实测过它连点 4 次同一个错位置，因为没有「报告卡住」的出口）。所以「连续失败 N 次就停」这个判断必须由代码做。

## 降级：熔断之后的动作

熔断不能只是拒绝。三种降级方式，按用户感受排序：

**一、降级到便宜模型。** 质量下降但还能用。适合非关键任务。

**二、降级到缓存或预置答案。** 对常见问题给一个固定回答，并说明「当前无法实时处理」。

**三、明确拒绝并说明原因。** 最差但最诚实 —— 比让用户等 60 秒然后失败好。

三种的选择依据是**这个任务有多关键**。而关键是：**要提前决定，不能在熔断发生时临时想。** 熔断触发时系统已经在异常状态，那时做决策容易做出更糟的选择。

## 一个具体的数字：超支多少算异常

预算上限设多少？没有通用答案，但有一个可以用的方法：**先测量，再设上限为 P99 的 2 到 3 倍。**

步骤是：先跑一段时间不定上限（只记录），拿到单次任务 token 的分布；然后设上限。这样做的道理是：**上限的作用是拦住异常，不是拦住正常的长尾。** 设成 P50 会把一半的正常请求截断。

这个方法还有一个附带好处：它逼你先测量。而很多团队的上限是"拍脑袋定的一个看起来合理的数" —— 那个数通常远低于实际需求，然后被反复调高，最后没人知道它现在是多少。

## 一个反过来的检查

闸门也会失效 —— 静默地失效。三种常见形态：

**一、上限设了但没人看。** 超限时只是停止任务，而如果这个停止没有告警，你不会知道有多少任务被截断了。

**二、熔断阈值太松。** 连续失败 50 次才熔断 —— 那 50 次已经足够把你的上游打垮。

**三、降级路径从未被测试。** 熔断真的发生时才发现降级逻辑本身有 bug。

第三种最危险，因为**降级逻辑的代码路径只在异常时才会被执行** —— 而它平时跑不到，所以它是最容易腐烂的那部分代码。做法是**定期强制触发一次**（比如在测试环境把熔断阈值调到 1），确认降级可用。


## 一个真实的失败形态：预算被单轮吃掉

上面的三层里，单次调用那层有一个容易被忽略的坑：**思考型模型的输出预算**。

第 3 章和第 7 章都记录过这个形态：模型会先思考再回答，而长上下文让它思考更久。如果 `max_tokens` 设得太小，返回的是**空文本 + stop_reason 为 `max_tokens`** —— 看起来像「模型做不到」，实际是预算不够。

这件事在成本上有两个含义：

**一，单次调用的 `max_tokens` 要按最坏情况设。** 设 800 在简单任务上够用，在长上下文加思考任务上会整段失败。而失败的那次**照样计费**（思考的 token 已经产生了）。

**二，它是「单次调用」和「单次任务」两层之间的一个缝隙。** 单次调用没超（它只是停了），任务层也没超（第一轮就用完了预算而已）。但结果是任务失败且付了钱。

所以判据要加一条：**当 stop_reason 是 `max_tokens` 时，不要当成正常结果继续。** 它应该被记为一个异常，并触发重试（用更大的预算）或者直接失败 —— 而不是把空文本交给下一步。

## 一个组织问题：谁来决定预算上限

最后补一个非技术的点，但它往往是预算闸门能不能落地的关键：**上限该由谁定。**

三种常见安排，效果差别很大：

**由工程定。** 结果通常是按「技术上够用」设一个数，而那个数和业务价值没关系。表现是上限经常被调高，因为它拦住的都是正常业务。

**由业务定。** 结果通常是按「这个任务值多少钱」倒推，方向对，但业务方不了解 token 的量级，容易设出不现实的数字。

**两者一起定，而且用数据。** 具体形态是：工程提供单次任务的 token 分布（P50/P90/P99）和成本换算，业务方给出「这个任务愿意花多少」，两者对齐后定一个上限。

第三种唯一的额外成本是**要先测量**。而前面那个「设成 P99 的 2 到 3 倍」的方法正好提供了这份数据 —— 所以它不只是个技术方法，也是一份能拿去对齐的材料。

**这件事值得单独说，因为预算闸门失效的最常见原因不是技术，而是没人认领它。** 一个上限如果既不是工程定的、也不是业务定的，那它就会慢慢变成一个没人看的数字。
## 完整可运行代码

下面这段代码实现三层闸门加熔断，并跑一组会触发各种限的请求，看每一层的动作。

```python
"""三层预算闸门 + 熔断。纯本地模拟。实跑状态：2026-10-09。"""
TOKENS_PER_TURN = 3000
BUDGET_TASK = 30000       # 单次任务预算
MAX_TURNS = 30
BREAKER_THRESHOLD = 3     # 连续失败 N 次熔断


class Breaker:
    def __init__(self):
        self.fails = 0
        self.open = False

    def record(self, ok):
        if ok:
            self.fails = 0
            return
        self.fails += 1
        if self.fails >= BREAKER_THRESHOLD:
            self.open = True


def run_task(turns_before_failure, breaker):
    used = 0
    trace = []
    for turn in range(1, MAX_TURNS + 1):
        # 闸门检查（每轮开始前）
        if used + TOKENS_PER_TURN > BUDGET_TASK:
            trace.append("第 %d 轮：预算闸门触发（已用 %d / %d）→ 返回已有结果" % (turn, used, BUDGET_TASK))
            return "budget", used, trace
        if turn > turns_before_failure:
            breaker.record(False)
            trace.append("第 %d 轮：失败（连续 %d 次）" % (turn, breaker.fails))
            if breaker.open:
                trace.append("        → 熔断打开，拒绝后续所有请求")
                return "breaker", used, trace
            continue
        breaker.record(True)
        used += TOKENS_PER_TURN
        trace.append("第 %d 轮：成功（累计 %d token）" % (turn, used))
    trace.append("完成 %d 轮" % MAX_TURNS)
    return "ok", used, trace


if __name__ == "__main__":
    print("预算 %d token / 单轮 %d token / 最大 %d 轮 / 熔断阈值 %d"
          % (BUDGET_TASK, TOKENS_PER_TURN, MAX_TURNS, BREAKER_THRESHOLD))
    print()
    for label, fail_after in [("正常跑完", 99), ("第 8 轮开始持续失败", 8), ("第 20 轮开始持续失败", 20)]:
        b = Breaker()
        outcome, used, trace = run_task(fail_after, b)
        print("  【%s】结果：%s，用了 %d token" % (label, outcome, used))
        for line in trace[-4:]:
            print("      %s" % line)
        print()
    print("=== 三个要点 ===")
    print("  1. 闸门在**每轮开始前**检查。事后统计只能告诉你花了多少。")
    print("  2. 超预算的动作是**返回已有结果**，不是报错 —— 那部分往往已经能用。")
    print("  3. 熔断保护的不是成本，是上游服务和你自己（第 11 章）。")
    print()
    b = Breaker()
    run_task(8, b)
    print("  注意「第 8 轮开始失败」这一组的输出：熔断在第 10 轮打开，")
    print("  而如果没有熔断，它会一直失败到第 30 轮 —— 22 次无用调用。")
```

## 把常量换成从 usage 累加

上面那段演示里 `TOKENS_PER_TURN = 3000` 是常量，真实循环里必须从**每一轮响应的 `usage`** 累加，而且口径要和第 1 / 3 节接上：**总输入 = input_tokens + cache_read + cache_create**（缓存命中也要计入总输入，否则命中之后闸门会误以为没花钱）。

下面这段跑的正是第 1 节那 4 条真实记录（实跑 2026-10-12）：

```python
"""预算闸门：从每轮响应的 usage 累加，而不是用一个常量。"""
RECORDS = [
    {"turn": 1, "input_tokens": 341, "cache_read": 0, "cache_create": 0, "output_tokens": 129, "stop_reason": "tool_use"},
    {"turn": 2, "input_tokens": 227, "cache_read": 256, "cache_create": 0, "output_tokens": 57, "stop_reason": "tool_use"},
    {"turn": 3, "input_tokens": 169, "cache_read": 384, "cache_create": 0, "output_tokens": 56, "stop_reason": "tool_use"},
    {"turn": 4, "input_tokens": 238, "cache_read": 384, "cache_create": 0, "output_tokens": 22, "stop_reason": "end_turn"},
]
BUDGET = 2000

def billed_input(u):
    return u["input_tokens"] + u["cache_read"] + u["cache_create"]

def run(records, budget):
    used = 0
    for r in records:
        if used + billed_input(r) > budget:      # 每轮开始前检查（用本轮实际 usage）
            return "budget", used, "第 %d 轮触发：累计 %d + 本轮 %d > %d" % (
                r["turn"], used, billed_input(r), budget)
        used += billed_input(r)
        if r["stop_reason"] == "max_tokens":     # 截断记异常，不当正常结果
            return "truncated", used, "第 %d 轮 stop_reason=max_tokens，记异常并重试" % r["turn"]
    return "ok", used, "完成 %d 轮" % len(records)

if __name__ == "__main__":
    for budget in (2000, 1500, 1200):
        outcome, used, why = run(RECORDS, budget)
        print("预算 %-5d -> %-9s 已用 %-5d %s" % (budget, outcome, used, why))
```

实跑输出：

```text
预算 2000  -> ok        已用 1999  完成 4 轮
预算 1500  -> budget    已用 1377  第 4 轮触发：累计 1377 + 本轮 622 > 1500
预算 1200  -> budget    已用 824   第 3 轮触发：累计 824 + 本轮 553 > 1200
```

**和常量版的区别有三处，都要改：**

1. **提前量用本轮实际值。** 常量版假设「每轮固定 3000」；真实 usage 版直接用**本轮响应的三项之和**判断 —— 但严格说这是「事后」的：更稳的写法是用上一轮的实际值外推本轮（多留一点余量），或者在请求前按「上轮 × 增长率」估。上面为了可复现，用了逐轮实际值直接判。
2. **缓存命中不减免预算判断。** `cache_read` 便宜但**不是免费**，而且它同样占总输入——累计口径必须三项相加（上面 `billed_input` 就是干这个）。只读 `input_tokens` 会让命中轮次看起来「没花钱」，闸门永远不触发。
3. **`max_tokens` 单独记一类。** 它不是「预算超限」，而是「输出预算不够」—— 动作不同（重试/加预算），所以状态要分开，不能混进 `budget`。

## 超限和熔断都要有告警出口

L90 说「如果这个停止没有告警，你不会知道有多少任务被截断了」。落成两个计数器和一条规则：

- `agent_budget_exceeded_total{task_kind}` —— 被预算截断的任务数。它的**变化率**比绝对值有用：突然上升通常意味着某条路径变长或进了循环。
- `agent_truncated_total{model}` —— `stop_reason=max_tokens` 的次数。它和上一个分开，因为含义不同（输出预算 vs 任务预算）。
- 规则：**任一指标的周同比翻倍就告警**，而不是等绝对阈值。原因是预算上限本身可能被调过，绝对数失去了可比性。

**失败形态：** 只在日志里打一行「budget exceeded」。它不聚合、不告警，等于没有 —— 直到账单出来才发现某一类任务被反复截断了一整个月。

## 常见坑

- **只设单次调用的 `max_tokens`。** agent 累计 30 轮后单看每轮都正常，加起来是 30 倍。
- **事后统计代替事前检查。** 事后能告诉你花了多少，但拦不住第三次。
- **超预算时直接报错。** 应该返回已经完成的部分 —— 那部分往往已经能用了。
- **把预算和熔断混为一谈。** 前者防成本，后者防"坏太多次"；触发条件和作用范围都不同。
- **上限拍脑袋定。** 应该先测量，再设成 P99 的 2 到 3 倍 —— 上限的作用是拦异常，不是拦正常长尾。
- **降级路径从不测试。** 它只在异常时执行，是最容易腐烂的代码 —— 要定期强制触发一次。
