第 9 章给过四道闸门（活动范围、预算、熔断、不可逆确认）。这一节把「预算」和「熔断」这两道讲透。它们保护不同的边界：预算限制某个范围内可消耗的资源；熔断器在某个依赖持续异常时暂时停止向它发请求。两者都需要显式指标、状态与恢复策略。超预算可能由应用主动拦截，也可能由 provider 返回错误；告警是否会停止流量，取决于具体产品配置。

## 三个层次

预算要按作用范围和资源维度分别设。下面是常见的三个范围，不是每种 API 都会替你实现这些限制：

| 层次 | 计量单位 | 超限时做什么 |
|---|---|---|
| **单次模型调用** | 输入量、输出上限、请求 deadline | 预估/计数输入，设置 provider-specific 输出上限与 timeout；响应后核对 usage |
| **单次任务** | 该 run 的预计费用、token、调用/步骤数、总时长 | 请求前预留资源；响应后按 usage 对账；余量不足时不再启动下一步 |
| **用户/租户/项目/系统时间窗** | 一段时间内的配额、并发、费用 | admission、限流、告警或硬限额；具体作用范围、重置周期与强制行为按平台配置确认 |

对自建 agent loop，任务级累计预算通常需要由宿主应用实现；托管 runtime 可能提供限制，但要核实它覆盖的是费用、token、步骤还是时间。`max_tokens` 通常限制模型生成的输出，不等于请求总 token、整个任务预算或美元费用上限；超时也不保证远端已停止处理或不会计费。

如果每轮输入都固定为 3000 token，30 轮累计输入是 9 万 token，随轮数线性增长。只有在「每轮新增 3000 token，且每次请求都重发不断增长的完整上下文」这个简化假设下，各轮输入才是 3000、6000、……、90000，总和为 1,395,000 token，呈二次增长。缓存、服务端会话、摘要、工具结果和多模态输入会改变实际轨迹；应按目标 provider 的 response usage 和计价字段核对。

## 为什么必须在循环里检查，而不是只做事后统计

事后统计不能撤回已经发出的请求或已产生的费用。要在下一次调用前决定是否继续，必须先做资源预留或可解释的保守估算。

任务预算的硬闸门应在循环里、每次请求前执行。先估算当前请求会消耗的资源并预留；响应后以 provider-specific usage 对账，返还未用预留或记录超出。若无法得到可靠估算、usage 缺失或请求超时而结果未知，应按预先定义的保守策略处理，不能假设成本为零。示意判据：

```text
预留后预计任务费用 > 任务硬上限 → 不发起本次请求
完成步骤数 >= max_steps         → 结束任务
当前时间 >= task_deadline       → 不再启动新步骤，按任务契约收口
依赖在熔断器 OPEN 状态          → 不请求该依赖，执行已审查的 fallback 或失败
```

预算耗尽后的行为取决于任务契约：对允许部分完成的只读任务，可以返回带 `incomplete` 状态和缺失项说明的进度；要求原子一致、授权或完整结构的任务，应明确失败/待处理，不能把部分结果伪装成成功。已有外部副作用也不能因超限而假设已回滚。

## 熔断：和预算不同的一个机制

预算管的是「资源上限」，熔断器管的是「一个依赖当前是否值得继续请求」。熔断器通常跟踪特定下游的超时/可重试故障，进入 `OPEN` 后在冷却期快速失败，再通过受限的 `HALF_OPEN` 探测是否恢复；它不是对所有模型错误、任务失败或内容拒绝的通用处理器：

| 维度 | 任务预算 | 依赖熔断器 |
|---|---|---|
| 触发 | 该任务预计/实际资源达到任务策略 | 特定依赖在观察窗口内出现足够多的可熔断故障 |
| 作用范围 | 当前 run，或明确配置的用户/租户配额 | 被跟踪的依赖、模型/区域或路由；其他健康依赖不应一并停用 |
| 动作 | 不再预留/启动下一步；按任务契约返回 incomplete 或失败 | `OPEN` 时对该依赖快速失败或走已审查的 fallback，避免继续放大故障 |
| 恢复 | 新任务按新预算开始；时间窗配额按定义重置 | 冷却后只放行有限探测；成功关闭，失败重新打开 |

熔断器的目的，是在网络超时、上游不可用或持续高延迟时保护依赖和调用方；AWS 的模式说明了失败阈值、快速失败与周期性恢复探测的关系。它不等于 agent 的「无进展检测」：反复调用同一工具但服务健康时，应由任务步数/时间预算、重复动作检测或状态机不变量处理；模型拒答、参数错误、业务校验失败也不应自动计入上游熔断。阈值、观察窗、冷却、探测并发和跨进程共享状态都需要按依赖与流量设计。

## 降级：熔断之后的动作

熔断后的 fallback 要按任务契约和数据新鲜度选，不存在通用的用户体验排序：

**使用备用模型。** 只有当它经过同一任务验收、结构校验和安全约束，并且备用路由自身健康/有配额时才可用；更便宜不代表能完成相同工作。

**使用缓存或预置答案。** 仅当数据仍新鲜、任务允许陈旧结果、权限检查仍执行时可用；需要明确标注时间与来源。

**安全地拒绝或返回 incomplete。** 没有通过验证的备用路径时，明确说明依赖不可用以及哪些步骤未完成。

选择条件至少包括任务影响、备用结果质量、权限与新鲜度要求、剩余预算、恢复时限和用户可接受的状态。把 fallback 及禁止 fallback 的场景预先定义并测试。

## 如何设定任务预算

预算上限设多少？不能用分位数倍数直接决定。先按任务类型/风险/租户测量资源分布，再由产品定义可接受的质量、费用与截止时间；据此设每任务硬上限，并把 P95/P99 用作异常检测或容量观察信号，而不是默认 hard cap。

步骤是：在安全的额度内先记录按任务类型分层的完整 usage、费用估算、调用数、成功/不完整率和耗时；检查样本量、季节性与异常流量；再由业务负责人确定可接受的单任务最大花费/时长，由工程把它转换成请求前预留和任务硬闸门。分位数能描述历史分布，却不能说明某个长尾在业务上可接受，也不能拦住新故障路径。

同时记录上限的负责人、适用任务/租户、计量口径、版本、生效时间、告警动作和回滚方式；阈值调整后要比较截断率、任务完成质量和费用，不要只为减少告警而上调硬上限。

## 一个反过来的检查

闸门也会失效 —— 静默地失效。三种常见形态：

**一、上限设了但没人看。** 超限时只是停止任务，而如果这个停止没有告警，你不会知道有多少任务被截断了。

**二、熔断统计口径不对。** 把业务拒绝、无效参数、超预算或所有 endpoint 的失败混成一个计数器，可能会误伤健康依赖；阈值和时间窗应基于被保护依赖的真实故障信号设计。

**三、降级路径从未被测试。** 熔断真的发生时才发现降级逻辑本身有 bug。

第三种最危险，因为降级逻辑平时可能跑不到。做法是在隔离的测试环境通过故障注入验证 `OPEN → HALF_OPEN → CLOSED`、失败重开、取消/超时和 fallback 的契约；不要为了测试而改生产阈值，也不要让测试流量触发真实副作用。


## 输出上限、任务预算与 `stop_reason`

请求级输出上限里有一个容易被忽略的坑：**思考型模型的输出预算**。

`max_tokens`/`max_output_tokens` 的含义依 endpoint 而异，通常约束本次生成上限，不是输入或整项任务的费用上限。Anthropic Messages API 将 `stop_reason: max_tokens` 定义为达到本次输出上限；思考 token 会计入其输出预算。它表示响应到达上限，不自动等于 API 错误或业务失败：若任务要求完整 JSON、工具参数或最终结论，应按协议校验是否完整；任务允许部分输出时，也要把状态标为 incomplete。不同兼容端点的字段与语义需单独验证。

实现上有两点：

**一，按任务输出契约设置本次生成预算并留出必要余量。** 可见文本少不代表输出 token 少；实际计费字段和思考 token 的归类依 provider/model 而异，应以响应 usage 与费率文档为准。上限太低会截断，需要考虑继续生成是否安全、是否可能重复工具调用和是否还有任务预算。

**二，响应上限与任务硬预算是两道不同的闸门。** 本次生成到达上限时，应先核对 `stop_reason`、协议结构、实际 usage 与剩余任务预算，再决定继续、整理 partial 结果或终止。请求前预留与响应后对账都要覆盖它们。

因此：**当完整性是任务成功条件时，不要把 `stop_reason: max_tokens` 当作完整成功。** 只有在 continuation 协议、幂等性、重复副作用防护、预算与 deadline 都允许时才继续生成；否则返回明确的 incomplete/失败状态，不把未校验文本传给下游工具。

## 一个组织问题：谁来决定预算上限

预算策略需要明确的责任人：产品/业务定义任务价值、风险和可接受的失败/部分完成；工程定义按 endpoint 计量、请求前预留和拒绝语义；运营负责监控、告警和变更记录。阈值应有共同 owner，不是由某一方单独拍定。

工程提供按任务分类的 usage/费用/完成率分布；业务设定单任务业务价值和可容忍风险；运营明确监控告警与额度变更流程。上限记录 owner、endpoint/模型、费率/策略版本和生效日期，定期复核。这样可以讨论具体权衡，而不是把任意 P99 倍数误当成默认答案。
## 完整可运行代码

下面代码是一个固定 token 用量的**本地教学模拟**：演示单个 run 的预算检查，以及连续依赖失败的截止逻辑。失败调用不计入模拟用量，因此它不能估算真实费用；它也不实现账户/租户配额、请求超时、半开探测、跨进程共享状态、provider usage 解析或真实降级，不能直接作为生产熔断器。

```python
"""固定 token 的本地教学模拟，不含真实 provider 计量。实跑状态：2026-10-09。"""
TOKENS_PER_TURN = 3000
BUDGET_TASK = 30000       # 单次任务预算
MAX_TURNS = 30
BREAKER_THRESHOLD = 3     # 连续失败 N 次熔断


class Breaker:
    def __init__(self):
        self.fails = 0
        self.open = False

    def record(self, ok):
        if ok:
            self.fails = 0
            return
        self.fails += 1
        if self.fails >= BREAKER_THRESHOLD:
            self.open = True


def run_task(turns_before_failure, breaker):
    used = 0
    trace = []
    for turn in range(1, MAX_TURNS + 1):
        # 闸门检查（每轮开始前）
        if used + TOKENS_PER_TURN > BUDGET_TASK:
            trace.append("第 %d 轮：预算闸门触发（已用 %d / %d）→ 返回已有结果" % (turn, used, BUDGET_TASK))
            return "budget", used, trace
        if turn > turns_before_failure:
            breaker.record(False)
            trace.append("第 %d 轮：失败（连续 %d 次）" % (turn, breaker.fails))
            if breaker.open:
                trace.append("        → 熔断打开，拒绝后续所有请求")
                return "breaker", used, trace
            continue
        breaker.record(True)
        used += TOKENS_PER_TURN
        trace.append("第 %d 轮：成功（累计 %d token）" % (turn, used))
    trace.append("完成 %d 轮" % MAX_TURNS)
    return "ok", used, trace


if __name__ == "__main__":
    print("预算 %d token / 单轮 %d token / 最大 %d 轮 / 熔断阈值 %d"
          % (BUDGET_TASK, TOKENS_PER_TURN, MAX_TURNS, BREAKER_THRESHOLD))
    print()
    for label, fail_after in [("持续成功但预算先到上限", 99), ("第 8 轮开始持续失败", 8), ("第 20 轮故障未到达：预算先到上限", 20)]:
        b = Breaker()
        outcome, used, trace = run_task(fail_after, b)
        print("  【%s】结果：%s，用了 %d token" % (label, outcome, used))
        for line in trace[-4:]:
            print("      %s" % line)
        print()
    print("=== 三个要点 ===")
    print("  1. 闸门在**每轮开始前**检查。事后统计只能告诉你花了多少。")
    print("  2. 超预算后的结果由任务契约决定：允许时返回 incomplete，否则明确失败。")
    print("  3. 熔断保护的不是成本，是上游服务和你自己（第 11 章）。")
    print()
    b = Breaker()
    run_task(8, b)
    print("  注意：本模拟在连续失败达到阈值时立即停止，不含冷却或 HALF_OPEN 探测。")

```

## 把常量换成从 usage 累加

上面那段演示里 `TOKENS_PER_TURN = 3000` 是常量，真实循环里必须从**每一轮响应的 `usage`** 累加，而且口径要和第 1 / 3 节接上：**不能把下列本地快照公式当成 provider 通用字段**：该样本的归一化输入 = `input_tokens + cache_read + cache_create`。缓存命中是否包含在总输入及其价格，均需按目标 endpoint 的 usage 与费率定义校验。

下面片段回放第 1 节保存的四条历史记录（2026-10-12），用于演示按已知行累计时会在哪条记录前停止。它只累计该快照的**归一化输入 token**，记录里的 `output_tokens` 不计入这条输入预算，所以这是一条输入预算回放，不是总 token、费用或完整任务预算。它使用**事后已知的本轮 usage**，因此不是实时请求前的预测器或可直接用于生产的预留算法。

```python
"""预算闸门：从每轮响应的 usage 累加，而不是用一个常量。"""
RECORDS = [  # 仅是该历史 DeepSeek-flash 轨迹映射到本地 schema 的快照
    {"turn": 1, "input_tokens": 341, "cache_read": 0, "cache_create": 0, "output_tokens": 129, "stop_reason": "tool_use"},
    {"turn": 2, "input_tokens": 227, "cache_read": 256, "cache_create": 0, "output_tokens": 57, "stop_reason": "tool_use"},
    {"turn": 3, "input_tokens": 169, "cache_read": 384, "cache_create": 0, "output_tokens": 56, "stop_reason": "tool_use"},
    {"turn": 4, "input_tokens": 238, "cache_read": 384, "cache_create": 0, "output_tokens": 22, "stop_reason": "end_turn"},
]
INPUT_BUDGET = 2000

def normalized_input_for_this_snapshot(u):
    # 本例按记录的本地字段求和；不能推广成所有 provider 的字段/账单公式。
    return u["input_tokens"] + u["cache_read"] + u["cache_create"]

def run(records, input_budget):
    used = 0
    for r in records:
        if used + normalized_input_for_this_snapshot(r) > input_budget:  # 用本轮已知输入 usage 做历史回放判断
            return "budget", used, "第 %d 轮触发：累计 %d + 本轮 %d > %d" % (
                r["turn"], used, normalized_input_for_this_snapshot(r), input_budget)
        used += normalized_input_for_this_snapshot(r)
        if r["stop_reason"] == "max_tokens":     # 截断记异常，不当正常结果
            return "truncated", used, "第 %d 轮 stop_reason=max_tokens，记异常并重试" % r["turn"]
    return "ok", used, "完成 %d 轮" % len(records)

if __name__ == "__main__":
    for input_budget in (2000, 1500, 1200):
        outcome, used, why = run(RECORDS, input_budget)
        print("归一化输入预算 %-5d -> %-9s 已用输入 %-5d %s" % (input_budget, outcome, used, why))
```

实跑输出：

```text
归一化输入预算 2000  -> ok        已用输入 1999  完成 4 轮
归一化输入预算 1500  -> budget    已用输入 1377  第 4 轮触发：累计 1377 + 本轮 622 > 1500
归一化输入预算 1200  -> budget    已用输入 824   第 3 轮触发：累计 824 + 本轮 553 > 1200
```

**这段历史回放只能说明三个口径问题，不能构成真正的请求前闸门：**

1. **本轮实际 usage 是响应后才知道的。** 实时系统应在请求前用 provider token-count/输入估算加输出硬上限，或根据本任务剩余预算预留最大成本；响应后再按 usage 对账。上一轮值外推只是估算，不能提供硬上限保证。
2. **这条示例只限输入 token 预算。** `output_tokens` 虽然保存在记录中，但未参与本次累计；真实任务预算要把输入、输出、缓存等 usage 按目标 provider 的计量与费率分别核算，不能把这个输入预算结果当作总 token 或费用上限。输出 token 与美元费用需分别纳入任务预算。
3. **缓存 token 不能按一个通用价格处理。** Anthropic 把 cache-read/write 分列，DeepSeek Chat API 把 prompt tokens 拆为 cache-hit/miss；计量字段、是否包含于总量以及费率均按 provider/model/endpoint 文档实现 adapter。预算最好同时保留原始 usage、归一化资源量和按生效费率估算的成本，不能把这个历史 snapshot 的字段公式套给其它接口。
4. **`max_tokens`/`max_output_tokens` 与任务预算分开记录。** 前者是 request-level 输出上限；后者要覆盖多个请求的费用/资源预留。达到输出上限时按 `stop_reason` 与任务完整性契约处理，而不是自动记作账户熔断。

生产宿主的请求前路径可以概括为：`authenticate → classify task → estimate input and reserve worst-case request cost → check deadline/step/quota → call → parse complete provider response → reconcile actual usage → update task budget → decide whether another call is admissible`。若 provider 不返回可靠 usage、请求超时导致执行结果未知，应保守保留额度直到 reconciliation policy 处理，不能将 unknown 当 zero。

## 超限和熔断都要有告警出口

监控要能区分预算拒绝、输出截断、任务不完整和依赖熔断，并带上分母。建议按低基数维度（任务类型、provider/model、错误类别）记录：

- `agent_budget_reservation_rejected_total` 与请求总数：请求前预留被拒绝的比例。
- `agent_task_incomplete_total` 与任务总数：按原因区分预算耗尽、deadline、输出截断和依赖不可用。
- `agent_provider_usage_unknown_total`：请求结果或 usage 未知，需触发对账策略，不能当作零费用。
- `agent_circuit_state` 与状态转换计数：按被保护依赖观察 OPEN、HALF_OPEN、CLOSED 的持续时间和转换。

以任务类型和版本分层观察完成率、质量、费用与延迟，并设置业务批准的 SLO/硬上限告警。短时变化率可以作为信号，但需检查样本量、流量变化、阈值变更与季节性；避免用固定「同比翻倍」规则，也不要把 user_id、task_id 等高基数标识放进 metrics label。

**失败形态：** 只在日志里打一行「budget exceeded」。它不聚合、不告警，等于没有 —— 直到账单出来才发现某一类任务被反复截断了一整个月。

## 常见坑

- **只设单次调用的 `max_tokens`。** 它是本次生成上限，不是多轮任务费用上限；固定输入的多轮总量与不断增长上下文的总量也不同。
- **事后统计代替事前检查。** 事后 usage 只能用于结算与校准；下一次调用前需要估算或预留。
- **所有超预算任务都返回 partial。** 只有任务契约允许、结果明确标成 incomplete 且不存在原子性/权限问题时才能返回部分结果。
- **把预算和熔断混为一谈。** 预算限制资源；熔断器隔离特定依赖的持续故障；无进展循环应由任务预算或重复动作检测处理。
- **用固定分位数倍数拍预算。** P95/P99 可描述历史或触发调查，硬上限仍要基于任务价值、风险、质量、费用和截止时间确定。
- **降级路径从不测试。** 需验证 fallback 的质量、权限、新鲜度与状态语义，并演练故障恢复路径。
