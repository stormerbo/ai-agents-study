前两节讲的是「少花」和「快花」。这一节讲另一条路：**把不同难度的请求分给不同成本的模型。**

## 分级路由的基本形态

一句话概括：**简单的请求用便宜模型，难的请求用强模型。** 而它的全部难点在**怎么判断哪个是哪个**。

三种判断方式，可靠性差别很大：

| 判据 | 例子 | 可靠性 |
|---|---|---|
| **规则** | 输入长度、有没有工具调用、是不是结构化输出 | 高（确定） |
| **分类器** | 用一个小模型判断难度 | 中（要评估） |
| **模型自评** | 让模型自己说「这题难不难」 | 低（第 2 章实测过 self-eval 的边界） |

第一种最值得先做。因为它**确定、便宜、可解释** —— 而且它已经能覆盖很多场景。

## 几条可以立刻用的规则

**按输入长度分流。** 短请求（比如 1000 token 以内）用便宜模型。依据是第 2 节那个结论：短请求的延迟由固定开销主导，用强模型换不到多少速度，却贵得多。

**按有无工具调用分流。** 第 4 章实测过工具调用的可靠性差异 —— 需要精确参数的任务用强模型，纯文本生成用便宜模型。

**按输出结构分流。** 要严格 JSON（第 5 章）的任务用强模型，因为格式失败的重试成本会吃掉省下的钱。

**按步骤位置分流。** 在 agent 里，**规划步骤用强模型，执行步骤用便宜模型**。理由是规划错了整条路都错（第 10 章实测过静态计划在分支任务上 0/3），而执行步骤大多是有明确参数的机械动作。

最后一条在 agent 里价值最高 —— 因为它**不增加一次额外的模型调用**就能分流，而分类器方案要。

## 一个反直觉的成本算术

分级路由的收益看起来是「贵模型和便宜模型的价差」，但实际收益**没有那么大**，原因有两个。

**第一，输入每轮都重发（第 1 节）。** 如果按步骤位置分流，那么「贵的部分」只在第一步。「降价」只作用在一小段输入上。

**第二，分流本身的成本。** 如果用分类器，那是一次额外调用；而它要读的内容可能和原请求一样长，于是分类的成本可能接近被省下的钱。

所以一个实用的判据是：**只有当「贵模型」和「便宜模型」的成本差距足够大（比如 5 倍以上），且分流判据足够确定（规则而非分类器）时，分级路由才划算。**

这两条同时成立才做。而它们经常不同时成立。

## 三种路由策略的对比

| 策略 | 做法 | 什么时候合适 |
|---|---|---|
| **静态路由** | 按规则一次性决定 | 任务同质、规则明确 |
| **级联** | 先用便宜模型，不满意再升级 | 有可靠的「不满意」判据 |
| **并行** | 两个都跑，选好的 | 延迟不敏感、质量关键 |

第二种值得展开。它的形态是：便宜模型先答，然后用代码或小模型判断答案够不够好，不够再调强模型。

它节省的前提是「大部分请求便宜模型就够了」。**如果升级率超过一半，它比直接用强模型更贵** —— 因为失败的那一半付了两次钱。

所以级联必须**监控升级率**。这个数字超过 50% 就说明分流点选错了。

第三种（并行）看起来最浪费，但它有它的场景：**当错误代价远高于两次调用成本时**。第 2 章测过 self-consistency 在唯一答案题上零分歧 —— 那种情况下并行纯属浪费；但在主观任务上，两个答案让人选往往比一个答案更可靠。

## 一个容易被忽略的替代方案

在考虑分级路由之前，先问两个更基础的问题：

**一、这个请求真的需要模型吗？** 第 9 章实测过一个直接对照：同一件事创建用户，走 API 工具调用 384 token，走界面循环 5528 token —— **14.4 倍**。很多「agent 任务」其实是一个函数调用。

**二、输出能不能更短？** 第 2 节实测：输出每减 180 token 省 1 秒。让模型「只输出结论，不要解释」往往比换模型省得更多。

这两个问题的共同点是：**它们都指向「把工作从模型那里拿回来」，而不是「换个更便宜的模型」。** 而它们的收益常常比分级路由大。


## 一个可以照着抄的分流顺序

把上面几条规则排成一个决策顺序，从最便宜、最确定的判据开始：

```text
1. 这个请求需要模型吗？        → 不需要就直接用代码做（第 9 章实测差 14.4 倍）
2. 能改成结构化输出吗？        → 能就缩短输出（每减 180 token 省 1 秒）
3. 是 agent 的规划步骤吗？     → 是就用强模型
4. 需要严格 JSON 吗？          → 需要就用强模型（重试成本会吃掉省下的钱）
5. 输入很短且无工具吗？        → 是就用便宜模型
6. 以上都不适用                → 用强模型（默认保守）
```

六步的顺序有讲究：**前三步都是「不增加任何额外调用就能省」**，而它们往往比第 6 步那个「换模型」省得更多。

第 6 步的默认值是「用强模型」而不是「用便宜模型」，这一点值得说：**分流的收益是省钱，分流的风险是质量下降。** 当判据不明确时，保守是对的 —— 因为质量下降带来的返工成本，往往比省下的钱多。

## 一个容易忽略的维度：路由的一致性

分级路由有一个副作用，它在成本报表上看不出来：**同一个问题，因为分流判据的边界，可能得到不同的质量。**

具体形态是：一个请求落在规则边界附近，有时被分给强模型、有时被分给便宜模型。用户会感觉「这个功能时好时坏」—— 而它既不是模型的问题，也不是提示词的问题，是**路由的抖动**。

三种缓解方式：

**一，判据要稳定。** 用「输入 token 数大于 1000」这种确定量，而不是「看起来复杂」这种需要判断的量。后者会让同一请求在不同时间走不同路径。

**二，边界要有缓冲区。** 如果一个请求刚好在阈值附近，宁可升到强模型 —— 因为「时好时坏」的用户体验比「一直慢一点」更糟。

**三，把路由决策记进追踪。** 第 15 节那套轨迹里加上「走了哪条路」字段。否则你排查「这次回答质量差」时，根本不知道它当时用的哪个模型。

第三条和前面的成本标签是同一件事：**路由的效果要能被归因，否则它只是一个说不清的变量。**

## 一个具体的数字：规则路由能省多少

上面的判据可以用一组相对单价算清楚。假设强模型的输入单价是便宜模型的 5 倍、输出是 20 倍，1000 个请求里 20% 是难题：

```text
全部用强模型                     18,000,000  （便宜模型的 7.5 倍）
全部用便宜模型                    2,400,000  （便宜模型的 1.0 倍）
规则路由（难→强，易→便宜）          5,520,000  （便宜模型的 2.3 倍）
级联，升级率 20%                  6,300,000  （便宜模型的 2.6 倍）
级联，升级率 60%                 13,500,000  （便宜模型的 5.6 倍）
并行（两个都跑）                   20,400,000  （便宜模型的 8.5 倍）
```

（本地计算，2026-10-09。）

三个读数：

**规则路由省下 69%**（相对全用强模型），而且**不花任何额外调用**。

**级联反而比规则路由贵** —— 即使升级率只有 20%。因为它给每个请求都加了判定开销，而判定本身要读内容。

**升级率 60% 时级联几乎失去意义**（只比全用强模型省 25%），因为升级的那部分付了两次钱。

而规则路由的收益有上限：**它等于难题占比。**

```text
难题占比  5% → 相对全用强模型省 82%
难题占比 20% → 省 69%
难题占比 50% → 省 43%
难题占比 90% → 省 9%
```

最后一行是这条路的边界：**如果九成请求都是难题，分流就没有意义了** —— 那时该优化的是任务本身（能不能拆小、能不能换成代码做），而不是换模型。
## 完整可运行代码

下面这段代码实现三种路由策略，并用同一批请求对比它们的总成本 —— 包括级联的升级率对成本的影响。

```python
"""三种路由策略的成本对比。纯本地。实跑状态：2026-10-09。"""
CHEAP_IN, CHEAP_OUT = 1.0, 1.0        # 相对单价
STRONG_IN, STRONG_OUT = 5.0, 20.0     # 强模型贵 5 / 20 倍
REQ_IN, REQ_OUT = 2000, 400


def cost(use_strong, extra_in=0):
    i = REQ_IN + extra_in
    if use_strong:
        return i * STRONG_IN + REQ_OUT * STRONG_OUT
    return i * CHEAP_IN + REQ_OUT * CHEAP_OUT


def static_all_strong(n):   return n * cost(True)
def static_all_cheap(n):    return n * cost(False)
def rule_based(n, hard_ratio):
    hard = int(n * hard_ratio)
    return hard * cost(True) + (n - hard) * cost(False)
def cascade(n, escalate_ratio, judge_in=300):
    # 便宜模型先答（所有请求）+ 判定开销 + 升级的那部分再用强模型
    base = n * (cost(False) + judge_in * CHEAP_IN)
    return base + int(n * escalate_ratio) * cost(True)
def parallel(n):
    return n * (cost(False) + cost(True))


if __name__ == "__main__":
    N, HARD = 1000, 0.2
    print("1000 个请求，其中 20%% 是难题（相对单价，便宜模型为 1）")
    print()
    rows = [
        ("全部用强模型", static_all_strong(N)),
        ("全部用便宜模型", static_all_cheap(N)),
        ("规则路由（难→强，易→便宜）", rule_based(N, HARD)),
        ("级联，升级率 20%", cascade(N, 0.20)),
        ("级联，升级率 60%", cascade(N, 0.60)),
        ("并行（两个都跑）", parallel(N)),
    ]
    base = rows[1][1]
    for label, c in rows:
        print("  %-28s %12.0f  （便宜模型的 %.1f 倍）" % (label, c, c / base))
    print()
    print("=== 读法 ===")
    print("  级联在升级率 20%% 时比规则路由更贵（多付了判定开销 300 token/次），")
    print("  在升级率 60%% 时进一步恶化 —— 因为升级的那部分等于付了两次钱。")
    print("  而规则路由不花任何额外调用，所以它是最便宜的有效方案。")
    print()
    print("  规则路由的收益上限 = 难题占比。占比越低，收益越大。")
    for h in (0.05, 0.2, 0.5, 0.9):
        print("    难题占比 %2.0f%% → 相对全用强模型省 %.0f%%" %
              (h * 100, (1 - rule_based(N, h) / static_all_strong(N)) * 100))
```

## 常见坑

- **用模型自评当分流判据。** 第 2 章实测过 self-eval 的边界，它不比自己生成更可靠。
- **用分类器分流却没算分类本身的成本。** 它读的内容可能和原请求一样长。
- **级联不监控升级率。** 超过 50% 就比直接用强模型更贵 —— 失败的那一半付了两次钱。
- **只在「换模型」上想办法。** 先问「这个请求真的需要模型吗」，第 9 章实测过 14.4 倍的差别。
- **忘了输入每轮重发。** 按步骤位置分流时，「贵的部分」只作用在一小段输入上。
- **分流规则不固定。** 规则要能解释、能 review —— 否则出问题时无法归因。
