模型路由，是在任务满足质量、延迟、安全与能力约束的前提下，为一次调用选择可用模型或执行路径。它可能降低成本，也可能引入分类错误、额外调用、兼容问题和新的故障点。**目标不是让简单请求一律走便宜模型，而是找出在你的任务分布上满足要求的最低成本策略。**

不同模型的能力、价格、时延、上下文、工具和模态支持会变化，reasoning effort 等同模型配置也可能是一个可选决策维度。当前价格和产品能力应查供应商对应的官方页面；本节中的价格倍率是为了复算的构造参数，不代表任何具体模型或当前报价。

## 先定义路由要满足什么

把每个候选路线当作一项架构策略，而不是“难题用强模型”的口号。先建立离线评估集，再对目标任务集定义：

1. **质量门槛**：完成任务需要满足哪些可判定后置条件？哪些任务需人工或领域专家评审？
2. **安全与能力约束**：该模型/endpoint 是否支持所需模态、工具、区域、数据处理配置和响应协议？哪些动作必须由服务端授权、校验或人工批准？把这些安全约束作为硬门槛。
3. **延迟约束**：任务总 P50/P95 或首个可见进度目标是什么？多轮任务要量端到端关键路径。
4. **成本口径**：比较每个成功完成任务的实际成本，计入路由器、judge、失败调用、升级调用、工具、缓存和重试；不要只比输入单价。
5. **决策边界**：遇到缺少特征、评估器不确定、模型不可用或超出能力时，走什么默认路径？是否允许拒绝、排队或人工处理？

策略可表示为约束优化：在质量与安全不低于业务门槛、延迟满足服务目标的候选中，选择每个成功任务期望成本较低的路线。一个更强的模型不等于安全控制；工具授权、金额/对象校验、幂等、人工审批等控制仍须在模型外执行。

## 路由方式与判据边界

| 方式 | 怎么运行 | 成本和质量要检查什么 | 典型失败形态 |
|---|---|---|---|
| 固定模型 | 所有请求走同一个候选 | 作为基线，按任务成功率、成本/成功任务、P95 对比 | 一个 workload 的平均值掩盖稀有高风险任务 |
| 静态规则 | 根据已知任务类型、能力约束或显式 SLA 选择候选 | 规则命中覆盖、误分代价、版本回归；规则稳定不等于规则有效 | 代理特征（例如字符数）被误当成质量标签 |
| 统计分类器/路由模型 | 从请求特征预测哪条路线更合适 | 独立留出集、校准、误升级/漏升级、路由本身费用与时延 | 训练集偏差、分布漂移、router 开销抵消收益 |
| 级联（cascade） | 先走较低成本模型，再经一个验收门决定接受或升级 | 接受门的错误、升级率、每个最终成功任务总成本 | 低估漏检成本；验收门太保守，几乎每次都升级 |
| 并行/hedged 请求 | 同时或延迟启动多个候选，再依据规则选结果 | 重复计算成本、仲裁器成本、关键路径延迟、是否重复副作用 | “先到者”质量不够，或者裁决器更贵且无法稳定比较 |

输入长度、任务来源、输出格式、结构化输出要求、显式工具需求等可以成为**稳定、可执行的分组特征**，但它们**不是质量标签**。长 prompt 不必然难，短 prompt 也可能包含高影响决策；存在工具并不意味着所有环节都需要同一个模型；JSON 约束通常先由 API schema 与应用校验处理，不能仅因要求结构化就断定必须选更强模型。若在模型调用前应用还不知道是否需要某个工具，就不能把“是否发生工具调用”当作事前路由条件。规则的确定性只说明同样的输入特征会走同一分支，不说明这个分支能维持质量。

模型对自身信心的文字判断也不是已经校准的概率。若要用 router、分类器或模型自评，先检查其在代表性留出集上的错分代价、校准与总体收益；与固定模型和简单规则基线比较。数据集、候选池、任务类型、评估标准和成本函数都会影响路由结论，研究基准的结果不能直接当成你的生产保证。

这一点也能从较新的统一基准看到。Findings ACL 2026 的 [LLMRouterBench](https://aclanthology.org/2026.findings-acl.1881/) 在 21 个数据集、33 个模型和 10 种路由基线上做统一比较；作者报告多种方法表现接近，部分方法（包括商业路由器）未能稳定优于简单基线。这个结论只适用于论文的候选池、数据集和指标，不能推出路由在你的流量上无效；它支持的工程动作是保留固定最佳候选基线，并实测路由带来的增量质量、成本和延迟。

## 逐任务评估，不按“简单/困难”猜

实施路由前建立代表性、可复用的任务评估集。给每条样本定义任务类别、正确性判据、风险级别、允许的工具与完成条件；将不同候选放在同一请求语义、相同任务约束和可比设置下评估。对会产生副作用的任务，使用隔离的测试工具、只读副本或被授权的合成数据，不要把历史请求重放到真实写操作上。

输出评分需要与业务风险匹配。能由程序证明的条件优先用程序判（schema、枚举、范围、数据库后置条件）；程序无法决定的语义质量可由盲评人工或经过对照校验的评估器判。结构正确不等于事实正确，也不等于工具真实执行或业务操作被授权。分开报告每个任务类别的成功率、拒答/失败、错路比例、每成功任务成本、P50/P95 延迟、升级率和样本数量；只看全体平均会让小而重要的失败类别消失。

从基线逐步选择：

1. 先验证哪些工作可由确定性代码完成，给模型调用建立固定模型基线。
2. 在评估集上运行备选模型和同模型不同设置，记录质量、成本与时延；计入不同 token 使用量、缓存和重试，而不是假定每个模型输出等长。
3. 按任务类型与安全级别检查各候选是否满足质量门槛和 SLA，排除能力或数据边界不合格者。
4. 在剩余候选中比较每个成功任务的成本与 P95；只有能在约定容差下维持质量的分组策略才进入 shadow 测试。
5. 小流量验证后逐步放量，固定策略版本和模型快照；遇到漂移、provider 故障或质量护栏触发时回退到明确路线或转人工。

升级阈值应反映误升级和漏升级的代价。漏升级把质量不够的结果当成功，可能产生业务损害；误升级则增加成本、延迟和故障面。关键决策的安全门槛不能通过“换更强模型”替代。对医疗、支付、授权、删除等高影响操作，模型级别是可靠性设计的一个参数，实际动作仍须按服务端策略执行对象授权、参数限制、独立确认与后置条件核验。

## 级联何时才值得

级联需要一个有依据的接受门。结构检查可发现格式错误、必需字段缺失或输出截断等**候选无效信号**，但不能自动证明答案在语义上正确。`max_tokens`、`length` 等结束状态的名称与含义依 provider 而异；adapter 应按供应商契约归一化为“完整、达到输出限制、拒绝、调用错误、结果未知”等状态。输出达到上限意味着需要按任务契约检查是否完整，不应宣称所有这种响应必然无用，也不能把 provider 错误伪装成“低质量答案”直接升级模型；provider 错误与未知结果均不得盲目升级。

只有可安全重试或继续的内容质量失败才考虑升级。拒绝要服从安全/产品策略；临时限流按 provider 的 retry-after、幂等性和截止时间处理；连接中断而结果未知时先处理结果不确定性，不能盲目重放可能产生副作用的操作。小模型 judge 或语义门也会引入一次新的错误来源，它需要有标注留出集、误接受/误拒绝测量和人工抽检；未校准的“信心分”不能拿来当通过证明。

一个简化的级联成本式是：

```text
期望每请求成本 ≈ C_cheap + C_judge + r × C_strong
```

`C_cheap` 是便宜模型首次尝试成本，`C_judge` 是接受门/评估成本，`r` 是升级率，`C_strong` 是升级调用成本。要和“始终用强模型”比较，需在**相同质量门槛**下看：

```text
r < (C_strong - C_cheap - C_judge) / C_strong
```

这只是把所有请求成本简化为固定数的盈亏平衡升级阈值。真实请求的输入/输出长度、reasoning、工具使用、缓存、失败调用和成功分母都不同，应使用每任务逐条 usage 计算。更重要的是，级联不能只满足“便宜”：接受门漏掉错误答案，成本再低也不满足目标质量。**升级率没有通用的 50% 临界线**，阈值必须由两个候选的成本、judge 成本和质量/风险结果共同算出。

## 一个可复算的构造成本例子

以下是本地演算用的**假设值，不是模型价格或线上实测**：每个任务固定消耗 2,000 输入 token 与 400 输出 token；便宜候选的相对输入、输出倍率都为 1，较贵候选分别为 5 与 20；评估器每请求成本暂按 300 个便宜模型输入单位计，且忽略其输出和网络/工具开销。共 1,000 个请求，构造其中 20% 需要高能力候选；假设规则能完美识别这些请求。这些前提是刻意简化的，生产任务不能假定等 token、完美标签或 20% 难题占比。

```text
每请求相对成本：便宜候选 2,000×1 + 400×1 = 2,400
               较贵候选 2,000×5 + 400×20 = 18,000
               评估器成本（假设）= 300

1,000 请求，20% 走较贵候选：
固定较贵模型                  18,000,000
固定便宜模型                   2,400,000
完美规则路由                   5,520,000
级联，升级率 20%               6,300,000
级联，升级率 60%              13,500,000
并行跑两候选（不含仲裁器）     20,400,000
```

这组值给出的完美规则路由成本是固定较贵候选的 30.7%，即在这个理想化组合里少 69.3%；它不表示质量相同或生产能节省同样比例。难题占比越高、候选成本比越小，可节省空间就越小；两者之间不是“收益等于难题占比”的关系。级联的 20% 升级加评估开销后高于理想规则路由，但低于固定强模型；升到 60% 时仍低于固定强模型。该设定中级联对固定强模型的盈亏平衡升级率是 85%；换一组候选成本或评估器开销，界限会改变。并行成本还未计入仲裁器，且成本表不衡量赢家是否正确。

下面脚本将上述假设显式写出，输出成本演算和盈亏平衡率。结果只证明算式与假设参数一致，不评估真实路由质量，也不证明请求数量、模型定价或任务难度分布。

实跑状态：本节两段 Python 代码都已在本地 Python 3 下执行；它们只做构造数据计算和结构校验示范，不调用模型 API。

```python
"""离线复算构造的模型路由成本，不代表任何 provider 报价。"""

REQUESTS = 1000
HARD_SHARE = 0.20
ESCALATION_SHARES = (0.20, 0.60)

INPUT_TOKENS = 2000
OUTPUT_TOKENS = 400
CHEAP_INPUT_RATE = 1.0
CHEAP_OUTPUT_RATE = 1.0
STRONG_INPUT_RATE = 5.0
STRONG_OUTPUT_RATE = 20.0
JUDGE_COST = 300.0  # 假设的相对成本单位，未计 judge 输出/网络开销


def request_cost(input_tokens, output_tokens, input_rate, output_rate):
    return input_tokens * input_rate + output_tokens * output_rate


cheap = request_cost(INPUT_TOKENS, OUTPUT_TOKENS, CHEAP_INPUT_RATE, CHEAP_OUTPUT_RATE)
strong = request_cost(INPUT_TOKENS, OUTPUT_TOKENS, STRONG_INPUT_RATE, STRONG_OUTPUT_RATE)
fixed_strong = REQUESTS * strong
fixed_cheap = REQUESTS * cheap
perfect_rule = REQUESTS * ((1 - HARD_SHARE) * cheap + HARD_SHARE * strong)

print("固定较贵模型: %.0f" % fixed_strong)
print("固定便宜模型: %.0f" % fixed_cheap)
print("完美规则路由（假设难度标签准确）: %.0f" % perfect_rule)
for rate in ESCALATION_SHARES:
    cascade = REQUESTS * (cheap + JUDGE_COST + rate * strong)
    print("级联升级率 %.0f%%: %.0f" % (rate * 100, cascade))
parallel_without_judge = REQUESTS * (cheap + strong)
break_even = (strong - cheap - JUDGE_COST) / strong
print("并行两候选（未计仲裁）: %.0f" % parallel_without_judge)
print("对比固定较贵候选的盈亏平衡升级率: %.1f%%" % (break_even * 100))
print("规则路由相对固定较贵模型的成本降幅: %.1f%%" % (
    (1 - perfect_rule / fixed_strong) * 100
))
```

**正文曾经发生的计算错误（真实勘误）**：旧文把“升级率超过 50%”写成级联一定比直接强模型贵，还把规则路由节省说成“难题占比”。按上面明确的构造值，强模型 18,000、便宜模型 2,400、评估器 300，级联盈亏平衡升级率是 `(18,000 - 2,400 - 300) / 18,000 = 85%`；升级率 60% 的成本 13,500，仍低于始终用强模型的 18,000。规则路由降幅应按 `1 - ((1-h)×C_cheap + h×C_strong)/C_strong` 算，在 `h=20%` 时为 69.3%，并不等于 20%。旧表的四舍五入读数、升级率结论与收益解释已登记勘误；这些都只是构造演算，不是历史运行实测。

## 验收门要分开验证结构与语义

代码最适合验证可判定的不变量：schema 解析、字段类型、范围、业务规则，以及确定的 provider 结束状态。适配器先把不同 provider 的返回状态映射到本地受控枚举；以下示例的 `completion_status` 是教学用的归一化字段，不是某个 SDK 的原始字段。结构检查通过后，结果仍处于 `待语义/业务验收`，不能标记为成功。若验收失败，是否修复、重新生成、升级或交给人工，要依据失败类型、是否安全重试与剩余预算决定。

```python
"""用本地结构规则检查候选输出；不调用模型，也不判断事实是否正确。"""
import json

REQUIRED = {"order_id": str, "amount": (int, float), "currency": str}
ALLOWED_CURRENCIES = {"CNY", "USD"}


def validate_payload(raw_text):
    def reject_nonstandard_constant(_value):
        raise ValueError("invalid_json_number")

    try:
        value = json.loads(raw_text, parse_constant=reject_nonstandard_constant)
    except json.JSONDecodeError:
        return False, "json_parse_failed"
    except (TypeError, ValueError) as error:
        return False, str(error)
    if not isinstance(value, dict):
        return False, "not_an_object"
    for key, expected_type in REQUIRED.items():
        if key not in value:
            return False, "missing:" + key
        actual = value[key]
        if key == "amount" and isinstance(actual, bool):
            return False, "invalid_amount_type"
        if not isinstance(actual, expected_type):
            return False, "invalid_type:" + key
    if value["amount"] <= 0:
        return False, "amount_out_of_range"
    if value["currency"] not in ALLOWED_CURRENCIES:
        return False, "currency_not_allowed"
    return True, "structure_valid_needs_business_check"


def disposition(response):
    """completion_status 由 provider adapter 按官方契约归一化。"""
    status = response.get("completion_status", "unknown")
    if status != "complete":
        # provider 错误、拒绝、截断和未知结果不是同一种升级理由。
        return "handle_status_without_blind_model_upgrade:" + status
    valid, reason = validate_payload(response.get("text", ""))
    if not valid:
        return "repair_or_escalate_if_safe:" + reason
    return "business_and_semantic_acceptance_required"


examples = [
    {"completion_status": "complete", "text": '{"order_id":"A-1","amount":40,"currency":"CNY"}'},
    {"completion_status": "complete", "text": '{"order_id":"A-1","amount":true,"currency":"CNY"}'},
    {"completion_status": "complete", "text": '{"order_id":"A-1","amount":NaN,"currency":"CNY"}'},
    {"completion_status": "output_limit", "text": '{"order_id":"A-1"'},
    {"completion_status": "provider_error", "text": ""},
]
for item in examples:
    print(disposition(item))
```

本例拒绝 Python 中把 `bool` 当作 `int` 子类的 `true` 金额，也显式拒绝 Python JSON parser 默认可能接受的 `NaN` 常量；它仍不检查订单是否存在、金额是否来自可信业务系统、用户是否有权退款，或工具是否真的执行成功。实际业务规则应在授权服务和业务事务边界验证，模型输出只作为不可信输入。schema 中的 required 字段从服务端版本读取，也就是以服务端定义的 schema 为准，不能从模型回传的 `required` 列表接受约束；否则被检查的输入会控制检查规则本身。

验收门若用另一个模型打分，先用人工标注的独立样本测量它的误接受和误拒绝；报告具体分母、任务分层和置信范围。误接受会让坏答案通过，误拒绝会增加重试、升级和成本。一个不稳定的 judge 有时会让级联比直接选更适合的固定模型更差。遇到安全拒绝、策略拒绝或不支持能力时，也不能用强模型重试来绕过策略。

## 何时考虑并行

并行调用可以降低等待时间，也可能帮助选择质量，但通常要为所有候选付费。若选择“最快返回”，你得到的是最快完成的答案，不是经过质量证明的答案；若再加 judge 或人工仲裁，时间和成本也要计入。并行适用于有明确获胜规则、请求可安全重复且额外成本可接受的工作负载。写操作通常不能在未经幂等保护的情况下复制到多个模型/工具分支；检索、只读分析也要检查速率限制和数据访问边界。

并行的端到端时间一般由各分支最长等待与裁决/汇合时间构成，成本则是所有已启动分支与裁决器成本之和。如果采用 hedged request（达到延迟阈值后才启动备用候选），成本取决于触发比例和取消是否能真正停止计费；客户端取消不保证 provider 未处理或未计费。必须由具体 API 文档和实测核实，不要把抽象并行图当成已节省成本。

## 把路由决策写进 trace

每次模型调用记录实际 `provider`、model ID/版本、路由策略版本、匹配的规则 ID、决策理由类别、路由器/评估器版本、输入输出 usage、缓存 usage、开始/结束时间、重试次数、结束状态和最终任务结果。对每个任务保留 trace/run/step 关联，让你能从用户任务追到模型请求和工具结果。原始 prompt 可能含敏感数据，不要把全文或用户隐私字段作为指标标签；用允许的特征类别、策略理由枚举与受控追踪存储。

```json
{"trace_id":"tr_example","run_id":"run_42","step_id":"step_3","route_policy":"routing-v2","route_reason":"task_class:structured_extraction","provider":"provider-a","model_id":"model-snapshot","attempt":1,"completion_status":"complete","input_tokens":553,"output_tokens":56,"latency_ms":760,"task_outcome":"awaiting_business_validation"}
```

路由一致性也要监控：同一版本策略在同样的可观测特征下应作出同一决策；但规则稳定不会让模型输出稳定。新模型快照、prompt、schema、价格、候选集合或 router 更新都要重新跑回归集。按任务类别比较误升级和漏升级，而不是只看总体比例；把结果严重性也纳入看板，避免大量低风险成功掩盖少数高影响误路由。

## 旧数字的适用边界

旧文曾用“长度少于 1,000 token”作为便宜模型分流规则，并引用本章上一节四条不可独立复现的延迟摘要。该摘要不能证明短输入更适合便宜模型，也没有提供路由任务的质量对照，所以删除固定 1,000 阈值。实际选择必须由同任务评估和质量门槛决定。

另一段旧材料提过 API 工具调用与本地界面循环的 token 比值约 14.4 倍。那组路线的工具执行边界和成功判据不同（API 臂只生成 tool-use 参数，没有执行真实工具），因此**不能作为等价任务的质量/成本对比**。可保留的工程问题是：确定性工作是否应由代码完成；重新比较时必须对齐真实执行、授权、后置条件、usage、延迟和失败状态。要不要调用模型，是任务架构问题；选哪个模型，是在可行候选中做质量-成本-时延评估，两者不能用一个历史 token 比值替代。

## 本节检查点

- 能把质量门槛、安全/能力约束、延迟目标和成本口径写成一次模型评估的输入。
- 能区分“特征易于执行”与“特征能预测任务质量”，并指出代理特征误路由的风险。
- 能用 `C_cheap`、`C_judge`、`C_strong` 和升级率推导级联盈亏平衡点，而不把 50% 当成普遍阈值。
- 能说明结构校验、provider 错误、语义质量、授权和业务成功是不同验收状态。
- 能从每成功任务成本、任务分类质量、尾延迟和安全结果判断一个路由策略是否值得放量。
