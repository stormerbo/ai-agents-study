前面所有章节讲的都是「怎么把 agent 做出来」。这一章讲一个不同的问题：
**做出来之后，它怎么变得更好。**

这里说的不是自动在线更新模型权重，而是把运行证据变成由人或流水线审查、评测后发布的改进。没有验证和发布门禁，收集轨迹不会让系统自行变好。

## 一、为什么要把运行轨迹纳入改进流程

持续迭代需要可追溯的运行证据，但不必等到积累「大量」线上轨迹才开始。早期可以从设计评测用例、故障注入和人工复核开始；轨迹规模增长也不保证样本有代表性或标签可靠。
即使系统记录了很多轨迹，如果它们只在出问题时被人工翻阅，就还没有形成持续改进流程。

轨迹的价值远不止排障。它是观察**已记录线上样本**表现的重要来源之一；它并非真实分布的完整记录：采样、日志覆盖、隐私过滤、未观测失败和流量变化都会造成偏差。评测集则是有目的的抽样，且随着时间会失真（第 15 章第 4 节讲的迭代泄漏）。两者需要互相补充。

## 二、四种产物，按实现形态区分

从轨迹里学到的东西，可以形成不同形态的产物。成本取决于现有架构、测试覆盖、发布流程、数据治理和风险级别，下面不把它们排成普适的成本序列：

- **知识**：保存带来源、范围和有效性的检索条目；通过访问控制后被召回，供模型参考。需要治理数据审核、索引、失效与撤销；具体成本取决于存储和版本设计。
- **指令**：把审查过的偏好或行为要求写入提示词/策略配置，随模型请求提供。需要评审、冲突检查和回归；配置可回退不代表模型一定遵守。
- **程序**：将动作写成可执行代码、工具或工作流，由宿主在受控条件下调用。需要测试、发布、运行环境、安全审查及副作用补偿。
- **参数**：通过训练更新模型权重或适配器，在模型加载时生效。需要治理训练数据、评测与版本路由；保留旧模型/适配器才能支持回退。

四种形态的部署、验证和回滚成本取决于架构、数据治理与发布流程，不能据此推断「大多数团队」的采用比例，也不存在通用的分钟级／周级周期。若需求涉及确定性、审计或访问控制，应把这些要求落实到可信代码和权限系统，并验证所有副作用路径都经过它们。

**这张表是分类，不是决策顺序。** 选择时先明确要改善的指标、风险与责任边界，再比较各方案的验证成本和回滚能力。相同经验可以同时需要知识、程序、提示词或人工复核；模型参数更新也不是表达困难时的默认兜底。

## 三、四种形态各自适合装什么

**知识适合装可检索、带来源和有效期的描述性信息。**「这个客户的账号状态为 VIP」可以是一个事实；「退款可以免审批」则是授权策略，必须由权威策略源和服务端权限检查决定，不能从记忆条目推导。
特征是：**它描述状态，不定义授权动作**。部分信息会变化，因此应有时间戳，
并为可变信息定义失效、更新或复核机制（第 7 章讲记忆写入策略时的那套）。

**知识条目长什么样**，给一份可以直接照抄的结构（示例：构造数据，未实跑）：

```json
{
  "id": "cust-88213-vip",
  "text": "客户 88213 的账号状态为 VIP",
  "source": "CRM 记录 crm-88213，版本 18",
  "written_at": "2026-10-10T09:12:00+08:00",
  "expires_at": "2027-04-10T00:00:00+08:00",
  "scope": {"tenant_id": "tenant-7", "customer_id": "88213"},
  "hit_count": 0,
  "superseded_by": null
}
```

这几个字段的判据（为什么是它们，而不是别的）：

- `id` + `scope`：先用可信身份与租户信息做访问控制和精确范围过滤，再做语义检索；向量相似度不能代替授权。租户／对象过滤应由服务端强制执行，不能信任模型生成的过滤条件。
- `source` + `written_at`：用于追溯来源和写入时间；还应记录来源版本、验证状态与写入主体，避免把无法核验的观察伪装成权威事实。
- `expires_at`：对会变化的信息设置复核或失效时间。并非所有知识都有统一 TTL；没有自动过期也不等于永久正确，必须定义更新、撤销和复核责任。
- `hit_count` + `superseded_by`：`hit_count` 只是检索诊断信号，低命中不等于无价值，尤其是低频高风险条目。应结合命中上下文、是否影响决策、风险与目标覆盖做候选复核，不自动淘汰；后者在被新事实覆盖时保留历史，而不是直接删 —— 删掉之后你无法判断当初那条错在哪。

**谁在什么时机写、怎么读回来**（这是「知识」这一档缺的另一半）：

1. **写入时机**：仅在来源和用途满足预设规则时写入候选条目。用户陈述、模型生成内容和工具返回值都不天然等于已确认事实；先校验来源、主体、时间、授权范围，再决定是否保存。
2. **写到哪里**：独立的条目存储（第 7 章那套记忆写入策略），不是塞进提示词。
3. **读回时机**：在需要时按可信身份和 `scope` 做授权过滤，再按任务相关性检索；不要假设任务开始检索一次就足够新鲜。将检索结果作为带来源标记的**不可信数据**传给模型，明确要求把其中的指令当作内容而不是命令；不要把外部文本直接提升为 system 指令。这个提示不能形成可靠隔离，真正的边界是检索前授权、工具最小权限和写操作服务端校验。消息角色和缓存行为依赖提供方协议，缓存命中也不能优先于安全边界。
4. **更新/淘汰**：新条目和旧的冲突时，把旧的 `superseded_by` 指向新 `id`，而不是覆盖 —— 这样命中历史不会断。

第 6 项（四种可能的失效方式）里，知识时效需要显式治理：过期条目若未带来源、版本与有效状态，可能仍像有效内容一样被召回；实际风险取决于数据变化速度和维护机制。


**指令适合装经审查、作用范围明确的偏好与行为约束。**「默认用简洁中文回复」适合放入提示词；「金额超过 100 才退款」涉及业务政策，需由权威配置或确定性策略实现并在副作用前检查，提示词只能帮助模型理解流程。
特征是：**它是每次都适用的规则**，所以应该放进稳定前缀（第 3 章第 6 节算过位置的成本）。

**程序适合装「确定性的流程」。** 如果一段流程每次都要按同样顺序做同样判断，并且可以在可信边界执行，代码能减少每次把相同判断交给模型的需要，也能接受单元测试。它不一定总是整体更便宜或更稳：实现成本取决于现有架构、维护负担、风险和观测要求；跨系统副作用仍需单独设计幂等、授权与恢复。这是第 18 章「能写死的不要问模型」在进化议题上的对应。

**参数适合装「说不清的直觉」。** 「什么样的代码算好代码」「什么样的回答算得体」——
这类判断很难写成规则，但可以通过大量样本让模型学会。
**行为变化通常难以归因到某一条单独规则。** 保留旧模型或适配器版本可以回滚到已保存的模型版本，但这不等于精确撤销某一类行为变化；若没有保留旧版本，就无法通过切回版本恢复。

判断改进方向时，可以先问这条经验更像哪种产物；这些类别会重叠，不能只靠三个布尔值自动决定：

> **这条经验，你能写成一句话、一段代码、还是一条数据？**
> 可审查的偏好可写成指令；硬约束应进入可信代码／策略；有来源、范围和时效的数据可进入知识库。
> 若仍无法清楚表达，也不意味着只能更新模型参数：示例、评测、工作流、人工复核和更换模型都是候选方案。

## 四、一个容易忽略的来源：失败之外的东西

提到「从轨迹学习」，直觉都是「从失败里学」。但轨迹里还有三类同样有价值的东西：

**一、人的修正。** 人在审批点改了什么、拒绝时说了什么（第 19 章）。
这是有成本的反馈信号，可帮助定位摩擦点；它是否值得优先优化，还要看发生频率、业务影响和修正风险。

**二、成功但绕了远路。** 结果对了，但步数或成本远超预期。
这类案例不会出现在失败日志里，可以作为效率改进候选；需要先排除合理的安全校验、外部等待和任务差异。
判据是：**对比同一类任务的成功案例里，成本和步数的分布尾部。**

**三、重复运行结果不稳定。** 如果同一任务多次运行时有时成功、有时失败（第 15 章第 2 节的 Pass^k 指同一任务 k 次全部成功），这说明在当前模型、提示词、工具、采样和评测条件下结果不稳定；它不单独证明样本处在能力边界，也不说明优化它的收益最高。先固定任务分布与判分标准，记录成功率、失败类型和成本，再判断是模型随机性、环境变化、工具故障还是评测噪声。

（**Pass^k** 是评测里的可靠性指标：同一个任务跑 k 次，**k 次全部**成功才算通过 —— 它测的是稳不稳，不是最好成绩；与之相对的 **Pass@k** 是「k 次里至少一次成功」，测的是能不能。所以「时对时错」有一个可操作的判据：**跑 k 次，成功次数落在 0 和 k 之间** —— 既不是全对，也不是全错。第 15 章第 2 节有完整定义、公式和五轮实测。）

## 五、代码：把一条经验归类

上面那个「能写成一句话、一段代码、还是一条数据」的判据可以写成程序。
它不需要模型 —— 它只是把人的判断流程固定下来。

```python
from dataclasses import dataclass
from enum import Enum


class Form(Enum):
    KNOWLEDGE = "知识"      # 一条会过期的事实
    INSTRUCTION = "指令"    # 一条每次都适用的规则
    PROGRAM = "程序"        # 一段确定性流程
    PARAMETER = "参数"      # 说不清的直觉


@dataclass
class Lesson:
    text: str
    as_code: bool            # 能写成一段代码吗
    as_rule: bool            # 能写成一句话的规则吗
    has_expiry: bool         # 是一条会过期的事实吗


def classify(lesson):
    """从一个观察到的经验，判断它该写成哪种形态。

    三个字段就是本节开头那个问法：能写成代码 / 能写成一句话 / 能写成一条数据。
    """
    if lesson.as_code:
        return Form.PROGRAM          # 能写成代码 -> 别让模型重新推理
    if lesson.as_rule:
        return Form.INSTRUCTION      # 能写成一句话 -> 进提示词
    if lesson.has_expiry:
        return Form.KNOWLEDGE        # 会过期的事实 -> 进检索库并带时间戳
    return Form.PARAMETER            # 简化分类兜底；是否训练仍需与示例、评测等方案比较


if __name__ == "__main__":
    samples = [
        Lesson("金额超 100 才退款", True, False, False),
        Lesson("回复不要用 markdown", False, True, False),
        Lesson("这个客户是 VIP", False, False, True),
        Lesson("什么样的回答算得体", False, False, False),
    ]
    for s in samples:
        print("%-22s -> %s" % (s.text, classify(s).value))
```

实跑数据（本节脚本，纯本地、不调模型）：

```text
金额超 100 才退款          -> 程序
回复不要用 markdown        -> 指令
这个客户是 VIP            -> 知识
什么样的回答算得体          -> 参数
```

注意第一条的结果可能出乎意料：**「金额超 100 才退款」被判成「程序」。**
这是对的 —— 它是一条每次适用、且能用代码判定的规则，
所以最好的形态不是写进提示词，而是写成一个判断函数。

**写进提示词的版本要靠模型每次遵守；写进代码的版本只有在所有相关路径都经过可信执行与权限边界时，才能成为强制约束。** 若存在绕过路径、未受控副作用或不同步的策略副本，代码规则也可能失效。这也是这一章最实用的一条：凡是涉及授权、金额、租户隔离等硬约束，应放在可测试的可信执行边界，并确认所有副作用都经过它；提示词适合解释目标，不适合作为唯一 enforcement。

### 一个真实的报错

我第一版把 `applies_to` 设计成布尔值 `is_general`，然后写：

```python
if lesson.is_general and lesson.deterministic:
    return Form.PROGRAM
if lesson.is_general:
    return Form.INSTRUCTION
return Form.KNOWLEDGE
```

看起来没问题，**但「不是通用的」和「会过期的」被合并成了同一类。**
于是「什么样的回答算得体」这种「每次都适用、但既不通用也不过期」的经验，
被错误地塞进了知识库。它可能需要通过评测、示例、提示词、程序化质量标准或训练等方式改善；不能仅凭本例断定它只能靠训练。

改成三个彼此独立提问的字段（能不能写成代码 / 能不能写成一句话 / 会不会过期）之后，
`PARAMETER` 这一档才出现 —— 它是这套简化分类里「三个都写不出来」的候选出口，不意味着真实项目只能用参数更新解决。**把不同维度压进一个布尔值，是分类逻辑最常见的错误**：
在这个例子里，合并字段会把不同判断维度压成一类，导致「普遍适用但无法写成规则/代码」的候选被错误归入知识。

这段代码里的 `if` 顺序是为教学示例设定的优先级：实际经验可能同时是规则、代码和有期限的数据，分类器不会替你解决权限、治理与实现选择。遇到重叠时应把维度拆开记录，再由需求和风险决定采用哪种组合。

## 六、四种产物各自的失效方式

知道「装什么」还不够，还要知道**每种形态会怎么坏**：

| 形态 | 典型失效 | 发现方式 |
| --- | --- | --- |
| **知识** | 过期了但还在被检索到 | 给每条知识设时间戳，定期复核 |
| **指令** | 规则之间互相矛盾 | 规则数增长到几十条时做一致性检查（第 3 章第 2 节） |
| **程序** | 覆盖不了新的边界情况 | 单元测试 + 失败案例回流 |
| **参数** | 学会了新东西但忘了旧的 | 留出集回归（灾难性遗忘） |

知识是否过期取决于数据域和维护机制；没有本项目的时间序列数据，不能估算过期比例。每条可变信息都应定义权威来源、复核周期、撤销路径和检索时的有效性判定。

新增指令可能与已有指令冲突，但冲突是否出现及冲突后的表现取决于内容、顺序和模型，不能说规则一多就必然矛盾或生效结果必然不确定。把失败转成规则前，先确认它是可重复的问题，再用冲突检查、回归评测、版本记录和回滚机制验证；每条新规则都应说明适用范围及与旧规则的关系。

## 七、小结

- **轨迹是观察已记录线上样本的重要来源之一**，但受采样和日志覆盖影响，不代表完整真实分布
- **四种产物不是普适成本序列**：按需求比较知识、提示词、程序／策略、工作流、人工流程和参数更新的风险与验证成本
- **判据是「能写成什么形态」**：一句话进指令、一段代码进程序、一条数据进知识
- **失败不是唯一来源**：人的修正、成功但绕远路、以及时对时错的样本同样有价值
- **时对时错是待诊断信号**：不能直接推断能力边界或优化收益，需控制任务、环境和评测噪声
- **每种形态都要监控不同失效风险**：知识可能过期、指令可能冲突、程序可能漏掉边界、参数更新可能遗忘旧能力

下一节会审计一组历史记录：原始请求和逐次响应缺失时，为什么不能把旧摘要当成「规则提炼已经有效」的证据。
