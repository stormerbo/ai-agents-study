前面所有章节讲的都是「怎么把 agent 做出来」。这一章讲一个不同的问题：
**做出来之后，它怎么变得更好。**

注意这里说的不是「你再改提示词」—— 那是人在学。这里说的是**系统自己从运行里积累**。

## 一、为什么这个问题现在才出现

因为它依赖一个前提：**大量的真实运行轨迹。**
一个刚上线的 agent 没有这个；而一个跑了一段时间的 agent 有一堆 ——
但绝大多数项目的做法是「把日志留着，出问题的时候翻一翻」。

轨迹的价值远不止排障。它是观察**已记录线上样本**表现的重要来源之一；它并非真实分布的完整记录：采样、日志覆盖、隐私过滤、未观测失败和流量变化都会造成偏差。评测集则是有目的的抽样，且随着时间会失真（第 15 章第 4 节讲的迭代泄漏）。两者需要互相补充。

## 二、四种产物，按「改动成本」排序

从轨迹里学到的东西，最终会变成四种不同形态的产物。它们的成本从低到高：

| 产物 | 形态 | 生效方式 | 成本 | 可回滚 |
| --- | --- | --- | --- | --- |
| **知识** | 检索库里的条目 | 下一次检索命中 | 低 | 容易 |
| **指令** | 提示词里的一条规则 | 下一次调用生效 | 低 | 容易 |
| **程序** | 一段可执行代码 / 工具 | 被调用时执行 | 中 | 中等 |
| **参数** | 模型权重 | 需要重新训练 | 高 | **难** |

这也解释了为什么绝大多数团队只做前两种 —— **它们的反馈周期是分钟级，
而参数更新的周期是周级**，而且回滚成本完全不对等。

**排序本身就是一条设计建议：能用前面的形态解决，就不要动后面的。**
这和第 6 章那条「塞进去 / 检索 / 微调」的顺序是同一个道理，
只是这里多了「程序」这一档。

## 三、四种形态各自适合装什么

**知识适合装「事实」。** 「这个客户的账号是 VIP」「这台机器的磁盘分区是这样」。
特征是：**它是陈述，不是动作**，而且会过期。所以它需要带时间戳，
并且要有失效机制（第 7 章讲记忆写入策略时的那套）。

**知识条目长什么样**，给一份可以直接照抄的结构（示例：构造数据，未实跑）：

```json
{
  "id": "cust-88213-vip",
  "text": "客户 88213 是 VIP，退款可以免审批",
  "source": "工单 #4471 的人工备注",
  "written_at": "2026-10-10T09:12:00+08:00",
  "expires_at": "2027-04-10T00:00:00+08:00",
  "scope": {"customer_id": "88213"},
  "hit_count": 0,
  "superseded_by": null
}
```

这几个字段的判据（为什么是它们，而不是别的）：

- `id` + `scope`：检索要能**精确命中**（按 `customer_id` 查），不能只靠向量相似 —— 相似的客户不能共用一条知识。
- `source` + `written_at`：出问题时能回到「谁在什么时候说的」。缺了它，一条错知识无法追责。
- `expires_at`：知识会过期（见本节后面那张失效表）。**没有失效时间的知识等于一个永久假设。**
- `hit_count` + `superseded_by`：前者给「这条还有用吗」提供证据（命中少且从不改变决策 → 候选淘汰）；后者在被新事实覆盖时保留历史，而不是直接删 —— 删掉之后你无法判断当初那条错在哪。

**谁在什么时机写、怎么读回来**（这是「知识」这一档缺的另一半）：

1. **写入时机**：只在一个**新事实被确认**时写（人明确说了、或工具返回了一个稳定的外部事实），不是每轮都写，也不是任务结束时批量写。
2. **写到哪里**：独立的条目存储（第 7 章那套记忆写入策略），不是塞进提示词。
3. **读回时机**：任务开始时按 `scope` 检索一次；命中就把 `text` 拼进固定的 system 段（保持前缀稳定，第 3 章第 6 节算过位置的成本）。
4. **更新/淘汰**：新条目和旧的冲突时，把旧的 `superseded_by` 指向新 `id`，而不是覆盖 —— 这样命中历史不会断。

第 6 项（四种失效方式）里「知识过期」最难发现，原因就在这里：**条目只增不减，而一条过期知识看起来和有效知识一模一样。**


**指令适合装「偏好与约束」。** 「金额超过 100 才退款」「不要用 markdown 回复」。
特征是：**它是每次都适用的规则**，所以应该放进稳定前缀（第 3 章第 6 节算过位置的成本）。

**程序适合装「确定性的流程」。** 如果一段流程每次都要按同样顺序做同样判断，
那它不该靠模型每次重新推理 —— **写成代码更便宜、更稳、也能被测试**。
这是第 18 章「能写死的不要问模型」在进化议题上的对应。

**参数适合装「说不清的直觉」。** 「什么样的代码算好代码」「什么样的回答算得体」——
这类判断很难写成规则，但可以通过大量样本让模型学会。
**代价是你无法解释它为什么变了，也无法精确回滚。**

判断该用哪种形态，有一个简单的问法：

> **这条经验，你能写成一句话、一段代码、还是一条数据？**
> 能写成一句话的进指令，能写成代码的进程序，能写成数据的进知识。
> **三个都写不出来的，才轮到参数。**

## 四、一个容易忽略的来源：失败之外的东西

提到「从轨迹学习」，直觉都是「从失败里学」。但轨迹里还有三类同样有价值的东西：

**一、人的修正。** 人在审批点改了什么、拒绝时说了什么（第 19 章）。
这是最贵的信号 —— 一个人愿意花时间改，说明这个点值得改。

**二、成功但绕了远路。** 结果对了，但步数或成本远超预期。
这类案例不会出现在失败日志里，却是最容易被优化的一类。
判据是：**对比同一类任务的成功案例里，成本和步数的分布尾部。**

**三、模型的犹豫。** 如果一个任务在多次运行里时对时错（第 15 章第 2 节的 Pass^k 指的是「同一个任务跑 k 次、k 次全部成功」这个可靠性指标），
那它就是一个**能力边界上的样本** —— 比一个稳定失败的任务更有价值，
因为后者说明「根本不会」，而前者说明「差一点」。
**差一点的地方，往往是投入产出比最高的优化点。**

（**Pass^k** 是评测里的可靠性指标：同一个任务跑 k 次，**k 次全部**成功才算通过 —— 它测的是稳不稳，不是最好成绩；与之相对的 **Pass@k** 是「k 次里至少一次成功」，测的是能不能。所以「时对时错」有一个可操作的判据：**跑 k 次，成功次数落在 0 和 k 之间** —— 既不是全对，也不是全错。第 15 章第 2 节有完整定义、公式和五轮实测。）

## 五、代码：把一条经验归类

上面那个「能写成一句话、一段代码、还是一条数据」的判据可以写成程序。
它不需要模型 —— 它只是把人的判断流程固定下来。

```python
from dataclasses import dataclass
from enum import Enum


class Form(Enum):
    KNOWLEDGE = "知识"      # 一条会过期的事实
    INSTRUCTION = "指令"    # 一条每次都适用的规则
    PROGRAM = "程序"        # 一段确定性流程
    PARAMETER = "参数"      # 说不清的直觉


@dataclass
class Lesson:
    text: str
    as_code: bool            # 能写成一段代码吗
    as_rule: bool            # 能写成一句话的规则吗
    has_expiry: bool         # 是一条会过期的事实吗


def classify(lesson):
    """从一个观察到的经验，判断它该写成哪种形态。

    三个字段就是本节开头那个问法：能写成代码 / 能写成一句话 / 能写成一条数据。
    """
    if lesson.as_code:
        return Form.PROGRAM          # 能写成代码 -> 别让模型重新推理
    if lesson.as_rule:
        return Form.INSTRUCTION      # 能写成一句话 -> 进提示词
    if lesson.has_expiry:
        return Form.KNOWLEDGE        # 会过期的事实 -> 进检索库并带时间戳
    return Form.PARAMETER            # 简化分类兜底；是否训练仍需与示例、评测等方案比较


if __name__ == "__main__":
    samples = [
        Lesson("金额超 100 才退款", True, False, False),
        Lesson("回复不要用 markdown", False, True, False),
        Lesson("这个客户是 VIP", False, False, True),
        Lesson("什么样的回答算得体", False, False, False),
    ]
    for s in samples:
        print("%-22s -> %s" % (s.text, classify(s).value))
```

实跑数据（本节脚本，纯本地、不调模型）：

```text
金额超 100 才退款          -> 程序
回复不要用 markdown        -> 指令
这个客户是 VIP            -> 知识
什么样的回答算得体          -> 参数
```

注意第一条的结果可能出乎意料：**「金额超 100 才退款」被判成「程序」。**
这是对的 —— 它是一条每次适用、且能用代码判定的规则，
所以最好的形态不是写进提示词，而是写成一个判断函数。

**写进提示词的版本要靠模型每次遵守；写进代码的版本只有在所有相关路径都经过可信执行与权限边界时，才能成为强制约束。** 若存在绕过路径、未受控副作用或不同步的策略副本，代码规则也可能失效。这也是这一章最实用的一条：凡是涉及授权、金额、租户隔离等硬约束，应放在可测试的可信执行边界，并确认所有副作用都经过它；提示词适合解释目标，不适合作为唯一 enforcement。

### 一个真实的报错

我第一版把 `applies_to` 设计成布尔值 `is_general`，然后写：

```python
if lesson.is_general and lesson.deterministic:
    return Form.PROGRAM
if lesson.is_general:
    return Form.INSTRUCTION
return Form.KNOWLEDGE
```

看起来没问题，**但「不是通用的」和「会过期的」被合并成了同一类。**
于是「什么样的回答算得体」这种「每次都适用、但既不通用也不过期」的经验，
被错误地塞进了知识库。它可能需要通过评测、示例、提示词、程序化质量标准或训练等方式改善；不能仅凭本例断定它只能靠训练。

改成三个正交的字段（能不能写成代码 / 能不能写成一句话 / 会不会过期）之后，
`PARAMETER` 这一档才出现 —— 它是这套简化分类里「三个都写不出来」的候选出口，不意味着真实项目只能用参数更新解决。**把不同维度压进一个布尔值，是分类逻辑最常见的错误**：
它不报错，只是悄悄地少了一整类。

## 六、四种产物各自的失效方式

知道「装什么」还不够，还要知道**每种形态会怎么坏**：

| 形态 | 典型失效 | 发现方式 |
| --- | --- | --- |
| **知识** | 过期了但还在被检索到 | 给每条知识设时间戳，定期复核 |
| **指令** | 规则之间互相矛盾 | 规则数增长到几十条时做一致性检查（第 3 章第 2 节） |
| **程序** | 覆盖不了新的边界情况 | 单元测试 + 失败案例回流 |
| **参数** | 学会了新东西但忘了旧的 | 留出集回归（灾难性遗忘） |

四种失效里，**「知识过期」最容易被忽略**，因为知识库通常只增不减。
一个运营了半年的 agent，检索库里可能有一半的条目描述的是已经不存在的情况 ——
而它们看起来和有效知识一模一样。

「指令互相矛盾」排第二：第 3 章第 2 节实测过，规则一多必然出现自相矛盾，
而**矛盾的两条规则哪条生效是不确定的**。从轨迹里不断追加规则，
正是在加速这个过程。所以「把失败写成规则」这件事必须有配额的 ——
**不能只加不减** —— 每加一条规则，都应该问一句「它取代了哪条旧规则」。

## 七、小结

- **轨迹是观察已记录线上样本的重要来源之一**，但受采样和日志覆盖影响，不代表完整真实分布
- **四种产物按成本排序**：知识 → 指令 → 程序 → 参数，能用前面的就别动后面的
- **判据是「能写成什么形态」**：一句话进指令、一段代码进程序、一条数据进知识
- **失败不是唯一来源**：人的修正、成功但绕远路、以及时对时错的样本同样有价值
- **时对时错比稳定失败更有价值** —— 前者说明差一点，后者说明根本不会
- **每种形态都有自己的失效方式**：知识会过期、指令会互相矛盾、程序覆盖不了新边界、参数会遗忘

下一节会用一个实测说明：**把经验写成指令这一步，并不像看起来那么有效** —— 而原因和你以为的不一样。
