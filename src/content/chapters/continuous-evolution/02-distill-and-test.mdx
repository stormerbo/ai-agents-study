上一节说「经验可以写成指令」。这一节讨论如何把失败写成候选规则，再用可复核的评测判断它有没有用。

## 一、实验设计

选一类有 8 种变体的任务：日期归一化（把各种格式转成 `YYYY-MM-DD`）。
两种提炼条件：

- **条件 A**：只给模型**1 条**样本，让它总结一条规则，再去处理其余 7 条
- **条件 B**：给模型**全部 8 条**样本，总结规则，再去处理 4 条未参与提炼的**留出输入**

同时跑一个**对照组**：不加任何规则，直接处理同样 4 条。

**8 条样本就是这 8 个**（第 1 条是条件 A 唯一能看到的那条；条件 B 看到全部 8 条）：

```text
2026年10月10日      2026/10/11        12-10-2026         Oct 13, 2026
20261014            15.10.2026        2026-10-16T08:00:00Z   2026年10月17号
```

**4 条留出输入是**（条件 B 的验收集，也是对照组的输入）：

```text
18/10/2026          2026.10.19        October 20, 2026   20261021
```

把它们逐个列出来，是为了让留出集可审查。**这 4 条只是未参与提炼的具体输入，不是 4 个全新的格式族**：`18/10/2026` 与训练样本 `15.10.2026` 同为日-月-年，只换了分隔符；`2026.10.19` 与 `2026/10/11` 同为年-月-日，只换分隔符；`20261021` 与 `20261014` 是同一紧凑格式；`October 20, 2026` 与 `Oct 13, 2026` 都是英文月份形式，仅全称/缩写不同。因此这组数据只能检查已见格式族内的具体变体，不能支持严格的格式族留出泛化结论。

**本节新建的日期解析契约**：中文年月日按字面日期解释；`DD-MM-YYYY`、`DD.MM.YYYY` 和 `DD/MM/YYYY` 均按日-月-年；`YYYY/MM/DD` 与 `YYYY.MM.DD` 按年-月-日；紧凑 8 位数字按 `YYYYMMDD`；英文月份名不区分缩写与全称；带时区的 ISO 时间戳先转换到 UTC，再输出 UTC 日历日期。没有这类显式契约时，`12-10-2026` 这样的歧义输入应要求补充 locale 或拒绝猜测。这个契约只定义当前教学用 fixture，不能反向证明历史请求采用了相同规则。


## 二、历史记录与结论边界

```text
历史正文曾记为：A 7/7、B 4/4、对照组 4/4。
现存日志记为：A 6/7，但一条“错”的可见期望值与实际值相同；B 4/4、对照组 4/4。
完整请求、响应、stop_reason、usage 与 scorer 版本：未归档
```

**现有材料不足以确认这次实验的准确率，也不足以比较规则组和对照组。** 正文的 A 7/7 与日志计数 6/7 不一致，且可见错题行的期望/实际值相同；B 与对照组虽都记录 4/4，但逐条原始响应和可靠评分材料缺失。因此不能把同分解释为测不出提升，更不能归因为基线饱和、规则未改变输出或规则质量不足。正确结论是：**这份历史记录无法独立复核，原实验效果未知。**

**注意「未知」和「没用」的区别**：当前档案让效果未知；下一轮若要测，需用可复算的 scorer 与能区分效果的任务集。基线接近天花板可能降低某些指标的区分力，但不是唯一解释，也不意味着应该把真实基线人为压到中间。**如果本节只记一句，记这句：证据链不完整时，不要把不确定性改写成模型结论。**

条件 A 的规则被历史笔记描述为**窄的**（只管中文年月日），但 A 的计数与明细冲突，不能确认其余 7 条是否全部通过，也不能由此判断模型原有能力或规则贡献。

把输入与保存下来的输出摘要放在一起看。下面是档案记录，不是经过本轮重放的模型实验；日志标记 A=6/7，却有一个可见输出与期望相同的“错”项。工作树中的脚本时间戳晚于日志，且脚本没有保存原始响应、stop reason、usage、响应 ID 和 scorer 版本：

| 条件 | 看到的样本 | 提炼出的规则（原文） | 判在什么输入上 | 结果 |
|---|---|---|---|---|
| A | 只有 `2026年10月10日` 这 1 条 | 旧日志中的规则摘要 | 其余 7 条 | 旧日志计数 6/7；一条“错”记录显示期望值等于实际值，分数不可确认 |

**这三行目前不能支持效果结论。** A 的总分与明细冲突；B 与对照组的同分只存在于缺少逐次证据的历史摘要里，无法确认它们确实按相同 scorer 判分，更不能说已测出或测不出差异。

**这张表本身就是一个自查工具**：先核对每题输入、期望、原始响应、完成状态与 scorer；再确认对照组任务确实可答且分配匹配。只有这样，对照成绩才可用于解释差异。

这份历史档案不足以确认结果，更谈不上解释原因。若重新实验，应预先固定样本、分组、提示/模型版本、完整输出保存策略和评分规则；对两组跑同一任务集，必要时重复运行，并报告逐题差异、汇总区间及失败/未完成数。

## 三、怎样设计能回答问题的评测

“基线必须在中间区间”不是通用规则。基线接近天花板时，准确率指标可能不敏感；但把生产样本人为变难会损害外部有效性。应先定义要回答的问题，再设计代表目标分布的主评测集与针对预期失效模式的压力切片：

**在很多已稳定运行的领域，失败案例可能稀少或集中在尾部。**
如果规则主要从这些失败里提炼，验证时就需要构造或收集足够多、又与目标分布相关的样本。
这是一个常见的数据挑战，但不是“从失败学习”必然遇到的唯一障碍：

- 规则是从**罕见情况**里学来的
- 而验证规则要用**大量同类任务**
- 但成功任务通常不会进入失败日志，线上日志也未必覆盖所有相关输入

**因此，你手里的失败日志可能不足以验证这条规则。** 还要检查成功流量是否可采样、标签是否可信、目标分布是否覆盖尾部，以及是否能在不泄露敏感信息的前提下保留必要证据。

这说明工程难点常常落在数据与评测设计上；规则归因、上线治理和外部有效性同样需要单独处理。

实践中可考虑的几种路径（不是穷尽清单）：

**一、构造压力切片。** 针对规则声称解决的失效模式构造定向样例，并单独报告该切片；同时保留代表目标分布的样本。更难的合成题不自动代表真实流量，也不应为了得到更好看的差异而人为把生产基线“压到中间区间”。

**二、先做副作用回归。** 除了目标失效切片，还检查规则有没有让原本通过的用例变差。既有用例只有在仍代表目标任务、标签可信时才算充足；回归通过也只能说明当前覆盖范围内没有发现退步。

**三、分阶段观察。** 低风险规则可以先影子运行或小流量灰度，再决定是否扩大；观察命中率之外，还要定义结果指标、对照/分流方式、停止条件和回滚条件。仅记录“命中后成功”是相关性观察，不能单独说明规则造成了改善。

## 四、一次无法复核的历史记录：不能确认两个「假发现」

旧笔记把第一版实验描述成两个看起来很漂亮的结论：

```text
（错误的第一版结果）
条件 A：处理 7 条，1 条失败 —— 「12-10-2026」没转对
条件 B：提炼出的规则是空的 —— 所以「规则没带来提升」
```

当时的解释是两处都由 `max_tokens` 太小造成。但现在能找到的归档不足以验证这条因果解释，也不能把那两个现象当成已确认的模型行为。

先把这两个词说清，因为它们是这一节的诚信落点：

- **`max_tokens`** 是请求的生成上限；对 Anthropic Messages API，启用 extended thinking 时 thinking token 也计入该上限，具体行为需按 provider、模型和 API 版本确认。
- **`stop_reason`** 是响应字段，描述这次为何结束。Anthropic Messages API 当前列出的状态包括 `end_turn`、`max_tokens`、`stop_sequence`、`tool_use`、`pause_turn`、`refusal` 与 `model_context_window_exceeded`；截断或暂停、拒绝、工具调用不能混作同一类。启用 thinking 时，当前轮思考 token 计入 `max_tokens`；具体行为按模型和模式核对。兼容端点是否完整遵循这些语义，要核对该端点文档并检查实际响应。

保留下来的历史日志摘要（`experiments/results/exp-continuous-evolution-distill-review-20261021/historical-log.txt`）记录 A 计数为 6/7，但其中一行标为“错”，可见的期望值与实际值却都是 `2026-10-12`；计数、判分和展示值彼此冲突。该日志还只保存短输出，没有逐次原始响应、stop reason、usage、响应 ID 或 scorer 版本。审计时找到的本地脚本修改时间晚于日志，且脚本格式与日志不一致；检查摘要与源码哈希见 `experiments/results/exp-continuous-evolution-distill-review-20261021/inspected-scorer-facts.txt`。因此不能证明该脚本就是产生日志的版本。B 与对照组各记 4/4，但同样缺原始响应与完整判分记录。

更重要的是，当前脚本把 `max_tokens` 截断标记拼到输出文本上，随后仍用 `expected in out` 的子串匹配打分；如果截断前已有期望字符串，它仍可能被判通过。提炼规则的调用也没有验证 `stop_reason`。因此，仅把截断写进日志并不等于拒绝不完整样本。

所以旧笔记里“500 导致空输出、升到 3000 后修复”“A 恰为 7/7”以及“两处都是预算过小”的说法都应视为**未经独立确认的历史解释**，而不是本节实测结论。当前可下的结论是：归档计数和 scorer 不能支撑可靠的模型准确率比较；旧实验无法从现有材料重建。

Anthropic 当前文档列出 `end_turn`、`max_tokens`、`stop_sequence`、`tool_use`、`pause_turn`、`refusal` 和 `model_context_window_exceeded` 等 `stop_reason`；当前轮 thinking token 计入 `max_tokens`。这些是 Anthropic Messages API 的契约，兼容端点要按自己的文档和实测响应另行确认。

因此把这段作为**评测管线的失败案例**更准确：

> **只有在响应完整、符合任务协议且 scorer 可复算时，才把样本计入模型效果。**
> `stop_reason` 是必要诊断字段之一，不是唯一判据。

这件事和本节主题相关：如果评分器把未完成响应、解析失败或预期值错误混在一起，基础设施缺陷就会伪装成模型行为。排查时要把请求、响应状态、解析、标签和评分逐层分开。

## 五、一条规则应该怎么写成代码

「把失败写成规则」有一个很容易被忽略的技术问题：**规则写多具体。**

写太窄（「`2026年10月10日` 要转成 `2026-10-10`」）→ 只修那一例，换个日期就失效。
写太宽（「日期要归一化」）→ 模型本来就知道，等于没加。

这不是文字游戏，它有可操作的判据：**一条好规则应该覆盖一类输入，而不是一个输入**。下面用一个小型评估器检查候选规则在给定正例和反例上的表现。

```python
import re


def evaluate_candidate_rule(pattern, positive_examples, negative_examples):
    """只评估候选规则在给定样例上的行为；不会替你归纳规则。"""
    if not positive_examples or not negative_examples:
        raise ValueError("正例和反例都必须提供，避免只看覆盖率")

    regex = re.compile(pattern)
    false_negatives = [x for x in positive_examples if regex.fullmatch(x) is None]
    false_positives = [x for x in negative_examples if regex.fullmatch(x) is not None]
    return {
        "positive_coverage": (len(positive_examples) - len(false_negatives)) / len(positive_examples),
        "false_positive_rate": len(false_positives) / len(negative_examples),
        "false_negatives": false_negatives,
        "false_positives": false_positives,
    }


pattern = r"\d{4}年\d{1,2}月\d{1,2}[日号]"
result = evaluate_candidate_rule(
    pattern,
    ["2026年10月10日", "2026年10月17号"],
    ["2026/10/11", "October 13, 2026"],
)
assert result["positive_coverage"] == 1.0
assert result["false_positive_rate"] == 0.0
```

**实跑状态**：上面这段候选规则评估器已用离线正例/反例运行；本轮没有调用模型或复现旧实验。它只验证给定样例上的正例覆盖和反例误报，不证明规则质量或生产效果。

这个 helper 只对指定正反例计算覆盖率和误报率。它**不会从失败案例生成规则**，也不证明这些例子代表真实分布、标签正确或规则造成了效果。

这解决了一个实际困境：你常常不知道一条规则该写多宽。
**做法是先明确规则的适用范围，再用独立正例和反例检查覆盖率与误报** ——
覆盖率低不一定是写窄了，也可能是标签不一致或规则边界错了；**先问这些输入是否应属于同一类，以及标注是否可信**。

很多时候覆盖率低是对的 —— 那些输入本来就不该被同一条规则覆盖。
**一个规则管两件不同的事，是后面自相矛盾的源头。**

## 六、为什么「写成程序」比「写进提示词」值得优先考虑

回到第一节那个分类：**能写成代码的规则，就不该留给提示词。** 原因有四个：

**一、可以在执行边界强制。** 提示词里的规则，模型可以不遵守；代码规则只有在相关操作与副作用都经过可信 enforcement、没有旁路时，才可作为强约束。否则同一规则仍可能被绕过。

**二、可以被测试。** 一段判断逻辑能写单元测试，一条提示词规则只能靠评测通过率间接观察。

**三、执行逻辑本身不进入模型上下文。** 但工具定义、工具调用结果及传给模型的输出仍可能消耗 token；缓存是否命中由 provider 的具体缓存契约决定，不能笼统说代码不参与前缀哈希就没有上下文成本。

**四、改动是可见的。** 改代码有 diff、有 review、有发布记录；
改提示词里的一句话，很容易没人注意到。

所以一个很实用的转化动作是：**每次你往系统提示词里加一条规则，先问一句「这条能不能写成代码」。**
能写的就写代码，剩下的才进提示词 ——
**提示词里最终留下的，应该是真正需要模型判断的那部分。**

## 七、闭环的边界：什么时候「完成」不等于「进步」

最后一件事，它决定了整条闭环能不能长期运行。

闭环的形态是：**运行 → 收集 → 提炼 → 上线 → 再运行**。
它有一个隐含假设：**「这次做得对」等于「系统变好了」。**
而这两件事在三种情况下会分开：

**一、目标被改写。** 如果规则本身是错的，闭环会**高效地把错误固化下来**。
从失败里提炼的规则，质量取决于「失败原因的判断」是否正确 ——
而那个判断通常也是模型做的。**用一个可能出错的判断去生成规则，再让规则指导后续行为，
这是闭环最根本的风险。**

**二、反馈被稀释。** 如果规则只作用于少量流量，它对总体指标的影响可能被稀释；在规则命中切片上积累足够、可比较的结果，仍可评估它。能否回滚取决于是否保留版本、开关和责任流程，不能从指标是否明显直接推出。
**每条规则都需要可观测的版本与命中信号**，否则排查成本会上升；命中和结果相关联仍不能单独证明因果效果。

**三、指标被优化而目标没有。** 规则让通过率涨了，但涨的是「你测的那个通过率」，
不是用户满意度。这是第 15 章讲评测集时那个问题的长期版本：
**指标一旦被用于优化，它就开始失真。**

所以「可验证闭环的边界」这个说法值得保留：

> **闭环能优化的，只有它能观测的东西。**
> 对观测不到的部分，闭环不会保守，它会**自信地跑偏**。

实用做法是给闭环设三个闸门：**规则必须能被人读懂**（否则无法判断它是否合理）、
**必须能回滚**（否则一次坏规则就是永久的）、
**必须有独立于它的指标**（否则你在用它自己的标准评价它）。

### 命中信号记在哪、多久跑一次、怎么回滚

这三个闸门要落成具体结构才有用，否则它们只是三个形容词。

**一、命中信号记在轨迹里：一条规则的一次命中就是一条事件**（示例：构造数据，未实跑）：

```json
{
  "rule_id": "date-normalize-cn",
  "rule_version": "3",
  "evaluation_version": "date-eval-v2",
  "cohort": "shadow",
  "task_stratum": "cn-date-format",
  "triggered_at": "2026-10-12T10:03:17+08:00",
  "task_id": "task-9f21",
  "turn": 3,
  "outcome": "pass",
  "outcome_evidence_ref": "restricted://evaluation/run-abc123"
}
```

字段的判据：规则与评测版本、样本分层和 cohort 必须可区分；`task_id` + `turn` 只能回到授权保留的必要证据，避免把敏感原文放进普通日志。`outcome` 与命中关联可以帮助诊断，但受任务难度、流量选择等混杂因素影响，**不能由此断言规则带来改善**。因果评估需预先定义同一目标分布上的比较设计（例如随机分流，或同题配对回放并重复运行），保留对照、版本、评测器和不确定性；影子运行适合验证触发与兼容性，不等同于用户效果实验。

**二、触发时机：不要把固定频率当普遍答案。** 按失败量、风险、变化速度、人工审查容量和评估成本选择批次；高影响规则可以要求达到最小证据量或等待人工触发。单条失败通常不足以证明根因，也不意味着永远不能形成待验证的候选假设。

**三、一条规则从候选到受控发布的五步，每一步都有产物**：

```text
1. 筛样本    按规则可能命中的任务分层，收集失败样本与反例/回归样本
              产物：带标签、版本、来源和访问边界的候选集
2. 生成草案  让模型或工程师提出规则及适用条件，保持未生效
              产物：可审查的规则草案
3. 离线评测  用冻结的评测版本比较规则组与基线；覆盖代表性主集、目标压力切片和既有回归集
              产物：逐题结果、未完成/无效样本、分层指标与不确定性
4. 人工审批  检查适用范围、标签质量、副作用、评测结果和风险
              产物：批准/驳回记录、审批人及通过标准
5. 受控发布  通过审批后按低风险灰度或影子方式观察，并按预设停止条件扩展或回滚
              产物：带版本、曝光分母、命中与结果指标的发布记录
```

**离线评测是候选规则进入审批和发布前的门槛**：先预先写明通过标准，再用同一批任务和固定 scorer 做规则组/基线比较；把未完成、解析失败和业务不合格分别记录，不能混成普通错误或静默丢弃。代表性主集用于估计目标分布表现，压力切片用于诊断指定失效模式，回归集用于发现副作用；分层报告并给出不确定性。若评测不满足标准，产物是待修改草案或驳回记录，不是上线规则。

**这五步与后端里的 feature flag、测试和监控相对应**：第 3 步是离线验收，第 4 步是审批，第 5 步是受控发布；第 1 步的候选集也不自动等于灰度流量。影子方式可以确认触发、延迟和兼容性，不能单独证明用户效果。规则本体在提示词模板或代码里，命中事件在轨迹里，评测报告在实验档案里，审批与发布记录在变更日志里。

**四、回滚要写清楚三件事**，否则「能回滚」也只是形容词：

- **规则本体怎么撤**：从提示词/代码里删掉，或按 `rule_id` 置为 `disabled`。
- **历史命中记录怎么处理**：不删，保留并标注 `rolled_back_at` —— 删掉之后你无法复盘「它当时到底影响过多少任务」。
- **指标怎么对比**：用预先定义的匹配任务或受控 cohort 比较，报告分层结果和不确定性。单纯前后对比容易受时间趋势与流量变化影响，不能独立证明规则造成差异。

## 八、小结

- **当前档案无法确认规则的效果**：A 的计数与明细冲突，B/对照组只有不完整摘要，不能断言测法饱和
- **重新评测需同时看代表性任务与定向压力切片**；不应为了追求中间区间而人为扭曲目标分布
- **「从失败学习」有个结构性矛盾**：规则来自罕见情况，而验证要用大量同类任务
- **可补充副作用回归**，但既有用例是否充足、是否代表目标任务，也需要检查
- **旧实验的两个“假发现”不能复核**：先检查完整响应、stop reason、解析、标签与 scorer，不能把旧笔记的根因解释当成事实
- **一条好规则覆盖一类输入，不是一个输入** —— 但覆盖率低时先问「它们真的同类吗」
- **硬约束应在所有副作用路径都经过的可信边界 enforcement**：提示词可解释规则，但不能替代授权检查；程序约束仍要检查旁路
- **闭环只优化它能观测的东西** —— 观测不到的部分，它会自信地跑偏
