注入可能影响模型提出的动作，但外部请求也可能由宿主、渲染器或自动流程触发。这一节用数据可达性、请求路径和触发事件来**识别需要验证的外泄风险路径**，再按系统边界选择控制。

## 三要素：威胁建模启发式

做外泄威胁建模时，可以沿三条路径检查：**敏感数据是否可达、系统是否存在把数据送到外部的路径、以及什么事件会让这条路径被执行**。触发者可能是模型、用户、自动渲染器或其他代码，不一定是模型决定外传。三项同时存在意味着风险路径值得验证，不代表外泄必然成功或数据一定被对方收到；授权、网络策略、目标端行为和运行时错误都会影响结果。

下面的本地脚本只把三个布尔值代入预设逻辑。它没有调用模型、网络或真实权限系统，因此只证明玩具模型内部的分支行为，不能证明现实系统的必要/充分条件或控制的确定性。

## 控制放在哪

优先把控制放在可强制执行的边界：数据访问按主体和资源授权；网络请求按目的地与运行环境实施出口策略；文件、日志、错误和用户可见输出也列入数据流。提示词、输入标注和内容过滤可以降低特定样本的触发概率，但不能充当授权机制。访问控制与出口控制只有覆盖真实执行路径、身份可信且策略不可绕过时，才能阻断对应路径；代理、DNS/重定向、共享日志和替代出口都可能改变结论。

| 检查面 | 可用控制 | 需要验证的边界 |
|---|---|---|
| 触发 | 提示词、来源标注、审核与检测 | 对具体威胁样本测试，不能推成普遍成功率 |
| 数据访问 | 最小权限、对象级授权、字段投影 | 用可信主体逐请求校验，确认没有旁路 |
| 网络路径 | 默认拒绝、目的地策略、运行时出口控制 | 覆盖所有发起请求的组件，并检查 DNS、重定向与代理 |
| 其他接收方 | 文件、日志、错误、用户可见输出 | 追踪其后续同步、共享与保留策略 |

第 2 章保留的提示注入命中率是无法独立复核的历史摘要，不能用于估计攻击或防护的总体成功率。设计顺序应从威胁模型与覆盖面出发，而不是把禁网或切分 agent 当作任何场景都最有效的单一答案。

## 通道比你想的多

"通道"这个词容易让人只想到 HTTP 请求。但实际可达的通道有很多，而它们的防护方式不同：

| 通道 | 例子 | 怎么收 |
|---|---|---|
| HTTP 出站 | 工具直接请求攻击者域名 | 域名白名单 + 禁内网 |
| 邮件 | 调用发邮件工具 | 工具级审批（第 19 章） |
| URL 参数 | 把数据拼进一个图片地址 | **渲染层也要拦** —— 图片加载是浏览器发的请求 |
| 写文件 | 写进一个攻击者能读的地方 | 文件系统沙箱 |
| 错误信息 | 报错里带上数据 | 出站内容脱敏（[第 16 章《沙箱与权限》：执行策略与审计](/chapters/sandboxing/execution-policy)） |
| 日志 | 数据进了一个共享的日志系统 | 日志访问控制（[第 16 章《沙箱与权限》：执行策略与审计](/chapters/sandboxing/execution-policy)） |

第三行值得单独说（**渲染层**：把 markdown 变成可见页面、并顺带加载图片的那一层，可能在浏览器里，也可能在服务端）。**第 8 章实测过一个相关现象 —— 给模型一个 URL 图像，服务端会去下载它。** 那么反过来，如果模型能把数据编码进一个 URL，让渲染层去请求它，就是一个不走工具调用、不走 HTTP 工具的通道。**它绕过了你对"工具"的检查。**

这正是"通道要比工具清单更宽"的原因：**任何能让你的系统发起网络请求的地方，都是一个潜在通道** —— 包括图片加载、网页预览、webhook 回调。

## 一个反过来的检查：把三要素当审计清单

这套框架的实用价值在于，它可以当一份检查清单用。对自己的系统问三个问题：

**一、这个 agent 能读到的最敏感的数据是什么？** 如果答案是"生产数据库"，那么"访问"这一环就是敞开的 —— 而它本来可能是可以收窄的（[第 16 章《沙箱与权限》的最小权限](/chapters/sandboxing/least-privilege)）。

**二、它能发起的网络请求有哪些？** 注意不只是工具清单 —— 还要算上渲染层、回调、以及任何"看起来与网络无关"的组件。

**三、触发这一环，我做了哪些降低概率的措施？** 注意这里的措辞：**降低概率**，不是消除。把这一点想清楚，你就不会把提示词当成防线。

三个问题里，第二个最容易被漏。因为"通道"往往不在安全评审的视野里 —— 它可能是一行 `img src`，一个看起来无害的预览功能。


## 一个具体的判断：哪些数据本就不该让 agent 碰到

三项中，访问边界值得优先审查，但砍它需要先回答一个问题：**这份数据，这个 agent 真的需要吗？**

实际项目里经常出现的情况是：agent 需要的其实只是**数据的某个投影**，而它拿到的可能是超出任务需要的数据。

举几个具体的收窄方式：

- 需要"这个用户有没有下过单" → 给它一个返回布尔值的工具，而不是一个能查订单表的工具
- 需要"这个月的销售总额" → 给它一个返回聚合值的工具，而不是原始明细
- 需要"文档里关于退款的那一段" → 先检索出那一段再给它，而不是把整份文档塞进上下文

这三种做法的共同点是：把宽权限读取缩成用途明确的接口。精简返回能减少模型可见的数据，但是否真正只返回必要字段取决于接口实现、授权与下游处理，不能只凭函数签名保证。

这条和第 5 章那个"让代码算而不是让模型算"是同一个思路的两面：**能由你的代码确定的，就不要交给模型（或数据源）决定。**

## 上下文会增加数据处理范围

数据进入模型上下文后，可能被宿主写入轨迹或日志，也可能按所用 API 的语义在后续请求中再次发送给模型服务。具体是否保存、保留多久、谁能访问，取决于部署方式、服务商、产品/API、合同与数据保留设置；本地模型也可能完全不经过外部模型服务。不要把副本数变成 N 当作通用事实。

例如，Anthropic Messages API 的多轮对话调用是无状态的，应用需在请求中提供对话历史；这是该 API 的行为，不应推广到所有供应商或产品。服务端日志、追踪平台和保留策略则应逐项核对实际配置。工程上仍可采用数据最小化：避免把任务不需要的敏感字段放入上下文，并检查轨迹、错误和供应商处理边界。

## 完整可运行代码

下面脚本用预设布尔值演示一个简化模型的分支；它不调用模型、权限系统或网络，不能证明现实系统中的控制可靠性。

```python
"""数据外泄的三要素：访问、通道、触发。

脚本把访问、通道和触发表示为布尔值并预设成功条件；这只是教学用简化模型，不覆盖现实系统中的其他授权与传输条件。
纯本地（用模拟的读写动作，不依赖外部服务）—— 要测的是**机制**，不是模型。
实跑状态：2026-10-09。
"""

# 所有值均为合成占位数据，不对应真实个人或客户记录。
SECRET = "合成客户记录：phone=PHONE_SYNTHETIC / name=PERSON_SYNTHETIC / balance=12800"


def try_exfiltrate(has_access, has_channel, has_trigger):
    """返回 (是否成功外泄, 卡在哪一步)。"""
    log = []
    # 触发：模型有没有去拿这份数据
    if not has_trigger:
        log.append("模型没有去读这份数据（没有触发）")
        return False, "触发", log
    log.append("① 触发：模型决定读取客户表")
    # 访问：它够不够得着
    if not has_access:
        log.append("读客户表 → 权限拒绝")
        return False, "访问", log
    log.append("② 访问：读到了「%s」" % SECRET[:12] + "…")
    # 通道：它能不能送出去
    if not has_channel:
        log.append("尝试外发 → 出站被禁（无可用通道）")
        return False, "通道", log
    log.append("③ 通道：通过 HTTP 发往 attacker.example.com")
    return True, None, log


CASES = [
    ("什么都不做", False, False, False),
    ("只给通道（没有数据）", False, True, True),
    ("只给访问（没有出口）", True, False, True),
    ("访问 + 通道，但模型不去读", True, True, False),
    ("三要素齐全", True, True, True),
]

if __name__ == "__main__":
    print("简化模型：访问、通道和触发均为真时返回成功")
    print()
    for label, acc, ch, tr in CASES:
        ok, stuck, log = try_exfiltrate(acc, ch, tr)
        verdict = "⚠️ 玩具模型判定成功" if ok else "✅ 被拦住（卡在：%s）" % stuck
        print("  %-24s %s" % (label, verdict))
        for line in log:
            print("      %s" % line)
        print()
    print("=== 防护的对应关系 ===")
    print("  控制「触发」—— 取决于触发来源；若由模型判断，只能针对样本降低发生概率：")
    print("             提示词、输入标注、内容过滤。缓解效果取决于具体威胁样本，需在目标系统中单独验证。")
    print("  访问控制可限制特定数据路径；需验证身份、资源授权和旁路覆盖。")
    print("  出口策略可限制覆盖范围内的网络路径；需检查重定向、代理和其他接收方。")
    print()
    print("  关键结论：这只是玩具逻辑；真实系统需测试控制覆盖与绕过路径。")
    print("  防护重点：用可执行策略约束实际数据访问和接收路径，并测试其覆盖范围。")
```

## 渲染层与服务端取图是两种边界

如果浏览器会直接加载不可信 Markdown 中的图片，CSP 的 img-src 可以限制图片资源来源；connect-src 可限制规范覆盖的脚本连接请求。CSP 按浏览器资源类型生效，不是服务端网络出口防火墙。本文引用的 W3C CSP Level 3 页面截至 2026-09-16 标为 Working Draft；浏览器兼容性仍应在目标环境验证。服务端图片代理、PDF 导出器或预览服务若会抓取 URL，需要在各自出站执行边界做限制。是否两边都需要控制，取决于系统实际有哪些请求路径。

第 8 章记录的是：给特定 API 一个不存在的图像 URL 后，服务端返回 400，并包含下载失败信息。这说明该端点尝试服务端取图，构成需要评估的 SSRF 面；它不表示任意 Markdown 图片都会被取，也不证明敏感数据已经外泄。数据放进 URL 会使其暴露给 URL 接收方及中间系统，但只有请求实际发出并到达相应接收方，才能称为该路径上的传输。

生产代理必须把校验绑定到实际连接。单独查询 DNS 并检查 IP，之后再让 HTTP 客户端自行解析，可能受 DNS 重绑定或检查与使用时差影响。还需明确限制 scheme、port 和 credentials，禁止重定向或逐跳复核，设置超时与响应大小上限、校验响应类型。下面只列审查项目，不提供可直接部署的安全代理实现：

| 请求路径 | 核心控制 | 验证问题 |
|---|---|---|
| 浏览器加载图片 | 按实际资源类型配置 CSP | 是否有其他可发请求的页面或 worker？ |
| 服务端代理取图 | 对最终连接目标执行出口策略；禁止或逐跳复核重定向 | 校验 IP 是否与实际连接绑定？是否限制响应资源？ |
| PDF、预览、二次处理 | 按该组件真实网络能力单独控制 | 它是否绕开浏览器 CSP 或代理？ |

**失败形态：** 只在一个渲染入口过滤 URL，却让其他导出或预览入口复用原始 Markdown。要在每个实际发请求的组件实施和测试策略；存储时规范化 URL 可以减少遗漏，但不能替代请求时强制校验。

## 投影式接口：返回最少必要数据

投影可以缩小模型可见的数据范围，但它本身不等于授权。多租户接口必须从已验证的身份上下文取得 principal，并在每次请求上检查该主体对具体对象和动作的权限；不能把模型提供的 user_id 当作身份。返回字段仍应按业务需要最小化，并对资源 ID、租户边界和批量查询做负向测试。

| 任务需要 | 接口返回 | 必须同时检查 |
|---|---|---|
| 判断当前用户是否下过某 SKU 的订单 | 布尔值 | 身份来自认证上下文；仅查当前用户有权访问的订单 |
| 汇总一个月销售额 | 聚合值 | 调用者是否有该范围的统计权限 |
| 回答退款政策问题 | 少量检索片段 | 文档和片段的租户与 ACL 过滤在检索阶段执行 |

**判据：** 如果任务只需布尔、聚合或少量片段，就不应把整行记录或整篇文档交给模型。审查接口实现，确认它既少返回数据，也验证可信主体与资源权限；只检查返回 schema 不足以证明安全。

## 三问清单的数据模板

本节前面列出的三个问题，光问一遍记不住。给一份可以逐项填的结构（示例：构造数据，未实跑），字段就是「你能据此写防护」的最小集合：

```json
{
  "agent": "refund-assistant",
  "access": {
    "most_sensitive_data": "客户表（手机号、余额）",
    "fields_visible_to_agent": ["order_id", "amount", "currency"],
    "returns_projection": true,
    "read_tools": ["refund_passages", "order_status"]
  },
  "channels": {
    "tool_outbound": ["https://api.example.com"],
    "render_layer": {"img_src_allow": ["cdn.example.com"], "csp": true},
    "callbacks": [],
    "log_sinks": ["stdout->observability.example.com"]
  },
  "trigger_controls": {
    "input_tagging": true,
    "review_signals": ["unexpected destination", "sensitive fields in outbound payload"],
    "note": "这些信号用于复核，不替代授权与出口策略"
  }
}
```

**怎么用这份模板：** 每个字段填不出来，就对应一个缺口 —— `channels.render_layer` 填不出，说明你没检查过图片预览；`access.fields_visible_to_agent` 与 `most_sensitive_data` 对不上，说明投影没做到位。它和第 5 节那张四层表是同一类工具：**把「我们考虑了安全」逼成一张填得满或填不满的表。**

## 常见坑

本轮对交叉引用、示例数据标签和来源边界的修正见 `ERR-189`。

- **把玩具模型当成普遍定律。** 本地脚本只验证预设布尔分支，没有真实模型、权限或网络传输。
- **把特定注入样本的 6/6、0/6 写成总体成功率。** 它们只描述第 2 章记录的任务与样本。
- **只统计工具能发起的请求。** 浏览器图片加载、服务端预览、PDF 导出、回调和日志管道都可能形成数据路径；逐一确认哪个组件实际发起请求。
- **把 URL 参数直接等同于外泄。** URL 可能暴露给被引用域名及中间系统；区分构造、请求发出、接收端可见和后续保留。
- **把网络出口控制当成全部通道的控制。** 文件同步、日志、错误和用户可见输出需要单独的接收方与访问边界。
- **把数据投影误当成授权。** 返回字段变少有助于数据最小化，但仍需可信身份、对象级授权与逐请求校验。
- **把上下文副本与保留策略说成所有供应商都一样。** 按实际 API、部署、合同与配置核对数据如何传输、记录和保留。
