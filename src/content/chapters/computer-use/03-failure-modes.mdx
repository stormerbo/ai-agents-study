文本/工具任务的失败是否可见，取决于接口与业务判据；界面自动化同样既可能返回明显的点击落空，也可能造成表面上成功、业务状态却不符合预期的结果。本节复核的是一组本地合成表单与 2026-10-09 的历史模型运行摘要，不代表真实网站或计算机使用系统的总体失败率。

这一节用三种注入测它的失败形态。

## 实测一：小目标下的点击落空

把 Create 按钮从 180×52 缩到 **44×26**，回看历史 harness 摘要。先核对留存证据的范围：`cu-failures.py` 的入口只调用了 tiny 变体 4 次；其中嵌入的历史输出列出 4 条结果，另外两条变体分别运行 2 次和 1 次。原文“12 次、3 次失败、75% 成功率”没有相应的另外 8 条结果支持，必须撤回。

| 旧 harness 输出标签 | 次数 |
|---|---:|
| ✅（旧 harness 的判分标签） | 2 |
| ❌（旧 harness 的判分标签） | 2 |

这两个 ✅ 也不能当成任务成功：脚本用 `st["done"] and st["v"]["name"] == "Zhang San"` 判分，既不核对 email，也不要求两个字段精确等于预期值；它只是在本地把两个字段设为非空时设置 `done`。逐次 provider 响应没有保存，因此本节不报告目标尺寸对应的成功率。

失败长什么样？档案中的两条失败输出记录了落空距离：

```text
click:name → type → click:email → type
  → click:空空间  (离按钮中心 41 px)
  → click:空空间  (41 px)
  → click:空空间  (43 px)
  → click:空空间  (42 px)
  → click:空空间  (43 px)
  → click:空空间  (45 px)
  → click:空空间  (323 px)
```

这里能确认的是动作序列包含连续的空白点击；日志没有保存点击坐标。所谓“距离”由 harness 计算为落点到**当前登记元素中心中的最近距离**，不是一定到 Create 中心的距离。

不能据这份日志断言它反复点了同一个坐标，也无法判断模型是否根据每张新截图重新定位；距离相近不是坐标相同的证据。最后的 323 px 是相对某个已登记元素中心的最近距离，不足以证明具体点到了哪里或模型“开始乱试”。

还有一个与旧文案相反的实现细节：本地 harness 在空白点击后会设置 `Clicked empty space.`，并把这段错误画在下一张截图底部。因此这组小目标实验并非“界面完全没有提示”；模型后续仍输出空白点击，但缺少逐次原始响应，无法判断它是否读到了提示、提示为何没有改变其动作。

脚本插入记录中的旧 harness `token` 数值是 19,209 与 26,568；对应两个旧评分 ✅ 标签样本为 5,015 与 5,027。原脚本把 `input_tokens`、`cache_read_input_tokens`、`cache_creation_input_tokens` 和 `output_tokens` 相加作为显示值。当前 [DeepSeek Anthropic 兼容说明](https://api-docs.deepseek.com/guides/anthropic_api/)列出接口兼容字段，但没有定义这段求和是否等于可计费总量；逐轮响应与账单也未归档。因此，19,209/5,015 和 26,568/5,027 只是旧程序显示值之比（约 3.8 倍与 5.3 倍），不是经核实的 token 总量，不能视为失败成本倍数的可靠估计或预算预测。

这组存档只支持“短任务失败可能消耗更多调用与输入预算”这一风险提示，不足以建立成本分布。上线预算应记录目标工作负载里的完整逐轮 usage、任务级结果判据与超限/退出原因。

## 实测二：点击无效时重复提交，但没有可核验的失败状态

第二个注入是让点 Create **不改变界面状态** —— 在这个本地 noop 变体里，既没有错误提示，也没有加载动画。这是特定合成 harness 的行为，不代表真实站点的反馈。

旧 harness 的动作摘要显示，模型在提交按钮完全无反应时重复输出提交动作：

```text
click:name → type → click:email → type → click:submit × 4
```

这说明旧摘要记录了 4 次重试，并不证明模型识别了异常：这个 `noop` 变体不会设置错误提示或改变界面，原始响应也没有归档，因此行为动机不可知。

**动作 schema 没有「报告卡住」或「失败原因」状态。** 模型可以输出 `done` 退出，但这会与“任务已完成”混淆；在旧控制器里它继续重试，最终由 8 步上限结束。更稳妥的设计是让控制器区分 `succeeded`、`failed_unconfirmed`、`budget_exhausted` 等结果，而不是把模型的 `done` 当作业务成功。

（本次留存的 harness 只列出一条 noop 运行：8 步、11,827 token。正文旧写的“两次运行”和约 12,000 token 均缺少第二条对应记录；与约 5,000 token 样本的 2.4 倍只是粗略算术，不是可推广的实验结论。）

这个结果直接决定了两件事，第 4 节会展开：

**一，宿主应掌握停止与结果分类。** 「连续 N 步界面无变化」可以作为一种停滞启发式，但阈值需要按界面动态和任务风险校准；不能把触发该启发式直接当作业务失败或成功。

**二，给未确认状态留出显式出口。** 可以由宿主在超限时返回 `failed_unconfirmed`，也可以允许模型报告卡住；无论哪种，仍要由独立判据确认业务结果，不能把一个模型动作直接当作真实失败状态。

## 实测三：相邻的诱饵按钮 —— 未复现

第三个注入是在 Create 旁边并排放一个同样显眼的 Cancel（点了会清空表单），看它会不会点错。

入口脚本只运行了 2 次 decoy，而不是正文曾写的 4 次。存档只输出两个旧判分 ✅，不保留动作序列或目标字段回读；由于成功判分没有核对 email，也无法据此断言两次都点中了 Create。相邻按钮混淆在现存输出中没有被记录，但这个小样本不能证明它不会发生。

两个按钮的文案、位置可能影响模型行为，但本轮没有足够轨迹检验原因；这仍是待测假设。

## 真正危险的不是「点不中」

把已记录的场景分开看，至少有两类不同的风险；它们的严重度取决于动作与业务后果：

| 失败类型 | 表现 | 后果 |
|---|---|---|
| **动作未命中/未生效** | 空白点击、界面无变化或重复动作 | 可能被适配器提示发现，也可能无信号；会增加成本或导致状态未知 |
| **作用对象/业务状态错误** | 点到另一控件、字段值不符或副作用目标错误 | 可能被页面提示，也可能产生表面正常但业务不符的结果；影响取决于副作用 |

本节可执行 harness 只测试小按钮空白点击、无响应提交与诱饵控件，没有实现真实业务副作用，也没有实现后文的 `swap` 变体。下方字段错位例子是一个构造的验收 fixture，不是模型端到端实测。真实系统需要按后果等级定义检测与授权策略，不能从这份合成实验推导两类风险的普遍排序。

字段填错但提交被接受，是一种可能的静默错误：页面可以显示成功，而业务字段仍不符合任务要求。是否能从界面发现取决于应用反馈；本节的构造 fixture 只用于说明需要校验业务后置条件。

因此这类任务应定义独立的业务后置条件：对可权威读取的记录逐字段核对；若数据源不可读，使用适合任务的独立确认路径并明确剩余不确定性。界面结束、模型 `done` 或成功提示都可作为证据的一部分，但单独使用通常不足以证明副作用和字段值符合预期。

## 怎么提高发现错误的机会

适配器可能报告点击落空，但这依赖接口；作用对象错误也可能有页面反馈，不能一概而论。下面是几种互补的核验办法，不构成适用于所有任务的可靠性排序：

**一，定义业务后置条件，并优先使用权威状态源核对。** 模型自评和成功页面可以作为信号，但不一定足以证明结果；如果数据源不可读，就选另一条可信的确认路径并记录不确定性。核对可由代码或独立流程执行，关键是判据不依赖模型单方面宣称完成。

**二，关键动作前后留存足够的证据。** 对本节的截图/坐标路线，保留截图、动作坐标、时间戳及适配器返回状态，便于事后排查；它们仍不能单独证明业务操作成功，必要时还要查询应用状态或业务记录。适配器和平台提供的其他日志也应纳入审计。

**三，评估重试的重复副作用，并尽可能使用幂等操作或去重键。** 「设置 Name = Zhang San」通常比「追加 Zhang San」更容易安全重放。无法幂等时，应先查询状态、使用去重机制、补偿或转人工；是否自动重试取决于动作语义和业务风险。

**四，按风险与授权要求设计审批。** 不可逆或高影响动作通常需要更强的授权、确认或独立校验；具体是否可自动执行取决于用户授权、业务策略和补偿能力，不能仅由“是否可逆”一个条件决定。

这些做法共同要求：把任务完成定义成可验证的业务条件，并选取与风险相称的证据。数据层常是有力的确认来源，但并非所有系统都能读取；此时应明确替代证据的局限。

### 一个构造的字段错位验收 fixture

下面只构造一个字段错位后的记录，演示逐字段检查器能否发现它；`swap` 不在本节完整脚本的 `VARIANTS` 中，这个样例没有连接 UI、没有调用模型，也没有执行数据写入。实际 renderer 会用蓝色边框标出焦点框，因此若真把焦点交换接入界面，截图也可能暴露变化，不能声称它“看起来完全正常”或只有数据源检查才能发现。

设想模型提议的动作序列仍是标准的五步：

```text
click:name → type "Zhang San" → click:email → type "zhang@example.com" → click:submit
```

若某个执行器或 fixture 把两个焦点映射对调，构造的最终记录可以是：`name="zhang@example.com"`、`email="Zhang San"`。字段都非空不代表它满足任务后置条件；这是假设状态，不是本节实验观察。

```text
假设页面只根据“字段非空”显示成功：SUCCESS
user created: zhang@example.com
```

这个 fixture 说明“提交被接受”与“字段满足预期”是两个不同判据；它没有证明真实 UI 会隐藏焦点变化，也没有测试模型会如何响应该截图。

如果能从可信 API 或数据源读取结果，可按预期逐字段核对。下面将比较函数和构造样例放在一起，便于直接运行。字段值与“SUCCESS”文案都是构造数据；函数只比较给定字段，不连接数据库/API，也不证明身份、数据来源或授权。执行它会看到字段错位被报告、正确记录通过：

```python
def check_record(created, expected, fields=("name", "email")):
    """比较查询结果与预期字段，返回不一致项；不负责证明数据源可信。"""
    bad = []
    for key in fields:
        if created.get(key) != expected.get(key):
            bad.append("%s: 期望 %r，实际 %r" % (key, expected.get(key), created.get(key)))
    return bad


if __name__ == "__main__":
    expected = {"name": "Zhang San", "email": "zhang@example.com"}
    swapped = {"name": "zhang@example.com", "email": "Zhang San"}
    correct = {"name": "Zhang San", "email": "zhang@example.com"}

    mismatches = check_record(swapped, expected)
    assert len(mismatches) == 2
    assert check_record(correct, expected) == []

    print("[界面层] SUCCESS 页显示：user created: zhang@example.com  -> 看起来成功 ✅")
    print("[数据层] 查回记录 %r -> ❌ %d 处不一致" % (swapped, len(mismatches)))
    for mismatch in mismatches:
        print("  " + mismatch)
    print("[对照：正确提交] -> ✅ 一致")
```

示例只覆盖两个字符串字段的精确相等比较。生产检查还要明确可信身份与查询路径、字段清单、归一化规则、缺失值处理和并发更新语义；若权威记录不可读，应改用另一条可信确认路径并标明局限，不能把页面文案或模型自评当成确定事实。
## 完整可运行代码

脚本实现的是本地表单环境、tiny/decoy/noop 三种变体和一个真实 API 调用循环；需要 Pillow、可用字体文件、网络及 `VERIFY_MODEL`、`ANTHROPIC_BASE_URL`、`ANTHROPIC_AUTH_TOKEN`。环境与本地状态机可复现，模型输出、usage 与路由不保证复现。其判分器仅检查 name 和 `done`，因此示例输出的 ✅ 不是完整任务验收；脚本不执行真实桌面动作，也不提供生产级动作校验、授权或隔离。

```python
"""失败模式注入：小目标 / 诱饵按钮 / 点击无效。

自包含 —— 环境、循环、三种失败注入都在这个文件里。

实跑状态：历史运行记录日期为 2026-10-09、模型别名 `deepseek-flash`；原始逐次响应与可验证的路由版本未保存，本轮未重跑在线请求。
"""
import os
import base64, json, os, urllib.request
from io import BytesIO
from PIL import Image, ImageDraw, ImageFont

FONT = "/System/Library/Fonts/Supplemental/Arial.ttf"
W, H = 820, 520
BASE = {"name": (60, 150, 500, 196), "email": (60, 250, 500, 296)}

# 三种失败注入。submit 的尺寸直接决定「点得中吗」
VARIANTS = {
    "normal": {"submit": (60, 380, 240, 432)},                 # 180x52
    "tiny":   {"submit": (60, 380, 104, 406)},                 # 44x26
    "decoy":  {"submit": (60, 380, 240, 432), "cancel": (270, 380, 430, 432)},
    "noop":   {"submit": (60, 380, 240, 432)},                 # 点了毫无反应
}


def render(state, els):
    img = Image.new("RGB", (W, H), "white")
    d = ImageDraw.Draw(img)
    f = lambda s: ImageFont.truetype(FONT, s)
    d.rectangle([0, 0, W, 64], fill=(240, 244, 250))
    d.text((60, 24), "NEW USER FORM", fill=(20, 30, 50), font=f(20))
    d.text((60, 110), "Name", fill=(90, 100, 115), font=f(14))
    d.text((60, 210), "Email", fill=(90, 100, 115), font=f(14))
    for key in ("name", "email"):
        x0, y0, x1, y1 = els[key]
        on = state["focus"] == key
        d.rectangle([x0, y0, x1, y1], outline=(60, 120, 220) if on else (170, 180, 195),
                    width=3 if on else 1)
        d.text((x0 + 12, y0 + 14), state["v"][key], fill=(20, 20, 20), font=f(18))
    x0, y0, x1, y1 = els["submit"]
    small = (x1 - x0) < 100
    d.rectangle([x0, y0, x1, y1], fill=(30, 110, 220))
    d.text((x0 + 12, y0 + 6), "Create", fill="white", font=f(15 if small else 18))
    if "cancel" in els:
        cx0, cy0, cx1, cy1 = els["cancel"]
        d.rectangle([cx0, cy0, cx1, cy1], fill=(235, 238, 243))
        d.text((cx0 + 26, cy0 + 15), "Cancel", fill=(60, 70, 90), font=f(18))
    if state["err"]:
        d.rectangle([60, 452, W - 60, 486], fill=(255, 238, 238))
        d.text((72, 460), state["err"], fill=(190, 40, 40), font=f(14))
    if state["done"]:
        d.rectangle([0, 0, W, H], fill=(240, 252, 245))
        d.text((60, 200), "SUCCESS", fill=(20, 140, 70), font=f(34))
    b = BytesIO()
    img.save(b, format="PNG")
    return b.getvalue()


SYS = "\n".join([
    "你是一个通过截屏操作界面的 agent。只输出一个 JSON 对象，不要解释、不要代码块。",
    '{"action":"click","x":<整数>,"y":<整数>} 或 {"action":"type","text":"..."}' + ' 或 {"action":"done"}',
])
TASK = "在表单里填入 Name = Zhang San、Email = zhang@example.com，然后点 Create。"


def ask(history):
    body = json.dumps({"model": os.environ["VERIFY_MODEL"], "max_tokens": 600,
                       "system": SYS, "messages": history}).encode()
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages", data=body,
        headers={"content-type": "application/json",
                 "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
                 "anthropic-version": "2023-06-01"})
    with urllib.request.urlopen(req, timeout=180) as resp:
        data = json.loads(resp.read())
    u = data.get("usage", {})
    tok = (u.get("input_tokens", 0) + u.get("cache_read_input_tokens", 0)
           + u.get("cache_creation_input_tokens", 0)) + u.get("output_tokens", 0)
    text = "".join(b.get("text", "") for b in data.get("content", []) if b.get("type") == "text")
    return text.strip(), tok


def run(variant, max_steps=12):
    els = dict(BASE)
    els.update(VARIANTS[variant])
    if variant != "decoy":
        els.pop("cancel", None)
    st = {"focus": None, "v": {"name": "", "email": ""}, "err": None, "done": False}
    hist = [{"role": "user", "content": [{"type": "text", "text": TASK + "\n当前屏幕："},
             {"type": "image", "source": {"type": "base64", "media_type": "image/png",
              "data": base64.b64encode(render(st, els)).decode()}}]}]
    steps, toks, seq, hit, miss = 0, 0, [], 0, []
    while steps < max_steps and not st["done"]:
        steps += 1
        text, t = ask(hist)
        toks += t
        i = text.find("{")
        try:
            act, _ = json.JSONDecoder().raw_decode(text[i:])
        except Exception:
            seq.append("PARSE_FAIL")
            break
        kind = act.get("action")
        if kind == "done":
            seq.append("done")
            break
        if kind == "click":
            x, y = float(act["x"]), float(act["y"])
            target, best = None, 1e9
            for k, (x0, y0, x1, y1) in els.items():
                cx, cy = (x0 + x1) / 2, (y0 + y1) / 2
                best = min(best, ((x - cx) ** 2 + (y - cy) ** 2) ** 0.5)
                if x0 <= x <= x1 and y0 <= y <= y1:
                    target = k
            seq.append("click:" + (target or "空空间"))
            if target is None:
                miss.append(round(best, 0))
            if target in ("name", "email"):
                st["focus"], st["err"] = target, None
            elif target == "cancel":
                st["v"], st["focus"], st["err"] = {"name": "", "email": ""}, None, None
            elif target == "submit":
                if variant == "noop":
                    pass                                   # 界面完全不变
                elif st["v"]["name"] and st["v"]["email"]:
                    st["done"] = True
                else:
                    st["err"] = "Name and Email are both required."
            else:
                st["focus"], st["err"] = None, "Clicked empty space."
            hit += 1 if target else 0
        elif kind == "type":
            seq.append("type")
            if st["focus"]:
                st["v"][st["focus"]] += str(act.get("text", ""))
            else:
                st["err"] = "Nothing is focused."
        hist.append({"role": "assistant", "content": text})
        if st["done"]:
            break
        hist.append({"role": "user", "content": [{"type": "text", "text": "新的屏幕："},
                     {"type": "image", "source": {"type": "base64", "media_type": "image/png",
                      "data": base64.b64encode(render(st, els)).decode()}}]})
    return st, steps, toks, seq, miss


if __name__ == "__main__":
```

## 本节小结

1. **历史样本不能提供成功率**：tiny 入口记录四次运行，但旧评分器未核对完整目标值，逐次响应缺失。
2. **适配器的反馈因环境而异**：本地 tiny 变体会显示空白点击错误；noop 变体无变化。不能推广为所有 UI 都有/没有提示。
3. **终止原因要显式建模**：步数上限、模型退出与任务成功是不同状态；为停滞/失败留出宿主侧结果和转人工路径。
4. **验收应匹配业务后置条件**：在权威数据可读时逐字段核对；其他环境选独立、可信的确认方式并报告不确定性。
## 常见坑

- **用「跑完了没有」判断成功。** 控制器退出、模型输出 `done` 与业务后置条件满足是不同状态。
- **把动作空间缺少失败标签当成所有系统的限制。** 本例 schema 没有显式卡住状态；宿主可自行分类超限/未确认退出，也可设计报告动作，并应与业务成功状态区分。
- **把本地 harness 的 ✅ 当成端到端成功。** 它只核对 `done` 与 name，没有逐字段验证 email。
- **把 4 次历史输出当作目标尺寸的成功率。** 样本小、评分器不完整且响应缺失，不能计算可用于部署的命中率。
- **把两个成本比例当成预算常数。** 19,209 与 26,568 等总量只来自旧运行摘要，应使用目标端点的逐轮 usage 与任务级验收重新测量。
- **把两条 decoy 摘要标签当成混淆测试通过。** 存档没有动作序列，且成功判据不完整；只能说这些输出未提供可核验的误点记录。
