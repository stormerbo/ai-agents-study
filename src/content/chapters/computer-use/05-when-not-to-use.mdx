这一章的最后一节要回答一个问题：**同样一件事，走 API 还是点界面？**

这个问题有一个强有力的默认答案，而它值得用数据讲清楚，而不是靠「API 更快」这种印象。

## 实测：同一件事，两条路线的代价

任务完全相同 —— 「创建用户 Zhang San / zhang@example.com」。一条走 API（一次工具调用），一条走界面（第 2 节那个观测-动作循环）：

| 路线 | token | 模型往返次数 |
|---|---:|---:|
| A 走 API（一次工具调用） | **384** | **1** |
| B 走界面（观测-动作循环） | **5,528** | **5** |
| 差距 | **14.4 倍** | **5 倍** |

（实跑数据，2026-10-09，`deepseek-flash`。各跑 3 次取的代表值；API 路线三次是 386 / 384 / 384。）

而且注意：API 路线这一次就拿到了完全正确的入参 —— `{"name": "Zhang San", "email": "zhang@example.com"}`，一次就成了。

**14.4 倍的差距不是实现水平问题，是结构问题。** 它来自第 1 节那三点区别的叠加：

- 观测是像素 → 每步要付一张截图的钱（约 283 token），而工具调用传的是几十个 token 的 JSON
- 动作是通用原语 → 一个动作只走一步，而工具调用可以在一次入参里把整件事说完
- 没有返回值 → 每步都需要一次新的观测才能确认，往返次数被迫翻倍

## 由此得到的一条默认规则

**有 API 就别点界面。** 这条规则应当默认遵守，只有当它明确不成立时才考虑界面路线。

这个「明确不成立」有具体的判据，不是感觉：

| 情况 | 该走哪条 | 理由 |
|---|---|---|
| 有官方 API 或 SDK | **API** | 便宜 14 倍、往返少 5 倍、而且结果是结构化的 |
| 有非官方的稳定接口（内部系统） | **API**（优先） | 只要它稳定，收益和上面一样 |
| 界面里有数据，但接口不开放 | **界面**（或抓取） | 拿不到结构化数据，视觉是唯一通道 |
| 桌面软件，没有 HTTP 接口 | **界面** | 没有别的选择 |
| 一次性任务，量很小 | **看情况** | 写集成的成本可能高于点几次界面 |

第四行和第五行是界面路线真正站得住的场景。它们的共同特征是：**没有接口，或者接口的获取成本高于任务本身的价值。**

## 一个更容易踩的坑：混合路线

上面的表格假设任务是「要么全 API，要么全界面」。真实场景更常见的是混合的，而混合里有一个很划算的形态容易被忽略：

**用 API 做决策，用界面做执行。**

比如批量录入 100 条记录：解析、去重、字段映射、校验全部由代码完成（这些是确定性的，不该花模型的钱），只在**真正需要点界面**的那一步交给视觉。这样模型只负责「往哪个框里填什么」，而不是从头到尾走一遍循环。

反过来的形态也要小心：**用界面做决策、用 API 做执行**。这通常是个坏组合 —— 你付出了视觉的全部成本，却只为了触发一个本来可以直接调用的接口。

## 那这一章的价值在哪

如果结论是「尽量别用」，那用一整章讲它值得吗？值得，理由有两个。

**第一，它有你绕不开的场景。** 内部系统、老后台、桌面软件 —— 这些场景在真实工作里占比并不低，而且往往是「数据就在这里，但只能手点」的那种。

**第二，它把这个领域的边界讲清楚了。** 前面几章建立的直觉是「给模型合适的接口，它就能做好」；这一章是那条直觉的反面：**当接口不存在时，你要付出什么代价。** 知道这个代价的量级（14 倍、5 倍往返、失败时再翻 2 到 5 倍），你才能在选型会上给出一个有依据的判断，而不是「这个应该能做吧」。

## 如果一定要用界面：一份上线前的清单

判断必须走界面路线之后，在写循环之前先把这几件事定下来。它们全部来自本章的实测。

**一，把「完成」写成可核对的判据。** 不是「完成任务」，而是「数据库里多了一条 `name=Zhang San, email=zhang@example.com` 的记录」。第 3 节的结论：验收必须落在数据层。写不出这个判据，说明任务本身还没定义清楚。

**二，画出活动范围。** 列出允许点击的矩形区域。范围越小越好 —— 白名单之外一律拦截，不需要模型理解为什么。

**三，按失败路径定预算。** 实测失败是成功的 2.4 到 5.3 倍。步数上限和 token 上限都要设，缺一个都不行。

**四，定熔断阈值。** 连续几步界面无变化就中止。实测 3 到 4 步是合理的起点，2 会误杀正常流程。

**五，列出不可逆动作，并指定批准入口。** 批准入口必须在循环之外。如果一个动作无法撤销、又无法人工确认，那它就不该被自动执行。

**六，把动作幂等化。** 「设置」而不是「追加」。因为重试是常态，而不是异常。

**七，先在小样本上测出真实成功率。** 第 3 节实测：目标 180×52 时接近 100%，缩到 44×26 掉到 75%。批处理 100 条而成功率 75%，意味着 **25 条要人工兜底** —— 这个数字必须在上线前知道，而不是上线后发现。

七条里有五条是「在写循环之前就该定好的」。这也是本章最后想留下的印象：**界面自动化的难点不在循环本身，而在给循环画边界。**
## 完整可运行代码

下面这段代码把两条路线并排跑一次 —— 同一件事，同一个模型，唯一的差别是走 API 还是走界面。

```python
"""同一件事：走 API（工具调用） vs 走界面（观测-动作循环）。

实跑状态：2026-10-09，deepseek-flash。
"""
import importlib.util, json, os, urllib.request

spec = importlib.util.spec_from_file_location("cu", "verify-output/cu-loop.py")
cu = importlib.util.module_from_spec(spec)
spec.loader.exec_module(cu)

TOOL = {
    "name": "create_user",
    "description": "在系统里创建一个用户。",
    "input_schema": {
        "type": "object",
        "properties": {"name": {"type": "string"}, "email": {"type": "string"}},
        "required": ["name", "email"],
    },
}


def api_arm():
    body = json.dumps({
        "model": os.environ["VERIFY_MODEL"], "max_tokens": 500,
        "tools": [TOOL],
        "messages": [{"role": "user", "content":
                      "创建一个用户：姓名 Zhang San，邮箱 zhang@example.com。"}],
    }).encode()
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages", data=body,
        headers={"content-type": "application/json",
                 "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
                 "anthropic-version": "2023-06-01"})
    with urllib.request.urlopen(req, timeout=180) as resp:
        data = json.loads(resp.read())
    u = data.get("usage", {})
    tin = (u.get("input_tokens", 0) + u.get("cache_read_input_tokens", 0)
           + u.get("cache_creation_input_tokens", 0))
    tool = [b for b in data.get("content", []) if b.get("type") == "tool_use"]
    return tin, u.get("output_tokens", 0), (tool[0].get("input") if tool else None)


if __name__ == "__main__":
    print("同一个任务：创建用户 Zhang San / zhang@example.com")
    print()
    print("--- 路线 A：走 API（一次工具调用）---")
    for i in range(3):
        tin, tout, args = api_arm()
        print("  第%d次：输入 %d + 输出 %d = %d token，1 次往返" % (i + 1, tin, tout, tin + tout))
        if i == 0:
            print("        工具入参：%s" % json.dumps(args, ensure_ascii=False))
    print()
    print("--- 路线 B：走界面（观测-动作循环）---")
    cu.VARIANT = "baseline"
    totals = []
    for i in range(3):
        state, log, tokens, steps, _ = cu.run_trial()
        totals.append((tokens, steps))
        print("  第%d次：%d token，%d 次往返（%s）" % (i + 1, tokens, steps,
                                                     "成功" if state["done"] else "失败"))
    avg_b = sum(t for t, _ in totals) / len(totals)
    print()
    print("  界面路线平均 %.0f token / %.1f 次往返" % (avg_b, sum(s for _, s in totals) / len(totals)))
```

## 本节小结

1. **同一件事，界面路线贵 14.4 倍、往返多 5 倍** —— 这是结构决定的，不是实现水平问题。
2. **「有 API 就别点界面」应当默认遵守**，破例要能说出具体理由。
3. **混合路线通常最优**：代码做决策与校验，视觉只做无法 API 化的那一步。
4. **本章的结论是「尽量别用」，但代价必须知道** —— 内部系统、老后台、桌面软件这些场景你绕不开，而选型时需要的是量级（14 倍、5 倍往返、失败再翻 2 到 5 倍），不是「这个应该能做吧」这种印象。
## 常见坑

- **「有 API 但还是点了界面」。** 同一个任务实测差 14.4 倍 token、5 倍往返。这条规则要默认遵守，例外要能说出理由。
- **只看 token，不看往返。** 5 次往返意味着 5 次延迟、5 个可能失败的环节。界面路线在延迟上通常也明显更差。
- **忘了算失败路径。** 界面路线失败时还要再翻 2.4 到 5.3 倍（第 3 节实测），而 API 调用的失败成本几乎可以忽略。
- **把「能跑通」当成「可以上线」。** 第 3 节实测的成功率是 75% 到 100%，取决于目标大小；这个区间对批处理任务往往不够。
- **忽略混合路线。** 「代码做决策、视觉只做执行」通常比「全程视觉」便宜一个数量级，而且确定性高得多。
- **用界面路线去触发一个本来就能直接调用的接口。** 付出视觉的全部成本，换来一个本该免费的动作。
