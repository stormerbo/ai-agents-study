本站 2026-10-08 的历史实验曾记录：合成表格图在 290 与 1,061 token 时都得到 36/36。**这只是单次历史观察，不能证明分辨率不影响准确率，也不能支撑旧文中的 186/996 固定费用阈值。** 逐次响应、精确模型快照、完整 usage 口径和重复运行没有完整留存；生成图时字号还随画布宽度改变，实验同时改变了字号与总像素，不能把差异单独归因于分辨率。更小尺寸下的一次错误也不能证明错误与尺寸无关。本节撤回这些通用结论，改为给出按目标 endpoint 建立成本和质量证据的方法。

## 三种不同的成本

| 成本 | 主要影响因素 | 测量方法 |
|---|---|---|
| 模型输入成本 | provider 图像预处理、模型档位、图像与文本上下文、缓存和价格 | 保存响应 usage，并按当日价格核对账单 |
| 请求字节与延迟 | 编码大小、网络、重复上传、请求体限制 | 记录编码字节和端到端上传耗时 |
| 任务质量 | 有效像素、字号、压缩伪影、旋转/裁剪、任务类型 | 用答案键统计字段准确率、漏读和错读 |

压缩可以降低请求字节和传输量，但不能由字节数直接推断视觉 token。重度有损压缩也可能破坏细线和小字；必须评估实际送出的图像。

截至 **2026-10-22** 查阅的官方文档显示，不同 provider 的计算路径不同：

- DeepSeek Vision 描述了按比例自动缩放：总像素较小时会放大，较大时缩至约 1300×1300 像素规模，单图估算上限 1024 tokens；官方同时提示实际 usage 可能略有差异。只把它用于文档覆盖的 DeepSeek API。
- Claude Vision 按 28×28 像素 patch 估算 visual tokens，并依模型档位设置长边与视觉 token 上限。规则按模型变化。
- 兼容 API 不保证沿用原厂的图像预处理、usage 字段或计费方式。记录 base URL、API 模式和响应中的 model id，再解释观测结果。

预算公式只是估算：

```text
估算输入成本 = Σ（各计费类别的 token usage × 对应单价）
```

如果某个 endpoint 将这些输入 token 都按同一单价计费，可以合并后相乘；若缓存读写、长上下文等类别有独立费率，就按响应 usage 中的类别分别计算。这里得到的仍是估算值，最终以该 endpoint 的计费规则和账单为准。

缓存、折扣、批处理和服务档位都可能改变最终账单；价格会变。每次运行记录日期、响应 model、finish reason、usage 字段与请求 ID，以 endpoint 返回的 usage 和账单校准估算器。

## 怎样选择分辨率

先定义质量门槛。低分辨率往往先伤害小字号、密集表格、勾选框、图表标签和坐标定位；大图也可能被服务端缩放或拒绝。不要用「越清楚越准」或「图越小越省」替代测量。

| 任务 | 质量指标 |
|---|---|
| 页面分类 | 各类别召回率、混淆矩阵 |
| 字段抽取 | 每字段精确匹配、漏字段率 |
| 表格读取 | 单元格准确率、行列错位、完整行率 |
| 屏幕定位 | 目标框/坐标误差及缩放后的坐标映射 |
| 图表理解 | 数值误差、趋势或排序正确率 |

实验固定原图内容、提示词、endpoint、model、输出 schema 与采样参数，每次只改变一个变量。分别比较原图、应用侧缩小图、按 provider 文档处理的图；测压缩时还要记录尺寸、色彩空间和质量参数。候选方案用同一批样本配对比较，并做重复运行和独立留出验证。输出失败、截断、拒答、解析失败、缺失 usage 都应作为单独状态保存；不能把空文本记为模型错误，也不能把缺失 usage 当成零成本。

结果应保留逐样本记录，而不是只贴一行平均值：例如记录样本 ID、图片哈希、处理档位、精确匹配字段数、总字段数、finish reason、usage 与请求 ID。先按模板、页面类型或来源拆分误差，避免同一模板泄漏到调参集和评估集。样本量由你需要的置信度和预期错误率决定；小样本适合发现明显问题，不能用来证明两个尺寸等价。若决策涉及成本与精度的权衡，先定义可接受错误上限，再比较达到该门槛的方案。

## 分块：以信息增益证明额外成本

裁剪主要解决整图缩放后关键细节不可读，或需要对局部放大检查的情况。它会增加图片数量、请求字节、延迟和潜在视觉 token，并削弱局部块与整页的空间关系。每块固定最低 token、切块必然贵几倍等说法都不是跨 provider 规律。

决策步骤：

1. 先测完整图，确认模型是否缩放、拒绝，关键文字是否可读。
2. 若关键区域变得不可读，裁切时保留行列标题、页码和必要上下文。
3. 需要跨区域比较时，为每块标注页码、区域序号及坐标范围。
4. 用答案键比较整图与裁块方案的质量、usage、延迟和失败率；只有达到质量门槛且增益值得成本时才采用裁块。

实跑状态：本节裁剪函数已由 4 个离线断言检查，包括合成图片的三个边界与无效参数。测试使用 fake image 对象；未运行真实 Pillow、图像模型或计费 endpoint。下面代码只验证本地几何裁剪，不代表任何 API 的 token 计算，也不证明裁块能提升模型质量。overlap 是实验参数，不是推荐的通用比例。

```python
import math
from PIL import Image


def split_vertical(image: Image.Image, parts: int, overlap: float = 0.0):
    """返回 (index, y_start, y_end, crop)；overlap 是基础块高的比例。"""
    if isinstance(parts, bool) or not isinstance(parts, int) or parts < 1:
        raise ValueError("parts must be an integer >= 1")
    if (
        isinstance(overlap, bool)
        or not isinstance(overlap, (int, float))
        or not math.isfinite(overlap)
        or not 0 <= overlap < 1
    ):
        raise ValueError("overlap must be a finite number in [0, 1)")
    width, height = image.size
    if width < 1 or height < 1 or parts > height:
        raise ValueError("image height must be >= parts")

    result = []
    for i in range(parts):
        core_top = i * height // parts
        core_bottom = (i + 1) * height // parts
        pad = round((core_bottom - core_top) * overlap)
        top = max(0, core_top - (pad if i else 0))
        bottom = min(height, core_bottom + (pad if i < parts - 1 else 0))
        result.append((i, top, bottom, image.crop((0, top, width, bottom))))
    return result


if __name__ == "__main__":
    page = Image.new("RGB", (1000, 3000), "white")
    blocks = split_vertical(page, 3, 0.10)
    assert [(top, bottom) for _, top, bottom, _ in blocks] == [
        (0, 1100), (900, 2100), (1900, 3000)
    ]
    print([(i + 1, top, bottom, crop.size)
           for i, top, bottom, crop in blocks])
```

输出：

```text
[(1, 0, 1100, (1000, 1100)), (2, 900, 2100, (1000, 1200)), (3, 1900, 3000, (1000, 1100))]
```

这是合成 1000×3000 图片的本地边界检查；不是 API 或模型实验。重叠区域会重复发送；若做文档抽取，还要防止重叠区重复计数。涉及账务、审批或执行动作的字段须经过确定性校验或人工复核。

正式质量实验中，按一张源图建立配对组，每个变体使用同一提示词、schema 和抽取字段，并保留每次的原始响应与解析结果。图片如果来自多个模板或来源，应报告各组指标，不能让一个容易识别的模板支配总体分数。对解析失败的响应仍保留请求、终止原因与原文；只有完成状态、结构合法且字段可评分的样本才进入字段准确率分母，同时单独报告失败率。这样才能区分“模型看错了”和“请求没完成”这两种工程问题。

选档时同时看质量与成本，而不是先选尺寸再为它找理由：横轴可以是实际图像 usage 或单位处理费用，纵轴为预先指定的字段指标；质量未达标的方案直接淘汰。若两档差距小于样本不确定性，就不能声称某一档更准，应扩大样本、增加重复或选择成本较低且质量风险可接受的一档。没有通用的重复次数，具体样本量取决于错误率、任务分布和可接受的不确定度。

## 多轮图像的费用

「后续轮次能看见先前图像」不等于「每次都以相同方式重复上传或重复计费」。无状态客户端可能每轮重发完整历史；服务端会话、文件引用、缓存及不同 API 的上下文管理方式都可能不同。应分别测传输量、上下文 usage、缓存 usage 与最终账单。

仅在每轮都重发完整历史、旧图像每次都重新计入输入的假设下，设每轮新增文本输入为 T、历史图像折算输入为 V、调用 N 次，累计输入量近似为：

```text
N × T + V × N × (N + 1) / 2
```

此公式是特定无状态场景的推导，不是所有 Agent/API 的成本规律。

## 常见错误

- **套用历史 186/996/512/1280 阈值**：这些数字不能代表当前各 provider 的通用边界；查目标 API 文档并核对真实 usage。
- **用单次 36/36 断言尺寸无关**：原实验还改变字号，且没有重复；控制变量并配对测量。
- **字节少就认定 token 少**：字节、视觉 token、质量是不同指标，分别记录。
- **切块后默认更清楚、更便宜**：测量额外图块带来的质量增益，并计入重叠、延迟和 usage。
- **把估算值当账单**：估算、API usage 和扣费是三个口径，逐次保留证据。
- **把截断记为视觉误读**：分别处理 max_tokens、拒答、网络失败、解析失败与识别错误。
- **把完整历史重发成本推广到所有接口**：确认会话状态、文件引用和缓存语义，再按轮对账。

决策原则：**先满足任务质量门槛，再按目标 endpoint 的 usage、延迟和账单优化图像输入；任何尺寸、压缩和分块参数都要按具体 API 验证。**
