拿到一份 PDF 时，你有三条路：直接把 PDF 交给模型、把它渲染成图片、或者自己先把文本抽出来。

三条路都能写出来，而且都「能跑」。但它们**在同一个端点上的实际行为差别巨大**，其中一条会给你一个看起来成功、实际什么都没做的响应。

## 实测：同一份 PDF，三条路线

我手写了一份最小合法 PDF（一张 8 行的发票表格，含 Widget A/B/C 与合计 119.50），然后用三条路线问同一个问题。答案键是构造出来的，可以逐字比对：

| 路线 | 输入 token | 回答正确 | 模型实际说了什么 |
|---|---:|---|---|
| A 直接发 PDF（document 块） | **59** | ❌ | 「无法确定（文档不受支持，未提供可读取的表格内容）」 |
| B 渲染成 PNG 发（image 块） | 337 | ✅ | 逐行读出了 A/B/C 的数量、单价与金额 |
| C 自己抽文本发（text 块） | 123 | ✅ | 「37.50,119.50」 |

（实跑数据，2026-10-08，`deepseek-flash`。三路线用同一份内容、同一个问题。）

## 路线 A 的问题不是「不支持」，是「静默」

先看最关键的地方：**路线 A 返回的是 HTTP 200，不是错误。**

59 个输入 token 也说明了问题 —— 那份 PDF 有 874 字节，如果真的被解析，输入 token 不可能只有 59（那只够装下提问本身）。也就是说：**PDF 的字节被收下了，然后被丢掉了。**

这件事比「不支持 PDF」严重得多：

- 如果是 400，你的代码会立刻报错，你会知道要换方案
- 现在是 200 + 一句「文档不受支持」，如果提示词里没有明确要求「读不出就说读不出」，模型完全可能**开始编**

换句话说，**这条路线把「我读不到」这件事从「HTTP 层」降级到了「模型自觉性」层**，而后者不是可靠的保障。

这也解释了为什么第 5 章那条规律在这里又出现一次：**凡是有静默降级的地方，都要有代码层的守卫。** 就本条而言，守卫是：拿到 PDF 之后不要盲发，先自己判断这份文档该怎么走。

## 路线 C 是可行的，而且便宜

我用 `pdfplumber` 从**同一份 PDF** 里抽文本：

```text
pdfplumber 从同一份 PDF 抽出 159 字符，含 37.50: True
```

（实跑数据，2026-10-08。）

文本层的 PDF 是**结构化数据**，抽取是确定性的、可以单元测试、不需要任何模型。而且它最便宜：123 token，是图片路线（337）的 2.7 分之一。

但它有一个前提，而且这个前提经常不成立：**PDF 里得有文本层。** 扫描件、截图导出的 PDF、以及很多「打印成 PDF」的报表，里面只有整页的图片，没有可抽取的文字。这种情况下 pdfplumber 会抽出空字符串，而路线 C 直接失效。

所以真正的决策不是「哪条路线更好」，而是**先判断你手上这份 PDF 属于哪一类**：

| PDF 类型 | 判断方法 | 该走哪条路 |
|---|---|---|
| 文本层 PDF | 抽取能拿到足够字符 | **C**（便宜、确定、可测） |
| 扫描 / 图片 PDF | 抽取几乎为空 | **B**（渲染成图） |
| 版面即信息（表格、表单） | 抽取出来的字符**顺序全乱** | **B**，或者 C + 版面重建 |

第三行是最容易被忽略的：文本层 PDF 抽出来的字符流，**不保留二维位置**。一张三列表格抽出来常常变成「所有第一列、所有第二列、所有第三列」这样的顺序，行列关系全丢。这种情况下「抽取成功」是个假象 —— 字符是拿到了，但结构没了。

## 路线 B 的代价与收益

图片路线贵 2.7 倍，但它换来的是**版面**。

表格的对齐、跨行单元格、印章、手写批注、复选框的勾选状态 —— 这些在文本层里要么丢失，要么变形。第 4 节会看到视觉提取的准确率实测，这里先记住结论的一半：**它相当准，但错误是偶发且静默的。**

另一个实际差别是**可验证性**。路线 C 的结果可以和源文件逐字符 diff；路线 B 的结果只能和「你以为图里写了什么」比 —— 而那个「以为」本身可能来自同一张图。所以走视觉路线时，交叉校验不是可选项（第 5 节展开）。

## 怎么用代码判断该走哪条路

判断不该靠人看，要写成函数。三个可测的判据：

**一，字符密度。** 抽出字符数 ÷ 页数。文本层 PDF 通常每页几百到几千字符，扫描件接近 0。设一个下限（比如每页 100 字符）就能把两类分开。

**二，字符的可读性。** 有些 PDF 能抽出字符，但抽出来是乱码（字体缺少正确的 ToUnicode 映射）。判据是「可打印 ASCII + 常用中文字符」的占比，低于阈值就按扫描件处理。

**三，版面结构。** 这一条最容易被跳过。抽取时保留每个词的坐标（`pdfplumber` 的 `extract_words()` 会给出每个词的 x0 / x1 / top），然后检查：按 top 分组能不能形成稳定的行？每行的词块数量是否一致？

如果一份三列表格抽出来的词块都堆在同一个 x 区间里，说明行列关系已经丢了 —— 这时该走图片路线，而不是硬解析。

三个判据都是确定性的、可单元测试的。这一点很重要：**「该走哪条路」这个判断本身不该交给模型**，否则你只是把一次静默失效换成了另一次。

## 多页文档的成本怎么算

单页的差距看起来不大（337 对 123），但多页会把它放大：

| 页数 | 图片路线 | 文本路线 | 倍数 |
|---:|---:|---:|---:|
| 1 | 337 | 123 | 2.7x |
| 10 | 3,370 | 1,230 | 2.7x |
| 50 | 16,850 | 6,150 | 2.7x |

（按本节实测的单页数字线性外推。）

倍数是固定的，但绝对量不是 —— **50 页走图片路线要 16,850 token 一次**。如果这份文档还要在 agent 循环里反复看，按第 1 节的账还要再乘轮次：20 轮的累计会到 35 万 token 量级。

所以对多页文档，**「只渲染相关页」比「选哪条路线」更重要**。分页策略的正确性依赖第 6 章的检索能力（先定位到页，再决定渲染哪几页），这也是为什么这一章放在检索与记忆之后。

## 常见坑

- **直接发 document 块就当成了。** 实测返回 HTTP 200、输入只有 59 token —— 内容被静默丢弃，模型只能说「读不到」。
- **把「200」当成「读到了」。** 这条路线把失败从协议层降级到了模型自觉性层，而模型完全可能开始编。
- **以为 PDF 一定有文本层。** 扫描件、截图导出的 PDF 抽出来是空的，这时候路线 C 直接失效。
- **抽到了文本就以为结构也对。** 三列表格抽出来的字符流往往按列堆叠，行列关系全丢 —— 那是假象，不是成功。
- **只用一条路线就上线。** 正确做法是先判断 PDF 类型再选路线，而且把判断写成代码（可测），而不是写进提示词（不可测）。
- **忘了图片路线也要按第 1 节的账算。** 337 token 是单次的两倍多，在循环里会按轮放大。
