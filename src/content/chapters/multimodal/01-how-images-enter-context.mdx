前七章都假设输入是文本。这一章开始处理另一半：**只存在于像素里的信息**。

第一个要建立的认知是：图像不是一个「附件」。

## 图像怎样进入请求

图像不是对话界面里的“附件”；在 API 请求里，它会按目标 provider 的协议，作为一类输入内容随消息提交。**消息块形状不是通用标准**：DeepSeek 的 Anthropic-compatible `/messages` 使用 `image` block，OpenAI-compatible Chat Completions 使用 `image_url`，Responses API 又使用 `input_image`。调用前要查目标 API 文档，不能把其中一家格式直接复制到另一家。[DeepSeek Vision 文档](https://api-docs.deepseek.com/guides/vision/)分别列出了这些形式；它还说明当前图像输入可用 base64、公开 URL 或 Files API `file_id`。

下面是 DeepSeek 的 Anthropic-compatible `/messages` 形状示意：

```json
[
  {
    "type": "image",
    "source": {
      "type": "base64",
      "media_type": "image/png",
      "data": "..."
    }
  },
  { "type": "text", "text": "这张图是什么颜色？" }
]
```

Base64 是把二进制编码为可打印字符的方式；编码后字节数大约增加三分之一（还未计 JSON/HTTP 的其他开销）。它不是压缩或加密。若复用图片，部分 API 提供 Files API 的 `file_id`，可以在后续请求中引用已上传文件；这减少重复传送图像字节，但**不能仅凭此推断视觉 token 或账单会下降**，要看目标 API 的 usage 与缓存语义。

在客户端维护完整历史的无状态请求里，旧图像若仍作为 inline 内容留在 messages 中，客户端通常要随完整历史再次提交它；如果删除旧图像或改为只保留文字摘要，模型就不再能直接查看那张图。服务端管理会话、文件引用和缓存则可能改变实际请求体与计费方式。先明确你的状态模型，再按真实请求记录上下文 token 和网络字节。

一个很小的历史对照曾记下纯文本 34 tokens、文本加 1×1 PNG 为 224 tokens，但两次请求的提示词也不相同（`回复「收到」` 与 `只回复「收到」`），且逐次请求、原始响应、完整 usage 与模型快照未归档。它只能作为未经独立复核的历史摘要，不能把差值 190 解释为图像的固定 token 开销，也不能称为图像信息量为零。

## URL 输入会把取图工作交给服务端

历史请求对 `https://example.com/a.png` 记录了一条 `HTTP 400`，错误文本包含 `Failed to download image from`。它能说明该次请求在取图阶段失败；当前 DeepSeek Vision 文档也明确写明，外部公开 URL 由模型服务下载。它不能证明私网地址可达，也不能证明任何 provider 都采取相同的抓取策略。

把 URL 传给 provider，本质上是把取图工作交给对方服务。不要把任意用户 URL 直接转发给外部模型服务；优先接收你控制的对象 ID，再映射到受控存储或使用 provider 的文件上传功能。如果你的应用需要自己下载用户提供的 URL，这就是你自己的 SSRF 攻击面：应限制协议与目的地，校验 DNS 解析到的目标 IP 并绑定实际连接、谨慎处理重定向，设置大小/超时限制并配合出口网络策略。单独做字符串校验或 DNS 查询不能替代连接时的目标控制。[OWASP SSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)给出了这些边界。

## 历史分辨率记录与当前 provider 估算

下表抄录自 2026-10-08 的单次调用摘要。逐次原始响应、确切 endpoint 与模型后端快照、完整 usage 和 scorer 未归档，因此无法独立重算；下表是历史观察，不是现在可依赖的 DeepSeek 计费曲线。

| 尺寸 | PNG 字节 | 历史摘要记录的 input tokens | 历史摘要记录的增量 |
|---|---:|---:|---:|
| （纯文本） | — | 34 | — |
| 64×64 | 848 | 220 | 186 |
| 256×256 | 1,899 | 220 | 186 |
| 512×512 | 3,294 | 220 | 186 |
| 640×640 | 4,441 | 310 | 276 |
| 768×768 | 5,561 | 418 | 384 |
| 896×896 | 6,740 | 544 | 510 |
| 1,024×1,024 | 7,857 | 688 | 654 |
| 1,280×1,280 | 10,658 | 1,030 | 996 |
| 1,568×1,568 | 14,338 | 1,030 | 996 |
| 2,048×2,048 | 21,895 | 1,030 | 996 |
| 3,000×3,000 | 40,642 | 1,030 | 996 |

这组摘要曾被解释为“186 的固定下限、996 的固定上限”和“每 1,600 像素约 1 token”。由于缺少原始响应和多次重复，这些模式不能作为当前 endpoint 的固定规格；一组等值也无法单独证明服务端如何缩放图像。

**截至 2026-10-22，DeepSeek 当前 Vision 文档**称图像 token 根据尺寸估算、推理前会调整图像大小：总像素较小时会放大，较大时缩放至约 1300×1300 像素规模；文档给出每图 1024 token 的上限，并明确实际用量可能与估算略有差异，应以目标 API 返回的 usage 为准。[Vision](https://api-docs.deepseek.com/guides/vision/)与[Token & Token Usage](https://api-docs.deepseek.com/quick_start/token_usage/)限定的是当前文档所述 DeepSeek API 行为，不能反推旧样本，也不能套到其他 provider。正式使用时记录每次请求的模型标识、响应模型、图片尺寸、提示词、终态和 usage；不要把 prompt cache 字段未经文档定义就与总输入字段相加。

PNG 字节数、Base64 请求体大小、视觉 token 和模型表现是不同指标。降采样或有损压缩可能减少上传字节，也可能损失小字或细节；图像 token 应按 provider 规则估算并从响应核对，业务效果则用代表性任务单独评测。替换 JPEG/PNG 编码后“token 一定不变”不是跨 provider 的保证。

## 图像在多轮请求中的影响

只有当你的客户端在每轮请求里都提交完整历史，并且旧图像仍留在历史中时，图像才会随着请求重复进入上下文。对每轮新增一个图像、并完整重发历史的简化模型，令每张图的输入用量为 `I`、每轮新增文字为 `T`、轮数为 `N`，则仅统计这些输入片段的累计 token volume：

```text
图像片段：I × N(N+1)/2
文字片段：T × N(N+1)/2
```

例如设 `I=1000`、`T=300`（**纯假设，不是价格或模型实测**）：

| 轮次 N | 图像片段累计 token volume | 文字片段累计 token volume |
|---:|---:|---:|
| 5 | 15,000 | 4,500 |
| 10 | 55,000 | 16,500 |
| 20 | 210,000 | 63,000 |

这个公式只计算新图像/文字片段在完整历史里的累计出现次数，不包含 system prompt、模型输出、工具结果、缓存、重试或 provider 的其他上下文管理；**token volume 也不等于账单**。要测费用，应按目标 provider 的 usage/缓存字段与价格文档另算。

在视觉循环里可以只保留最新截图、用文字摘要表示已完成步骤；但这会丢弃旧画面证据，不能盲目把所有截图都替换。先判断后续动作是否还需要回看旧状态，再设计保存完整图像、文件引用、截图索引或摘要的策略。状态与 messages 分开维护有助于明确哪些证据进入下一次请求：

```python
# 示例：构造数据，未实跑。messages 的图片块必须按目标 provider 的协议构造。
def build_messages(state):
    evidence = list(state["required_prior_evidence"])
    if state["latest_screenshot_b64"] is not None:
        evidence.append(state["latest_screenshot_b64"])
    return render_provider_messages(summary=state["summary"], images=evidence)

# 每轮先更新显式状态，再从状态构建新请求；
# 是否保留旧截图由任务的回看需求决定，而不是默认全部累积或全部删除。
messages = build_messages(state)
```

## 三种提供方式怎么选

DeepSeek 当前文档列出三种图像输入方式；其他 provider 的可用项可能不同：

| 方式 | 谁提供内容 | 需要核对的边界 |
|---|---|---|
| base64 / data URL | 客户端上传图像内容 | 图像格式、请求体限制和 block 形状依 endpoint 而定 |
| 外部 URL | 客户端给地址，provider 服务取图 | 只使用公开且获授权的地址；不要转发任意用户 URL |
| Files API `file_id` | 客户端先上传，再引用文件 ID | 可避免重复上传字节；token/计费语义仍按 API 文档检查 |

不要把“SDK 接受文件对象”误认为消息协议有一个通用的原始字节块。SDK 可能会代你编码或上传，实际线上格式仍由具体 API 决定。

**Base64 编码后的二进制长度约增加三分之一**，这说的是编码 payload 大小，不是视觉 token 数或费用。它可能影响请求体上限与传输时间；token 使用应按 provider 文档估算，再读取响应 usage 核对。
下面的脚本用 DeepSeek 当前 OpenAI-compatible Chat Completions 格式，对一条纯文本请求和多种尺寸的合成图像请求做一次 smoke test。每个请求使用完全相同的文字提示，结果逐次保存到 JSONL，并保留 response model、finish reason 和 API 实际返回的 usage 字段。它不是重复评测或质量评估：每个尺寸只请求一次，模型/后端仍可能变化。

**实跑状态：代码由本节离线 fake SDK 测试；未向 DeepSeek 或其他 provider 发请求。** 只有显式设置 `RUN_LIVE_IMAGE_PROBE=1` 才会执行 12 次在线请求，可能产生费用。按 DeepSeek Vision 文档安装并锁定 `openai`、`Pillow` 版本，设置 `DEEPSEEK_API_KEY`；兼容 API 的 endpoint 与格式需自行核对。

```python
"""运行单图 usage smoke test 前，必须显式设置 RUN_LIVE_IMAGE_PROBE=1。"""

import base64
import hashlib
import json
import os
from io import BytesIO
from pathlib import Path

from openai import OpenAI
from PIL import Image, ImageDraw

MODEL = os.environ.get("DEEPSEEK_MODEL", "deepseek-flash")
PROMPT = "Reply with exactly RECEIVED and nothing else."
SIZES = [
    (64, 64), (256, 256), (512, 512), (640, 640), (768, 768),
    (896, 896), (1024, 1024), (1280, 1280), (1568, 1568),
    (2048, 2048), (3000, 3000),
]
USAGE_FIELDS = (
    "prompt_tokens",
    "completion_tokens",
    "total_tokens",
    "prompt_cache_hit_tokens",
    "prompt_cache_miss_tokens",
)


def make_image(width: int, height: int) -> bytes:
    image = Image.new("RGB", (width, height), "white")
    draw = ImageDraw.Draw(image)
    for position in range(0, max(width, height), 20):
        draw.line([(position, 0), (position, height)], fill=(200, 210, 220), width=1)
        draw.line([(0, position), (width, position)], fill=(200, 210, 220), width=1)
    draw.rectangle(
        [width // 8, height // 8, width // 2, height // 2],
        outline="black",
        width=2,
    )
    draw.text((10, 10), f"TEST {width}x{height}", fill="black")
    output = BytesIO()
    image.save(output, format="PNG")
    return output.getvalue()


def make_record(route: str, width: int | None, height: int | None,
                image_bytes: bytes | None, response) -> dict:
    choice = response.choices[0] if response.choices else None
    finish_reason = getattr(choice, "finish_reason", None)
    message = getattr(choice, "message", None)
    text = getattr(message, "content", None)
    text = text if isinstance(text, str) else ""
    complete = finish_reason == "stop" and bool(text)
    usage = getattr(response, "usage", None)
    usage_record = (
        {field: getattr(usage, field, None) for field in USAGE_FIELDS}
        if usage is not None else None
    )
    return {
        "route": route,
        "width": width,
        "height": height,
        "image_bytes": len(image_bytes) if image_bytes is not None else None,
        "image_sha256": (
            hashlib.sha256(image_bytes).hexdigest()
            if image_bytes is not None
            else None
        ),
        "requested_model": MODEL,
        "response_model": getattr(response, "model", None),
        "request_id": getattr(response, "id", None),
        "finish_reason": finish_reason,
        "status": "complete" if complete else "incomplete",
        "answer": text,
        "answer_correct": complete and text.strip() == "RECEIVED",
        "usage": usage_record,
    }


def request(client: OpenAI, image_bytes: bytes | None) -> dict:
    content = [{"type": "text", "text": PROMPT}]
    if image_bytes is not None:
        encoded = base64.b64encode(image_bytes).decode("ascii")
        content.append({
            "type": "image_url",
            "image_url": {"url": "data:image/png;base64," + encoded},
        })
    return client.chat.completions.create(
        model=MODEL,
        max_tokens=16,
        messages=[{"role": "user", "content": content}],
    )


def main() -> None:
    if os.environ.get("RUN_LIVE_IMAGE_PROBE") != "1":
        raise SystemExit("Set RUN_LIVE_IMAGE_PROBE=1 to allow the 12 live requests.")
    client = OpenAI(
        api_key=os.environ["DEEPSEEK_API_KEY"],
        base_url=os.environ.get("DEEPSEEK_BASE_URL", "https://api.deepseek.com"),
    )
    output_path = Path(
        os.environ.get("IMAGE_PROBE_OUTPUT", "image-usage-results.jsonl")
    )
    with output_path.open("w", encoding="utf-8") as output:
        cases = [("text_only", None, None, None)]
        for width, height in SIZES:
            cases.append(("image", width, height, make_image(width, height)))
        for route, width, height, image_bytes in cases:
            try:
                response = request(client, image_bytes)
                record = make_record(route, width, height, image_bytes, response)
            except Exception as error:
                record = {
                    "route": route,
                    "width": width,
                    "height": height,
                    "status": "request_error",
                    "error_type": type(error).__name__,
                }
            output.write(json.dumps(record, ensure_ascii=False) + "\n")
            output.flush()
            print(route, width, height, record["status"], record.get("usage"))
    print(
        f"Per-request records saved to {output_path}; verify the API usage "
        "definition before comparing."
    )


if __name__ == "__main__":
    main()
```

结果解释时，先确认每条记录的请求完成、`finish_reason` 正常，且 `usage.prompt_tokens` 存在；缺字段应记为缺失，不能用 0 代替。比较图像与文本请求时，这个差值仍同时受输入封装与服务端预处理影响，不等同于普遍图像 token 价格。完整结论需要多次重复、多个代表性图像、任务质量判分、目标 endpoint 文档与响应记录。

## 常见坑

- **把一种 provider 的消息格式当成通用协议。** Anthropic-compatible `image`、Chat Completions 的 `image_url` 与 Responses API 的 `input_image` 形状不同，先核对目标 endpoint 文档。
- **把历史 token 摘要当当前成本曲线。** 2026-10-08 的 186/996 tokens 缺逐次记录，不能拿来当固定下限/上限；查询当前估算并保留真实 usage。
- **把 prompt cache 字段随意相加。** 只有当目标 API 文档明确字段含义时才能计算总输入或账单；缺字段不等于零。
- **把用户 URL 直接转给 provider。** 远端 URL 取图是服务端 fetch；使用授权且公开的对象地址，或走受控文件上传。应用自己抓取 URL 时，必须把它当 SSRF 面保护。
- **假定 stateless 请求每次都必须重传 inline 图片，或假定文件引用能省 token。** 依据具体 API 的会话、Files API 与缓存语义区分 request bytes、上下文 token 和实际费用。
- **把输入 token volume 直接等同账单。** 缓存计费、输出、重试和价格规则需要分开核对。
