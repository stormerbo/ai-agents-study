## 历史摘要：重复提取差异能发现什么

最直觉的校验策略是「同一张图多跑几次，不一致的地方就是可疑的」。这个说法听起来合理，但没人告诉你它能抓住多少。

历史摘要称曾对一张 120 行合成表做三次提取并逐格比对（360 个答案键单元格）；但请求/响应、精确 endpoint/model、完整 scorer 和随机性参数未归档，以下比例不能独立复算或代表当前模型：

| 指标 | 数值 |
|---|---:|
| 第 1 / 2 / 3 次各自的错误格数 | 6 / 9 / 8 |
| 三次里出过错的格数（并集） | **12 / 360（3.3%）** |
| 「三次结果不一致」标记出的格数 | 8 |
| 其中真的错了 | 8 |
| **召回率**（抓到多少真错） | **67%** |
| **精确率**（标记出来的有多少是真错） | **100%** |

（2026-10-08 历史摘要，标记为 deepseek-flash；未归档逐次原始响应/模型快照/scorer，不能独立复核。）

这两个历史指标的定义不同，但原始记录缺失，不能据此比较策略效果。

这组历史摘要里，8 个被标记的格子恰好都在答案键比较中判错，但样本很小、评分与逐次响应未归档，不能证明策略在其他图像上也有 100% 精确率。实际系统应把不一致视为复核信号，而不是已确认错误；还要用独立信源检查一致但错误的结果。

历史摘要称，12 个错误格中有 4 个三次都以同样方式出错；因原始轨迹缺失，这一比例也不可复核。它只能用来说明一种可能的失效模式：稳定偏差会通过重复一致性检查。

## 为什么会有「每次都错成一样」

这一失效模式比不可复核的历史比例更值得纳入设计考虑。

想象某个单元格的字形在渲染或缩放时正好落在一个临界点上：那一笔的闭合被抹掉了，于是「8」稳定地看起来像「6」。这种情况下：

- 第一次读成 6
- 第二次读成 6
- 第三次还是读成 6

**三次完全一致，一致性校验完全失明。** 而它恰恰是最容易被信以为真的情况 —— 因为你验证过了，三次都一样。

所以必须把这句话写进任何用视觉做数据提取的设计里：**一致 ≠ 正确。** 一致性校验能发现「不稳定的错」，发现不了「稳定的错」。

## 组合校验策略

可以按信源独立性与错误影响来设计校验；以下是工程决策顺序，不是经本节实验验证的效果排名：

**一，先问「这份信息有没有非视觉的来源」。** 如果有可信且语义匹配的数据库、API 或原始文本，优先将它作为校验依据；视觉可用于补充版面和图像特有的信息。所谓“独立”要检查来源链，复制自同一错误记录的数据不构成独立证据。

**二，加可计算的内部一致性。** 表格里的合计、行数、字段和、编号连续性 —— 这些都是代码能算的，而错一个数就会破坏它们。注意合计本身也可能被读错，所以它降低了风险但没有消除风险。

写成函数是这样（合计一栏必须来自**独立信源**，理由见下）：

```python
from decimal import Decimal, InvalidOperation


def nonnegative_int(value):
    if isinstance(value, bool):
        return None
    if isinstance(value, int) and value >= 0:
        return value
    if isinstance(value, str) and value.isdecimal():
        return int(value)
    return None


def finite_decimal(value):
    if isinstance(value, (bool, float)) or value is None:
        return None
    try:
        amount = Decimal(str(value))
    except (InvalidOperation, TypeError, ValueError):
        return None
    return amount if amount.is_finite() else None


def check_consistency(rows, id_start=101, expect_rows=120,
                     total_qty=None, total_amount=None):
    """rows: [(item, qty, amount), ...]；合计必须来自独立信源。"""
    errs = []
    expected_count = nonnegative_int(expect_rows)
    start = nonnegative_int(id_start)
    if expected_count is None:
        return ["expect_rows 必须是非负整数"]
    if start is None:
        return ["id_start 必须是非负整数"]
    if not isinstance(rows, (list, tuple)):
        return ["rows 必须是列表或元组"]
    if len(rows) != expected_count:
        errs.append("行数 %d != %d" % (len(rows), expected_count))

    parsed = []
    for i, row in enumerate(rows):
        row_number = i + 1
        if not isinstance(row, (list, tuple)) or len(row) != 3:
            errs.append("第 %d 行必须包含 3 个字段" % row_number)
            continue
        item, raw_qty, raw_amount = row
        expected_id = "ITM-%03d" % (start + i)
        if item != expected_id:
            errs.append("第 %d 行编号是 %s，应为 %s" % (
                row_number, item, expected_id
            ))

        qty = nonnegative_int(raw_qty)
        if qty is None:
            errs.append("第 %d 行 qty 必须是非负整数" % row_number)
        amount = finite_decimal(raw_amount)
        if amount is None:
            errs.append("第 %d 行 amount 必须是有限十进制数" % row_number)
        elif amount.quantize(Decimal("0.01")) != amount:
            errs.append("第 %d 行 amount 最多保留两位小数" % row_number)
        if qty is not None and amount is not None:
            parsed.append((qty, amount))

    all_rows_valid = len(parsed) == len(rows)
    if total_qty is not None:
        expected_qty = nonnegative_int(total_qty)
        if expected_qty is None:
            errs.append("total_qty 必须是非负整数")
        elif all_rows_valid:
            actual_qty = sum(qty for qty, _ in parsed)
            if actual_qty != expected_qty:
                errs.append("qty 合计 %d != %d（差 %d）" % (
                    actual_qty, expected_qty, actual_qty - expected_qty
                ))
    if total_amount is not None:
        expected_amount = finite_decimal(total_amount)
        if expected_amount is None:
            errs.append("total_amount 必须是有限十进制数")
        elif expected_amount.quantize(Decimal("0.01")) != expected_amount:
            errs.append("total_amount 最多保留两位小数")
        elif all_rows_valid:
            actual_amount = sum(
                (amount for _, amount in parsed), Decimal("0.00")
            )
            if actual_amount != expected_amount:
                errs.append("amount 合计 %.2f != %.2f" % (
                    actual_amount, expected_amount
                ))
    return errs
```

内部一致性规则能发现部分错误，但存在盲区：行数和编号检查不能发现合法范围内的错值；合计比较可能发现部分数值错误，却无法定位单元格，且不同错误可能相互抵消。金额汇总应使用十进制定点运算，并先验证字段形状、类型和范围。旧档案曾记录 2026-10-12 的答案键与错误注入汇总，但对应 fixture 与逐项运行记录不完整，本节不再把该汇总呈现为可复核结果。

**三，跑多次比对差异。** 历史摘要报告召回 67%、精确率 100%，但不能独立复核，也不代表新任务的表现。重复调用可能增加延迟与计费用量，实际影响取决于 provider 的状态、缓存和计费规则；先在代表性样本上记录每次请求与 usage，再决定是否只用于高风险字段。

**四，抽样人工复核。** 抽样可以发现部分系统性问题，但没有一个通用的 5% 比例能保证发现某类错误。按字段风险、预期错误率、分层结构和可接受漏检风险确定样本量；高影响记录应设置逐条复核或独立信源核验。

**这几种措施要按任务组合。** 先确认是否存在可信的非视觉信源，再根据业务风险组合结构校验、重复提取和人工复核；各措施能发现的错误类型不同，不能仅按一个固定比例或成本顺序替代设计。

## 接进循环时要注意的两件事

**第一，控制输出预算并检查 stop_reason。** 大表输出可能被截断。处理每次响应时都要检查终止原因、JSON 完整性、精确行数和字段 schema；缺字段或终止状态不完整时应进入失败/复核路径。旧摘要记载曾遇到截断，但原始响应未归档，不能据此判断原因就是预算不足。

**第二，把校验放在代码里，不要放在提示词里。** 「请你仔细核对每个数字」这类指令无法验证是否被执行；而「三次结果不一致就送复核」可以用代码实现并单元测试；本地测试能验证标记逻辑，不能验证模型输出的准确率。第 5 章那条规律在这里同样成立：**能由代码算的，不要让模型保证。**

## 本节小结

1. **历史摘要报告精确率 100%，但不可独立复核。** 不一致应作为复核信号，不能直接判定错误。
2. **历史摘要报告召回率 67%，同样不可独立复核。** 稳定错成同一个值的格子可能漏过一致性检查。**一致 ≠ 正确。**
3. **可信的独立信源通常能提供更直接的交叉核验**；仍需验证其来源、字段映射和时效性。
4. **校验必须写在代码里**，并且要检查 stop_reason —— 截断的 JSON 会被误读成提取失败。

## 什么时候该用视觉

把这一章的五节合起来，就是一个可执行的选择规则。三个问题，按顺序问。

**第一个问题：这份信息能不能用文本拿到？**

能从数据库、API、HTML 或 PDF 抽取与任务相符的字段时，先评估可验证的文本/结构化路线；是否更省 token 或费用取决于具体 provider、抽取结果和 usage，不能用第 2 节未归档的 123/337 token 摘要作通用对比。图像路线适合文本抽取无法提供的版面信息，但输出仍需字段级校验与可信证据。

拿不到（截图、扫描件、照片、只有版面才携带信息的表格）才进入下一步。

**第二个问题：视觉的结果会被用来做什么？**

如果只是「看个大概」—— 界面上有没有报错、这张图大致是什么内容 —— 单次视觉可能足够；是否满足质量门槛、成本是否可接受，应按目标任务与 provider 用量判断。

如果要进入计算或写进数据库（金额、数量、编号），就必须有校验，而且**优先去找非视觉信源**。进入数据库或触发业务动作前，应按错误影响设置验收门槛，并使用可审计的字段校验、可信来源核对或人工审批。第 4 节的历史错误率与本节多次比对比例均缺少可复核记录，不能用来量化当前风险。

**第三个问题：一次要看多少、要看几遍？**

单张、低频与多图/循环观察应按目标 API 的图像估算器和响应 usage 评估；第 1 节 186–996 token 是缺少逐次原始记录的历史摘要，不能当当前固定区间。客户端若每轮重发完整历史，历史内容可能反复计入请求上下文；文件引用、缓存和服务端会话会改变字节传输与费用，需分别核对。OpenAI Responses API 支持 `previous_response_id` 链接对话状态，但[当前文档](https://developers.openai.com/api/docs/guides/conversation-state)明确说明，响应链中先前的输入 token 仍按 input tokens 计费。这个规则只说明 OpenAI API 的行为，不能直接推断其他 provider 的图像处理、上下文或账单。

三句话可以记成：**能用文本就别用视觉；用了视觉就别把它当唯一信源；要反复看就先算成本。**

这三条是本章的工程建议；相关历史数字缺少可复核的原始记录，不能用于量化当前模型或业务的错误率。如果只能记住一句，就记住：**格式正确不等于内容正确，重复一致也不等于有独立证据。** 本章历史摘要不足以量化当前模型的错误率；生产流程应保留原始输入、逐字段证据、校验结果与人工处置记录。

下面的离线例子只验证“不同结果会被标记”这段确定性逻辑。它使用构造数据，不调用模型，也不估计真实视觉错误率。

```python
expected = {"A": "18", "B": "42", "C": "105"}
runs = [
    {"A": "18", "B": "42", "C": "105"},
    {"A": "18", "B": "47", "C": "105"},
    {"A": "18", "B": "42", "C": "105"},
]

def disagreements(records):
    keys = set().union(*(record.keys() for record in records))
    return {key for key in keys if len({r.get(key) for r in records}) > 1}

flagged = disagreements(runs)
print("需复核:", sorted(flagged))
# -> 需复核: ['B']

# 若三次稳定地读错为同一值，差异检测不会标记它。
stable_wrong = [{"A": "16"}] * 3
print("稳定错误需复核:", sorted(disagreements(stable_wrong)))
# -> 稳定错误需复核: []
```

这个 fixture 的输出是代码逻辑的演示，不是模型实验。真实任务还应校验缺失键、额外键、类型、范围、终止状态和来源证据，并将无效或截断响应送入失败处理。

## 常见坑

- **把「跑多次结果一致」当成「读对了」。** 历史摘要称 12 格错误里有 4 格每次错得一模一样；这一数字未独立复核，一致性校验完全抓不到。
- **全表机械地增加重复调用。** 历史摘要的召回值不能外推，且调用次数不等同于实际计费倍数；先在本环境测 usage、延迟和错误类型，再决定是否重复提取。
- **用提示词要求模型「仔细核对」。** 无法验证是否执行。校验要写成代码。
- **忘了查 stop_reason。** 密集表格的 JSON 输出可能被截断；每次调用都应先检查终止原因与 schema 完整性。旧历史摘要称曾遇到截断，但原始响应未归档。
- **直接跳到人工复核而不先问「有没有独立信源」。** 多数情况下那份数据本来就在数据库里 —— 先问这一句，能省掉整套校验。
- **把视觉当唯一信源还要求高准确率。** 第 4 节的错误率是不可独立复核的历史摘要，不能作为当前任务的风险估计。应按业务后果设定字段级验收和复核策略。
