Plan-Execute（先规划、后执行）是把一次任务拆成两段：模型先提出一份计划，宿主程序检查并执行计划，再根据执行结果决定是否综合、继续或重规划。把它想成后端服务消费一份由外部提交的工作清单：清单是输入数据，不是可直接信任的程序，也不是已经完成的业务事实。

“先列出全部步骤”不是所有 Plan-Execute 的共同实现。计划可以是线性列表、有依赖关系的有向无环图（DAG），也可以包含条件路由或阶段边界；宿主也可以在步骤执行后重新询问模型。真正需要设计的是计划允许表达什么、谁判断下一步、每一步执行前检查什么，以及新观察何时使旧计划失效。

## 先拆清三个控制流

设计一个天气查询任务：查北京和上海明天的最高温，再查温度较高城市后天的最高温。设北京明天 31°C、上海明天 27°C。第一批查询可以预先写出，但第三步的 `city` 要等到观测返回后才能确定。

这是一个依赖，不等于只能使用 ReAct。至少有三种实现：

1. **静态计划**：把已知的独立查询列出来，执行器验证后执行。若后续参数未知，执行器应暂停在边界，不能把描述句当成城市名。
2. **代码条件路由**：先执行两个查询，再由确定性代码根据结构化结果挑出较高温城市，生成第三步。步骤图里可以有条件边；分支由代码根据状态计算。
3. **模型重规划 / ReAct**：把新观察交给模型，让它提出下一步动作。宿主仍需验证动作、授权工具并决定是否执行。

LangGraph 的 [条件边 API](https://reference.langchain.com/python/langgraph/graph/state/StateGraph/add_conditional_edges) 就是图状态上的条件路由 API；因此“DAG 无法表达分支”是错误的。一个依赖图可以无环，同时让路由函数按状态选择下一节点。只有当分支判据本身需要模型基于新观察做语义判断时，才需要模型参与该决策。即便如此，模型提出动作也不代表动作获得授权。

## 历史记录能支持什么

下表来自 2026-10-09 的旧摘要，声称每个条件各运行 3 次。原始逐次请求、响应、精确模型快照和完整评分记录没有归档，所以它们只能作为待复核历史，不足以估计准确率或推广成本。

| 任务 / 方案 | 旧摘要 | 可保留的边界 |
|---|---:|---|
| T2 ReAct | 旧启发式检查器 3/3；平均 1,971 token | 评分器只看答案子串与调用列表；不能确认答案映射正确 |
| T2 Plan-Execute | 旧启发式检查器 0/3；平均 3,087 token | 曾记录非法 `city` 参数样例；不能断言最终答案全错或普遍更贵 |
| T1 Plan-Execute / ReAct | 旧 token 摘要 506 / 1,203 | 没有逐次 usage，不能归因于范式本身 |

旧记录中的三个 `city` 值分别写成“北京或上海中明天最高温更高的城市”“北京和上海中明天最高温更高的城市”及一个字符串形式的三元表达式。它们展示了一个有用的接口错误形状：把待计算的表达式塞进要求具体枚举值的字段。原始 response 不在归档中，不能再把这些字符串当作可复核的模型原始输出，也不能以它们证明某一范式失败。

## 计划需要四种不同检查

JSON Schema 可以检查字段、类型与枚举；它不能单独证明计划覆盖了用户请求、依赖顺序正确、前提仍然新鲜或副作用获准。把这四类检查拆开，避免“JSON 合法”被误读成“可以安全执行”。

| 检查 | 要回答的问题 | 例子 |
|---|---|---|
| 结构 | 形状、必填字段、ID 是否符合约定？ | `depends_on` 是数组，step ID 唯一 |
| 可执行性 | 工具、参数、依赖是否在宿主能力范围内？ | `city` 属于宿主维护的城市表；引用的依赖 ID 存在 |
| 完整性 | 计划是否覆盖任务要求、满足结果不变量？ | 两个基线查询和最终温差都被计算 |
| 运行时授权 / 前提 | 此刻是否允许执行，原先观察是否仍有效？ | 用户权限仍有效；写操作基于当前版本且幂等键一致 |

下面的 JSON 是给读者看的产物示例，数据与步骤是构造内容，尚未执行：

```json
{
  "steps": [
    {"id": "bj-tomorrow", "tool": "get_weather", "city": "北京", "day": "明天", "depends_on": []},
    {"id": "sh-tomorrow", "tool": "get_weather", "city": "上海", "day": "明天", "depends_on": []}
  ],
  "after_observation": "由宿主比较两项结果，再路由到胜出城市的后天查询"
}
```

这里没有让模型生成可执行代码或任意表达式。宿主只接受预先定义的工具和参数类型；“选择胜者”也不是传给天气工具的 `city` 字符串。若模型需要表达复杂条件，可用受限的条件 DSL，并为每个条件规定可引用字段、比较操作、类型和失败行为；不要用 `eval` 执行模型生成的表达式。

## 从校验到执行：本地离线例子

下面的完整 Python 例子用构造数据演示（实跑状态：Python 3.14.7，本地离线执行，2026-10-21）：先校验整份计划，再执行；依赖图由宿主拓扑排序；尚未知道的分支则在观察返回后用普通代码选择。它不调用模型、网络或真实天气服务，因此只验证本地控制逻辑，不代表模型或框架行为。

```python
"""Synthetic Plan-Execute fixture: Python 3 standard library only."""
from collections import deque

TEMPERATURES = {
    ("北京", "明天"): 31,
    ("上海", "明天"): 27,
    ("北京", "后天"): 24,
    ("上海", "后天"): 26,
}
ALLOWED_CITIES = {"北京", "上海"}
ALLOWED_DAYS = {"明天", "后天"}
TOOL = "get_weather"


def validate_plan(plan):
    if not isinstance(plan, list) or not plan:
        raise ValueError("plan must be a non-empty list")
    by_id = {}
    for step in plan:
        if not isinstance(step, dict) or set(step) != {
            "id", "tool", "city", "day", "depends_on"
        }:
            raise ValueError("step shape is invalid")
        step_id = step["id"]
        if not isinstance(step_id, str) or not step_id:
            raise ValueError("step id is invalid")
        if step_id in by_id:
            raise ValueError("duplicate step id")
        if step["tool"] != TOOL:
            raise ValueError("unknown tool")
        if step["city"] not in ALLOWED_CITIES or step["day"] not in ALLOWED_DAYS:
            raise ValueError("arguments are outside the host allowlist")
        if not isinstance(step["depends_on"], list) or not all(
            isinstance(dep, str) for dep in step["depends_on"]
        ):
            raise ValueError("depends_on must be a list of step ids")
        by_id[step_id] = step

    indegree = {step_id: 0 for step_id in by_id}
    children = {step_id: [] for step_id in by_id}
    for step_id, step in by_id.items():
        for parent in step["depends_on"]:
            if parent not in by_id:
                raise ValueError("unknown dependency")
            indegree[step_id] += 1
            children[parent].append(step_id)

    ready = deque(step_id for step_id, degree in indegree.items() if degree == 0)
    order = []
    while ready:
        current = ready.popleft()
        order.append(current)
        for child in children[current]:
            indegree[child] -= 1
            if indegree[child] == 0:
                ready.append(child)
    if len(order) != len(plan):
        raise ValueError("dependency cycle")
    return by_id, order


def execute_plan(plan, calls):
    by_id, order = validate_plan(plan)  # whole-plan validation precedes dispatch
    results = {}
    for step_id in order:
        step = by_id[step_id]
        if any(dep not in results for dep in step["depends_on"]):
            raise RuntimeError("dependency result is unavailable")
        calls.append((step["tool"], step["city"], step["day"]))
        results[step_id] = TEMPERATURES[(step["city"], step["day"])]
    return results


def make_step(step_id, city, day, depends_on=None):
    return {
        "id": step_id,
        "tool": TOOL,
        "city": city,
        "day": day,
        "depends_on": [] if depends_on is None else depends_on,
    }


def main():
    calls = []
    first_phase = [
        make_step("bj", "北京", "明天"),
        make_step("sh", "上海", "明天"),
    ]
    observations = execute_plan(first_phase, calls)

    # The condition is known only now; host code owns this deterministic route.
    winner_id = max(observations, key=observations.get)
    winner_city = {"bj": "北京", "sh": "上海"}[winner_id]
    second_phase = [make_step("winner-next-day", winner_city, "后天")]
    final_observation = execute_plan(second_phase, calls)["winner-next-day"]
    print("winner=%s; tomorrow=%dC; next_day=%dC" % (
        winner_city, observations[winner_id], final_observation
    ))
    print("host tool calls=%d; providerCalls=0; externalNetworkCalls=0" % len(calls))

    invalid_batch = [
        make_step("valid-first", "北京", "明天"),
        make_step("invalid-second", "北京或上海中较高的城市", "后天"),
    ]
    before = list(calls)
    try:
        execute_plan(invalid_batch, calls)
    except ValueError as exc:
        assert calls == before  # no partial dispatch when any step is invalid
        print("invalid batch rejected before dispatch: %s" % exc)
    else:
        raise AssertionError("invalid plan was accepted")

    cycle = [
        make_step("a", "北京", "明天", ["b"]),
        make_step("b", "上海", "明天", ["a"]),
    ]
    before = list(calls)
    try:
        execute_plan(cycle, calls)
    except ValueError as exc:
        assert calls == before
        print("cyclic plan rejected before dispatch: %s" % exc)
    else:
        raise AssertionError("cyclic plan was accepted")


if __name__ == "__main__":
    main()
```

```text
winner=北京; tomorrow=31C; next_day=24C
host tool calls=3; providerCalls=0; externalNetworkCalls=0
invalid batch rejected before dispatch: arguments are outside the host allowlist
cyclic plan rejected before dispatch: dependency cycle
```

这是构造 fixture 的真实本地输出；三次调用只表示本地字典查找，不是模型往返、线上 API 请求或端到端成功率。执行器本例串行处理拓扑序，生产系统可将同一就绪层的独立步骤并发调度，但必须另外处理限流、部分失败、取消和结果汇合；拓扑排序本身不提供并发安全或事务语义。

## 运行时要防止过期与重复副作用

结构正确的计划也可能不完整：模型可以漏掉要求的检查，或者在重规划时忘记前面已完成的工作。因此，计划执行前还要用任务级不变量验证覆盖范围；执行后要验证最终答案满足业务条件。示例里的城市 allowlist 只能检查参数形状与许可范围，不能证明选出的城市符合用户要求。

计划也会过期。查询结果、权限、库存、文件版本、审批状态可能在生成计划后发生变化。每个可能改变外部状态的步骤应在执行时重新检查必要前提；若前提失效，暂停并明确地重新规划。不能靠“模型记得最初计划”解决状态漂移，也不应将旧计划中未完成的副作用盲目重放。

执行中断时，要区分“未执行”“执行成功但响应丢失”和“结果未知”。对写操作，使用业务幂等键、持久化每步状态，并在重试前对账；计划 step ID 可用于追踪，但它本身不是外部系统支持的幂等保证。执行审批、租户隔离、权限撤销和预算也必须在副作用发生时检查，而不是只在计划生成时检查。

把进度存成宿主维护的状态，而不是在每次重试时重新读一遍计划并从第一步开跑。最小记录通常需要任务 ID、计划版本、step ID、输入摘要、状态、尝试次数、结果引用和更新时间。状态至少要能区分尚未开始、正在执行、成功、确定失败、结果未知与因前置条件跳过；如果把“请求超时”一律记成失败，恢复程序就可能重复触发已经成功的副作用。

例如发送退款请求后连接断开，客户端不知道服务端是否已经提交。此时把 step 标记为 `unknown`，先用业务订单号或接收方提供的操作键查询结果；查到已提交就补录结果，查到未提交且可安全重试时才重放，仍不能确定就暂停并转人工或对账流程。计划版本更新时，保留旧版本和已经完成的步骤，只将依赖变更部分重新校验；不要悄悄覆盖历史计划，否则无法解释哪些动作依据哪个假设执行。

检查点不等于授权记录：权限可能被撤销，记录也可能过时。执行器应在每个敏感副作用前用当前调用者身份重查资源范围、审批状态和动作限额，并把拒绝原因写入可追踪事件。读操作也可能泄露跨租户数据，所以“无副作用”不代表“无安全影响”。这些机制需要与实际工具的事务边界和幂等契约对齐；离线示例没有验证这些生产性质。

## 何时静态计划值得用

先列出待解决的依赖，再判断哪一层负责路由：若下一步的输入已经确定，静态计划让执行前审查与批次校验更直接；若分支能从明确状态机械计算，使用代码条件路由；若要根据新观察作开放式判断，才让模型提出新动作或计划。三种方式可以组合，不存在由“线性/非线性”直接推出哪种范式更准、更便宜的普遍规则。

真正的比较单位是同一任务与同一成功标准下的端到端 trace：用户请求、模型计划、每次观察、工具参数、执行结果、重规划、最终答案、usage 和失败原因都要保留。评测要同时检查答案、调用轨迹和业务不变量；只检查输出里出现某个城市或温度，会把字段对应错误也算成功。历史 T1/T2 的逐次 trace 未归档，无法据旧摘要重算这类比较。

[Anthropic 的 Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 与 LangGraph 条件边文档可帮助理解实现形状，但它们不证明某种模式在你的任务上更便宜或准确。选型后仍要用目标任务、生产授权边界、超时/重试语义和可恢复性做评测。本文示例仅验证宿主侧计划校验和确定性路由，不验证模型规划质量、LangGraph 运行行为或生产系统的恢复保证。
