ReAct 是 **Reasoning + Acting**。原论文把模型生成的推理轨迹与动作交替起来，让环境返回的观察能够进入下一轮生成；这里的“推理文本”是模型输出，不等于完整、可信的内部推理。工程上最重要的变化不是多了一种工具协议，而是把“根据新观察选下一步”放进一个循环。

现代工具 API 中，模型提出工具调用，宿主解析并决定是否执行；执行结果再回到对话。模型可以提出动作或结束信号，但身份、授权、参数校验、预算、工具执行和任务验收仍由宿主控制。[ReAct 原论文](https://arxiv.org/abs/2210.03629)描述的是思考与行动交替的任务方法；下面的工具协议示例则是一个离线教学夹具，不是论文复现，也不是任何 provider 的性能测试。

## 一轮循环里有哪些东西

一次模型响应不一定等于一次工具调用：一个响应可能提出多个工具调用，也可能不含工具调用而正常结束。实现时把不同计数分开：

- **模型回合**：宿主向模型请求并收到响应的次数。
- **工具调用**：宿主实际准许并执行的动作数；一回合可以是 0、1 或多次。
- **任务完成**：满足业务验收条件的任务数。`end_turn` 只表示模型结束当前生成，不证明答案正确或任务已完成。

对 Anthropic Messages API，`stop_reason=tool_use` 表示响应请求客户端工具；宿主执行后用对应的 `tool_use_id` 回填 `tool_result`。`end_turn` 表示自然结束；`max_tokens` 与 `model_context_window_exceeded` 是不完整状态；`refusal` 是拒绝；`pause_turn` 用于服务端工具循环，不是客户端 `tool_use` 的替代值。枚举和恢复动作属于 API 契约，其他 provider 需单独适配，未知值不能默认当作成功。[Anthropic stop reasons 文档](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)

| 响应状态 | 宿主应该做什么 | 不应该据此推出什么 |
|---|---|---|
| `tool_use` | 校验整批调用，再逐个授权、限额、执行，并按 ID 回填结果 | 模型有权直接执行动作 |
| `end_turn` | 抽取最终候选，再按任务契约校验 | 任务已正确完成；文本一定非空 |
| `max_tokens` / 上下文超限 | 标记不完整，按策略失败、续写或重试 | 这是 JSON 格式错误或模型能力结论 |
| `refusal` / 未知值 | 进入拒绝或未知状态处理 | 可以继续执行残缺工具块 |
| `pause_turn` | 仅对支持服务端工具的 API 按其契约继续 | 等同客户端工具调用 |

## 什么时候循环有帮助，什么时候会失效

如果下一步依赖尚未得到的工具结果，逐步决策可能比执行一个预先写死的计划更直接。例如先查两个城市的明日温度，再根据比较结果决定查哪个城市的后天温度。若分支能够由确定性代码直接计算，就应比较代码路由与模型决策；ReAct 本身不保证更准确、更快或更便宜。

循环还会带来一组宿主必须处理的失败路径：

1. **无进展重复**：模型连续提出相同动作，工具每次返回相同观察。指纹或业务状态可用于检测，但重复读取有时是合法的；重复规则只能作为策略信号，不能代替最大回合、最大工具调用、截止时间和资源预算。
2. **错误结果被当成事实**：工具失败若被包装成普通成功结果，模型可能继续基于错误状态行动。协议支持时应显式标记工具错误，并返回可操作、经过脱敏的错误信息。
3. **过早结束或空答案**：模型可能在验收条件满足之前结束；某些 API 也允许空的自然结束响应。宿主需要独立的完成校验，空响应应单独处理。
4. **上下文和费用增长**：若调用方每轮重发完整历史，输入处理量会随历史增长；缓存、服务端会话、截断策略和 provider 计费语义会改变实际测量。应从目标 endpoint 的 usage 与账单测量，不能把轮数直接当 token 或费用。

历史记录曾报告一个线性任务 2 个模型回合、条件任务 3 个模型回合，以及一个卡住样本 8 回合、5,926 token；同一摘要还把正常线性任务记为 1,296 token。这些数字缺少逐次请求/响应、模型快照、usage 原件和评分器，**无法独立复算**。它们只留下待检验的现象线索，不支持“ReAct 必然几步完成”“失败成本是成功的固定倍数”或生产失败率结论。下面的离线夹具会展示相似的控制流形状，但其合成结果不能验证这些历史观察。

## 从响应到动作：先校验整批，再执行

执行前的顺序很重要。先检查 stop 状态，再解析完整工具批次；确认所有 ID 唯一、工具名和参数符合允许范围，并且整批不超过剩余预算，然后才能开始 dispatch。否则一个坏 ID、未知工具或预算超限，可能在一部分副作用已经发生之后才被发现。真实系统还要处理取消、超时、重放安全、授权撤销和部分执行；此处只用只读天气查询演示校验边界。

## 完整可运行代码：离线控制流夹具

**实跑状态：Python 3.14.7，本地离线执行**。示例使用固定的 `FakeProposer` 产生响应，不会联网，也不会调用模型。天气数据、模型响应和输出答案都是合成夹具，因此可用来验证宿主分支与评分器，不能作为模型质量证据。

```python
import json

WEATHER = {
    ("北京", "明天"): 31,
    ("上海", "明天"): 27,
    ("北京", "后天"): 24,
}

def get_weather(city, day):
    value = WEATHER.get((city, day))
    if value is None:
        return {"error": "没有对应天气记录"}
    return {"city": city, "day": day, "temp_c": value}

class FakeProposer:
    """逐次返回预置的 API 形状响应；耗尽时显式报错。"""
    def __init__(self, responses):
        self.responses = list(responses)

    def __call__(self, _history):
        if not self.responses:
            raise RuntimeError("合成响应耗尽")
        return self.responses.pop(0)

def tool_call(call_id, city, day):
    return {
        "type": "tool_use",
        "id": call_id,
        "name": "get_weather",
        "input": {"city": city, "day": day},
    }

def run_react(proposer, max_turns, max_tool_calls, dispatch_log=None):
    """演示宿主控制；真实应用还须接入身份授权、deadline 与任务验收。"""
    history = []
    executed = []
    last_batch = None
    turns = 0
    log = dispatch_log if dispatch_log is not None else []

    while turns < max_turns:
        turns += 1
        response = proposer(history)
        reason = response.get("stop_reason")
        blocks = response.get("content", [])

        if reason == "end_turn":
            answer = "".join(
                block.get("text", "")
                for block in blocks
                if block.get("type") == "text"
            ).strip()
            status = "candidate_response" if answer else "completed_without_text"
            return {
                "status": status, "answer": answer,
                "turns": turns, "tool_calls": len(executed),
            }
        if reason in ("max_tokens", "model_context_window_exceeded"):
            return {"status": "incomplete", "turns": turns, "tool_calls": len(executed)}
        if reason == "refusal":
            return {"status": "refused", "turns": turns, "tool_calls": len(executed)}
        if reason != "tool_use":
            return {"status": "unknown_stop", "turns": turns, "tool_calls": len(executed)}

        calls = [block for block in blocks if block.get("type") == "tool_use"]
        ids = [call.get("id") for call in calls]
        if (
            not calls
            or any(not isinstance(call_id, str) or not call_id.strip() for call_id in ids)
            or len(set(ids)) != len(ids)
        ):
            return {"status": "invalid_tool_batch", "turns": turns, "tool_calls": len(executed)}

        normalized = []
        for call in calls:
            args = call.get("input")
            if (
                call.get("name") != "get_weather"
                or not isinstance(args, dict)
                or set(args) != {"city", "day"}
                or (args.get("city"), args.get("day")) not in WEATHER
            ):
                return {"status": "invalid_tool_batch", "turns": turns, "tool_calls": len(executed)}
            normalized.append((args["city"], args["day"]))

        # 整批预算预检，避免超限时先执行部分调用。
        if len(executed) + len(calls) > max_tool_calls:
            return {"status": "tool_budget_exhausted", "turns": turns, "tool_calls": len(executed)}

        # 精确重复只是一个无进展信号；生产策略需考虑合法重复读取的场景。
        if normalized == last_batch:
            return {"status": "repeated_action", "turns": turns, "tool_calls": len(executed)}
        last_batch = normalized

        results = []
        for call in calls:
            args = call["input"]
            log.append({"name": call["name"], "input": dict(args)})
            result = get_weather(**args)
            executed.append(call)
            results.append({
                "type": "tool_result",
                "tool_use_id": call["id"],
                "content": json.dumps(result, ensure_ascii=False),
                "is_error": "error" in result,
            })
        history.extend([{"role": "assistant", "content": blocks}, {"role": "user", "content": results}])

    return {"status": "turn_budget_exhausted", "turns": turns, "tool_calls": len(executed)}

def main():
    linear = FakeProposer([
        {"stop_reason": "tool_use", "content": [
            tool_call("a1", "北京", "明天"),
            tool_call("a2", "上海", "明天"),
        ]},
        {"stop_reason": "end_turn", "content": [{
            "type": "text",
            "text": '{"beijing":31,"shanghai":27}',
        }]},
    ])
    conditional = FakeProposer([
        {"stop_reason": "tool_use", "content": [
            tool_call("b1", "北京", "明天"),
            tool_call("b2", "上海", "明天"),
        ]},
        {"stop_reason": "tool_use", "content": [
            tool_call("b3", "北京", "后天"),
        ]},
        {"stop_reason": "end_turn", "content": [{
            "type": "text",
            "text": '{"extra_city":"北京","extra_temp_c":24}',
        }]},
    ])
    repeating = FakeProposer([
        {"stop_reason": "tool_use", "content": [tool_call("c1", "北京", "明天")]},
        {"stop_reason": "tool_use", "content": [tool_call("c2", "北京", "明天")]},
    ])
    truncated = FakeProposer([
        {"stop_reason": "max_tokens", "content": []},
    ])

    for label, proposer in (
        ("linear", linear),
        ("conditional", conditional),
        ("repeating", repeating),
        ("truncated", truncated),
    ):
        print(label, run_react(proposer, max_turns=5, max_tool_calls=4))

if __name__ == "__main__":
    main()
```

```text
conditional {'status': 'candidate_response', 'answer': '{"extra_city":"北京","extra_temp_c":24}', 'turns': 3, 'tool_calls': 3}
repeating {'status': 'repeated_action', 'turns': 2, 'tool_calls': 1}
truncated {'status': 'incomplete', 'turns': 1, 'tool_calls': 0}
```

这里的回合数是脚本固定的响应数；它只证明该控制器按预置路径处理了这些状态。它没有验证模型是否会选择正确分支、真实工具是否安全、业务答案是否正确，也没有测量 provider 的 token、费用或延迟。

## 重复检测与预算的判据

精确重复可以通过工具名和规范化参数形成指纹；上面的夹具比较相邻两个模型回合的整批动作。更复杂的运行时可能用任务状态、工具结果摘要或窗口化频次做进展判断，但这些启发式有误报和漏报。将它与硬边界组合：最大模型回合、最大工具调用数、deadline、token/费用预算，以及失败后的停止或交接策略。多工具响应要先按整批做预算预检，不能把“最大回合数”误当成最大工具调用数。

## ReAct 与一次工具调用的关系

工具 schema、动作块和结果回填沿用工具调用章节的协议；ReAct 增加的是宿主循环，以及把新观察送回下一轮。这个组合让模型有机会根据真实工具结果调整下一步，但错误结果也可能影响后续决策。应用应保留来源、执行状态和错误标记；在有副作用的动作前，每一轮都要重新检查当前主体授权、参数、幂等策略和剩余预算。

## 一次超时之后，工具结果可能仍是未知

模型提出工具调用，宿主开始执行，但网络在响应到达前断开。此时不是“工具失败”，而是**调用结果未知**：接收端可能还没收到请求，也可能已经提交了动作，只是回执丢失。把同一个调用再发一次，是否安全取决于工具的幂等契约、业务键和接收端去重，不能从模型回合或 `tool_use_id` 自身推断。该 ID 用于把 `tool_result` 和原调用配对，不自动成为跨请求、跨服务的幂等键。

可以把宿主状态至少分成“已提议、已校验、执行中、结果已知、结果未知、已完成”。每个工具结果要关联调用 ID 和本地执行状态；超时后先按业务操作 ID 查询或对账，若无法确认则保留未知状态并交由恢复策略决定。盲目重试可能重复副作用；直接把超时包装成成功结果也会让模型基于虚构事实继续。只读查询通常比转账、发信或写库更容易安全重试，但仍要看目标接口对缓存、时效和一致性的定义。

同一响应里的多个调用也不构成事务。全批静态校验和预算预检可以避免参数错误或明显超限后才开始执行；然而真实授权可能在执行时变化，前一个副作用成功后，后一个动作仍可能被拒绝或失败。需要全有或全无时，应由业务服务提供事务或显式协调协议；否则逐项记录状态，并设计部分成功后的恢复与人工处理。

模型看到的上一轮授权结果也可能过期；资源归属、权限或审批状态变化后，宿主应在实际副作用前按当前主体和对象重新判断。历史消息中的“已同意”不能代替这次检查。

## 常见坑

- **把模型文本当作工具请求**：按目标 API 协议解析结构化调用，不从自然语言猜动作；协议请求仍须经过宿主校验。
- **把任何非 `tool_use` 都当完成**：截断、拒绝、未知 stop 状态与正常结束不同；`end_turn` 也仍需要任务级验收。
- **先执行再检查整批**：同一响应可能含多个动作。先验证 ID、工具、参数和总预算，再开始副作用。
- **把失败包装成成功数据**：按协议标出工具错误，并对返回内容做隐私最小化；模型不能替代宿主的事实与权限检查。
- **只限制模型回合**：单个响应可有多个工具调用，因此还需要独立的工具调用、时间和资源上限。
- **把精确重复直接等同于循环**：同一只读请求可能是合理的；重复检测是启发式，须与目标状态和硬预算配合。
- **把历史样本当作普遍基准**：本节旧 provider 摘要没有原始轨迹，不能推出稳定成功率、费用倍率或 ReAct 相对静态计划的普遍优势。
