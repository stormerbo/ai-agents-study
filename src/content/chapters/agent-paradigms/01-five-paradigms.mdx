本节用「范式」讨论任务如何被拆成模型请求、代码步骤、工具执行与结果复核。入门时列出的几种模式**不是同一层级、互斥的分类**：单次调用、显式 workflow、ReAct 和 Plan-Execute 是四种控制流骨架；Reflection 是可叠加的复核策略。多智能体描述多个模型实例间的协作拓扑，下一章单独讨论。

这里关心两个不同的问题：**谁提出下一步**，以及**谁有权执行和判定完成**。模型可以提出工具调用、计划或终止信号；宿主（运行模型请求、校验动作、调用工具和保存状态的应用代码）仍需执行授权、验证参数、控制预算、处理结果并决定能否结束。ReAct 原论文描述的是推理轨迹和行动提议交替，不意味着模型直接掌管宿主或副作用。[ReAct 原论文](https://arxiv.org/abs/2210.03629)

## 五种常见实现模式（并非同层级分类）

**一、单次调用。** 对模型发起一次请求并处理这一轮响应；若需调用外部工具并拿回结果继续生成，那已经包含额外的宿主步骤或模型往返。它适合作为无工具任务的基线，但是否满足质量、安全与反馈要求仍需评估。

**二、显式 workflow。** 应用代码决定下一步执行哪个节点。节点可以是代码、模型请求或工具操作；workflow 可以包含条件边、并行或失败分支，不等于固定的一串模型调用。

**三、ReAct。** 模型基于当前观察，逐轮提出行动或结束建议；宿主解析建议、验证权限与参数、执行工具，再把结果交回模型。模型输出不直接执行副作用，宿主也不能只凭模型的结束建议就认定任务成功。

**四、Plan-Execute。** 模型根据任务和已提供上下文提出一份计划；宿主先验证计划与当前状态、权限及预算，再执行并处理结果。计划可能过期，需要条件路由或重新规划；“计划在执行前生成”不等于“模型在没有任何输入数据时规划”。

**五、Reflection（复核策略）。** 在上述任一骨架上增加批评、检查或修订环节。它可以使用外部反馈，也可以只让模型重读同一答案；这两者的证据强度不同。反思文本本身不等于独立验证。论文中的 **Reflexion** 是一个更具体的方法：将任务反馈转成语言化反思，保存在 episodic memory，供后续尝试使用，并不只是“同一答案再读一遍”。[Reflexion 原论文](https://arxiv.org/abs/2303.11366)

Tree-of-Thoughts（ToT）让模型探索多个连贯的中间推理路径，并评估路径以决定扩展方向；它描述搜索/推理策略，不是宿主工具执行边界。[ToT 原论文](https://arxiv.org/abs/2305.10601) 多智能体则描述多个模型实例之间的协作拓扑，见第 12 章。

**真实误判例子：** 旧 T1 检查器只检查文本是否出现「广州、上海、34、27、7」。因此「广州不是最高，上海最高；温差 7」也会通过，尽管最高/最低城市角色写反。这个例子复现了评分器的假阳性，不代表本轮重跑模型。

**旧检查器把三种结果都标为通过，token 记录最高约为最低的 5.1 倍。** 这只描述未复核的历史摘要，不支持正确率结论或跨任务成本排序。其用途是提醒读者：比较之前，先固定任务、评分器、模型配置、运行边界与用量口径，并保存逐次轨迹。

Plan-Execute 的控制流可以先表示多个待执行动作，再由宿主逐项验证与执行；ReAct 则允许模型在看到新观察后重新提出下一步。它们的模型往返、工具调用、校验和执行延迟取决于具体实现。由于历史逐次响应与 trace 缺失，不能把 506 与 1,203 的差异归因于某个单一机制。

Reflection 增加复核步骤，成本可能来自额外模型请求、检索、工具或校验；具体代价取决于实现。历史 2,568 token 摘要既不能证明答案等价，也不能证明反思提高了正确率。

## 请求结构如何影响成本（机制说明，不是本节的测量结论）

模型请求通常伴随输入输出、网络往返和 provider 计量；workflow 还可能有代码执行、工具 I/O、并行等待与失败处理。讨论成本时要分别记录模型往返、token/账单、工具调用与墙钟延迟，不能仅凭范式标签推算。

**Plan-Execute** 可以把一组拟议动作放入一个计划对象，但计划生成、宿主校验、工具执行和最终综合是不同步骤；工具数不等于模型往返数，多个动作也不必然并行。

**ReAct** 通常在工具结果或其他新观察之后再请求模型决策。宿主可能裁剪或摘要上下文，所以每轮输入既不必完整重发，也不保证只增加固定成本。

**Reflection** 可以是另一次模型评审，也可以是程序校验、外部 evaluator、检索或测试。它是否增加模型请求、能否发现错误，取决于具体信号与实现；“再让同一个模型读一遍”不构成独立证据。

因此，几种模式不是能力或成本的固定等级。选型应看目标任务、质量与安全门槛，并对照可复算的同任务测量。

## 别把这张表当成结论

有一个必须说清的限制：**上面那组数字来自一个线性任务与弱字符串评分器**，原始逐次响应没有归档。换一个任务形状可能改变控制流与成本，但第 3 节旧判分结果不能用来比较准确率，也不能证明普遍的成本排序。

这也是本书反复出现的那个提醒（见第 3 章第 5 节）：写「A 比 B 好」之前，先问清楚**你在什么任务上比的**。这些名称本身不保证全局最优方案；需要把候选放进目标任务、质量与安全门槛、运行预算和恢复要求中评估。

## 控制流之外还要交代什么

上面的几种模式只描述了请求如何推进。真实系统还必须说明上下文如何构建与共享、任务状态存在哪里、宿主按什么验收条件结束、遇到拒绝/超时/工具失败时如何处理。多智能体会引入多个上下文与通信关系，但这不自动带来隔离、安全或质量提升；并发与协调成本须按实现测量。

“谁决定做完”也不能只按模式名回答：模型可输出一个终止提议，计划也可以执行完，但应用仍要根据验收条件、剩余预算、权限和副作用状态决定返回成功、拒绝、升级还是继续。

## 换范式的迁移成本

最后补一个很实际的判断：**从一种范式换到另一种，哪些东西要重写。**

| 资产 | 迁移时检查什么 |
|---|---|
| 工具定义与 schema | 概念或 schema 可能复用；核验目标 runtime 的参数表示、验证规则、身份上下文和副作用语义 |
| 工具结果与错误 | 保持错误语义与结果来源；确认新的流程能区分拒绝、业务错误、可重试错误与结果未知 |
| 上下文策略 | 按新流程重新验证哪些状态/证据会进入下一轮，裁剪后是否仍满足判据 |
| 停止与恢复 | 统一验收、预算、取消、超时、重规划、幂等与对账边界；不把模型结束信号单独当成功 |

表格给的是迁移审查清单，不是“工具层永远不改”的承诺。成本应通过代表性的改动演练估算，覆盖代码、配置、数据状态、权限、日志、测试和运维，而非只比较行数。

## 同一个任务，不同模式的产物

前面的概念可落到具体产物上。下面天气数据是**本地构造的 fixture**，用于说明代码和轨迹结构，不是真实天气，也不是模型输出或范式 benchmark。模型不可用时，单次调用应说明缺少数据源，而不是编造温度。

**单次调用** —— 一次请求；没有工具结果时，正确行为可能是说明证据不足：

```json
{"messages": [{"role": "user", "content": "查三个城市的明日最高温；若没有可用数据源，请说明缺少数据。"}]}
```

（示例：构造数据，未实跑；只展示消息片段，不是完整 provider 请求。）

**显式 workflow** —— 应用代码安排节点；节点可以是代码、工具或模型调用，并可按状态走条件分支：

```python
steps = [("get_weather", {"city": city, "day": "明天"})
         for city in ["北京", "上海", "广州"]]
```

（示例：构造数据，未实跑。）

**ReAct** —— 模型输出动作提议、宿主执行并回填观察；下面轨迹是结构示意，不表示模型可直接调用工具：

```text
轮 1  模型提议查询北京；宿主校验并执行
      observation = {city: "北京", day: "明天", temp_c: 31}
轮 2  模型根据观察提议查询上海与广州；宿主再次校验并执行
      observation = [...]
轮 3  模型提出最终 JSON；宿主按验收条件检查
```

（示例：构造数据，未实跑。）

**Plan-Execute** —— 模型提出计划，宿主先校验，再执行；计划在代码执行前存在，不意味着没有初始任务数据：

```json
[{"tool":"get_weather","city":"北京","day":"明天"},
 {"tool":"get_weather","city":"上海","day":"明天"},
 {"tool":"get_weather","city":"广州","day":"明天"}]
```

（示例：构造数据，未实跑。）

**Reflection** —— 复核是叠加步骤。若只有原答案，模型的批评未必获得新信息；把工具证据、判定器反馈或明确 rubric 一并提供，才可检验它能否发现具体错误：

```text
待复核答案：广州最高 34℃，上海最低 27℃，温差 7℃。
可用证据：北京 31℃；上海 27℃；广州 34℃。
复核任务：逐字段比对证据与答案；若信息不足，指出缺失，不补造事实。
```

（示例：构造数据，未实跑。）

本节保存的 **2026-10-12 provider 用量记录**仍是历史摘要：轮 1 in=378/out=154、轮 2 in=614/out=150、合计 1,296 token；2026-10-09 的历史摘要为 1,203。逐次请求/响应和评分轨迹未归档，故未在本轮重跑或独立验证。这些数字只保留为历史观察，不用于校准下方离线示例。

这些产物分别展示请求、代码编排、逐步动作提议、计划对象和复核输入。模式名本身不说明授权、上下文共享、验收器或恢复行为；需要在实现中另行定义。

## 完整可运行代码

下面用一个确定性的本地 fixture 展示五种模式产生的控制流产物。它不会运行语言模型，也不比较准确率、token、成本或延迟；`fixture_proposal` 只是固定策略，用来模拟 ReAct 的逐步提议位置。实际系统需要把它替换成模型输出，并继续保留宿主校验。

**实跑状态：2026-10-21，Python 3.10+，仅标准库；无凭据、provider 或网络调用。** 温度字典是构造数据，不是真实天气：

```python
import json

TEMP = {
    ("北京", "明天"): 31,
    ("上海", "明天"): 27,
    ("广州", "明天"): 34,
}
ALLOWED_CITIES = {"北京", "上海", "广州"}


def get_weather(city, day):
    if city not in ALLOWED_CITIES or day != "明天":
        raise ValueError("工具参数不在本示例允许范围内")
    return {"city": city, "day": day, "temp_c": TEMP[(city, day)]}


def build_answer(observations):
    by_city = {item["city"]: item["temp_c"] for item in observations}
    if set(by_city) != ALLOWED_CITIES:
        raise ValueError("证据不完整，不能生成答案")
    high = max(by_city, key=by_city.get)
    low = min(by_city, key=by_city.get)
    return {
        "highest_city": high,
        "highest_temp_c": by_city[high],
        "lowest_city": low,
        "lowest_temp_c": by_city[low],
        "difference_c": by_city[high] - by_city[low],
    }


def single_call():
    # 只有任务文本、没有天气工具结果；不猜温度，明确需要证据。
    return {"status": "needs_evidence", "tool_calls": []}


def workflow():
    # 固定顺序由应用代码决定；这里的节点是本地工具函数。
    observations = [get_weather(city, "明天") for city in ("北京", "上海", "广州")]
    return {"answer": build_answer(observations), "observations": observations}


def fixture_proposal(observations):
    # 确定性策略替代模型，仅用于演示逐步提出下一动作的控制流。
    seen = {item["city"] for item in observations}
    return next((city for city in ("北京", "上海", "广州") if city not in seen), None)


def react_fixture():
    observations = []
    proposals = []
    while True:
        city = fixture_proposal(observations)
        if city is None:
            break
        proposals.append({"tool": "get_weather", "city": city, "day": "明天"})
        # 宿主在执行前检查动作范围；模型提议本身没有执行权限。
        if city not in ALLOWED_CITIES:
            raise PermissionError("宿主拒绝越界动作")
        observations.append(get_weather(city, "明天"))
    return {"answer": build_answer(observations), "proposals": proposals}


def plan_execute_fixture():
    # 计划是构造的 JSON 数据；宿主先校验完整结构和每项参数，再执行。
    plan_json = json.dumps([
        {"tool": "get_weather", "city": city, "day": "明天"}
        for city in ("北京", "上海", "广州")
    ], ensure_ascii=False)
    plan = json.loads(plan_json)
    if not isinstance(plan, list) or len(plan) != 3:
        raise ValueError("计划结构无效")
    for step in plan:
        if set(step) != {"tool", "city", "day"} or step["tool"] != "get_weather":
            raise ValueError("计划字段或工具无效")
        if step["city"] not in ALLOWED_CITIES or step["day"] != "明天":
            raise ValueError("计划参数越界")
    observations = [get_weather(step["city"], step["day"]) for step in plan]
    return {"answer": build_answer(observations), "validated_plan": plan}


def reflection_overlay(base_result):
    # 只构造复核输入，不伪装成已调用模型或已验证答案。
    return {
        "draft": base_result["answer"],
        "evidence": base_result["observations"],
        "review_request": "逐字段检查答案是否受证据支持；证据不足时报告未知。",
        "reviewer_invoked": False,
    }


if __name__ == "__main__":
    one = single_call()
    fixed = workflow()
    reactive = react_fixture()
    planned = plan_execute_fixture()
    review_input = reflection_overlay(fixed)
    assert one["status"] == "needs_evidence" and one["tool_calls"] == []
    assert fixed["answer"] == reactive["answer"] == planned["answer"]
    assert len(reactive["proposals"]) == len(planned["validated_plan"]) == 3
    assert review_input["reviewer_invoked"] is False
    print("数据性质：本地合成控制流演示；不是模型运行或性能比较")
    print("single_call: status=%s; tool_calls=%d" % (one["status"], len(one["tool_calls"])))
    print("workflow: status=completed; tool_calls=%d; answer=%s" % (len(fixed["observations"]), json.dumps(fixed["answer"], ensure_ascii=False, sort_keys=True)))
    print("react_fixture: proposals=%d; host_executed=%d; answer_matches_workflow=%s" % (len(reactive["proposals"]), len(reactive["proposals"]), reactive["answer"] == fixed["answer"]))
    print("plan_execute_fixture: validated_items=%d; host_executed=%d; answer_matches_workflow=%s" % (len(planned["validated_plan"]), len(planned["validated_plan"]), planned["answer"] == fixed["answer"]))
    print("reflection_overlay: evidence_items=%d; reviewer_invoked=%s" % (len(review_input["evidence"]), review_input["reviewer_invoked"]))
```

示例输出用于验证 fixture 代码路径，不表示模型能够按该轨迹运行。尤其是 Reflection 行只展示复核输入，真实复核者是否发现错误必须另行评估。

```text
数据性质：本地合成控制流演示；不是模型运行或性能比较
single_call: status=needs_evidence; tool_calls=0
workflow: status=completed; tool_calls=3; answer={"difference_c": 7, "highest_city": "广州", "highest_temp_c": 34, "lowest_city": "上海", "lowest_temp_c": 27}
react_fixture: proposals=3; host_executed=3; answer_matches_workflow=True
plan_execute_fixture: validated_items=3; host_executed=3; answer_matches_workflow=True
reflection_overlay: evidence_items=3; reviewer_invoked=False
```

## 常见坑

- **把模型提议当成宿主权限。** ReAct 动作、Plan-Execute 计划和结束信号都只是输入；宿主必须在副作用发生前验证身份、对象范围、参数与预算。
- **把 workflow 想成固定的一串模型调用。** 节点可能是代码、工具或模型；条件边、并行、重试和失败路径要显式设计。
- **把 Reflection 当正确性证明。** 重读同一答案不能提供独立证据；需要明确 rubric、任务反馈、计算器、测试或可信来源，并测量其错误覆盖。
- **把某次 token 摘要解释成某范式普遍更贵或更准。** 本节历史调用缺逐次 trace 和评分器，不能归因，也不能外推。
- **把迁移成本等同于代码行数。** 调整控制流时，还要核验状态、权限、工具语义、失败恢复、观测与运行支持。
- **只看一种实现就定义范式。** 同一控制流可以由不同宿主、模型请求策略和工具执行器实现；记录具体职责与契约，而不只记模式名。
