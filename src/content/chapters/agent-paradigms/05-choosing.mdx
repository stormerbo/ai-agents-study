前四节介绍了五类范式及其边界。本节不做普遍优劣排名，而把两类判断分开：**任务失败的影响如何控制**，以及**下一步由谁、依据什么决定**。

先讨论风险，再讨论控制流，是一种分析顺序；两者相互影响，但并没有必须按这个顺序执行的技术规则。

**风险问题：做错了会造成什么影响，能否恢复？**

**控制流问题：下一步的条件与参数能否预先确定，还是要等新观察后再决定？**

前者帮助设计授权、校验、拒绝与恢复策略；后者帮助提出单次调用、显式 workflow、Plan-Execute 或 ReAct 等候选。范式选择不能代替风险控制。

## 第一个问题：失败代价

不要只用「能不能撤销」给任务贴标签。评估一次失败的**影响范围、授权依据、可逆程度、幂等性与恢复路径**；相同动作在不同数据范围和身份权限下，风险也不同。

| 评估维度 | 要问的问题 | 可选控制 |
|---|---|---|
| 影响 | 会影响谁、多少对象，是否对外可见？ | 限定作用范围、预览、速率或数量上限 |
| 授权 | 当前身份是否允许对这些对象执行此动作？ | 服务端逐对象授权；缺授权时拒绝 |
| 恢复 | 能否撤销、补偿或从备份恢复？ | 幂等键、补偿事务、备份与对账 |
| 验收 | 如何证明动作结果符合要求？ | 执行前校验、执行后读回、独立测试 |
| 人工介入 | 自动控制是否足够覆盖剩余风险？ | 按风险设审批、双人复核或拒绝 |

例如，发送邮件通常无法撤回，但可以先生成草稿、检查收件人和内容，再按业务规则审批；数据库写入虽可补偿，也仍可能影响下游。**“不可逆”是风险信号，不是“一律人工确认”的技术定律。** 范式不能替代执行策略。

## 第二个问题：下一步由谁决定

问的是：**下一步所需的条件与参数，能否在执行前确定？** 这里要区分三件事：计划能否预先表示、分支谓词能否由代码判定、以及新观察后是否需要模型做语义判断。

- 若步骤及参数可提前确定，静态计划是候选；执行器仍应验证计划、授权与前置条件。
- 若路径取决于中间状态，但分支谓词明确（例如余额是否足够），条件 workflow 可以在观察后由代码路由。它可以有条件边，DAG 也不等于“无分支”。
- 若下一步取决于无法预写成确定规则的新观察或语义判断，可把 ReAct 或显式重规划纳入候选，并约束工具权限、步数、成本、时间和终止条件。

是否存在回边不是判据；工作流、计划执行和模型驱动循环都可能表达分支。风险控制与控制流选择是两个相关但正交的设计轴。

## 一张决策表

把风险控制与控制流判断分开，再提出待评估的实现候选：

| 场景 | 可评估的候选 | 选择时检查 |
|---|---|---|
| 单次问答，结果格式固定 | 单次调用；必要时加 schema/代码校验 | 是否确实不需要工具、检索或多步反馈 |
| 步骤与参数提前已知 | 确定性 workflow 或经校验的静态计划 | 执行前校验参数、授权与前置条件；成本取决于模型调用、工具和运行环境 |
| 分支谓词确定、可从状态计算 | 条件 workflow | 代码路由是否完整覆盖边界和错误状态 |
| 新观察需要语义判断 | ReAct 或显式重规划 | 动态决策是否带来可测收益，且权限/预算/停止条件是否受宿主约束 |
| 有独立可计算的验收条件 | 在任一候选上添加独立校验 | 校验覆盖什么错误；失败如何拒绝、修复或升级 |
| 没有外部证据或明确判据 | 先补证据或表达不确定性 | 自我批评不能单独充当正确性证明；反思收益需单独评测 |

“步骤固定”不保证编译期就能发现所有错误，也不保证成本最低；一次调用也可能不满足质量、工具或安全要求。表格只用来缩小候选集，不能代替目标任务上的对照评估。

## 顺序建议：从满足要求的简单候选建立基线

先选择一个**满足质量、安全、延迟和可运维要求的最简单候选**，记录基线；只有当目标任务的证据表明不足时，再增加模型路由、重规划或反思。Plan-Execute、ReAct 与 Reflection 不是一条必然递增的成本阶梯，Reflection 还是可以叠加到其他控制流上的策略。对照应使用同一数据集、模型配置、工具、预算和评分器。

举个具体的：本章线性任务的历史 token 记录中 Plan-Execute 为 506、ReAct 为 1,203。评分器较弱、原始逐次响应缺失，所以只能把它们当作待复测的成本线索；要判断自己的实现，应在同一数据集、模型配置、评分器和预算下跑对照。

同样的道理：历史记录显示 Reflection 的 token 高于 ReAct，但弱检查器和缺失的逐次输出不能证明结果等价或准确率提升。需要用结构化判分重新测自己的任务。

因此实验顺序可以从满足要求的基线开始，再测试具体假设中的增强项；这不要求实现所有中间范式。每个增强项都应预先定义成功指标、成本口径和停止条件。

「测基线」不是一个形容词，它有具体的记法。列一张表，每一层一行，字段固定为这七个：

| 层 | 范式 | 样本数 | 旧检查器记录（非正确率） | 历史 token | 模型往返 | 相对基线 | 备注 |
|---|---|---:|---:|---:|---:|---:|---|
| 0 | 单次调用 | 5 | __/5 | | 1 | — | 最省的基线 |
| 1 | 链式 workflow | 5 | __/5 | | | | |
| 2 | ReAct | 3 | 3/3 | 1,203 | 2 | | T1 历史记录；旧检查器仅做子串检查 |
| 3 | Plan-Execute | 3 | 3/3 | 506 | 4 | | T1 历史记录；旧检查器仅做子串检查 |
| 4 | + Reflection | 3 | 3/3 | 2,568 | 3 | | T1 历史记录；旧检查器仅做子串检查 |

（第 0 / 1 行是空模板；第 2 到 4 行记录历史运行，但其旧检查器不足以证明答案正确，逐次原始响应未归档。模型往返/token 仅为历史记录，不作为当前基准。）

四个填表规则：

- **样本数要服务于目标。** n=1 可以做冒烟测试或发现明显错误；估计成功率、波动或比较范式时，样本量与重复设计要足以支持对应结论。
- **正确率要写判分口径**，不能只写「对」。本节历史 T2 判分代码只检查答案中是否出现 31/27/24，且“分支查对”只检查调用记录中是否出现北京；任务本身总会先查北京。因此该判分器不能证明答案数值与城市对应，也不能证明额外分支选对。历史 3/3 与 0/3 应读作旧启发式检查器的通过数，**不能当作准确率**；原始逐次响应未归档，无法重算。
- **token 写该层自己的总消耗**，不是增量 —— 增量容易在多轮重试里算错。
- **相对基线只在同任务、同评分口径和同预算下可比。** 换任务就要重填一张表，不能把两个任务的倍数混着说；对照差异如何改变结论，可参见本节「如何解释这组历史数据」。

## 如何解释这组历史数据

把本章数据放在一起，得到的是一组需要重新验证的问题：

**这组小实验只能提出待验证的假设，不能说明范式通常如何影响成本或准确率。**

历史记录来自单一模型、固定 mock 工具、每种范式三次运行；T1/T2 的答案评分器又只是字符串包含检查，T2 分支检查还会被必需的首轮查询自动满足。原始逐次响应未归档，所以 5.1 倍、57% 和 3/3 对 0/3 均保留为未独立复核的历史观测，不支持跨任务的普遍结论。评估自己的场景时，应使用结构化答案、逐字段断言与真实执行轨迹，并记录每次输入输出和停止原因。

这组记录更适合作为设计评测的反例：**没有可复算的答案与执行轨迹，就无法知道差异究竟来自哪一部分。** 对自己的任务，应先定义评分器与调用/成本口径，再运行对照。

换一个角度说：范式是控制流和信息获取方式的选择，也会影响成本与延迟；实际差异取决于任务、提示、模型、工具执行和判分设计。本章 2.4 到 5.1 倍只属于历史记录，不能推广。

## 可运行的离线评分器

本节原代码把“工具是 mock”误写成“每一步可复现”：它实际通过环境变量调用在线模型，模型输出随机性、凭据、网络和 provider 配置都会影响运行；代码并非离线示例，也不能重现历史结果。下面改为**本地合成夹具**：它只演示如何精确核对最终 JSON 与完整分支轨迹，不比较范式、不含模型调用，也不构成性能证据。

评分器同时验证答案字段映射、实际工具轨迹和终止状态。第二个样例故意让弱子串检查器误判为通过，精确评分器则拒绝它。运行环境为 Python 3.10+，仅使用标准库。**实跑状态：2026-10-21，本地合成夹具，未调用模型、provider 或网络。** 以下输出只说明评分代码行为：

```python
import json

CASES = {
    "T1": {
        "expected": {
            "highest_city": "广州", "highest_temp_c": 34,
            "lowest_city": "上海", "lowest_temp_c": 27,
            "difference_c": 7,
        },
        "expected_calls": [("北京", "明天"), ("上海", "明天"), ("广州", "明天")],
    },
    "T2": {
        "expected": {
            "beijing_temp_c": 31, "shanghai_temp_c": 27,
            "extra_city": "北京", "extra_day_temp_c": 24,
        },
        "expected_calls": [("北京", "明天"), ("上海", "明天"), ("北京", "后天")],
    },
}


def score(case_id, final_text, calls, terminal_state):
    """夹具评分：JSON 完整相等、调用轨迹有序相等、终态必须正常结束。"""
    case = CASES[case_id]
    try:
        answer = json.loads(final_text)
    except (json.JSONDecodeError, TypeError):
        answer = None
    return {
        "answer_ok": isinstance(answer, dict) and answer == case["expected"],
        "trace_ok": calls == case["expected_calls"],
        "terminal_ok": terminal_state == "completed",
    }


def legacy_substring_check(text):
    """历史式弱检查：只要数字都出现，就会忽略字段和值的对应关系。"""
    return all(value in text for value in ("31", "27", "24"))


if __name__ == "__main__":
    wrong_answer = json.dumps({
        "beijing_temp_c": 27, "shanghai_temp_c": 31,
        "extra_city": "上海", "extra_day_temp_c": 26,
        "comment": "expected temperature 24",  # irrelevant field tricks substring check
    }, ensure_ascii=False)
    wrong_calls = [("北京", "明天"), ("上海", "明天"), ("上海", "后天")]
    result = score("T2", wrong_answer, wrong_calls, "completed")

    print("数据类型：本地合成夹具（不是模型实验或范式 benchmark）")
    print("弱子串检查：%s" % ("PASS" if legacy_substring_check(wrong_answer) else "FAIL"))
    print("精确评分：答案=%s 轨迹=%s 终态=%s" % (
        "PASS" if result["answer_ok"] else "FAIL",
        "PASS" if result["trace_ok"] else "FAIL",
        "PASS" if result["terminal_ok"] else "FAIL",
    ))
    assert legacy_substring_check(wrong_answer)  # 演示假阳性
    assert result == {"answer_ok": False, "trace_ok": False, "terminal_ok": True}

    correct_answer = json.dumps(CASES["T2"]["expected"], ensure_ascii=False)
    correct_calls = CASES["T2"]["expected_calls"]
    assert score("T2", correct_answer, correct_calls, "completed") == {
        "answer_ok": True, "trace_ok": True, "terminal_ok": True,
    }
    print("正确夹具自检：PASS")
```

## 如果任务同时具备两种特征

真实任务往往混合线性段与条件分支。可以把确定性决策留给代码，把模型调用限制在确实需要语义判断的边界；这是一种待评估的架构候选，不是普遍最优定律。

例如，先由已授权的业务规则判断是否需要账户查询，再选择对应的静态步骤；工具执行后用规则检查是否需要升级，最后让模型把已核实结果组织成自然语言。授权和检查必须在服务端执行，不应把模型输出当权限判据。

下面是**流程伪代码，不可独立运行**。它把每个动作的边界标出来，实际实现还需提供经过授权的路由函数、计划注册表、工具执行器和失败处理器：

```text
route = deterministic_route(validated_task)
plan = approved_plans[route]
validate_plan(plan, principal, current_state)
results = execute_with_idempotency_and_audit(plan)
if deterministic_acceptance_check(results):
    return summarize_verified_results(results)
return escalate_or_reconcile(results)
```

代码分支本身没有额外的模型路由调用，但仍有实现、计算、存储、测试和运维成本；模型、工具和总系统成本应分别记录。若某个任务确实需要模型在新观察后决定下一步，可在受限权限、步数、时间和费用预算内评估 ReAct 或重规划。不同实现的调用次数并不固定，不能仅凭范式名称推断谁会多问几次。

拆分任务有助于发现哪些决策可以确定性执行，哪些需要模型判断，也让验收点更清楚。它不意味着所有所谓“需要 agent”的任务都应被改成 workflow；应由目标任务的成功条件、失败影响和测量结果决定。

## 本节小结

1. **风险与控制流分开判断**：失败影响、授权、可逆性和恢复能力决定所需控制；先谈风险只是讲解顺序。
2. **区分计划、路由与语义判断**：提前可表示的计划、代码可判定的条件分支、需要模型根据新观察作出的选择，是不同情形；DAG 也可以有分支。
3. **用满足要求的简单方案建立基线**：复杂度不是线性阶梯。只有测出目标任务的不足，才考虑增加路由、重规划或反思。
4. **给高影响动作设计执行边界**：校验、授权、幂等、审批、拒绝、恢复或对账应按具体风险组合。
5. **把历史数据当作待验证线索**：旧检查器只做字符串包含，原始逐次响应也未归档；3/3、0/3 和 token 差异不能支持普遍准确率或成本结论。

## 常见坑

- **把风险判断和范式选择混为一谈。** 不能从“动作不可逆”直接推出统一审批流程；按影响、授权、恢复路径和业务约束组合控制。
- **把“有分支”误解成“只能用 ReAct”。** 若谓词可由代码根据观察判断，条件 workflow 也能路由；只有需要模型动态语义判断时，才有理由评估模型驱动控制。
- **把固定计划用于无法预知的参数。** 先明确参数是在执行前已知、由状态规则计算，还是需模型观察后判断，并在执行前校验工具、参数与授权。
- **把历史样本当成范式排名。** 本节原始响应缺失，旧检查器又存在假阳性；报告时保留限制，使用自己的可复算数据。
- **只看一个指标。** 同时定义成功判据、预算、延迟、失败类型、权限边界和恢复要求。
- **把 Reflection 当作通用增强。** 自评没有独立证据时不能证明更正确；需要用外部信号和目标任务对照来测其增益。
- **以为换范式就要重写所有工具。** 工具定义可能复用；变化重点通常是状态管理、决策边界、预算和停止条件，但需按实现验证。
