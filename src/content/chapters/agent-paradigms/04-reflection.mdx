Reflection（自我反思）是这几类范式里最容易被高估的一个。它的说法听起来无懈可击：让模型检查自己的输出，发现错误就改。

问题在于：**同一个模型，用同一套知识，检查它自己刚给出的答案** —— 它能发现什么？

## 实测：在同一份答案上做批判

让 ReAct 先跑一遍 T1（查三城天气并比较），拿到一个**当时正确的答案**，然后把它交给模型批判：

| 组合 | 结果 | token |
|---|---|---:|
| ReAct 单独 | ✅ | 1,203 |
| ReAct + Reflection | ✅ | **2,568** |

（实跑数据，2026-10-09，`deepseek-flash`。）

**答案是同一个，账单翻了一倍多（+113%）。** 多出来的那些 token 买到的是一句「以上答案正确」。

## 但它确实改错过 —— 而且失败形态很有信息量

在带 Reflection 的运行里，有 **2 次把一个本来正确的答案改坏了**。其中一次的修订输出是：

```text
无法核实第一位助手的答案。
原因：我没有联网或实时天气数据，无法查询 2026-05-08 …
```

它给出的理由是「我没有天气数据」。**可那份数据刚刚才拿到过** —— 只是我在实现里没有把它一起交给批判者。

这暴露了一个真实的实现问题：**批判者看到的输入，决定了它能批什么。** 只给它一份结论，它会转而质疑「这个结论从哪来的」；把证据一起给它，它才能核对结论与证据是否一致。

后来我又做了 3 次对照 —— 同一个基础答案，分别用「只给答案」和「答案 + 工具原始结果」去批判：**两臂都是 3/3 通过，那次改错没有复现。** 所以如实记下：它是一个偶发现象（7 次里 2 次），不是稳定结论。

## 什么时候它有用，什么时候是纯支出

把上面的现象和第 2 章 self-eval 的实测放在一起，能提炼出一条判据。第 2 章测过：喂入构造的错答，模型 8/8 都抓住了、0/8 误报 —— 看起来很强。但那次有效的真实原因是：**正确答案可以由模型自己独立算出来**（「37 × 43」它可以重算一遍）。它做的不是「审阅」，是「重算」。

由此得到判据：

**Reflection 有用的前提，是「复核」这件事比「原答」多用了某些信息。** 具体有三种情况：

**一、有新的信息进入。** 比如批判者拿到了工具原始数据、拿到了 schema、拿到了外部校验结果。这时它不是在自言自语，而是在核对证据。

**二、原答案是在信息不足时给出的。** 比如模型没调工具就答了，那么「回头再检查一次，这次给你工具」是有效的 —— 但这其实更像 ReAct，不是反思。

**三、任务有可独立验证的结构。** 比如算术可以重算、JSON 可以校验、代码可以跑测试。这时复核是「用另一个通道再算一次」，能发现错误。

反过来说，如果三点都不成立 —— 只是把「一段创作」或「一个判断题」的答案原样交给同一个模型再看一遍 —— 那它大概率会点个赞，而你付了两倍的钱。

## 一个更省钱的做法

如果目的是「减少错误」，比追加一个反思回合更省钱的做法是：**把校验移出模型。**

能写成代码的检查就不要交给模型 —— JSON 的 schema、数值范围、字段间的一致性、引用的 id 是否存在，这些是确定性判断，代价接近零。只有当错误**结构上无法用代码判定**时（比如「这段话的语气是否符合品牌调性」），才值得交给模型复核。

这也和第 5 章的结论一致：**校验应该在代码里，模型只负责生成。** 反思之所以容易变成纯支出，根子上就是因为它被当成了一个「万能校验器」—— 而校验这件事，能写成代码的部分本就不该交给模型。

## 完整可运行代码

下面这段代码在同一个基础答案上做对照批判，只改变批判者的输入（只给答案 vs 答案 + 证据）。

```python
"""反思的输入该包含什么：只给答案 vs 答案 + 证据。

自包含：工具定义、ReAct 循环、判分都内联在这个文件里，不依赖外部脚本。
环境变量：ANTHROPIC_BASE_URL / ANTHROPIC_AUTH_TOKEN / VERIFY_MODEL（写在 .env.local）。
实跑状态：2026-10-09 的结论由等价脚本产出；下面的内联版可独立运行。
"""
import json
import os
import urllib.request

TEMP = {("北京", "明天"): 31, ("上海", "明天"): 27, ("广州", "明天"): 34, ("深圳", "明天"): 29}
TOOLS = [{"name": "get_weather", "description": "查询某个城市某一天的最高气温（摄氏度）。",
          "input_schema": {"type": "object",
                           "properties": {"city": {"type": "string"},
                                          "day": {"type": "string", "enum": ["明天", "后天"]}},
                           "required": ["city", "day"]}}]
T1 = "查北京、上海、广州明天的最高温，报告最高的是哪个城市、最低的是哪个，以及两者差多少度。"


def get_weather(city, day):
    k = (city, day)
    if k not in TEMP:
        return {"error": "没有 %s%s 的数据" % (city, day)}
    return {"city": city, "day": day, "temp_c": TEMP[k]}


def call(messages, system, tools=None, max_tokens=1200):
    body = {"model": os.environ["VERIFY_MODEL"], "max_tokens": max_tokens,
            "system": system, "messages": messages}
    if tools:
        body["tools"] = tools
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages",
        data=json.dumps(body).encode(),
        headers={"content-type": "application/json",
                 "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
                 "anthropic-version": "2023-06-01"})
    with urllib.request.urlopen(req, timeout=180) as resp:
        d = json.loads(resp.read())
    u = d.get("usage", {})
    tin = (u.get("input_tokens", 0) + u.get("cache_read_input_tokens", 0)
           + u.get("cache_creation_input_tokens", 0))
    return d, tin + u.get("output_tokens", 0)


def check1(text):
    """T1 判分：必须点出广州（34）、上海（27）、差 7 度。"""
    return ("广州" in text and "上海" in text and ("7" in text))


def react_with_evidence(task):
    """ReAct，但把工具结果一并留下，供批判者查看。"""
    sys = "你是一个会使用工具的助手。需要数据就调用工具，拿到足够信息后直接给出最终答案。"
    msgs = [{"role": "user", "content": task}]
    evidence = []
    for _ in range(10):
        d, t = call(msgs, sys, TOOLS)
        blocks = d.get("content", [])
        if d.get("stop_reason") != "tool_use":
            text = "".join(b.get("text", "") for b in blocks if b.get("type") == "text")
            return text, evidence
        msgs.append({"role": "assistant", "content": blocks})
        results = []
        for b in blocks:
            if b.get("type") == "tool_use":
                a = b.get("input", {})
                out = get_weather(a.get("city"), a.get("day"))
                evidence.append(out)
                results.append({"type": "tool_result", "tool_use_id": b["id"],
                                "content": json.dumps(out, ensure_ascii=False)})
        msgs.append({"role": "user", "content": results})
    return "（超步数）", evidence


N = 3
print("=== T1：对同一个 ReAct 答案做两次批判，只有输入不同 ===")
a_ok = b_ok = 0
for i in range(N):
    ans, ev = react_with_evidence(T1)
    base = check1(ans)
    # A 臂：只给答案
    d, _ = call([{"role": "user", "content": T1 + "\n\n第一位助手的答案：\n" + ans
                    + "\n\n请检查这个答案是否有错。如果正确，原样输出；如果有错，给出修正后的答案。"}],
                   "你是一个严格的事实核查者。", max_tokens=2000)
    fa = "".join(x.get("text", "") for x in d.get("content", []) if x.get("type") == "text")
    # B 臂：答案 + 证据
    d2, _ = call([{"role": "user", "content": T1 + "\n\n第一位助手查到的原始数据：\n"
                      + json.dumps(ev, ensure_ascii=False) + "\n\n它的答案：\n" + ans
                      + "\n\n请检查这个答案是否有错。如果正确，原样输出；如果有错，给出修正后的答案。"}],
                     "你是一个严格的事实核查者。", max_tokens=2000)
    fb = "".join(x.get("text", "") for x in d2.get("content", []) if x.get("type") == "text")
    oa, ob = check1(fa), check1(fb)
    a_ok += oa; b_ok += ob
    print("  第%d次：基础答案 %s | 只给答案 %s | 答案+证据 %s"
          % (i + 1, "✅" if base else "❌", "✅" if oa else "❌", "✅" if ob else "❌"))
    if base and not oa:
        print("      ⚠️ 只给答案时改成：%s" % fa.strip().replace("\n", " ")[:110])
print("  → 只给答案 %d/%d，答案+证据 %d/%d" % (a_ok, N, b_ok, N))
```

## 反思该放在循环的哪个位置

「加一个反思回合」这句话太粗了 —— **放在哪里，代价差好几倍。** 三种常见放法：

**一、每一步都反思。** 每次工具调用之后都让模型检查一次。这是最贵的放法，而且几乎总是过度 —— 你已经为这一步付过钱了，再付一次只为确认「刚才那步没问题」。

**二、结束时反思。** 拿到最终答案后检查一次。也就是本节实测的那种，附加成本 +113%。

**三、只在检测到异常时反思。** 由代码判断出了状况（校验不通过、工具返回错误、答案格式不对），才触发一次反思。**这是最省的，也最可能有用。**

第三条为什么更可能有用？因为它的判据不是「流程走完了」，而是「**有证据表明出错了**」。而当代码能判断出错时，它多半也能说出错在哪 —— 把那个具体原因交给模型，比让它自己去找错有效得多。第 5 章第 3 节实测过这个差别：空洞重试 0/6，把错误原因拼回去 6/6。

**触发条件就三类，全部由代码判断**（示例：构造数据，未实跑）：

```python
import json

def looks_parseable(text):
    try:
        json.loads(text)
        return True
    except Exception:
        return False

def needs_reflection(state, result, text):
    """只在检测到异常时反思：返回 (是否触发, 给模型的理由)。代价接近零。"""
    if state["validation_errors"]:                     # 1) 校验不通过
        return True, "校验失败：" + "；".join(state["validation_errors"])
    if result.get("is_error"):                          # 2) 工具返回错误
        return True, "工具 %s 报错：%s" % (state["last_tool"], str(result.get("content"))[:200])
    if not looks_parseable(text):                       # 3) 格式不对
        return True, "输出不是合法 JSON，前 80 字符：%s" % text[:80]
    return False, ""
```

触发之后只需要把第二个返回值拼进提示：

```python
trigger, reason = needs_reflection(state, result, text)
if trigger:
    messages.append({"role": "user", "content":
        "这一次的结果没有通过检查。具体原因：\n" + reason +
        "\n请只针对这个原因修正，输出完整的修正结果。"})
    # 再调一次模型；没触发就完全不反思
```

这段代码的关键在于：**没触发就不反思**。三条判据任何一条不成立，那 113% 的附加成本就直接省掉；一旦触发，交出去的不是「你再看看」，而是一条具体的错误原因 —— 第 5 章第 3 节实测过这个差别：空洞重试 0/6，把错误原因拼回去 6/6。

## 它和 self-consistency 是同一个问题

self-consistency（多次采样取多数）是另一种复核方式，第 2 章实测过它的边界：唯一答案题 5 次采样零分歧，创作题 6 次各不相同 —— 投票无事可做，成本 5.4 倍。

（这里说的采样由 `temperature` 控制：它指的是「采样随机性」这个参数 —— temperature=0 时模型每步都挑概率最高的词（近似确定），越高越发散。上文「temperature 1 和 0 采样结果一样」的意思就是：把随机性开到最大，这套题也没有产生第二个答案。）

它和 reflection 的共同假设是：**多算一次能带来新信息。** 而当答案由同一套知识、同一份输入得出时，多算一次只是多花一次钱。两者的失效机制是同一个。

区别在于 self-consistency 还多了一层「多样性能带来独立性」的希望 —— 实测里那个希望也没有兑现（temperature 1 和 0 采样结果一样）。两者的共同代价是**让同一套知识把同一件事再算一遍**，而独立性从来不是靠重算获得的，是靠换信源获得的。

## 反思的成本从哪来

「多花 113%」这个数字可以拆开。一次反思回合的开销有两部分：

**输入**是任务 + 原答案（有时还有整条轨迹）。在长任务里这部分才是大头 —— 轨迹越长，批判者要读的越多。

**输出**只是那段批判文字，通常几百 token。

所以在同一个任务上，反思的相对成本会**随着轨迹变长而上升**。线性任务上它是 2 倍；如果基础范式跑了十几步，反思的输入里就要重新装进那十几步的全部内容，倍数会更大。

这也给出一个实践上的提醒：**如果一定要加反思，尽量只给它需要的那部分，而不是整条轨迹。** 把工具原始结果抽出来给它（就像本节对照实验的 B 臂那样），比把整个对话历史倒进去便宜得多，而且更有针对性。

## 本节小结

1. **反思的判据只有一条**：复核时能不能拿到原答没有的信息。拿不到，它就是在自言自语。
2. **实测成本 +113%，而结果与不加反思相同**；线性任务上它是最贵的一档。
3. **只给结论不给证据，它会去质疑证据是否存在**（7 次里 2 次）；这个现象后来没有复现，如实记为偶发。
4. **触发条件应该是「有证据表明出错了」，而不是「流程走完了」** —— 把具体错误交给模型，比让它自己找错有效得多。
5. **能写成代码的校验就别交给模型**：schema、范围、一致性检查，这些的成本接近零。

## 常见坑

- **把反思当成免费的准确性提升。** 实测成本 +113%，而结果与不加反思相同。
- **只把结论交给批判者。** 实测里批判者会转而质疑「数据从哪来」，把正确答案改成「无法核实」。证据要和结论一起给。
- **在概率性任务上加反思。** 没有可独立验证的答案时，复核者能做的只有「再判断一次」，而它与第一次用的是同一套知识。
- **忘了反思也消耗上下文。** 它要把原答案（有时还有轨迹）连同任务一起重发，这部分开销往往比批判本身的输出更大。
- **忽略第 2 章那个结论的边界。** self-eval 8/8 抓住错答，是因为那些错答可以被独立重算 —— 不是因为它擅长审阅。
