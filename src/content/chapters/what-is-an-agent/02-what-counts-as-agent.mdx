```python
def process_contract(pdf_path: str) -> Contract:
    text = extract_text(pdf_path)              # 1. 取文本
    summary = llm_summarize(text)              # 2. 让模型概括

    validated = validate_schema(fields)        # 4. 校验
```

这里面调用了两次 LLM。团队里有人看到之后说：「我们在做 agent 了。」

**按本节采用的架构分类，这是一个 workflow。**

这个区分不是学术洁癖。它描述的是**控制流由谁编排**，并影响可靠性、测试方式与成本估算。workflow 的固定编排通常让路径更容易检查与估算，但「成本更可预测」是常见的比较结果，不是 workflow 的定义，也不代表账单可以精确预知：输入长度、条件分支、重试、缓存命中和供应商计费维度仍会改变实际用量。

## 核心区别：控制流主要由谁编排

先说明术语边界：业界对 *agent* 没有唯一、普遍接受的定义。Anthropic 把 workflow 与 agent 作为两种 agentic system 的架构形态：workflow 由预定义代码路径编排模型和工具；agent 则让模型动态决定过程与工具使用。本文沿用这套区分，方便做工程选型；它不是所有框架或论文都必须采用的术语标准。Anthropic 原文发表于 2024 年，页面也提醒其中的工具生态描述已经变化，因此这里只引用其架构分类，不把它当作当前产品能力说明。

模型也不会直接取得程序的执行权：模型提出下一步动作，宿主程序仍负责校验状态、权限、预算，并决定是否执行。这里的“控制权”说的是**谁主要决定下一步路径**，不是把安全边界交给模型。

- **workflow**：应用预先定义主要步骤与转移规则，LLM 在这些节点内处理任务。上面的合同处理就是「取文本 → 概括 → 抽字段 → 校验」；若代码按结果选择分支，它仍可属于 workflow。
- **agent**：模型根据当前观察动态提出动作或下一步，宿主决定是否执行并把结果交回模型。运行路径常常不能完全预先枚举，但动态步数是常见特征，不是单独的定义判据。

用上一节的实测数据来对照，就非常清楚：

```text
请求：北京今天天气怎么样？（附 get_weather 工具）
响应：stop_reason = tool_use
```

`stop_reason` 是 `tool_use`，意思是「我停下来，等你给我工具结果」。拿到结果之后模型会继续 —— 它可能直接回答，也可能决定再调用一次工具。**这个决定权不在你的代码里，在模型手里。**

这就是常见 agent loop 的最低形态：**模型提出动作，宿主执行受控动作并回传结果，再由模型决定继续还是结束。** 模型输出不是授权；终止、权限和预算仍由宿主实施。

## 一份轨迹长什么样

agent 与 workflow 的性质对照里，「调试」一栏写的是**要看完整轨迹**。这句话很容易被当成口号。

> **「轨迹」（trace）是什么**：它是把一次运行中的模型请求、模型输出、工具调用与结果等事件按关联 ID 和时间顺序串起来的观测记录。它可以帮助重建部分决策上下文，但不保证包含完整状态，也不自动证明根因；外部状态、未记录事件和非确定性都会影响复现。模型输入、工具参数和结果可能含敏感信息，应按数据策略做最小化、脱敏和访问控制，只有经明确授权时才记录必要内容。
> 它补充了审计日志：应用日志说明代码执行了什么，受控的模型事件可以帮助分析模型收到什么、返回什么。两者都可能不完整，定位问题时应结合状态快照、工具记录和可复现实验。第 15 章第 4 节的 `eta` 案例也只能说明关联输入输出有助于排查，不能说只有完整轨迹才能找到根因。

它落到文件上是一串按顺序发生的步骤记录 —— 同一句提问在 agent 循环里走完两步之后长这样：

```json

```

> （示例：构造数据，未实跑。第 1 步的 `id`、`input`、`tool_use` 类型、`stop_reason` 与 `usage` 取自本站第 1 章第 1 节的真实调用；第 2 步的报文与整份 JSON 的形状是我按这个结构手写的，**第 2 步的 token 数我故意没填 —— 那是另一个没跑过的数**。）

三件事值得注意：

1. **示例展示了 `model_input` 的逻辑位置，不是在要求生产环境完整留存原文。** 生产记录应按隐私与安全策略选择字段、脱敏或采样；缺少内容时也要明确标记不可完整重放。上下文被压缩或截断的问题，需要结合请求摘要、版本、状态和可用的受控记录排查。
2. **`tool_result` 挂在发起它那一步下面，用 `tool_use_id` 配对。** 不是按到达顺序拼接（第 4 章实测：漏了 `tool_result`、或 `tool_use_id` 对不上，都是 HTTP 400）。
3. **`budget` 是一等字段。** 轨迹不只用来事后排查，也是运行时判断「还剩几步」的依据 —— 后面 `handle_ticket` 里的 `max_steps` 就该从这里读，而不是散落在调用点。

## 为什么这个区分值钱

看两种形态的性质对比：

| | workflow | agent |
|---|---|---|
| 控制流 | 转移规则由代码预先编排；具体路径可依输入而变 | 模型参与逐步选择动作，轨迹在运行时展开 |
| 成本 | 通常更容易估算；仍有输入、分支、重试等变量 | 轨迹差异通常更大；需用分布估算并设硬上限 |
| 可测试性 | 可对固定步骤、分支和边界分别测试，也应评估端到端结果 | 可单测工具、策略和状态转移，并用轨迹评估整体行为 |
| 失败模式 | 通常更容易枚举，但仍可能受输入和外部依赖影响 | 路径组合可能更多；可用边界、故障注入和评估集管理 |
| 调试 | 结合应用日志、输入和外部依赖 | 结合模型事件、工具记录、应用日志与状态；记录范围受隐私策略约束 |
| 适配新输入 | 取决于代码定义的范围与分支 | 模型可能动态适应，但必须验证质量与安全边界 |
| 适合场景 | 流程明确的重复任务 | 流程不明确、需要探索的任务 |

**关键在于第一行的连锁反应。**

因为 workflow 的控制流由代码预先编排，所以通常：

- 在输入范围、路径、重试与价格规则已知时，可以建立成本估算或上界；实际账单仍要按供应商 usage 口径核对
- 每一步都能单独测试（给定输入，断言输出）
- 失败模式有限，可以穷举并针对性处理

而在 agent 中，模型参与动作选择，路径与调用次数通常要到运行时才确定；因此成本与测试需要更多运行时观测和预算护栏：

- 成本更依赖模型选出的轨迹；用代表性任务的分布估算，并由步数、token、时间与金额上限兜底
- 仍可对工具、策略、状态转移和预算边界做单步断言；开放式任务的整体质量通常还需轨迹或结果评估
- 失败路径可能组合增多，不能因此放弃对关键边界的枚举和故障测试

所以判断标准不是「谁更高级」，而是：**你是否需要把部分控制流交给模型，以换取对中间结果的适应能力？** 成本可预测性是一个重要的工程取舍，但不是两者的定义边界。

### 实测：三种实现的成本差距

上面的性质对比是理论上的。下面是实测数据 —— **同一个任务，三种实现方式**。

任务：从一段中文文本里抽出人名、公司名、城市，并统计文本字数。

| 实现方式 | 请求数 | token 消耗 | 相对成本 |
|---|---:|---:|---:|
| **单次调用**（一个 prompt 全做完） | 1 | **365** | 1.0× |
| **workflow**（固定两步：先摘要，再抽取） | 2 | **619** | 1.7× |
| **agent**（给 3 个工具，模型自主决定调用） | 2 轮 | **1625** | **4.5×** |

（实测数据，`deepseek-flash`，2026-09-24。agent 行是三次运行的平均值。）

三个数字各有含义：

**第一，额外调用可能增加累计输入。** 对要求客户端随请求提交对话历史的无状态接口，后续请求通常需要带上继续任务所需的历史；但这组历史摘要没有保存逐次请求、响应与 usage 明细，不能独立确认第二步实际重发了哪些内容，也不能把 619 对 365 token 的差值归因于上下文重发。这个两步对照只记录了该次历史摘要的总用量，不构成多轮累计输入呈平方增长的证据；平方增长还需要完整历史每轮重发且上下文随轮次增长等条件。

**第二，agent 的成本是单次调用的 4.5 倍。** 而这个任务**根本不需要 agent** —— 它就是一次抽取，没有任何需要探索的地方。多花的那 1260 token 买到了什么？什么也没买到。

**第三，agent 的成本有波动。** 三次运行分别是 1659 / 1520 / 1697 token，波动约 ±6%。而这个任务很简单，只跑了 2 轮。任务复杂时波动会大得多。

第三点最值得注意：在这组三次运行里，agent 的观测用量有波动。它提示我们要测轨迹分布并设预算上限，但不足以推出「任何 agent 成本都无法精确预估」；同样，单次调用的输入和输出长度也会随请求与生成变化。

这组实验只说明：在这个固定任务、模型、端点与计量口径下，三种实现的观测用量不同；它不能证明任意 workflow 都能精确预报账单，也不能把三次运行的波动推广到更复杂任务。更准确的比较是：固定编排通常更容易限定路径并估算成本，模型动态决策则需要额外考虑轨迹分布与运行时上限。

## 大多数需求，答案是不愿意

这一点值得反复强调，因为它与直觉相反。

**许多业务需求的主要流程是已知的。** 合同处理要经历哪几步、客服工单要怎么流转、数据 ETL 要走什么管道 —— 这些往往能在设计阶段明确。若流程与分支已经能被可靠地写清楚，把它们交给模型动态决定是否能改善结果，需要用任务评估验证；不能仅凭“更自主”就推断收益。

用 [Anthropic 的 *Building effective agents*](https://www.anthropic.com/engineering/building-effective-agents) 的说法：**先用最简单的方案，只在确实需要时才增加复杂度。** 那篇文章归纳了几种可组合的 workflow 模式，它们的共同点是：**用固定的编排结构获得大部分收益，而不承担 agent 的不确定性成本。**

| 模式 | 一句话定义 | 何时用 |
|---|---|---|
| **prompt chaining**（提示链） | 上一个调用的输出是下一个调用的输入，步骤写死 | 任务能明确拆成几段，且每段都该单独检查（如「先抽字段，再校验，再改写」） |
| **routing**（路由） | 先用一次调用（或规则）判断类型，再分发给不同的固定流程 | 流量天然分几类，各类要的处理方式不同（发票 / 退款 / 咨询各走各的） |
| **parallelization**（并行化） | 同一输入拆成多个互不依赖的子任务同时跑，再合并；或同一任务跑多次取一致结果 | 子任务之间没有中间依赖，或需要「多票复核」降低随机性 |
| **orchestrator-workers**（编排者-工人） | 编排者根据输入动态拆解任务、分给工人，最后汇总 | 子任务难以预先确定、但有清晰拆解与汇总职责时；编排者可以是 LLM。它仍可作为 workflow 模式，由应用定义何时启动、如何授权工具、怎样限制并发/预算及何时结束 |
| **evaluator-optimizer**（评估者-优化者） | 一个调用产出、另一个调用按明确标准评估并给改进意见，循环有限次 | 有可写下来的验收标准（如「必须覆盖这几个字段」），且迭代能收敛 |

这五个模式是常见 workflow 结构，不代表模型只能在固定节点里生成文本：例如 orchestrator-workers 会让 LLM 动态决定子任务。workflow 的关键是应用仍定义总体编排与边界；若模型持续决定主要执行过程并据环境结果迭代，则更接近本文所说的 agent。判断标准不是「用了几个 LLM」，也不能仅凭子任务是否动态来判定。

具体到实践，判断顺序应该是：

## 一个容易误判的中间地带

现实中更常见的情况不是「纯 workflow」或「纯 agent」，而是**混合**：

> **示意代码片段，未实跑**：`Ticket`、`Response`、模型调用和 agent loop 均为占位接口；此处只展示混合编排的控制流，不可直接运行。

```python
def handle_ticket(ticket: Ticket) -> Response:
    # 固定步骤：分类（workflow 部分）
    category = llm_classify(ticket.text)

    if category == "simple":
        return llm_answer(ticket.text)          # 固定路径

    # 复杂工单交给 agent 自主处理（agent 部分）
    return run_agent(
        goal=f"解决这个工单：{ticket.text}",
        tools=[search_docs, query_order, issue_refund],
        max_steps=8,                            # 必须有上界
    )
```

这种设计很常见，也很合理：**用 workflow 兜住确定的部分，只把真正需要探索的部分交给 agent。** 它同时拿到了两者的好处 —— 大部分流量走可预测路径，少数复杂情况才有不确定性成本。

注意代码里的 `max_steps=8`。生产 agent 应有宿主强制执行的停止与资源边界，例如最大步数、截止时间、token/金额预算，以及必要时的人工暂停；具体组合取决于任务和供应商计量。仅在 prompt 里要求模型停下不构成硬上界。

## 判断清单

面对一个需求时，按顺序问自己：

1. **单次 LLM 调用能解决吗？** 很多「看起来需要 agent」的需求，其实一次调用加一个精心设计的 prompt 就够了。
2. **步骤是已知的吗？** 已知 → workflow。这一步能筛掉大多数需求。
3. **需要根据中间结果决定下一步吗？** 不需要 → workflow。需要 → 考虑 agent。
4. **如果用 agent，我能给出明确的上界吗？** 步数上界、token 上界、时间上界、金额上界。给不出 → 先别做 agent。
5. **错误的代价有多大？** 高风险场景（涉及资金、对外发送、不可逆操作）用 agent 时必须有额外护栏（第 16 章）。

## 常见误判

**「用了 LLM 就是 AI agent」。** 不是。上面那段合同处理代码用了两次 LLM，但它是 workflow。

**「agent 更先进，所以应该用 agent」。** 复杂度不是优点。能写死的流程写死，是工程判断力而不是保守。

**「先做成 agent，效果不好再退回去」。** 方向反了。从 workflow 加 agent 是渐进的，反向通常要重写。

**「agent 自主性越高越好」。** 更多模型决策通常意味着更多运行时路径需要评估和约束，但代价取决于具体系统。目标应该是「**只把经验证确有价值的决策权交给模型**」。

**「没有步数上界的 agent 更灵活」。** 没有上界的循环不是灵活，是失控。第 9 章会把这一点做成可运行的实验——你会亲眼看到一个没有循环检测的 agent 如何重复调用同一个工具直到耗尽预算。

## 怎么验证这一节说的

| 论断 | 怎么验 |
|---|---|
| agent 的步骤数不固定 | 用同一个任务跑多次，统计每次的工具调用次数 |
| 成本估算依赖路径与计费规则 | 试着给「处理这份合同」分别列出流程、输入范围、分支、重试和计费维度，再说明估算误差来自哪里 |
| 去掉上界会失控 | 第 9 章的实验：故意不设 `max_steps`，观察它跑多少轮 |

第二个验证仍有参考价值，但只能作成本估算的线索：若流程、输入范围、重试和计费规则都能预先界定，通常更容易给出可靠的估算或上界。它不能单独判定架构；workflow 也会有可变分支与运行时波动，agent 也可以通过限制动作和预算收窄成本范围。
