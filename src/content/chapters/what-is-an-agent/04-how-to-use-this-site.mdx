**本站为什么这样安排顺序**，用几个课程设计例子说明；它们是主要依赖的解释，不是说所有项目都必须按此顺序实施：

- **阶段 1 在阶段 2 之前**：不理解上下文是有损的，就无法理解为什么工具返回值要写得那么讲究
- **阶段 3 在阶段 4 之前**：不知道一次 agent 循环会产生多少种失败模式，就没法设计评估指标
- **阶段 4 把生产约束集中展开**：包括评估、沙箱、安全、成本、人机协作与部署；这些主题各自成章，不只是一节「部署」

> 路径图里两个缩写先给一句解释，后面各章会展开：
> **RAG**（Retrieval-Augmented Generation，检索增强生成）：它指的是**先检索出外部知识的片段、再拼进上下文**让模型据此作答，而不是指望模型记住它 —— 可以类比成把「数据库查询结果」注入 prompt，而不是让程序凭内存猜。它解决的是「模型的参数里没有你的私有数据」这个问题（阶段 2 的第 6 章）。
> **MCP**（Model Context Protocol）= 一套**把工具与数据源接进模型的标准协议** —— 相当于给模型侧的 USB-C 接口：工具提供方实现一次 server，任何客户端都能用，不必为每家 agent 框架各写一遍适配（阶段 3 的第 14 章）。

### 第一轮动手路径

如果你已经会写后端服务，不必等读完整个阶段再见到 Agent 循环。下面这条短路径只让模型选择一个**只读**工具，查询固定的只读订单 fixture，再把结果交回模型；不连接真实订单系统，也不修改数据或联系客户。

1. 先读[消息 API 与一轮对话](/chapters/llm-api-basics/messages-api)，确认请求、响应和结束原因。
2. 再读[指令与数据边界](/chapters/prompt-engineering/instruction-clarity)，知道哪些是可信指令、哪些只是用户输入。
3. 接着读[工具调用的真实过程](/chapters/tool-calling/what-really-happens)，理解模型提出调用后，仍由宿主执行工具并回填结果。
4. 最后跑[最小 Agent 循环](/chapters/agent-loop/minimal-loop)，观察 `tool_use → 本地只读查询 → tool_result → end_turn`。

可从仓库根目录运行示例。它使用 Anthropic Messages API 形状；支持该协议的兼容端点也可通过环境变量配置：

```bash
set -a
. ./.env.local  # 本地文件已被 git 忽略；不要把密钥写进脚本、命令参数或提交记录
set +a
python3 examples/first-loop/readonly_support.py
```

示例只有 `lookup_order` 一个工具，订单号和数据都固定在本地。它把输出上限设为 512 token、最多进行 4 轮模型请求；参数错误、未知订单、拒绝、暂停、上下文超限、截断、协议异常、空白最终文本和超轮次都有不同状态。模型输出具有随机性，所以应检查轨迹和状态，不要把某次自然语言答案当成固定测试快照。该短路径用于看见第一轮控制流，不替代阶段 3 的完整循环项目，也不改变章节前置依赖。

这里有三个重要边界：`end_turn` 但没有非空文本时，示例返回 `completed_without_text`，不把协议终止当成有答案；执行任何工具前，先检查整批 `tool_use.id` 都是非空且唯一；如果最后一轮才收到工具提议，因为已经没有下一次模型请求来消费 `tool_result`，就直接以 `max_rounds` 结束而不执行工具。脚本也拒绝 HTTP 重定向：`urllib.request` 的普通请求头可能跟随重定向发送，若兼容端点返回 302，先检查并填写可信的最终 `ANTHROPIC_BASE_URL`，不要为了“跑通”而自动跟随。

## 一章里有什么

每一章由**节**组成。每一节包含固定的几块内容：

| 内容 | 说明 |
|---|---|
| 正文 | 讲解与代码 |
| 自检清单 | 需要你自己回答的问题，附参考答案 |
| 延伸阅读 | 外部资源，每条写明「为什么值得读」 |

### 关于自检清单：请先自己回答

自检清单的答案默认折叠。**强烈建议先自己想，再展开对照。**

这不是形式主义。LLM 领域有一个特点：**读的时候觉得都懂，动手时发现全是坑。** 自检清单是检测这个落差最廉价的手段 —— 如果你答不上来，说明那一节需要再看一遍，而不是说明问题太难。

### 关于答案的「依据标注」

每条自检答案下面都有一行标注，说明这条内容的依据类型：

| 标注 | 含义 |
|---|---|
| **有文档依据** | 官方文档或规范里明确写着，附可点的来源链接 |
| **经验判断** | 作者基于工程经验的推理，不是可查证的事实 |
| **未能核实** | 无法确认，但认为值得保留，会说明为什么核实不了 |

这个机制的存在有一个很实际的理由：**AI 领域的技术细节变化极快，而错误的断言与正确的断言在语气上没有任何区别。** 如果不标注，你无法分辨「这是官方文档写着的」和「这是作者的经验之谈」，而这两者被误认的代价完全不同。

所以在你看到「经验判断」时，请保持正常的怀疑；看到「有文档依据」时，可以直接去点那个链接核实。

**一条自检项在数据里长这样**（以第 1 章的一条为例，字段直接来自站内的数据文件）：

```json
{
  "id": "token-estimation",
  "question": "为什么不能按字符数估算 token？",
  "answer": "因为字符与 token 的换算关系随文本类型剧烈变化……",
  "basis": "documented",
  "sourceIds": ["claude-models-overview"],
  "note": "「中文 token 密度更高」是共识，但没有官方给出的确切倍数，因此只做定性描述。"
}
```

看懂这五个字段，也就看懂了本站的准确性机制：`answer` 是可以错的（它是作者的理解），
`basis` 说明这条依据有多强，`sourceIds` 指向可点开核实的来源，而 `note` 专门写**哪里没能核实**。
测试会强制这些字段合规 —— 标成「有文档依据」却没有来源，构建立刻失败。

## 关于动手实验

**站内实验已经可以用了。** 入口在顶部导航的「实验」，或者从任意章节的实验卡片点进去。

用法很简单：填入你自己的 API Key，直接运行。关于 Key 的处理方式，有三件事你要知道：

- 你可以选择浏览器持久保存，或只在当前会话内存保存；持久模式使用 `localStorage`
- 点击运行时，浏览器会把 Key 发给本站 `/api/chat`，本站服务再用它请求所选模型 provider。Key 会经过本站服务并在请求处理中可见；本站没有账号同步或服务端凭据库，但这不等于部署平台没有日志，也不保证错误内容绝不会回显
- 使用你信任的部署，选择**专用、低权限**的 Key，用完后吊销；部署平台的基础设施日志与访问控制也应按自己的部署环境核实

第一次进去时把**厂商、端点地址、模型名、API Key** 配成一组。持久模式下这组值会保存在本地浏览器并在下次打开时恢复；选择“仅本次会话”时关闭标签页后需要重新填写。第三方兼容端点只有在本站部署允许自定义端点且符合安全校验时才可使用，不能假设任意中转地址都能直接填入。

### 实验会展示记录到的轨迹，而不只是最终答案

> **轨迹**在这里指实验实际记录到的事件序列：请求与响应内容、工具调用、可取得的 token 用量和停止原因。不同厂商与端点暴露的字段并不相同；轨迹也不一定包含模型服务端的全部上下文、隐藏指令或内部状态，因此是排查问题的重要材料，**不是保证精确复现的唯一依据**（详见第 0 章第 2 节的定义与示例）。复现还需要记录模型/端点版本、采样参数、工具数据与运行环境；有些服务端因素仍不可见。

这是它与「跑个 demo 看看效果」的区别。每个实验都会给出：

| 看到什么 | 为什么重要 |
|---|---|
| 厂商返回的**推理内容（若有）**（可展开） | 当端点提供这类内容时，可以检查其中暴露的判断线索；它不等于模型的完整内部思考 |
| 每一次**工具调用**及参数 | 理解「模型只生成意图，不执行任何东西」 |
| **token 用量**与停止原因 | 建立成本直觉，识别截断 |
| **原始事件**（协议层，折叠在最后） | 核对「厂商实际发的」与「语义层展示的」是否对得上 |

最后一项是特意保留的。协议层事件能帮助核对客户端实际观察到的请求与响应；它不包含服务端全部状态，也不能证明工具副作用或业务结果成功。遇到异常时，应结合 provider 文档、应用日志、工具结果与业务后置条件一起判断。

## 内容的生产方式与局限

这一条很重要，请认真看。

**章节正文与大纲由 AI 辅助撰写；资源与技术结论按现存证据分级核查。** 链接巡检只能说明页面可访问，不能证明页面内容或所有正文论断正确。

具体来说，本站做了这些：

| 做了什么 | 怎么做的 |
|---|---|
| 链接可用性 | 有巡检脚本定期检查所有外链（`scripts/check-links.mjs`） |
| 仓库状态 | 用 GitHub API 查过归档状态与最后更新时间 |
| 具体数字 | 要么标注来源与核实日期，要么不写 |
| 代码示例 | 凡是跑过的会标明「实测」；没跑过的会标明「未实跑」 |

**没有做什么：**

| 没做 | 后果 |
|---|---|
| 逐条核实所有技术论断 | 标「经验判断」的部分可能有误 |
| 全部代码在官方端点实跑 | 部分示例只做过语法检查 |
| 独立专家全书审阅 | 尚未完成逐条、独立的领域专家审阅 |

**你应该怎么对待这些内容**：把本站当作**一条有组织的路径和一份判断依据**，而不是权威参考。涉及具体 API 细节、版本行为、数字的地方，**第一手资料永远是官方文档**。

## 关于「实测数据」

正文中的某些数据块会标注为「实测」或「历史观测」。例如，曾有记录称 `deepseek-flash` 在 `temperature=0` 下三次咖啡命名输出有两种文本；但原始请求、逐次响应、模型快照和评分器未归档，该记录已降级为不可独立复核的历史摘要，不能用来证明温度因果或当前模型行为。

阅读数据时检查四件事：

1. **来源与原始产物**：是否保存请求、逐次响应和模型/SDK 版本？没有时就按摘要或推断处理。
2. **实验单位与评分规则**：分母是什么，什么算成功，是否保留失败和截断样本？
3. **适用边界**：日期、provider、模型、任务与配置是否明确？小样本观察不能直接外推。
4. **重跑方法**：脚本能否复现测量过程？重跑能核对流程，不保证输出或数值相同。

因此不要因为一段文字带有模型名和日期就把它当成已验证事实；按本节和相关 errata/实验记录中的证据范围判断。涉及当前 API 行为时，回到目标 provider 的官方文档与可控测试。

## 一些阅读约定

**技术术语保留英文原词。** 原因很实际：你要读的文档、论文和报错信息都是英文。把术语翻成中文反而会增加你搜索时的阻力。术语第一次出现时会给出中文解释。

**代码以 Python 为主。** 因为官方 SDK、论文复现代码、主流 agent 框架的示例大多是 Python。涉及浏览器、Node、MCP Server 时会补 TypeScript。

**每章都有一个「后端视角对照」小节**，明确列出哪些已有经验可以直接迁移、哪些直觉会失效。这是本站与其他教程最大的区别 —— 它假设你**已经是一个有经验的工程师**，而不是从零开始的学生。

## 你也可以复核这里的每个数字

本站的「实测数据」应附复核或重跑方法；符合条件时，你可以在当前可用的端点与凭据下重新采集。**重跑能核对测量流程，不保证得到相同输出或数值**：模型版本、端点实现、服务端配置和时间都会影响结果，历史观测也可能缺少足够的原始数据而无法逐项复算。

API 采集脚本的模式见 `scripts/verify-api.mjs`：从 `.env.local` 读凭据、不打印 Key，并把脚本实际采到的响应写入 `verify-output/`。不是每个历史实验都能用这个脚本重现；应以该实验旁边列出的命令、结果和证据范围为准。内容体量（每节的中文与说明文字字数）也做成了脚本 —— `node scripts/content-stats.mjs` 会按节列出四个指标，验收标准写在 `AGENTS.md` 里。

之所以把验证方法写进这一节，是因为**这套路径的可靠性依赖于「你能检查它」**。任何一个数字，都应说明证据从哪里来，以及读者能否在自己的环境里重跑。

## 申请 API Key 并配置实验

按所选 provider 当前控制台的说明创建凭据，再在实验页配置对应 provider、endpoint、model 和 key。开户、账单与免费额度随地区和时间变化，本节不承诺固定申请时长或免费额度。

**第 1 步：选一家。** 三家任选其一，第 1 章的实验都支持。差别只在门槛：

| 厂商 | 官方控制台 | 凭据与账单 |
|---|---|---|
| Anthropic（Claude） | [platform.claude.com](https://platform.claude.com/) | 按控制台当前要求创建凭据并查看账单 |
| DeepSeek | [platform.deepseek.com](https://platform.deepseek.com/) | 按控制台当前要求创建凭据并查看账单 |
| OpenAI | [platform.openai.com](https://platform.openai.com/) | 按控制台当前要求创建凭据并查看账单 |

> 不同地区、账户和时间的开通/计费规则可能不同。不要根据旧教程推断当前免费额度、绑卡要求或限额能力；以所选控制台显示的信息为准。

**第 2 步：建一把专用的 Key。** 不要用生产环境的 Key，也不要复用它。在控制台里新建一把，命名成 `study-site` 之类。如果控制台提供预算、用量告警或限额，就为这把 Key 配上；没有这些功能时，先用小额测试、定期查看账单，并在不用后禁用或删除。各家的 Key 权限、过期和预算功能并不相同，不要假设它们都支持月度上限。原因很直接：这把 Key 会被你用在本站实验页里，也可能被你复制进脚本。

**第 3 步：按控制台说明安全保存。** 有些控制台只在创建时显示完整 key；如果是这样，及时存入密码管理器，或写入本地 `.env.local`（**不要提交进 git**）。

**第 4 步：把四项配置填进实验页（或在脚本里设成环境变量）。** 这四个值必须成套匹配，混搭是新手最常见的失败：

```text
厂商      从实验页当前支持项中选择
端点地址  使用官方端点或你获准使用的兼容端点
模型名    填写该 endpoint 当前支持的 model ID
API Key   粘贴该 provider 签发的凭据；不要写进代码或提交记录
```

（这是配置字段示意，不是可复制的当前模型配置。模型名与 endpoint 必须配对，并以该 provider 当前文档/控制台为准。）

**判断四项是否配对成功**：发一次最简单的请求（哪怕只是「只回复两个字：收到」）。成功会返回 JSON，但响应字段取决于 API 格式：Anthropic Messages 使用 `usage.input_tokens`、`usage.output_tokens` 和 `stop_reason`；OpenAI Chat Completions 及 DeepSeek Chat Completions 使用 `usage.prompt_tokens`、`usage.completion_tokens` 和 `choices[].finish_reason`。流式请求若中断，最后的用量块也可能收不到。可对照 [Anthropic Messages API](https://platform.claude.com/docs/en/api/messages)、[OpenAI Chat Completions](https://platform.openai.com/docs/api-reference/chat/object) 和 [DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/) 的响应格式。失败则对照：

| 报错关键词 | 大概率是 | 怎么办 |
|---|---|---|
| `401` / `403` 或 SDK 的认证异常 | 凭据无效、权限不足，或认证方式不匹配 | 异常名称和认证方式由 SDK 与 endpoint 决定；核对所选端点的官方文档，并确认请求没有把 key 写入日志或错误消息 |
| `invalid model`/「支持的模型名是 ……」 | 模型名与端点不匹配 | 直接用报错里列出的名字，并核对该端点当前支持的模型列表 |
| 余额/额度相关错误（状态码与措辞因 endpoint 而异） | 账户余额、账单或权限不满足该请求 | 查看所选 endpoint 的官方错误语义和控制台状态 |
| 连接超时 | 地址/网络/代理问题，或上游响应超时 | 先核对协议、主机和路径，再检查网络与代理；重试前确认请求是否可能已到达，避免把有副作用的操作重复提交 |

## 现在可以开始了

如果你还没有 API Key，按上面步骤查看所选 provider 的当前申请与账单要求。实验页当前支持哪些 provider/endpoint 以实际配置为准；**使用专用、低权限凭据，避免复用生产环境的 Key。**

准备好之后，从第 1 章开始。第一章会带你完成第一次调用，并且告诉你**为什么那次调用会花钱、会失败、会在什么地方让你意外**。
