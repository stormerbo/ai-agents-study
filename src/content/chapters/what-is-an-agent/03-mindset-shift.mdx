我们先用一个真实的失败开场。

你写了一个 LLM 调用，为了让它「稳定」，把 `temperature` 设成 `0`。

> `temperature` 是什么：模型每生成一个 token，都是从一张「下一个 token 的概率分布表」里**采样**出来的。`temperature` 是这张表的**平坦度旋钮** —— 调低会让分布更尖（几乎只取概率最高的那个），调高会更平（低概率选项也有机会）。所以它影响的是**随机性**，不是「正确性」。后面第 2 章会给出实测曲线，并说明这个旋钮在新一代 Claude 模型上已经无法设置。

然后你写了这个测试：

```python
def test_extract_company_name():
    result = extract("张三上周加入了字节跳动")
    assert result["company"] == "字节跳动"     # 精确匹配
```

它通过了。你很高兴 —— 这说明这条链路是可靠的。

**然后它在 CI 里偶发失败。** 重跑一次又过了。再跑又挂了。

你去查日志，输出看起来「一样但不一样」：字段顺序变了、多了一个空格、或者措辞略有差异。你开始怀疑是自己代码的问题，花了半天，最后把断言改成 `in "字节跳动"`，测试通过了，问题被掩盖了。

**这个坑的根源是一个后端直觉：同样的输入应该得到同样的输出。**

在确定性系统里这是公理。在 LLM 系统里它不成立。

这一节讲三个会失效的直觉。它们失效的方式都很隐蔽 —— 不是报错，而是「大部分时候对」。

## 直觉一：同样的输入 → 同样的输出

### 实测数据

同一个提示，`temperature = 0`，连跑三次：

```text
#1  三味咖啡
#2  三味咖啡
#3  三咖小馆        ← 第三次不同
```

（实测数据，`deepseek-flash`，2026-09-24。）

**两次相同，一次不同。** 这就是最难处理的那种失败：它不总是发生，所以你会以为是偶发；但它确实会发生，所以在生产里一定会撞上。

### 为什么

原因不止一个，而且都不在你这一侧：

| 原因 | 说明 |
|---|---|
| 浮点运算的非确定性 | GPU 上的矩阵运算，执行顺序会因批大小、并行策略而变，微小的数值差异会被逐步放大 |
| 服务端批处理 | 你的请求会和其他并发请求打包处理，同一次请求在不同批次里的计算结果可能有差异 |
| 模型版本更新 | 服务端可能在你不知情时更新权重或推理实现 |
| 服务端负载 | 部分服务会根据负载调整路由或精度策略 |

**没有一项是你能通过「把参数调对」解决的。**

### 替代方案

**把断言写在结构性属性上，而不是具体值上。**

```python
def test_extract_company_name():
    result = extract("张三上周加入了字节跳动")

    # 结构断言：字段存在、类型正确
    assert "company" in result
    assert isinstance(result["company"], str)
    assert len(result["company"]) > 0

    # 语义断言：允许措辞差异，但要求包含关键信息
    assert "字节" in result["company"]

    # 或者：用一组样本统计成功率，而不是要求单次通过
```

更完整的做法是**用样本集统计成功率**：

但「统计成功率」这句话本身要落到三样具体的东西上，否则那两个函数 `load_test_cases()` / `is_valid()` 就是两个空壳：**样本从哪来、判据怎么定、阈值怎么定。**

**样本从哪来**：从你生产日志里抽真实输入，**抽最近 N 条**（而不是你手挑的好例子 —— 手挑的样本一定偏简单）。N 取多少取决于你要检测多大的差异：按本站第 1 章（评估章）的二项模型计算，想分辨 10 个百分点的差异，每组大约要 **195 条**；只想看个位数级别的波动，几十条是不够的。先跑 100 条拿到基线，再决定要不要加到 200。

**判据怎么定**：把「对」写成代码，不写成印象。`extract()` 返回的是结构化的 dict，所以判据也应该是结构化的 —— 每次只检查一条可判定的规则，而不是「看起来对不对」。

**阈值怎么定**：不是先定 0.95 再看结果，而是**先跑基线、再看噪声**。把同一批样本在未改动的版本上跑 3 遍，观察成功率的波动范围；阈值取「基线 − 噪声」。`0.95` 只是一个常见起手值，**不是标准** —— 一个从 0.70 基线出发的链路，卡 0.95 只会永远红着。

```python
# success_rate_test.py
"""把「抽取是否可靠」做成一个可跑的统计验收。"""

import json
import re
from collections.abc import Iterable

# 1) 样本：从生产日志里抽出来的真实输入 + 人工/下游系统确认过的期望结果
#    （示例：构造数据，未实跑 —— 真实跑请把这里换成你自己日志里抽出的至少 100 条）
CASES = [
    {"input": "张三上周加入了字节跳动",   "expected": {"company": "字节跳动"}},
    {"input": "李四从腾讯离职，去了小米", "expected": {"company": "小米"}},
    {"input": "王五还在阿里",             "expected": {"company": "阿里"}},
]

# 2) 判据：每条都可判定，不靠「看起来像」
def is_valid(got: dict, expected: dict) -> bool:
    """逐字段比对；公司名允许后缀差异，所以用包含判定而不是 =="""
    if set(expected) - set(got):
        return False                      # 缺字段直接判错
    for key, want in expected.items():
        have = got.get(key)
        if not isinstance(have, str) or not have.strip():
            return False                  # 空串也算错（第 5 章的「必填逼幻觉」）
        if want not in have and have not in want:
            return False
    return True


def success_rate(cases: Iterable[dict], min_rate: float) -> float:
    cases = list(cases)
    passed = sum(is_valid(extract(c["input"]), c["expected"]) for c in cases)
    rate = passed / len(cases)
    # 阈值必须来自你自己的基线，不能照抄；下面这个 0.9 是示例值
    assert rate >= min_rate, f"抽取成功率 {rate:.1%}，低于阈值 {min_rate:.0%}"
    return rate


if __name__ == "__main__":
    print(f"{success_rate(CASES, min_rate=0.9):.1%}")
    # 上线前把同一批样本跑 3 遍，看这个数字的抖动范围 —— 那才是你的噪声底线
```

> （上面这段是**示例代码：构造数据，未实跑**。它的作用是给出「样本 / 判据 / 阈值」三件事的落点，`extract()` 换成你自己的抽取函数。）

注意这里有个连锁后果：**`temperature` 在新一代 Claude 模型上已经无法设置了**（第 2 章）。所以「调低温度换稳定」这条路现在完全走不通 —— 你**只能**从测试和校验层面解决。

## 直觉二：失败会明确报错

### 后端世界的假设

你习惯了这样：调用失败 → 抛异常 → 有错误码 → 有堆栈 → 你知道该改哪里。

### 实际情况

LLM 相关的失败，大部分**不报错**。

**例一：静默忽略参数。**

同一个参数 `temperature`，在不同平台上的行为：

| 平台 | 传 `temperature: 0.2` |
|---|---|
| Claude 新模型 | 400 错误，立刻发现 |
| DeepSeek 兼容端点 | 200 成功，参数生效 |
| 某些聚合层 | **200 成功，参数被静默忽略** |

最后一种最坑：请求成功，参数无效，你的「调参」从头到尾什么都没做。

**例二：截断不报错。**

`max_tokens` 设得过小时，请求返回 **200**，你拿到一个被腰斩的 JSON。只有在 `JSON.parse` 时才会报错 —— 而那个错误信息（`Expecting ',' delimiter`）完全不会指向真正的原因。

正确的做法是**检查 `stop_reason`**：

```python
response = client.messages.create(...)

if response.stop_reason == "max_tokens":
    # 这才是真正的失败信号 —— 输出被硬截断了
    raise TruncatedOutputError("输出被截断，需要提高 max_tokens")
```

### 替代方案

**建立「静默失败」的检查清单。** 这类失败不能靠异常捕获发现，只能靠主动检查：

| 检查项 | 判据 |
|---|---|
| 输出是否完整 | `stop_reason != "max_tokens"` |
| 参数是否真的生效 | 对比传入参数与响应中的实际配置 |
| 内容是否符合预期结构 | schema 校验，而不是 `json.loads` 成功即通过 |
| 成本是否异常 | 单次调用的 token 数是否在预期区间 |

一个反直觉的建议：**把「成功的响应」也当作可疑对象**。在 LLM 系统里，「没报错」的置信度远低于其他系统。

## 直觉三：状态可以精确控制

### 后端世界的假设

你有 session、有缓存、有数据库。你放进什么，读出来就是什么。状态是**精确的**。

### 实际情况

上下文不是这样的。它是**有损的、且被稀释的**。

两个机制：

**第一，注意力会被稀释。** 上下文里内容越多，模型对其中每一部分的关注度越低。这不是容量问题 —— 你可能只用了窗口的 10%，但漏掉了关键信息。

**第二，中间位置最容易被忽略。** 有实证研究（[*Lost in the Middle*](https://arxiv.org/abs/2307.03172)，TACL 2024）显示，模型对长上下文各位置的利用率呈 U 形：开头和结尾最高，中间明显衰减。

反直觉的推论是：**把关键信息埋在长上下文的中部，效果可能比只给它这一句话还差。**

### 但我试着复现这个效应，没有成功

论文是 2023 年的工作。我按它的思路在 2026 年的模型上测了一遍，**没能复现**。

实验设计：把一条极其明确的机械约束（「回答的最后一行输出 `CHECKPOINT-OK`」）放在一段长干扰文本的不同位置，看模型是否遵守。

```text
干扰文本 12164 字符

约束位置 | 遵守 | 输入 token
  开头   |  ✓   |   7078
  中间   |  ✓   |   7080
  结尾   |  ✓   |   7077
```

（实测数据，`deepseek-flash`，2026-09-24。干扰文本从 2383 字符到 12164 字符各测一轮，结果一致。）

**三个位置都遵守了。**

这说明什么？我先排除几个可能：

| 可能原因 | 是否成立 |
|---|---|
| 干扰不够长 | 不太可能 —— 12000 字符已远超论文的测试规模 |
| 模型完全没这个问题 | **证据不足** —— 一个实验不能证明普遍结论 |
| **测试方法太简单** | **最可能** —— 「输出一个标记」是机械可检查的，模型容易定位。论文测的是需要**理解并运用**的信息 |

**我不认为这个结果推翻了论文。** 更合理的结论是：

1. **论文结论不是普适常数** —— 它在特定模型、特定任务、特定规模上测得
2. **换模型、换任务，结论可能不成立**（也可能更强）
3. **你应该在自己的场景里验证，而不是照搬任何结论 —— 包括论文，也包括我这里的说法**

这恰好呼应本站的一个核心主张：**在 AI 领域，「某个结论是否还成立」本身就需要持续验证。**

> 如果你想自己测，建议用**真实任务**而不是机械标记：在一份长文档的中间埋一个「只有读了才能正确回答」的问题，看模型能否答对。这比测试「能否输出一个标记」更接近论文的原始设定。

### 自己跑一遍：可运行的对照脚本

上面的三种位置是我手工摆的。下面这个脚本把三件事写死成变量：「干扰文本多长」、「关键信息放哪」、「看模型有没有答对」。改 `FILLER_CHARS` 就能把规模从现在这个量级推到 13 万 token（第 7 章做过，仍未复现）。

```python
# lost_in_the_middle.py
"""把一条关键事实埋进长干扰文本的不同位置，看模型能否用它作答。"""

import os
import urllib.request
import json

BASE_URL = os.environ["ANTHROPIC_BASE_URL"].rstrip("/")
API_KEY = os.environ["ANTHROPIC_AUTH_TOKEN"]
MODEL = os.environ["VERIFY_MODEL"]

# 关键事实：只在某一条里出现，且必须读了才能答对
NEEDLE = "本公司唯一的海外仓编号是 WH-7742，位于鹿特丹。"
QUESTION = "本公司的海外仓编号是多少？只回答编号。"
FILLER_CHARS = 12_000        # 想推到 13 万 token 量级就调大这个数
POSITIONS = {"开头": 0.0, "中间": 0.5, "结尾": 1.0}

FILLER = ("本季度运营会议纪要：各部门汇报了既定的常规事项，"
          "讨论了办公用品采购、员工培训计划与季度复盘安排。") * 200


def build_document(ratio: float) -> str:
    """把关键事实插进填充文本的 ratio 处。"""
    filler = FILLER[:FILLER_CHARS]
    cut = int(len(filler) * ratio)
    return filler[:cut] + "\n" + NEEDLE + "\n" + filler[cut:]


def ask(document: str) -> tuple[str, dict]:
    body = {
        "model": MODEL,
        "max_tokens": 2000,        # 长上下文下模型思考更久，别卡紧（见 AGENTS.md 的踩坑记录）
        "messages": [{"role": "user",
                      "content": f"读下面的资料，然后回答问题。\n\n{document}\n\n{QUESTION}"}],
    }
    req = urllib.request.Request(
        BASE_URL + "/v1/messages",
        data=json.dumps(body).encode(),
        headers={"x-api-key": API_KEY, "anthropic-version": "2023-06-01",
                 "content-type": "application/json"},
    )
    with urllib.request.urlopen(req, timeout=300) as resp:
        data = json.loads(resp.read())
    text = "".join(b.get("text", "") for b in data["content"] if b["type"] == "text")
    return text, data["usage"]


if __name__ == "__main__":
    for label, ratio in POSITIONS.items():
        text, usage = ask(build_document(ratio))
        # 判据：编号出现 + stop_reason 不是 max_tokens（否则是空输出，不是「没读到」）
        hit = "WH-7742" in text
        print(f"{label:>4} 命中={hit}  input={usage['input_tokens']}  "
              f"停止原因见响应（必须确认不是 max_tokens 才能下结论）")
```

> **实跑状态：未实跑。** 这个脚本是本次新写的，用来补上本节「只有结果表、没有脚本」的缺口 —— 它没在这台机器上跑过，所以**不要把它给出的任何数字当实测**。想验证就自己跑一次：判据是「关键事实放中间时命中率是否下降」，而不是「模型有没有输出某个标记」。


### 为什么会这样

类比一下你的直觉来源：session 是有索引的键值存储，读取是精确的。而上下文更像**一个带宽有限的注意力通道** —— 内容确实都在，但「被读到」不是自动发生的。

  chart={`
flowchart TB
    A["你要给模型的信息"] --> B{"放在哪里？"}
    B -->|"后端习惯：全部塞进上下文"| C["内容确实都在<br/>但注意力被稀释"]
    C --> C1["开头 / 结尾：利用率高"]

关键在于：**「放进去」是一个动作，「被读到」是另一个动作** —— 后端里这两件事是同一件，LLM 里不是。

### 替代方案

| 后端做法 | LLM 里应该改成 |
|---|---|
| 把状态都存在内存里，需要时读 | 只保留当前需要的，其余用检索按需取 |
| 日志越详细越好（为了排查） | 上下文里越少越好（为了效果），详细内容存外部 |
| 状态必须精确一致 | 假设模型会漏读，关键约束要在开头和结尾各说一次 |
| 缓存能减轻开销 | 缓存能省钱，但不能解决注意力稀释 |

## 哪些直觉仍然有效

不是所有后端经验都要推翻。**大部分仍然直接适用**，而且用得更狠：

| 仍然有效的直觉 | 在 agent 系统里为什么更重要 |
|---|---|
| 重试与退避 | LLM 失败率高且随机，重试是必需品而非优化 |
| 幂等 | 重试、模型重复调用、流中断重放都会导致重复执行副作用 |
| 超时与熔断 | 单次调用可能跑几分钟，失控循环可能烧光预算 |
| 可观测性 | 出问题时你需要完整轨迹，而不是一个错误码 |
| 资源配额 | 成本是实打实的钱，必须有硬上限 |
| 分层隔离 | 把不确定性关在边界内，核心逻辑保持确定性 |

**一个粗略的划分**：

- **关于「系统怎么运转」的直觉**（可靠性、资源、可观测性）→ 基本都有效
- **关于「程序怎么执行」的直觉**（确定性、精确状态、明确失败）→ 大部分失效

前者是你的优势区。后者是你需要重新建立认识的部分。

## 怎么验证这一节说的

| 论断 | 怎么验 |
|---|---|
| `temperature=0` 不可复现 | 第 2 章的实验脚本，跑 3 次以上 |
| 参数被静默忽略 | 传一个明显生效的参数（如 `max_tokens`），对比不同平台的行为 |
| 截断返回 200 | 把 `max_tokens` 设成 5，看状态码与 `stop_reason` |
| 中间位置被忽略 | 把一条关键约束放在长 prompt 的中部，观察模型是否遵守 |

最后一项特别值得亲手验一次 —— 因为它最反直觉，而一旦你亲眼见到，后面第 3 章的上下文工程就会变得非常具体。
