先看一个教学场景：模型按提示返回 JSON，公司名字段有时被引号、空格或解释文字包住。若测试直接比较整段原始响应，格式差异会让 CI 失败；但这不意味着所有精确断言都不合适。

```python
raw = '{"company": "字节跳动"}'
expected = '{"company":"字节跳动"}'
print("raw text equal:", raw == expected)  # 仅空格不同，整串比较失败
```

```text
raw text equal: False
```

如果 API 契约要求归一化后的公司名必须精确等于“字节跳动”，应先解析并规范化，再对这个业务字段做精确断言。若字段允许别名或自然语言变体，则定义对应的语义判据，不能随意把断言改成子串包含。

> `temperature` 可以影响采样行为，但不是正确性旋钮，也不提供逐字节复现保证。参数支持与具体语义按 provider 和目标模型版本核对；见下文及第 2 章。

因此本节的核心不是“LLM 测试不能精确断言”，而是：**断言对象要对应系统契约**。原始文本格式、解析后的 schema、业务字段和最终任务成功是不同层次，需要不同的检查。

纯函数在依赖、状态和输入都固定时可按确定性契约测试；托管模型 API 通常不承诺相同请求逐字节复现。具体差异要按 provider、模型版本、参数和任务实测，不能把一次变化归因于某个推理机制。

下面讨论三个需要重新核实的默认假设：输出可重复、成功状态代表任务成功、上下文像精确状态存储。它们不是所有场景都会失败，而是不能再未经验证地当作系统契约。

## 直觉一：同样的输入 → 同样的输出

### 不要把模型响应当成纯函数

一条历史记录摘要称：同一个提示在 `temperature = 0` 时三次输出如下。原始请求、逐次响应、模型快照和评分标准没有归档，因此这里只把它当作**不可独立复核的历史记录**：

```text
#1  三味咖啡
#2  三味咖啡
#3  三咖小馆        ← 第三次不同
```

（历史记录标注为 `deepseek-flash`、2026-09-24；缺少原始轨迹，无法验证模型名称、请求是否完全相同或输出是否经过筛选。）

如果这份摘要准确，它至多说明那三次输出并非逐字一致。三次样本不能估计生产发生率，也不能证明差异会在你的任务或当前模型上复现。

### 怎么理解

不要从一次输出差异推断底层原因。你能控制的实验条件包括请求体、模型标识、SDK/provider、调用时间、随机性参数和评分器；服务端实现等因素可能不可见。先记录可观察的请求与响应字段，再用多题、多次和固定评分规则评估差异。Anthropic 当前 API 文档也明确说明：即使 `temperature=0`，结果仍不保证完全确定；这条说明适用于 Anthropic API，不应自动推广为所有 provider 的同一实现机制。[来源：Anthropic Messages API 参数说明](https://platform.claude.com/docs/en/api/messages/create)。

### 替代方案

**把断言写在契约对应的层次上。** 对格式可做解析与 schema 校验；对有明确业务值的字段，可以精确比较；对有容许差异的自然语言，使用经过校准的语义判据。

```python
# 示意片段，未实跑：extract 和测试框架由具体项目提供。
def test_extract_company_name():
    result = extract("张三上周加入了字节跳动")

    # 结构断言：字段存在、类型正确
    assert "company" in result
    assert isinstance(result["company"], str)
    assert len(result["company"]) > 0

    # 业务契约要求规范化后的公司名精确匹配
    assert result["company"] == "字节跳动"

    # 或者：用一组样本统计成功率，而不是要求单次通过
```

更完整的做法是**用样本集统计成功率**：

但「统计成功率」这句话本身要落到三样具体的东西上，否则那两个函数 `load_test_cases()` / `is_valid()` 就是两个空壳：**样本从哪来、判据怎么定、阈值怎么定。**

**样本从哪来**：先明确目标任务与允许使用的数据，再建立覆盖常见、边界和高风险输入的固定样本集。生产日志可能含个人或机密信息；抽样前要按组织的数据政策授权、最小化和脱敏，不能把“最近 N 条”当成无偏代表样本。

**判据怎么定**：把“对”写成可复核的规则。结构化输出可检查 schema、字段语义和业务不变量；答案或动作需要任务特定 grader，不能只靠字符串包含。保存评分器版本，并对边界案例做人工校准。

**阈值怎么定**：不照抄固定通过率，也不以三次重复的波动直接设阈值。先定义重要的回归差异、实验单位、比较方案与错误代价；对同一批题配对比较候选版本，并报告样本覆盖和不确定性。统计设计和样本量依赖基线率、目标差异、独立任务数及检验功效，见第 13 章评估设计；没有这些前提就不能给出通用的“每组 195 条”。

```python
# success_rate_test.py
"""把「抽取是否可靠」做成一个可跑的统计验收。"""

from collections.abc import Callable

# 样本：这里用构造 fixture 演示评分，不读取生产日志。
CASES = [
    {"input": "张三上周加入了字节跳动", "expected": {"company": "字节跳动"}},
    {"input": "李四从腾讯离职，去了小米", "expected": {"company": "小米"}},
    {"input": "王五还在阿里", "expected": {"company": "阿里"}},
]


def is_valid(got: dict, expected: dict) -> bool:
    """本 fixture 的契约要求归一化字段与标注值完全相等。"""
    return got == expected


def success_rate(extract: Callable[[str], dict], cases: list[dict], min_rate: float) -> float:
    if not cases:
        raise ValueError("cases 不能为空")
    if not 0.0 <= min_rate <= 1.0:
        raise ValueError("min_rate 必须在 [0, 1] 内")
    passed = sum(is_valid(extract(case["input"]), case["expected"]) for case in cases)
    rate = passed / len(cases)
    if rate < min_rate:
        raise AssertionError(f"抽取成功率 {rate:.1%}，低于项目门槛 {min_rate:.0%}")
    return rate


def extract_fixture(text: str) -> dict:
    """仅供离线演示评分器；实际模型适配器由读者实现。"""
    known = {
        "张三上周加入了字节跳动": "字节跳动",
        "李四从腾讯离职，去了小米": "小米",
        "王五还在阿里": "阿里",
    }
    return {"company": known[text]}


if __name__ == "__main__":
    print(f"fixture pass rate={success_rate(extract_fixture, CASES, min_rate=1.0):.1%}")
```

> **实跑状态：本地假实现可以运行，输出 100%，没有调用 provider。** 该数字只验证 fixture 和评分器连通，不代表模型质量。将 extract_fixture 换成真实适配器、提供有授权的目标任务样本，并记录模型/API 版本与评分器版本后，测得结果才对应那组特定配置。三题示例不支持总体准确率、置信区间或上线结论。min_rate=1.0 只为演示失败门禁，实际门槛由任务风险与预先定义的评测目标决定。

## 直觉二：请求成功不等于任务成功

### 后端世界的假设

传统服务的成功状态码通常意味着请求通过了协议处理；接下来仍要检查业务语义，但响应一般会让你知道请求在哪个协议阶段结束。接入生成式 API 后，最好把传输/API、生成终止、结构有效、语义符合、业务副作用完成分成独立状态，而不是将它们压成一个 success=true。

### 需要分开的失败层

| 层次 | 例子 | 应由谁判断 |
|---|---|---|
| 传输与 API | DNS、超时、认证失败、速率限制、服务端错误、参数校验失败 | SDK/provider 响应、重试策略和调用预算 |
| 生成结束状态 | 输出长度达到上限、模型拒绝、请求转入工具调用或其它非最终状态 | 目标 provider 的停止字段与协议文档 |
| 结构 | JSON 无法解析、必填字段缺失、类型错误、额外字段不允许 | 本地 parser 与 schema validator |
| 语义 | 字段格式正确但实体、日期、引用或结论错误 | 任务特定 grader、权威数据对照或人工抽样 |
| 业务效果 | 工具执行失败、审批未完成、外部结果不确定 | 宿主状态机、授权层、幂等与结果对账 |

HTTP 2xx 不是“模型答对”；它只说明 API 在自己的协议层返回成功。反过来，解析失败也不一定意味着 API 调用失败。以 Anthropic Messages API 为例，响应会包含 stop_reason；max_tokens 表示输出达到上限，客户端如果只检查 HTTP 状态，可能把截断文本送去解析。字段名和取值都不是跨厂商标准，其它 API 应单独查文档，不能拿 Anthropic 字段硬套。

**错误示例（边界示意，未实跑；省略 SDK client、导入和持久化实现）：**

```python
# 片段只用于展示错误边界；client、json 与 save_to_database 未在此定义。
response = client.messages.create(...)
payload = json.loads(response.content[0].text)
save_to_database(payload)  # 把“可解析”直接当成“任务成功”
```

至少要依次问：响应是否以目标 API 的可接受原因结束？拒答、截断或工具提议是否有单独分支？内容是否符合 schema？字段是否满足业务不变量？若动作已经执行，系统是否能确认效果？对工具调用尤其如此：模型提出动作不等于宿主执行，宿主执行返回也不一定等于下游业务已持久提交。

下面是 Anthropic 协议边界示意，不是适用于所有 provider 的通用字段。代码仅为未实跑伪代码，异常类型、解析器和业务校验器由接入方实现：

```python
# 示意代码，未实跑：省略具体 SDK 类型与校验器实现。
def handle_anthropic_response(response):
    if response.stop_reason == "max_tokens":
        raise TruncatedOutputError("输出到达上限，不能按完整结果解析")
    if response.stop_reason == "refusal":
        return Refused(response.content)
    if response.stop_reason != "end_turn":
        return NeedsProtocolHandling(response.stop_reason)

    payload = parse_and_validate(response.content)
    return validate_business_invariants(payload)
```

真实代码还需按目标 SDK 的响应类型处理 content blocks、工具使用、空内容和异常类型。这里刻意不把所有非 end_turn 情况都转成一个错误：例如，工具提议是协议中的下一步，不等于应重试，也不等于用户请求已完成。

### 重试必须按失败层设计

重试不是因为“LLM 失败概率高”而自动打开。对 429 或暂时性服务端错误，遵守 provider 的退避/重试建议、Retry-After、总 deadline 和费用上限；认证、参数校验、拒答或稳定的 schema 错误通常需要修配置或进入其它处理路径，而不是盲目重复同一请求。客户端超时也不一定意味着服务端没有处理该请求，所以必须区分“安全重试”和“结果未知”。

如果一次模型响应只产生文本，可以评估有限重试是否有价值；如果响应触发了付款、发信、工单创建或其它外部副作用，重试必须由业务幂等键、任务状态与下游查询/对账协议保护。API request ID、tool-use ID 或模型返回的 action ID 都不能自动充当你的业务幂等键。章节后面的 tool calling、持久化与人工审批会分别展开这些边界。

**操作清单**：

1. 将每次调用记录为有明确状态的事件：request accepted、generation ended、parse passed、task graded、effect committed/unknown。
2. 使用目标 provider 的正式文档定义重试类别；把最大次数、退避、deadline 与费用预算绑定在同一个调用策略中。
3. 失败后判断有没有可能已经产生外部效果。若不能确认，进入 unknown/对账状态，不要通过重复调用掩盖不确定性。
4. 监控结构有效率、任务成功率、拒答/截断率、API 错误率和副作用结果；各指标分母要与相应层次一致。
5. 对请求参数是否生效，优先依赖目标模型的官方参数契约。若接口不回显有效参数，单靠一次请求/一个结果无法证明参数造成了行为差异；用配对、重复并控制其它条件的评测，且将结论限定到测试范围。

## 直觉三：prompt 不是权威状态存储

### 后端世界的假设

会话、缓存与数据库都是有明确读写语义的应用组件；它们的读一致性、事务和过期行为由具体系统契约规定。LLM 的上下文则是一次请求的输入。把数据放进消息，不会自动建立键值查询、权限控制、事务隔离或跨轮持久化。

需要区分三个问题：

- **状态在哪里**：用户权限、订单状态、审批结果等权威事实应由应用/数据库管理。
- **哪些内容进入本次上下文**：由宿主根据任务构造，并考虑容量、隐私、权限与成本。
- **模型是否正确利用了内容**：要通过目标任务的评分来检验；不能由“输入里有这段字”推断。

长上下文研究提供了一个重要警示，但不是所有负载的通用定律。Lost in the Middle 论文在特定模型的多文档问答和键值检索任务中观察到相关信息位置会影响表现；部分设置中，信息在中间位置时低于位于开头或结尾。研究本身不能证明所有模型、长度、提示方式、检索任务都有相同曲线，更不能说明每个错答都是“注意力被稀释”。上下文利用率应作为要在自己的目标模型和任务上验证的质量维度。

### 本站机械标记实验的证据边界

旧记录称：在长段干扰文本里，把 CHECKPOINT-OK 放在开头、中间、结尾，各跑一次都通过。这不是有效的 Lost-in-the-Middle 复现：题目只要求抄写固定字符串，没有检验对长文档事实的检索和运用；不同位置之间也没有多题重复、随机顺序和不确定性估计。原始请求/逐次响应、精确模型版本和判分脚本未归档，旧表不能被独立重算。

当时拟写的脚本也未实跑，代码中的填充文本重复次数不足以保证 FILLER_CHARS 配置所称的字符长度。因此，不应引用旧脚本作为“可复现步骤”，更不能把三次成功解释为没有位置效应。这个例子在本书里保留的教学价值，是展示如何识别一个不具备构念效度的实验，并把结论降级为“未知”；不是提供模型性能基线。

### 设计一个能回答实际问题的评测

**问题**：在我们的目标任务和目标模型上，相关事实位置是否改变回答成功率？

**产物**：一份脱敏/合成文档集、逐题唯一答案、三份只改事实位置的请求、固定评分器、模型/SDK/API 版本记录，以及按位置汇总的结果表。

**判据**：只给模型提供一条可从文档定位的事实；问题需要正确提取该事实，答案必须匹配标注值。文档长度、其它文字、提问方式、system prompt、工具配置和输出上限保持不变。对拒答、截断、API 错误、无效答案分别记录，不能把它们混成“未读到”。

**步骤**：

1. 从真实任务里抽取有代表性的检索问题，或先用合成文档做机制测试。若样本来自生产数据，先遵守数据授权、脱敏、留存和访问策略；“抽最近 N 条”不是代表性抽样的充分理由。
2. 对每题生成同一份文档的三个版本，仅将目标事实移至前、中、后位置。按 token 而非字符长度控制上下文规模，并检查分词与边界，避免事实位置变化同时改变输入长度。
3. 预先定义模型与 API 版本、采样参数、每题重复数、请求顺序随机化方法、超时和停止原因判据。若版本或 prompt 改变，就作为新条件记录。
4. 使用精确的事实 grader；保留逐题成功/失败和失败类型。对于含并列事实、否定、时间或实体歧义的题，先确认标注本身可判定。
5. 按任务样本报告三组结果和差值，并说明独立题数、重复次数与不确定性。对同一题的多个位置答案属于配对观测，不能把所有调用都当成互相独立的任务；需要统计推断时，按第 13 章的评测设计选择方法。

**失败形态**：标记本身出现在 prompt 末尾；中间位置恰好有更长文本导致 token 数更大；三个版本不是同一题；评分器只查子串；截断响应被算作模型未找到事实；多题重复却当成独立样本；测试只用一种模型或单一长度，却宣称适用于所有长上下文。任一情况都会让“位置效应”与其它变量混淆。

在某次任务中没看到明显下降，也不能据此推翻论文；看到下降也不能马上归因于注意力机制。可以得出的结论应写成：“在日期、模型/API 版本、样本、长度和评分规则列明的这组评测中，我们观察到……”。这类陈述可以被下一次评测修订，而不是伪装成恒定规律。

### 哪些后端契约仍然有用

session / 数据库可以作为应用状态的权威来源；prompt 是给模型的一次输入，不是事务性读取接口。应用应明确状态所有者、构造模型输入，并对关键任务结果进行验证。

| 后端做法 | Agent 系统里需要补上的检查 |
|---|---|
| 把状态存到数据库，需要时读取 | 明确哪些状态进 prompt、哪些由宿主读取；校验检索结果与版本 |
| 日志越详细越好 | 按诊断目的记录最少必要字段，脱敏并设置访问/保留策略 |
| 状态必须精确一致 | 将权威状态保存在宿主或数据库；不要把模型上下文当成事务性状态存储 |
| 缓存能减轻开销 | 缓存解决重复计算/费用的一部分，不保证模型正确利用上下文 |

## 哪些直觉仍然有效

不是所有后端经验都要推翻。可靠性工程仍然重要，但需要明确它作用于哪一层：

| 后端经验 | 在 Agent 系统中的使用方式 |
|---|---|
| 重试与退避 | 只对明确可重试的瞬态错误重试；遵守 provider 指引、预算和 deadline，并避免重放未知副作用 |
| 幂等 | 在宿主侧为业务动作定义幂等键与状态机，不能把模型调用 ID 当业务幂等 |
| 超时与熔断 | 为请求、任务和循环分别设 deadline/预算；具体限制按交互体验与风险确定 |
| 可观测性 | 记录足以定位问题的脱敏事件、版本和结果；完整原文轨迹可能泄露敏感数据 |
| 资源配额 | 对输入/输出 token、工具次数、并发和费用设明确上限，并处理达到上限的终态 |
| 分层隔离 | 把不确定性限制在边界内，让授权、状态更新和副作用提交由可审计代码控制 |

**一个粗略的划分**：

- **关于明确契约的经验**（超时、预算、幂等、状态所有权、最小化日志）仍然有用，但要按模型调用与工具副作用的边界重新落地。
- **关于纯函数的默认假设**（相同请求逐字节相同、成功状态码代表业务成功、发送了上下文就等于状态可读）需要额外验证，不能作为托管模型的默认契约。

前者是你的优势区。后者是你需要重新建立认识的部分。

## 怎么验证这一节说的

| 论断 | 怎么验 |
|---|---|
| 输出是否需要容差 | 先区分原始文本格式、解析结构和业务字段，再按契约写断言 |
| 目标模型是否支持参数 | 查该模型/API 当前文档；不要用跨厂商的概括替代核对 |
| 输出是否被截断 | 在目标 API 中触发低上限，记录 HTTP 状态、停止字段和解析结果 |
| 信息位置是否影响任务表现 | 对真实检索问题只改变信息位置，控制上下文长度并报告分位置结果；不要用固定标记任务代替语义检索 |

是否观察到位置效应由任务和模型决定；即使没观察到，也不能据此推翻论文或推广到其它负载。
