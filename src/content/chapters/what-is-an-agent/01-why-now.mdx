先看一段真实的交互。下面是我对一个模型发出的请求，以及它返回的原始响应结构：

```text
请求：北京今天天气怎么样？
（同时附上了一个工具定义：get_weather(city: string)）

响应：
  stop_reason: tool_use
  content:
    [thinking]   （模型的内部推理，未展开）
    [text]       "I'll check the current weather in Beijing for you."
    [tool_use]   name=get_weather  id=call_00_gZoTZGIoOSdb4RuDd7m87359
                 input={"city":"北京"}
  usage: input_tokens=300  output_tokens=69
```

（实测数据，`deepseek-flash`，2026-09-24。完整采集脚本见本节末尾。）

注意 `stop_reason` 这个字段：**`tool_use`**。

它不是 `end_turn`。模型没有在回答完这句话之后结束，而是**主动停下来，等着你给它工具的执行结果**。它自己判断出「这个问题我答不了，需要调用工具」，并从工具的 JSON Schema 中生成了一个符合结构的参数 `{"city":"北京"}`。

这个能力，是整个 agent 开发领域存在的前提。

## 为什么这件事不平凡

如果你只有调用 LLM API 的经验，可能觉得这没什么：模型输出一段结构化的 JSON 而已。

但回到几年前，模型做不到这件事。当时的常见做法是：**让模型输出自由文本，然后用正则表达式去解析"它想调用哪个函数"**。

那种做法的失败率高得离谱，因为：

| 问题 | 表现 |
|---|---|
| 格式漂移 | 你要 `{"city": "北京"}`，它回 `city: 北京`、`{"city": 北京}`、或者带上一句"好的，我来查询" |
| 幻觉参数 | 你要求城市名，它生成了一个不存在的城市编码 |
| 无法表达"不需要工具" | 它总得输出点什么，于是硬塞一个调用 |
| 多轮无法串联 | 前一轮的调用结果，下一轮它不认 |

**关键差别在于：工具调用把「意图」从自然语言里抽了出来，变成了一个可校验的结构。** 有了 `tool_use` 这个类型化的输出，你的代码可以：

- 直接 `JSON.parse` 参数，不需要正则
- 用 JSON Schema 校验参数合法性
- 通过 `stop_reason` 明确知道模型是「说完了」还是「在等工具结果」
- 用 `tool_use_id` 把调用与结果精确配对

这不是「模型变聪明了」，而是**接口形态变了**。而接口形态的变化，才是工程上能大规模使用它的原因。

## 但代价也在数据里

回到上面那段实测数据，有个数字值得单独看：

```
input_tokens = 300
```

而同一模型处理一句纯文本请求（不带工具定义），输入只有 **33 token**。

**多出来的 270 多个 token，全是工具相关的开销。**

进一步测下去，会得到一个更精确的结构。同一句「回复：好」，只改变工具定义的数量：

| 工具数量 | input_tokens | cache_read | **总输入** |
|---:|---:|---:|---:|
| 0 | 33 | 0 | **33** |
| 1 | 306 | 0 | **306** |
| 3 | 174 | 256 | **430** |
| 5 | 170 | 384 | **554** |

（实测数据，`deepseek-flash`，2026-09-24。）

### 先注意中间那个陷阱

单看 `input_tokens` 这一列，**3 个工具（174）竟然比 1 个工具（306）还少** —— 看起来像「工具越多越便宜」。

不是。看 `cache_read` 那列就明白了：**服务端自动做了 prompt caching**，把重复的工具定义缓存住了。而 `input_tokens` 的定义是「**未命中缓存的**输入 token」—— 缓存命中越多，这个数字越小。

这本身是个值得记住的坑：

```
总输入 token = input_tokens + cache_read_input_tokens + cache_creation_input_tokens
```

**只看 `input_tokens` 算成本，会系统性低估。** 这是我自己第一次做这个实验时被误导的地方 —— 数据看起来自相矛盾（1 个工具比 3 个工具贵），不做交叉验证就会得出错误结论。

### 真实的成本结构

按总输入看，规律就清楚了：

```
0 个工具 →  33 token
1 个工具 → 306 token    （开了 tools 数组，+273）
3 个工具 → 430 token    （每个工具约 +62）
5 个工具 → 554 token    （每个工具约 +62）
```

线性拟合一下：

- **启用工具调用本身有约 200 token 的固定开销** —— tools 数组的结构包装
- **每个工具再约 60 token** —— name、description、JSON Schema

这个结构值得记住，因为它直接决定两个工程决策：

**决策一：要不要用工具调用？** 有约 200 token 的入场费。如果你只需要偶尔调一次工具，也许直接让模型输出 JSON 更划算。

**决策二：给几个工具？** 每个约 60 token。10 个工具就是 600 token，**而且每一次请求都要付一遍**。一个有 20 轮工具调用的任务，光工具定义就要花掉 12000 token —— 这还没算上模型实际输出的内容。

> 注意：这里说的「每次都付」指的是**没有缓存命中**的情况。如果工具定义稳定不变且平台支持缓存，重复部分可以按折扣价读取（第 5 章会详细讲缓存的规则与陷阱）。但缓存有前提条件，不能假定它一定生效。

这件事后面会反复出现：

- 第 4 章会讲工具数量膨胀如何同时拖累效果与成本
- 第 5 章会讲怎么让工具定义本身可缓存
- 第 15 章会讲成本优化的整体策略

现在你只需要记住一个判断：**「模型能调用工具了」这个能力是免费的，但你让它知道有哪些工具可用，是要花钱的。**

## 三个条件

agent 从「论文里能跑」到「工程上能用」，需要三个条件同时成立。

### 条件一：工具调用成为模型的可靠原生能力

上面已经用实测数据说明。补充一点：**不同厂商在这件事上的进度不一样**。

实测中我发现 DeepSeek 的兼容端点完整支持工具调用，包括 `tool_use` 类型的 content block 与 `stop_reason`。但兼容性有边界——同一份兼容文档里列出了一些**被忽略**的字段。

这提醒一件事：**「支持工具调用」是一个需要逐家验证的结论，不能从「兼容 API」推出。**

### 条件二：上下文窗口足以装下任务状态

当前 Claude 主力模型的上下文窗口是 **100 万 token**（[模型总览](https://platform.claude.com/docs/en/about-claude/models/overview)）。

这个数字的意义不在于「能塞多少文档」，而在于**一次任务的状态能一直留在上下文里**。

回想工具调用的流程：模型要求调用工具 → 你执行 → 把结果喂回去 → 模型可能再要求调用另一个工具 → 如此反复。假设一个任务要调用 10 次工具，那么整个过程中：

- 每一步的工具调用记录
- 每一次的执行结果
- 原始任务描述与系统提示

**全都要留在上下文里**，否则模型会丢失上下文、重复调用、或者忘记目标。

在小窗口时代，这类多步任务跑几步就爆了。100 万 token 让「一个任务跑几十步」成为可能。

代价是：**上下文里内容越多，模型对每一部分的关注度越低**（context rot）。所以「窗口够大」只是让长任务**可能**成立，能不能**用好**是第 3 章的问题。

### 条件三：成本与延迟落在可接受区间

这一条最容易被忽略，但它决定的是商业可行性而不是技术可行性。

不做具体数字的计算（价格变动太快，见[定价页](https://platform.claude.com/docs/en/about-claude/pricing)），而是给你一个判断框架：

**agent 的单次任务成本，要能和「人工完成同样任务」的成本比较。**

一个 agent 任务如果平均调用 20 次模型、消耗几十万 token，它的成本能否被它节省的人力覆盖？这个问题的答案决定了你该做 agent 还是做 workflow。

这里有个容易忽略的点：**成本是随任务长度非线性增长的**。

- 每一轮都要重发历史（第 1 章讲过，这是平方级增长）
- 每一轮可能触发多次工具调用
- 失败重试会成倍放大

所以估算 agent 成本时，**不能按"单次调用成本 × 次数"算**，而要按「任务平均步数 × 每步平均 token × 单价」算，并且给重试留出余量。

## 为什么是「同时」成立

三个条件里**任何一个缺失，agent 都会退化成不可用的东西**：

| 缺哪个 | 会退化成 |
|---|---|
| 缺条件一 | 靠正则解析自由文本 —— 可靠性不足，无法产品化 |
| 缺条件二 | 长任务中途遗忘 —— 多步工具调用无法串联 |
| 缺条件三 | 单次任务比人工还贵 —— 技术上可行，商业上不成立 |

这也是为什么「agent」这个概念其实不新（ReAct 论文发表于 2022 年，见 [arXiv:2210.03629](https://arxiv.org/abs/2210.03629)），但工程实践是近几年才起来的 —— **不是想法变了，是条件齐了。**

## 这对你意味着什么

作为一个后端工程师，这个判断有很实际的后果。

**你已有的能力大部分可以直接迁移**：重试、幂等、超时、可观测性、资源配额 —— agent 系统全都要用，而且用得更狠（因为它比普通服务更不确定、更贵、更容易失控）。

**但有一部分直觉会失效**，而且失效得很隐蔽。举一个最小的例子：

> 你习惯了「同样的输入应该得到同样的输出」。这个假设在 agent 系统里不成立 —— 即使你把 `temperature` 设为 0。

实测数据：同一个提示在 `temperature=0` 下跑三次，得到了「三味咖啡 / 三味咖啡 / 三咖小馆」——**三次里有一次不同**。原因不止一个（浮点运算的非确定性、服务端批处理、模型版本更新），详见第 2 章。

**你要重新学的，主要是这类"哪些假设不再成立"的判断。**

## 怎么验证这一节说的

我在这节里做了几个论断，你都可以自己验：

| 论断 | 怎么验 |
|---|---|
| 工具调用返回 `stop_reason: tool_use` | 用本节末尾的脚本跑一次 |
| 工具定义吃掉约 265 token | 同一个提示，分别带工具定义和不带，对比 `input_tokens` |
| `temperature=0` 不可复现 | 第 2 章的实验脚本 |

我倾向于把「可验证」当作这类内容的底线。**如果一个说法你没法用代码验证、也找不到官方文档支撑，那它更可能是作者的印象而不是事实。**

## 附录：采集工具调用数据的脚本

```python
# probe_tool_call.py
"""观察一次完整的工具调用：模型返回了什么、花了多少 token。

需要环境变量中的凭据。base_url 留空则用 Anthropic 官方端点。
"""

import json
import os

import anthropic

client = anthropic.Anthropic(
    api_key=os.environ.get("ANTHROPIC_API_KEY")
    or os.environ.get("ANTHROPIC_AUTH_TOKEN"),
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)

MODEL = os.environ["VERIFY_MODEL"]

TOOLS = [
    {
        "name": "get_weather",
        "description": "查询指定城市当前的天气",
        "input_schema": {
            "type": "object",
            "properties": {"city": {"type": "string", "description": "城市名"}},
            "required": ["city"],
        },
    }
]

PROMPT = "北京今天天气怎么样？"


def call(with_tools: bool) -> dict:
    kwargs = {
        "model": MODEL,
        "max_tokens": 2000,
        "messages": [{"role": "user", "content": PROMPT}],
    }
    if with_tools:
        kwargs["tools"] = TOOLS

    response = client.messages.create(**kwargs)

    return {
        "stop_reason": response.stop_reason,
        "blocks": [b.type for b in response.content],
        "tool_use": [
            {"name": b.name, "input": b.input}
            for b in response.content
            if b.type == "tool_use"
        ],
        "input_tokens": response.usage.input_tokens,
        "output_tokens": response.usage.output_tokens,
    }


if __name__ == "__main__":
    with_tools = call(True)
    without = call(False)

    print("带工具定义:")
    print(json.dumps(with_tools, ensure_ascii=False, indent=2))
    print("\n不带工具定义:")
    print(json.dumps(without, ensure_ascii=False, indent=2))

    delta = with_tools["input_tokens"] - without["input_tokens"]
    print(f"\n工具定义本身的开销: {delta} token")
```

> **实跑状态**：**数据是实测的** —— 本节的响应结构与 token 数字来自真实调用。但上面这份 Python 脚本用的是 SDK 写法，而我的采集用的是直接 HTTP 请求；字段名一致，脚本本身未在官方端点验证。
