先看一个 Anthropic Messages API 客户端工具调用的协议示意。它不是下面那组历史 DeepSeek usage 记录的原始响应：

```text
请求：北京今天天气怎么样？
（同时附上了一个工具定义：get_weather(city: string)）

响应：
  stop_reason: tool_use
  content:
    [text]       "I'll check the current weather in Beijing for you."
    [tool_use]   name=get_weather  id=toolu_example
                 input={"city":"北京"}
```

（协议示意，非实测原文；`stop_reason`、`tool_use` 与 `tool_result` 的含义按 Anthropic Messages API 文档说明。DeepSeek 兼容端点的历史观测另行标注，不能假定两者字段行为完全一致。）

注意 `stop_reason` 这个字段：**在 Anthropic Messages API 的这个客户端工具示例中，它是 `tool_use`**。其他厂商的字段和枚举可能不同，兼容端点也要按实际响应核对。

（Anthropic Messages API 的 `stop_reason` 用来描述该响应的停止原因：`end_turn` 表示模型本轮结束，`tool_use` 表示返回客户端工具调用，`max_tokens` 表示达到输出 token 上限。应按具体 API 的协议判断终态；一个字段不能独自证明任务成功。详见 [工具调用流程](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) 与 [停止原因](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)。）

它不是 `end_turn`。在这个 API 契约里，模型返回了工具调用提议；如果这是客户端工具，宿主还要校验并执行，再把结果回传。模型根据请求和工具定义提出了 `{"city":"北京"}`，这不等于宿主必须执行，也不等于参数已通过业务授权。

结构化工具调用是现代 agent 工程的重要接口能力之一，但不是 agent 概念的起点，也不是所有 agent 的必要条件。ReAct 等研究早于现在的工具调用 API；工程变化在于主流 API 逐步提供了更标准的动作表示和宿主往返协议。

## 为什么这件事不平凡

如果你只有调用 LLM API 的经验，可能觉得这没什么：模型输出一段结构化的 JSON 而已。

较早的 API 集成常要让模型按约定输出文本或 JSON，再由应用解析；模型并非完全不能生成结构化文本，而是应用与模型之间缺少统一、可校验的工具调用协议。如今也不能把所有接口都概括成同一种工具调用格式。

自由文本解析可能遇到这些失败形态；这里列的是工程风险示例，不是有分母支持的失败率结论：

| 问题 | 表现 |
|---|---|
| 格式漂移 | 你要 `{"city": "北京"}`，它回 `city: 北京`、`{"city": 北京}`、或者带上一句"好的，我来查询" |
| 幻觉参数 | 你要求城市名，它生成了一个不存在的城市编码 |
| 无调用表达容易含糊 | 自由文本可说明“不需要工具”，但应用要区分说明文字、无调用和格式错误 |
| 多轮状态依赖约定 | 应用需明确把工具结果与调用关联并按协议回填；非结构化拼接可能丢失关联或重复结果 |

**关键差别在于：工具调用协议把「动作提议」从自然语言里抽出来，表示成结构化数据。** 有了 `tool_use` 这类类型化输出，你的代码可以：

- 按 SDK/API 的结构读取参数，不必从自由文本猜调用意图
- 在宿主侧执行 schema、业务规则和授权校验；schema 约束能力取决于具体 API/模式
- 通过 `stop_reason` 明确知道模型是「说完了」还是「在等工具结果」
- 用 `tool_use_id` 把调用与结果精确配对

这不只是「模型变聪明了」，也是**模型能力、API 协议和宿主工程共同演进**。结构化接口降低了集成成本，但不会自动保证参数正确、工具安全或任务成功。

## 但代价也在数据里

### 先把 token 定义清楚

**token 不是字符，也不是单词**，而是模型词表切分后的单位。token 数会影响上下文容量与处理成本，也会影响部分延迟；计费口径、缓存计量和时间关系都由模型/API/服务商决定（第 1 章会展开切分规则）。本节下文提到的 `input_tokens=300` 是单独的历史 DeepSeek usage 摘要，不是上面协议示意中的数值。

为什么不能按字算？因为模型读的是一串整数下标，每个下标对应词表里的一个片段。同一句话在不同模型上切出来的片段数可以不同，所以「多少个字」推不出「多少个 token」。

回到实测数据，这个换算可以拆得很具体。同一模型处理一句 7 个字符的纯文本请求，输入是 **35 token**：

```text
「什么是幂等性？」 → 35 token
   ├─ 文本内容本身  约  5 token
   └─ 请求结构开销  约 30 token   ← role / content 包装 + 服务端附加
```

（这是本站第 1 章第 1 节保留的历史测量摘要，曾标注 `deepseek-flash`；原始逐样本请求与采集文件未归档，无法复核。「约 5 / 约 30」是当时的拆分估算，不是官方字段。）

**量级锚**：第 1 章的一组历史摘要曾观察到该语料/模型下中文字符与 token 大约为 1:0.8；原始样本未归档，这不是跨文本、模型或 API 的换算规则。估算时，用目标模型的 tokenizer 或 token-count API 对自己的输入抽样测量；`input_tokens=300` 也不能直接换算成固定页数。

> 关于 `JSON Schema`（上面工具定义里那个 `input_schema` 字段）：它是描述 JSON 数据形状的声明式语法，可以表达字段、类型和必填项。工具定义通常使用 JSON Schema 的一个受支持子集；是否由服务端强制、支持哪些关键字，取决于具体 API 与模式。宿主仍需做业务校验与授权。第 5 章会专门讲约束力边界。

回到上面那段实测数据，有个数字值得单独看：

```text
input_tokens = 300
```

而历史记录里同一模型处理一句纯文本请求（不带工具定义）时，`input_tokens` 记为 **33 token**。

两条历史记录中 `input_tokens` 相差 267；这个字段差值不能单独归因于 schema，也可能含 API 封装、缓存口径和请求设置差异。

进一步测下去，历史记录里有一组同一句「回复：好」的观测，尝试只改变工具定义数量：

| 工具数量 | input_tokens | cache_read | **已报告字段小计** |
|---:|---:|---:|---:|
| 0 | 33 | 0 | **33** |
| 1 | 306 | 0 | **306** |
| 3 | 174 | 256 | **430** |
| 5 | 170 | 384 | **554** |

（历史实测摘要曾标注 `deepseek-flash`。正文旧日期为 2026-09-24，但项目数据台账 `docs/DATA.md` 将这组相同数值记为 2026-10-08；原始逐次请求未归档，无法判断是日期错误还是不同批次，也无法独立复算。）

表中的小计只把展示出的 `input_tokens` 与 `cache_read` 相加；`cache_creation` 等字段未在历史材料中保留，因此这些数字不是完整上下文输入或账单。

### 先注意中间那个陷阱

单看 `input_tokens` 这一列，**3 个工具（174）竟然比 1 个工具（306）还少** —— 看起来像「工具越多越便宜」。

不能据此说工具越多越便宜。此兼容端点当时返回了 `cache_read` 字段，显示有部分输入被报告为缓存读取；而单独的 `input_tokens` 无法代表完整上下文输入或账单。该字段语义是端点特定的，应以对应文档和原始响应核对，不能推广为所有 API 的定义。

> **prompt caching 是什么**：服务商可能缓存符合其规则的请求前缀，以减少重复处理或降低缓存输入价格。缓存边界、最小长度、过期时间、计量字段和失效范围由 endpoint 决定；前缀后部变化不必然让此前所有缓存失效。可对照 [Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) 与 [DeepSeek context caching](https://api-docs.deepseek.com/guides/kv_cache/) 的差异，并核对目标 endpoint 的响应字段（第 5 章会展开）。

这是一个值得记住的计量边界：

```text
以 Anthropic Messages API 返回这些分项的情况为例：窗口输入量 = input_tokens + cache_read_input_tokens + cache_creation_input_tokens
```

**单看一个 usage 字段可能漏掉缓存读取或写入。** 但加总上下文 token 也不等于账单金额：缓存读写可能适用不同价格，且计费项由服务商定义。历史表格缺原始请求与逐字段 usage，不能据它断言 1 个工具比 3 个工具贵或便宜。

若这些历史字段和为上下文输入计量，可按下面方式复算记录到的 token 数（不等于账单金额）：

```text
1 个工具：input 306 + cache_read 0 = 306  ← 仅按历史表格已展示字段求和
3 个工具：input 174 + cache_read 256 = 430  ← 未知 cache_creation；不能据此计算完整用量或账单
```

（示例：构造数据，未实跑 —— 按表中字段求和；原始 usage 未归档，不能验证字段口径。）

3 工具样本的记录上下文输入更多，但**这不足以判定账单更贵**，需要使用该 endpoint 的缓存计价规则和完整 usage 计算。

### 历史 usage 摘要能说明什么

按历史摘要的记录上下文输入看，工具数增加时观测值上升，但样本不足以推导通用边际成本：

```text
0 个工具 →  33 已报告字段小计
1 个工具 → 306 已报告字段小计（比 0 工具样本 +273）
3 个工具 → 430 已报告字段小计（比 1 工具样本 +124）
5 个工具 → 554 已报告字段小计（比 3 工具样本 +124）
```

历史摘要给出的 0/1/3/5 工具数对应已报告字段小计 33/306/430/554；它不能证明总 input 或账单金额。摘要显示 `0→1` 的差值与之后区间不同，但因原始逐次 usage、cache_creation 字段和请求设置未归档，无法可靠拆出固定开销或单工具 schema 成本。

对目标系统，应在相同模型、提示与消息设置下记录不带工具和带工具请求的完整 usage，并区分未缓存输入、缓存写入与缓存读取。工具定义可能占据请求上下文；实际计费还取决于 endpoint 的缓存策略、工具加载协议和当前价格。不要把旧样本的“约 60 token/工具”当成通用常数。

是否改用 JSON 输出、host 分组或延迟加载，要按具体任务核算：包括额外路由调用、总输入、缓存、选择质量、延迟和授权边界。工具列表本身的 token 差值不足以单独决定架构。

这件事后面会反复出现：

- 第 4 章会用受限样本区分工具请求输入与选择质量，不把工具数量直接等同于准确率下降
- 第 5 章会讲怎么让工具定义本身可缓存
- 第 15 章会讲成本优化的整体策略

现在先记住：工具定义可能增加请求上下文；实际费用需结合 endpoint 的 usage、缓存与工具加载协议测量。

## 三类工程约束

下面三项是这节用于解释工程落地的观察框架，**不是 agent 的必要且充分条件，也不是所有任务都必须同时满足的门槛**。系统能否部署，还取决于任务风险、质量证据、授权与隔离、可观测性、故障恢复和产品价值等因素。

### 约束一：动作接口与宿主策略要匹配任务

上面说明了结构化工具提议的一种 API 形态。补充一点：**不同厂商、API 模式和服务端工具的协议不同**。

历史实测记录显示，DeepSeek Anthropic 兼容端点在当时返回了 `tool_use` content block 与 `stop_reason`。该记录缺少可重放的完整请求/响应，不能据此确认当前兼容范围；兼容文档列出的忽略字段也只适用于其声明的端点和版本。

这提醒一件事：**“支持工具调用”必须按目标 endpoint、API 模式和所需字段逐项验证，不能仅从“兼容 API”标签推出。**

### 约束二：上下文窗口与外部状态要共同管理

截至 2026-10-21，Anthropic 的模型总览列出多款 Claude 模型具有 **100 万 token 上下文窗口**；这只是厂商与模型系列当前的规格，平台可用性、单次请求限制和其他厂商规格需另查[模型文档](https://platform.claude.com/docs/en/models/overview)。

窗口大小影响单次请求可容纳多少输入与输出，但不是“任务状态存储”的替代品。

回想工具调用的流程：模型要求调用工具 → 你执行 → 把结果喂回去 → 模型可能再要求调用另一个工具 → 如此反复。假设一个任务要调用 10 次工具，那么整个过程中：

- 每一步的工具调用记录
- 每一次的执行结果
- 原始任务描述与系统提示

这些信息可能在后续请求中以完整对话、摘要、结构化状态或外部检索等方式提供。不是每个历史 token 都必须永久塞回上下文；需要明确状态如何压缩、保留、重建和校验。

较大的窗口能容纳更长的单次上下文，但不会自动让“几十步任务”可靠；工具结果膨胀、状态漂移、权限和预算仍要单独设计。Anthropic 将 [compaction](https://platform.claude.com/docs/en/build-with-claude/compaction) 列为长对话和 agentic workflow 的上下文管理策略，并提醒 [token 增长可能造成 context rot](https://platform.claude.com/docs/en/build-with-claude/context-windows)。

代价是：**上下文里内容越多，模型对每一部分的关注度越低**（context rot）。所以「窗口够大」只是让长任务**可能**成立，能不能**用好**是第 3 章的问题。

### 约束三：成本与延迟符合产品目标

这一条决定系统是否符合产品目标，目标可以包括单位经济性、延迟、可访问性或服务质量，不只等于“比人工便宜”。

不做具体数字的计算（价格变动太快，见[定价页](https://platform.claude.com/docs/en/about-claude/pricing)），而是给你一个判断框架：

**agent 的单次任务成本，应与任务价值、人工介入成本和质量/延迟目标一起比较。**

例如一个任务需要多次模型调用和大量上下文，需测算运行成本是否被任务价值抵消；这只是部署决策的一部分，不能单独决定选 agent 还是 workflow。

这里有个容易忽略的点：**累计输入成本可能随任务长度超线性增长**。

- 若每轮都把持续增长的历史完整重发，累计输入量可能随轮数呈超线性增长；摘要、检索、缓存和上下文编辑会改变这条成本曲线
- 每一轮可能触发多次工具调用
- 失败重试会成倍放大

所以估算 agent 成本时，不应只拿“单次平均成本 × 平均调用次数”作为完整账单。逐次请求的输入会随上下文变化，还要分开统计输入/输出、缓存读写、工具和重试成本；按代表性任务报告分布与尾部，并用宿主强制的预算边界控制最坏情形。具体计费字段按供应商文档核对。

## 为什么这三类约束值得一起看

三类因素可能造成约束，但后果并非二元，也不一定令系统不可用：

| 观察到的约束 | 可考虑的响应 |
|---|---|
| 动作接口或工具策略不匹配 | 可能需要改用结构化协议、规则或人工步骤；不是所有 agent 都依赖模型工具调用 |
| 上下文或状态管理不足 | 可考虑摘要、检索、外部状态、分阶段任务或缩小任务范围 |
| 成本/延迟超出目标 | 可能采用 workflow、缩小适用范围、批处理、人工协作或不部署 |

ReAct 是 2022 年一篇有影响力的 [LLM 方法论文](https://arxiv.org/abs/2210.03629)，展示了推理与行动交替的设计；它不是 agent 概念的起源。近年工程实践变化来自模型能力、标准化 API、运行时与工具生态等多因素演进，不宜归结为“三个条件同时齐备”。

> **ReAct 是什么**：它把「推理」与「行动」交替成一个循环 —— Reason（模型提出下一步）→ Act（宿主按策略决定是否调用工具）→ Observe（把工具结果读回来），再进入下一轮 Reason。模型可以通过协议响应提出工具调用或表示本轮回答结束（例如某些 API 的 `tool_use` / `end_turn`）；**这些是模型给出的信号，不是宿主必须服从的控制命令。** 宿主仍负责校验响应、权限与预算，并决定执行、拒绝、重试、暂停或终止；状态机和硬上限可以在模型信号之外结束循环。上面那段实测只是「模型提出工具调用，宿主收到信号后等待工具结果」的一步。第 10 章会把 ReAct 与 Plan-Execute、Reflection 放在一起实测对比。

## 这对你意味着什么

作为一个后端工程师，这个判断有很实际的后果。

**你已有的能力大部分可以直接迁移**：重试、幂等、超时、可观测性、资源配额 —— agent 系统仍然需要；模型输出波动、动态路径与额外资源消耗则要求把这些机制按任务重新验证。

**但有一部分直觉会失效**，而且失效得很隐蔽。举一个最小的例子：

> 你习惯了「同样的输入应该得到同样的输出」。对托管模型 API，固定输入和 `temperature=0` 也不一定构成逐字复现契约；稳定性取决于 provider、模型快照和运行环境。

历史记录摘要称，同一提示在 `temperature=0` 下三次得到「三味咖啡 / 三味咖啡 / 三咖小馆」。原始响应、模型快照与请求配置未归档，无法独立复核；即使记录属实，也只能说明那组运行并未逐字一致，不能确认具体原因或估算一般发生率。详见第 2 章的验证范围说明。

**你要重新学的，主要是这类"哪些假设不再成立"的判断。**

我在这节里做了几个论断，你都可以自己验：

| 论断 | 怎么验 |
|---|---|
| 当前目标 endpoint 如何表示工具调用与停止原因 | 用本节末尾的脚本跑一次，并对照该 endpoint 文档 |
| 工具定义对 usage 的影响 | 固定 endpoint、模型、提示和请求参数；重复配对并交替请求顺序，记录每次完整 usage 与缓存读写字段。单次差值只是该次响应的描述，不能单独归因于工具 schema |
| 历史三次调用的输出不同 | 第 2 章的实验记录；重跑只能得到新样本，不能恢复原始实验 |

我倾向于把「可验证」当作这类内容的底线。**如果一个说法你没法用代码验证、也找不到官方文档支撑，那它更可能是作者的印象而不是事实。**

## 从这里开始：把上面的数字跑一遍

协议示意可通过自有凭据复测；历史 token 数与架构归纳不能靠重新运行一次就证明。下面脚本只用于观察当前 endpoint 返回的字段。

在 Python 3.10+ 的隔离虚拟环境安装 Anthropic SDK；分享或部署时固定实际验证过的 SDK 版本。此脚本只适用于该 SDK 支持的 Anthropic-compatible endpoint。API 字段和认证应以该 endpoint 的文档为准。

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install anthropic
```

先准备三个配置项；API Key 支持两种环境变量名。脚本只读取下表列出的这些配置：

| 环境变量 | 填什么 | 从哪拿 |
|---|---|---|
| `ANTHROPIC_API_KEY` 或 `ANTHROPIC_AUTH_TOKEN` | 你的 API Key；代码优先读取 `ANTHROPIC_API_KEY`，再回退到 `ANTHROPIC_AUTH_TOKEN` | 官方 SDK 环境变量名或兼容端点文档指定的变量；见下方「取 Key」 |
| `ANTHROPIC_BASE_URL` | 端点地址；**留空则用 Anthropic 官方端点** | 用官方端点就不设；用中转/兼容端点则填它给的地址，形如 `https://api.deepseek.com/anthropic` |
| `VERIFY_MODEL` | 模型名（本节的实测值） | 端点支持哪些模型名，看它文档或报错信息 —— 模型名写错时，DeepSeek 的错误响应会直接把可用模型名列出来 |

**取 Key（Anthropic 或明确兼容 Anthropic Messages API 的服务商）**：

1. 打开 Anthropic 或目标 Anthropic-compatible 服务商的控制台 → API Keys 页面
2. 建一把**专用的** Key；如控制台支持预算或限额，按你的风险策略配置，不要复用生产凭据
3. 把 Key 粘进 `ANTHROPIC_AUTH_TOKEN`。**不要写进代码、也不要提交进仓库**

本站在 2026-10-09 对 DeepSeek Anthropic-compatible endpoint 的记录显示，该端点当时使用 `x-api-key`，而本项目尝试的 Bearer 认证失败；这只适用于该次端点与配置。SDK 如何发送凭据应结合版本和服务商文档确认。

跑起来：

```bash
export ANTHROPIC_AUTH_TOKEN="sk-..."
# 用官方端点时下面两行不用设
export ANTHROPIC_BASE_URL="https://api.deepseek.com/anthropic"
export VERIFY_MODEL="deepseek-flash"
python3 probe_tool_call.py
```

它会按固定顺序各发一次请求（先带工具定义，再不带），显示 endpoint 返回的 usage 字段。**这是一对接口探针，不是受控 A/B 实验**：两次调用间的缓存状态、后端路由或模型快照可能变化，单次差值不能单独归因于工具定义。若要估计工具定义带来的 usage 差异，应在目标 endpoint 能力允许的范围内保持模型、提示与请求参数一致，重复配对并交替顺序，保存每次完整请求/响应与缓存读写字段；无法控制缓存时，应分层报告或只作描述性观察。当前复测数字不能替代或验证日期与原始请求均不确定的历史观测。

## 附录：采集工具调用数据的脚本

```python
# probe_tool_call.py
"""观察模型请求、工具调用提议和 endpoint 返回的 usage 字段。

脚本不会执行工具。需要环境变量中的凭据；base_url 留空则用 Anthropic 官方端点。
"""

import json
import os

import anthropic

client = anthropic.Anthropic(
    api_key=os.environ.get("ANTHROPIC_API_KEY")
    or os.environ.get("ANTHROPIC_AUTH_TOKEN"),
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)

MODEL = os.environ["VERIFY_MODEL"]

TOOLS = [
    {
        "name": "get_weather",
        "description": "查询指定城市当前的天气",
        "input_schema": {
            "type": "object",
            "properties": {"city": {"type": "string", "description": "城市名"}},
            "required": ["city"],
        },
    }
]

PROMPT = "北京今天天气怎么样？"


def reported_context_input(usage: dict) -> int | None:
    required = {"input_tokens", "cache_read_input_tokens", "cache_creation_input_tokens"}
    if not required.issubset(usage):
        return None
    return sum(int(usage[name]) for name in required)


def call(with_tools: bool) -> dict:
    kwargs = {
        "model": MODEL,
        "max_tokens": 2000,
        "messages": [{"role": "user", "content": PROMPT}],
    }
    if with_tools:
        kwargs["tools"] = TOOLS

    response = client.messages.create(**kwargs)

    return {
        "stop_reason": response.stop_reason,
        "blocks": [b.type for b in response.content],
        "tool_use": [
            {"name": b.name, "input": b.input}
            for b in response.content
            if b.type == "tool_use"
        ],
        # Preserve all usage fields the SDK received. Field availability and
        # meanings can differ across compatible endpoints.
        "usage": response.usage.model_dump(exclude_none=True),
    }


if __name__ == "__main__":
    with_tools = call(True)
    without = call(False)

    print("带工具定义:")
    print(json.dumps(with_tools, ensure_ascii=False, indent=2))
    print("\n不带工具定义:")
    print(json.dumps(without, ensure_ascii=False, indent=2))

    with_total = reported_context_input(with_tools["usage"])
    without_total = reported_context_input(without["usage"])
    if with_total is None or without_total is None:
        print("\nendpoint 未返回完整缓存 usage 字段，无法计算可比的上下文输入总量")
    else:
        print(f"\n记录到的上下文输入差值: {with_total - without_total} token")
        print("此差值不是账单差值；请按 endpoint 的缓存计价规则计算。")
```

> **实跑状态**：本节引用的 DeepSeek 响应与 usage 数字是作者记录的历史调用摘要，原始请求和逐字段响应没有归档，现无法独立复算。上面的 Python 脚本使用 Anthropic SDK，未在官方端点实跑；兼容端点对模型名、认证、工具协议和 usage 字段的支持也需单独验证。脚本打印 endpoint 实际返回的 usage 字段；仅在输入、缓存读取和缓存写入字段都存在时才计算它们的 token 小计，该小计不是账单差值。
