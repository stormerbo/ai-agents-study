绝大多数检索项目的流程是这样：选一个向量库、接一个嵌入模型、把文档丢进去、调 top-k。**切分**这一步往往只有一个默认值，没人回头看它。

但它是最难补救的一步。向量库可以换、重排模型可以加，而**切分的粒度决定了这些手段能看到什么** —— 一个被从中间切断的段落，后面的所有环节都救不回来。

这一节全部用词法检索（BM25）做实验，语料是本站的 28 篇正文。为什么用词法而不是向量，第 1 节末尾交代过：先量清楚基线。

## 先说一个我自己踩的坑：评测粒度选错，结论会反转

第一版实验里，我的指标是「**正确答案在哪一篇**，检索结果里有没有这一篇」。三种切分策略跑出来是这样：

| 策略 | recall@1 | recall@3 | recall@5 | recall@10 |
|---|---:|---:|---:|---:|
| 固定 400 字、无重叠 | 10/15 | 12/15 | 13/15 | 14/15 |
| 固定 400 字、重叠 80 | 9/15 | 12/15 | 13/15 | 14/15 |
| 按结构边界切 | 11/15 | 12/15 | 12/15 | 14/15 |

三列几乎一样。如果我停在这里，会写出一句「切分方式对召回影响不大」—— 而这与我的工程经验直接矛盾。

问题出在粒度上：**语料只有 28 篇，而每篇是一个主题明确的文件**。只要命中那一篇就算对，而「那一篇里的哪一段」才是真正被送进模型的东西。

把指标下沉到**章节级**（金标是该答案所在的 ## 小节，平均 524 字符），同一套检索、同一批查询：

| 策略 | recall@1 | recall@3 | recall@5 | MRR |
|---|---:|---:|---:|---:|
| 固定 400 字、无重叠 | 5/15 | 6/15 | 8/15 | 0.389 |
| 固定 400 字、重叠 80 | 4/15 | 8/15 | **11/15** | 0.440 |
| 按结构边界切（上限 800） | 5/15 | 6/15 | 7/15 | 0.372 |
| 按结构边界切（上限 1500） | 3/15 | 6/15 | 7/15 | 0.294 |

**同一个「固定 400 字、无重叠」策略，文件级 recall@5 是 13/15（87%），章节级只有 8/15（53%）。**

从「基本没问题」变成「一半找不到」，只换了一个指标口径。这件事的直接教训是：**指标的粒度必须匹配你真正交给模型的那个单位。** 你送进上下文的是段落，就该按段落评。按文件评，等于在测试一个你并不使用的系统。

## 实测：切分方式影响的不只是「召没召回」

上面那张表里，重叠策略的 recall@5 明显最高（11/15，比无重叠高 37%）。这是重叠的预期作用 —— 缓解被切断的语义。

但还有两个数字不该被忽略。我在同一批查询上量了两个新指标：

- **top1 纯度**：检索到的那一段里，有多大比例真的落在金标小节内。纯度低 = 你塞进上下文的大部分是无关内容。
- **top1 覆盖**：金标小节被这一段覆盖了多少。覆盖低 = 答案没拿全。

| 策略 | 块数 | 平均块长 | recall@5 | 纯度 | 覆盖 |
|---|---:|---:|---:|---:|---:|
| 固定 400 字、无重叠 | 361 | 385 | 8/15 | 0.10 | 0.07 |
| 固定 400 字、重叠 80 | 439 | 390 | 11/15 | 0.13 | 0.11 |
| 按结构边界切（上限 800） | 314 | 391 | 7/15 | **0.35** | **0.34** |
| 按结构边界切（上限 1500） | 288 | 436 | 7/15 | 0.22 | 0.25 |

**结构切分的纯度是固定切分的 3 倍以上**（0.35 对 0.10）。意思是：同样取 5 段喂给模型，按结构切的那 5 段里约有三分之一的内容真正相关；按固定长度切的那 5 段里，只有十分之一是。

这部分浪费是**每一轮都要重付的**。第 3 章那条规律在这里同样成立：成本不只取决于你取了几段，还取决于每段里有多少是废话。

注意两列数字没有同时最优的选项：重叠策略召回最高但纯度最低，结构策略纯度最高但召回只有 7/15。**这不是「选哪个更好」的问题，而是你要先决定优化哪一项** —— 而这个决定取决于你的下游：如果交给模型的是完整段落，纯度更要紧；如果你还会再重排一次，先多召回一些更划算（下一节讲）。

## 不用标注数据也能算的指标：边界完整率

上面那组实验需要人工标注 15 条查询的金标章节。有没有不需要标注、又能反映切分质量的做法？有。

**边界完整率**：一个块的结尾是否落在语义边界上（句末标点或段落结束）。它回答的是「这一块单独拿给模型看，意思完整吗」。本站三篇正文上的结果：

| 文件 | 固定 400 / 无重叠 | 固定 400 / 重叠 80 | 结构边界 / 上限 800 |
|---|---:|---:|---:|
| retrieval/01-why-retrieval（8,060 字符） | 25% | 36% | **83%** |
| context-engineering/04-compaction（5,928 字符） | 30% | 29% | **60%** |
| llm-api-basics/01-tokens-and-context（12,108 字符） | 21% | 24% | **78%** |

（实跑数据，2026-10-08，脚本见本节末尾。）

固定切分的边界完整率在 21% 到 30% 之间 —— 也就是说，**你交给模型的段落里，大约每四段有三段是「从半句话开始、到半句话结束」的**。这个数字不需要任何标注就能算出来，适合在自己语料上先跑一遍。

## 完整可运行代码

这个脚本只用标准库，对任意 Markdown 或纯文本文件跑三种切分，打印块数、平均块长与边界完整率。

```python
"""三种切分策略的对照：块数、平均块长、边界完整率。

用法：python3 chunk.py <某个 .mdx 或 .txt 文件>
只用标准库。

「边界完整率」的定义：一个块以段落结束符（连续换行）或句末标点结尾，就算切在了边界上。
它衡量的是「这一块单独拿给模型看，语义完不完整」——不需要任何标注数据就能算。

实跑状态：2026-10-08，已跑通。
"""

import re
import sys

FENCE = re.compile(r"```[\s\S]*?```")


def strip_code(text):
    """把代码块替换成等长空格：保住字符偏移，同时不让代码参与切分。"""
    return FENCE.sub(lambda m: " " * len(m.group(0)), text)


def fixed(text, size, overlap):
    step = size - overlap
    out = []
    for i in range(0, len(text), step):
        piece = text[i:i + size]
        if len(piece.strip()) > 20:
            out.append(piece)
        if i + size >= len(text):
            break
    return out


def structural(text, max_len):
    """按 Markdown 标题切；超长的小节再按空行切，仍然不跨段落。"""
    out = []
    for sec in re.split(r"\n(?=#{2,3} )", text):
        if len(sec) <= max_len:
            if len(sec.strip()) > 20:
                out.append(sec)
            continue
        buf = ""
        for para in re.split(r"\n\n+", sec):
            if buf and len(buf) + len(para) + 2 > max_len:
                out.append(buf)
                buf = para
            else:
                buf = buf + "\n\n" + para if buf else para
        if len(buf.strip()) > 20:
            out.append(buf)
    return out


def boundary_rate(chunks):
    """块尾是否落在语义边界上。"""
    ok = 0
    for c in chunks:
        tail = c.rstrip()
        if not tail:
            continue
        if tail.endswith(("。", "！", "？", "：", "|")) or c.endswith("\n\n"):
            ok += 1
    return ok / len(chunks) if chunks else 0.0


if __name__ == "__main__":
    path = sys.argv[1] if len(sys.argv) > 1 else "src/content/chapters/retrieval/01-why-retrieval.mdx"
    raw = open(path, encoding="utf-8").read()
    raw = re.sub(r"^---[\s\S]*?---", lambda m: " " * len(m.group(0)), raw)
    text = strip_code(raw)
    print("文件: %s，%d 字符" % (path, len(text)))
    print()
    print("%-22s %6s %10s %12s" % ("策略", "块数", "平均块长", "边界完整率"))
    for name, chunks in [
        ("固定 400 / 无重叠", fixed(text, 400, 0)),
        ("固定 400 / 重叠 80", fixed(text, 400, 80)),
        ("结构边界 / 上限 800", structural(text, 800)),
    ]:
        avg = sum(len(c) for c in chunks) / len(chunks)
        print("%-22s %6d %10.0f %11.0f%%" % (name, len(chunks), avg, boundary_rate(chunks) * 100))
```

## 一个反直觉的取舍：块不是越大越好

从结构切分的两个上限能看出这件事：上限从 800 提到 1500，块数从 314 降到 288，平均块长从 391 升到 436 —— 看起来更省了。但**纯度从 0.35 掉到 0.22，覆盖也从 0.34 掉到 0.25**。

原因是：上限调大之后，一个块里会**塞进两个小节**。检索命中其中一个小节时，另一个小节的内容就成了搭便车的噪声。块变大省下的索引空间，远不及它带来的上下文污染。

这个取舍有个可操作的判据：**一个块应该大致等于「一个能独立回答一类问题的完整单位」**。在 Markdown 里那通常就是一个小节；在某类文档里可能是「一条记录」「一个函数」。长度只是兜底约束，不是设计目标。

## 常见坑

- **直接沿用默认切分参数。** 默认值通常按英文和固定长度设计，对中文技术文档（混排代码、表格）往往是坏的起点。
- **按固定字数硬切，包括代码块和表格。** 它们被切断之后语义完全变了。本节的脚本先把代码块替换掉，就是为了不让它们参与切分。
- **用「答案在哪一篇」这类粗粒度指标评检索。** 本次实测里，它把 53% 的章节级召回率显示成了 87%。
- **只盯召回率，不看纯度。** 纯度低意味着每一轮都在为无关内容付费，而这个成本在召回指标上完全看不见。
- **以为块越大越省。** 本次实测：上限从 800 提到 1500，纯度掉了 37%。
- **指望切分解决排序问题。** 四种策略的 recall@1 都在 3/15 到 5/15 之间 —— 切分能改善「能不能捞到」，但改变不了「捞到的排不排得前」。
