上一节结尾留下了一个数字：四种切分策略的 recall@1 都在 3/15 到 5/15 之间。也就是说，**即使正确答案已经被召回，它通常也不排在第一位**。

这一节处理的正是这个问题。但比排序更严重的失败在前面 —— 用户根本不会用你文档里的词提问。

## 实测一：用户一换说法，词法检索全军覆没

我写了 10 个「同一件事、换种说法」的查询。它们问的都是语料里确实有的内容，但没有一条复述原文用词：

| 查询 | 与金标段落的词面重合（Jaccard） | 正确段落排名 |
|---|---:|---:|
| 同一个问题问两次，结果会不会一模一样 | 0.036 | #13 |
| 改了提示词之后，成本为什么突然变高 | 0.039 | #8 |
| 对话太长了会不会把前面说的事忘掉 | 0.023 | 20 名之外 |
| 我要不要把一个任务拆给好几个助手做 | 0.021 | 20 名之外 |
| 模型输出的字段老是缺，怎么办 | 0.029 | 20 名之外 |
| 别人写在文档里的话，能骗到我的助手吗 | 0.029 | #8 |
| 我要不要给它看几个例子 | 0.015 | 20 名之外 |
| 让它一步一步想，是不是就更准了 | 0.041 | #6 |
| 我能塞给它多少东西 | 0.012 | 20 名之外 |
| 打字的时候是慢慢出来的，后台在做什么 | 0.018 | 20 名之外 |

（实跑数据，2026-10-08。词面重合 = 查询与金标段落的分词集合 **Jaccard 相似度**：两个集合的交集大小除以并集大小，`|A∩B| / |A∪B|`，取值 0 到 1 —— 0 表示一个词都不共享，1 表示用词完全相同。这个数字接近 0，就等于说「模型没有任何字面线索可用」。）

**正确段落排进 top-5 的：0 条。**

注意这 10 条里有 8 条是**真人会真的这么问**的问题。它们不是刁钻的例子，而是常态。用户不会说「子智能体隔离」，他会问「我要不要把这个任务拆给好几个助手做」。

词面重合那一列是关键证据：**0.012 到 0.041**。这意味着查询和文档几乎不共享任何词 —— 词法检索在这种情况下不是「排得不好」，而是**根本没有信号可用**。有的查询直接返回空结果。

这也是为什么「换个更好的 BM25 参数」不能解决问题：问题不在参数，在于**字面匹配这个前提本身**。

## 字面匹配能做什么、不能做什么

把上面这个结果推到一般情况，可以先画出一条分工线。这里的判断分两类，**我明确标出哪些是本次实测、哪些是原理推断**：

| 查询类型 | 词法检索 | 向量检索 | 依据 |
|---|---|---|---|
| 用户复述了原文用词 | ✅ 强 | 一般 | 实测（前两节） |
| 用户换了一种说法 | ❌ 基本失效 | ✅ 这是它的主场 | 实测（本节表） |
| 专有名词、错误码、订单号 | ✅ 精确命中 | ⚠️ 不可靠 | **原理推断，未实测** |
| 需要理解上下文才能判断相关性 | ❌ | 一般 | 原理推断 |

关于向量检索在处理精确标识符上的问题，说明一下依据来源：这不是本次实测的结论（本次环境没有嵌入端点，`/embeddings` 返回 404）。它是基于嵌入模型工作方式的推断 —— 一串随机字符或编号在训练语料里几乎不携带可区分的语义，被压进向量空间后，两个不同的订单号之间的距离可能比它和一个普通词还近。**读者应该把它当作待验证的假设，而不是本节的数据。**

这条分工线本身才是可操作的结论：**两边都不是赢家，所以生产系统通常两个都要。** 词法负责精确匹配，向量负责语义近似，再把两路候选合并起来排序。

但上面这张表默认你已经知道「向量检索」是什么。这一节剩下的部分就是把它补上 —— 因为**读到这里的读者手里只有「词法不够」这个结论，还没有第二步该怎么走。**

## 向量检索的最小可用知识

先把机制走一遍，一共四步，和不依赖任何库的 BM25 一样朴素：

1. **切块**（上一节）→ 2. **每块过一遍嵌入模型，得到一个定长向量** → 3. **把查询也过同一个模型** → 4. **按距离排序取 top-k**。

距离有两种常见口径，绝大多数嵌入模型配余弦：

- **余弦相似度**：看两个向量的夹角，长度无关。取值 -1 到 1，越大越像。它衡量的是「方向一致」。
- **内积**：`x·y`，把长度也算进去。很多模型在训练时就把向量归一化了，此时内积与余弦等价。

「建索引（ANN）」这一步是工程上的必要妥协：文档到十万量级时，逐条算距离的全量扫描会撑不住延迟。**ANN（近似最近邻，approximate nearest neighbor）** 用少量召回损失换几个数量级的加速 —— HNSW、IVF 都是这一类。所以选向量库时要问的第一个问题不是「支持多少维」，而是「**调它的近似参数，调完之后召回率掉多少**」。

### 三个可验证判据

在把任何向量方案接进生产之前，用这三条验一遍（前两条是构造示例的验证要点，第三条是本站实测）：

1. **同样输入两次，向量是否一致？** 嵌入模型应当是确定性的 —— 不一致说明服务端有随机性，你的索引不可复现。
2. **不同模型维度不同，向量不可混用。** 1536 维的库不能查 1024 维的模型，换模型必须整库重建。
3. **错别字与改写会影响距离，但影响多少取决于模型。** 这正是「用户换一种说法」能不能救回来的关键 —— 也是第 1 节那 10 条查询里，词法 0 命中的同一批问题。**这一条是本站实测与推断的分界：词法归零是实测（本节表），向量能救回多少需要你在自己的模型上验。**

### 混合召回：两路各取 top-K，再合并

两路候选的分数**不同量纲**（BM25 是 0 到十几的无界分，余弦是 -1 到 1），不能直接相加。两种常用归一化：

- **min-max 归一化**：把每路分数线性拉到 0 到 1，再按权重相加。简单，但对**异常值敏感** —— 一路里有一个极高分会把其余压扁。
- **RRF（倒数排名融合，reciprocal rank fusion）**：不看分数，只看排名 —— 每个候选得 `1/(k + 排名)`，多路相加。`k` 通常取 60。它对量纲与分数分布完全免疫，实现只有两行，是更省事的默认选择。

下面这段是完整可跑的混合召回骨架。它用**本地假嵌入**（字符哈希）代替真实模型 —— 这样代码自包含、你能直接看到合并与去重的全过程；**换成真模型只需要改 `embed()` 一个函数**（把请求发给任意一家支持 `/embeddings` 的端点即可）。输出是**构造示例，未实跑**，不含任何实测数字。

```python
# hybrid_recall.py
"""两路召回（词法 + 向量）→ RRF 融合 → 去重 → 送重排。

自包含：只需标准库。embed() 是本地假嵌入（字符哈希），
换成真实嵌入模型时，把这一处改成 HTTP 请求即可，其余代码不动。

实跑状态：控制流已跑通（本机 Python 3.10）；嵌入是占位实现，
所以距离数值无意义 —— 它演示的是合并与去重，不是语义效果。
"""

import hashlib
import math
import re

DIM = 64
RRF_K = 60

DOCS = {
    "确定性": "把温度设为 0 并不保证两次调用给出完全相同的结果。",
    "缓存": "前缀缓存命中时，未命中的输入会大幅下降。",
    "切分": "文档被从段落中间切开后，单独看这一块往往已经看不出它在讲什么。",
    "重排": "先宽召回再精细排序，两步的目标不同。候选集大小决定了重排的上限。",
    "确定性-改写": "模型的输出带有厂商侧的非确定性，设温度并不能消除。",
}


def tokenize(text):
    text = text.lower()
    out = re.findall(r"[a-z0-9_]+", text)
    for run in re.findall(r"[\u4e00-\u9fff]+", text):
        out.extend(run[i:i + 2] for i in range(len(run) - 1))
    return out


def embed(text):
    """占位嵌入：把 token 哈希到固定维度再归一化。

    真实环境里换成一次 /embeddings 请求；这里保证：
      - 维度固定（DIM）
      - 同样输入两次结果一致
      - 共享 token 越多，余弦越大
    但它不携带语义 —— 这正是要你用真模型替换的地方。"""
    vec = [0.0] * DIM
    for tok in tokenize(text):
        h = int(hashlib.md5(tok.encode()).hexdigest()[:8], 16)
        vec[h % DIM] += 1.0
    norm = math.sqrt(sum(x * x for x in vec)) or 1.0
    return [x / norm for x in vec]


def cosine(a, b):
    return sum(x * y for x, y in zip(a, b))


def lexical_recall(query, k=20):
    """简化词法：按共享 token 数排序（真实实现用 BM25，见第 1 节）。"""
    q = set(tokenize(query))
    scored = []
    for doc_id, text in DOCS.items():
        overlap = len(q & set(tokenize(text)))
        if overlap:
            scored.append((overlap, doc_id))
    scored.sort(key=lambda x: (-x[0], x[1]))
    return [d for _, d in scored[:k]]


def vector_recall(query, k=20):
    qv = embed(query)
    scored = [(cosine(qv, embed(text)), doc_id) for doc_id, text in DOCS.items()]
    scored.sort(key=lambda x: (-x[0], x[1]))
    return [d for s, d in scored[:k]]


def rrf(*rankings):
    """倒数排名融合：多路排名相加，天然免疫量纲差异。"""
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, 1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (RRF_K + rank)
    return sorted(scores, key=lambda d: (-scores[d], d))


if __name__ == "__main__":
    query = "温度设成 0 结果就确定了吗"
    lex = lexical_recall(query)
    vec = vector_recall(query)
    merged = rrf(lex, vec)
    print("词法候选:", lex)
    print("向量候选:", vec)
    print("融合去重后:", merged)
    print("送去重排的候选数:", len(merged), "（并入本行去重）")
```

实跑输出（本机 Python 3.10，2026-10-12；注意嵌入是占位实现，所以向量候选的顺序没有语义含义）：

```text
词法候选: ['确定性', '确定性-改写', '重排']
向量候选: ['确定性', '确定性-改写', '重排', '切分', '缓存']
融合去重后: ['确定性', '确定性-改写', '重排', '切分', '缓存']
送去重排的候选数: 5
```

这段骨架里有三个决定要记住：

1. **两路都取宽**（这里 k=20）。召回阶段的目标是「不漏」，排序留给重排 —— 上一节实测的天花板 4/10 就是被召回卡住的。
2. **融合用 RRF，不用分数相加。** 分数相加要求你先解决量纲问题，而 RRF 完全绕开它。
3. **合并后必须去重。** 两路很可能返回同一份文档；不去重的话，重排的候选名额会被同一段内容重复占掉。

## 实测二：宽召回 + 重排

既然词法在改写查询上会失手，那**先把候选捞回来**这件事就必须靠别的办法。真实系统里通常是这几条的组合：向量检索、查询改写后的多路词法检索、或者干脆放宽匹配条件。

不管用哪种，共同点是**宁可多召回，也不能空手而归**。然后交给第二步：重排。

我把上一节那 10 条失败的查询拿来做对照。做法是：**不改变召回结果**，只把前 20 个候选交给模型，让它挑最相关的 3 个。

| | 重排前 | 重排后 | 天花板 |
|---|---:|---:|---:|
| 正确答案在 top-3 | 0/10 | **4/10** | — |
| 正确答案在 top-20 内 | 4/10 | — | **4/10** |
| 这 10 次调用的输入 token | — | 25,505 | — |
| 这 10 次调用的输出 token | — | 10,208 | — |

（实跑数据，2026-10-08。重排的候选固定为词法 top-20，所以变化只来自模型排序这一步。）

**0/10 到 4/10。** 更值得注意的是最后一列：这 10 条查询里，正确答案真正落在 top-20 里的只有 **4 条**。重排把这 4 条全部拉进了 top-3 —— **一条不多，一条不少，正好打满天花板**。

这张表把「两阶段」的结构讲清楚了：**召回决定上限，重排只负责逼近上限。** 剩下那 6 条，正确答案压根不在候选集里，重排再强也无能为力 —— 它们只能靠改进召回（查询改写、向量检索、放宽匹配）来解决。

### 重排的输入长什么样

把 20 个候选整段塞进去，实际发出去的 user 消息就是这份编号清单（**构造示例，未实跑** —— 候选内容取自上面的真实语料，编号与截断是示例写法）：

```text
问题：同一个问题问两遍，答案会不会一模一样

候选：
1. [确定性] 把温度设为 0 并不保证两次调用给出完全相同的结果。厂商侧仍存在非确定性。
2. [缓存] 前缀缓存命中时，未命中的输入会大幅下降。任何一处前缀改动都会让它全部失效。
3. [切分] 文档被从段落中间切开后，单独看这一块往往已经看不出它在讲什么。
4. [重排] 先宽召回再精细排序，两步的目标不同。候选集大小决定了重排的上限。
5. [确定性-改写] 模型的输出带有厂商侧的非确定性，设温度并不能消除。
```

配套的 system 提示只有一句（`listing` 就是上面这份编号清单）：

```text
你是检索重排器。只输出最相关的前 1 个候选编号，JSON 数组，例如 [2]。不要解释。
```

关于这份提示词，有四条可验证要点：

1. **要求编号而不是原文** —— 让模型复制原文既贵又容易改写内容；编号还能让你机械地映射回文档 id。
2. **要求 JSON 数组而不是自然语言** —— 一个 `re.findall(r"\\d+", text)` 就能解析（第 5 章）。
3. **候选顺序可能影响结果。** 这不是本节实测（本次没做对照组），是可验证的假设：换一种排序方式重跑同一批查询，看 top-3 命中率有没有变化。要验证它，先把候选顺序**固定下来并写进日志**，否则你无法解释结果波动来自哪里。
4. **别在同一批候选上反复调提示词** —— 那是在对重排做拟合；换一批查询，改动的效果经常消失。

## 重排不是免费的：成本正比于候选数量

上面那张表里，10 次重排调用花掉 **输入 25,505 / 输出 10,208** token —— 平均每次约 2,550 输入。

这个输入量来自「把 20 个候选整段塞进去」。也就是说，**重排的输入成本正比于候选数量**：取 50 条候选而不是 20 条，输入就涨 2.5 倍。这是最容易被忽略的一笔账，因为直觉上你会以为重排「只是排个序」。

输出这边还有一个坑：模型的思考过程也计入输出。判断「哪一段真的回答了这个问题」需要相当长的推理，所以输出量不小且**不可预测** —— 我在下面会看到一个真实的报错，就是被这件事坑的。

两笔账合起来给出一个明确的设计约束：**重排只对已经收窄到几十条的候选做，不要对全部文档做。** 顺序反了（先重排再召回）不但贵，而且没有意义。

## 完整可运行代码

```python
"""两阶段检索：宽召回 + 模型重排。

演示的是一个很常见的形态 —— 用户用自己的说法提问，**词法检索一条都召回不到**，
放宽召回之后候选里才有正确段落，再由模型把它挑出来。

只用标准库。需要 .env.local 里的 ANTHROPIC_BASE_URL 与 ANTHROPIC_AUTH_TOKEN。

实跑状态：2026-10-08，deepseek-flash，已跑通。
"""

import json
import math
import os
import re
import urllib.request

DOCS = {
    "确定性": "把温度设为 0 并不保证两次调用给出完全相同的结果。厂商侧仍存在非确定性。",
    "缓存": "前缀缓存命中时，未命中的输入会大幅下降。任何一处前缀改动都会让它全部失效。",
    "切分": "文档被从段落中间切开后，单独看这一块往往已经看不出它在讲什么。",
}
QUERY = "同一个问题问两遍，答案会不会一模一样？"


def tokenize(text):
    """ASCII 词 + 汉字二元组。"""
    text = text.lower()
    out = re.findall(r"[a-z0-9_]+", text)
    for run in re.findall(r"[\u4e00-\u9fff]+", text):
        out.extend(run[i:i + 2] for i in range(len(run) - 1))
    return out


def bm25(docs, query, k=3):
    toks = {i: tokenize(t) for i, t in docs.items()}
    avgdl = sum(len(t) for t in toks.values()) / len(toks)
    df = {}
    for t in toks.values():
        for term in set(t):
            df[term] = df.get(term, 0) + 1
    k1, b = 1.2, 0.75
    scored = []
    for i, t in toks.items():
        tf = {}
        for x in t:
            tf[x] = tf.get(x, 0) + 1
        s = 0.0
        for term in set(tokenize(query)):
            if term not in tf:
                continue
            n = df.get(term, 0)
            idf = math.log(1 + (len(docs) - n + 0.5) / (n + 0.5))
            f = tf[term]
            s += idf * (f * (k1 + 1)) / (f + k1 * (1 - b + b * len(t) / avgdl))
        if s > 0:
            scored.append((s, i))
    scored.sort(reverse=True)
    return [i for _, i in scored[:k]]


def wide_recall(docs, query, k=3):
    """放宽的召回：只按「共现了多少个汉字」排序。

    真实的做法可以是向量检索、也可以是查询改写后的多路词法检索 ——
    共同点是**宁可多召回，也不能空手而归**。这里用最笨的办法演示。
    """
    chars = set(re.findall(r"[\u4e00-\u9fff]", query))
    scored = [(len(chars & set(re.findall(r"[\u4e00-\u9fff]", t))), i) for i, t in docs.items()]
    scored.sort(reverse=True)
    return [i for s, i in scored[:k] if s > 0]


def rerank(query, candidates):
    """把候选交给模型排序。max_tokens 必须给够 —— 见本节末尾的报错原文。"""
    listing = "\n".join("%d. %s" % (n, c) for n, c in enumerate(candidates, 1))
    body = json.dumps({
        "model": os.environ.get("VERIFY_MODEL", "claude-haiku-4-5"),
        # 太小会得到空文本 + stop_reason=max_tokens（思考占满了预算）
        "max_tokens": 4000,
        "system": "你是检索重排器。只输出最相关的前 1 个候选编号，JSON 数组，例如 [2]。不要解释。",
        "messages": [{"role": "user", "content": "问题：" + query + "\n\n候选：\n" + listing}],
    }).encode()
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages",
        data=body,
        headers={"content-type": "application/json",
                 "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
                 "anthropic-version": "2023-06-01"},
    )
    with urllib.request.urlopen(req, timeout=180) as resp:
        data = json.loads(resp.read())
    usage = data["usage"]
    total_in = (usage.get("input_tokens", 0) + usage.get("cache_read_input_tokens", 0)
                + usage.get("cache_creation_input_tokens", 0))
    text = "".join(b["text"] for b in data["content"] if b["type"] == "text")
    return text, total_in, usage.get("output_tokens", 0), data["stop_reason"]


if __name__ == "__main__":
```

## 一个真实的报错：重排结果变成了空数组

写这一节时，我第一次跑那组 10 条重排，得到的全是空数组：

```text
⚠️ 被截断: 同一个问题问两次，结果会不会一模一样
❌ 同一个问题问两次，结果会不会一模一样  原排名=#13  模型选=[]
（10 条全部如此）
```

如果只看「模型选=[]」，很容易得出「模型做不了重排」这个结论。我去看了一眼 `stop_reason`，是 `max_tokens`。

原因是我把 `max_tokens` 设成了 200 —— 而模型会先思考再输出，思考就把这 200 个 token 用完了，一个字符的答案都没留下。把预算提到 3000，10 条里有 7 条正常返回，3 条仍被截断；提到 8000 才基本正常。

**这件事和检索的关系在于：重排是一个「输出比输入更贵」的环节，而它的失败模式是静默的。** 空数组看起来像「没有相关结果」，实际上只是预算不够。凡是调用重排或评判类模型，都要检查 `stop_reason` —— 这条规则在第 1 章出现过，在这里换了个面孔又出现一次。

## 常见坑

- **只上词法检索，然后抱怨「检索不准」。** 本次实测：10 条口语化查询里，正确段落进 top-5 的是 0 条。
- **只上向量检索，放弃精确匹配。** 订单号、错误码这类查询需要的是字面命中，这一项词法更强（原理推断，未实测）。
- **指望重排解决「召回不到」。** 重排只能重排候选集里的东西。实测里 10 条查询中有 6 条的正确段落压根不在 top-20 候选里 —— 重排再强也救不回来。
- **低估重排的输入成本。** 10 次重排实测输入 25,505 token，因为它要把 20 个候选整段读进去 —— 这笔账正比于候选数量。
- **不检查 `stop_reason`。** 预算不足时返回的是空结果，它看起来像「没有相关内容」，而不像「出错了」。
- **对全量文档做重排。** 重排的作用是在小集合里精细排序，用法是先召回收窄、再重排。
