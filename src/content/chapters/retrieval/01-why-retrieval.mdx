你要给一个内部助手接上知识库。资料不多：28 篇内部文档，加起来十几万字。

团队里的第一反应通常是「那就全塞进 prompt」——**prompt 就是你在这一轮请求里发给模型的全部输入**（系统指令 + 用户问题 + 你附加的资料），后端读者可以直接类比成「一次 HTTP 请求的请求体」。既然窗口看起来很大，这个想法值得认真对待，而不是直接否定 —— 所以我先量了它的价钱。

## 历史摘要一：整份资料有多贵

语料用本站自己的 28 篇正文（真实中文技术文，含代码块，原文共 179,525 字符）。测量方法很直接：把整篇正文当输入发一次，读 `usage` 里的输入 token 数。

| 指标 | 数值 |
|---|---:|
| 语料总量 | 28 篇 / 179,525 字符 |
| 旧记录中的 token 消耗 | 约 89,136 token |
| 换算比例 | 0.497 token/字符 |
| 单篇平均 | 约 3,183 token |

（历史摘要标注 `deepseek-flash`、2026-10-08：抽样 3 篇后外推，非逐篇测量。原始请求、usage 响应、精确 endpoint/model 指纹和语料快照未归档，89,136 与 0.497 无法独立复核；本节只复核其算术关系与不应泛化的范围。）

0.497 这个数字只描述这次混合语料的抽样外推：**平均每个字符约 0.497 个 token，也就是约 2 个字符对应 1 个 token**。这比「一个字符一个 token」更省 token；其中英文、代码和标点会改变比例，但这次结果不能推广成所有中文文档的固定换算率。要估自己的输入量，应使用目标端点的 tokenizer 或实际响应 usage。

## 先把 usage 口径说清楚：缓存字段不能跨端点照搬

下面这组缓存数字来自 2026-10-08 的历史记录，标注为 `deepseek-flash` 的 Anthropic 兼容端点：

```text
第 1 次调用  input_tokens=30935
第 2 次调用  input_tokens=215
第 3 次调用  input_tokens=211

另一次记录  input_tokens=198  cache_creation=0  cache_read=30720
```

它可以提醒我们：只看某个名为 `input_tokens` 的字段，可能会误读输入与缓存。但这批记录没有逐次原始响应、模型指纹、完整请求和账单明细，字段名也不是 DeepSeek 当前 Chat Completions 文档中的 `prompt_tokens` / `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`。因此，156 倍只能保留为**不可独立复核的历史摘要**，不能当作当前 DeepSeek 或其他 provider 的字段定义、总量公式或账单证据。

使用 API 时，应按**目标 endpoint 的当前文档**解释 usage：DeepSeek Chat Completions 文档将 `prompt_tokens` 定义为缓存命中与未命中 token 之和；DeepSeek Responses API 使用 `input_tokens` 并将缓存命中放在 `input_tokens_details.cached_tokens`；DeepSeek Anthropic 兼容文档则说明 `cache_control` 会被忽略。缓存也不能假设采用同一套建立、匹配、过期和计价规则。可分别核对[DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)、[DeepSeek Responses API](https://api-docs.deepseek.com/api/create-response/)、[DeepSeek Context Caching](https://api-docs.deepseek.com/guides/kv_cache/)与[DeepSeek Anthropic 兼容说明](https://api-docs.deepseek.com/guides/anthropic_api/)。

工程上保留原始 usage、endpoint、模型标识/指纹、请求配置和观测时间；只有在字段口径已核实时才归一化成本。缓存命中字段是诊断信号，不要用一个 provider 的字段公式去计算另一个 endpoint 的总量或账单。旧实验表格中的成本、准确率和延迟也缺少逐题请求/响应与评分材料，以下仍是历史摘要，不足以推出稳定的质量或性能结论。

## 实测二：装得下，不等于用得好

「塞不进去」其实是这里最弱的理由。我把 10 篇、64,880 字符（约 3.1 万 token）整段发过去，**HTTP 200，没有任何报错** —— 它装得下。

真正的问题在别处。旧记录称：同样 6 个有标准答案的问题，两种给法各跑一遍。原始逐题请求/响应、任务集版本、精确 endpoint/model 快照和 scorer 均未归档；下表只是无法独立复核的历史摘要，不能据此断言稳定质量、成本或延迟差异：

| | 全量塞入 | 检索 top-5 |
|---|---:|---:|
| 答对 | 6/6 | 5/6 |
| 记录的输入 token 合计（旧记录口径，无法复核） | 185,613 | 9,955 |
| 输出 token 合计 | 4,276 | 1,931 |
| 平均耗时 | 3,532 ms | 1,897 ms |

旧记录中的输入 token 数相差约 18.6 倍；这不是货币成本比，缓存、费率与字段口径均未核实。

表头里的 `top-5` 就是检索参数：**取分数最高的前 5 条返回**，`top-5` 的 5 就是那个 k（后面会写成 `recall@k` / `top-k`，都是同一个 k）。它是这套系统里容易调整、也会影响上下文规模的参数。提高 top-k 通常会增加送入模型的文本量，但实际 token 用量与费用还取决于 chunk 长度、上下文去重/截断、缓存和目标 endpoint 的计量规则；不能把「多取一条」直接等同于固定增加一笔费用。

即使暂时只把这张表当作待复核的历史记录，也能提出两个后续验证问题：全量上下文是否包含了大量本题用不到的资料；检索是否漏掉了答案证据。旧摘要称检索臂答错一题，但由于原始记录缺失，这只能作为待核实线索，不能据此判定错误由召回造成。

所以，检索的取舍要在同一任务集、同一 endpoint 和明确的 usage/计费口径下比较质量、成本与延迟。当前这组历史摘要不能回答这笔买卖是否划算；本章后续会给出如何自行建立可复核对照的方法。

## 常见路径：上下文、检索、工具查询与微调

把外部知识接给模型，不只有一种架构。先把四种常见路径分开看；真实系统也会组合使用。关键不是选出一个“最强方案”，而是确认**数据在哪里、怎么取、谁负责校验**：

| 路径 | 主要改变 | 适用线索 | 主要限制 |
|---|---|---|---|
| 直接放入 prompt | 本轮模型可见的信息 | 资料少、问题需要同时看多个已知片段 | 上下文、延迟与输入成本需实测；更新内容要保证注入的是新版本 |
| 文档检索（RAG） | 每轮选出的文档片段 | 非结构化资料多、需要出处、按文档语义找证据 | top-k 可能漏证据；权限、版本、新鲜度与引用需由系统保证 |
| 工具/API 查询 | 模型可请求的结构化或权威数据操作 | 当前余额、订单状态、库存、跨文档计数等由数据库/API 给出 | 工具执行要受宿主授权、参数校验、超时和副作用规则控制；这不等于文档 RAG |
| 微调 | 模型对特定输入的行为倾向 | 有稳定任务、代表性训练数据与离线评测，且提示/工具方案不足以满足要求 | 不应作为动态事实的唯一来源；知识更新与遗忘要单独评测 |

普通 top-k 检索只把少量候选片段交给模型。如果问题要求统计或比较整批资料，而检索器没有执行对应的聚合查询，答案可能不在召回片段里。此时可以考虑全量上下文（规模允许时）、分块 map/reduce、数据库查询或专门工具；不能简单断言“检索一定错”或只靠调排序。判断问题是：**所需答案能否由被取回的证据支持？若不能，是否有权威查询/聚合路径？**

- 「这单退款到账要几天」如果答案在当前政策文档里，检索可找出处；若问某一笔订单的实际退款状态，应查询订单服务。
- 「回答一律用表格，不要寒暄」先用 prompt 与输出校验；只有在稳定、重复的任务和充分评测下，才考虑微调。
- 「几百份产品手册里哪些条款提到灰度发布」可用文档检索找候选证据；若要精确统计总数，应使用覆盖完整语料的检索/聚合流程或可审计查询，而非单次 top-k。

信息会变化，意味着需要明确**事实的权威源与同步时效**。它可能是文档索引，也可能是事务数据库或实时 API；选择索引前先问读路径是否能满足新鲜度、权限和审计要求。微调可以帮助稳定行为，但不应替代动态数据的权威来源。

还要区分**检索没提供必要证据**与**正确证据已充分提供但模型仍未完成任务**。后一种情况继续扩大 top-k 未必有帮助，应检查任务分解、提示、工具或确定性计算；但这不是说检索和推理完全独立——更好的证据可能改变模型能否完成某项推断，必须在具体任务上评估。

## 关于本章的实验方法：为什么用词法检索

本章前几节的本地检索对照采用**词法检索**（BM25），不是向量检索；数字只适用于正文所述的语料、切分、tokenize 与检索实现。**词法检索**的意思是「按字面匹配」：把文档和查询都切成词，谁和查询共享的稀有词多，谁就排前面 —— 它不需要任何模型，ES 的默认打分就是这一类。

与之相对的是**向量检索**，它缺不了下面这个组件：

**嵌入模型**（embedding model）通常把文本映射为固定维度的数值向量；具体维数、归一化与相似度算法由模型/系统决定。向量可按余弦相似度或内积等规则排序，但“距离近”只是模型训练目标下的相关性信号，不保证两段文字在当前业务任务上相关。embedding 是向量表示，不是压缩或摘要。

它和你熟悉的东西的对照是：**倒排索引把「哪些文档含这个词」记下来，嵌入把「这段文本是什么意思」编码成一个可算距离的点。** 前者依赖用词匹配，后者依据嵌入空间里的相似度排序；当模型把改写后的查询与相关文档映射到相近区域时，向量检索可能补上词法检索漏掉的候选，但效果取决于模型、编码方式与任务，不能保证所有换说法的查询都能召回。第 3 节会用本章语料展示词法基线在特定改写上的失效。

代价包括 embedding 生成与部署/调用、维度和版本管理。更换模型或其向量空间通常需要重建或显式迁移索引；来自不同模型/版本的向量不能默认放在同一空间直接比较。是否使用托管 API、开源本地模型或自建服务，取决于约束。

本次实验环境只提供对话端点，`/embeddings` 与 `/v1/embeddings` 都返回 404，没有可用的嵌入模型。

本地 BM25 基线让同一份代码与语料下的排序较易重复，但不意味着正文中的历史 provider 对照可复现。引入向量前先测词法基线，有助于定位语义改写等查询上的差距；向量路线则应记录 embedding 模型/版本、预处理、索引和距离度量，避免把配置差异误当成检索原理。

本章先用词法基线讲清「切分」「召回」「评测」的方法，再讨论向量检索可能补足的查询类型。具体结果依赖语料、分词、切分、检索器和评测集，不应宣称与检索引擎或模型配置无关。

## 完整可运行代码

下面这份代码不用任何第三方库，只用标准库，把「检索 → 组装上下文 → 调用模型」这条链完整跑一遍。它包含了上面两个教训：中文用二元组分词；usage 原样保留并按目标 endpoint 解释，不把不同 provider 的缓存字段硬加成一个总量。

代码里会用到两个请求/响应字段（第 5 章讲过，这里再用一次）：`max_tokens` 是**请求里设的本次生成上限**，`stop_reason` 是**响应里说明为什么停下来**的字段 —— 取值 `end_turn`（正常说完）、`max_tokens`（撞上上限，输出被切断）、`tool_use`（要求调用工具）。**凡是要解释「回答不完整」，先看 `stop_reason`。**

```python
"""最小可用的检索问答：BM25 检索 + 组装上下文 + 调用模型。

不需要任何第三方库（连 rank_bm25 都不需要），只用标准库。
把 DOCS 换成你自己的文档，把 query 换成你的问题就能跑。

实跑状态：2026-10-08，deepseek-flash，已跑通。
"""

import json
import math
import os
import re
import urllib.request

DOCS = {
    "退款政策": "退款需在签收后 7 天内发起，超过 7 天只能换货。退款到账时间 3 到 5 个工作日。",
    "换货政策": "换货不限时间，但商品需保持完好。破损商品可直接申请换新，无需寄回原件。",
    "发票问题": "电子发票在订单完成后 2 小时内开具。需要纸质发票请在备注里说明，会随下一次物流寄出。",
    "价格保护": "商品签收后 15 天内降价，可申请退差价。参与秒杀的商品不适用价格保护。",
}


def tokenize(text):
    """中文没有空格：用「ASCII 词 + 汉字二元组」。这是中文检索的常规做法，无需分词库。"""
    text = text.lower()
    tokens = re.findall(r"[a-z0-9_]+", text)
    for run in re.findall(r"[\u4e00-\u9fff]+", text):
        tokens.extend(run[i:i + 2] for i in range(len(run) - 1))
        tokens.extend(run)
    return tokens


class BM25:
    def __init__(self, docs, k1=1.2, b=0.75):
        self.ids = list(docs)
        self.tokens = [tokenize(docs[i]) for i in self.ids]
        self.k1, self.b = k1, b
        self.avgdl = sum(len(t) for t in self.tokens) / len(self.tokens)
        self.df = {}
        for toks in self.tokens:
            for term in set(toks):
                self.df[term] = self.df.get(term, 0) + 1

    def search(self, query, k=2):
        scored = []
        for idx, toks in enumerate(self.tokens):
            tf = {}
            for t in toks:
                tf[t] = tf.get(t, 0) + 1
            score = 0.0
            for term in set(tokenize(query)):
                if term not in tf:
                    continue
                n = self.df.get(term, 0)
                idf = math.log(1 + (len(self.ids) - n + 0.5) / (n + 0.5))
                f = tf[term]
                score += idf * (f * (self.k1 + 1)) / (
                    f + self.k1 * (1 - self.b + self.b * len(toks) / self.avgdl)
                )
            if score > 0:
                scored.append((score, idx))
        scored.sort(reverse=True)
        return [(self.ids[i], s) for s, i in scored[:k]]


def build_context(hits, docs):
    """把检索结果拼成上下文。带上来源，模型才有机会引用。"""
    parts = []
    for doc_id, score in hits:
        parts.append("[来源: %s]\n%s" % (doc_id, docs[doc_id]))
    return "\n\n".join(parts)


def ask_model(question, context):
    base = os.environ["ANTHROPIC_BASE_URL"].rstrip("/")
    body = json.dumps({
        "model": os.environ.get("VERIFY_MODEL", "claude-haiku-4-5"),
        "max_tokens": 1024,
        "system": "只根据给定的资料回答。资料里没有的，直接说「资料里没有提到」，不要推测。",
        "messages": [{"role": "user", "content": context + "\n\n问题：" + question}],
    }).encode()
    req = urllib.request.Request(
        base + "/v1/messages",
        data=body,
        headers={
            "content-type": "application/json",
            "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
            "anthropic-version": "2023-06-01",
        },
    )
    with urllib.request.urlopen(req, timeout=120) as resp:
        data = json.loads(resp.read())
    text = "".join(b["text"] for b in data["content"] if b["type"] == "text")
    usage = data["usage"]
    # 不跨 endpoint 推导 token 总量或账单；保留原始 usage 供调用方按接口文档解释。
    return text, usage, data["stop_reason"]


if __name__ == "__main__":
    index = BM25(DOCS)
    for question in ["退款几天能到账", "秒杀商品降价了能退差价吗"]:
        hits = index.search(question, k=2)
        context = build_context(hits, DOCS)
        print("问题:", question)
        print("  召回:", [h[0] for h in hits])
        if os.environ.get("ANTHROPIC_AUTH_TOKEN"):
            answer, usage, stop = ask_model(question, context)
            print("  回答:", answer.strip()[:120])
            print("  usage:", json.dumps(usage, ensure_ascii=False, sort_keys=True))
            print("  stop_reason:", stop)
        print()
```

跑起来是这样（实跑输出，2026-10-08）：

```text
问题: 退款几天能到账
  召回: ['退款政策', '价格保护']
  回答: 退款到账时间为 3 到 5 个工作日。[来源: 退款政策]
  token: 输入 132 / 输出 68, stop_reason=end_turn

问题: 秒杀商品降价了能退差价吗
  召回: ['价格保护', '换货政策']
  回答: 不能。资料显示：参与秒杀的商品不适用价格保护，因此秒杀商品降价不能申请退差价。
  token: 输入 125 / 输出 133, stop_reason=end_turn
```

注意第二个问题：它问的是「秒杀 + 退差价」，而答案在「价格保护」这条里，且是个**否定回答**。这类问题最容易暴露检索的问题 —— 如果你的检索只按字面匹配「秒杀」而没抓到「价格保护」，模型就会答成「可以退」。这也是为什么检索系统必须有自己的评测，而不是只看最终答案对不对（第 4 节专门讲）。

## 那 1/6 错在哪

回到上面那张对照表。检索臂答错的是这道题：

> 结构化输出校验失败后，哪种重试方式有效？

它的正确答案（带具体错误信息重试，6/6 有效）确实在语料里，但在第 5 章某篇的中间位置。BM25 取回的 top-5 里没有它 —— 召回没拿到，模型自然答不出来。

这个案例的价值在于它**划出了检索的能力边界**：检索的失败是**召回失败**，而召回失败在最终答案上是看不出来的 —— 你只看到「答错了」，看不到「为什么错」。第 4 节会把这条界线画清楚。

## 常见坑

- **把 usage 字段跨 endpoint 相加。** 同名字段的定义、缓存字段与计费口径可能不同。保留原始响应和 endpoint 身份，依对应文档解释；本节的 156 倍只是缺少原始响应的历史摘要。
- **以为检索是「因为上下文装不下」才需要的。** 3.1 万 token 塞得进一个窗口，而且没有报错。真正的约束是成本、延迟与准确性 —— 不是硬上限。
- **把「答案错了」一律算在模型头上。** 至少要先确认一件事：正确答案有没有被召回。没召回的话，改 prompt 一万次也没用。
- **指望检索解决推理问题。** 检索改变「模型看得到什么」，不改变「模型会不会推」。
- **忘了引用来源。** 检索结果里带上出处（代码里的 `[来源: xxx]`）几乎不花成本，却让回答可核对 —— 这也是后面几节要反复依赖的抓手。
