# 索引有生命周期：更新、删除与切换

## 这一节要解决什么

不少 RAG 教程把“把文件切块、算 embedding、写入向量库”讲完就算结束。真正接进业务后，文档还会改名、修改、撤回、迁移、重建；消息也可能重复或乱序。若系统只保存一组向量，却说不清它们对应源文档的哪个版本，召回结果就可能混有旧政策、已删除内容和不同批次的 chunk。模型即使回答得很流畅，也无法替索引生命周期修复这些错误。

本节的目标是把文档从首次入库到更新、删除、重建、发布、退役的过程变成可追踪状态机。交付物包括文档身份与版本记录、generation 构建与发布流程、删除抑制规则和离线回归用例。验收判据是：相同输入重放不会产生新版本；过期来源事件不会覆盖新内容；删除后旧索引项不会继续暴露；构建失败或快照过期不会替换当前 generation。

## 先区分四种版本

**文档身份 `doc_id`** 标识逻辑上的那份资料，不是文件路径，也不是 chunk 序号。路径会改，内容也会改；如果路径直接当主键，改名容易造成“一份旧文档仍在、又多出一份新文档”的重复。业务系统应使用源系统提供的稳定 ID，或在首次接入时分配稳定 ID 并保存映射。

**来源修订 `source_revision`** 表示源系统中变更的先后顺序。示例用整数，收到比当前修订更小的事件就忽略。真实来源可能给的是事件序号、数据库版本、ETag 或时间戳；只有当它确实能判断新旧时才可用作排序。一个不具备顺序语义的 ETag 只能判断相等，不能说明 A 一定早于 B。此时应通过源系统版本号、变更日志序号或重新读取当前源数据解决乱序，不能假造总序。

**内容 hash** 用于判断实际内容是否变化，避免仅因为重复投递就重新切块或计算 embedding。hash 是变更检测辅助，不是文档身份，也不构成访问授权。若相同 `source_revision` 却收到不同内容，应将其视为上游契约冲突并告警，而不是悄悄选择一个版本。配套代码对传入字符串的 UTF-8 字节计算 SHA-256，不做空白或 Unicode 规范化；生产管线若要规范化，必须先定义并稳定执行同一规则。

**索引 generation 与 pipeline version** 则描述“这批索引是怎样构建出来的”。generation 是一次完整的构建快照；pipeline version 记录切分器、规范化规则、embedding 模型或维度、元数据 schema 等配置的版本。只更新文档内容可能只需增量计算；切分规则或 embedding 模型变化通常需要全量重建。二者不可混为一个数字：一套 pipeline 可生成许多 generation，而一个 generation 只应对应明确的 pipeline 配置。

## 更新、删除与读取必须一起设计

一次文档更新不只是“新增向量”。同一个 `doc_id` 的旧 chunk 必须失效，新内容的 chunk 必须全部进入同一文档版本；否则一条回答可能混用新旧段落。每个 chunk 至少要带 `doc_id`、`doc_version`、`generation_id` 和必要的来源定位信息，便于追踪召回证据来自哪一份资料。用于重算的内容与访问策略也应有明确保留边界，不能因为要做索引就无限复制原文。

删除要经过 tombstone（删除标记）传播。若直接从源表抹掉记录，消费者可能无法分辨“从未见过”和“已删除但旧向量仍残留”。tombstone 保留逻辑 ID 与来源修订，旧事件到达时就能识别它已经过时。对严格删除要求，还需要定义删除在向量服务、缓存、检索日志、导出物和备份中的传播及证明过程。示例只验证本地目录与活动快照，不声称完成隐私法规意义上的全副本擦除。

更容易漏掉的是删除到重建之间的窗口：旧 generation 仍可能包含已撤回内容。安全的读取路径要把活动索引项与权威文档版本/删除状态核对，至少应让 tombstone 立即抑制旧版本，而不是等下一次离线重建完成才生效。更新也可以短暂过滤掉版本不匹配的旧 chunk；这可能降低召回，随后由新 generation 恢复，但不会把旧内容误交给模型。授权过滤是另一条独立边界，见下一节：内容仍有效也不表示当前用户可以看到它。

## 先完整构建，再发布 generation

在活动向量索引上边写边删会暴露部分状态：一半文档已切换，一半还未切换；某个批次失败后甚至难以判断哪些 chunk 已经生效。更稳的模式是不可变 generation：选定一个源快照和 pipeline version，在新 generation 下构建全部候选记录，验证数量、维度、hash 和预期元数据，再发布一个小型活动指针。读请求先读活动指针，再限定在该 generation 中检索。

“原子切换”只在指针与索引数据的边界真的具备原子性时才成立。如果向量存储和关系数据库是两个独立服务，不能把分别写成功描述成跨服务事务。常见方案是先在向量侧完整写入不可变 generation 并确认可读，再用数据库事务切换唯一活动 generation；读路径只查询指针指向的版本。若中间失败，旧指针继续服务，新 generation 可重试或回收。若系统无法保证指针与向量可见性的一致顺序，就必须设计 readiness 标记、回滚和对账，不能仅靠“最后更新一下配置”作为保证。

发布之前还要检查构建快照是否过期。假设 generation 正在计算 embedding 时，某份政策又被更新；如果仍将旧快照切成活动版本，新内容就会被回滚。简单的教学实现会比较 generation 中每份文档的 `doc_version` 和 hash 与当前目录是否一致；不一致就拒绝发布并重建。大规模系统可以使用源变更水位、快照 ID 或事件日志 offset 做类似判定，但必须说明它比较的是哪个一致性边界。

## 可运行的 SQLite 教学模型

本节的完整离线示例位于 `examples/index-lifecycle/`。它用 SQLite 保存来源修订、文档版本、tombstone、generation 明细和活动指针，不调用 embedding API，也不模拟向量相似度。实跑状态：代码以 Python 标准库实现，使用下列命令可离线运行测试：

```bash
python3 -m unittest discover -s examples/index-lifecycle -v
```

本轮实跑结果：6 个测试全部通过。覆盖同内容重放、内容版本递增、乱序旧事件不能复活删除文档、删除后活动查询立即抑制旧记录、generation 过期拒绝发布，以及在 SQLite 写入 generation 明细的中途注入失败后，事务回滚候选 generation 并保留旧活动指针。最后一项只证明此模型把 generation 与明细写在同一 SQLite 事务中；它不模拟 embedding/向量服务部分失败，也不证明 PostgreSQL 多进程锁、跨服务一致性或生产级重试。该最小模型也没有持久化 `pipeline_version`、每条 generation entry 对应的 `source_revision`、chunk 内容或向量；前文对这些字段和构建配置的要求是架构设计判据，不是这份示例已经实现的能力。代码和测试是可复制的实测依据；如果修改了例子，重新运行同一命令。

最小调用形态如下，完整逻辑在配套模块中：

```python
from index_catalog import IndexCatalog, StaleGeneration

catalog = IndexCatalog("index-catalog.db")
catalog.upsert_document("policy-17", source_revision=1, content="退货期限为 30 天")
generation = catalog.build_generation()
catalog.activate_generation(generation)

# 来源版本 2 删除文档：旧 generation 里的条目会先被当前目录过滤，
# 后续完整重建再把删除反映进新的 generation。
catalog.delete_document("policy-17", source_revision=2)
assert catalog.active_document_ids() == []

try:
    catalog.activate_generation(generation)  # 已经活动，不能重复发布
except ValueError:
    pass
catalog.close()
```

注意这里展示的是可组合的调用片段：`StaleGeneration` 在建立新 generation 后、源内容发生变化、再尝试激活旧候选时触发；如果要观察该异常，应照测试 `test_stale_generation_cannot_replace_current_index` 的顺序操作。生产代码还必须确保连接关闭和异常清理，配套示例通过 `finally`/测试清理做到这一点。

## 失败案例：旧文档没有消失

一个客服助手检索到“退货 30 天”，而业务后台已经把规则改成“退货 14 天”。排查发现目录表中的新文本确实保存成功，但切块任务按文件路径生成向量 ID；新版本写入了新向量，旧向量却没有被删除。搜索仍能命中旧片段，模型因此生成了过期答复。日志里“upsert 成功”是真的，但它只证明新记录写入成功，不证明旧记录已失效。

定位从身份和版本开始：对照 `doc_id`、源修订、内容 hash、pipeline version、每个 chunk 的 generation 和活动指针。随后用固定查询分别检查权威目录、向量存储与最终过滤后的召回结果，确认错误发生在哪一层。修复增加稳定逻辑 ID 与文档版本元数据，让新版本可以使旧版本失效；删除时先写 tombstone，查询路径立即过滤删除/版本不匹配条目；全量构建在独立 generation 完成后才切换活动指针。最后用“重复投递、乱序更新、删除后查询、构建中源内容再变、发布失败”做回归，不能只验证新向量确实出现。

配套测试还给出另一个可复现失败形态：先构建 generation，再以更高来源修订更新文档，激活旧 generation 会抛出下面的原始异常，活动指针保持不变。这是刻意失败的断言，不是异常系统状态。没有这个检查，重建期间的旧快照可能覆盖新内容，事故表面上看起来会像“索引随机回滚”。

```text
StaleGeneration: generation 2 no longer matches source state
```

## 实施步骤与验收清单

1. 定义稳定 `doc_id`，记录来源系统和映射规则；不要让路径、chunk 顺序或向量内容承担身份职责。
2. 选取有顺序语义的 `source_revision`，对重复事件与迟到事件分别制定规则；同版本内容冲突应暴露为上游错误。
3. 先定义是否需要内容规范化，再对规范化后的稳定输入计算 hash；示例只 hash 原样传入的字符串。只有内容、元数据或 pipeline version 变化时才重跑对应阶段；生产索引中的派生 chunk 应能回溯到文档版本。
4. 维护 tombstone，并定义删除对活动召回、缓存、日志与备份的可验证传播；权限判定继续使用受信身份，不从文档元数据推导用户授权。
5. 在不可变 generation 中构建并检查候选索引，检查失败不能推进活动指针。
6. 发布前校验源快照仍有效；切换活动指针后再按保留策略清理旧 generation，并提供失败回滚和人工对账入口。
7. 为“重复、乱序、变更、删除、重建失败、重建期间再次变更、切换后读到的版本”分别写确定性测试。

验收时看三类证据：目录记录能解释当前有效文档版本；检索结果能追溯到活动 generation 与源修订；故障注入证明任何失败都不会意外把半成品设为活动索引。还要记下检索暂时漏召回的窗口、旧 generation 的保留时间和清理失败告警。单纯展示向量库里有数据，无法证明这三个条件。

## 后端经验能迁移什么

可直接迁移的是主键设计、幂等消费、乐观版本检查、删除标记、快照发布、回滚和对账。需要重新建立的直觉是：派生索引不是主数据，重算可能很慢；一次文档变更可以同时改变多个 chunk；模型/切分配置变更会让全量索引需要重建；多个存储之间通常没有共同事务。把“数据库已经提交”当作“检索已经更新”，会把异步链路的中间态藏起来。

最重要的三个产物分别是文档版本目录、不可变索引 generation、可审计的活动指针。它们缺一不可：只有目录无法证明检索时没读旧向量；只有 generation 无法解释它覆盖了哪些源修订；只有指针而没有构建和删除记录则无法安全恢复。用这些产物回答：当前检索的是哪一批索引、它来自哪些文档修订、撤回后旧内容如何被立即压制、失败构建如何回滚，就构成了本节的完成判据。
