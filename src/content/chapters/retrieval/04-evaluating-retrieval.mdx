助手的回答错了。接下来做什么？

先检查交付给模型的证据是否充分、正确且获准。若支持证据未进入上下文，单纯要求模型“仔细阅读”无法补出缺失信息；提示仍可能影响拒答、查询改写等行为，因此要记录各阶段输入后再定位。

这一节讲的是如何把失败拆成可检查的环节。分层是诊断工具，不意味着召回和生成彼此独立：上下文、切分、问题类型与模型行为会互相影响。

## 诊断失败：证据供给与模型使用

先用两个问题做初步分流（这是诊断视角，不是穷尽所有失败原因）：

- **召回层**：正确答案所在的那一段，有没有被取回来？
- **生成层**：取回来了，模型有没有用好它？

最终答案错了，可能是相关证据缺失/不完整、候选排序或截断有误，也可能是证据已提供但模型没有正确使用；解析、权限过滤、版本新鲜度和业务规则也可能出错。先记录每一步实际交付的证据，再针对对应环节做对照，不能仅凭一次“给金标后答对”就断定因果。

## 先看一份评测集长什么样

后续指标依赖标注口径，先把一条样本具体化（**构造示例，未实跑**）。此表是讲解用的 5 条：前 4 条是有答案的检索任务，最后一条是无相关证据的边界样本；它不是下文历史实验的 6 条数据集。

| id | query | 相关证据（金标） | 样本类型 | 检索判据 | 回答/接口判据 |
|---|---|---|---|---|---|
| e01 | 切分粒度会影响召回吗 | retrieval/chunking#历史摘要：评测粒度会改变“命中”的含义 | 有答案 | 命中金标 | 回答由证据支持 |
| e02 | 上下文压缩会丢什么 | context-engineering/compaction#历史样本二：摘要记录中遗漏一条硬约束 | 有答案 | 命中金标 | 回答含「硬约束丢失」 |
| e03 | 子智能体是不是更贵 | multi-agent/cost-model#实测：两次不同背景规模下的倍数 | 有答案 | 命中金标 | 按证据回答成本比较 |
| e04 | 记忆什么时候该忘 | memory/forgetting-and-conflict#有效期如何设定 | 有答案 | 命中金标 | 回答不得超出证据范围 |
| e05 | 检索里 `**` 为什么没渲染 | — | 无答案边界 | 不计入有答案 recall | 按产品契约拒答/说明无证据 |

把检索判分与最终回答判分分开。**检索相关性标注**说明哪些证据足以支持答案；**端到端期望行为**还可以要求模型正确回答或在无证据时拒答：

- **有答案样本**：对每个问题标注一条或多条能支持回答的 evidence span；查询里是否使用原文词，应作为样本属性，不是相关性定义。
- **无答案/越权边界样本**：单独标注“没有获准的支持证据”，评估误召回、拒答与授权行为；不能把它混入有答案样本的 recall 分母。

对每题一个金标，可用 `hit@k` / `success@k` 表示前 k 是否命中，数值与该题 `recall@k` 相同。多金标题用 `|retrieved ∩ gold| / |gold|` 计算每题 recall，再按预先选定的宏/微平均聚合。对标准 precision/recall 定义可参阅 [Stanford《Introduction to Information Retrieval》评测章节](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-unranked-retrieval-sets-1.html)。MRR 用首个相关结果的位置；它不替代多证据召回或分级相关性指标。

一个有用的诊断对照是把经人工核验的支持证据直接放进上下文，再与真实检索输出比较。它只能在固定问题、提示、模型版本、预算和评分器下提供一个对照；不能单凭一次对照把错误因果归到某一层。

## 困难样本长什么样

「设计困难样本」这句话很空。落到这份评测集里，三类困难样本各有一条具体的样子（**构造示例，未实跑**）：

- **空查询**：`query = ""`。应用契约可以要求**代码层直接拒绝**，而不是把空输入记成检索失败；将这种输入作为接口边界测试。
- **超长查询**：把上面 e02 的问题扩写成 400 字的背景描述，里面混进三个相邻主题的词（压缩、摘要、上下文窗口）。它测的是「长查询里真正的问题意图有没有被淹掉」。
- **相邻主题混淆**：e03「子智能体是不是更贵」—— 语料里另有一节讲子智能体的机制，词面更接近，但答案不在这里。它测的是排序，不是召回。

这些是构造的故障假设，不是本节实测。拒绝、意图漂移与排序错误需要不同判据；统一塞进一个 retrieval recall 数字会掩盖问题类型。
## 召回失败其实是两种

“最终没命中”还可按候选集分流：候选集里有支持证据但没排进最终 top-k，属于候选内排序/截断问题；候选集里没有支持证据，则要调查召回、过滤、切分或标注。下面 4/10、6/10 是不可独立复核的旧摘要，仅作问题分类示意：

| 情况 | 10 条里的条数 | 重排能救吗 | 该动什么 |
|---|---:|---|---|
| 正确答案在候选集内，但没排进前列 | 4 | ✅ 全部救回 | 加一个重排环节 |
| 正确答案压根不在候选集里 | 6 | ❌ 无能为力 | 改查询改写、向量检索、放宽匹配 |

两种情形的后续检查不同：候选中已有 gold 时，可以评估重排是否改善目标排名；候选中没有 gold 时，调整 reranker 无法补出缺失证据。历史 4/10 与 6/10 未复核，不能说明增加重排必然“全部救回”。

候选集合对重排存在严格上界：gold 不在候选里时无法被重排选中。但候选内命中不等于答案充分或可用；记录各阶段真实交付的候选和最终上下文，再按目标任务分别评测：

- **候选召回覆盖**：gold evidence 是否存在于候选集合，候选深度取实际送入重排的数量。
- **最终证据覆盖与排序**：重排/截断后，足以支持答案的证据是否仍然存在、处于合适位置。
- **端到端答案与边界行为**：模型是否基于证据作答、拒绝无证据请求，并通过业务校验。

候选覆盖低时，先检查召回与过滤；候选覆盖足够而最终位置差时，可测试排序策略。加 reranker 是否有价值，取决于它在固定候选和目标判据上的效果/成本，不由两项旧摘要决定。
## 指标：recall@k、MRR，以及粒度决定你能看见什么

分流只提供调查方向；要衡量改动带来的变化，需要先定义指标。

**recall@k**：对一个 query，前 k 个结果里命中的相关证据数量，占该 query 全部已标注相关证据的比例；多 query 的宏平均会让每个 query 权重相同，微平均则汇总相关证据计数后再计算，须说明采用哪种口径。它适合衡量证据覆盖，但不衡量排序内部位置、证据新鲜度、授权或最终回答正确性。precision 与上下文预算和噪声有关；何者更重要取决于任务风险、候选用途与预算，不能排成通用优先级。

**MRR**（平均倒数排名）：对每个有答案 query 找到首个相关结果的 rank r，取 `1/r` 后求平均；在完整排序中没有命中的有答案 query 计 0，无答案/越权边界 query 应按单独的拒答与误召回指标评估。它强调第一个相关结果的位置，但忽略后续相关证据，也不表达 graded relevance。下面本地 fixture 展示 hit@k 与 MRR 的不同响应；它不是生产检索质量测量。

旧报告曾按文件级与章节级口径汇总同一组 15 条查询，但原始 query、gold 映射、排序结果与 scorer 未归档。下表仅是不可复核的历史摘要；当前文件没有足够证据判断旧指标究竟是 hit rate 还是严格定义的 recall，它不能证明差异只由评测粒度造成：

| 评测口径 | 历史记录的 top-5 命中统计 |
|---|---:|
| 「答案在哪一篇」（文件级） | 13/15（87%） |
| 「答案在哪个小节」（章节级） | 8/15（53%） |

评测单位要对应实际决策：若候选是 chunk，可用原始 evidence span 映射判断它是否覆盖支持内容；若系统先返回文档再抽取 chunk，就分别记录 document recall 与 chunk/evidence coverage。文件命中不等于模型拿到充分证据，chunk 命中也不自动证明足以回答。

## 完整可运行代码

```python
"""检索评测的最小骨架：recall@k 与 MRR。

只用标准库。这个本地 fixture 每题只有一个金标；hit@k 与单金标 recall@k 数值相同。它展示指标计算，不评测真实检索系统。

实跑状态：本轮在 Python 3.14.7 离线运行；这是小型合成 BM25 fixture，不调用 provider、不代表检索质量。
"""

import math
import re

DOCS = {
    "参数总览": "温度、top_p、max_tokens 都会影响输出。温度越高越发散，温度越低越确定。",
    "确定性": "把温度设为 0 并不保证两次调用完全相同。厂商侧仍存在非确定性。",
    "缓存": "前缀缓存命中时，未命中的输入会大幅下降。任何一处前缀改动都会让它全部失效。",
    "切分": "文档被从段落中间切开后，单独看这一块往往看不出它在讲什么。",
}

# 构造的本地 fixture：每题一个金标；真实数据需脱敏并记录采样来源。
EVAL_SET = [
    ("温度设成 0 结果就一定一样吗", "确定性"),
    ("改了前缀为什么成本突然高了", "缓存"),
    ("块被切开之后会怎样", "切分"),
    ("温度这个参数是干什么的", "参数总览"),
]


def tokenize(text):
    text = text.lower()
    out = re.findall(r"[a-z0-9_]+", text)
    for run in re.findall(r"[\u4e00-\u9fff]+", text):
        out.extend(run[i:i + 2] for i in range(len(run) - 1))
    return out


def search(docs, query, k):
    if not docs:
        raise ValueError("docs must not be empty")
    if type(k) is not int or k < 1:
        raise ValueError("k must be a positive integer")
    toks = {i: tokenize(t) for i, t in docs.items()}
    if not any(toks.values()):
        raise ValueError("docs must contain at least one token")
    avgdl = sum(len(t) for t in toks.values()) / len(toks)
    df = {}
    for t in toks.values():
        for term in set(t):
            df[term] = df.get(term, 0) + 1
    k1, b = 1.2, 0.75
    scored = []
    for i, t in toks.items():
        tf = {}
        for x in t:
            tf[x] = tf.get(x, 0) + 1
        s = 0.0
        for term in set(tokenize(query)):
            if term not in tf:
                continue
            n = df.get(term, 0)
            idf = math.log(1 + (len(docs) - n + 0.5) / (n + 0.5))
            f = tf[term]
            s += idf * (f * (k1 + 1)) / (f + k1 * (1 - b + b * len(t) / avgdl))
        if s > 0:
            scored.append((s, i))
    scored.sort(reverse=True)
    return [i for _, i in scored[:k]]


def metrics(docs, eval_set, k=3):
    """返回单金标 hit@k 与全排名 MRR；没命中计 0。"""
    if not eval_set:
        raise ValueError("eval_set must not be empty")
    if type(k) is not int or k < 1:
        raise ValueError("k must be a positive integer")
    hits = 0
    rr = 0.0
    detail = []
    for query, gold in eval_set:
        ranking = search(docs, query, len(docs))
        topk = ranking[:k]
        rank = ranking.index(gold) + 1 if gold in ranking else 0
        if gold in topk:
            hits += 1
        if rank:
            rr += 1.0 / rank
        detail.append((query, gold, rank, topk))
    return hits / len(eval_set), rr / len(eval_set), detail


if __name__ == "__main__":
    for k in (1, 2, 3):
        hit_rate, mrr, _ = metrics(DOCS, EVAL_SET, k)
        print("k=%d  hit@%d = %.2f   MRR = %.2f" % (k, k, hit_rate, mrr))
    print()
    print("逐条明细（k=3）：")
    _, _, detail = metrics(DOCS, EVAL_SET, 3)
    for query, gold, rank, got in detail:
        mark = "OK " if rank else "MISS"
        print("  %s %-20s 金标=%-6s 排名=%s  候选=%s" % (mark, query, gold, rank or "未召回", got))
```

本地实跑输出（Python 3.14.7，2026-10-21）：

```text
k=1  hit@1 = 0.75   MRR = 0.88
k=2  hit@2 = 1.00   MRR = 0.88
k=3  hit@3 = 1.00   MRR = 0.88

逐条明细（k=3）：
  OK  温度设成 0 结果就一定一样吗      金标=确定性    排名=1  候选=['确定性', '参数总览']
  OK  改了前缀为什么成本突然高了        金标=缓存     排名=1  候选=['缓存', '切分']
  OK  块被切开之后会怎样            金标=切分     排名=1  候选=['切分']
  OK  温度这个参数是干什么的          金标=参数总览   排名=2  候选=['切分', '参数总览', '确定性']
```

在这个本地 fixture 的最后一条，金标「参数总览」排第 2，「切分」排第 1。由于每题只有一个 gold，hit@3 仍为 1；MRR 会对 rank 2 记 1/2。但 MRR 只关注首个命中，不判断第 1 个结果的危害，也不适用于单独衡量多证据或分级相关性。

## 评测集从哪来，多小才够

真实失败案例有助于覆盖实际故障，但线上样本可能偏向已知失败，也可能含个人或敏感信息。按数据最小化策略脱敏、抽样并记录来源；再用人工编写和合成的边界样本补足低频情形。任何一类都不能单独代表完整生产分布。

其次是**边界样本**：你能想到的最刁钻的输入（空查询、超长查询、与所有文档都不相关的查询、以及像上面「温度这个参数是干什么的」这种会与相邻主题混淆的查询）。

**几十条能说明多少？** 标准误公式可说明抽样估计的波动规模，但不能单独回答样本量是否足够；足够与否取决于目标总体、要区分的差异、置信/错误率要求和 query 相关性。若把每条查询的结果视为来自目标分布的独立 Bernoulli 样本，样本比例的 plug-in 标准误估计为 `sqrt(p_hat(1-p_hat)/n)`。它是标准误，不是置信区间；以下只列算术结果（非实测），不能用于相关样本、偏置抽样或小样本的可靠区间推断：

| 观察到的比例 p̂ | n=15 的标准误 | n=30 的标准误 | n=100 的标准误 | n=400 的标准误 |
|---:|---:|---:|---:|---:|
| 0.5 | 12.9 pp | 9.1 pp | 5.0 pp | 2.5 pp |
| 0.6 | 12.6 pp | 8.9 pp | 4.9 pp | 2.4 pp |
| 0.9 | 7.7 pp | 5.5 pp | 3.0 pp | 1.5 pp |

例如 p̂=0.60、n=30 时，plug-in 标准误约为 9.1 个百分点。不要把“观察差值除以一个标准误”直接当作显著性检验：两组独立样本与同一批 query 的配对设计有不同误差结构；配对二元结果可检查逐题不一致对，或用按 query 配对的 bootstrap，并预先规定统计方法和决策阈值。若样本来自重复用户/同一意图簇，还需处理相关性。

可把固定回归集用于 CI，把代表性评测集用于版本判断；两者用途不同。前后比较尽量使用同一批 query，并按 query 保留配对结果，但它不会自动消除模型随机性或样本相关性。另设未参与调参的留出集；其 query、标注和判定规则应冻结，并避免相似题跨集合泄漏。

最后一条容易被忽略：评测集反复用于调参会产生选择偏差。将 query 按任务/来源分组后切分，避免近重复样本跨集合；冻结留出集及标签，只在预设评审节点使用。若数据持续用于决策，它就不再是未触碰的 holdout，应另收新样本。

## 常见坑

- **答案错了就去改 prompt。** 先检查交付给模型的证据、上下文组装、解析与授权路径；历史 6/6 对照不可复核，不能证明问题不在生成层。
- **用文件级指标评段落级系统。** 历史摘要报告文件级 13/15、章节级 8/15，但缺逐题 query、gold、排序和 scorer；不能当作可复核效果差异。当前任务应按实际送入模型的证据单位重新标注和评测。
- **只看 hit@k，不看排名。** 本地 fixture 的 `hit@3` 是 1.00，而「参数总览」实际排第 2；全排名 MRR=0.88 提供了不同信息。
- **以为「多送几段」一定更好或更差。** 评候选深度时同时看证据覆盖、最终回答、误召回、token、延迟和上下文预算；本节 321/1,659 token 与 6/6、5/6 都是不可复核历史摘要。
- **只报告总体通过率。** 总体值可能掩盖相邻主题、无答案和权限边界上的失败。按目标分布报告分层结果，并另设风险边界压力集；压力集用于发现弱点，不应冒充生产分布的通过率。
- **拿评测集反复调参。** 调久了它就是一份被记住的答案，留一份留出集。
- **忽略响应终态。** 截断、拒绝、工具交接、解析失败和正常回答应分别记录；端到端未交付可以计任务失败，但不能不加区分地归类成检索错误。
