助手的回答错了。接下来做什么？

多数人的第一反应是改 prompt —— 加一句「请仔细阅读资料」「不要编造」。如果失败的原因是检索根本没把正确的段落取回来，这些改动不会有任何效果，而你会花掉半天时间并得出结论「模型不太行」。

这一节讲的是怎么在动手之前，先把这个失败**定位到层**。

## 两层：召回层与生成层

一个检索问答链路有两个独立的失败点：

- **召回层**：正确答案所在的那一段，有没有被取回来？
- **生成层**：取回来了，模型有没有用好它？

这两种失败在最终输出上长得一模一样 —— 都是「答错了」。但修法完全相反：召回失败要去改切分、索引、查询改写、重排；生成失败要去改上下文组织、指令、或者模型档位。

分开它们的办法很直接：**人为构造一次「完美检索」，看模型层的上界在哪。**

## 实测：完美检索下，模型能答对几题

做法是跳过检索，直接把**金标小节本身**放进上下文（只有几百个字符），再问同样那 6 个问题：

| | 完美检索（给金标小节） | 词法 top-5 检索 |
|---|---:|---:|
| 答对 | **6/6** | 5/6 |
| 输入 token 合计 | 1,925 | 9,955 |
| 平均每题输入 | 321 | 1,659 |

（实跑数据，2026-10-08，`deepseek-flash`。）

这张表给了两个结论，第二个比第一个更有价值。

**结论一：生成层的上界是 6/6。** 这意味着那 1 题答错**不是模型的问题** —— 同一个模型，只要上下文对，它每次都能答对。所以改进方向明确指向检索，而不是 prompt。

**结论二：金标小节平均只有 321 token，比 top-5 检索便宜 5 倍，而且更准。** 这句话值得反复读。它说明**检索质量比检索数量重要得多**：与其多送几段「可能有关系」的内容，不如想办法让那一段对的进来。多送的那 1,300 多个 token 不但没帮忙，还稀释了注意力。

## 召回失败其实是两种

「没召回」这个说法太粗。上面那组重排数据里，它能再分一层：

| 情况 | 10 条里的条数 | 重排能救吗 | 该动什么 |
|---|---:|---|---|
| 正确答案在候选集内，但没排进前列 | 4 | ✅ 全部救回 | 加一个重排环节 |
| 正确答案压根不在候选集里 | 6 | ❌ 无能为力 | 改查询改写、向量检索、放宽匹配 |

这两种失败的修法完全不同。**把「召回不到」当成「排序不好」去调重排，是这类项目里最常见的方向性错误** —— 你会反复调整重排的提示词，而那 6 条永远不会好转。

分界线就是你的候选集大小。重排看到的候选是 20 条，那 20 就是天花板。所以评测时要同时看两个数：

- **最终命中率**（比如 top-3）—— 用户实际得到的效果
- **候选集内命中率**（比如 top-20）—— 你这套召回的上限

两者差距大，说明该加重排；**两者都低，说明问题在召回本身，重排加了也没用。** 本次实验里这两个数是 4/10 与 4/10 —— 重排已经打满上限，再优化它一分钱都赚不到；而那 6 条要动的是召回。
## 指标：recall@k、MRR，以及粒度决定你能看见什么

上一步只回答「哪一层有问题」。要回答「改完之后变好了多少」，需要指标。

**recall@k**：正确答案落在前 k 条里的比例。它是这类系统最重要的一个数字，因为它有个残酷的性质 —— **没被召回的文档等于不存在**，后面所有环节都无法挽回。所以召回率低是致命的，而精确率低只是浪费一点上下文预算。

**MRR**（平均倒数排名）：正确答案排在第几位的倒数的平均。recall@k 只关心「在不在前 k」，不关心排第几。这两者的差别在下面的实跑里看得很清楚。

不过比指标定义更容易出错的是**指标的口径**。本次实验里，同一套检索、同一批 15 条查询：

| 评测口径 | recall@5 |
|---|---:|
| 「答案在哪一篇」（文件级） | 13/15（87%） |
| 「答案在哪个小节」（章节级） | 8/15（53%） |

**同一个系统，只换了一个口径，从「基本没问题」变成「一半找不到」。**

原因不难理解：语料里每篇是一个主题明确的文件，只要求命中那一篇，任务就太容易了。而你真正送进模型的是**段落**，所以评的应该是段落。

这条规则可以写成一句：**评测的粒度必须等于你实际交给模型的那个单位。** 送段落就评段落，送整篇就评整篇，别用自己的方便去定义口径。

## 完整可运行代码

```python
"""检索评测的最小骨架：recall@k 与 MRR。

只用标准库。核心是 metrics 那 10 行 —— 有了它，
「这次改动是变好还是变坏」才变成一个能回答的问题。

实跑状态：2026-10-08，已跑通。
"""

import math
import re

DOCS = {
    "参数总览": "温度、top_p、max_tokens 都会影响输出。温度越高越发散，温度越低越确定。",
    "确定性": "把温度设为 0 并不保证两次调用完全相同。厂商侧仍存在非确定性。",
    "缓存": "前缀缓存命中时，未命中的输入会大幅下降。任何一处前缀改动都会让它全部失效。",
    "切分": "文档被从段落中间切开后，单独看这一块往往看不出它在讲什么。",
}

# 评测集：问题 + 金标段落。真实项目里这些应当来自线上失败案例。
EVAL_SET = [
    ("温度设成 0 结果就一定一样吗", "确定性"),
    ("改了前缀为什么成本突然高了", "缓存"),
    ("块被切开之后会怎样", "切分"),
    ("温度这个参数是干什么的", "参数总览"),
]


def tokenize(text):
    text = text.lower()
    out = re.findall(r"[a-z0-9_]+", text)
    for run in re.findall(r"[\u4e00-\u9fff]+", text):
        out.extend(run[i:i + 2] for i in range(len(run) - 1))
    return out


def search(docs, query, k):
    toks = {i: tokenize(t) for i, t in docs.items()}
    avgdl = sum(len(t) for t in toks.values()) / len(toks)
    df = {}
    for t in toks.values():
        for term in set(t):
            df[term] = df.get(term, 0) + 1
    k1, b = 1.2, 0.75
    scored = []
    for i, t in toks.items():
        tf = {}
        for x in t:
            tf[x] = tf.get(x, 0) + 1
        s = 0.0
        for term in set(tokenize(query)):
            if term not in tf:
                continue
            n = df.get(term, 0)
            idf = math.log(1 + (len(docs) - n + 0.5) / (n + 0.5))
            f = tf[term]
            s += idf * (f * (k1 + 1)) / (f + k1 * (1 - b + b * len(t) / avgdl))
        if s > 0:
            scored.append((s, i))
    scored.sort(reverse=True)
    return [i for _, i in scored[:k]]


def metrics(docs, eval_set, k=3):
    """返回 recall@k 与 MRR。召回不到就计 0，不给任何部分分。"""
    hits = 0
    rr = 0.0
    detail = []
    for query, gold in eval_set:
        got = search(docs, query, k)
        rank = got.index(gold) + 1 if gold in got else 0
        if rank:
            hits += 1
            rr += 1.0 / rank
        detail.append((query, gold, rank, got))
    return hits / len(eval_set), rr / len(eval_set), detail


if __name__ == "__main__":
    for k in (1, 2, 3):
        recall, mrr, _ = metrics(DOCS, EVAL_SET, k)
        print("k=%d  recall@%d = %.2f   MRR = %.2f" % (k, k, recall, mrr))
    print()
    print("逐条明细（k=3）：")
    _, _, detail = metrics(DOCS, EVAL_SET, 3)
    for query, gold, rank, got in detail:
        mark = "OK " if rank else "MISS"
        print("  %s %-20s 金标=%-6s 排名=%s  召回=%s" % (mark, query, gold, rank or "未召回", got))
```

实跑输出（2026-10-08）：

```text
k=1  recall@1 = 0.75   MRR = 0.75
k=2  recall@2 = 1.00   MRR = 0.88
k=3  recall@3 = 1.00   MRR = 0.88

逐条明细（k=3）：
  OK  温度设成 0 结果就一定一样吗    金标=确定性    排名=1  召回=[确定性, 参数总览]
  OK  改了前缀为什么成本突然高了      金标=缓存     排名=1  召回=[缓存, 切分]
  OK  块被切开之后会怎样          金标=切分     排名=1  召回=[切分]
  OK  温度这个参数是干什么的        金标=参数总览   排名=2  召回=[切分, 参数总览, 确定性]
```

看最后一条。它的金标是「参数总览」，排在**第 2 位**，而排第一的是「切分」—— 一个完全不相关的段落。

但 `recall@3` 显示 1.00。**recall 指标对这次排序错误完全没有反应**，因为正确答案确实在前 3 里。这就是 MRR 存在的理由：它把「排第一」和「排第三」区分开。只盯 recall 的系统会觉得自己没问题，而用户每次拿到的上下文里，第一段都是无关内容。

## 评测集从哪来，多小才够

**最值钱的来源是真实失败案例。** 每次线上出问题，把当时的输入原样存下来，修好之后加进评测集 —— 这条闭环保证你不会在同一个坑里摔两次。它的价值高于任何人工构造的样本，因为它是真实分布。

其次是**边界样本**：你能想到的最刁钻的输入（空查询、超长查询、与所有文档都不相关的查询、以及像上面「温度这个参数是干什么的」这种会与相邻主题混淆的查询）。

**几十条够用吗？** 够回答「这次改动是明显变好还是明显变坏」，比如召回率从 53% 到 80% 一定看得出来。**不够分辨 88% 和 90%** —— 那种差距需要几百条才具备统计意义。所以实用做法是分两层：小而快的集合进 CI，每次改动都跑；大而慢的定期跑，只用于做选型决策。

最后一条容易被忽略：**评测集一旦被反复用来调参，就会过拟合。** 缓解办法是留一份从不参与调优的留出集，只在做最终判断时打开。

## 常见坑

- **答案错了就去改 prompt。** 先分层。本次实测里，同样的模型在完美检索下 6/6 全对，说明问题根本不在生成层。
- **用文件级指标评段落级系统。** 本次实测：同一个系统的 recall@5 在两种口径下是 87% 与 53%。
- **只看 recall，不看排名。** 实跑里 `recall@3` 是 1.00，而正确答案其实排在无关段落之后。
- **以为「多送几段」能提高成功率。** 金标小节平均 321 token 就够 6/6，而 top-5 检索用 1,659 token 只到了 5/6。
- **评测集里全是容易的样本。** 一个 90% 通过率的集合如果 90% 都是容易题，它发现不了任何问题。困难样本的比例才是它的价值来源。
- **拿评测集反复调参。** 调久了它就是一份被记住的答案，留一份留出集。
- **忽略 `stop_reason`。** 预算不够时的空输出会被你的评测记成「答错」，让你去优化一个不存在的问题。
