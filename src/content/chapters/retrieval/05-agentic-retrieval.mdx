前面四节把检索当成一条**固定管线**：查询进来、召回、重排、送进上下文。这条管线什么时候跑、跑几次，都是你的代码决定的。

另一条路是把它反过来：**把检索做成一个工具，让模型自己决定要不要查、查什么、查几次。** 这就是 agentic retrieval。它听起来更「智能」，很多框架也默认这么做。

所以我量了一下它到底好多少。结果和我预期相反。

## 实测：三种形态的对照

用同一批 10 条口语化查询（就是第 3 节里词法检索全军覆没的那批），三种做法：

- **臂 A**：原问题直接拿去检索（固定管线，不做任何处理）
- **臂 B**：让模型把问题改写成 3 条检索词，检索一次，合并结果
- **臂 C**：把检索做成工具，让模型自己决定查什么、查几轮，上限 3 轮

每种做法跑 3 轮，看正确答案有没有落进最终候选集：

| 做法 | 命中（3 轮） | 平均 | 调用次数 | 输入 token | 输出 token |
|---|---|---:|---:|---:|---:|
| A 原问题直接检索 | 0 / 0 / 0 | **0/10** | 0 | — | — |
| B 改写查询后检索一次 | 6 / 5 / 8 | **6.3/10** | 10.0 | 754 | 4,276 |
| C 多轮自主检索 | 3 / 4 / 3 | **3.3/10** | 18.7 | 5,660 | 7,527 |

（实跑数据，2026-10-08，`deepseek-flash`。token 为三项之和，含缓存命中部分。）

表格里的「命中」指的是**正确答案所在的小节落进了最终候选集**（章节级口径，见第 4 节）。如果换成「答案在哪一篇」这种粗口径，三种做法的差距会被抹平 —— 这是第 4 节那个坑的又一次出现，所以每次报指标都要写清楚口径。

三件事同时发生了：

1. **原问题直接检索：一条都没命中。** 这验证了第 3 节的结论 —— 用户不会用你文档里的词。
2. **让模型改写一次查询：命中率从 0 涨到 6.3/10。** 这是最大的一步改进，成本只有 10 次调用。
3. **让它自己决定查几次：反而掉到 3.3/10**，而且调用次数几乎是 B 的两倍、输入 token 是 B 的 7.5 倍。

第 3 点需要解释。如果「自主」意味着更聪明，为什么它会比「改写一次」更差？

## 原因：它经常选择不查

我把臂 C 每一轮实际发出的查询词打了出来。10 条里有 **平均 3.3 条从头到尾一次检索都没发** —— 模型第一轮就直接输出了 DONE。

也就是说，**它自认为知道答案，于是不查。** 而这些问题的正确答案恰恰不在模型的参数里（它们是我自己文档里的实测结论）。

这件事在小规模上可以直接复现。下面这段代码跑的是一模一样的循环逻辑：

```text
问题: 同一个问题问两遍结果会一样吗
  轮1  查询=DONE（未检索）                      命中=[]

问题: 温度设成 0 会不会更稳定
  轮1  查询=temperature 0 是否更稳定 大语言模型 确定性  命中=[确定性]
  轮2  查询=DONE（未检索）                      命中=[]
```

第一个问题，模型**一次都没查**。第二个问题它查了一次，而且查得很好 —— 命中正确段落。同一个提示词、同一个模型，差别只在于它**判断自己需不需要查**。

而它对这个判断是没有依据的：要判断「我知不知道答案」，模型只能依赖自己的参数记忆，可它并不知道哪些信息在你的私有文档里。**「要不要查」这个决定，落在模型最不可靠的那一类判断上。**

这和第 3 章的一个观察是同一类：模型在「状态未知」时反而谨慎，行为很难预测。**凡是把关键决策交给模型自行判断的地方，都要先量一遍它判断得准不准。**

## 那什么时候该用多轮

多轮检索不是没用，而是它的适用范围比看起来窄得多。它真正有优势的场景只有一类：**第一轮的结果会改变下一步该查什么。**

- **多跳问题**：「A 方案在哪个版本被废弃，替代它的是什么？」—— 第二跳的查询词只有在第一跳的答案出来之后才能确定。这类问题固定管线做不了。
- **跨文档比对**：需要先定位两份文档，再对比。
- **探索式任务**：用户自己也不知道要什么，需要边看边收窄。

反过来说，如果问题本身已经清楚（「退款几天到账」），多轮不会带来任何收益，只会增加轮次与不确定性。

还有一条务实的中间路线值得优先考虑：**固定管线打底，把「再查一次」做成显式的工具调用，并由你设上限。** 这样既保留了多跳能力，又不会把「要不要查」整个交给模型 —— 你可以在代码里规定「第一次必须查」。

## 如果要用多轮，把它关进笼子

上面那组数据能直接推出四条设计规则：

1. **强制第一轮必查。** 臂 C 失败的直接原因是模型可以选 DONE，而它做这个判断时没有依据。做法很简单：第一轮不由模型决定 —— 用改写后的查询直接查一次，把结果放进上下文，之后才交给模型决定要不要追加。实测里 6.3/10 的臂 B 正是这么做的。
2. **上限写死在代码里。** 不是「在提示里告诉它最多查 3 次」，而是循环条件里的 `max_rounds`。模型可以忘记指令，循环计数器不会。
3. **每一轮都记日志。** 记下查询词、命中数、耗时。本次如果没有这份日志，我会把「一次都没查」误判成「查了但没命中」—— 而这恰好是第 4 节说的那两种完全不同的问题。
4. **把成本算进设计。** 臂 C 的输入是臂 B 的 7.5 倍。多轮带来的收益必须超过这个倍数才划算，而本次实验里它的命中率反而更低。

这四条合起来是一句话：**多轮是一种能力，不是一个默认值。** 只有当「第一轮的结果会改变下一步该查什么」这个条件成立时，它才值得开。
## 成本：别忘了第 3 章那条规律

臂 C 的输入 token 是臂 B 的 7.5 倍（5,660 对 754）。这个差距不是线性的：**每一轮的检索结果都会留在对话历史里，之后每一轮都要重新发一遍。**

这正是第 3 章得出的那条规律：**成本 = 内容 × 装载次数**。多轮检索的代价不只是「多一次工具调用」，而是「多一轮历史」。

第 3 章还给过一个交叉点，可以直接搬到这里用：固定 40 篇文档时，需要的占 2 / 8 / 20 / 40 篇，按需取的成本分别是预加载的 0.64 / 0.95 / 2.47 / 3.60 倍 —— **交叉点在「需要的约占 20%」附近**。

也就是说：**如果你要的资料占总量的一小部分，按需检索划算；如果你几乎每次都要读一大半，老实预加载更便宜。** 判断依据是「这次任务需要其中的多大比例」，而不是「资料多不多」。

## 完整可运行代码

```python
"""把检索做成工具、让模型自己决定查几次 —— 以及它的失败模式。

只用标准库。这段代码的价值不在「能跑」，而在它的循环上限与日志：
没有上限的自主检索会一直烧钱，而没有日志你根本不知道它查了几次。

实跑状态：2026-10-08，deepseek-flash，已跑通。
"""

import json
import math
import os
import re
import urllib.request

DOCS = {
    "确定性": "把温度设为 0 并不保证两次调用完全相同。厂商侧仍存在非确定性。",
    "缓存": "前缀缓存命中时，未命中的输入会大幅下降。任何一处前缀改动都会让它全部失效。",
    "切分": "文档被从段落中间切开后，单独看这一块往往看不出它在讲什么。",
    "重排": "先宽召回再精细排序，两步的目标不同。候选集大小决定了重排的上限。",
}


def tokenize(text):
    text = text.lower()
    out = re.findall(r"[a-z0-9_]+", text)
    for run in re.findall(r"[\u4e00-\u9fff]+", text):
        out.extend(run[i:i + 2] for i in range(len(run) - 1))
    return out


def search(docs, query, k=2):
    """工具：按查询词返回最相关的段落。"""
    toks = {i: tokenize(t) for i, t in docs.items()}
    avgdl = sum(len(t) for t in toks.values()) / len(toks)
    df = {}
    for t in toks.values():
        for term in set(t):
            df[term] = df.get(term, 0) + 1
    k1, b = 1.2, 0.75
    scored = []
    for i, t in toks.items():
        tf = {}
        for x in t:
            tf[x] = tf.get(x, 0) + 1
        s = 0.0
        for term in set(tokenize(query)):
            if term not in tf:
                continue
            n = df.get(term, 0)
            idf = math.log(1 + (len(docs) - n + 0.5) / (n + 0.5))
            f = tf[term]
            s += idf * (f * (k1 + 1)) / (f + k1 * (1 - b + b * len(t) / avgdl))
        if s > 0:
            scored.append((s, i))
    scored.sort(reverse=True)
    return [i for _, i in scored[:k]]


def call(system, messages, max_tokens=3000):
    body = json.dumps({
        "model": os.environ.get("VERIFY_MODEL", "claude-haiku-4-5"),
        "max_tokens": max_tokens,
        "system": system,
        "messages": messages,
    }).encode()
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages",
        data=body,
        headers={"content-type": "application/json",
                 "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
                 "anthropic-version": "2023-06-01"},
    )
    with urllib.request.urlopen(req, timeout=180) as resp:
        data = json.loads(resp.read())
    text = "".join(b["text"] for b in data["content"] if b["type"] == "text")
    return text, data["stop_reason"]


def agentic(question, max_rounds=3):
    """关键：max_rounds 必须有，否则它可能一直查下去。"""
    system = ("你是一个会主动检索的助手。每次只输出一条指令："
              "SEARCH: <查询词> 或 DONE。不要输出别的。")
    messages = [{"role": "user", "content":
                 "问题：" + question + "。需要查资料就输出 SEARCH: <查询词>，"
                 "已经能确定答案就输出 DONE。"}]
    log = []
    for rnd in range(1, max_rounds + 1):
        text, stop = call(system, messages)
        m = re.search(r"SEARCH:\s*(.+)", text)
        if not m:
            log.append((rnd, "DONE（未检索）", []))
            break
        q = m.group(1).strip()
        hits = search(DOCS, q, k=2)
        log.append((rnd, q, hits))
        messages.append({"role": "assistant", "content": text})
        snippet = "\n".join("[%s] %s" % (h, DOCS[h]) for h in hits) or "（无结果）"
        messages.append({"role": "user", "content":
                         "检索结果：\n" + snippet + "\n\n继续：输出 SEARCH 或 DONE。"})
    return log


if __name__ == "__main__":
    for q in ["同一个问题问两遍结果会一样吗", "温度设成 0 会不会更稳定"]:
        print("问题:", q)
        for rnd, query, hits in agentic(q):
            print("  轮%d  查询=%-34s 命中=%s" % (rnd, query, hits))
        print()
```

注意两个细节：`max_rounds` 是必须的（没有它，轮次不可预测），以及每一轮都把查询词记进 `log`（没有它，你根本不知道它查了几次 —— 我也是打了日志才发现「一次都没查」这件事）。

## 常见坑

- **默认「让模型自己决定要不要检索」是更好的设计。** 实测 3.3/10 与 6.3/10 的差距就出在这个决定上，而且它往往选择不查。
- **不记录每轮的查询词。** 只看最终结果，你会把「一次没查」和「查了但没命中」混为一谈，而这两种失败的修法相反。
- **不给多轮设上限。** 轮次不可预测意味着成本和延迟都不可预测。
- **忽略历史累积。** 多轮的输入是 7.5 倍 —— 因为每轮的检索结果都会留在历史里被重复发送。
- **在「问题本身已清楚」的场景用多轮。** 没有多跳需求时，它只增加轮次和不确定性。
- **忘了交叉点。** 需要的内容占总量比例高时，预加载比按需取更便宜（第 3 章实测约在 20% 处交叉）。
