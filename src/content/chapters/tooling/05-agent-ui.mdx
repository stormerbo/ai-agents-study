第 19 章讲了审批该展示什么、进度该怎么表达。那些是设计结论 —— 这一节把它们落成代码，并说清一个实现上的关键判断。

## 一个反直觉的实现判断

先说结论：**审批界面可以完全不需要客户端状态。**

常见的做法是把它做成一个带 modal 状态、loading 状态、二次确认状态的前端组件 —— 那些状态都来自一个隐含的模型：**「先选中，再提交」**。

而审批的四个选项（同意 / 拒绝 / 修改后同意 / 换个方式）**本质上是四条不同的请求**，不是一个「选择」：

```text
同意          → 执行原动作
拒绝          → 取消并重新规划（第 19 章：中止是最后手段）
修改后同意    → 执行修改后的版本（不重新规划 —— 人的修改是约束）
换个方式      → 重新规划，把人的意见当约束
```

四条各自的下一步完全不同，所以它们**不需要先被选中再一起提交**。理解这一点之后，界面就退化成了一组按钮 —— 而它可以是纯 server component，**零客户端 JS**。

**"四条请求"具体长什么样：**

```text
POST /api/approval/ap_8f3c21/approve        {}                                   → 执行冻结的参数
POST /api/approval/ap_8f3c21/reject         {}                                   → 重新规划（第 19 章：中止是最后手段）
POST /api/approval/ap_8f3c21/approve        {"params": {"to": "lisi@example.com"}} → 执行修改后的参数，不重新规划
POST /api/approval/ap_8f3c21/retry          {"constraint": "改用 reply 工具"}        → 带着人的约束重新规划
```

（示例：构造数据，未实跑 —— 接口形状的示例，字段判据见下。）

**四个端点里有两个共用 `approve`，靠 body 里有没有 `params` 区分** —— 这是刻意的："同意"和"修改后同意"在服务端是同一件事（执行一个动作），只在"用哪组参数"上分叉。而 `reject` 与 `retry` 是真正不同的动作（一个可能终止、一个必须继续规划）。

**参数为什么是 `{"params": {...}}` 而不是散在 body 顶层。** 因为服务端要用它算一次哈希，和冻结记录里的 `params_hash` 比对（第 19 章第 3 节那条防线）—— **包一层让"这次提交的是哪组参数"成为一个单独的对象**，比对逻辑才不会去猜哪些字段算参数。

**服务端的路由骨架（每个端点一份，形状一致）：**

```python
# app/api/approval/[id]/approve/route.py 的概念形态（伪代码）
def approve_route(approval_id, body):
    rec = store.get("approval:%s" % approval_id)          # 从存储读回，不是从内存
    if rec is None:
        return {"status": "not_found"}, 404
    if rec["status"] == "executed":                        # 幂等：点两次是合法行为
        return {"status": "already_executed"}, 200

    params = body.get("params") or rec["frozen_params"]   # 修改后同意就走这一支
    if body.get("params") and hash_params(params) != rec["params_hash"]:
        return {"status": "params_changed"}, 409           # 有人改过冻结的那份
    result = execute_atomically(rec, params)               # 副作用与标记同一事务
    return {"status": "executed", "result": result}, 200
```

**这个骨架里有三处对应第 19 章的结论：** `store.get` 而不是内存字典（状态必须落盘）、`already_executed` 的幂等分支（点两次不能执行两次）、以及 `execute_atomically`（检查与执行不能分开）。**三处少任何一处，界面上看起来都完全正常** —— 只有用户真的点了两次、或者服务重启了，问题才会出现。

**四个选项各自的界面状态怎么同步：**

| 选项 | 服务端返回 | 界面接下来显示 |
|---|---|---|
| 同意 | `executed` + 结果 | 把那条审批收起来，直接接上执行结果 |
| 拒绝 | `replanning` | 保留已生成内容，标一句"已按你的意见重新规划" |
| 修改后同意 | `executed` + 结果 | 同"同意"，但要显示实际用的是修改后的参数 |
| 换个方式 | `replanning` | 同上，且把人的约束原样显示出来（让用户确认它被采纳了） |

**这一列是本节最容易漏的东西。** 如果四个选项在界面上都只是"按钮变灰"，用户无法知道自己的操作产生了什么后果 —— 而第 19 章那条"控制感"要求的正是这个反馈。

**还没接后端时怎么验证？** 用一个本地的小状态机跑一遍，把四个请求各自的返回与界面文案对照出来（不需要任何凭据）：

```python
"""四个审批选项 → 状态迁移 → 界面该显示什么。纯本地。

实跑状态：2026-10-12。
"""

PENDING = {"ap_8f3c21": {"status": "pending", "params": {"to": "zhangsan@example.com"}}}


def handle(option, body=None, rec=None):
    """模拟服务端路由：返回 (HTTP 状态, 响应体, 界面句子)。"""
    rec = rec if rec is not None else PENDING["ap_8f3c21"]
    if rec["status"] == "executed":
        return 200, "already_executed", "这个动作已经执行过，未重复执行"
    if option == "approve":
        params = (body or {}).get("params") or rec["params"]
        rec["status"] = "executed"
        rec["params"] = params
        return 200, "executed", "已执行：发送给 %s" % params["to"]
    if option == "reject":
        rec["status"] = "replanning"
        return 200, "replanning", "已按你的意见重新规划（其后的步骤可能全变）"
    if option == "retry":
        rec["status"] = "replanning"
        return 200, "replanning", "已带约束重新规划：%s" % (body or {}).get("constraint")
    return 400, "bad_option", "未知选项"


if __name__ == "__main__":
    print("选项            状态码  响应体             界面显示")
    # 每个选项都从"初始待审批状态"开始，否则前一个选项的状态会污染后一个
    CASES = (("approve", None),
             ("approve", {"params": {"to": "lisi@example.com"}}),
             ("reject", None),
             ("retry", {"constraint": "改用 reply 工具"}))
    for opt, body in CASES:
        fresh = {"status": "pending", "params": {"to": "zhangsan@example.com"}}
        code, status, ui = handle(opt, body, rec=fresh)
        print("  %-14s %-6d %-18s %s" % (opt, code, status, ui))

    # 同一条记录被点两次：第二次必须命中幂等分支，而不是再执行一次
    rec = {"status": "pending", "params": {"to": "zhangsan@example.com"}}
    print()
    print("  同一条审批被点了两次：")
    print("    第 1 次：%s" % handle("approve", None, rec=rec)[2])
    print("    第 2 次：%s" % handle("approve", None, rec=rec)[2])
```

**注意上面第二次 `approve` 会返回 `already_executed`** —— 因为第一次已经把记录推到了 `executed`。这恰好演示了那条幂等防线在界面上的样子：**用户点了两次，第二次看到的是"已经执行过"，而不是第二次发送。**

**先说清"水合"是什么，因为它是这一节唯一一个纯前端概念。** 水合（hydration）指的是：服务端已经渲染出一份 HTML，浏览器拿到之后，前端框架再**在上面"挂"一遍事件与状态**，让静态的标记变成可交互的组件。

面向后端的类比是：**服务端渲染出来的 HTML 相当于一份"快照"，水合是"用代码把这份快照重新实例化成一个活对象"。** 而风险在于 —— 实例化时用的是浏览器里的状态，如果它和服务端渲染时的状态不一致（比如服务端没有 localStorage），两边算出的界面不同，框架就会报 hydration mismatch，并把客户端那一版重新渲染一遍。**所以凡是依赖浏览器独有状态的界面，都要特别处理首屏**（项目里记录过这个坑，修法是用 useSyncExternalStore 的 getServerSnapshot）。

**而本节这个界面从原理上不需要水合**：它的选项是表单与链接，没有"先选中再提交"的内存状态 —— 服务端渲染出的 HTML 本身就是完整的，没有可以"对不上"的东西。

三个设计点值得单独说：

**一，信息按「会改变什么」组织，不是按参数。** 界面说的是「发送回复 → zhangsan@example.com（外部地址）」而不是「调用 send_reply」。第 19 章那条结论（减少的是心理推算，不是信息量）就落在这里。

**二，「为什么需要你确认」直接说出来。** 那一行「可逆性：发出后无法撤回」不是装饰 —— 它让用户理解这次打断的理由，而理解了才会真的看内容。

**三，四个选项而不是两个。** 「修改后同意」和「换个方式」是最常见的真实需求；只给同意/拒绝时，用户的反应通常是拒绝然后重说一遍，而那浪费了 agent 已经做好的部分。

## 进度：为什么不用百分比

第 19 章的结论是**按动作显示**，而不是按步数算百分比。代码上的形态就是一串动作描述：

```text
✓ 读取订单 A-1001
✓ 检索退款政策
✓ 整理要点
⏸ 等待确认发送给 zhangsan@example.com
```

为什么不用百分比？因为**步数在 agent 里不可预知**。第 10 章实测过静态计划在分支任务上有 0/3 的成功率 —— 计划本身都不可靠，用它来算总步数就更不可靠。百分比会因此跳来跳去，还给出虚假的精确感。

而上面那串动作具体、不会跳，信息量并不比百分比少。**如果确实需要一个粗糙的进度感**，用可预知的阶段（已找到资料 → 正在整理 → 准备发送），而不是用步数。

## 一个容易忽略的状态：卡住了

第 19 章讲过「三类必须暴露的异常」：卡住了、降级了、不确定。界面层要做的就是给它们**各自的显示**：

| 状态 | 界面显示 |
|---|---|
| **卡住了** | 「同一个动作已重试 3 次，没有进展」+ 一个「停止」按钮 |
| **降级了** | 「当前使用简化处理」—— 用户有权知道在用哪个版本 |
| **不确定** | 允许模型输出「需要确认」，而不是强制它填一个值（第 5 章实测过：不存在的事实被 5/5 编了出来） |

三行里第二行最容易被漏。它的代价是：用户以为自己拿到的是完整能力的结果，而实际上不是 —— **那会让他在错误的前提上做判断。**

## 和前面几章的关系

这一节没有新概念 —— 它把第 19 章的结论落成了代码。三处对应：

| 第 19 章的结论 | 这一节的实现 |
|---|---|
| 审批展示三样信息 | 三行 `dl`：动作与目标 / 影响范围 / 可逆性 |
| 四个响应选项 | 四个按钮，各自对应不同的下一步 |
| 进度按动作而非百分比 | 一串动作描述，没有百分比 |

**这个对应关系本身就是一条经验：设计结论和实现之间通常隔着一层「隐含的模型」。** 这里那一层是「先选中再提交」—— 拆掉它之后，实现反而变简单了（从有状态组件变成纯 server component）。


## 一个具体的实现细节：为什么用 details 而不是 state

上面那个组件里，正文的折叠用的是原生 `<details>`/`<summary>`，不是 React 的 `useState`。这个选择有三个具体好处：

| 用 `<details>` | 用 `useState` |
|---|---|
| 服务端就能渲染，首屏可见 | 要等水合才能交互 |
| 零 JS | 增加客户端 bundle |
| 不会被水合状态不一致影响 | §4.7 记录过这类坑 |

**第三条特别值得说。** 本站自己在 Playground 上踩过一次 localStorage 与首屏渲染不一致的坑（服务端没有 localStorage，客户端有）—— 那次修复方式是用 `useSyncExternalStore` 的 `getServerSnapshot`。

而 `<details>` **从原理上避开了这类问题**：折叠状态不在 React 里，也不在 localStorage 里，它在浏览器的原生行为里。**能用平台能力解决的问题，不要用状态解决** —— 这是同一类判断。

## 一个和「谁在维护」有关的取舍

最后补一个非技术的点。上面那个实现之所以能是纯 server component，前提是**四个选项各自对应一条明确的请求**。

而这个前提在一种情况下不成立：**如果审批要支持「先改几处、再一起提交」**（比如同时改收件人、正文、发送时间），那它确实需要客户端状态 —— 因为那才是真正的「先编辑再提交」。

所以取舍不是「有状态不好」，而是**先看清楚这次交互到底是「四条路选一条」还是「编辑后提交」**。前者不需要状态，后者需要。

而这个问题应该在设计阶段回答，不是实现阶段 —— 因为它的答案决定了组件的形状。第 19 章那张「四个响应选项」的表其实已经回答了它：**那四个是一组并列的动作，不是一个表单。**

## 常见坑

- **把审批做成「先选中再提交」。** 四个选项是四条不同的请求，不是一次选择 —— 想清楚这点就不需要客户端状态。
- **只显示参数不显示影响。** 用户要判断的是「这会改变什么」，不是「它调用了哪个工具」。
- **只给同意/拒绝。** 缺「修改后同意」和「换个方式」，用户会拒绝然后重说一遍，浪费已完成的部分。
- **进度用百分比。** 步数不可预知（第 10 章实测计划 0/3），百分比会跳且是虚假精度。
- **不显示降级。** 用户有权知道他在用哪个版本，否则会在错误前提上做判断。
- **不给「不确定」出口。** 第 5 章实测：不存在的事实被 5/5 编了出来 —— 要允许模型说「需要确认」。
