第 19 章讲了审批该展示什么、进度该怎么表达。那些是设计结论 —— 这一节把它们落成代码，并说清一个实现上的关键判断。

## 先把界面状态与审批状态分开

审批界面**可以不需要客户端 React state**，但这不等于“审批不需要状态”，也不等于静态按钮会自动发请求。待审批、已批准、已拒绝、执行中、结果未知等状态属于服务端的持久化工作流；界面只是读取并呈现它们。

如果每个选项都是独立提交的动作，可以用原生表单或链接；在 Next.js App Router 中，Server Component 可以渲染表单，Server Action 可作为表单 action。需要事件处理器、即时 loading、局部编辑器等交互时，再把那一小块做成 Client Component。服务端表单也必须在每个入口重新认证、授权和校验，界面是否显示按钮不是安全边界。[Next.js Server/Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)、[Forms](https://nextjs.org/docs/app/guides/forms)。

四种产品选项只是可选的交互设计，**不是所有审批都必须提供四个选项**。它们应对应清晰且不同的工作流：

```text
同意原提案      → 批准服务端冻结的原参数，再排入执行
拒绝            → 将提案标记为拒绝；是否另行重新规划由产品明确决定
修改后再审批    → 创建一份新提案并重新审批，不能沿用旧提案的批准
提出替代方案    → 把用户意见送入重新规划；新提案生成后仍需单独审批
```

“修改后同意”不能把新参数直接塞进旧审批的 `approve` 请求并照常执行。上一章规定参数、目标或权限变化会使旧批准失效；人的修改应成为新提案。类似地，收到一条“换个方式”的意见，只能证明用户提交了约束，不能证明模型已采纳；界面应展示新生成的提案，让用户核对后再批准。

以下路由是**构造出来的 API 形状示例，不是本站后端，也未实跑**：

```text
POST /api/approvals/ap_8f3c21/approve
body: {} → 批准冻结提案，进入 queued
POST /api/approvals/ap_8f3c21/reject
body: {} → 提案变为 rejected
POST /api/approvals/ap_8f3c21/proposals
body: {"params": {"to": "lisi@example.com"}} → 创建新的 pending 提案
POST /api/tasks/task_123/replan
body: {"constraint": "改用 reply 工具"} → 重新规划，产出待核对的新提案
```

审批记录中的 `frozen_params` 与其规范化摘要应由服务端保存。批准请求只携带审批记录 ID 与并发版本等必要引用，不接受客户端重发一份参数来覆盖已冻结内容。参数被修改时，服务端校验并冻结新提案、重新走审批。

**服务端处理的边界也要画清楚。** 数据库事务可以原子地完成“检查当前状态、将 pending 提案 claim/更新为 queued、写入唯一 outbox 事件”；它不能一般性地把任意外部邮件发送与本地状态更新变成同一个原子事务。worker 可能在外部接收方已执行、但本地未收到回执时崩溃；此时应进入 unknown/reconciling，按接收端幂等能力对账，不能仅凭本地审批状态宣称 exactly-once。

```text
# 伪代码：只原子化本地审批状态与 outbox 写入，不声称外部效果原子。
def approve(actor, approval_id, expected_version):
    with db.transaction():
        rec = db.select_approval_for_update(approval_id)
        if rec is None:
            return {"status": "not_found"}, 404
        authorize(actor, rec)  # 从可信会话解析 actor，并检查 tenant / 对象 / 审批权限
        if rec["status"] != "pending" or rec["version"] != expected_version:
            return {"status": "conflict"}, 409
        assert verify_frozen_params(rec["frozen_params"], rec["params_hash"])
        db.update_approval(approval_id, status="queued", version=rec["version"] + 1)
        db.insert_outbox_once(approval_id, rec["frozen_params"])
    return {"status": "queued"}, 202
```

这个骨架仍省略了数据库 API、拒绝/过期竞态、策略版本复核、worker 租约、接收端幂等与结果对账；它只说明审批确认与本地入队的事务边界。

## 返回状态要如实呈现

服务端状态与界面文案应一一对应，但具体状态名是应用契约，不是通用标准：

| 交互 | 服务端结果示例 | 界面反馈 |
|---|---|---|
| 批准原提案 | `queued` | “已提交执行”，继续显示执行中；完成后展示结果 |
| 拒绝 | `rejected` | “提案已拒绝”；是否重新规划让用户另行选择 |
| 修改参数 | 新的 `pending` 提案 | 展示新提案与变化，等待再次审批 |
| 提出替代方案 | 新的 `pending` 提案 | 展示模型生成的提案供核对；不要直接说约束已采纳 |

如果界面把所有响应都变成“按钮变灰”，用户会失去操作结果的反馈。错误、冲突、过期和未知结果也应单独呈现；网络超时不能当作动作失败或成功，需查询服务端状态。

下面的本地例子**只验证 UI 文案映射**，不模拟数据库、并发、授权、持久化或外部副作用，也不能替代集成测试：

```python
"""把示例工作流结果映射为界面文案；纯本地，不执行审批。"""


def status_message(status, proposal_id=None):
    messages = {
        "queued": "已提交执行，正在等待结果",
        "rejected": "提案已拒绝；是否重新规划由你决定",
        "conflict": "提案状态已变化，请刷新后核对",
        "expired": "提案已过期，需要生成并审批新提案",
        "unknown": "执行结果尚不确定，正在核对；请勿重复提交",
    }
    if status == "pending_new_approval":
        return "新提案 %s 已生成，请核对后再批准" % proposal_id
    return messages.get(status, "状态未知，请联系系统管理员")


if __name__ == "__main__":
    for status, proposal_id in [
        ("queued", None),
        ("rejected", None),
        ("pending_new_approval", "ap_new"),
        ("conflict", None),
        ("expired", None),
        ("unknown", None),
    ]:
        print(status, "->", status_message(status, proposal_id))
```

**先说清“水合”是什么，因为它是理解本节前端渲染边界的一个关键概念。** 在 React 中，hydration 是把事件处理器连接到服务端预渲染 HTML 的过程；Next.js 首屏会用 HTML 先显示预览，再用 RSC payload 协调组件树，并水合 Client Components。Server Component 本身不因此获得浏览器事件处理能力。[Next.js 对首屏渲染与 hydration 的说明](https://nextjs.org/docs/app/getting-started/server-and-client-components)。

如果初始客户端渲染读取 `localStorage` 等浏览器状态，而服务端无法读取同一值，初始 HTML 与客户端首次渲染可能不一致。可让两侧使用一致的初始快照，再在客户端读取浏览器状态；也可把依赖浏览器状态的交互收进 Client Component。`useSyncExternalStore` 适用于有明确订阅与 server snapshot 契约的外部 store，不能自动修复所有 hydration mismatch。

本节的示意组件没有事件处理器，也没有需要水合才能生效的客户端交互。实际审批若用原生表单/链接，可以不写客户端 React state；需要即时交互时再加 Client Component。

## 本站的组件是静态界面示意

`src/components/mdx/approval-demo.tsx` 是一个真实渲染的 Server Component，用来展示信息层级、进度和按钮外观：

<ApprovalDemo />

**它不是接入后端的审批界面。** 当前四个按钮只有 `type="button"`，没有 `action`、表单或事件处理器；点击不会发请求，也不会改变服务端状态。它没有组件专属客户端交互代码。若要让原生 HTML 表单调用服务端 mutation，可用 `<form action={serverAction}>`；服务端仍须逐请求认证、授权、校验。Next.js 文档支持 Server Action 表单与渐进增强，但这并不让当前示意按钮自动变为可用按钮。

这个示意里值得保留的是展示原则，不是按钮数量：

**一，按影响组织信息。** 示例展示“发送回复 → 收件人”“影响范围”“可逆性”，而不只显示内部工具名。这让审批人有材料可核对，但不能证明他已经理解或认真检查。

**二，说明要求确认的原因。** 给出可逆性与影响依据，让用户知道为什么暂停；敏感字段仍应遵循最小必要披露。

**三，选项由任务决定。** 同意、拒绝、编辑后重新审批或提出替代方案可以作为产品选项，但不应预设四种都适用。

## 进度：百分比需要一个可信的分母

如果任务分支、重试或工具调用会动态改变总工作量，百分比的分母就不稳定，显示“已完成 70%”可能制造虚假精度。若流程确有稳定、可解释的总步骤或阶段，百分比可以是合理摘要；应说明它代表什么，不把估计进度当作完成保证。

对于分支不定的 agent，按动作列出可观察事件通常更诚实：

```text
✓ 读取订单 A-1001
✓ 检索退款政策
✓ 整理要点
⏸ 等待确认发送给 zhangsan@example.com
```

对于分支不定的任务，按动作列出已观察到的进展与当前等待，比根据未知总步数计算精确百分比更可核对。若采用阶段进度，应让阶段定义稳定，并将阶段完成与任务成功区分。

## 异常状态要区分

可将卡住、降级和无法确认结果等情况分别呈现。下面是文案设计示例，不是通用重试阈值或行为规范：

| 状态 | 界面显示 |
|---|---|
| **无进展** | 展示已发生的重试/等待和可用的停止或人工接管操作；次数阈值由系统策略决定 |
| **降级** | 当能力、数据新鲜度或保证发生变化时，说明变化及其影响 |
| **结果未知** | 明示尚未核实，提供查询或对账路径；避免用户把超时误读为成功或失败 |

是否让模型表达不确定性，应与任务契约和应用侧验证结合；文案不能代替事实核验。

## 和前面几章的关系

这一节将第 19 章的展示原则转成了静态界面示意与服务端工作流草图：

| 第 19 章的原则 | 本节的对应内容 |
|---|---|
| 展示动作、目标和影响 | 示例用三组说明字段呈现 |
| 用户响应必须有清晰后果 | 对照批准、拒绝、新提案和重新规划的状态反馈 |
| 进度应表达可观察事实 | 示例列出已完成动作和当前等待 |

`<ApprovalDemo />` 只展示视觉信息，不实现提交、审批或执行。投产还需要服务端状态转换、身份/对象授权、并发控制、可靠入队和结果对账。

## 一个具体的实现细节：为什么用 details 而不是 state

上面那个组件里，正文的折叠用的是原生 `<details>`/`<summary>`，不是 React 的 `useState`。这个选择有三个具体好处：

| 用 `<details>` | 用 `useState` 控制折叠 |
|---|---|
| 服务端可渲染，首屏可见 | 初始状态要与预渲染结果一致 |
| 浏览器原生负责折叠交互 | 需要客户端事件处理器 |
| 不依赖 React 折叠状态 | 状态需随组件更新与恢复 |

**第三条特别值得说。** 本站自己在 Playground 上踩过一次 localStorage 与首屏渲染不一致的坑（服务端没有 localStorage，客户端有）—— 那次修复方式是用 `useSyncExternalStore` 的 `getServerSnapshot`。

`<details>` 的展开/折叠由浏览器原生处理，因此这个控件本身不需要 React state 或客户端事件处理器。这个结论只针对折叠状态；页面的其它交互仍需按各自的数据来源和渲染方式处理。

## 一个和「谁在维护」有关的取舍

最后补一个实现取舍。原生多字段表单可以完成“先编辑、再提交”，不必然要求客户端 React state；即时校验、乐观更新或复杂局部交互才可能需要客户端状态。问题应由交互需求、渐进增强要求和服务端状态契约决定，不能把“有编辑”直接等同于“必须 useState”。

## 常见坑

- **把界面没有客户端状态误当作审批没有状态。** 服务端仍需持久化状态、校验操作者、处理过期与并发请求。
- **把展示按钮误当成已接通动作。** 当前 `<ApprovalDemo />` 的按钮是静态示意，不会发请求。
- **修改后继续使用旧批准。** 参数或目标改变时创建新提案，并重新核对、审批。
- **把用户意见当成模型已采纳。** 重新规划后展示生成结果，不要只回显提交的约束。
- **只显示内部参数，不显示影响。** 提供足够信息核对动作、目标与范围，同时减少无关敏感数据。
- **总量未知仍显示精确百分比。** 先定义分母；无法定义时展示实际动作、等待或稳定阶段。
- **把未知外部结果当作失败并重放。** 先查询或对账，避免重复副作用。
