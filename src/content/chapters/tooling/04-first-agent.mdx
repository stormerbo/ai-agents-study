## 环境准备（以及为什么要隔离）

第 2 节实测过一个冲突：`langgraph 1.2.14` 要求 `langchain-core<2,>=1.4.7`，而本站环境是 `0.3.63`。所以这一步用独立 venv：

```text
python3 -m venv /tmp/lgvenv
/tmp/lgvenv/bin/pip install langgraph
# 装完：langgraph 1.2.14 + langchain-core 1.6.9（主环境仍是 0.3.63）
```

**这不是仪式感。** 它保证第 13 章那些绑在 `0.3.63` 上的实测结论仍然可复现 —— 而这正是第 2 节那张冲突表的产出。

## 最小 agent 的骨架

LangGraph 的模型是**状态图**：节点是函数，边是转移，状态在节点之间传。一个最小 agent 长这样：

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

class S(TypedDict):
    out: list

def work(state: S):
    return {"out": state["out"] + ["done"]}

g = StateGraph(S)
g.add_node("work", work)
g.add_edge(START, "work")
g.add_edge("work", END)
app = g.compile(checkpointer=InMemorySaver())      # ← 检查点在这里接上
app.invoke({"out": []}, {"configurable": {"thread_id": "t1"}})
```

把它和第 11 章那个手写循环比一下，能直接看出框架的定位：**它给的多是「状态与恢复」这一层，少的是「agent 逻辑」这一层。** 你要自己写的 `work` 函数，和手写循环里那个 `step` 函数没有区别。

## 实测：检查点防不住什么

第 11 章测过一个现象：在「工具已执行、状态未落盘」之间崩溃，恢复后副作用会重复。**那么换成带检查点的框架，它防住了吗？**

我照同样的构造测了一遍 —— 节点内先写库、再返回状态，中间注入崩溃：

```text
第 1 次执行后  库里 1 条
第 2 次崩溃：注入崩溃：副作用已发生，状态未落盘
崩溃后        库里 2 条
恢复后        库里 3 条

work 节点被执行 3 次
库里写入的 user: [u2, u2, u2]
有重复吗: ❌ 有
```

（实跑数据，2026-10-09。langgraph 1.2.14。）

**没有防住。** 而原因值得讲清楚 —— 它不是框架的缺陷，是**检查点机制的原理边界**：

**LangGraph 的检查点在节点返回之后才写。** 所以「副作用已经发生、节点还没返回」这个窗口，它覆盖不到 —— 恢复时整节点重跑，副作用因此重复。

换句话说：**它保证的是「已完成节点的状态不丢」，不保证「未完成节点的副作用不重」。** 第 11 章那条结论（幂等要自己写）在用了框架之后**仍然成立**。

## 一个我自己的测量错误（值得记下来）

第一次跑这个实验时，我写的是 `n = len(DB) + 1` —— **自增 id**。于是每次重跑写进去的都是新值，永远不会撞，结果显示「没有重复」。

**那是我的构造错了，不是框架防住了。** 第 11 章那个实验写的是**固定 id**（处理用户 u2），重跑才会撞。改成固定 id 之后，重复立刻出现。

这件事的教训和全书反复出现的那个模式一样：**当结果符合你的预期时，反而要更小心地检查测量方法。** 我第一次的结果是「没有重复」，而它看起来完全合理。

## 那框架换来了什么

既然它防不住重复副作用，那用它的理由是什么？答案是**另外三样**：

| 换来的 | 手写要自己做 |
|---|---|
| **状态的结构化管理** | 自己定义状态结构、自己序列化 |
| **跨进程恢复** | 把 checkpointer 换成数据库即可；手写要自己设计存储与恢复语义 |
| **流式与可视化** | 手写要自己接 SSE、自己画图 |

所以判断要不要用它，可以问一句：**你的 agent 需不需要跨进程恢复和多人协作运维？**

- 不需要 → 手写更清楚（第 11 章那个循环只有几十行，而且每一行你都知道为什么）
- 需要 → 框架省下的正是最难自己写好的那一层

**注意这里的措辞：不是「框架更好」或「手写更好」，是「你的需求在哪一侧」。** 这和第 13 章的结论一致 —— 那一条讲的是抽象模型，这一条讲的是具体能力。

## 一个具体的对比：同一件事，手写 vs 框架

把第 11 章那个手写循环和这一节的 LangGraph 版本放在一起，能看清框架的边界在哪：

| 你还是要自己写的 | 框架替你做的 |
|---|---|
| **agent 逻辑**（什么时候调什么工具、怎么判断结束） | **状态的结构化管理** |
| **工具的幂等**（实测过的那个窗口） | **检查点的持久化与恢复** |
| **预算闸门**（第 18 章那三层） | **状态转移的调度** |
| **执行策略与审计**（第 16 章） | **流式输出与可视化** |
| **提示词与工具定义** | 状态在节点间的传递 |

左列有五行，右列也是五行 —— **这不是巧合，而是分工的形状**：框架管「状态在图上怎么流动」，你管「每一步具体做什么、以及出错了怎么办」。

而左列那五行恰好是前面十二章的内容。**所以「学框架」不能替代「学机制」** —— 框架只覆盖了机制里的一层。这也是这本书把框架放在第 13 章而不是第 1 章的原因。

## 一个具体的数字：这个最小 agent 有多少行

上面那个可运行的 LangGraph 骨架（含状态定义、节点、边、编译、调用）大约 **15 行**；第 11 章那个手写循环的核心也在同一量级。

**行数相近，差别在「框架那 15 行里有多少是替你做掉的」。** 骨架阶段看不出差距 —— 差距出现在你要加「跨进程恢复」的时候：手写要设计存储格式与恢复语义，而框架只要把 `InMemorySaver` 换成数据库的 checkpointer。

这也解释了为什么很多人「先用框架，后来改手写」—— 他们在骨架阶段觉得框架多余，在生产阶段（第 20 章那些需求出现时）才需要它。**反过来也行，只是那条路要返工。**
## 完整可运行代码

下面这段代码就是上面那个实验：一个带检查点的 LangGraph 图，在副作用之后注入崩溃，看恢复时会不会重复。

```python
"""用真 LangGraph 验证第 11 章那个问题：框架能防住「崩溃后重复副作用」吗？

第 11 章的实测：在「工具已执行、状态未落盘」之间注入崩溃，
恢复后朴素版写入了 u1, u2, u2, u3（4 条，重复 1）。

关键：那次副作用写的是**固定 id**（处理用户 u2），所以重跑才会撞。
这一版照同样的构造重做 —— 第一版我用了自增 id，永远不会重复，
结果测出来的「没有重复」是我的构造错误（见文末说明）。

环境：langgraph 1.2.14 / langchain-core 1.6.9（独立 venv）。实跑状态：2026-10-09。
"""
import logging
from typing import TypedDict

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

DB = []
RUNS = []          # 记录每个节点被执行了几次
CRASH = {"armed": False}


class S(TypedDict):
    done: list


def work(state: S):
    """副作用：为固定用户写一条记录（固定的 id，重跑会撞）。"""
    RUNS.append("work")
    DB.append({"user": "u2", "action": "send_reply"})     # ← 固定身份，不做自增
    if CRASH["armed"]:
        CRASH["armed"] = False
        raise RuntimeError("注入崩溃：副作用已发生，状态未落盘")
    return {"done": state["done"] + ["u2"]}


def build():
    g = StateGraph(S)
    g.add_node("work", work)
    g.add_edge(START, "work")
    g.add_edge("work", END)
    return g.compile(checkpointer=InMemorySaver())


if __name__ == "__main__":
    logging.getLogger("langgraph").setLevel(logging.ERROR)
    app = build()
    cfg = {"configurable": {"thread_id": "t1"}}

    # 1) 正常跑一次
    app.invoke({"done": []}, cfg)
    print("  第 1 次执行后  库里 %d 条：%s" % (len(DB), DB))

    # 2) 同样的 thread，在副作用之后崩溃
    CRASH["armed"] = True
    try:
        app.invoke({"done": []}, cfg)
    except RuntimeError as e:
        print("  第 2 次崩溃：%s" % e)
    print("  崩溃后        库里 %d 条：%s" % (len(DB), DB))

    # 3) 恢复：重跑同一个 thread
    app.invoke({"done": []}, cfg)
    print("  恢复后        库里 %d 条：%s" % (len(DB), DB))
    print()

    users = [r["user"] for r in DB]
    dup = len(users) != len(set(users))
    print("=== 结果 ===")
    print("  work 节点被执行 %d 次" % len(RUNS))
    print("  库里写入的 user: %s" % users)
    print("  有重复吗: %s" % ("❌ 有" if dup else "✅ 没有"))
    print()
    print("=== 结论 ===")
    print("  LangGraph 的检查点**在节点返回之后**才写。")
    print("  所以「副作用已发生、节点还没返回」这个窗口它覆盖不到 ——")
    print("  恢复时整节点重跑，副作用因此重复。")
    print()
    print("  这不是框架的缺陷，是**检查点机制的原理边界**：")
    print("    它保证「已完成节点的状态不丢」，不保证「未完成节点的副作用不重」。")
    print("  第 11 章那条结论在这里仍然成立：幂等要自己写。")
```


## 一个和「学框架」有关的建议

上面那张对比表说明框架只覆盖了机制里的一层。这给出一条学习顺序上的建议：

**先理解机制，再学框架。** 理由是：框架的 API 会变，而机制不会。这一节那个最小 agent 在下一个大版本里可能写法全变，但它背后的「状态图 + 检查点」这个模型是稳定的 —— 而第 11 章那个手写循环教的正是那个模型。

反过来（先学框架再补机制）会有一个具体的代价：**你会把框架的抽象当成问题的本质。** 比如以为「节点」和「边」是 agent 的固有结构，而实际上它们只是 LangGraph 表达控制流的一种方式（第 13 章讲过的几种抽象模型之一）。

而一旦把抽象当成本质，换框架时就会觉得「什么都不会了」—— 因为学到的是 API，不是判断力。
## 常见坑

- **以为用了框架就不用写幂等。** 实测：检查点不覆盖「副作用已发生、节点未返回」这个窗口，重复照旧。
- **在主环境装框架。** 第 2 节实测过冲突；用独立 venv，保住已验证环境的可复现性。
- **用自增 id 测重复。** 那样永远不会撞 —— 我第一次就这么错了，得到假阴性。
- **把框架的价值记成「帮你写 agent 逻辑」。** 它给的多是状态与恢复那一层，agent 逻辑仍是你写的。
- **不区分「已完成节点的状态」和「未完成节点的副作用」。** 检查点保证前者，不保证后者。
- **结果符合预期就不查测量方法。** 那是假阴性最容易溜过去的时刻。
