## 最小状态图的骨架

LangGraph 用**状态图**表达工作流：节点处理状态并返回更新，边决定后续节点。下面是最小图骨架；它只展示编排结构，不包含模型决策或工具循环：

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

class S(TypedDict):
    out: list

def work(state: S):
    return {"out": state["out"] + ["done"]}

g = StateGraph(S)
g.add_node("work", work)
g.add_edge(START, "work")
g.add_edge("work", END)
app = g.compile(checkpointer=InMemorySaver())      # ← 检查点在这里接上
app.invoke({"out": []}, {"configurable": {"thread_id": "t1"}})
```

实跑状态：2026-10-21，Python 3.14.7、`langgraph==1.2.14`、`langchain-core==1.6.12`。该图离线运行，不发起模型或 provider 请求。
**先把 `thread_id` 的作用边界说清楚**。它是 checkpointer 用来分组和定位某条图状态的标识；要跨进程恢复，除了同一个 `thread_id`，还必须使用持久化 checkpointer。`InMemorySaver` 只在当前进程内存中保存状态，进程重启后数据会丢。`thread_id` 不是用户身份凭证，也不替代租户/对象授权；服务端必须把已认证用户与允许访问的任务、thread 做绑定。实际项目可以在自己的任务记录中保存 `task_id → thread_id` 映射，但应由服务端校验映射的所有权。

两个容易踩的边界：

- **`thread_id` 标识检查点所属的 thread，不会自动把每次调用的输入都追加成对话**。同一 id 下会从已有检查点继续，但本次输入、字段 reducer、图的终态与调用方式共同决定状态如何变化；不要把它当作“自动累加”的保证。下面的故障实验固定同一个 id，是为了沿同一 thread 观察失败后的节点重跑。
- **`InMemorySaver` 只在进程内**。上面接入的是内存 checkpointer，重启后检查点会丢。需要跨进程恢复时，应选用 LangGraph 支持的持久化 checkpointer，并按其部署说明配置；长期跨 thread 的用户偏好等数据属于 store/业务存储，不应混作当前 thread 的检查点状态。

把它和第 11 章那个手写循环比一下，可以看到框架表达控制流与状态更新的方式。本节 `work` 只是确定性节点函数；实际 Agent 还需要模型决策、工具协议、宿主授权、失败处理和预算等逻辑，不能从这张状态图直接推断框架已替你提供这些能力。

## 故障注入：同一 thread 再次调用可能重复副作用

第 11 章讨论过工具执行与状态落盘之间的失败窗口。这里用 LangGraph 1.2.14 做一个**同进程异常注入**：节点先向测试用列表追加固定业务键，再抛异常。**本例由调用方捕获异常后再次调用 `invoke`；这不是配置 LangGraph 的自动 retry policy。** 随后观察同一 thread 上节点是否重跑。本例不是杀进程或重启测试，没有真实数据库、网络副作用或 provider 调用；`InMemorySaver` 不支持跨进程恢复。

关键输出摘录（对应完整 stdout）：

```text
第 1 次执行后  测试列表 1 条
第 2 次 invoke 抛出：注入异常，副作用已发生、节点状态未返回
异常后        测试列表 2 条
再次 invoke 后 测试列表 3 条

work 节点被执行 3 次
测试列表中的 user: [u2, u2, u2]
有重复吗: ❌ 有
```

（2026-10-21 实跑：Python 3.14.7、langgraph 1.2.14、langchain-core 1.6.12；同进程异常后再次 invoke，节点累计执行 3 次，测试列表出现 3 条相同 user 记录。）

**这次同一 thread 的再次调用没有防住重复副作用**。官方文档说明，配置 checkpointer 后图状态在 super-step 边界保存；节点执行中途失败后再恢复或重试，受影响节点会从函数开头重新执行。本脚本实际验证的是同进程异常后由调用方再次 `invoke` 的路径；结果只支持这个固定脚本与版本，不等同于真实进程崩溃、持久化 saver、并行节点或生产外部副作用测试。

**LangGraph 的图状态检查点位于 super-step 边界，不会在普通节点函数执行到一半时保存函数局部进度**。因此本例中“副作用已发生、节点尚未完成”时失败，恢复会从该节点开始重跑，固定写入随之重复。配置 `task` 可以保存已完成 task 的结果，让恢复时跳过这部分已完成工作；但副作用成功后、task 结果持久化前仍有不确定窗口，跨数据库/外部系统的 exactly-once 也不能仅靠图检查点得到。副作用仍要用业务幂等键、事务、接收端去重或结果对账设计。

因此应把结论限定为： **图状态检查点不等于外部副作用的 exactly-once 保证**。节点异常后可能重跑；`task` 可保存完成操作的结果以缩小重做范围，但外部效果仍需业务幂等键、事务、接收端去重与对账。

## 一个我自己的测量错误（值得记下来）

第一次跑这个实验时，我写的是 `n = len(DB) + 1` —— **自增 id**。于是每次重跑写进去的都是新值，永远不会撞，结果显示「没有重复」。

**那是我的构造错了，不是框架防住了**。 第 11 章那个实验写的是**固定 id**（处理用户 u2），重跑才会撞。改成固定 id 之后，重复立刻出现。

这件事的教训和全书反复出现的那个模式一样： **当结果符合你的预期时，反而要更小心地检查测量方法**。 我第一次的结果是「没有重复」，而它看起来完全合理。

## 那框架换来了什么

既然单靠图状态检查点防不住外部副作用重放，那用它的理由是什么？框架提供的是图状态与控制流的结构化管理，并能配合 checkpointer 支持恢复与检查；实际能力取决于 saver、部署方式和调用模式：

| 换来的 | 手写要自己做 |
|---|---|
| **状态的结构化管理** | 自己定义状态结构、自己序列化 |
| **持久化恢复** | 配置持久化 checkpointer、thread 关联、访问控制与保留策略；手写要自己设计存储与恢复语义 |
| **LangGraph Graph API 提供图事件流与图可视化** | 手写要自己设计状态与事件观察；浏览器传输仍由应用实现（例如 API / SSE） |

所以判断要不要用它，可以问一句： **你的工作流是否需要图状态检查、暂停/恢复或跨进程恢复**？多人协作运维还需要服务端的身份、thread 授权和操作审计。

- 不需要 → 手写更清楚（第 11 章那个循环只有几十行，而且每一行你都知道为什么）
- 需要 → 框架省下的正是最难自己写好的那一层

**注意这里的措辞：不是「框架更好」或「手写更好」，是「你的需求在哪一侧」**。 这和第 13 章的结论一致 —— 那一条讲的是抽象模型，这一条讲的是具体能力。

## 一个具体的对比：同一件事，手写 vs 框架

把第 11 章那个手写循环和这一节的 LangGraph 版本放在一起，能看清框架的边界在哪：

| 你还是要自己写的 | 框架替你做的 |
|---|---|
| **agent 逻辑**（什么时候调什么工具、怎么判断结束） | **状态的结构化管理** |
| **工具的幂等**（实测过的那个窗口） | **检查点的持久化与恢复** |
| **预算闸门**（第 18 章那三层） | **状态转移的调度** |
| **执行策略与审计**（第 16 章） | **图事件流与可视化；浏览器传输仍由应用实现** |
| **提示词与工具定义** | 状态在节点间的传递 |

左列有五行，右列也是五行 —— **这不是巧合，而是分工的形状**：框架管「状态在图上怎么流动」，你管「每一步具体做什么、以及出错了怎么办」。

而左列那五行恰好是前面十二章的内容。 **所以「学框架」不能替代「学机制」** —— 框架只覆盖了机制里的一层。这也是这本书把框架放在第 13 章而不是第 1 章的原因。

## 完整可运行代码

下面的脚本是可复现的本地异常注入示例：它在内存列表追加记录后抛出异常，再次 invoke 同一个 thread，观察同进程重试。它不模拟进程被杀或真实外部写入。

```python
"""用真 LangGraph 验证第 11 章那个问题：同一 thread 再次 invoke 时，是否会重复副作用？

第 11 章的实测：在「工具已执行、状态未落盘」之间注入崩溃，
原章节记录朴素版写入了 u1, u2, u2, u3（4 条，重复 1）；这是历史摘要，本次脚本只验证自己的固定列表情形。

关键：那次副作用写的是**固定 id**（处理用户 u2），所以重跑才会撞。
这一版照同样的构造重做 —— 第一版我用了自增 id，永远不会重复，
结果测出来的「没有重复」是我的构造错误（见文末说明）。

历史环境记录：langgraph 1.2.14 / langchain-core 1.6.9（2026-10-09）；该旧运行没有完整依赖锁。
本节当前验证环境：langgraph 1.2.14 / langchain-core 1.6.12（2026-10-21）。
"""
import logging
from typing import TypedDict

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

DB = []
RUNS = []          # 记录每个节点被执行了几次
CRASH = {"armed": False}


class S(TypedDict):
    done: list


def work(state: S):
    """副作用：为固定用户写一条记录（固定的 id，重跑会撞）。"""
    RUNS.append("work")
    DB.append({"user": "u2", "action": "send_reply"})  # 内存列表测试替身；固定业务键，不做自增
    if CRASH["armed"]:
        CRASH["armed"] = False
        raise RuntimeError("注入异常：副作用已发生，节点状态未返回")
    return {"done": state["done"] + ["u2"]}


def build():
    g = StateGraph(S)
    g.add_node("work", work)
    g.add_edge(START, "work")
    g.add_edge("work", END)
    return g.compile(checkpointer=InMemorySaver())


if __name__ == "__main__":
    logging.getLogger("langgraph").setLevel(logging.ERROR)
    app = build()
    cfg = {"configurable": {"thread_id": "t1"}}

    # 1) 正常跑一次
    app.invoke({"done": []}, cfg)
    print("  第 1 次执行后  测试列表 %d 条：%s" % (len(DB), DB))

    # 2) 同样的 thread，在副作用之后抛出异常
    CRASH["armed"] = True
    try:
        app.invoke({"done": []}, cfg)
    except RuntimeError as e:
        print("  第 2 次 invoke 抛出异常：%s" % e)
    print("  异常后        测试列表 %d 条：%s" % (len(DB), DB))

    # 3) 调用方再次 invoke 同一个 thread
    app.invoke({"done": []}, cfg)
    print("  再次 invoke 后 测试列表 %d 条：%s" % (len(DB), DB))
    print()

    users = [r["user"] for r in DB]
    dup = len(users) != len(set(users))
    print("=== 结果 ===")
    print("  work 节点被执行 %d 次" % len(RUNS))
    print("  测试列表中的 user: %s" % users)
    print("  有重复吗: %s" % ("❌ 有" if dup else "✅ 没有"))
    print()
    print("=== 结论 ===")
    print("  普通图状态在 super-step 边界检查点；节点函数中途失败后可能从节点开头重跑。")
    print(
        "  因此副作用可能在节点再次执行时重复。"
        "task 可记录已完成操作的返回值，但不提供外部 exactly-once。"
    )
    print("  仍需使用业务幂等键、事务、接收端去重或结果对账。")
    print()
    print("  本例只验证同进程异常后由调用方再次 invoke 的路径，不验证进程崩溃与持久化恢复。")
    print("  本例中的 DB 是内存列表，不代表真实数据库或外部服务。")
```

实跑状态：2026-10-21，Python 3.14.7、`langgraph==1.2.14`、`langchain-core==1.6.12`；两个 Python 示例均离线执行，无模型/provider 调用。故障脚本复现 3 次节点执行与 3 条列表项，不代表真实数据库或进程重启行为。

上面那张对比表说明框架只覆盖了机制里的一层。这给出一条学习顺序上的建议：

**先理解机制，再学框架**是本书采用的教学顺序，不是适用于所有读者的唯一路径。API 可能随版本演进；状态、控制流、持久化和副作用边界这些概念，有助于读者把经验迁移到其他框架。节点和边是 LangGraph 表达控制流的一种方式，不是所有 Agent 都必须采用的内部结构。
## 常见坑

- **以为用了框架就不用写幂等**。 节点失败时可能重跑；本节只用同进程异常和内存列表验证这一种路径。
- **在主环境装框架**。 第 2 节实测过冲突；用独立 venv，保住已验证环境的可复现性。
- **用自增 id 测重复**。 那样永远不会撞 —— 我第一次就这么错了，得到假阴性。
- **把状态图骨架称作完整 Agent**。 本例没有模型、工具或决策循环；图只负责表达工作流状态与控制流。
- **不区分「已保存的图状态」和「未完成节点的副作用」**。 检查点不自动让外部系统与图状态处于同一事务。
- **结果符合预期就不查测量方法**。 那是假阴性最容易溜过去的时刻。
