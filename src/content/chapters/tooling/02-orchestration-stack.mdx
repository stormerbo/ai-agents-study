第 13 章讲了框架的抽象模型与选型判据。这一节补两件它没讲的：**装一个框架的真实成本**，以及**可观测性平台解决的是哪一刻的问题**。

## 先讲一件被低估的事

一个常见的流程是：选定了框架，`pip install`，然后发现环境里某个东西坏掉了。

而这件事**在装之前就能算出来**，而且只需要一行。先看一个真实例子。

## 实测：这个环境装不了 langgraph

本站环境里装着这些（第 13 章那次为了测抽象泄漏装的）：

```text
langchain_core 0.3.63
langchain      0.3.7
pydantic       2.9.2
```

现在想装 `langgraph 1.2.14`。把它的依赖声明和当前的版本放一起比：

```text
langchain-core   要求 <2,>=1.4.7      当前 0.3.63    ❌ 冲突
pydantic         要求 >=2.7.4         当前 2.9.2     ✅ 兼容
```

（实跑数据，2026-10-09。）

**`langchain-core` 冲突。** 而后果不只是「装不上」—— pip 会把它升到 1.x，于是 `langchain 0.3.7` 坏掉，而第 13 章那些绑在 `0.3.63` 上的实测结论**失去可复现性**。

这不是「框架不好」，而是**依赖是有成本的**，而那个成本在你决定用它的时候就已经发生了。

## 解法：先算，再隔离

两步，都很简单。

**第一步，装之前先算。** 把候选包声明的约束和你当前的版本放一起比一遍 —— 就是上面那张表，用 `packaging` 标准库十几行就能自动生成。**冲突的话，你在装之前就知道了。**

**第二步，用独立 venv 试。** 框架可以试，但不许污染已经验证过的环境：

```text
python3 -m venv /tmp/lgvenv
/tmp/lgvenv/bin/pip install langgraph     # 只影响这个 venv
# 主环境仍然是 langchain_core 0.3.63，第 13 章的实测仍然可复现
```

这两步对后端工程师不新鲜 —— 新鲜的是**要把它算进「选型成本」**。第 13 章的判据讲的是「框架的抽象好不好、让不让路」，这一节补的是另一半：**它和你已有的东西冲不冲突。**

## 一个具体的产出：冲突表

算完的产出应该是一张表，而且它有三个用途：**决定要不要隔离**（有冲突就必须）、**决定升级顺序**（先升谁、影响面多大）、以及**写进交付文档**（第 22 章那块「判断依据」）。

第三点容易被忽略：**「为什么这个项目用独立 venv」需要一个能被查到的理由。** 不然半年后有人会「顺手统一一下版本」，然后在某个下午把整个环境升坏。

## 可观测性平台：它解决哪一刻的问题

第 15 章讲过自己写轨迹（四个字段：步骤序号、原始参数、原始返回值、token 与耗时）。那套东西能让**你在场时**定位到一个失败发生在哪一步。

## 那四个字段到底长什么样

"四个字段"这句话不够用 —— 关键是**每一步写一条还是每个任务写一条**，以及字段具体叫什么。答案是：**每一步写一条记录，任务级的信息（模型、发布单元）在每条上都带一次**（冗余但便宜，且省掉了 join）：

```json
{
  "trace_id": "tr_7f21a9",
  "task_id": "t_7f21a9",
  "step": 4,
  "tool": "query_order",
  "params": { "order_id": "A-1001" },
  "result": [],
  "is_error": false,
  "in_tokens": 1661,
  "out_tokens": 132,
  "latency_ms": 1840,
  "release_id": "rel_2026_10_12_a"
}
```

（示例：构造数据，未实跑 —— 它是记录格式的示例。）

**四个字段与它们的对应关系：** 步骤序号是 `step`；原始参数是 `params`（**存原始对象，不要存格式化后的字符串** —— 后者会让"模型到底看到了什么"无法复原）；原始返回值是 `result`（加上 `is_error`，否则失败与"返回了空"分不开）；token 与耗时是 `in_tokens` / `out_tokens` / `latency_ms`。

**三个容易写错的点：**

- **`result` 必须按收到时的原样存。** 如果你在写轨迹之前先做了截断或美化，排查时看到的就不是模型看到的（第 15 章那个 `eta` 字段的例子就是靠"原始返回值"才定位到）。
- **`trace_id` 与 `task_id` 分开。** 一个任务可能被恢复重跑，于是有两条轨迹指向同一个任务 —— 合成一个 id 这两种情况就分不开了。
- **`release_id` 每条都带。** 它让"这次失败发生在哪个版本"变成一个可以直接过滤的字段，而不是要去别处查时间戳。

**"只写这四个字段、不写整个上下文"也是口径的一部分。** 把完整 prompt 与历史消息存进每一步，会让追踪量涨一两个数量级（第 15 节那条"失败全记、成功采样"就是为这个准备的）。

而平台补的是另外三件事 —— 每一件都对应一个「你不在场」的场景：

| 平台多给的 | 对应哪一刻 |
|---|---|
| **聚合** | 你想知道「哪些输入模式在失败」，而不是「这一次为什么失败」 |
| **留痕与共享** | 别人需要看你看到的那次轨迹 —— 值班、交接、排查协作 |
| **时间轴对比** | 这次变差是从哪个版本开始的（第 20 章的发布单元 id 用在这里） |

所以判据可以是这一句：**「出问题的时候，除了你还有谁会来看？」**

- 只有你一个人看 → 自己写轨迹就够了，平台的边际价值很低
- 有值班、有交接、有多个服务 → 平台的价值立刻出现，因为它把「你脑子里的上下文」变成了**别人能打开的东西**

这个判据的好处是它不依赖工具对比。**自己写 vs 用平台不是技术问题，是组织问题** —— 第 19 章讲人机协作时的那条思路在这里同样成立：先问「谁在什么时候需要它」，再问「用什么实现」。

## 一个容易做反的顺序

常见的错误顺序是：先选平台，再接 SDK，然后才发现「我们其实只需要把一个 id 打进日志」。

正确的顺序是**从问题往回推**：先写下「上次出事时，我需要知道什么、谁还需要知道」，再判断自己写够不够，最后才是选平台。

这个顺序的收益很具体：**它会让你发现自己可能根本不需要一个平台** —— 而第 22 章那个 capstone 就是这种情况（单文件脚本、只有作者一个人看，于是自己写轨迹就够了）。

## 一个更根本的方式：把「装之前」变成一条命令

上面那张冲突表可以自动化，而且值得自动化 —— 因为它是一个**每次引入依赖都要做**的动作。

形态是一条命令：给它一个包名，它输出冲突表。三步：

```text
1. 读候选包的元数据（Requires-Dist）
2. 读当前环境里对应包的版本
3. 用 packaging 的 specifier 逐条判断，输出冲突
```

**第三步是关键**：不要用字符串比较版本，要用 `packaging.requirements.Requirement` 的 `specifier` —— 它会正确处理 `<2,>=1.4.7` 这种区间、以及 `~=` 这类复合写法。自己写字符串比较一定会漏掉边界。

一个具体的边界：`>=1.4.7` 对 `1.4.7` 是满足的，对 `1.4.6` 不满足。而 `0.3.63` 与 `1.4.7` 的比较**不是数字大小问题** —— `0.3.63` 的主版本号更小，所以先比主版本。用字符串比较会得到「0.3.63 更大」（因为 `3` > `1`），完全反了。

## 一个和「可观测性」有关的成本判断

平台通常按 trace 条数或事件量计费 —— 而 agent 的 trace 量比普通服务大得多，因为**一次任务有几十步**（第 15 节那四个字段，每一步一条）。

所以引入平台之前值得先估一个数量级：**日调用量 × 平均步数**。如果那个数字是千万级，采样策略就不是可选项而是必需项（第 15 节讲过：失败全记、成功采样）。

而这个估算有一个附带好处：**它会让你重新审视「要不要记那么细」**。第 15 节那条「只记结构化字段，不记整个上下文」在成本上的意义就在这里 —— 记录粒度直接决定 trace 量，而 trace 量直接决定账单。
## 完整可运行代码

下面这段代码做上面第一步：给定候选包的依赖声明，逐条和你当前的版本比对，输出冲突表。

```python
"""引入依赖之前先算冲突。实跑状态：2026-10-09。"""
import importlib.metadata as md
from packaging.requirements import Requirement
from packaging.version import Version, InvalidVersion

CANDIDATE = "langgraph"


def declared_requirements(pkg):
    try:
        return [Requirement(r) for r in (md.metadata(pkg).get_all("Requires-Dist") or [])]
    except md.PackageNotFoundError:
        return None


def installed_version(name):
    try:
        return md.version(name)
    except md.PackageNotFoundError:
        return None


if __name__ == "__main__":
    cand = declared_requirements(CANDIDATE)
    if cand is None:
        print("（候选包 %s 未安装，这里假设它已下载元数据）" % CANDIDATE)
        cand = [Requirement(s) for s in ("langchain-core<2,>=1.4.7", "pydantic>=2.7.4",
                                        "xxhash>=3.5.0")]
    print("候选：%s" % CANDIDATE)
    print("当前环境（本站）：langchain_core 0.3.63 / langchain 0.3.7 / pydantic 2.9.2")
    print()
    print("  %-18s %-20s %-12s %s" % ("依赖", "它要求", "当前", "判定"))
    conflicts = 0
    # 用本站的真实版本做对照 —— 这样这个脚本在任何环境上跑结论都一样
    env = {"langchain-core": "0.3.63", "pydantic": "2.9.2", "xxhash": None}
    for r in cand:
        cur = env.get(r.name, installed_version(r.name))
        if cur is None:
            verdict = "未装（兼容）"
        else:
            try:
                ok = Version(cur) in r.specifier
            except InvalidVersion:
                ok = False
            verdict = "兼容" if ok else "❌ 冲突"
            if not ok:
                conflicts += 1
        print("  %-18s %-20s %-12s %s" % (r.name, str(r.specifier), cur or "—", verdict))
    print()
    if conflicts:
        print("结论：%d 处冲突 —— **不要直接装**，先用独立 venv 试。" % conflicts)
        print("     直接装会把冲突的包升级，可能顶掉已验证过的行为。")
    else:
        print("结论：无冲突，可以直接装。")
    print()
    print("注：版本比较必须用 packaging 的 specifier，不能比字符串 ——")
    print("   字符串比较会认为 0.3.63 > 1.4.7（因为 3 > 1），完全反了。")
```


## 一个和「框架选型」重合的判断

第 13 章给过一条：**框架不是能力**。这一节那句「依赖是有成本的」是同一条的另一面 —— 它们合起来是一个完整的选型观：

| 问题 | 在哪一章 |
|---|---|
| 框架的抽象好不好、让不让路 | 第 13 章 |
| 它和已有的东西冲不冲突 | 本节 |
| 用了它之后，哪些事还是要自己写 | 第 4 节 |

三问都答完，选型才算做完。**只答第一问是最常见的漏 —— 而它恰好是最主观的一问。** 后两问都有客观数据（冲突表、框架边界表），而它们往往能直接推翻第一问的结论。
## 常见坑

- **装之前不算依赖。** 实测：langgraph 要求 langchain-core>=1.4.7，而环境是 0.3.63 —— 装了会顶掉已验证的结论。
- **在主环境里试框架。** 用独立 venv；框架可以试，已验过的环境不该被污染。
- **把「能装上」当成「选型通过」。** 依赖冲突是选型成本的一部分。
- **为了可观测性先上平台。** 先问「除了我还有谁看」—— 只有你一个人时，自己写轨迹就够。
- **把「先算」变成拖延。** 算的目的是避免破坏，不是避免引入。
- **忘了平台真正多给的是「共享」。** 聚合、留痕、时间轴 —— 三样都指向「别人能看你看到的东西」。
