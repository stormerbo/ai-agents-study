第 13 章讲了框架的抽象模型与选型判据。这一节补两件它没讲的：**装一个框架的真实成本**，以及**可观测性平台解决的是哪一刻的问题**。

## 先讲一件被低估的事

一个常见的流程是：选定了框架，`pip install`，然后发现环境里某个东西坏掉了。

而这件事可以在真正安装前先检查。下面用一组精确版本作例子；历史安装是否按记录发生，会单独标明。

## 历史案例：这组依赖声明存在冲突

本站环境里装着这些（第 13 章那次为了测抽象泄漏装的）：

```text
langchain_core 0.3.63
langchain      0.3.7
pydantic       2.9.2
```

现在想试 `langgraph 1.2.14`。以下已装版本是 2026-10-09 的历史环境记录，原始 resolver 输出没有保存在当前工作树，本轮不能复核当时的安装过程。依赖声明则可从 PyPI 保存的精确发行版元数据核对；先把声明与当时报告的环境版本放一起比：

```text
langchain-core   要求 <2,>=1.4.7      当前 0.3.63    ❌ 冲突
pydantic         要求 >=2.7.4         当前 2.9.2     ✅ 兼容
```

依赖声明已由 PyPI 精确发行版元数据核对：[`langgraph 1.2.14`](https://pypi.org/pypi/langgraph/1.2.14/json) 要求 `langchain-core>=1.4.7,<2`；[`langchain 0.3.7`](https://pypi.org/pypi/langchain/0.3.7/json) 要求 `langchain-core>=0.3.15,<0.4`，两个区间没有交集。`pydantic 2.9.2` 满足这两个发行版各自声明的 Pydantic 范围。

**这组版本约束不兼容。** 如果单独运行 `pip install langgraph`，pip 可能为了满足新包把 `langchain-core` 换到 1.x，而让未列入本次安装目标的 `langchain 0.3.7` 留在原地并变得不兼容；pip 文档明确提醒，单独安装一个包时可能破坏其他已安装包。若把现有应用的全部直接依赖一并交给 resolver，它也可能直接报告无法同时满足。结果取决于完整命令、pip 版本和约束，不能概括成每次都会“升坏”。这次历史安装结果没有原始日志，不能独立确认。

这不是「框架不好」，而是**依赖是有成本的**，而那个成本在你决定用它的时候就已经发生了。

## 解法：先算，再隔离

两步，都很简单。

**第一步，先做完整解析的 dry run。** 用项目实际采用、能理解其依赖输入/锁文件的包管理器，在隔离环境中检查完整依赖集合；不能把任意格式的 lockfile 直接交给 pip。若项目使用 pip 和 requirements 文件，可以在临时 venv 中运行 `python -m pip install --dry-run --report /tmp/install-plan.json -r requirements.txt`，并确认文件包含完整的目标约束。pip 的 dry run 只预览给定输入在当前索引/环境条件下的解析计划，不证明运行时兼容；安装后还可运行 `python -m pip check` 检查已装包声明依赖的冲突。下方 Python 片段只是 PEP 440 的直接约束演示：`packaging` 是 PyPA 的第三方库，不是 Python 标准库；代码不处理完整传递依赖、环境 marker、extras、平台条件或 pip 升级策略，不能代替 resolver。

**第二步，用独立 venv 试。** 框架可以试，但不许污染已经验证过的环境：

```text
python3 -m venv /tmp/lgvenv
/tmp/lgvenv/bin/pip install langgraph     # 只影响这个 venv
# 主环境仍然是 langchain_core 0.3.63，第 13 章的实测仍然可复现
```

这两步对后端工程师不新鲜 —— 新鲜的是**要把它算进「选型成本」**。第 13 章的判据讲的是「框架的抽象好不好、让不让路」，这一节补的是另一半：**它和你已有的东西冲不冲突。**

## 一个具体的产出：冲突表

冲突表是风险摘要，不是自动决策。出现冲突后，可以整体升级并锁定、选择兼容版本、换包或在独立环境试验；按改动范围、复现需要和部署边界决定是否隔离。它还可以记录升级顺序、影响面和交付时的判断依据。

第三点容易被忽略：**「为什么这个项目用独立 venv」需要一个能被查到的理由。** 不然半年后有人会「顺手统一一下版本」，然后在某个下午把整个环境升坏。

## 可观测性平台：它解决哪一刻的问题

第 15 章讲过自己写轨迹（四个字段：步骤序号、原始参数、原始返回值、token 与耗时）。那套东西能让**你在场时**定位到一个失败发生在哪一步。

## 那四个字段到底长什么样

"四个字段"这句话不够用 —— 关键是**每一步写一条还是每个任务写一条**，以及字段具体叫什么。答案是：**每一步写一条记录，任务级的信息（模型、发布单元）在每条上都带一次**（冗余但便宜，且省掉了 join）：

```json
{
  "trace_id": "tr_7f21a9",
  "task_id": "t_7f21a9",
  "step": 4,
  "tool": "query_order",
  "params": { "order_id": "[REDACTED]" },
  "result_summary": { "status": "not_found" },
  "is_error": false,
  "in_tokens": 1661,
  "out_tokens": 132,
  "latency_ms": 1840,
  "release_id": "rel_2026_10_12_a"
}
```

（示例：构造数据，未实跑 —— 它是记录格式的示例。）

**这只是一个示意 schema，不是必须照抄的四字段标准。** `step` 可表示步骤；`params` 应优先保存经筛选、脱敏的结构化摘要；`result_summary` 只保留诊断所需的结果类别；`is_error` / `error_type`、token 与耗时是否记录，按排查问题选择。原始 `params` 和 `result` 可能含个人信息、凭据或业务敏感内容，不能默认原样写入 trace。若确需保存原文以支持调查或回放，应先确认用途与合法边界，并落实脱敏、访问控制、加密和保留期限。

**记录设计的三个注意点：**

- **先定义安全边界，再决定是否保存原始输入/输出。** 优先保留足以区分失败类型的摘要；若必须留原文，先脱敏并限制访问和保留时间。
- **区分运行追踪 ID 与业务任务 ID。** 若恢复或重试会产生新的运行轨迹，使用不同 ID 有助于关联到同一业务任务；ID 也不能充当授权凭证。
- **版本字段按排查需要设计。** `release_id` 可以帮助关联发布，但具体字段名称、传播方式和覆盖范围要与部署/trace 系统约定，不能假设每个平台会自动填充。

**默认不存完整 prompt 与历史消息，是数据最小化和成本控制的一部分。** 只有明确的排查需求、授权和保留策略支持时，再通过受控方式保存必要原文；把完整上下文写入每一步会增加敏感数据暴露面、存储量和检索成本。

而符合需求的平台可能提供聚合、共享和版本比较等能力；具体产品的功能、数据保留和访问控制各不相同，需要逐项核对：

| 平台多给的 | 对应哪一刻 |
|---|---|
| **聚合** | 你想知道「哪些输入模式在失败」，而不是「这一次为什么失败」 |
| **留痕与共享** | 别人需要看你看到的那次轨迹 —— 值班、交接、排查协作 |
| **时间轴对比** | 这次变差是从哪个版本开始的（第 20 章的发布单元 id 用在这里） |

所以判据可以是这一句：**「出问题的时候，除了你还有谁会来看？」**

- 只有你一个人看 → 自己写轨迹就够了，平台的边际价值很低
- 有值班、有交接、有多个服务 → 平台的价值立刻出现，因为它把「你脑子里的上下文」变成了**别人能打开的东西**

团队协作需求是一个选型维度，但还要同时检查敏感数据边界、保留期限、访问控制、集成成本、可用性和预算。先明确谁会在何时用这些数据，再验证自建方案或候选平台是否覆盖所需能力。

## 一个容易做反的顺序

常见的错误顺序是：先选平台，再接 SDK，然后才发现「我们其实只需要把一个 id 打进日志」。

正确的顺序是**从问题往回推**：先写下「上次出事时，我需要知道什么、谁还需要知道」，再判断自己写够不够，最后才是选平台。

这个顺序的收益很具体：**它会让你发现自己可能根本不需要一个平台** —— 而第 22 章那个 capstone 就是这种情况（单文件脚本、只有作者一个人看，于是自己写轨迹就够了）。

## 一个更根本的方式：把「装之前」变成一条命令

上面那张冲突表可以自动化，而且值得自动化 —— 因为它是一个**每次引入依赖都要做**的动作。

生产环境的完整检查应交给包管理器的 resolver，并对项目的完整直接依赖清单做 dry run；不能只给候选包名，因为还要解析项目已有约束、传递依赖与环境条件。下面的小脚本只是一个可离线运行的直接约束示例：

```text
1. 读候选包的元数据（Requires-Dist）
2. 读当前环境里对应包的版本
3. 用 packaging 的 specifier 逐条判断，输出冲突
```

**第三步是关键**：不要用字符串比较版本，要用 `packaging.requirements.Requirement` 的 `specifier` —— 它会正确处理 `<2,>=1.4.7` 这种区间、以及 `~=` 这类复合写法。自己写字符串比较一定会漏掉边界。

一个具体的边界：`>=1.4.7` 对 `1.4.7` 是满足的，对 `1.4.6` 不满足。按字符串排序和按版本规则排序并不总一致。例如字符串比较会把 `"1.10.0"` 排在 `"1.9.0"` 前面（字符 `1` 小于 `9`），但 PEP 440 版本顺序是 `1.10.0 > 1.9.0`。用 `packaging.version.Version` 解析版本，不要自己拆字符串。

## 一个和「可观测性」有关的成本判断

可观测性产品的计费单位因产品与套餐而异，可能涉及事件数、摄取数据量、保留期或席位等；Agent 的逐步轨迹也可能让单个任务产生多条记录。

所以引入候选方案前，先按产品真实计费单位估算事件量和字节量：**每日任务数 × 每任务事件数 × 平均每条字节数 × 保留天数**。再根据预算、诊断目标、敏感字段、保留配置和平台限额选择全量、采样、字段裁剪或分层保留；没有跨产品通用的“千万级”采样阈值。

而这个估算有一个附带好处：**它会让你重新审视「要不要记那么细」**。第 15 节那条「只记结构化字段，不记整个上下文」在成本上的意义就在这里 —— 记录粒度直接决定 trace 量，而 trace 量直接决定账单。
## 完整可运行代码

下面这段代码做上面第一步：给定候选包的依赖声明，逐条和你当前的版本比对，输出冲突表。它需要 PyPA 的 `packaging` 库；在项目 venv 中先执行 `python -m pip install packaging`，或把它加入项目依赖后再运行。

```python
"""用固定快照演示直接依赖约束；不是完整包管理器 resolver。"""
from packaging.requirements import Requirement
from packaging.version import Version

candidate_requirements = [
    "langchain-core>=1.4.7,<2",
    "pydantic>=2.7.4",
]
installed_snapshot = {
    "langchain-core": "0.3.63",
    "pydantic": "2.9.2",
}


def package_key(name):
    return name.lower().replace("_", "-")


for raw in candidate_requirements:
    requirement = Requirement(raw)
    current = installed_snapshot.get(package_key(requirement.name))
    if current is None:
        verdict = "未知：需由完整 resolver 决定"
    elif Version(current) in requirement.specifier:
        verdict = "兼容"
    else:
        verdict = "冲突"
    print("%-16s %-16s %-10s %s" % (
        requirement.name,
        str(requirement.specifier),
        current or "—",
        verdict,
    ))
```

**实跑状态**：完整示例在临时 Python 3.14.7 虚拟环境（`packaging` 26.3）中运行，输出 `langchain-core` 冲突、`pydantic` 兼容。该运行只验证固定快照下的直接约束比较，不是历史安装重放，也不是完整 dependency resolver。

## 一个和「框架选型」重合的判断

第 13 章给过一条：**框架不是能力**。这一节那句「依赖是有成本的」是同一条的另一面 —— 它们合起来是一个完整的选型观：

| 问题 | 在哪一章 |
|---|---|
| 框架的抽象好不好、让不让路 | 第 13 章 |
| 它和已有的东西冲不冲突 | 本节 |
| 用了它之后，哪些事还是要自己写 | 第 4 节 |

三问都答完，选型才算做完。**只答第一问是最常见的漏 —— 而它恰好是最主观的一问。** 后两问都有客观数据（冲突表、框架边界表），而它们往往能直接推翻第一问的结论。
## 常见坑

- **装之前不算依赖。** 实测：langgraph 要求 langchain-core>=1.4.7，而环境是 0.3.63 —— 装了会顶掉已验证的结论。
- **在主环境里试框架。** 用独立 venv；框架可以试，已验过的环境不该被污染。
- **把「能装上」当成「选型通过」。** 依赖冲突是选型成本的一部分。
- **为了可观测性先上平台。** 先问「除了我还有谁看」—— 只有你一个人时，自己写轨迹就够。
- **把「先算」变成拖延。** 算的目的是避免破坏，不是避免引入。
- **忘了平台真正多给的是「共享」。** 聚合、留痕、时间轴 —— 三样都指向「别人能看你看到的东西」。
