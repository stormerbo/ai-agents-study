「本地模型省钱」不是一个可脱离场景成立的结论。本节先明确部署约束，再讨论如何比较质量、成本和运营负担。

## 几类可能推动本地部署的约束

**第一，数据必须留在本组织控制的处理边界内。** 这不自动等于所有托管服务都不合适：不同 provider、云区域、专属部署、合同与功能的数据处理方式不同。先把边界说清楚，再核对候选服务的数据处理条款、保留策略、部署区域与日志链路；如果没有一种获批的托管配置满足要求，才把自托管/本地部署列为硬约束。比如 Azure Foundry 与 OpenAI 的企业数据说明描述的是各自产品和功能，不代表数据完全不离开组织，也不能互相外推。

**第二，必须离线运行或无法依赖可用的网络出口。** 这是可测试的部署约束：确定断网时必须支持哪些请求、模型与依赖是否已缓存、离线更新怎么交付。只有确实不能使用获批的私有网络或远程部署时，它才会排除托管方案。

**第三，需要更强的变更控制或可复现性。** 托管服务有时提供版本化 model ID 或部署版本，有时只提供会变化的标识；即使能固定标识，服务也可能弃用它，且模型标识本身不等于整条推理栈永远不变。自托管能增加对权重和运行时的控制，但仍需锁定模型文件、tokenizer、推理引擎、量化与配置，并验证升级。

**怎么判断变更是否可追溯？** 查 provider 对当前 endpoint/model ID 的文档与生命周期政策，并保存请求中的模型标识、部署/配置版本和时间。响应里的 `model` 字段不一定是底层权重或构建版本的证明；字段含义应按 provider 契约理解。固定评测集只能监测行为变化，不能识别具体模型版本。若无法取得可信的版本标识，就把它记作可复现性限制，而不要据短名称猜它是滚动别名。

**判据不是看名字长短，而是检查证据链**：能否按请求追溯 endpoint、请求 model ID、部署版本、运行配置及当时使用的评测集；缺少哪一项，就明确标为不可追溯。

**还要核对模型使用与分发的许可。** “可下载权重”不自动代表模型符合开放 AI 的定义，也不能单凭“开源”标签推定商业部署、修改或再分发均获准。OSI 的 [Open Source AI Definition](https://opensource.org/ai/open-source-ai-definition) 描述使用、研究、修改和分享的自由及开放 AI 系统需要的材料；Hugging Face 的 [Model Cards](https://huggingface.co/docs/hub/model-cards) 允许发布者登记许可证元数据，但标签本身不是对具体用途的许可结论。

选定模型版本后，逐项核对完整许可文本、acceptable-use policy、署名条件、商业使用、托管调用、权重修改与再分发条款，并检查基座模型、tokenizer 和运行依赖的许可。把模型 revision/commit、权重来源、许可证版本和审批记录一起归档；条款不清楚时标为未核实并走组织审核，不把它当作已获准的生产候选。本节给出的是工程筛查步骤，不代替法律意见。

这些是选型约束的例子，不是穷尽清单。**先判定硬约束，再比较可行方案的总成本与质量**：本地不是唯一能满足数据边界或版本控制的方案；托管也不天然更便宜。成本要把运维、并发容量、质量差异和迁移/退出成本都算进去。

## 三个真实的代价

**一、你要承担运维。** GPU/CPU 容量、模型加载、并发、监控、补丁和故障处理都要有人负责。托管服务会替你管理其服务边界内的基础设施，但你的应用、网络、配额和调用治理仍由你负责。

**二、质量和行为可能不同。** 模型家族、尺寸、量化、推理配置与任务都会影响结果；不能只凭“开源小模型”推断质量。用目标任务集比较成功率、错误类型、延迟和成本，再决定需要哪些校验、重试或人工兜底。

**三、升级责任改变了。** 托管服务要按 provider 的弃用、迁移和版本政策管理；自托管让你控制发布时机，但评测、回滚、运行时兼容与安全更新都由你承担。

第三条值得强调：**「可控」和「要管」是同一件事的两面。** 自部署买到的是控制权，付出的是一直要有人管它。

## 一个可选的轻路径：评估本地编码任务

有些场景可以把向量编码与生成式推理拆开，但这不是所有任务都能按能力清晰二分：

- embedding、分类和抽取并不天然比生成任务简单；分类/抽取可以依赖大型生成模型，也可能需要敏感上下文。
- 若 embedding 服务的输入数据必须留在本组织边界内，可比较本地模型、获批的私有托管服务及其治理条件；是否需要 GPU 取决于模型、吞吐、延迟和硬件。
- 在线持续编码时，推理成本会随请求量累积；只有在特定离线批量建索引等场景，重算频率低时才近似一次性成本。

embedding 是一个常见例子。本站曾做过以下一次离线批量实测：

```text
模型：BAAI/bge-small-zh-v1.5（512 维）
运行环境：纯 CPU
吞吐：246 块/秒
1311 块编码耗时：5.3 秒
向量矩阵占用：2.6 MiB（按 1024² 字节换算；不含索引）
```

（实跑数据，2026-10-09。sentence-transformers 3.2.1。）

**这组数字只适用于该机器、模型、批大小和语料。** 它说明这次离线批量运行无需 GPU 服务；不证明其他硬件、在线并发或其他模型也无需 GPU。索引文档更新、模型升级或数据变动时，仍可能需要重新编码。

所以一个可验证的方案是：在目标数据和负载上比较本地编码与合规托管编码，再比较端到端质量和总成本；如果生成阶段仍会接触敏感内容，也必须把那段纳入数据处理审查。

## 一个具体的判断顺序

把上面几段合成一个可以照着走的顺序：

```text
1. 写清数据与运行边界，再核对每个候选托管方案的条款、区域、状态功能和日志链路；不满足获批边界的方案淘汰
2. 写清断网时的服务要求，做离线演练；有获批且可靠的私有链路时，不必仅因数据敏感选择本地
3. 定义可复现性要求，核对版本标识、生命周期和可追溯字段；把无法证明的部分登记为风险
4. 按任务切分编码、检索、分类、生成等阶段，但每阶段都以自己的评测集验证质量
5. 对仍然可行的方案测并发吞吐、延迟、故障恢复、质量与总成本，再选型
```

这个顺序的关键在于先写出可验证的约束和淘汰条件，再算钱。自部署总成本包括人力和质量返工；而数据边界、断网能力、可追溯性也必须变成能检查的要求，不能只凭感觉判断。

## 一个反过来的提醒：不要为了「自主」而自建

最后补一个方向相反的坑。有一个诱惑是「全都自己跑，不依赖任何厂商」—— 它听起来更可控，但会增加由你维护的模型、运行时、硬件和发布环节；实际增加多少取决于现有平台与团队能力。

判据仍然是明确约束：**如果没有数据边界、离线能力或变更控制等硬需求，自托管是否值得取决于可测的质量、成本和运营能力，而不是“自主”这个标签。** 第 13 章讲框架选型时的结论在这里同样适用：**能自己写的那一层不引依赖，但不该自己写的那一层也不要硬写。**


## 一个具体的算账方式

上面说「先算成本账」，但那个账怎么算？三个变量，而且都不难估：

| 变量 | 怎么估 | 为什么它在分母上 |
|---|---|---|
| **质量差带来的返工** | 弱模型上多做的那部分错误处理与重试 | 它是隐藏成本，最容易被漏 |
| **运维人力** | GPU 维护、升级、值班 | 按人天折算，而不是按机器 |
| **机会成本** | 自建期间没法做的功能 | 最难估，但常常最大 |

第二行值得展开：**自部署账单里也要计入运维工时。** 机器费用相对容易列出；值班、升级和故障处理的工时则取决于团队的运行方式，常被预算遗漏。

所以一个实用的判据是：**如果自建需要「有人一直盯着」，那它的真实成本是那个人力成本，而不是机器成本。** 而人力的价格通常远高于机器。

## 一个反过来的检查：本地模型什么时候反而更难

最后补一个方向相反的坑。本地模型在**演示环境**里通常很顺，而在生产里会暴露三个额外的复杂度：

**一、并发下的容量。** 单请求测试不能代表目标并发；显存/内存会受模型权重、KV cache、上下文长度、批处理与推理引擎影响。用生产形态的并发压测确定排队和超时策略，不把“10 个请求”当通用阈值。

**二、模型的加载与常驻。** 冷启动时间取决于模型、硬件、缓存和服务方式；测量冷启动与空闲回收，再确定预热、保活或按需加载。

**三、多版本的共存。** 若要新旧版本并行做灰度或回滚，资源会增加，但不一定简单翻倍；看权重是否共享、量化、并发分配与服务架构，实际压测后再预留容量。

三个都和「单机跑通」无关，而它们都在「上线」那一刻出现。这也是为什么第 20 章把版本化与灰度放在部署章里 —— 本地模型的升级同样是发布。
## 完整可运行代码

下面这段代码量本地 embedding 的吞吐与占用 —— 它是判断「本地够不够用」最直接的一组数字。

```python
"""本地 embedding 的吞吐与占用 —— 判断「本地够不够用」。实跑状态：2026-10-09。"""
import time

MODEL = "BAAI/bge-small-zh-v1.5"

if __name__ == "__main__":
    from sentence_transformers import SentenceTransformer
    t0 = time.time()
    m = SentenceTransformer(MODEL)
    print("模型：%s" % MODEL)
    print("加载耗时：%.1fs（首次含下载；之后走本地缓存）" % (time.time() - t0))
    print("向量维度：%d" % m.get_sentence_embedding_dimension())
    print()
    for n in (200, 1000, 5000):
        texts = ["第 %d 段测试文本，讲的是工具调用、结构化输出与检索。" % i for i in range(n)]
        t = time.time()
        v = m.encode(
            texts,
            batch_size=64,
            show_progress_bar=False,
            normalize_embeddings=True,
        )
        dt = time.time() - t
        print("  %5d 段：%6.2fs（%5.0f 段/秒）  向量占用 %5.1f MB"
              % (n, dt, n / dt, v.nbytes / 1024 / 1024))
    print()
    print("读法：")
    print("  · 这次测量使用纯 CPU；其他模型、负载和硬件需要重新评估")
    print("  · 新增/更新文档或更换模型时，可能需要重新编码")
    print("  · 按这次吞吐线性外推，万级批量约几十秒；不含模型加载与更新")
    print()
    print("按自己的数据边界与工作负载，比较本地运行和获批托管方案。")
```


## 一个具体的场景：什么情况下这条轻路径不成立

上面那条「评估本地编码」的路径有一个前提：数据流允许拆分，而且本地方案通过目标任务的质量、延迟和容量评测。

而在有些场景里切不开：

- **任务本身是一体的**（比如「读一份文档并从中抽取结构化字段」）—— 抽取也可能需要推理，而且整段处理都会受到敏感数据边界约束
- **数据敏感的部分在生成型任务里** —— 必须把生成阶段也纳入同一数据边界审查；只有不存在获批托管方案时才需要整体自托管
- **延迟要求很紧** —— 本地和托管方案都可能排队；按目标并发压测，再比较可满足 SLO 的方案与容量成本

所以这条路径的准确表述是：**只有在数据流允许拆分、且目标任务评测证明本地模型满足质量和延迟要求时，才考虑把编码阶段本地化。** 切不开时，应比较整个流程可接受的本地、私有托管或其他方案。

这个区分很重要，因为它避免了一种常见的误判：把一个原本可以轻量评估的需求，直接判成「必须自建推理服务」。先问「能不能切」，再问「有哪些满足数据边界的方案」，最后测算质量、延迟和全生命周期成本。
## 常见坑

- **把「省钱」当主要理由。** 本地总成本要计入计算资源、人力、评测、更新和故障恢复。
- **把敏感数据等同于必须自托管。** 先定义边界，再逐项核验托管产品、地区、合同、功能和日志。
- **假定编码任务简单、无需 GPU 或只发生一次。** 用目标负载测质量、并发、延迟和更新频率。
- **只根据模型大小判断质量。** 用自己的代表性数据评测，关注失败类型和兜底。
- **把「可控」和「要管」分开看。** 自部署增加权重与运行时控制，也增加运维责任。
- **把接口中的模型标识当成构建版本证明。** 保存 provider 约定的字段，并明确仍然无法追溯的部分。
- **不做吞吐实测就开始选模型。** 本地够不够用是一个可量的问题，不是一个感觉。
