「本地模型省钱」是一个流传很广的说法，但它是**三个理由里最弱的一个**。这一节把它拆开。

## 三个必须本地的理由

**第一，数据不能出机器。** 这是唯一「花钱也解决不了」的理由。如果数据里有人信息、有合规约束、或者只是业务上不能给第三方 —— 那托管模型直接出局，成本比较没有意义。

**第二，离线或网络不可靠。** 生产环境未必有稳定的出口。这一条在演示环境里看不出来，但它会在某个客户的内网里突然变成硬约束。

**第三，要固定版本。** 第 20 章讲过托管模型有两种形态：给固定版本号的（能锁），和只给滚动别名的（锁不住）。**后者意味着「厂商什么时候更新，你说了不算」** —— 而对一个已经验证过的系统，那是一个真实的风险。

三个理由里，前两个和成本无关。**所以正确的判断顺序是：先问有没有前两个** —— 有，就本地，成本账不用算了；没有，再算成本，而那时托管通常赢。

## 三个真实的代价

**一、你要承担运维。** GPU、显存、模型加载、并发、以及「半夜 OOM 了谁去看」。托管模型把这些全包了。

**二、质量可能下降。** 开源小模型在复杂推理上通常不如前沿模型。**而这个差距会以「返工」的形式回来** —— 第 4 章那条「错误要说明原因」、第 5 章那条「重试策略」，在弱模型上都要更用力地做。

**三、升级不自由了。** 这是反过来的那一面：托管模型你不能控制它更新，而自部署你得自己承担升级 —— 包括评测、回滚、以及新版本的兼容性。

第三条值得强调：**「可控」和「要管」是同一件事的两面。** 自部署买到的是控制权，付出的是一直要有人管它。

## 一个被低估的轻路径：本地只做「编码型」任务

很多「数据不能出机器」的需求，其实不需要自建推理服务。因为**任务分两类**：

- **生成型**：写文案、做推理、调工具 —— 这类用前沿模型，质量差距明显
- **编码型**：embedding、分类、抽取 —— 这类用本地小模型，质量差距小，而且**不需要 GPU**

第二类里最典型的是 embedding。本站实测（第 1 节那组数据的另一面）：

```text
模型：BAAI/bge-small-zh-v1.5（512 维）
运行环境：纯 CPU
吞吐：246 块/秒
1311 块编码耗时：5.3 秒
向量占用：2.6 MB
```

（实跑数据，2026-10-09。sentence-transformers 3.2.1。）

**这几个数字的意义是：「本地」的成本在这个量级上几乎可以忽略。** 没有 GPU、没有模型服务、没有并发问题 —— 而且它是**一次性**的（建完索引就不用再编）。

所以一条实用的路径是：**生成型任务继续用托管模型，编码型任务换成本地小模型。** 这个切分能覆盖「数据敏感」需求的一大部分，而它比自建推理服务的成本低一个数量级。

## 一个具体的判断顺序

把上面几段合成一个可以照着走的顺序：

```text
1. 数据能不能出机器？        不能 → 必须本地，跳到第 4 步
2. 网络稳不稳？              不稳 → 必须本地
3. 能不能锁住模型版本？      锁不住且有风险 → 倾向本地
4. 任务是不是「编码型」？    是 → 本地小模型就够（无 GPU、一次性成本）
5. 以上都不是 → 算成本账，而托管通常赢
```

这个顺序的关键在于**它不先算钱**。因为钱是最容易算错的（自部署的真实成本包括人力和质量返工），而前三个理由都是定性的、明确的。

## 一个反过来的提醒：不要为了「自主」而自建

最后补一个方向相反的坑。有一个诱惑是「全都自己跑，不依赖任何厂商」—— 它听起来更可控，但代价是**你要维护的组件数量翻倍**，而其中大部分和你的业务无关。

判据仍然是那三个理由：**如果前两个理由不成立，那自建买到的主要是「心理上的自主」，付出的却是真实的运维负担。** 第 13 章讲框架选型时的结论在这里同样适用：**能自己写的那一层不引依赖，但不该自己写的那一层也不要硬写。**


## 一个具体的算账方式

上面说「先算成本账」，但那个账怎么算？三个变量，而且都不难估：

| 变量 | 怎么估 | 为什么它在分母上 |
|---|---|---|
| **质量差带来的返工** | 弱模型上多做的那部分错误处理与重试 | 它是隐藏成本，最容易被漏 |
| **运维人力** | GPU 维护、升级、值班 | 按人天折算，而不是按机器 |
| **机会成本** | 自建期间没法做的功能 | 最难估，但常常最大 |

第二行值得展开：**自部署的成本里，人力通常比机器贵。** 一台机器的钱是确定的；而「半夜 OOM 要有人起来看」的成本取决于你的团队规模 —— 而它不会出现在任何一份预算表里。

所以一个实用的判据是：**如果自建需要「有人一直盯着」，那它的真实成本是那个人力成本，而不是机器成本。** 而人力的价格通常远高于机器。

## 一个反过来的检查：本地模型什么时候反而更难

最后补一个方向相反的坑。本地模型在**演示环境**里通常很顺，而在生产里会暴露三个额外的复杂度：

**一、并发下的显存。** 单请求测试时显存够，并发 10 个就不够了 —— 而那时你要处理排队与超时。

**二、模型的加载与常驻。** 冷启动几秒到几十秒，而用户不会等；于是你要写预热与保活逻辑。

**三、多版本的共存。** 升级模型时你要能同时跑新旧两版做对比 —— 那意味着显存翻倍。

三个都和「单机跑通」无关，而它们都在「上线」那一刻出现。这也是为什么第 20 章把版本化与灰度放在部署章里 —— 本地模型的升级同样是发布。
## 完整可运行代码

下面这段代码量本地 embedding 的吞吐与占用 —— 它是判断「本地够不够用」最直接的一组数字。

```python
"""本地 embedding 的吞吐与占用 —— 判断「本地够不够用」。实跑状态：2026-10-09。"""
import time

MODEL = "BAAI/bge-small-zh-v1.5"

if __name__ == "__main__":
    from sentence_transformers import SentenceTransformer
    t0 = time.time()
    m = SentenceTransformer(MODEL)
    print("模型：%s" % MODEL)
    print("加载耗时：%.1fs（首次含下载；之后走本地缓存）" % (time.time() - t0))
    print("向量维度：%d" % m.get_sentence_embedding_dimension())
    print()
    for n in (200, 1000, 5000):
        texts = ["第 %d 段测试文本，讲的是工具调用、结构化输出与检索。" % i for i in range(n)]
        t = time.time()
        v = m.encode(texts, batch_size=64, show_progress_bar=False, normalize_embeddings=True)
        dt = time.time() - t
        print("  %5d 段：%6.2fs（%5.0f 段/秒）  向量占用 %5.1f MB"
              % (n, dt, n / dt, v.nbytes / 1024 / 1024))
    print()
    print("读法：")
    print("  · 这个吞吐是**纯 CPU** 上的 —— 编码型任务不需要 GPU")
    print("  · 它是**一次性**成本：建完索引就不用再编")
    print("  · 万级语料在这个速度下是几秒到几十秒的量级")
    print()
    print("所以「数据不能出机器」这个需求，往往不需要自建推理服务 ——")
    print("把编码型任务换成本地小模型，就能覆盖它的很大一部分。")
```


## 一个具体的场景：什么情况下这条轻路径不成立

上面那条「编码型任务换本地小模型」听起来很好用，但它有一个前提：**你要能把任务切成两类。**

而在有些场景里切不开：

- **任务本身是一体的**（比如「读一份文档并从中抽取结构化字段」）—— 抽取是编码型，但理解和判断是生成型，两者在同一个调用里
- **数据敏感的部分在生成型任务里** —— 那就只能整体本地，或者整体不出机器
- **延迟要求很紧** —— 本地小模型虽然吞吐高，但在并发下仍要排队（上一节那三个生产复杂度）

所以这条路径的准确表述是：**当任务可以被切成「编码」和「生成」两段时，把编码那段本地化。** 切不开的时候，它就退化回「整体本地或整体托管」那个更重的选择。

这个区分很重要，因为它避免了一种常见的误判：把一个原本可以做轻量化处理的需求，直接判成「必须自建推理服务」。而后者意味着 GPU、运维和人力 —— 代价高出一个数量级。换句话说，先问「能不能切」，再问「要不要自建」，这个顺序能省下大部分不必要的投入。
## 常见坑

- **把「省钱」当主要理由。** 它是最弱的一个；前两个理由（数据不能出机器、网络不可靠）与成本无关。
- **为了数据安全就自建推理服务。** 先看任务是不是「编码型」—— 那类用本地小模型就够，无 GPU、一次性成本。
- **忘了质量下降会以返工形式回来。** 弱模型需要更用力的错误处理与重试设计。
- **把「可控」和「要管」分开看。** 自部署买到控制权，付出的是一直要有人维护。
- **为了「自主」自建。** 前两个理由不成立时，自建主要买到心理上的自主。
- **不做吞吐实测就开始选模型。** 本地够不够用是一个可量的问题，不是一个感觉。
