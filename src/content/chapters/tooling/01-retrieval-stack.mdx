第 6 章讲了检索的机制。这一节讲**要装什么** —— 以及一个更前置的问题：**要不要装。**

## 一条检索链路有五段

把「检索」这个词拆开，它其实是五段流水线，每一段有自己的工具选择：

| 段 | 做什么 | 要装什么 |
|---|---|---|
| **切分** | 把文档切成可检索的块 | 常常不需要工具 —— 按结构切往往比按长度切好（第 6 章） |
| **编码** | 把文本变成向量 | embedding 模型（本地小模型或 API）。embedding 指的是"文本映射成向量"这件事本身，详见下节 |
| **索引** | 让召回能规模化 | 向量库 —— **这一段的必要性取决于规模** |
| **召回** | 找出候选 | 同一套索引，或暴力检索 |
| **重排** | 从候选里挑出真正相关的 | 交叉编码器或模型重排（第 6 章实测过它的天花板） |

**注意第三段的措辞：「取决于规模」。** 这一节的核心就是把那个「取决于」量成一个数字。

## 先把第二段说清楚：编码到底在做什么

五段里只有"编码"是**必须选一个模型**的（下面会讲为什么），而它也是最不容易自己写的一段。所以先用四句话把它讲穿：

**一、embedding 指的是"把一段文本映射成固定长度的一串数字"（一个向量）。** 这串数字是模型算出来的，它的性质是：**语义相近的文本，映射出的向量方向也相近。** 所以检索就变成了"找方向最接近的那几条" —— 不需要关键词完全匹配。这也是为什么它能搜到"取消订单"和"退单"这类换词的句子。

**二、判断"方向相近"用的是余弦相似度（cosine）。** 它算的是两个向量的夹角，不是长度。而如果你在编码时要求**归一化**（`normalize_embeddings=True`，把每个向量缩成长度 1），那么**点积就等于余弦** —— 于是"检索"退化成一次矩阵乘法：

```python
best = int(np.argmax(V @ q))     # V 是 N×512 的已归一化矩阵，q 是归一化的查询向量
```

**这就是前面那句"一行矩阵乘法顶得上一套向量库"的由来。** 归一化是它的前提：不归一化的话，点积会被向量长度污染，长文档会莫名其妙地排前面。

**三、维度和质量、成本的关系不单调。** 维度不是越高越准：它取决于模型训练时的选择（本站用的 `bge-small-zh-v1.5` 是 512 维）。**你不能自己"调"维度** —— 换维度等于换模型。而更高的维度意味着更大的向量文件与更慢的暴力检索（内存是 `N × 维度 × 4 字节`，浮点 32 位）。

**四、交叉编码器（cross-encoder）和 embedding 不是一类东西。** embedding 是"双塔"：文档和查询**各自独立**编码，然后比向量 —— 所以文档可以提前算好、建索引，但两者之间没有交互。交叉编码器是**把查询和文档拼在一起送进模型**，直接输出一个相关性分数 —— 更准，但**没法预先建索引**：每个候选都要现算一次。所以它只能用在"重排"那一段（候选通常几十到几百条），不能用来做全库召回。这就是第 6 章那条天花板结论的机制来源。

**一次最小调用长这样**（可以直接跑）：

```python
"""编码两句话并比较相似度 —— 20 行理解 embedding 在做什么。

依赖：pip install sentence-transformers（首次运行会下载模型）。
实跑状态：2026-10-12。
"""
from sentence_transformers import SentenceTransformer

m = SentenceTransformer("BAAI/bge-small-zh-v1.5")
pairs = [
    ("我把订单退了", "帮我取消这笔订单"),
    ("我把订单退了", "今天天气不错"),
    ("这段代码会重复执行副作用", "重试时同一个动作被执行了两次"),
    ("这段代码会重复执行副作用", "数据库连接池配了 8 个连接"),
]
texts = [t for p in pairs for t in p]
V = m.encode(texts, normalize_embeddings=True)      # ← 归一化：点积即 cosine
for i, (a, b) in enumerate(pairs):
    cos = float((V[2 * i] * V[2 * i + 1]).sum())    # 已归一化，点积就是 cosine
    print("  cos=%.3f  %s  ↔  %s" % (cos, a, b))
```

跑出来是这样（同一份代码的输出）：

```text
cos=0.805  我把订单退了  ↔  帮我取消这笔订单
cos=0.369  我把订单退了  ↔  今天天气不错
cos=0.662  这段代码会重复执行副作用  ↔  重试时同一个动作被执行了两次
cos=0.425  这段代码会重复执行副作用  ↔  数据库连接池配了 8 个连接
```

（实跑数据，2026-10-12。`bge-small-zh-v1.5`，512 维，纯 CPU。）

**这四行把上面那条性质变成了可验证的：** 语义相近的两对（0.805、0.662）明显高于不相关的两对（0.369、0.425）。**而"多少算高"没有通用阈值** —— 它是相对的，只能在同一批数据内部比大小。所以第 6 章那套"用你自己的数据评测检索"不是可选项。

**"近似最近邻"（approximate nearest neighbor，ANN）指的是索引用的那类算法。** 它和暴力检索的区别是：暴力要比较全部 N 条（精确，但线性增长），ANN 只访问其中一部分（不保证 100% 找回最近的那条，但增长慢得多）。第 18 节那个交叉点就是这么来的 —— **向量库不是"更快"，而是"增长更慢"。**

## 一个被问错的问题

「哪个向量库好」是一个常见的问法，但它是个**错问题**。理由是：向量库解决的核心问题只有一个 —— **数据量大到暴力检索扛不住时，仍然能快速召回**。如果数据量没到那个点，向量库带来的只有成本（依赖、运维、以及每次调用自己的开销）。

所以正确的问法是：**「我的 N 有多大？」** 而这个问题可以量。

## 实测：交叉点在哪

我用本站的真实语料跑了一遍。语料是这 112 节正文切成 1311 块（每块 300 字符），用本地模型编码成 512 维向量：

```text
语料：1311 块（每块 300 字符，来自本站 112 节）
本地编码 5.3s（246 块/秒），维度 512，向量共 2.6 MB

方式                  建索引(ms)       查询中位(ms)
numpy 暴力             0（无索引）           0.02
chromadb                476               0.83
```

（实跑数据，2026-10-09。sentence-transformers 3.2.1 + chromadb 0.5.18。）

**numpy 暴力比向量库快 40 倍** —— 0.02 毫秒对 0.83 毫秒。而它的实现是一行：

```python
# 全部「检索」就是这么一句：N 个向量各和查询做点积，取最大的那个
best = int(np.argmax(V @ q))
```

这不是说向量库不好 —— 而是说**在这个规模上它没必要**。那 0.83 毫秒里大头是 chromadb 自己的调用开销（参数校验、客户端跳转、结果组装），不是索引慢。

## 放大之后，交叉点出现在 1 万到 5 万之间

1311 块说明不了交叉点在哪。我用合成向量放大到 20 万，找到它：

```text
N               numpy(ms)   chromadb(ms)       内存(MB)
10000                0.83           1.50         19.5
50000                4.58           1.73         97.7
200000              17.23         （跳过）        390.6
```

（实跑数据，2026-10-09。）

**交叉点在 1 万到 5 万之间**：1 万时 numpy 还快（0.83 对 1.50），5 万时向量库反超（1.73 对 4.58）。

这条曲线还给出另一个数字：**numpy 的查询耗时随 N 线性增长**（10k→0.83ms、50k→4.58ms、200k→17.23ms，正好 5 倍和 21 倍）。而向量库走近似索引，增长慢得多 —— 那才是它真正的价值：**不是更快，是增长得更慢。**

还有一列别忽略：**内存**。20 万条 float32 向量占 390 MB，而且**全在 RAM 里**。如果语料到千万级，光向量本身就装不下 —— 那时向量库的价值又多一条：它有自己的存储与分片策略。

## 那五段里，其余几段怎么选

**切分常常不需要工具。** 第 6 章实测过：按固定长度切对表格和代码特别有害，而按结构切（标题、段落、代码块）通常更好 —— 那就自己写几十行。引入一个「文档加载器」库，往往带来的是它对格式的**假设**，而不是能力。

**编码是唯一必须做选择的**（上面已经讲过：模型不是你能自己实现的东西）。选它的判据不是"哪个更准"，而是三条：**语料规模与重建频率**（决定本地够不够用）、**语料语言与长度**（决定要不要多语言或长文本模型）、以及**数据能不能出机器**（决定能不能用 API）。第 3 节给这三个判据配上实测数字。

**重排要看数据量。** 第 6 章实测过一个天花板：正确答案不在候选集里时，重排救不回来。所以先量召回，再加重排。

这三段的共同点是：**它们的必要性来自你的数据，不是来自工具的能力。** 而向量库那一段最容易被当成「必须的」—— 这一节的实验就是给那件事一个数字。


## 一个具体的判断：五段里哪几段真的需要工具

上面那张五段表容易让人以为每段都要选一个库。实际上**只有一段是必须选的**，其余四段常常自己写更好。逐个说：

| 段 | 自己写要多少 | 引入库的代价 |
|---|---|---|
| 切分 | 几十行（按标题/段落切） | 库对文档格式有自己的假设，那些假设会限制你 |
| 编码 | **必须选**（模型不是你能写的） | —— |
| 索引 | 一行矩阵乘法（小规模） | 依赖 + 运维 + 每次调用的固定开销 |
| 召回 | 同上 | 同上 |
| 重排 | 接一个模型，或自己写规则 | 要等召回量够大才有意义（第 6 章的天花板） |

**唯一真正的「必须选一个」是编码那一段** —— 因为模型不是一个你能自己实现的东西。其余四段都是「可以自己写，也可以引入库」，而判断依据是**它的必要性来自你的数据还是来自工具的能力**。

这个区分很实用：它把「工具地图」从一份清单变成了一个判断流程 —— 先问这一段解决的是不是我真实存在的问题，再问要不要用库。

## 一段真实的经历

我写这一节时先做的是「装一个向量库然后测它」。跑出来 chromadb 比 numpy 慢 40 倍，我一度以为是自己用错了。

然后我把 N 放大到 20 万，才看清那不是用错 —— **是两个东西在解决不同规模的问题**。小规模时向量库的固定开销占主导，大规模时它的近似索引才开始发挥。

**如果我只跑 1311 块那一档，会得出「向量库没用」这个过头的结论；如果只跑 20 万那一档，会得出「向量库必须上」。两个结论都是错的** —— 而它们都来自只看了一个点。这也是本节要给出**交叉点**而不只是给出两组数字的原因。
## 完整可运行代码

下面这段代码跑的就是上面两张表：用本站语料量真实规模，再用合成向量放大找交叉点。

```python
"""向量库要不要上？量出交叉点。

问题不是「哪个向量库好」，而是**「什么时候需要向量库」**。

两段实验：
  一、用本站真实语料（1311 块）—— 看真实规模下暴力检索够不够
  二、用合成向量放大到 10 万 / 100 万 —— 找交叉点在哪

环境：sentence-transformers 3.2.1（BAAI/bge-small-zh-v1.5，512 维）+ chromadb 0.5.18。
实跑状态：2026-10-09。
"""
import glob, os, re, time
import numpy as np

CHUNK = 300
DIM = 512


def load_corpus():
    docs = []
    for p in sorted(glob.glob("src/content/chapters/*/*.mdx")):
        t = open(p, encoding="utf-8").read()
        t = re.sub(r"^---[\s\S]*?---", "", t)
        t = re.sub(r"```[\s\S]*?```", "", t)
        t = re.sub(r"<Mermaid[\s\S]*?/>", "", t)
        t = re.sub(r"\s+", " ", t).strip()
        ch = p.split("/")[2] + "/" + os.path.basename(p)[:-4]
        for i in range(0, len(t), CHUNK):
            if len(t[i:i + CHUNK]) > 80:
                docs.append({"id": "%s#%d" % (ch, i // CHUNK), "text": t[i:i + CHUNK]})
    return docs


def bench(fn, n=5):
    ts = []
    for _ in range(n):
        t0 = time.perf_counter(); fn(); ts.append((time.perf_counter() - t0) * 1000)
    return sorted(ts)[len(ts) // 2]


def chroma_query_time(V, ids, q, n=3):
    import chromadb
    c = chromadb.EphemeralClient()
    try: c.delete_collection("bench")
    except Exception: pass
    col = c.create_collection("bench", metadata={"hnsw:space": "cosine"})
    t0 = time.time()
    step = 5000
    for i in range(0, len(ids), step):
        col.add(ids=ids[i:i + step], embeddings=[list(map(float, v)) for v in V[i:i + step]])
    build = (time.time() - t0) * 1000
    t = bench(lambda: col.query(query_embeddings=[list(map(float, q))], n_results=5), n=n)
    return build, t


if __name__ == "__main__":
    docs = load_corpus()
    print("=== 一、真实语料 ===")
    print("  语料：%d 块（每块 %d 字符，来自本站 112 节）" % (len(docs), CHUNK))
    from sentence_transformers import SentenceTransformer
    m = SentenceTransformer("BAAI/bge-small-zh-v1.5")
    t0 = time.time()
    V = m.encode([d["text"] for d in docs], batch_size=64, show_progress_bar=False,
                 normalize_embeddings=True)
    enc = time.time() - t0
    q = m.encode(["崩溃之后恢复，副作用会不会重复"], normalize_embeddings=True)[0]
    print("  本地编码 %.1fs（%.0f 块/秒），维度 %d，向量共 %.1f MB"
          % (enc, len(docs) / enc, V.shape[1], V.nbytes / 1024 / 1024))
    ids = [d["id"] for d in docs]
    qa = bench(lambda: np.argmax(V @ q))
    build, qb = chroma_query_time(V, ids, q)
    print()
    print("  %-14s %12s %14s" % ("方式", "建索引(ms)", "查询中位(ms)"))
    print("  %-14s %12s %14.2f" % ("numpy 暴力", "0（无索引）", qa))
    print("  %-14s %12.0f %14.2f" % ("chromadb", build, qb))
    print()
    print("  → 这个规模下，暴力的查询是 %.2f 毫秒，而它只有一行代码。" % qa)
    print("    （注意 chromadb 那 0.9ms 大头是它自己的调用开销，不是索引不行。）")
    print()

    print("=== 二、放大到 1 万 / 5 万 / 20 万（合成向量）===")
    rng = np.random.default_rng(7)
    print("  %-10s %14s %14s %12s" % ("N", "numpy(ms)", "chromadb(ms)", "内存(MB)"))
    for N in (10000, 50000, 200000):
        Vs = rng.random((N, DIM), dtype=np.float32)
        Vs /= np.linalg.norm(Vs, axis=1, keepdims=True)
        qs = rng.random(DIM).astype(np.float32)
        qs /= np.linalg.norm(qs)
        ta = bench(lambda: np.argmax(Vs @ qs), n=3)
        t0 = time.time()
        ids_s = ["c%d" % i for i in range(N)]
        tb = float('nan') if N > 50000 else chroma_query_time(Vs, ids_s, qs, n=2)[1]
        print("  %-10d %14.2f %14s %12.1f" % (N, ta, ("%.2f" % tb) if tb == tb else "（跳过）", Vs.nbytes / 1024 / 1024))
    print()
    print("=== 怎么读 ===")
    print("  numpy 暴力 = 一次矩阵乘法（N×512 点积）。BLAS 会把它编译得很紧，")
    print("  所以它在 N 小的时候快得离谱 —— 而**零依赖、零运维、结果精确**。")
    print("  向量库的价值不在「更快」，在**「N 大到暴力扛不住时仍然可用」**，")
    print("  以及过滤、更新、持久化这些暴力实现要自己写的东西。")
```


## 一个可以带走的判据

如果只记一句关于「要不要上向量库」的，记这个：

**先估 N，再问「除了召回我还需要什么」。**

第一半给出量级判断（1 万以内暴力就够，5 万以上考虑索引），第二半给出剩下的那部分 —— 因为到了交叉区，真正决定选型的往往不是速度，而是**过滤、增量更新、持久化、分片**这四件事。

而它们的共同点是：**都是自己写会痛苦、但只有到一定规模才需要的东西。** 这也解释了为什么「向量库」这个品类存在 —— 它卖的不是算法（近似最近邻的算法是公开的），而是**把这四件事做好的工程**。

理解这一点之后，选型问题就变清楚了：**不是选「哪个库最快」，是选「谁把那四件事做得最合你的场景」。** 而速度，在交叉区之后，各家差别不大 —— 因为大家都用的是同一族近似最近邻算法。
## 常见坑

- **问「哪个向量库好」而不是「我的 N 有多大」。** 前者没有答案，后者可以量。
- **给几千条的语料上向量库。** 实测 1311 块时暴力检索 0.02ms，比重型方案快 40 倍。
- **忽略内存这一列。** 20 万条 512 维 float32 就是 390MB，全在 RAM；千万级装不下。
- **以为向量库的价值是「更快」。** 是「增长更慢」—— 暴力是线性的，索引是近似的。
- **给检索链路每段都引入一个库。** 切分和重排常常自己写更清楚，也能避免库带来的格式假设。
- **先加重排再量召回。** 重排救不回候选集里没有的答案（第 6 章的天花板结论）。
