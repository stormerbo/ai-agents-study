第 6 章讲了检索的机制。这一节讲**要装什么** —— 以及一个更前置的问题：**要不要装。** 下文以向量/语义检索作为主线；纯词法检索（例如 BM25）不需要 embedding 模型，混合检索则可以组合词法与稠密召回。

## 一条检索链路有五段

把「检索」这个词拆开，它其实是五段流水线，每一段有自己的工具选择：

| 段 | 做什么 | 要装什么 |
|---|---|---|
| **切分** | 把文档切成可检索的块 | 常常不需要工具 —— 按结构切往往比按长度切好（第 6 章） |
| **编码** | （可选）把文本变成稠密向量 | 只有采用稠密向量检索时，才需要选择 embedding 模型（本地或托管）；词法检索不需要 |
| **索引** | 让召回能规模化 | 向量库 —— **这一段的必要性取决于规模** |
| **召回** | 找出候选 | 同一套索引，或暴力检索 |
| **重排** | 从候选里挑出真正相关的 | 交叉编码器或模型重排（第 6 章实测过它的天花板） |

**注意第三段的措辞：「取决于规模」。** 这一节的核心就是把那个「取决于」量成一个数字。

## 如果选择稠密向量检索：编码到底在做什么

只有在采用稠密向量检索时，才需要选择 embedding 模型；BM25 等词法检索可以直接基于词项与倒排索引检索。embedding 指的是"文本映射成向量"这件事本身，下面讲清向量方案的机制与代价：

**一、embedding 指的是"把一段文本映射成固定长度的一串数字"（一个向量）。** 这串数字是模型算出来的，它的性质是：**语义相近的文本，映射出的向量方向也相近。** 所以检索就变成了"找方向最接近的那几条" —— 不需要关键词完全匹配。这也是为什么它能搜到"取消订单"和"退单"这类换词的句子。

**二、判断"方向相近"用的是余弦相似度（cosine）。** 它算的是两个向量的夹角，不是长度。而如果你在编码时要求**归一化**（`normalize_embeddings=True`，把每个向量缩成长度 1），那么**点积就等于余弦** —— 于是"检索"退化成一次矩阵乘法：

```python
best = int(np.argmax(V @ q))     # V 是 N×512 的已归一化矩阵，q 是归一化的查询向量
```

**这就是前面那句"一行矩阵乘法顶得上一套向量库"的由来。** 归一化是它的前提：不归一化的话，点积会被向量长度污染，长文档会莫名其妙地排前面。

**三、维度和质量、成本的关系不单调。** 维度不是越高越准：它取决于模型与 API 的能力（本站用的 `bge-small-zh-v1.5` 输出 512 维；OpenAI `text-embedding-3` 系列可通过 `dimensions` 请求较短向量）。是否可配置要查具体模型/endpoint，不能把一种模型的限制推广给所有模型。更改模型或输出维度后，查询与文档向量必须保持兼容，通常还要重算并重建索引；评估质量变化后再决定。float32 向量矩阵本身的单位为 MiB（按 1024² 字节换算），估算式是 `N × 维度 × 4 / 1024²`；该值不含索引、元数据和进程开销。

**四、交叉编码器（cross-encoder）和 embedding 不是一类东西。** embedding 是"双塔"：文档和查询**各自独立**编码，然后比向量 —— 所以文档可以提前算好、建索引，但两者之间没有交互。交叉编码器把查询和候选文档一起送进模型，输出相关性分数；查询相关的 cross-encoder 分数不能像文档 embedding 一样提前独立缓存。大语料通常先用词法或向量检索缩小候选集，再用 cross-encoder 重排；但小语料可以直接对全库候选做 cross-encoder 打分。是否改善相关性、可接受的候选数和延迟都需要按任务测量。

**一次最小调用长这样**（可以直接跑）：

```python
"""编码两句话并比较相似度 —— 20 行理解 embedding 在做什么。

依赖：pip install sentence-transformers（首次运行会下载模型）。
实跑状态：2026-10-12。
"""
from sentence_transformers import SentenceTransformer

m = SentenceTransformer("BAAI/bge-small-zh-v1.5")
pairs = [
    ("我把订单退了", "帮我取消这笔订单"),
    ("我把订单退了", "今天天气不错"),
    ("这段代码会重复执行副作用", "重试时同一个动作被执行了两次"),
    ("这段代码会重复执行副作用", "数据库连接池配了 8 个连接"),
]
texts = [t for p in pairs for t in p]
V = m.encode(texts, normalize_embeddings=True)      # ← 归一化：点积即 cosine
for i, (a, b) in enumerate(pairs):
    cos = float((V[2 * i] * V[2 * i + 1]).sum())    # 已归一化，点积就是 cosine
    print("  cos=%.3f  %s  ↔  %s" % (cos, a, b))
```

跑出来是这样（同一份代码的输出）：

```text
cos=0.805  我把订单退了  ↔  帮我取消这笔订单
cos=0.369  我把订单退了  ↔  今天天气不错
cos=0.662  这段代码会重复执行副作用  ↔  重试时同一个动作被执行了两次
cos=0.425  这段代码会重复执行副作用  ↔  数据库连接池配了 8 个连接
```

（实跑数据，2026-10-12。`bge-small-zh-v1.5`，512 维，纯 CPU。）

**这四行把上面那条性质变成了可验证的：** 语义相近的两对（0.805、0.662）明显高于不相关的两对（0.369、0.425）。**而"多少算高"没有通用阈值** —— 它是相对的，只能在同一批数据内部比大小。所以第 6 章那套"用你自己的数据评测检索"不是可选项。

**"近似最近邻"（approximate nearest neighbor，ANN）指的是一类索引/搜索方法。** 暴力检索会计算全部 N 条的分数，通常随 N 线性增长且在选定距离度量下精确；ANN 通过索引减少常见查询要访问的候选，但会在召回率、延迟、内存和构建成本之间取舍。具体扩展行为取决于索引算法、数据分布、参数与硬件，不能由“用了向量库”直接保证。

## 一个被问错的问题

「哪个向量库好」是一个常见的问法，但它是个**错问题**。向量库可以提供 ANN 召回，也可能提供持久化、元数据过滤、增量更新、分片和运维接口；具体能力与代价因产品而异。即使暴力召回够快，这些其他需求也可能使向量存储有价值；反过来，是否需要 ANN 仍要按延迟、召回质量、内存与构建成本实测。

所以正确的问法是：**「我的 N 有多大？」** 而这个问题可以量。

## 实测：怎样重新测出自己的交叉点

这只是 2026-10-09 时的语料快照：当时本站 112 节正文切成 1311 块（每块 300 字符），再用本地模型编码成 512 维向量。当前仓库的 MDX 数量不同，重跑会得到不同语料和结果；下列历史结果不能由现在的脚本直接复现。

```text

chromadb                476               0.83
```

（历史实测，2026-10-09。sentence-transformers 3.2.1 + chromadb 0.5.18；单机 CPU、当时的默认 HNSW 参数与客户端调用路径。历史逐次请求和环境快照是否齐全以原实验记录为准。）

**这组历史数据不能直接支持“numpy 快 40 倍”的结论。** 配套代码让 NumPy 只取 top-1，而 Chroma 返回 top-5；两边做的不是同一项查询。历史逐次延迟和当时的测量脚本没有归档，不能事后校正这些摘要。下面的可运行示例会把两边都设成 top-1，各先预热一次，再用 11 次查询的中位数作方法演示；它能复测比较方法，不能复现旧表格。

```python
# 全部「检索」就是这么一句：N 个向量各和查询做点积，取最大的那个
best = int(np.argmax(V @ q))
```

这不是说向量库不好。0.83 毫秒是这次本机 `EphemeralClient` 查询路径的历史摘要，包含客户端库与索引查询等路径；没有 profiling 数据，不能判断哪一部分占主导，也不能推断网络部署的时延。

## 历史摘要里出现了排序反转，但还不能叫交叉点

1311 块说明不了这台机器上的性能交叉点。我曾用合成向量测试 1 万、5 万和 20 万条；这只留下了特定环境的历史查询耗时摘要：

```text
N               numpy(ms)   chromadb(ms)       内存(MiB)
10000                0.83           1.50         19.5
50000                4.58           1.73         97.7
200000              17.23         （跳过）        390.6
```

（实跑数据，2026-10-09。）

**历史摘要显示**：这次报告的 1 万条结果是 numpy 较快（0.83 对 1.50ms），5 万条则是 Chroma 较快（4.58 对 1.73ms）。但随文代码在两种规模下都让 NumPy 返回 top-1、Chroma 返回 top-5；1 万条的 NumPy 延迟取 3 次中位数，Chroma 只取 2 次中的较大值。原始逐次测量没有归档，所以既不能把这组数据称作同任务的性能交叉，也不能判断排序反转是否稳定。数据还是合成随机向量，不评估语义召回质量或 ANN 召回率。**把它当作需要用等价查询、相同统计口径重新测量的历史线索。**

这条曲线还给出另一个观察：本次 numpy 查询耗时随 N 增加（10k→0.83ms、50k→4.58ms、200k→17.23ms）；这些单机测量不是复杂度证明或延迟 SLA。ANN 的查询和构建表现需在自己的数据分布、召回目标、索引参数和硬件上测量。

还有一列别忽略：**内存**。20 万条 512 维 float32 向量本身占 390.6 MiB（按 `N × 维度 × 4 / 1024²` 计算），未计索引、元数据和进程开销。向量存储系统对持久化、内存映射、过滤与分片的支持各不相同；超出 RAM 时要核对具体系统能否满足存储和扩展要求，不能假设任意向量库都会自动分片。

## 那五段里，其余几段怎么选

**切分常常不需要工具。** 第 6 章实测过：按固定长度切对表格和代码特别有害，而按结构切（标题、段落、代码块）通常更好 —— 那就自己写几十行。引入一个「文档加载器」库，往往带来的是它对格式的**假设**，而不是能力。

**如果选择稠密向量检索，就要为 embedding 方案做选择。** 可比较本地与托管模型的质量、语料规模与重建频率、语料语言和长度、数据边界，以及维护模型和索引的成本。若只用 BM25 等词法检索，则不需要 embedding 模型。第 3 节讨论向量方案的选择因素。

**重排要看数据量。** 第 6 章实测过一个天花板：正确答案不在候选集里时，重排救不回来。所以先量召回，再加重排。

这三段的共同点是：**它们的必要性来自你的数据，不是来自工具的能力。** 而向量库那一段最容易被当成「必须的」—— 这一节的实验就是给那件事一个数字。


## 一个具体的判断：五段里哪几段真的需要工具

上面那张五段表容易让人以为每段都要选一个库。实际取决于选用的检索方式：词法检索可以不做向量编码；使用稠密向量时才需要 embedding 模型；索引、召回、重排则按功能和规模选择实现。逐个说：

| 段 | 自己写要多少 | 引入库的代价 |
|---|---|---|
| 切分 | 几十行（按标题/段落切） | 库对文档格式有自己的假设，那些假设会限制你 |
| 编码 | 不使用稠密检索时可以省略 | 采用稠密检索时需选择模型/服务 |
| 索引/存储 | 小样本可把向量矩阵常驻内存，不建 ANN 索引 | 依赖、运维和存储开销 |
| 召回 | 精确暴力搜索可用矩阵乘法；也可用词法检索或 ANN | 实现与运维成本，按质量/延迟/过滤需求评估 |
| 重排 | 接一个模型，或自己写规则 | 要等召回量够大才有意义（第 6 章的天花板） |

**只有选用稠密检索时，编码才需要选择模型或服务。** 词法检索、静态数据集的直接查询等路径不需要 embedding。分词、切分、过滤、召回和重排也可以按场景选自写代码或库；判断依据是**你的目标数据与运维需求是否真的需要这项能力**。

这个区分很实用：它把「工具地图」从一份清单变成了一个判断流程 —— 先问这一段解决的是不是我真实存在的问题，再问要不要用库。

## 一段真实的经历

我写这一节时先做的是「装一个向量库然后测它」。历史摘要里，Chroma 的查询延迟高于 NumPy；重新审查配套代码后发现，两边返回的结果数量不同，所以不能把差值解释成同一查询下的性能差异。

后来我把 N 放大到 20 万，Chroma 那一档因资源开销跳过了；而且回头检查发现，之前比较时 NumPy 返回 top-1、Chroma 返回 top-5。因此这些记录不能证明是两个工具在不同规模下的性能交叉，也不能据此断言大规模时 ANN 一定更快。

**只看 1311 块的一档，容易过度推广“向量库没用”；只看 20 万块的一档，因为没有 Chroma 对照，也无法证明“向量库必须上”。** 要得到可用的交叉点，至少要统一查询的 top-k、重复次数、计时边界，再在目标数据、召回要求和硬件上测量。
## 完整可运行代码

下面的代码可以重测当前仓库语料和合成向量规模。它不复现 2026-10-09 的历史输出；Chroma 与 NumPy 都按 top-1、预热一次后 11 次查询的中位数比较。正式选型还应加入召回质量验证和目标部署环境。

```python
"""向量库要不要上？量出交叉点。

问题不是「哪个向量库好」，而是**「在我的负载下，向量库提供的能力值不值得它的成本」**。

两段测量：
  一、用本站真实语料（1311 块）—— 看真实规模下暴力检索够不够
  二、用合成向量放大到 1 万 / 5 万 / 20 万 —— 观察本机查询延迟；20 万条跳过 Chroma 对照

注意：脚本会读取运行时的当前仓库 MDX，不固定 2026-10-09 的 112 节历史语料；重跑可以复测方法，但不会自动重建表格对应的数据集或复现旧数字。

环境：sentence-transformers 3.2.1（BAAI/bge-small-zh-v1.5，512 维）+ chromadb 0.5.18。
实跑状态：2026-10-09。
"""
import glob, os, re, time
import numpy as np

CHUNK = 300
DIM = 512


def load_corpus():
    docs = []
    for p in sorted(glob.glob("src/content/chapters/*/*.mdx")):
        t = open(p, encoding="utf-8").read()
        t = re.sub(r"^---[\s\S]*?---", "", t)
        t = re.sub(r"```[\s\S]*?```", "", t)
        t = re.sub(r"<Mermaid[\s\S]*?/>", "", t)
        t = re.sub(r"\s+", " ", t).strip()
        ch = p.split("/")[2] + "/" + os.path.basename(p)[:-4]
        for i in range(0, len(t), CHUNK):
            if len(t[i:i + CHUNK]) > 80:
                docs.append({"id": "%s#%d" % (ch, i // CHUNK), "text": t[i:i + CHUNK]})
    return docs


def bench(fn, n=11):
    fn()  # 预热一次，不计入结果
    ts = []
    for _ in range(n):
        t0 = time.perf_counter(); fn(); ts.append((time.perf_counter() - t0) * 1000)
    # 使用奇数次测量，排序后取中位数。
    return sorted(ts)[len(ts) // 2]


def chroma_query_time(V, ids, q, n=11):
    import chromadb
    c = chromadb.EphemeralClient()
    try: c.delete_collection("bench")
    except Exception: pass
    t0 = time.time()
    col = c.create_collection("bench", metadata={"hnsw:space": "cosine"})
    step = 5000
    for i in range(0, len(ids), step):
        batch_ids = ids[i:i + step]
        batch_vectors = [list(map(float, v)) for v in V[i:i + step]]
        col.add(ids=batch_ids, embeddings=batch_vectors)
    build = (time.time() - t0) * 1000

    def query_top1():
        query = [list(map(float, q))]
        return col.query(query_embeddings=query, n_results=1)

    t = bench(query_top1, n=n)
    return build, t


if __name__ == "__main__":
    docs = load_corpus()
    print("=== 一、真实语料 ===")
    print("  语料：%d 块（每块 %d 字符；读取当前仓库 MDX，包含章节数以文件为准）" % (len(docs), CHUNK))
    from sentence_transformers import SentenceTransformer
    m = SentenceTransformer("BAAI/bge-small-zh-v1.5")
    print("  模型设备：%s" % m.device)
    m.encode(["warm-up"], normalize_embeddings=True, show_progress_bar=False)
    t0 = time.time()
    V = m.encode([d["text"] for d in docs], batch_size=64, show_progress_bar=False,
                 normalize_embeddings=True)
    enc = time.time() - t0
    q = m.encode(["崩溃之后恢复，副作用会不会重复"], normalize_embeddings=True)[0]
    print("  本地编码 %.1fs（%.0f 块/秒），维度 %d，向量共 %.1f MiB"
          % (enc, len(docs) / enc, V.shape[1], V.nbytes / 1024 / 1024))
    ids = [d["id"] for d in docs]
    qa = bench(lambda: np.argmax(V @ q), n=11)
    build, qb = chroma_query_time(V, ids, q)
    print()
    print("  %-14s %12s %14s" % ("方式", "建集合+索引(ms)", "查询中位(ms)"))
    print("  %-14s %12s %14.2f" % ("numpy 暴力", "0（无索引）", qa))
    print("  %-14s %12.0f %14.2f" % ("chromadb", build, qb))
    print()
    print("  → 这个规模下，暴力 top-1 查询是 %.2f 毫秒，而它只有一行代码。" % qa)
```

## 一个可以带走的判据

如果只记一句关于「要不要上向量库」的，记这个：

**先估 N，再问「除了召回我还需要什么」。**

第一半只提供待测假设：这次单机测量的查询耗时在 1 万与 5 万条之间交叉，不能当成通用切换点。第二半提醒你检查**过滤、增量更新、持久化和分片**是否是实际需求，以及候选系统是否提供这些能力。

而它们的共同点是：这些能力各自有实现与运维成本，但是否需要它们取决于数据量、更新模式、过滤条件和可用性要求。不同向量库对持久化、过滤、分片和容量管理的支持不同，逐项查候选产品文档。

理解这一点之后，选型问题就变清楚了：**不是选「哪个库最快」，是选「谁把你确实需要的能力做得符合目标负载」。** 在自己的硬件和数据集上同时测召回质量、过滤、更新、持久化、延迟、吞吐和资源，不要由算法家族推断不同产品的速度相近。
## 常见坑

- **问「哪个向量库好」而不是「我的 N 有多大」。** 前者没有答案，后者可以量。
- **把不等价的历史摘要当成性能结论。** 1311 条摘要和合成规模表里的 NumPy top-1 / Chroma top-5 不同，逐次测量也未归档；不能据此断言 40 倍优势或通用交叉点。用同一 top-k 和统计口径，在目标负载上重测。
- **忽略向量内存估算与其他开销。** 20 万条 512 维 float32 向量本身是 390.6 MiB（不含索引和进程开销）；实际内存与存储要求按候选系统测量。
- **以为向量库必然更快或复杂度必然更优。** ANN 与暴力检索有不同的召回、延迟、构建和内存取舍，需要在目标负载上测量。
- **给检索链路每段都引入一个库。** 切分和重排常常自己写更清楚，也能避免库带来的格式假设。
- **先加重排再量召回。** 重排救不回候选集里没有的答案（第 6 章的天花板结论）。
