前面几节讲怎么测分数。这一节讲一个更具体的问题：**当分数变了，是哪个改动引起的？**

最直觉的答案是「一次只改一样，看分数动不动」。这个方法叫**消融（ablation）**，
但它有一个很常见的失败模式 —— 我实测了一次，结果比预想的有意思。

## 一、实测：单变量消融会低估

我准备了一个有明确组件的提示词，和一个有 8 条可机器校验约束的任务（生成 15 条测试用例）。
然后逐个去掉组件，每个条件跑 5 次，记录**约束合规得分（满分 8）**：

```text
条件                每次得分      均值    相对完整提示词    输出 token 均值
完整提示词          8 8 8 8 8     8.0       —                2404
去掉角色定义        8 8 8 8 8     8.0      +0.0              2582
去掉格式要求        8 8 8 8 8     8.0      +0.0              2872
两者都去掉          8 8 3 8 8     7.0      -1.0              2781
```

**满分 8 是哪 8 条？** 原文就是这样，取自本次实测的判分函数 `score()` —— 任务原文是「为『订单退款』接口生成 15 条用例，每行 `TC-两位序号 | 输入 | 预期 | 优先级 P0/P1/P2`」：

1. 恰好 15 行
2. 编号 TC-01 到 TC-15 连续
3. 无表头（行首不是「用例 / 编号 / 序号 / |」）
4. P0 恰好 3 条
5. P1 恰好 5 条
6. P2 恰好 7 条
7. 每一行都含「金额」二字
8. 不含「测试」二字**且没有被 max_tokens 截断**（`stop_reason == "end_turn"`）

注意第 8 条把两个条件绑在一起：**被截断的输出看起来像格式违规，其实是测量故障。** 这是本项目撞过三次的坑（第 2 节也记了一条）。

先看最反直觉的一行：**去掉角色定义（那句「你是测试工程师」），分数一点没动。**
（这部分也和评测集饱和有关，上一节讨论过。）

去掉格式要求（那句「严格按格式逐行输出，不要解释」）也**没有影响正确率**。

但**两个一起去掉**，分数掉到 7.0 —— 而且掉分的那一次明细是 `8 8 3 8 8`，
也就是某一次没达标。

**这就是单变量消融的陷阱：**

> 两个组件各自都是「可以去掉」的，因为它们**互相冗余**。
> 只去掉一个时，另一个还在兜底；两个都去掉，兜底没了才暴露出来。

如果你只做单变量消融，你会得出「这两个组件都没用」的结论，然后把它们都删掉。
而实际后果是分数会掉 —— 只是这个后果在你删第二个的时候才出现。

## 二、第二个发现：去掉约束，输出反而更长

看最后一列。完整提示词的输出 token 均值是 **2404**；去掉格式要求后是 **2872**，
去掉两个之后是 **2781**。

**都是变长的。** 这违反直觉 —— 你可能会以为「要求越多，模型说得越多」。

实际机制是：**约束是在收窄输出空间。** 那句「恰好 15 行，不要表头、不要总结」
不只是格式要求，它同时**禁止了模型加前言与后记**。去掉它之后，模型会把
「下面是 15 条测试用例」「希望对你有帮助」这类内容也写出来。

这个发现有两个实际用途：

**一、约束不只是为了好解析，它也省钱。** 一次任务多 400 个输出 token，
在长任务上会累积成可观的成本。这也是第 18 章（成本与延迟）里那条
「输出预算也是预算」的具体例子。

**二、评估提示词改动时，要把成本一起看。** 如果一次改动让正确率 +1pp 但输出 token +20%，
那不是免费的改进。

## 三、正确的消融设计

知道陷阱之后，设计就有章法了。四条：

**一、单变量是起点，组合是重点。** 保留单变量（它便宜且能发现强依赖），
但**必须**加上「去掉一半」「去掉全部」这两组。至少要覆盖：每个组件单独去掉、
以及**全去掉**（建立下界）。

**二、预先声明你要看哪个指标。** 上面那次消融里，正确率变化很小，
但**输出 token 变了 19%**。如果我事先只盯正确率，就会错过真正的影响。
所以消融前先定好主要指标，同时把所有能自动量的指标都记下来。

**三、重复多次，看分布不看单次。** 上面「两者都去掉」是 `8 8 3 8 8` ——
**五次里只有一次不合格**。如果你只跑一次恰好抽到 8，就会得出「完全没影响」的结论。
这是消融实验里最常见的假阴性。

**四、别把「没有影响」当成「没有价值」。** 角色定义在这组指标上没影响，
但它可能在别的指标上有效（比如语气、拒答率）。
**消融只回答「在当前指标上有没有影响」这个窄问题。**

### 什么算「一个组件」

消融的第一步是切组件，而切分的判据只有一条：**去掉它时，提示词在语义上仍然完整。** 按这个标准：

- **算一个组件**：角色定义、格式要求、示例（few-shot）、输出字段清单、禁止项 —— 去掉之后任务还成立，只是约束少了。
- **不算一个组件**：任务本身（「为退款接口生成 15 条用例」）。去掉它任务就不存在了，谈不上消融。

如果两个组件必须一起改才有意义（比如「输出 JSON」必须配「字段清单」），它们就该合成一个组件 —— 否则你测的是两个互相依赖的半成品，结论解释不清。

## 四、消融回答不了的那一半问题

消融能回答「这个组件在当前评测集上有没有用」，但它**回答不了三个更实际的问题**。
知道它回答不了什么，比会用这个方法更重要。

**一、回答不了「在真实数据上有没有用」。** 评测集是你挑出来的分布。
一个组件可能在这 15 条用例上毫无影响，却在线上那批长尾输入上是决定性的。
上面「角色定义没影响」的结论，严格来说只是「在这批题上没影响」。
想缩小这个缺口，办法是**让评测集持续吸收线上失败案例**（第 3 节讲过），
而不是指望消融本身给出普适结论。

**二、回答不了「两个组件合起来有没有协同」。** 上面那次消融恰好是**冗余**（互为兜底），
但组件之间也可能是**互补**的 —— 两个都需要，去掉任一个分数都掉；
或者可能是**拮抗**的 —— 两个都在时反而不如只有一个。
这三种关系的区分，只能靠**全子集**消融（就是上面代码里那个 `combinations` 循环），
单变量方法在原理上就区分不出来。

从结果表读关系，是这么读的（第一行来自本次实测，后两行为构造示例，未实跑）：

| 对比 | 全保留 | 只去掉 X | 只去掉 Y | 都去掉 | 关系 |
|---|---|---|---|---|---|
| 角色 × 格式 | 8.0 | 8.0 | 8.0 | 7.0 | **冗余**：各自都能被对方兜住，同时去掉才暴露 |
| 角色 × 示例 | 8.0 | 5.0 | 6.0 | 2.0 | **互补**：去掉任一个都掉分，一起去掉掉更多 |
| 角色 × 格式 | 8.0 | 5.0 | 5.0 | 6.0 | **拮抗**：同时在场反而不如只留一个 |

读法只有一句：**比较「都去掉」和「只去掉一个」之间的距离。** 距离为零 → 冗余；都掉且「都去掉」掉更多 → 互补；都掉但「都去掉」反而回升 → 拮抗。

**三、回答不了「改动是否值得」。** 消融给出的是「有没有影响」，
而工程决策要的是「影响值不值这个代价」。一个组件让正确率 +0.5pp 但让延迟 +800ms，
消融只能说前者存在，判断取舍要靠人来定。
这也是第 20 章（部署）里那条「每个改动都要能说清它买到了什么」的由来。

还有一个常见的混淆值得单独点出来：**消融不是 A/B 测试**。
消融改的是**系统本身**（去掉一个组件），A/B 测的是**不同用户看到不同版本**。
消融在同一个环境里做，所以能控制变量；A/B 在真实流量里做，所以能测出
评测集里没有的长尾。两者互补：**先用消融在离线把候选砍到两三个，再用 A/B 在线上定夺。**
直接上 A/B 的问题是成本高、周期长，而且如果候选有十个，你不可能全测。

## 五、代码：一个最小消融框架

```python
from itertools import combinations
from statistics import mean


def ablate(components, run_fn, metric_fn, repeats=5):
    """对组件集合做组合消融。

    components: {"角色": "...", "格式": "..."}
    run_fn(sys_prompt) -> 模型输出
    metric_fn(output) -> 分数（0 到满分）
    """
    names = list(components)
    results = []
    # 从「全部保留」到「一个不留」，覆盖每个子集
    for size in range(len(names), -1, -1):
        for keep in combinations(names, size):
            sys_prompt = chr(10).join(components[k] for k in keep)
            scores = [metric_fn(run_fn(sys_prompt)) for _ in range(repeats)]
            results.append({
                "keep": keep,
                "mean": mean(scores),
                "min": min(scores),
                "scores": scores,
            })
    # 按保留组件数排序，先看全保留与全去掉这两个端点
    results.sort(key=lambda r: -len(r["keep"]))
    return results


def marginal_effect(results, component):
    """某个组件在「其他组件都在」与「其他组件都不在」两种语境下的边际效应。"""
    with_it, without_it = [], []
    for r in results:
        others = [k for k in r["keep"] if k != component]
        # 只比较同样「其他组件集合」的两组，这是配对比较的思想
        (with_it if component in r["keep"] else without_it).append(r["mean"])
    return (mean(with_it) if with_it else 0) - (mean(without_it) if without_it else 0)
```

上面框架要能跑，缺的是一个真的 `metric_fn`。下面这份用的就是那 8 条约束 —— **它可以直接复制去用**（正则判前 3 条与另外几条，实际就是完整 8 条）：

```python
import re

def metric_fn(txt, stop_reason="end_turn"):
    """返回 0-8 的合规分。用的是**分级分数**，不是 0/1（理由见下面的报错）。"""
    lines = [l.strip() for l in txt.split(chr(10)) if l.strip()]
    nums = [int(m.group(1)) for m in (re.match(r"TC-(\d+)", l) for l in lines) if m]
    p0 = sum(1 for l in lines if re.search(r"P0\s*$", l))
    p1 = sum(1 for l in lines if re.search(r"P1\s*$", l))
    p2 = sum(1 for l in lines if re.search(r"P2\s*$", l))
    checks = [
        len(lines) == 15,
        nums == list(range(1, 16)),
        not re.search(r"^\s*(用例|编号|序号|\|)", txt, re.M),
        p0 == 3,
        p1 == 5,
        p2 == 7,
        all("金额" in l for l in lines) and len(lines) > 0,
        all("测试" not in l for l in lines) and stop_reason == "end_turn",
    ]
    return sum(checks)
```

**最小自检**（不用 API，直接喂两段文本）：把 15 行合规文本喂进去应得 8 分，把少了表头、P0 数量不对的文本喂进去分数要下降。跑一次就知道自己的判据有没有写反 —— **判据本身也要有测试**。

本次修复中实跑这段自检（2026-10-12，实跑数据）：合规文本 8 分、带表头且 P0 数量不对的文本 2 分、合规但被 max_tokens 截断的文本 7 分。

这段代码有三个设计点：

**一、遍历全部子集，而不是只做「去一个」。** 2 的 n 次方在 n 小时完全可接受（3 个组件 8 组），
超过 5 个组件才需要退化成抽样。

**二、同时记 `mean` 与 `min`。** 上面 `8 8 3 8 8` 那组的均值是 7.0，看起来很轻微，
但最小值 3 说明**有 20% 的概率严重不合格**。生产上你关心的是尾部的失败，不是均值。

**三、`marginal_effect` 用「同语境配对」。** 先说它算的是什么：**边际效应 = 在相同的其余组件下，有它和没它的平均分差。** 把「其他组件都在」的结果和「其他组件都不在」的结果直接比，会把交互效应算进去；正确做法是在**相同的其余组件集合**下比较 —— 这正是下一节配对比较的主题。

### 结果要记成什么

`ablate` 返回的列表 dump 成 JSONL 就够，但每行要带全五样，否则事后无法复核（示例：构造数据，未实跑）：

```json
{"run_at": "2026-10-09", "model": "deepseek-flash", "experiment": "prompt-ablation",
 "keep": ["角色"], "scores": [8, 8, 3, 8, 8], "mean": 7.0, "min": 3,
 "metric": "约束合规(8)", "prompt_sha8": "a1b2c3d4"}
```

带 `prompt_sha8` 是因为**结果必须能追溯到当时那份提示词** —— 提示词一改，这行数据就不可复现了。`scores` 要留原始的那 5 个值，不能只留 `mean`：**`8 8 3 8 8` 和 `7 7 7 7 7` 的均值都是 7.0，但它们是两种完全不同的失败**（见下面的报错）。

### 一个真实的报错

我第一版把 `metric_fn` 写成返回 0 或 1，然后直接 `mean`。
看起来没问题，直到我要比较两组「五次里各失败一次」的结果时发现：
**0/1 的均值丢掉了「失败得有多严重」这个信息。**

上面那次 `8 8 3 8 8` 和另一次假设的 `7 7 7 7 7`，均值都是 7.0，
但前者是「四次完美一次崩」、后者是「每次都差一点」。
**这两种失败在生产里的处理方式完全不同** —— 前者要查那个偶发的坏输入，
后者要整体调提示词。

所以指标至少要有两个层次：**分级分数**（知道差多少）和**合格率**（知道失败频率）。

## 六、小结

- **单变量消融会低估**：两个组件可以互为兜底，单独去掉都没事，两个都去掉才暴露
- **要做组合消融**：至少覆盖「每个单独去掉」与「全去掉」
- **重复多次看分布**：`8 8 3 8 8` 跑一次可能抽到 8，得出「没影响」的假阴性
- **约束会收窄输出空间**：去掉格式要求后输出 token 从 2404 涨到 2872
- **指标要分层**：分级分数看「差多少」，合格率看「多久崩一次」，两者不能互相替代
- **预先声明主要指标，但把所有能自动量的都记下来**
