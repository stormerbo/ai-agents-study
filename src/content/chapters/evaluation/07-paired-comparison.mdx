前面几节反复出现同一个困境：**绝对分数分不出两个方案的差别。**
这一节讲一个能把灵敏度提上来的方法 —— 配对比较。

## 一、实测：正确率分不出，成本分得出

我准备了 8 个结构相同、内容不同的任务（为 8 个不同接口写测试用例），
然后在**每个任务上**分别跑两个提示词变体：

- **A**：只要结果，不要求过程
- **B**：多一句「先在内部列出你打算覆盖的场景，再输出最终答案」

每个任务上 A、B 各跑一次，配对。结果：

```text
任务          A 得分/token    B 得分/token    Δtoken
订单退款        7 / 2155        7 / 2192       +37
用户注册        7 / 1942        7 / 1981       +39
优惠券核销       7 / 2147        7 / 3444      +1297
地址修改        7 / 2333        7 / 2640       +307
发票开具        7 / 1807        7 / 1844       +37
密码重置        7 / 2863        7 / 2661       -202
余额提现        7 / 2339        7 / 1805       -534
商品下架        7 / 2392        7 / 3229       +837
```

**正确率上 A 与 B 完全一样**（每一格都是 7/7，见下面那个错误的说明）。
但**成本上有差别**：B 平均每个任务多花 **227 个输出 token**。

如果只看正确率，你的结论会是「两个方案等价，随便选」。
而看成本，结论是「B 更贵，但没换到任何正确率」—— 这是两个完全不同的决策。

### 一个必须先说的错误：我把分母数错了

上面那张表里每一格都是 7。我第一反应是「**16 次运行全是 7/8，没有一次满分 ——
说明有一条约束从来没被满足，这不正常**」，甚至准备把它当成一个发现写进来。

回去数了一下约束列表：那里只有 **7 条**，不是 8 条。
**7 就是满分。** 从头到尾没有任何一条约束失败过。

这个错误值得单独记一笔，因为它有两个特点：

- **它是静默的** —— 分数 7 本身看不出对错，你有疑虑时才会去数分母
- **它会生成假发现** —— 「有一条约束从不通过」听起来很像个真问题，
  如果不核对，它会变成一个假的改进任务

**报告任何分数时都要写清分母。**「7 分」没有意义，「7/7」和「7/8」是完全不同的结论。
这一条在人工填表时最容易出错，所以它也该尽量由代码算 —— 和第 2 节那个答案键的教训是同一个。

## 二、配对比较为什么更灵敏

回到成本那列。两种看法：

**绝对比较。** A 组 8 个数的标准差是 321.0，B 组是 625.7。
两组的均值差要跟这两团噪声一起比 —— 标准误是：

```text
SE(未配对) = sqrt(321.0^2 / 8 + 625.7^2 / 8) = 248.6
```

**配对比较。** 看的是每个任务内部的差值（Δtoken 那一列）。
这 8 个差值的标准差是 584.8，标准误是：

```text
SE(配对) = 584.8 / sqrt(8) = 206.8
```

**配对把标准误从 248.6 降到 206.8，降了约 17%。**

降下来的部分来自哪里？来自**任务本身造成的那部分波动**。
「优惠券核销」这个任务天然就写得长，「发票开具」天然写得短 ——
这部分差异在两组的绝对值里都存在，会互相干扰；
而配对做差之后，任务级的差异被**消掉了**，剩下的只有「同一任务下 A 与 B 的差别」。

注意这只降到 17%，不是降到零。因为任务之间的**差值**本身也有波动 ——
「优惠券核销」B 比 A 长 1297，而「余额提现」B 比 A 短 534。
**配对消掉的是任务的平均水平，消不掉任务对改动的敏感度差异。**

## 三、配对之后还要做检验

配对只是把数据整理好，**它本身不给结论**。判定「B 是不是真的更贵」还需要一个检验。

最省事的是**符号检验**：只看每个任务的差值方向，不看大小。

```text
8 个任务里：B 比 A 长 6 次，短 2 次
假设两方案无差别（p = 0.5），出现「至少 6 次同向」的概率：
  = [C(8,6) + C(8,7) + C(8,8)] / 2^8
  = (28 + 8 + 1) / 256 = 37 / 256 ≈ 0.145
```

**p ≈ 0.145，不显著。**

这是一个必须如实说出来的结果。方向是明确的（6 比 2），
但 **8 个样本不足以判定它不是随机波动**。

如果我要一个可靠结论，需要多少样本？按同样的方向性（约 75% 同向）估算，
想让 p 小于 0.05 大约需要 15~20 个任务。
**这就是「配对提升了灵敏度」和「灵敏度仍然不够」是两件事** ——
配对让你在同样样本下更强，但样本太少时它救不了你。

## 四、什么时候该用配对

配对的前提是**每个样本能在两种条件下各测一次**，而且两次之间可比。
这个前提在很多评测场景里成立，但有几个常见的破坏它的做法：

**一、两次运行之间环境变了。** 如果 A 跑完之后你改了工具返回格式，再跑 B，
那 A 与 B 的差里就混进了环境的变化。
**配对要求两个条件在同一环境下、尽量接近的时间点完成。**

**二、任务本身有先后依赖。** 如果任务 2 依赖任务 1 的产出，
那么「先跑完所有 A 再跑所有 B」和「每个任务 A/B 挨着跑」会给出不同结果。

**三、配对破坏了随机化。** 配对的一个隐含要求是**在同一对内随机决定谁先跑**。
如果永远是 A 先 B 后，你测到的可能是顺序效应（比如 B 享受了缓存命中）。

对应的做法：**同一对内随机顺序、交错执行、记录每对的执行时间戳**。

## 五、把检验写成代码

下面这段不需要第三方库，直接能跑。它做了两件事：**符号检验**与**配对/未配对标准误的对比**。

```python
import math
from statistics import mean, stdev


def sign_test(diffs):
    """符号检验：只看方向，不看大小。返回单侧 p 值。"""
    nz = [d for d in diffs if d != 0]
    n = len(nz)
    if n == 0:
        return 1.0, 0, 0
    k = sum(1 for d in nz if d > 0)
    # P(X >= k)，X ~ Binomial(n, 0.5)
    p = sum(math.comb(n, i) for i in range(k, n + 1)) / 2 ** n
    return p, k, n


def compare_paired(a, b):
    """a、b 是同一批任务上两个条件的结果，一一对应。"""
    assert len(a) == len(b), "配对要求两组样本数相同"
    diffs = [y - x for x, y in zip(a, b)]
    n = len(diffs)

    se_paired = stdev(diffs) / math.sqrt(n)
    se_unpaired = math.sqrt(stdev(a) ** 2 / n + stdev(b) ** 2 / n)
    p, k, nz = sign_test(diffs)

    return {
        "均值差": mean(diffs),
        "SE_配对": se_paired,
        "SE_未配对": se_unpaired,
        "灵敏度提升": 1 - se_paired / se_unpaired,
        "p值": p,
        "同向": "%d/%d" % (k, nz),
    }
```

有了它，上面那组数据就是一次调用：

```python
tok_a = [2155, 1942, 2147, 2333, 1807, 2863, 2339, 2392]
tok_b = [2192, 1981, 3444, 2640, 1844, 2661, 1805, 3229]
r = compare_paired(tok_a, tok_b)
print("均值差 %+.0f" % r["均值差"])
print("SE 配对 %.1f / 未配对 %.1f  → 降 %.0f%%"
      % (r["SE_配对"], r["SE_未配对"], 100 * r["灵敏度提升"]))
print("符号检验 %s 同向，p = %.3f → %s"
      % (r["同向"], r["p值"], "显著" if r["p值"] < 0.05 else "不显著"))
```

实跑输出（2026-10-10，用本节的真实数据）：

```text
均值差 +227
SE 配对 206.8 / 未配对 248.6  →  降 17%
符号检验 6/8 同向，p = 0.145 →  不显著
```

### 一个真实的报错

我第一版 `compare_paired` 里写的是：

```python
diffs = [y - x for x, y in zip(a, b)]
# 然后直接比较 mean(a) 与 mean(b)
```

看起来没问题，**但如果 a 与 b 的样本顺序不一致（比如 b 被 shuffle 过），
配对就悄悄退化成未配对了** —— 差值全是噪声，SE 反而更大，
而你不会收到任何错误提示。

所以我加了那句 `assert len(a) == len(b)`。它防不住乱序，但至少能防住长度不匹配这一类。
**更可靠的做法是给每个样本一个 id，按 id 对齐，而不是按列表下标。**
凡是「两组数组一一对应」的代码，都值得问一句：**这个对应关系是有保证的，还是碰巧的？**

## 六、配对在 agent 评测里的三个典型场景

**一、两个提示词的对比。** 这是本节做的。要点是**同一批任务上各跑一次**，
而不是「提示词 A 跑 50 个任务、提示词 B 跑另外 50 个」。后者看起来样本更多，
但它把任务差异混进来了，灵敏度和 8 个任务的配对版差不多。

**二、两个模型的对比。** 在这里配对还有一个额外好处：**它自动控制了任务难度**。
如果模型 X 在简单任务上跑分高、模型 Y 在困难任务上跑分高，绝对均值会互相抵消；
而配对会发现「在同一个任务上谁更好」，于是能给出更细的结论 ——
比如「Y 在简单任务上更好，X 在困难任务上更好」，这比一个总均值有用得多。

**三、同一个模型两个版本的对比。** 这是最实用的一类：你改了系统提示词或加了一个工具，
想知道有没有变好。**这种情况下配对几乎是必须的**，因为同一批用例跑两次的成本很低，
而不配对的话，你会把大量样本浪费在「任务之间本来就有差异」这件事上。

有一个反例值得注意：**配对不适用于「每个条件需要不同样本」的场景**。
比如比较「给 5 条示例」与「给 20 条示例」，你没法在同一个任务上同时做两件事 ——
这时候只能用非配对设计，代价就是需要更多样本才能看出同样的差异。

## 七、小结

- **绝对分数分不出差别时，先试成本这类连续指标** —— 本实验里正确率 A/B 相同，但 token 差 227
- **配对把任务级差异消掉**，标准误从 248.6 降到 206.8（本实验降 17%）
- **配对只整理数据，不给结论** —— 还要做检验；本实验符号检验 p≈0.145，**不显著**
- **样本太少时配对也救不了你** —— 按本实验的方向性，约需 15~20 个任务
- **报告分数必须写清分母** —— 我把 7/7 读成了 7/8，差点造出一个假发现
