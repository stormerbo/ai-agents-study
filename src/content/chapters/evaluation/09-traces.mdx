评测告诉你「变差了」。追踪告诉你「哪里变差了」。没有第二件事，第一件事就只带来焦虑。

## 为什么最终答案不够

我构造了一个具体的例子。一个三段式任务：查订单、查物流、查退货政策，然后综合成一条回复。其中**第二个工具返回了一个字段名对不上的数据** —— 它用 `eta` 返回时间，而综合步骤把它当成可直接展示的字段。

最终答案长这样：

```json
{"order": "A-1001", "status": "已发货", "amount": 1288.50,
 "预计送达": 1288.50, "退货天数": 7}
```

**问题很明显：预计送达是 1288.5（金额）。** 但那只是「现象」，不是「根因」。看着这一份输出，你能提出的所有解释都只是猜测：

- 模型算错了？
- 某个工具返回了脏数据？
- 字段名对不上，模型猜错了？
- 提示词没说清楚这个字段是什么？

而且注意 —— 这些猜测**指向四份不同的代码**。你要挨个去查。

## 有轨迹时看到的东西

同一个任务，加上轨迹记录：

```text
第 1 步  调用 get_order({"order_id": "A-1001"})
第 1 步  返回 {"id": "A-1001", "status": "已发货", "amount": 1288.5}
第 2 步  调用 get_shipping({"order_id": "A-1001"})
第 2 步  返回 {"id": "A-1001", "carrier": "顺丰", "eta": 1288.5}
第 3 步  调用 get_policy({"region": "华东"})
第 3 步  返回 {"region": "华东", "return_days": 7}
第 4 步  最终答案 {"order": "A-1001", ..., "预计送达": 1288.5, "退货天数": 7}
```

对照第 2 步的返回值和最终答案，**根因立刻确定**：

- 值是同一个（1288.5），字段名是 `eta`
- 工具返回的是 `eta`（estimated arrival 的简写），语义是时间
- 综合步骤把它当成了一个可直接展示的字段
- 而这一次它的值恰好与金额相同，所以它表现得像一个**脏数据**，而不是一个**类型错误**

**这个结论只有轨迹能给出。** 最终答案里没有任何信息指向第 2 步。

## 四个必记字段

从上面这个例子里能直接提取出要记什么：

| 字段 | 为什么 |
|---|---|
| **步骤序号** | 用来回答「第几轮」 |
| **动作与参数（原始 JSON）** | 参数是排查的第一现场 |
| **返回值（原样）** | 不要只记长度或摘要 —— 根因常常在一个具体字段上 |
| **token 与耗时** | 成本或延迟异常时，定位到「哪一步变贵了」 |

第三条特别值得强调。一个常见的省事做法是只记「工具调用成功/失败」和结果长度 —— **那恰好把这次排查需要的信息丢掉了**。要记原始返回值。

第二条也有个具体理由：**要记原始 JSON，不要记解析后的对象。** 第 10 章实测过一个案例 —— 模型把一个三元表达式写进了工具参数（`${北京明天最高温 > 上海明天最高温 ? '北京' : '上海'}`）。只有原始字符串能看出这件事；解析成对象之后它只是一个普通的字符串字段，看不出异常。

## 轨迹的三个用途

**一、定位失败。** 就是上面那个例子。

**二、成本归因。** 第 9 章实测过一个现象：界面 agent 每步要多花约 300 token（一张截图）。当你发现一个任务变贵了，轨迹能告诉你是**步数变多了**还是**每步变贵了** —— 这两个的修法完全不同（前者改提示或加闸门，后者改上下文或换模型）。

**三、评测集的来源。** 这是被低估的一条：**每一条线上失败都应该变成一条评测用例。** 第 2 节讲过评测集的三种来源，其中最有价值的就是这一类 —— 而它的前提是你有轨迹。没有轨迹，你只知道「这次用户不满意」，不知道失败在哪，也就无法变成一条可复现的用例。

## 和「审计轨迹」的区别

第 11 章讲过一个也叫轨迹的东西 —— 审计轨迹。两者记录的内容很像，但目的不同：

| | 审计轨迹（第 11 章） | 追踪（本节） |
|---|---|---|
| 目的 | 出事之后能复盘「它做了什么」 | 开发和排查时定位失败 |
| 面向 | 安全与合规 | 调试与评测 |
| 保留期 | 长（可能是月或年） | 短（几天到几周） |
| 采样 | 不能采样，必须全量 | 可以采样 |

最后一行是实际的区别。**审计不能采样** —— 你没记下来的那次恰好出事，就完了。而追踪可以采样，因为它服务于开发，样本量够就行。

所以两者可以共用一套记录机制，但保留策略要分开：审计的那份不可丢，追踪的那份可以滚动清理。

## 采样与实际开销

全量记录是有成本的：存储、写入开销、以及（如果轨迹里有大对象）序列化时间。三个降成本的做法，按优先级：

**一、只记结构化字段，不记整个上下文。** 记「调用了什么工具、参数是什么、返回了什么」，不要记「当时完整的消息历史」。前者是几十字节，后者可能几十 KB。

**二、失败全记，成功采样。** 失败的轨迹一定要留（那是你排查的依据），成功的按 1% 到 10% 采。这个策略的假设是「成功的样子都差不多，失败各有各的样子」，而它在实践中大体成立。

**三、设置保留窗口。** 追踪数据滚动删除（比如 14 天），审计数据单独存。两者的生命周期不同，不该混在一个存储里。


## 记到多细才够

「记结构化字段」是对的，但「什么算一个字段」需要判断。记太粗会丢信息，记太细会淹掉信号。

一个实用的判据：**问「这次排查我需要什么？」，而不是问「系统里有什么？」**

具体来说，按排查时的问题倒推：

| 排查时的问题 | 要记的字段 |
|---|---|
| 第几轮出的问题？ | 步骤序号、时间戳 |
| 它当时看到了什么？ | 那一刻的工具返回值（原样） |
| 它决定做什么？ | 工具名 + **原始参数 JSON** |
| 结果是什么？ | 原始返回值、是否标了 is_error |
| 这一步贵不贵？ | 该步的输入/输出 token、耗时 |

五行里，第二个和第四个容易被省成「成功/失败」。而**省掉的恰好是排查时唯一有用的东西** —— 因为根因几乎总在一个具体的字段值上。

反过来，有一类东西**不该记**：完整的消息历史。它的体积比其余所有字段加起来还大一个数量级，而排查时你几乎从不翻它 —— 你需要的是「第 2 步返回了什么」，不是「第 2 步时上下文里有什么」。

一个折中：**记消息历史的指纹（hash）和长度，不记内容。** 需要时可以根据指纹去别处捞；不需要时它只占几十字节。

**记录真的落到存储里长这样**（示例：构造数据，未实跑；字段就是上面那张表的落点）：

```json
{"trace_id": "8f21c-04", "task": "refund_status", "step": 2,
 "tool": "get_shipping", "args": {"order_id": "A-1001"},
 "result": {"id": "A-1001", "carrier": "顺丰", "eta": 1288.5},
 "is_error": false, "tokens_in": 812, "tokens_out": 57, "ms": 421,
 "context_sha8": "d4f1a9c2", "at": "2026-10-12T14:03:21+08:00"}
```

两个字段值得单独解释：`is_error` 是第 4 章工具结果里的布尔标记 —— tool_result 显式标 `is_error: true` 时，模型知道「这个工具失败了」，而不是「工具成功返回了一段错话」；排查时它比返回内容更早告诉你这一步的性质。`context_sha8` 是上下文的指纹（上面那条折中）；`at` 是时间戳，跨用例排查时它和步骤序号一起用。

## 在哪一层写这几行

四个字段不是「想记就记」，它们有唯一的插入点：**agent 循环里执行工具的那一步**（第 11 章那个循环）。形态是：

```python
import time

for step, tool_use in enumerate(model_turns, start=1):
    t0 = time.time()
    result, is_error, usage = execute(tool_use)          # ← 执行
    record(step=step, kind="tool_result", tool=tool_use["name"],
           args=tool_use["input"],                        # 原始参数 JSON
           result=result, is_error=is_error,
           tokens_in=usage["in"], tokens_out=usage["out"],
           ms=int((time.time() - t0) * 1000))             # ← 记录
```

**采样在哪做。** 「失败全记、成功按 1%-10% 采」的落点也在 `record()` 里，而不是事后从全量日志里筛 —— 存全量再筛，成本已经付过了：

```python
import random

def record(..., is_error=False, sample_rate=0.05):
    if not is_error and random.random() > sample_rate:
        return                      # 成功且没抽中 → 不落盘（进程内仍可留最近 N 条）
    store.write(...)
```

`sample_rate=0.05` 就是 5%；失败路径无条件落盘。**注意采样只对「追踪」成立** —— 审计轨迹（第 11 章）不能采样，那条分流要在这里就做掉。

## 失败轨迹 → 评测用例

前面说「每一条线上失败都应该变成一条评测用例」，这一步可以写成一个函数。输入是一条失败轨迹，输出是第 3 节那种用例 JSON：

```python
from datetime import date

def reverse_expected(trace):
    """从失败轨迹反推期望行为的**草稿**，必须人工确认后才入库。

    机器只能给出线索：失败那步返回了什么、最终答案错在哪。
    它给不出「对的应该是什么」—— 那一步只能由人写。
    """
    bad = next((e for e in trace if e.get("is_error")), None)
    if bad:
        return "这一步的 %s(%s) 不应失败；期望返回正常数据" % (
            bad["tool"], json.dumps(bad["args"], ensure_ascii=False))
    return "最终答案不应包含错误字段（人工确认具体断言）"


def trace_to_case(trace):
    """一条失败轨迹 → 一条评测用例。三个字段自动填，期望值留给人。"""
    ids = [e for e in trace if e.get("trace_id")]
    return {
        "id": "trace-%s" % (ids[0]["trace_id"] if ids else "unknown"),
        "question": ids[0]["task_input"] if ids else "",
        "expected": reverse_expected(trace),      # 草稿，人工确认后定稿
        "source": "线上失败 · trace-%s" % (ids[0]["trace_id"] if ids else "unknown"),
        "added": date.today().isoformat(),
    }
```

**为什么 `reverse_expected` 只能给草稿**：机器只知道「它错了」，不知道「对的应该是什么」。其余四个字段可以自动填 —— 这正是把失败入库做成流水线的意义：**人只补一句期望，其余不花时间。**

## 一个反例：太粗的轨迹

我在这个实验之前先写了一个粗粒度版本，它记的是：

```text
step=2 tool=get_shipping status=ok duration=12ms
```

跑出来之后我发现它**完全没用** —— status=ok 是真的（调用成功了），耗时也正常，但返回的数据里那个字段的值是错的。**粗粒度轨迹只能告诉你「哪一步失败了」，而这次的问题是「哪一步都没失败，但结果是错的」。**

这正是 agent 系统里最常见的一类失败：**每一环都成功，合起来不对。** 要发现它，轨迹必须记到**具体字段**这一层。
## 完整可运行代码

下面这段代码跑的就是上面那个例子：同一个任务，先看「只有最终答案」时你能知道什么，再看「有轨迹」时你能知道什么。

```python
"""追踪：一次失败要能定位到那一轮。

这个脚本跑一个三段式 agent 任务，并在中间注入一个隐蔽的错误，
然后演示「只有最终答案」和「有轨迹」两种情况下，排查难度差多少。

纯本地模拟，不需要 API —— 因为要测的是**记录与排查**这件事，不是模型。
实跑状态：2026-10-09。
"""
import json, time

TRACE = []


def record(step, kind, **kw):
    TRACE.append({"step": step, "kind": kind, "t": round(time.time() - T0, 3), **kw})


T0 = time.time()

# 三个工具：第二个返回了**一个字段名不同**的数据（真实系统里最常见的坑）
def get_order(order_id):
    return {"id": order_id, "status": "已发货", "amount": 1288.50}


def get_shipping(order_id):
    # ⚠️ 注入的错误：字段名是 eta 而不是 promised_date，
    #    而且值和上一步的 amount 一样 —— 看起来像正常数据
    return {"id": order_id, "carrier": "顺丰", "eta": 1288.50}


def get_policy(region):
    return {"region": region, "return_days": 7}


def run(verbose_trace):
    TRACE.clear()
    global T0
    T0 = time.time()
    order_id = "A-1001"

    record(1, "tool_call", tool="get_order", args={"order_id": order_id})
    o = get_order(order_id)
    record(1, "tool_result", tool="get_order", result=o)

    record(2, "tool_call", tool="get_shipping", args={"order_id": order_id})
    s = get_shipping(order_id)
    record(2, "tool_result", tool="get_shipping", result=s)

    record(3, "tool_call", tool="get_policy", args={"region": "华东"})
    p = get_policy("华东")
    record(3, "tool_result", tool="get_policy", result=p)

    # 综合步骤：它误用了 eta 这个字段（因为名字看着像日期）
    answer = {
        "order": o["id"],
        "status": o["status"],
        "amount": o["amount"],
        "预计送达": s["eta"],          # ← 错在这里：eta 其实是金额的重复值
        "退货天数": p["return_days"],
    }
    record(4, "final", answer=answer)
    return answer


if __name__ == "__main__":
    ans = run(True)

    print("=== 只有最终答案时，你看到的是 ===")
    print(json.dumps(ans, ensure_ascii=False, indent=1))
    print()
    print("问题：预计送达 = 1288.5。这个数明显不对 —— 但它从哪来的？")
    print("      只看最终答案，你无法回答。你能想到的所有可能都在猜测范围内：")
    print("        · 模型算错了？   · 工具返回错了？   · 字段名对不上？   · 提示词没说清楚？")
    print()

    print("=== 有轨迹时，你看到的是 ===")
    for e in TRACE:
        if e["kind"] == "tool_call":
            print("  第 %d 步  调用 %s(%s)" % (e["step"], e["tool"], json.dumps(e["args"], ensure_ascii=False)))
        elif e["kind"] == "tool_result":
            print("  第 %d 步  返回 %s" % (e["step"], json.dumps(e["result"], ensure_ascii=False)))
        else:
            print("  第 %d 步  最终答案 %s" % (e["step"], json.dumps(e["answer"], ensure_ascii=False)))
    print()

    print("=== 定位 ===")
    print("  对照第 2 步的返回值 {'carrier': '顺丰', 'eta': 1288.50} 和最终答案的 预计送达: 1288.50")
    print("  → 值是同一个，字段名是 eta。")
    print("  → 根因：工具方用了 eta（estimated arrival 的简写）返回**时间**，")
    print("     而综合步骤把它当成了可直接展示的字段；恰好这一次 eta 的值与金额相同，")
    print("     所以看起来像一个脏数据，而不是一个类型错误。")
    print()
    print("  这个结论**只有轨迹能给出**。最终答案里没有任何信息指向第 2 步。")
    print()
    print("=== 要记录的四个字段 ===")
    print("  1. 步骤序号 —— 用来定位「第几轮」")
    print("  2. 动作与参数（原始 JSON，不是解析后的对象）")
    print("  3. 返回值（原样，不要只记长度或摘要）")
    print("  4. token 与耗时 —— 成本异常时用来找「哪一步变贵了」")
    print()
    print("  第 2 条特别说明：要记**原始 JSON**。第 10 章实测过一个案例 ——")
    print("  模型把三元表达式写进了工具参数，只有原始字符串能看出这件事。")
```

## 常见坑

- **只记「成功/失败」和结果长度。** 那恰好丢掉了排查需要的字段 —— 要记**原始返回值**。
- **记解析后的对象而不是原始 JSON。** 第 10 章实测过：模型的异常参数只有原始字符串能看出来。
- **只记成功的调用。** 排查时你需要的恰恰是失败那几次的现场。
- **对审计轨迹做采样。** 审计必须全量；可采样的是服务于开发的追踪，两者要分开存。
- **把轨迹和评测集当成两件事。** 每条线上失败都该变成一条用例 —— 这是评测集保持相关的唯一健康方式。
- **记了整个上下文。** 那会把成本推高一个数量级，而排查时你几乎从不需要它。
