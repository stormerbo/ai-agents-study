前面十四章都在讲「怎么做」。这一章要回答一个更前面、也更难的问题：**怎么知道你做对了。**

这件事在 agent 上比在普通软件上难得多，因为它的输出是自然语言、它的过程是多步的、而且「好」往往没有唯一答案。

## 先区分目标、约束与诊断信号

「这个 agent 好不好」不是一组对所有系统都适用的固定维度。先写清楚产品要交付的**任务结果**，再把不能违反的**安全/业务约束**列出来；工具轨迹、成本、延迟等是诊断信号或运行约束，具体要不要作为质量门槛取决于场景。比如客服退款 Agent 的首要目标可能是正确解决退款问题；未授权退款是硬约束；工具调用次数和 P95 延迟用来定位效率与体验问题。

| 类别 | 要回答的问题 | 例子 |
|---|---|---|
| 任务结果 | 用户的目标是否按业务定义完成？ | 符合政策且退款状态正确 |
| 输出质量 | 事实、计算、引用或格式是否正确？ | 金额与权威订单记录一致 |
| 过程诊断 | 哪一步导致成功或失败？ | 工具选择、参数、检索证据是否合适 |
| 安全与业务约束 | 哪些行为无论结果如何都不可接受？ | 未授权写操作必须为 0 |
| 运行约束 | 质量目标需在什么成本/延迟范围内达成？ | 每个成功任务成本上限、P95 延迟 SLO |

这些类别**相关但不互相替代**。任务成功率不能证明过程可靠；平均成本不能抵消一次越权写入；也不应把它们随意加权成单一总分。若产品确实需要一个综合指标，先明确权重、硬约束和权衡理由，同时保留各分项及失败样本，避免总分掩盖回归。

有客观真值的检查通常更容易自动化，但「客观」不等于「完整」：格式合法不代表事实正确，工具调用合法不代表授权充分，引用存在也不代表引用支持结论。主观目标也不必丢弃；可以用明确 rubric、人工标注或经校准的 judge 评估，并报告评估器本身的不确定性。

## 把目标写成可审查的判据

回归评测需要稳定的操作定义，但「两个人必须总是打出同一分」不是所有目标的前提。对规则、schema、金额和授权边界，可用确定性断言；对有歧义的质量判断，要先写 rubric，再用独立标注样本检查标注者一致性、分歧类型和判据覆盖范围。遇到分歧应澄清定义或升级人工复核，不能把分歧简单抹掉。

「答案质量不错」「回答比较专业」—— 单独作为判据时，它们只是未定义的印象：

- **定义不足**：读者无法知道什么证据算通过
- **标注不稳定**：不同标注者或同一标注者在不同时间可能分歧
- **诊断能力弱**：一个总分变化无法指向具体失败环节

所以定义「好」的过程，是把业务目标转成**可观察、可复核、与目标相关**的判据；能确定性计算时再写成代码。

一个可判定的判据长这样：

```text
❌ 「摘要要抓住重点」
✅ 「摘要必须包含原文中的三个关键数字，且数字与原文完全一致」

❌ 「回答要友好」
✅ 「回答的第一句必须包含用户问题里的实体名」

❌ 「不要乱调工具」
✅ 「本次任务中 refund_order 的调用次数不超过 1 次」
```

右边的例子更具体，但仍要检查它们是否真的代表目标：关键词命中可能漏掉同义表达，长度阈值可能奖励废话，调用次数限制也要由业务风险决定。代码只保证按规则执行，不保证规则有效。规则能进 CI；它是否测到了目标，需要用人工复核、反例和线上结果持续验证。

## 三步把模糊目标变成判据

**第一步，界定评测决策。** 说明要比较什么改动、谁会受影响、决策会怎么变。再收集成功、失败和边界样本；只有失败样本会导致评测集偏向已知问题，无法估计日常表现。

**样本从哪来？** 可组合脱敏后的生产轨迹、专家设计的边界用例、合成变体和公开基准；每种来源覆盖不同风险。生产数据需遵守授权、隐私与保留政策。合成题和公开题不能自动代表线上分布；记录来源并分开报告。

**第二步，写指标契约。** 至少记录：评测单位、目标总体、分子/分母、成功条件、失败/拒答/超时如何计数、判定器版本、样本来源和适用范围。比如「输出里的状态值必须来自本次授权查询返回的状态集合」比「没有编造」更可执行；仍需处理空结果和过期数据。

**第三步，选择与风险匹配的评估方式。**

- **有可靠真值/规则** → 写确定性检查，并用正例、负例、边界例验证检查器
- **需要语义判断** → 定义 rubric 和人工参考标注；可以评估 judge 与参考标注的一致性、偏差和误差，再决定是否辅助筛查
- **目标仍含糊** → 先做定性复核或补充产品定义，不要把未经验证的代理指标包装成目标本身

代理指标只有经过验证才有用。「回答是否包含问题里的关键词」虽容易计算，却可能奖励复述问题、误伤同义表达；可把它当作便宜的筛查信号，抽样复核其假阳性/假阴性，不要直接当成「切题率」。如果没有可信代理，就诚实保留人工评审或暂不自动化。

## 一个站内案例：工具参数的判定口径

第 4 章保留了一组 2026-10-08 的历史摘要：对自由字符串和 enum 两种天气工具参数形式，各记录 3 次调用。

**模糊版本的判据**是「工具描述够不够清楚」—— 这个没法测，因为「清楚」没有定义。

**实际用的判据**是：

```text
给定 3 个问题，观察模型传进 city 参数的取值：
  自由字符串描述 → 合法值 0/3（"最高"/"低"/"紧急"）
  enum 约束描述 → 合法值 3/3
```

判分规则本身可以很明确：提取参数值，与允许集合比较。但该历史摘要没有保存逐次请求/响应，分母口径不可独立重建；每组仅 3 次，也不能据此归因于 enum 或推出生成期约束保证。它适合作为一个**待复验假设**：在自己的模型、端点和 schema 模式下记录原始输入、返回参数、解析状态与评分器版本，再验证。

这个例子说明了两件不同的事：指标定义可以是确定性的；观测到的模型行为是否可靠，则需要可复核数据和合适的实验设计。自动化判分不会补回缺失的历史证据。

## 怎么判断一条判据够不够好

最后给一份检查清单。一条判据要能用于回归测试，至少考虑以下五项：

| 要求 | 为什么 |
|---|---|
| **操作定义明确** | 样本单位、通过条件、拒答/错误处理方式可被复核 |
| **结果可复现** | 固定输入、系统版本、工具状态与 scorer 版本后可重放；随机模型输出需重复或声明采样策略 |
| **与目标相关** | 指标变化能回答预先写下的产品/工程决策，不只因便宜而选 |
| **误差可见** | 抽查误报、漏报、人工分歧与未知状态，不把解析失败当成模型失败或成功 |
| **有区分度** | 通过已知正例、负例和边界例，确认指标能区分相关行为 |

误差可见和区分度最容易漏，也最难自查。**一条永远通过的判据，和没有判据是一样的** —— 它测不出任何改动的效果，却会让你的评测报告看起来一切正常。第 2 节会讲怎么构造有区分度的评测集，以及为什么「全对」的评测集反而最没有信息量。


## 不同类型的判据长什么样

任务目标、约束与诊断信号的判定方式不同，以下给出一些常见形式。

**有权威真值的输出检查**通常适合确定性判定：

```text
- 输出里的金额必须等于数据库里的金额（逐字比对）
- 输出的日期必须落在给定区间内
- 输出里的引用必须真的存在于来源文档中（第 6 章的检索场景）
- 计算类任务的答案必须与代码算出的结果一致
```

这类检查把模型输出与权威数据或规则比对。但真值也必须有来源、版本和时间语义：退款政策可能更新，订单状态可能在请求后变化；只比较字符串而不处理单位、时区、空值或数据新鲜度，会产生错误裁决。能由代码可靠计算的部分交给代码，语义支持关系仍需单独评估。

**任务是否解决**通常需要多个互补信号，而非单个代理指标：

```text
- 后端业务状态是否达到目标终态（需定义副作用与延迟窗口）
- 输出是否给出有证据支持、与用户情境匹配的下一步（语义判定或人工 rubric）
- 用户是否追问/重试/转人工（可观测代理信号，需按渠道、任务类型和用户群分层）
```

追问是有用的**代理信号**，不是失败的直接真值：用户可能在补充问题、切换意图，或因界面/网络重试；未追问也不等于解决。要先定义识别窗口与去重方法，并抽样检查信号与人工判断/业务终态的对应关系。

**安全与过程约束**可以从宿主轨迹和业务记录检查，但日志是否完整、权限是否真实生效也需要验证：

```text
- 本次任务调用了哪些工具、各几次（第 11 章的审计轨迹）
- 有没有调用被禁止的工具（执行层拦截，第 9 节那种闸门）
- 总 token 与总步数是否超预算
- 不可逆动作前有没有确认点
```

有日志不代表覆盖完整，也不代表约束真正执行。要测试拒绝/拦截路径、审计丢失和未知状态；成本与延迟也需统一口径、计入重试/工具/子 Agent，并区分成功任务与全部尝试。

## 一个例子：把目标变成可验证的判据

下面用一个构造场景说明如何把目标变成检查方案；它不是线上数据，也不证明这个标准适用于所有订单业务。

**原始目标**：「让 agent 的回答更有帮助。」

这句话缺少任务范围和成功定义。先把决策写成「改动是否提升未收到货咨询的正确解决率，同时不增加未经授权的退款」；再拆成结果指标和硬约束。

**第一步，固定任务与权威状态。** 假设这是合成例子：用户报告已发货未收到，查询到的订单状态是 `shipped`，政策允许用户先核对物流并在订单页申诉。需要覆盖正常样本、状态冲突、查询失败和不满足申诉条件等边界。

```text
用户：我的订单显示已发货但我没收到
回答：请联系客服。
```

**第二步，写可复核的判据。** 结果判据可以要求建议与当前订单状态/政策一致，并给出适用的下一步；硬约束要求未授权退款次数为 0。评测记录须保存脱敏输入、权威状态快照、输出、工具轨迹、版本和判定理由。

**第三步，区分机器检查和人工/语义检查。** 代码可判定订单状态字段与权威快照是否一致、是否发生未经授权的写操作；“下一步是否适用于该用户”需要 rubric 或人工参考标注。仅检查出现“查/确认/点击”等词，不能证明答案有帮助。

```text
代理信号（未经验证，不作为通过标准）：回答含「查询 / 申诉」等动作词
```

这个信号便宜，但可能误把无关长答案判为合格，也会漏掉用其他表达方式给出正确指引的短答案。先用人工标注样本估计误报/漏报，再决定它适合作为筛查、趋势监控还是完全弃用。

可交付的产物不是单一数字，而是一份版本化评测契约：目标总体、样本、判据、失败分类、硬约束、判定器及局限。这样结果变化才能触发有依据的调查，而不是把代理信号误当成业务成功。

这就是第 1 节那句话的完整含义：**把「好」定义清楚，不等于把每个目标都自动化；可靠规则交给代码，语义与主观目标用明确的 rubric、人工参考和经过校准的 judge，并持续检查它们的误差与适用范围。**
## 完整可运行代码

下面代码演示为何关键词/长度代理不能独自裁决「有帮助」。期望标签是构造样例的人工参考，不是普遍真值；脚本只计算代理与参考标签的混淆情况，不调用模型。

```python
"""检查一个弱代理在构造样例上的误报与漏报。

参考标签仅适用于以下三条合成回答，不代表真实用户总体。
实跑状态：2026-10-21，本地 Python 标准库，无 provider 调用。
"""
import re

SAMPLES = [
    {
        "id": "useful_specific",
        "reference_helpful": True,
        "answer": "先在订单详情核对物流单号；若显示已签收但你未收到，请联系承运商核实签收信息，并按订单页指引发起未收到货申诉。",
    },
    {
        "id": "long_but_unsafe",
        "reference_helpful": False,
        "answer": "请立即点击退款并提交申请，不需要核对订单状态，也不用确认是否符合政策。查询物流只是浪费时间，直接操作即可，之后再联系平台处理。",
    },
    {
        "id": "concise_synonym",
        "reference_helpful": True,
        "answer": "核对运单；若本人未收货但系统显示签收，按订单页流程提交申诉。",
    },
]


def proxy(answer):
    """故意弱的启发式：词面命中且达到长度阈值。"""
    has_action_word = bool(re.search(r"查|确认|点击|发起|联系|提交|下载|申诉", answer))
    long_enough = len(answer) >= 40
    return has_action_word and long_enough


def confusion(samples):
    counts = {"tp": 0, "fp": 0, "tn": 0, "fn": 0}
    for sample in samples:
        predicted = proxy(sample["answer"])
        expected = sample["reference_helpful"]
        key = "tp" if predicted and expected else "fp" if predicted else "fn" if expected else "tn"
        counts[key] += 1
    return counts


if __name__ == "__main__":
    result = confusion(SAMPLES)
    print("构造样例数：%d" % len(SAMPLES))
    print("代理判据混淆计数：TP={tp} FP={fp} TN={tn} FN={fn}".format(**result))
    print("解释：FP/FN 表明词面规则不能单独代表帮助性；样本太少，不能估计总体误差率。")
```

### 什么时候让评测阻断 CI

不是「任何一条未通过就让 CI 变红」这么简单。先区分不可违反的硬约束与允许统计波动的质量指标：在受控模拟环境里，发现未授权副作用可直接阻断；对随机模型输出，通常要预先设定样本、重复策略、最低质量门槛和置信/差异规则，避免单个随机样本决定发布。判定器自身要用预期通过/失败/边界样例测试，并保存题目、系统、prompt、工具、模型与 scorer 版本。CI 只执行既定门禁，不替团队决定目标是否合理。

## 常见坑

- **把任务成功、硬约束和成本延迟混成一个总分。** 先独立报告，再依据显式权衡做决策。
- **把代码可执行误当成指标有效。** 关键词、长度、格式检查只能证明规则执行，不证明它测到目标。
- **只收失败样本。** 失败案例适合回归和覆盖已知风险，不可单独估计代表性总体成功率。
- **把用户追问直接记为失败。** 追问是受渠道、用户行为与后续意图影响的代理信号，需验证关联。
- **用 LLM judge 取代真值、人工复核和授权检查。** Judge 可能有偏差，不能裁决硬安全边界或其自身正确性。
- **忘记检查区分度与误差。** 用正例、负例和边界样本找出误报/漏报；不报告抽查结果会让错误判定看起来像确定事实。
