前面十四章都在讲「怎么做」。这一章要回答一个更前面、也更难的问题：**怎么知道你做对了。**

这件事在 agent 上比在普通软件上难得多，因为它的输出是自然语言、它的过程是多步的、而且「好」往往没有唯一答案。

## 「好」至少有三条轴

把「这个 agent 好不好」拆开，通常落在三条互相独立的轴上：

**一、正确性。** 输出的事实对不对、算得对不对、有没有编造。这一条最接近传统软件的质量定义，也最容易判定。

**二、有用性。** 它有没有真的解决问题。一个完全正确的答案可能毫无用处 —— 比如用户问「怎么退款」，它准确复述了退款政策却没有告诉他该点哪个按钮。

**三、可控性。** 它有没有在边界内行事。调用了不该调的工具吗？花了多少钱？在不可逆的动作前停下来了吗？

**三条轴要分开测。** 把它们揉成一个分数，会得到一个无法行动的数字：分数降了 5%，你不知道是该改提示词、该加工具、还是该收紧闸门。

而这三条里，只有第一条是「有客观答案」的。后两条的判定需要你想清楚判据 —— 这正是本节的主题。

## 判据必须是「可判定的」

这是本节最重要的一个要求：**一个判据如果两个人打分不同，它就不能用来做回归测试。**

「答案质量不错」「回答比较专业」—— 这类说法不是判据，是印象。它们有三个致命问题：

- **不可复现**：同一个人换个时间打的分可能不同
- **不可比较**：昨天的 8 分和今天的 8 分不是一回事
- **不可归因**：分数变了，你不知道是哪一处改动引起的

所以定义「好」的过程，其实就是**把印象翻译成可判定的判据**。

一个可判定的判据长这样：

```text
❌ 「摘要要抓住重点」
✅ 「摘要必须包含原文中的三个关键数字，且数字与原文完全一致」

❌ 「回答要友好」
✅ 「回答的第一句必须包含用户问题里的实体名」

❌ 「不要乱调工具」
✅ 「本次任务中 refund_order 的调用次数不超过 1 次」
```

右边那三句的共同点是：**判定可以写成代码。** 而写成代码这件事又带来两个好处 —— 它能进 CI，而且它不会随心情变化。

## 三步把模糊目标变成判据

**第一步，收集反例。** 不要从「什么是好」开始，从「什么是坏」开始 —— 更容易说清楚，也更具体。翻一遍历史失败案例，把它们写下来。

**反例从哪翻？** 最可靠的来源是线上追踪记录（第 11 节四周计划里第一周做的那件事）—— 那里有真实的失败现场。如果还没有追踪，那么这一章的起点不在这里，而是先花一周只记轨迹；**靠想象编出来的反例，会和你真正会踩的坑错开。**

**第二步，给每个反例写一句「怎么发现它」。** 这句话就是你想要的判据雏形。比如「它编了一个不存在的订单状态」→ 判据是「输出里的状态值必须来自查库结果」。

**第三步，判断这条判据能不能被代码判定。**

- **能** → 直接写成断言，这是最可靠的一类
- **不能，但能被另一个模型稳定判定** → 做成 LLM-as-judge（让另一个模型当裁判：按你给的判据给两份答案打分或比较。它只适合判定清单式判据，不适合「哪个更好」这类整体印象 —— 第 3 节展开）
- **两个都不能** → 这条判据暂时不要用，或者退一步找一个能判定的近似

第三步里那个「退一步」很关键。很多目标是可以找到可判定近似的。比如「回答是否切题」不好判定，但「回答是否包含问题里的关键词」可以 —— 它是个粗糙的近似，但它稳定、便宜、能进 CI，比一个不可判定的好指标有用得多。

## 一个真实的例子

我在第 4 章做过一个实验：验证「工具描述写清楚参数枚举」有没有用。

**模糊版本的判据**是「工具描述够不够清楚」—— 这个没法测，因为「清楚」没有定义。

**实际用的判据**是：

```text
给定 3 个问题，观察模型传进 city 参数的取值：
  自由字符串描述 → 合法值 0/3（"最高"/"低"/"紧急"）
  enum 约束描述 → 合法值 3/3
```

右边这个是可判定的：**取出参数值，和允许的集合比对。** 于是「描述清不清楚」这个大问题，被翻译成了一个 0/3 对 3/3 的小实验 —— 而它可以被重复做、被自动化、被写进回归测试。

**这就是把「好」定义清楚的收益：一个说不清的目标，变成了一个能自动跑的数字。**

## 怎么判断一条判据够不够好

最后给一份检查清单。一条判据要能用于回归测试，至少满足四条：

| 要求 | 为什么 |
|---|---|
| **可判定** | 两个人打分必须一致 |
| **可复现** | 同一份输入、同一个系统，结果必须一样 |
| **单一** | 一条判据只测一件事，否则无法归因 |
| **有区分度** | 好版本和坏版本要能测出差别，否则它永远通过、也永远没用 |

第四条最容易漏，也最难自查。**一条永远通过的判据，和没有判据是一样的** —— 它测不出任何改动的效果，却会让你的评测报告看起来一切正常。第 2 节会讲怎么构造有区分度的评测集，以及为什么「全对」的评测集反而最没有信息量。


## 三条轴各自的判据长什么样

上面说了要分开测，这里给出每条轴上判据的具体形态。它们的判定难度差别很大。

**正确性**是最容易的，因为多数时候有客观答案：

```text
- 输出里的金额必须等于数据库里的金额（逐字比对）
- 输出的日期必须落在给定区间内
- 输出里的引用必须真的存在于来源文档中（第 6 章的检索场景）
- 计算类任务的答案必须与代码算出的结果一致
```

这一类判据的共同点是：**把「模型说的」和「代码算的」做比对。** 而第 5 章那条结论在这里直接适用 —— 能由代码算的答案就让代码算，模型只负责生成。

**有用性**要难一些，因为它涉及「解决了没有」。但可以拆成几个可判定的子问题：

```text
- 输出是否包含用户问题里的关键实体（能判定）
- 输出是否给出了至少一个可执行的下一步（近似可判定：检查是否含动词短语）
- 用户是否追问了同一件事（线上信号，能统计）
```

最后一条是最有价值的 —— **它不需要任何判据，只需要统计数据。** 如果用户在你回答之后又问了一遍同样的问题，那次回答就没有解决问题。

**可控性**最容易被忽略，但它的判据是最硬的：

```text
- 本次任务调用了哪些工具、各几次（第 11 章的审计轨迹）
- 有没有调用被禁止的工具（执行层拦截，第 9 节那种闸门）
- 总 token 与总步数是否超预算
- 不可逆动作前有没有确认点
```

这一类的特点是：**它们全部由你的代码产生，不依赖对输出的理解。** 也就是说，可控性的测量成本几乎为零 —— 只要你在第 11 章那套闸门里记了日志。

## 一个反例：把不可判定的目标翻译一遍

最后用一个真实的例子走完整个翻译过程。

**原始目标**：「让 agent 的回答更有帮助。」

这句话不可判定。翻译分三步：

**第一步，收集反例。** 翻历史记录，找出几条「没帮助」的回答。它们大多长这样：

```text
用户：我的订单显示已发货但我没收到
回答：请联系客服。
```

**第二步，给每个反例写「怎么发现它」。** 这条反例的问题是：**没有给出可执行的下一步**，只把问题推回给了用户。所以判据的雏形是「回答必须包含至少一个用户可执行的动作」。

**第三步，判断能不能被代码判定。** 「可执行的动作」不好精确判定，但可以退一步：

```text
近似判据：回答里包含「查/确认/点击/发起/联系」这类动作词，且长度不少于 40 字
```

这个近似很粗糙，但它**可判定、可复现、能进 CI**。而且它确实抓住了那条反例 —— 「请联系客服」只有 5 个字，也没有具体的动作对象。

**收益是具体的**：原来那句「更有帮助」是一个谁都能说、谁都没法测的目标；现在它变成了一个可以自动跑、可以看趋势、可以在下次改动时告诉你「这次改动让回答变短了」的数字。

这就是第 1 节那句话的完整含义：**把「好」定义清楚，就是把它翻译成能自动判定的东西。**
## 完整可运行代码

下面这段代码把「一个说不清的目标」拆成可判定的判据，并逐条判定。它不依赖模型，因为**判据本身必须是确定性的**。

```python
"""把「好」翻译成可判定的判据，并逐条判定。

它演示第 1 节那条要求：判据必须**能被代码判定**。
所以这个脚本不调用模型 —— 它只做确定性检查。

实跑状态：2026-10-09。
"""
import re

# ---- 判据用声明式写法，而不是散落在代码里 ----
CRITERIA = [
    {"id": "C1", "name": "包含可执行的动作词",
     "test": lambda a: bool(re.search(r"查|确认|点击|发起|联系|提交|下载", a)),
     "why": "反例「请联系客服」不含具体动作对象，只有动词也不算过 —— 见 C2"},
    {"id": "C2", "name": "动作后有具体对象",
     "test": lambda a: bool(re.search(r"(查|确认|点击|发起|联系|提交|下载)[^。；，]{2,}", a)),
     "why": "区分「已发货」和「查订单页的物流单号」"},
    {"id": "C3", "name": "长度不少于 40 字",
     "test": lambda a: len(a) >= 40,
     "why": "太短的回答通常信息量不足（近似判据，粗糙但稳定）"},
    {"id": "C4", "name": "没有编造时限",
     "test": lambda a: not re.search(r"\d+\s*(小时|天|工作日)内(一定|保证|肯定)", a),
     "why": "无来源的承诺是第 5 章讲的幻觉，要单独拦"},
    {"id": "C5", "name": "引用了订单状态而不是泛泛而谈",
     "test": lambda a: bool(re.search(r"物流|订单|签收|售后", a)),
     "why": "把回答锚定在具体场景上"},
]

SAMPLES = [
    ("差：把问题推回给用户", "请联系客服。"),
    ("差：只有铺垫没有动作", "这种情况很常见，不用担心，耐心等待就好了，一般都会到的，请放心。"),
    ("中：有动作但太笼统", "你可以去查一下物流情况，然后根据需要决定要不要申请售后处理。"),
    ("好：动作具体、可执行", "先查物流单号；若超过 7 天未更新，点「申请售后」→「未收到货」，我们会在 24 小时内跟进。"),
    ("差：编造了时限承诺", "别担心，我们保证 2 小时内一定送到，请耐心等待，你也可以随时联系我们查询。"),
]


def judge(answer):
    return [c for c in CRITERIA if not c["test"](answer)]


if __name__ == "__main__":
    print("判据（可判定、可复现、单一）：")
    for c in CRITERIA:
        print("  %-4s %s" % (c["id"], c["name"]))
    print()
    print("逐条判定：")
    print()
    for label, ans in SAMPLES:
        failed = judge(ans)
        tag = "✅ 全过" if not failed else "❌ 未过 %s" % ",".join(c["id"] for c in failed)
        print("  %-22s %s" % (label, tag))
        print("      「%s」" % (ans[:44] + ("…" if len(ans) > 44 else "")))
        for c in failed:
            print("        · %s —— %s" % (c["name"], c["why"]))
        print()
    print("注意最后一条：它同时通过 C1/C2/C3/C5，只有 C4 拦住它。")
    print("如果判据里没有 C4，一个「编造了时限承诺」的回答会被判为合格 ——")
    print("而第 5 章实测过，编造时限正是模型最常见的幻觉形态之一。")
```

### 判据放哪，怎么被 CI 调起

上面那段是**判据清单**，它不该散在某个脚本里。放法：`evals/criteria.py` 只放清单（`CRITERIA`）与判定函数（`judge`），`evals/run_criteria.py` 做 CI 入口 —— 任何一条样例被拦就返回非零退出码，CI 才会红：

```python
# evals/run_criteria.py —— CI 入口：任何一条样例被拦就 fail
import sys
from criteria import judge, SAMPLES

bad = []
for label, ans in SAMPLES:
    failed = judge(ans)
    if failed:
        bad.append((label, failed))
for label, failed in bad:
    print("FAIL %s：%s" % (label, ",".join(c["id"] for c in failed)))
sys.exit(1 if bad else 0)
```

CI 里跑一行 `python evals/run_criteria.py` 就够。**这就是「判据可判定」这句话的落地形态** —— 它能进 CI，而且不会随心情变化。至于判据清单本身怎么演化（哪些题进哪层、多久体检一次），是第 11 节的内容。

## 常见坑

- **把三条轴揉成一个分数。** 分数降了 5%，你不知道该改哪一层。
- **用「不错」「专业」这类词当判据。** 那不是判据，是印象 —— 不可复现、不可比较、不可归因。
- **从「什么是好」开始定义。** 从反例开始更容易：翻历史失败案例，给每个写一句「怎么发现它」。
- **判据不可判定就直接放弃。** 通常能找到可判定的近似（比如「切题」近似成「包含关键词」）。
- **忘记检查区分度。** 一条永远通过的判据等于没有判据 —— 它测不出任何改动的效果。
