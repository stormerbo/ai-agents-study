前面几节都在讲**指标与题目**。这一节讲一个更容易被忽略的东西：**被测的那个世界**。

先看一个实验。我搭了一个最小的工具型任务：环境里有三笔退款申请 `R-001/R-002/R-003`，
问模型「现在有多少笔退款申请」。

```text
干净环境（3 条）                模型答：3   ✓
未重置环境（3 条 + 2 条脏数据）    模型答：5   ✗
```

**真实记录数始终是 3。** 模型答 5 不是模型的错 —— 它老老实实读了工具返回的 5 条，
只不过那 5 条里有 **2 条是上一轮跑完没清理掉的**。

这就是本节要说的第一件事：

> **你测出来的分数，是「模型 + 环境」这个组合的属性，不是模型的属性。**

## 一、评测环境的五个要素

一个能复现的评测环境，至少要把五件事定清楚：

| 要素 | 说清楚什么 | 不定清楚的后果 |
| --- | --- | --- |
| **初始状态** | 开始前世界是什么样 | 跑第二次结果就变了（上面那个实验） |
| **工具集** | 有哪些工具、返回什么格式 | 换一版工具描述就测不出是不是模型变好 |
| **终止条件** | 什么算「做完了」 | 有的跑到 3 步就停，有的跑到 20 步 |
| **验证器** | 判成功的依据是什么 | 分数不可复现，两人打分不同 |
| **隔离方式** | 每个用例之间怎么互不影响 | 用例顺序会影响结果 |

这五条里，**初始状态和隔离方式是工程上最容易漏、后果最严重的两条**。
它们不会让评测报错，只会让分数悄悄偏移。

## 二、为什么「状态污染」特别难发现

上面那个实验的失败形态很典型：分数从 3 变成 5，**看起来像是模型多找出了两笔**，
你甚至可能觉得这是好事。

真正的问题在于**它不会报错**。环境没重置不会抛异常，工具照常返回、模型照常作答、
验证器照常打分 —— 只是打在一个错的世界状态上。

更麻烦的是它**有方向性**：状态通常只会累积（上一条测试留下的数据还在），
所以错误往往表现为「分数偏高」。而评测分数偏高是最不容易被质疑的方向。

## 三、一个可复用的环境骨架

先给「初始状态」一个真实形态 —— 它是五要素里第一个，也是最容易被写成 `{}` 的一个（示例：构造数据，未实跑）：

```json
{
  "refunds": ["R-001", "R-002", "R-003"],
  "orders": {"A-1001": {"status": "已发货", "amount": 1288.50}},
  "audit": []
}
```

它要满足一个判据：**一个用例跑完之后，这份状态必须能被完整还原。** 凡是 agent 执行中会改的东西（表、文件、审计日志）都要在这里；只读的外部依赖（比如一个固定的政策文档）不必进，但要单独记录版本。

下面这段是评测环境的正确形状。关键不是代码复杂度，而是**每个用例前后都有明确的边界**。

```python
import copy


class EvalEnv:
    """一个可复现的评测环境。核心是 setup / teardown 成对出现。"""

    def __init__(self, initial_state):
        self.initial = copy.deepcopy(initial_state)
        self.state = None

    def setup(self):
        """每个用例开始前必须调用。深拷贝 —— 否则 initial 会被第一次跑坏。"""
        self.state = copy.deepcopy(self.initial)
        self.trace = []

    def teardown(self):
        """每个用例结束后必须调用。断言状态已回到初始。"""
        assert self.state == self.initial, (
            "环境没回到初始状态：%r" % (self.state,)
        )
        # 故意不在这里重置 —— 让忘记 setup 的代码在下一次跑时立刻暴露

    def call_tool(self, name, args):
        self.trace.append((name, args))
        if name == "list_refunds":
            return {"refunds": list(self.state["refunds"])}
        raise ValueError("未知工具: %s" % name)


def run_case(initial_state, case, agent_fn):
    """一个用例 = 一个新的环境实例 + 一次 agent 执行。

    三个参数语义固定：initial_state 是世界初始快照，case 是这个用例的输入，
    agent_fn(env, case) 是被测系统。分开传，避免「环境」与「用例」互相污染。
    """
    env = EvalEnv(initial_state)
    env.setup()
    try:
        result = agent_fn(env, case)
    finally:
        env.teardown()          # finally —— 用例抛异常也要清理
    return result
```

三个设计点值得单独说：

**一、`setup` 用深拷贝。** 直接赋值会让 `initial` 被第一次运行改掉，
于是第二次的「初始状态」已经不是初始状态了。

**二、`teardown` 里那句 `assert`。** 它把「环境没清干净」变成一个**立刻失败**，
而不是让污染悄悄流到下一个用例。这比事后分析轨迹便宜得多。

**三、`teardown` 故意不自动重置。** 如果它顺手帮你重置了，
那么忘记调 `setup` 的用例仍然能跑对 —— 污染就被掩盖了。**让它暴露，比让它自愈更有价值。**

### 验证器、终止条件、隔离方式

上面骨架只解决了「初始状态」这一要素，另外三样各给一个可执行形态（示例：构造数据，未实跑）：

```python
# ---- 验证器：判定成功看**环境终态**，不看模型说了什么 ----
def validate(env, case):
    return env.state["refunds"] == case["expect_refunds"]

# ---- 终止条件：先给硬上限，再给「目标达成」 ----
def should_stop(env, case, step):
    if step >= case.get("max_steps", 8):
        return "steps_exhausted"                 # 硬上限，防止不收敛
    if env.state["refunds"] == case["expect_refunds"]:
        return "solved"                          # 目标达成
    return None

# ---- 隔离方式：每个用例一个新环境实例（进程内最简单的一种）----
# 需要更强隔离时换成「每用例一个新 schema / 一个新容器」，判据不变：
# 用例 A 结束后，用例 B 看到的世界必须只有 B 的初始状态。

CASE = {"id": "refund-count", "expect_refunds": ["R-001", "R-002", "R-003"]}
```

三样的分工要记清：**验证器回答「算不算成功」，终止条件回答「什么时候停」，隔离方式回答「用例之间看不看得见」。** 少任何一样，分数都不再可复现。

**实跑状态**：本节的环境骨架与三条自检在 2026-10-12 的修复中跑通；开头那个退款实验的 3 / 5 是实测数据（2026-10-09）。

### 一个真实的报错

我第一次写这个骨架时，`teardown` 里写的是：

```python
def teardown(self):
    self.state = copy.deepcopy(self.initial)     # 错
```

看起来很贴心，实际上它让整套机制失效了：**`setup` 从此变成可选的**，
漏调也不会被发现，而污染依旧会在 `setup` 缺失时发生。
正确的做法是**让 teardown 只负责检查，不负责修复**。

## 四、怎么发现你的环境在污染分数

上面那个实验是我**故意构造**出来的，所以一眼能看出问题。真实场景里不会这么明显。
三个可操作的检测办法，按成本从低到高：

**一、把同一套用例连跑两遍，比较两次分数。**
如果第二次和第一次不同，环境里一定有跨用例的状态。这是最便宜的自检，
一条命令就能做，而且能抓到绝大多数显式污染。

**二、打乱用例顺序，再跑一遍。**
如果分数随顺序变化，说明用例之间存在依赖 —— 要么共享了状态，要么前一个用例
改变的全局配置影响了后一个。这一条比第一条更严格：连跑两遍只能发现「累积型」污染，
换顺序能发现「相互干扰型」。

**三、换并发度再跑一遍。**
这一条针对的是批量并发：如果你的评测框架并发跑用例，而它们共享一个环境实例，
那么结果会随并发度变化。判据很简单 —— **把并发度从 1 调到 4，看分数是否变**。
变了就说明环境没有做到用例级隔离，不变才说明隔离成立。它和前两条测的不是同一件事：
前两条测「状态有没有跨用例泄漏」，这一条测「并发路径与串行路径是不是同一个世界」。

这三条都可以写成自动化检查，放进评测脚本里：

```python
from concurrent.futures import ThreadPoolExecutor


def check_environment_stability(initial_state, cases, agent_fn):
    """三条环境自检。任何一条不过，先修环境，别看分数。"""

    def run_all(cs):
        return [run_case(initial_state, c, agent_fn) for c in cs]

    # 一、同一套用例连跑两遍
    a = run_all(cases)
    b = run_all(cases)
    if a != b:
        return "❌ 两次运行结果不同 —— 存在跨用例状态"

    # 二、打乱顺序（反过来跑，再把结果翻回来）
    c = list(reversed(run_all(list(reversed(cases)))))
    if c != a:
        return "❌ 换顺序后结果不同 —— 用例之间互相干扰"

    # 三、换并发度：并发 4 与串行必须给出同一个世界
    with ThreadPoolExecutor(max_workers=4) as ex:
        d = list(ex.map(lambda x: run_case(initial_state, x, agent_fn), cases))
    if d != a:
        return "❌ 并发度 4 与串行结果不同 —— 用例之间没有做到隔离"

    return "✅ 环境自检通过"
```

**这三条应该跑在评测之前，而不是跑完之后。** 理由很直接：
如果环境不稳定，后面所有关于「模型变好还是变坏」的讨论都没有意义 ——
你只是在比较两个不同的世界。

## 五、两种形态的环境，难点不一样

评测环境大体分两类，它们的工程难点完全不同：

**工具调用型。** 世界状态是明确的（数据库、文件、API 返回），验证器可以写成代码。
上面那个退款实验就是这一类。

**它的难点是「状态与隔离」** —— 也就是本节前半部分讲的那些。
好处是判定客观，坏处是要把被测系统周围的那一圈全部模拟出来，工作量往往比写 agent 本身还大。

**人机交互型。** 世界状态里有一个「人」，它的反馈是模型生成的或人扮演的。
客服、销售、谈判类任务属于这一类。

**它的难点是「反馈的一致性」** —— 同一个用户输入，扮演者这次说「可以」、下次说「不行」，
分数就不可比了。缓解办法有两个：**把扮演者的提示词固定并版本化**，
以及**同一组用例上固定扮演者的种子**（如果你的扮演者也是模型，至少把参数固定）。

还有第三个不那么显眼但很重要的区别：**工具调用型的失败通常可归因，
人机交互型的失败常常无法归因**。前者你能看到「调了哪个工具、传了什么参数」，
后者你只有一段对话，而「这次为什么没谈成」可能连人自己也说不清。
所以人机交互型任务更适合用**配对比较**（下一节讲）而不是绝对分数。

## 六、环境也是被测系统的一部分

这一节最容易被读成「工程细节」。但它的推论其实很硬：

**如果你改了环境，之前的评测结果就不能直接对比。**

常见的情形：你为了修一个 bug 改了工具的返回格式（比如从字符串改成结构化对象），
然后发现分数涨了 8 个百分点。**这 8 个百分点里有多少来自模型、多少来自环境？**
如果你没把环境版本记下来，这个问题没有答案。

所以评测报告里至少要记三样：**模型版本、提示词版本、环境版本**。
少一样，跨时间的比较就不可解释。

## 七、小结

- **分数是 (模型 + 环境) 的属性** —— 环境未重置时，模型答 5 而真实值是 3
- **环境五要素**：初始状态、工具集、终止条件、验证器、隔离方式
- **状态污染不报错且有方向性**：通常让分数偏高，而偏高最不易被质疑
- **`setup` 要深拷贝，`teardown` 只检查不修复** —— 让它暴露，比让它自愈有价值
- **环境改动会让历史分数不可比**，所以报告要记录模型/提示词/环境三个版本

一句话收尾：**在你怀疑模型之前，先确认世界是对的。**
我看到「模型答 5」时的第一反应是去查模型为什么多数了两笔，
而正确答案是**环境里本来就有五笔** —— 模型一点错都没有。
这类误判的代价很高，因为它会让你去改一个根本没坏的东西 —— 而真正的 bug 还留在那儿，下一次它换个形态再咬你一口 —— 而那时你已经忘了上一轮这处误判。
