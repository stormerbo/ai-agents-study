有些东西代码判不了 —— 「这段回答好不好」「这个摘要抓到重点没有」。这时候需要一个判断者。模型判分是可规模化的选项之一，尤其适合开放式文本；确定性规则、检索/事实核验、成对人工标注和人工抽审也都能承担一部分判分工作。应按判据选择组合，不能把 LLM judge 当成唯一方案或真值。

用模型打分（LLM-as-judge）有两个绕不开的问题：**它在什么条件下与目标判据一致**，以及**它的分数意味着什么**。研究已报告位置、冗长和自我偏好等风险，但它们会随模型、任务、提示和样本变化；本节旧实验的逐次原始响应、完整请求与评分器版本没有归档，无法独立重放，因此只能作为历史摘要，不能据此说偏见已被排除。

## 已报道的三个偏差风险

研究讨论过多种可能的系统性偏差，下面三个是便于设计检查的例子，不是穷尽清单；具体表现依赖模型、任务、提示和答案分布。基础研究报告过位置、冗长、自我偏好等现象，并提出对调顺序等缓解办法；这不代表每个 judge 都必然出现这些偏差。[来源：Zheng 等，MT-Bench 研究](https://arxiv.org/abs/2306.05685)；提示注入防护背景见 [OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)。

1. **位置偏见**：同一对答案，放在 A 还是 B 会改变结论
2. **冗长偏见**：偏好更长的回答，即使长的更差
3. **自我偏好**：偏好自己（或同族模型）生成的答案

前两个可以设计对照检查，但小样本中没有观察到翻转不能证明偏差不存在。下面保留的是 2026-10-09 的历史记录摘要；当前没有原始逐次响应、完整请求、采样配置和 scorer 版本，数字无法独立复算。它们适合说明实验设计和解释风险，不作为模型稳定性或偏差率证据。

## 实验一：位置偏见（悬殊对）

4 组「好 vs 明显差」的答案对。每组判两次：一次好的放 A，一次好的放 B。

| 组 | 好的在 A 时 | 好的在 B 时 | 结论 |
|---|---|---|---|
| P1 | A（对） | B（对） | 两次都判对 |
| P2 | A（对） | B（对） | 两次都判对 |
| P3 | A（对） | B（对） | 两次都判对 |
| P4 | A（对） | B（对） | 两次都判对 |

旧记录报告位置翻转 0/4、与人工标注一致 8/8；因逐次原始结果和人工标签未归档，**这些计数无法独立复核，不能解释为 100% 准确或无位置偏差**。

## 实验二：位置偏见（接近对）—— 把难度调上来

第一轮的对太悬殊，判断题太容易，偏见可能根本没机会出现。所以第二轮用**两个都合理、差别很小**的答案对，每题判三次：

| 组 | run1 | run2（同序重复） | run3（对调） | 重复一致性 | 位置 |
|---|---|---|---|---|---|
| C1 | B | B | A | ✅ 一致 | ✅ 同一个答案 |
| C2 | A | A | B | ✅ 一致 | ✅ 同一个答案 |
| C3 | B | B | A | ✅ 一致 | ✅ 同一个答案 |
| C4 | B | B | A | ✅ 一致 | ✅ 同一个答案 |

旧记录报告同序一致 4/4、换序后仍选同一答案 4/4；该记录没有足够原始材料供独立复算。即使数字准确，它也只描述这 4 组与当时配置，不能支持总体偏差为零。

旧记录自述该组数据于 2026-10-09 在 `deepseek-flash` 上运行；逐次原始响应与配置未归档，现无法独立重放。

注意这张表怎么读：C1 的 run1 选 B、run3 选 A —— 看起来像翻转，其实不是。按旧记录对候选身份的对应，run1 里 B 是「较完整那个」，run3 里它被放到了 A 位，判官仍然选了它。**它选的是同一个答案，不是同一个位置。** 如果这份摘要准确，这四对里没有观察到换序导致的答案身份翻转；但逐次输出缺失、样本也很少，所以它只能描述这组记录，不能证明 judge 没有位置偏差。

## 一个我差点写错的结论

实验二跑完时，我注意到一件事：**4/4 都选了更长、更详细的那个答案。**

一个自然的结论是「存在冗长偏见」。但我停下来问了一句：**在我的这几组对照里，「更长」和「更完整」是不是同一件事？**

我构造答案时，更完整的版本自然更长。这个对照无法区分「偏好完整度」与「偏好长度」，也可能同时受具体措辞等因素影响；所以 4/4 不能支持其中任一种解释。

**若要区分长度与完整度**，需在保持任务信息、正确性和风格尽可能可比时单独操纵长度，并重复运行；简单造一个“长但差”的版本仍可能混入相关性、重复和语气等因素。旧记录里的第三组是一次尝试，不构成经过验证的因果设计。

## 实验三：冗长偏见（长答案注水）

旧记录称设置了 3 组对照，每组包含短答案和被扩写的长答案。由于完整 prompt、逐次响应及评分器缺失，无法检查长度之外的相关差异是否被控制。

| 组 | 短答案在 A 时 | 短答案在 B 时 | 结论 |
|---|---|---|---|
| V1 | A（短） | B（短） | 两次都选短 |
| V2 | A（短） | B（短） | 两次都选短 |
| V3 | A（短） | B（短） | 两次都选短 |

旧记录报告选择注水长答案为 0 / 6；该数字无法独立复核。

冗长注水版长这样（实际用的材料）：

```text
「这个问题确实比较常见，首先我想说的是，遇到这种情况请不要着急，因为物流运输涉及
  多个环节，包括仓储、分拣、干线运输、末端配送等等，每个环节都可能出现延迟。……」
（大量铺垫，最后只给出一句「如果超过 7 天没有更新，那么你可以发起售后。」）
```

干脆版是：

```text
「先查物流单号；若超过 7 天未更新，发起售后，我们代为跟进。」
```

历史摘要称两种顺序下都选了短答案；原始逐次输出不可用，不能复算这一结果。

旧记录称另外两组（V2、V3）也使用了同题的短答案与注水长答案对照；逐次原始 prompt 和完整候选未归档，下面只保留旧文中登记的示例摘要：

```text
【V2 短】若物流显示已签收但你未收到，属于投递异常，请立即发起售后并选择「未收到货」。
【V2 长】关于这个问题，我们需要具体情况具体分析。物流状态有很多种，比如已揽收、
        运输中、派送中、已签收等等。不同的状态对应不同的处理方式。……（大量并列铺陈，
        最后停在「建议你联系客服」）

【V3 短】查物流单号 → 若停滞超 3 天，属于异常件，发起售后，24 小时内处理。
【V3 长】感谢你的提问。关于订单物流的问题，这是一个在电商购物中非常普遍的情况。
        首先，我们要理解物流的基本流程：商家发货后，包裹会进入快递公司的网络……
        （通篇流程科普，最后停在「建议你保持关注」）
```

这些材料意在构造“更长但较差”的候选，但长度同时伴随信息密度、相关性和语气变化；因此它们没有单独识别长度效应。

因此，这些旧摘要**不能得出“位置偏差或冗长偏差未复现”这样的实证结论**。历史材料中，长答案同时更完整，构造混淆使“长度偏好”与“内容完整度偏好”无法区分。注水版本的记录也缺少逐次响应和 scorer，不能证明该 judge 不受长度影响。

（三组实验的历史登记数字为：位置翻转 0/12、同序重复一致 4/4、注水长答案被选 0/6；均未独立复核，不代表总体偏差率。）

## 但这不等于「judge 可以放心用」

旧记录不能支持「在我的场景里它很稳」：样本小、材料由作者构造、且原始输出缺失。即便某次可复核实验没有观察到问题，也只能说明在该样本、模型快照、提示、解码设置和判据下未观测到相应现象。

**第一，我的对照是我自己写的。** 我知道哪一个是好答案，也是我构造的材料 —— 这意味着我可能在无意中把「好」写得很显眼（用词更具体、结构更清楚）。真实的线上答案对往往没有这么明显的差别。

**第二，成对比较与绝对打分有不同误差来源。** 成对判断避免了直接解释分数刻度的问题，但仍会受候选顺序、候选组合与判据影响；绝对分数若没有分档 rubric，同样难解释。不能据此断言一种方法对所有任务都更稳定。

**第三，观测结果只适用于实际样本与配置。** 小样本没看到某种现象，不能估计其在目标总体中的发生率；应设计能暴露敏感性的检查、保留不确定结果，并用独立参考评估影响。

## 降低误判风险的四条做法

**一、对调顺序，测敏感性并保留不确定结果。** 对同一候选对分别跑 (A,B) 与 (B,A)，按候选身份而非字母比较结果；若不一致，记录为不确定并送人工复核。两次一致只是一个诊断信号，**不能保证消除位置影响**：共同偏好、提示模板、候选风格、模型随机性和判据缺陷仍可能影响两次结果。分析时同时报告翻转比例、无效/平局比例，以及 judge 对 A/B 槽位的选择分布；仅统计翻转会漏掉稳定偏向某一槽位的情况。对高风险或重要指标，要在代表性样本上做重复、人工对照并报告不确定性。

**二、把长度从判据里排除。** 如果长度不该影响质量，就在提示里明确说「长度本身不是评判标准」，或者在评分量规里把长度单独列出、不并入总分。

**评分量规是什么？** 它指的是给绝对打分（「1 到 5 分」）用的**分档描述** —— 每一档对应一组可观察行为，而不是一个形容词。没有量规的 1-5 分就是五个印象。前面说「3 分和 4 分的界限没有定义」，量规就是把那个界限写出来：

| 档 | 可观察行为 |
|---|---|
| 5 | 给出了可执行的下一步，引用了正确的订单状态，没有编造时限；用户不需要再追问 |
| 3 | 方向正确但停在泛泛的建议（「联系客服」这类），或缺少场景里的关键字段 |
| 1 | 与问题无关、把责任推回用户、或包含无来源的承诺 |

写量规的判据同第 1 节：**每一档必须描述「能看到什么」，不能描述「感觉多好」。** 档数不用多，三档就够用（对应「不合格 / 及格 / 可直接用」）。

**三、用清单式判据，而不是整体印象。** 不要问「哪个更好」，问「哪一个满足以下三条：① 给出了可执行下一步 ② 引用了正确的订单状态 ③ 没有编造时限」。清单式判据能把评测目标说清楚，但不会自动让 judge 正确；仍需检查判据覆盖性、误报/漏报及人工一致性。

**四、留出人工参考集并持续审计。** 在与开发/提示调优样本分离、且覆盖目标任务分层的样本上，由人工按同一 rubric 标注，再比较 judge。样本量没有通用的「20 到 30 条」门槛：应根据目标总体、类别占比、可接受误差和所需检验功效规划；小样本可用于发现明显问题，但不能支撑很精确的总体估计。若同一批项目由人和 judge 配对标注，比较版本时应估计**配对差异**的不确定性，不能拿某个区间的半宽直接当通用告警阈值。记录至少固定抽样规则、项目/标签、judge 与提示版本、重复策略及分歧处理方式。示例数据（构造，未实跑）：

```json
{"date": "2026-10-12", "n": 30, "agree": 24, "rate": 0.800,
 "judge_version": "judge-v2", "criteria_version": "c3"}
```

**两次记录之间才看得出趋势**；单次的 0.800 只是一个点，不构成「下降」。

## 三个高风险误用场景

下面场景中，若把 judge 单独当作确定门禁，分数会掩盖它的不确定性。它可以用于筛查，但应结合可信信源、人工复核或确定性检查。

**一、需要外部事实的判定。** 若答案依赖数据库、文档或当前状态，应以可信数据源、程序化约束或领域专家为事实依据。Judge 可以在给定证据的前提下辅助检查回答是否被证据支持，但它本身不能替代事实源、授权检查或确定性校验。

**二、需要专业判断的判定。** 例如代码并发安全、医疗或法律结论，judge 可作为筛查/解释辅助，但不应仅凭模型自身判断作最终验收。是否可用取决于具体任务、所给证据、错误代价以及是否有专家复核；不能一概断言它与生成者知识边界相同。

**三、判据本身还没定义清楚的。** 这是最容易踩的一个：判据不清楚时，judge 仍可能给出看似精确的分数，但它没有明确的目标含义，不能解释成产品质量。**先把判据写清楚，再上 judge** —— 顺序反了会得到一份看起来很专业、实际测不出东西的评分表。

## 完整可运行代码

下面代码用合成标签演示如何按候选身份比较交换顺序后的结果，并拒绝歧义输出。它只验证解析与聚合逻辑，**不调用模型，也不能复现历史实验或证明 judge 的偏差**。

**实跑状态**：Python 3.14.7，本地离线运行通过；不访问 provider 或外部服务。

```python
"""离线演示：如何按候选身份比较交换顺序后的 judge 标签。

这是评分/聚合契约的合成演示，不调用 LLM，也不复现本节的历史结果。
"""
import re

def parse_choice(text):
    """只接受唯一标签，拒绝解释性或含糊输出。"""
    match = re.fullmatch(r"(?:answer\s*:\s*)?([AB])(?:[.!])?", text.strip(), re.I)
    if not match:
        raise ValueError(f"invalid judge label: {text!r}")
    return match.group(1).upper()

def compare_swapped(original, swapped):
    """original: good 在 A；swapped: 同一 good 答案移到 B。"""
    first = parse_choice(original)
    second = parse_choice(swapped)
    first_winner = "good" if first == "A" else "bad"
    swapped_winner = "bad" if second == "A" else "good"
    return {
        "status": "order_invariant" if first_winner == swapped_winner else "order_sensitive",
        "winner_original": first_winner,
        "winner_swapped": swapped_winner,
    }

examples = [
    ("stable-content-choice", "A", "B"),
    ("same-slot-choice", "A", "A"),
]
for case_id, first, swapped in examples:
    print(case_id, compare_swapped(first, swapped))

try:
    parse_choice("A or B")
except ValueError as error:
    print("invalid-output-rejected", error)
```

## 常见坑

- **把两次对调当成偏见消除保证。** 它是敏感性检查；一致不等于结论正确，分歧应保留并复核。
- **用「哪个更好」这种整体印象提问。** 尽量把目标拆成可观察判据，再用人工参考验证这些判据是否覆盖目标。
- **没做对照组就宣布「有偏见/没偏见」。** 我差点把「偏好完整」写成「冗长偏见」，是因为对照里长度和完整度是同一件事。
- **让它判需要外部事实的事。** 那应该查库或查文档，不该问 judge。
- **判据还没定义清楚就上 judge。** 它会给一个稳定的数字，而那个数字测的是它自己。
- **没有独立人工参考。** 定期复核有助于发现 judge 与判据漂移；按目标总体、分层和误差容忍度规划样本，不把小样本一致率误当成普遍准确率。
