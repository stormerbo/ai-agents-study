有些东西代码判不了 —— 「这段回答好不好」「这个摘要抓到重点没有」。这时候需要一个判断者。模型判分是可规模化的选项之一，尤其适合开放式文本；确定性规则、检索/事实核验、成对人工标注和人工抽审也都能承担一部分判分工作。应按判据选择组合，不能把 LLM judge 当成唯一方案或真值。

用模型打分（LLM-as-judge）有两个绕不开的问题：**它有没有偏见**，以及**它的分数意味着什么**。这一节用三组实测来回答第一个。

## 先看它被判死刑的三个理由

文献和工程经验里，模型当裁判最常见的三个偏见是：

1. **位置偏见**：同一对答案，放在 A 还是 B 会改变结论
2. **冗长偏见**：偏好更长的回答，即使长的更差
3. **自我偏好**：偏好自己（或同族模型）生成的答案

前两个是可以直接测的。我测了，**两个都没有复现**。下面是过程和数据 —— 包括我一开始差点得出错误结论的那一步。

## 实验一：位置偏见（悬殊对）

4 组「好 vs 明显差」的答案对。每组判两次：一次好的放 A，一次好的放 B。

| 组 | 好的在 A 时 | 好的在 B 时 | 结论 |
|---|---|---|---|
| P1 | A（对） | B（对） | 两次都判对 |
| P2 | A（对） | B（对） | 两次都判对 |
| P3 | A（对） | B（对） | 两次都判对 |
| P4 | A（对） | B（对） | 两次都判对 |

**位置偏见 0/4，与人工标注一致 8/8（100%）。**

## 实验二：位置偏见（接近对）—— 把难度调上来

第一轮的对太悬殊，判断题太容易，偏见可能根本没机会出现。所以第二轮用**两个都合理、差别很小**的答案对，每题判三次：

| 组 | run1 | run2（同序重复） | run3（对调） | 重复一致性 | 位置 |
|---|---|---|---|---|---|
| C1 | B | B | A | ✅ 一致 | ✅ 同一个答案 |
| C2 | A | A | B | ✅ 一致 | ✅ 同一个答案 |
| C3 | B | B | A | ✅ 一致 | ✅ 同一个答案 |
| C4 | B | B | A | ✅ 一致 | ✅ 同一个答案 |

**重复一致性 4/4，位置偏见 0/4。**

（实跑数据，2026-10-09，`deepseek-flash`。）

注意这张表怎么读：C1 的 run1 选 B、run3 选 A —— 看起来像翻转，其实不是。run1 里 B 是「较完整那个」，run3 里它被放到了 A 位，判官仍然选了它。**它选的是同一个答案，不是同一个位置。** 这正是没有位置偏见的证据。

## 一个我差点写错的结论

实验二跑完时，我注意到一件事：**4/4 都选了更长、更详细的那个答案。**

一个自然的结论是「存在冗长偏见」。但我停下来问了一句：**在我的这几组对照里，「更长」和「更完整」是不是同一件事？**

是。我构造答案时，更完整的版本自然更长。所以这 4/4 完全可以用「它偏好更完整」来解释 —— 而那不是偏见，是正确的。

**要分离开这两者，必须让长答案更差。** 于是有了实验三。

## 实验三：冗长偏见（长答案注水）

3 组对照，每组的**长答案故意注水**：绕、重复、答非所问地扩写；短答案干脆准确。

| 组 | 短答案在 A 时 | 短答案在 B 时 | 结论 |
|---|---|---|---|
| V1 | A（短） | B（短） | 两次都选短 |
| V2 | A（短） | B（短） | 两次都选短 |
| V3 | A（短） | B（短） | 两次都选短 |

**选到注水长答案的次数：0 / 6。**

冗长注水版长这样（实际用的材料）：

```text
「这个问题确实比较常见，首先我想说的是，遇到这种情况请不要着急，因为物流运输涉及
  多个环节，包括仓储、分拣、干线运输、末端配送等等，每个环节都可能出现延迟。……」
（大量铺垫，最后只给出一句「如果超过 7 天没有更新，那么你可以发起售后。」）
```

干脆版是：

```text
「先查物流单号；若超过 7 天未更新，发起售后，我们代为跟进。」
```

判官 **6 次全部选了短的那条**，两种顺序下都是。

另外两组材料（V2、V3，同样是实跑时用的原文；为省篇幅只列短答案，长答案都是同题注水版）：

```text
【V2 短】若物流显示已签收但你未收到，属于投递异常，请立即发起售后并选择「未收到货」。
【V2 长】关于这个问题，我们需要具体情况具体分析。物流状态有很多种，比如已揽收、
        运输中、派送中、已签收等等。不同的状态对应不同的处理方式。……（大量并列铺陈，
        最后停在「建议你联系客服」）

【V3 短】查物流单号 → 若停滞超 3 天，属于异常件，发起售后，24 小时内处理。
【V3 长】感谢你的提问。关于订单物流的问题，这是一个在电商购物中非常普遍的情况。
        首先，我们要理解物流的基本流程：商家发货后，包裹会进入快递公司的网络……
        （通篇流程科普，最后停在「建议你保持关注」）
```

三组的长答案共同点是：**字数更多、信息更少、结尾更软** —— 这正是用来分离「偏好长」与「偏好完整」的对照形态。

**所以：位置偏见未复现，冗长偏见也未复现。** 而实验二那个「4/4 偏好更长」，到这里被解释清楚了 —— 它偏好的是**完整**，不是**长度**。

（三组实验合计：位置偏见 0/12、重复一致性 4/4、冗长偏见 0/6。）

## 但这不等于「judge 可以放心用」

我把三个实验都做完了，结论是「在我的场景里它很稳」。但这个结论的边界要说清楚，否则它会被误用。

**第一，我的对照是我自己写的。** 我知道哪一个是好答案，也是我构造的材料 —— 这意味着我可能在无意中把「好」写得很显眼（用词更具体、结构更清楚）。真实的线上答案对往往没有这么明显的差别。

**第二，我测的是「哪个更好」，不是「打几分」。** 相对比较比绝对打分容易得多。要给单个答案打 1 到 5 分，稳定性会差很多 —— 因为「3 分和 4 分的界限在哪」本身就没有定义。

**第三，偏见是概率性的。** 12 次里没出现，不代表第 13 次不会。所以工程做法不是「相信它没有偏见」，而是**设计上让偏见无法影响结论**。

## 让偏见无法影响结论的四条做法

**一、对调顺序，取一致的结果。** 判定 (A,B) 和 (B,A)，只有当两次指向同一个答案时才采纳。两次矛盾的一律标为「不确定」交给人看 —— 这条能把位置偏见的影响直接消掉，不需要它不存在。

**二、把长度从判据里排除。** 如果长度不该影响质量，就在提示里明确说「长度本身不是评判标准」，或者在评分量规里把长度单独列出、不并入总分。

**评分量规是什么？** 它指的是给绝对打分（「1 到 5 分」）用的**分档描述** —— 每一档对应一组可观察行为，而不是一个形容词。没有量规的 1-5 分就是五个印象。前面说「3 分和 4 分的界限没有定义」，量规就是把那个界限写出来：

| 档 | 可观察行为 |
|---|---|
| 5 | 给出了可执行的下一步，引用了正确的订单状态，没有编造时限；用户不需要再追问 |
| 3 | 方向正确但停在泛泛的建议（「联系客服」这类），或缺少场景里的关键字段 |
| 1 | 与问题无关、把责任推回用户、或包含无来源的承诺 |

写量规的判据同第 1 节：**每一档必须描述「能看到什么」，不能描述「感觉多好」。** 档数不用多，三档就够用（对应「不合格 / 及格 / 可直接用」）。

**三、用清单式判据，而不是整体印象。** 不要问「哪个更好」，问「哪一个满足以下三条：① 给出了可执行下一步 ② 引用了正确的订单状态 ③ 没有编造时限」。**问题越具体，judge 越稳** —— 这和本节开头那条「判据必须可判定」是同一件事，只是判定者换成了模型。

**四、留一个人工校准集。** 定期抽 20 到 30 条人工标注，和 judge 的打分比。**一致率下降就是一个信号** —— 可能是 judge 漂了，也可能是你的判据变了。

**一致率怎么算、多少算下降：** 一致率 = 人工与 judge **结论相同**的条数 / 标注重数（必须是同一侧：都选 A 才算一致，不能算「都选了某一个」）。告警阈值沿用第 10 节那套区间口径：先把**校准基线**的一致率算出来，再算它的 95% 区间（30 条上这个区间并不窄），**只有下降幅度超过区间半宽才当信号**；否则先增加标注条数再判断。记录形态（示例：构造数据，未实跑）：

```json
{"date": "2026-10-12", "n": 30, "agree": 24, "rate": 0.800,
 "judge_version": "judge-v2", "criteria_version": "c3"}
```

**两次记录之间才看得出趋势**；单次的 0.800 只是一个点，不构成「下降」。

## 什么时候根本不该用它

有三类场景，模型打分给出的数字比没有数字更糟 —— 因为它会给你一种虚假的确定感。

**一、需要外部事实的判定。** 「这个答案对不对」如果依赖数据库或文档，那应该去查，不该问 judge。第 5 章那条结论在这里同样成立：能由代码验证的，不要交给模型。

**二、需要专业判断的判定。** 「这段代码有没有并发问题」—— 判官的知识边界和生成者一样。它能做的只是「看起来有没有问题」。

**三、判据本身还没定义清楚的。** 这是最容易踩的一个：判据不清楚时，judge 会给你一个稳定的数字，而那个数字测的是它自己的偏好。**先把判据写清楚，再上 judge** —— 顺序反了会得到一份看起来很专业、实际测不出东西的评分表。

## 完整可运行代码

下面这段代码跑的是实验一的形态：同一组答案对，分别在对调顺序下判两次，看结论是否跟着位置走。这是三条做法里最值得照抄的一个 —— 它不要求判官没有偏见，只要求你不被偏见影响。

```python
"""LLM-as-judge 可信吗？测两件事：位置偏见与顺序一致性。

做法：4 组「好/差」答案对，每组判两次 —— 一次 (A,B)，一次把顺序换成 (B,A)。
如果判定跟着顺序翻转，那就是位置偏见。

我自己的标注（哪一个是好答案）就是标准答案。

实跑状态：2026-10-09，deepseek-flash。
"""
import os
import json, os, urllib.request

TASK = "用户问：我的订单显示已发货但我没收到，怎么办？"

PAIRS = [
    {"id": "P1", "good": "请先在订单页确认物流单号，再联系承运方查件。若超过 7 天未更新，可在这里直接发起售后，我们会代为跟进。",
     "bad": "联系客服。"},
    {"id": "P2", "good": "已发货但未收到，通常是运输中或投递异常。先查物流单号；若物流停滞超过 3 天，属于异常件，请发起售后，我们会在 24 小时内处理。",
     "bad": "你可以申请退款，具体看你自己的情况，一般都能解决。"},
    {"id": "P3", "good": "第一步查物流单号（订单详情页）；第二步若超过 7 天未更新，点「申请售后」→「未收到货」；第三步我们会在 24 小时内联系承运方并回复你。",
     "bad": "这种情况很常见，不用担心，耐心等待就好了，一般都会到的。"},
    {"id": "P4", "good": "先查物流。若显示已签收但你没收到，属于投递异常，请立即发起售后并选择「未收到货」，我们会联系承运方核实。",
     "bad": "打客服电话。"},
]

JUDGE_SYS = ("你是一个严格的答案评审。用户会给你一个问题和两个回答（A 和 B）。"
             "请判断哪一个更好地解决了用户的问题。只输出一个字母：A 或 B。不要解释。")


def judge(task, a, b):
    body = json.dumps({"model": os.environ["VERIFY_MODEL"], "max_tokens": 3000,
                       "system": JUDGE_SYS,
                       "messages": [{"role": "user", "content":
                                     "%s\n\n回答 A：%s\n\n回答 B：%s\n\n哪个更好？只回答 A 或 B。"
                                     % (task, a, b)}]}).encode()
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages", data=body,
        headers={"content-type": "application/json",
                 "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
                 "anthropic-version": "2023-06-01"})
    with urllib.request.urlopen(req, timeout=180) as resp:
        d = json.loads(resp.read())
    if d.get("stop_reason") == "max_tokens":
        raise RuntimeError("测量故障：max_tokens 截断")
    t = "".join(x.get("text", "") for x in d.get("content", []) if x.get("type") == "text")
    t = t.strip().upper()
    return "A" if "A" in t[:4] else ("B" if "B" in t[:4] else "?")


if __name__ == "__main__":
    print("每组判两次：一次好的放 A，一次好的放 B（顺序对调）")
    print()
    print("  %-5s %-22s %-22s %s" % ("组", "好的在 A 时判", "好的在 B 时判", "结论"))
    flip = 0
    correct = 0
    for p in PAIRS:
        r1 = judge(TASK, p["good"], p["bad"])     # 好的在 A → 期望 A
        r2 = judge(TASK, p["bad"], p["good"])     # 好的在 B → 期望 B
        ok1 = (r1 == "A")
        ok2 = (r2 == "B")
        correct += ok1 + ok2
        flipped = (r1 == "A") != (r2 == "B")
        if flipped:
            flip += 1
        concl = "⚠️ 跟着顺序翻转" if flipped else ("✅ 两次都判对" if (ok1 and ok2) else "在两种顺序下都判错同一侧")
        print("  %-5s %-22s %-22s %s" % (p["id"], r1 + ("（对）" if ok1 else "（错）"),
                                          r2 + ("（对）" if ok2 else "（错）"), concl))
    n = len(PAIRS)
    print()
    print("=== 结果 ===")
    print("  位置偏见（同一对，换顺序后判定翻转）：%d / %d" % (flip, n))
    print("  与人工标注一致：%d / %d（%.0f%%）" % (correct, n * 2, correct / (n * 2) * 100))
    print()
    print("读法：如果翻转率不是 0，那么「用 judge 打分排名」这件事就不稳 ——")
    print("     同一份答案，只因为放在 A 还是 B，结论就可能不同。")
```

## 常见坑

- **只判一次就采纳。** 位置偏见是概率性的，对调判两次只在一致时才采纳，成本翻倍但结论可信。
- **用「哪个更好」这种整体印象提问。** 应该给清单式判据 —— 问题越具体，judge 越稳。
- **没做对照组就宣布「有偏见/没偏见」。** 我差点把「偏好完整」写成「冗长偏见」，是因为对照里长度和完整度是同一件事。
- **让它判需要外部事实的事。** 那应该查库或查文档，不该问 judge。
- **判据还没定义清楚就上 judge。** 它会给一个稳定的数字，而那个数字测的是它自己。
- **没有人工校准集。** 定期抽 20 到 30 条比对；与人工标注的分歧率是发现 judge 漂移的重要信号之一；也可结合评分分布、版本变更和独立评测集观察。
