前三节讲了怎么定义判据、怎么建评测集、怎么用模型打分，以及怎么定位失败。这一节把它们接进日常开发 —— 因为**一份不会被自动跑的评测集等于不存在**。

## 三层结构

第 2 节给过一个分层建议，这里是它的可执行形态：

| 层 | 题量 | 什么时候跑 | 职责 |
|---|---|---|---|
| **冒烟集** | 10-20 | 每次改动 | 拦住明显的崩坏 |
| **回归集** | 100-300 | 每天 / 发版前 | 判断改动是否值得合并 |
| **失败集** | 持续增长 | 每天 | 保证修过的问题不再回来 |

三层里最容易漏的是第三层。前两层建好之后就固定了，而**输入分布会变** —— 半年前的用户问「怎么退款」，现在问「怎么改地址」。只有失败集会跟着真实分布一起长大。

而失败集的来源就是第 4 节的追踪：**每一条线上失败都入一条用例。** 这条流水线一接上，评测集就从一个静态资产变成了一个持续生长的东西。

## 回归报告必须有三样

多数回归脚本只报一个百分比差。那是**不够的**，而且有时是误导的。我用一个 30 题的评测集演示了这件事：

```text
基线：30 题通过 26 题（86.7%）
这套评测的噪声底线（90% 区间宽度）：±20.0 个百分点

改动 A：修好 1 题、碰坏 1 题
    通过率 86.7% → 86.7%（Δ +0.0）
    退步的用例：[7]      修好的用例：[3]

改动 B：修好 2 题、没有碰坏
    通过率 86.7% → 90.0%（Δ +3.3）
    退步的用例：无        修好的用例：[11]

改动 C：修好 4 题、碰坏 2 题
    通过率 86.7% → 86.7%（Δ +0.0）
    退步的用例：[7, 8]    修好的用例：[3, 11]
```

（实跑数据，2026-10-09。纯本地模拟，因为要测的是流程与判读。）

**注意改动 A。** 它的总分**一动不动**（+0.0）—— 但它修好了一题、碰坏了一题。只看总分，这次改动看起来「没有影响」；而它实际上改变了两条用例的行为，其中一条是退化。

**再看那三个裁决。** 三个候选改动的**全部**落在噪声内（±3.3 个点对 ±20 个点的噪声底线）。这不是巧合 —— 30 题在 p≈87% 时的噪声本来就有 ±20 个点，而多数改动的预期收益只有 3 到 5 个点。

**这就是为什么回归报告必须同时给三样：**

1. **总分变化** —— 看长期趋势
2. **逐条 diff** —— 看具体动了什么（**这一项比总分重要**）
3. **噪声底线** —— 判断总分变化是否值得当真

第 3 项是多数脚本缺的。没有它，团队会追着一个 ±20 个点噪声里的 +3 个点做决策，然后下次又掉回去，反复几次之后所有人都不再相信这份评测。

## 一个反直觉的建议：优先看 diff

上面的数据支持这个建议：**总分在 30 题的量级上几乎不携带信息**（噪声 ±20 点）。而逐条 diff 携带的信息要多得多 —— 它告诉你「第 7 题从过变成不过」，而那是一个确定的事实，不受噪声影响。

所以回归脚本的输出顺序应该是：

```text
1. ❌ 退步的用例（逐条列出，这是要被 block 的）
2. ✅ 修好的用例
3. 📊 总分变化 + 噪声底线（参考）
```

**把退步放在第一位，总分放最后。** 因为退步是确定的，总分是不确定的 —— 而人天生会先看那个醒目的数字。

## 阈值怎么定

一个常见问题是「掉多少算退化」。答案取决于层：

- **冒烟集**：任何一条退步都值得看一眼（10-20 题，退步是稀有事件）
- **回归集**：单条退步要看是不是关键用例；超过 3 条退步应当 block
- **失败集**：修好的用例**不允许退回去** —— 硬阈值，零容忍

第三层的零容忍有道理：那些用例来自真实的线上失败。让它们退回去，等于把已经踩过的坑再踩一遍。

前两层的阈值**不该设成「总分掉 X%」**，因为那个数字在噪声里。**按条数设阈值比按百分比更稳** —— 条数是确定的事实。

## 接进 CI 的四个实际考虑

**一、成本。** 一次回归是几百次模型调用。所以回归集不该在每次 push 上跑 —— 冒烟集跑 push，回归集跑每日或发版前。

**二、非确定性。** 模型输出有随机性，跑一次和跑两次结果可能不同。三种处理：把 temperature 设为 0（能减少但不能消除）；对关键用例跑 3 次取多数；**把评测结果存下来做趋势对比**，而不是只看单次。第三种最实用 —— 单次的分数有噪声，但 30 次运行的**趋势**很稳。

**三、判据的回归。** 别忘了评测集自己也会坏。第 2 节讲过：通过率接近 100% 就说明它失效了。所以 CI 里应该有一条**关于评测集的检查** —— 通过率过高时报警，提示「该补充难题或更新题目了」。

**四、人工校准。** 如果用了模型打分（第 3 节），要定期抽 20 到 30 条人工标注比对。**一致率下降是唯一能发现 judge 漂移的信号** —— 没有它，你会在 judge 悄悄改变偏好之后继续相信它的分数。

## 回到第 1 节

这一章从「先把好定义清楚」开始，到这里收口。三节的链条是：

**判据可判定**（第 1 节）→ **评测集有区分度且够大**（第 2 节）→ **判分者可信**（第 3 节）→ **失败能定位**（第 4 节）→ **流程能自动跑**（本节）。

链条上任何一环断了，后面的都不会成立：判据不可判定则评测集无从建起；评测集全对则测不出改动；判分者不稳则分数没有意义；没有轨迹则失败无法变成用例；不自动跑则前面四条都会随时间失效。

**而这条链的起点是一句很朴素的要求：把「好」写成一个能自动判定的东西。**


## 从零开始：一个分四周的落地顺序

这套流程不小，一次全上会拖垮。可行的顺序是分四周：

**第一周：只做追踪。** 不建评测集，先把第 4 节的四个字段记下来。收益立刻可见 —— 出问题时你能定位了。而且这一周的产出（轨迹）正是后面评测集的来源。

**第二周：从轨迹里挑 10 条失败，建成冒烟集。** 不要一次性建 100 条 —— 先建 10 条，接进每次 push。10 条足够拦住明显的崩坏，而且维护成本几乎为零。

**第三周：补齐判据。** 把冒烟集里那些「判不准」的用例拿出来，按第 1 节的三步走一遍，把判据写成代码。做到这一步，你会发现有些用例根本写不出判据 —— 那说明它们不该在这层（该交给人，或者该退一步找近似）。

**第四周：把失败自动入库。** 接上第 4 节末尾那条流水线：线上失败 → 自动变成一条用例。**这一条是让整套流程活起来的那个开关** —— 没有它，评测集从建好那天起就开始过期。

四周里最容易被跳过的是第一周。团队倾向于直接建评测集（因为那看起来更像「正经工作」），但**没有轨迹的评测集只能测你想到的东西，测不到真正发生的事**。

## 怎么让团队真的用它

最后一个实际问题：怎么让这套东西不被绕过。三条做法，按有效性排：

**一，把「退步 0 条」设成合并门槛。** 不是「分数不低于 X」—— 那在噪声里。是「退步条数必须为 0」。这条是确定的事实，有争议时可以逐条看，没有解释空间。

**二，让评测结果出现在每次 PR 里，而不是一个需要主动去看的仪表盘。** 需要主动去看的东西会被忽略。

**三，把「新增了哪条用例」也放进 PR 描述。** 这条的作用是文化性的：它让「修好一个 bug 就补一条用例」变成一个被看见的动作，而不是一种美德。
## 完整可运行代码

下面这个运行器做三件事：逐条比对基线与现状、算出噪声底线、据此给出裁决。

```python
"""把评测接进开发流程：一个回归运行器。

它做三件事：
  1. 跑一遍用例集，和基线逐条比对（哪些退步了、哪些修好了）
  2. 用第 2 节的二项模型算出**噪声底线**
  3. 据此给出裁决：这次改动是真的有效，还是落在噪声里

第 3 步是关键 —— 多数「回归脚本」只报一个百分比差，而那个差可能毫无意义。

纯本地模拟（不需要 API），因为要测的是**流程与判读**。
实跑状态：2026-10-09。
"""
import math, random

N_CASES = 30
Z = 1.6449


def ci_width(p, n):
    return 2 * Z * math.sqrt(p * (1 - p) / n) * 100


def run_suite(seed, failures):
    """模拟一次评测：返回每个用例的通过与否。failures 指定哪些用例失败。"""
    return [i not in failures for i in range(N_CASES)]


def compare(base, cur):
    reg = [i for i in range(len(base)) if base[i] and not cur[i]]
    fix = [i for i in range(len(base)) if not base[i] and cur[i]]
    return reg, fix


if __name__ == "__main__":
    # 基线：30 题里错 4 题（通过率 86.7%）
    baseline = run_suite(0, {3, 11, 19, 25})

    print("=== 三个候选改动，看它们能不能被这套评测分辨 ===")
    print()
    print("  基线：%d/%d 通过（%.1f%%）" % (sum(baseline), N_CASES, sum(baseline) / N_CASES * 100))
    print()

    scenarios = [
        ("改动 A：修好 1 题、碰坏 1 题", {11, 19, 25, 7}),
        ("改动 B：修好 2 题、没有碰坏", {3, 19, 25}),
        ("改动 C：修好 4 题、碰坏 2 题", {19, 25, 7, 8}),
    ]
    p0 = sum(baseline) / N_CASES
    noise = ci_width(p0, N_CASES)
    print("  这套评测的噪声底线（90%% 区间宽度）：±%.1f 个百分点" % noise)
    print()

    for label, fails in scenarios:
        cur = run_suite(0, fails)
        reg, fix = compare(baseline, cur)
        p1 = sum(cur) / N_CASES
        delta = (p1 - p0) * 100
        verdict = ("✅ 超出噪声，可以下结论" if abs(delta) > noise / 2
                   else "⚠️ 落在噪声内，**不能**据此判断有效")
        print("  %s" % label)
        print("      通过率 %.1f%% → %.1f%%（Δ %+.1f 个百分点）" % (p0 * 100, p1 * 100, delta))
        print("      退步的用例：%s" % (reg if reg else "无"))
        print("      修好的用例：%s" % (fix if fix else "无"))
        print("      裁决：%s" % verdict)
        print()

    print("=== 关键点 ===")
    print("  改动 A 的净通过率没变（+0.0），但它**修好了 1 题、碰坏了 1 题** ——")
    print("  只看总分你完全看不到这件事，而它可能正是一次隐蔽的退化。")
    print()
    print("  所以回归报告必须同时给三样：")
    print("    1. 总分变化       —— 看趋势")
    print("    2. 逐条 diff      —— 看具体动了什么（这一项比总分重要）")
    print("    3. 噪声底线       —— 判断总分变化是否值得当真")
    print()
    print("  第 3 项是多数回归脚本缺的：30 题在 p≈87%% 时的噪声就有 ±%.0f 个百分点，" % noise)
    print("  而很多改动预期只带来 3 到 5 个点 —— 那根本测不出来。")
```

实跑输出（2026-10-09）：

```text
改动 A：修好 1 题、碰坏 1 题
    通过率 86.7% → 86.7%（Δ +0.0 个百分点）
    退步的用例：[7]      修好的用例：[3]
    裁决：⚠️ 落在噪声内，不能据此判断有效
```

注意「净变化 0」但「退步 1 条」—— 只看总分看不到这件事。

## 常见坑

- **只报一个百分比差。** 改动可能修好一题、碰坏一题，净变化为 0 —— 而其中包含一次退化。
- **不报噪声底线。** 30 题的噪声约 ±20 个点，而多数改动只带来 3 到 5 个点。没有这个数字，团队会追噪声。
- **按总分百分比设阈值。** 那不是确定的事实。按**退步条数**设阈值更稳。
- **冒烟集承担判断改动的职责。** 它只能拦明显崩坏，判断改动要用回归集。
- **失败集的用例允许退回去。** 那些来自真实线上失败，零容忍。
- **忘了评测集自己会失效。** 通过率接近 100% 时要报警 —— 该补题了。
- **单次分数当结论。** 存下来看趋势；单次有噪声，30 次运行的趋势很稳。
