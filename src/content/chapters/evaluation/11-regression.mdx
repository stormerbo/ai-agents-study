前三节讲了怎么定义判据、怎么建评测集、怎么用模型打分，以及怎么定位失败。这一节把它们接进日常开发 —— 因为**一份不会被自动跑的评测集等于不存在**。

## 三层结构

第 2 节给过一个分层建议，这里是它的可执行形态：

| 层 | 题量 | 什么时候跑 | 职责 |
|---|---|---|---|
| **冒烟集** | 10-20 | 每次改动 | 拦住明显的崩坏 |
| **回归集** | 100-300 | 每天 / 发版前 | 判断改动是否值得合并 |
| **失败集** | 持续增长 | 每天 | 保证修过的问题不再回来 |

三层里最容易漏的是第三层。前两层建好之后就固定了，而**输入分布会变** —— 半年前的用户问「怎么退款」，现在问「怎么改地址」。只有失败集会跟着真实分布一起长大。

而失败集的来源就是第 4 节的追踪：**每一条线上失败都入一条用例。** 这条流水线一接上，评测集就从一个静态资产变成了一个持续生长的东西。

## 回归报告必须有三样

多数回归脚本只报一个百分比差。那是**不够的**，而且有时是误导的。我用一个 30 题的评测集演示了这件事：

```text
基线：30 题通过 26 题（86.7%）
单组区间粗略参考（90% 区间宽度）：20.0 个百分点

改动 A：修好 1 题、碰坏 1 题
    通过率 86.7% → 86.7%（Δ +0.0）
    退步的用例：[7]      修好的用例：[3]

改动 B：修好 2 题、没有碰坏
    通过率 86.7% → 90.0%（Δ +3.3）
    退步的用例：无        修好的用例：[11]

改动 C：修好 4 题、碰坏 2 题
    通过率 86.7% → 86.7%（Δ +0.0）
    退步的用例：[7, 8]    修好的用例：[3, 11]
```

（本地构造的流程示例，不含随机模型调用。）

**注意改动 A。** 它的总分**一动不动**（+0.0）—— 但模拟基线中一条由失败变通过，另一条由通过变失败。只看总分会掩盖候选差异；在概率模型中要复跑后再确认退化。

**再看那三个候选改动。** 总分变化只有 0 到 3.3 个百分点；相对于 30 题单组区间宽度约 20 个点的粗略参照，它们不足以据此作统计结论。逐条 diff 可定位候选变化，但概率输出仍要重复确认。

**这就是为什么回归报告必须同时给三样：**

1. **总分变化** —— 看長期趋势（概率输出需重复运行）
2. **逐条 diff** —— 定位候选变化；概率输出要重复确认
3. **区间/不确定性** —— 按正确的比较设计判断总分变化

第 3 项用于避免把小样本总分变化过度解读；正式判断新旧版本差异应采用有明确设计和假设的统计方法。

> **口径提醒：** 20.4 个百分点是单组比例的 90% 区间宽度，仅用于展示小样本的不确定性；它不是新旧版本差值的置信区间。正式比较应按独立两组或配对设计计算。

## 一个反直觉的建议：优先看 diff

上面的数据支持这个建议：**30 题的总分精度有限**（单组 90% 区间宽度约 20 个百分点）。而逐条 diff 能定位「第 7 题从过变成不过」；对于确定性判据这是可复现事实，对于随机输出则是一个需要复跑确认的候选变化。

所以回归脚本的输出顺序应该是：

```text
1. ❌ 已确认退步的用例（逐条列出，按门槛处理）
2. ✅ 修好的用例
3. 📊 总分变化 + 按设计计算的不确定性（参考）
```

**把已确认的退步放在第一位，总分放最后。** 确定性判据的逐条退步是确定事实；概率输出的单次差异则需要复跑或裁决。

## 阈值怎么定

一个常见问题是「掉多少算退化」。答案取决于层：

- **冒烟集**：任何一条退步都值得看一眼（10-20 题，退步是稀有事件）
- **回归集**：单条退步要看是不是关键用例；超过 3 条退步应当 block
- **失败集**：确定性且可复现的修复用例零容忍；概率输出先重复评测并对分歧裁决

对可确定复现的线上失败，零容忍有道理。若用例依赖随机模型输出，应先确认退化（重复评测或人工裁决）；否则单次波动可能制造误报。

前两层的阈值**不该只设成「总分掉 X%」**，因为那个数字在小样本不确定性中。确定性判据可按**确认退步条数**设阈值；概率判据应先重复运行或裁决。

## 接进 CI 的四个实际考虑

**一、成本。** 一次回归是几百次模型调用。所以回归集不该在每次 push 上跑 —— 冒烟集跑 push，回归集跑每日或发版前。

**二、非确定性。** 模型输出有随机性，跑一次和跑两次结果可能不同。三种处理：把 temperature 设为 0（能减少但不能消除）；对关键用例跑 3 次取多数；**把评测结果存下来做趋势对比**，而不是只看单次。第三种最实用 —— 单次分数有噪声；重复运行可以估计波动，但 30 次也不自动保证趋势可靠，仍要看任务相关性、样本量和置信区间。

**三、判据的回归。** 别忘了评测集自己也会坏。第 2 节讲过：通过率接近 100% 可能说明它饱和，需结合难度和区分度判断。所以 CI 里应该有一条**关于评测集的检查** —— 通过率持续过高且难度/区分度不足时报警，提示检查题目是否饱和。

**四、人工校准。** 如果用了模型打分（第 3 节），要定期抽 20 到 30 条人工标注比对。**与人工标注的分歧率是发现 judge 漂移的重要信号之一** —— 没有它，你会在 judge 悄悄改变偏好之后继续相信它的分数。

### 一份最小 CI 产物

「把评测接进 CI」在仓库里就是两个文件：工作流 + 基线。先看工作流（示例：构造数据，未实跑；用 GitHub Actions 语法，别的 CI 换成对应的触发与命令行即可）：

```yaml
# .github/workflows/eval.yml
name: eval
on:
  push:                    # 每次 push：只跑冒烟集
  release:
    types: [published]     # 发版：跑回归集

jobs:
  smoke:
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python evals/run_suite.py --suite smoke --baseline evals/baseline.json
      # 退出码约定：确定性/已确认的退步超过策略阈值 → exit 1

  regression:
    if: github.event_name == 'release'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python evals/run_suite.py --suite regression --baseline evals/baseline.json
      - run: python evals/check_suite_health.py    # 通过率 > 95% 报警：该补题了
```

**触发条件、命令、退出码三样齐了，这条链才算接上。** 缺退出码，CI 永远是绿的；缺触发条件，回归集从没被跑过。对确定性不变量，可用「确认退步条数 > 0 → exit 1」；随机输出则先重复评测并按预设门槛/裁决流程形成确认结果，不能把一次抽样的逐条 diff 自动等同真实退步。退出码应反映该分类后的结果。

### 基线存什么

逐条比较要和**哪份基线的哪条用例**比，得写清楚。基线不能只存一个通过率；对随机输出，应保存每条用例的多次运行结果/汇总规则与区间，以及三个版本号（示例：构造数据，未实跑）：

```json
{
  "suite": "regression",
  "recorded_at": "2026-10-11",
  "model": "deepseek-flash",
  "prompt_sha8": "a1b2c3d4",
  "env_sha8": "e5f6a7b8",
  "pass_rate": 0.867,
  "ci90": [0.750, 0.967],
  "cases": [
    {"id": "refund-001", "passed": true},
    {"id": "addr-004", "passed": false},
    {"id": "coupon-002", "passed": true}
  ]
}
```

四个要点：`cases[].id` 用于逐条 diff（第 3 节要求用例带 `id` 就是为了这一步）；`model` / `prompt_sha8` / `env_sha8` 是第 5 节说的「改了环境分数就不可比」，不记版本号的跨时间比较没有意义；`ci90` 存区间而非单点，**否则你会把基线的噪声当成新版本的退步**（假回归）；`recorded_at` 决定这份基线多久该复核一次（第 2 节的时效性）。

### temperature 是什么，为什么设 0 还不够

前面说「把 temperature 设为 0」，这里把它解释清楚：

- **是什么。** `temperature` 是采样参数，控制模型输出的随机程度：越高越发散，越低越倾向于选概率最高的 token。它是**每次请求里的一个字段**，在第 1 章的 messages API 里就能看到（`"temperature": 0`）。
- **在哪设。** 在发给模型的请求体里设；对评测来说要给**所有会调用模型的地方**都设 —— 包括主 agent、judge、以及任务里调用的任何子模型。漏掉一个，随机性就从那里进来。
- **为什么 0 不能消除随机。** 两层原因：服务端的批处理与硬件并行会让同一个请求给出不同结果（浮点累加顺序不保证一致）；「选最高概率」在多个 token 概率接近时也可能被实现细节左右。**所以评测报告仍要存区间、看趋势，而不是把一次 temperature=0 当成确定性。**
- **「对关键用例跑 3 次取多数」的成本。** 就是 3 倍调用：关键用例 20 条，每次评测多花 40 次模型调用。**只在关键用例上做**，不要全量 —— 全量三次会让 CI 成本直接翻三倍，而多数用例本来就不需要。

## 回到第 1 节

这一章从「先把好定义清楚」开始，到这里收口。三节的链条是：

**判据可判定**（第 1 节）→ **评测集有区分度且够大**（第 2 节）→ **判分者可信**（第 3 节）→ **失败能定位**（第 4 节）→ **流程能自动跑**（本节）。

链条上任何一环断了，后面的都不会成立：判据不可判定则评测集无从建起；评测集全对则测不出改动；判分者不稳则分数没有意义；没有轨迹则失败无法变成用例；不自动跑则前面四条都会随时间失效。

**而这条链的起点是一句很朴素的要求：把「好」写成一个能自动判定的东西。**


## 从零开始：一个分四周的落地顺序

这套流程不小，一次全上会拖垮。可行的顺序是分四周：

**第一周：只做追踪。** 不建评测集，先把第 4 节的四个字段记下来。收益立刻可见 —— 出问题时你能定位了。而且这一周的产出（轨迹）正是后面评测集的来源。

**第二周：从轨迹里挑 10 条失败，建成冒烟集。** 不要一次性建 100 条 —— 先建 10 条，接进每次 push。10 条足够拦住明显的崩坏，而且维护成本几乎为零。

**第三周：补齐判据。** 把冒烟集里那些「判不准」的用例拿出来，按第 1 节的三步走一遍，把判据写成代码。做到这一步，你会发现有些用例根本写不出判据 —— 那说明它们不该在这层（该交给人，或者该退一步找近似）。

**第四周：把失败自动入库。** 接上第 4 节末尾那条流水线：线上失败 → 自动变成一条用例。**这一条是让整套流程活起来的那个开关** —— 没有它，评测集从建好那天起就开始过期。

四周里最容易被跳过的是第一周。团队倾向于直接建评测集（因为那看起来更像「正经工作」），但**没有轨迹的评测集只能测你想到的东西，测不到真正发生的事**。

## 怎么让团队真的用它

最后一个实际问题：怎么让这套东西不被绕过。三条做法，按有效性排：

**一，把适合硬判的退步设成合并门槛。** 确定性、可复现的不变量（schema、权限边界、确定性工具结果、明确的安全禁令）可以逐条零容忍。对随机模型输出，单次运行出现一条差异不是已确认回归；应对关键用例重复运行、按预先定义的规则汇总，并对分歧样本人工裁决，再决定是否阻塞。

**二，让评测结果出现在每次 PR 里，而不是一个需要主动去看的仪表盘。** 需要主动去看的东西会被忽略。

**三，把「新增了哪条用例」也放进 PR 描述。** 这条的作用是文化性的：它让「修好一个 bug 就补一条用例」变成一个被看见的动作，而不是一种美德。
## 完整可运行代码

下面这个运行器做三件事：逐条比对模拟基线与现状、计算单组区间参考、输出非推断性提示。

```python
"""把评测接进开发流程：一个回归运行器。

它做三件事：
  1. 跑一遍用例集，和基线逐条比对（哪些退步了、哪些修好了）
  2. 用第 2 节的二项模型算出单组区间参考值（不是两组差异的检验）
  3. 输出示范性提示；单次模拟不能裁决真实改动是否有效

单次候选差异仅作教学演示，不用于真实版本放行决策。

纯本地模拟（不需要 API），因为要测的是**流程与判读**。
实跑状态：2026-10-09。
"""
import math, random

N_CASES = 30
Z = 1.6449


def ci_width(p, n):
    return 2 * Z * math.sqrt(p * (1 - p) / n) * 100


def run_suite(seed, failures):
    """模拟一次评测：返回每个用例的通过与否。failures 指定哪些用例失败。"""
    return [i not in failures for i in range(N_CASES)]


def compare(base, cur):
    reg = [i for i in range(len(base)) if base[i] and not cur[i]]
    fix = [i for i in range(len(base)) if not base[i] and cur[i]]
    return reg, fix


if __name__ == "__main__":
    # 基线：30 题里错 4 题（通过率 86.7%）
    baseline = run_suite(0, {3, 11, 19, 25})

    print("=== 三个候选改动，看它们能不能被这套评测分辨 ===")
    print()
    print("  基线：%d/%d 通过（%.1f%%）" % (sum(baseline), N_CASES, sum(baseline) / N_CASES * 100))
    print()

    scenarios = [
        ("改动 A：修好 1 题、碰坏 1 题", {11, 19, 25, 7}),
        ("改动 B：修好 2 题、没有碰坏", {3, 19, 25}),
        ("改动 C：修好 4 题、碰坏 2 题", {19, 25, 7, 8}),
    ]
    p0 = sum(baseline) / N_CASES
    noise = ci_width(p0, N_CASES)          # 90% 区间的**宽度**
    half = noise / 2                       # 半宽 —— 仅作单组参考
    print("  单组 90%% 区间宽度 %.1f 个百分点（不是两组差值的区间）" % noise)
    print("  仅作演示：将单组区间参考带用于两组差异不是正式检验。")
    print()

    for label, fails in scenarios:
        cur = run_suite(0, fails)
        reg, fix = compare(baseline, cur)
        p1 = sum(cur) / N_CASES
        delta = (p1 - p0) * 100
        verdict = ("⚠️ 单次差异超过粗略参考带；需按两组设计复测"
                   if abs(delta) > half
                   else "⚠️ 单次差异未超过粗略参考带；不能据此判断有效")
        print("  %s" % label)
        print("      通过率 %.1f%% → %.1f%%（Δ %+.1f 个百分点）" % (p0 * 100, p1 * 100, delta))
        print("      退步的用例：%s" % (reg if reg else "无"))
        print("      修好的用例：%s" % (fix if fix else "无"))
        print("      裁决：%s" % verdict)
        print()

    print("=== 关键点 ===")
    print("  改动 A 的净通过率没变（+0.0），但它**修好一个模拟用例、使另一个模拟用例失败** ——")
    print("  只看总分你完全看不到这件事；对概率输出，逐条变化仍需复跑确认是否稳定。")
    print()
    print("  所以回归报告必须同时给三样：")
    print("    1. 总分变化       —— 看趋势")
    print("    2. 逐条 diff      —— 定位候选变化；概率输出要复跑确认")
    print("    3. 不确定性       —— 按正确的比较设计判断总分变化")
    print()
    print("  第 3 项是多数回归脚本缺的：30 题单组 90%% 区间宽度约 %.0f 个百分点；" % noise)
    print("  这是精度参考，不等于两组检验；小样本的总分差异要谨慎解释。")
```

本地模拟输出（2026-10-09；记录的原始数值保留，以下只展示单次提示，不构成显著性裁决）：

```text
单组区间粗略参考：90% 区间宽度 20.4 个百分点（非两组检验）

改动 A：修好 1 题、碰坏 1 题
    通过率 86.7% → 86.7%（Δ +0.0 个百分点）
    退步的用例：[7]      修好的用例：[3]
    提示：⚠️ 单次差异未超过粗略单组参考带；不能据此判断有效
```

注意「净变化 0」但「退步 1 条」—— 只看总分看不到这件事。

## 常见坑

- **只报一个百分比差。** 改动可能修好一题、碰坏一题，净变化为 0；逐条 diff 可指出候选变化，但随机输出需复跑确认。
- **把单组区间直接当成两组差异检验。** 30 题的单组 90% 区间约有 20 个百分点宽度；两组比较需要考虑两组方差、配对关系、α、功效与多重查看，不能用这里的简化参考带做显著性裁决。
- **按总分百分比设阈值。** 那不是确定的事实。按**确认退步条数**设阈值更稳；随机输出应先复跑/裁决。
- **冒烟集承担判断改动的职责。** 它只能拦明显崩坏，判断改动要用回归集。
- **对概率输出单次 diff 零容忍。** 单次差异不是已确认退化；重复关键用例并对分歧样本 adjudicate（人工裁决）。
- **忘了评测集自己会失效。** 通过率持续接近 100% 且缺乏区分度时要检查是否需要补题。
- **单次分数当结论。** 存下来看趋势；重复运行可估计变异，但需按任务、设计与样本量解释区间。
