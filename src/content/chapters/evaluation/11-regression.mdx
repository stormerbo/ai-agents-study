前三节讲了怎么定义判据、怎么建评测集、怎么用模型打分，以及怎么定位失败。这一节把适合自动化的检查接进日常开发，让团队能按风险稳定运行并比较结果。

## 三层结构

第 2 节给过一个分层建议，这里是它的可执行形态：

| 层 | 规模 | 什么时候跑 | 职责 |
|---|---|---|---|
| **冒烟集** | 小型、覆盖关键路径 | 每次相关改动或 PR | 快速发现确定性契约破坏与明显退步 |
| **回归集** | 覆盖主要任务与风险切片 | 按成本、时效和发布风险安排 | 在完整场景上判断变化及其不确定性 |
| **已复现失败集** | 去重、脱敏并完成归因初筛的失败用例 | 随修复与版本变化运行 | 检查已知问题是否再次出现 |

这三类集合的用途不同，不能用失败样本代替代表性生产抽样。线上失败、用户反馈和监控告警适合作为**候选用例来源**；进入回归集前还要去重、脱敏、确认判据，并判断它属于可复现缺陷、环境/评分问题还是新的任务类型。失败日志天然偏向已知故障，无法单独代表当前用户分布；应另行维护按目标抽样的代表性样本，并记录数据版本与纳入规则。[OpenAI 的评测指南](https://developers.openai.com/api/docs/guides/evaluation-best-practices)也建议数据集贴近真实任务，并将目标、数据、指标与比较流程分开设计。

第 4 节的可关联追踪能帮助定位和复现问题，但不保证记录了完整模型上下文或所有服务端状态。将候选失败纳入集合前，应保存必要的来源与环境指纹，并按隐私策略处理原始输入；评测集需要维护、审查和版本化，自动收集不会自动产生高质量用例。

## 回归报告必须有三样

多数回归脚本只报一个百分比差。那是**不够的**，而且有时是误导的。我用一个 30 题的评测集演示了这件事：

```text
基线：30 题通过 26 题（86.7%）
单组区间粗略参考（90% 正态-Wald 区间宽度）：20.4 个百分点

改动 A：修好 1 题、碰坏 1 题
    通过率 86.7% → 86.7%（Δ +0.0）
    退步的用例：[7]      修好的用例：[3]

改动 B：修好 2 题、没有碰坏
    通过率 86.7% → 93.3%（Δ +6.7）
    退步的用例：无        修好的用例：[3, 11]

改动 C：修好 2 题、碰坏 2 题
    通过率 86.7% → 86.7%（Δ +0.0）
    退步的用例：[7, 8]    修好的用例：[3, 11]
```

本例仅用固定失败集合演示逐题比较和比例算术；没有调用 provider，也不代表任何模型效果。

**注意改动 A。** 它的总分**一动不动**（+0.0）—— 但模拟基线中一条由失败变通过，另一条由通过变失败。只看总分会掩盖候选差异；在概率模型中要按预先定义的重复与裁决规则确认变化。

**再看那三个候选改动。** 这里的 A/B/C 是固定集合构造出的确定性演示，不是随机样本；它们只能说明总分与逐题 diff 的关系，不能支持版本效果或显著性结论。若真实系统输出有波动，要按预先声明的重复、配对/独立设计和判据分析。

**这就是为什么回归报告必须同时给三样：**

1. **总分变化** —— 看長期趋势（概率输出需重复运行）
2. **逐条 diff** —— 定位候选变化；概率输出要重复确认
3. **区间/不确定性** —— 按正确的比较设计判断总分变化

第 3 项用于避免把小样本总分变化过度解读；正式判断新旧版本差异应采用有明确设计和假设的统计方法。

> **口径提醒：** 20.4 个百分点来自独立 Bernoulli 假设下的正态-Wald 单组比例近似，仅用于说明小样本的精度可能很差；边界比例、小样本或任务聚类下覆盖率可能不理想。它不是新旧版本差值的置信区间，也不能用两个单组区间是否重叠来替代差异检验。正式比较应按实验单位、重复结构和预先声明的配对/独立组设计分析；可参照 [NIST 比例区间说明](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)。

## 一个实用的建议：先看 diff

上面的构造数据说明：**30 题的总分精度有限**（本例单组正态-Wald 90% 区间宽度约 20.4 个百分点）。逐条 diff 能定位「第 7 题从过变成不过」；对于确定性判据这是可复现事实，对于随机输出则只是候选变化，需要按设计复跑或人工裁决。

所以回归脚本的输出顺序应该是：

```text
1. ❌ 已确认退步的用例（逐条列出，按门槛处理）
2. ✅ 修好的用例
3. 📊 总分变化 + 按设计计算的不确定性（参考）
```

**把已确认的退步放在第一位，总分放最后。** 确定性判据的逐条退步是确定事实；概率输出的单次差异则需要复跑或裁决。

## 门槛怎么定

一个常见问题是「掉多少算退化」。答案取决于层：

- **冒烟集**：按风险为关键路径设门槛；失败应定位并分类，不能因为集合小就把退步当作稀有事件
- **回归集**：确定性硬约束的已确认退步可直接阻断；其它退步按预先声明的严重度、比较设计和不确定性规则处理。没有通用的“退步几条就 block”阈值
- **已复现失败集**：确定性修复用例应保持通过；概率输出需定义重复策略、聚合判据和分歧处理，避免把单次抽样当作确认回归

对可确定复现的线上失败，零容忍有道理。若用例依赖随机模型输出，应先确认退化（重复评测或人工裁决）；否则单次波动可能制造误报。

门槛**不该只设成「总分掉 X%」**。确定性判据可按关键约束和确认退步处理；概率判据应依据预先声明的实验单位、效应门槛、重复结构和不确定性作判断，不应从本例的题数推导通用阈值。

## 接进 CI 的四个实际考虑

**一、成本与时效。** 云端评测的开销取决于样本、重复次数、工具调用链、judge 和计费口径，没有固定的“每次回归调用数”。可以让低成本契约检查在 PR 上运行，把较大的或需要人工裁决的评测安排在定时/发布流程；门禁频率应按风险、成本与反馈时效选择。

**二、模型与服务波动。** 同一请求的结果是否稳定取决于采样参数、模型版本、服务端实现及任务本身；`temperature: 0` 不构成跨 provider 或跨版本的通用确定性保证。可对关键用例重复评测并保存逐次结果，但不能机械地用“跑三次取多数”当作可靠性证明：应预先定义实验单位、汇总/裁决规则，并考虑重复间相关性。重复运行有助于估计变异，不会自动消除版本漂移或样本偏差。

**三、评测集与判据的健康度。** 数据、预期答案、运行环境和评分器都可能过时。CI 可检查 fixture/schema、缺失标签、重复用例、评分器版本和关键风险切片覆盖；高通过率只是需要结合任务分布、难度和区分能力调查的信号，不存在适用于所有集合的固定饱和百分比。

**四、人工校准。** 如果用了模型打分（第 3 节），定期从目标任务与风险切片抽样，由合格标注者独立复核，并报告一致性、误报/漏报或分歧类型。样本量按目标精度、风险和标注成本设计，不设通用条数。与人工判断的差异是发现 judge 变化的信号之一，但人工标签也要有清晰 rubric 与争议裁决。

### 一份最小 CI 产物

「把评测接进 CI」可以从工作流、运行器和版本化基线开始。下面是构造性的 GitHub Actions 片段，未实跑，省略了 Python 安装、依赖锁定与项目配置；实际使用时要固定执行环境，并将需要的凭据放到 CI 的受控 secret/身份机制中，不要写入基线或日志：

```yaml
# .github/workflows/eval.yml
name: eval
on:
  push:
  pull_request:
  release:
    types: [published]

jobs:
  smoke:
    if: github.event_name == 'push' || github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python evals/run_suite.py --suite smoke --baseline evals/baseline.json
      # 退出码约定：确定性/已确认的退步超过策略阈值 → exit 1

  regression:
    if: github.event_name == 'release'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python evals/run_suite.py --suite regression --baseline evals/baseline.json
      - run: python evals/check_suite_health.py    # 检查 fixture、标签、评分器版本和风险切片覆盖
```

示例把 `push` 与 `pull_request` 都接到冒烟 job，只有 release 的 `published` 活动才运行完整回归集。上面的 `actions/checkout@v4` 是便于阅读的 tag 写法；正式仓库应按组织策略将 action 锁到完整 commit SHA（或使用经审查的 workflow dependency lockfile），并通过受控流程更新。

**触发条件、运行命令和失败策略三样齐了，这条链才算接上。** 如果 runner 没有把已确认失败映射为非零退出码，CI 可能仍显示通过；如果触发条件没覆盖目标改动，评测就不会执行。对确定性不变量，可用「确认退步 → exit 1」；随机输出则先重复评测并按预设门槛/裁决流程形成确认结果，不能把一次抽样的逐条 diff 自动等同真实退步。退出码应反映该分类后的结果。

### 基线存什么

逐条比较要和**哪份基线的哪条用例**比，得写清楚。基线不能只存一个通过率；要记录足以重建比较条件的版本与运行信息。下面是构造性字段示意，不是完整 schema，也不是实测结果：

```json
{
  "suite": "regression",
  "recorded_at": "<UTC timestamp>",
  "model_snapshot_or_alias": "provider-returned-model-id",
  "endpoint": "provider-and-api-format",
  "dataset_revision": "support-smoke@3",
  "prompt_sha256": "<full-content-digest>",
  "tool_schema_sha256": "<tool-schema-digest>",
  "env_sha256": "<full-environment-digest>",
  "grader_version": "grader-v4",
  "run_config": {"sampling_params": {"temperature": 0}, "max_output_tokens": 1200},
  "baseline_summary": {"n": 30, "passed": 26, "pass_rate": 0.867,
    "single_run_wald90": [0.765, 0.969]},
  "case_results_ref": "eval-store://run-2026-10-11-abc123"
}
```

`case_results_ref` 指向受控存储中的逐题、逐次结果，里面应保留 task ID、基线与候选配对、原始响应的受控定位和评分结果；不要把敏感原文或密钥直接放进 CI artifact。示例中的 `single_run_wald90` 只是单组比例的正态-Wald 粗略区间（26/30），**不能直接用来判新旧版本差异**；正式比较要保存配对关系及足够的逐次结果，并按设计分析差值。刷新基线也要保留历史版本与变更原因。

### 采样参数与可重复性

前面提到 `temperature`，这里补充它的适用边界：

- **是什么。** 对支持该参数的 API，`temperature` 用于调整 token 采样分布；通常较低会使分布更集中，但参数范围、默认值和行为按 provider/model 契约核对。它不是所有 endpoint 都支持或采用相同语义。
- **在哪设。** 在支持它的请求中记录实际值；评测报告还应记录主 agent、judge 与任务内子模型的各自配置。缺少该参数不等于唯一的随机性来源。
- **为什么 0 不是跨服务保证。** 参数语义与确定性能力由 endpoint/provider 定义；即便采样配置相同，版本别名漂移、服务更新或未公开的执行差异也会影响重现性。只有在固定模型快照与服务契约明确承诺时，才能据此主张相应范围内的可重复性。
- **重复评测的成本。** 调用量随重复数增加，但账单还受每次输入/输出 usage、工具链、缓存和 judge 影响；应按实际记录估算。只对有决策价值的场景增加重复，且把重复策略、停止规则与聚合方式预先写入评测协议。

## 回到第 1 节

这一章从「先把好定义清楚」开始，到这里收口。几类工作之间的关系是：

**目标与判据明确**（第 1 节）→ **评测集适合目标且覆盖风险**（第 2 节）→ **评分方式经过校准**（第 3 节）→ **故障可关联并定位**（第 4 节）→ **适合自动化的检查接入开发流程**（本节）。

这些工作相互依赖，但不要求每种判据都自动化：无法稳定自动评分的任务仍可采用人工复核或混合方式。集合失去区分能力、评分方式发生变化、故障记录不完整或检查没有按计划执行，都会削弱相应结论；报告应指出缺失环节，而不是把局部测试通过扩大成系统整体可靠。

**而这条链的起点是一句很朴素的要求：把「好」写成可检查的判据，并为机器评分、人工复核或两者组合选合适的方法。**


## 从零开始：一个分阶段的落地顺序

这套流程可以按团队能力分阶段引入。下面是顺序示例，不是普遍工期或最低样本量：

**第一阶段：先做最小必要追踪。** 不急着收集完整对话或敏感内容；记录故障定位所需的关联 ID、版本和可观测事件，并按保留策略控制访问。它能帮助挑选后续评测样本，但不会替代代表性抽样。

**第二阶段：从已审查的故障与代表性任务中选一组关键场景，建成冒烟集。** 优先覆盖可重复、判据明确且影响较大的路径；规模由运行时延、成本与覆盖目标共同决定，不假设某个固定题数足够。

**第三阶段：补齐判据。** 把冒烟集里那些「判不准」的用例拿出来，按第 1 节的流程选择机器评分、人工复核或组合方式。暂时无法稳定自动化的判据，可以保留为人工审查项，不等于用例不该存在。

**后续阶段：把候选失败接入审查流程。** 从线上信号创建候选记录，再经脱敏、去重、可复现性与判据审查后，决定加入回归集、失败集或仅保留为监控事件。评测集要通过版本化和代表性抽样持续维护，不能把原始生产请求自动复制到 CI。

团队可以从合适的阶段开始，但要保留评测数据的来源与代表性说明；有限的追踪也可能遗漏 provider 隐藏状态或未记录事件。

## 怎么让团队真的用它

最后一个实际问题：怎么让这套东西进入日常开发。下面三条是可执行建议，实际采用顺序按团队流程决定：

**一，把适合硬判的退步设成合并门槛。** 确定性、可复现的不变量（schema、权限边界、确定性工具结果、明确的安全禁令）可以逐条零容忍。对随机模型输出，单次运行出现一条差异不是已确认回归；应对关键用例重复运行、按预先定义的规则汇总，并对分歧样本人工裁决，再决定是否阻塞。

**二，让评测结果出现在每次 PR 里，而不是一个需要主动去看的仪表盘。** 需要主动去看的东西会被忽略。

**三，把「新增了哪条用例」也放进 PR 描述。** 这条的作用是文化性的：它让「修好一个 bug 就补一条用例」变成一个被看见的动作，而不是一种美德。
## 完整可运行代码

下面这个运行器做三件事：逐条比对模拟基线与现状、计算单组区间参考、输出非推断性提示。

```python
"""把评测接进开发流程：一个回归运行器。

它做三件事：
  1. 跑一遍用例集，和基线逐条比对（哪些退步了、哪些修好了）
  2. 用第 2 节的二项模型算出单组区间参考值（不是两组差异的检验）
  3. 输出示范性提示；单次模拟不能裁决真实改动是否有效

单次候选差异仅作教学演示，不用于真实版本放行决策。

纯本地模拟（不需要 API），因为要测的是**流程与判读**。
实跑状态：2026-10-09。
"""
import math

N_CASES = 30
Z = 1.6449


def ci_width(p, n):
    return 2 * Z * math.sqrt(p * (1 - p) / n) * 100


def run_suite(failures):
    """模拟一次确定性评测：返回每个用例的通过与否。"""
    return [i not in failures for i in range(N_CASES)]


def compare(base, cur):
    if len(base) != len(cur):
        raise ValueError("baseline and candidate must contain the same cases")
    reg = [i for i in range(len(base)) if base[i] and not cur[i]]
    fix = [i for i in range(len(base)) if not base[i] and cur[i]]
    return reg, fix


if __name__ == "__main__":
    # 基线：30 题里错 4 题（通过率 86.7%）
    baseline = run_suite({3, 11, 19, 25})

    print("=== 三个候选改动，看它们能不能被这套评测分辨 ===")
    print()
    print("  基线：%d/%d 通过（%.1f%%）" % (sum(baseline), N_CASES, sum(baseline) / N_CASES * 100))
    print()

    scenarios = [
        ("改动 A：修好 1 题、碰坏 1 题", {11, 19, 25, 7}),
        ("改动 B：修好 2 题、没有碰坏", {19, 25}),
        ("改动 C：修好 2 题、碰坏 2 题", {19, 25, 7, 8}),
    ]
    p0 = sum(baseline) / N_CASES
```

## 常见坑

- **只报一个百分比差。** 改动可能修好一题、碰坏一题，净变化为 0；逐条 diff 可指出候选变化，但随机输出需复跑确认。
- **把单组区间直接当成两组差异检验。** 本例 30 题的单组正态-Wald 90% 区间宽约 20.4 个百分点；两组比较需考虑实验单位、两组方差、配对关系、α、功效与多重查看，不能用单组区间或其半宽做显著性裁决。
- **按总分百分比设阈值。** 那不是确定的事实。按**确认退步条数**设阈值更稳；随机输出应先复跑/裁决。
- **冒烟集承担判断改动的职责。** 它只能拦明显崩坏，判断改动要用回归集。
- **对概率输出单次 diff 零容忍。** 单次差异不是已确认退化；重复关键用例并对分歧样本 adjudicate（人工裁决）。
- **忘了评测集自己会失效。** 通过率持续接近 100% 且缺乏区分度时要检查是否需要补题。
- **单次分数当结论。** 存下来看趋势；重复运行可估计变异，但需按任务、设计与样本量解释区间。
