上一节讲评测集从哪来。这一节讲它会怎么坏掉 —— 而且**坏掉之后它仍然是绿的**。

## 一、泄漏有三种，后两种最容易被忽略

**第一种：训练集泄漏。** 你的测试题在模型训练时见过了。这一种你基本无能为力，
只能靠选新题、看发布日期的 cutoff。它是三类里最出名、却最少发生在自己项目上的。

**第二种：提示词泄漏。** 评测时你把「参考答案」或「相似样例」放进了上下文。
这种情况很隐蔽 —— 你只是为了让模型「表现好一点」而加了几个例子，
而那几条例子的答案恰好覆盖了测试集。

**第三种：迭代泄漏。** 你反复用同一套评测集调参数，直到分数好看。
这时候**分数已经不代表能力了，它代表你对这套题的拟合程度**。

说实话，在自己项目里，**第三种的杀伤力远大于前两种**。它不需要任何外部条件，
只要你有「改一版、跑一下、再改一版」这个循环，它就在发生。

## 二、比泄漏更常见的坑：用模型生成评测集

「评测集不够，让模型生成一批」是很自然的想法。我实测了一遍，看它会带来什么。

任务是让模型围绕「AI agent 的上下文工程」出 20 道单选题，要求覆盖不同知识点，
并按指定格式输出题干、四个选项、正确答案。

### 缺陷一：答案分布严重偏斜

两次独立运行的结果：

```text
第一次：A 10.0%   B 60.0%   C 30.0%   D  0.0%
第二次：A 10.5%   B 73.7%   C 15.8%   D  0.0%
```

均匀出题时四个选项各应占 25%。第二次的卡方统计量是 **16.80**，
自由度 3 的临界值在 p=0.05 下是 7.81 —— **显著偏离均匀**。

这两个数的来历：**卡方统计量衡量「观测分布」和「理论分布（这里就是四个选项各 25%）」偏得有多远** —— 每个选项算 `(观测数 − 期望数)² / 期望数` 再加总（就是下面代码里那个 `chi2`）。自由度 = 选项数 − 1 = 3，因为四个数被「总题数固定」这一个条件约束住了。7.81 是自由度 3 时 p=0.05 的临界值：卡方超过它，说明「偏成这样」在均匀假设下发生的概率不到 5%，所以判定为真偏离，而不是随机波动。

**两次运行里 D 选项一次都没出现过，而 B 占了六到七成。**

这意味着什么？如果这些题被直接拿去做评测，**一个「总是选 B」的模型能拿到 60%~74% 的分数**。
而你看到这个数字时，会以为它在认真答题。

### 缺陷二：考点高度重复

我让模型给每道题标一个「考点」，然后按语义归并。结果：

```text
名义题数 19   →   实际覆盖概念 6 个     重复率 68%

  上下文隔离            6 道   ######
  中间遗失 / 位置偏差    5 道   #####
  工具结果压缩          4 道   ####
  前缀缓存              2 道   ##
  上下文卸载            1 道   #
  上下文注入            1 道   #
```

**三个概念占了 15/19 道题。** 注意它连措辞都会漂移 ——
「中间遗失」「位置偏差」「位置偏见」是同一件事，
「工具结果压缩」「工具结果剪裁」「工具输出治理」也是同一件事。
字面上看是 19 个不同考点，去重之后只剩 6 个。

这解释了一个很常见的困惑：**为什么我扩充到 200 道题，分数还是不准？**
因为那 200 道题可能只覆盖了 20 个概念，其余 180 道是换皮。

「换皮」长什么样，看这次生成里的两道（真实生成原文，来自上面那次实测）：第 4 题问「把关键系统指令与大量检索文档拼接时怎么布局」，考点标「中间遗失」；第 5 题问「为缓解迷失中间，关键信息放哪」，考点标「位置偏差」。两道题的正确答案都是 B，问的是同一件事。**这就是为什么按名义题数报「覆盖 19 个考点」会高估——它们去重之后是 6 个。**

### 缺陷三：格式并不总是听话

我给了严格的输出格式（题干 / A-D / 答案）。第一次运行 **8 道里 3 道解析不出答案**（62.5% 合规），
第二次 20 道里 1 道不合格（95% 合规）。

**这个失败率不可复现。** 我重跑同一条指令得到的是不同的合规率。
所以别指望「提示词写清楚了」就等于「输出一定可解析」——
如果你要用模型批量生成结构化数据，**必须有解析失败的重试与兜底**，而不是假设它一定成功。

## 三、一个反直觉的观察：题太简单，也测不出泄漏

我原本还想做另一个对比：同一主题下「模型自己出的题」它答得更好，还是「人工出的题」它答得更好。
如果前者更高，就能证明模型在回避自己不会的东西。

结果是 **10 道模型题 100%、8 道人工题也 100%**。这个实验**没有测出任何差异** ——
因为我的人工题也太简单了，两边一起顶在天花板上。

**这是同一个坑的第二次出现**（上一节刚讲过评测集饱和）。它带来一个很实际的推论：

> **一个测不出泄漏的评测集，同样也测不出能力。**

你没法用一批「谁都能答对」的题去证明「模型在偷看答案」，
因为天花板把所有的差异都压平了。
先解决饱和，再谈泄漏。

## 四、怎么检测

下面这段代码不需要模型，直接对着评测集跑，能查出上面三类问题里的两类。

```python
import re
from collections import Counter


def answer_distribution(answers):
    """检查选择题的答案分布是否均匀。卡方统计量，自由度 3。"""
    n = len(answers)
    c = Counter(answers)
    exp = n / 4
    chi2 = sum((c.get(L, 0) - exp) ** 2 / exp for L in "ABCD")
    return c, chi2, chi2 > 7.81        # 7.81 是 p=0.05 的临界值


def concept_overlap(fields):
    """考点去重：返回「名义题数 / 实际概念数」。"""
    norm = [re.sub(r"[\s，。、]", "", f) for f in fields]
    return len(norm), len(set(norm))


def ngram_leakage(eval_texts, train_texts, n=8):
    """n-gram 重叠检测：评测集里有多少片段在训练语料里出现过。"""
    def grams(t):
        t = re.sub(r"\s+", "", t)
        return {t[i:i + n] for i in range(len(t) - n + 1)}
    train = set()
    for t in train_texts:
        train |= grams(t)
    hits = 0
    total = 0
    for t in eval_texts:
        g = grams(t)
        if not g:
            continue
        total += 1
        if len(g & train) / len(g) > 0.5:   # 一半以上片段命中就判定为泄漏
            hits += 1
    return hits, total


if __name__ == "__main__":
    # 实测里那两次生成的结果
    run2 = list("B B B B C B B B B B B C B B B B B B B B")
    c, chi2, bad = answer_distribution(run2)
    print("答案分布:", dict(c), " 卡方=%.2f" % chi2, " 显著偏离" if bad else " 正常")

    focus = ["工具结果压缩", "上下文隔离", "上下文隔离", "中间遗失", "位置偏差",
             "工具结果压缩", "工具结果剪裁", "上下文隔离", "上下文隔离", "工具输出治理",
             "提示缓存", "位置偏见", "位置偏差", "上下文卸载", "上下文隔离",
             "上下文隔离", "位置偏差", "上下文注入", "提示缓存"]
    nom, real = concept_overlap(focus)
    print("考点去重: 名义 %d → 实际 %d   重复率 %.0f%%" % (nom, real, 100 * (nom - real) / nom))
```

实跑数据（2026-10-10，用实测里那两次生成的真实数据）：

```text
答案分布: 'B': 16, 'C': 2   卡方=24.40  显著偏离
考点去重: 名义 19 → 实际 9   重复率 53%
```

注意「实际 9」和正文表格里的「实际 6」不同：**代码只做字面去重，不做语义归并**。
「位置偏差」和「位置偏见」在代码眼里是两个概念，在人眼里是一个。
所以这个脚本给的是**重复率的下界** —— 真实重复比它更严重。
这本身就是个教训：**能自动化的检测往往偏宽松，别把「脚本没报问题」当成「没问题」。**

## 五、提示词泄漏怎么测

第二种泄漏（提示词泄漏）不像前两种那么显眼，因为它藏在你的 few-shot 例子里。

**先把这个词解释清楚。** few-shot 指的是**在提示词里放几条「输入 → 期望输出」的示范**，让模型照着格式与风格回答。不放示范叫 zero-shot，放一条叫 one-shot，放几条叫 few-shot。它和评测集在物理上是分开的：示范写在 system prompt 里，评测集是 `evals/*.json` 里的数据文件（第 3 节）。**正因为分开，才有泄漏** —— 你的示范里带着答案，而评测题恰好和示范同源。

一段真实形态的提示词（示例：构造数据，未实跑；分界处就是 few-shot 那一段）：

```text
你是客服助手。回答要给出可执行的下一步，不要编造时限。

【示范 1】
用户：我的订单显示已发货但没收到。
标准输出：先查物流单号；若超过 7 天未更新，点「申请售后」→「未收到货」，我们代为跟进。

【示范 2】
用户：我要改收货地址。
标准输出：订单未发货时在订单页点「修改地址」；已发货则联系承运方改派。

【以下才是真实请求】
用户：优惠券核销失败，提示不在有效期。
```

上面【示范 1】【示范 2】这两段就是 few-shot。**测泄漏时删的就是它们，不是任务描述、不是【以下才是真实请求】那一句。**

测法很直接：**做一次消融**。

把当前提示词跑一遍评测集，记下分数；然后把 few-shot 例子**整段删掉**再跑一遍。

- 如果分数只掉一点点 → 例子在教格式，这是它该干的
- 如果分数掉很多 → **例子在给答案**，你已经测不出模型的真实能力了

反过来也要测一次：**把例子换成与评测集完全无关的另一批**。
如果分数几乎不变，说明例子的内容本身不重要（只起格式示范作用），这是好事；
如果分数明显下降，说明原来的例子和评测集有内容上的重合 —— 那就是泄漏。

这个测试之所以有效，是因为它**改变了「答案是否可得」，而没有改变任务本身**。
凡是这类改动能让分数跳变的，中间就夹着泄漏。

顺带说一个更隐蔽的形态：**few-shot 例子的答案分布也会带入偏斜**。
如果你给的三个例子里有两个答案是 B，模型会更倾向于选 B ——
这和上面测出的「模型自己出题时 B 占七成」是同一个机制。
例子要配平，不只是题要配平。

三种对照各改哪里，写成提示词 diff 最清楚。**保持原样**就是上面的提示词。

**删掉示范**：

```diff
  你是客服助手。回答要给出可执行的下一步，不要编造时限。
-
- 【示范 1】
- 用户：我的订单显示已发货但没收到。
- 标准输出：先查物流单号；若超过 7 天未更新，点「申请售后」→「未收到货」，我们代为跟进。
- 【示范 2】
- 用户：我要改收货地址。
- 标准输出：订单未发货时在订单页点「修改地址」；已发货则联系承运方改派。
-
  用户：优惠券核销失败，提示不在有效期。
```

**换成无关示范**（内容与评测集不重合，只保留「输入 → 标准输出」这个格式）：

```diff
  你是客服助手。回答要给出可执行的下一步，不要编造时限。
-
- 【示范 1】用户：我的订单显示已发货但没收到。 标准输出：先查物流单号……
- 【示范 2】用户：我要改收货地址。 标准输出：订单页点「修改地址」……
+ 【示范 1】用户：怎么开发票？ 标准输出：在「我的 - 发票」里选择订单开票。
+ 【示范 2】用户：能开专票吗？ 标准输出：专票需在提交时填写税号，1-3 个工作日寄出。
  用户：优惠券核销失败，提示不在有效期。
```

**掉多少算泄漏？** 不能靠「掉很多」这种说法。可执行的口径是：**看它有没有超过噪声底线。** 按第 11 节那套 —— 30 题上 p≈87% 时 90% 区间的半宽就有 ±10 个点，所以「删掉示范后掉 8 个点」在 30 题上说明不了任何事。判据是：掉的幅度超过噪声（第 10、11 节给了算法与样本量口径），且方向在配对比较下稳定（第 7 节）；样本不够时，只能记录而不能下结论。

**怎么配平。** 「主动配平答案分布」也不能停在口号上。两个动作就够：**答案位置轮转**（第 i 题把正确答案放到 A/B/C/D 的第 i mod 4 位）+ **难度分层抽题**（每个考点至少一条简单、一条困难）：

```python
def balance(cases, labels="ABCD"):
    """把正确答案的位置轮转，避免一批题全押在 B。"""
    out = []
    for i, c in enumerate(cases):
        want = labels[i % len(labels)]                 # 目标位置轮转
        opts = dict(c["options"])
        cur = c["answer"]
        if cur != want:
            opts[cur], opts[want] = opts[want], opts[cur]   # 交换选项内容，题面不动
        out.append({**c, "options": opts, "answer": want})
    return out

# 用法：生成 100 道 → 人工筛 20 道 → balance() 配平 → 写入 evals/regression.json
```

配平之后要复算一次分布（就是上面那个 `answer_distribution`@@）—— **配平是动作，复算是验收。**

## 六、防泄漏的四条做法

**一、留出集从不参与调优。** 把评测集分两份，一份进 CI 天天跑（可以随便调），
一份锁起来只在做最终判断时打开。这是唯一能对抗「迭代泄漏」的办法。

执行方式要比口号具体一点，否则「锁起来」很快会变成「也在同一个目录里」：留出集放**独立目录**（如 `evals/heldout/locked.json`），CI 配置只跑 `evals/smoke.json` 与 `evals/regression.json`，留出集的运行入口**不进 CI**；换留出集的题要走一次单独的、记录在案的复核。只要它出现在任何一个「改一版跑一下」的循环里，它就退化成普通评测集了。

**二、模型生成的题只当候选池。** 生成 100 道，人工筛出 20 道，并且**主动配平答案分布**、
**补齐缺失的概念**。生成环节放开，准入环节收紧。

**三、每道题记录来源与日期。** 字段就是第 3 节那份用例 JSON 里的 `source` 与 `added`：`source` 决定它属于哪一层，`added` 用来算年龄。来自线上失败案例的题会随时间陈旧（产品改了，那个 bug 不再可能出现），需要定期复核。

**四、把「当前成功率」当监控指标。** 如果某个子集的通过率长期 100%，
它已经不再度量任何东西 —— 要么加难度，要么换题。

## 七、小结

- **泄漏有三种**：训练集泄漏、提示词泄漏、迭代泄漏。自己项目里最危险的是第三种
- **模型出题有三个可测的缺陷**：答案偏斜（B 占 73.7%、D 两次都是 0）、考点重复（19 题 → 6 个概念）、格式不稳（两次 62.5% 与 95%）
- **答案偏斜最致命**：一个「总选 B」的策略能拿 70 分
- **扩充题量不等于扩充覆盖**：先去重看概念数，再谈规模
- **模型生成的题只能当候选池**，准入必须人工筛 + 配平
- **饱和的评测集测不出泄漏**，也测不出能力 —— 先解决饱和

最后回到那句话：泄漏最麻烦的地方不是它让分数变高，而是**它让分数变得无法解释**。
分数涨了 5 个百分点，你不知道那是系统真的变好了，还是这一轮恰好撞上了模型更熟的那几个考点。
**可解释性比准确性更难保住，也更值钱。**

一个可操作的自检：拿你的评测集，随机打乱标签后重跑一遍。
如果分数没有明显下降，说明你的评测集**对标签不敏感** ——
那它测的很可能不是你想测的东西。
