这一节要从两个长得几乎一样的指标说起。它们只差一个字符（`@` 和 `^`），结论却常常相反：

- **Pass@k** —— k 次里**至少有一次**成功
- **Pass^k** —— k 次**全部**成功（@@B@@^@@B@@ 读作「幂」：把单次成功率连乘 k 次，所以它随 k 下降）

第一个问的是「它**能不能**做对」，第二个问的是「它**稳不稳**」。
在 demo 阶段你只看第一个，在上生产之前你必须看第二个。

## 一、先把两个指标写清楚

给定一个任务，跑 k 次，`c` 表示其中成功的次数：

```text
Pass@k = P(至少一次成功)     —— 能力上限
Pass^k = P(k 次全部成功)     —— 可靠性下限
```

当 k=1 时两者相等，都等于单次成功率 p。**k 越大，它们离得越远**：

- Pass@k 只会上升（多试几次总能碰上）
- Pass^k 只会下降（要求每一次都对）

**这就是为什么它们不该混用。**「我们的 agent Pass@5 有 95%」听起来很好，
但如果 Pass^5 只有 60%，意思是**每五个用户里就有两个会遇到至少一次失败**。

## 二、实测：我五次没测出差异

这一节我本来准备放一组「Pass@k 上升、Pass^k 下降」的漂亮数据。结果**跑了五轮，全是 100%**。

| 轮次 | 任务形态 | 单次成功率 | Pass@5 | Pass^5 |
| --- | --- | --- | --- | --- |
| 1 | 多步算术（折扣、税、年龄） | 100% | 100% | 100% |
| 2 | 大数计算、模幂、字符串变换 | 100% | 100% | 100% |
| 3 | 40 行日志里按多条件精确抽取 | 100% | 100% | 100% |
| 4 | 多步工具调用（3 个工具，环境终态判定） | 100% | 100% | 100% |

第 4 行的「环境终态判定」指的是：**不看模型最后说了什么，而是看它执行完之后环境里的状态**（数据库里那笔退款在不在、文件改没改）对不对。理由见第 5 节 —— 自然语言的结论会骗人，状态不会。
| 5 | 同上，但工具 **35% 概率返回瞬时错误** | 100% | 100% | 100% |

第 5 轮我特意做了「工具间歇性失败」，考的是遇到 429 会不会重试 —— 它每次都重试了。

**五轮全 100% 不是「模型完美」，而是「我的评测集对这个模型饱和」。**
一个测不出任何差异的评测集，比一个测错的评测集更危险 —— 因为它是**静默**的：
你看到一片绿，会以为系统很稳。

根因不是粗心，而是**用同一套直觉检查同一套直觉**。所以这一节的代码里，
**所有期望值一律由代码算**，不手写：

```python
EXP = {
    "h1": str(sum(1 for i in range(1, 1001) if i % 3 and i % 7)),
    "h4": str(2**10 + 3**5 - 7**3),
    "h7": str(0xDEAD + 0b1011),
    "e2": str(pow(7, 100, 13)),
}
```

**能由程序生成的答案键，就交给程序。** 手写的那部分，必须用另一个方法复核。

### 一道题长什么样

上面 `EXP` 只给了四个答案，读者没法复现这组校准。补三道完整的，其余同构（示例：构造数据，未实跑；格式取自本次校准）：

| id | 题面 | 期望值来源 | 判定方式 |
|---|---|---|---|
| `h1` | 1 到 1000 里，既不能被 3 整除也不能被 7 整除的数有多少个？ | `sum(1 for i in range(1,1001) if i % 3 and i % 7)` | 输出里出现该整数 |
| `h4` | 计算 2^10 + 3^5 − 7^3，只回答数字 | `2**10 + 3**5 - 7**3` | 输出里出现该整数 |
| `e2` | 计算 7^100 mod 13，只回答数字 | `pow(7, 100, 13)` | 输出里出现该整数 |

三道题的结构是固定的三件套：**题面（受控文本）+ 期望值（由代码算，不手写）+ 判定方式（能写成断言）**。第 3 节会把这三件套落成用例文件里的字段。

**用 5 次观测估 Pass^10 会错在哪**：`pass_pow_k(runs)` 直接返回「观测到的这 k 次是否全对」，所以拿 5 次观测去估 Pass^10 时，它回答的是「这 5 次全对吗」，**不是**「第 10 次也全对的概率」。样本不够时它只会给你 0 或 1，没有中间值 —— 要估 Pass^k，每组必须真跑满 k 次，再重复多组、用全对率的分布去估计（样本量口径见第 10 节：40 次全通过只能断言 [91.2%, 100%]）。

## 四、Pass^k 真正的用处在「规模化」

上面的饱和是因为**任务太短**。单步任务上 100% 是常见的；但 agent 的价值恰恰在长任务。

下面这张表是纯解析解：单步成功率 p 的任务，连续 n 步全对的概率是 `p^n`。

```text
p=0.999   1步= 99.9%   5步= 99.5%  10步= 99.0%  20步= 98.0%  50步= 95.1%
p=0.99    1步= 99.0%   5步= 95.1%  10步= 90.4%  20步= 81.8%  50步= 60.5%
p=0.95    1步= 95.0%   5步= 77.4%  10步= 59.9%  20步= 35.8%  50步=  7.7%
p=0.90    1步= 90.0%   5步= 59.0%  10步= 34.9%  20步= 12.2%  50步=  0.5%
```

这四行值得盯一会儿：

- **99% 听起来很好**。但一个 50 步的任务，全对率只有 **60.5%** —— 差不多四成的会话会失败
- **95% 听起来还行**。20 步只剩 **35.8%**，50 步几乎必然失败（7.7%）
- 而 99.9% 和 99.0% 看起来只差 0.9 个百分点，在 50 步上差了 **35 个百分点**（95.1% vs 60.5%）

**这就是 Pass^k 的意义：它把「单步小概率」放大成「任务级大概率」。**
你在单步上看到的 1% 抖动，到了任务级就是三分之一。

注意最下面那个框：**当 n 大的时候，提升可靠性的手段不是「换个更强的模型」，而是工程手段** ——
重试、检查点、幂等、把人放进关键决策点。
这也是本站第 11 章（agent 循环）和第 16 章（沙箱）为什么强调那些东西的原因。

**一个最小例子。** 长任务里「加检查点与重试」落到代码上通常长这样：每一步把已完成的动作记下来，重试时跳过已完成的、并且给副作用带上幂等键：

```python
STATE = {}                       # 真实项目里要持久化，不能只放内存

def step_once(step_id, fn, idem_key):
    if STATE.get(step_id) == "done":
        return STATE[step_id]                          # 已完成的步骤不重放
    for attempt in range(3):                           # 重试
        try:
            out = fn(idem_key=idem_key)                # 副作用必须幂等
            STATE[step_id] = ("done", out)             # 检查点
            return out
        except (TimeoutError, ConnectionError):        # 只重试可恢复的失败
            continue
    raise RuntimeError("步骤 %s 三次都失败" % step_id)
```

三个词连在一起才成立：**重试**处理随机失败，**幂等**保证重试不会重复扣款，**检查点**让已经走完的步骤在进程重启后不用重放。只做其中一样，都会在长任务上露馅。

## 五、怎么校准一组「不饱和」的评测集

饱和的评测集没有信息量。判断和修的办法：

**判据一：先跑一遍看分布。** 如果一批题全对或全错，这批题对该模型无效。
你需要的是**成功率落在中间区间**的题 —— 经验上 50%~90% 最好用。

**判据二：从「失败案例」造题，而不是从「知识」造题。** 我上面五轮的题都是**我凭空想的**，
所以我只能想到这个模型会做的题。真实项目里最有价值的题来自**线上失败轨迹** ——
那些题天然就在模型的能力边界上。

**判据三：让难度可调。** 同一个任务可以做成「简单版 / 标准版 / 困难版」，
例如抽取题从句 2 个条件加到 4 个条件、日志从 40 行加到 400 行。这样你能主动把难度推到边界。

**判据零：先确认这批题真的在测你要测的东西。** 我上面五轮的题全是自足任务：输入给全、

答案唯一、不依赖环境。它们测的是**模型的推理能力**，而不是**agent 的工程可靠性**。

两者会给出完全不同的结论 —— 前者可以全绿，后者一上多步就崩。造评测集之前先回答一句：
**这批题失败了，说明的是模型不行，还是我的系统不行？**

**判据四：别只看总分，看方差。** 同一个题跑 5 次，结果是否一致？
**五次全对和五次要试三次才对，在总分上可能一样，但在生产里完全不同。**

## 六、把两个指标算出来

下面这段可以直接跑，无第三方依赖。它同时算 Pass@k、Pass^k 与 bootstrap 置信区间 ——
最后一个决定了「你看到的差异是不是噪声」。

**先解释那个方法：bootstrap 置信区间**，机制是「有放回地重采样」—— 把观测到的 n 次结果当成全部世界，每次从里面随机抽 n 个（同一个结果可以被抽中多次），重复上万次，看均值怎么分布，取 2.5% 与 97.5% 分位就是 95% 区间。它不要求假设分布，代价是在极端比例（几乎全成功 / 全失败）上会失效 —— 第 10 节有实测。

```python
import random


def pass_at_k(runs, k):
    """k 次里至少一次成功的概率（无偏估计，k<=len(runs)）。"""
    n, c = len(runs), sum(runs)
    if n - c < k:
        return 1.0
    # 1 - C(n-c, k) / C(n, k)，用连乘避免大数
    prob = 1.0
    for i in range(k):
        prob *= (n - c - i) / (n - i)
    return 1 - prob


def pass_pow_k(runs):
    """k 次全对 —— 直接把观测到的全对率当成估计。"""
    return 1.0 if all(runs) else 0.0


def bootstrap_ci(runs, n_boot=10000, seed=0):
    """对单次成功率做 bootstrap，返回 95% 区间。"""
    rng = random.Random(seed)
    n = len(runs)
    means = []
    for _ in range(n_boot):
        s = sum(rng.choice(runs) for _ in range(n))
        means.append(s / n)
    means.sort()
    lo, hi = means[int(0.025 * n_boot)], means[int(0.975 * n_boot)]
    return lo, hi


# 模拟：20 个任务各跑 5 次，单次成功率约 90%
rng = random.Random(42)
n_task, k = 20, 5
per_task = [[rng.random() < 0.9 for _ in range(k)] for _ in range(n_task)]
flat = [x for runs in per_task for x in runs]

print("单次成功率     %.1f%%" % (100 * sum(flat) / len(flat)))
print("Pass@%d        %.1f%%" % (k, 100 * sum(pass_at_k(r, k) for r in per_task) / n_task))
print("Pass^%d        %.1f%%" % (k, 100 * sum(pass_pow_k(r) for r in per_task) / n_task))
lo, hi = bootstrap_ci(flat)
print("95%% 置信区间   [%.1f%%, %.1f%%]  宽度 %.1fpp" % (100 * lo, 100 * hi, 100 * (hi - lo)))
```

实跑数据（2026-10-10）：

```text
单次成功率     90.0%
Pass@5        100.0%
Pass^5         59.0%
95% 置信区间   [85.0%, 95.0%]  宽度 10.0pp
```

**三个数字一起看才完整**：单次 90%、至少一次 100%、五次全对 59%。
只报中间那个就是误导。

那行置信区间同样是必需信息：**宽度 10pp 意味着你用 20 个任务分辨不出 85% 和 95% 的差异**。
想分辨 5pp 的差距，样本量要按宽度平方放大 —— 大约 4 倍。

### 一个真实的报错

上面 `pass_at_k` 我第一版写成：

```python
def pass_at_k(runs, k):
    return 1.0 if any(runs) else 0.0      # 错
```

它把「k 次里至少一次」当成了「观测到的这 k 次里有没有一次成功」。
在 k 等于运行次数时两者恰好相同，所以小样本下看不出来；
一旦你想用 5 次观测去估计 **Pass@10**，它就直接错 —— 它会返回「这 5 次的结果」，而不是「再试到第 10 次时的概率」。

正确的口径是 `1 - C(n-c, k) / C(n, k)`，也就是**从未成功的那些次里抽 k 次全都失败**的补集。
这也是评测脚本最容易出错的地方：**指标的 k 和运行次数是两件事**。

## 七、小结

- **Pass@k 测能力上限，Pass^k 测可靠性下限。** k=1 时相等，k 越大差得越远
- **两个数字必须一起报。** 只报 Pass@k 会掩盖失败率
- **评测集饱和时你是测不出差异的**，而且它静默 —— 先校准难度再谈结论
- **答案键尽量让代码算。** 我五轮校准里手写的 4 个键全错，且第一遍自查通过
- **长任务上单步的小概率会被放大**：99% 的单步，50 步只剩 60.5%
- **提升长任务可靠性靠工程手段**（重试、检查点、幂等），不只是换模型

最后补一句关于**饱和**本身：一个全绿的评测集最危险的地方在于**它不报错**。

它会一直躺在 CI 里，每次改动都给你一个绿色的勾，直到线上出事你才发现它从来没测到东西。
所以评测集需要和代码一样被维护 —— 每次系统变强，评测集也得变难，
否则它会随着你的系统一起「通过」，而不再度量任何东西。

一个实用的做法是**给评测集记一个「当前成功率」，把它当监控指标看**：
长期 100% 不是好信号，是该加难度了。
