这一节比较两个按任务聚合的指标。给定同一批任务，每个任务独立运行 k 次，并用事先定义、对所有运行一致的判定器记成功/失败：

- **Pass@k**：每题 k 次运行中至少一次成功的任务比例。它回答「在给定采样预算下，有多少题至少找到一个成功结果？」
- **Pass^k**：每题 k 次运行全部成功的任务比例。这里用 `Pass^k` 作为本节对「k 次全成功率」的记号；它不是所有 Agent 评测都统一采用的标准符号。

这两个统计量描述不同事件，不能互相替代。它们也不是无条件的「能力上限」和「可靠性下限」：结果依赖任务分布、采样策略、判定器、温度/解码参数、工具与预算。Pass@k 允许从 k 个候选里挑成功者；真实系统若没有可靠验证器与安全选择/执行机制，就不能把这个数字当作可交付成功率。

## 一、先把两个指标写清楚

设固定任务的单次运行成功概率为 `p`。只有在每次运行独立且成功概率相同的假设下，才有：

```text
理论 Pass@k = 1 - (1-p)^k
理论 Pass^k  = p^k
```

在真实评测里，各任务通常难度不同、同一任务的多次运行也可能相关，因此应先对每题计算，再按目标任务总体聚合。异质任务下的 `E[1-(1-p_i)^k]` 与 `E[p_i^k]` 通常不等于把总体平均成功率直接代入公式；若有恢复、重试或状态改变，独立同分布假设也可能不成立。

当 `k=1` 时两者对应同一个事件；随 k 增加，观察到的 Pass@k 不会下降、Pass^k 不会上升（在固定观测样本中如此），但这不代表真实系统一定能安全重试或从多候选中挑选。

本节会同时报告二者，但不设「所有系统必须同时汇报」的绝对规则：选择指标要匹配产品语义。若用户一次提交只执行一个结果，应报告单次任务成功与失败代价；若系统会生成多个候选并由可信判定器选择，可报告候选预算下的 Pass@k；若必须重复执行且每次都要成功，才需要类似 Pass^k 的指标。

## 二、五轮历史记录：饱和观察仍待复核

正文旧稿记录了五轮全 100% 的摘要。原始逐题 prompt、响应、工具轨迹、运行环境快照和判定器没有随项目归档，因此**这些数字目前是无法独立复核的历史记录，不是本次重新实跑的结果，也不能证明模型完美或评测集必然饱和**。保留它们是为了说明旧稿当时如何解读；要把它们升级为证据，需恢复原始材料并重跑评分。

| 轮次 | 任务形态 | 旧稿所记单次成功率 | 旧稿所记 Pass@5 | 旧稿所记 Pass^5 |
| --- | --- | --- | --- | --- |
| 1 | 多步算术（折扣、税、年龄） | 100% | 100% | 100% |
| 2 | 大数计算、模幂、字符串变换 | 100% | 100% | 100% |
| 3 | 40 行日志里按多条件精确抽取 | 100% | 100% | 100% |
| 4 | 多步工具调用（3 个工具，环境终态判定） | 100% | 100% | 100% |
| 5 | 同上；旧稿称工具有 35% 概率返回瞬时错误 | 100% | 100% | 100% |

旧稿还称第 5 轮遇到工具错误后每次都会重试。缺少逐次记录，无法判断实际故障次数、重试策略、失败是否被隐藏或任务是否真的达到预设终态；因此不能从这份摘要推出「重试有效」。

如果一套评测真的持续全通过，首先应检查样本是否覆盖目标风险、判定器是否独立有效、任务是否有足够区分度；全通过只是一个诊断信号，不会自动证明评测集无效。

## 三、答案键错误也是待复核的历史记录

旧稿还记录了一次 12 道题的校准：8 通过、4 失败，随后作者按手工验算认为答案键有误，并列出 924 vs. 686、57016 vs. 57032 等例子。但原题、模型原始输出、评分脚本和独立复核记录均未归档，所以「四个键都错、模型实际 12/12」只能视为旧稿作者的历史判断，**不能作为已证实的模型结果或已证实的答案键错误**。下面保留程序生成答案键的工程做法，用构造题展示如何让评分依据可重算。

这件事也说明，答案键与评分器应尽可能由独立、可执行的逻辑生成，并用单元测试覆盖边界；同一作者手工写题、手工写答案，再凭直觉检查，容易把同一错误带进数据和复核。

```python
EXP = {
    "h1": str(sum(1 for i in range(1, 1001) if i % 3 and i % 7)),
    "h4": str(2**10 + 3**5 - 7**3),
    "h7": str(0xDEAD + 0b1011),
    "e2": str(pow(7, 100, 13)),
}
```

### 一道题长什么样

上面 `EXP` 只给了四个答案，读者没法复现一组完整的评分数据。以下是构造样例（未实跑模型）：

| id | 题面 | 期望值来源 | 判定方式 |
|---|---|---|---|
| `h1` | 1 到 1000 里，既不能被 3 整除也不能被 7 整除的数有多少个？ | `sum(1 for i in range(1,1001) if i % 3 and i % 7)` | 解析完整整数并与期望值相等；不能用子串包含 |
| `h4` | 计算 2^10 + 3^5 − 7^3，只回答数字 | `2**10 + 3**5 - 7**3` | 解析完整整数并与期望值相等 |
| `e2` | 计算 7^100 mod 13，只回答数字 | `pow(7, 100, 13)` | 解析完整整数并与期望值相等 |

这些样例只检验确定性数学题，不代表通用 Agent 评分器。复杂任务应有明确任务终态、硬约束、环境状态与评分器契约；模型说「完成了」不能代替环境断言。

用少于 k 次观测不能直接计算该任务的经验 Pass^k。每题必须恰好跑满 k 次，才可将「这 k 次是否全成功」记作一个 0/1 观测；多个独立任务上的全成功比例才是该指标的样本估计。更高 k 的外推需要额外概率模型与假设，不能把 5 次结果改称 Pass^10。

## 四、Pass^k 与长任务的乘积关系

下面这张表是**独立、同分布且每步成功率相同**时的解析计算，不是本项目测得的 Agent 任务成功率。若步骤 success probability 不同但条件概率可明确，整个路径概率应按链式法则相乘；只有各步条件成功率都等于同一 `p` 时才简化成 `p^n`。若步骤间相关、出现恢复分支或路径会随先前结果变化，直接使用 `p^n` 会错。

```text
p=0.999   1步= 99.9%   5步= 99.5%  10步= 99.0%  20步= 98.0%  50步= 95.1%
p=0.99    1步= 99.0%   5步= 95.1%  10步= 90.4%  20步= 81.8%  50步= 60.5%
p=0.95    1步= 95.0%   5步= 77.4%  10步= 59.9%  20步= 35.8%  50步=  7.7%
p=0.90    1步= 90.0%   5步= 59.0%  10步= 34.9%  20步= 12.2%  50步=  0.5%
```

这张表只说明给定模型假设下的路径概率如何变化。它不能推出「长任务一定该换工程手段而不是模型」；应先用轨迹诊断失败来自模型、工具、权限、超时、数据或编排，再选择提示、模型、验证、重试、补偿或人工审批。重试只有在副作用和未知结果语义已设计清楚时才安全。

图里的工程手段需要按失败机制选择。检查点只说明已持久化的进度；超时不等于副作用没发生；有副作用的步骤必须由接收端支持稳定幂等键或提供查询/对账机制。以下是内存级教学示例，**仅适用于接收端对同一幂等键去重且调用返回可解释结果的假设**，不能提供进程崩溃恢复或 exactly-once 保证：

```python
STATE = {}  # 教学用内存；生产环境需事务化持久化


def step_once(step_id, fn, idem_key):
    saved = STATE.get(step_id)
    if saved is not None and saved[0] == "done":
        return saved[1]

    for attempt in range(3):
        try:
            # 同一逻辑动作重试必须复用同一个 key；接收端负责原子去重。
            out = fn(idem_key=idem_key)
            STATE[step_id] = ("done", out)
            return out
        except (TimeoutError, ConnectionError):
            # 超时可能发生在远端已提交之后。只有接收端幂等，或查询确认未提交，才重放。
            if not getattr(fn, "replay_safe", False):
                raise RuntimeError("结果未知；先对账，不能盲目重放")
            continue

    raise RuntimeError("步骤重试耗尽；检查最后一次调用的结果是否未知")
```

这个片段不含持久化事务、租约、并发 worker 竞争或真实接收端实现；它表达的是边界：重放语义要显式证明，检查点和幂等键各自都不构成端到端 exactly-once。

## 五、怎么校准有区分度的评测集

评测集全通过或全失败时，先检查它与目标场景、样本难度、判定器有效性和样本量是否匹配；不要把「50%~90%」当作普适最佳区间。可按用途分别维护：

- **回归集**用来抓已知故障；它适合验证修复，但通常不能估线上发生率。
- **代表性样本**用来估目标分布表现；记录抽样框、时间窗与权重，避免把刻意过采样的失败题当作线上比例。
- **专家、合成与对抗样本**用来覆盖边界和高风险情形；单独报告，不能与生产频率混为一谈。
- **校验判定器**：抽样人工复核，检查误报、漏报、空值和异常格式；结果尽量基于外部状态或明确 rubric，而不是模型自述。
- **检查难度和方差**：按任务类型和风险分层查看结果；重复运行可诊断随机性，但任务是总体推断单位时，不能把同题重复当成额外独立任务。
- **版本化更新**：根据系统变化、已知缺陷和目标分布变化维护数据集，同时保留受控确认集，避免根据反复查看结果调到只适合当前评测集。

旧的「五轮全绿」「答案键全错」记录仍属未复核历史摘要，不可直接当作评测集饱和或模型准确性的实证。

## 六、把两个指标算出来

下面这段可以直接运行，无第三方依赖。它按任务先聚合，再以整个任务为单位 bootstrap；这样不会把同一道题的多次运行误当作相互独立的任务样本。这里的 percentile 区间只作小样本演示，20 个任务不足以保证区间有名义覆盖率。

Pass@k 的组合数估计量来自代码生成评测：对每题生成 `n >= k` 个候选，数出 `c` 个通过自动测试的候选，再估计从候选池随机抽 k 个时至少一个通过的概率。它依赖候选可交换抽样和有效测试 oracle；若真实 Agent 没有可信判定器或候选选择机制，不应把这个估计直接当生产成功率。来源：[Chen et al., Evaluating Large Language Models Trained on Code](https://arxiv.org/abs/2107.03374)。

```python
import random


def validate_runs(runs):
    if not runs:
        raise ValueError("至少需要一次运行")
    if any(type(value) is not bool for value in runs):
        raise TypeError("每次运行必须由判定器明确标为 True 或 False")


def pass_at_k(runs, k):
    """Chen et al. 的组合数估计量；runs 是 n 个候选的 pass/fail。"""
    validate_runs(runs)
    n, c = len(runs), sum(runs)
    if type(k) is not int or not 1 <= k <= n:
        raise ValueError("Pass@k 要求 1 <= k <= 候选数 n")
    if n - c < k:
        return 1.0
    # 1 - C(n-c, k) / C(n, k)，用连乘避免大数。
    all_fail = 1.0
    for i in range(k):
        all_fail *= (n - c - i) / (n - i)
    return 1.0 - all_fail


def pass_pow_k(runs, k):
    """本节定义的任务级 k 次全成功指示量。"""
    validate_runs(runs)
    if type(k) is not int or k < 1 or len(runs) != k:
        raise ValueError("Pass^k 要求每个任务恰好有 k 次运行")
    return 1.0 if all(runs) else 0.0


def task_metrics(per_task, k):
    if not per_task:
        raise ValueError("至少需要一个任务")
    for runs in per_task:
        if len(runs) != k:
            raise ValueError("所有任务都必须恰好运行 k 次")
        validate_runs(runs)
    single = sum(sum(runs) / k for runs in per_task) / len(per_task)
    at_k = sum(pass_at_k(runs, k) for runs in per_task) / len(per_task)
    pow_k = sum(pass_pow_k(runs, k) for runs in per_task) / len(per_task)
    return single, at_k, pow_k


def percentile_interval(values):
    values = sorted(values)
    if len(values) < 2:
        raise ValueError("bootstrap 至少需要两次重采样")
    lo = values[int(0.025 * (len(values) - 1))]
    hi = values[int(0.975 * (len(values) - 1))]
    return lo, hi


def cluster_bootstrap_ci(per_task, k, n_boot=10000, seed=0):
    """重采样完整任务组，分别估计三个任务级指标的 percentile 区间。"""
    if n_boot < 2:
        raise ValueError("n_boot 至少为 2")
    task_metrics(per_task, k)  # 校验任务组结构
    rng = random.Random(seed)
    n_task = len(per_task)
    samples = {"single": [], "pass_at_k": [], "pass_pow_k": []}
    for _ in range(n_boot):
        selected = [rng.choice(per_task) for _ in range(n_task)]
        single, at_k, pow_k = task_metrics(selected, k)
        samples["single"].append(single)
        samples["pass_at_k"].append(at_k)
        samples["pass_pow_k"].append(pow_k)
    return {name: percentile_interval(values) for name, values in samples.items()}


# 构造模拟：20 个任务各运行 5 次，每次成功概率设为 90%；不是模型实测。
rng = random.Random(42)
n_task, k = 20, 5
per_task = [[rng.random() < 0.9 for _ in range(k)] for _ in range(n_task)]
single, at_k, pow_k = task_metrics(per_task, k)
intervals = cluster_bootstrap_ci(per_task, k)

print("任务等权单次成功率 %.1f%%" % (100 * single))
print("Pass@%d              %.1f%%" % (k, 100 * at_k))
print("Pass^%d               %.1f%%" % (k, 100 * pow_k))
for name, label in (("single", "单次成功率"), ("pass_at_k", "Pass@k"), ("pass_pow_k", "Pass^k")):
    lo, hi = intervals[name]
    print("%s 的任务级 percentile 区间 [%.1f%%, %.1f%%]" % (label, 100 * lo, 100 * hi))

# 边界回归：非法 k、空样本、非布尔判定与任务重复次数不一致都应拒绝。
for bad_k in (0, 6):
    try:
        pass_at_k([True, False, True, False, True], bad_k)
    except ValueError:
        pass
    else:
        raise AssertionError("非法 k 应触发 ValueError: %s" % bad_k)
for bad_runs in ([], [1, 0, 1, 1, 0]):
    try:
        pass_pow_k(bad_runs, 5)
    except (ValueError, TypeError):
        pass
    else:
        raise AssertionError("无效运行记录应触发错误")
try:
    task_metrics([[True, False]], 5)
except ValueError:
    pass
else:
    raise AssertionError("任务运行数不一致应触发 ValueError")
```

该模拟固定 seed，说明程序如何在 20 个合成任务上计算指标；它不是模型总体估计。集群 bootstrap 的重采样单位是任务，保留同一任务内部 5 次运行的结构；区间仍依赖独立任务抽样、任务样本代表目标总体等假设。只有 20 个任务，区间会很粗糙，不能据此承诺 95% 覆盖率。集群重采样为何保留组内相关，可参见 [Simple Approaches for Dealing With Correlated Data](https://academic.oup.com/aje/article/192/4/507/6973188)。

**实跑状态**：本地 Python 3.14.7 离线运行了固定种子合成模拟；未调用模型 provider。输出：单次成功率 91.0%、Pass@5 100.0%、Pass^5 60.0%；单次成功率的任务级 percentile 区间为 [86.0%, 96.0%]，Pass@5 为 [100.0%, 100.0%]，Pass^5 为 [40.0%, 80.0%]。这是 20 个构造任务各运行 5 次、单次成功率参数设为 90% 的模拟样本，不是历史模型表现。只有 20 个独立任务组，区间很粗糙，名义 95% 覆盖率没有验证。若需缩小不确定性，应增加目标任务总体中的独立任务数，而不是仅给相同任务追加重试。

### 一个可复现的指标错误

上面 `pass_at_k` 我第一版写成：

```python
def pass_at_k(runs, k):
    return 1.0 if any(runs) else 0.0      # 错
```

它没有使用参数 `k`，只回答「这 n 个已观察候选里是否存在成功」。当 `k=n` 时，这个事件与观测到的全体候选至少一条成功相同；但当 `k<n` 时，它没有估算从 n 个候选中抽 k 个的成功概率。例如 `runs=[True, False, False, False, False]` 时，Pass@1 的组合数估计为 20%，而错误函数返回 100%。此外，函数也没有拒绝 `k>n`。

组合数估计量 `1 - C(n-c, k) / C(n, k)` 估算的是从 n 个候选中无放回选 k 个时至少一个通过的概率；它不是对任意 Agent 重试过程的保证。对于本节合成样例 `n=k=5`，Pass@5 就等于该题这五个运行中是否至少一次成功。若要报告 Pass^k，每题必须恰好有 k 次运行并按全成功记 0/1；若从更少运行外推概率，必须另外声明模型假设，不能把有限观察直接改称 Pass^k。

## 七、小结

- **Pass@k**在本节指：每题从 `n` 个可判定候选中随机抽取 `k` 个，至少一个成功的估计；它依赖可交换的候选、有效判定器，以及真实产品有能力安全选择成功结果。不要把它无条件称为能力上限。
- **Pass^k**在本节是每题恰好 k 次运行全部成功的任务级比例记号；它不是通用标准术语，也不能仅凭少于 k 次观察外推。
- 只有单题各步独立且条件成功率相同，连续 n 步全成功率才是 `p^n`。任务异质、依赖路径和恢复机制都要求更细的分层或直接按任务终态评估。
- 评测全通过是诊断信号，不是饱和的证明。检查目标分布、风险覆盖、判定器有效性和样本量；没有固定的 50%–90% 最佳通过率。
- 同题多次运行共享任务难度。估计任务总体不确定性时，应按抽样设计重采样独立任务单元；任务聚类少时，bootstrap 区间本身也可能不可靠。
- 旧稿的五轮全 100% 与「12 题实际 12/12」没有原始轨迹可复核，继续保留为历史说法，不作当前模型或工具结论。

下一步是把目标写成可以独立判定的任务终态，再选择与交付流程一致的单次、多候选、重复可靠性指标。若需要在多次尝试中挑一个成功结果，先证明判定器可信、候选可安全验证且选择动作不会重复副作用；若一次执行就会产生不可逆影响，应优先设计授权、对账与失败恢复，而不是只提高 Pass@k。
