[界面动作与工具调用的区别](/chapters/computer-use/what-differs)说明界面 agent 的动作空间是**开放**的：同一个 click 既能点「创建」，也能点「删除」。[工具注册表](/chapters/agent-loop/tool-registry)登记服务端暴露给模型的工具和参数；它限制可提出的调用名称，却不替代服务端授权。

这一章要处理的是第三种情况：**模型能调的工具，权限太大了**。这里的“模型能调”指宿主把该工具暴露给模型；提示和工具注册表都不保证执行环境的可达范围；工具注册表本身不是授权边界，服务端仍须校验调用。

## 三个威胁建模前提

下面是用于设计隔离策略的工程前提，不是由有限样本估出的概率，也不是对模型行为的保证。

**前提一：模型输出和工具调用可能不符合任务要求。** 有限评测只能展示被测试到的失败形态，不能证明所有输入都覆盖；提示可能改善某些输出，但不能替代服务端的参数校验、授权和执行边界。参见[最小 Agent 循环](/chapters/agent-loop/minimal-loop)与[工具注册表](/chapters/agent-loop/tool-registry)中的本地失败处理示例。

**前提二：模型可读到的内容可能受攻击者影响。** 网页、文件、工具返回值和代码注释都可能包含诱导性文字。提示注入可尝试影响模型的后续行为；若它还持有有副作用的工具，攻击是否成功取决于模型、上下文、工具权限和宿主控制；提示注入是风险路径，不是成功保证。参见[提示注入与能力边界](/chapters/agent-security/injection-escalation)。

**前提三：工具调用会使用宿主授予的能力。** 活动范围、预算、熔断和高影响动作审批能限制一部分调用（见[权限与活动范围](/chapters/computer-use/safety-and-scope)）；如果这些检查没有约束具体对象或目标资源，仍可能出现**动作类型获准、实际访问范围过大**的情况。

例如，一个「读文档」工具如果直接打开未受限的用户路径，攻击者控制的路径可能越过预期目录。若上层只判断“允许调用 read_file”而没有做对象级路径授权，工具动作虽合法，访问对象仍可能越权。

**这就是隔离要解决的问题：不是「能不能调这个工具」，而是「调了之后它够得着什么」。** 实际影响范围取决于宿主身份、挂载、网络出口和执行器配置；必须在目标部署环境验证。

## 隔离与权限的分工

这两件事经常被混在一起，但它们防的东西不同：

| | 防什么 | 例子 |
|---|---|---|
| **工具授权** | 主体可以请求哪些动作 | 不许调用转账工具 |
| **隔离**（本节） | 进程能接触哪些文件、网络和资源 | 执行环境被 OS 限制在指定目录与出口 |

身份认证用于确认调用主体；工具授权与对象级授权分别决定主体能否请求动作、能否访问具体对象；隔离限制进程实际可达的资源。它们解决的问题不同，缺一项可能留下漏洞：

- 只有工具授权没有对象级授权：主体获准调用 `read_file`，但实现仍可能读到不该访问的路径。
- 只有隔离没有授权：进程的可达范围虽有限，主体仍可能在该范围内发起不该发生的动作或消耗资源。
- 只有身份认证没有授权：确认了“是谁”，不等于该主体获准执行这项动作或访问这个对象。

## 一个具体的成本对比

隔离的价值可以用「出事之后的爆炸半径」衡量。三种做法：

**不做独立隔离。** 工具进程能访问的资源通常受宿主身份与部署配置决定；如果它能读敏感数据，且输出或网络路径可把数据带走，影响范围可能很大。能读取不等于数据必然外泄，读取权限与外传通道要分别限制。

**做隔离，但做得不严。** 比如只用字符串前缀检查限制目录。在[最小权限](/chapters/sandboxing/least-privilege)一节的固定夹具里，这个具体实现被 6 种输入中的 4 种绕过；朴素版放过 4/6 种攻击（仅本固定夹具），不代表其他路径检查或生产系统的漏洞率。这里的六种输入是代码内嵌固定输入，不是随机抽样或覆盖度证明。

**按最小权限设置可执行的边界。** 由 OS/运行时限制文件范围、资源和网络出口，并只暴露任务所需的数据。用户态 `realpath` 检查可帮助识别固定路径夹具中的穿越，但 `realpath → 类型检查 → open` 由多个独立操作组成，本身不是竞态安全的生产边界；[Linux 路径解析文档](https://docs.kernel.org/filesystems/path-lookup.html)介绍了 `openat2` 等内核路径解析约束，实际能力还取决于宿主配置和输出通道。

**中间那一档容易制造虚假的安全感。** 因为团队付出了实现成本，可能误以为风险已被覆盖；上面的固定夹具展示了一种具体的前缀检查漏洞，不推出“中等隔离总是最危险”的普遍排序。

## 隔离有代价，需要按威胁模型权衡

代价有三条，都要认：

**一、能力受限。** 沙箱内的模型做不了沙箱外的事。这可能让某些合法任务变得做不到 —— 那就需要你**显式地开一个口子**，而不是默认全开。

**二、实现复杂度。** 要维护目录映射（把模型给的相对路径映射到沙箱内的真实位置，由隔离层解析，不交给工具实现）、要处理**路径规范化**（把 `..` 与符号链接解析到目标路径再做边界判断 —— 见[最小权限](/chapters/sandboxing/least-privilege)中的固定夹具）、要管生命周期（什么时候创建、什么时候清理）。

**三、调试变难。** 出问题时你面对的不只是业务错误，还有权限拒绝。所以策略/隔离边界需要可观察的拒绝结果（见[执行策略与审计](/chapters/sandboxing/execution-policy)），否则你可能只看到「工具失败」而不知道由哪条控制拒绝。

第三条常被忽略：没有可观测拒绝原因的隔离层会增加排障成本，团队可能在压力下放宽策略；日志也应遵循最小化原则，避免记录原始参数或宿主路径。

## 一个判断该不该隔离的问题

最后给一条可以在设计评审上用的判据：**问「如果这个工具的输入完全由攻击者控制，最坏会发生什么」。**

注意「完全由攻击者控制」这个前提。不要问「模型会不会给奇怪的输入」—— 那是在问模型的意图；要问「如果输入是恶意的，这个工具能造成什么」。

用这条判据过一遍几个常见工具：

| 工具 | 最坏情况（输入完全恶意） | 要不要隔离 |
|---|---|---|
| 查天气（参数是城市名） | 参数若被不安全地拼进查询，可能触发注入 | 按具体解析器与下游接口校验；必要时使用参数化接口 |
| 读文件（参数是路径） | 访问范围可能超出任务所需 | 做对象级授权；若路径边界无法由工具可靠落实，再由 OS/运行时隔离限制可达文件 |
| 执行代码（参数是不可信代码） | 代码可能触及当前进程可访问的资源 | 应由 OS/运行时提供与威胁模型匹配的边界；“最强”不是可移植的配置等级 |
| 发 HTTP 请求（参数是 URL） | 可能请求非预期目标或泄露数据 | 做目标校验与连接层/出口策略；隔离执行环境本身不等于 SSRF 防护（[图像如何进入上下文](/chapters/multimodal/how-images-enter-context)中的例子说明 provider 可以在服务端获取其请求体里提供的公开图片 URL） |
| 查订单（参数是订单号） | 越权查别人的订单 | 要**鉴权**而不是隔离 |

最后一行的核心防护是鉴权与对象级授权。隔离限制进程可达的资源，鉴权决定调用主体身份；一个查订单的工具即使运行在沙箱中，若后端未校验订单归属，仍可能越权。隔离可以缩小其他可达范围，但不能替代授权。

因此评审时至少分别检查：**身份认证**（主体是谁）、**工具授权**（允许请求哪些动作）、**对象级授权**（能否访问这个具体对象）和**隔离**（进程实际能接触什么）。它们回答不同问题；具体控制应按身份、对象、执行环境和网络出口分别落实。

## 一个反过来的问题：隔离做过头

前面都在讲「隔离不够」。但有一个同样真实的失败：**隔离做得太严，导致正常任务做不到。**

它的表现很具体：模型反复尝试同一个操作、每次都拿到权限拒绝、然后在回答里说「我无法完成这个任务」。而**从你的角度看，这个任务是能做的** —— 只是你没给它那条路。

三个防过头的做法：

**一，从任务出发列白名单，不要只依赖黑名单。** [隔离的层级](/chapters/sandboxing/isolation-levels)一节中的 L1 fixture 展示了一个绕过例子，并不表示所有黑名单实现都必然失效。做法是把这个工具**真正需要**访问的路径/域名列出来，其他默认拒绝。

**二，拒绝时要提供安全且可操作的反馈。** 笼统的「权限不足」没有说明允许的范围，模型可能无法据此修正请求；也不要回显敏感路径、身份信息或内部策略细节。根据产品边界返回受控的可选操作，并限制重试轮数。

**三，把拒绝记进日志。** 如果疑似合法的操作被频繁拒绝，那是需要排查策略与任务定义的信号；先确认拒绝是否正确，再决定是否调整。没有记录时，你可能只看到「模型做不好这件事」。

## 一个数字：4/6

这一章会用到 **4/6** 这个固定夹具结果：朴素路径前缀检查在 6 个选定输入中，4 个读取到了夹具根目录外的无害标记文件。它展示这个具体实现会越界；不是攻击覆盖度，也不是其他路径检查、隔离方案或生产系统的漏洞率；它不是攻击成功率或生产漏洞率。
## 完整可运行代码

下面这段代码实现两个版本的「沙箱目录读取」检查，并用 6 种攻击手法做对照 —— 其中一个版本会读到它不该读到的东西。

```python
"""对照演示路径字符串检查与 realpath 检查的差异。

纯本地 fixture，不是生产沙箱。实跑状态：2026-10-21。
"""
import atexit
import os
import shutil
import tempfile

ROOT = tempfile.mkdtemp(prefix="sandbox-demo-")
atexit.register(shutil.rmtree, ROOT, ignore_errors=True)
SANDBOX = os.path.join(ROOT, "sandbox")
os.makedirs(os.path.join(SANDBOX, "sub"))

# 无害标记只用于识别 fixture 数据，不是真实凭据。
with open(os.path.join(ROOT, "secret.env"), "w") as f:
    f.write("SENSITIVE_MARKER=fixture\n")
with open(os.path.join(SANDBOX, "ok.txt"), "w") as f:
    f.write("这是沙箱内允许读的文件\n")
os.symlink(os.path.join(ROOT, "secret.env"), os.path.join(SANDBOX, "sub", "link.txt"))

LOG = []


def naive_read(rel):
    """第一版：把根目录拼上去，然后检查字符串前缀。"""
    full = os.path.join(SANDBOX, rel)
    if not full.startswith(SANDBOX):
        return "❌ 拒绝（前缀检查）"
    try:
        with open(full) as f:
            return "✅ 读到：" + f.read().strip()[:32]
    except Exception as e:
        return "读取失败：" + type(e).__name__


def safe_read(rel):
    """静态演示：规范化路径后检查边界；不是竞态安全的沙箱。"""
    base = os.path.realpath(SANDBOX)
    full = os.path.realpath(os.path.join(SANDBOX, rel))
    if full != base and not full.startswith(base + os.sep):
        LOG.append({"rule_id": "R-safe", "target_scope": "outside-sandbox", "reason": "真实路径越界"})
        return "❌ 拒绝（真实路径越界）"
    if not os.path.isfile(full):
        LOG.append({"rule_id": "R-safe", "target_scope": "in-sandbox-non-regular", "reason": "不是普通文件"})
        return "❌ 拒绝（不是普通文件）"
    try:
        with open(full) as f:
            return "✅ 读到：" + f.read().strip()[:32]
    except Exception as e:
        return "读取失败：" + type(e).__name__


ATTACKS = [
    ("正常读取（应该在沙箱内）", "ok.txt"),
    ("用 .. 往回跳一级", "../secret.env"),
    ("往回跳两级", "sub/../../secret.env"),
    ("符号链接（沙箱内的 link 指向外部）", "sub/link.txt"),
    ("绝对路径", "/etc/hosts"),
    ("带多余斜杠的越界", "./.././secret.env"),
]

if __name__ == "__main__":
    print("沙箱外的 fixture 文件含有无害标记，不是真实密钥")
    print("  %-34s %-30s %s" % ("攻击手法", "朴素前缀检查", "realpath 检查"))
    leaks = 0
    for label, rel in ATTACKS:
        n = naive_read(rel)
        s = safe_read(rel)
        if n.startswith("✅") and s.startswith("❌"):
            leaks += 1
        print("  %-34s %-30s %s" % (label, n[:24], s[:24]))
    print("朴素版放过 %d/%d 种攻击（仅本固定夹具）" % (leaks, len(ATTACKS)))
    print("=== 拒绝日志（%d 条；不含原始参数或宿主绝对路径）===" % len(LOG))
    for event in LOG[:3]:
        print("  " + str(event))
    print("realpath 示例只展示静态路径规范化；并发目录替换仍可能造成 TOCTOU。")
```


本地运行输出（Python 标准库；随机临时目录名不显示）：

```text

  攻击手法                               朴素前缀检查                         realpath 检查

  用 .. 往回跳一级                         ✅ 读到：SENSITIVE_MARKER=fi       ❌ 拒绝（真实路径越界）
  往回跳两级                              ✅ 读到：SENSITIVE_MARKER=fi       ❌ 拒绝（真实路径越界）
  符号链接（沙箱内的 link 指向外部）               ✅ 读到：SENSITIVE_MARKER=fi       ❌ 拒绝（真实路径越界）

  {'rule_id': 'R-safe', 'target_scope': 'outside-sandbox', 'reason': '真实路径越界'}
  {'rule_id': 'R-safe', 'target_scope': 'outside-sandbox', 'reason': '真实路径越界'}
```

那个 4/6 由代码数出来（`n.startswith("✅") and s.startswith("❌")`），不是肉眼数的 —— 这一点重要，因为「看着对」的检查最容易骗过的就是写它的人。

## 被拒调用长什么样：一行日志的字段

上面那段代码里，`safe_read` 每次拒绝都往 `LOG` 追加一条。这条记录就是隔离层的**可观察载体** —— 没有它，你看到的只有「工具失败」，看不到「为什么失败、是哪条规则拦的」。

一条最小记录可以长这样（示例：构造数据，未实跑；不把模型原始参数或宿主路径放进普通日志）：

```json
{
  "request_id": "host-generated-id",
  "tool": "read_file",
  "rule_id": "R-safe",
  "target_scope": "outside-sandbox",
  "reason": "真实路径越界",
  "decision": "deny"
}
```

原始路径与解析后的宿主路径可能含个人信息或目录结构；如确需取证，应单独评估目的、访问控制和保留期限。**默认不记录完整路径**，可通过宿主生成的请求/任务 ID 关联受控追踪。

字段怎么定？判据只有一条：**事后能不能只靠这条日志回答三个问题**。

| 字段 | 回答的问题 | 丢了会怎样 |
|---|---|---|
| `request_id` | 与宿主侧受控追踪关联 | 无法定位对应请求 |
| `rule_id` | 是哪条规则拦的 | 分不清策略决策与实现问题 |
| `target_scope` | 目标属于哪个策略范围 | 无法快速判断拒绝类别 |
| `reason` | 为什么拒绝（可安全回填的摘要） | 调用方拿不到可操作的错误类别 |
| `decision` | 最终允许还是拒绝 | 审计事件语义不清 |

落地步骤：

1. **谁写** —— 策略/沙箱的**实现层**写，不是每个工具作者手写。散在工具里的检查会随工具数量增加而失真。
2. **写到哪里** —— 与业务日志分开的审计流；访问控制与保留期限应按日志敏感级别配置。
3. **下一轮怎么读回来** —— 只把不含敏感信息的拒绝摘要作为工具错误回填给模型；宿主绝对路径默认不进普通日志也不回填。
4. **怎么更新** —— 日志字段本身不改；拒绝频率只是诊断信号之一；结合任务结果、拒绝原因、用户身份和策略命中路径调查，不能仅凭频率就放宽规则。

**失败形态：** 观察到一段时间内只有 allow、没有 deny。可能是拒绝路径未接入日志、日志接收端丢失事件，也可能这段时间确实没有请求被拒；在判定隔离状态前，要验证拒绝事件覆盖与日志管道健康。没有可观测性会增加排障成本，压力下也可能诱使团队放宽控制。

## 常见坑

- **以为提示词能代替隔离。** 提示可以影响模型行为，但不限制工具进程的文件、网络或资源可达范围。
- **只做权限不做隔离。** 「读文档」是合法动作，但它的实现可能够得着整个文件系统。
- **做了隔离但不验证。** 本文的固定 fixture 中，朴素前缀检查有 4/6 个输入越过了目录边界；该比例不代表其他实现的漏洞率。
- **隔离层不记日志。** 它会变成黑箱，而团队遇到权限错误时的第一反应是把它关掉。
- **默认全开、需要时再收。** 应该反过来：默认最小，需要时显式开口子 —— 而且开口子的动作要留下记录。
