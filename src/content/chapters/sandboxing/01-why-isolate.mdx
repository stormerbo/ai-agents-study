第 9 章讲过界面 agent 的动作空间是**开放**的：同一个 click 既能点「创建」，也能点「删除」。第 11 章讲过工具注册表（服务端登记「有哪些工具、各自什么参数」的那份清单）是**封闭**的：模型只能调你注册的那些。

这一章要处理的是第三种情况：**模型能调的工具，权限太大了。**

## 三个真实的前提

隔离不是偏执，它建立在三个已经被前面章节证实的前提上。

**前提一：模型会犯错，而且错法不可预测。** 第 4 章实测过它把错误当数据写进表格；第 9 章实测过它反复点同一个错位置 8 次；第 10 章实测过它把三元表达式写进工具参数。这些不是「偶尔糊涂」，是**输出空间的固有性质** —— 你没法用更好的提示词把它消除。

**前提二：输入可以被操纵。** 第 17 章会展开，但结论可以先给：**任何进入上下文的内容都是输入**，包括你不认为是输入的那些 —— 工具返回值、网页正文、文件名、代码注释。而指令注入 —— 把一段伪装成指令的文字混进模型会读到的内容里，让它改变行为 —— 在 agent 里会被放大，因为**它不只是让模型说错话，而是让模型调用工具**。

**前提三：动作有后果。** 第 9 章那四道闸门（活动范围、预算、熔断、不可逆确认）解决的是「不该做的动作不要做」。但它们防不住一类情况：**这个动作确实该做，只是它的权限范围太大了。**

具体说：一个「读文档」工具，如果实现里直接打开用户给的路径，那么模型被注入之后可以用它读系统敏感文件。闸门拦不住 —— 因为读文档是合法的，路径也在「工具允许的参数」范围内。

**这就是隔离要解决的问题：不是「能不能调这个工具」，而是「调了之后它够得着什么」。**

## 隔离与权限的分工

这两件事经常被混在一起，但它们防的东西不同：

| | 防什么 | 例子 |
|---|---|---|
| **权限**（第 9、11 章） | 不该做的动作 | 不许调用转账工具 |
| **隔离**（本章） | 该做的动作能造成多大破坏 | 读文件只能读沙箱内 |

一个类比：**权限是「谁能进这栋楼」，隔离是「进去之后能开哪几扇门」。** 两件事都要做，缺一个都不够：

- 只有权限没有隔离：合法用户进了楼，能进任何房间
- 只有隔离没有权限：房间是锁着的，但你可以无限次尝试开锁（成本与噪声）

## 一个具体的成本对比

隔离的价值可以用「出事之后的爆炸半径」衡量。三种做法：

**不做隔离。** 一个读文件的工具能读整个文件系统。一次成功的注入 = 一次完整的数据泄露。

**做隔离，但做得不严。** 比如用一个前缀检查限制目录。第 3 节会实测：**这类检查有 4/6 的攻击手法能绕过** —— 而它给人的感觉是「已经做了防护」。

**做隔离，且按最小权限。** 沙箱目录、规范化后的真实路径检查、只允许普通文件、网络默认关闭。攻击面被压到「沙箱内的普通文件」。

**中间那一档最危险。** 因为它既付出了成本，又让人以为已经安全了 —— 而实际上没有。第 3 节会具体演示这件事。

## 隔离也有代价，但它通常可接受

代价有三条，都要认：

**一、能力受限。** 沙箱内的模型做不了沙箱外的事。这可能让某些合法任务变得做不到 —— 那就需要你**显式地开一个口子**，而不是默认全开。

**二、实现复杂度。** 要维护目录映射（把模型给的相对路径映射到沙箱内的真实位置，由隔离层解析，不交给工具实现）、要处理**路径规范化**（把 `..` 与符号链接解析成唯一的真实路径再做判断 —— 第 3 节实测了不做这一步的后果）、要管生命周期（什么时候创建、什么时候清理）。

**三、调试变难。** 出问题时你面对的不只是业务错误，还有权限拒绝。所以隔离层必须**记日志**（第 5 节），否则你会看到「工具失败」而不知道为什么。

三条里第三条最容易被忽略：**没有日志的隔离层会变成黑箱**，团队遇到权限错误时的第一反应会是「把它关掉」。

## 一个判断该不该隔离的问题

最后给一条可以在设计评审上用的判据：**问「如果这个工具的输入完全由攻击者控制，最坏会发生什么」。**

注意「完全由攻击者控制」这个前提。不要问「模型会不会给奇怪的输入」—— 那是在问模型的意图；要问「如果输入是恶意的，这个工具能造成什么」。

用这条判据过一遍几个常见工具：

| 工具 | 最坏情况（输入完全恶意） | 要不要隔离 |
|---|---|---|
| 查天气（参数是城市名） | 参数被拼进某个查询 → 注入 | 看实现：如果拼字符串就要 |
| 读文件（参数是路径） | 读任意文件 | **必须要** |
| 执行代码（参数是代码） | 执行任意代码 | **必须要，而且要最强的那层** |
| 发 HTTP 请求（参数是 URL） | 访问内网、云元数据端点 | **必须要**（第 8 章实测过 URL 图像会被服务端下载） |
| 查订单（参数是订单号） | 越权查别人的订单 | 要**鉴权**而不是隔离 |

最后一行值得单独说：**它的防护方式不是隔离，而是鉴权。** 隔离管的是「够得着哪些资源」，鉴权管的是「以谁的身份够」。一个查订单的工具在沙箱里跑，仍然能查到别人的订单 —— 因为沙箱不改变身份。

所以完整的三层是：**权限**（能不能调）、**隔离**（够得着什么）、**鉴权**（以谁的身份）。三者正交，缺一个都留着一条口子。

## 一个反过来的问题：隔离做过头

前面都在讲「隔离不够」。但有一个同样真实的失败：**隔离做得太严，导致正常任务做不到。**

它的表现很具体：模型反复尝试同一个操作、每次都拿到权限拒绝、然后在回答里说「我无法完成这个任务」。而**从你的角度看，这个任务是能做的** —— 只是你没给它那条路。

三个防过头的做法：

**一，从任务出发列白名单，不要从「什么危险」出发列黑名单。** 黑名单永远漏（第 2 节的 L1 就是这个问题的示范）。做法是：把这个工具**真正需要**访问的路径/域名列出来，其他的默认拒绝。

**二，拒绝时要说明原因和可选项。** 一句笼统的「权限不足」会让模型原地重试（第 9 章实测过这个行为）。回到「**你只能访问 /workspace 下的文件**」它才知道该怎么办。

**三，把拒绝记进日志。** 如果一个合法的操作被频繁拒绝，那是**策略需要放宽**的信号 —— 而如果你没记，你只会看到「模型做不好这件事」。

## 一个数字：4/6

这一章后面会反复出现一个数字：**4/6**。

它指的是第 3 节那个实验 —— 一个「看着完全正确」的沙箱路径检查，在 6 种常见攻击手法里被绕过了 4 种。那 4 次都成功读到了沙箱外的文件。

这个数字值得先放在这里，因为它回答了「为什么必须隔离」这个问题的另一半：**不是「要不要隔离」，而是「你以为的隔离可能不成立」。** 中间那一档最危险 —— 付出了实现成本，却没有得到安全，而且它看起来是安全的。
## 完整可运行代码

下面这段代码实现两个版本的「沙箱目录读取」检查，并用 6 种攻击手法做对照 —— 其中一个版本会读到它不该读到的东西。

```python
"""把一个「看着对」的沙箱检查攻破，再给出修好的版本。

这是第 16 章最核心的一次演示：**权限检查的直觉几乎总是错的。**
纯本地，不依赖任何外部服务。实跑状态：2026-10-09。
"""
import os, shutil, tempfile

ROOT = os.path.join(tempfile.gettempdir(), "sandbox-demo")
if os.path.exists(ROOT):
    shutil.rmtree(ROOT)
SANDBOX = os.path.join(ROOT, "sandbox")
os.makedirs(os.path.join(SANDBOX, "sub"))

# 沙箱外的「机密」：一个正常系统里到处都有的东西
with open(os.path.join(ROOT, "secret.env"), "w") as f:
    f.write("API_KEY=sk-live-9f3a...（这就是不该被读到的东西）\n")
with open(os.path.join(SANDBOX, "ok.txt"), "w") as f:
    f.write("这是沙箱内允许读的文件\n")

# 在沙箱内造一个指向外部的符号链接 —— 看起来完全无害
os.symlink(os.path.join(ROOT, "secret.env"), os.path.join(SANDBOX, "sub", "link.txt"))

LOG = []   # 被拒的调用都记在这里（真实系统里落盘/上报）


def naive_read(rel):
    """第一版：把根目录拼上去，然后检查前缀。看着很对。"""
    full = os.path.join(SANDBOX, rel)
    if not full.startswith(SANDBOX):
        return "❌ 拒绝（前缀检查）"
    try:
        with open(full) as f:
            return "✅ 读到：" + f.read().strip()[:32]
    except Exception as e:
        return "读取失败：" + type(e).__name__


def safe_read(rel):
    """第二版：先规范化成真实路径，再检查它是否真在沙箱内。"""
    base = os.path.realpath(SANDBOX)
    full = os.path.realpath(os.path.join(SANDBOX, rel))
    # 注意结尾的分隔符：否则 /sandbox-evil 会被当成在 /sandbox 内
    if full != base and not full.startswith(base + os.sep):
        LOG.append({"rule_id": "R-safe", "raw": rel, "resolved": full, "reason": "真实路径越界"})
        return "❌ 拒绝（真实路径越界）"
    if not os.path.isfile(full):
        LOG.append({"rule_id": "R-safe", "raw": rel, "resolved": full, "reason": "不是普通文件"})
        return "❌ 拒绝（不是普通文件）"
    try:
        with open(full) as f:
            return "✅ 读到：" + f.read().strip()[:32]
    except Exception as e:
        return "读取失败：" + type(e).__name__


ATTACKS = [
    ("正常读取（应该在沙箱内）", "ok.txt"),
    ("用 .. 往回跳一级", "../secret.env"),
    ("往回跳两级", "sub/../../secret.env"),
    ("符号链接（沙箱内的 link 指向外部）", "sub/link.txt"),
    ("绝对路径", "/etc/hosts"),
    ("带多余斜杠的越界", "./.././secret.env"),
]

if __name__ == "__main__":
    print("沙箱目录：%s" % SANDBOX)
    print("沙箱外有一个 secret.env —— 它就是不能读到的东西")
    print()
    print("  %-34s %-30s %s" % ("攻击手法", "朴素前缀检查", "真实路径检查"))
    leaks = 0
    for label, rel in ATTACKS:
        n = naive_read(rel)
        s = safe_read(rel)
        if n.startswith("✅") and s.startswith("❌"):
            leaks += 1          # 朴素放行、真实路径拒绝 = 一次绕过
        print("  %-34s %-30s %s" % (label, n[:24], s[:24]))
    print()
    print("朴素版放过 %d/%d 种攻击（判定：朴素放行、真实路径拒绝）" % (leaks, len(ATTACKS)))
    print()
    print("=== 拒绝日志（%d 条）===" % len(LOG))
    for e in LOG[:3]:
        print("  " + str(e))
    print()

    print("=== 关键点 ===")
    print("  朴素版把 '%s/../secret.env' 拼出来，它的前缀**确实是**沙箱路径 ——" % SANDBOX.split('/')[-1])
    print("  所以 startswith 检查通过了。前缀检查的问题在于：它检查的是**字符串**，")
    print("  而不是**文件实际在哪**。")
    print()
    print("  修好的版本有两处关键改动：")
    print("    1. realpath —— 把 .. 和符号链接都解析掉，得到真实路径")
    print("    2. 结尾加分隔符 —— 否则 /sandbox-evil 会被误判为在 /sandbox 内")
    print()
    print("  还有第三条不在路径里但同样重要：**只允许普通文件**。")
    print("  如果 path 指向一个目录或设备文件（比如 /dev/zero），读它会挂住。")
```

实跑输出（2026-10-12）：

```text

  正常读取（应该在沙箱内）                       ✅ 读到：这是沙箱内允许读的文件               ✅ 读到：这是沙箱内允许读的文件
  用 .. 往回跳一级                         ✅ 读到：API_KEY=sk-live-9f3       ❌ 拒绝（真实路径越界）
  往回跳两级                              ✅ 读到：API_KEY=sk-live-9f3       ❌ 拒绝（真实路径越界）

  {'rule_id': 'R-safe', 'raw': 'sub/../../secret.env', 'resolved': '/private/var/folders/_h/fkcs12zx23x_53fxg9lt_qbm0000gn/T/sandbox-demo/secret.env', 'reason': '真实路径越界'}
  {'rule_id': 'R-safe', 'raw': 'sub/link.txt', 'resolved': '/private/var/folders/_h/fkcs12zx23x_53fxg9lt_qbm0000gn/T/sandbox-demo/secret.env', 'reason': '真实路径越界'}
```

那个 4/6 由代码数出来（`n.startswith("✅") and s.startswith("❌")`），不是肉眼数的 —— 这一点重要，因为「看着对」的检查最容易骗过的就是写它的人。

## 被拒调用长什么样：一行日志的字段

上面那段代码里，`safe_read` 每次拒绝都往 `LOG` 追加一条。这条记录就是隔离层的**可观察载体** —— 没有它，你看到的只有「工具失败」，看不到「为什么失败、是哪条规则拦的」。

一条完整记录长这样（示例：构造数据，未实跑）：

```json
{
  "ts": "2026-10-12T10:03:41.512+08:00",
  "tool": "read_file",
  "rule_id": "R-safe",
  "raw_path": "sub/link.txt",
  "resolved_path": "/tmp/sandbox-demo/secret.env",
  "reason": "真实路径越界",
  "decision": "deny"
}
```

字段怎么定？判据只有一条：**事后能不能只靠这条日志回答三个问题**。

| 字段 | 回答的问题 | 丢了会怎样 |
|---|---|---|
| `rule_id` | 是哪条规则拦的 | 分不清是策略错还是实现错，只能重跑复现 |
| `raw_path` | 模型当时要读什么 | 分不清「注入在试探」和「正常任务被误拦」 |
| `resolved_path` | 它实际会打开哪个文件 | 前缀合法的绕过在日志里和正常读取一模一样 |
| `reason` | 为什么拒绝（可回填给模型） | 模型拿不到可选项，原地重试（第 9 章实测过） |

落地步骤：

1. **谁写** —— 策略/沙箱的**实现层**写，不是每个工具作者手写。散在工具里的检查会随工具数量增加而失真。
2. **写到哪里** —— 与业务日志分开的审计流（第 5 节那套），访问控制和业务系统同级（第 4 节）。
3. **下一轮怎么读回来** —— 只把 `reason` 作为工具错误回填给模型；`resolved_path` 只进审计，不回填 —— 它会泄露宿主目录结构。
4. **怎么更新** —— 日志字段本身不改；**被拒频率**是策略松紧的信号：某个合法操作被频繁拒，说明策略太严。

**失败形态：** 日志里清一色 allow、一条 deny 都没有。这通常不是「没人试探」，而是拒绝路径没有走到记录点 —— 那一刻起，隔离层就是黑箱，而团队遇到权限错误的第一个动作会是把它关掉。

## 常见坑

- **以为提示词能代替隔离。** 第 4、9、10 章都实测过模型会犯错，而错法不可预测。
- **只做权限不做隔离。** 「读文档」是合法动作，但它的实现可能够得着整个文件系统。
- **做了隔离但不验证。** 第 3 节会实测：一个「看着对」的前缀检查有 4/6 的攻击手法能绕过。
- **隔离层不记日志。** 它会变成黑箱，而团队遇到权限错误时的第一反应是把它关掉。
- **默认全开、需要时再收。** 应该反过来：默认最小，需要时显式开口子 —— 而且开口子的动作要留下记录。
