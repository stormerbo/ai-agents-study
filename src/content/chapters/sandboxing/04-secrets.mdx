隔离管的是「够得着什么」。这一节管的是另一件东西：**模型能看到什么。**

具体说，是凭据 —— API key、数据库密码、token。它们不该出现在模型看得到的任何地方。

## 三条泄露路径

这不是假设。凭据进上下文有三条很自然的路，每一条都是工程里常见的写法。

**路径一：当作工具参数。** 一个「调用外部 API」的工具，如果它的 schema（描述工具参数名、类型与必填项的 JSON Schema，第 4 章）里有一个 api_key 字段，模型就会在调用时把它填上。于是它出现在工具调用块里、被写进**轨迹**（trace：这一步从请求到结果的逐步记录，排查与成本归因都靠它，第 15 节）、被发给模型厂商。

**路径二：混进报错信息。** 这个更隐蔽。一个 API 调用失败，错误信息里带着 key（很多客户端会把它拼进 URL 或错误文本）。第 4 章的结论是「错误要说明原因，否则模型不知道该怎么改」—— 于是这段含 key 的错误被**原样回填**给模型。

**路径三：整份配置序列化。** 「把上下文给模型看看」这种写法，如果直接把配置对象序列化进去，key 就在里面。

我跑了一遍这三条：

```text
路径一：当作工具参数          轨迹里含明文凭据：是
路径二：混进报错信息          轨迹里含明文凭据：是
路径三：整份配置序列化        轨迹里含明文凭据：是
```

（实跑数据，2026-10-09。用一个形如 sk-live- 开头的字符串作检测目标。）

三条全部泄露。

## 一旦进了上下文，会同时发生三件事

这是关键 —— 凭据进上下文不是一个单点问题，它一次触发三个后果：

**一，它被写进了日志。** 第 15 节讲过轨迹是排查依据，所以它会被长期保存。于是你的密钥躺在日志系统里 —— 那个系统的访问控制通常比业务系统松。

**二，它被发给了模型厂商。** 每一轮都要重发上下文。所以它不只是在你的机器上，还在第三方那里。

**三，它会被回填进后续轮次。** 工具结果一旦进入消息历史，后面每一步都带着它。**泄露的半径随步数增长。**

第三条最容易被忽略，也最难收拾 —— 因为 agent 的循环特性决定了「同一份内容被重发很多次」（第 11 章实测过每步重发的成本）。

## 正确做法：名字进上下文，值在边界解析

核心只有一条：**让模型看到「要用哪个凭据」，而不是「凭据是什么」。**

```text
❌ 工具 schema：{"name": "call_api", "properties": {"api_key": {...}, "q": {...}}}
   → 模型必须知道密钥才能调用

✅ 工具 schema：{"name": "call_api", "properties": {"q": {...}}}
   → 密钥在工具实现里取（从环境变量或密钥服务）
   → 模型只知道「有这个工具」，不知道它用什么凭据
```

如果确实有多种凭据（比如多租户），做法是**传标识而不是传值**：

```text
{"name": "call_api", "properties": {"tenant": {"enum": ["A", "B"]}, "q": {...}}}
→ 工具内部根据 tenant 去取对应的凭据
```

这样即使模型被完全操纵，它最多能做的就是「用 A 的身份查询」—— 而那属于鉴权问题（能不能查 A），不是凭据泄露问题。**两个问题的边界因此变清楚了。**

## 脱敏是兜底，不是主防线

第二层防护：所有出站到日志/轨迹的内容过一遍脱敏。

```python
def redact(text):
    return re.sub(r"sk-[A-Za-z0-9\-]{8,}", "sk-***（已脱敏）", text)
```

我验证了它能工作：

```text
原始: {"api_key": "sk-live-9f3a7b2c1d4e5f60718293a4b5c6d7e8"}
脱敏: {"api_key": "sk-***（已脱敏）"}
有效: 是
```

但**它只能是兜底**，理由有三个：

- **模式匹配总有漏网的。** 上面的正则只认 sk- 开头的字符串。换一个厂商、换一种密钥格式，它就失效了。
- **它保护不了「已经发出去的那一份」。** 脱敏发生在写日志时，但密钥在更早的步骤就已经发给了模型厂商。
- **它制造一种虚假的安全感。** 「我们做了脱敏」可能让人不再去看真正的源头。

**主防线是「凭据根本不进上下文」，脱敏只是万一漏了之后的止损。** 这个主次关系不能反。

## 还有三件配套的事

**一，密钥要能轮换。** 如果轮换需要改代码、重新部署、通知所有调用方，那它实际上不会被轮换。设计时要让密钥的来源是一个可替换的引用（环境变量、**密钥服务** —— 集中保管密钥、按身份下发短期凭据的服务，云上的 Secrets Manager / Vault 一类），而不是硬编码。

**二，每个用途一把密钥。** 一把密钥打通所有服务，等于它的泄露半径是全部服务。按工具、按环境分开 —— 这和第 3 节讲的「最小权限」是同一个思路，只是对象从「路径」变成了「凭据」。

**三，给密钥设额度。** 泄露了但额度很小，损失是有限的。这是唯一一个「即使前面都做错了也还能兜住」的措施。

## 一个检查清单

过一遍你现在的系统：

| 检查 | 不合格意味着 |
|---|---|
| 有没有任何工具的 schema 含凭据字段？ | 模型必须知道密钥才能调用 |
| 工具的错误信息会不会带出密钥？ | 会被原样回填给模型 |
| 有没有地方把配置对象整体序列化进上下文？ | 密钥在里面 |
| 日志/轨迹有没有脱敏？ | 密钥长期躺在日志系统里 |
| 每个用途是不是独立的密钥？ | 泄露半径是全部服务 |

## 一个反直觉的推论：凭据不该给模型，但也不该给工具

上面讲的都是「凭据不进上下文」。但有一个更进一步的推论值得说清楚。

既然凭据不该让模型看到，那它应该留在哪？自然的答案是「工具实现里」。但**工具实现本身也可能是危险的** —— 第 3 节刚讲过，一个参数完全由攻击者控制的工具可以读到沙箱外的东西。

所以更准确的说法是：**凭据的可见范围应该和它的使用范围一样小。**

具体说：

- 模型看得到：**工具名和参数**（不含凭据）
- 工具看得到：**它自己那一把凭据**，不是所有凭据
- 只有计量和审计系统看得到：**用了几次、什么时候用的**

这三层的划分带来的好处很实际：**当一把凭据泄露时，你能确定泄露源在哪一层。** 如果所有凭据都放在同一个配置对象里，一次泄露你无法知道是从哪个工具出去的。

## 另一个推论：日志本身是敏感数据

最后一条，容易被忽略：**你在脱敏的那份日志，本身就是敏感数据。**

它包含用户输入、工具返回值、有时还有业务数据。所以：

- 日志系统的访问控制要**和业务系统一样严**，而不是「内部系统所以松一点」
- 日志要有保留期限（第 15 节讲过追踪数据可以滚动删除）
- 导出日志（比如发给外部排查）要单独走一次脱敏，不能直接用原文件

一个具体的反例：把轨迹日志接到一个所有人可见的分析平台上「方便调试」。那等于把第 4 节讲的调试便利，换成了第 17 节讲的数据外泄面。
## 完整可运行代码

下面这段代码复现上面那三条泄露路径，并对每一条给出脱敏后的样子。

```python
"""凭据是怎么泄露到上下文里的 —— 三条最常见的路径。

纯本地演示，实跑状态：2026-10-09。
"""
import json, re

SECRET = "sk-live-9f3a7b2c1d4e5f60718293a4b5c6d7e8"


def path1_tool_argument():
    """路径一：把凭据当工具参数传给模型。"""
    trace = []
    # 模型输出：{"tool":"call_api","args":{"api_key":"<SECRET>","q":"查订单"}}
    tool_call = {"tool": "call_api", "args": {"api_key": SECRET, "q": "查订单"}}
    trace.append({"step": 1, "kind": "tool_call", "args": tool_call["args"]})
    return trace


def path2_error_message():
    """路径二：报错信息里带出了凭据。"""
    def call_api(key):
        raise RuntimeError("401 Unauthorized: key=%s is invalid" % key)
    trace = []
    try:
        call_api(SECRET)
    except RuntimeError as e:
        # 这个错误会被原样回填给模型（第 4 章的结论：错误要说明原因）
        trace.append({"step": 1, "kind": "tool_result", "content": str(e)})
    return trace


def path3_config_dump():
    """路径三：把整个配置对象序列化进上下文。"""
    config = {"endpoint": "https://api.example.com", "api_key": SECRET, "timeout": 30}
    # 常见的「把上下文给模型看看」写法
    return [{"step": 1, "kind": "context", "content": json.dumps(config, ensure_ascii=False)}]


def redact(text):
    return re.sub(r"sk-[A-Za-z0-9\-]{8,}", "sk-***（已脱敏）", text)


if __name__ == "__main__":
    for label, fn in [("路径一：当作工具参数", path1_tool_argument),
                      ("路径二：混进报错信息", path2_error_message),
                      ("路径三：整份配置序列化", path3_config_dump)]:
        trace = fn()
        raw = json.dumps(trace, ensure_ascii=False)
        leaked = SECRET[:12] in raw
        print("  %-22s 轨迹里含明文凭据：%s" % (label, "❌ 是" if leaked else "✅ 否"))
        if leaked:
            print("      %s" % raw[:100])
        print("      脱敏后：%s" % redact(raw)[:100])
        print()

    print("=== 关键点 ===")
    print("  三条路径的共同点是：**凭据进入了一个会被记录、会被重发的通道。**")
    print("  一旦它进了轨迹，就意味着三件事同时发生：")
    print("    1. 它被写进了日志（第 15 节讲轨迹是排查依据，所以日志会被长期保存）")
    print("    2. 它被发给了模型厂商（每一轮都要重发上下文）")
    print("    3. 它可能被回填进后续轮次，进一步扩散")
    print()
    print("  两条防线：")
    print("    · 凭据只以**名字**出现在上下文里，真实值在边界处解析（工具内部）")
    print("    · 所有出站到轨迹/日志的内容过一遍脱敏 —— 这是兜底，不是主防线")
```


## 一个反直觉的推论：凭据的可见范围要和它的使用范围一样小

既然凭据不该让模型看到，那它该留在哪？自然的答案是「工具实现里」。但工具实现本身也可能危险 —— 第 3 节刚讲过，参数完全由攻击者控制的工具能读到沙箱外的东西。

所以更准确的说法是：**凭据的可见范围应该和它的使用范围一样小。** 模型看得到工具名和参数（不含凭据）；工具看得到自己那一把凭据，不是所有凭据；只有计量与审计系统看得到「用了几次、什么时候用的」。

这三层划分的实际收益是：**当一把凭据泄露时，你能确定泄露源在哪一层。** 如果所有凭据都在同一个配置对象里，一次泄露你无法判断是从哪个工具出去的。
## 主防线的实现：schema 无凭据字段，值在边界解析

前面两段 schema 片段停在「应该长这样」。补一个能跑的完整工具实现：**schema 里没有凭据字段，值只在工具内部取，错误归一化后再回填**。

运行前准备（三个环境变量是本节例子里用的，按需替换）：

- `TENANT_A_TOKEN` / `TENANT_B_TOKEN`：两个租户各自的凭据。**怎么拿到**：本地演示 `export TENANT_A_TOKEN=sk-demo-a`；真实环境由密钥服务在进程启动时注入环境变量，代码只认变量名。
- 只用标准库（`os` / `json` / `re`），无需安装任何包。

```python
"""凭据不进上下文：工具 schema 无凭据字段，值在边界解析，错误归一化。

需要两个环境变量（本地演示用假值）：
  export TENANT_A_TOKEN=sk-demo-a
  export TENANT_B_TOKEN=sk-demo-b
真实环境里它们的值由密钥服务注入。
"""
import json
import os
import re

LOG = []          # 只给运维看的通道（含细节）
SECRET_RE = re.compile(r"sk-[A-Za-z0-9\-]{8,}")

def redact(text):
    return SECRET_RE.sub("sk-***（已脱敏）", text)

def tool_schema():
    return {
        "name": "call_api",
        "description": "调用外部订单查询接口。",
        "input_schema": {
            "type": "object",
            "properties": {"tenant": {"type": "string", "enum": ["A", "B"]}, "q": {"type": "string"}},
            "required": ["tenant", "q"],
        },
    }

CRED_REF = {"A": "TENANT_A_TOKEN", "B": "TENANT_B_TOKEN"}   # 名字 -> 环境变量名（可替换的引用）

def call_api(tenant, q):
    env_name = CRED_REF.get(tenant)
    token = os.environ.get(env_name) if env_name else None
    if not token:
        return {"error_code": "unknown_tenant", "hint": "tenant 只能是 A 或 B"}
    try:
        # 模拟上游把 key 拼进了报错文本
        raise RuntimeError("401 Unauthorized: key=%s rejected" % token)
    except RuntimeError as e:
        LOG.append({"level": "error", "tenant": tenant, "detail": str(e)})   # 细节只进日志
        return {"error_code": "upstream_auth_failed", "hint": "请确认 tenant 是否正确，稍后可重试"}

if __name__ == "__main__":
    schema_text = json.dumps(tool_schema(), ensure_ascii=False)
    print("1) 序列化后的工具定义：")
    print("   " + schema_text)
    print()
    secrets = [os.environ.get(v, "") for v in CRED_REF.values() if os.environ.get(v)]
    leaked = any(s and s in schema_text for s in secrets)
    print("2) 断言：工具定义里不含任何凭据值 -> %s" % ("❌ 含" if leaked else "✅ 不含"))
    print()
    print("3) 模型能拿到的返回（错误已归一化）：")
    print("   " + json.dumps(call_api("A", "查订单"), ensure_ascii=False))
    print("   " + json.dumps(call_api("C", "查订单"), ensure_ascii=False))
    print()
    print("4) 日志通道里的同一次失败（含细节，出站前脱敏）：")
    for e in LOG:
        print("   " + redact(json.dumps(e, ensure_ascii=False)))
```

实跑输出（2026-10-12，两个 token 用假值注入）：

```text
1) 序列化后的工具定义：
   {"name": "call_api", "description": "调用外部订单查询接口。", "input_schema": {"type": "object", "properties": {"tenant": {"type": "string", "enum": ["A", "B"]}, "q": {"type": "string"}}, "required": ["tenant", "q"]}}

2) 断言：工具定义里不含任何凭据值 -> ✅ 不含

3) 模型能拿到的返回（错误已归一化）：
   {"error_code": "upstream_auth_failed", "hint": "请确认 tenant 是否正确，稍后可重试"}
   {"error_code": "unknown_tenant", "hint": "tenant 只能是 A 或 B"}

4) 日志通道里的同一次失败（含细节，出站前脱敏）：
   {"level": "error", "tenant": "A", "detail": "401 Unauthorized: key=sk-***（已脱敏） rejected"}
```

三个点值得单独看：

**一、第 2 行那个断言就是本节的验收判据，不是可选项。** 它是「名字进上下文、值在边界解析」这句话唯一能被程序验证的形式 —— 光读代码看不出某个深层字段有没有把 token 带出来，序列化一遍再断言就看得出。把它放进 CI，回归时自动拦住。

**二、错误归一化是两个通道，不是一个。** 给模型的是 `error_code + hint`（可操作、不含内部结构）；给日志的是 `detail`（含细节、出站前脱敏）。第 3 节讲过错信息也是输出面，这里给出它的实现 —— **模型能改，外部看不到内部结构**。

**三、失败形态：** 如果 `os.environ.get` 返回 `None` 而代码照样发请求，就会拿着 `"None"` 当 token 发出去，报错里还会把它带回来。所以取不到凭据要**在调用上游之前**返回结构化错误，而不是继续。

## 可轮换的引用长什么样

L94 说「来源是一个可替换的引用」，具体形态就是上面那个 `CRED_REF`：**名字 -> 环境变量名**的映射，而不是**名字 -> 密钥值**。字段就这两列：

```json
{
  "tenant": "A",
  "credential_ref": "TENANT_A_TOKEN",
  "scope": ["orders:read"],
  "rotated_at": "2026-10-01"
}
```

- `credential_ref` 是**引用**（解析得到值的地方），换成密钥服务时这里写服务里的 key 名，代码不用动。
- `scope` 让「最小权限」可审计：一个租户的凭据只开它需要的 scope。
- `rotated_at` 让轮换可监控：超过约定周期的引用应当告警，否则「定期轮换」只是口号。

**失败形态：** 把值写进配置文件或数据库字段 —— 轮换就要改数据、重启、通知调用方，于是实际不会轮换。判据很简单：**轮换一次需不需要改代码或改数据？需要，就说明引用设计错了。**

## 常见坑

- **把凭据做成工具参数。** 模型会填它，于是它进工具调用块、进轨迹、发给厂商。
- **让错误信息带出密钥。** 第 4 章要求错误说明原因，于是含密钥的文本被原样回填。
- **把配置对象整体序列化进上下文。** 密钥就在里面。
- **以为脱敏就够了。** 它保护不了已经发出去的那一份，也总有漏网的模式 —— 它是兜底，不是主防线。
- **一把密钥打通所有服务。** 泄露半径等于全部服务。按工具、按环境分开。
- **密钥轮换需要改代码。** 那它实际上不会被轮换。来源要是一个可替换的引用。
