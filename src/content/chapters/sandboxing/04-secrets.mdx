隔离管的是「够得着什么」（可参见[隔离层级](/chapters/sandboxing/isolation-levels)）。这一节管的是另一件东西：**模型能看到什么。**

具体说，是凭据 —— API key、数据库密码、token。它们不该出现在模型看得到的任何地方。

## 三条泄露路径

以下是三种可能把凭据放入模型可见数据的代码形状。是否发生取决于具体实现；下面的本地 fixture 只检查构造出的对象，不测生产系统。

**路径一：把凭据值放进模型请求的工具参数或示例。** 仅声明字段名 `api_key` 不会自动把值发送给模型；真实凭据必须由消息构造、默认参数、示例或先前上下文等路径带入。若请求 payload 确实含有凭据值，API 提供方就会收到它；轨迹是否另行记录工具调用参数，取决于应用与 tracing 配置。

**路径二：把凭据拼进异常或工具结果。** 如果宿主把包含密钥的异常原文回填给模型，凭据就会进入后续模型请求。错误应映射为安全的错误码和必要上下文，而不是透传原始异常。

**路径三：序列化整份配置。** 若配置对象含凭据且被直接序列化到消息或工具结果中，凭据就进入模型可见数据。应构造经过字段白名单筛选的 DTO，而不是传递任意配置对象。

我跑了一遍这三条：

```text
路径一：当作工具参数          待发送对象含测试字符串：是
路径二：混进报错信息          待发送对象含测试字符串：是
路径三：整份配置序列化        待发送对象含测试字符串：是
```

（本地合成演示，2026-10-09：脚本只在内存对象中构造测试字符串并检查序列化结果；没有调用模型 provider，也没有观察真实 trace 或生产日志。）

在这个合成 fixture 中，三种错误实现都会把测试字符串放入准备发送给模型的对象。它证明的是这些代码形状会携带该字符串，不证明生产系统都记录或保留了密钥。

## 凭据进入模型请求后的影响面

如果某次模型请求包含凭据，凭据就已暴露给该 API 的处理路径；后续影响取决于应用日志、代理日志、请求是否重发、服务端会话与提供方的数据保留设置。

**一，日志可能留下副本。** 如果应用、SDK、代理或追踪系统记录了包含凭据的请求/错误，它可能进入日志。不要记录原始授权头、错误详情或完整配置；按需记录事件类型、主体、凭据引用和结果。

**二，该次请求会把它发送给 API 提供方。** 是否重发取决于后续请求怎样携带上下文；保留、训练和删除规则取决于提供方、产品与账户设置，不能仅从 API 调用推断。

**三，它可能扩散到后续轮次。** 如果工具结果含凭据且被写回消息历史，后续重发这些历史的请求也会带上它。

所以要在凭据进入模型可见数据前阻断，并检查每个日志和工具返回边界；具体是否重发和计费按目标 API 的会话模式与 usage 核实。

## 正确做法：授权上下文由宿主绑定，凭据在受控边界解析

核心是两条独立规则：**模型输入不能包含凭据值；身份与租户授权由宿主从已认证会话绑定，不能由模型参数决定。** 工具可见的权限也应限于当前操作需要的范围。

```text
❌ 工具 schema：{"name": "call_api", "properties": {"api_key": {...}, "q": {...}}}
   → 不要把凭据字段放入模型可见的工具 schema

✅ 工具 schema：{"name": "call_api", "properties": {"q": {...}}}
   → 密钥在工具实现里取（从环境变量或密钥服务）
   → 模型只知道「有这个工具」，不知道它用什么凭据
```

多租户场景下，**不要让模型选择租户后再由工具据此取凭据**。请求中的 `tenant_id`/资源 ID 即使是不可猜的，也不能作为授权证明。宿主应从认证会话取得调用者身份，在每次操作时向下游策略检查其对目标租户和资源的权限；通过后再为该租户、该用途解析凭据。权限必须在下游或可信宿主端执行，不能依赖模型遵守 enum。

## 脱敏是纵深措施，不替代不记录

第二层防护：先用字段白名单设计日志，只记录排障和审计所需的元数据；在所有应用、SDK、代理和导出边界配置脱敏，避免写入原始凭据。脱敏规则只能作为纵深措施，不能证明所有格式和日志路径都已覆盖。

```python
import re

def redact(text):
    return re.sub(r"sk-[A-Za-z0-9\-]{8,}", "sk-***（已脱敏）", text)

sample = '{"api_key": "sk-test-only-a1b2c3d4e5f6"}'
print(redact(sample))
```

对下面这个符合该模式的测试字符串，规则会匹配并替换；它不覆盖其他供应商格式或所有日志路径：

```text
原始: {"api_key": "sk-live-9f3a7b2c1d4e5f60718293a4b5c6d7e8"}
脱敏: {"api_key": "sk-***（已脱敏）"}
有效: 是
```

运行前一段短示例时，stdout 为：

```text
{"api_key": "sk-***（已脱敏）"}
```

但**它只能是兜底**，理由有三个：

- **模式匹配总有漏网的。** 上面的正则只认 sk- 开头的字符串。换一个厂商、换一种密钥格式，它就失效了。
- **它保护不了「已经发出去的那一份」。** 脱敏发生在写日志时，但密钥在更早的步骤就已经发给了模型厂商。
- **它制造一种虚假的安全感。** 「我们做了脱敏」可能让人不再去看真正的源头。

**主防线是「凭据根本不进模型可见输入与返回值」，并避免记录凭据；脱敏负责降低意外写入的影响。** 日志系统仍应限制访问、设置保留期并测试脱敏覆盖。

## 还有三件配套的事

**一，优先删除或替换长期凭据。** 若下游支持工作负载身份或短期凭据，按任务需要申请最短可用期限；确需长期密钥时，用密钥管理服务集中存储、限制读取身份，并按凭据类型、风险和服务能力安排自动轮换。发现暴露时立即撤销/轮换；不要把固定周期套用于所有凭据类型。

**二，按用途和环境缩小权限与爆炸半径。** 使用独立服务身份和最小 scope；多租户权限还要绑定已认证主体，并在每次请求执行对象级授权。单独的服务密钥有助于区分服务身份，但不能单独证明最终用户身份。

**三，设置可用的速率、预算和异常告警。** 如果 provider 提供硬限额，可将其作为损失控制；预算告警、速率限制和额度不等同于数据授权，也不保证账单损失有绝对上限。与撤销能力、最小权限和审计配合使用。

这些生命周期与最小权限建议可对照 [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) 和 [AWS Well-Architected SEC02-BP03](https://docs.aws.amazon.com/wellarchitected/latest/security-pillar/sec_identities_secrets.html)。日志敏感字段处理见 [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)；在多租户下游执行对象级授权的原则见 [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

## 一个检查清单

过一遍你现在的系统：

| 检查 | 不合格意味着 |
|---|---|
| 工具 schema 是否包含凭据值、租户身份或授权声明？ | 模型可影响凭据暴露或授权选择 |
| 工具错误是否可能含密钥或敏感响应？ | 返回值可能泄露；先做结构化错误映射与字段审查 |
| 有没有地方把配置对象整体序列化进上下文？ | 密钥在里面 |
| 日志是否采用字段白名单，并在写入/导出边界测试敏感字段？ | 敏感值可能进入日志或外部分析系统 |
| 凭据权限是否限定到用途、环境和租户？ | 降低跨服务/跨租户影响范围 |
| 是否优先使用短期身份；静态凭据轮换是否自动且可回滚？ | 降低长期凭据暴露时间与人工操作风险 |
| 是否配置限额、速率限制、告警与撤销流程？ | 这些是损失控制，不替代授权 |


## 凭据不该进入模型，也不该暴露给整个执行环境

上面讲的都是「凭据不进上下文」。但还要明确执行环境的信任边界。

模型不应看到凭据；同时也不应把密钥注入可能执行模型生成代码或不可信插件的通用进程。凭据应由一个窄范围的可信组件按请求使用，优先通过工作负载身份或短期凭据访问下游。若只能使用静态密钥，应限定运行身份、权限和用途，并避免让执行沙箱或子进程继承它。

审计记录只保留可信宿主绑定的 actor、tenant、credential reference、操作范围和结果等元数据，不写凭据值。专用服务身份有助于归因到服务；要归因到最终用户，还需由宿主单独传递并记录已认证主体。

## 另一个推论：日志本身是敏感数据

最后一条，容易被忽略：**你在脱敏的那份日志，本身就是敏感数据。**

它包含用户输入、工具返回值、有时还有业务数据。所以：

- 按日志中数据的敏感度、用途和风险实施访问控制与审计；不要因为系统在内网就默认放宽
- 日志要有符合用途、敏感度、法规与组织政策的保留期限（参见[轨迹数据治理](/chapters/evaluation/traces)）
- 导出日志（比如发给外部排查）要单独走一次脱敏，不能直接用原文件

一个具体的反例：把轨迹日志接到一个所有人可见的分析平台上「方便调试」，会扩大敏感数据的访问面；应同时评估[轨迹数据治理](/chapters/evaluation/traces)和[数据外泄威胁路径](/chapters/agent-security/exfiltration)。
## 完整可运行代码

下面的纯本地代码构造三种待发送对象并检查测试字符串是否出现，再演示一个有限的正则脱敏规则。它没有调用模型 API，也没有验证生产日志、provider 保留策略或真实密钥格式。

```python
"""凭据是怎么泄露到上下文里的 —— 三条最常见的路径。

纯本地演示，实跑状态：2026-10-09。
"""
import json, re

SECRET = "sk-test-only-a1b2c3d4e5f6"


def path1_tool_argument():
    """路径一：把凭据当工具参数传给模型。"""
    trace = []
    # 模型输出：{"tool":"call_api","args":{"api_key":"<SECRET>","q":"查订单"}}
    tool_call = {"tool": "call_api", "args": {"api_key": SECRET, "q": "查订单"}}
    trace.append({"step": 1, "kind": "tool_call", "args": tool_call["args"]})
    return trace


def path2_error_message():
    """路径二：报错信息里带出了凭据。"""
    def call_api(key):
        raise RuntimeError("401 Unauthorized: key=%s is invalid" % key)
    trace = []
    try:
        call_api(SECRET)
    except RuntimeError as e:
        # 错误文本被示例适配器原样回填；生产代码应映射为安全错误码。
        trace.append({"step": 1, "kind": "tool_result", "content": str(e)})
    return trace


def path3_config_dump():
    """路径三：把整个配置对象序列化进上下文。"""
    config = {"endpoint": "https://api.example.com", "api_key": SECRET, "timeout": 30}
    # 常见的「把上下文给模型看看」写法
    return [{"step": 1, "kind": "context", "content": json.dumps(config, ensure_ascii=False)}]


def redact(text):
    return re.sub(r"sk-[A-Za-z0-9\-]{8,}", "sk-***（已脱敏）", text)


if __name__ == "__main__":
    for label, fn in [("路径一：当作工具参数", path1_tool_argument),
                      ("路径二：混进报错信息", path2_error_message),
                      ("路径三：整份配置序列化", path3_config_dump)]:
        trace = fn()
        raw = json.dumps(trace, ensure_ascii=False)
        leaked = SECRET in raw
        redacted = redact(raw)
        print("  %-22s 待发送对象含测试字符串：%s" % (label, "是" if leaked else "否"))
        print("      仅测试值脱敏后仍含测试字符串：%s" % ("是" if SECRET in redacted else "否"))
        print()

    print("=== 关键点 ===")
    print("  本地 fixture 只证明：这些错误实现会把测试字符串放入待发送对象。")
    print("  它不证明生产系统一定记录、保留或在每轮重发这些内容。")
    print("  是否写日志、重发历史或保留请求，取决于应用、SDK、代理和 provider 配置。")
    print()
    print("  防线：凭据不进入模型可见数据；日志使用字段白名单并测试各记录边界。")
```

## 凭据边界不是模型与工具的二分

既然凭据不该让模型看到，那它该留在哪？自然的答案是「工具实现里」。但工具实现本身也可能危险 —— 第 3 节刚讲过，参数完全由攻击者控制的工具能读到沙箱外的东西。

所以更准确的说法是：**凭据只对完成当前已授权操作所需的可信组件开放。** 模型参数不携带租户授权；凭据 broker 或下游策略按宿主绑定的身份决定是否允许并解析对应凭据。

这种分层能缩小授权范围并改善审计归因，但不能保证确定泄露根因；仍需对所有凭据读取、下游调用和日志出口做审计。
## 主防线的实现：宿主授权、窄范围凭据解析

策略判定应由可信宿主执行（见[执行策略与审计](/chapters/sandboxing/execution-policy)），凭据 broker 只向通过授权的调用开放所需凭据。

下面的完整 Python 示例只验证边界逻辑，不访问外部 API。AuthContext 必须由宿主从已认证会话构造，绝不能从模型参数反序列化；模型只能提交查询文本。生产实现应在每次调用前对主体、租户、资源和 scope 做服务端授权，并通过 workload identity 或密钥服务获取短期凭据。

```python
"""合成演示：授权在宿主绑定，模型不能选择租户或读取凭据。"""
from dataclasses import dataclass
import json

TOOL_SCHEMA = {
    "name": "query_orders",
    "input_schema": {
        "type": "object",
        "properties": {"q": {"type": "string", "minLength": 1}},
        "required": ["q"],
        "additionalProperties": False,
    },
}

@dataclass(frozen=True)
class AuthContext:
    actor_id: str       # 可信宿主从登录会话绑定
    tenant_id: str      # 可信宿主授权后的租户，不来自模型参数
    scopes: frozenset[str]

class FakeCredentialBroker:
    """仅用于本地测试；生产环境应接 workload identity / secrets manager。"""
    def __init__(self, tokens):
        self._test_tokens = tokens
        self.requests = []

    def resolve(self, tenant_id, scope):
        self.requests.append((tenant_id, scope))
        if scope != "orders:read" or tenant_id not in self._test_tokens:
            raise PermissionError("credential not available")
        return self._test_tokens[tenant_id]

class FakeUpstream:
    def __init__(self, expected_token, fail=False):
        self.expected_token = expected_token
        self.fail = fail
        self.received_expected_token = False

    def query_orders(self, query, token):
        self.received_expected_token = token == self.expected_token
        if self.fail:
            # 模拟上游异常可能含有认证材料；调用方不应记录原始异常。
            raise RuntimeError("upstream rejected token=" + token)
        return {"items": []}

SAFE_LOG = []

def execute_tool(raw_args, auth, broker, upstream):
    try:
        args = json.loads(raw_args)
    except (TypeError, json.JSONDecodeError):
        return {"error_code": "invalid_arguments"}
    if not isinstance(args, dict) or set(args) != {"q"}:
        return {"error_code": "invalid_arguments"}
    if not isinstance(args["q"], str) or not args["q"].strip():
        return {"error_code": "invalid_arguments"}
    if "orders:read" not in auth.scopes:
        return {"error_code": "permission_denied"}

    try:
        token = broker.resolve(auth.tenant_id, "orders:read")
        result = upstream.query_orders(args["q"], token)
    except Exception:
        # 只记允许列表字段；不要记录 exception、请求头或完整请求对象。
        SAFE_LOG.append({
            "event": "upstream_failure",
            "actor_id": auth.actor_id,
            "tenant_id": auth.tenant_id,
            "error_code": "upstream_unavailable",
        })
        return {"error_code": "upstream_unavailable"}
    return {"status": "ok", "orders": result["items"]}


def require(condition, message):
    if not condition:
        raise AssertionError(message)

TEST_TOKEN = "test-only-secret-a"
broker = FakeCredentialBroker({"tenant-a": TEST_TOKEN})
auth_a = AuthContext("user-17", "tenant-a", frozenset({"orders:read"}))
upstream = FakeUpstream(TEST_TOKEN)

schema_text = json.dumps(TOOL_SCHEMA)
require("tenant" not in schema_text and "token" not in schema_text,
        "the model schema must not select a tenant or carry a credential")
ok = execute_tool('{"q":"查订单"}', auth_a, broker, upstream)
require(ok == {"status": "ok", "orders": []} and upstream.received_expected_token,
        "an authorized request should use its host-bound credential")

# 即使模型伪造另一个租户字段，也必须在凭据解析前拒绝。
reads_before = len(broker.requests)
forged = execute_tool('{"q":"查订单","tenant_id":"tenant-b"}', auth_a, broker, upstream)
require(forged["error_code"] == "invalid_arguments" and len(broker.requests) == reads_before,
        "model-supplied tenant must not reach credential resolution")

no_scope = AuthContext("user-18", "tenant-a", frozenset())
denied = execute_tool('{"q":"查订单"}', no_scope, broker, upstream)
require(denied["error_code"] == "permission_denied" and len(broker.requests) == reads_before,
        "authorization must fail before secret resolution")

failure_upstream = FakeUpstream(TEST_TOKEN, fail=True)
failed = execute_tool('{"q":"查订单"}', auth_a, broker, failure_upstream)
visible = json.dumps({"result": failed, "logs": SAFE_LOG}, ensure_ascii=False)
require(TEST_TOKEN not in visible and "token=" not in visible,
        "model result and structured logs must omit raw credentials and exception text")

print("PASS schema excludes tenant and credential fields")
print("PASS host-bound authorized request succeeds")
print("PASS forged tenant rejected before credential lookup")
print("PASS missing scope rejected before credential lookup")
print("PASS failure response/log omit raw credential and exception")
print("providerCalls=0; FakeBroker/FakeUpstream only")
```

## 引用和生命周期怎么设计

长期凭据需要在服务端保存一个**由宿主持有的引用**，而不是把 secret value 放进模型参数或应用配置文本。下面是一个仅供架构说明的服务端元数据示例，**不是工具 schema，也不进入模型上下文**：

```json
{
  "credential_ref": "secret://prod/orders-reader",
  "audience": "orders-api",
  "scope": ["orders:read"],
  "owner": "orders-service",
  "rotation": "automated-when-supported"
}
```

先判断能否移除凭据，或改用 workload identity / 短期 token；必须使用长期 secret 时，通过密钥管理服务按服务身份、scope 和目标 audience 解析。轮换策略应按凭据类型、风险和下游支持来定，不能用同一个固定周期覆盖所有令牌/密钥；暴露时要能及时撤销、替换并调查历史使用。稳定的 reference 可避免把密钥值写进代码或模型协议，但引用本身也应视为内部元数据并做访问控制。

租户身份由认证宿主绑定，不能让模型通过枚举值选择 secret。授权每次在可信宿主或下游系统对 actor、tenant、resource 和 action 完整校验；通过后才解析凭据。凭据 scope 是防御纵深，不是业务对象授权的替代品。

## 常见坑

- **把凭据做成模型可见的工具参数。** 模型可能生成该参数，凭据会进入相应请求；轨迹是否保存参数取决于实现。
- **透传包含密钥的错误文本。** 若宿主将原始异常回填给模型，凭据可能进入下一次模型请求；应映射为安全错误码。
- **把配置对象整体序列化进上下文。** 若对象含凭据，该字段也会进入模型可见数据；用白名单 DTO 限定字段。
- **以为脱敏就够了。** 写日志时的模式替换不能收回已发送的数据，也可能漏过未覆盖的格式；优先避免记录，再将脱敏作为纵深措施。
- **一把密钥打通所有服务。** 泄露半径等于全部服务。按工具、按环境分开。
- **轮换依赖手工改代码。** 将秘密移入受控管理边界，并按类型、风险和下游能力设计轮换；暴露时要能撤销。
- **把额度当授权控制。** 速率限制与硬限额只能降低部分损失，不能证明调用者有权访问目标数据。
