隔离不是一个开关，是一个谱系。从「什么都不做」到「虚拟机」，每一层能拦住的东西和付出的代价都不同。

这一节把谱系摆出来，并给出一条选择依据 —— **不是「哪个更安全」，而是「我能接受多大的爆炸半径」。**

## 五个层级

**L0：进程内。** 工具就是你的一个函数，和你的服务跑在同一个进程里。它有的权限就是你的服务有的权限。

**L1：语言层限制。** 在同一个进程里，但限制语言能力 —— 比如禁掉危险的函数、用受限的解释器。**这一层有已知的绕过手法**，所以它不构成安全边界（下面有演示）。它适合当「防误用」，不适合当「防攻击」。

**L2：独立进程。** 把不可信的工作放进子进程，用操作系统的资源限制（CPU 时间、内存、文件描述符）和超时来控制它。

这一层能拦住「资源耗尽」这一类风险，也把崩溃隔离开（子进程挂了不影响主进程）。但它**默认仍然能读写文件、访问网络** —— 资源限制管的是「用多少」，不是「碰什么」。

**L3：容器。** 容器就是本机上的一个受约束进程：它用**命名空间**（namespace，把进程看到的文件树、网络、进程列表切开，让它看不见宿主的那一份）和 **capabilities**（内核权限位，比如「能不能重新挂载文件系统」「能不能发原始网络包」）来收窄能力。文件系统、网络、能力可以各自单独收。只读挂载、禁网、丢弃特权 —— 这些都是容器层能做到的。

**L4：虚拟机 / 微虚拟机。** 最强的一层，内核都是独立的。代价是启动时间（从毫秒级变成秒级）和资源占用。

## 实测：同一段代码在四层下的差别

我用「执行一段代码」当例子跑了四层：

```text
层级                   结果                         耗时        说明
L0 进程内              333332833333500000         0.039     无隔离：可以读任意文件、可以用光内存
L1 禁内建黑名单         333332833333500000         0.039     黑名单不是边界：能通过对象树拿回危险函数
L2 子进程+CPU 上限      被 SIGXCPU 杀掉（返回码 -24）   1.014     资源被限制住了；但文件与网络仍放得开
L2b 子进程+墙钟超时      被墙钟超时终止                 1.005     墙钟与 CPU 限制不能互相替代
```

（实跑数据，2026-10-09。）

三个值得注意的点。

**第一，L1 那一行看起来完全正常。** 它算出了正确答案，耗时也一样 —— 也就是说**如果这是一次攻击，你看不出任何异常**。而它的问题不在输出上，在「它还能做什么」上。

**第二，CPU 限制和墙钟超时是两件事。** 上面两行都是 1 秒左右，但它们防的东西不同：CPU 限制管「算了多久」，墙钟管「等了多久」。一个 sleep 30 秒的程序不花 CPU，但会让你的请求挂住 —— 只设 CPU 限制拦不住它。**两个都要设。**

**第三，L2 拦不住文件与网络。** 资源限制的字面意思就是「资源」。它不检查你打开了哪个文件、连了哪个地址。要拦那些，需要 L3。

## 怎么选

选择依据是**爆炸半径**，不是安全等级。具体问三个问题：

**一、这段代码是「我们的」还是「不可信的」？**

自己写的工具 → L0 或 L1 就够（隔离的意义在于防误用，不是防攻击）。
模型生成的代码、第三方的脚本 → 至少 L3。
来自不受信任来源的可执行内容 → L4。

**二、它需要碰什么？**

只需要计算 → L2 就够（限资源）。
需要读文件 → L3（只读挂载一个目录）。
需要访问网络 → L3（而且默认应该是禁网，需要时白名单）。

**三、出事的代价有多大？**

读错了数据 → 低，L2 够。
能改数据或对外发请求 → 高，L3 起步。
能接触到生产系统 → 最高，L4 或者干脆不要让它跑。

三个问题的答案合起来决定层级。**注意三个都是「这段代码」的问题，不是「这个模型」的问题** —— 同一个模型调不同的工具，需要的隔离层级完全不同。

## 一个常见的误解：容器不是万能

容器隔离的是**内核之外**的东西（文件系统、网络、进程视图、能力）。它共享宿主的内核 —— 所以内核漏洞、以及配置错误（比如把宿主目录挂进去、给了特权模式）仍然是逃逸路径。

这不是说容器不够用，而是说：**用了容器不等于隔离做对了。** 第 3 节会看到，一个「做了隔离」的检查也可能有 4/6 的攻击手法能绕过 —— 同样的事会发生在容器配置上。

所以每一层都要**验证**，不能只在设计文档里写「我们用了容器」。


## 隔离和「能力」的关系

最后补一个概念上的澄清，它能解释为什么「隔离」这个词经常被误解。

安全领域里有一个成熟的说法：**不要把「能力」和「隔离」混为一谈。**

- **隔离**是「你被关在哪里」（沙箱、命名空间、虚拟机）
- **能力**是「你手里有什么钥匙」（token、文件描述符、句柄）

两者的关系是：**隔离划出边界，能力在边界内授权。** 一个进程在沙箱里，但它手里的文件描述符可能是沙箱外的 —— 这时隔离形同虚设。

这解释了三个常见现象：

**现象一：明明在容器里，还是读到了宿主文件。** 因为挂载了宿主目录 —— 那是「能力」层面的问题，不是隔离不够强。

**现象二：沙箱里的代码通过一个已打开的 socket 发出去了数据。** socket 是能力，沙箱没拦住它。

**现象三：给了最小权限，但工具内部又去读了配置里的其他路径。** 权限在入口处收窄了，工具实现里又放开了。

所以检查隔离是否有效，不能只看「用了什么隔离技术」，要看**这个进程手里实际握着什么**：打开了哪些文件、连了哪些 socket、有哪些环境变量。**这才是它能做的最坏的事的上界。**

## 一个常被忽略的维度：生命周期

前面讲的都是「隔离得多严」。还有一个同样重要、但经常被跳过的维度：**这个沙箱活多久。**

三种做法，代价和安全差别很大：

**每任务重建。** 每次任务开一个全新的沙箱，结束就销毁。最安全（状态不会跨任务泄漏），代价是启动开销。

**复用但清理。** 沙箱长期存在，任务之间清理临时文件。省了启动开销，但「清理干净」很难验证 —— 残留的文件、环境变量、缓存都可能泄露上一个任务的信息。

**全局共享。** 所有任务共用一个沙箱。最省，但它意味着任务之间可以互相影响 —— 一个任务写的文件，另一个任务能读到。

选择依据和前面一样是爆炸半径：**如果任务之间不该互相看见，那就必须每任务重建。** 而这一条经常被忽略，因为「复用」在压测时看起来完全正常 —— 信息泄露只在真实的多租户场景里才会出现。

一个折中：**沙箱实例复用，但文件系统每任务重建**（挂一个新建的临时目录）。这样启动开销摊掉了，而状态仍然是隔离的。
## 完整可运行代码

下面这段代码把四个层级并排跑一遍，演示它们在「能力」与「代价」上的实际差别。

```python
"""隔离的层级：同一段代码在四层隔离下的能力与代价。

纯本地，实跑状态：2026-10-09。
"""
import resource, subprocess, sys, time


def l0_inline():
    """L0：进程内直接算 —— 没有任何隔离。"""
    t = time.time()
    out = str(sum(i * i for i in range(1000000)))
    return out, time.time() - t, "无隔离：可以 import os、可以读任意文件、可以用光内存"


def l1_blacklist():
    """L1：语言层黑名单 —— 禁掉危险内建。"""
    banned = {"__import__", "open", "eval", "exec", "compile", "input", "breakpoint"}
    safe = {k: v for k, v in vars(__builtins__).items() if k not in banned} \
        if not isinstance(__builtins__, dict) else \
        {k: v for k, v in __builtins__.items() if k not in banned}
    t = time.time()
    try:
        out = str(eval("sum(i*i for i in range(1000000))", {"__builtins__": safe}))
        note = "但黑名单不是边界：().__class__.__mro__[1].__subclasses__() 能拿回对象树"
    except Exception as e:
        out, note = "失败", type(e).__name__
    return out, time.time() - t, note


def l2_cpu_limit():
    """L2：独立进程 + CPU 时间上限。跑一个死循环，看内核是否拦住。"""
    def limit():
        resource.setrlimit(resource.RLIMIT_CPU, (1, 1))     # 1 秒 CPU 后就 SIGXCPU
    t = time.time()
    p = subprocess.run([sys.executable, "-c", "while True: pass"],
                       capture_output=True, text=True, timeout=15, preexec_fn=limit)
    dt = time.time() - t
    sig = "被 SIGXCPU 杀掉（返回码 %d）" % p.returncode if p.returncode < 0 else "返回码 %d" % p.returncode
    return sig, dt, "资源被内核限制住了；但文件与网络**仍然完全放得开**"


def l2_wall_timeout():
    """L2b：墙钟超时 —— 另一条不同的限制。"""
    t = time.time()
    try:
        subprocess.run([sys.executable, "-c", "import time; time.sleep(30)"],
                       capture_output=True, text=True, timeout=1)
        out = "居然没超时"
    except subprocess.TimeoutExpired:
        out = "被墙钟超时终止"
    return out, time.time() - t, "墙钟管「等了多久」，CPU 限制管「算了多久」—— 两者不能互相替代"


if __name__ == "__main__":
    print("同一段代码，四种处理方式：")
    print()
    print("  %-20s %-26s %-9s %s" % ("层级", "结果", "耗时", "说明"))
    for name, fn in [("L0 进程内", l0_inline), ("L1 禁内建黑名单", l1_blacklist),
                     ("L2 子进程+CPU 上限", l2_cpu_limit), ("L2b 子进程+墙钟超时", l2_wall_timeout)]:
        out, dt, note = fn()
        print("  %-20s %-26s %-9.3f %s" % (name, str(out)[:24], dt, note))
    print()
    print("=== 层级越高，能拦住的越多，代价也越大 ===")
    print("  L0  进程内        —— 只能靠「相信代码」")
    print("  L1  语言层黑名单  —— 有已知绕过手法，不构成安全边界")
    print("  L2  独立进程      —— 资源可限，但文件与网络仍放得开")
    print("  L3  容器          —— 文件系统、网络、能力可以各自单独收")
    print("  L4  虚拟机        —— 最强，代价是秒级的启动时间")
    print()
    print("选择依据不是「哪个更安全」，而是「我能接受多大的爆炸半径」——")
    print("读文件的任务不需要容器，执行模型写的代码则至少要到 L3。")
```


## 层级的另一个维度：时间

前面讲的是「隔离多严」，还有一个正交的维度是「隔离活多久」—— 每任务重建、复用但清理、还是全局共享。它的代价与安全差别比层级选择还大，而且经常被完全忽略。

选择依据仍然是爆炸半径：**如果任务之间不该互相看见，就必须每任务重建。** 这条在压测时看不出问题 —— 信息泄露只在真实的多任务场景里才出现。

一个折中做法是**沙箱实例复用、但文件系统每任务新建**：启动开销摊掉了，状态仍然是隔离的。
## L3 的实体：一段可复制的容器配置

L3 不是一句「用容器」，它是一组具体的开关。下面这段可以直接改路径后运行（用 Docker / containerd 一类运行时；gVisor、Firecracker 是同一档里更重的选择，接口不同、目标一致）：

```bash
docker run --rm \
  --read-only \
  --tmpfs /workspace:rw,size=64m,mode=1777 \
  --network none \
  --user 65534:65534 \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  --pids-limit 64 \
  --memory 256m --memory-swap 256m \
  --cpus 0.5 \
  --mount type=bind,src="$(pwd)/task-input",dst=/input,readonly \
  python:3.12-alpine python /app/runner.py
```

每个开关对应一个失效模式，不是装饰：

| 开关 | 没有它会怎样 |
|---|---|
| `--read-only` + `--tmpfs` | 容器内能写宿主可见的任何路径；只读根让它只能写显式挂载的 tmpfs |
| `--network none` | 默认可以出网（第 3 节的通道问题），也能访问同宿主上的其他服务 |
| `--user` | 默认 root；即使丢了 capabilities，root 仍能碰更多东西 |
| `--cap-drop ALL` | 默认保留一批 capability，其中若干足以做越权操作 |
| `--pids-limit / --memory / --cpus` | 一段跑飞的代码能拖垮整台宿主（第 2 节 L2 的老问题） |
| `src=...,readonly` | 把宿主目录读写挂进去 = 容器隔离形同虚设（本节 L89 那条结论的实体） |

**边界必须说清楚：容器共享宿主内核。** 所以内核漏洞、以及上面那些配置错误，仍是逃逸路径。这也是 L89 那句「用了容器不等于隔离做对了」的由来 —— 强度取决于配置，不取决于「用了容器」这个事实。

## 验证：把「我们用了容器」变成可复跑的结果

L93 说「每一层都要验证」。验证的做法不是读配置，而是**在沙箱里跑一个探针，逐项报告隔离是否成立**。下面这段脚本放进容器执行（本次实跑：Docker 29.3.1，镜像 `python:3.12-alpine`，实跑数据 2026-10-12）：

```python
import os

def t_write_blocked():          # 根文件系统只读
    try:
        open('/probe_write', 'w').write('x'); return False, '根目录可写'
    except OSError as e:
        return True, type(e).__name__

def t_no_eth():                 # --network none：没有路由网卡
    lines = open('/proc/net/dev').read().splitlines()[2:]
    ifaces = [l.split(':')[0].strip() for l in lines if ':' in l]
    eth = [i for i in ifaces if i.startswith('eth')]
    return (not eth), '路由网卡=%s（全部网卡：%d 个）' % (eth, len(ifaces))

def t_non_root():               # 非 root
    return (os.getuid() != 0), 'uid=%d' % os.getuid()

def t_host_mount_hidden():      # 没挂进来的宿主路径不可见
    return (not os.path.exists('/hosttmp/host-marker')), 'exists=%s' % os.path.exists('/hosttmp/host-marker')

def t_workspace_writable():     # 该能写的地方能写
    try:
        open('/workspace/ok.txt', 'w').write('x'); return True, '可写'
    except OSError as e:
        return False, type(e).__name__

for name, fn in [('只读根文件系统', t_write_blocked), ('无 eth 网卡（--network none）', t_no_eth),
                 ('非 root 用户', t_non_root), ('宿主挂载点未泄露', t_host_mount_hidden),
                 ('tmpfs 工作目录可写', t_workspace_writable)]:
    ok, detail = fn()
    print('  %-4s %-22s %s' % ('PASS' if ok else 'FAIL', name, detail))
```

在这一节的配置下跑（宿主 `/tmp` 里先放一个 `host-marker`，但不挂进容器）：

```text
=== 配置正确（--read-only --network none --user 65534 --tmpfs /workspace）===
  PASS 只读根文件系统                OSError
  PASS 无 eth 网卡（--network none） 路由网卡=[]（全部网卡：10 个）
  PASS 非 root 用户              uid=65534
  PASS 宿主挂载点未泄露               exists=False
  PASS tmpfs 工作目录可写           可写
```

把配置换成「默认 root + 默认网络 + 把宿主 `/tmp` 挂进去」，同一个脚本立刻翻车：

```text
=== 配置错误（默认 root + 默认网络 + 挂载宿主 /tmp）===
  FAIL 只读根文件系统                根目录可写
  FAIL 无 eth 网卡（--network none） 路由网卡=['eth0']（全部网卡：11 个）
  FAIL 非 root 用户              uid=0
  FAIL 宿主挂载点未泄露               exists=True
  FAIL tmpfs 工作目录可写           FileNotFoundError
```

**这就是「验证过的隔离」和「配了隔离」的区别。** 两边的架构描述可以写得一模一样，探针的输出不会撒谎。把这段探针纳入 CI 或启动自检，配置被人改坏时会立刻暴露。

> 一处如实说明：最初用「能不能连上 `1.1.1.1:443`」测网络，两次运行都返回被禁（TimeoutError）——**本机的网络策略让这个测法在这里不可靠**，它分不出「容器禁网」和「宿主本来就出不去」。换成「有没有 eth 网卡」之后才有确定信号。这也是本项目对待未复现结果的一贯做法：测不出来就说测不出来，换一个能分辨的判据。

## 生命周期：谁创建、清理什么、怎么验证清理干净

L119 提了「每任务重建 / 复用但清理 / 全局共享」三种，但没说这三件事谁做、做什么。补上：

**谁创建。** 由**调度层**（跑 agent 循环的那个服务）在任务开始时创建，不是在工具里临时创建 —— 工具作者不该负责沙箱生命周期，否则又会散成 20 处。

**清理什么。** 一份清单，按「跨任务泄露」的风险排序：

| 要清的东西 | 不清会怎样 |
|---|---|
| 可写目录里的文件与临时文件 | 上一个任务的输出被下一个任务读到 |
| 环境变量里注入的凭据 | 下一个任务拿到了不属于它的身份 |
| 已打开的 socket / 连接 | 复用进程时，上一任务的连接继续可用 |
| 进程表里的残留进程 | 后台进程活过任务边界，继续占资源 |
| 本地缓存（如 pip / npm cache） | 缓存投毒跨任务传递 |

**怎么验证清理干净。** 判断方式是**下一个任务开始前先跑一个「洁净探针」**，而不是靠 review 清理代码：探针检查「可写目录文件数 == 0」「环境变量与白名单一一对应」「上一任务写的 marker 文件不存在」。三项全过才继续；任一项失败就把这个实例标记为脏、销毁重建。这与上面的隔离探针是同一个套路：**把「我以为清干净了」变成一个可复跑的结果。**

**选哪种。** 判据还是爆炸半径：如果任务之间不该互相看见，就每任务重建；确实要摊启动开销时，用「实例复用 + 文件系统每任务新建（挂一个新建的 tmpfs）」，绝不要「全局共享 + 清理」—— 因为清理的遗漏是静默的，而进程与环境的残留最难查。

## 常见坑

- **把语言层黑名单当安全边界。** 它有已知绕过手法，只适合防误用。
- **只设 CPU 限制，不设墙钟超时。** 一个 sleep 程序不花 CPU，但会让请求挂住。
- **以为 L2 拦得住文件访问。** 资源限制只管「用多少」，不管「碰什么」。
- **以为用了容器就等于隔离做对了。** 配置错误（挂了宿主目录、给了特权）仍然是逃逸路径。
- **按安全等级选层级，而不是按爆炸半径。** 读文件的任务不需要虚拟机；执行模型写的代码则需要。
- **只算权限和隔离，忘了鉴权。** 沙箱不改变身份 —— 在沙箱里仍然能查到别人的订单。
