接着[为什么需要隔离](/chapters/sandboxing/why-isolate)这一节，本文把隔离从「什么都不做」到「虚拟机」排成一个谱系：每一层能拦住的东西和付出的代价都不同。

这一节把谱系摆出来，并给出一条选择依据 —— **不是「哪个更安全」，而是「我能接受多大的爆炸半径」。**

## 五个层级

**L0：进程内。** 工具就是你的一个函数，和你的服务跑在同一个进程里。它有的权限就是你的服务有的权限。

**L1：语言层限制。** 在同一个进程里，但限制语言能力 —— 比如禁掉危险的函数、用受限的解释器。**这一层有已知的绕过手法**，所以它不构成安全边界（下面有演示）。它适合当「防误用」，不适合当「防攻击」。

**L2：独立进程。** 把工作放进子进程，可用 `resource` 等 OS 接口限制某些资源，并为调用设置墙钟期限。Python `resource` 模块仅适用于 Unix，具体限制随操作系统而异；`RLIMIT_CPU` 是进程 CPU 时间限制，不自动限制整个进程树或容器。`subprocess` 的超时处理也不等于自动清理整个派生进程树；执行器需按平台实现并验证进程组或作业对象的终止。子进程仍继承或可访问父进程允许的文件、环境和网络能力，除非执行器另外收窄。

**L3：容器。** 容器是共享宿主内核、由 namespace、挂载、cgroup、Linux capabilities 及安全配置共同约束的一组进程。namespace 切分进程、挂载和网络等视图；Linux `CAP_*` 是内核权限集合。只读挂载、限制网络、丢弃不需要的 capability 能缩小权限，但具体保护依赖容器运行时、宿主配置和实际挂载。Docker 的这些选项只描述容器配置，是否覆盖目标威胁还要在部署环境验证。

**L4：虚拟机 / 微虚拟机。** Guest OS 运行自己的内核，通过 hypervisor/KVM 与宿主隔离；边界仍依赖 hypervisor、设备模型和宿主补丁。它通常比普通容器提供不同的内核隔离边界，但不能据此称为绝对“最安全”。gVisor 使用用户态 application kernel，不能简单等同于 VM 或 syscall filter；Firecracker 则提供基于 KVM 的 microVM。启动和资源开销依平台、镜像和配置而变，不能用固定的毫秒/秒范围概括。

## 本地演示：不同机制各自能说明什么

下面是 2026-10-09 的历史摘要，不是“同一段代码”在四种环境中的性能对照：L0/L1 计算一个求和；L2 用死循环触发 CPU 限额；L2b 用 `sleep` 触发墙钟期限。输入负载不同，0.039s、1.014s、1.005s 不能拿来比较隔离开销；旧运行日志与完整环境信息未归档，因此不能独立复核具体耗时。

```text
历史摘要（2026-10-09；仅说明机制，不用于性能比较）
L0 / L1：求和结果均登记为 333332833333500000；各记 0.039s
L2：CPU-bound 死循环登记为 SIGXCPU / return code -24；记 1.014s
L2b：sleep(30) 在 1s 墙钟期限后登记为 TimeoutExpired；记 1.005s
```

这些摘要支持的教学点有限：**CPU 限额与墙钟期限保护不同故障模式**。死循环持续消耗 CPU；休眠任务几乎不耗 CPU，却仍会占住请求等待时间。旧数字只作历史记录，不据此推断性能、隔离开销或不同机器的阈值。

L2 的资源约束也**不等于文件/网络隔离**：它限制某些资源消耗，并不会自动撤销子进程继承的文件权限、环境变量或 socket。资源耗尽、访问边界、身份权限要分别设计和测试。

## 怎么选

选择依据是**爆炸半径**，不是安全等级。具体问三个问题：

**一、这段代码是「我们的」还是「不可信的」？**

自己编写、受代码审查且不执行不可信内容的窄工具，可留在 L0；L1 只适合降低误用，不防攻击。模型生成或第三方可执行代码应放入外部强制的隔离边界，通常从配置过的 L3 起步；涉及多租户对抗或宿主内核风险时，评估 L4/microVM，并配套最小挂载、禁用不需的网络和不给长期凭据。L4 也不代表零风险。

**二、它需要碰什么？**

纯计算仍要限制时间、CPU、内存和进程数；这些由 L2/容器资源控制实施。需要读数据时，只挂载必需目录且优先只读；需要网络时按目标与方法放行；出口策略和审计边界见[执行策略与审计](/chapters/sandboxing/execution-policy)。当外部内容可能影响工具调用、且执行环境能访问敏感数据或外部目标时，还要评估[数据外传路径](/chapters/agent-security/exfiltration)。Docker `--network none` 不接入外部 Docker 网络，loopback 仍存在；应结合运行时与路由/出口策略验证，不以接口名称推断全部网络隔离。

**三、出事的代价有多大？**

只影响可重建的临时数据，使用资源受限的隔离环境并限制副作用。
能改业务数据或对外发请求，加入对象级授权、幂等与对账，并加强文件/网络边界。
接触生产或跨租户数据时，优先不运行不可信代码；必须运行则选择与威胁模型相符的 VM/microVM 边界，并独立评审宿主、凭据和网络控制。

三个问题的答案合起来决定层级。**注意三个都是「这段代码」的问题，不是「这个模型」的问题** —— 同一个模型调不同的工具，需要的隔离层级完全不同。

## 一个常见的误解：容器不是万能

容器通过共享内核提供的 namespace、挂载和资源控制，把进程看到的文件系统、网络、进程视图和资源范围收窄；它**不提供独立的宿主内核**。因此内核漏洞、危险设备/挂载和运行时配置错误仍可能扩大影响范围。容器配置是否有效，要检查实际挂载、身份、capabilities、网络和资源限制。

这不是说容器不够用，而是说：**用了容器不等于隔离做对了。** [文件系统与网络的最小权限](/chapters/sandboxing/least-privilege)中的固定路径夹具展示了具体路径检查的边界；容器配置也要按自身威胁模型验证，不能只凭“用了容器”推断隔离有效。

所以每一层都要**验证**，不能只在设计文档里写「我们用了容器」。


## 隔离和「能力」的关系

最后补一个概念上的澄清，它能解释为什么「隔离」这个词经常被误解。

安全领域里有一个成熟的说法：**不要把「能力」和「隔离」混为一谈。**

- **隔离边界**是进程受哪些 OS/VM 控制（namespace、mount、cgroup、安全配置、虚拟机）。
- **对象能力（object capability）** 是进程实际持有的引用，例如已打开的文件描述符、socket 或句柄；这与容器 `--cap-drop` 调整的 Linux `CAP_*` 权限不是同一概念。

边界和已持有的引用需要一起检查：容器即使禁了后续网络连接，预先传入的 socket 仍可能允许通信；只读挂载之外已打开的文件描述符也不会因路径策略改变而自动失效。

这解释了三个常见现象：

**现象一：明明在容器里，还是读到了宿主文件。** 因为挂载了宿主目录 —— 那是「能力」层面的问题，不是隔离不够强。

**现象二：沙箱里的代码通过一个已打开的 socket 发出去了数据。** socket 是能力，沙箱没拦住它。

**现象三：给了最小权限，但工具内部又去读了配置里的其他路径。** 权限在入口处收窄了，工具实现里又放开了。

所以检查隔离是否有效，不能只看「用了什么隔离技术」，要看**这个进程手里实际握着什么**：打开了哪些文件、连了哪些 socket、有哪些环境变量。**这才是它能做的最坏的事的上界。**

## 一个常被忽略的维度：生命周期

前面讲的都是「隔离得多严」。还有一个同样重要、但经常被跳过的维度：**这个沙箱活多久。**

三种做法，代价和安全差别很大：

**每任务新环境。** 每个任务使用独立容器/VM 与新建可写层，结束后销毁。它降低跨任务状态复用风险，但仍要确认宿主挂载、外部凭据和共享服务不会泄漏；启动开销依运行时而异。

**复用但清理。** 沙箱长期存在，任务之间尝试清理临时文件。省了启动开销，但只有进程、环境变量、socket、凭据、缓存和可写层均被隔离并验证时，才能主张任务间不共享状态；单靠删除临时文件不足以做到这一点。

**全局共享。** 所有任务共用一个沙箱。最省，但若没有额外的每任务隔离，任务可能互相影响 —— 一个任务写的文件，另一个任务能读到。

选择依据和前面一样是爆炸半径：**如果任务之间不该互相看见，就必须建立可验证的每任务隔离单元。** 这可以是每任务重建，也可以是经过验证的隔离执行器复用；压测通过不能证明跨租户信息不可见。

一个折中：**沙箱实例复用，但文件系统每任务重建**（挂一个新建的临时目录）。这样启动开销摊掉了，而状态仍然是隔离的。
## 完整可运行代码

下面这段代码把四个层级并排跑一遍，演示它们在「能力」与「代价」上的实际差别。

```python
"""隔离的层级：演示语言层黑名单绕过与进程资源限制。

纯本地演示；旧性能数字见上文历史摘要，不在此复测。
"""
import resource, subprocess, sys, time, warnings


def l0_inline():
    """L0：进程内直接算 —— 没有任何隔离。"""
    t = time.time()
    out = str(sum(i * i for i in range(1000000)))
    return out, time.time() - t, "无隔离：可以 import os、可以读任意文件、可以用光内存"


def l1_blacklist():
    """L1：从对象树取回 importer，再只读当前进程 PID。"""
    banned = {"__import__", "open", "eval", "exec", "compile", "input", "breakpoint"}
    safe = {k: v for k, v in vars(__builtins__).items() if k not in banned} \
        if not isinstance(__builtins__, dict) else \
        {k: v for k, v in __builtins__.items() if k not in banned}
    # warnings 在可信宿主侧导入；eval 的 builtins 仍不含 __import__。
    # PoC 只读取 PID，不访问文件、网络或修改状态。可用对象随 Python 版本变化。
    t = time.time()
    try:
        out = str(eval("sum(i*i for i in range(1000000))", {"__builtins__": safe}))
        escape = eval("next(c for c in ().__class__.__base__.__subclasses__() if c.__name__ == 'catch_warnings')()._module.__builtins__['__import__']('os').getpid()", {"__builtins__": safe})
        note = "黑名单绕过成功：经 warnings.catch_warnings 取回 __import__，只读当前 pid=%s" % escape
    except Exception as e:
        out, note = "失败", type(e).__name__
    return out, time.time() - t, note


def l2_cpu_limit():
    """L2：独立进程 + CPU 时间上限。Unix 单线程本地演示。"""
    def limit():
        resource.setrlimit(resource.RLIMIT_CPU, (1, 1))     # 1 秒 CPU 后就 SIGXCPU
    t = time.time()
    # resource 仅适用于 Unix；preexec_fn 在多线程父进程中不安全且可能死锁。
    # 生产服务不要照搬：应由专用 launcher/container 设置限制，并负责进程树清理。
    p = subprocess.run([sys.executable, "-c", "while True: pass"],
                       capture_output=True, text=True, timeout=15, preexec_fn=limit)
    dt = time.time() - t
    sig = "被 SIGXCPU 杀掉（返回码 %d）" % p.returncode if p.returncode < 0 else "返回码 %d" % p.returncode
    return sig, dt, "资源被内核限制住了；但文件与网络**仍然完全放得开**"


def l2_wall_timeout():
    """L2b：墙钟超时 —— 另一条不同的限制。"""
    t = time.time()
    try:
        # subprocess timeout 的清理针对直接子进程；不能据此保证后代进程退出。
        subprocess.run([sys.executable, "-c", "import time; time.sleep(30)"],
                       capture_output=True, text=True, timeout=1)
        out = "居然没超时"
    except subprocess.TimeoutExpired:
        out = "被墙钟超时终止"
    return out, time.time() - t, "墙钟管「等了多久」，CPU 限制管「算了多久」—— 两者不能互相替代"


if __name__ == "__main__":
    print("不同机制演示（负载并不相同，耗时不可横向比较）：")
    print()
    print("  %-20s %-26s %-9s %s" % ("层级", "结果", "耗时", "说明"))
    for name, fn in [("L0 进程内", l0_inline), ("L1 禁内建黑名单", l1_blacklist),
                     ("L2 子进程+CPU 上限", l2_cpu_limit), ("L2b 子进程+墙钟超时", l2_wall_timeout)]:
        out, dt, note = fn()
        print("  %-20s %-26s %-9.3f %s" % (name, str(out)[:24], dt, note))
    print()
    print("=== 不同层级的边界不同；实际约束取决于实现与配置 ===")
    print("  L0  进程内        —— 只能靠「相信代码」")
    print("  L1  语言层黑名单  —— 有已知绕过手法，不构成安全边界")
    print("  L2  独立进程      —— 资源可限，但文件与网络仍放得开")
    print("  L3  容器          —— 文件系统、网络、能力可以各自单独收")
    print("  L4  虚拟机        —— 独立 guest kernel；仍依赖 hypervisor 与宿主配置")
    print()
    print("选择依据不是「哪个更安全」，而是「我能接受多大的爆炸半径」——")
    print("执行不可信代码需由宿主强制外部隔离，具体边界按威胁模型验证。")
```


## 层级的另一个维度：时间

前面讲的是「隔离多严」，生命周期是另一个维度：每任务新容器/VM、复用执行器但重建隔离单元、或共享同一沙箱。复用是否安全取决于进程、凭据、socket、缓存和可写层是否能跨任务访问；“清理代码已运行”不等于隔离成立。选用复用时，应通过并发/顺序跨租户 marker 测试，并将不确定状态的实例销毁重建。
## L3 的实体：一段可复制的容器配置

L3 不是一句「用容器」，它是一组具体的开关。下面示例假定当前目录有 `runner.py` 和 `task-input/`。实际部署应固定并核验镜像 digest；这里的可变标签只便于本地演示。Docker 的 `--network none` 仍保留容器内 loopback。gVisor 通过用户态 application kernel 增加隔离；Firecracker 则提供基于 KVM 的 microVM，两者边界和配置接口不同。

`runner.py` 是可信的执行入口；不可信任务代码不应由调用者任意替换它：

```python
from pathlib import Path

for path in sorted(Path('/input').iterdir()):
    print(path.name)
```

```bash
docker run --rm \
  --read-only \
  --tmpfs /workspace:rw,size=64m,mode=1777 \
  --network none \
  --user 65534:65534 \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  --pids-limit 64 \
  --memory 256m --memory-swap 256m \
  --cpus 0.5 \
  --mount type=bind,src="$(pwd)/runner.py",dst=/app/runner.py,readonly \
  --mount type=bind,src="$(pwd)/task-input",dst=/input,readonly \
  python:3.12-alpine python /app/runner.py
```

每个开关对应一个失效模式，不是装饰：

| 开关 | 没有它会怎样 |
|---|---|
| `--read-only` + `--tmpfs` | 容器内能写宿主可见的任何路径；只读根让它只能写显式挂载的 tmpfs |
| `--network none` | 通常接入 bridge 网络并可能访问外部或已连接网络中的服务；实际可达目标取决于路由、防火墙和 Docker 网络配置（见[文件系统与网络的最小权限](/chapters/sandboxing/least-privilege)） |
| `--user` | 默认 root；即使丢了 capabilities，root 仍能碰更多东西 |
| `--cap-drop ALL` | 默认保留一批 capability，其中若干足以做越权操作 |
| `--pids-limit / --memory / --cpus` | 任务可能消耗过多宿主资源；cgroup 配额可限制容器资源，但宿主仍需按并发负载配置余量 |
| `src=...,readonly` | 若把范围过大的宿主目录以读写方式挂进去，任务就能读写该挂载范围；只挂必要路径并设为只读（仍需验证宿主文件权限） |

**边界必须说清楚：容器共享宿主内核。** 所以内核漏洞、以及上面那些配置错误，仍是逃逸路径。这也是「用了容器不等于隔离做对了」的由来 —— 强度取决于配置，不取决于「用了容器」这个事实。

## 验证：把「我们用了容器」变成可复跑的结果

前面说「每一层都要验证」。验证的做法不是读配置，而是**在沙箱里跑一个探针，逐项报告隔离是否成立**。下面脚本应挂载为只读 `/app/probe.py`，再用同一组约束执行（本次实跑：Docker 29.3.1，镜像 `python:3.12-alpine`，实跑数据 2026-10-12）：

```python
import os

def t_write_blocked():          # 根文件系统只读
    try:
        open('/probe_write', 'w').write('x'); return False, '根目录可写'
    except OSError as e:
        return True, type(e).__name__

def t_no_default_route():       # --network none：无非 loopback 默认路由
    routes = open('/proc/net/route').read().splitlines()[1:]
    ipv4_default = any(row.split()[0] != 'lo' and row.split()[1] == '00000000'
                       and row.split()[7] == '00000000' for row in routes)
    ipv6 = open('/proc/net/ipv6_route').read().splitlines()
    ipv6_default = any(row.split()[0] == '0' * 32 and row.split()[1] == '00'
                       and row.split()[-1] != 'lo' for row in ipv6)
    return not (ipv4_default or ipv6_default), 'external_default_route=%s' % (ipv4_default or ipv6_default)

def t_non_root():               # 非 root
    return (os.getuid() != 0), 'uid=%d' % os.getuid()

def t_host_mount_hidden():      # 没挂进来的宿主路径不可见
    return (not os.path.exists('/hosttmp/host-marker')), 'exists=%s' % os.path.exists('/hosttmp/host-marker')

def t_workspace_writable():     # 该能写的地方能写
    try:
        open('/workspace/ok.txt', 'w').write('x'); return True, '可写'
    except OSError as e:
        return False, type(e).__name__

for name, fn in [('只读根文件系统', t_write_blocked), ('无非 loopback 默认路由（--network none）', t_no_default_route),
                 ('非 root 用户', t_non_root), ('宿主挂载点未泄露', t_host_mount_hidden),
                 ('tmpfs 工作目录可写', t_workspace_writable)]:
    ok, detail = fn()
    print('  %-4s %-22s %s' % ('PASS' if ok else 'FAIL', name, detail))
```

将这段代码保存为当前目录的 `probe.py` 后，用下列命令运行：

```bash
docker run --rm --read-only \
  --tmpfs /workspace:rw,size=64m,mode=1777 \
  --network none --user 65534:65534 --cap-drop ALL \
  --security-opt no-new-privileges --pids-limit 64 \
  --memory 256m --memory-swap 256m --cpus 0.5 \
  --mount type=bind,src="$(pwd)/probe.py",dst=/app/probe.py,readonly \
  python:3.12-alpine python /app/probe.py
```

在这一节的配置下跑（宿主 `/tmp` 里先放一个 `host-marker`，但不挂进容器）：

```text
=== 配置正确（--read-only --network none --user 65534 --tmpfs /workspace）===
  PASS 只读根文件系统                OSError
  PASS 无非 loopback 默认路由（--network none） external_default_route=False
  PASS 非 root 用户              uid=65534
  PASS 宿主挂载点未泄露               exists=False
  PASS tmpfs 工作目录可写           可写
```

把配置换成「默认 root + 默认网络 + 把宿主 `/tmp` 挂进去」，同一个脚本立刻翻车：

```text
=== 配置错误（默认 root + 默认网络 + 挂载宿主 /tmp）===
  FAIL 只读根文件系统                根目录可写
  FAIL 无非 loopback 默认路由（--network none） external_default_route=True
  FAIL 非 root 用户              uid=0
  FAIL 宿主挂载点未泄露               exists=True
  FAIL tmpfs 工作目录可写           FileNotFoundError
```

**这就是「验证过的隔离」和「配了隔离」的区别。** 两边的架构描述可以写得一模一样，探针只报告实际执行的检查；未覆盖的边界仍需另行验证。把这段探针纳入 CI 或启动自检，可以在配置变化时尽早暴露已覆盖的回归。

> Docker 文档描述 `none` 网络只保留 loopback。实测 Docker 29.3.1 的本地运行环境还显示若干没有默认路由的 tunnel 设备名，因此探针不把接口名集合硬编码为 `{'lo'}`，而是检查 IPv4/IPv6 路由表中是否有非 loopback 默认路由。没有非 loopback 默认路由只是路由表观察，不能证明防火墙、宿主控制面或 loopback 服务不可达；外部连接探测也受本机网络策略影响，不能单独归因于容器配置。

## 生命周期：谁创建、清理什么、怎么验证清理干净

前面提了「每任务重建 / 复用但清理 / 全局共享」三种，但没说这三件事谁做、做什么。补上：

**谁创建。** 由**调度层**（跑 agent 循环的那个服务）在任务开始时创建，不是在工具里临时创建 —— 工具作者不该负责沙箱生命周期，否则又会散成 20 处。

**清理什么。** 一份清单，按「跨任务泄露」的风险排序：

| 要清的东西 | 不清会怎样 |
|---|---|
| 可写目录里的文件与临时文件 | 上一个任务的输出被下一个任务读到 |
| 环境变量里注入的凭据 | 下一个任务拿到了不属于它的身份 |
| 已打开的 socket / 连接 | 复用进程时，上一任务的连接继续可用 |
| 进程表里的残留进程 | 后台进程活过任务边界，继续占资源 |
| 本地缓存（如 pip / npm cache） | 缓存投毒跨任务传递 |

**怎么验证清理干净。** 判断方式是**下一个任务开始前先跑一个「洁净探针」**，而不是靠 review 清理代码：探针检查「可写目录文件数 == 0」「环境变量与白名单一一对应」「上一任务写的 marker 文件不存在」。三项全过才继续；任一项失败就把这个实例标记为脏、销毁重建。这与上面的隔离探针是同一个套路：**把「我以为清干净了」变成一个可复跑的结果。**

**选哪种。** 判据还是爆炸半径：如果任务之间不该互相看见，就使用每任务隔离单元；确实要摊启动开销时，可以复用执行器，但需为每任务重建文件系统/进程/凭据边界，并用跨任务 marker 与并发测试验证。未经验证的「全局共享 + 清理」不能作为租户隔离保证。

## 常见坑

- **把语言层黑名单当安全边界。** 它有已知绕过手法，只适合防误用。
- **只设 CPU 限制，不设墙钟超时。** 一个 sleep 程序不花 CPU，但会让请求挂住。
- **以为 L2 拦得住文件访问。** 资源限制只管「用多少」，不管「碰什么」。
- **以为用了容器就等于隔离做对了。** 配置错误（挂了宿主目录、给了特权）仍然是逃逸路径。
- **按安全等级选层级，而不是按爆炸半径。** 读文件的任务不需要虚拟机；执行模型写的代码则需要。
- **只算权限和隔离，忘了鉴权。** 沙箱不改变身份 —— 在沙箱里仍然能查到别人的订单。
