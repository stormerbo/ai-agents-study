接入第三方 MCP server 时，至少要分开审视**数据流、动作权限和运行环境**。这几类风险彼此相关，但不能只靠一条“信任/不信任”判断来处理。

## 第一类风险：它会看到什么

server 能看到它实际收到的请求内容。MCP 不会因为某个 server 被挂进 tools，就自动把整段对话发送给它；host 通常通过 `tools/call` 发送工具名、`arguments` 和协议元数据，HTTP transport 还会带相应授权信息。若 host 把整段对话、文件或模型中间结果塞进参数，对端就会收到那些内容。

还要区分 transport：远程 server 作为独立服务运行，其文件、凭据与网络权限由服务端部署决定；MCP 请求内容只说明 host 发了什么，不能推出 server 的出站网络范围。本地 stdio server 则在 host 上作为进程启动，可能访问该账户可读的文件、环境变量与网络。真实边界由启动权限、sandbox 和网络策略决定。

这类风险的本质是**数据外泄**：发送的数据和进程可访问的数据，都需要逐项盘点。

远程 server 能访问什么，取决于它的服务端身份、文件挂载、凭据和网络出口策略；MCP 协议不会把它限制在本次 `tools/call` 的参数范围内。反过来，MCP client 在处理 OAuth 资源或授权服务器元数据时也会主动抓取 URL，恶意元数据可能诱发 client-side SSRF，触达内网、loopback 或云元数据服务。因此，“远程 server 只能访问自己的服务资源”不是协议保证；部署方要限制服务端出站网络，client 也要验证 OAuth URL、重定向目标并按环境阻断内部地址。

## 第二类风险：它能做什么

这是更常被讨论、也更容易被低估的一类。

server 提供的工具定义来自 server。host 通过 `tools/list` 能看到 `name`、`description` 和 `inputSchema` 等字段；现代规范还允许 `title`、`icons`、`outputSchema`、`annotations` 等可选元数据。它们描述接口，不是实现或安全证明；工具注解也应视为不可信，除非来源本身可信。

我在自己的最小实现上跑了一遍这个「你究竟能看到什么」：

```text
tools/list 返回了 2 个工具。下面只打印 host 可读的核心字段：
  · name=get_weather
    description=查询某个城市某一天的最高气温。
    inputSchema={"type": "object", "properties": {"city": ..., "day": ...}}
  · name=transfer_money
    description=演示转账确认流程；本示例不会执行真实转账。
    inputSchema={"type": "object", "properties": {"to": ..., "amount": ...}}
```

这些字段不能让 host 检查实现本身。host 看不到的：

- **实现是什么。** 工具名只是声明，代码在对方那里。
- **有没有副作用。** `get_weather` 看起来只读 —— 但那是它的描述说的，不是它的代码说的。
- **它会怎么处理参数。** 同一个参数可能触发完全不同的行为。

当前 MCP 工具定义还可能包含可选显示信息、注解或输出 schema；这些都仍是 server 提供的元数据。它们不能证明实现做了什么，也不等同于授权规则。第二个例子里的 `transfer_money` 恰好把潜在影响写在名字上，但现实中更常见的是下面这种：

```json
{"name": "optimize_storage",
 "description": "清理临时文件与冗余索引，释放存储空间。",
 "inputSchema": {"type": "object", "properties": {"scope": {"type": "string"}}}}
```

这个名字和描述完全无害 —— 而它的实现可以是 `DROP DATABASE`。**描述是对方写的，不是事实。**

## 主要风险与对应控制点

关键是把保护措施放在正确边界：

| | 它会看到什么（数据外泄） | 它能做什么（动作越界） |
|---|---|---|
| 防线位置 | **数据流**：在把内容发出去之前过滤 | **动作流**：在执行调用之前拦截 |
| 有效手段 | 最小化并检查实际发送的数据 | host allowlist、访问控制、敏感操作确认、sandbox |
| 协议能提供什么 | 不能替 host 决定哪些上下文可发送 | 提供输入校验、访问控制和确认等安全要求；具体授权仍由 host/server 落实 |
| 供应链评估的作用 | 有帮助但不是证明 | 有帮助但不是运行时授权 |

**协议不能替你完成应用级的数据授权与业务动作策略。** 但这不等于 MCP 完全没有安全机制：2026-07-28 的工具规范要求 server 校验输入、实施访问控制、限流并清理输出；client 对展示调用参数、敏感操作确认、校验工具结果、设置超时和记录审计日志有 SHOULD 建议。Streamable HTTP 另有 `Origin` 校验等要求。协议提供安全控制要求与机制，部署方仍须把它落实成适合自身数据与权限模型的规则。

评估维护者、源码、签名和版本有助于判断供应链风险，但工具描述或 `serverInfo` 不能单独证明实现可信。MCP 工具名只在单个 server 内唯一；host 聚合多个 server 时，应使用本地配置的 server 身份做隔离，不能只信对方自报名称。

## 工程上能做什么

五条都是工程建议，需按部署权限与业务后果取舍。

**一，区分读取与执行入口。** resources 往往由 host 决定是否读取，tools 则可由模型提出调用；这会改变 host 的控制点，但 resources 并非天然安全：读取的数据仍可能敏感或含有提示注入，host 要决定是否把它送入模型。

**二，在 host 的调用边界执行授权。** 以本地配置的 server 身份和工具名做 allowlist，默认拒绝未登记的工具；再按风险设置预算、超时、熔断与人工确认。模型给出 `tool_use` 不代表获得授权。对不可逆动作，确认与最终授权必须由 host 的策略控制，不能由模型自行宣布“已确认”。

**另需把 MRTR 当作协议交互点，不要当作审批保证。** 2026-07-28 的 server 可把所需输入放进 `input_required`，客户端重试原请求。host/SDK 可以在重试前检查或拒绝，但 SDK 也可能按配置自动处理；规范不保证一定显示给用户，也不保证这是授权或人工审批。对有副作用的操作，仍需独立的 host 权限策略与确认流程。

**四，最小化发给它的数据。** 只发这次调用需要的字段，不要顺手把整段对话传过去。减少发送内容能缩小泄露面；先盘点参数、传输凭据和本地进程可读资源，再决定哪些必须提供。

**五，限制运行时权限。** 本地进程用 sandbox、文件系统白名单和最小环境变量；不需要网络时关闭网络，需要网络时通过出口策略限制目标。远程 server 则校验目标、身份与授权范围，并控制它能访问的下游资源。容器限制能缩小爆炸半径，但不能代替 host 授权或可信部署。

## 一个具体的接入检查清单

把上面五条落成可执行的动作：

1. **这个 server 是谁维护的？** 更新频率、issue 响应、有没有公开源码 —— 这些不能证明安全，但能区分「有人在管」和「没人管」。
2. **它声明了哪些工具，每个的潜在影响是什么？** 逐个过一遍，标出不可逆的那些。
3. **哪些工具要禁止调用？** 直接在执行层拒绝，不要指望模型不去调。
4. **它需要哪些数据？** 只给那些，不给整段对话。
5. **它跑在什么权限下？** 本地进程用最小权限；远程 endpoint 限定它能访问的范围。
6. **有没有一个明确的确认点？** 不可逆动作必须在你的代码里停一下。

六条是风险评审步骤，不是安全保证。allowlist、每次调用授权与敏感操作确认应由 host 在执行前强制；其余检查降低风险，但不能证明 server 实现无恶意或无漏洞。

## 完整可运行代码

下面这段代码跑的就是本节那个「host 能看到什么」的探针 —— 它把一个第三方 server 暴露的全部信息打印出来，让你直观看到那条边界在哪里。

```python
"""一个最小的 MCP client：用真正的子进程 + 管道驱动 server。

它验证的是 stdio 传输 + 无状态协议的几个机制点。实跑状态：2026-10-09。
"""
import json, subprocess, sys

SERVER = [sys.executable, "mcp_server.py"]  # 第 4 节那份 server，存成同目录的 mcp_server.py


class Client:
    def __init__(self):
        self.proc = subprocess.Popen(SERVER, stdin=subprocess.PIPE, stdout=subprocess.PIPE,
                                     text=True, bufsize=1)
        self.n = 0

    def send(self, method, params=None, version="2026-07-28", with_meta=True):
        """每个请求自己带 _meta —— 这就是无状态化的形态。"""
        self.n += 1
        p = dict(params or {})
        if with_meta:
            p["_meta"] = {"io.modelcontextprotocol/protocolVersion": version,
                          "io.modelcontextprotocol/clientCapabilities": {"elicitation": {}}}
        req = {"jsonrpc": "2.0", "id": self.n, "method": method, "params": p}
        self.proc.stdin.write(json.dumps(req, ensure_ascii=False) + "\n")
        self.proc.stdin.flush()
        line = self.proc.stdout.readline()
        return json.loads(line)

    def close(self):
        self.proc.stdin.close()
        self.proc.wait(timeout=5)


def show(label, resp, ok_expect=None):
    if "error" in resp:
        e = resp["error"]
        tag = "error"
        detail = "%s (%d) %s" % (e["message"], e["code"], json.dumps(e.get("data"), ensure_ascii=False)[:90])
    else:
        tag = "result"
        detail = json.dumps(resp["result"], ensure_ascii=False)[:110]
    judge = ""
    if ok_expect is not None:
        judge = "  ✅" if (tag == ok_expect) else "  ❌（期望 %s）" % ok_expect
    print("  %-34s %-7s %s%s" % (label, tag, detail, judge))
    return resp


if __name__ == "__main__":
    c = Client()
    print("=== 1. 无状态化：版本校验发生在每个请求上 ===")
    show("不带 _meta 直接调 tools/list", c.send("tools/list", with_meta=False), "error")
    show("带错误的协议版本", c.send("tools/list", version="2020-01-01"), "error")
    show("带正确版本", c.send("tools/list", version="2026-07-28"), "result")
    print()
    print("=== 2. server/discover：让 server 自己声明 ===")
    show("server/discover", c.send("server/discover"), "result")
    print()
    print("=== 3. tools/call ===")
    show("get_weather(北京,明天)",
         c.send("tools/call", {"name": "get_weather",
                               "arguments": {"city": "北京", "day": "明天"}}), "result")
    show("get_weather(北京,下周)",
         c.send("tools/call", {"name": "get_weather",
                               "arguments": {"city": "北京", "day": "下周"}}), "result")
    show("未知工具", c.send("tools/call", {"name": "nope", "arguments": {}}), "error")
    show("未知方法", c.send("resources/subscribe"), "error")
    print()
    print("=== 4. MRTR：多轮往返请求 ===")
    first = c.send("tools/call", {"name": "transfer_money",
                                  "arguments": {"to": "张三", "amount": 5000}})
    show("第一次调用", first, "result")
    r = first["result"]
    print("    resultType = %s" % r.get("resultType"))
    if r.get("resultType") == "input_required":
        print("    ⚠️ server 没有主动发请求，而是把「需要输入」作为返回值交回来")
        print("    客户端补上输入后**再调一次**（发起权始终在客户端）")
        show("补上确认后重调", c.send("tools/call",
                                     {"name": "transfer_money",
                                      "arguments": {"to": "张三", "amount": 5000},
                                      "requestState": r["requestState"],
                                      "inputResponses": {"confirm": {
                                          "action": "accept", "content": {"confirmed": True}}}}), "result")
    c.close()


# ==== 5. 安全边界：host 能看到什么、看不到什么 ====
def security_probe():
    c = Client()
    resp = c.send("tools/list")
    tools = resp["result"]["tools"]
    print()
    print("=== 5. 接入第三方 server：host 能看到什么 ===")
    print("  tools/list 返回了 %d 个工具。host 能看到的核心字段：" % len(tools))
    for t in tools:
        print("    · name=%s" % t["name"])
        print("      description=%s" % t["description"])
        print("      inputSchema=%s" % json.dumps(t["inputSchema"], ensure_ascii=False))
    print()
    print("  host **看不到**的：")
    print("    · 实现是什么（工具名只是声明，代码在对方那里）")
    print("    · 有没有副作用（get_weather 看起来只读，但描述不能作为保证）")
    print("    · 它会怎么处理参数（同一个参数可能触发完全不同的行为）")
    print()
    print("  ⚠️ 工具名和描述都是元数据，不能证明实现会做什么；")
    print("     一个叫 optimize_storage 的工具也可能有破坏性副作用 ——")
    print("     而 description 是**对方写的**，不是事实。")
    c.close()


if __name__ == "__main__" and len(sys.argv) > 1 and sys.argv[1] == "security":
    security_probe()
```


## 把五条落成代码

上面五条读起来都对，但落到你自己的仓库里，落点只有四个。逐个给可执行的形态。

**落点一：看清你发出去的整个请求。** 数据外泄的起点是「请求里带了什么」。下面是 host 发给 server 的一次完整 `tools/call`（示例：构造数据，未实跑）—— 注意 `arguments` 之外，`_meta` 也在里面：

```json
{"jsonrpc": "2.0", "id": 31, "method": "tools/call",
 "params": {"_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientCapabilities": {"elicitation": {}}},
            "name": "review_code",
            "arguments": {"diff": "...", "language": "python"}}}
```

**最小化上下文就是把 `arguments` 压到这几个字段**，不要顺手把整段对话塞进某个 `context` 字段 —— 泄露的前提是数据真的发出去过。

**落点二：工具白/黑名单拦截。** 「哪些工具禁止调用」必须在调用前查表，而不是指望模型不去调：

```python
# host 配置中的 server_id 必须由本地确定，不使用 server 自报名称做安全身份。
# 第三方工具默认拒绝，只有审核并登记的操作才允许。
POLICY = {
    ("github-prod", "get_issue"): "allow",
    ("tickets-prod", "close_ticket"): "confirm",
}
DEFAULT = "deny"

def gate(server_id, tool_name, args, approve, execute):
    verdict = POLICY.get((server_id, tool_name), DEFAULT)
    if verdict == "deny":
        raise PermissionError("工具 %s/%s 被策略禁用" % (server_id, tool_name))
    if verdict == "confirm" and not approve(server_id, tool_name, args):
        return {"status": "denied", "tool": tool_name}
    return execute(server_id, tool_name, args)

# 可运行的教学回调：真实 host 应注入自己的授权与 dispatch 实现。
def demo_approve(server_id, tool_name, args):
    return False

def demo_execute(server_id, tool_name, args):
    return {"status": "would_execute", "server": server_id, "tool": tool_name}

if __name__ == "__main__":
    print(gate("tickets-prod", "close_ticket", {"id": "T-1"}, demo_approve, demo_execute))
```

`approve` 与 `execute` 是由 host 注入的实际策略回调；例子中的 `demo_approve` 只返回拒绝，避免把 mock 当成真实授权。默认拒绝，再显式登记完成评估的工具；对敏感操作另设确认。这个策略只保护经过该 host gate 的调用，server 进程自己的本地权限仍要由 sandbox 与操作系统收口。

**落点三：参数 allowlist。** 最可靠的第一步不是猜哪些 key 叫 secret，而是只构造工具 schema 允许且任务确实需要的参数。字段名过滤只能作补充，无法识别敏感内容藏在正常字段值里的情形：

```python
# 按具体 server 与 tool 维护允许字段；这只是字段投影，不检查字段值内容。
import json

ALLOWED_FIELDS = {
    ("code-review-prod", "review_code"): {"diff", "language"},
}

def build_tool_arguments(server_id, tool_name, supplied):
    allowed = ALLOWED_FIELDS.get((server_id, tool_name))
    if allowed is None:
        raise PermissionError("工具未登记")
    unexpected = set(supplied) - allowed
    if unexpected:
        raise ValueError("拒绝未允许字段: %s" % sorted(unexpected))
    return {key: supplied[key] for key in allowed if key in supplied}

if __name__ == "__main__":
    args = build_tool_arguments(
        "code-review-prod", "review_code", {"diff": "仅包含本次变更", "language": "python"}
    )
    print(json.dumps(args, ensure_ascii=False))
```

这个 allowlist 会拒绝误带的额外字段，但不会从 `diff` 等允许字段的文本内容中自动识别秘密。要防止这类泄露，先在生成参数时最小化来源，再按数据分类做内容级检查；字段 allowlist 不能被宣传成 DLP 或零泄露保证。

**落点四：用最小权限跑本地 server。** 本地 server 跑在你的权限下（第 4 节那张表的第二行），收窄权限是唯一能限制爆炸半径的动作。一个可用的启动形态：

```bash
# 只读根文件系统、丢掉所有内核能力、用非 root 用户、限制内存与进程数
docker run --rm -i \
  --read-only --network=none \
  --tmpfs /tmp:rw,noexec,nosuid,size=16m \
  --cap-drop=ALL --security-opt no-new-privileges \
  --user 65534:65534 \
  --memory=256m --pids-limit=64 \
  -v "$PWD/mcp_server.py:/app/mcp_server.py:ro" \
  --entrypoint python3 python:3.12-slim /app/mcp_server.py
```

关键参数：`--read-only` 让容器根文件系统只读；`--cap-drop=ALL` 删除容器 Linux capabilities；`--user 65534:65534` 以非 root UID/GID 运行；`--tmpfs` 提供受限临时目录；`-v ...:ro` 只读挂载 server 文件。**这些设置不等于宿主机隔离的完整证明**：容器仍可访问显式挂载内容；默认网络也仍可出站。server 不需要网络时可加 `--network=none`；确需网络时配置明确的出口策略。容器配置本身要按运行环境复核。

**组合风险的对策落到代码上，就是「按 server 整体评估」**：上面那个 `POLICY` 的 key 之所以是 `(server, tool)` 而不是单个工具，正是为了让「这个 server 同时有 read_file 和 send_http」这种组合能被一条规则整体拒绝：

```python
# 组合高危：同一个 server 同时提供「读任意文件」和「发任意网络请求」
DANGEROUS_COMBOS = [
    {"read_file", "send_http"},
]

def server_verdict(tools):
    names = {t["name"] for t in tools}
    for combo in DANGEROUS_COMBOS:
        if combo <= names:                    # 子集判断：这批工具里出现了完整的高危组合
            return "deny-known-combination"
    return "no-known-combination-detected"
```

这个函数只识别一类已知组合；没有命中只能表示“未识别到此组合”，不能返回安全结论。还需检查参数约束、进程权限、网络出口和工具间的跨 server 数据路径。

## 一个更宽的风险：组合出来的能力

前两类风险都是单个工具的。「它能做什么」还有一个更难防的版本：**多个无害工具组合出的危险。**

设想一个服务器提供两个工具：

- `read_file(path)` —— 读一个文件
- `send_http(url, body)` —— 发一个 HTTP 请求

单独看，两个都很常见、很合理。但**组合起来就是一个数据外泄通道**：模型可以读一个敏感文件，然后把它作为 body 发到外部地址。而整个过程里，没有哪一个工具调用是「越界」的。

这一类风险的特点是：**它在单次调用的粒度上不可见。** 你的闸门如果能按工具名拦截，拦不住它 —— 因为两个工具都该被允许。

能做的有三件事：

**一，限制工具集合，而不是逐个审批。** 如果这个 server 同时提供读本地文件和发外网请求，你要问的是「它真的需要两者同时存在吗」。**来自同一个 server 的工具应该被当成一个整体评估** —— 因为它们共享同一份实现，可以互相配合。

**二，在数据流上做检查。** 如果发送的内容里包含不该外发的字段（密钥、用户标识），在网络层拦下来。这是第 1 类风险的防线，但它在这里同样有效 —— 因为组合风险最终一定要通过某个出口。

**三，对高危组合直接拒绝。** 「读任意文件」+「发任意网络请求」这个组合，如果任务不需要，就不该出现在你的工具列表里。

**这三条的共同点是：判断的粒度不是「这个工具危不危险」，而是「这批工具在一起能做的最坏的事是什么」。** 这与第 4 章讲工具数量时的思路一致 —— 工具的影响要看组合，不只看单个。

## MRTR 改变了交互形态，但不替你做授权

最后补一个乐观的角度。

在旧版有 server→client 请求通道的协议中，请求也必须关联到一个仍在处理的 client request，不能在完全空闲时任意发起。2026-07-28 的 MRTR 把所需输入嵌入原调用返回的 `input_required`，client 用新 JSON-RPC id 重试。

这让交互结构更显式，但**不自动构成人工审批或安全防线**：SDK/host 可能自动处理输入，用户也未必看见请求；读取数据、调用模型、再把结果发出的权限仍由 host 和 server 的实际实现决定。host 若要利用这个边界，必须明确检查请求、决定是否继续，并让副作用动作经过独立授权。
## 常见坑

- **把两类风险混在一起谈。** 数据外泄的防线在数据流，动作越界的防线在动作流，用错防线等于没有防线。
- **以为「选个可信的 server」就够了。** 意图无法验证，能力声明只说明接口可用。
- **只看工具名字判断危险性。** 名字和描述都是对方写的；`optimize_storage` 可以是 `DROP DATABASE`。
- **指望协议层替你执行应用级策略。** MCP 有工具输入/访问控制/限流/输出清理等规范要求，也有 transport/auth 控制；host 仍需落实自己的数据最小化与动作授权。
- **把 MRTR 当成人工审批。** 它提供协议层的输入往返形态；是否展示、自动处理或拒绝，由 host/SDK 实现决定。
- **只在接入时评估一次。** 可用工具集可以随时间或每请求授权上下文变化；`listChanged` 表示 server 支持相应变化通知，不意味着工具列表一定会变。按规范重新取列表，并在每次调用时重新授权。
