MCP 的角色划分有一个容易被误解的地方：**client 不是「一个客户端」。**

## 三个角色

**host** 是用户面对的那个 AI 应用 —— 一个编码助手、一个客服系统、一个数据分析工具。它持有模型、上下文和用户界面。

**server** 是能力提供方 —— 一个 GitHub 连接器、一个数据库查询服务、一个内部工单系统的适配器。

**client** 是 host 与某个 server 通信的协议端点抽象。host 通常按 server 分别创建 client，便于隔离配置、能力与调用策略；但 client 对象不等于一条永久连接。旧版协议可在连接或 session 上保留协商状态；2026-07-28 版逐请求携带协议元数据，stdio 仍可能是长寿命子进程，而 Streamable HTTP 普通调用按请求往返。

所以关系是：

```text
host
 ├── client ──── server A（GitHub）
 ├── client ──── server B（数据库）
 └── client ──── server C（工单系统）
```

**为什么要把 client 单独拿出来？** 因为这样每个 server 的能力边界与生命周期就各自独立了：

- server A 挂了，不影响 server B 的连接
- 每个 server 有独立的协议端点与能力边界；在 2026-07-28 版中，版本由每个请求声明，server 对请求逐次接受或拒绝
- host 可以把来自不同 server 的工具放在不同的权限桶里（「权限桶」= 一份按 server 维度维护的允许清单：调用前先查「这个 server 的这个工具在不在允许范围内」，见本节末尾的可执行写法）

如果把所有 server 都塞进一个没有边界的 client 对象，上面这些配置与故障隔离会更难表达。按 server 划分 client 是一种常见的 host 实现方式；它是应用架构选择，不是 MCP 规范强制的连接或 session 模型。

## 三类能力：协议语义与交互控制

server 对外提供的不只有工具。MCP 定义了 tools、resources、prompts 三类能力，它们有不同的协议语义，也有各自常见的交互模式：

| 能力 | 协议语义 | 常见交互模式（不是协议强制的 UI） |
|---|---|---|
| **tools** | 可调用的操作；是否产生副作用取决于实现 | 设计上由模型决定何时调用；host 可以提供其他交互，也负责决定是否暴露、批准和执行调用 |
| **resources** | 以 URI 标识、可读取的数据 | 通常由应用决定如何纳入上下文；可以由用户选择、规则自动加入，或由模型协助选择 |
| **prompts** | server 提供的结构化消息与指令 | 设计为 user-controlled，通常由用户显式选择；host 可以采用其他交互界面 |

「模型 / 应用 / 用户」是规范描述的**设计意图与常见控制路径**，不是 MCP 对所有 host 强制规定的执行流程。Tools 规范明确允许 host 采用其他 UI 模式；resources 规范允许 host 按需要决定如何使用资源，甚至允许基于模型选择；prompts 的内容由 server 编写，而 user-controlled 描述的是谁决定何时使用，不是内容由谁创作。实现时应区分模型提出调用、host 的策略与审批、client/server 的协议执行，以及 server 的业务授权。

接入第三方 server 时，不要把某一种能力标签当作安全等级。resource 通常没有工具式的直接动作副作用，但读取它可能泄露敏感数据，也可能把恶意指令带进模型上下文；prompt 同样由 server 提供内容。按身份和资源范围授权，最小化送入上下文的数据，并把 server 返回的文本当作不可信输入。tools 则要在 host 和 server 两侧分别校验调用策略、参数及副作用授权。

## 一个容易混淆的点：server 的「能力声明」

能力的获知方式取决于协议版本：旧版在 initialize 握手中交换能力；2026-07-28 版 server 必须实现 `server/discover`，但 client 是否先调用它是可选的，也可以直接调用 RPC 并处理版本/能力错误。工具是否可用还可能随本次请求的授权身份而变化。

这个声明**不是安全机制**，它只是让 host 知道该不该调用某些方法。一个恶意的 server 完全可以声明自己支持 X 却在实现里做 Y —— 协议层无法验证。

所以读能力声明时要知道它的性质：**它是「接口是否可用」的信息，不是「它会做什么」的保证。** 第 5 节会详细讲这个区别为什么重要。

## 为什么是三类而不是一类

一个自然的疑问：既然 tools 已经能读数据了（写一个 get_file 工具），为什么还要单列 resources？

两者功能可能重叠，但协议接口不同：tool 是带参数的可调用操作，调用结果作为工具结果返回；resource 是由 URI 标识、通过 `resources/read` 获取的数据。应用可以在系统设计中选择使用哪种接口，并决定怎样呈现或纳入上下文。两种能力本身都不替代访问控制：读取资源前仍要检查用户身份与数据权限，调用工具前仍要检查动作授权。即便内容只读，也要考虑提示注入、隐私与上下文预算。


## 三类能力长什么样

上面那张表是判据，这里给三种能力的**实际报文形态** —— 没有这个，接一个 server 时你还是不知道 `resources` 该怎么用。（以下报文为示例：构造数据，未实跑；字段按规范里的常见形态。第 4 节那个 server 只实现了 tools，没有实现下面这两个方法。）

**resources：可读数据。** `resources/list` 返回一份目录。每个 Resource 必须有 `uri`（唯一标识）和 `name`；`mimeType` 是可选字段，通常建议提供以描述内容格式。现代结果还带有 `resultType: "complete"`：

```json
{"jsonrpc": "2.0", "id": 2, "result": {"resultType": "complete", "resources": [
  {"uri": "file:///team/coding-standards.md",
   "name": "团队编码规范",
   "mimeType": "text/markdown"},
  {"uri": "db://orders/schema",
   "name": "订单表结构",
   "mimeType": "application/json"}
]}}
```

`resources/read` 是 client 发给 server 的请求。host/client 决定何时读取；MCP 不规定这次选择必须由用户还是应用代码做出。现代请求的 `_meta` 每次都要带协议版本和 client capabilities：

```json
{"jsonrpc": "2.0", "id": 3, "method": "resources/read",
 "params": {"_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
            "io.modelcontextprotocol/clientCapabilities": {}},
            "uri": "file:///team/coding-standards.md"}}
```

```json
{"jsonrpc": "2.0", "id": 3, "result": {"resultType": "complete", "contents": [
  {"uri": "file:///team/coding-standards.md", "mimeType": "text/markdown",
   "text": "# 编码规范\\n1. 所有接口必须幂等……"}
]}}
```

**读回来放哪里？** MCP 只定义 client 如何请求并收到 resource 内容，不规定 host 必须把它拼进 system 或 user 消息。host 应按内容来源和用途明确标注来源、信任等级与适用范围，再交给模型；即使是团队规范，也不要把 resource 的内容升级为系统级指令。固定前缀是否有缓存收益取决于具体 provider/API 与请求布局。

**prompts：server 提供的结构化消息。** `arguments` 列表是可选的；有参数时 host 可以据定义呈现输入控件：

```json
{"jsonrpc": "2.0", "id": 4, "result": {"resultType": "complete", "prompts": [
  {"name": "review_code",
   "description": "按团队规范审查一段代码",
   "arguments": [
     {"name": "language", "description": "代码语言", "required": true},
     {"name": "focus", "description": "关注点，如 security / perf", "required": false}
   ]}
]}}
```

用户在界面上选了 `review_code`、填了参数后，client 调用 `prompts/get`。**server 返回已解析的 messages**；host 按自己的模型适配器决定如何使用这些 `user` / `assistant` 消息：

（用户选择 review_code，language=python，focus=security）
```json
{
  "jsonrpc": "2.0",
  "id": 5,
  "method": "prompts/get",
  "params": {
    "name": "review_code",
    "arguments": {"language": "python", "focus": "security"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
```
server 返回的 messages 可能只有一条，也可能由多条 user / assistant 消息组成。这里简化成一条 user message：

```json
{
  "jsonrpc": "2.0",
  "id": 5,
  "result": {
    "resultType": "complete",
    "messages": [{
      "role": "user",
      "content": {
        "type": "text",
        "text": "请以 python 代码审查者的身份，重点检查 security 问题。下面是代码：……"
      }
    }]
  }
}
```

`prompts/get` 返回的消息不保证只有一条或只有 `user` role；消息内容也可以包含图像、音频、resource link 或 embedded resource。MCP 定义这些协议消息，不定义 host 到具体模型 API 的序列化方式。若模型侧需要区分来源或信任边界，host 必须显式保留这些信息；不能假设不同 MCP 能力经任意适配后仍天然可区分，也不能假设模型调用层完全看不见来源。

**权限桶的可执行写法。** 落在代码里就是一张按 server 维度维护的允许清单，调用前查表：

```python
# 每个 server 一条记录：被允许调用哪些工具，以及哪些必须人工确认
ALLOW = {
  "github":  {"allowed": {"get_issue", "list_prs"}, "confirm": set()},
  # confirm 是 allowed 的子集：先允许进入策略评估，再要求额外确认
  "tickets": {"allowed": {"create_ticket", "close_ticket"}, "confirm": {"close_ticket"}},
  "review":  {"allowed": {"read_file"}, "confirm": set()},
}

def permitted(server_name, tool_name):
    if not isinstance(server_name, str) or not isinstance(tool_name, str):
        return "deny"
    bucket = ALLOW.get(server_name, {"allowed": set(), "confirm": set()})
    if tool_name not in bucket["allowed"]:
        return "deny"                      # 不在清单里 → 直接拒绝
    return "confirm" if tool_name in bucket["confirm"] else "allow"
```

这条清单是第 5 节那份接入检查清单的落点：不信任某个 server 时可以先禁用它的 tools，但这不自动意味着它的 resources 安全。读取仍要按用户身份和数据范围授权，并对返回内容做信任标注；若需要验证内容或动作，再分别增加对应的校验与审批门。

## 客户端与传输的生命周期

host 往往按 server 配置 client，但 client 对象、底层传输连接、MCP 协议 session 是不同层次的概念。一次交互可按四步理解：

**一、建立传输。** host 按配置启动 stdio 子进程，或连接远程 HTTP endpoint。旧版协议可能随后执行 initialize 握手；2026-07-28 版没有这次握手，协议版本与客户端能力随每个请求携带（第 3 节）。

**二、发现或直接调用。** 客户端可以调用 server/discover 查看支持的版本与能力，但现代协议不要求先发现；也可以直接发送请求并处理 UnsupportedProtocolVersion 或 MissingRequiredClientCapability。工具列表通过 tools/list 获取，可能随请求凭据改变。

**三、逐请求执行。** host 将选中的工具调用转发给对应 client，再由 client 经当前传输发送请求。不要把某个请求的授权、工具列表或任务状态误当成连接级保证。

**四、关闭传输。** stdio 关闭子进程的标准流并回收进程；HTTP 结束请求流或订阅流。旧版 session 的清理与应用自己的业务状态生命周期分别处理。

发现结果只是当时可见能力的快照，不是后续每次调用的授权保证。安全策略仍须在工具调用时检查权限、参数和副作用（第 5 节）。

## 一个接入决策的实例

把三类能力用到实际取舍上。假设团队要接入一个第三方的「代码审查」server，它提供：

- tools：审查一段代码、自动修复问题
- resources：团队的代码规范文档
- prompts：几个常见的审查指令模板

一个稳妥的接入顺序是：

**第一步，评估只读资源。** 先确认资源的访问授权和敏感级别，再决定是否读取、向模型提供多少内容，以及如何标出来源。这通常减少了直接写入副作用，但仍有数据泄露、提示注入和上下文污染风险；应用控制读取时机并不等于数据可信。

**第二步，评估 prompts。** prompt 是 server 提供的消息内容，协议设计意图是让用户控制何时使用；host 可以采用不同交互界面。检查其返回内容和嵌入资源，并避免把 server 提供的指令提升为可信的系统策略。

**第三步，最后才考虑 tools。** 而且要先回答：审查工具会改我的代码吗？如果会，它是不可逆的吗？—— 如果是，那就该走第 9 章那套闸门，而不是直接交给模型。

这个顺序是风险评估的示例，不是通用安全等级。对每一种能力分别问：谁能触发、哪些身份可用、数据会流向哪里、能否产生副作用、失败后如何恢复。协议类型能帮助定位接口，不能代替威胁建模与应用侧控制。
## 完整可运行代码

下面这段代码里有一个最小的 server，它同时暴露了两类东西：一个 tools 列表，以及（在 server/discover 里）自己的能力声明。

```python
"""一个最小 MCP server（stdio + 换行分隔的 JSON-RPC 2.0）。

按 2026-07-28 那版的**无状态**形态实现：
  - 没有 initialize 握手，每个请求自己在 _meta 里带协议版本与客户端能力
  - 版本不匹配 → UnsupportedProtocolVersionError
  - server/discover 是 server 必须实现的 discovery 方法；client 可选择先调用
  - 需要补充输入时不主动发请求，而是返回 InputRequiredResult（MRTR）

它只在**形态**上照做，没有对接官方 SDK —— 所以它验证的是这个离线教学实现的路径，
不是官方实现互操作。只处理带 ID 的 request/response 示例，不实现 notifications，也不支持 legacy initialize。
`transfer_money` 仅用于展示 MRTR 的确认往返，代码不会转账；真实系统还必须在副作用入口独立鉴权、校验金额与目标并对账。实跑状态：2026-10-22，本轮离线复核。
"""
import json, math, sys

SUPPORTED_VERSIONS = ["2026-07-28"]

TOOLS = [
    {"name": "get_weather",
     "description": "查询某个城市某一天的最高气温。",
     "inputSchema": {"type": "object",
                     "properties": {"city": {"type": "string"},
                                    "day": {"type": "string", "enum": ["明天", "后天"]}},
                     "required": ["city", "day"]}},
    {"name": "transfer_money",
     "description": "给指定账户转账（不可逆）。",
     "inputSchema": {"type": "object",
                     "properties": {"to": {"type": "string"}, "amount": {"type": "number"}},
                     "required": ["to", "amount"]}},
]

TEMP = {("北京", "明天"): 31, ("上海", "明天"): 27}


def error(req_id, code, message, data=None):
    err = {"code": code, "message": message}
    if data:
        err["data"] = data
    return {"jsonrpc": "2.0", "id": req_id, "error": err}


def result(req_id, payload):
    return {"jsonrpc": "2.0", "id": req_id, "result": payload}


def handle(req):
    """处理一个请求。注意：这里是**无状态**的 —— 没有 session 对象可查。"""
    if not isinstance(req, dict):
        return error(None, -32600, "Invalid Request")
    req_id = req.get("id")
    if (req.get("jsonrpc") != "2.0" or not isinstance(req.get("method"), str)
            or not (isinstance(req_id, str) or type(req_id) is int)):
        return error(None, -32600, "Invalid Request")
    method = req.get("method")
    params = req.get("params", {})
    if not isinstance(params, dict):
        return error(req_id, -32602, "params must be an object")
    meta = params.get("_meta", {})
    if not isinstance(meta, dict):
        return error(req_id, -32602, "_meta must be an object")
    version = meta.get("io.modelcontextprotocol/protocolVersion")
    client_caps = meta.get("io.modelcontextprotocol/clientCapabilities")

    # --- 无状态化的核心：版本校验发生在**每个请求**上，而不是握手时 ---
    if not isinstance(version, str) or not isinstance(client_caps, dict):
        return error(req_id, -32602, "Missing required per-request _meta fields")
    if version not in SUPPORTED_VERSIONS:
        return error(req_id, -32022, "Unsupported protocol version",
                     {"requested": version, "supported": SUPPORTED_VERSIONS})

    if method == "server/discover":
        return result(req_id, {"resultType": "complete",
                               "supportedVersions": SUPPORTED_VERSIONS,
                               "capabilities": {"tools": {}},
                               "_meta": {"io.modelcontextprotocol/serverInfo":
                                         {"name": "demo-server", "version": "1.0.0"}}})

    if method == "tools/list":
        return result(req_id, {"resultType": "complete", "tools": TOOLS})

    if method == "tools/call":
        name = params.get("name")
        args = params.get("arguments", {})

        if not isinstance(args, dict):
            return error(req_id, -32602, "arguments must be an object")

        if name == "get_weather":
            if not isinstance(args.get("city"), str) or args.get("day") not in {"明天", "后天"}:
                return error(req_id, -32602, "invalid city or day")
            out = TEMP.get((args.get("city"), args.get("day")), {"error": "没有数据"})
            return result(req_id, {"resultType": "complete",
                                   "content": [{"type": "text", "text": json.dumps(out, ensure_ascii=False)}]})

        if name == "transfer_money":
            amount = args.get("amount")
            if (not isinstance(args.get("to"), str) or not args["to"].strip()
                    or type(amount) not in (int, float) or not math.isfinite(amount)
                    or amount <= 0):
                return error(req_id, -32602, "invalid transfer arguments")
            # MRTR：InputRequests / InputResponses 都是按服务端分配键索引的 map。
            input_responses = params.get("inputResponses", {})
            if not isinstance(input_responses, dict):
                return error(req_id, -32602, "inputResponses must be an object")
            if "confirm" not in input_responses:
                return result(req_id, {
                    "resultType": "input_required",
                    "inputRequests": {"confirm": {
                        "method": "elicitation/create",
                        "params": {"mode": "form",
                                   "message": "确认给 %s 转账 %s 元？" % (args.get("to"), args.get("amount")),
                                   "requestedSchema": {"type": "object",
                                                       "properties": {"confirmed": {"type": "boolean"}},
                                                       "required": ["confirmed"]}}}}})
            response = input_responses["confirm"]
            if not isinstance(response, dict):
                return error(req_id, -32602, "confirm response must be an object")
            content = response.get("content", {})
            if not isinstance(content, dict):
                return error(req_id, -32602, "confirm content must be an object")
            if response.get("action") != "accept" or content.get("confirmed") is not True:
                return result(req_id, {"resultType": "complete",
                                       "content": [{"type": "text", "text": "用户未确认；未执行"}]})
            return result(req_id, {"resultType": "complete",
                                   "content": [{"type": "text", "text":
                                                "模拟完成：确认已收到；本示例没有执行真实转账"}]})

        return error(req_id, -32602, "Unknown tool: %s" % name)

    return error(req_id, -32601, "Method not found: %s" % method)


def main():
    for line in sys.stdin:
        line = line.strip()
        if not line:
            continue
        try:
            req = json.loads(line)
        except Exception as e:
            print(json.dumps(error(None, -32700, "Parse error: %s" % e)), flush=True)
            continue
        print(json.dumps(handle(req), ensure_ascii=False), flush=True)


if __name__ == "__main__":
    main()
```

## 常见坑

- **把 client、传输连接和协议 session 混为一谈。** host 可按 server 分别配置 client；具体传输与 session 生命周期取决于协议版本和 transport。
- **把设计意图当成强制交互流程。** tools / resources / prompts 各有典型控制模式，但 host 的实际 UI 与模型适配方式并非由协议强制规定。
- **把 server 的能力声明当安全保证。** 它只说明接口可用，协议层无法验证实现。
- **把 resources 或 prompts 当成安全输入。** server 提供的资源与消息可能包含敏感数据或恶意内容；分别检查访问授权、信任标注、数据流和潜在副作用。
- **以为一个 server 只能提供一类能力。** 三类可以同时提供，也可以只提供其中一类。
