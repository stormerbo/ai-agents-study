第 4 章讲了工具调用。那一章里的工具都是你自己写的：函数在你手里、schema 由你定义、执行在你的进程里。

这一章要讲的是另一件事：**当工具由别人提供时，你和他之间靠什么对话。**

## N×M 问题

假设有 N 个 AI 应用（编码助手、客服机器人、数据分析工具），M 个能力提供方（GitHub、数据库、内部工单系统、Slack）。没有共享接口时，每个应用都可能要为每个提供方维护一套专用适配，最多形成 N×M 个成对集成。

MCP 统一的是**双方交换能力和调用结果的协议接口**：每个 host 接入一次 MCP client 能力，每个提供方实现一次 MCP server 适配，概念上的接口实现数从 N×M 变成 N+M。它不会自动生成业务适配器，也不会消除 host 的配置、授权、模型 API 转换或 server 对下游系统的封装。N+M 是集成边界的计数模型，不等于工程工时必然按同一比例下降。

这个模式在工程史上出现过很多次 —— 打印机驱动、数据库驱动（ODBC/JDBC）、编辑器协议（LSP）。它们的共同结构是：

**把「谁提供能力」和「谁消费能力」解耦，让双方分别实现同一套接口。**

MCP 的定位是 AI 应用与外部能力之间的协议层。它和 LSP 一样采用 JSON-RPC，但两者的生命周期并不相同：MCP 2026-07-28 路径移除了旧版 initialize 握手，LSP 仍有自己的初始化流程。类比用于理解解耦，不代表两种协议可以互换。



## 但协议能解决的问题有边界

本节要划清的是**协议边界与应用决策边界**。MCP 规定 host、client、server 如何交换上下文和能力；它本身不是完整的 agent runtime。

MCP 核心协议不会替应用决定：

- **模型如何选择工具。** host 把 server 的工具定义交给模型，模型如何选择还受提示、模型行为和应用策略影响。
- **工具如何实现、是否安全。** 协议定义调用和结果的结构；server 仍负责输入校验、访问控制、限流和输出处理，host 仍负责哪些调用获准执行。协议还规定了相关安全控制与建议，不能说它“完全不负责安全”。
- **应用级 agent 如何编排。** 模型调用循环、预算、重试和业务状态由应用负责。协议的 Tasks 等扩展能提供特定的长任务交互机制，但不会替应用定义整个 agent 工作流。
- **业务授权与副作用策略。** MCP 授权规范和安全建议是协议层机制；具体用户、租户、数据范围与动作授权仍需 host/server 结合应用落实。

这些边界决定了排查位置。工具选择不理想时，检查 host 暴露给模型的工具集、工具说明与模型策略；连接、协议版本、传输头或 JSON-RPC 报文不匹配时，检查协议和 transport；工具有未授权副作用时，检查 host/server 的授权执行路径，而不是期待协议替你决定业务规则。

可对照 [MCP 架构与规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/index) 和 [安全最佳实践](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)。

## 一个具体的判断：什么时候值得上协议

判断时看**复用对象、现有生态和边界成本**，不要只数 host 和 server：

- **工具由你写，只给一个应用使用** → 直接写本地工具通常更简单；如果你预期未来要给多个 host 复用，标准接口可能值得提前采用。
- **同一能力要被多个 host 使用，或多个 server 要接入同一 host** → MCP 能减少每一对组合都单独实现协议适配的需要，但每个 server 的业务封装、host 授权和运行配置仍要维护。
- **服务只提供 MCP 接口** → host 需要 MCP client 或兼容层；若同一服务也有 REST/SDK，需把互操作、运维和授权成本一起比较。
- **host/server 会变更** → 标准协议能降低接口耦合，但切换仍要验证工具语义、身份授权、错误处理和行为兼容，不能只改一个配置就假设等价。

一个粗略判据：当两端都可能被多个实现复用，且双方能遵循兼容的 MCP 版本和能力范围，协议的标准化收益更容易摊薄额外运维成本。单个 host 连单个 server 也可能因现成 SDK、治理要求或未来复用而值得使用；它并非天然“多余”。

## 一个具体的前后对比

把接口数量摆到一个小例子里。假设有 3 个 host（编码助手、数据分析、客服）和 4 个能力提供方（GitHub、工单、数据库、Slack）：

| 方式 | 需要维护的集成边界 | 说明 |
|---|---:|---|
| 每对系统专用对接 | 最多 3 × 4 = 12 | 每个 host-provider 组合各自处理认证、参数、错误和结果 |
| 统一为 MCP | 3 个 host 侧接入 + 4 个 server 适配 = 7 | host 按 MCP 接入；每个 provider 暴露 MCP server |

这张表只数接口边界，不声称 12 份和 7 份代码具有相同复杂度。一个 MCP client SDK 可以由多个 host 复用，但每个 host 仍须处理产品配置、授权、展示和模型 API；每个 server 仍要实现它自己的业务适配。协议减少的是成对接口的重复，不会消除业务逻辑或运行成本。若 N、M 都很小，运维和安全边界的成本可能超过接口复用收益。

## 为什么是 JSON-RPC

MCP 采用 **JSON-RPC 2.0** 表达请求、通知和响应。请求有 method、params 与 id；通知没有 id；响应携带 result 或 error。这个通用 envelope 让不同实现能围绕相同的消息结构互通。

它的工程取舍可以这样理解：

- **结构容易检查。** JSON 易于日志化和调试，但生产实现仍要正确处理版本、schema 校验、错误语义、取消和权限。stdio 下 stdout 是协议通道，日志应走 stderr。
- **协议与 transport 分层。** stdio 在进程间交换 JSON-RPC 消息；Streamable HTTP 还规定 HTTP 请求头、状态码、响应体与 SSE 行为。两种 transport 可承载同一类协议操作，但 HTTP 封装并非“只换管道”。
- **动态 schema，缺少静态类型保证。** MCP 工具定义可用 JSON Schema 描述输入与输出；运行时仍需验证，且不同 SDK 的类型映射要按版本核对。

2026-07-28 的现代 MCP 把协议版本与客户端能力放进每个请求的 `params._meta`，并移除了旧版协议级 initialize/session。这个变化不等于业务应用不能保存状态；需要跨请求状态时，应用可通过显式 handle 或扩展管理。参见[官方规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/index)。

## 协议层的历史参照

**ODBC / JDBC** 展示了数据库驱动的解耦方式：应用面向统一 API，数据库提供对应驱动。这个类比只说明接口复用，不表示 MCP 提供 SQL、事务或数据库一致性语义。

**LSP（语言服务器协议）** 则更接近 MCP 的“宿主 + 能力提供方”形态；二者都使用 JSON-RPC。生命周期仍有差异：LSP 的 initialize 流程并未因 MCP 2026-07-28 移除握手而改变，不能把某一方的版本变化套到另一方。

**协议的一般边界**是：它定义参与方如何表达与交换消息，不保证对端实现正确、结果真实或调用安全。使用协议减少了接口耦合，同时也要求你验证版本、能力、实现和权限。

## 它和函数调用的关系

最后澄清一个最容易混的地方：**MCP 与模型厂商提供的 tool calling 是不同层次的接口。** 对 tools 场景，host 把 MCP server 的工具定义映射到模型 API 的工具 schema，再把模型提出的调用转成 MCP `tools/call`。模型通常不直接发送 MCP 报文；它看到的工具名、schema 和结果由 host 按模型 API 适配。

- 工具由应用本地实现：host 直接调用本地函数。
- 工具由 MCP server 提供：host/client 通过 MCP 协议调用 server。

因此，第 4 章关于工具 schema、模型提出调用、host 执行并回填结果的基本概念仍适用；但具体 schema 映射、错误结构、内容块和结果格式由模型 API 与 MCP 版本共同决定，不能认为“一条都不用改”。增加的边界还包括协议版本、transport、server 掉线、授权以及 MRTR 的交互处理。

### 那一跳具体长什么样

先把第 4 章那两个词展开，因为后面会一直用到：

- **tool_use 块**：模型返回的结构化「我要调这个工具」请求，里面有工具名和参数 —— 注意它只有请求，没有结果。
- **tool_result 回填**：你的代码执行完，把结果按工具调用 id 包成一个 tool_result 块放回消息列表，模型下一轮才能看到。

**没有 MCP 时**，host 直接调用本地函数；**有 MCP 时**，host/client 把模型 API 的调用映射成 JSON-RPC `tools/call`。MCP 报文通常由 host/client 与 server 交换，模型不直接发送这套报文。若 server 需要 client 侧输入，现代协议会返回 `input_required`；SDK 可能自动处理，也可以交由 host 的交互层决定如何满足，再用新 JSON-RPC id 重试原请求。这是 **MRTR（多轮往返请求，Multi Round-Trip Requests）**，第 3 节展开。

下面两条报文说明 host/client 与 MCP server 的协议边界（示例数据，非真实 API 响应）。第一段是一个现代请求；JSON-RPC id 与上层模型的 tool_use id 分属不同协议，host 需要分别保存它们的关联：

```json
{"jsonrpc": "2.0", "id": 7, "method": "tools/call",
 "params": {"_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientCapabilities": {"elicitation": {}}},
            "name": "get_weather",
            "arguments": {"city": "北京", "day": "明天"}}}
```

第二段是一次完成响应。server 的 `_meta` 身份字段供诊断显示，不能作为安全凭据；host 再把 MCP 结果转换成当前模型 API 要求的 tool result：

```json
{"jsonrpc": "2.0", "id": 7,
 "result": {"resultType": "complete",
            "content": [{"type": "text", "text": "{\"北京明天\": 31}"}],
            "_meta": {"io.modelcontextprotocol/serverInfo":
                      {"name": "demo-server", "version": "1.0.0"}}}}
```

host 侧适配必须把 MCP 中间交互和模型工具结果分开。下面示例返回 Anthropic Messages 风格的 `tool_result`；其他模型 API 的字段结构需按其文档转换。假设使用第 4 节的 `Client.send`，它每次请求都会分配新的 JSON-RPC id；`collect_inputs` 由 host/SDK 按自己的交互策略实现：

```python
import json


def handle_tool_use(tool_use, client, collect_inputs, max_rounds=5):
    """仅当 MCP 调用完成后，才返回模型侧 tool_result。"""
    params = {"name": tool_use["name"], "arguments": tool_use["input"]}

    for _ in range(max_rounds):
        # Client.send 每次调用都会生成新的 JSON-RPC id。
        resp = client.send("tools/call", params)
        if "error" in resp:
            return {
                "type": "tool_result",
                "tool_use_id": tool_use["id"],
                "is_error": True,
                "content": json.dumps(resp["error"], ensure_ascii=False),
            }

        out = resp["result"]
        result_type = out.get("resultType")
        if result_type == "input_required":
            requests = out.get("inputRequests")
            if not isinstance(requests, dict) or not requests:
                raise ValueError("input_required 缺少可处理的 inputRequests")
            # 返回值按 server 分配的 request key 映射；具体是询问用户还是自动处理，
            # 由 host/SDK 决定。MRTR 自身不等于审批。
            params["inputResponses"] = collect_inputs(requests)
            if "requestState" in out:
                params["requestState"] = out["requestState"]
            continue

        if result_type != "complete":
            raise ValueError("未知 MCP resultType: %r" % result_type)

        blocks = out.get("content", [])
        if any(block.get("type") != "text" for block in blocks):
            raise NotImplementedError("本示例只映射 MCP text 内容块")
        text = "\n".join(block.get("text", "") for block in blocks)
        tool_result = {
            "type": "tool_result",
            "tool_use_id": tool_use["id"],
            "content": text or json.dumps(out.get("structuredContent", {}), ensure_ascii=False),
        }
        # MCP 的 isError 是成功 JSON-RPC 响应里的工具结果标记，与顶层协议 error 不同。
        if out.get("isError"):
            tool_result["is_error"] = True
        return tool_result

    raise RuntimeError("MRTR 超过 host 配置的最大往返次数")
```

这里有几个可检查的不变量：模型的 `tool_use_id` 要关联到最终回填；MCP 每次重试都用新 JSON-RPC id，但原始工具名和参数保持一致；`input_required` 必须留在协议交互层，只有 `complete` 才进入模型的 tool result。顶层 JSON-RPC `error` 与完成结果里的 MCP `isError` 是两种不同错误形态，host 都要映射到模型 API 支持的错误表示。上面没有演示非文本内容块，生产 host 必须按其模型 API 映射图片、音频等内容，不能静默丢弃。

## 可运行的 server 实现

本节保留一份最小 stdio server，便于直接观察 JSON-RPC。它与[第 4 节的实现](/chapters/mcp/build-a-server)保持一致；完整 client 与多条请求测试也在那里。维护时应同步两处，本项目的审计脚本会比较两份 server 代码。（本地教学 server/client 路径实跑状态：2026-10-20；本轮未做官方 SDK/provider 互操作。）

```python
"""一个最小 MCP server（stdio + 换行分隔的 JSON-RPC 2.0）。

按 2026-07-28 的**无状态**路径实现：
  - 不执行 initialize 握手；每个请求在 _meta 中带协议版本与客户端能力
  - 不支持的版本返回 JSON-RPC error code -32022
  - server/discover 与 tools/list 返回规范要求的缓存元数据
  - 需要 client 输入时返回 input_required，client 用新 request id 携带 inputResponses 与原 requestState 重试

教学实现不是官方 SDK 的兼容性认证；当前代码仅覆盖声明的无状态 stdio 工具路径。
"""
import json, math, sys

SUPPORTED_VERSIONS = ["2026-07-28"]

TOOLS = [
    {"name": "get_weather",
     "description": "查询某个城市某一天的最高气温。",
     "inputSchema": {"type": "object",
                     "properties": {"city": {"type": "string"},
                                    "day": {"type": "string", "enum": ["明天", "后天"]}},
                     "required": ["city", "day"]}},
    {"name": "transfer_money",
     "description": "演示转账确认流程；本示例不会执行真实转账。",
     "inputSchema": {"type": "object",
                     "properties": {"to": {"type": "string"}, "amount": {"type": "number"}},
                     "required": ["to", "amount"]}},
]

TEMP = {("北京", "明天"): 31, ("上海", "明天"): 27}


def error(req_id, code, message, data=None):
    err = {"code": code, "message": message}
    if data:
        err["data"] = data
    return {"jsonrpc": "2.0", "id": req_id, "error": err}


def result(req_id, payload):
    # serverInfo 放在每个成功响应 result 的 _meta 中；它用于识别/诊断，不是安全凭据。
    payload = dict(payload)
    meta = dict(payload.get("_meta", {}))
    meta["io.modelcontextprotocol/serverInfo"] = {"name": "demo-server", "version": "1.0.0"}
    payload["_meta"] = meta
    return {"jsonrpc": "2.0", "id": req_id, "result": payload}


def tool_failure(req_id, message):
    """把可供调用方修正的输入/业务错误作为 tool result 返回。"""
    return result(req_id, {"resultType": "complete", "isError": True,
                           "content": [{"type": "text", "text": message}]})


def handle(req):
    """处理一个请求。注意：这里是**无状态**的 —— 没有 session 对象可查。"""
    if not isinstance(req, dict) or req.get("jsonrpc") != "2.0" or not isinstance(req.get("method"), str):
        return error(None, -32600, "Invalid Request")
    method = req.get("method")
    req_id = req.get("id")
    if isinstance(req_id, bool) or not isinstance(req_id, (str, int)):
        return error(None, -32600, "Invalid Request id")
    params = req.get("params", {})
    if not isinstance(params, dict):
        return error(req_id, -32602, "params must be an object")
    meta = params.get("_meta", {})
    if not isinstance(meta, dict):
        return error(req_id, -32602, "params._meta must be an object")
    version = meta.get("io.modelcontextprotocol/protocolVersion")
    client_caps = meta.get("io.modelcontextprotocol/clientCapabilities")

    # --- 无状态化的核心：版本校验发生在**每个请求**上，而不是握手时 ---
    if not isinstance(version, str) or not version or not isinstance(client_caps, dict):
        return error(req_id, -32602, "Missing required per-request _meta fields")
    if version not in SUPPORTED_VERSIONS:
        return error(req_id, -32022, "Unsupported protocol version",
                     {"requested": version, "supported": SUPPORTED_VERSIONS})

    if method == "server/discover":
        return result(req_id, {"resultType": "complete",
                               "supportedVersions": SUPPORTED_VERSIONS,
                               "capabilities": {"tools": {}},
                               "ttlMs": 300000, "cacheScope": "public"})

    if method == "tools/list":
        # 缓存元数据是 ListToolsResult 的规范字段；public 表示结果不随用户身份变化。
        return result(req_id, {"resultType": "complete", "tools": TOOLS,
                               "ttlMs": 300000, "cacheScope": "public"})

    if method == "tools/call":
        name = params.get("name")
        args = params.get("arguments", {})
        if not isinstance(name, str) or not isinstance(args, dict):
            return error(req_id, -32602, "tools/call requires a string name and object arguments")

        if name == "get_weather":
            city, day = args.get("city"), args.get("day")
            if not isinstance(city, str) or not city.strip() or day not in ("明天", "后天"):
                return tool_failure(req_id, "get_weather 输入无效：city 不能为空，day 只能是明天或后天")
            out = TEMP.get((city, day))
            if out is None:
                # 业务执行失败仍是一个 tool result；用 isError 告诉调用方不要把它当成功数据。
                return result(req_id, {"resultType": "complete", "isError": True,
                                       "content": [{"type": "text", "text": "没有该城市/日期的天气数据"}]})
            return result(req_id, {"resultType": "complete", "isError": False,
                                   "content": [{"type": "text", "text": json.dumps({"temperature": out}, ensure_ascii=False)}]})

        if name == "transfer_money":
            amount, recipient = args.get("amount"), args.get("to")
            if (not isinstance(recipient, str) or not recipient.strip()
                    or isinstance(amount, bool) or not isinstance(amount, (int, float))
                    or not math.isfinite(amount) or amount <= 0):
                return tool_failure(req_id, "transfer_money 输入无效：收款方不能为空，amount 必须是正数")
            # MRTR：结果通过 InputResponses map 回来；这只是教学交互，不是真实转账授权。
            input_responses = params.get("inputResponses", {})
            if not isinstance(input_responses, dict):
                return error(req_id, -32602, "inputResponses must be an object")
            response = input_responses.get("confirm")
            expected_state = json.dumps({"to": recipient, "amount": amount},
                                        sort_keys=True, ensure_ascii=False)
            if response is None:
                return result(req_id, {
                    "resultType": "input_required",
                    "inputRequests": {"confirm": {
                        "method": "elicitation/create",
                        "params": {"mode": "form",
                                   "message": "确认给 %s 转账 %s 元？" % (args.get("to"), args.get("amount")),
                                   "requestedSchema": {"type": "object",
                                                       "properties": {"confirmed": {"type": "boolean"}},
                                                       "required": ["confirmed"]}}}},
                    "requestState": expected_state})
            # 生产系统应对有安全意义的状态做签名/MAC；这里仅演示逐字回传与绑定参数。
            if params.get("requestState") != expected_state:
                return error(req_id, -32602, "requestState missing or does not match this action")
            if response.get("action") != "accept" or not response.get("content", {}).get("confirmed"):
                return result(req_id, {"resultType": "complete",
                                       "content": [{"type": "text", "text": "用户未确认；未执行"}]})
            return result(req_id, {"resultType": "complete",
                                   "isError": False,
                                   "content": [{"type": "text", "text": "教学模拟：确认已通过；本示例未连接转账系统，不会发生真实转账（%s 元给 %s）"
                                                % (amount, recipient)}]})

        return error(req_id, -32602, "Unknown tool: %s" % name)

    return error(req_id, -32601, "Method not found: %s" % method)


def main():
    for line in sys.stdin:
        line = line.strip()
        if not line:
            continue
        try:
            req = json.loads(line)
        except Exception as e:
            print(json.dumps(error(None, -32700, "Parse error: %s" % e)), flush=True)
            continue
        print(json.dumps(handle(req), ensure_ascii=False), flush=True)


if __name__ == "__main__":
    main()
```

### 怎么把它跑起来

将这段代码存为 `mcp_server.py`。它会等待 stdin 的 JSON-RPC 请求；下面命令发一条带 2026-07-28 `_meta` 的 `tools/list` 请求：

```bash
# 一条消息一行，直接喂给 server
printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}}}}' \
  | python3 mcp_server.py
```

返回是一行 JSON。要验证完整 client/server 往返（含 MRTR 新 id 重试），运行[第 4 节的 client 示例](/chapters/mcp/build-a-server)。这份手写实现只用于学习协议形态；生产环境优先使用维护中的 SDK，并按目标版本做互操作测试。

## 常见坑

- **以为 MCP 会替模型挑工具。** 选择仍由 host 和模型完成；但 MCP 传递的工具描述、schema 和结果会影响模型所看到的内容，不能说它对模型行为“完全透明”。
- **以为协议会替应用做业务授权。** MCP 定义了一些安全控制和建议；host/server 仍须落实具体的身份、数据范围、授权与确认策略。
- **把 N×M → N+M 当作必然省工。** 先比较复用收益和 SDK、运维、授权成本；一对一场景可能适用，也可能不值得引入抽象。
- **把 MCP 和某个具体框架绑定。** 它是一个协议；第 13 章那些框架只是它的消费者或提供者之一。
- **以为手写 demo 等于生产可用实现。** JSON-RPC 易读不代表完整实现简单；版本、schema、transport、安全与 SDK 互操作都要验证。
