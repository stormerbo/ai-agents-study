当系统持续写入并召回记忆时，可能累积过期信息或出现相互矛盾的候选；发生频率取决于数据类型、写入策略与更新流程。

第 2 节讲的是如何在写入时做筛选，但后续仍可能出现信息更新、来源更正或环境变化。本节讨论如何区分同一事实的新版本、条件不同的并存事实，以及无法自动裁决的冲突候选。

## 历史实验摘要：一次小样本对照不足以证明时间戳的效果

旧记录称以相同的两条冲突陈述做了两组提示，各运行 3 次；但逐次请求、响应、提示快照、评分器与精确模型路由未归档。下面保留的是历史摘要，不是本轮复现：

| 注入方式 | 旧摘要所报的 3 次输出 | 历史摘要标签 |
|---|---|---|
| A 不带时间戳 | 中文、英文、英文 | 摘要称“不稳定” |
| B 带时间戳（英文那条是 2026-10-01，中文那条是 2026-03-01） | 英文、英文、英文 | 摘要称“取最新” |

（仅存 2026-10-08 的摘要；没有逐次请求/响应、提示快照、评分器与准确模型路由，本轮未复现。）

旧摘要报告条件 A 的 3 次输出分成两种语言。由于原始逐次轨迹与判分依据未留存，不能确认除时间戳外的输入是否一致，也不能据此判定模型能力、输出差异的原因或未来运行的随机性。缺少来源、范围、确认时间和更新关系的冲突确实没有可靠的自动裁决依据；安全策略应让它进入待处理状态，而不是把决定交给无依据的模型猜测。

旧摘要报告条件 B 的三次输出都选择了时间较新的陈述；但这组样本很小且缺少可复核材料，不能证明时间戳导致稳定，也不能推出“取最新”普遍正确。

冲突处理的前提是知道比较的是同一主体、同一范围和同一事实，并保留来源、时区明确的事件时间、确认状态及更新关系。时间戳是证据之一，不足以单独决定哪条事实为真。

## 冲突从哪来

冲突可能来自意图更新、证据错误、范围不同或环境变化；先区分“同一事实的新版本”和“两个不同条件下都成立的事实”：

**用户明确更新偏好。** 例如从“不要发邮件”改为“可以发摘要”。只有在确认是同一主体、同一范围且明确替代旧偏好的情况下，才建立 supersedes 关系；该确认必须来自有权的用户/审核者或可验证的权威流程，不能仅由模型推断生成。实现中 `supersession_confirmed` 是受信任写入路径产生的证据字段，不是信任模型传入的布尔值；缺失或为 false 时必须待审。仅凭较新时间不能证明用户想覆盖旧规则。

**写入来源和事实状态混淆。** 第 2 节的历史摘要称模型曾把带有“可能”的陈述改写为确定偏好，但逐次输出不可复核。工程上应把推断标作候选，并要求来源证据与业务授权；后续还要允许用户修正或撤回。

**环境变了。** 「目标服务器是 k8s」在两年前成立，现在迁到了别的平台。这不是矛盾，是过期 —— 处理方式是时效闸门，而不是裁决。

## 裁决顺序：先确定性规则，再交给人

遇到冲突时，按代价从低到高：

**一，先检查来源是否可比较。** 用户陈述、系统观测和模型推断表示不同证据类型，不能跨场景固定排成一个通用真值顺序。按用途定义可接受的证据；推断默认保持候选，观测也要检查采集质量、主体和时间范围。

**二，仅在同一范围、同一事实且更新关系明确时应用版本顺序。** 可比较的时区时间能提供顺序线索；并发更新、时间相同、来源强度不同或无法证明语义等价时，应保留冲突并请求确认。历史 3/3 摘要不构成该策略的验证。

**三，仍然无法判断时，停止注入并进入待处理队列。** 需要时向用户澄清；低风险场景也可按明示产品策略保留多个带时间范围的事实。这时最糟的做法是把两条一起塞给模型「让它自己看着办」—— 那等于把冲突转嫁给一个没有裁决依据的组件（无裁决依据时应保持待审状态，而不是让模型猜测）。

## 关键：在写入侧解决，而不是让矛盾长期共存

读取侧的筛选只能作为防线。写入侧应先判断候选是否与同一主体、范围和事实相关，再记录新版本或保留冲突待确认；不要默认覆盖旧值。对需要审计的产品，使用带时间范围的版本记录，并通过状态与权限闸门阻止失效记录进入召回。

版本关系字段本身也必须有可信来源：仅存一个 `supersedes_id`，若该边由模型任意生成，代码就会把模型猜测提升成裁决依据。下面的 resolver 要求关系已由信任边界之外的流程确认为 `supersession_confirmed=True`；生产 schema 还应保存确认主体、时间和证据引用。

这样做还有一个附带好处：库里的条目数不会无限增长。如果每次改口都新增一条，一年后同一个偏好会有几十个版本，召回时它们互相挤占名额（第 2 节讲去重时说过这个问题）。

## 遗忘必须是显式功能

遗忘策略需要随数据风险和用途设计。数据规模增长本身不必然降低精确率；但缺少过期过滤或删除机制可能让陈旧内容再次进入提示。误召回是否改变任务结果，应单独用有标签的任务数据评估，不能由单个历史案例外推。

显式遗忘至少要有三样东西：

- **有效期**：依数据类型与用途确定，并记录时区明确的 `valid_until` 或更新时间与 TTL。不要把“几个月/几周”当通用默认值；通过过时数据损失、确认频率和误用风险制定可检查的策略。
- **失效条件**：被新事实取代时，怎么标记它。注意是「标记」而不是「删除」，因为审计时你可能还需要知道它曾经存在过。
- **删除能力**：区分撤销召回、逻辑删除和按产品保留策略执行的物理清理。删除需要身份与范围校验、可恢复失败处理，并确保索引、缓存和下游副本遵循同一状态。具体法律义务与期限取决于产品部署地与数据类型。

## 完整可运行代码

```python
"""本地冲突门：只对同 scope/key 且明确版本关系的数据做裁决。

这是确定性规则示例，不调用模型，也不复现下方历史 provider 摘要。
实跑状态：2026-10-21，本机 Python 3.14.7 的固定 fixture 通过；不含 provider 与存储验证。"""
from datetime import datetime

MEMORIES = [
    {"id": "m1", "scope": "project:demo", "key": "reply_language",
     "source": "user_stated", "text": "所有回复用中文",
     "event_at": "2026-03-01T09:00:00+08:00", "valid_until": None,
     "status": "active", "supersedes_id": None},
    {"id": "m2", "scope": "project:demo", "key": "reply_language",
     "source": "user_stated", "text": "replies must be in English",
     "event_at": "2026-10-01T09:00:00+08:00", "valid_until": None,
     "status": "active", "supersedes_id": "m1", "supersession_confirmed": True},
]


def parse_aware(value):
    parsed = datetime.fromisoformat(value)
    if parsed.utcoffset() is None:
        raise ValueError("timestamp must include a UTC offset")
    return parsed


def resolve(records, *, scope, key, now):
    """Return a unique explicit version tip, or fail closed for review."""
    now = parse_aware(now)
    candidates = []
    for record in records:
        if record.get("scope") != scope or record.get("key") != key:
            continue
        if record.get("status") != "active":
            continue
        parse_aware(record["event_at"])
        until = record.get("valid_until")
        if until is None or now < parse_aware(until):
            candidates.append(record)

    if not candidates:
        return {"status": "none"}
    if len(candidates) == 1:
        return {"status": "resolved", "record": candidates[0]}
    ids = {record["id"] for record in candidates}
    if any(record.get("supersedes_id") in ids and record.get("supersession_confirmed") is not True
           for record in candidates):
        return {"status": "needs_review", "ids": sorted(ids)}
    if len({record.get("source") for record in candidates}) != 1:
        return {"status": "needs_review", "ids": sorted(r["id"] for r in candidates)}

    parents = [record.get("supersedes_id") for record in candidates
               if record.get("supersedes_id") in ids]
    tips = [record for record in candidates if record["id"] not in parents]
    if len(tips) != 1:
        return {"status": "needs_review", "ids": sorted(ids)}

    # Require one explicit, acyclic chain covering every candidate.
    visited = set()
    current = tips[0]
    while current is not None:
        if current["id"] in visited:
            return {"status": "needs_review", "ids": sorted(ids)}
        visited.add(current["id"])
        parent_id = current.get("supersedes_id")
        current = next((r for r in candidates if r["id"] == parent_id), None)
    if visited != ids:
        return {"status": "needs_review", "ids": sorted(ids)}
    return {"status": "resolved", "record": tips[0]}


if __name__ == "__main__":
    args = {"scope": "project:demo", "key": "reply_language",
            "now": "2026-10-21T00:00:00+08:00"}
    print("有明确版本链:", resolve(MEMORIES, **args)["record"]["id"])
    ambiguous = [dict(record, supersedes_id=None) for record in MEMORIES]
    print("没有版本链:", resolve(ambiguous, **args)["status"])
```

```text
有明确版本链: m2
没有版本链: needs_review
```

### 删除能力：接口形态与行为约定

用户发起删除时，需要先阻止该内容继续被读取，再清理搜索索引和其他副本。跨数据库与向量索引通常不是单个原子事务；以下是状态机接口草图，不是可直接部署的实现：

```python
# delete_memory_protocol.py
"""接口草图：权威存储、outbox 与检索索引由应用实现。"""

def request_deletion(tx, principal, scope, memory_id, now):
    """在权威库事务中先写 tombstone，再排队清理；失败可重试。"""
    with tx.atomic():
        tx.authorize(principal, scope, memory_id)
        targets = tx.deletion_targets(memory_id, scope)  # 按产品策略含关联版本
        for record in targets:
            if record["scope"] != scope:
                raise PermissionError("scope mismatch")
            revision = record["revision"] + 1
            tx.tombstone_and_clear_payload(record["id"], revision=revision, at=now)
            tx.enqueue_outbox({"kind": "purge_memory", "id": record["id"],
                               "scope": scope, "revision": revision})
    return {"status": "deletion_pending", "count": len(targets)}


def apply_purge_event(store, index, event):
    """幂等清理；索引更新必须使用 revision 防止旧 upsert 复活数据。"""
    record = store.get(event["id"], scope=event["scope"])
    if record is None or record["revision"] != event["revision"]:
        return "stale_event"
    if record["status"] != "deletion_pending":
        return "already_handled"
    index.remove(event["id"], if_revision_at_most=event["revision"])
    store.mark_deleted(event["id"], revision=event["revision"])
    return "deleted_from_primary_and_index"


# 检索命中后、注入前仍需向权威库校验 status/scope/revision；
# 删除期间的 tombstone 必须使其不可注入，即使索引清理尚未完成。
```

（**上述接口草图未实跑，且不覆盖副本、缓存、备份和法律保留策略。**）核心顺序是先在权威库事务中使记录不可读并写 outbox，再异步清理索引；召回路径必须以权威状态为准，不能只依赖索引删除。若异步步骤失败，告警与重试应持续工作；对需要物理清除的场景，还要枚举所有副本和保留介质并验证清理结果。

删除与失效的区别，一张表说清：

| | 触发者 | 记录怎么处理 | 还能不能审计 | 用户能查到它存在过吗 |
|---|---|---|---|---|
| **版本失效**（superseded） | 确认新版本替代旧值 | 旧版本按产品策略保留；召回过滤掉旧版本 | 视保留策略而定 | 不应作为当前值注入 |
| **用户删除**（deletion requested） | 经过授权的删除请求 | 先 tombstone 并阻止读取，再按策略清理主库、索引与副本 | 仅保留明确允许的最少审计元数据 | 删除状态对用户可见；原始内容不可召回 |

区分版本失效与用户删除，既能保留必要的版本关系，也能避免把“软删除标记”误当成所有副本都已清理。

## 怎么检测出矛盾

「检测到矛盾就覆盖」说起来简单，但**发现两条记忆矛盾**本身是个独立问题，而且是这里最容易被低估的一步。

可以按结构化程度逐步处理：

**一，显式主题与事实键。** 相同 scope/key 下出现多个值时进入待审队列。这不需要关键词检索，但依赖可靠的写入映射，结构化错误同样会误判。

**二，同一规范键下的值冲突。** 如果写入时能可靠抽取 `scope + subject + predicate`，就能在相同事实键上发现不同值；映射错误会漏报或误报。嵌入相似度可以帮助找候选，但“语义相近”不代表互相矛盾，必须再检查极性、对象、时间范围与业务含义。

**三，跨记录约束冲突。** 例如禁止任何邮件与要求定时发送邮件摘要相冲突。可以用产品规则、约束求解或模型产生冲突候选；模型输出需由用户确认或确定性策略验证。没有统一的“只能靠模型”实现。

起步时可以先依赖结构化的 `scope`、主题和事实键，把同键多值送入待裁决队列。这能使队列逻辑可测试，但覆盖率取决于提取与映射质量；它不会自动发现多数真实冲突。

## 第一层检测：主题枚举表

主题表是产品 schema 与队列策略的示例（**构造数据，未实跑**）；这些阈值不表示语义矛盾，也不是推荐的通用容量：

| 主题（枚举值） | 示例值 | 待审阈值（示例） | 发现多条后的默认动作 |
|---|---|---:|---|
| `reply_language` | `user_stated` | 1 | 待确认；不得仅因超阈值自动覆盖 |
| `output_format` | `user_stated` | 3 | 待确认；多项偏好可能同时成立 |
| `tech_stack` | `user_stated` | 5 | 先按项目与技术子类分 scope/key |
| `deploy_env` | `observed` / `user_stated` | 1 | 核对环境范围和观测时间 |
| `user_role` | `user_stated` | 2 | 核对主体与时间范围 |
| `project_state` | `user_stated` | 3 | 结合明确有效期与项目范围 |

这里的阈值只是用来演示“队列容量/审查触发器”的构造数据，不是由主题逻辑推导出的正确条目上限，也不应直接用于生产。是否冲突还要看主体、项目、时间范围、来源和字段；同一主题里可能有多条合法偏好。超阈值时示例代码只打上待审标记。

```python
# topic_gate.py
"""按显式 scope/topic 字段统计待审候选，不做文本语义判断。
实跑状态：2026-10-21，本机 Python 3.14.7 的固定 fixture 通过；阈值为构造值。"""
from datetime import datetime, timezone

REVIEW_LIMITS = {
    "reply_language": 1,
    "output_format": 3,
    "tech_stack": 5,
    "deploy_env": 1,
    "user_role": 2,
    "project_state": 3,
}


def classify(records):
    groups = {}
    for record in records:
        if record.get("status") != "active":
            continue
        scope, topic = record.get("scope"), record.get("topic")
        if not scope or topic not in REVIEW_LIMITS:
            continue
        groups.setdefault((scope, topic), []).append(record)

    pending = []
    for (scope, topic), items in groups.items():
        limit = REVIEW_LIMITS[topic]
        if len(items) > limit:
            pending.append({"scope": scope, "topic": topic,
                            "ids": [r["id"] for r in items],
                            "count_over_limit": len(items) - limit})
    return groups, pending


def mark_pending(records, pending, now=None):
    now = now or datetime.now(timezone.utc).isoformat(timespec="seconds")
    pending_keys = {(group["scope"], memory_id)
                    for group in pending for memory_id in group["ids"]}
    for record in records:
        key = (record.get("scope"), record.get("id"))
        if key in pending_keys:
            record["pending_review"] = now
            record["pending_reason"] = "review threshold exceeded"
        else:
            record.pop("pending_review", None)
            record.pop("pending_reason", None)
    return records


if __name__ == "__main__":
    records = [
        {"id": "m1", "scope": "project:demo", "topic": "reply_language",
         "text": "用户要求回复使用中文。", "status": "active"},
        {"id": "m2", "scope": "project:demo", "topic": "reply_language",
         "text": "用户要求 replies must be in English.", "status": "active"},
        {"id": "m3", "scope": "project:demo", "topic": "output_format",
         "text": "用户偏好表格输出。", "status": "active"},
    ]
    _, pending = classify(records)
    mark_pending(records, pending, now="2026-10-21T00:00:00+00:00")
    print("待审组:", pending)
    print("标记后:", [(r["id"], bool(r.get("pending_review"))) for r in records])
```

```text
待审组: [{'scope': 'project:demo', 'topic': 'reply_language', 'ids': ['m1', 'm2'], 'count_over_limit': 1}]
标记后: [('m1', True), ('m2', True), ('m3', False)]
```

该示例只按显式主题字段和人为设定的 active 数量上限生成待审队列，不理解文本语义，也不验证两条事实是否真的互斥。每个产品需定义 scope、主题分类、候选状态和冲突操作；即使某主题配置上限为 1，也不要据此自动覆盖用户陈述。

## 有效期如何设定

没有适用于所有产品的固定 TTL。把数据变化频率、误用后果、再次确认成本和用户撤销方式一起纳入策略；对高风险或易变事实，过期后先阻止注入并要求刷新。

| 信息类别 | 过期/复核策略（需按产品验证） | 到期后的默认安全行为 |
|---|---|---|
| 回复风格偏好 | 用户可随时修改；定期提示确认是否仍有效 | 保留为低风险偏好，或按产品策略到期 |
| 技术栈、部署环境 | 绑定项目与环境，并在部署变更时刷新 | 未确认前不用于高影响操作 |
| 当前项目状态、进行中的任务 | 绑定明确任务状态与 `valid_until` | 过期即不注入，要求重新确认 |
| 模型推断候选 | 除非得到来源核实和授权，否则保持候选 | 不作为用户确认事实注入 |

模型推断与用户确认事实应使用不同状态和来源标记。TTL 只能约束时间，不能补足来源真实性或用户授权；产品若允许推断参与决策，应把它保留为明确标记的低置信度候选，并按风险设定独立策略。
## 本节小结

1. **历史冲突对照只有摘要** —— 3 次输出不能证明时间戳的因果效果；生产裁决需依赖明确的 scope、事实键、证据和版本关系。
2. **只有适用条件满足时才自动解析**：显式版本链可确定当前版本；同键多值、来源不匹配或关系不清时进入待审队列。
3. **写入侧避免无依据覆盖**：记录明确的替代关系或保留冲突待确认，并在召回时排除 pending 与失效记录。
4. **过期、失效与用户删除是不同操作**：明确状态、scope、召回过滤、索引清理与失败重试；有效期策略需按业务验证。
5. **每一个机制都要能回答「它改善了哪个指标」** —— 这是下一节的主题。没有这个答案，你无法判断该不该给它加预算。
## 冲突与遗忘的三种失败形态

以下是需要由不变式与指标发现的失败形态；是否静默取决于具体实现：

**一，待审队列可能被错误注入。** 如果召回查询没有过滤 `pending_review`，冲突值可能被一起注入；**怎么发现**：监控待审数量、队列等待时间、待审记录被召回/注入次数及拒绝率。数量增长也可能是流量增长，必须与吞吐量和 SLA 一起看。**所以怎么做**：按风险定义队列服务目标；达到时限后停止自动注入待审事实，按产品策略降级或请求用户确认。不要把特定 24 小时数字当通用门槛。

**二，版本链断开或跨 scope。** 错误的 `supersedes_id` 可能指向不存在、范围不一致或已删除的数据，导致无法还原更新关系。**怎么发现**：加一个不变式检查 —— 每条 `status=superseded` 的记录必须指向同一 scope 内、版本关系合法且可审计的替代记录；替代记录未必永远是 active，允许形成经过校验的版本链。**所以怎么做**：把版本链完整性与 scope 一致性写入校验，并覆盖删除/过期后的引用更新。

**三，索引残留让已 tombstone 的记录再次命中。** 如果召回后没有查权威状态，旧向量可能导致被删除内容继续影响候选。**怎么发现**：删除后立刻用被删除的原文当查询跑一次检索，断言结果里不含这个 id。**所以怎么做**：集成测试分别验证 tombstone 立即阻断注入、索引清理可重试、过期 revision 不会删错新数据；跨库操作不应假设可整体回滚。

用不变式、指标、告警与可重试流程共同检查；各项检查应对应明确的存储与召回边界。

## 常见坑

- **把小样本历史摘要当因果结论。** 旧输出摘要不能证明缺少时间戳导致不稳定；未裁决的冲突应在可确认前阻止自动注入。
- **只用更新时间裁决。** 更新时间能排序事件，不能证明同一范围、事实或用户意图；版本关系和来源边界也要保存。
- **要求模型给无来源冲突选边。** 模型可以生成解释或待确认的问题，但不能代替用户意图、来源质量或产品策略。
- **把新值直接覆盖旧值。** 保留版本或显式标注 supersession，避免丢掉审计所需的时间与更新关系。
- **假设状态标记自动删除了所有副本。** 召回侧需要强制过滤，异步副本还要有幂等清理和失败监控。
- **把软删除等同于用户删除完成。** 只改主表状态不足以证明缓存、索引、备份和其他副本已清理。
