记忆库用久了，一定会出现两种东西：**过期的**和**互相矛盾的**。

第 2 节讲的是怎么在写入时做减法，但减法解决不了全部问题 —— 用户就是会改口，环境就是会变。所以这一节处理的是：当库里已经躺着两条互相矛盾的事实，系统该怎么办。

## 实测：同一份冲突输入，加不加时间戳差别很大

构造两条直接冲突的记忆，内容不变，只改注入方式，各跑 3 次：

| 注入方式 | 3 次结果 | 稳定性 |
|---|---|---|
| A 不带时间戳 | 中文、英文、英文 | ❌ 不稳定 |
| B 带时间戳（英文那条是 2026-10-01，中文那条是 2026-03-01） | 英文、英文、英文 | ✅ 稳定遵循「取最新」 |

（实跑数据，2026-10-08，`deepseek-flash`。脚本见本节末尾。）

条件 A 的结果值得多看一会儿：**同一份输入、同一个模型，三次跑出了两种不同的语言。** 而这不是「模型能力不行」—— 是因为这份输入里**根本没有可以用来裁决的信息**。两条记忆都自称是「用户偏好」，没有任何一条能说明自己更新。模型只能任选一条，于是每次选择都可能不同。

条件 B 只多做了一件事：给每条记忆带上时间戳。结果立刻稳定下来，3/3 都选了更新的那条。

**所以冲突本身不可怕，不可裁决才可怕。** 而「可裁决」的前提条件，就是在写入那一刻把时间戳和来源记下来 —— 这也是第 2 节那三条标准里第三条的实际用途。

## 冲突从哪来

三种来源，处理方式不同：

**用户真的改口了。** 「不要给我发邮件」→「可以发」。这是最正当的冲突，答案是取最新。

**写入时混进了推断。** 第 2 节的实测里，模型把「我可能对价格比较敏感吧」整理成了「用户对价格较敏感」。如果后来又观测到一次相反的信号，库里就有两条相互矛盾的「事实」，而其中一条本来就不该存在。**这类冲突的根源在写入侧，不在裁决侧。**

**环境变了。** 「目标服务器是 k8s」在两年前成立，现在迁到了别的平台。这不是矛盾，是过期 —— 处理方式是时效闸门，而不是裁决。

## 裁决顺序：先确定性规则，再交给人

遇到冲突时，按代价从低到高：

**一，按来源等级。** 用户明说 > 系统观测 > 模型推断。这条能解决大部分由推断混入导致的冲突 —— 而且它是纯规则，不需要模型参与。

**二，同来源等级时取最新。** 这是上面条件 B 验证过的做法，实测 3/3 稳定。

**三，仍然无法判断时，交给人。** 比如两条都是用户明说、时间也很接近、内容直接互斥。这时最糟的做法是把两条一起塞给模型「让它自己看着办」—— 那等于把冲突转嫁给一个没有裁决依据的组件（条件 A 的结果已经演示了会发生什么）。

## 关键：在写入侧解决，而不是让矛盾长期共存

上面那套裁决是**读取时**的兜底。更好的做法是让冲突根本不存在：**检测到矛盾就在写入侧处理掉** —— 新记忆覆盖旧记忆，或者在旧记忆上标记失效，而不是让两条并存。

这样做还有一个附带好处：库里的条目数不会无限增长。如果每次改口都新增一条，一年后同一个偏好会有几十个版本，召回时它们互相挤占名额（第 2 节讲去重时说过这个问题）。

## 遗忘必须是显式功能

「遗忘」听起来像一个可以推迟的问题，但它的成本是随时间单调上升的：库越大，召回越容易捞到过时信息；噪声越多，精确率越低；而**每一次错误召回都会污染模型的判断**（第 3 节实测过）。

显式遗忘至少要有三样东西：

- **TTL**：这条记忆什么时候该失效。按类型不同 —— 偏好可以是几个月，环境配置可能几周。
- **失效条件**：被新事实取代时，怎么标记它。注意是「标记」而不是「删除」，因为审计时你可能还需要知道它曾经存在过。
- **删除能力**：用户要求删除时能真的删干净。这既是合规要求，也是调试时的救命手段 —— 没有它，你连「把某条可疑记忆拿掉再试一次」都做不到。

## 完整可运行代码

```python
"""冲突裁决：两条互相矛盾的记忆，怎么决定用哪条。

前半段是确定性规则（不需要网络），后半段用模型验证规则是否真的生效。

实跑状态：2026-10-08，deepseek-flash，已跑通。
"""

import json
import os
import urllib.request

# 两条冲突的记忆，都带来源与时间戳 —— 没有这两样，下面的裁决一步都做不了
MEMORIES = [
    {"id": "m1", "text": "用户偏好：所有回复必须用中文。", "at": "2026-03-01"},
    {"id": "m2", "text": "用户偏好：replies must be in English.", "at": "2026-10-01"},
]
INJECTION_ORDER = ["m1", "m2"]        # 注入顺序也固定，避免它成为变量


def render(mems, with_time):
    """把记忆拼成注入文本。with_time 决定要不要带时间戳。"""
    parts = []
    for m in mems:
        parts.append(("[%s] " % m["at"] if with_time else "") + m["text"])
    return "\n".join(parts)


def resolve(mems):
    """确定性裁决：同级来源时取时间最新的那条。"""
    return sorted(mems, key=lambda m: m["at"], reverse=True)[0]


def ask(system, user, max_tokens=1200):
    body = json.dumps({"model": os.environ.get("VERIFY_MODEL", "claude-haiku-4-5"),
                       "max_tokens": max_tokens, "system": system,
                       "messages": [{"role": "user", "content": user}]}).encode()
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages", data=body,
        headers={"content-type": "application/json",
                 "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
                 "anthropic-version": "2023-06-01"})
    with urllib.request.urlopen(req, timeout=180) as resp:
        data = json.loads(resp.read())
    return "".join(b["text"] for b in data["content"] if b["type"] == "text")


def language_of(text):
    return "中文" if any("一" <= c <= "鿿" for c in text) else "英文"


if __name__ == "__main__":
    print("确定性规则给出的答案：%s（最新的一条）" % resolve(MEMORIES)["text"])
    print()
    if not os.environ.get("ANTHROPIC_AUTH_TOKEN"):
        print("（未配置凭据，跳过模型部分）")
        raise SystemExit
    for label, with_time in [("不带时间戳", False), ("带时间戳", True)]:
        langs = []
        for _ in range(3):
            text = ask(render(MEMORIES, with_time), "用一句话介绍你自己，不要解释。")
            langs.append(language_of(text))
        print("%s：3 次结果是 %s" % (label, "、".join(langs)))
```

实跑输出（2026-10-08）：

```text
确定性规则给出的答案：用户偏好：replies must be in English.（最新的一条）

不带时间戳：3 次结果是 中文、英文、英文
带时间戳：3 次结果是 英文、英文、英文
```

### 删除能力：接口形态与行为约定

「用户要求删除时能真的删干净」是一句要求，落到代码上是一个函数和三条约定：

```python
# delete_memory.py
"""删除：标记失效 → 物理删除 → 确保索引里也不留。"""


def delete_memory(store, memory_id, hard=False):
    """硬删除（合规请求）与软删除（正常遗忘）走同一个入口，但结果不同。

    约定：
      1. 先删索引，再删表 —— 顺序反了会出现「库里没有、检索还能召回」
      2. 软删除只把 status 置为 deleted，text 清空（下游不该再注入它的内容）
      3. 硬删除必须先检查 superseded_by 链，把指向它的记录一起处理
    """
    rec = store.get(memory_id)
    if rec is None:
        return {"ok": False, "reason": "not_found"}

    # 第 1 步：索引先删。这一步失败就不要继续动表——留下孤儿索引比报错更糟
    store.index.remove(memory_id)

    if not hard:
        rec["status"] = "deleted"
        rec["text"] = ""              # 软删除也要让内容不可见
        rec["deleted_at"] = now_iso()
        return {"ok": True, "mode": "soft", "affected": 1}

    # 第 2 步：硬删除前先处理引用链
    affected = 1
    for other in store.all():
        if other.get("superseded_by") == memory_id:
            other["superseded_by"] = rec.get("superseded_by")  # 链尾接链头
            affected += 1
    store.table.delete(memory_id)
    return {"ok": True, "mode": "hard", "affected": affected}


def now_iso():
    from datetime import datetime, timezone, timedelta
    return datetime.now(timezone(timedelta(hours=8))).isoformat(timespec="seconds")
```

（**上述删除实现是示例：构造数据，未实跑。**）三条约定里最反直觉的是第一条：**先删索引再删表** —— 反过来做的话，任何一次中途报错都会留下一份「数据库里查不到、但检索还能召回」的索引，而它造成的后果正是用户最不能接受的那一种。

删除与失效的区别，一张表说清：

| | 触发者 | 记录怎么处理 | 还能不能审计 | 用户能查到它存在过吗 |
|---|---|---|---|---|
| **失效**（superseded） | 系统检测到冲突 | 保留，`status=superseded`，`text` 保留 | 能 | 能（这是正确的） |
| **删除**（deleted） | 用户请求 / 合规 | 软删：`status=deleted` 且 `text` 清空；硬删：物理移除 | 只剩删除日志 | 不能 |

The distinction matters because conflating them means either losing audit trails unnecessarily or keeping data that users have explicitly requested to be removed.

## 怎么检测出矛盾

「检测到矛盾就覆盖」说起来简单，但**发现两条记忆矛盾**本身是个独立问题，而且是这里最容易被低估的一步。

三个层次的检测，代价递增：

**一，同主题关键词命中。** 「回复语言」「输出格式」这类偏好可以归类，同类里出现多条就送去人工检查。成本低，但只能覆盖你事先想到过的类别。

**二，语义相似但结论互斥。** 两条记忆说的是同一件事，取值却相反。这需要语义判断 —— 纯词法在这里没用（第 6 章的实测结论），得靠嵌入或模型。**嵌入**在这里指的是把每条记忆过一个嵌入模型、得到定长向量（第 6 章第 3 节给了最小实现），然后比两条向量的余弦相似度：**相似度高但取值不同**，就是这一层要抓的信号；而**语义相似**（semantic similarity）就是「两条文本的向量方向接近、余弦值高」，它和「字面用词相同」是两回事 —— 中文里「回复用中文」和「别跟我说英文」字面几乎不重合，语义却很近。

**三，跨记忆的逻辑冲突。** 例如「不要给我发邮件」与「每天发一封汇总邮件」。两条各自看都没问题，放在一起才冲突。这一层基本只能靠模型通读一遍，成本最高。

务实的做法是**先做第一层**：把记忆按主题分类（语言偏好、输出格式、技术栈、部署环境……），同类内出现多条就标记为待裁决。它能覆盖多数真实冲突，而且完全可预测、可测试。

## 第一层检测：主题枚举表

「把记忆按主题分类」这句话要能用，就得有一份**枚举表**。下面是起步版本（**示例：构造数据，未实跑**）：

| 主题（枚举值） | 判定关键词 | 已有条目上限 | 同主题多条怎么处理 |
|---|---|---:|---|
| `reply_language` | 中文/英文/语言/用……回复 | 1 | 取 `updated_at` 最新的，旧的标 `superseded` |
| `output_format` | 表格/列表/JSON/Markdown/不要寒暄 | 3 | 通常是可叠加的，超过上限才裁决 |
| `tech_stack` | PostgreSQL/MySQL/k8s/Docker/框架名 | 5 | 同一技术类目内互斥（数据库、运行时各一条） |
| `deploy_env` | 部署/服务器/集群/环境 | 1 | 互斥，取最新 |
| `user_role` | 我是……/职位/团队规模 | 2 | 通常稳定，超过 2 条视为描述漂移 |
| `project_state` | 当前项目/进行中/这个季度 | 3 | 强时效，配合 `ttl_days` 一起用 |

**上限那一列怎么定，是这张表的全部价值。** 它的判据只有一句话：**这个主题里，两条不同的值能不能同时成立？** 回复语言不能（互斥，上限 1）；输出格式能（可叠加，上限放宽）；技术栈是半互斥的（数据库与运行时各一条，所以上限 5 而不是 1）。选错上限的后果是可预测的：定成 1，你会丢掉合法的叠加偏好；定成 5，你会让两条互斥的语言偏好长期并存。

```python
# topic_gate.py
"""第一层冲突检测：同主题第二条第几条 → 标记待裁决。

自包含：纯本地逻辑。实跑状态：本机 Python 3.10 实跑（2026-10-12）。"""

from datetime import datetime, timezone, timedelta

CN = timezone(timedelta(hours=8))

# 主题 → (判定关键词, 上限)
TOPICS = {
    "reply_language": (("中文", "英文", "语言"), 1),
    "output_format": (("表格", "列表", "JSON", "寒暄"), 3),
    "tech_stack": (("PostgreSQL", "MySQL", "k8s", "Docker"), 5),
    "deploy_env": (("部署", "服务器", "集群"), 1),
}


def topic_of(text):
    for topic, (keywords, _) in TOPICS.items():
        if any(k.lower() in text.lower() for k in keywords):
            return topic
    return None


def classify(records):
    """把 active 记录按主题分组，标出超限的组。"""
    groups = {}
    for r in records:
        if r["status"] != "active":
            continue
        topic = topic_of(r["text"])
        if topic is None:
            continue
        groups.setdefault(topic, []).append(r)

    pending = []
    for topic, items in groups.items():
        limit = TOPICS[topic][1]
        if len(items) > limit:
            # 超过上限 → 全部标为待裁决，交规则或人处理
            pending.append((topic, [r["id"] for r in items], len(items) - limit))
    return groups, pending


def mark_pending(records, pending, now=None):
    """标记待裁决：不改 status，只加一个显式字段。"""
    now = now or datetime.now(CN).isoformat(timespec="seconds")
    ids = {mid for _, mids, _ in pending for mid in mids}
    for r in records:
        if r["id"] in ids:
            r["pending_review"] = now
            r["pending_reason"] = "同主题多条，超过上限"
    return records


if __name__ == "__main__":
    records = [
        {"id": "m1", "text": "用户要求回复使用中文。", "status": "active"},
        {"id": "m2", "text": "用户要求 replies must be in English.", "status": "active"},
        {"id": "m3", "text": "用户偏好表格输出。", "status": "active"},
    ]
    groups, pending = classify(records)
    print("分组:", {k: [r["id"] for r in v] for k, v in groups.items()})
    print("待裁决:", pending)
    mark_pending(records, pending)
    print("标记后:", [(r["id"], r.get("pending_reason", "-")) for r in records])
```

```text
分组: {'reply_language': ['m1', 'm2'], 'output_format': ['m3']}
待裁决: [('reply_language', ['m1', 'm2'], 1)]
标记后: [('m1', '同主题多条，超过上限'), ('m2', '同主题多条，超过上限'), ('m3', '-')]
```

注意它**只标记、不自动裁决**。语言偏好这种互斥主题，两条都带时间戳时「取最新」是对的（本节实测 3/3 稳定）；但如果你把这条规则套到「用户同时喜欢表格和 JSON」上，就会无缘无故删掉一条合法偏好 —— 所以自动裁决只对上限为 1 的主题开，其余全部走人工。

## TTL 该设多长

TTL 的设置标准是**这条信息的自然变化周期**，而不是「希望它多准」：

| 记忆类型 | 建议 TTL | 理由 |
|---|---|---|
| 回复语言 / 输出格式偏好 | 半年以上 | 变化极慢，而且用户会主动纠正 |
| 技术栈、部署环境 | 1 到 3 个月 | 会随项目迁移变化，但不频繁 |
| 当前项目状态、进行中的任务 | 数天 | 任务结束就失效 |
| 模型推断出来的条目 | 不设 TTL，直接不注入 | 见第 2 节：它不该作为事实存在 |

最后一行值得单独说：给推断类条目设 TTL 是一种自我安慰。它们的问题不是「会过期」，而是「本来就不该被当作事实」。正确做法是让它们永远不进入注入队列 —— 第 3 节的来源闸门就是干这个的。
## 本节小结

1. **冲突不可怕，不可裁决才可怕** —— 实测：无时间戳时同一份输入 3 次跑出 2 种答案；加上时间戳后 3/3 稳定。
2. **裁决顺序**：来源等级 → 时间新旧 → 交给人。前两步都是确定性规则，只有第三步需要人。
3. **根治在写入侧**：检测到矛盾就覆盖或标记失效，不要让两条长期共存。
4. **遗忘是显式功能**，要有 TTL、失效标记与删除能力 —— 缺任何一个，事故发生时你都没有干预手段。
5. **每一个机制都要能回答「它改善了哪个指标」** —— 这是下一节的主题。没有这个答案，你无法判断该不该给它加预算。
## 冲突与遗忘的三种失败形态

上面每一步都会以特定方式坏掉，而且这三种坏法都不会报错：

**一，未裁决的冲突堆成队列（静默降级成「两条并存」）。** 最像成功的一种失败：`pending_review` 的记录一直在库里、一直在被召回，而两条互斥的值同时进入上下文 —— 模型又回到了本节开头条件 A 的状态（3 次跑出 2 种答案）。**怎么发现**：把 `pending_review` 的条数做成一个看板数字，它单调上升就说明裁决没人在做。**所以怎么做**：给待裁决队列设一个服务级目标（比如 24 小时内清空），清不掉就必须降级 —— 把该主题整体排除出注入队列，而不是让它继续参与召回。

**二，`superseded_by` 链写歪，审计断掉。** 如果只在新记录上写指针、旧记录不写，或链尾不接链头，回查时你会看到一条没有取代者的孤儿记录。**怎么发现**：加一个不变式检查 —— 每条 `status=superseded` 的记录必须同时满足「`superseded_by` 非空」且「目标记录存在且为 active」。**所以怎么做**：把这个不变式写成断言，在写入后跑一遍；它很便宜，却能挡住绝大多数手写排序留下的错误。

**三，删了表但没删索引（用户仍然被召回删除的内容）。** 这是三种里最严重的，因为它直接违反用户的合规请求，而且从表面完全看不出来。**怎么发现**：删除后立刻用被删除的原文当查询跑一次检索，断言结果里不含这个 id。**所以怎么做**：把这条断言放进删除流程本身（上面 `delete_memory` 的第一步就是在做这件事），并让硬删除失败时整体回滚。

三种失败形态有一个共同点：**它们都不产生报错**，只产生一个看起来正常的系统。所以对付它们的办法也不是更仔细，而是**不变式 + 断言** —— 把「应该成立的事」写成可以随时执行的检查。

## 常见坑

- **让矛盾的记忆长期共存。** 实测里这会直接导致行为不稳定：同一份输入 3 次跑出 2 种答案。
- **不记时间戳。** 没有它，「取最新」这个最简单的规则都无法执行 —— 而它是绝大多数冲突的正确解。
- **把冲突塞给模型裁决。** 两条地位相同、都无时间戳的断言，模型没有依据可选，它只能任选。
- **只做读取时的裁决，不做写入时的覆盖。** 前者是兜底，后者才是根治；只做前者会让库无限膨胀。
- **把「遗忘」当成以后再说的事。** 不遗忘的成本随时间单调上升，而且每一次错误召回都是静默的。
- **只有删除、没有失效标记。** 审计时你会需要知道某条记忆曾经存在过。
