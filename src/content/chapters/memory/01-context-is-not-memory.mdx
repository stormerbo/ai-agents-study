「那就把历史都留着。」

这句话在讨论记忆方案时几乎一定会出现。它听起来像是某种保守的默认值 —— 反正现在的上下文窗口很大，留着总比丢了强。

这个想法值得认真测一遍，而不是靠「窗口会满」这种说法直接否定。因为如果你去测，会发现**窗口比你以为的大得多**。

## 实测一：窗口到底有多大

用重复的英文词做填充（一个词约等于一个 token，便于控制输入量），逐档往上推：

| 填充词数 | HTTP 状态 | 实际输入 token | 耗时 |
|---:|---|---:|---:|
| 300,000 | 200 | 390,038 | 5.0 s |
| 500,000 | 200 | 650,038 | 7.9 s |
| 800,000 | 200 | **1,040,038** | 13.1 s |

（历史实测记录，2026-10-08：请求使用 `deepseek-flash`，`https://api.deepseek.com/anthropic` 的 Anthropic Messages 兼容接口；800,000 个 ASCII 填充词对应的输入用量按 `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` 求和，记录值为 1,040,038。原始逐次响应未归档，因此保留为当日端点观测，不视为可独立复算的原始证据。它不证明其他模型、其他 API 形态或当前配置都接受该长度，也不定义模型上下文上限。DeepSeek 当前官方模型目录列出 DeepSeek-V4.1-Flash / DeepSeek-V4-Pro 的上下文长度为 1M；见[官方模型与价格表](https://api-docs.deepseek.com/quick_start/pricing/)。实际可用输入还受模型版本、输出预算、请求协议和服务端限制影响。）

当日这条请求返回成功，只能说明该模型标识、端点、请求形态和当时服务配置接受了这一次约 104 万输入 token 的请求。实验没有继续探测上限，也没有完整归档逐次响应，**不能据此推出上下文窗口至少有 1,040,038 token，更不能推广到其他模型或当前服务**。截至本文核对日，DeepSeek 官方目录列出的 V4.1-Flash / V4-Pro 上下文长度为 1M；官方限额是当前模型说明，历史兼容别名的行为仍应以实际路由与响应为准。

这仍然不能支持「历史应该全部留在上下文里」。对任何单次调用而言，上下文只是该次交给模型处理的输入视图；容量是一个需按模型和接口核实的约束，而不是记忆设计的全部问题。

## 实测二：海捞针，而且是在十三万 token 的草堆里

容量够，那会不会是「装进去了但找不到」？这是另一个常见的说法：内容一多，中间的东西就容易被忽略。

我做了个大海捞针测试：在约 10 万个填充词（实测约 13 万 token）里埋一句唯一的备注，问模型那串验证码是什么。埋点分别放在整段材料的开头、正中、结尾：

| 针的位置 | 是否找到 | 实际输入 |
|---|---|---:|
| 开头 10% | ✅ | 130,074 token |
| 正中 50% | ✅ | 130,074 token |
| 结尾 90% | ✅ | 130,074 token |

（实跑数据，2026-10-08。三次回答都精确输出了那串字符。）

**3/3 全中，位置没有影响。**

这条结果还有一个额外价值：第 3 章曾经在 2.2 万 token 的规模上没能复现位置效应。这次把它推到了 **13 万 token**，仍然没有复现。也就是说，那个否定结论的适用范围比原来宽得多 —— 至少在这个模型、这类文本上，「中间位置被忽略」不是主要矛盾。

## 所以真正的理由是什么

这条有限范围的单次输入观测既不能证明容量不是问题，也不能代表注意力检索能力。那「上下文不是记忆」到底成立在哪？下一组实验转而比较一种无状态 API 客户端每轮重发历史时的累计输入量。

## 实测三：它的账是按轮滚的

上一节那个约 104 万 token 的请求只发生**一次**。在无状态 messages API 的常见客户端模式下，若应用保留对话历史并在下一轮重发，历史会随轮次增长；托管会话 API 则可能由服务端维护状态，需按接口合约确认。本节后面的实测只代表当时采用的重发模式。

我跑了一段 12 轮的对话，每轮新增约 740 token 的材料，记录每一轮的输入：

| 轮次 | 本轮输入 | 累计输入 |
|---:|---:|---:|
| 1 | 743 | 743 |
| 3 | 2,220 | 4,444 |
| 6 | 4,441 | 15,544 |
| 9 | 6,675 | 33,333 |
| 12 | 8,907 | **57,822** |

（实跑数据，2026-10-08。）

末轮的请求记录为 8,907 输入 token，而**十二轮累计处理了 57,822 —— 是「每段内容只处理一次」的 6.5 倍**。这里比较的是输入用量字段之和，不等同于所有厂商的账单成本；缓存命中可能改变价格，且各 API 对 usage 字段的定义不同。

在“不使用外部记忆、每轮重发全部历史”的假设下，累计输入量会随轮次增长。下面是用相同每轮新增量外推的示意，不含 provider 的缓存折扣，也不是另一组 API 实测：

| 对话轮次 | 历史留在上下文 | 外部记忆（每轮注入 300 token） | 比值 |
|---:|---:|---:|---:|
| 12 | 63,720 | 9,600 | 6.6x |
| 24 | 234,000 | 19,200 | 12.2x |
| 50 | 968,500 | 40,000 | **24.2x** |

**在这个输入量模型里，同样一批内容采用每轮重发会重复计入输入；按需取回只计入每轮召回的片段。** 这比较的是输入 token 规模，不包括模型缓存折扣、记忆写入/存储成本或检索基础设施成本。

这给出一个具体工程取舍：在无状态 API 的重发模式中，全量历史使累计输入随轮次增长；外部记忆按需召回可以降低传入模型的文本量，但会引入检索、写入和存储成本。实际账单还取决于 provider 的缓存计费规则，不能仅凭输入 token 总数判断。

## 记忆系统还需要哪些语义

容量与注意力、状态生命周期都可通过具体产品/API 测量或查文档。本节关注的是系统设计需要明确的语义：

**第二，上下文本身不等于跨调用持久化。** 对一次调用来说，上下文是该次提交给模型的输入；如果应用下一次仍要提供历史，就必须从某处取得并重新组织它。但这不代表所有产品都会在请求结束时删除状态：应用可以把 messages 持久化，供应商也可能提供会话/响应状态接口。具体生命周期取决于应用和 API 合约，应该查对应文档。新建空 messages 数组只是无状态消息接口的一种调用方式，不是上下文的固有属性。

**第三，许多消息接口把本次输入表示为一个有序序列，但序列可否编辑由宿主决定。** 应用可以删改自己的存储记录、摘要或下一次发送的消息；某些供应商托管会话接口可能只允许追加或受特定操作约束。因而「上下文只能追加」不是普遍规律。真正缺失的是自动的长期记忆语义：哪条事实应写入、如何被检索、何时过期，以及新旧冲突如何裁决，都需要应用或服务明确实现。

所以「上下文不是记忆」应理解为**单次模型输入本身不自动构成记忆系统**，而不是声称上下文必然易失或不可编辑。设计时先查清所用产品/API 的状态模型，再决定要不要另建持久化、检索、更新和冲突裁决层。

## 那「压缩历史」算不算记忆

不算，但值得说清楚它差在哪。

压缩历史解决的是**同一份内容太长**的问题：把 20 轮对话缩成 5 段摘要。它通常仍是下一次调用输入的一部分，因此仍需要应用决定何时保存、何时重发以及如何修订摘要；是否跨会话保留取决于宿主的状态管理。压缩不会自动提供逐条事实的来源、有效期与冲突裁决。

第 3 章实测过压缩的代价：一次性任务里，摘要的 token（2272）反而比原文（1952）更多；而且摘要丢掉了「不要动生产库」这条硬约束，模型在无指令时把「摘要里没写」当成了「不允许」。

所以压缩的定位是**上下文内部的减负手段**，它和记忆是两个不同层的工具：

- 压缩回答「这一轮的上下文里放多少」
- 记忆回答「哪些东西要跨会话存在，以及怎么取回来」

判断标准也不同：压缩看的是省了多少 token、丢了什么；记忆看的是写入规则、召回准确率与冲突裁决。
## 外部记忆那一列是怎么来的

上面那张对比表里，外部记忆每轮注入 300 token —— 这个数不是拍出来的，它是「按需取回」的实现决定的。先补上那个实现，对比才从数字变成可跑的东西。

**关键的一步是「谁决定注入哪几条」**：不是把库里所有记忆都塞进去，而是每轮拿当前问题去检索，只取回最相关的 k 条。下面这段是自包含的最小版本（词典当库、字符重合当检索分数 —— 真实系统把 `recall()` 换成向量或 BM25 即可）：

```python
# on_demand_recall.py
"""按需取回：存 N 条，每轮按 query 取 k 条，拼进 system。

纯标准库、可独立运行。实跑状态：控制流在本地 Python 3.10 上跑通；
注入条数是示例（构造数据，未实跑），真实 k 由你的上下文预算决定。
"""

STORE = {
    "语言": "用户要求回复使用中文。",
    "格式": "用户偏好表格形式的输出。",
    "技术栈": "团队使用 PostgreSQL，不要 MySQL 方案。",
    "部署": "部署环境是 k8s，走 kubectl。",
    "历史": "上次会话处理过订单 A-1001 的退款。",
}


def recall(query, k=3):
    """检索：命中的字越多分越高。真实系统用 BM25 或向量（第 6 章）。"""
    ranked = sorted(STORE, key=lambda key: len(set(query) & set(key)), reverse=True)
    return ranked[:k]


def build_system(base_prompt, query, k=3):
    """把取回的记忆拼进 system 段：放前面是为了保住前缀稳定。"""
    mem = "\n".join("[%s] %s" % (key, STORE[key]) for key in recall(query, k))
    return base_prompt + "\n\n已知的长期偏好与事实：\n" + (mem or "（无）")


if __name__ == "__main__":
    for query in ["帮我写一段部署脚本", "我想要什么样的输出格式"]:
        text = build_system("你是一个助手。", query)
        print("问题:", query)
        print(text)
        print("system 段字符数:", len(text), "（token 数按你的模型换算）")
        print()
```

两个细节决定了那 300 token 的量级：**k 取 3**（每条几十 token，加上标题与分隔符大约 300），以及**将稳定规则和变化内容分开放置** —— 在支持相应前缀缓存的 API 上，变化内容放到静态前缀之后通常更利于复用；是否命中和成本变化要看具体 provider 的缓存契约及 usage。

## 完整可运行代码

这段代码把上面那条曲线算出来，并对比「历史留在上下文」与「外部记忆」两笔账。纯本地计算，不需要任何凭据。

先交代代码里那个 `system=500`：system prompt 是请求中承载角色设定、规则等指令的部分，是否每轮重发、是否被缓存取决于客户端与所用 API。此处为便于本地估算，假设它每轮都发送、每轮按 500 token 计；这个数是估算值，不是实测，也没有计入任何 provider cache discount（脚本末尾有说明）。

```python
"""上下文 ≠ 记忆：把「历史留在上下文里」的账算清楚。

纯本地计算，不需要网络。它复现的是正文里那组 12 轮实测的形状。

实跑状态：2026-10-08，已跑通。
"""


def history_cost(turns, per_turn, system=500):
    """每轮都把完整历史重发一遍时，累计输入 token。"""
    total = 0
    rows = []
    for t in range(1, turns + 1):
        # 第 t 轮要发：system + 前 t-1 轮的全部内容 + 本轮新内容
        sent = system + (t - 1) * per_turn + per_turn
        total += sent
        rows.append((t, sent, total))
    return rows


def memory_cost(turns, retrieved_per_turn, system=500):
    """换成外部记忆：历史不重发，每轮只取回相关的那几条。"""
    return turns * (system + retrieved_per_turn)


if __name__ == "__main__":
    TURNS, PER_TURN = 12, 740          # 与实测一致：每轮新增约 740 token
    rows = history_cost(TURNS, PER_TURN)
    print("%4s %10s %10s" % ("轮次", "本轮输入", "累计输入"))
    for t, sent, total in rows:
        print("%4d %10d %10d" % (t, sent, total))
    last, total = rows[-1][1], rows[-1][2]
    print()
    print("末轮输入 %d，累计输入 %d —— 是「只发一次」的 %.1f 倍" % (last, total, total / last))
    mem = memory_cost(TURNS, retrieved_per_turn=300)
    print("同样 12 轮，改成外部记忆（每轮只注入 300 token）：累计 %d" % mem)
    print("省下 %.0f%%，而且轮次再多也是线性增长" % ((1 - mem / total) * 100))
    print()
    print("把轮次拉长看曲线：")
    for n in (12, 24, 50):
        h = history_cost(n, PER_TURN)[-1][2]
        m = memory_cost(n, 300)
        print("  %2d 轮：历史留在上下文 %7d   外部记忆 %6d   比值 %.1fx" % (n, h, m, h / m))
```

## 常见坑

- **把一次长输入的成功当作上下文容量通用结论。** 104 万 token 只是一条日期、端点和模型标识均有限定的历史观测；容量应查当前模型/API 文档并在目标端点实测。真正的记忆设计还需要处理持久化、选择性写入、检索与冲突裁决。
- **把历史全留着当默认方案。** 在本节的无状态重发输入量模型中，12 轮约为每段内容只处理一次的 6.5 倍，50 轮约 24 倍；缓存计费和外部记忆的检索/存储成本另算。
- **以为「压缩历史」等于「有了记忆」。** 压缩只是把同一份内容写短一点；它不会自动提供事实级写入、来源、有效期与冲突裁决，持久化行为由宿主决定。
- **把特定消息 API 的状态限制当成上下文的固有属性。** 应先核对所用应用/API 能否保存、修改或重放状态，再设计跨调用记忆。
- **把一组海捞针结果当作长上下文注意力的普遍结论。** 本次 13 万 token 样本中 3/3 命中，只能说明该模型、该任务与这三次运行未复现位置效应，不能消除其他场景的注意力风险。
