记忆读写都要花钱，而它到底改善了哪个指标 —— 这件事必须能被说清楚，否则你无法判断该不该继续投入。

## 成本的四笔账

一个记忆系统的成本可以拆成四块，而它们的量级差别很大：

| 成本项 | 什么时候发生 | 量级 |
|---|---|---|
| **写入** | 每次「提取记忆」的模型调用，要读一遍当前上下文 | 中 |
| **存储** | 条目落库 | 几乎可忽略 |
| **召回** | 每轮一次检索（本地索引近乎免费） | 低 |
| **注入** | 每轮都要把注入的内容重发一遍 | **高** |

最后一项是主要成本，也是最容易被低估的 —— 因为它在直觉上「只是几条偏好而已」。而第 1 节那张表已经说明：**留在上下文里的内容是按轮计费的。**

用 20 轮对话、每条记忆 40 token 算一笔账：

| 常驻注入条数 | 注入成本 | 写入成本 | 合计 |
|---:|---:|---:|---:|
| 0（不用记忆） | 0 | 8,300 | 8,300 |
| 3 | 2,400 | 8,300 | 10,820 |
| 10 | 8,000 | 8,300 | 16,700 |
| 30 | 24,000 | 8,300 | 33,500 |

（模型计算，2026-10-08，脚本见本节末尾。写入成本按「每轮 0.2 次提取调用」估算。）

两个观察。**第一，写入成本是固定的** —— 它与注入多少条无关，因为它取决于对话本身有多长。所以「少记一点」不会让写入变便宜。

**第二，注入从 3 条涨到 10 条，注入成本涨了 3.3 倍**，而你能多拿到的有效信息往往远不到 3 倍 —— 因为多数记忆在多数轮次里根本用不上（第 3 节的分级判断就是这个意思）。

## 它改善了哪个指标

成本能算清楚之后，下一个问题才是关键：**这些钱买到了什么？**

常见的三个候选指标，按可信度排序：

**一，跨会话任务的完成率。** 「上次没做完的任务，这次接着做」这类场景的成功率。它最直接对应记忆的价值，代价是需要构造跨会话的评测（要等，或者模拟）。

**二，需要重复澄清的次数。** 用户第二次解释同一件事的频率。它便宜、可测，而且下降通常意味着记忆真的生效了。

**三，用户纠正「你记错了」的频率。** 它是**唯一的负向指标**，而且极其重要 —— 第 3 节实测过，误召回会静默改变输出。这个指标是少数能捕捉到它的信号。

要警惕的是**活动指标**：召回了多少次、库里有几条记忆、命中率多少。这些是活动量，不是效果。一个召回得很频繁的系统，完全可能只是在频繁地把无关信息塞进上下文 —— 实测里那条 Python 2.7 的记忆就是被「正确召回」的。

## 怎么判断值不值得

把它还原成一个可回答的问题：**关掉记忆，上面三个指标会变差多少？**

这个对照很便宜：同一批任务，一次带记忆一次不带。如果指标没有明显差异，那这套系统的成本就是净支出。注意这和检索那章的「完美检索上界」是同一个方法 —— **先测上界，再决定要不要投入。**

## 跨会话评测怎么构造

「跨会话任务完成率」听起来要等很久才能测，其实可以构造。做法是**把多次会话模拟成一次批处理** —— 这里说的**批处理**就是「一口气把多组任务的多次会话跑完」，不去做真正的持久化进程重启：每组的两段会话在内存里是**两个互不相干的 messages 数组**，跑完即弃。它和真实跨会话只差一件事（进程生命周期），而那一件事与记忆效果无关。

1. 准备一组任务，每个任务拆成 2 到 3 次「会话」（每次是一段独立的 messages 数组）
2. 第一次会话结束时，走正常的写入流程把记忆落库
3. 第二次会话**开一个全新的 messages 数组**（关键：不能复用上一次的上下文），注入召回的记忆，再问后续问题
4. 判断这次会话能不能完成任务

关键在于第 3 步必须真的清空上下文。如果偷懒复用了上一次的 messages，你测的就不是记忆，而是长上下文 —— 而且这个错误会让结果「看起来更好」，所以很容易被放过。

这个评测集不需要很大。十几组任务就足以回答「加记忆前后有没有差别」，而那正是你要回答的问题。真正难的是**构造出「没有记忆就一定做不成」的任务** —— 如果任务本身在单次会话里就能完成，记忆的收益会被完全淹没在噪声里。

## 评测集：15 组任务长什么样

先把它具体化。「跨会话」不是让你等一天，而是**同一批任务拆成两次独立会话**（**示例：构造数据，未实跑**）：

| 组 | 会话 1（建立上下文） | 会话 2（检验记忆） | 期望完成标志 |
|---:|---|---|---|
| 01 | 我们团队用 PostgreSQL，别给 MySQL 方案 | 帮我写个查询用户表的 SQL | 答案含 PostgreSQL 方言 |
| 02 | 输出一律用表格 | 列出这三个方案的区别 | 输出为表格 |
| 03 | 部署环境是 k8s | 写一段上线脚本 | 用 kubectl / manifest |
| 04 | 我在做订单退款模块 | 这个模块的边界条件有哪些 | 提到订单与退款 |
| 05 | 不要给我发邮件提醒 | 定一个提醒方案 | 不含邮件 |
| … | … | … | … |
| 15 | 上次那单 A-1001 还没结 | 帮我看看要不要催 | 引用 A-1001 |

**先剔除「单会话也能完成」的组。** 判据是：把会话 2 的问题单独发给模型、不给任何背景，**它能不能靠常识答对**。能，这组就没有测量价值 —— 它的收益会被噪声淹没。上面第 02 组（表格）和第 03 组（k8s）是这类的高危项：模型很可能凭默认行为蒙对。剔除后剩下的大约是**必须依赖会话 1 那些事实**的 8 到 10 组。

## `eval_memory.py`：可运行的评测骨架

```python
# eval_memory.py
"""跨会话记忆评测骨架：会话1 写入 → 断言上下文已清空 → 会话2 注入 → 判分。

自包含：不依赖网络。下面 respond/judge 是测试替身（stub），
把它们换成真实模型调用即可；控制的流程一字不用改。

实跑状态：控制流在本机 Python 3.10 上跑通（2026-10-12）。
下面的完成率数字来自测试替身，不是模型实测。"""

import re

TASKS = [
    {"id": "01", "s1": "我们团队用 PostgreSQL，别给 MySQL 方案",
     "s2": "帮我写个查询用户表的 SQL", "expect_any": ("postgres", "postgresql")},
    {"id": "02", "s1": "输出一律用表格",
     "s2": "列出这三个方案的区别", "expect_any": ("|", "表格")},
    {"id": "03", "s1": "部署环境是 k8s",
     "s2": "写一段上线脚本", "expect_any": ("kubectl", "k8s")},
]


def new_session():
    """一次会话 = 一个全新的 messages 数组。"""
    return []


def respond(question, ctx, memory_on):
    """一次模型调用。测试替身：memory_on=False 时返回通用答案，否则跟随 ctx。

    ★ 换成真实调用时，这一处改成 client.messages.create(...)，
      其余代码（清空断言、判分、统计）完全不动。"""
    if not memory_on:
        return "SELECT * FROM users;"
    return "SELECT * FROM users;  /* PostgreSQL 方言 */" if "PostgreSQL" in ctx else "SELECT * FROM users;"


def write_memory(session1_messages):
    """会话 1 结束时提取记忆。真实系统在这里调模型 + should_write。"""
    return " ".join(m["content"] for m in session1_messages)


def retrieve(memory_text, question, k=3):
    """召回：按需取回相关记忆。这里是朴素实现，真实系统用第 6 章那套。"""
    return memory_text


def judge(answer, task):
    """规则判分：只看期望关键词有没有出现，不给部分分。"""
    return any(k.lower() in answer.lower() for k in task["expect_any"])


def run_one(task, memory_on):
    """跑一组：两次会话，中间必须清空。"""
    # 会话 1：建立上下文、写入记忆
    ctx1 = new_session()
    ctx1.append({"role": "user", "content": task["s1"]})
    memory = write_memory(ctx1)

    # ★ 防呆：会话 2 必须是全新的数组。复用 ctx1 会让结果「看起来更好」，
    #   而那是长上下文的效果，不是记忆的效果。
    assert not new_session(), "新会话必须是空的"
    ctx2 = new_session()
    assert ctx2 is not ctx1, "不能复用会话 1 的上下文"

    # 会话 2：只注入召回的记忆
    if memory_on:
        ctx2.append({"role": "user", "content": "已知：" + retrieve(memory, task["s2"])})
    ctx2.append({"role": "user", "content": task["s2"]})
    answer = respond(task["s2"], ctx2[-2]["content"] if memory_on else "", memory_on)

    return {"id": task["id"], "done": judge(answer, task), "memory": memory_on,
            "clarified": 0, "misremembered": 0}


def report(rows):
    for flag in (False, True):
        subset = [r for r in rows if r["memory"] is flag]
        if not subset:
            continue
        done = sum(r["done"] for r in subset)
        print("记忆%-4s 完成率 %d/%d = %.0f%%   重复澄清 %d 次   记错 %d 次" % (
            "开" if flag else "关", done, len(subset), 100 * done / len(subset),
            sum(r["clarified"] for r in subset), sum(r["misremembered"] for r in subset)))


if __name__ == "__main__":
    rows = []
    for task in TASKS:
        rows.append(run_one(task, memory_on=False))
        rows.append(run_one(task, memory_on=True))
    report(rows)
```

```text
记忆关    完成率 0/3 = 0%   重复澄清 0 次   记错 0 次
记忆开    完成率 1/3 = 33%   重复澄清 0 次   记错 0 次
```

（上表是**测试替身**的输出，不是模型实测 —— 它证明的是骨架能跑、断言会拦，不是记忆真的把完成率从 0 提到 33%。那两个数字完全由 `respond()` 这个替身决定：替身只在上下文里出现 `PostgreSQL` 时才给出对的答案，另外两组任务照旧返回通用答案。换成真实模型调用之后，这两个数字才有意义。）

骨架里有三处刻意设计，每一处都对应前面某一节的失败：

1. **`assert ctx2 is not ctx1`**：防线设在「上下文没清空」这个最容易偷懒、且结果恰好更好的地方。
2. **判分是规则，不是模型**：关键词命中即可，能给出确定答案。要用模型判分也可以，但必须先用一批人工标好的样本验一遍它 —— 否则你测的是两个模型的嘴，不是一个记忆系统。
3. **三列指标一次算完**：完成率、重复澄清、记错。只报完成率会漏掉误召回（第 3 节：它是静默的）。

真实跑一次花多少：**成本 = 任务数 × 会话数 × 单次调用的 token**。15 组、每组 2 次会话、每次约 1,000 输入 token，乘上你端点的单价即可估算；耗时以每次调用几秒记，总时长在分钟级。**这两个数随你的任务长度与模型走，不要从别处抄。**

## 对照与显著性：多大的差异才算数

「关掉记忆的对照」要落地，必须先定义**重复澄清**与**记错**怎么计：

- **重复澄清**：会话 2 里模型问「你用什么数据库？」这类**会话 1 已经给过答案**的问题。计数方式是规则匹配那几条已知事实的词，人工抽检校准。
- **记错**：注入了记忆，但模型用它用反了（比如把 PostgreSQL 写成 MySQL）。它是**唯一的负向指标**，必须单独列。

至于差异多大算显著，用与第 6 章同一套粗糙口径：**15 组配对任务的完成率，标准误约 ±13 个百分点**（`sqrt(0.5×0.5/15)`）。所以：

- 完成率从 3/15 提到 12/15（20% → 80%）**值得看**，它远超噪声；
- 从 12/15 到 13/15（80% → 87%）**不能下结论**，必须扩样本；
- 两组必须跑**同一批任务**（配对），不能一批容易题配一批难题。

**「关掉记忆」的对照结果表**（示意表 —— 示例：构造数据，未实跑；真实数字要你自己跑）：

| 条件 | 完成率 | 重复澄清次数 | 记错次数 |
|---|---:|---:|---:|
| 关记忆 | ?/15 | 高（用户要重述） | 0（没有记忆，不会记错） |
| 开记忆 | ?/15 | 应显著下降 | **这里是重点**：不为 0 就说明门槛太松 |

注意「关记忆」那一列的记错次数**天然是 0** —— 这不是它的优点，恰恰说明这一列只有在开记忆时才有信息量。

## 渐进上线的观测表

前面那三步每一步看哪个数字、什么阈值算过关（阈值是**建议起点**，示例值，不是实测）：

| 阶段 | 这一阶段看什么 | 阈值（建议起点） | 没达标的动作 |
|---|---|---|---|
| 一，只写不读 | 库里 `model_inferred` 占比 | < 10% | 收紧写入侧 `should_write()`，不让推断进库 |
| 二，只注入来源可靠 + 稳定的 | 「用户纠正你记错了」频率 | ≈ 0 | 门槛回退到只留 `user_stated`，条数降到 2 |
| 三，加入按需取回 | 跨会话完成率、重复澄清次数 | 关闭记忆时明显更差 | 说明「条件相关」那批没被召回，检查召回闸门 |

**每一阶段的退出条件都是可观测的**，这正是分步的价值：一次全开时，你无法判断出问题的是写入、召回还是注入。

## 渐进上线的路径

记忆系统不该一次全开。可行的路径是分三步：

**第一步，只写不读。** 正常提取并存储，但不注入任何内容。这一阶段收集真实数据：库里会长出什么、有多少推断类条目混进来。成本只有写入那一项。

**第二步，只注入来源可靠且稳定的条目。** 也就是第 3 节那两道确定性闸门（来源 + 时效），条数控制在 2 到 3 条。观察「用户纠正你记错了」的频率 —— 它应该接近零；如果明显大于零，说明召回门槛还是太松。

**第三步，加入按需取回。** 把条件相关的记忆做成工具，让模型自己查。这一步才真正需要检索能力（第 6 章），而收益也最大。

这样分步的价值在于：**每一步的失败半径都很小**，而且每一步都有明确的观测指标。反过来，一次全开的系统在出问题时，你无法判断是写入、召回还是注入的环节出了错。
## 完整可运行代码

```python
"""记忆系统的成本模型：四笔账，以及每一笔有多大。

纯本地计算。它回答的是一个很具体的问题：
「给对话加上记忆」这件事，钱到底花在哪一项上。

实跑状态：2026-10-08，已跑通。
"""


def cost(turns, memories, inject_per_turn, retrieve_per_turn=1,
         write_calls_per_turn=0.2, tokens_per_memory=40, system=500,
         summary_tokens=150):
    """返回四项成本（单位：token）。

    write_calls_per_turn：平均每轮触发多少次「提取记忆」的模型调用。
                       会话结束时一次性提取则相当于很小的值。
    """
    # 1) 写入：每次提取调用都要读一遍当前上下文
    write = sum(int((system + t * summary_tokens) * write_calls_per_turn)
                for t in range(1, turns + 1))
    # 2) 存储：通常可直接忽略，这里只列出量级
    store = memories * tokens_per_memory
    # 3) 召回：每轮一次检索（本地索引则近乎免费）
    retrieve = 0
    # 4) 注入：这是主要成本 —— 每轮都要重发注入进去的内容
    inject = turns * inject_per_turn * tokens_per_memory
    return {"写入": write, "存储": store, "召回": retrieve, "注入": inject}


if __name__ == "__main__":
    TURNS = 20
    print("20 轮对话、每条记忆 40 token：")
    print("%-14s %10s %10s %10s" % ("常驻注入条数", "注入成本", "写入成本", "合计"))
    for keep in (0, 3, 10, 30):
        c = cost(TURNS, memories=keep, inject_per_turn=keep)
        print("%-14d %10d %10d %10d" % (keep, c["注入"], c["写入"], sum(c.values())))
    print()
    base = sum(cost(TURNS, memories=0, inject_per_turn=0).values())
    print("不注入记忆时的基线（只有写入成本）：%d token" % base)
    c3 = sum(cost(TURNS, memories=3, inject_per_turn=3).values())
    c10 = sum(cost(TURNS, memories=10, inject_per_turn=10).values())
    print("注入 3 条：%d token（是基线的 %.1f 倍）" % (c3, c3 / base))
    print("注入 10 条：%d token（是基线的 %.1f 倍）" % (c10, c10 / base))
    print()
    print("注意 3 条到 10 条：注入成本涨了 3.3 倍，而你能多拿到的信息往往远不到 3 倍。")
```

## 这一章的收束

把五节连起来，其实是一条从「不值得做」到「什么情况下值得做」的判断链：

1. 不要把「窗口会满」当理由 —— 实测一百零四万 token 都没报错，真正的理由是计费方式、跨会话、不可修改（第 1 节）。
2. 写不写，按三条标准判断，并且记住来源（第 2 节）。
3. 取不取，靠来源与时效这两道确定性闸门，相关度交给检索能力（第 3 节）。
4. 冲突靠时间戳与来源裁决，并且根治在写入侧（第 4 节）。
5. 最后用「关掉它会差多少」来验证这一切值不值（本节）。

## 本节小结

1. **四笔账里只有「注入」随记忆条数增长** —— 优化要冲着它去；写入成本由对话长度决定，省不掉。
2. **用效果指标，不用活动指标** —— 召回次数与库容量都不能说明问题。
3. **唯一的负向指标是「用户纠正你记错了」**，它也是少数能捕捉静默误召回的信号。
4. **判断值不值得的方法只有一个**：关掉记忆，看那三个指标会不会变差。这个对照不需要评测集，跑两次就能回答 —— 它是本章唯一一个「不用信我、你自己就能验」的结论。

这条判断方法和其他几章是一致的：第 6 章用「完美检索」测上界，第 3 章用子智能体做对照，本节用「关掉记忆」。**共同点是先量化收益、再决定投入** —— 而不是先建好一个系统，再想办法证明它有用。
## 常见坑

- **只看总成本，不拆项。** 四笔账里只有「注入」随记忆条数增长，优化要冲着它去。
- **按活动指标评估。** 召回次数、库容量、命中率都不是效果 —— 实测里那条把部署流程带偏的记忆，是被「正确召回」的。
- **不做「关掉记忆」的对照。** 那是最便宜也最有说服力的验证：同一批任务跑两次。
- **只统计正向指标。** 「用户纠正你记错了」的频率是唯一的负向指标，漏掉它等于对静默失败完全无感。
- **以为少记一点就能省钱。** 写入成本由对话长度决定，与记忆条数无关 —— 能省的是注入。
- **在没测过之前就上向量库与重排。** 先把来源、时效两道规则闸门做扎实，它们不需要任何模型能力，却能拦掉大部分危险条目。
