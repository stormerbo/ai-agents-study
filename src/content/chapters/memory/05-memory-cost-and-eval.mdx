记忆读写都要花钱，而它到底改善了哪个指标 —— 这件事必须能被说清楚，否则你无法判断该不该继续投入。

## 成本的四笔账

「成本」先要分清计量单位。一次记忆流程可能同时产生：**模型调用成本**（输入/输出 token、缓存读写、调用次数）、**存储成本**（记录与索引占用、保留时间）、**检索基础设施成本**（数据库/向量检索/重排）和**工程运营成本**（监控、人工复核、删除与故障处理）。这些项目不能直接用 token 相加；要么分别报告，要么按当前供应商与部署的单价换算成同一货币，再计算总账。

下面只建一个**模型输入 token 算术模型**：写入阶段反复读取上下文会产生输入 token；注入到后续请求的记忆也会重复计入输入。存储与检索没有被这个模型计价，不能据此说它们“几乎可忽略”或“免费”。模型是否缓存、上下文如何压缩、何时提取、输出 token 和价格都要单独按部署测量。

以 20 轮、每条记忆约 40 token、每轮都注入固定数量为例。写入假设为每轮以 0.2 次的平均频率处理一份从 1 轮累积到当轮的上下文（500 token 固定提示 + 每轮 150 token）：

| 常驻注入条数 | 写入输入 token | 注入输入 token | 模型输入 token 合计 |
|---:|---:|---:|---:|
| 0（不注入） | 8,300 | 0 | 8,300 |
| 3 | 8,300 | 2,400 | 10,700 |
| 10 | 8,300 | 8,000 | 16,300 |
| 30 | 8,300 | 24,000 | 32,300 |

这是公式输出，不是供应商账单或当前 API 的实测。表格的“合计”只加写入与注入的模型输入 token，不含存储、检索、输出 token、缓存折扣或人工运营。注入条目越多，注入 token 按此假设线性增长；写入值只有在对话长度、摘要策略、提取频率和缓存条件固定时才不变。若改成会话结束才提取、增量摘要或写入前筛选，写入成本也会变化。存储快照条数不能当成每轮 token 费用。

在这个构造例子里，3 条增加到 10 条使注入输入从 2,400 增至 8,000，约 3.3 倍；这只能说明 token 负载的算术关系，不能证明收益随之低于三倍。收益需要单独通过任务结果测量。

## 它改善了哪个指标

成本算式不能替代效果评测。先把产品目标写成任务级结果，再定义可观察指标，例如：跨会话任务完成率、需要用户重复提供已知信息的比例、事实/偏好被错误采用的比例，以及用户纠正率。它们各自覆盖不同失败：用户可能没有注意到静默错误，也可能选择不纠正；所以纠正率不是唯一负向指标。对高影响场景，应抽样复核最终回答与实际副作用，记录漏用和误用，并给关键错误单独设门槛。

召回次数、库容量、命中率属于活动或诊断指标，可帮助排查系统行为，但不能单独证明任务收益。某条记忆在检索器看来“命中”并不表示它相关、正确、获准使用或改善了答案。指标应有明确分母、任务机会、判定规则与观察窗口；比如只在会话 2 确实有机会使用已存事实的样本里计算误用率，避免拿不同任务构成的百分比直接比较。

## 跨会话评测怎么构造

离线批处理可以模拟会话边界，但它不自动等价于真实跨会话部署。最少要分别验证两件事：**任务/提示是否隔离**，以及**记忆是否通过真实持久化路径写入、读取和授权**。若只用两个独立的 `messages` 数组，测到的是“给定一段记忆文本后的答案差异”；它没有覆盖进程重启、存储故障、用户/租户隔离、过期、删除或并发更新。记忆即使来自用户，也不能因此升级为系统级指令；注入时需保留来源与 scope，把记录当作不可信数据处理，并测试恶意文本、越权内容和跨用户泄漏。

可以先用内存 fixture 做低成本的行为测试，再用部署集成测试确认持久层和权限边界。一个可解释的离线配对流程是：

1. 先写出任务目标、事实来源和人工评分标准；准备覆盖记忆有用、记忆无关、过期/冲突、误召回有害等场景的任务。
2. 每个任务只执行一次写入流程并冻结同一份候选记忆。条件组共享任务与模型配置；控制组不提供这份记忆。避免两组在不同时间各自重新提取而引入额外变量。
3. 每次答案请求都创建全新的对话上下文；条件组只注入通过策略检查且被检索到的记录。把输出、条件、任务 ID、记忆版本、模型/提示快照与评分依据关联保存，并按数据政策控制日志内容。
4. 预先定义评分规则与失败严重度；尽可能盲化人工评分，抽样复核自动判分。记录每个任务的两种条件结果，而不只保存汇总百分比。
5. 对模型随机性可重复运行每个条件，并将同一任务的多次运行视为任务内重复，而不是把每次调用都当独立任务。随机化条件顺序，减少时间、缓存或状态带来的偏差；代码里的固定 seed 只为复现实例，真实实验应生成并记录本轮 seed 与逐题顺序。

关键在第 3 步真的隔离对话上下文，但任务集、记忆写入、模型配置、顺序与评分也会影响结果。离线模拟适合验证流程和判据，不足以单独证明真实产品收益。

## 任务表：构造样例长什么样

先把它具体化。「跨会话」不是让你等一天，而是**同一批任务拆成两次独立会话**（**示例：构造数据，未实跑**）：

| 组 | 会话 1（建立上下文） | 会话 2（检验记忆） | 期望完成标志 |
|---:|---|---|---|
| 01 | 我们团队用 PostgreSQL，别给 MySQL 方案 | 帮我写个查询用户表的 SQL | 答案含 PostgreSQL 方言 |
| 02 | 输出一律用表格 | 列出这三个方案的区别 | 输出为表格 |
| 03 | 部署环境是 k8s | 写一段上线脚本 | 用 kubectl / manifest |
| 04 | 我在做订单退款模块 | 这个模块的边界条件有哪些 | 提到订单与退款 |
| 05 | 不要给我发邮件提醒 | 定一个提醒方案 | 不含邮件 |
| … | … | … | … |
| 15 | 上次那单 A-1001 还没结 | 帮我看看要不要催 | 引用 A-1001 |

任务数没有适用于所有记忆系统的固定答案。先用小型、分层的 pilot 检查题目、记忆策略和评分器是否工作；是否扩样应由目标人群覆盖、任务间差异、预期最小收益、错误代价与所需不确定性共同决定。若任务不代表真实使用，即使样本很多也不能外推；同一任务重复调用也不能替代任务覆盖。

表格中有些任务（例如 SQL 方言）可能凭模型默认知识答对，也有些任务需要严格依赖会话 1。应先运行无记忆基线并检查每题是否真的需要历史事实；评分规则还应允许正确的安全澄清，避免把合理行为算错。表中的组数与“期望完成标志”仅为构造示例，不是 pilot 选出的有效评测集，也不支持 8–10 或 15 组足够的结论。

## `eval_memory.py`：可运行的评测骨架

```python
# eval_memory.py
"""跨会话记忆评测骨架：会话1 写入 → 断言上下文已清空 → 会话2 注入 → 判分。

自包含：不依赖网络。下面 respond/judge 是测试替身（stub），
接入真实系统时还必须实现 provider 请求/响应适配、持久层、权限隔离、错误处理与经校准的评分；仅替换函数不足以得到有效评测。

实跑状态：控制流在本机 Python 3.10 上跑通（2026-10-12）。
完成率数字由人为写定的替身输出决定，不是模型实测，也不验证记忆抽取或检索质量。"""

import random
import re

TASKS = [
    {"id": "01", "s1": "我们团队用 PostgreSQL，别给 MySQL 方案",
     "s2": "帮我写个查询用户表的 SQL", "expect_any": ("postgres", "postgresql")},
    {"id": "02", "s1": "输出一律用表格",
     "s2": "列出这三个方案的区别", "expect_any": ("|", "表格")},
    {"id": "03", "s1": "部署环境是 k8s",
     "s2": "写一段上线脚本", "expect_any": ("kubectl", "k8s")},
]


def new_session():
    """一次会话 = 一个全新的 messages 数组。"""
    return []


def respond(question, ctx, memory_on):
    """一次模型调用。测试替身：memory_on=False 时返回通用答案，否则跟随 ctx。

    这是确定性测试替身。接入真实 API 时需适配 provider 请求/响应、角色与不可信记忆边界，
      并重做经校准的评分与错误记录；不能只替换这一行。"""
    if not memory_on:
        return "SELECT * FROM users;"
    return "SELECT * FROM users;  /* PostgreSQL 方言 */" if "PostgreSQL" in ctx else "SELECT * FROM users;"


def write_memory(session1_messages):
    """会话 1 结束时提取记忆。真实系统在这里调模型 + should_write。"""
    return " ".join(m["content"] for m in session1_messages)


def retrieve(memory_text, question, k=3):
    """召回：按需取回相关记忆。这里是朴素实现，真实系统用第 6 章那套。"""
    return memory_text


def judge(answer, task):
    """规则判分：只看期望关键词有没有出现，不给部分分。"""
    return any(k.lower() in answer.lower() for k in task["expect_any"])


def run_one(task, memory_on):
    """跑一组：两次会话，中间必须清空。"""
    # 会话 1：建立上下文、写入记忆
    ctx1 = new_session()
    ctx1.append({"role": "user", "content": task["s1"]})
    memory = write_memory(ctx1)

    # ★ 防呆：会话 2 必须是全新的数组。复用 ctx1 会让结果「看起来更好」，
    #   而那是长上下文的效果，不是记忆的效果。
    ctx2 = new_session()
    assert ctx2 is not ctx1 and ctx2 == [], "会话 2 必须是全新的空消息数组"

    # 会话 2：只注入召回的记忆
    if memory_on:
        ctx2.append({"role": "user", "content": "已知：" + retrieve(memory, task["s2"])})
    ctx2.append({"role": "user", "content": task["s2"]})
    answer = respond(task["s2"], ctx2[-2]["content"] if memory_on else "", memory_on)

    return {"id": task["id"], "done": judge(answer, task), "memory": memory_on,
            "clarified": 0, "misremembered": 0}


def report(rows):
    for flag in (False, True):
        subset = [r for r in rows if r["memory"] is flag]
        if not subset:
            continue
        done = sum(r["done"] for r in subset)
        print("记忆%-4s 完成率 %d/%d = %.0f%%   重复澄清 %d 次   记错 %d 次" % (
            "开" if flag else "关", done, len(subset), 100 * done / len(subset),
            sum(r["clarified"] for r in subset), sum(r["misremembered"] for r in subset)))


def run_study(tasks, seed=None):
    """每道题都配对运行；用固定种子的伪随机顺序平衡先后效应。"""
    rng = random.Random(seed)
    rows = []
    for task in tasks:
        conditions = [False, True]
        rng.shuffle(conditions)
        for memory_on in conditions:
            rows.append(run_one(task, memory_on=memory_on))
    return rows


if __name__ == "__main__":
    rows = run_study(TASKS, seed=20261022)
    report(rows)
```

```text
记忆关    完成率 0/3 = 0%   重复澄清 0 次   记错 0 次
记忆开    完成率 1/3 = 33%   重复澄清 0 次   记错 0 次
```

（上表是**测试替身**的输出，不是模型实测 —— 它证明的是骨架能跑、断言会拦，不是记忆真的把完成率从 0 提到 33%。那两个数字完全由 `respond()` 这个替身决定：替身只在上下文里出现 `PostgreSQL` 时才给出对的答案，另外两组任务照旧返回通用答案。换成真实模型调用之后，这两个数字才有意义。）

骨架里有三处刻意设计，每一处都对应前面某一节的失败：

1. **`assert ctx2 is not ctx1`**：防线设在「上下文没清空」这个最容易偷懒、且结果恰好更好的地方。
2. **判分是规则，不是模型**：关键词命中即可，能给出确定答案。要用模型判分也可以，但必须先用一批人工标好的样本验一遍它 —— 否则你测的是两个模型的嘴，不是一个记忆系统。
3. **三列指标一次算完**：完成率、重复澄清、记错。只报完成率会漏掉误召回（第 3 节：它是静默的）。

真实运行成本要按调用清单估算：分别记录写入、召回/重排、回答和评分调用的输入/输出 token、缓存读写及调用次数，再使用目标 provider 当前价格换算；另列数据库、向量索引、人工复核与运营费用。任务数 × 会话数只是调用次数的粗略提示，不能替代实际 token usage 与账单。耗时也受排队、重试、并发、限速和存储影响，应从运行日志测量。不要把固定的任务数、单次 token 量或分钟级耗时当作通用值。

## 对照结果应该怎样解释

「关掉记忆」不是只把两个完成率相减。对每个配对任务，应保留“关/开”两种条件的原始判分与错误类型，先列出四格配对表：两边都成功、只有开记忆成功、只有关记忆成功、两边都失败。二元任务结果可用配对二项方法（例如 McNemar 检验）检验不一致对的方向；报告开/关成功率差值及按配对设计计算的区间，并说明预先设定的最小有意义改善和错误代价。不要用两组各自的独立比例标准误或区间代替配对差值的不确定性。方法资料可参见 [NIST McNemar Test](https://www.itl.nist.gov/div898/software/dataplot/refman1/auxillar/mcnemar.htm) 与 [Fagerland 等人的配对二项比例检验和区间比较](https://doi.org/10.1002/sim.6148)；[NIST 比例区间](https://itl.nist.gov/div898/handbook/prc/section2/prc241.htm) 补充说明单个比例在小样本时正态近似区间可能不准确，并非配对差值区间。

这里不能把 `sqrt(0.5×0.5/15)` 写成这套配对设计的“标准误”：它只是把单组成功率假定为 0.5、样本独立同分布时的单比例标准误近似，不是两种条件的配对差值标准误，也不是置信区间。小样本下正态近似区间也可能不准确。实际不确定性依赖任务间差异与开/关条件的配对结果，不能只凭样本数 15 给固定误差条。

同样，20% 到 80% 的边际变化可能提示值得扩大验证，但仅知道两个边际比例无法完成配对检验；需要知道每道题两种条件下是否成功。80% 到 87% 也不能因为“只差一题”就断言无效或必然要扩样：应结合任务代表性、配对不一致数、预先定义的最小效果、错误代价与需要达到的区间精度判断。样本量规划至少要说明实验单位、基线率、最小可检测差异、显著性水平、目标功效、预期不一致比例与重复运行的聚类方式；pilot 的十几题只适合发现设计缺陷，不自动提供确认性证据。

## 渐进上线的观测表

前面那三步每一步看什么、如何决定是否继续。阈值需由目标任务、风险预算和 pilot 结果预先确定；下面不提供跨产品通用数值：

| 阶段 | 这一阶段看什么 | 继续条件（按产品预先定义） | 没达标的动作 |
|---|---|---|---|
| 一，只写不读 | 候选与获准写入记录的比例、拒绝原因、删除请求 | 按产品风险与容量预先设定，并先采集基线 | 收紧或调整写入策略；检查用户控制与敏感信息处理 |
| 二，受控注入 | 错误采用、漏用、用户纠正与严重度分布 | 由风险预算和人工审查规则设定，不以“必须为零”替代区间估计 | 暂停扩展条件；回看具体记录、来源、范围和注入上下文 |
| 三，按需取回 | 任务结果、误用/漏用、延迟与每任务成本 | 按目标任务的最小收益、错误代价和服务约束预先设定 | 分析候选召回、策略阻断、注入和任务判分；必要时回退 |

**每一阶段的退出条件都是可观测的**，这正是分步的价值：一次全开时，你无法判断出问题的是写入、召回还是注入。

## 渐进上线的路径

记忆系统不该一次全开。可行的路径是分三步：

**第一步，只写不读。** 正常提取并存储，但不注入任何内容。这一阶段收集真实数据：库里会长出什么、有多少推断类条目混进来。此阶段没有回答时的记忆注入成本，但仍有写入模型调用、存储、检索索引维护与审核成本；应按实际产品分项记录。

**第二步，受控注入。** 先定义允许的来源、scope、时效、敏感级别和产品授权，再从低风险样本逐步开放。不要把 2–3 条或“用户纠正接近零”当成通用配置；同时监测错误采用、漏用、澄清、静默错误抽检和严重度，达到预设风险边界时暂停扩展并复盘。

**第三步，加入按需取回。** 把条件相关的记忆做成工具，让模型自己查。这一步才真正需要检索能力（第 6 章），而收益也最大。

这样分步的价值在于：**每一步的失败半径都很小**，而且每一步都有明确的观测指标。反过来，一次全开的系统在出问题时，你无法判断是写入、召回还是注入的环节出了错。
## 完整可运行代码

```python
"""记忆系统的成本模型：四笔账，以及每一笔有多大。

纯本地计算。它回答的是一个很具体的问题：
「给对话加上记忆」这件事，钱到底花在哪一项上。

实跑状态：2026-10-08，已跑通。
"""


def cost(turns, memories, inject_per_turn, write_calls_per_turn=0.2,
         tokens_per_memory=40, system=500, summary_tokens=150):
    """返回模型输入 token 的分项估算；存储条数单独报告，不相加。"""
    # 写入：假设每轮按给定平均频率重读截至当轮的上下文。
    write_input_tokens = sum(
        int((system + turn * summary_tokens) * write_calls_per_turn)
        for turn in range(1, turns + 1)
    )
    # 注入：假设每条记忆每轮都以固定 token 数进入模型输入。
    inject_input_tokens = turns * inject_per_turn * tokens_per_memory
    return {
        "写入输入token": write_input_tokens,
        "注入输入token": inject_input_tokens,
        "模型输入token合计": write_input_tokens + inject_input_tokens,
        "存储条数": memories,
    }


if __name__ == "__main__":
    TURNS = 20
    print("20 轮对话、每条记忆 40 token：")
    print("%-14s %12s %12s %12s" % ("常驻注入条数", "写入输入", "注入输入", "输入合计"))
    for keep in (0, 3, 10, 30):
        c = cost(TURNS, memories=keep, inject_per_turn=keep)
        print("%-14d %12d %12d %12d" % (
            keep, c["写入输入token"], c["注入输入token"], c["模型输入token合计"]))

    print()
    print("假设：写入调用频率固定为每轮 0.2 次；不含输出、缓存折扣、检索基础设施或存储费用。")
    print("3 条到 10 条时，构造模型中的注入输入 token 从 2400 增至 8000（3.3 倍）。")
```

## 这一章的收束

把五节连起来，其实是一条从「不值得做」到「什么情况下值得做」的判断链：

1. 不要把「窗口会满」当理由 —— 实测一百零四万 token 都没报错，真正的理由是计费方式、跨会话、不可修改（第 1 节）。
2. 写不写，按三条标准判断，并且记住来源（第 2 节）。
3. 取不取，靠来源与时效这两道确定性闸门，相关度交给检索能力（第 3 节）。
4. 冲突先校验范围、来源与明确的更新关系；无法安全裁决时阻止注入并进入确认流程（第 4 节）。
5. 最后用预先设计的任务对照估计收益、风险与成本，并按证据强度决定是否扩大验证（本节）。

## 本节小结

1. **按单位拆成本**：在本节的固定假设下，注入 token 随条数增长；写入 token 也会随提取频率、上下文与缓存策略变化。存储、检索和人工运营须另计。
2. **用任务效果和风险指标**：活动指标用于诊断，不能单独说明记忆改善了结果。
3. **同时观测误用、漏用与用户纠正**：纠正率会漏掉静默错误，不能作为唯一负向指标。
4. **用配对对照形成证据**：关/开记忆应在同一任务、同一配置下比较，并检查逐题差异、评分可靠性、任务代表性和不确定性。一次小样本对照只能帮助决定下一步，不能自动证明普遍收益。

这条判断方法和其他几章是一致的：第 6 章用「完美检索」测上界，第 3 章用子智能体做对照，本节用「关掉记忆」。**共同点是先量化收益、再决定投入** —— 而不是先建好一个系统，再想办法证明它有用。
## 常见坑

- **把不同单位硬加成总成本。** Token、存储字节、检索资源与人工复核应分项报告，或按同一货币和时间范围换算。
- **按活动指标评估。** 召回次数、库容量和命中率能帮助诊断，不能单独证明效果；历史例子也不能脱离原始轨迹推广为频率或因果结论。
- **把小型对照当成结论。** 同一批任务配对能减少任务难度差异，但仍需检查代表性、评分、运行顺序、随机性和配对不确定性。
- **只统计正向指标或用户纠正。** 同时抽检静默误用、漏用、严重度与正确澄清；未收到纠正不等于没有错误。
- **以为少记一点只会影响注入成本。** 在示例固定假设中，注入输入随记忆条数增长；真实写入成本还取决于提取频率、历史长度、摘要、缓存和模型调用策略。
- **在目标与基线不清楚时先上复杂检索。** 先定义需要解决的任务与错误代价，再用适当基线判断规则、检索或重排是否带来可复核收益。
