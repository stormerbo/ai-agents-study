记忆系统最容易被跳过的一步是**写入规则**。多数实现的做法是「把这一轮值得记的东西抽出来存进去」—— 抽什么，交给模型判断。

而这就是问题的起点。我把两种写入策略放在同一段对话上跑了一遍。

## 实测：同一段对话，两种写入策略

对话里有 7 句话，我事先标注好了「正确答案」：

- **该记的 3 条**（满足跨会话 + 稳定 + 用户明说）：偏好表格输出、团队用 PostgreSQL、部署环境是 k8s
- **一次性信息 3 条**（本轮用完即弃）：看看报表、今天有点热、翻回上一页
- **模型推断 2 条**（用户没说，只是「可能」）：对价格敏感

两种写入指令，同样的对话：

| | 无差别记录 | 按规则筛选 |
|---|---|---|
| 该记的 3 条 | 3/3 | 3/3 |
| 记住了一次性信息 | **3 项全中** | 无 |
| 把推断当成事实存下 | **2 项** | 无 |

（实跑数据，2026-10-08，`deepseek-flash`。脚本见本节末尾。）

注意第一行：**两种策略在「该记的」上完全一样，都是 3/3。** 差别全在「不该记的」那一侧。

这也是为什么很多团队觉得「无差别记录」没问题 —— 你抽查它记住了什么，会发现该记的都在，看起来工作正常。问题要到几个月后才浮现：

- 那次「今天有点热」被写成了一条记忆，之后每次对话都可能被召回进去
- 「我可能对价格比较敏感吧」被整理成了「用户对价格较敏感」—— 一个带保留的猜测，变成了一条确凿的事实

第二条是最危险的。**推断一旦被写成事实，你就再也分不清哪些记忆来自观察、哪些来自模型的猜测。** 而后续所有决策（包括「该不该向用户确认」）都建立在「这条是事实」这个前提上。

## 三条标准，以及为什么必须是三条

一条信息要值得写进长期记忆，需要**同时**满足：

**一，跨会话仍然有效。** 「今天有点热」「先看这个报表」不满足 —— 它们只在当前任务里成立。这条标准的操作化问法是：**这条信息在三个月后的另一次会话里还有用吗？**

**二，相对稳定。** 「用户现在在用 k8s」满足；「用户当前正在看第 3 页」不满足。稳定不等于永远不变 —— 它意味着变化足够慢，值得存下来再更新。

**三，可归因。** 这条是三条里最容易被忽略的：**你能说清它是从哪来的吗？** 用户明说的、系统观测到的、还是模型推断的？三者混在一起，就没法在下游做分级处理。

三条缺一不可。只有第一条会漏掉「用户正在看第 3 页」；只有第二条会漏掉「用户下个月要出差」（会变，但重要且可以更新）；缺第三条则会让推断悄悄混入。

## 每条记忆都该带来源

第三条标准落到数据结构上，就是**每条记忆必须带来源字段**。这不是洁癖 —— 它是第 3 节「召回闸门」能工作的前提：你可以规定「只注入用户明说的记忆」，把推断类整体挡在上下文之外。本次实验里，来源闸门一次性挡掉了 2 条（两条推断），而它的行为是完全确定的、可预测的。

这也和第 5 章那个 `status_source` 字段解决的是同一个问题：**让「这条信息从哪来」在数据结构里可分辨**，而不是靠你记住。

## 一条记忆记录长什么样

「每条记忆必须带来源字段」这句话落到工程上，需要一整条记录，而不是一个字段。下面这份 schema 和示例可以直接抄（**示例：构造数据，未实跑**）：

```json
{
  "id": "m_7f3a91",
  "text": "团队使用 PostgreSQL，不要 MySQL 方案。",
  "source": "user_stated",
  "status": "active",
  "created_at": "2026-09-28T10:12:03+08:00",
  "updated_at": "2026-09-28T10:12:03+08:00",
  "superseded_by": null,
  "ttl_days": 90,
  "dedup_key": "tech_stack.postgresql"
}
```

| 字段 | 类型 | 一句话用途 | 支撑哪一节的功能 |
|---|---|---|---|
| `id` | TEXT 主键 | 召回日志里引用它 | 第 3 节的注入轨迹 |
| `text` | TEXT | 注入进上下文的那句话 | 全部 |
| `source` | ENUM | 这条是谁说的：`user_stated` / `system_observed` / `model_inferred` | 第 3 节**来源闸门** |
| `status` | ENUM | `active` / `superseded` / `deleted` | 第 4 节失效标记与删除 |
| `created_at` | ISO 8601 带时区 | 首次写入时间 | 审计 |
| `updated_at` | ISO 8601 带时区 | 最近一次确认的时间 | 第 3 节**时效闸门** |
| `superseded_by` | TEXT 可空 | 被哪条取代 | 第 4 节冲突裁决 |
| `ttl_days` | INTEGER | 多少天后该复核 | 第 4 节 TTL |
| `dedup_key` | TEXT | 同主题归一化键，查重用 | 本节去重 |

**时间戳用 ISO 8601 带时区（`+08:00`），不用「秒」或「天」这种相对值。** 理由很实际：第 3 节的时效闸门要算天数、第 4 节的裁决要比较先后，而相对值一旦跨了进程就没有参照点。

**这里有一个和下一节的口径冲突，必须显式处理。** 第 3 节的代码里 `source` 写的是中文字符串（`"用户明说"`），而上面这个 schema 用的是英文枚举（`user_stated`）。两种口径不能混用：

- **如果在同一套系统里混用**，来源闸门的 `source in ALLOWED` 就会因为字符串不等而永远拦下或者永远放行 —— 一个静默的、不可能靠抽查发现的 bug。
- **选法**：写进库的用英文枚举（稳定、不受语言与大小写影响），只在 prompt 与日志展示时映射回中文。下面 `to_record()` 就是那个唯一的映射点。

## 把三条标准写成代码：`should_write()`

三条标准（跨会话 / 稳定 / 可归因）在正文里是问句，落到代码里是布尔判断。**可归因是唯一一条不需要模型介入的 —— 它只是查一个枚举。**

```python
# should_write.py
"""三条标准 → 布尔判断；通过后写一条带来源的记录。

自包含：纯本地逻辑，不需要网络。
实跑状态：本机 Python 3.10 实跑（2026-10-12）。"""

import json
import re
from datetime import datetime, timezone, timedelta

CN = timezone(timedelta(hours=8))
WRITEABLE_SOURCES = ("user_stated", "system_observed")   # model_inferred 不允许作为事实写库

# 稳定性门槛：命中「一次性」词表 → 判断只在本轮成立
ONE_OFF = re.compile(r"今天|刚才|这一页|这次|临时|顺便")


def should_write(text, source):
    """返回 (是否能写, 原因)。三条标准缺一不可。"""
    if not text.strip():
        return False, "空内容"
    if source == "model_inferred":
        return False, "不可归因：推断类不作为事实写入"
    if source not in WRITEABLE_SOURCES:
        return False, "来源取值非法：%s" % source
    if ONE_OFF.search(text):
        return False, "不稳定：只在本轮成立"
    if len(text) < 4:
        return False, "信息量不足，跨会话没有价值"
    return True, "可写"


def to_record(text, source, dedup_key, ttl_days=90):
    now = datetime.now(CN).isoformat(timespec="seconds")
    return {
        "id": "m_" + re.sub(r"\W", "", dedup_key)[:8],
        "text": text,
        "source": source,            # 英文枚举入库
        "status": "active",
        "created_at": now,
        "updated_at": now,
        "superseded_by": None,
        "ttl_days": ttl_days,
        "dedup_key": dedup_key,
    }


if __name__ == "__main__":
    samples = [
        ("团队使用 PostgreSQL，别给我 MySQL 的方案。", "user_stated", "tech_stack.postgresql"),
        ("今天有点热。", "system_observed", "weather.today"),
        ("用户可能对价格比较敏感吧。", "model_inferred", "user.price_sensitivity"),
    ]
    for text, source, key in samples:
        ok, why = should_write(text, source)
        print("%-8s %s  <- %s" % ("写入" if ok else "丢弃", why, text))
        if ok:
            print("         ", json.dumps(to_record(text, source, key), ensure_ascii=False))
```

```text
写入     可写  <- 团队使用 PostgreSQL，别给我 MySQL 的方案。
          {"id": "m_tech_sta", "text": "团队使用 PostgreSQL，别给我 MySQL 的方案。", "source": "user_stated", "status": "active", "created_at": "2026-10-12T15:54:30+08:00", "updated_at": "2026-10-12T15:54:30+08:00", "superseded_by": null, "ttl_days": 90, "dedup_key": "tech_stack.postgresql"}
丢弃     不稳定：只在本轮成立  <- 今天有点热。
丢弃     不可归因：推断类不作为事实写入  <- 用户可能对价格比较敏感吧。
```

注意 `should_write()` 里**第一条就拦推断**，而且没有给模型留任何裁量空间 —— 这正是它可靠的原因。模型在写入环节只负责一件事：**从原文里抽出候选文本并打上来源标签**；「要不要写」由这个函数决定。

## 去重阈值怎么定

「相似度过阈值就合并」是一句空话，除非你把两件事定下来：**用什么相似度**，以及**阈值多少**。

- **用什么**：词法（Jaccard / 字符重合）能抓「同一句话的改写」，抓不住「同义表述」；嵌入能抓语义，但引入模型依赖。务实做法：**先用词法做第一层，`dedup_key` 做第二层** —— 后者是人定的归一化主题（`tech_stack.postgresql`），它对「说法变了但主题没变」免疫。
- **阈值多少**：这是**你的语料决定的**，不能从别处抄。定法是取 20 组「同一件事的两种说法」和 20 组「相邻主题」，看这两批的分数分布有没有重叠区，阈值取在中间。本站第 6 章实测过词法在改写查询上的词面重合只有 0.012 到 0.041 —— **它意味着纯词法的合并阈值在中文改写上几乎无处可放**，这也正是要补 `dedup_key` 的原因。

**合并不等于覆盖**：命中去重时更新 `updated_at` 并累加「确认次数」，而不是重写 `text` —— 第 4 节的时效闸门依赖 `updated_at`，你把它改掉，等于让一条老记忆看起来像新的。

## 写入的时机：每轮写，还是结束时写

三条标准决定「记什么」，但还有一个同样重要的问题：**什么时候执行写入**。三种做法各有代价。

**每轮都写。** 每轮结束都调用一次「提取记忆」。它最及时 —— 会话中途崩溃也不会丢。代价是成本：把这一步计入第 1 节那张表，每次对话的调用数接近翻倍，而大部分轮次其实没有值得记的东西。

**会话结束时写。** 只在结束时做一次提取。便宜得多，风险是会话如果意外中断（关掉页面、超时、报错），这次会话的所有信息都丢了。

**显式触发。** 由用户或某个明确条件触发（「记住这个」、或检测到一段陈述句）。它最省，可靠性取决于触发条件的质量。

实践上的折中是**两者组合**：会话结束时做一次完整提取作为兜底，同时对明确的用户陈述（「我们用 PostgreSQL」「以后都用表格」）即时写入。判断依据很简单：**如果这条信息丢了会让你后悔，就即时写；否则等结束。**

**这笔差可以用第 1 节的成本模型直接算。** 「每轮写」意味着第 t 轮要把当前上下文再发一遍给提取调用；而第 1 节实测过：**历史每轮重发，12 轮累计是「只发一次」的 6.5 倍**，50 轮是 24 倍。把它套到写入上：

| 写入时机 | 12 轮对话的提取调用 | 相对成本 | 失败时丢什么 |
|---|---|---:|---|
| 结束时写一次 | 1 次，带全部历史 | 1x（基准） | 会话中断 → 整段丢 |
| 每轮写 | 12 次，每次带当轮为止的全部历史 | 约 6.5x（沿用第 1 节的 12 轮倍数，未单独实测） | 最多丢最后几轮 |

所以「每轮写」贵的不是调用次数（12 次），而是**每次都要重发历史**。这也是为什么本节开头说「大多数轮次其实没有值得记的东西」——你为 12 次里可能只有 2 次有产出的提取，付了 6.5 倍的钱。

## 还要做去重

写入规则有一个容易漏的副作用：**同一条偏好会被反复写入**。用户每次说「我喜欢表格」，都可能生成一条新记忆。一个月后库里躺着 20 条几乎一样的偏好，而召回时它们会占掉 top-k 的名额 —— 你花了 5 个位置，只拿到 1 条信息。

两种处理方式，按成本排序：

- **写入前查重**：新条目与已有条目相似度过阈值就合并（更新时间戳），而不是新增。
- **合并成偏好强度**：把「说过几次」作为权重存下来 —— 因为**反复强调的偏好比说过一次的重要**，而这个信号只有在合并那一刻才能拿到，事后无法重建。

注意这里和第 6 章用到了同一套相似度判断，所以纯词法的局限也一并带过来了：词面重合对改写几乎无效（第 6 章实测：10 条口语化查询里，正确段落进 top-5 的是 0 条）。

## 一句话总结写入规则

把三条标准和时机合起来，写入侧其实只有一句话：**在写入那一刻做减法，并且记住每一条是从哪来的。**

减法比事后清理容易得多。已经存进去的推断，你没法在不重新审视全部历史的前提下把它挑出来；而写入时多问一句「这是用户说的，还是我猜的」，成本几乎为零。
## 完整可运行代码

写入脚本里用到的两个字段（第 5 章讲过，这里再用一次）：`max_tokens` 是请求里设的本次生成长度上限，`stop_reason` 是响应里说明为什么停下来的字段 —— 遇到 `max_tokens` 就说明输出被截断了，那一轮的结果不能计入统计。

```python
"""两种写入策略的对照：无差别记录 vs 按规则筛选。

它把正文里那组实测跑一遍。需要 .env.local 里的凭据。

实跑状态：2026-10-08，deepseek-flash，已跑通。
"""

import json
import os
import urllib.request

CONVO = "\n".join([
    "用户：帮我看看这个报表。",
    "用户：我比较喜欢表格形式的输出。",
    "用户：今天有点热。",
    "用户：我们团队用 PostgreSQL，别给我 MySQL 的方案。",
    "用户：刚才那页再翻一下。",
    "用户：我可能对价格比较敏感吧。",
    "用户：部署环境是 k8s，这个别忘了。",
])

NAIVE = "你是一个带长期记忆的助手。把用户对话里所有的信息点整理成长期记忆条目，逐条列出。"

RULE = "\n".join([
    "你是一个带长期记忆的助手。从用户对话里提炼值得长期记住的信息。",
    "判断标准（三条必须同时满足）：1) 跨会话仍然有效；2) 相对稳定；3) 是用户明确说过的，不是你的推断。",
    "不满足的不要写。每条标注来源：用户明说 / 推理得到。推理得到的一律不写入。",
    "输出格式：每行一条，形如「- 内容 [来源]」。",
])

# 人工标注的「正确答案」：只有这三条同时满足三条标准
STABLE = ["表格", "PostgreSQL", "k8s"]
ONE_OFF = ["今天有点热", "报表", "翻页"]
INFERRED = ["价格", "敏感"]


def ask(system, user, max_tokens=6000):
    body = json.dumps({"model": os.environ.get("VERIFY_MODEL", "claude-haiku-4-5"),
                       "max_tokens": max_tokens, "system": system,
                       "messages": [{"role": "user", "content": user}]}).encode()
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages", data=body,
        headers={"content-type": "application/json",
                 "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
                 "anthropic-version": "2023-06-01"})
    with urllib.request.urlopen(req, timeout=180) as resp:
        data = json.loads(resp.read())
    text = "".join(b["text"] for b in data["content"] if b["type"] == "text")
    return text, data["stop_reason"]


def insert(out):
    """按上面那条记录的形状接收写入。真实系统里这行是 INSERT。"""
    for line in out.splitlines():
        text = line.strip().lstrip("- ").split(" [")[0]
        if not text:
            continue
        for keyword, key, source in (
            ("表格", "output.format_table", "user_stated"),
            ("PostgreSQL", "tech_stack.postgresql", "user_stated"),
            ("k8s", "deploy.k8s", "user_stated"),
        ):
            if keyword in text:
                ok, why = should_write(text, source)
                if ok:
                    print("  写入:", json.dumps(to_record(text, source, key), ensure_ascii=False)[:120], "...")


def audit(label, text):
    hit = lambda kws: [k for k in kws if k in text]
    stable = hit(STABLE)
    print("[%s]" % label)
    print("  该记的（3 条）:", stable, "→ 命中 %d/3" % len(stable))
    print("  一次性信息（不该记）:", hit(ONE_OFF) or "无")
    print("  模型推断（不该记）:", hit(INFERRED) or "无")
    insert(text)      # 只有通过 should_write 的才会真的落库
    print()


if __name__ == "__main__":
    for label, sys in [("无差别记录", NAIVE), ("按规则筛选", RULE)]:
        text, stop = ask(sys, "对话记录：\n" + CONVO)
        if stop == "max_tokens":
            print("[%s] 警告：stop_reason=max_tokens，结果不可用" % label)
        audit(label, text)
```


## 给写入规则做一次回归测试

写入规则和 prompt 一样，改一个字就可能改变行为，所以它需要自己的对照。做法比检索评测简单得多。

构造 10 到 20 段短对话，每段事先标注三类条目（该记 / 一次性 / 推断）。每次改动写入指令后跑一遍，看三个数字：**该记的命中率**、**一次性信息的误入数**、**推断的误入数**。

关键是后两个数字。本次实测里两种策略的「该记命中率」都是 3/3 —— 只看这一个指标，你会以为两种策略没差别。真正的差别全在误入数上（一次性信息 3 项对 0 项、推断 2 项对 0 项）。

这和检索那章的教训是同一个：**指标要选在那个能看见问题的地方。** 而「该记的有没有记住」恰好是最看不见问题的那一个 —— 它几乎总是满分。

这个测试的成本很低（十几段对话、几十次调用），而它防的是「改了一条写入指令，悄悄开始记录一切」这类退化 —— 那类退化在抽查时完全看不出来。
## 常见坑

- **把「提取记忆」整件事交给模型。** 实测里，两种策略在「该记的」上都是 3/3 —— 差别全在噪声那侧，而噪声在抽查时看不出来。
- **不区分「用户明说」与「模型推断」。** 推断被写成事实后，你再也无法分辨，也无法在下游按来源分级。
- **用「这条有用吗」当唯一标准。** 一次性信息也有用 —— 只是用在当前这一轮，不属于长期记忆。判据要加上「跨会话」。
- **无差别记录然后指望检索过滤。** 检索能过滤不相关的，但过滤不掉「同主题的过时信息」—— 而那恰恰是推断与陈旧偏好最常见的样子。
- **忘了时间戳。** 没有它，第 4 节的冲突裁决根本无从下手：你连哪条更新都不知道。
- **写入时不记来源，等到用的时候再想。** 来源信息在写入那一刻才知道，事后无法重建。
