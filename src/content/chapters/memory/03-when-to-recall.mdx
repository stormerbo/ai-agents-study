记忆写进去了，下一个问题是**什么时候取出来**。

这个问题看起来比写入简单 —— 相关就取，不相关就不取。但「相关」是一个判断，而任何判断都会有错。这一节要看的是：判断错的代价有多大。

## 历史观察：一条不相关的记忆，可能改变输出

任务很简单：**写一段部署脚本，把服务发到服务器上**。现存历史摘要记录了 2026-10-08 的三种条件各一次：

| 条件 | 历史摘要中的输出 | 摘要记录的记忆使用情况 |
|---|---|---|
| A 不注入记忆 | npm ci && npm run build，再 scp 与 systemctl restart | — |
| B 注入**不相关**记忆：「用户的脚本必须用 Python 2.7」 | python2.7 -m pip install -r requirements.txt …… | ⚠️ **跟随了** |
| C 注入**相关**记忆：「目标是 k8s，走 kubectl」 | kubectl apply / kubectl set image / rollout status | ✅ 正确采纳 |

历史摘要把条件 B 记为一次“输出包含 Python 2.7 安装命令”的观察，A 与 B 的差异据称是一条记忆。它提供了一个值得调查的失效假设：无关信息可能影响生成。但原始逐次请求、响应、评分器、模型路由与运行参数未归档，本轮无法独立复核；这条记录不能证明普遍因果关系，也不能估计误召回发生率。

如果一条过期或无关记忆导致模型生成语法正常但不适用的命令，常规格式校验未必能发现。不过这份历史摘要没有保留原始回复、运行日志或检测结果，无法验证当时是否有提示、告警或人工发现；“静默失败”在这里是待评估的风险假设。

## 为什么误召回可能更难发现

这是本节最重要的一个判断，值得说清楚推理链条。

**召回不到**可能让模型缺少完成任务所需的信息；它可能拒答、追问，也可能用先验补全甚至产生幻觉。不能假设“没召回就会说不知道”。

**误召回**则可能把一个与当前情境无关的事实放进输入；如果模型把它当成可信前提，输出就可能被带偏。它也不必然被采纳，模型可能忽略或识别冲突。

所以不能把“误召回一定比漏召回更严重”当作通用规律。对一条特定记忆，应比较误注入与漏注入对任务成功、安全和可发现性的影响；尤其当无关记忆会被当成用户约束或授权依据时，误召回可能静默地改变行为。当前保留下来的 2026-10-08 摘要不足以证明这类效应的普遍性。

## 三道闸门

可以把召回决策拆成来源、时效和相关性几项检查。固定来源/TTL 策略的执行可做到确定性；相关性阈值的选择和适用性仍需用目标数据评估。

**来源闸门。** 按记录的来源字段执行一项明确策略。本节代码使用一个偏保守的示例策略：只允许“用户明说”，把模型推断和系统观测先拦下；这不是适用于所有产品的通则。系统观测可否使用，取决于它的证据来源、校验方式和权限语义。

**时效闸门。** 超过记录自身有效期时降权或排除。上面图里的 **TTL** 指记录的 `ttl_days`（见第 2 节 schema），不是定时任务的运行时长；示例用时区明确的 `updated_at + ttl_days` 与当前时刻比较。具体边界应写进策略并测试。原 Python 2.7 记忆摘要没有保存可供检查的更新时间或 TTL，因此不能说历史实验验证了时效闸门；后面的本地构造样例会单独覆盖它。

**相关度闸门。** 相关性取决于当前任务，不能只看记忆文本本身。本节的词面重合示例中，部署问题下“表格输出偏好”和“PostgreSQL 项目约束”都得 0.000；若产品策略要求保留前者、排除后者，这个分数无法把它们分开。这说明该评分器在此样例上区分力不足，不等于所有词法方法都不能设阈值。实际系统要对目标问题与记忆对标注、校准并验证相关性判据。

### 相关度闸门换成向量之后，阈值怎么定

相似度阈值可以用于向量或词法检索；分数的尺度和方向取决于具体算法，某个分数范围本身不会给出通用阈值。**阈值必须在目标任务和数据上校准**。可以先构造标注好的“问题—记忆”对，标出哪些应作为候选；20+20 对只能算小规模试点，不是充分样本。下面代码中的 4+4 个分数只是演示阈值计算，不是效果评估。查看正负分布和误判成本后再选候选阈值。随后用独立留出集验证精确率、召回率和任务影响，避免在同一小批样本上调参又报效果。换嵌入模型、记忆类型或任务分布时应重新校准。

无论选哪种算法，保底规则都应明确：低于阈值的候选不注入，而不是为了凑够 k 条而放行。分数相同也不意味着语义等价；生产判据要结合标注和任务后果。以下是**构造的离线示例，未实跑模型**。**实跑状态：** 2026-10-21 使用 Python 3.14 执行了本地评分 fixture；它只验证示例逻辑，不代表模型检索效果。

```python
"""Higher score means more similar; this is a threshold fixture, not a universal metric."""


def gate(similarities, threshold):
    """Keep only candidates whose higher-is-better score meets the configured threshold."""
    return [(memory_id, score) for memory_id, score in similarities if score >= threshold]


def summarize(positive, negative):
    """Compare labeled positive and negative calibration scores; empty labels are invalid."""
    if not positive or not negative:
        raise ValueError("positive and negative calibration sets must both be non-empty")
    lowest_positive = min(positive)
    highest_negative = max(negative)
    if lowest_positive > highest_negative:
        return "校准样本可分：候选阈值位于 %.2f 到 %.2f 之间" % (
            highest_negative, lowest_positive
        )
    candidate = (lowest_positive + highest_negative) / 2
    return "校准样本边界重叠：折中候选 %.2f；需用独立集评估误判" % candidate


if __name__ == "__main__":
    relevant = [0.91, 0.88, 0.93, 0.85]       # 构造的相关候选分数
    irrelevant = [0.62, 0.71, 0.58, 0.44]     # 构造的不相关候选分数
    print(summarize(relevant, irrelevant))
```

## 注入还是做成工具

最后是形态问题：记忆该**每轮自动注入**，还是**做成工具让模型自己查**？

判据是「这条记忆是普遍相关，还是条件相关」。

**普遍相关**（回复语言偏好、输出格式偏好）适合少量常驻注入 —— 但必须严格控制条数，因为它们每一轮都要重新计费（第 1 节那张表在这里同样成立）。

**条件相关**（「这个项目上次用的部署环境」）适合做成工具按需查。自动注入的代价是：不相关的记忆会影响行为，而且失败是静默的。

可以把“常驻少量高频偏好、条件相关信息按需查询”作为待验证的起始设计。文中的“2 到 3 条”只是预算示例，不是通用最优数量；应按每轮 token 成本、实际使用率、错误影响和任务评测结果决定。

```python
"""本地构造样例：来源、时效与词面候选分开处理。"""

import math
import re
from datetime import datetime, timedelta

# 固定回放时刻，保证示例可重复；在线服务应注入当前可信时钟。
TODAY = datetime.fromisoformat("2026-10-08T00:00:00+08:00")

MEMORIES = [
    {"id": "m1", "text": "用户偏好表格形式的输出。", "source": "用户明说", "updated_at": "2026-09-20T10:00:00+08:00", "ttl_days": 90},
    {"id": "m2", "text": "用户团队使用 PostgreSQL，不要给 MySQL 方案。", "source": "用户明说", "updated_at": "2026-09-28T10:00:00+08:00", "ttl_days": 90},
    {"id": "m3", "text": "用户的所有脚本必须用 Python 2.7 编写。", "source": "系统观测", "updated_at": "2025-01-05T10:00:00+08:00", "ttl_days": 180},
    {"id": "m4", "text": "用户可能对价格比较敏感。", "source": "模型推断", "updated_at": "2026-10-01T10:00:00+08:00", "ttl_days": 30},
    # 独立的过期用户陈述，专门验证时效闸门；不是历史 provider 实验的记录。
    {"id": "m5", "text": "用户旧项目曾使用 Python 2.7，旧环境已退役。", "source": "用户明说", "updated_at": "2025-01-05T10:00:00+08:00", "ttl_days": 180},
]

# 这只是一个保守策略样例，生产系统应按来源类型定义信任和授权规则。
ALLOWED_SOURCES = ("用户明说",)


def tokenize(text):
    text = text.lower()
    out = re.findall(r"[a-z0-9_]+", text)
    for run in re.findall(r"[\u4e00-\u9fff]+", text):
        out.extend(run[i:i + 2] for i in range(len(run) - 1))
    return out


def lexical_score(query, text):
    a, b = set(tokenize(query)), set(tokenize(text))
    if not a or not b:
        return 0.0
    return len(a & b) / math.sqrt(len(a) * len(b))


def is_expired(memory):
    ttl_days = memory.get("ttl_days")
    if isinstance(ttl_days, bool) or not isinstance(ttl_days, int) or ttl_days < 0:
        raise ValueError("ttl_days must be a non-negative integer")
    updated_value = memory.get("updated_at")
    if not isinstance(updated_value, str) or not updated_value.strip():
        raise ValueError("updated_at must be a non-empty ISO timestamp")
    updated_at = datetime.fromisoformat(updated_value)
    if updated_at.utcoffset() is None:
        raise ValueError("updated_at must include a timezone")
    return updated_at + timedelta(days=ttl_days) <= TODAY


def recall(query):
    candidates, blocked = [], []
    for memory in MEMORIES:
        if memory["source"] not in ALLOWED_SOURCES:
            blocked.append((memory, "来源闸门：本例策略不允许 %s" % memory["source"]))
        elif is_expired(memory):
            blocked.append((memory, "时效闸门：记录已过期"))
        else:
            # 这里仅形成候选，不等于已经决定注入。
            candidates.append((memory, lexical_score(query, memory["text"])))
    return candidates, blocked


def self_test():
    assert not is_expired(MEMORIES[0])
    assert is_expired(MEMORIES[4])
    candidates, blocked = recall("帮我写一段部署脚本，把服务发到服务器上")
    assert [memory["id"] for memory, _ in candidates] == ["m1", "m2"]
    assert [(memory["id"], reason.split("：")[0]) for memory, reason in blocked] == [
        ("m3", "来源闸门"), ("m4", "来源闸门"), ("m5", "时效闸门")
    ]
    return 4


if __name__ == "__main__":
    print("本地闸门测试：%d 项通过" % self_test())
    for query in ["帮我写一段部署脚本，把服务发到服务器上", "我比较喜欢什么样的输出格式"]:
        print("问题:", query)
        candidates, blocked = recall(query)
        for memory, score in candidates:
            print("  ✅ 候选 [%s] %s（词面相关度 %.3f）" % (memory["id"], memory["text"], score))
        for memory, reason in blocked:
            print("  ⛔ %s 拦下 [%s]" % (reason.split("：")[0], memory["id"]))
        print("  → 拦截 %d 条，保留 %d 条候选" % (len(blocked), len(candidates)))
        print()
    print("来源策略拦下系统观测与模型推断；时效策略单独拦下 m5。")
    print("词面分数只供排序参考；候选是否注入仍须经过相关性与任务策略校验。")
```

## 注入几条才合适

常驻注入的记忆可能在每轮重复进入输入，因此应测量请求形态、缓存计费与使用频率，再按预算决定数量；具体账单规则依 provider 契约而定。

一个纯算术示例：若每条平均 40 token，注入 10 条就是 400 token/轮；20 轮合计 8,000 token。这里不含 provider 缓存、计费折扣或请求格式差异，不能直接换算成费用。

反过来，注入太少也不行，那等于记忆白做了。建议的做法是按「这条记忆在这一轮真的会被用到吗」分级：

- **第一级（常驻 2 到 3 条）**：几乎每一轮都会影响输出的偏好，例如回复语言、输出格式。

  具体是哪几条，可以直接照下面这份清单起步（**示例：构造数据，未实跑**）：

  | 常驻条目 | 为什么是它 |
  |---|---|
  | 回复语言（中文） | 关掉它，**每一轮**输出都可能变 |
  | 输出格式（表格优先） | 同上，且用户会主动纠正 |
  | 「不要寒暄」这类语气约束 | 影响面广、几乎与话题无关 |

  三条的共同点是：**它们回答的是「怎么答」，不是「答什么」。** 而「这个项目用 PostgreSQL」属于「答什么」—— 只在相关话题出现时才有用，所以它落在第二级。
- **第二级（按需取回）**：只在相关话题出现时才有用的信息，例如某个项目的技术栈。
- **第三级（永不注入）**：来源不可靠或已过期的条目 —— 它们只该留在库里等人工确认。

判断一条记忆属于哪一级，有个很实用的操作化问法：**如果把它关掉，这一轮的输出会变吗？** 如果答案是「大多数轮次都不会变」，它就不该常驻。

## 怎么发现误召回

误召回最麻烦的性质是静默，所以它只能靠可观测性来发现。两个具体做法：

**一，把「本轮注入了哪些记忆」写进轨迹。** 要求很低：记下每条被注入记忆的 id 就够。这样当某次输出看起来不对劲时，你能回看当时注入了什么 —— 没有这份记录，你连怀疑的方向都没有。

## 注入轨迹：把「本轮注入了什么」写下来

前面反复说误召回是静默的，所以只能靠可观测性发现。落地就只有一件事：**每轮把「注入了哪些记忆、过了哪道闸门、分数多少」写下来。**

先定义**轨迹**这个词：它是**对话之外的一份持久记录**（写日志文件或一张表），记的是「这一轮系统做了什么决定」，而不是对话内容本身。它和 messages 是两回事 —— messages 会随会话消失，轨迹要留下来供事后回查。

一条检索决策写一条结构化轨迹。示例记录七项：时间、request ID、轮次、实际注入的记忆 ID、被拦截的 ID 与原因、阈值、已注入项的分数。request ID 用来关联受控的请求日志，不把查询正文直接复制进记忆审计日志。

|---|---|---:|---|---|---:|---|
| 2026-10-21T15:55:08+08:00 | req-demo-001 | 1 | m1,m2 | m3:source; m4:source; m5:ttl | — | 0.183,0.000 |

这样既能查到哪些记忆真正注入，也能查到候选为何被拦。生产日志仍需设置权限、脱敏和保留期限；request ID 应为不含用户文本的引用标识。

```python
# recall_trace.py
"""记录实际注入与拦截决策；不保存查询正文。"""

import json


def record_trace(ts, request_id, turn, injected, blocked, threshold=None):
    """injected: [(memory_id, score)]；blocked: [(memory_id, reason)]。"""
    return {
        "ts": ts,
        "request_id": request_id,
        "turn": turn,
        "injected_ids": [memory_id for memory_id, _ in injected],
        "blocked": [{"id": memory_id, "reason": reason} for memory_id, reason in blocked],
        "threshold": threshold,
        "scores": [round(score, 3) for _, score in injected],
    }


def trace_line(row):
    """返回单行 JSON，便于写入受控的 append-only 日志。"""
    return json.dumps(row, ensure_ascii=False, separators=(",", ":"))


if __name__ == "__main__":
    timestamp = "2026-10-21T15:55:08+08:00"  # 固定示例时间，保证输出可复现
    first = record_trace(
        timestamp,
        "req-demo-001",
        1,
        [("m1", 0.183), ("m2", 0.0)],
        [("m3", "source_policy"), ("m4", "source_policy"), ("m5", "expired")],
    )
    second = record_trace(
        timestamp,
        "req-demo-002",
        2,
        [("m5", 0.512)],
        [("m2", "below_similarity_threshold")],
        threshold=0.30,
    )
    lines = [trace_line(first), trace_line(second)]
    print(lines[0])
    print(lines[1])
```

**二，做「关闭记忆」的诊断对照。** 固定同一任务，分别运行带记忆与不带记忆的版本，可以帮助定位输出差异；它本身不能证明普遍因果，也无法从单次对照估计效果。要评估质量，应使用多条代表性任务，固定模型/API/提示与记忆快照，配对运行并按预先定义的任务判据评分，同时保存原始响应、usage 和注入轨迹。历史 A/B 记录缺这些材料，故只作为待验证的观察。

## 本节小结

三句话：

1. 误召回与漏召回都可能伤害任务；要比较目标任务的影响和可发现性，不能把一条历史摘要推广成普遍规律。
2. 来源与 TTL 可按明确定义的策略执行；相关性阈值也可以程序化，但它的选择和适用性必须经过校准与独立验证。
3. 常驻记忆数量按预算和任务证据决定，记录实际注入与拦截决策，并为日志设定隐私边界。
## 常见坑

- **把候选命中当成应该注入。** 检索分数只生成候选；来源、时效、相关性和任务策略仍需分别判定。
- **用同一分数阈值替代来源、TTL 与相关性策略。** 它们应分别定义；相关性阈值需用目标数据校准。
- **把一个词面分数当成普遍相关性判据。** 本例中有一组需要区分的候选同为 0.000；这暴露了该评分器的区分能力不足。
- **把历史单次观察当作普遍规律。** 对照差异可提示风险，但要估计发生率或任务影响，仍需固定任务、保存原始轨迹并运行有重复的配对评测。
- **把「常驻 2–3 条」当作标准答案。** 这只是设计起点，需按 token 成本、实际使用率和错误代价评估。
