记忆写进去了，下一个问题是**什么时候取出来**。

这个问题看起来比写入简单 —— 相关就取，不相关就不取。但「相关」是一个判断，而任何判断都会有错。这一节要看的是：判断错的代价有多大。

## 实测：一条不相关的记忆，会悄悄改写输出

任务很简单：**写一段部署脚本，把服务发到服务器上**。三种条件下各跑一遍（2026-10-08）：

| 条件 | 输出 | 是否用到注入的记忆 |
|---|---|---|
| A 不注入记忆 | npm ci && npm run build，再 scp 与 systemctl restart | — |
| B 注入**不相关**记忆：「用户的脚本必须用 Python 2.7」 | python2.7 -m pip install -r requirements.txt …… | ⚠️ **跟随了** |
| C 注入**相关**记忆：「目标是 k8s，走 kubectl」 | kubectl apply / kubectl set image / rollout status | ✅ 正确采纳 |

条件 B 是关键。那条记忆和「部署脚本」这个任务并没有关系 —— 它是很久以前观测到的一条环境约束。但模型**照做了**：输出里出现了 python2.7 -m pip install，而条件 A 里根本没有这一句。

而且注意：**没有任何东西提示你这件事发生了。** 输出格式正常、命令合法、语法正确。它不是「错误」，只是「被一条不该出现的记忆带偏了」。

## 为什么误召回比召回不到更糟

这是本节最重要的一个判断，值得说清楚推理链条。

**召回不到的时候**，模型面对的是信息缺失。它至少有机会说「我不确定」或者「资料里没有提到」—— 第 5 章实测过，只要指令明确，模型会如实承认不知道。

**误召回的时候**，模型拿到的是一条**看起来可信、但与当前情境无关**的信息。它没有理由怀疑它（记忆库本来就是「可信来源」），于是会把它当作前提使用。结果是带着错误前提产出一个逻辑自洽的答案。

两者的差别不在严重程度，而在**可发现性**：前者常常会暴露（模型说不知道、或者答得很虚），后者在日志里完全看不出来。

所以召回的门槛应该比检索更高 —— 检索误召回一段无关文本，模型可能直接忽略；而记忆带着「这是关于用户的已知事实」这个身份，权重完全不同。

## 三道闸门

好在召回可以通过几道**确定性的**闸门来控制，而且它们的可靠程度差别很大。

**来源闸门。** 只注入「用户明说」的记忆，把「模型推断」与「系统观测」整体挡在外面。它是纯规则，行为完全可预测 —— 本次实验里它稳定地拦下 2 条。

**时效闸门。** 超过一定天数没更新的记忆降权或排除。同样是纯规则。它防的是那种「三年前观测到、早就过期」的约束 —— 上面条件 B 里的那条正属于这类。

**相关度闸门。** 这一道最难，因为「相关」需要语义判断。本节末尾的代码会展示它的局限：用词面重合打分时，同一个问题里该注入的那条可能得 0.000，而不该注入的也是 0.000 —— **它只能排序，不能按阈值过滤**。

这也解释了为什么记忆的召回必须建立在第 6 章那套检索能力之上：相关性判断是一个检索问题，而纯词法解决不了它。

## 注入还是做成工具

最后是形态问题：记忆该**每轮自动注入**，还是**做成工具让模型自己查**？

判据是「这条记忆是普遍相关，还是条件相关」。

**普遍相关**（回复语言偏好、输出格式偏好）适合少量常驻注入 —— 但必须严格控制条数，因为它们每一轮都要重新计费（第 1 节那张表在这里同样成立）。

**条件相关**（「这个项目上次用的部署环境」）适合做成工具按需查。自动注入的代价是：不相关的记忆会影响行为，而且失败是静默的。

一个务实的中间形态：**常驻注入只保留 2 到 3 条最稳定的偏好，其余全部走工具。** 这样把静默失败的面积压到最小，同时保留了按需取回的能力。

## 完整可运行代码

```python
"""召回闸门：把「不该注入的记忆」拦在上下文之外。

三道闸门分开看，因为它们的可靠程度完全不同：
  - 来源闸门：确定性规则，最可靠
  - 时效闸门：确定性规则，可靠
  - 相关度闸门：需要语义判断，纯词法基本不可用（见第 6 章）

实跑状态：2026-10-08，已跑通。
"""

import math
import re

TODAY = "2026-10-08"
MAX_AGE_DAYS = 180

MEMORIES = [
    {"id": "m1", "text": "用户偏好表格形式的输出。", "source": "用户明说", "at": "2026-09-20"},
    {"id": "m2", "text": "用户团队使用 PostgreSQL，不要给 MySQL 方案。", "source": "用户明说", "at": "2026-09-28"},
    {"id": "m3", "text": "用户的所有脚本必须用 Python 2.7 编写。", "source": "系统观测", "at": "2025-01-05"},
    {"id": "m4", "text": "用户可能对价格比较敏感。", "source": "模型推断", "at": "2026-10-01"},
]
ALLOWED_SOURCES = ("用户明说",)   # 只有用户明确说过的才允许长期注入


def tokenize(text):
    text = text.lower()
    out = re.findall(r"[a-z0-9_]+", text)
    for run in re.findall(r"[\u4e00-\u9fff]+", text):
        out.extend(run[i:i + 2] for i in range(len(run) - 1))
    return out


def lexical_score(query, text):
    a, b = set(tokenize(query)), set(tokenize(text))
    if not a or not b:
        return 0.0
    return len(a & b) / math.sqrt(len(a) * len(b))


def age_days(at):
    y1, m1, d1 = (int(x) for x in at.split("-"))
    y2, m2, d2 = (int(x) for x in TODAY.split("-"))
    return (y2 - y1) * 365 + (m2 - m1) * 30 + (d2 - d1)


def recall(query):
    kept, blocked = [], []
    for m in MEMORIES:
        if m["source"] not in ALLOWED_SOURCES:
            blocked.append((m, "来源闸门：%s（非用户明说）" % m["source"]))
        elif age_days(m["at"]) > MAX_AGE_DAYS:
            blocked.append((m, "时效闸门：已 %d 天未更新" % age_days(m["at"])))
        else:
            kept.append((m, lexical_score(query, m["text"])))
    return kept, blocked


if __name__ == "__main__":
    for q in ["帮我写一段部署脚本，把服务发到服务器上", "我比较喜欢什么样的输出格式"]:
        print("问题:", q)
        kept, blocked = recall(q)
        for m, s in kept:
            print("  ✅ 候选 [%s] %s（词面相关度 %.3f）" % (m["id"], m["text"], s))
        for m, why in blocked:
            print("  ⛔ %s 拦下 [%s] %s" % (why.split("：")[0], m["id"], why.split("：", 1)[1]))
        print("  → 拦截了 %d 条，候选剩 %d 条" % (len(blocked), len(kept)))
        print()
    print("两个观察：")
    print("1) 来源与时效是确定性规则 —— 每次都拦下同样两条，行为可预测。")
    print("2) 词面相关度只能排序、不能按阈值过滤：m1 在第二个问题里是 0.183，")
    print("   在第一个问题里是 0.000；而 m2 两次都是 0.000 却也没被排除。")
    print("   给一个统一阈值，要么全留要么全砍 —— 这就是纯词法闸门的局限。")
```

实跑输出（2026-10-08）：

```text
  ⛔ 来源闸门 拦下 [m4] 模型推断（非用户明说）
  → 拦截了 2 条，候选剩 2 条

  ✅ 候选 [m1] 用户偏好表格形式的输出。（词面相关度 0.183）
  ✅ 候选 [m2] 用户团队使用 PostgreSQL，不要给 MySQL 的方案。（词面相关度 0.000）
  ⛔ 来源闸门 拦下 [m3] 系统观测（非用户明说）

2) 词面相关度只能排序、不能按阈值过滤：m1 在第二个问题里是 0.183，
   在第一个问题里是 0.000；而 m2 两次都是 0.000 却也没被排除。
   给一个统一阈值，要么全留要么全砍 —— 这就是纯词法闸门的局限。
```

## 注入几条才合适

常驻注入的记忆是**每一轮都要重付**的内容，所以它的条数应该按预算来定，而不是按「可能有用」来定。

一个粗算：假设每条记忆平均 40 token，注入 10 条就是 400 token 一轮；一段 20 轮的对话因此多付 8,000 token。而第 1 节那张表的结论是 —— 这部分成本随轮次累积，不是一次性的。

反过来，注入太少也不行，那等于记忆白做了。建议的做法是按「这条记忆在这一轮真的会被用到吗」分级：

- **第一级（常驻 2 到 3 条）**：几乎每一轮都会影响输出的偏好，例如回复语言、输出格式。
- **第二级（按需取回）**：只在相关话题出现时才有用的信息，例如某个项目的技术栈。
- **第三级（永不注入）**：来源不可靠或已过期的条目 —— 它们只该留在库里等人工确认。

判断一条记忆属于哪一级，有个很实用的操作化问法：**如果把它关掉，这一轮的输出会变吗？** 如果答案是「大多数轮次都不会变」，它就不该常驻。

## 怎么发现误召回

误召回最麻烦的性质是静默，所以它只能靠可观测性来发现。两个具体做法：

**一，把「本轮注入了哪些记忆」写进轨迹。** 要求很低：记下每条被注入记忆的 id 就够。这样当某次输出看起来不对劲时，你能回看当时注入了什么 —— 没有这份记录，你连怀疑的方向都没有。

**二，做一次「关掉记忆」的对照。** 同一个任务，一次带记忆、一次不带，比较输出差异。本次实验正是这么做的：条件 A 与条件 B 的差别只有一条记忆，而输出从 npm 流程变成了 python2.7 流程。这个对照不需要评测集，跑两次就能看出来。

这两个做法合起来，能把「静默失败」转成「可回查的事实」。第 4 阶段会把它们扩成完整的可观测性体系，但记忆系统的门槛其实就这么低 —— **记下注入了什么，并且偶尔关掉它试试。**
## 本节小结

三句话：

1. **误召回的代价高于召回不到**，因为它是静默的 —— 实测里一条无关记忆把部署流程改成了 Python 2.7，而输出看起来完全正常。
2. **来源与时效可以写成确定性规则**，相关度不行 —— 后者本质上是一个检索问题，得靠第 6 章那套能力，而不是一个阈值。
3. **注入条数按预算定，不按「可能有用」定**，并且记录每一轮到底注入了什么。
## 常见坑

- **把召回当成「越全越好」。** 实测里一条不相关的记忆就把部署流程改成了 Python 2.7 流程，而且没有任何提示。
- **用同一个阈值同时管来源、时效与相关度。** 它们应该分开 —— 来源和时效是可写死的规则，相关度不是。
- **指望词面重合做相关度闸门。** 本次代码里它只能排序：该注入的与不该注入的都可能得 0.000。
- **忽略「误召回是静默的」这一性质。** 它不会报错、不会让输出格式异常，只会在某天让你发现行为被一条陈年记忆带偏了。
- **常驻注入一大串记忆。** 每一轮都要重发，而且每一条都是一个静默失败的机会。
