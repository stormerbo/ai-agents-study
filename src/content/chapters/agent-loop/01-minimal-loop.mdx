前一章讲了五种范式。这一章要回答一个更底层的问题：**如果你不用框架，这个循环到底长什么样。**

写一遍的价值不在于「省一个依赖」，而在于你会知道哪些部分是必须的、哪些是框架替你补的。第 5 节会把两者对照起来看。

## 短路径前置与边界

从第 0 章「第一轮动手路径」跳来的读者，先确认自己已经读过消息 API、指令与数据边界，以及工具调用的真实过程。短路径只用一个只读订单 fixture、有限轮数和固定输出上限，目的是看清宿主如何把 `tool_use` 变成本地查询，再把 `tool_result` 交回模型。

这个练习不包含身份认证、持久化恢复或写工具，也不验证模型在所有输入上的选择质量。完整状态恢复见本章后续小节；真实业务接入还需要在工具执行前做身份、资源和参数授权。短路径不改变本章的前置章节，也不代表已经完成阶段 3 的编排项目。

这一节先写出最小的那个版本，并画出它的边界。

## 一个循环只有三个组成部分

**ReAct**（Reasoning + Acting）指的是一种交替进行的循环：模型先「想一步」（reasoning），再「做一个动作」（acting，也就是调用工具），拿到结果再想 —— 直到它觉得可以回答了。它不是某个框架，而是一种把推理和动作写进同一个循环的范式；第 10 章讲它的五种变体，这里只取最朴素的形态。

把 ReAct 的循环拆到底，只剩三样东西：

1. **一份消息历史**（模型看到什么）
2. **一个工具注册表**（能做什么）
3. **一个停止判据**（什么时候结束）

从**控制流骨架**看，界面、日志、重试、并发和持久化不是这个最小循环的组成部分，而是按需求加在外围的能力。但“骨架之外”不等于“生产环境可省”：身份与授权、参数校验、预算与轮数限制、错误处理、持久化恢复等，是否必需取决于风险和运行要求；面向真实用户的系统必须逐项做出明确设计，不能把这段教学代码直接上线。

本节只讲由宿主执行的 **client-side tools**。示例将 `tool_use` 交给本地注册表执行；Anthropic 的 server-side tools 可能以 `server_tool_use` / `mcp_tool_use` 和 `pause_turn` 等形式出现，服务端调用的继续协议不同，不能把响应中的每个调用块都当作本地函数处理。若启用 server tools，应按对应 API 流程单独处理（见 [Anthropic stop reasons](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons) 与[工具调用概览](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）。

最小实现长这样：

```python
messages = [{"role": "user", "content": task}]

while True:
    resp = call_model(messages, tools=registry.specs())
    if resp.stop_reason == "end_turn":
        answer = text_of(resp)
        if not answer.strip():
            raise RuntimeError("end_turn 但没有可展示文本；不能据此认定任务成功")
        return answer
    if resp.stop_reason != "tool_use":
        raise RuntimeError(f"未处理的 stop_reason: {resp.stop_reason}")

    messages.append({"role": "assistant", "content": resp.content})
    results = []
    for block in tool_use_blocks(resp):
        out = registry.execute(block.name, block.input)
        results.append(tool_result(block.id, out))
    messages.append({"role": "user", "content": results})
```

这就是最小骨架。后面四节讲的每一件事，都是往这几行上加的。

这段代码里有三个不是标准库的函数，它们是循环和外界的三个接口点：

- `call_model(messages, tools=...)` —— 把消息历史发给模型，返回一个响应对象。
- `tool_use_blocks(resp)` —— 从响应里挑出「模型想调工具」的那些块。
- `tool_result(block.id, out)` —— 把一次工具执行的结果包装成回填给模型的消息块。

它们长什么样，决定循环能不能接到真模型上。下面把 `call_model` 拆开。

## 真模型那一侧：`call_model` 发什么、收到什么

真实调用只依赖标准库 `urllib`，需要两个环境变量：

> **历史记录的复现边界：** 下方 DeepSeek `deepseek-flash` 的两次响应和两条 400 报文是 2026-10-12 保存进正文的历史摘录；这次审计没有找到配套的原始 HTTP 请求/响应归档、精确端点快照或可复跑脚本，不能独立复现这些具体报文。它们只用于展示当时记录的字段形状，不证明当前 DeepSeek 兼容性、错误文案或模型行为；协议规则以当前 provider 官方文档核对。

- `ANTHROPIC_BASE_URL`：API 的基础地址（厂商官方端点或中转平台给的地址）。
- `ANTHROPIC_AUTH_TOKEN`：调用凭据，在平台控制台生成；本项目放在 `.env.local`，已被 `.gitignore` 覆盖，不会进仓库。

```python
"""最小真实调用：只依赖标准库 urllib。需要上面两个环境变量。"""
import json
import os
import urllib.request

BASE = os.environ["ANTHROPIC_BASE_URL"].rstrip("/")
TOKEN = os.environ["ANTHROPIC_AUTH_TOKEN"]
MODEL = os.environ.get("VERIFY_MODEL", "deepseek-flash")

TOOLS = [{
    "name": "get_weather",
    "description": "查询某个城市某一天的最高气温。",
    "input_schema": {"type": "object",
                     "properties": {"city": {"type": "string"},
                                    "day": {"type": "string", "enum": ["明天", "后天"]}},
                     "required": ["city", "day"]},
}]


def call_model(messages):
    # max_tokens 是输出预算字段：这次调用最多生成多少 token
    body = {"model": MODEL, "max_tokens": 512, "tools": TOOLS, "messages": messages}
    req = urllib.request.Request(
        BASE + "/v1/messages",
        data=json.dumps(body).encode(),
        headers={"content-type": "application/json",
                 "anthropic-version": "2023-06-01",
                 "x-api-key": TOKEN},        # 注意：是 x-api-key，不是 Authorization: Bearer
    )
    with urllib.request.urlopen(req, timeout=120) as r:
        return json.loads(r.read().decode())
```

任务「帮我查一下北京明天的最高气温。」第一次调用在历史记录中返回如下响应摘录（`deepseek-flash`，2026-10-12，未独立复核）：

```json
{
  "id": "3a970f7b-1d41-4f90-8052-07b90bc0d9b9",
  "type": "message",
  "role": "assistant",
  "model": "deepseek-flash",
  "content": [
    {
      "type": "thinking",
      "thinking": "The user wants to know Beijing's high temperature tomorrow. I should call get_weather with city=\"北京\", day=\"明天\".",
      "signature": "3a970f7b-1d41-4f90-8052-07b90bc0d9b9"
    },
    {
      "type": "tool_use",
      "id": "call_00_HBKStfbV27FuShuOllK34287",
      "name": "get_weather",
      "input": {"city": "北京", "day": "明天"}
    }
  ],
  "stop_reason": "tool_use",
  "stop_sequence": null,
  "usage": {"input_tokens": 320, "cache_creation_input_tokens": 0,
            "cache_read_input_tokens": 0, "output_tokens": 81}
}
```

四个字段决定你的循环怎么写：

- `content` 是**块数组**，不是字符串。块靠 `type` 区分：`thinking` 是推理、`tool_use` 是要调工具、`text` 是回答。
- `tool_use.id` 是这次调用的**配对凭证**，回填结果时必须原样带回去。
- `tool_use.input` 已经是**解析好的对象**，不需要再 `json.loads`。
- `stop_reason` 是「模型为什么停下」：在本节的 client-side tool 路径中，`tool_use` 表示需要宿主执行工具并回填结果；`end_turn` 表示模型这一轮自然结束，不等于业务任务成功。Anthropic 当前文档还记录了 `end_turn` 携带空 `content` 的情况；因此不能只看 stop reason 就交付结果，要检查是否存在可展示文本，并由业务闸门判断是否满足任务要求。`max_tokens` 表示达到输出上限，响应可能不完整，不能当作答案成功。Messages API 还有其他停止原因和 server-side tool 流程；这个最小例子只处理客户端 `tool_use` 和非空 `end_turn`，其余一律失败关闭，真实宿主应按所用 API 的完整状态集合分别处理（参见 [Anthropic stop-reason 文档](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)）。

把结果回填之后，第二次请求里的 `messages` 数组长这样 —— 注意 `tool_use.id` 和 `tool_result.tool_use_id` 是同一个字符串：

```json
[
  {"role": "user", "content": "帮我查一下北京明天的最高气温。"},
  {"role": "assistant", "content": [
     {"type": "thinking", "thinking": "...", "signature": "..."},
     {"type": "tool_use", "id": "call_00_HBKStfbV27FuShuOllK34287",
      "name": "get_weather", "input": {"city": "北京", "day": "明天"}}]},
  {"role": "user", "content": [
     {"type": "tool_result", "tool_use_id": "call_00_HBKStfbV27FuShuOllK34287",
      "content": "{\"city\": \"北京\", \"day\": \"明天\", \"temp_c\": 31}"}]}
]
```

那条 `tool_result` 是**一条新的 user 消息**，不是 assistant 消息的一部分 —— 这是最容易写错的地方。第二次调用的历史响应摘录如下（`deepseek-flash`，2026-10-12，未独立复核）：

```json
{
  "content": [
    {"type": "thinking", "thinking": "", "signature": "4874467f-31d9-4811-82ab-364878d61c8a"},
    {"type": "text", "text": "北京明天（明天）的最高气温是 31℃。\n\n需要的话我可以再帮你查后天，或者查其他城市～"}
  ],
  "stop_reason": "end_turn",
  "usage": {"input_tokens": 175, "cache_read_input_tokens": 256, "output_tokens": 27}
}
```

这条历史响应的 `stop_reason` 是 `end_turn`。注意 `usage` 里出现 `cache_read_input_tokens: 256`：缓存读 token 仍属于输入上下文；缓存的具体计价由 provider、模型和当前价格表决定，字段本身不证明当前单价。预算示例应分别保留 provider usage 字段，并在计算费用时核对适用的价格表。

### 假模型字段对照真实字段

本节末尾的 `FakeModel` 用的是自定义字典。看懂这张映射表，你就能把手写循环接到任何兼容端点：

| 假模型里的写法 | 真实响应里的位置 | 说明 |
|---|---|---|
| `{"stop_reason": "tool_use"}` | 顶层 `stop_reason` | 取值同名，语义一致 |
| `{"blocks": [...]}` | 顶层 `content`（数组） | 真实字段叫 `content`，块的类型在 `type` 上 |
| `b["id"]` | `content[i].id`（仅 tool_use 块） | 回填时写成 `tool_result.tool_use_id` |
| `b["name"]` / `b["input"]` | `content[i].name` / `content[i].input` | `input` 已是对象 |
| `{"text": ...}` | `content` 里 `type=="text"` 的块 | 可能有多个文本块 |
| `{"type": "tool_result", ...}` | 下一条 **user** 消息的 `content` 数组 | 必须紧跟 assistant 的 tool_use |

### 写错配对关系会怎样

判据一句话：每个 `tool_result.tool_use_id` 必须对应前一条 assistant 消息里的某个 `tool_use.id`。当时记录的 DeepSeek 兼容端点错误摘录如下（2026-10-12，未独立复核；确切 HTTP 状态与文案应按目标端点验证）：

```json
{"error":{"message":"unexpected `messages.2.content.0: tool_use_id` found in `tool_result` blocks: call_00_WRONG_ID. Each `tool_result` block must have a corresponding `tool_use` block in the previous message.","type":"invalid_request_error"}}
```

另一条历史错误摘录报告了缺少 `tool_result` 的情况（2026-10-12，未独立复核）：

```json
{"error":{"message":"messages.2: `tool_use` ids were found without `tool_result` blocks immediately after: call_00_ABC123. Each `tool_use` block must have a corresponding `tool_result` block in the next message.","type":"invalid_request_error"}}
```

这两类 400 能拦截缺少 `tool_result` 或 ID 配错的消息结构；但协议只验证对话格式，无法证明宿主真的执行过工具。`tool_result` 是调用方提交的内容，可能来自成功结果、执行错误，也可能是不可信或错误的数据。是否执行、执行结果是否可信、调用者是否有权限，都必须由宿主与工具后端负责（参见 [Handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)）。

## 边界在哪

说「最小」的时候，更重要的是说清楚**它省略了什么**。下面这些都不在上面那段代码里，而它们每一个都会在真实系统里变成问题：

| 省略的东西 | 会出什么事 |
|---|---|
| 模型调用轮次上限 | 模型绕圈子时循环永不结束（第 9 章实测过这种卡死）；它不等于工具调用次数上限 |
| 停止原因分支 | 把 `max_tokens`、拒绝或未知原因当作正常答案，导致截断或错误状态被误报成功 |
| 工具参数校验 | 模型给出不存在的工具名或越界参数，直接抛异常 |
| 工具错误标记 | 错误被当正常数据回填，后面每一步都建在它上面（第 4 章实测） |
| 状态持久化 | 进程一挂，整轮任务从头再来 |
| 副作用幂等 | 恢复时重复执行已经生效的操作（第 4 节会实测） |
| 上下文管理 | 历史无限增长，成本按步数累积 |

所以「最小实现」是一个**用来理解结构的东西**，不是一个用来上线的东西。它的价值在于：你知道后面加进来的每一块是在补哪个洞。

预算还要按动作分别计数：本节完整代码的 `max_steps` 统计模型响应轮次；一个模型响应可以包含多个 `tool_use`，所以模型调用次数不等于工具调用次数。示例在最后一个可用模型轮次收到 `tool_use` 时会拒绝执行这批工具，因为没有剩余轮次接收结果；生产宿主仍需另设工具调用/副作用预算，并在每次 dispatch 前检查。`end_turn` 但没有文本时也不能返回空字符串冒充成功。

## 循环的边界其实不在代码里

有一个容易被忽略的观察：**上面那段骨架没有一行是业务逻辑。**

任务描述、工具定义、停止判据 —— 它们都在循环之外。循环本身只做一件事：**在「模型决策」和「执行动作」之间来回搬运。** 这也解释了为什么这一章讲的东西可以跨任务复用：它是骨架，不是内容。

反过来，一个常见的设计错误是把业务判断塞进循环里：

```python
# ❌ 循环开始知道业务了
if "订单" in task and step > 3:
    messages.append({"role": "user", "content": "别忘了检查库存"})
```

这段代码一出现，循环就不再是骨架了 —— 它变成了一段只对某一类任务有效的流程，而且这段流程的判据藏在循环内部，改任务时你会忘记它。

正确的做法是把这类信息放进 **system 提示**或**工具描述**里，让循环保持无知。对本节使用的 Anthropic Messages API，首轮 system 提示通过请求体顶层 `system` 参数传入，不是 `messages` 数组里的第一条 `role: "system"` 消息。Anthropic 当前文档另列了部分模型支持的 beta 中途 system message，但这不改变首轮写法；其他 API 的消息格式要按各自文档核对（见 [Messages API 参考](https://platform.claude.com/docs/en/api/messages) 与[中途 system messages 文档](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)）。本节前面的最小请求没有设置 system prompt，所以它的 `messages` 历史不含该字段。第 2 节的工具注册表和第 3 节的闸门都遵守这条。

## 循环边界的一个具体判据

最后给一条代码审查启发：如果通用循环里出现任务相关常量（某个工具名、某个业务字段、某句任务提示），先检查这段逻辑是否该交给注册表、schema、提示模板或业务闸门。少数协议适配器确实需要处理 provider-specific 字段；关键是不要把业务规则藏进通用控制流。

- 工具名 → 应该在注册表里
- 字段名 → 应该在 schema 里（schema 指的是工具参数的 JSON 结构定义：有哪些字段、类型是什么、哪些必填）
- 提示语 → 应该在 system 或工具描述里
- 完成判据 → 应该在闸门里

循环本身只应该认三样东西：**消息、工具调用块、停止原因。** 消息、工具调用块和停止原因的**外层结构**由 API 协议定义；但消息内容、工具名和参数承载着业务语义。通用循环不应自行解释这些业务值，而应按协议解析后交给工具注册表和业务闸门。因此它能复用的是控制流骨架，不是与业务完全无关。

## 三种边界情况

最小循环能跑通正常路径，但真实系统里最先遇到的是这三种边界。它们都是我在实现这一章的代码时实际撞到的。

**一、模型调用了不存在的工具。** 它可能拼错名字，也可能用一个你在旧版本里删掉的工具。若注册表直接用字典索引且没有捕获异常（如 `registry[name]`），就会抛 `KeyError` 并终止循环；也可以把它转换为带 `is_error: true` 的 `tool_result`，让模型看到具体失败原因后再尝试。是否能改正取决于模型与任务，不能保证。下面的可运行示例采用后一种教学策略；生产实现还需限制错误重试次数。

**二、同一轮里重复调用同一个工具。** 模型可以在一次回复里发出两个内容相同的 `tool_use` 块。多个块出现在同一回复，只说明模型一次提出了多个调用；由宿主决定串行还是并发执行。Anthropic 文档明确由宿主选择串行、并行或混合执行（见[Parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)）；本节的 `for` 循环按返回顺序串行执行，但相同副作用调用仍会真实执行两次。如果工具是幂等的（如纯查询），重复的影响较小；如果它有副作用，就是一个隐藏的重复。

**三、在没有工具结果的情况下直接给答案。** 通用循环不知道某个任务是否必须先查数据；模型可以跳过工具、凭已有知识回答，而 `end_turn` 只表示这一轮结束，不表示任务事实已经核验。若宿主既不强制必要工具调用，也不记录并检查工具轨迹，答案可能看起来正常。第 5 章实测过这种幻觉（schema 强制要一个状态字段，模型 5/5 编了一个）；生产系统应按任务需要添加业务闸门和可审计轨迹。

从可观测性看，第三种尤其容易漏掉：前两种通常留下错误或工具调用记录，而跳过工具后直接回答可能看起来正常。是否最危险仍取决于任务的业务后果。

    E -->|否| F2["或回填 is_error=true 的 tool_result"]
    F2 --> J
    E -->|是| G["执行"]
    G --> H{"有副作用吗？"}
    H -->|"有"| I["⚠️ 边界二：同一轮重复调用<br/>就会真的执行两次"]
    H -->|"没有"| J["回填结果"]
    I --> J
    J --> B
    C -->|"end_turn"| K["模型结束本轮"]
    K --> L{"宿主是否强制要求查询？"}
    L -->|"是"| M["检查工具轨迹；未查到就拒绝完成"]
    L -->|"否"| N["正常返回，但不能证明事实已核验"]
`}
/>

## 循环该不该知道自己在第几步

一个看似无害、其实影响很大的设计问题。

**记录步数是必须的**（预算、日志、熔断都要用它）。但**把步数告诉模型**是另一件事，而且通常不该做。

第一，它可能变成进度信号。如果你把「这是第 3 步，最多 10 步」放进上下文，模型可能据此调整规划或更早收敛；是否跳过验证、合并操作取决于模型与任务，不能当成必然结果。把步数限制留在宿主侧，是一种减少无关运行细节、避免提示改变行为的工程选择。

第二，它会把运维状态带入模型上下文。步数上限通常属于宿主的运行控制信息；只有当任务规划确实需要知道剩余预算时才提供。它不是安全边界，不能靠不告诉模型来替代服务端预算强制。

第三，它不稳定。改了上限，模型的行为就变了 —— 而这两件事本该无关。

如果任务需要模型知道「还剩多少余量」，可以把经过筛选的剩余预算作为动态上下文或工具结果提供，同时仍由宿主强制执行上限。放在工具反馈里不天然比放进 system prompt 更有效；应按任务比较提前告知、临近上限告知和完全不告知时的质量、成本与违规率。

一个例外：**长任务的检查点**。如果任务跨越几十步，把「已完成步骤的摘要」给模型是有价值的（这就是第 3 章讲的压缩）。但那是**业务状态**，不是**步数计数器** —— 两者容易混，要注意区分。

## 完整可运行代码

下面是一个最小的、能真正跑起来的循环。它用脚本化的动作策略代替模型，所以不需要凭据也能跑 —— 这样你能专注在骨架本身。

```python
"""最小的 agent 循环：最小循环骨架。

用脚本化的动作策略代替模型，所以不需要凭据也能跑 ——
你能专注在骨架本身，而不是模型的输出。

实跑状态：2026-10-09，已跑通。
"""

import json


class FakeModel:
    """代替真模型的确定性策略：按脚本产出「工具调用」或「最终答案」。

    为便于阅读，它把真实响应的 content/text 摘成 blocks/text 字段；
    回填的 tool_result 则保留 Messages API 的消息字段。
    """

    def __init__(self, script):
        self.script = script
        self.i = 0

    def __call__(self, messages):
        self.last_messages = messages
        if self.i >= len(self.script):
            return {"stop_reason": "end_turn", "text": "完成了。"}
        step = self.script[self.i]
        self.i += 1
        if step[0] == "tool":
            return {"stop_reason": "tool_use",
                    "blocks": [{"type": "tool_use", "id": "t%d" % self.i,
                                "name": step[1], "input": step[2]}]}
        return {"stop_reason": "end_turn", "text": step[1]}


REGISTRY = {
    "add": lambda a, b: {"sum": a + b},
    "double": lambda x: {"result": x * 2},
}


def execute(name, args):
    """分发。真实实现里这里还要做参数校验（见第 2 节）。"""
    if name not in REGISTRY:
        return "Error: 未知工具 %r" % name, True
    value = REGISTRY[name](**args)
    return json.dumps(value, ensure_ascii=False), False


def run(task, model, max_steps=8):
    """最小骨架。后面几节加的东西都挂在它上面。"""
    messages = [{"role": "user", "content": task}]
    for step in range(1, max_steps + 1):
        resp = model(messages)
        if resp["stop_reason"] == "end_turn":
            answer = resp.get("text")
            if not isinstance(answer, str) or not answer.strip():
                raise RuntimeError("end_turn 但没有可展示文本；不能据此认定任务成功")
            return answer, step
        if resp["stop_reason"] != "tool_use":
            raise RuntimeError("未处理的 stop_reason: %s" % resp["stop_reason"])
        if step == max_steps:
            return "（达到步数上限；最后一轮的 tool_use 不执行）", step
        messages.append({"role": "assistant", "content": resp["blocks"]})
        results = []
        for b in resp["blocks"]:
            out, is_error = execute(b["name"], b["input"])
            result = {"type": "tool_result", "tool_use_id": b["id"], "content": out}
            if is_error:
                result["is_error"] = True
            results.append(result)
        messages.append({"role": "user", "content": results})
    return "（达到步数上限）", max_steps


if __name__ == "__main__":
    # 正常路径
    m = FakeModel([("tool", "add", {"a": 3, "b": 4}),
                   ("tool", "double", {"x": 7}),
                   ("final", "结果是 14。")])
    text, steps = run("算 (3+4)*2", m)
    print("正常路径：%s（%d 步）" % (text, steps))

    # 边界一：工具名不存在 —— 观察宿主如何把错误回填给模型
    m2 = FakeModel([("tool", "add_two", {"a": 1, "b": 2}), ("final", "收到工具错误。")])
    text2, steps2 = run("算 1+2", m2)
    print("工具错误回填：%s" % m2.last_messages[-1]["content"])
    print("模型结束：%s（%d 步）" % (text2, steps2))

    # 边界二：绕圈子 —— 最小循环无法自救，只能撞上限
    m3 = FakeModel([("tool", "add", {"a": 1, "b": 1})] * 20)
    text3, steps3 = run("算 1+1", m3)
    print("绕圈子：  %s（%d 步）" % (text3, steps3))
    print()
    print("第三个结果说明最小循环缺了什么：它没有能力识别「在原地打转」。")
    print("第 3 节会给它加上这个能力。")
```

## 怎么测一个循环

最后补一个工程问题：**这种循环怎么写测试？**

难点在于它依赖模型，而模型不稳定。可行的做法是把测试分成两层：

**骨架层用假的模型。** 把「调模型」也做成一个可注入的依赖，测试时注入一个脚本化的策略（就是本节代码里用的那种）。这样能确定性地覆盖所有边界：工具名错、参数越界、绕圈子、中途崩溃。**循环的 bug 几乎都在这层**，而这层不需要花一分钱 API 费。

**端到端层用真模型，先跑少量 smoke case。** 可以从正常任务、多步任务和预期失败任务各选一个，检查模型与骨架能否完成基本交互；这只是冒烟覆盖，不是普遍充分的回归集。是否增加用例，要按风险、任务分布和成本来定。

两层分开的价值：**骨架的回归测试要能跑在 CI 里、不花钱、不抖动。** 如果你的循环测试依赖真模型，它就会变成「偶尔红」的那种测试 —— 然后所有人开始忽略它。

## 常见坑

- **把最小循环直接上线。** 它省略的这些保护每一样都可能造成事故，其中幂等和步数上限是最常见的两个。
- **把业务判断写进循环。** 判据是：循环里出现任务相关的常量就写错了地方。
- **用「文本里有没有工具名」判断该不该执行工具。** 判据应该是停止原因，那是协议层的事实。
- **忘记把工具结果追加成一条新消息。** 只记进日志的话，模型下一轮看不到，会重复调用同一个工具。
- **以为循环需要知道任务是什么。** 它不需要 —— 任务在消息里，工具在注册表里，它只是一个搬运工。
