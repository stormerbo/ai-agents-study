前一章讲了五种范式。这一章要回答一个更底层的问题：**如果你不用框架，这个循环到底长什么样。**

写一遍的价值不在于「省一个依赖」，而在于你会知道哪些部分是必须的、哪些是框架替你补的。第 5 节会把两者对照起来看。

这一节先写出最小的那个版本，并画出它的边界。

## 一个循环只有三个组成部分

把 ReAct 的循环拆到底，只剩三样东西：

1. **一份消息历史**（模型看到什么）
2. **一个工具注册表**（能做什么）
3. **一个停止判据**（什么时候结束）

除此之外都是可选的。界面、日志、重试、并发、持久化都是围着这三样长出来的。

最小实现长这样：

```python
messages = [{"role": "user", "content": task}]

while True:
    resp = call_model(messages, tools=registry.specs())
    if resp.stop_reason != "tool_use":
        return text_of(resp)

    messages.append({"role": "assistant", "content": resp.content})
    results = []
    for block in tool_use_blocks(resp):
        out = registry.execute(block.name, block.input)
        results.append(tool_result(block.id, out))
    messages.append({"role": "user", "content": results})
```

**十七行。** 这就是全部。后面四节讲的每一件事，都是往这十七行上加的。

## 边界在哪

说「最小」的时候，更重要的是说清楚**它省略了什么**。下面这些都不在上面那段代码里，而它们每一个都会在真实系统里变成问题：

| 省略的东西 | 会出什么事 |
|---|---|
| 步数上限 | 模型绕圈子时循环永不结束（第 9 章实测过这种卡死） |
| 工具参数校验 | 模型给出不存在的工具名或越界参数，直接抛异常 |
| 工具错误标记 | 错误被当正常数据回填，后面每一步都建在它上面（第 4 章实测） |
| 状态持久化 | 进程一挂，整轮任务从头再来 |
| 副作用幂等 | 恢复时重复执行已经生效的操作（第 4 节会实测） |
| 上下文管理 | 历史无限增长，成本按步数累积 |

所以「最小实现」是一个**用来理解结构的东西**，不是一个用来上线的东西。它的价值在于：你知道后面加进来的每一块是在补哪个洞。

## 循环的边界其实不在代码里

有一个容易被忽略的观察：**上面那十七行没有一行是业务逻辑。**

任务描述、工具定义、停止判据 —— 它们都在循环之外。循环本身只做一件事：**在「模型决策」和「执行动作」之间来回搬运。** 这也解释了为什么这一章讲的东西可以跨任务复用：它是骨架，不是内容。

反过来，一个常见的设计错误是把业务判断塞进循环里：

```python
# ❌ 循环开始知道业务了
if "订单" in task and step > 3:
    messages.append({"role": "user", "content": "别忘了检查库存"})
```

这段代码一出现，循环就不再是骨架了 —— 它变成了一段只对某一类任务有效的流程，而且这段流程的判据藏在循环内部，改任务时你会忘记它。

正确的做法是把这类信息放进 **system 提示**或**工具描述**里，让循环保持无知。第 2 节的工具注册表和第 3 节的闸门都遵守这条。

## 循环边界的一个具体判据

最后给一条实践判据：**如果循环里出现了任务相关的常量（某个工具名、某个字段名、某句提示），那它就写错地方了。**

- 工具名 → 应该在注册表里
- 字段名 → 应该在 schema 里
- 提示语 → 应该在 system 或工具描述里
- 完成判据 → 应该在闸门里

循环本身只应该认三样东西：**消息、工具调用块、停止原因。** 这三样都是协议层的概念，与你的业务无关。

## 三种边界情况

最小循环能跑通正常路径，但真实系统里最先遇到的是这三种边界。它们都是我在实现这一章的代码时实际撞到的。

**一、模型调用了不存在的工具。** 它可能拼错名字，也可能用一个你在旧版本里删掉的工具。最小实现里的 `registry.execute(name, ...)` 会直接抛 `KeyError`，循环当场终止。而模型其实完全有能力换一个工具 —— 只要你告诉它「没有这个工具」。

**二、同一轮里重复调用同一个工具。** 模型可以在一次回复里发出两个内容相同的工具调用块。第 1 章讲过，工具调用是并发的（多个块在一次回复里），所以这会变成两次真实执行。如果你的工具是幂等的（查数据），无所谓；如果它有副作用，就是一个隐藏的重复。

**三、在没有工具结果的情况下直接给答案。** 这是最隐蔽的一种：模型跳过了工具，基于自己的记忆回答了。循环会正常结束、返回一段合理的文本，而**你没有任何信号知道它没查数据**。第 5 章实测过这种幻觉（schema 强制要一个状态字段，模型 5/5 编了一个），在循环里它的表现是「跑完了，答案看起来也对」。

三个边界里，第三个最危险 —— 因为前两个会报错或留下痕迹，第三个什么都没发生。

## 循环该不该知道自己在第几步

一个看似无害、其实影响很大的设计问题。

**记录步数是必须的**（预算、日志、熔断都要用它）。但**把步数告诉模型**是另一件事，而且通常不该做。

第一，它会被当成进度暗示。如果你在消息里写「这是第 3 步，最多 10 步」，模型会开始「节省步数」——表现为跳过验证、合并操作、提前给答案。**你在教它偷工减料。**

第二，它会泄漏你的实现细节。步数上限是运维参数，不是任务信息；把它写进上下文，等于让模型知道你的预算结构。

第三，它不稳定。改了上限，模型的行为就变了 —— 而这两件事本该无关。

那如果需要让它知道「还有多少余量」怎么办？答案是**通过工具反馈，而不是通过系统提示**。比如当步数接近上限时，闸门可以往最后一条工具结果里追加一句「本次任务剩余步骤不多，请优先给出阶段性结论」。这比一开始就把预算摊开更有效 —— 因为它出现在真正需要收敛的时刻。

一个例外：**长任务的检查点**。如果任务跨越几十步，把「已完成步骤的摘要」给模型是有价值的（这就是第 3 章讲的压缩）。但那是**业务状态**，不是**步数计数器** —— 两者容易混，要注意区分。

## 完整可运行代码

下面是一个最小的、能真正跑起来的循环。它用脚本化的动作策略代替模型，所以不需要凭据也能跑 —— 这样你能专注在骨架本身。

```python
"""最小的 agent 循环：十七行的骨架。

用脚本化的动作策略代替模型，所以不需要凭据也能跑 ——
你能专注在骨架本身，而不是模型的输出。

实跑状态：2026-10-09，已跑通。
"""


class FakeModel:
    """代替真模型的确定性策略：按脚本产出「工具调用」或「最终答案」。

    真模型返回的是 content blocks 和 stop_reason，这里用同样的形状，
    只是内容是预先写好的。
    """

    def __init__(self, script):
        self.script = script
        self.i = 0

    def __call__(self, messages):
        if self.i >= len(self.script):
            return {"stop_reason": "end_turn", "text": "完成了。"}
        step = self.script[self.i]
        self.i += 1
        if step[0] == "tool":
            return {"stop_reason": "tool_use",
                    "blocks": [{"type": "tool_use", "id": "t%d" % self.i,
                                "name": step[1], "input": step[2]}]}
        return {"stop_reason": "end_turn", "text": step[1]}


REGISTRY = {
    "add": lambda a, b: {"sum": a + b},
    "double": lambda x: {"result": x * 2},
}


def execute(name, args):
    """分发。真实实现里这里还要做参数校验（见第 2 节）。"""
    if name not in REGISTRY:
        return {"error": "没有名为 %s 的工具" % name}
    return REGISTRY[name](**args)


def run(task, model, max_steps=8):
    """十七行的骨架。后面几节加的东西都挂在它上面。"""
    messages = [{"role": "user", "content": task}]
    for step in range(1, max_steps + 1):
        resp = model(messages)
        if resp["stop_reason"] != "tool_use":
            return resp["text"], step
        messages.append({"role": "assistant", "content": resp["blocks"]})
        results = []
        for b in resp["blocks"]:
            out = execute(b["name"], b["input"])
            results.append({"type": "tool_result", "tool_use_id": b["id"], "content": out})
        messages.append({"role": "user", "content": results})
    return "（达到步数上限）", max_steps


if __name__ == "__main__":
    # 正常路径
    m = FakeModel([("tool", "add", {"a": 3, "b": 4}),
                   ("tool", "double", {"x": 7}),
                   ("final", "结果是 14。")])
    text, steps = run("算 (3+4)*2", m)
    print("正常路径：%s（%d 步）" % (text, steps))

    # 边界一：工具名不存在 —— 看错误怎么被翻译
    m2 = FakeModel([("tool", "add_two", {"a": 1, "b": 2}), ("final", "换个工具重试。")])
    text2, steps2 = run("算 1+2", m2)
    print("工具名错：%s（%d 步）" % (text2, steps2))

    # 边界二：绕圈子 —— 最小循环无法自救，只能撞上限
    m3 = FakeModel([("tool", "add", {"a": 1, "b": 1})] * 20)
    text3, steps3 = run("算 1+1", m3)
    print("绕圈子：  %s（%d 步）" % (text3, steps3))
    print()
    print("第三个结果说明最小循环缺了什么：它没有能力识别「在原地打转」。")
    print("第 3 节会给它加上这个能力。")
```

## 怎么测一个循环

最后补一个工程问题：**这种循环怎么写测试？**

难点在于它依赖模型，而模型不稳定。可行的做法是把测试分成两层：

**骨架层用假的模型。** 把「调模型」也做成一个可注入的依赖，测试时注入一个脚本化的策略（就是本节代码里用的那种）。这样能确定性地覆盖所有边界：工具名错、参数越界、绕圈子、中途崩溃。**循环的 bug 几乎都在这层**，而这层不需要花一分钱 API 费。

**端到端层用真模型，只测少量路径。** 三条就够：一个正常任务、一个需要多步的任务、一个必然失败的任务（比如工具永远返回错误）。这一层测的是「模型和骨架配合得对不对」，不是骨架本身。

两层分开的价值：**骨架的回归测试要能跑在 CI 里、不花钱、不抖动。** 如果你的循环测试依赖真模型，它就会变成「偶尔红」的那种测试 —— 然后所有人开始忽略它。

## 常见坑

- **把最小的十七行直接上线。** 它省掉的六样东西每一样都会变成事故，其中幂等和步数上限是最常见的两个。
- **把业务判断写进循环。** 判据是：循环里出现任务相关的常量就写错了地方。
- **用「文本里有没有工具名」判断该不该执行工具。** 判据应该是停止原因，那是协议层的事实。
- **忘记把工具结果追加成一条新消息。** 只记进日志的话，模型下一轮看不到，会重复调用同一个工具。
- **以为循环需要知道任务是什么。** 它不需要 —— 任务在消息里，工具在注册表里，它只是一个搬运工。
