前两节的循环都有一个隐含假设：**它会一直跑到结束。** 真实系统里这个假设不成立 —— 进程会被重启、部署会滚动、机器会挂。一个跑了 8 步的任务，在第 7 步崩溃之后应该怎么办？

答案看起来很简单：把状态存下来，恢复时接着跑。但这里藏着一个**每一轮都会踩的坑**，这一节用实测把它挖出来。

## 循环的状态到底是什么

先把「状态」这个词拆开。一个 agent 循环有三个层次的东西，它们的持久化难度完全不同：

| 层次 | 内容 | 能不能序列化 |
|---|---|---|
| **消息历史** | 模型看到的请求/响应与工具往返 | 规范化后通常可序列化；多模态内容可能要存对象引用，且格式受 provider/schema 版本影响 |
| **进度位置** | 走到第几步、完成到哪 | 通常可存为步骤、状态和版本化检查点 |
| **外部副作用** | 已经写进数据库/文件/支付系统的东西 | 外部效果不会随本地 checkpoint 自动回滚；可否补偿或查询要看下游能力 |

前两项描述的是宿主已记录的状态，第三项是外部系统已经发生的事实。恢复可以重放本地数据，却不能自动把数据库、支付服务或邮件收件箱回到旧时刻；具体操作可能有补偿、查询或幂等重放接口，必须按下游契约处理。

## 实测：状态落盘和副作用之间的缝

设计一个最小实验。任务：创建三条记录（u1、u2、u3）。循环每一步做两件事：执行工具（产生副作用），然后把进度落盘。

在第 2 步**工具执行之后、状态落盘之前**模拟一次崩溃。然后从落盘的进度恢复，跑完。看最终盘面上有几条记录。

两个版本，唯一差别是工具是否幂等：

| 版本 | 崩溃后盘面 | 恢复跑完后的写入序列 | 最终条数 |
|---|---|---|---|
| 朴素版 | 2 条 | `u1, u2, u2, u3` | **4 条（重复 1）** |
| 幂等版 | 2 条 | `u1, u2, u3` | 3 条 ✅ |

（实跑数据，2026-10-09。脚本用脚本化策略，结果完全可复现。）

**朴素版把 u2 写了两遍。** 原因很直白：崩溃时副作用已经发生了（u2 已写入），但进度还停在「第 1 步完成」，所以恢复后循环重做了第 2 步 —— 而重做意味着再写一次。

在这个特定崩溃点，恢复逻辑会再次尝试第 2 步，所以这次操作呈现 at-least-once 重放。它不证明所有 agent 执行都有相同投递语义；关键取决于副作用与 checkpoint 的提交顺序。若改成先推进 checkpoint 再做副作用，则可能漏做操作。

## 这里有一个我差点报错的测量陷阱

第一次跑这个实验时，两版的结果都是「3 条，没有重复」。看起来结论是「朴素版也没问题」。

**错的是我的计数方法。** 我数的是**去重后的 id 集合**：`len({"u1","u2","u3"})` = 3。而重复写入同一个 id 在集合里根本看不出来。

改成数**文件行数**之后，朴素版立刻变成 4 行，写入序列是 `u1, u2, u2, u3`。

这个错误的类型和第 8 章那次「解析器贪婪匹配」是同一个：**测量方法把要测的东西藏起来了。** 当时是把「解析失败」记成了「模型全错」，这次是把「重复写入」记成了「正常」。两次的共同点是：**结果看起来完全合理，所以不会有人去质疑它。**

教训可以写得很具体：**当你测的是「有没有重复」时，计数方式必须能表达重复。** 集合、去重、distinct count —— 这些默认行为都会把重复吃掉。

## 三类恢复策略与适用边界

知道了问题的形状，解法就清楚了。

**一、让接收方按稳定操作键幂等处理。** 本地教学脚本在单进程顺序执行下先查 id 再写；生产环境不能把“先查再插入”当作并发安全保证。若副作用与业务记录在同一数据库，可用唯一约束/原子 upsert，并在同一事务保存首次结果；若副作用发生在外部 API，必须确认该接收方支持幂等键或提供可查询的操作状态。重试要复用同一个操作键与相同参数，不能每次生成新键。

这是常用的首选路线，但它不等于跨系统 exactly-once。幂等键需绑定到业务操作并保存足够长时间；模型返回的 `tool_use.id` 只用于协议结果配对，不应默认充当持久的业务幂等键。

**二、先持久化意图，再做对账。** 发出副作用前记录操作键、不可变参数摘要和 `pending` 状态；得到可确认结果后再记录 `succeeded` 或确定失败。若进程在两者之间崩溃，状态应是 `outcome_unknown`，先查询下游或用同一幂等键对账，不要把“记录了意图”误当成已执行，也不要盲目换键重试。

意图记录并不会自动与外部系统形成两阶段提交；除非两边共享原子事务或协议，否则仍有“外部效果已发生、回执未落盘”的窗口。无法确认时应暂停任务、报告结果未知并交由对账流程处理。第 4 章一次模型响应选择了不重试，但这只是该样本的行为观察，不能作为防重复的控制措施。

**三、使用操作账本/去重表。** 它可以保存 operation key、参数 hash、状态和首次结果，供重试与恢复查询。但如果账本与外部副作用不在同一原子边界、下游也不识别该 key，单有一张本地表仍解决不了跨系统崩溃窗口。

方案选择取决于副作用在哪个系统、接收方是否支持幂等键、能否查询/补偿，以及不可判定时由谁处理；不存在对所有工具都最省的单一方案。幂等键还必须绑定不可变参数：同一 key、同一参数才可返回首次结果；同一 key 携带不同参数应明确冲突，不能静默当作成功。

## 状态该存成什么

最后给一个实用建议：**把状态存成「可重建的输入」，而不是「进程的内存快照」。**

换句话说，持久化的对象应该是：

- 完整消息历史（或能重建它的东西）
- 工具调用的记录（调了什么、结果是什么）
- 进度位置

而不是「当前的 Python 对象」「当前的栈」。序列化数据更容易迁移，但并不自动获得跨版本兼容；恢复时仍要检查 schema、工具定义、提示版本、provider/model 与执行策略是否兼容。

消息历史可以作为持久化的一部分，但不能独立代表完整执行状态，也不是永远稳定的通用格式。多模态 payload 可能要保存不可变对象引用，provider 的 tool-use block 受 API 版本约束；应给 checkpoint 标记 schema/version，并保存模型、工具 schema、prompt/policy 版本和 operation ledger。部署升级时先迁移或拒绝恢复不兼容任务，再继续执行。

## 恢复之后，模型会知道发生了什么吗

一个容易被忽略的细节：**恢复时你交给模型的消息历史，决定了它能不能理解当前处境。**

最差的做法是只恢复进度位置，让模型从「第 N 步」重新开始 —— 它会发现自己在没有前文的情况下被要求继续，于是要么重做前面的步骤，要么困惑。

恢复兼容的消息历史能让模型理解之前的对话，但不保证它不会再次提出相同动作，更不保证外部副作用不重复。宿主还要恢复 operation ledger，并在重新 dispatch 前对账或校验幂等键。

但这里有一个例外情况需要处理：**崩溃那一刻的那一轮，可能已经执行了工具但没回填结果。** 这时消息历史里有一个 `tool_use` 块，却没有对应的 `tool_result`。

对 Anthropic Messages API 而言，`tool_result` 必须在紧随 `tool_use` assistant 消息的下一条 user 消息中按 `tool_use_id` 配对；缺失时请求会因 transcript 不完整而返回 400。这个协议错误说明“不能直接续传该 transcript”，但不代表应伪造成功/失败结果，或把恢复选择交给模型。应先查操作账本和下游状态：确认成功后回填真实结果；确认未执行后才可以用相同的持久操作键重试；若仍不可判定，就暂停模型续跑并报告 `outcome_unknown`。只有工具是只读，或接收方确认支持同一操作键的幂等重试时，才考虑重放未完成动作；截断 assistant turn 本身不能防止模型再次发出动作。

### 恢复时遇到悬空 tool_use：先对账，别伪造结果

Anthropic Messages API 要求每个 client-side `tool_use` 都由紧随其后的 user message 中对应 `tool_result` 回答；存在多项时，结果块必须排在这条 user message 的其他文本之前。漏结果可能得到 400。`tool_result.is_error=true` 表示工具结果被标记为错误；它本身不证明副作用一定没有发生。比如请求超时或连接中断时，下游可能已提交操作，但宿主没收到确认。应按下游契约查询或用相同业务键对账；不能为了让 transcript 通过校验，就伪造一条“状态未知”的结果并把它交给模型：模型可能继续调用，提示词也不能阻止宿主执行副作用。

恢复时要先检查持久化的 operation key 和下游状态。确认已成功，就回填持久化的真实结果；确认未执行，才可按相同操作键和参数重试；若结果无法查明，就暂停 provider 对话并向调用方报告 `outcome_unknown`，进入人工或后台对账。删除未完成的 assistant turn 也不能单独解决风险：重新问模型可能再次产生动作，宿主仍须用稳定操作键阻止重复效果。

下面的本地 helper 只检查对话末尾是否有尚未配对的 client tool calls；它不执行副作用、不生成假的 `tool_result`，也不保证此前整段 history 都合法：

```python
"""识别对话末尾未配对的 client-side tool_use；不伪造工具结果。"""


def content_blocks(message):
    content = message.get("content")
    return content if isinstance(content, list) else []


def trailing_unanswered_tool_uses(messages):
    """返回 transcript 尾部 assistant turn 中尚未配对的 tool_use blocks。"""
    if not messages:
        return []
    last = messages[-1]
    if last.get("role") == "assistant":
        uses = [b for b in content_blocks(last)
                if isinstance(b, dict) and b.get("type") == "tool_use"]
        answered_ids = set()
    elif (last.get("role") == "user" and len(messages) >= 2
          and messages[-2].get("role") == "assistant"):
        uses = [b for b in content_blocks(messages[-2])
                if isinstance(b, dict) and b.get("type") == "tool_use"]
        answered_ids = {
            b.get("tool_use_id") for b in content_blocks(last)
            if isinstance(b, dict) and b.get("type") == "tool_result"
        }
    else:
        return []
    return [b for b in uses if b.get("id") not in answered_ids]


if __name__ == "__main__":
    crashed = [
        {"role": "user", "content": "创建订单 ORD-1"},
        {"role": "assistant", "content": [
            {"type": "tool_use", "id": "call_00_ORD1", "name": "create_order",
             "input": {"id": "ORD-1"}}
        ]},
    ]
    pending = trailing_unanswered_tool_uses(crashed)
    print("未配对 tool_use：%s" % [b["id"] for b in pending])
    print("恢复动作：先按持久化 operation key 对账；未确认前不继续请求模型")
```

示例输出：

```text
未配对 tool_use：['call_00_ORD1']
恢复动作：先按持久化 operation key 对账；未确认前不继续请求模型
```

对话格式合法只是继续请求的必要条件，不是副作用安全保证。安全判据来自宿主的持久 operation ledger、接收方幂等能力和对账结果；`tool_use.id` 只用于把结果配回模型协议。

## 完整可运行代码

> 说明：下面这个实验为了把变量隔离干净，**只把 `step` 落盘** —— 那是为了暴露「副作用 vs 进度」这条缝，不是推荐的持久化格式。真实系统需要版本化 checkpoint、消息/策略快照和 operation ledger。恢复数据还要与当前工具定义和 provider schema 做兼容检查。

下面这个脚本就是上面那张表的来源。它用脚本化策略跑两次：一次朴素版、一次用本地文件查重的幂等演示，都在同一个位置注入崩溃。两个文件都创建在脚本自己的临时目录中，运行结束自动清理，不会覆盖当前目录里同名文件。教学版按 id 读取首次记录：相同 id 和相同 JSON payload 去重；同 id 携带不同 payload 时返回冲突。比较时用排序键后的 JSON 表示，避免 Python 把 `True` 与 `1` 当作相等。第二种实现仍是单进程、顺序运行的教学代码；文件扫描再追加不是并发安全的生产幂等方案。

```python
"""断点恢复实验：副作用发生了，但状态还没落盘 —— 恢复之后会重复吗？

这个实验用**脚本化的动作策略**（不是真模型），因为要测的是循环骨架的行为，
而不是模型的行为。策略固定，结果完全可复现。

本版本于 2026-10-21 在 Python 3.14.7 本地复跑；它验证当前确定性夹具，不是复现 2026-10-09 历史环境。
"""
import json, os, tempfile

# The demo assigns both paths inside a private temporary directory in main().
RECORDS = None
STATE = None

PLAN = [("create_record", {"id": "u1", "name": "张三"}),
        ("create_record", {"id": "u2", "name": "李四"}),
        ("create_record", {"id": "u3", "name": "王五"}),
        ("done", {})]


def reset():
    for p in (RECORDS, STATE):
        if os.path.exists(p):
            os.remove(p)


def append_record(rec_id, name):
    with open(RECORDS, "a") as f:
        f.write(json.dumps({"id": rec_id, "name": name}, ensure_ascii=False) + "\n")


def existing_records():
    if not os.path.exists(RECORDS):
        return {}
    with open(RECORDS, encoding="utf-8") as f:
        return {record["id"]: record for line in f if line.strip()
                for record in [json.loads(line)]}


def line_count():
    """⚠️ 必须数**行数**，不能数 id 集合 —— 重复写入同一个 id 在集合里看不出来。"""
    if not os.path.exists(RECORDS):
        return 0
    return sum(1 for l in open(RECORDS) if l.strip())


def canonical_json(value):
    """比较 JSON payload 时区分 true 与 1，并忽略对象键顺序。"""
    return json.dumps(value, ensure_ascii=False, sort_keys=True, separators=(",", ":"))


def tool_create_record(args, idempotent):
    """幂等版：同一个 id 和相同参数只写一次；参数冲突时明确拒绝。"""
    if idempotent:
        payload = {"id": args["id"], "name": args["name"]}
        existing = existing_records().get(payload["id"])
        if existing is not None:
            if canonical_json(existing) == canonical_json(payload):
                return {"ok": True, "deduped": True}
            return {"ok": False, "error": "idempotency key reused with different payload"}
    append_record(args["id"], args["name"])
    return {"ok": True, "deduped": False}


def save_state(msg_count, step):
    with open(STATE, "w") as f:
        json.dump({"msg_count": msg_count, "step": step}, f)


def load_state():
    if not os.path.exists(STATE):
        return 0
    return json.load(open(STATE))["step"]


def run(crash_at=None, idempotent=False, label=""):
    """跑循环。crash_at = 在第几步的工具**执行之后、状态落盘之前**模拟崩溃。"""
    start = load_state()
    step = start
    while step < len(PLAN):
        name, args = PLAN[step]
        if name == "done":
            save_state(step + 1, step + 1)
            break
        res = tool_create_record(args, idempotent)
        if not res["ok"]:
            raise RuntimeError(res["error"])
        # ⚠️ 副作用已经发生，但状态还没落盘 —— 此刻崩溃
        if crash_at is not None and step == crash_at:
            print("    💥 在工具执行后、状态落盘前崩溃（第 %d 步）" % (step + 1))
            return "crashed"
        save_state(step + 1, step + 1)
        step += 1
    return "done"


def main():
    global RECORDS, STATE
    # 碰撞安全：脚本只在自己创建的临时目录中写入，并在退出时清理。
    with tempfile.TemporaryDirectory(prefix="agent-state-resume-") as temp_dir:
        RECORDS = os.path.join(temp_dir, "records.jsonl")
        STATE = os.path.join(temp_dir, "state.json")
        print("任务：创建 3 条记录（u1/u2/u3），工具在第 2 步执行后、状态落盘前崩溃")
        print()
        for idem in (False, True):
            reset()
            tag = "幂等版" if idem else "朴素版"
            print("=== %s ===" % tag)
            r1 = run(crash_at=1, idempotent=idem)
            after_crash = line_count()
            print("    崩溃后盘面记录数：%d，已落盘的进度：第 %d 步" % (after_crash, load_state()))
            r2 = run(idempotent=idem)
            final = line_count()
            print("    恢复并跑完：%s，最终记录数：%d" % (r2, final))
            with open(RECORDS, encoding="utf-8") as f:
                lines = [json.loads(line) for line in f if line.strip()]
            print("    实际写入序列：%s" % [x["id"] for x in lines])
            print("    期望 3 条 → %s" % ("✅ 没有重复" if final == 3 else "❌ 重复了 %d 条" % (final - 3)))
            print()
        conflict = tool_create_record({"id": "u1", "name": "不同参数"}, idempotent=True)
        print("同 id + 不同参数：%s" % conflict)


if __name__ == "__main__":
    main()


```

## 常见坑

- **以为「状态存下来就能恢复」。** 你的状态能回到任意时间点，世界的状态不能 —— 而重复就发生在这条缝里。
- **用去重计数验证「有没有重复」。** 实测里我因此把「重复写入 u2」看成了「3 条正常」。测重复就要用能表达重复的计数方式。
- **在循环里做幂等，而不是在工具里。** 幂等的复杂度属于工具，放在循环里会让循环开始知道业务。
- **依赖自增 id 做业务键。** 重试时你会拿到一个新的自增 id，去重立刻失效。业务键必须是任务本身稳定的东西。
- **把内存快照当状态持久化。** 代码一改就可能失效；可序列化不等于跨版本兼容，要带 schema、prompt、工具与 provider 版本并执行恢复迁移。
- **把消息历史当作副作用账本。** transcript 说明模型提出了什么和宿主回填了什么，不证明下游是否已经提交效果。
- **崩溃恢复后盲目重放。** 如果副作用状态未知，应由宿主查询、按同一持久操作键幂等重放，或暂停报告；模型曾有一次不重试的观察不能充当防重复控制。
