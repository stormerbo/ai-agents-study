前两节的循环都有一个隐含假设：**它会一直跑到结束。** 真实系统里这个假设不成立 —— 进程会被重启、部署会滚动、机器会挂。一个跑了 8 步的任务，在第 7 步崩溃之后应该怎么办？

答案看起来很简单：把状态存下来，恢复时接着跑。但这里藏着一个**每一轮都会踩的坑**，这一节用实测把它挖出来。

## 循环的状态到底是什么

先把「状态」这个词拆开。一个 agent 循环有三个层次的东西，它们的持久化难度完全不同：

| 层次 | 内容 | 能不能序列化 |
|---|---|---|
| **消息历史** | 模型看到的所有消息 | 能，就是一个 JSON 数组 |
| **进度位置** | 走到第几步、完成到哪 | 能，一个整数或状态名 |
| **外部副作用** | 已经写进数据库/文件/支付系统的东西 | **不能回滚**，这才是麻烦的来源 |

前两个是「你的状态」，第三个是「世界的状态」。断点恢复的难点全部来自第三个 —— 因为**你的状态可以恢复到任意时间点，世界的状态不能。**

## 实测：状态落盘和副作用之间的缝

设计一个最小实验。任务：创建三条记录（u1、u2、u3）。循环每一步做两件事：执行工具（产生副作用），然后把进度落盘。

在第 2 步**工具执行之后、状态落盘之前**模拟一次崩溃。然后从落盘的进度恢复，跑完。看最终盘面上有几条记录。

两个版本，唯一差别是工具是否幂等：

| 版本 | 崩溃后盘面 | 恢复跑完后的写入序列 | 最终条数 |
|---|---|---|---|
| 朴素版 | 2 条 | `u1, u2, u2, u3` | **4 条（重复 1）** |
| 幂等版 | 2 条 | `u1, u2, u3` | 3 条 ✅ |

（实跑数据，2026-10-09。脚本用脚本化策略，结果完全可复现。）

**朴素版把 u2 写了两遍。** 原因很直白：崩溃时副作用已经发生了（u2 已写入），但进度还停在「第 1 步完成」，所以恢复后循环重做了第 2 步 —— 而重做意味着再写一次。

这就是分布式系统里那个老问题（「至少一次」语义）在 agent 循环里的形态。它和消息队列、定时任务里的重复投递是同一件事，只是换了个场景。

## 这里有一个我差点报错的测量陷阱

第一次跑这个实验时，两版的结果都是「3 条，没有重复」。看起来结论是「朴素版也没问题」。

**错的是我的计数方法。** 我数的是**去重后的 id 集合**：`len({"u1","u2","u3"})` = 3。而重复写入同一个 id 在集合里根本看不出来。

改成数**文件行数**之后，朴素版立刻变成 4 行，写入序列是 `u1, u2, u2, u3`。

这个错误的类型和第 8 章那次「解析器贪婪匹配」是同一个：**测量方法把要测的东西藏起来了。** 当时是把「解析失败」记成了「模型全错」，这次是把「重复写入」记成了「正常」。两次的共同点是：**结果看起来完全合理，所以不会有人去质疑它。**

教训可以写得很具体：**当你测的是「有没有重复」时，计数方式必须能表达重复。** 集合、去重、distinct count —— 这些默认行为都会把重复吃掉。

## 三种解法，按代价排序

知道了问题的形状，解法就清楚了。

**一、让副作用幂等（推荐）。** 工具内部先查再做：如果这个 id 已经存在，直接返回成功，不做第二次写入。实测里幂等版就是 3 条，一次重复都没有。

这是首选方案，因为它的复杂度在工具内部，不在循环里 —— 循环可以放心重试。代价是**每个有副作用的工具都要单独处理**，而且需要一个稳定的业务键（比如订单号），不能依赖自增 id。

**二、先记意图，再执行（两阶段）。** 执行前先把「我打算做 X」落盘，执行后再标「已完成」。恢复时如果看到「意图存在但未完成」，就知道这一步的状态**未知** —— 这时不要盲目重试。

这个方案更严谨，但要多写一个状态字段，而且要处理「未知」状态。第 4 章实测过这个场景：当工具返回「状态未知」时，模型会主动不重试并说明理由 —— 因为重复执行有副作用。这是模型在这一点上做对了的一个例子。

**三、用去重表。** 每次执行前查一张「已处理过的操作 id」表。它本质上是把幂等性抽出来做成通用的，好处是工具本身不用改。代价是你多了一个需要维护的基础设施。

三种方案里，**方案一的性价比最高**，因为它的成本落在「写工具的时候顺手做掉」，而不是运行时的额外依赖。

## 状态该存成什么

最后给一个实用建议：**把状态存成「可重建的输入」，而不是「进程的内存快照」。**

换句话说，持久化的对象应该是：

- 完整消息历史（或能重建它的东西）
- 工具调用的记录（调了什么、结果是什么）
- 进度位置

而不是「当前的 Python 对象」「当前的栈」。理由是前者跨版本兼容（你明天改了代码，还能恢复昨天的任务），后者只要代码一变就失效。

具体一点：**消息历史本身就是一个很好的持久化格式** —— 它是 JSON、是协议层的结构、不依赖你的代码。恢复时把它读回来继续即可。这也是为什么第 10 章说「工具定义跨范式复用」：消息格式是稳定的那一层。

## 恢复之后，模型会知道发生了什么吗

一个容易被忽略的细节：**恢复时你交给模型的消息历史，决定了它能不能理解当前处境。**

最差的做法是只恢复进度位置，让模型从「第 N 步」重新开始 —— 它会发现自己在没有前文的情况下被要求继续，于是要么重做前面的步骤，要么困惑。

正确的做法是**把完整消息历史一起恢复**。这样模型看到的是「前面已经查过北京和上海，现在轮到第三步」，它不会重复前面的工作。

但这里有一个例外情况需要处理：**崩溃那一刻的那一轮，可能已经执行了工具但没回填结果。** 这时消息历史里有一个 `tool_use` 块，却没有对应的 `tool_result`。

这个状态在协议层是非法的 —— 直接发出去会得到 400（第 4 章实测过「漏 tool_result」的报错）。所以恢复逻辑必须处理它，两种做法：

- **补一条 tool_result**，内容说明「这一步的状态未知，请勿重复执行有副作用的操作」
- **把那一轮整段截掉**，从上一个完整的往返继续

第一种更诚实，也更安全 —— 它把「未知」这个事实交给了模型，而第 4 章实测过模型面对「状态未知」时的判断是正确的（它会主动不重试）。第二种更简单，但有风险：如果那个操作其实已经生效了，截掉之后模型会重新做一遍。

选哪一种，取决于你能不能接受重复。如果能（操作幂等），选简单的那种；如果不能，选诚实的那种。

## 完整可运行代码

下面这个脚本就是上面那张表的来源。它跑两次：一次朴素版、一次幂等版，都在同一个位置注入崩溃。

```python
"""断点恢复实验：副作用发生了，但状态还没落盘 —— 恢复之后会重复吗？

这个实验用**脚本化的动作策略**（不是真模型），因为要测的是循环骨架的行为，
而不是模型的行为。策略固定，结果完全可复现。

实跑状态：2026-10-09。
"""
import json, os

RECORDS = "verify-output/al-records.jsonl"
STATE = "verify-output/al-state.json"

PLAN = [("create_record", {"id": "u1", "name": "张三"}),
        ("create_record", {"id": "u2", "name": "李四"}),
        ("create_record", {"id": "u3", "name": "王五"}),
        ("done", {})]


def reset():
    for p in (RECORDS, STATE):
        if os.path.exists(p):
            os.remove(p)


def append_record(rec_id, name):
    with open(RECORDS, "a") as f:
        f.write(json.dumps({"id": rec_id, "name": name}, ensure_ascii=False) + "\n")


def existing_ids():
    if not os.path.exists(RECORDS):
        return set()
    return {json.loads(l)["id"] for l in open(RECORDS) if l.strip()}


def line_count():
    """⚠️ 必须数**行数**，不能数 id 集合 —— 重复写入同一个 id 在集合里看不出来。"""
    if not os.path.exists(RECORDS):
        return 0
    return sum(1 for l in open(RECORDS) if l.strip())


def tool_create_record(args, idempotent):
    """幂等版：同一个 id 只写一次。朴素版：每次都写。"""
    if idempotent:
        if args["id"] in existing_ids():
            return {"ok": True, "deduped": True}
    append_record(args["id"], args["name"])
    return {"ok": True, "deduped": False}


def save_state(msg_count, step):
    with open(STATE, "w") as f:
        json.dump({"msg_count": msg_count, "step": step}, f)


def load_state():
    if not os.path.exists(STATE):
        return 0
    return json.load(open(STATE))["step"]


def run(crash_at=None, idempotent=False, label=""):
    """跑循环。crash_at = 在第几步的工具**执行之后、状态落盘之前**模拟崩溃。"""
    start = load_state()
    step = start
    while step < len(PLAN):
        name, args = PLAN[step]
        if name == "done":
            save_state(step + 1, step + 1)
            break
        res = tool_create_record(args, idempotent)
        # ⚠️ 副作用已经发生，但状态还没落盘 —— 此刻崩溃
        if crash_at is not None and step == crash_at:
            print("    💥 在工具执行后、状态落盘前崩溃（第 %d 步）" % (step + 1))
            return "crashed"
        save_state(step + 1, step + 1)
        step += 1
    return "done"


if __name__ == "__main__":
    print("任务：创建 3 条记录（u1/u2/u3），工具在第 2 步执行后、状态落盘前崩溃")
    print()
    for idem in (False, True):
        reset()
        tag = "幂等版" if idem else "朴素版"
        print("=== %s ===" % tag)
        r1 = run(crash_at=1, idempotent=idem)
        after_crash = line_count()
        print("    崩溃后盘面记录数：%d，已落盘的进度：第 %d 步" % (after_crash, load_state()))
        r2 = run(idempotent=idem)
        final = line_count()
        print("    恢复并跑完：%s，最终记录数：%d" % (r2, final))
        lines = [json.loads(l) for l in open(RECORDS) if l.strip()]
        print("    实际写入序列：%s" % [x["id"] for x in lines])
        print("    期望 3 条 → %s" % ("✅ 没有重复" if final == 3 else "❌ 重复了 %d 条" % (final - 3)))
        print()
```

实跑输出（2026-10-09）：

```text

    崩溃后盘面记录数：2，已落盘的进度：第 1 步
    恢复并跑完：done，最终记录数：4
    实际写入序列：['u1', 'u2', 'u2', 'u3']
    期望 3 条 → ❌ 重复了 1 条

=== 幂等版 ===
    崩溃后盘面记录数：2，已落盘的进度：第 1 步
    恢复并跑完：done，最终记录数：3
    实际写入序列：['u1', 'u2', 'u3']
    期望 3 条 → ✅ 没有重复
```

## 常见坑

- **以为「状态存下来就能恢复」。** 你的状态能回到任意时间点，世界的状态不能 —— 而重复就发生在这条缝里。
- **用去重计数验证「有没有重复」。** 实测里我因此把「重复写入 u2」看成了「3 条正常」。测重复就要用能表达重复的计数方式。
- **在循环里做幂等，而不是在工具里。** 幂等的复杂度属于工具，放在循环里会让循环开始知道业务。
- **依赖自增 id 做业务键。** 重试时你会拿到一个新的自增 id，去重立刻失效。业务键必须是任务本身稳定的东西。
- **把内存快照当状态持久化。** 代码一改就失效。存消息历史这种协议层结构才能跨版本恢复。
- **崩溃恢复后盲目重放。** 如果工具有副作用且状态未知，正确的动作是暂停并报告，而不是重试 —— 第 4 章实测过模型在这种情况下的判断是对的。
