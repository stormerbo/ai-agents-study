前四节从零写了一个循环。这一节把它和框架对照 —— 不是为了推荐哪个，而是为了让你在**用框架的时候知道它在替你做什么**。

理由很实际：一个不知道自己依赖了什么的人，在它出问题的时候没有排查方向。

## 前四节到底写了什么

先把这一章的产出列清楚。一个能用的循环需要这些东西：

1. **消息搬运**：把历史发给模型、把工具结果追加回去（第 1 节）
2. **工具注册表**：schema、分发、参数校验、异常翻译（第 2 节）
3. **停止判据**：停止原因、预算上限、循环检测（第 3 节）
4. **状态持久化**：断点恢复、幂等（第 4 节）

这只是一个教学循环的范围，不是完整 Agent 运行时的范围。真实框架还可能提供 checkpoint、流式事件、人工中断、观测、重试策略和部署集成；这些能力也能用更底层的组件组合出来，但实现成本、语义和维护责任不同。

因此，本节不把“框架默认做对”当结论，而是逐项问：**哪个组件替你承担了什么契约？默认值是什么？失败时能否观测、替换和恢复？** 下面的表是审查清单，不是所有框架的统一能力表。

## 框架具体替你做了什么

逐条对照：

| 要审查的部分 | 具体问题 | 不能据此推断 |
|---|---|---|
| 消息搬运（第 1 节） | `invoke` / `run` 实际发送哪些消息、停止原因如何映射？ | 一行调用不代表只有一轮，也不代表协议细节消失 |
| 工具注册表（第 2 节） | schema、运行时校验、授权分别发生在哪层？ | 类型注解不一定覆盖业务约束或权限判断 |
| 停止判据（第 3 节） | 有哪些轮次/递归/成本上限？循环信号能否自定义？ | 步数上限不等于语义循环检测，也不必然是成本熔断 |
| 状态持久化（第 4 节） | 使用什么 checkpointer、thread/session id 和恢复语义？ | 状态检查点不等于外部副作用恰好执行一次 |

**循环检测要按具体框架与版本核对。** 最大迭代数或递归限制能给执行步数设上界，但不会自动判断“重复调用同一工具”是否无进展；语义检测还要定义状态相似度、误报和领域边界。不要把一家框架某版本的能力写成全行业结论。

**持久化的语义各家差别很大。** “有 checkpointer”和“崩溃后不重复副作用”是两件事：前者保存执行状态，后者还要求副作用具备幂等键、事务边界或可对账能力。第 4 节的实验只支持本地教学模型中的结论。

## 三种常见控制流形态

下面是便于比较的三种形态，不是互斥分类，也不是“模型自主性逐级提高”的统一尺度。一个系统可以把它们组合起来；控制流由代码还是模型决定，应逐段判断。

**一、链式 workflow。** 把调用按预设顺序串起来，输出传给下一步。它通常由代码控制，但某个步骤仍可调用模型或委托一个 agent，所以不能仅凭“chain”这个名字断定它不是 agent。

**二、图式 workflow。** 节点表示工作单元，边表示可能的转移，条件路由可由代码或模型计算。它可以表达分支、循环与并行；图结构本身不意味着控制权交给模型，也不意味着状态已经持久化。

**三、模型驱动的 agent loop。** 宿主把目标、上下文和工具交给模型，模型提出下一步动作；宿主验证、授权、执行并决定是否继续。模型对动作选择有更大影响，但执行边界仍由宿主负责。

比较框架时，把“控制流在哪里定义”“谁决定下一步”“状态如何恢复”作为独立维度，而不要把 chain、graph、agent 排成一条固定的自主性阶梯。第 13 章会展开选型。

## 实测：状态图多出来的是什么

我写了一个最小的对照：同一个任务，一种用手写循环，一种用「节点表 + 解释器」的状态图。

两种写法跑出的轨迹完全一致：

```text
手写循环的轨迹：['search', 'fetch', 'fetch', 'summarize']
状态图的轨迹：  ['search', 'fetch', 'fetch', 'summarize']
两者一致：True
```

**结果一样，差别在三处：**

**第一，控制流的位置。** 手写的控制流在 `while` 和 `break` 里；状态图的控制流在节点表里。前者是代码，后者是数据。

**第二，要表达「循环取直到取完」，状态图的边必须是一个函数（路由器）。** 静态的 `next` 字符串做不到。这一点很重要：**抽象并没有消除条件判断，只是把它挪了个位置。** 如果你以为「用状态图就不用写 if 了」，那是个误解 —— 你还是写了，只是写成了路由函数。

**第三，图运行时显式维护状态和执行位置。** 这让框架能够在配置了 checkpointer 时保存 checkpoint，并按 thread id 查找线程状态；仅把一个 `node` 字符串序列化，不等于已实现安全恢复。恢复还要明确检查点时机、失败中的节点如何重放，以及外部副作用如何幂等或对账。

而代价也在同一处：**节点表和状态 schema 都是程序的一部分，配置可以错误或不兼容。** 手写循环里的 `break` 写错了会造成逻辑错误；图里无效路由、状态迁移或升级后的 schema 不兼容，也可能在运行时失败。

好处和风险来自同一处：**显式控制流更便于检查、测试和持久化，但持久化能力取决于配置与恢复契约。**

## 真框架长什么样：LangGraph 的最小状态图

上面那张 `NODES` 表是我手写的替身。下面用 LangGraph 1.2.14 重跑了同一条无模型、无外部副作用的状态图（2026-10-20）：

```python
"""LangGraph 的最小状态图：与上面手写的 NODES 表做同一件事。

需要 pip install langgraph。
实跑状态：2026-10-20，LangGraph 1.2.14；无模型调用与外部副作用。
"""
from typing import TypedDict

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver


class State(TypedDict):
    pending: list
    trace: list


def search(state):
    return {"pending": [1, 2], "trace": state["trace"] + ["search"]}


def fetch(state):
    return {"pending": state["pending"][1:], "trace": state["trace"] + ["fetch"]}


def summarize(state):
    return {"trace": state["trace"] + ["summarize"]}


def after_fetch(state):
    return "fetch" if state["pending"] else "summarize"


builder = StateGraph(State)
builder.add_node("search", search)
builder.add_node("fetch", fetch)
builder.add_node("summarize", summarize)
builder.add_edge(START, "search")
builder.add_edge("search", "fetch")
builder.add_conditional_edges("fetch", after_fetch, {"fetch": "fetch", "summarize": "summarize"})
builder.add_edge("summarize", END)

saver = InMemorySaver()                      # 只存进程内存；重启后检查点丢失
graph = builder.compile(checkpointer=saver)
config = {"configurable": {"thread_id": "t-1"}}
out = graph.invoke({"pending": [], "trace": []}, config)
```

跑出来的轨迹和手写循环、和上面那张 `NODES` 表完全一致：`['search', 'fetch', 'fetch', 'summarize']`。手写版多出来的那个 `node` 变量（现在在哪一步），在框架里由 checkpoint 承担：`get_state(config).next` 给出下一个要跑的节点，`metadata.step` 给出步数 —— 本次跑完是 `step: 4`、`next: ()`（没有下一步了）。

本次 checkpoint 摘要如下（2026-10-20，LangGraph 1.2.14；省略随机 ID、`versions_seen` 和易变的内部 `channel_versions` 标识）：

```json
{
  "v": 4,
  "ts": "2026-10-20T11:40:00.343374+00:00",
  "updated_channels": ["trace"],
  "channel_values": {
    "pending": [],
    "trace": ["search", "fetch", "fetch", "summarize"]
  }
}
```

这些内部字段不是本节要依赖的公共业务契约，格式可能随实现版本变化：

- **它记录了状态快照与通道元数据。** 配置 checkpointer 和 `thread_id` 后，运行时可读取该线程的状态；示例用的是 `InMemorySaver`，只在当前进程有效，重启会丢失。生产恢复需选择持久化 saver，并确认数据库初始化、保留策略和部署配置。
- **`updated_channels` 与 `channel_versions` 不是节点来源或并发仲裁证据。** 它们是运行时维护的通道更新/版本元数据；不能据此断言“哪个节点改了字段”或“并行写入时谁赢”。节点更新如何合并由 state reducer 等规则决定；并行更新的顺序也不应作为业务保证。需要确定性时要显式定义 reducer 或串行化写入。
- **checkpoint 不证明外部步骤的效果。** 若节点在写入外部系统后、保存下一检查点前崩溃，恢复可能重放该节点。把 LangGraph 的 checkpoint 作为执行恢复机制时，还要为副作用设计幂等、事务或对账。

## 那要不要用框架

这一节不给结论 —— 第 13 章会专门讲选型。这里只留一条判据，它是这一章手写一遍的实际收益：

**如果你能说清楚框架在你的循环里替换掉了哪几行，你就有能力判断它值不值得。** 反过来说，如果你说不出它做了什么，那么它出问题时你也说不出该从哪查。

这也是本书为什么把「手写一遍」放在「讲框架」之前 —— 顺序反过来的话，你会把框架的行为当成这个领域的规律，而不是一个可以被替换的实现选择。

## 完整可运行代码

下面是最小的两种写法对照：手写循环 vs 状态图。它不依赖任何框架，只用一张字典和二十行解释器。

```python
"""同一个任务，两种写法：手写循环 vs 框架式的状态图。

比的是**控制流写在哪里**，以及多出来的那层抽象替你做了什么、又藏起了什么。

实跑状态：2026-10-09，已跑通。
"""

IDS = [1, 2]

# ---- 共用的动作序列 ----
PLAN = [("search", {"q": "ai agents"}),
        ("fetch", {"id": 1}),
        ("fetch", {"id": 2}),
        ("summarize", {"ids": [1, 2]})]


class Actions:
    def __init__(self):
        self.i = 0

    def next(self):
        if self.i >= len(PLAN):
            return None
        a = PLAN[self.i]
        self.i += 1
        return a


# ---- 写法 A：手写循环。控制流是一条 while ----
def hand_written(actions):
    trace = []
    while True:
        act = actions.next()
        if act is None:
            break
        trace.append(act[0])
    return trace


# ---- 写法 B：状态图。控制流是一张表 + 一个解释器 ----
# 注意 fetch 的边是一个**路由器函数** —— 要表达「还有就继续取」，
# 静态的 next 字符串不够用，必须引入判断。
def fetch_router(state):
    return "fetch" if state["pending"] else "summarize"


NODES = {
    "start":     {"do": None,        "next": lambda s: "search"},
    "search":    {"do": "search",    "next": lambda s: (s.update(pending=list(IDS)), "fetch")[1]},
    "fetch":     {"do": "fetch",     "next": lambda s: (s["pending"].pop(), fetch_router(s))[1]},
    "summarize": {"do": "summarize", "next": lambda s: "end"},
    "end":       {"do": None,        "next": lambda s: None},
}


def graph_runner():
    state = {"pending": []}
    node, trace = "start", []
    while node != "end":
        spec = NODES[node]
        if spec["do"]:
            trace.append(spec["do"])
        node = spec["next"](state)
    return trace


if __name__ == "__main__":
    a = hand_written(Actions())
    b = graph_runner()
    print("手写循环的轨迹：%s" % a)
    print("状态图的轨迹：  %s" % b)
    print("两者一致：%s" % (a == b))
    print()
    print("=== 差别在哪 ===")
    print("1. 手写的控制流在 while 和 break 里；状态图的控制流在 NODES 这张表里。")
    print("2. 要表达「循环取直到取完」，状态图的边必须是一个**函数**（路由器）——")
    print("   静态的 next 字符串做不到。所以抽象并没有消除条件，只是把它挪了个位置。")
    print("3. 状态图显式保存 node 变量，可序列化；持久化与恢复还依赖")
    print("   checkpointer、thread_id、存储后端和副作用幂等设计。")
    print()
    print("代价：NODES 是数据，数据可以被改坏、可以指向不存在的节点。")
    print("好处和风险来自同一处 —— 这一点在第 5 节展开。")
```

本次复跑输出（2026-10-20）：

```text
手写循环的轨迹：['search', 'fetch', 'fetch', 'summarize']
状态图的轨迹：  ['search', 'fetch', 'fetch', 'summarize']
两者一致：True

=== 差别在哪 ===
1. 手写的控制流在 while 和 break 里；状态图的控制流在 NODES 这张表里。
2. 要表达「循环取直到取完」，状态图的边必须是一个**函数**（路由器）——
   静态的 next 字符串做不到。所以抽象并没有消除条件，只是把它挪了个位置。
3. 状态图显式保存 node 变量，可序列化；持久化与恢复还依赖
   checkpointer、thread_id、存储后端和副作用幂等设计。
```

## 框架替你省下什么

行数不是可比的工程指标：两个实现可能覆盖不同的错误处理、并发、检查点和可观测性契约。本节的手写解释器只比较控制流放在哪里；LangGraph 示例验证的是该版本 API 的最小图执行，不构成与手写系统的等价功能或性能基准。

**真正要比较的是责任边界。** 手写时，你需要决定工具参数错了怎么办、执行如何设上限、崩溃后从哪里恢复；使用框架时，这些问题依然存在。某些能力由库、存储后端或托管运行时承担，某些需要显式配置，另一些仍由应用负责。必须按框架、版本、部署模式和配置核对，不能把默认行为笼统说成“更正确”。

框架的价值在于提供可复用的机制与约定；风险在于你可能不了解它们的适用边界。审查时把契约写清楚，比比较一行调用和几百行代码更可靠。

这也是为什么这一章要手写一遍：不是为了以后都不用框架，而是为了**在用它的时候，知道自己在依赖哪些约定**。

## 常见坑

- **把框架的行为当成领域的规律。** 「框架默认这样」和「这件事必须这样」是两回事，手写一遍才能分清。
- **以为用状态图就不用写条件判断。** 实测里表达循环必须靠路由器函数 —— 条件被挪了位置，没有被消除。
- **把步数上限当语义循环检测或成本熔断。** `max_iterations` / recursion limit 可限制执行步数，但具体框架是否提供额外检测、成本预算和超时必须逐项核实；重复但有进展的循环也不能仅凭重复次数一概中断。
- **以为有 checkpointer 就等于不重复副作用。** checkpoint 记录的是图状态；副作用成功但新 checkpoint 尚未保存时，节点可能被重放。应为外部效果设计幂等键、事务或恢复对账。
- **说不出框架替你做了什么就开始用。** 判据是：你能不能指出它替换掉了你哪几行代码。
