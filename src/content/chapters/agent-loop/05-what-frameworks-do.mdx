前四节从零写了一个循环。这一节把它和框架对照 —— 不是为了推荐哪个，而是为了让你在**用框架的时候知道它在替你做什么**。

理由很实际：一个不知道自己依赖了什么的人，在它出问题的时候没有排查方向。

## 前四节到底写了什么

先把这一章的产出列清楚。一个能用的循环需要这些东西：

1. **消息搬运**：把历史发给模型、把工具结果追加回去（第 1 节）
2. **工具注册表**：schema、分发、参数校验、异常翻译（第 2 节）
3. **停止判据**：停止原因、预算上限、循环检测（第 3 节）
4. **状态持久化**：断点恢复、幂等（第 4 节）

加起来大概两百行到四百行代码，取决于你写得多细。这就是「框架替你做的事情」的全部范围。

**注意这个范围里没有的东西**：没有神秘的算法、没有模型能力、没有任何你用裸 API 做不到的事。框架的价值在于**把这些容易写漏的部分默认做对**，而不是提供你做不到的能力。

## 框架具体替你做了什么

逐条对照：

| 你在第几节写的 | 框架通常怎么处理 | 它会藏起什么 |
|---|---|---|
| 消息搬运（第 1 节） | 一行 `agent.invoke(task)` | 每一轮实际发出去的消息长什么样 |
| 工具注册表（第 2 节） | 装饰器 + 类型注解自动生成 schema | schema 的具体内容、校验发生在哪一层 |
| 停止判据（第 3 节） | 通常有 `max_iterations`，循环检测一般**没有** | 参数校验失败时是抛异常还是回填 |
| 状态持久化（第 4 节） | 有的有 checkpointer，有的没有 | 崩溃时副作用和进度的相对顺序 |

第三行和第四行值得单独说。

**循环检测通常是缺失的。** 大多数框架给你一个最大迭代数，但不会检测「连续三次调用同一个工具」—— 因为这个判据太领域相关（第 3 节讲过，文本循环和界面 agent 的判据都不一样）。所以这一块你多半还是要自己写。

**持久化的语义各家差别很大。** 「有 checkpointer」和「崩溃后不重复副作用」是两件事 —— 前者是能力，后者是正确性。第 4 节实测过：只做状态落盘、不做幂等，恢复后照样重复写入。

## 三种抽象模型

如果去看这些框架的设计，它们大致落在三种抽象上。这一节先铺垫，第 13 章会详细展开。

**一、链式（chain）。** 把调用串成一条线，每一步的输出是下一步的输入。它对应的就是我们写的那个顺序执行 —— 控制流完全在你手里。优点是简单、可预测；缺点是它不是 agent，只是 workflow。

**二、图（graph）。** 节点是步骤，边是转移，条件边是路由器。本节下面的实测就是这种。它比链式多了一个关键能力：**能表达循环和分支**，而且执行位置（当前节点）是一个可以序列化的值。

**三、自主 agent（autonomous）。** 你给一个目标和一组工具，它自己决定走多少步。这是第 1 到第 4 节写的形态。

三种抽象不是「越来越好」，而是**控制权逐步从你手里转移到模型手里**。选哪一种，取决于任务需要多少自主性 —— 第 10 章第 5 节给过判据。

## 实测：状态图多出来的是什么

我写了一个最小的对照：同一个任务，一种用手写循环，一种用「节点表 + 解释器」的状态图。

两种写法跑出的轨迹完全一致：

```text
手写循环的轨迹：['search', 'fetch', 'fetch', 'summarize']
状态图的轨迹：  ['search', 'fetch', 'fetch', 'summarize']
两者一致：True
```

**结果一样，差别在三处：**

**第一，控制流的位置。** 手写的控制流在 `while` 和 `break` 里；状态图的控制流在节点表里。前者是代码，后者是数据。

**第二，要表达「循环取直到取完」，状态图的边必须是一个函数（路由器）。** 静态的 `next` 字符串做不到。这一点很重要：**抽象并没有消除条件判断，只是把它挪了个位置。** 如果你以为「用状态图就不用写 if 了」，那是个误解 —— 你还是写了，只是写成了路由函数。

**第三，状态图多出一个 `node` 变量。** 它就是「现在在哪一步」—— 一个可序列化的进度位置。第 4 节讲的断点恢复因此变得容易：把 `node` 存下来，恢复时从那里继续。

而代价也在同一处：**节点表是数据，数据可以被改坏、可以指向不存在的节点。** 手写循环里的 `break` 写错了，编译器会告诉你；节点表里指错一个节点名，只会在运行时变成「走到一半停住」。

好处和风险来自同一个地方：**你把控制流变成了可以被检查、被序列化、也可以被改坏的东西。**

## 真框架长什么样：LangGraph 的最小状态图

上面那张 `NODES` 表是我手写的替身。真框架的状态图长这样（LangGraph 1.2.14，本次实跑，2026-10-12）：

```python
"""LangGraph 的最小状态图：与上面手写的 NODES 表做同一件事。

需要 pip install langgraph。
实跑状态：2026-10-12，langgraph 1.2.14。
"""
from typing import TypedDict

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver


class State(TypedDict):
    pending: list
    trace: list


def search(state):
    return {"pending": [1, 2], "trace": state["trace"] + ["search"]}


def fetch(state):
    return {"pending": state["pending"][1:], "trace": state["trace"] + ["fetch"]}


def summarize(state):
    return {"trace": state["trace"] + ["summarize"]}


def after_fetch(state):
    return "fetch" if state["pending"] else "summarize"


builder = StateGraph(State)
builder.add_node("search", search)
builder.add_node("fetch", fetch)
builder.add_node("summarize", summarize)
builder.add_edge(START, "search")
builder.add_edge("search", "fetch")
builder.add_conditional_edges("fetch", after_fetch, {"fetch": "fetch", "summarize": "summarize"})
builder.add_edge("summarize", END)

saver = InMemorySaver()                      # checkpointer：把每一步的状态存下来
graph = builder.compile(checkpointer=saver)
config = {"configurable": {"thread_id": "t-1"}}
out = graph.invoke({"pending": [], "trace": []}, config)
```

跑出来的轨迹和手写循环、和上面那张 `NODES` 表完全一致：`['search', 'fetch', 'fetch', 'summarize']`。手写版多出来的那个 `node` 变量（现在在哪一步），在框架里由 checkpoint 承担：`get_state(config).next` 给出下一个要跑的节点，`metadata.step` 给出步数 —— 本次跑完是 `step: 4`、`next: ()`（没有下一步了）。

框架持久化出来的 checkpoint 内容是（本次实跑；为可读性只删掉了 `versions_seen` 等重复字段，其余逐字保留）：

```json
{
  "v": 4,
  "ts": "2026-10-12T07:49:14.898716+00:00",
  "id": "1f1c6116-bb55-6b40-8004-9d7c79f61268",
  "channel_versions": {
    "pending": "00000000000000000000000000000005.0.5222923297448746",
    "trace": "00000000000000000000000000000006.0.14968576797672228"
  },
  "updated_channels": ["trace"],
  "channel_values": {
    "pending": [],
    "trace": ["search", "fetch", "fetch", "summarize"]
  }
}
```

这张表把「框架藏起了什么」从断言变成了可打印的对象：

- **它替你存了状态。** `channel_values` 就是恢复时要读的东西 —— 你手写时要自己设计 `save_state` / `load_state`（第 4 节），框架替你做了。
- **它替你记了「哪一步改了什么」。** `channel_versions` 和 `updated_channels` 是增量信息，框架知道每个字段是被哪个节点改的；手写版没有这一层。
- **它也藏起了东西。** `channel_versions` 里那一长串版本号是并发控制用的（多个节点同时改同一字段时决定谁赢），不读源码不知道它的存在；第 2 节那个问题 —— 工具参数校验失败时是抛异常还是回填 —— 同样不在这个文件里。

## 那要不要用框架

这一节不给结论 —— 第 13 章会专门讲选型。这里只留一条判据，它是这一章手写一遍的实际收益：

**如果你能说清楚框架在你的循环里替换掉了哪几行，你就有能力判断它值不值得。** 反过来说，如果你说不出它做了什么，那么它出问题时你也说不出该从哪查。

这也是本书为什么把「手写一遍」放在「讲框架」之前 —— 顺序反过来的话，你会把框架的行为当成这个领域的规律，而不是一个可以被替换的实现选择。

## 完整可运行代码

下面是最小的两种写法对照：手写循环 vs 状态图。它不依赖任何框架，只用一张字典和二十行解释器。

```python
"""同一个任务，两种写法：手写循环 vs 框架式的状态图。

比的是**控制流写在哪里**，以及多出来的那层抽象替你做了什么、又藏起了什么。

实跑状态：2026-10-09，已跑通。
"""

IDS = [1, 2]

# ---- 共用的动作序列 ----
PLAN = [("search", {"q": "ai agents"}),
        ("fetch", {"id": 1}),
        ("fetch", {"id": 2}),
        ("summarize", {"ids": [1, 2]})]


class Actions:
    def __init__(self):
        self.i = 0

    def next(self):
        if self.i >= len(PLAN):
            return None
        a = PLAN[self.i]
        self.i += 1
        return a


# ---- 写法 A：手写循环。控制流是一条 while ----
def hand_written(actions):
    trace = []
    while True:
        act = actions.next()
        if act is None:
            break
        trace.append(act[0])
    return trace


# ---- 写法 B：状态图。控制流是一张表 + 一个解释器 ----
# 注意 fetch 的边是一个**路由器函数** —— 要表达「还有就继续取」，
# 静态的 next 字符串不够用，必须引入判断。
def fetch_router(state):
    return "fetch" if state["pending"] else "summarize"


NODES = {
    "start":     {"do": None,        "next": lambda s: "search"},
    "search":    {"do": "search",    "next": lambda s: (s.update(pending=list(IDS)), "fetch")[1]},
    "fetch":     {"do": "fetch",     "next": lambda s: (s["pending"].pop(), fetch_router(s))[1]},
    "summarize": {"do": "summarize", "next": lambda s: "end"},
    "end":       {"do": None,        "next": lambda s: None},
}


def graph_runner():
    state = {"pending": []}
    node, trace = "start", []
    while node != "end":
        spec = NODES[node]
        if spec["do"]:
            trace.append(spec["do"])
        node = spec["next"](state)
    return trace


if __name__ == "__main__":
    a = hand_written(Actions())
    b = graph_runner()
    print("手写循环的轨迹：%s" % a)
    print("状态图的轨迹：  %s" % b)
    print("两者一致：%s" % (a == b))
    print()
    print("=== 差别在哪 ===")
    print("1. 手写的控制流在 while 和 break 里；状态图的控制流在 NODES 这张表里。")
    print("2. 要表达「循环取直到取完」，状态图的边必须是一个**函数**（路由器）——")
    print("   静态的 next 字符串做不到。所以抽象并没有消除条件，只是把它挪了个位置。")
    print("3. 状态图多出一个东西：node 变量。它就是「现在在哪一步」，")
    print("   可以序列化、可以持久化 —— 断点恢复因此变得容易（见第 4 节）。")
    print()
    print("代价：NODES 是数据，数据可以被改坏、可以指向不存在的节点。")
    print("好处和风险来自同一处 —— 这一点在第 5 节展开。")
```

实跑输出（2026-10-09）：

```text
手写循环的轨迹：['search', 'fetch', 'fetch', 'summarize']
状态图的轨迹：  ['search', 'fetch', 'fetch', 'summarize']
两者一致：True

=== 差别在哪 ===
1. 手写的控制流在 while 和 break 里；状态图的控制流在 NODES 这张表里。
2. 要表达「循环取直到取完」，状态图的边必须是一个**函数**（路由器）——
   静态的 next 字符串做不到。所以抽象并没有消除条件，只是把它挪了个位置。
3. 状态图多出一个东西：node 变量。它就是「现在在哪一步」，
   可以序列化、可以持久化 —— 断点恢复因此变得容易（见第 4 节）。
```

## 框架替你省下的其实不是代码量

一个常见的误解是「用框架能少写代码」。对照上面的清单算一下：手写四样东西大约两三百行，而框架版的等价实现大概是几十行 —— 确实少了。

但代码量不是重点。**真正的差别在于「哪些决定被默认做掉了」。**

手写的时候，你必须回答每一个问题：工具参数错了怎么办？循环卡住怎么发现？崩溃之后状态在哪？这些问题写在你的代码里，答案看得见。

用框架的时候，这些问题**依然存在**，只是答案藏在了默认行为里。它们有的默认是对的（参数校验通常做得比手写细），有的默认是缺失的（循环检测基本没有），有的默认在不同版本之间会变。

所以框架真正的价值是：**它把一批常见决定固化成了约定**，让你不必每次重新想一遍。而它的风险是同一件事的另一面 —— 你不再知道那些约定的具体内容，直到它们出问题。

这也是为什么这一章要手写一遍：不是为了以后都不用框架，而是为了**在用它的时候，知道自己在依赖哪些约定**。

## 常见坑

- **把框架的行为当成领域的规律。** 「框架默认这样」和「这件事必须这样」是两回事，手写一遍才能分清。
- **以为用状态图就不用写条件判断。** 实测里表达循环必须靠路由器函数 —— 条件被挪了位置，没有被消除。
- **依赖框架的 max_iterations 当熔断。** 它只是步数上限，不检测绕圈子，而后者才是更早、更省的信号。
- **以为有 checkpointer 就等于不重复副作用。** 第 4 节实测过：状态落盘做对了，副作用照样重复。
- **说不出框架替你做了什么就开始用。** 判据是：你能不能指出它替换掉了你哪几行代码。
