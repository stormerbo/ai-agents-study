第 9 章给界面 agent 画过四道闸门。这一节把它移植到文本循环上 —— 但**不是照搬**，因为两者的观测形态不同，判据也要跟着变。

## 三个停止条件，各自防不同的东西

**一、模型自然停止。** `stop_reason=end_turn`。这是正常路径，也是最不可靠的一条：它可能在信息不足时停下，也可能在自己觉得够了时停下。

**二、预算上限。** 两种预算都要设 —— 步数和 token。**token 是模型的计费与容量单位**：它不是字符也不是单词，而是把文本按词表切分后的片段（第 1 章的实测里，7 个字符被切成了 35 个 token）。为什么不能只设一个？因为它们防的不是同一件事：

- 步数上限防的是「无限循环」，它关心的是**时间**和「什么时候必须放弃」
- token 上限防的是「每步都很贵」，它关心的是**钱**

单张截图可以接近 996 token（第 8 章实测的上限），而一个复杂的工具返回值可能上千 token。所以同样 8 步，token 总量可以差出好几倍。只设步数，等于对成本没有任何约束。

**三、循环检测。** 识别「在原地打转」。它比前两个更早触发，也更省。

### token 从哪来

上面说 token 上限防钱，那这个数从哪取？**从每次响应的 `usage` 字段累加**，而且四项要分开记，不要合并成一个数：

```python
def add_usage(acc, usage):
    """把一次响应的 usage 累加进累计器。四项分开记，不要合并。"""
    acc["input"] += usage.get("input_tokens", 0)
    acc["output"] += usage.get("output_tokens", 0)
    acc["cache_read"] += usage.get("cache_read_input_tokens", 0)
    acc["cache_creation"] += usage.get("cache_creation_input_tokens", 0)
    return acc
```

为什么分开：

- `input_tokens` 是这次新处理的输入，`output_tokens` 是生成量。**预算判据用 `input + output` 最稳**，因为这两个字段在兼容端点上通常都有。
- `cache_read_input_tokens` 是命中前缀缓存的部分，计价更低，但它仍然占上下文。算「上下文有多大」要把它加进去；算「花了多少钱」不要按全价算。
- `cache_creation_input_tokens` 是这次写入缓存的量，通常按更高的价格计一次。

拿第 1 节那次真跑的两个响应算一遍（`deepseek-flash`，2026-10-12）：第一轮 `input 320 / output 81`，第二轮 `input 175 / cache_read 256 / output 27`。两轮合计新输入 495、输出 108、缓存读取 256 —— 这个两步任务一共处理了 859 token 的量。**所以「8 步上限」和「2 万 token 上限」哪个先触发，取决于每一步多大，拍脑袋定不出来。**

## 循环检测：判据要跟着观测形态走

这是本节最值得展开的一点。

第 9 章的界面 agent 用**截图指纹**做熔断（指纹指的是把当前状态压成一个可比较的短值：截图指纹是画面的哈希，后面的动作指纹是「工具名 + 参数」的字符串）—— 因为它的观测就是画面，「界面没变」是最直接的信号。

文本循环不能用这一招：它没有截图，它的观测是**工具返回值**。而工具返回值天然可能重复（查同一个城市两次，结果当然一样 —— 这可能完全合理）。

所以文本循环的判据是**动作指纹**，不是观测指纹：

```python
fp = (tool_name, json.dumps(args, sort_keys=True))
if fp == last_fp:
    repeat += 1
    if repeat >= repeat_limit:
        raise RuntimeError("连续 %d 次相同的调用，判定为绕圈子" % (repeat + 1))
```

实测跑出来是这样：

```text
get_weather(北京) → 放行
get_weather(北京) → 放行
get_weather(北京) → 拦截：连续 3 次相同的调用，判定为绕圈子
```

注意阈值是 3 而不是 2。原因和界面 agent 一样：**有些操作本来就要重复两次**（先试探再确认、先取列表再取详情）。设成 2 会误杀正常流程。

## 动作指纹有两个盲区

第一个盲区：**参数在轮换的循环。** 如果模型在「北京 → 上海 → 北京 → 上海」之间来回查，指纹每次都不同，闸门不会触发。而这同样是打转。

要抓这一种，判据得换成「**结果集有没有增长**」—— 如果连续几步拿到的信息没有增加任何新东西，那无论动作怎么变，循环都没有进展。这个判据比动作指纹更难做（要比较信息量），但更接近问题的本质。

第二个盲区：**工具返回值里的时间戳或随机 id。** 如果你的工具返回里带了这些东西，那么「结果有没有变化」这个判据会永远为真。这也是为什么动作指纹比观测指纹更可靠 —— 它不受返回值噪声影响。

### 补上盲区：信息增量判据

「结果集有没有增长」听着抽象，落到代码上其实很小：**把每次工具结果的键集合记下来，连续几轮没有新键，就判无进展。**

```python
def result_keys(out):
    """把一次工具结果压成一个键集合签名。只认结构，不认具体值。"""
    if isinstance(out, dict):
        return set(out.keys())
    return {type(out).__name__}


class ProgressGuard:
    """连续 limit 轮的工具结果没有引入任何新键，判为无进展。"""
    def __init__(self, limit=2):
        self.seen, self.limit, self.flat = set(), limit, 0

    def observe(self, outputs):
        keys = set()
        for out in outputs:
            keys |= result_keys(out)
        new = keys - self.seen
        self.seen |= keys
        self.flat = 0 if new else self.flat + 1
        return self.flat < self.limit, "新增键：%s" % (sorted(new) or "无")
```

实跑输出（2026-10-12），输入是四轮「北京天气」的结果：

```text
第 1 轮 → 继续，新增键：['city', 'temp_c']
第 2 轮 → 继续，新增键：无
第 3 轮 → 判定无进展，新增键：无
第 4 轮 → 判定无进展，新增键：无
```

它比动作指纹宽松：第 2 轮的返回其实和第 1 轮一模一样，但它只在连续两轮都没有新键时才判定。代价是两个已知缺口：**值变了但键不变**（例如查询结果更新了）会漏判；返回值里带随机 id 或时间戳的字段，会让「新键」永远为真。所以它是动作指纹的补充，不是替代。

检测到无进展之后要立刻收紧预算，而不是继续走：

```python
def tighten(self, remaining=2):
    """把步数上限压到「当前步数 + remaining」，逼它给阶段性结论。"""
    self.max_steps = min(self.max_steps, self.steps + remaining)
```

两个盲区合起来说明一件事：**没有哪个单一判据能覆盖所有打转。** 实际系统里通常是「动作指纹 + 步数上限 + 预算上限」三条一起上，各自覆盖一部分。

## 预算该按哪条路径定

这条结论在第 9 章量过，这里可以直接用：**按失败路径定，不要按成功路径定。**

第 9 章实测：一次成功的界面操作约 5,000 token，而卡住的运行是 12,000 到 27,000 —— **2.4 到 5.3 倍**。文本循环的形状一样：正常任务 2 到 5 步，一旦绕圈子就会一直走到上限。

所以如果你按「正常 5 步」设了 8 步的上限，那么每一次卡住都会把预算耗尽 —— 而卡住是常态的一部分，不是异常。

一个更实际的做法是**分级**：给正常路径一个宽松的预算，给「已经检测到重复」的路径一个收紧的预算。检测到绕圈子之后，与其继续走，不如立刻把剩余步数砍到一两步，让模型给出阶段性结论。

## 和界面 agent 的闸门对照

把两章的闸门并排看，能清楚看到「判据跟着观测形态走」这条规律：

| 闸门 | 界面 agent（第 9 章） | 文本循环（本节） |
|---|---|---|
| 活动范围 | 允许点击的矩形白名单 | 工具注册表（动作空间天然封闭） |
| 预算 | 步数 + token | 步数 + token（一样） |
| 熔断 | **截图**指纹连续 N 步不变 | **动作**指纹连续 N 次相同 |
| 不可逆确认 | 确认点必须在循环之外 | 一样，且工具本身要幂等（第 4 节） |

第一行和第二行的差别值得注意：界面 agent 需要显式声明活动范围，因为屏幕上的任何一点都能点；而文本循环的活动范围**由注册表天然给定** —— 这一点是工具调用相对计算机使用最大的结构性优势。

## 完整可运行代码

下面把三个停止条件落成可测试的代码：步数上限、token 上限、动作指纹检测。

```python
"""预算、上限与循环检测：一个循环的三道闸门。

纯本地逻辑，不需要凭据。它把第 3 节讲的三个停止条件落成可测试的代码。

实跑状态：2026-10-09，已跑通。
"""

import json


class LoopGuard:
    """包在循环外面的一层。模型说继续不算数，它先过这里。"""

    def __init__(self, max_steps=8, max_tokens=20000, repeat_limit=2):
        self.max_steps = max_steps
        self.max_tokens = max_tokens
        self.repeat_limit = repeat_limit     # 同一个动作连续重复几次算绕圈子
        self.steps = 0
        self.tokens = 0
        self.last_fp = None
        self.repeat = 0
        self.log = []

    def check_step(self, tokens_used):
        """每一轮开始前调用。返回 (是否继续, 原因)。"""
        self.steps += 1
        self.tokens += tokens_used
        if self.steps > self.max_steps:
            return False, "步数超上限（%d/%d）" % (self.steps, self.max_steps)
        if self.tokens > self.max_tokens:
            return False, "token 超上限（%d/%d）" % (self.tokens, self.max_tokens)
        return True, "ok"

    def check_action(self, tool_name, args):
        """每个动作执行前调用。识别「同一个工具+同一组参数」的重复。"""
        fp = (tool_name, json.dumps(args, sort_keys=True, ensure_ascii=False))
        if fp == self.last_fp:
            self.repeat += 1
            if self.repeat >= self.repeat_limit:
                return False, "连续 %d 次相同的调用，判定为绕圈子" % (self.repeat + 1)
        else:
            self.repeat = 0
        self.last_fp = fp
        return True, "ok"


if __name__ == "__main__":
    print("=== 闸门一：步数上限 ===")
    g = LoopGuard(max_steps=4)
    for i in range(1, 7):
        ok, why = g.check_step(500)
        print("  第 %d 轮（累计 %d token）→ %s" % (i, g.tokens, "继续" if ok else "停止：" + why))
        if not ok:
            break

    print()
    print("=== 闸门二：token 上限（同样 8 步，但每轮更贵）===")
    g2 = LoopGuard(max_steps=99, max_tokens=4000)
    for i in range(1, 8):
        ok, why = g2.check_step(1000)
        print("  第 %d 轮（累计 %d token）→ %s" % (i, g2.tokens, "继续" if ok else "停止：" + why))
        if not ok:
            break

    print()
    print("=== 闸门三：绕过圈子（同一个工具+同一组参数）===")
    g3 = LoopGuard()
    calls = [("get_weather", {"city": "北京"}), ("get_weather", {"city": "北京"}),
             ("get_weather", {"city": "北京"}), ("get_weather", {"city": "上海"})]
    for name, args in calls:
        ok, why = g3.check_action(name, args)
        print("  %s(%s) → %s" % (name, args["city"], "放行" if ok else "拦截：" + why))
        if not ok:
            break

    print()
    print("注意第三个闸门只拦「完全相同」的重复。")
    print("把参数换一下（北京 → 上海的轮换查询）就不会触发 —— 那是另一个问题，")
    print("需要用「结果是否在变化」来判定，比动作指纹更难做。")
```

实跑输出（2026-10-09）：

```text
=== 闸门一：步数上限 ===
  第 1 轮（累计 500 token）→ 继续
  ...
  第 5 轮（累计 2500 token）→ 停止：步数超上限（5/4）

=== 闸门二：token 上限（同样 8 步，但每轮更贵）===
  第 5 轮（累计 5000 token）→ 停止：token 超上限（5000/4000）

=== 闸门三：绕过圈子（同一个工具+同一组参数）===
  get_weather(北京) → 放行
  get_weather(北京) → 放行
```

## 预算的两种花法

设了上限之后，还有一个更细的问题：**同样一笔预算，该怎么花？**

两种花法：

**广度优先**：每一步都尽量多做事（一次并发多个工具调用），尽快覆盖完任务需要的所有信息。实测里 ReAct 在线性任务上就是这么做的 —— 一次调三个查询，两步完成。它省的是**往返次数**。

**深度优先**：每一步只做一件事，但要把它做透（多轮打磨、逐步细化）。它省的是**单次上下文的规模**，代价是需要更多轮。

选择取决于任务的形状：信息可以并行获取时广度优先更省；每一步的输入依赖上一步的输出时，只能深度优先。

而这里有一点要提醒：**上限是兜底，不是预算。** 如果你的正常路径要用到上限的 80%，那这个上限就是错的 —— 它会在任何一次小幅波动时被撞到。合理的设置是让正常路径用掉上限的三分之一左右，剩下的留给重试和异常。

## 一个真实案例：卡死是怎么发生的

在这一章的代码里，我实际撞到过一次打转。任务是要模型查三个城市并比较，而它反复调用同一个查询：

```text
第 1 轮  get_weather(北京) → {"temp_c": 31}
第 2 轮  get_weather(北京) → {"temp_c": 31}
第 3 轮  get_weather(北京) → {"temp_c": 31}
...
```

原因不是模型「笨」—— 是因为**我的回填格式有问题**：我把工具结果写成了 `{"result": "31"}`，没有带上城市名和日期。模型看到三个内容相同的 `31`，无法确认哪个对应哪个城市，于是重复查询来「确认」。

修好回填（把 city 和 day 一起放进去）之后，它立刻正常了。

这个案例的教训比「记得设上限」更具体：**打转往往是回填信息不足的症状，而不是模型的行为问题。** 在加熔断之前，先检查一下：模型拿到的工具结果里，有没有足够的信息让它推断出「这一步已经做过了」。


## 一个反直觉的建议：上限要留余量

最后一条实操建议，和直觉相反：**上限不要设成「刚好够用」。**

如果你的正常路径要用掉上限的 80%，那么这个上限就是错的 —— 它会在任何一次小幅波动时被撞到（模型多绕一步、工具重试一次、返回内容长一点）。而撞上限的形态是「任务半途而废」，不是「优雅降级」。

合理的设置是让正常路径用掉三分之一左右。剩下的留给重试、留给异常、留给「这次任务比预想复杂一点」。**上限的作用是兜底，不是规划。** 用兜底值来规划，等于没有留任何余地。

## 常见坑

- **只设步数上限不设 token 上限。** 两者防的不是同一件事：步数管时间，token 管钱。同样 8 步，成本可以差好几倍。
- **把第 9 章的截图指纹照搬到文本循环。** 观测形态不同，判据也要变 —— 文本循环该用动作指纹。
- **重复阈值设成 2。** 有些操作本来就需要两次，实测里设 3 才是合理起点。
- **以为动作指纹能覆盖所有打转。** 参数轮换的循环（北京/上海来回查）指纹每次都不同，抓不到 —— 那是另一个判据。
- **按成功路径设预算。** 实测失败路径是成功路径的 2.4 到 5.3 倍。按正常 5 步设的上限，每次卡住都会耗尽。
- **检测到绕圈子后还继续走。** 正确的做法是把剩余预算砍掉，让模型给阶段性结论，而不是继续烧。
