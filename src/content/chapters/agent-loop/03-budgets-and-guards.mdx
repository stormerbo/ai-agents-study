第 9 章给界面 agent 画过四道闸门。这一节把它移植到文本循环上 —— 但**不是照搬**，因为两者的观测形态不同，判据也要跟着变。

## 三类停止信号，各自防不同的东西

**一、模型协议正常终止。** 例如 Anthropic Messages 返回 `stop_reason=end_turn`。这只表示该 API 将这一轮标为结束，不保证有可展示文本、答案符合 schema，或任务已经完成；仍需按目标 API 契约检查响应，并由应用执行业务验收。

**二、预算上限。** 至少分别设步数、容量和成本控制。token 是词表切分后的片段（第 1 章的实测里，7 个字符被切成了 35 个 token），但**上下文占用、计费 usage 和模型可接受的容量不是同一个指标**。为什么不能只设一个？因为它们防的不是同一件事：

- 步数上限防的是「无限循环」，它关心的是**时间**和「什么时候必须放弃」
- token/成本上限防的是「每步都很贵」，它关心的是**消耗**；按 token 数做预算只是近似，实际账单还受模型、缓存计价、推理 token 计价和供应商计量口径影响
- 单请求上下文与输出上限防的是「这一轮装不下或生成不完」，需要遵守当前模型和端点的容量约束；它们不能由累计账单预算替代

单张截图的视觉 token 取决于 provider、模型与图片尺寸；DeepSeek 当前文档给出每图最高约 1024 token 的估算边界，实际以响应 usage 为准，其他 provider 口径不同。第 8 章旧 996 token 只是缺少逐次记录的历史摘要，不是通用上限。复杂工具返回值也可能占用大量上下文。因此同样 8 步，token volume 与账单都可能相差很大；只设步数，既不能限制总消耗，也不能保证每次请求装得下。

**三、循环检测。** 识别「在原地打转」。它比前两个更早触发，也更省。

### token 从哪来

上面提到的 usage/成本预算该如何估算？**先从每次响应的 `usage` 字段收集端点报告的分项**，再按该端点计量与价格规则换算成成本；usage token 的合计本身不是金额，而且四项要分开记，不要合并成一个数：

```python
def add_usage(acc, usage):
    """Anthropic Messages 字段形状的示意；适配器映射后才可用于内部累计。缺失 usage 保持未知，不能当 0。"""
    if not isinstance(usage, dict):
        for target in ("input", "output", "cache_read", "cache_creation"):
            acc[target] = None
        return acc
    for source, target in (
        ("input_tokens", "input"),
        ("output_tokens", "output"),
        ("cache_read_input_tokens", "cache_read"),
        ("cache_creation_input_tokens", "cache_creation"),
    ):
        value = usage.get(source)
        if type(value) is not int or value < 0:
            acc[target] = None
        elif acc.get(target) is not None:
            acc[target] = acc.get(target, 0) + value
    return acc
```

这个片段假设累计器中每个字段初始为 `0`；一旦某轮缺少对应字段，累计值就变成 `None`，后续不能再把它当作完整总量。生产实现还应由**供应商适配器**把各家不同的字段映射到内部结构，并保留原始 usage 与来源。缺失字段、请求失败或确实导致 usage 不完整的响应截断都应标为「未知」，不能用默认 `0` 掩盖；如果响应仍给出可信且完整的 usage，就按该端点字段记录。

为什么要分开记录：

- 输入、输出、缓存读取/创建、推理 token 等字段的名字、是否包含在其他字段中、是否计费，都会随供应商和端点变化；不要假设兼容 API 的字段完全同义。把观察到的 provider 字段保留并通过适配层归一化，再按该端点的文档核算。
- **上下文占用**描述单次请求实际送入模型上下文的内容及其占用，应结合端点的计数器或 tokenizer 估算；缓存命中可能改变计费，却不意味着上下文内容消失。跨多轮的累计输入也不等于单次上下文窗口占用。
- **计费 usage**应按供应商公布的计量与价格规则分项核算。仅把 `input + output` 相加既可能漏掉缓存/推理等分项，也可能把已包含的字段重复计算，所以它不是通用的「最稳」成本口径。
- **容量约束**还要分别考虑单次输入上下文窗口和最大输出/推理预算；设置每轮及全任务的硬上限，并在发请求前估算、发请求后根据 usage 校准。

拿第 11 章第 1 节保存的历史摘要算一遍（`deepseek-flash`，2026-10-12）：记录的两次字段分别为 `input 320 / output 81` 与 `input 175 / cache_read 256 / output 27`。据该摘要，记录值相加为 input 495、output 108、cache_read 256；但首轮原始响应、完整 request/response trace 与精确端点快照未归档，无法独立复算这些历史字段。它们只展示分项记账方法，不能直接跨供应商推导通用 token 总量或账单。`input + output` 可以作为某些端点的局部计数指标，不能替代上下文容量校验，也不能在字段定义未确认时当作通用成本判据。

## 循环检测：判据要跟着观测形态走

这是本节最值得展开的一点。

第 9 章的界面 agent 用**截图指纹**做熔断（指纹指的是把当前状态压成一个可比较的短值：截图指纹是画面的哈希，后面的动作指纹是「工具名 + 参数」的字符串）—— 因为它的观测就是画面，「界面没变」是最直接的信号。

文本循环不能用这一招：它没有截图，它的观测是**工具返回值**。而工具返回值天然可能重复（查同一个城市两次，结果当然一样 —— 这可能完全合理）。

所以文本循环的判据是**动作指纹**，不是观测指纹：

```python
fp = (tool_name, json.dumps(args, sort_keys=True))
repeat = repeat + 1 if fp == last_fp else 1
last_fp = fp
if repeat >= repeat_limit:
    raise RuntimeError("连续 %d 次相同的调用，判定为绕圈子" % repeat)
```

实测跑出来是这样：

```text
get_weather(北京) → 放行
get_weather(北京) → 放行
get_weather(北京) → 拦截：连续 3 次相同的调用，判定为绕圈子
```

注意阈值是 3 而不是 2。原因和界面 agent 一样：**有些操作本来就要重复两次**（先试探再确认、先取列表再取详情）。设成 2 会误杀正常流程。

## 动作指纹有两个盲区

第一个盲区：**参数在轮换的循环。** 如果模型在「北京 → 上海 → 北京 → 上海」之间来回查，指纹每次都不同，闸门不会触发。而这同样是打转。

要发现这种轮换，动作指纹之外还可以加一个**结果结构新颖度启发式**，例如观察是否出现新的字段键。它只能衡量结构变化，不能判断业务信息是否增加或任务是否前进；真正的进展判据要由具体任务定义。

第二个盲区：**工具返回值里的时间戳或随机 id。** 如果你的工具返回里带了这些东西，那么「结果有没有变化」这个判据会永远为真。这也是为什么动作指纹比观测指纹更可靠 —— 它不受返回值噪声影响。

### 补一个结构新颖度启发式

「结果结构是否出现新字段」可以用一个很小的启发式演示：**把每次工具结果的键集合记下来，连续几轮没有新键，就标记为结构上无新颖度。** 这不是语义信息增量，更不能单独证明任务没有进展。

```python
def result_keys(out):
    """把一次工具结果压成一个键集合签名。只认结构，不认具体值。"""
    if isinstance(out, dict):
        return set(out.keys())
    return {type(out).__name__}


class ProgressGuard:
    """连续 limit 轮的工具结果没有引入任何新键，判为无进展。"""
    def __init__(self, limit=2):
        self.seen, self.limit, self.flat = set(), limit, 0

    def observe(self, outputs):
        keys = set()
        for out in outputs:
            keys |= result_keys(out)
        new = keys - self.seen
        self.seen |= keys
        self.flat = 0 if new else self.flat + 1
        return self.flat < self.limit, "新增键：%s" % (sorted(new) or "无")
```

实跑输出（2026-10-12），输入是四轮「北京天气」的结果：

```text
第 1 轮 → 继续，新增键：['city', 'temp_c']
第 2 轮 → 继续，新增键：无
第 3 轮 → 判定无进展，新增键：无
第 4 轮 → 判定无进展，新增键：无
```

它比动作指纹宽松：第 2 轮的返回其实和第 1 轮一模一样，但它只在连续两轮都没有新键时才判定。它还把 list、字符串、数字等非 dict 结果都压成类型名（例如所有 list 都记作同一个 `list`），不比较列表长度或值。因而会忽略值更新、列表变化，也可能被随机键或时间戳字段干扰。它只是结构启发式，需按任务定制；不能称为通用的“信息增量”或进展判据。

检测到无进展之后可以收紧当前任务的后续步数，但要把“停止执行”和“再调用模型生成收尾”分开：如果希望模型生成阶段性结论，应在任务开始时预留独立的收尾预算；没有预留就返回部分结果和停止原因，不要越过硬预算追加请求。

```python
def tightened_step_cap(current_max_steps, steps_used, remaining=2):
    """返回新的绝对步数上限；调用者仍需在每次请求前检查它。"""
    return min(current_max_steps, steps_used + remaining)
```

两个盲区合起来说明一件事：**没有哪个单一判据能覆盖所有打转。** 实际系统里通常是「动作指纹 + 步数上限 + 预算上限」三条一起上，各自覆盖一部分。

## 预算该按哪条路径定

这条结论在第 9 章量过，这里可以直接用：**按失败路径定，不要按成功路径定。**

第 9 章的历史合成界面摘要保留了两条旧 scorer 标记为失败的 tiny 输出（19,209、26,568 token）和一条 noop 输出（11,827 token）；两条旧 scorer 标记为成功的 tiny 样本约 5,000 token。但完整目标字段未被评分，原始逐次响应也缺失，因此这些数值不能支持通用失败成本倍率、失败概率或期望预算。文本循环的尾部消耗同样应按目标任务、工具和 provider 单独测量。

更可靠的做法是先用同类任务的运行数据设置硬上限，并为重试、失败路径和必要的收尾单独预留预算。检测到绕圈子后，立刻禁止新的工具动作并收紧后续预算；只有预留额度仍足够时，才额外调用模型整理阶段性结论。否则让宿主返回已完成部分、停止原因和未完成项。

## 和界面 agent 的闸门对照

把两章的闸门并排看，能清楚看到「判据跟着观测形态走」这条规律：

| 闸门 | 界面 agent（第 9 章） | 文本循环（本节） |
|---|---|---|
| 活动范围 | 允许点击的矩形白名单 | 本次运行由宿主授权并暴露的工具集合；动态注册或远程工具仍需单独审核 |
| 预算 | 步数 + token | 步数 + token（一样） |
| 熔断 | **截图**指纹连续 N 步不变 | **动作**指纹连续 N 次相同 |
| 不可逆确认 | 确认点必须在循环之外 | 一样，且工具本身要幂等（第 4 节） |

第一行和第二行的差别值得注意：界面 agent 需要显式声明可操作范围；文本循环应只向模型暴露本次运行由宿主授权的工具集合。但注册表本身不是授权策略：动态注册、远程端点、参数级权限、用户/租户身份与运行时撤销，都仍要由宿主或工具在执行时核验。

## 完整可运行代码

下面把三类停止信号落成可测试的代码：步数上限、累计 token 体积示例、动作指纹检测。它是**教学用的局部计数器**：不核算账单，也不检查单次上下文/输出容量；`token_reservation` 是请求前的保守预留，不是服务商回报的实际 usage。生产实现须另接 provider 计量适配器与请求前容量校验，并在响应后用可信 usage/成本对账、释放未使用预留；usage 未知时按明确的保守策略处理。

```python
"""预算、上限与循环检测：一个循环的三道闸门。

纯本地逻辑，不需要凭据。它演示步数、累计 token 体积与重复动作三类闸门；token 数只作为本地消耗代理，不等于价格或容量判据。

实跑状态：2026-10-09，已跑通。
"""

import json


class LoopGuard:
    """包在循环外面的一层。模型说继续不算数，它先过这里。"""

    def __init__(self, max_steps=8, max_token_volume=20000, repeat_limit=3):
        self.max_steps = max_steps
        self.max_token_volume = max_token_volume
        self.repeat_limit = repeat_limit     # 同一个动作连续出现几次算绕圈子（含第一次）
        self.steps = 0
        self.tokens = 0
        self.last_fp = None
        self.repeat = 0
        self.log = []

    def check_step(self, token_reservation):
        """请求前预留预算；被拒绝的步骤不计入已准入步数或预留量。"""
        if type(token_reservation) is not int or token_reservation < 0:
            return False, "token 预留必须是非负整数"
        if self.steps >= self.max_steps:
            return False, "步数超上限（%d/%d）" % (self.steps + 1, self.max_steps)
        projected = self.tokens + token_reservation
        if projected > self.max_token_volume:
            return False, "累计 token 预留超上限（%d/%d）" % (projected, self.max_token_volume)
        self.steps += 1
        self.tokens = projected
        return True, "ok"

    def check_action(self, tool_name, args):
        """每个动作执行前调用。识别「同一个工具+同一组参数」的重复。"""
        fp = (tool_name, json.dumps(args, sort_keys=True, ensure_ascii=False))
        if fp == self.last_fp:
            self.repeat += 1
        else:
            self.repeat = 1
        self.last_fp = fp
        if self.repeat >= self.repeat_limit:
            return False, "连续 %d 次相同的调用，判定为绕圈子" % self.repeat
        return True, "ok"


if __name__ == "__main__":
    print("=== 闸门一：步数上限 ===")
    g = LoopGuard(max_steps=4)
    for i in range(1, 7):
        ok, why = g.check_step(500)  # 请求前按本地估算预留
        print("  第 %d 轮（已准入步数 %d / 预留 %d token）→ %s" %
              (i, g.steps, g.tokens, "继续" if ok else "停止：" + why))
        if not ok:
            break

    print()
    print("=== 闸门二：累计 token 体积代理上限（不等于账单金额）===")
    g2 = LoopGuard(max_steps=99, max_token_volume=4000)
    for i in range(1, 8):
        ok, why = g2.check_step(1000)  # 请求前按本地估算预留
        print("  第 %d 轮（已准入步数 %d / 预留 %d token）→ %s" %
              (i, g2.steps, g2.tokens, "继续" if ok else "停止：" + why))
        if not ok:
            break

    print()
    print("=== 闸门三：绕过圈子（同一个工具+同一组参数）===")
    g3 = LoopGuard()
    calls = [("get_weather", {"city": "北京"}), ("get_weather", {"city": "北京"}),
             ("get_weather", {"city": "北京"}), ("get_weather", {"city": "上海"})]
    for name, args in calls:
        ok, why = g3.check_action(name, args)
        print("  %s(%s) → %s" % (name, args["city"], "放行" if ok else "拦截：" + why))
        if not ok:
            break

    print()
    print("注意第三个闸门只拦「完全相同」的重复。")
    print("把参数换一下（北京 → 上海的轮换查询）就不会触发 —— 那是另一个问题，")
    print("可加结构新颖度启发式，但它不能判断语义进展。")
```

## 并行与顺序：由依赖关系决定

设了上限之后，还有一个更细的问题：**同样一笔预算，该怎么花？**

两种花法：

**并行获取**：对彼此独立的查询，可以在一轮提出多个工具调用，减少模型往返；代价可能是更高的并发、单轮结果体积和部分无用结果。

**顺序获取**：当下一步依赖上一结果时，宿主应等待观察后再决定；这增加模型往返，但能避免预先请求尚不需要的信息。

两种路径都不天然更省 token、费用或上下文。比较时应固定任务、验收标准和工具集，记录端到端完成率、请求数、usage、延迟与副作用，再按任务依赖关系选择。

因此先按任务类型收集成功与失败路径的请求数、输入/输出 usage、成本和墙钟时长，再根据可接受的尾部失败率与单任务硬上限设定预算。不要把某个固定利用率当作普适阈值；也要为必要重试或预留的收尾调用单独计入预算。

## 一个历史记录中的查询打转

旧写作记录描述过一次查询打转：任务是查三个城市并比较，而模型反复调用同一个查询。原始 trace 未保存在当前工作树，无法独立复现这次行为或确认下述回填格式是唯一原因：

```text
第 1 轮  get_weather(北京) → {"temp_c": 31}
第 2 轮  get_weather(北京) → {"temp_c": 31}
第 3 轮  get_weather(北京) → {"temp_c": 31}
...
```

旧记录把重复查询归因于**回填格式缺少任务所需上下文**：工具结果只写成 `{"result": "31"}`，没有带城市名和日期，因而模型无法区分结果对应的城市。这个解释合理，但缺少原始 trace，不能确认它是唯一原因。

旧记录称补上 `city` 和 `day` 后，后续运行恢复正常；由于 trace 与逐次输出缺失，这仍是不可独立复核的因果解释。

这个历史案例提示：回填信息不足可能导致重复调用，但打转也可能来自其他规划、状态或工具故障。增加熔断前，应检查 trace 中模型实际收到的结果、动作参数与任务状态；同时保留硬预算与授权门禁，不能把原因诊断寄托在启发式上。


## 一个反直觉的建议：上限要留余量

预算上限是强制约束，不是系统自动完成优雅降级的机制。设置时要基于目标任务的运行分布、可接受的尾部风险和业务硬上限；重试、收尾调用与工具副作用对账成本也要显式计入。到达硬上限时，宿主应返回部分结果与停止原因；只有事先预留了额度，才能再调用模型生成收尾。

## 常见坑

- **只设步数上限，不设消耗与容量约束。** 步数限制无法约束成本，也无法保证单次请求满足上下文和输出容量；累计 token 体积只能作为代理指标，金额需按端点计价规则计算。
- **把第 9 章的截图指纹照搬到文本循环。** 观测形态不同，判据也要变 —— 文本循环该用动作指纹。
- **重复阈值设成 2。** 本例按连续相同调用的总次数计数，设 3 表示前两次放行、第三次拦截；真实阈值要按正常重复操作与误拦截成本校准。
- **以为动作指纹能覆盖所有打转。** 参数轮换的循环（北京/上海来回查）指纹每次都不同，抓不到 —— 那是另一个判据。
- **按成功路径设预算。** 第 9 章的界面任务样本中，失败路径比成功路径贵 2.4–5.3 倍；这是该任务、端点和样本的观察，不是通用倍率。按正常路径估计时，还要为失败路径和必要重试留出有依据的空间。
- **检测到绕圈子后还继续走。** 停止工具执行与追加模型收尾是两件事；收尾调用必须事先预留预算，否则应由宿主返回部分结果和停止原因。
