成本那一节讨论多智能体的用量与费用。这一节分析上下文隔离可能提供的一个价值：让各个运行单元看到经过选择的上下文。隔离不是多智能体唯一的收益，也不自动提升结果。

## 隔离解决的是什么问题

第 3 章第 5 节留下过一组 20 篇材料的历史 token 摘要。逐次请求/响应、模型指纹、usage 细目、任务映射与评分未归档；以下数值无法独立复算，也不能据此确认两种方案质量等价。

- **两条路线**：旧摘要列出最大请求输入 6,816 与 1,258 token，以及全流程总 token 25,913 与 9,182；逐次请求和样本映射缺失，当前不能独立确认各数值分别对应哪条路线。

这些是无法复算的历史汇总，不能据此断言窗口容量、总账单或答案质量变化，也不能确认两种方案等价。最大请求输入不等同于可用上下文容量，总 token 也不等同于账单或答案质量。

Anthropic 对其 Research 系统的复盘报告称，在其 BrowseComp 分析中，token usage、tool calls 与 model choice 合计解释了 95% 的性能方差，其中 token usage 单独解释 80%。这是特定系统和评测的分析值，不是上下文隔离的因果消融，也不证明 token 增加本身会改善任意任务。[Anthropic：How we built our multi-agent research system](https://www.anthropic.com/research/multi-agent-research-system)

隔离可能让主 agent 少接收探索细节；它是否带来容量、质量或费用收益，取决于运行时实际传递的内容和任务验收。本节把这些列为待验证的设计假设，不把历史 token 摘要当作普遍规律：

1. **控制主 agent 接收的内容**。若宿主只传回短结果，主上下文中的探索消息会更少；是否扩大可用容量，要以实际请求和窗口定义验证。
2. **单独管理探索过程**。日志或 artifact 可保留回查证据；丢弃原始轨迹可能让遗漏更难发现。
3. **划分故障报告边界**。子运行可以单独报告失败，但宿主仍需维护状态、重试和副作用治理。

正确的问法是：**本任务需要哪种上下文传递与复核能力？** 隔离只是候选设计；应同时测质量、费用、延迟、窗口压力和结果可审计性。

## 边界形态决定信息损失风险

在“子任务只回传摘要”的实现里，边界会丢掉未被摘要带回的信息；采用 handoff、共享状态或保留外部证据时，边界形态不同。第 4 节讨论的是摘要式返回可能出现的失败。

按材料切分的 worker **如果只收到局部材料和窄目标**，就可能无法利用其他上下文判断重要性；若宿主提供全局约束或共享证据，边界则不同。历史摘要曾报告「不要动生产库」约束在一次压缩链路中遗漏，但原始轨迹和评分过程不可用，无法确认或估计发生率。

## 两组不可复核的历史摘要

一个历史摘要称，D2 中「任何扩容都必须避开生产库」在单 agent 与主管/工人两条路线的最终回答里都出现。逐次提示、完整响应、模型版本和语义评分没有归档，因此本节无法独立确认这两条记录，也不能将其当作“约束不会丢失”的复现实测。

另一个历史摘要报告 8 条要点压成摘要后遗漏了生产写入约束，同样缺少原始轨迹与 scorer。两个摘要的任务、材料长度和交接步骤不同，无法建立压缩比与遗漏概率的定量关系。可以将压缩率作为评估变量，并在代表性任务集上预先定义关键约束覆盖判据。

## 那该怎么设计隔离

若目标是减少主流程接收的探索细节，同时让 worker 仍有完成子任务所需的信息，设计上要明确边界与验收：**缩小不必要的输入，并验证必要信息没有丢失。**

三条具体做法：

**一、工人生成结构化结果，而不是只给散文。** Schema 能约束字段和类型，但不能保证字段内容正确、完整或忠实于来源；需要校验值并保留可回查证据。

**二、在工人的提示里给出「必须保留」的清单。** 可把硬约束、例外、否定式要求列为显式验收项，再检查输出是否覆盖；它们是否更容易丢失，要由目标任务集验证。

**三、给主 agent 一个回查的通道。** 如果主 agent 能按需再问工人「D2 里有没有约束类内容」，丢失就可以被补救。这本质上是第 6 章的检索问题 —— 把工人的原始材料当成一个可检索的库。

这三项是可组合的缓解手段，成本与可靠性取决于 schema 校验、证据存储、回查调用和维护方式；不应把任何一项当成必然防止信息损失的措施。

### 第一条怎么落地：一份工人回传的结构

「结构化结果」具体长什么样？下面是这一章用的一份（示例：构造数据，未实跑）：

```json
{
  "doc_id": "D2",
  "worker_id": "w2",
  "key_points": ["数据库连接池上限为 20"],
  "must_keep": [
    {"text": "任何扩容操作都必须避开生产库", "kind": "硬约束", "source_span": "D2:第2句"},
    {"text": "只能先在预发环境验证", "kind": "否定式", "source_span": "D2:第2句"}
  ],
  "not_found": ["没有找到与容量规划相关的数字"]
}
```

三条字段设计判据：

1. **可校验** —— 每个值都能被程序检查（字符串是否出现、字段是否为空、编号是否在材料清单里），不需要模型再判一次。
2. **不可空** —— `key_points` 允许是空数组，但不能缺字段。`not_found` 就是用来记录「我确实没查到」的，不是可以不填；缺字段和空数组在语义上是两回事，前者是流程错误。
3. **能追溯到原文位置** —— `source_span` 可指向材料里的具体句子，帮助主管核对；也可以用 `doc_id` 重新读取权威原文。任何引用都需要宿主检查是否确实对应输入并支持结论。

`must_keep.kind` 可以按业务定义分类，例如硬约束、例外和否定式要求；这些是本例的标签约定，不是通用标准。单独字段能便于机器检查和抽样复核，但不能保证模型完整提取或遵守。历史遗漏摘要缺少可复核轨迹，不能据此证明这种字段设计能防止丢失。

### 第三条怎么落地：回查通道是一个工具

「给主 agent 一个回查的通道」不必是新的检索系统 —— 它可以是主管手里的一个工具（示例：构造数据，未实跑）：

```json
{
  "name": "ask_worker",
  "description": "向某个工人追问它材料里的原文。用在主管怀疑结论有遗漏、或想核对细节时。",
  "input_schema": {
    "type": "object",
    "properties": {
      "worker_id": {"type": "string"},
      "question": {"type": "string"}
    },
    "required": ["worker_id", "question"]
  }
}
```

host 可依据 worker_id/doc_id 查找仍然保留的上下文或权威原文，再返回片段。若只需核对材料是否含某句话，应由代码直接读取或定位原文；若要求模型解释含义，就属于新的模型调用。宿主还要验证查询范围、访问权限、来源引用及其新增用量，不能依提示词假设通道只会执行某一种回答。

## 一个判断顺序

最后给一个判断顺序，把成本和隔离两条线合起来：

1. **定义同一项任务和验收规则。** 包含结果质量、关键信息覆盖、权限约束、可审计性以及失败后的处理。
2. **先测最简单的基线。** 单 agent、上下文整理和按需检索都可以作为候选；检索仍会把命中的材料放入实际调用上下文。
3. **再比较隔离方案。** 只有当子任务能按目标边界独立推进时，才比较拆分；记录所有 worker、主管、重试与回查调用的 input/output usage、账单、延迟分布和任务质量。
4. **按预设门槛决策。** 只有代表性任务上的收益能覆盖额外协调、验证与失败处理成本，才在对应工作负载采用。

隔离不天然降低总 token 或费用，也不只在主上下文接近窗口上限时才可能有用；并行、信息访问边界和独立失败处理也可能是目标，必须在具体系统中评估。


## 错误结果的传播边界

如果 host 将未经验证的工具错误或 worker 结论写入后续上下文，它们可能影响之后的判断；是否传播取决于消息传递、状态保留和校验方式。拆分执行有机会把原始探索过程留在 worker 侧，但一旦错误摘要被转交给主管，它仍可能进入主流程。隔离本身不提供错误过滤。

第 4 章保存过一项历史摘要：一个 Anthropic-style `tool_result` 未标记 `is_error` 时，模型被报告为 3/3 将错误内容用于结果表格。逐次响应、模型版本和评分过程未归档，不能确认重现、归因 `is_error` 标记的作用或外推发生率。工具错误标记的协议语义也应限定到对应 API；host 仍应对返回值做结构、来源和业务校验。

若要让主管质疑 worker 结论，应将原始引用、验收规则、冲突状态和必要的失败信息一并保存，并通过独立校验或人工复核检查。提示词可表达检查要求，但不保证它一定发现错误。

## 需要全局关系的任务

需要说明的是，隔离不是万能的。有一类任务它反而有害：**需要全局一致性判断的任务。**

比如「把这三段代码合并成一个不重复的实现」。三个工人各看一段，各自给出「这段没问题」—— 但重复恰恰发生在段与段之间。任何一个工人都看不到这个问题，因为**问题不在任何一份材料里，它在材料之间**。

这类任务可以先让一个能访问全量材料的环节做最终合并；也可以先分块处理，再用显式交叉引用、共享状态或全量复核补上跨材料关系。是否值得采用隔离，取决于接口能否保留必要证据、全量复核的代价，以及同一任务集上的结果。判断信号是：**如果正确答案依赖两份材料之间的关系，局部 worker 的输出就不足以单独作为最终答案。**

因此，第 4 节把「切分维度」单独拿出来讲：它会影响可见证据和协调成本；最终是否能回答跨材料问题，还取决于后续合并与验证环节。
## 完整可运行代码

下面保留一个单 agent 与主管/工人的请求形状示例。它按顺序调用，不实现并行，也不做约束语义评分；两种共享背景各运行一次，不能估计趋势或复现历史结果。DeepSeek Anthropic-compatible 文档说明其 URL/header 与请求兼容范围，但没有在该页定义完整 usage 与 stop_reason 返回契约。运行前应针对目标 endpoint 核实这些字段。

**实跑状态**：2026-10-21，仅在本地 mock transport 下执行 6 项断言；没有调用模型 provider。该验证不证明示例能通过真实 endpoint，也不验证答案质量、并行调度或历史结果。

```python
"""单 agent 与主管/工人请求形状示例；不评分质量或硬约束语义。"""
import json
import os
import urllib.request

BG_SMALL = ("团队规范：所有对外输出用简体中文；数值保留两位小数；"
            "不允许编造未在材料中出现的数字；每条结论必须标注来源文档编号。")
BG_LARGE = BG_SMALL + "\n\n" + "\n".join(
    "约定 %d：服务命名用 kebab-case；配置项放 config/ 下；日志必须带 trace_id；"
    "所有对外接口要有超时与重试；数据库变更走迁移脚本；异常不得吞掉。" % i
    for i in range(1, 41))

DOCS = {
    "D1": "订单服务本周 P99 延迟 820ms，上周 610ms。排查发现新增的推荐调用占用了 34% 的时间。",
    "D2": "数据库连接池上限为 20。注意：任何扩容操作都必须避开生产库，只能先在预发环境验证。",
    "D3": "推荐服务的内存占用从 1.2GB 增长到 2.8GB，主要来自缓存未设上限。",
}
TASK = "根据三份材料写一份技术复盘，指出三个最需要优先处理的问题，并说明理由。"


def call(messages, system, max_tokens=8000):
    body = json.dumps({"model": os.environ["VERIFY_MODEL"], "max_tokens": max_tokens,
                       "system": system, "messages": messages}).encode()
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages", data=body,
        headers={"content-type": "application/json",
                 "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
                 "anthropic-version": "2023-06-01"})
    with urllib.request.urlopen(req, timeout=180) as resp:
        result = json.loads(resp.read())
    usage = result.get("usage")
    if not isinstance(usage, dict):
        raise RuntimeError("缺少 usage 对象；不把缺失字段当作 0")
    counts = {}
    for field in ("input_tokens", "output_tokens"):
        value = usage.get(field)
        if type(value) is not int or value < 0:
            raise RuntimeError("usage.%s 缺失或无效" % field)
        counts[field] = value
    if result.get("stop_reason") != "end_turn":
        raise RuntimeError("响应未以 end_turn 正常结束；不能作为完整文本样本")
    blocks = result.get("content")
    if not isinstance(blocks, list):
        raise RuntimeError("content 缺失或不是列表")
    text = "".join(block.get("text", "") for block in blocks
                   if isinstance(block, dict) and block.get("type") == "text")
    if not text.strip():
        raise RuntimeError("没有可用文本输出")
    return text, counts


def arm_single(background):
    material = "\n\n".join("%s：%s" % (key, value) for key, value in DOCS.items())
    return call([{"role": "user", "content":
                  background + "\n\n" + material + "\n\n" + TASK}],
                "你是一个严谨的技术分析助手。")


def arm_multi(background):
    """三个 worker 与一个 supervisor 顺序调用；不是并行实现。"""
    usage = {"input_tokens": 0, "output_tokens": 0}
    partials = []
    for key, value in DOCS.items():
        text, counts = call([{"role": "user", "content":
                              background + "\n\n材料 %s：%s\n\n请提炼相关要点。" %
                              (key, value)}],
                            "你是一个提炼助手，只输出要点。")
        for field in usage:
            usage[field] += counts[field]
        partials.append("%s 的要点：%s" % (key, text.strip()))
    merged, counts = call([{"role": "user", "content":
                            background + "\n\n" + TASK + "\n\n各工人的提炼：\n" +
                            "\n".join(partials)}],
                          "你是一个严谨的技术分析助手。")
    for field in usage:
        usage[field] += counts[field]
    return merged, usage


def run_pair(label, background):
    _, single = arm_single(background)
    _, multi = arm_multi(background)
    print("%s | single input/output=%d/%d | serial workers+supervisor input/output=%d/%d" %
          (label, single["input_tokens"], single["output_tokens"],
           multi["input_tokens"], multi["output_tokens"]))


if __name__ == "__main__":
    print("任务：%s" % TASK)
    print("usage 只按 endpoint 返回的 input/output token 字段分别汇总；不等于费用或质量")
    run_pair("小背景", BG_SMALL)
    run_pair("大背景", BG_LARGE)
    print("两档各运行一次；本脚本不测语义正确性、并行延迟或一般成本倍率。")
```

## 常见坑

- **把隔离直接等同于省钱或省窗口。** 两者取决于所有调用、上下文窗口定义、缓存、输出、重试和任务表现；历史 token 汇总缺少逐次记录，不能复算。
- **把必要约束只留在主管上下文。** 若 worker 需要遵守它，宿主应将适用约束送入 worker 输入，并为关键要求设置独立验收。
- **把 schema 当成内容正确保证。** schema 可验证字段形状；还需核对来源、完整性、语义与权限。
- **把历史一次「没丢」或一次遗漏推广成概率关系。** 两条历史记录均无逐次响应和 scorer，且任务条件不同；没有证据建立压缩率与遗漏率的数量关系。
- **把回查通道称作唯一补救机制。** 还可直接读取权威来源、运行确定性校验或升级人工复核；回查本身也需要授权和用量评估。
