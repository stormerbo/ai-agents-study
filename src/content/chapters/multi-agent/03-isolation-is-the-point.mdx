成本那一节讲了多智能体贵在哪。这一节讲它**为什么有时候值得** —— 而答案不是「人多力量大」，是**上下文隔离**。

## 隔离解决的是什么问题

第 3 章第 5 节量过一个具体的场景：主 agent 需要处理 20 篇材料。两种做法：

- **不隔离**：20 篇全部装进主上下文，峰值 6,816 token
- **隔离**：每篇交给一个子 agent，主上下文只保留结论，峰值 1,258 token

**主上下文峰值降到五分之一。** 而总 token 反而是涨的（9,182 对 25,913，隔离版更贵）。

所以隔离的收益不是省钱，是**让主上下文不被细节淹没**。它的价值在于：

1. **主上下文能装下更多轮次**。峰值低了，同样的窗口能支撑更长的对话。
2. **注意力不被稀释**。第 3 章测过「context rot」没有复现，但细节挤占空间是确定的。
3. **失败可以局部化**。一个工人搞砸了，主上下文里只是一条坏结论，不是一大堆错数据。

所以正确的问法是：**我需要的是「省钱」，还是「让主上下文保持干净」？** 如果是后者，隔离是对的，即使总成本上升。

## 隔离的代价就在同一处

隔离靠的是边界，而边界是单向、有损的。第 4 节讲的那三种失败都从这里来。

但还有一个更隐蔽的代价：**隔离之后，工人看不到全局。** 它只能基于自己那一份材料判断「什么重要」。而第 3 章实测过一个残酷的例子 —— 摘要丢掉的恰好是「不要动生产库」这条硬约束。

工人不是不认真，是**它没有足够的信息判断什么重要**。主 agent 知道最终要干什么，工人只知道「提炼这份材料」。

## 我的实测：这次没丢

在这一章的对照实验里，我在材料 D2 里埋了同一条约束（「任何扩容都必须避开生产库」），然后看它能不能穿过工人的摘要活到最后。

结果：**单 agent 提到了，多智能体也提到了**（两次实验都是 ✅ / ✅）。

所以如实记下：**「边界信息损失」这个失败模式在我的样本里没有复现。** 这条和第 3 章那次不同，说明它是低频的、依赖具体表述的 —— 而不是必然发生。

但这不构成反驳。原因是：

- 我的材料只有三份、每份几十字，工人有充足的余量把要点全部带上
- 第 3 章那次是把 8 条压成摘要，压缩比高得多，丢东西的概率也高得多

**信息损失的概率随压缩比上升。** 这不是一个「会不会」的问题，是一个「在多大压缩比下会」的问题。

## 那该怎么设计隔离

既然隔离的收益是「主上下文干净」，代价是「工人看不见全局」，设计方向就清楚了：**让边界尽量窄，但要保证关键信息能过去。**

三条具体做法：

**一、工人生成结构化结果，而不是自由文本。** 结构化字段不会在传递中变形，也不会因为「看起来像细节」被省略。这是最可靠的一条。

**二、在工人的提示里给出「必须保留」的清单。** 硬约束、例外、否定式要求 —— 这三类东西最容易在压缩中丢失，明确要求保留它们。

**三、给主 agent 一个回查的通道。** 如果主 agent 能按需再问工人「D2 里有没有约束类内容」，丢失就可以被补救。这本质上是第 6 章的检索问题 —— 把工人的原始材料当成一个可检索的库。

三条里第一条最便宜、最可靠；第三条最灵活、也最贵。实际落地时通常是「先做第一条」，因为它是一次性的提示改动，几乎没有额外成本 —— 而它挡住的恰恰是代价最大的那类失败（硬约束丢失）。

## 一个判断顺序

最后给一个判断顺序，把成本和隔离两条线合起来：

1. **先问主上下文是不是真的装不下。** 如果装得下，隔离没有收益。
2. **再问能不能靠检索解决。** 如果材料能按需取，就不需要同时装进任何上下文（第 6 章）。
3. **最后才问隔离。** 到这一步，隔离是对的 —— 但要按上一节的模型算一次成本，按这一节的清单管住边界。

三步的顺序不能反。反过来就会出现「为了省 token 而引入隔离，结果总 token 涨了 8 倍」这种情况 —— 那不是假设，是第 3 章实测出来的数字。

再强调一次这条顺序背后的判断：**隔离买的是「主上下文的余量」，不是「更少的 token」。** 如果你现在的痛点是账单，隔离大概率帮不上忙；如果你现在的痛点是主上下文被细节塞满、导致后面几轮开始丢东西，那隔离是对的。搞清楚自己缺哪一样，这一步就不会走反。


## 隔离的另一个收益：失败不会污染全局

前面讲的三条收益（余量、注意力、局部化）里，第三条最容易被低估。

在一个不隔离的系统里，一个工具返回了错误数据、模型把它当成事实写进了推理 —— 那么这个错误会**留在主上下文里**，并影响后面每一轮。第 4 章实测过这个形态：不标 `is_error` 时，模型 3/3 把错误当数据写进了结果表格。

而隔离之后，同样的错误只存在于那个工人的上下文里。它交回来的是一条坏结论，主 agent 看到的是一个可疑的输入 —— **它有机会不接受**。

这个差别在长任务里会放大：不隔离时，一个早期错误会跟着你走完全程；隔离时，它最多影响一次汇总。所以隔离的价值随着任务长度上升。

当然前提是主管**会**质疑工人的结论。如果你给主管的提示是「汇总以下结论」，它会照单全收。要让它真的起到过滤作用，提示里得明确要求它检查结论之间的一致性、指出可疑之处。

## 一个常见的反例

需要说明的是，隔离不是万能的。有一类任务它反而有害：**需要全局一致性判断的任务。**

比如「把这三段代码合并成一个不重复的实现」。三个工人各看一段，各自给出「这段没问题」—— 但重复恰恰发生在段与段之间。任何一个工人都看不到这个问题，因为**问题不在任何一份材料里，它在材料之间**。

这类任务的正确做法是**不隔离**，或者隔离之后加一个能看到全量的环节。判断方法很简单：**如果正确答案依赖「两份材料之间的关系」，那就不能按材料切分。**

这也解释了为什么第 4 节把「切分维度」单独拿出来讲 —— 它不只是决定成本，还决定了**某些答案是否在结构上可达**。
## 完整可运行代码

下面这段代码把两条路线并排跑，并检查一条硬约束能不能穿过工人的摘要 —— 这是本节「压缩比决定损失概率」那条结论的检验手段。

```python
"""单 agent vs 主管 + 工人：成本模型与边界信息损失。

设计要点：
  1. 文档 D2 里埋了一条**硬约束**（不要动生产库），看它能不能穿过多层摘要活到最后。
  2. 共享背景做成两种规模 —— 因为成本倍数主要由「共享内容相对单份内容有多大」决定。

实跑状态：2026-10-09，deepseek-flash。
"""
import json, os, urllib.request

BG_SMALL = ("团队规范：所有对外输出用简体中文；数值保留两位小数；"
            "不允许编造未在材料中出现的数字；每条结论必须标注来源文档编号。")

# 大背景：模拟「团队规范 + 代码库约定 + 历史模板」这类真实共享上下文
BG_LARGE = BG_SMALL + "\n\n" + "\n".join(
    "约定 %d：服务命名用 kebab-case；配置项放 config/ 下；日志必须带 trace_id；"
    "所有对外接口要有超时与重试；数据库变更走迁移脚本；异常不得吞掉。" % i
    for i in range(1, 41))

DOCS = {
    "D1": "订单服务本周 P99 延迟 820ms，上周 610ms。排查发现新增的推荐调用占用了 34% 的时间。",
    "D2": "数据库连接池上限为 20。注意：任何扩容操作都必须避开生产库，只能先在预发环境验证。",
    "D3": "推荐服务的内存占用从 1.2GB 增长到 2.8GB，主要来自缓存未设上限。",
}

TASK = "根据三份材料写一份技术复盘，指出三个最需要优先处理的问题，并说明理由。"


def call(messages, system, max_tokens=8000):
    body = json.dumps({"model": os.environ["VERIFY_MODEL"], "max_tokens": max_tokens,
                       "system": system, "messages": messages}).encode()
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages", data=body,
        headers={"content-type": "application/json",
                 "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
                 "anthropic-version": "2023-06-01"})
    with urllib.request.urlopen(req, timeout=180) as resp:
        d = json.loads(resp.read())
    u = d.get("usage", {})
    tin = (u.get("input_tokens", 0) + u.get("cache_read_input_tokens", 0)
           + u.get("cache_creation_input_tokens", 0))
    text = "".join(b.get("text", "") for b in d.get("content", []) if b.get("type") == "text")
    if not text.strip() and d.get("stop_reason") == "max_tokens":
        raise RuntimeError("测量故障：空输出 + max_tokens，需调大预算，不是模型失败")
    return text, tin + u.get("output_tokens", 0)


def arm_single(bg):
    """一个 agent 读完三份材料，直接产出复盘。"""
    material = "\n\n".join("%s：%s" % (k, v) for k, v in DOCS.items())
    return call([{"role": "user", "content": bg + "\n\n" + material + "\n\n" + TASK}],
                "你是一个严谨的技术分析助手。")


def arm_multi(bg):
    """三个工人各读一份（每人都要装一遍共享背景），主管汇总。"""
    tok, partials = 0, []
    for k, v in DOCS.items():
        text, t = call([{"role": "user", "content":
                         bg + "\n\n材料 %s：%s\n\n请提炼这份材料里对复盘有用的要点。" % (k, v)}],
                        "你是一个提炼助手，只输出要点。")
        tok += t
        partials.append("%s 的要点：%s" % (k, text.strip()))
    merged, t2 = call([{"role": "user", "content":
                        bg + "\n\n" + TASK + "\n\n各工人的提炼：\n" + "\n".join(partials)}],
                       "你是一个严谨的技术分析助手。")
    tok += t2
    return merged, tok, len(partials)


def run_pair(label, bg):
    single, t1 = arm_single(bg)
    multi, t2, n = arm_multi(bg)
    alive = ("✅" if "生产库" in single else "❌") + " / " + ("✅" if "生产库" in multi else "❌")
    print("%-14s %-10d %-12d %-9.2fx %s" % (label, t1, t2, t2 / t1, alive))
    return single, multi


if __name__ == "__main__":
    print("任务：%s" % TASK)
    print("三份材料共 %d 字" % sum(len(v) for v in DOCS.values()))
    print()
    print("%-14s %-10s %-12s %-10s %s" % ("共享背景", "单 agent", "主管+3 工人", "倍数", "硬约束存活"))
    s1, m1 = run_pair("小（%d 字）" % len(BG_SMALL), BG_SMALL)
    s2, m2 = run_pair("大（%d 字）" % len(BG_LARGE), BG_LARGE)
    print()
    print("看点：两次的倍数很接近（见上表），并没有随背景变大而明显升高。")
    print("机制解释：多智能体只把【输入】乘以份数，【输出】不乘 ——")
    print("  3 个工人的输出很小，主管的输出与单 agent 相当。")
    print("所以背景越大、输入占比越高时，倍数才会趋近「份数」（这里是 4）。")
    print("本次两个规模都还没到那个区间（输出仍与输入同量级），所以看不出差异。")
    print()
    print("=== 大背景下的单 agent 输出（前 400 字）===")
    print(s2.strip()[:400])
```

## 常见坑

- **以为隔离是为了省钱。** 实测里隔离版总 token 更高（9,182 对 25,913 中的后者）。它的收益是主上下文峰值下降，不是成本下降。
- **隔离之后指望工人自己判断什么重要。** 它看不到最终任务。硬约束、例外、否定式要求这三类必须显式要求保留。
- **让工人输出自由文本。** 结构化字段不会在传递中变形，是最便宜的一条缓解。
- **把一次「没丢」当成「不会丢」。** 本次实测没复现，但第 3 章在高压缩比下丢了硬约束。概率随压缩比上升。
- **忘记加回查通道。** 主 agent 能按需追问工人，是唯一能补救信息损失的机制 —— 它本质上是检索。
