「多智能体」这个词容易让人想到一群平等的 agent 在开会。实际上能稳定工作的多智能体系统，绝大多数是**严格的层级结构** —— 有人汇报、有人汇总，谁也不跟谁平级讨论。

这一节把三种常见拓扑摆出来，说明它们各自的形状、适用场景和代价。

## 拓扑一：主管 + 工人

一个主管把任务拆开，分给若干工人，收齐结果后汇总。工人之间不通信。

这是最常用的形态，也是**唯一一个在大规模下被验证过能稳定工作**的形态。原因很实际：它的通信路径是星形的，消息条数是 O(N)（主管到每个工人各一条来回），而不是 O(N²)。

适合的场景：任务可以**拆成互相独立的子任务**。比如「读三份材料各提炼要点」「查五个城市的天气」「对二十个文件各写一段摘要」。

不适合：子任务之间需要频繁协商的场景。那会退化成下面两种。

## 拓扑二：流水线

工人按顺序排成一列，前一个的输出是后一个的输入。它其实是第 0 章讲过的 workflow —— 只不过每一步可能由不同的模型/提示来执行。

严格说它不算「多智能体」，因为**没有多个自主决策者**，只有多个执行阶段。但它在工程上经常被当成多智能体来讨论，所以放在这里说清楚。

适合：任务天然分段，且每段的工作性质不同。比如「抽取 → 校验 → 改写 → 格式化」，每一段用不同的提示词和不同的校验规则。

它的优点是**每段的上下文都很小**（只需要前一段的输出），成本接近线性。缺点是错误会累积 —— 第 3 章第 4 节实测过：摘要阶段丢掉的那一条恰好是硬约束，而后面每一段都建在它上面。

## 拓扑三：对等 / 辩论

多个 agent 平等地交换意见，最后表决或收敛。这一类在论文里很常见，在工程里很少见。

原因是成本：**每两个 agent 之间都可能有一次通信**，消息条数是 O(N²)；而且它通常需要多轮收敛，所以实际的调用次数更高。

更关键的是收益不明确。第 2 章实测过 self-consistency（同一问题多次采样投票）：唯一答案题 5 次采样零分歧，创作题各不相同 —— 投票无事可做，成本 5.4 倍。多个 agent 辩论面对的是同一个问题：**它们的知识来自同一个模型，独立性是假的。**

什么时候对等拓扑真的有用？当不同的 agent **确实掌握不同信息**时（比如一个读代码库、一个读需求文档、一个读线上日志）。这时候它们的「分歧」来自信息差，而不是随机性 —— 那才是有价值的辩论。而这时它本质上仍然是主管-工人的一种变体，只是增加了一个交叉质询的环节。

## 和子智能体的关系

第 3 章第 5 节讲过「子智能体」—— 把一段工作放进一个独立的上下文里跑，只把结论带回来。那是**上下文隔离**的机制，而这一节讲的是**谁向谁汇报**的拓扑。

两者是不同维度的问题，但经常一起出现：

- 子智能体解决「主上下文被塞满」
- 拓扑解决「任务怎么拆、结果怎么合」

一个主管 + 工人的系统，通常每个工人就是一个子智能体。但也可以只有一个子智能体（单工人），那就没有拓扑问题了。

## 一个判断拓扑的简单方法

不要先想「用几个 agent」，先回答三个问题：

1. **子任务之间需要互相看见对方的过程吗？** 不需要 → 主管-工人；需要 → 你多半在做一个流程
2. **每一步的输入依赖上一步的输出吗？** 依赖 → 流水线；不依赖 → 可以并行，也就是主管-工人
3. **不同角色掌握的信息真的不同吗？** 不同 → 值得让它们交叉质询；相同 → 辩论只是重复采样

三个问题答完，拓扑基本就定了。剩下的是成本问题，那是下一节的内容。

## 为什么层级结构最稳

三种拓扑里，主管 + 工人之所以被大量采用，有三个不浪漫但很实际的原因。

**第一，错误有归属。** 主管汇总时可以看到每个工人交回来的东西。如果最终结果不对，你能定位到是哪个工人的产出有问题 —— 而流水线里错误会一路传下去，到终点时已经分不清源头。

**第二，可以并行。** 工人之间不通信，所以它们可以同时跑。这意味着**延迟是 max(工人耗时)，不是 sum**。对延迟敏感的任务，这一点比成本更重要。

**第三，上下文互相隔离。** 每个工人只看到自己那一份输入，主管只看到汇总后的结论。这个隔离是第 3 节的主题 —— 它既是成本来源，也是最大的收益来源。

代价也很清楚：**主管的上下文会成为新的瓶颈。** 所有工人的结论都要装进它那里。工人越多、结论越长，主管的上下文就越接近单 agent 直接做整件事的规模 —— 这时候多智能体的收益就消失了，只剩下成本。

## 一个具体的拆解案例

举个任务：「分析这个 200 文件的代码库，找出五个最主要的技术债。」

**拆法一（按文件分）**：200 个工人，每人读一个文件。缺点是没人能看到跨文件的问题 —— 而技术债往往正是跨文件的（重复实现、循环依赖）。

**拆法二（按怀疑对象分）**：先让一个「侦察」agent 扫一遍目录结构和依赖图，列出 20 个可疑点；再让工人分别深入这 20 个点。这里前一步是**探索**，后一步是**验证**。

**拆法三（按视角分）**：三个工人分别从「重复代码」「依赖复杂度」「测试覆盖」三个角度看全部 200 个文件。每个工人都要看全量，所以上下文没有省下来，但视角不同。

三种拆法里，**拆法二最接近多智能体的正确用法**：先用一次便宜的扫描缩小范围，再让工人并行深入。它的关键在于**第一步的成本很低、信息量很大** —— 而后两步才是真正的并行。

而拆法一和拆法三的问题分别是：前者切分维度错了（按文件切，但问题跨文件），后者根本没有省下上下文（每个工人都要看全量，等于把同一份背景装了 N 遍）。后者正是下一节要量的那个成本结构。

这也给出一条更一般的判断：**好的拆解会让每一份上下文都变小；坏的拆解只是把同一份上下文复制了 N 份。** 后者的成本一定会涨，而收益为零。

## 完整可运行代码

下面这段代码实现了主管 + 工人和单 agent 两种形态，跑同一个任务并对比成本。它还埋了一条硬约束，用来检验信息能不能穿过工人的摘要活到最后。

```python
"""单 agent vs 主管 + 工人：成本模型与边界信息损失。

设计要点：
  1. 文档 D2 里埋了一条**硬约束**（不要动生产库），看它能不能穿过多层摘要活到最后。
  2. 共享背景做成两种规模 —— 因为成本倍数主要由「共享内容相对单份内容有多大」决定。

实跑状态：2026-10-09，deepseek-flash。
"""
import json, os, urllib.request

BG_SMALL = ("团队规范：所有对外输出用简体中文；数值保留两位小数；"
            "不允许编造未在材料中出现的数字；每条结论必须标注来源文档编号。")

# 大背景：模拟「团队规范 + 代码库约定 + 历史模板」这类真实共享上下文
BG_LARGE = BG_SMALL + "\n\n" + "\n".join(
    "约定 %d：服务命名用 kebab-case；配置项放 config/ 下；日志必须带 trace_id；"
    "所有对外接口要有超时与重试；数据库变更走迁移脚本；异常不得吞掉。" % i
    for i in range(1, 41))

DOCS = {
    "D1": "订单服务本周 P99 延迟 820ms，上周 610ms。排查发现新增的推荐调用占用了 34% 的时间。",
    "D2": "数据库连接池上限为 20。注意：任何扩容操作都必须避开生产库，只能先在预发环境验证。",
    "D3": "推荐服务的内存占用从 1.2GB 增长到 2.8GB，主要来自缓存未设上限。",
}

TASK = "根据三份材料写一份技术复盘，指出三个最需要优先处理的问题，并说明理由。"


def call(messages, system, max_tokens=8000):
    body = json.dumps({"model": os.environ["VERIFY_MODEL"], "max_tokens": max_tokens,
                       "system": system, "messages": messages}).encode()
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages", data=body,
        headers={"content-type": "application/json",
                 "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
                 "anthropic-version": "2023-06-01"})
    with urllib.request.urlopen(req, timeout=180) as resp:
        d = json.loads(resp.read())
    u = d.get("usage", {})
    tin = (u.get("input_tokens", 0) + u.get("cache_read_input_tokens", 0)
           + u.get("cache_creation_input_tokens", 0))
    text = "".join(b.get("text", "") for b in d.get("content", []) if b.get("type") == "text")
    if not text.strip() and d.get("stop_reason") == "max_tokens":
        raise RuntimeError("测量故障：空输出 + max_tokens，需调大预算，不是模型失败")
    return text, tin + u.get("output_tokens", 0)


def arm_single(bg):
    """一个 agent 读完三份材料，直接产出复盘。"""
    material = "\n\n".join("%s：%s" % (k, v) for k, v in DOCS.items())
    return call([{"role": "user", "content": bg + "\n\n" + material + "\n\n" + TASK}],
                "你是一个严谨的技术分析助手。")


def arm_multi(bg):
    """三个工人各读一份（每人都要装一遍共享背景），主管汇总。"""
    tok, partials = 0, []
    for k, v in DOCS.items():
        text, t = call([{"role": "user", "content":
                         bg + "\n\n材料 %s：%s\n\n请提炼这份材料里对复盘有用的要点。" % (k, v)}],
                        "你是一个提炼助手，只输出要点。")
        tok += t
        partials.append("%s 的要点：%s" % (k, text.strip()))
    merged, t2 = call([{"role": "user", "content":
                        bg + "\n\n" + TASK + "\n\n各工人的提炼：\n" + "\n".join(partials)}],
                       "你是一个严谨的技术分析助手。")
    tok += t2
    return merged, tok, len(partials)


def run_pair(label, bg):
    single, t1 = arm_single(bg)
    multi, t2, n = arm_multi(bg)
    alive = ("✅" if "生产库" in single else "❌") + " / " + ("✅" if "生产库" in multi else "❌")
    print("%-14s %-10d %-12d %-9.2fx %s" % (label, t1, t2, t2 / t1, alive))
    return single, multi


if __name__ == "__main__":
    print("任务：%s" % TASK)
    print("三份材料共 %d 字" % sum(len(v) for v in DOCS.values()))
    print()
    print("%-14s %-10s %-12s %-10s %s" % ("共享背景", "单 agent", "主管+3 工人", "倍数", "硬约束存活"))
    s1, m1 = run_pair("小（%d 字）" % len(BG_SMALL), BG_SMALL)
    s2, m2 = run_pair("大（%d 字）" % len(BG_LARGE), BG_LARGE)
    print()
    print("看点：两次的倍数很接近（见上表），并没有随背景变大而明显升高。")
    print("机制解释：多智能体只把【输入】乘以份数，【输出】不乘 ——")
    print("  3 个工人的输出很小，主管的输出与单 agent 相当。")
    print("所以背景越大、输入占比越高时，倍数才会趋近「份数」（这里是 4）。")
    print("本次两个规模都还没到那个区间（输出仍与输入同量级），所以看不出差异。")
    print()
    print("=== 大背景下的单 agent 输出（前 400 字）===")
    print(s2.strip()[:400])
```

## 常见坑

- **先决定「用几个 agent」再想任务怎么拆。** 顺序反了。拓扑是拆解方式的结果，不是起点。
- **用对等拓扑做可以并行的事。** 明明互不依赖的子任务，套上一层辩论只会把 O(N) 变成 O(N²)。
- **把流水线当成多智能体。** 它是 workflow —— 没有多个自主决策者，每段的工作是你预先定义的。
- **以为多个 agent 的意见是独立的。** 它们的知识来自同一个模型，第 2 章实测过这种「独立性」的收益是零。
- **忘记工人之间不通信是一个设计决定。** 它让成本可控，代价是工人可能重复劳动或得出矛盾结论 —— 那要靠主管的汇总提示来处理。
