「多智能体」可以采用多种控制与通信结构：中心协调、固定流水线、稀疏协作或对等通信。本节比较三种简化形态；不根据案例文章或少数实现推断哪种拓扑在行业里占多数，也不把某一种结构称为天然最稳定。

这一节比较三种常见的教学模型，说明各自的形状、适用场景和代价。

## 拓扑一：主管 + 工人

一个主管把任务拆开，分给若干工人，收齐结果后汇总。工人之间不通信。

主管-工人是一个被公开实践过的模式：协调者拆任务、派发给工人，再综合结果；Anthropic 的多智能体研究系统是一个具体案例，不足以证明它在行业中占主导或必然稳定。它适合可以并行处理的独立子任务。若中心协调者有 W 个工人，并向每个工人各派发一次任务、收回一次结果，约有 2W 条有向消息和 W 条工人-主管通信边，都是 O(W)；若有 P 个参与者的完全互联图中每一对至少通信一次，潜在通信对数为 P(P−1)/2，即 O(P²)。稀疏对等网络、单向传递或多轮对话会有不同的边数和调用数。单一汇总点便于集中检查冲突，却不保证冲突一定被发现。

适合的场景：任务可以**拆成互相独立的子任务**。比如「读三份材料各提炼要点」「查五个城市的天气」「对二十个文件各写一段摘要」。

注意：若子任务之间频繁协商，简单的中心汇总模型不再完整描述实际通信图；应把往返轮次、共享状态和冲突处理画进拓扑。

## 拓扑二：流水线

工人按顺序排成一列，前一个的输出是后一个的输入。它其实是第 0 章讲过的 workflow —— 只不过每一步可能由不同的模型/提示来执行。

按 Anthropic 对 agentic systems 的区分，预先由代码规定调用顺序的流程属于 workflow；本节沿用这个操作性定义，所以把流水线与动态选择下一步的 agent 分开讨论。其他文献和框架可能使用更宽的 multi-agent 定义，术语边界不是自然定律。

适合：任务天然分段，且每段的工作性质不同。比如「抽取 → 校验 → 改写 → 格式化」，每一段用不同的提示词和不同的校验规则。

固定阶段数时，API 调用次数可随阶段数线性增长；token 用量和费用仍取决于每段的输入、输出、重试与缓存。每段上下文只有在流程设计确实只传递必要字段时才会变小；如果每步都重发完整材料，流水线不会自动节省上下文。前序遗漏可能传到后续阶段，因此应在关键边界保存来源引用、硬约束和校验结果。第 3 章第 4 节的历史记录曾报告摘要遗漏硬约束，但缺逐次请求/响应与语义评分，不能当作该类流程的发生率或因果证明。

## 拓扑三：对等 / 辩论

多个 agent 可以交换意见，再由表决、规则或人工仲裁汇总。研究中存在多智能体辩论实验，但本节没有证据判断这种做法在论文或生产工程里的普及程度。

若采用完全互联拓扑并让每一对 agent 至少通信一次，通信边数为 O(N²)；若使用稀疏邻接关系，边数可以更少。通信边不等于模型 API 调用数：一次调用可携带多条消息，往返轮数、聚合方式和实际并发都会改变调用数、延迟与费用。

收益需要在目标任务上测量。第 2 章有两组不能混为一谈的历史摘要：self-consistency 对 10 道程序生成的算术/计数题各采样 5 次，记录为 0/10 题出现分歧，并报告单次与 5 次投票的平均 token 为 237/1281（约 5.4 倍）；另一个温度探测用单个唯一答案题和单个创作题，在 temperature 0 与 1 下各采样 6 次，记录为唯一答案题每组 1/6 个不同答案、创作题每组 6/6 个不同答案。逐次响应、模型快照、完整 usage、样本映射与评分记录未归档，不能独立复算或推广到其他任务。相同模型、上下文和近似提示可能造成相关错误，应把错误相关性当成待测因素；不能只凭角色名称或样本相似就推断误差独立或完全相同。

什么时候对等拓扑可能有用？当不同的 agent **确实掌握不同信息或承担不同检验目标**时（比如一个读代码库、一个读需求文档、一个读线上日志）。交叉质询可能暴露信息差，但也要评估错误相关性、通信成本和收敛规则。它不必然等价于主管-工人；是否需要中心仲裁取决于控制与责任边界。

## 和子智能体的关系

第 3 章第 5 节讲过「子智能体」—— 把一段工作放进一个独立的上下文里跑，只把结论带回来。那是**上下文隔离**的机制，而这一节讲的是**谁向谁汇报**的拓扑。

两者是不同维度的问题，但经常一起出现：

- 子智能体解决「主上下文被塞满」
- 拓扑解决「任务怎么拆、结果怎么合」

主管-工人实现可以把每个工人作为独立子智能体；一个主管只调用一个子智能体也是可能的退化结构。是否将它称为多智能体，取决于系统边界与术语定义。

## 一个判断拓扑的简单方法

不要先想「用几个 agent」，先回答三个问题：

1. **下一步由谁决定？** 若应用代码预先规定步骤，可先评估固定 workflow（即使其中有条件分支）；若模型根据中间结果选择下一步，再评估动态控制的 agent 结构。
2. **有哪些子任务能在不等待彼此结果时独立完成？** 这些任务可评估是否并行；依赖前序结果的任务需要串行或分阶段执行。
3. **参与者是否拿到不同证据，或承担不同且可验证的检查目标？** 若否，多角色辩论可能只是重复采样；若是，也仍需用任务集验证其是否改善结果。

这些问题用于生成候选结构，不会自动决定拓扑。还要把失败代价、共享状态、权限边界、预算与验收方式放进决策；成本是其中一项，下一节会展开。

## 中心协调结构的收益与代价

中心协调可能带来三类工程便利，但都依赖实现和验收，不能仅凭拓扑图保证：

**第一，输出可以带来源标识。** 若工人回传包含 worker/task/document ID 和来源 span，主管或审计工具可以定位到对应输入；ID 只帮助定位，不能证明来源准确或语义正确。流水线也可以保留逐阶段来源，因此这不是层级拓扑独有的能力。

**第二，独立任务有机会并行。** 工人之间无需互相等待时，调度器可以并发发起请求。在理想的同时启动、无队列/限流/共享瓶颈情况下，worker 阶段墙钟时间接近最慢 worker 的耗时；真实端到端时间还包括排队、限流、编排、重试与汇总，不保证等于 max，也不能据此说成本降低。

**第三，可以按任务限制输入范围。** 只有在 host 确实只向 worker 提供所需材料且控制共享状态时，才形成上下文隔离。它可能减少单次调用里的无关材料，也可能因重复共享背景、更多摘要和 supervisor 汇总而增加总用量；净收益需按同一任务比较。

代价包括中心节点故障、汇总上下文/队列压力、单点权限与仲裁责任。worker 越多，返回内容可能越多；它是否抵消输入隔离或并行收益，取决于压缩、过滤、复核和任务质量，不能只凭规模推断。

## 一个具体的拆解案例

举一个构造任务：「分析一个 200 文件的代码库，找出五个需要核验的技术债候选。」

**拆法一（按文件分）**：200 个工人，每人读一个文件。缺点是没人能看到跨文件的问题 —— 而技术债往往正是跨文件的（重复实现、循环依赖）。

**拆法二（按怀疑对象分）**：先让一个「侦察」agent 扫一遍目录结构和依赖图，列出 20 个可疑点；再让工人分别深入这 20 个点。这里前一步是**探索**，后一步是**验证**。

**拆法三（按视角分）**：三个工人分别从「重复代码」「依赖复杂度」「测试覆盖」三个角度看全部 200 个文件。每个工人都要看全量，所以上下文没有省下来，但视角不同。

拆法二是一个可评估的候选：先用扫描生成候选区域，再让 worker 并行核验。它成立的条件包括扫描召回足够、worker 可独立推进，并且验证收益超过扫描与汇总的开销；“便宜且高信息量”需实测。

拆法一可能漏掉跨文件依赖，可通过依赖图或跨文件验收补足；拆法三会重复装载背景，但不同视角可能带来可验证的覆盖收益。要把重复输入成本与质量/覆盖收益分别测量。

因此，“每份上下文变小”不是拆解质量的充分判据；还要检查被省略的信息、交接成本和最终任务结果。共享背景重复会增加输入量，但不同分工仍可能改善覆盖，需用配对评估判定净收益。

## 主管的提示与工人的回传格式

「来源可定位」「冲突被发现」不会由提示词自动保证。结构化回传可帮助校验字段形状；host 仍需验证来源引用、硬约束、业务规则和权限，必要时把冲突升级给负责人。

### 主管的 system 提示

下面这份提示词可作为起点（构造示例，未实跑）；它不能单独保证主管识别所有冲突或遗漏：

```text
你是一个汇总助手。你会收到若干工人对各自材料的提炼结果，你的任务是产出一份技术复盘。

必须遵守：
1. 逐条检查工人结论之间是否冲突。若有两条结论方向相反，必须把冲突显式列出、说明各自依据，不允许挑一个写。
2. 每条结论必须标注来源文档编号（形如 [D2]）。找不到来源的判断不要写。
3. 无法判断时保留冲突，并写明「需要人工确认」，不要为了给出结论而折中。
4. 工人的提炼可能有遗漏。如果某条结论缺少必要信息，在末尾单列一节说明还缺什么。
```

这段提示词表达了希望主管执行的检查规则，是软约束而非强制保证。要防止冲突被静默合并，应用还应保留原始回传、用规则或人工抽查关键字段，并对遗漏、冲突和拒绝定义显式状态。

### 工人回传的结构

若下游需要机器检查，可以要求工人返回 schema 化结构，而不是只给自由文本。样例为构造数据，未实跑；schema 只能限制字段形状和类型，不能证明字段内容真实：

```json
{
  "worker_id": "w2",
  "doc_id": "D2",
  "key_points": ["数据库连接池上限为 20"],
  "must_keep": [
    {"text": "任何扩容操作都必须避开生产库", "kind": "硬约束", "source_span": "D2:第2句"}
  ],
  "not_found": ["没有找到与容量规划相关的数字"]
}
```

`doc_id`、`worker_id` 和 `source_span` 可用于定位原始记录；宿主必须核验 ID 与 span 对应实际输入，并检查引用内容是否支持结论。`must_keep` 只是字段名，不会让模型必然保留约束；要把它作为硬门槛，需有独立 validator 和失败处理路径。

（另外，本章示例代码会直接读响应里的两个字段：`stop_reason` 是响应里的停止原因字段，`max_tokens` 是输出预算字段 —— 它们的取值与语义在第 11 章第 1 节讲过。）

## 完整可运行代码

下面的历史脚本顺序调用 DeepSeek Anthropic-compatible endpoint，并分别汇总 API 返回的 input/output token 字段。它没有实现并行调度、任务质量评分或语义约束校验；历史版按子串检查“生产库”也不能证明硬约束遵守，本轮已删除这一伪评分。逐次原始响应、完整 usage 与环境快照未归档，因此不应将脚本今天的输出称为对 2026-10-09 结果的复现。DeepSeek 当前文档说明 `/anthropic` endpoint 的 header/请求字段兼容范围，但未在该页列出完整 usage 与 stop reason 语义；再次运行前应先确认目标端点契约。[DeepSeek Anthropic API 文档](https://api-docs.deepseek.com/guides/anthropic_api/)

```python
"""单 agent vs 主管 + 工人：成本模型与边界信息损失。

设计要点：
  1. 文档 D2 里包含一条敏感约束（不要动生产库）；本代码不对最终回答做语义评分，不能判断约束是否保留。
  2. 共享背景做成两种构造规模，便于观察输入变化；每档只有一次运行，不能据此拟合成本倍率或扩展趋势。

**实跑状态：** 这是 2026-10-09 的历史 provider 记录
（`deepseek-flash`），本轮未调用 provider。逐次响应、完整 usage 与
版本指纹没有归档，不能复现历史数字。下面代码只作为 live 调用模板；
运行前须核对目标 endpoint 契约，并将新结果单独采集和登记。
"""
import json
import os
import urllib.request

BG_SMALL = ("团队规范：所有对外输出用简体中文；数值保留两位小数；"
            "不允许编造未在材料中出现的数字；每条结论必须标注来源文档编号。")

# 大背景：模拟「团队规范 + 代码库约定 + 历史模板」这类真实共享上下文
BG_LARGE = BG_SMALL + "\n\n" + "\n".join(
    "约定 %d：服务命名用 kebab-case；配置项放 config/ 下；日志必须带 trace_id；"
    "所有对外接口要有超时与重试；数据库变更走迁移脚本；异常不得吞掉。" % i
    for i in range(1, 41))

DOCS = {
    "D1": "订单服务本周 P99 延迟 820ms，上周 610ms。排查发现新增的推荐调用占用了 34% 的时间。",
    "D2": "数据库连接池上限为 20。注意：任何扩容操作都必须避开生产库，只能先在预发环境验证。",
    "D3": "推荐服务的内存占用从 1.2GB 增长到 2.8GB，主要来自缓存未设上限。",
}

TASK = "根据三份材料写一份技术复盘，指出三个最需要优先处理的问题，并说明理由。"


def call(messages, system, max_tokens=8000):
    body = json.dumps({"model": os.environ["VERIFY_MODEL"], "max_tokens": max_tokens,
                       "system": system, "messages": messages}).encode()
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages", data=body,
        headers={"content-type": "application/json",
                 "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
                 "anthropic-version": "2023-06-01"})
    with urllib.request.urlopen(req, timeout=180) as resp:
        d = json.loads(resp.read())
    u = d.get("usage")
    if not isinstance(u, dict):
        raise RuntimeError("缺少 usage 对象，不能把缺失用量当作 0")
    counts = {}
    for key in ("input_tokens", "output_tokens"):
        value = u.get(key)
        if type(value) is not int or value < 0:
            raise RuntimeError("usage.%s 缺失或无效" % key)
        counts[key] = value
    if d.get("stop_reason") != "end_turn":
        raise RuntimeError("响应未以 end_turn 正常结束；当前示例不汇总截断/其他终态")
    text = "".join(
        b.get("text", "")
        for b in d.get("content", [])
        if b.get("type") == "text"
    )
    if not text.strip():
        raise RuntimeError("没有可评分的文本输出；不能将其计作有效结果")
    return text, counts


def arm_single(bg):
    """一个 agent 读完三份材料，直接产出复盘。"""
    material = "\n\n".join("%s：%s" % (k, v) for k, v in DOCS.items())
    return call([{"role": "user", "content": bg + "\n\n" + material + "\n\n" + TASK}],
                "你是一个严谨的技术分析助手。")


def arm_multi(bg):
    """三个工人各读一份（每人都要装一遍共享背景），主管汇总。"""
    usage, partials = {"input_tokens": 0, "output_tokens": 0}, []
    for k, v in DOCS.items():
        text, counts = call([{"role": "user", "content":
                         bg + "\n\n材料 %s：%s\n\n请提炼这份材料里对复盘有用的要点。" % (k, v)}],
                        "你是一个提炼助手，只输出要点。")
        for key in usage:
            usage[key] += counts[key]
        partials.append("%s 的要点：%s" % (k, text.strip()))
    merged, counts = call([{"role": "user", "content":
                        bg + "\n\n" + TASK + "\n\n各工人的提炼：\n" + "\n".join(partials)}],
                       "你是一个严谨的技术分析助手。")
    for key in usage:
        usage[key] += counts[key]
    return merged, usage, len(partials)


def run_pair(label, bg):
    single, t1 = arm_single(bg)
    multi, t2, n = arm_multi(bg)
    print(
        "%s | single input/output=%d/%d | "
        "serial workers+supervisor input/output=%d/%d | workers=%d"
        % (label, t1["input_tokens"], t1["output_tokens"],
           t2["input_tokens"], t2["output_tokens"], n)
    )
    return single, multi


if __name__ == "__main__":
    print("任务：%s" % TASK)
    print("三份材料共 %d 字" % sum(len(v) for v in DOCS.values()))
    print()
    print("usage 字段仅是 endpoint 报告的 token 数；不是费用、质量或延迟指标")
    s1, m1 = run_pair("小（%d 字）" % len(BG_SMALL), BG_SMALL)
    s2, m2 = run_pair("大（%d 字）" % len(BG_LARGE), BG_LARGE)
    print()
    print("这是每种背景规模各一次的顺序调用，不足以估计波动、并行延迟、语义质量或一般成本倍率。")
    print()
    print("=== 大背景下的单 agent 输出（前 400 字）===")
    print(s2.strip()[:400])
```

## 常见坑

- **先决定「用几个 agent」再想任务怎么拆。** 顺序反了。拓扑是拆解方式的结果，不是起点。
- **用完全互联辩论做可独立并行的任务。** 完全图有 O(N²) 条潜在边；按任务需要选择更稀疏的连接和聚合方式。
- **把流水线与 agent 的术语边界当成唯一标准。** 本章按预定义控制流称其为 workflow，读其他文献时要先核对作者定义。
- **把多个 agent 当成独立证据。** 共同模型、提示和上下文可能产生相关错误；用同任务基线测覆盖和质量。
- **忘记工人之间不通信是一个设计决定。** 它减少了工人之间的直接通信边，但不自动控制总费用；工人仍可能重复劳动或得出矛盾结论，需要显式任务分配、结果聚合和冲突处理。
