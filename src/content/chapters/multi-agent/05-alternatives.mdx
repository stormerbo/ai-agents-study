这一章讲多智能体，这一节先比较更简单的方案。多智能体不是必然的升级：它会增加模型调用、输入/输出 token、协调与错误处理成本，也可能靠独立并行探索、上下文容量或任务隔离换来质量、覆盖或时延收益。具体哪一侧占优取决于任务、调度、缓存、模型与成功标准，因此先建立单 agent 基线，再做同任务对照。

## 为什么它容易被当成第一层

它常被画成「AI 团队」—— 一个主管带着几个专家。这个比喻很直观，但仅增加角色并不能证明有收益。

需要核算的成本包括：每次模型调用实际读取的输入（共享提示可能重复，缓存规则因 provider 而异）、各阶段生成的输出、协调/合并调用、工具与存储、重试、日志和人工复核。摘要可能丢信息，但不是每次摘要都必然造成任务损失；不同上下文与独立探索也可能提升覆盖率。并行只有在子任务能独立推进、运行时确实并发且没有限速/排队瓶颈时，才可能缩短关键路径。

因此先比较三种较简单的替代方案，再按目标任务测量收益与成本；这是一条排查顺序，不是适用于所有系统的固定架构等级。

## 替代一：先把单个 agent 做到位

有些看起来需要多智能体的任务，实际瓶颈可能是单 agent 的提示、工具或上下文管理；也有些开放式、宽搜索任务确实需要多个独立方向。不要靠架构直觉归类，先记录单 agent 在目标任务上的质量、错误类型、成本和延迟，再测试具体替代方案。

第 6 章讲检索，第 7 章讲记忆，第 3 章讲上下文工程 —— 这三章解决的问题，正是「单个 agent 上下文装不下」这一类。**如果瓶颈只是材料无法全部装入上下文，先比较按需检索与多智能体拆分；哪一种更合适要按任务质量、成本和延迟测量。**

一个具体的检查顺序：

1. 内容真的需要同时装进一个上下文吗？还是可以按需检索？（第 6 章）
2. 历史真的需要全部保留吗？还是可以压缩成结构化笔记？（第 3 章第 4 节）
3. 工具的结果真的需要完整回填吗？还是可以只回填摘要？

这些检查能指出一个较便宜的候选方案，但不会单独证明多智能体没有价值；仍要在同一任务和质量门槛下比较。

## 替代二：用工具调用代替子任务

「让一个专门的 agent 去做 X」经常可以被「写一个工具来做 X」替代。

工具通常封装固定的数据读取或业务操作；agent 会通过模型调用选择步骤或调用工具。若某个操作的业务规则和输入输出契约已经明确，把执行逻辑做成普通函数/工具通常更容易测试、重试与审计；但调用方仍可能需要模型来选择何时调用、填什么参数，因此不能笼统承诺成本更低或不需要模型。

不要用第 10 章的 14.4 倍支持这个选择：那一节比较的是 API 工具提议与本地合成 UI 自动化，两边执行边界和“成功”判据不同，原始逐次响应也缺失。它不能量出“确定性工具 vs agent 子任务”的成本差异（见 ERR-067）。

一个「用工具代替 agent」的具体形状（示例：伪代码，说明形状，不可直接运行；真实项目里用第 13 章那套工具装饰器）：

```python
@tool
def extract_points(doc_id: str) -> dict:
    """读取指定文档，按固定规则抽取要点。doc_id 形如 D1/D2/D3。"""
    text = DOCS[doc_id]
    return {"doc_id": doc_id, "sentences": split_sentences(text)}
```

注意它没有「自己决定读哪份」的能力 —— 读哪份由调用方给定。这样可以减少模型要处理的开放式决策；整体成本仍要把调用方模型、工具执行、输入输出与运维放在一起比较。

## 替代三：用 workflow 编排代替 agent 编排

如果子任务之间的关系是固定的（先 A 再 B 再 C），那就写成 workflow。你不需要 agent 来决定顺序 —— 顺序你本来就知道。

第 1 章讲过 workflow 和 agent 的分界：**控制流在谁手里。** 有些主管式架构把步骤选择交给模型，也可以由 host 代码安排多个 agent、并行执行或按显式状态机路由。若业务步骤固定，就让代码掌握顺序，并只在需要理解或判断的节点调用模型，减少不必要的决策与失败路径。

一个实用的判断：如果阶段、状态转换和业务分支规则已知且可表达为代码，就让 workflow/host 控制这些步骤；把确实需要开放式理解或生成的节点交给模型。能画流程图本身不够，因为图中的条件也可能仍需模型理解输入后才能判断。

下面是一个固定顺序的 workflow，自包含、可运行 —— 注意四步的顺序全在 `STEPS` 这个列表里，没有任何一步由模型决定：

```python
def extract(text):
    return text.split("。")


def validate(items):
    return [x for x in items if len(x) > 4]


def rewrite(items):
    return ["（改写）" + x for x in items]


STEPS = [extract, validate, rewrite]


def run_workflow(text, steps=STEPS):
    for step in steps:
        text = step(text)
    return text


if __name__ == "__main__":
    print(run_workflow("订单服务延迟上升。缓存未设上限。ok。"))
```

## 那什么时候它可能值得

把它当成一个待验证的方案，而不是由三条口号自动推出的选择。至少要回答：

1. **任务能否拆成可并行或需要隔离的子任务？** 先标出依赖关系。存在依赖的步骤仍可由多个 agent 执行，但并行节省会减少，交接和协调则会增加。
2. **每个子任务是否有清晰、互补的职责或上下文？** 只换角色名不保证观点多样；多个 agent 读取同一材料也并非必然无效，但应检查它们是否找到不同证据、错误或方案，而不是只产生改写。
3. **在相同任务与验收标准下，预期质量、覆盖、隔离或延迟收益是否值得新增调用、输出、协调与故障成本？** 单 agent 的上下文不够只是一个可能理由，不是唯一理由。

并行可能缩短墙钟时间，但“总延迟 = 最慢工人”只适用于所有工人真正同时启动、彼此无依赖且不受调度、限速、排队和汇总阶段影响的理想化部分；端到端延迟还包括规划、交接、汇总与重试。测量时同时报告关键路径时延和每任务总用量，不要用理论并行收益代替实测。

所以，“不需要并行且上下文也够”可以是回退到单 agent 的信号之一；如果独立验证、不同权限或任务分解能改善质量/风险，仍应比较其净收益。

## 一个诚实的总结

这一章花了很多篇幅讲多智能体，最后却建议先别用 —— 这两件事不矛盾。

多智能体是一个可用于特定任务形态的架构选项：例如独立方向的并行探索、相互隔离的工作空间，或确实不同的子任务。它不代表架构升级。若分解没有提升目标质量、覆盖、风险边界或时延，额外的模型调用、汇总与故障路径可能只增加成本；这些损失不一定抛异常，因此应把质量与成本指标一起纳入验收。

第 2 节的成本模型可以帮助估算新增调用的输入和输出负载；它不能单独判断质量或风险收益。是否值得仍要在目标任务的基线和验收标准下比较。


## 一份可执行的决策顺序

把这一节的三个替代方案整理成一条可以照着走的顺序：

**第一步，定义基线与验收。** 选定代表性任务集、任务级评分 rubric、严重错误定义、endpoint/模型版本、预算与延迟口径。单 agent 和候选方案对同一任务集做配对比较；一次运行只能用于调试，不能支持稳定的质量结论。

**第二步，检查单 agent 的具体瓶颈。** 看提示、材料、历史与工具回填：能否按需检索，能否在验证不丢关键信息的前提下压缩，能否只回填必要字段？这些是候选改进，需要在同一任务与评分标准下测，不能预设任何一项必然优于多智能体。

**第三步，检查哪些步骤已确定。** 固定的数据访问、校验、权限与状态转换可以放进工具或 workflow；仍需模型理解输入或生成内容的节点保留模型。第 10 章的 384 与 5,528 来自执行边界和成功条件不同的演示，不能量化工具与 agent 的成本差距（ERR-067）。

**第四步，再评估多智能体。** 汇总所有 worker、manager、工具调用、重试与输出成本，并比较任务质量、严重错误、端到端延迟和隔离收益。只有达到预先设定的产品门槛，收益才足以支持引入复杂度。

这条顺序强调先写清任务与验收，再比较实现方案。前期检查可以降低无效实现，但不能替代真实对照；多智能体可能出现结果看似合理、质量却未达标的静默错误，因此要把质量与成本一起纳入验收。

## 如果已经用了，怎么判断该不该退回去

一个很实际的问题：系统已经跑起来了，怎么知道该不该拆掉这层多智能体？三个信号：

**信号一，token 体积明显上升，而质量或延迟没有达到预设目标。** 第 3 章的 8.1 倍只是缺少原始轨迹和质量评分的历史 token 摘要，不能证明那层拆解没有收益。比较前要固定任务、质量门槛和 endpoint 计量口径。

**信号二，工人的输入内容高度重叠，职责与输出也高度重复。** 字数接近本身不是问题：不同子任务可以读相近长度但关注不同证据；字数差异也不能证明信息隔离。比较材料来源、片段重叠、任务目标和输出中新增的信息，并查看重复上下文占用。

**信号三，主管提示重复编码了本来可由 host 明确执行的业务状态转换。** 这提示可以把确定性路由、权限与重试策略移到 workflow；开放式内容判断仍可交给模型。不要单凭提示中“如果……就……”的数量判断，因为模型也需要清楚的业务约束。

这些都是诊断线索，不是自动退役阈值。先按任务 ID 关联两条路径，配对记录输入/输出用量、真实端到端时延、质量与严重错误；预算与 token 增幅筛查值应由团队按风险和服务目标预先设定。
## 本地配对指标示例

比较单 agent 与多智能体时，每一行应绑定同一个任务 ID，并记录**全链路**输入 token、输出 token、墙钟延迟和按预先定义 rubric 得到的任务结果。多智能体一行需汇总所有 worker、manager、grader 与重试调用；不要只用 worker 输入长度或某个局部请求代表总成本。下例数据完全构造，只用于展示怎样汇总配对结果（每题每组仅运行一次，不支持统计推断）：

```python
from statistics import mean

SINGLE = [
    {"id": "a", "input": 1000, "output": 200, "seconds": 2.0, "passed": True},
    {"id": "b", "input": 1000, "output": 180, "seconds": 2.4, "passed": False},
    {"id": "c", "input": 1000, "output": 220, "seconds": 2.1, "passed": True},
    {"id": "d", "input": 1000, "output": 190, "seconds": 2.3, "passed": False},
]
MULTI = [
    {"id": "a", "input": 2800, "output": 500, "seconds": 2.4, "passed": True},
    {"id": "b", "input": 3000, "output": 400, "seconds": 2.7, "passed": True},
    {"id": "c", "input": 2600, "output": 600, "seconds": 2.5, "passed": True},
    {"id": "d", "input": 2700, "output": 450, "seconds": 2.6, "passed": False},
]


def by_id(rows):
    result = {row["id"]: row for row in rows}
    if len(result) != len(rows):
        raise ValueError("task IDs must be unique within each condition")
    return result


def summarize(rows):
    return {
        "tasks": len(rows),
        "passed": sum(row["passed"] for row in rows),
        "input_tokens": sum(row["input"] for row in rows),
        "output_tokens": sum(row["output"] for row in rows),
        "mean_seconds": round(mean(row["seconds"] for row in rows), 2),
    }


def paired_summary(single, multi):
    left, right = by_id(single), by_id(multi)
    if left.keys() != right.keys():
        raise ValueError("conditions must cover the same task IDs")
    improved = sum(not left[key]["passed"] and right[key]["passed"] for key in left)
    regressed = sum(left[key]["passed"] and not right[key]["passed"] for key in left)
    return {"only_multi_passed": improved, "only_single_passed": regressed,
            "both_passed": sum(left[k]["passed"] and right[k]["passed"] for k in left),
            "both_failed": sum(not left[k]["passed"] and not right[k]["passed"] for k in left)}


if __name__ == "__main__":
    print("single:", summarize(SINGLE))
    print("multi:", summarize(MULTI))
    print("paired outcomes:", paired_summary(SINGLE, MULTI))
```

构造输出为：单 agent 2/4 通过，输入/输出 4,000/790 token；多智能体 3/4 通过，输入/输出 11,100/1,950 token；配对结果是仅多智能体通过 1 题、仅单 agent 通过 0 题、两边都通过 1 题、两边都失败 2 题。**这只是代码输出的样例，不是模型实测**；4 道题的配对差异也不能证明质量提升。真实对照要固定评分标准、顺序随机化、重复随机模型运行，并以任务/用户为抽样单位评估区间。时延需用实际并发实现测量；本例只汇总给定延迟记录，不模拟调度。

## 旧实验脚本的适用边界

下面保留的是 2026-10-09 的 DeepSeek Anthropic 兼容端点脚本形状，不能作为当前模型表现或多智能体收益证据。旧报告只留有汇总数字，逐次请求/响应、准确模型版本、评分记录和账单未归档，因此无法复算。脚本按顺序执行 worker，并没有实现并行，也没有测量延迟；它只打印接口返回的 token 用量和文本，不能据此判断质量、风险或“成本倍数”。

运行前需设置 `VERIFY_MODEL`、`ANTHROPIC_BASE_URL` 和 `ANTHROPIC_AUTH_TOKEN`。代码把每次请求的 input/output usage 分开记录；只有 `stop_reason == "end_turn"` 且提取到非空文本时才返回，避免把截断、其他终止状态或空完成响应当作有效答案。不同兼容端点的 stop-reason 语义应以对应 provider 文档和实际响应验证。脚本仍然是顺序单次调用：不随机化顺序、不重复采样、不评分，也不控制缓存/限速；请把它当作 API 接线示例，不是可复现的评测 harness。

```python
"""顺序调用演示：统计接口 usage，不对质量、延迟或架构收益下结论。"""
import json
import os
import urllib.request

BG = "团队规范：对外使用简体中文；数字必须来自材料；结论标注来源。"
DOCS = {
    "D1": "订单服务本周 P99 延迟 820ms，上周 610ms；新增推荐调用占用 34% 时间。",
    "D2": "连接池上限 20；扩容必须先在预发验证，禁止操作生产库。",
    "D3": "推荐服务内存从 1.2GB 增至 2.8GB，主要来自无上限缓存。",
}
TASK = "根据材料写技术复盘，列出优先处理的问题和来源。"


def call(messages, system, max_tokens=2000):
    payload = json.dumps({
        "model": os.environ["VERIFY_MODEL"],
        "max_tokens": max_tokens,
        "system": system,
        "messages": messages,
    }).encode()
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages",
        data=payload,
        headers={
            "content-type": "application/json",
            "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
            "anthropic-version": "2023-06-01",
        },
    )
    with urllib.request.urlopen(req, timeout=180) as response:
        data = json.loads(response.read())

    stop_reason = data.get("stop_reason")
    if stop_reason != "end_turn":
        raise RuntimeError(f"non-final response; stop_reason={stop_reason!r}")
    usage = data.get("usage", {})
    text = "".join(
        block.get("text", "")
        for block in data.get("content", [])
        if block.get("type") == "text"
    ).strip()
    if not text:
        raise RuntimeError("final response contains no text")
    return {
        "text": text,
        "stop_reason": stop_reason,
        "input_tokens": (
            usage.get("input_tokens", 0)
            + usage.get("cache_read_input_tokens", 0)
            + usage.get("cache_creation_input_tokens", 0)
        ),
        "output_tokens": usage.get("output_tokens", 0),
    }


def run_single():
    material = "\n\n".join(f"{key}: {value}" for key, value in DOCS.items())
    return call(
        [{"role": "user", "content": f"{BG}\n\n{material}\n\n{TASK}"}],
        "你是严谨的技术分析助手。",
    )


def run_manager_workers():
    # 注意：for 循环是串行调度，不代表并行架构。
    workers = []
    total_input = total_output = 0
    for key, value in DOCS.items():
        result = call(
            [{"role": "user", "content": f"{BG}\n\n{key}: {value}\n提炼相关事实。"}],
            "只提炼材料事实并保留来源编号。",
        )
        total_input += result["input_tokens"]
        total_output += result["output_tokens"]
        workers.append(f"{key}: {result['text']}")

    manager = call(
        [{"role": "user", "content": f"{BG}\n\n{TASK}\n\n" + "\n".join(workers)}],
        "你是严谨的技术分析助手。",
    )
    return {
        "text": manager["text"],
        "input_tokens": total_input + manager["input_tokens"],
        "output_tokens": total_output + manager["output_tokens"],
    }


if __name__ == "__main__":
    for label, run in (("single", run_single), ("manager+workers", run_manager_workers)):
        result = run()
        print(
            f"{label}: input={result['input_tokens']} "
            f"output={result['output_tokens']}"
        )
        print(result["text"])
```

## 常见坑

- **把多智能体当成「更高级的架构」。** 它是在特定条件下正确的工具，不是升级路径。
- **跳过检索直接上多智能体。** 当问题是材料无法全部装入上下文时，按需检索是值得与拆分方案对照的候选路径。
- **用 agent 执行完全确定的步骤。** 若决策规则已经明确，先评估能否将其放进可测试的函数或 workflow；工具边界是否更便宜，仍需按同一完整任务与成本口径比较。
- **只看理论并行收益。** 只有实际并发且子任务可独立推进时，才可能缩短关键路径；记录真实端到端延迟与全链路成本。
- **只看运行成功或 token 倍数。** 看起来像模像样的输出不等于达到任务验收；同时记录质量、严重错误、总用量和实际延迟。
