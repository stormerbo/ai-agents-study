这一章讲的是多智能体，但这一节的建议是**先别用**。理由不是它不好，而是它的成本结构决定了它是最后才该考虑的那一层 —— 而它经常被当成第一层。

## 为什么它容易被当成第一层

因为它听起来最像「AI 团队」—— 一个主管带着几个专家。这个比喻很直观，也很有吸引力，但它在工程上是**最贵的一种拆法**。

回顾一下代价：每多一个上下文，就要多付一遍装进它的内容；多一份摘要，就多一次信息损失的机会；多一条边界，就多一个失败点。而这些代价换来的是**并行**和**隔离** —— 只有当任务确实需要这两样时，这笔钱才花得值。

所以这一节给三个替代方案，按「先试哪个」的顺序排。

## 替代一：先把单个 agent 做到位

绝大多数被判为「需要多智能体」的任务，问题其实出在单个 agent 身上：提示不够具体、工具不够好用、上下文管理没做。

第 6 章讲检索，第 7 章讲记忆，第 3 章讲上下文工程 —— 这三章解决的问题，正是「单个 agent 上下文装不下」这一类。**如果你还没试过按需检索，就直接上多智能体，你是在用最贵的方式解决一个更便宜的问题。**

一个具体的检查顺序：

1. 内容真的需要同时装进一个上下文吗？还是可以按需检索？（第 6 章）
2. 历史真的需要全部保留吗？还是可以压缩成结构化笔记？（第 3 章第 4 节）
3. 工具的结果真的需要完整回填吗？还是可以只回填摘要？

三个问题的答案如果都是「可以优化」，那多智能体就不是必需的。

## 替代二：用工具调用代替子任务

「让一个专门的 agent 去做 X」经常可以被「写一个工具来做 X」替代。

区别在于：agent 是一个会自己决策的东西，工具是一个确定性的东西。如果那段工作的步骤是固定的，**写成一个工具比派一个 agent 便宜得多** —— 没有额外上下文、没有信息损失、没有边界。

第 10 章的第 5 节量过这个差别：同一件事，走 API 工具调用 384 token，走 agent 循环 5,528 token —— **14.4 倍**。虽然那是界面自动化的对比，但结论的机制是一样的：**能确定的事情不要交给会决策的东西。**

一个「用工具代替 agent」的具体形状（示例：伪代码，说明形状，不可直接运行；真实项目里用第 13 章那套工具装饰器）：

```python
@tool
def extract_points(doc_id: str) -> dict:
    """读取指定文档，按固定规则抽取要点。doc_id 形如 D1/D2/D3。"""
    text = DOCS[doc_id]
    return {"doc_id": doc_id, "sentences": split_sentences(text)}
```

注意它没有「自己决定读哪份」的能力 —— 读哪份由调用方给定。**把决策从这一步里拿掉，就是它比 agent 便宜的全部原因。**

## 替代三：用 workflow 编排代替 agent 编排

如果子任务之间的关系是固定的（先 A 再 B 再 C），那就写成 workflow。你不需要 agent 来决定顺序 —— 顺序你本来就知道。

第 1 章讲过 workflow 和 agent 的分界：**控制流在谁手里。** 多智能体把控制流交给了主管模型；而如果流程是固定的，交给它就是白花一笔决策的钱，还多了一个出错的地方。

一个实用的判断：**如果你能画出流程图，就写成 workflow。** 只有当图上的分支条件需要模型来判断时，才把那一处交给模型。

下面是一个固定顺序的 workflow，自包含、可运行 —— 注意四步的顺序全在 `STEPS` 这个列表里，没有任何一步由模型决定：

```python
def extract(text):
    return text.split("。")


def validate(items):
    return [x for x in items if len(x) > 4]


def rewrite(items):
    return ["（改写）" + x for x in items]


STEPS = [extract, validate, rewrite]


def run_workflow(text, steps=STEPS):
    for step in steps:
        text = step(text)
    return text


if __name__ == "__main__":
    print(run_workflow("订单服务延迟上升。缓存未设上限。ok。"))
```

实跑输出（2026-10-12）：`['（改写）订单服务延迟上升', '（改写）缓存未设上限']`。如果这段流程交给 agent 编排，你付的是「让模型判断该不该改写」的钱，而答案你早就知道。

## 那什么时候它是对的

三条同时成立时：

1. **任务可以拆成互相独立的子任务**（主管-工人拓扑成立）
2. **子任务的输入真的不同**（不是把同一份内容复制 N 份）
3. **并行带来的延迟收益值得那份成本**，或者单个上下文确实装不下

第 3 条里的「并行收益」经常被忽略。多智能体的一个真实好处是**延迟**：三个工人并行跑，总延迟是 max 而不是 sum。对交互式产品，这一点可能比 token 成本更重要。

所以有一条很实际的判据：**如果你不需要并行、也不是上下文真的装不下，那就别用多智能体。**

## 一个诚实的总结

这一章花了很多篇幅讲多智能体，最后却建议先别用 —— 这两件事不矛盾。

多智能体是一个**在特定条件下正确**的工具：需要隔离、需要并行、且子任务的信息确实不同。它不是一个「更高级的架构」。而它最危险的地方在于：**用错了不会有明显的错误信号** —— 系统会跑通，结果看起来也合理，只是慢了几倍、贵了几倍。

第 2 节的成本模型就是用来发现这件事的：算一下「内容 × 装载次数」，你就能提前知道这次拆解值不值。


## 一份可执行的决策顺序

把这一节的三个替代方案整理成一条可以照着走的顺序：

**第一步，先量单 agent 的基线。** 跑一次单 agent 版本，记下 token、延迟、成功率。没有基线，后面所有比较都是感觉。

**第二步，检查上下文是不是真的不够。** 把单 agent 的提示和材料过一遍：有没有可以按需检索的内容？有没有可以压缩的历史？工具返回有没有可以只回填摘要的？三处只要有一处能优化，先做它。

**第三步，检查子任务是不是确定的。** 如果一段工作的步骤是固定的，把它写成工具或 workflow —— 不要派一个 agent。第 10 章实测过这个量级差别（384 对 5,528）。

**第四步，到这一步才考虑多智能体。** 并且先算一次成本倍数，再问一句「这份并行/隔离值不值这个倍数」。

这条顺序的本质是：**从最便宜的可能性开始排除。** 它的成本很低 —— 前四步里前面几步都是读代码和算账，不需要真的实现多智能体。而如果跳过它们直接上多智能体，你可能会花几天时间实现一个贵 8 倍、收益为零的系统，而且它跑起来没什么异常。

**多智能体最贵的成本不是 token，是「用错了也不会报错」这件事。** 所以这一节的重点不是劝你别用，是劝你先花十分钟算一下 —— 那十分钟大概率能省下几天。

## 如果已经用了，怎么判断该不该退回去

一个很实际的问题：系统已经跑起来了，怎么知道该不该拆掉这层多智能体？三个信号：

**信号一，总 token 是单 agent 版本的 3 倍以上，而延迟没有明显下降。** 说明你既没拿到并行的好处，也没拿到隔离的好处 —— 那这层拆解只有成本。第 3 章那个 8.1 倍的案例就是这种形状。

**信号二，工人的输入长度彼此很接近。** 如果每个工人装的材料差不多大，说明你可能是把同一份内容切成了几份，而不是真的按信息差拆的。这正好是下一节成本模型里说的「B 被重复装载，M 没有变小」。

**信号三，主管的提示里出现了大量「如果……就」的规则。** 那说明真正的编排逻辑是你写的，不是主管判断的 —— 那就该把它写成 workflow，而不是让一个模型去执行你写好的规则。

三个信号里，第一个最好量（就是跑两次比较），第三个最好认（看一眼主管的提示就知道）。
## 第一步要的采集代码：一个可复用的基线脚手架

「先量单 agent 的基线」需要一个能量倍数的壳。下面这个自包含（示例：构造数据，未实跑 —— FakeAgent 的输入是构造的，脚本本次已跑通）：

```python
"""可复用实验脚手架：量出「多智能体 / 单 agent」的倍数与延迟。

默认用 FakeAgent（不需要凭据）；把 fake_single / fake_multi 换成你自己的 agent 函数即可。
  用法：python scaffold.py             # 跑对照
        python scaffold.py --baseline  # 只跑单 agent，建立基线
实跑状态：2026-10-12。
"""
import argparse
import time

FILES = {"D1": 900, "D2": 900, "D3": 900}     # 每份材料按字符数量级计
BG = 200                                       # 共享背景按字符数量级计
COPIES = len(FILES) + 1                        # 每个工人一遍 + 主管一遍


def fake_single(task):
    return {"output": "复盘", "tokens": BG + sum(FILES.values()) + 400}


def fake_multi(task):
    time.sleep(0.05)                           # 模拟主管汇总的额外延迟
    return {"output": "复盘",
            "tokens": BG * COPIES + sum(FILES.values()) + 80 * len(FILES) + 400}


def measure(fn, task):
    t0 = time.time()
    r = fn(task)
    return {"tokens": r["tokens"], "seconds": round(time.time() - t0, 3)}


def retreat_signals(base, multi, worker_inputs):
    """「该退回去」那三个信号，各给一个可算的探针。"""
    mean = sum(worker_inputs) / len(worker_inputs)
    spread = max(worker_inputs) - min(worker_inputs)
    return {
        "1_token 是基线 3 倍以上、延迟却没降": multi["tokens"] / base["tokens"] > 3
        and (base["seconds"] - multi["seconds"]) < 0.1,
        "2_工人输入长度彼此接近": spread < 0.1 * mean,
    }


def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--baseline", action="store_true", help="只跑单 agent，建立基线")
    args = ap.parse_args()

    task = "根据三份材料写技术复盘"
    base = measure(fake_single, task)
    print("基线（单 agent）：%s" % base)
    if args.baseline:
        return
    multi = measure(fake_multi, task)
    print("对照（主管 + 3 工人）：%s" % multi)
    print("倍数：%.2fx，延迟差：%.3f 秒" % (multi["tokens"] / base["tokens"],
                                          multi["seconds"] - base["seconds"]))
    print("退回信号：%s" % retreat_signals(base, multi, [1080, 1050, 1120]))


if __name__ == "__main__":
    main()
```

实跑输出（2026-10-12，延迟差随机器波动）：

```text
基线（单 agent）：{'tokens': 3300, 'seconds': 0.0}
对照（主管 + 3 工人）：{'tokens': 4140, 'seconds': 0.051}
倍数：1.25x，延迟差：0.051 秒
退回信号：{'1_token 是基线 3 倍以上、延迟却没降': False, '2_工人输入长度彼此接近': True}
```

用的时候把 `fake_single` / `fake_multi` 换成你自己的 agent 函数（返回 `{"output", "tokens"}` 即可），另外两个探针就会在你的真实数据上给出判断：信号一（token 三倍以上、延迟却没降）和信号二（工人输入长度彼此接近）。**没有这个壳，第 5 节那三个信号永远只是三个句子。**

## 完整可运行代码

下面这段代码把单 agent 与主管 + 工人两条路线并排跑，并打印倍数的拆解 —— 它就是本节「先算一次」那条建议的实现。

```python
"""单 agent vs 主管 + 工人：成本模型与边界信息损失。

设计要点：
  1. 文档 D2 里埋了一条**硬约束**（不要动生产库），看它能不能穿过多层摘要活到最后。
  2. 共享背景做成两种规模 —— 因为成本倍数主要由「共享内容相对单份内容有多大」决定。

实跑状态：2026-10-09，deepseek-flash。
"""
import os
import json, os, urllib.request

BG_SMALL = ("团队规范：所有对外输出用简体中文；数值保留两位小数；"
            "不允许编造未在材料中出现的数字；每条结论必须标注来源文档编号。")

# 大背景：模拟「团队规范 + 代码库约定 + 历史模板」这类真实共享上下文
BG_LARGE = BG_SMALL + "\n\n" + "\n".join(
    "约定 %d：服务命名用 kebab-case；配置项放 config/ 下；日志必须带 trace_id；"
    "所有对外接口要有超时与重试；数据库变更走迁移脚本；异常不得吞掉。" % i
    for i in range(1, 41))

DOCS = {
    "D1": "订单服务本周 P99 延迟 820ms，上周 610ms。排查发现新增的推荐调用占用了 34% 的时间。",
    "D2": "数据库连接池上限为 20。注意：任何扩容操作都必须避开生产库，只能先在预发环境验证。",
    "D3": "推荐服务的内存占用从 1.2GB 增长到 2.8GB，主要来自缓存未设上限。",
}

TASK = "根据三份材料写一份技术复盘，指出三个最需要优先处理的问题，并说明理由。"


def call(messages, system, max_tokens=8000):
    body = json.dumps({"model": os.environ["VERIFY_MODEL"], "max_tokens": max_tokens,
                       "system": system, "messages": messages}).encode()
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages", data=body,
        headers={"content-type": "application/json",
                 "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
                 "anthropic-version": "2023-06-01"})
    with urllib.request.urlopen(req, timeout=180) as resp:
        d = json.loads(resp.read())
    u = d.get("usage", {})
    tin = (u.get("input_tokens", 0) + u.get("cache_read_input_tokens", 0)
           + u.get("cache_creation_input_tokens", 0))
    text = "".join(b.get("text", "") for b in d.get("content", []) if b.get("type") == "text")
    if not text.strip() and d.get("stop_reason") == "max_tokens":
        raise RuntimeError("测量故障：空输出 + max_tokens，需调大预算，不是模型失败")
    return text, tin + u.get("output_tokens", 0)


def arm_single(bg):
    """一个 agent 读完三份材料，直接产出复盘。"""
    material = "\n\n".join("%s：%s" % (k, v) for k, v in DOCS.items())
    return call([{"role": "user", "content": bg + "\n\n" + material + "\n\n" + TASK}],
                "你是一个严谨的技术分析助手。")


def arm_multi(bg):
    """三个工人各读一份（每人都要装一遍共享背景），主管汇总。"""
    tok, partials = 0, []
    for k, v in DOCS.items():
        text, t = call([{"role": "user", "content":
                         bg + "\n\n材料 %s：%s\n\n请提炼这份材料里对复盘有用的要点。" % (k, v)}],
                        "你是一个提炼助手，只输出要点。")
        tok += t
        partials.append("%s 的要点：%s" % (k, text.strip()))
    merged, t2 = call([{"role": "user", "content":
                        bg + "\n\n" + TASK + "\n\n各工人的提炼：\n" + "\n".join(partials)}],
                       "你是一个严谨的技术分析助手。")
    tok += t2
    return merged, tok, len(partials)


def run_pair(label, bg):
    single, t1 = arm_single(bg)
    multi, t2, n = arm_multi(bg)
    alive = ("✅" if "生产库" in single else "❌") + " / " + ("✅" if "生产库" in multi else "❌")
    print("%-14s %-10d %-12d %-9.2fx %s" % (label, t1, t2, t2 / t1, alive))
    return single, multi


if __name__ == "__main__":
    print("任务：%s" % TASK)
    print("三份材料共 %d 字" % sum(len(v) for v in DOCS.values()))
    print()
    print("%-14s %-10s %-12s %-10s %s" % ("共享背景", "单 agent", "主管+3 工人", "倍数", "硬约束存活"))
    s1, m1 = run_pair("小（%d 字）" % len(BG_SMALL), BG_SMALL)
    s2, m2 = run_pair("大（%d 字）" % len(BG_LARGE), BG_LARGE)
    print()
    print("看点：两次的倍数很接近（见上表），并没有随背景变大而明显升高。")
    print("机制解释：多智能体只把【输入】乘以份数，【输出】不乘 ——")
    print("  3 个工人的输出很小，主管的输出与单 agent 相当。")
    print("所以背景越大、输入占比越高时，倍数才会趋近「份数」（这里是 4）。")
    print("本次两个规模都还没到那个区间（输出仍与输入同量级），所以看不出差异。")
    print()
    print("=== 大背景下的单 agent 输出（前 400 字）===")
    print(s2.strip()[:400])
```

## 常见坑

- **把多智能体当成「更高级的架构」。** 它是在特定条件下正确的工具，不是升级路径。
- **跳过检索直接上多智能体。** 第 6 章的按需检索往往能用更低成本解决「上下文装不下」。
- **用 agent 做步骤固定的工作。** 第 10 章实测过：能确定的事交给会决策的东西，代价是 14 倍量级。
- **忘记算延迟收益。** 多智能体真正的强项之一是并行 —— 如果不需要并行，成本就白付了。
- **用错了却没有反馈。** 它跑通、结果也像模像样，只是贵几倍。所以要主动算倍数，而不是等出问题。
