多智能体保留了单个 agent 的错误来源（错误判断、格式不符、工具失败），还增加了**跨组件交接**带来的风险：信息遗漏、口径不一致、冲突没有被解决，以及汇总阶段成为资源瓶颈。本节把它们作为需要检查的失败类别，不声称多 agent 的故障都发生在边界上。

这一节讨论三类典型风险，并区分可复核的本地机制、历史观察摘要和仍需按任务验证的假设。

## 失败一：信息在边界上丢失

每个工人通常只把约定的回传结果交给主管，不能假定完整过程会自动进入主管上下文。如果某个细节没有写进当前摘要，主管此刻就看不到它；只要原始材料或工人执行记录仍被保留，就可以通过检索、回查或重跑恢复。若源材料与记录都已丢弃，才可能无法恢复。因此应明确保存策略与可回查路径，而不要把「不在摘要里」说成「永久消失」。

第 3 章第 4 节的历史记录称：一份摘要把 8 条要点压缩为 7 条，遗漏了「不要动生产库」约束。逐次请求/响应、提示、精确模型快照和判分记录没有归档，因此这里只能把它作为**未独立复核的历史案例摘要**，不能据此估计约束丢失率或认定这类约束更易被丢弃。

本章原对照脚本把最终文本是否含有「生产库」子串当成约束存活判据。这个检查无法区分遵守、否定、误用或只是在解释风险时提到该词；因此原记录中的「两边都存活」没有可靠的语义评分支持，不能据此说失败未复现，更不能称其为低频。

在只给工人局部目标、没有传递最终任务或必须保留字段的设计中，工人可能无法按主管的后续决策来优化回传；如果完整目标、证据或共享状态也传给了工人，这个风险会不同。故障机制取决于具体交接契约，而不是 worker 天生看不到主管任务。

缓解办法可以分为三类，单独使用任何一类都不构成正确性保证：

1. **把必须保留的字段写进交接契约。** 为硬约束、例外与禁止项预留字段或稳定 ID；提示只能提高注意度，仍须检查缺项和错误值。
2. **使用结构化回传并在宿主侧校验。** schema 能约束字段形状和类型，不能证明事实正确、证据匹配或业务语义完整；无效结果应进入拒绝、回查或人工复核路径。
3. **保留可回查的来源。** 如果原文、工具结果或 worker 记录仍可访问，主管可按需重新取证；材料已被丢弃、过期或权限撤销时，回查不能恢复原始信息。

## 失败二：工人之间的结论互相矛盾

在 supervisor-worker 的独立任务设计中，worker 可能不直接通信；这是拓扑选择，可减少直接协调路径，但不保证总成本可控。此时 worker 可能得出互相矛盾的结果 —— 而且**两边都自认为有依据**。

一个构造例子：任务按地区拆给工人，给出的比率分别是华东 Q1 12%、Q2 8%，华南 Q1 6%、Q2 11%。一个地区下降、另一个上升；两份分区结论并不矛盾，只是回答了不同子问题。要判断整体方向，还必须拿到每个分区的分子、分母、时间窗口和纳入规则，再按总分子/总分母汇总。仅凭百分比或地区标签，无法推出整体趋势。

主管拿到两份矛盾结论时可能会挑一个、并列呈现，或请求补充证据；哪一种选择都不是必然行为。前者可能漏掉真实趋势，后者可能把未解决的矛盾交给用户。应通过提示、显式裁决规则和测试来约束，而不是把某个行为当作模型固定倾向。

当主管缺少人口权重或原始数据时，不能让它凭空裁决。可以要求补充数据/再查一轮，也可以选择更适合问题的切分维度。按地区切可能需要在汇总时结合权重，按时间切也不自动保证没有混杂因素；这些是拆解启发式，不是普遍定律。

切分维度决定了每个 worker 能观察到哪些数据，但**换一个维度不保证矛盾消失**。任务若涉及跨分区关联、不同口径、重叠数据或共同原因，仍可能出现结论冲突；应定义共同的指标、时间窗、分母和证据来源，并在冲突时补充数据或交由显式规则裁决。

## 失败三：主管成为新的瓶颈

这个失败最反直觉，因为它出现在**系统明明跑通了**的时候。

主管要接收工人结论、证据和必要的原始上下文。工人数量、回传长度和重试都会影响汇总阶段的输入规模；系统也可能通过分层汇总、外部存储或多轮处理改变这一形态。主管上下文变大是容量、延迟和成本的一个信号，但不单独证明并行、专门化或覆盖收益已经被抵消。

可先记录一个可计算的诊断量：每个 worker 的输入/输出、主管接收的输入、重试与最终答案的 usage，并与同一任务的单 agent 基线比较。若主管汇总输入已接近单 agent 基线，这提示汇总没有减少输入负担；但是否“白拆”仍要看质量、覆盖、延迟、隔离和全流程成本等结果。

第 3 章第 5 节保留了一组历史摘要：8 个子 agent 路线总 token 68,548，对照路线 8,430（摘要比值 8.1）。逐次请求、准确 endpoint、缓存 usage 与质量评分未留存，不能确认差异由重复背景单独造成，也不能把它称为费用或收益比。

## 三种失败背后的同一个结构

在 supervisor-worker 且通过摘要交接的实现中，这几类风险可能同时出现；它们不是所有多智能体拓扑共有的不变量。共享状态、双向消息、引用式证据或分层汇总会改变交接路径，也会带来新的同步和授权问题。

- **信息可见范围**：worker 能看到哪些任务目标、原始资料与其他 worker 的结果？
- **交接保真度**：哪些字段/证据必须返回，哪些可以省略？
- **同步方式**：冲突何时被发现，谁有权补查或裁决？

理解交接契约后，可以针对具体风险调整切分粒度、数据可见范围、结构校验、来源保留和同步策略；它们的成本与收益依实现而变。设计时应对同一任务比较质量、完整用量、延迟、故障恢复和访问边界，而不是假定增加校验一定增加费用或必然消除信息损失。


## 怎么在运行时发现边界失败

这些问题未必会自动变成异常，因此可以为关键路径建立观测与验收。四个可落地的检查点：

**一、对照必需字段与来源。** 为金额、硬约束、版本号等字段分配稳定 ID，检查它们是否在 handoff 与最终结果中保留，并检查来源引用。自由文本的子串命中只能作为候选信号：出现关键词不等于遵守约束，未出现关键词也不必然代表违背约束。

**二、记录各阶段用量与拒绝/重试情况。** 输出很短可能是提前停止、调用失败、成功压缩或无结果；长度异常只能触发调查，需结合 `stop_reason`、usage、失败状态与任务评分解释。

**三、比较主管汇总输入与单 agent 基线。** 同时记录全部 worker 输入/输出、主管输入/输出、缓存和重试，并用相同任务验收质量、覆盖和延迟。单看主管上下文大小不能判定架构是否获益。

**四、显式处理冲突。** 将结论规范化为相同的对象、指标、时间窗口、分母与来源后再比较；无法用数据或预先定义规则解释的冲突，保留双方依据并升级处理。仅靠提示要求报告冲突不是可靠的检测器。

对稳定 ID、字段类型、来源链接和显式状态等契约，可以用代码做确定性校验；这只能证明契约条件满足，不能替代语义评分、来源真实性或业务验收。高风险约束还应由可信代码路径检查，而不是只依赖模型自报。

## 这三种失败和单 agent 的失败怎么区分

最后给一个诊断上的提醒：**多智能体的失败看起来很像单 agent 的失败。**

信息丢了，看起来像「模型没注意到」；结论矛盾，看起来像「模型判断力不行」；主管瓶颈，看起来像「模型上下文不够用」。三种都会被误诊成模型能力问题。

定位时要用相同任务、同一评分标准和可比较的运行记录，逐层检查**第一个出现偏差的位置**：

- 如果原始材料齐全而 worker 回传缺必需字段 → 检查 worker 目标、提示和回传契约
- 如果单个 worker 的证据充分而汇总结论与证据不符 → 检查主管输入、冲突规则和聚合代码
- 如果两条路线都失败 → 检查共同的模型、数据、工具或任务定义，不能把原因预先归到架构边界

一次对照不足以定位根因；保存可追溯的 stage/worker ID、输入来源、停止原因、工具结果与评分结果，并对代表性任务做重复或配对比较。
## 把必需交接字段变成可校验契约

对必须穿过交接的硬约束，先由宿主定义稳定 ID 与权威来源 ID，再检查 worker 和 supervisor 是否都引用了它。下面的本地 helper 检查“条目/来源是否缺失”；它不判断自然语言有没有正确解释约束，所以不能把 ID 命中当作语义验收。

```python
"""检查 handoff 是否保留宿主预先登记的必需事实及来源。"""

REQUIRED_SOURCES = {"no-production-write": "d2"}
WORKER_RESULTS = [
    {"fact_id": "no-production-write", "source_id": "d2", "summary": "仅在预发环境验证"},
    {"fact_id": "pool-limit", "source_id": "d2", "summary": "连接池上限为 20"},
]
FINAL_FACTS = [
    {"fact_id": "no-production-write", "source_id": "d2", "summary": "生产环境不得写入"},
]


def handoff_gaps(records, required_sources):
    """返回缺失或来源不匹配的 required IDs；不做语义/真实性判定。"""
    observed = {}
    for record in records:
        fact_id = record.get("fact_id")
        source_id = record.get("source_id")
        if not isinstance(fact_id, str) or not isinstance(source_id, str):
            raise ValueError("fact_id 与 source_id 必须是字符串")
        observed.setdefault(fact_id, set()).add(source_id)
    return {
        fact_id: {
            "expected_source": expected_source,
            "observed_sources": sorted(observed.get(fact_id, set())),
        }
        for fact_id, expected_source in required_sources.items()
        if observed.get(fact_id, set()) != {expected_source}
    }


assert not handoff_gaps(WORKER_RESULTS, REQUIRED_SOURCES)
assert not handoff_gaps(FINAL_FACTS, REQUIRED_SOURCES)
assert handoff_gaps(
    [{"fact_id": "no-production-write", "source_id": "d1"}], REQUIRED_SOURCES
) == {"no-production-write": {
    "expected_source": "d2", "observed_sources": ["d1"]
}}
print("worker and supervisor handoff IDs/sources: valid")
print("wrong source fixture: rejected")
print("semantic meaning and source truth: not evaluated")
```

这个校验适合挡住缺字段、拼错 ID 或错误来源引用。即使 ID 与 source_id 都匹配，`summary` 仍可能误述原文；高风险约束需进一步与权威材料核验，并由宿主授权逻辑执行。自然语言子串检测、输出长度或模型自报的“已保留”都只能作为排查线索。

### 第二个失败的切分维度对照

用有分子和分母的构造数据，可以区分分区发现与整体趋势（示例：构造数据，未实跑）：

| 期间 | 地区 | 退款数 / 订单数 | 分区退款率 |
|---|---|---:|---:|
| Q1 | 华东 | 120 / 1,000 | 12% |
| Q1 | 华南 | 60 / 1,000 | 6% |
| Q2 | 华东 | 80 / 1,000 | 8% |
| Q2 | 华南 | 110 / 1,000 | 11% |

按地区切分，华东 worker 报告 Q1→Q2 下降，华南 worker 报告上升，两个局部结论都与表中数据一致。整体退款率应按总退款数/总订单数计算：Q1 为 180/2,000 = 9%，Q2 为 190/2,000 = 9.5%，因此整体上升。把任务按期间切分时，每个 worker 也必须拿到该期间所有地区的分子/分母，否则仍然不能重建整体值。**判据不是“按哪个维度切”，而是每个结论的口径能否对齐、聚合是否保留必要的分母与证据。**

## 完整可运行示例：汇总分区数据并检查 handoff

**实跑状态：** 下方数据是构造样例；两个 Python 片段已在本机编译并运行，没有调用模型或 provider。

下面的本地脚本演示两个确定性动作：按分子/分母计算整体指标，并检查宿主预先定义的必需事实 ID 与来源是否经过 worker 和 supervisor。它用构造数据，不调用模型；`refunds` 与 `orders` 必须是非布尔整数，因为 Python 的 `bool` 是 `int` 的子类型，单用 `isinstance(value, int)` 会把 `True` 当作 1 接受。不能验证模型摘要准确率、并行收益或生产权限。

```python
"""用构造的地区数据演示口径对齐和必需事实的交接检查。"""

from collections import defaultdict

ROWS = [
    {"period": "Q1", "region": "华东", "refunds": 120, "orders": 1000},
    {"period": "Q1", "region": "华南", "refunds": 60, "orders": 1000},
    {"period": "Q2", "region": "华东", "refunds": 80, "orders": 1000},
    {"period": "Q2", "region": "华南", "refunds": 110, "orders": 1000},
]
REQUIRED_SOURCES = {"no-production-write": "d2"}
WORKER_HANDOFF = [{"fact_id": "no-production-write", "source_id": "d2"}]
SUPERVISOR_HANDOFF = [{"fact_id": "no-production-write", "source_id": "d2"}]


def aggregate_rate(rows):
    grouped = defaultdict(lambda: {"refunds": 0, "orders": 0})
    for row in rows:
        refunds, orders = row["refunds"], row["orders"]
        invalid_count_type = any(
            isinstance(value, bool) or not isinstance(value, int)
            for value in (refunds, orders)
        )
        if invalid_count_type:
            raise ValueError("refunds and orders must be integers")
        if orders <= 0 or refunds < 0 or refunds > orders:
            raise ValueError("invalid count data")
        grouped[row["period"]]["refunds"] += refunds
        grouped[row["period"]]["orders"] += orders
    return {
        period: counts["refunds"] / counts["orders"]
        for period, counts in grouped.items()
    }


def missing_required_sources(records, required_sources):
    seen = defaultdict(set)
    for record in records:
        seen[record["fact_id"]].add(record["source_id"])
    return {
        fact_id: sorted(seen[fact_id])
        for fact_id, expected_source in required_sources.items()
        if seen[fact_id] != {expected_source}
    }


overall = aggregate_rate(ROWS)
assert overall == {"Q1": 0.09, "Q2": 0.095}
assert not missing_required_sources(WORKER_HANDOFF, REQUIRED_SOURCES)
assert not missing_required_sources(SUPERVISOR_HANDOFF, REQUIRED_SOURCES)
assert missing_required_sources(
    [{"fact_id": "no-production-write", "source_id": "d1"}], REQUIRED_SOURCES
) == {"no-production-write": ["d1"]}

print("区域趋势：华东 12%→8%，华南 6%→11%")
print("整体趋势：Q1 9.0%，Q2 9.5%（按总退款数/总订单数计算）")
print("required handoff：缺失或来源错误会被检测")
print("semantic correctness、模型行为与业务授权：本例未测试")
```

## 常见坑

- **把摘要没提到等同于信息永久丢失。** 先确认原文、工具结果、worker state 和日志是否仍在、是否有权回查。
- **把 prompt 或 JSON Schema 当成语义保证。** 结构有效不等于来源可信、约束被正确解释或最终动作获准；用宿主策略和业务验收兜底。
- **按各 worker 的百分比直接平均。** 率类指标应先核对时间窗与分母，再从总分子/总分母计算；分区权重变化可能反转整体趋势。
- **把局部结论冲突交给主管自由选边。** 先核对指标定义、范围和证据；规则无法裁决时应补数或升级，不要编造共识。
- **只看主管上下文大小。** 把全链路 usage、延迟和同任务结果与单 agent 基线配对比较，避免用代理指标替代收益。
- **把代码检查通过当作语义/模型测试通过。** 本节脚本只验证构造记录的计数和 ID/source 字段，不测试模型是否遵守约束。
