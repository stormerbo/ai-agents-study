第 4 节讲的是**边界**上的失败：信息在边界丢、结论互相矛盾、主管成瓶颈。
这一节讲另一类 —— **协作**上的失败。两套是互补的，不是子集关系。

前三种的共同点是「消息传错了」，后三种的共同点是「**动作**做错了」。

## 失败一：共享资源的并发冲突

这一条不需要模型就能演示，但它在多 agent 系统里特别容易发生，
因为 agent 天然就是「读一个状态、想一会儿、写回去」的模式。

```text
8 个 agent 各做一次「读-改-写」，期望结果 8
实际结果：1  —— 丢失 7 次更新
```

**每个 agent 都「成功了」，没有任何报错。** 这不是模型的问题，
而是「读-改-写」这个动作本身在并发下就不安全：

```text
agent A  读 n=0 .......... 写 n=1
agent B  读 n=0 .......... 写 n=1     <- B 读到的还是 0
agent C  读 n=0 .......... 写 n=1     <- 同上
...
结果 n=1，而实际发生了 8 次「成功」的更新
```

关键在那个「……」的间隙 —— 它代表 agent 的思考时间，
而 agent 的思考时间**比普通程序长几个数量级**（一次模型调用几百毫秒到几秒）。
**间隙越长，冲突窗口越大。** 这解释了一个反直觉的现象：
同样的并发代码，人写起来偶尔出问题，agent 用起来每次都出问题。

这段演示的脚本是自包含的（本次实跑，2026-10-12）：

```python
"""并发读-改-写：8 个 agent 同时改一份共享状态，会丢几次更新？

自包含，不需要模型：这是经典的 lost update（丢失更新）。
实跑状态：2026-10-12。
"""
import threading
import time

state = {"counter": 0}


def worker(lock):
    if lock is not None:
        lock.acquire()
    current = state["counter"]          # 读（必须在临界区内）
    time.sleep(0.02)                    # 模拟「思考」耗时；没有它几乎必然不丢
    state["counter"] = current + 1      # 改-写：用的是读到的旧值
    if lock is not None:
        lock.release()


if __name__ == "__main__":
    for label, use_lock in (("裸读-改-写", False), ("锁罩住「读-改-写」", True)):
        state["counter"] = 0
        lock = threading.Lock() if use_lock else None
        ts = [threading.Thread(target=worker, args=(lock,)) for _ in range(8)]
        for t in ts:
            t.start()
        for t in ts:
            t.join()
        print("%s：期望 8，实际 %d，丢失 %d 次更新" % (label, state["counter"], 8 - state["counter"]))
```

实跑输出（2026-10-12）：

```text
裸读-改-写：期望 8，实际 1，丢失 7 次更新
锁罩住「读-改-写」：期望 8，实际 8，丢失 0 次更新
```

> 这是我第一版脚本的 bug：我一开始把 `lock.acquire()` 写在「读」之后，结果加锁版也是「期望 8、实际 1」。**锁必须罩住整个「读-改-写」，罩住半截等于没罩。** 这个错误和第 2 节那个「用文本相似度衡量结论趋同」是同一类：工具用错了，结论看起来完全合理。

### 为什么这类失败特别难查

因为它有三个性质叠加：

- **静默** —— 没有异常，每个 agent 都报告成功
- **非确定** —— 换个时间跑，丢失的次数可能不同
- **在业务层不可见** —— 你看到的是「最终值不对」，而不是「某次更新失败」

排查时要把两类不确定性分开：共享状态发生 lost update、版本冲突或非原子写入，属于并发问题；在没有共享状态竞争时，模型采样、provider 端点或运行配置仍可能使同一请求产生不同文本。仅凭「同样输入重跑结果不同」不能定位并发。先检查写入前后的状态版本、冲突日志和原子性；再固定模型输出/使用确定性替身重放编排。如果固定输出后仍丢更新，优先查并发；若状态写入正确但模型文本改变，再单独评估模型与端点的非确定性。

## 失败二：同质趋同

多 agent 的一个常见论据是「多个视角能互相补足」。实测下来，这件事**需要更仔细地定义**。

在这组特定样本中，我让 5 个「独立」agent 用**同一个上下文**回答同一个问题（20 人团队引入代码评审 agent 的方案）。下面这个指标叫 **Jaccard 相似度**：指的是两个集合的交集除以并集，取值 0 到 1 —— 这次 0.24 表示两两之间的用词重叠较低，但它不衡量语义观点差异：

```text
两两 Jaccard 相似度：均值 0.24（措辞层面差异很大）
完全相同的输出对：0 / 10

但五个方案的**第一条**分别是：
  1. agent 只产出建议与初筛清单，最终决策权留在人
  2. agent 只做低风险检查，架构与安全决策仍归人
  3. agent 只做只读评论、不设合并门禁
  4. agent 只评审增量 diff，架构与业务语义留给人类
  5. agent 只出评论建议、不阻塞合并，门禁仍由 CI 与人工决定
```

**措辞各异，结论完全一致。**

这就暴露了我第一版的**测量错误**：我用 Jaccard 相似度衡量「同质趋同」，
量出来 0.24（很低），差点得出「没有趋同」的结论。
但那个指标测的是**用词重叠**，而趋同发生在**结论层**。

**「表述多样」和「观点多样」是两件事。** 一个系统可以输出 5 段完全不同的话，
却指着同一个方向 —— 这恰恰是最难发现的一种同质。

这组实验里更有用的观察是：**把每个 agent 的结论压成一句话，再比较这些结论。** 五条结论在这次样本中都倾向于「agent 只建议、最终决策留给人」。这提示我们应分别评估措辞多样性和观点多样性；五个样本不足以证明所有同模型同上下文的 agent 都会同质趋同。

那怎么才能真的获得多样性？两条实际有效的路：

**一、给不同的上下文。** 让每个 agent 看不同的资料切片，
而不是五个都看同一份。**差异必须来自输入，不能指望来自模型。**

**二、给不同的目标或约束。** 比如一个 agent 专门找「这个方案在什么情况下会失败」，
另一个专门找「成本上不划算的地方」。角色不同，产出才会不同。

**同一个模型 + 同一个上下文 + 同一个问题，可能产生相似结论的不同说法；这组五次运行正是一个样本。**
这是多 agent 设计里最需要先接受的事实。

## 失败三：错误的级联放大

第三个失败模式是前两个的下游：**一个 agent 的错误被下一个当作前提。**

```text
A 读到一个过期的数据 -> 得出「退款率 12%」
B 基于 12% 计算风控阈值
C 基于 B 的阈值调整提示词
D 基于 C 的结果写进运行手册

最终：没人知道 12% 这个数是错的，因为它已经变成了「背景知识」
```

这种失败的特点是**越往后越难发现**：第一个环节的错误是有据可查的（数据过期），
但到了第四个环节，它已经成了一个没有出处的前提。
这和第 7 章讲的「误召回静默改写」是同一个机制 ——
**错误一旦被写进上下文，它就有了和事实一样的外观。**

缓解办法是**让每个环节标注它的输入来自哪里**，
并在最终产物上回溯源头。产物上的字段至少要有两个（示例：构造数据，未实跑）：

```json
{
  "value": "退款率 12%",
  "source": "D1:2026-09-30 的导出报表",
  "derived_from": ["退款率 12%"],
  "as_of": "2026-09-30"
}
```

`source` 指向这条结论直接读到的原始位置，`derived_from` 列出它依赖的上游结论（这里是 B 从 A 的「12%」算出的阈值）。**回溯时顺着 `derived_from` 往回走，才能定位到第一处错误** —— 只看 `source` 只能看到「引用了谁」，看不到「谁引用了错的东西」。这和第 5 章讲追踪的理由是一样的：
**不是为了记录发生了什么，而是为了在出错时能定位第一处。**

## 另外三种：扯皮、失控、理解债

书里列的六种失败模式里，还有三种值得点一下，它们不需要实测就能说清，
但每一条都有明确的工程信号。

**互相扯皮。** 两个 agent 意见不合，各自改对方的产出，来回几轮没有进展。
信号很明确：**同一对 agent 之间的消息数持续增长，而任务状态没有变化。**
这和单 agent 的「循环失控」是同一种病，只是发生在两个体之间。
缓解办法是设一个仲裁者（第三个 agent 或人），或者约定「同一争议最多两轮，之后升级」。
第 11 章那套循环检测（同一动作重复、状态无变化）在这里同样适用，
只是要把「状态」定义成两个 agent 的共识而非单个 agent 的进度。

**循环失控。** A 让 B 做一件事，B 做完发现还需要 A 确认，A 确认完又要求 B 补充，
如此往复。它和扯皮的区别是「**每一步看起来都在推进**」，
所以更难发现。判据是看**总步数**：如果一个任务的步数远超预期，
先去看它是不是在两个 agent 之间来回传。

**理解债与认知投降。** 这条最隐蔽，也最值得警惕：
当一个 agent 的产出被下游 agent 反复当作用户输入接受时，
**没有人再回到原始需求去核对**。系统「运转正常」，但所有环节都在转述一个早期理解，
而那个理解可能从一开始就偏了。

「认知投降」这个说法的价值在于它点出了责任问题：
多 agent 系统容易产生一种错觉 —— **每个环节都「验证过了」，所以整体是对的**。
但每层验证的都是「上游说得通吗」，而不是「原始需求是什么」。

缓解办法很朴素：**在链路末端放一个「回到原始需求」的检查。**
不是检查中间过程，而是拿最终产物和最初的需求描述对比。
这一步人做最可靠，也最适合放进审批点（第 19 章）。

## 怎么防

| 失败 | 判据 | 缓解 |
| --- | --- | --- |
| **并发冲突** | 状态版本冲突、写入覆盖或固定输出重放仍丢更新 | 锁 / 单写者 / 乐观并发（版本号） |
| **同质趋同** | 把结论压成一句话后五份相同 | 给不同上下文或不同角色 |
| **级联放大** | 找不到某个前提的出处 | 每个产物标注输入来源 |

三条里，**并发冲突最值得先处理** —— 它是唯一一个「工程上成熟、有标准解法」的，
而且它的失败是静默的。后两条更多是设计层面的判断。

## 小结

- **协作层的三种失败与边界层的三种互补**：前者是「动作做错了」，后者是「消息传错了」
- **8 个 agent 并发读-改-写，期望 8 实际 1** —— 丢失 7 次且没有任何报错
- **agent 的思考间隙是普通程序的几百倍**，所以同样的并发代码在 agent 场景下更容易崩
- **区分并发与模型非确定性**：查状态版本、冲突日志，并用固定模型输出重放编排
- **同质趋同要按结论比，不能只按文本比** —— 本次 5 个输出的措辞相似度为 0.24，结论趋向同一方案
- **差异必须来自输入或角色，不能指望来自模型**
- **扯皮的信号是「消息数涨而状态不变」，失控的信号是「总步数远超预期」，理解债的信号是「找不到原始需求」**

最后一句：这三种协作失败有一个共同点 —— **它们都不会报错。**
并发丢更新、结论趋同、错误级联，在日志里看起来都是「一切正常」。
所以多 agent 系统比单 agent 更需要**主动的、针对性的探针**，
而不能等着「出问题再说」—— 等到用户报告问题时，往往已经积累了几十次丢失的更新。
