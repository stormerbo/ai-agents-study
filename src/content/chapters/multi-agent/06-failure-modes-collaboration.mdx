## 失败一：共享资源的并发冲突

这一条不需要模型就能演示。风险出现在多个执行单元并发读写同一状态、而更新没有原子性或冲突检测时；agent 只是可能发起这些操作的调用方，不会天然导致数据竞争。

```text
8 个线程在屏障后同时写回各自读到的旧值，期望结果 8
构造结果：1 —— 这个受控交错中丢失 7 次更新
```

在这个内存示例中，线程操作都正常返回，但共享状态只增加 1。它说明没有冲突保护的「读-改-写」可能丢更新；不代表所有 agent 并发都会发生相同结果：

```text
线程 A  读 n=0 | 等待屏障 | 写 n=1
线程 B  读 n=0 | 等待屏障 | 写 n=1
线程 C  读 n=0 | 等待屏障 | 写 n=1
...
8 个线程都先读到 0，之后各写入 1，最终 n=1
```

屏障刻意让所有线程先读再写，因此这是为了稳定重现 lost update 的受控交错，不是模型耗时实验。若真实系统在模型调用期间一直持有数据库事务或锁，确实可能延长资源占用；应避免把慢速模型调用放在需要保护的事务临界区内。是否出现冲突取决于共享资源、调度、事务隔离和更新方式，不能从「用了 agent」直接推断。

这段自包含脚本用 `threading.Barrier` 强制所有线程读取同一旧值；它演示单进程内存竞争，不模拟模型、数据库事务或分布式锁。实跑状态：2026-10-21，本机 Python 标准库。

```python
"""并发读-改-写：8 个线程同时改一份共享状态，会丢几次更新？

自包含，不需要模型：这是经典的 lost update（丢失更新）。
屏障强制所有线程先读后写，结果可重复；不模拟 agent 或数据库。
"""
import threading
state = {"counter": 0}
WORKERS = 8


def worker(lock, barrier):
    if lock is None:
        current = state["counter"]
        barrier.wait()                  # 确保所有 worker 都读完再写
        state["counter"] = current + 1
    else:
        with lock:                      # 整个读-改-写都在临界区内
            current = state["counter"]
            state["counter"] = current + 1


if __name__ == "__main__":
    for label, use_lock in (("无保护的读-改-写", False), ("锁罩住「读-改-写」", True)):
        state["counter"] = 0
        lock = threading.Lock() if use_lock else None
        barrier = None if use_lock else threading.Barrier(WORKERS)
        ts = [
            threading.Thread(target=worker, args=(lock, barrier))
            for _ in range(WORKERS)
        ]
        for t in ts:
            t.start()
        for t in ts:
            t.join()
        expected = WORKERS if use_lock else 1
        assert state["counter"] == expected
        lost = WORKERS - state["counter"]
        print(
            "%s：期望 8，实际 %d，丢失 %d 次更新"
            % (label, state["counter"], lost)
        )
```

实跑输出（2026-10-21，本机线程 fixture）：

```text
无保护的读-改-写：期望 8，实际 1，丢失 7 次更新
锁罩住「读-改-写」：期望 8，实际 8，丢失 0 次更新
```

> 这是受控的内存示例，不足以证明生产系统已安全。进程内 mutex 不能保护其他进程或服务；数据库应使用适合该操作的原子更新、唯一约束、乐观并发控制或事务锁，并按所选数据库与隔离级别处理冲突、重试和死锁。

### 为什么这类失败特别难查

这类故障可能有几个观测特征，但不一定都同时出现：

- **可能静默** —— 写入请求返回成功，但业务不变量或最终计数不对；也可能由数据库冲突/序列化异常显式报告
- **结果受交错影响** —— 不同调度可能导致丢失量不同，受控屏障样例则固定为 7 次
- **根因需要跨层对照** —— 检查读写版本、事务日志、冲突/重试记录和最终业务状态

排查时要把两类不确定性分开：共享状态发生 lost update、版本冲突或非原子写入，属于并发问题；在没有共享状态竞争时，模型采样、provider 端点或运行配置仍可能使同一请求产生不同文本。仅凭「同样输入重跑结果不同」不能定位并发。先检查写入前后的状态版本、冲突日志和原子性；再固定模型输出/使用确定性替身重放编排。如果固定输出后仍丢更新，优先查并发；若状态写入正确但模型文本改变，再单独评估模型与端点的非确定性。

## 失败二：同质趋同

多 agent 有时被用于收集多个候选观点，但「多份输出」不等于「独立证据」或「观点覆盖更广」。应先说明要增加的是事实覆盖、方案多样性还是错误发现率，再选能测这个目标的判据。

2026-10-12 的历史记录报告：5 个 agent 用相同上下文回答代码评审方案时，词面 Jaccard 均值为 0.24，并称人工归纳后的结论相近。原始请求、五份完整响应、分词细节、结论标签和评分过程未归档，因此这些数字与归纳不能独立复算；它们不是模型同质性的普遍证据。下列句子是**构造例子，不是该次模型原文**：

Jaccard 相似度对两个 token 集合 A、B 定义为 `|A ∩ B| / |A ∪ B|`；结果受分词、大小写、停用词和 token 集合定义影响。即使词面 Jaccard 低，也不能据此推出观点不同。

```text
输出 A：review agent 只提建议，合并由人决定。
输出 B：自动检查标记风险；只有维护者可以合并。
```

两句词面重叠不高，但在本文预先定义的判据「谁拥有最终合并决策权」上答案相同。这个小构造只说明词面相似度与目标观点不是同一测量对象，不证明真实 agent 一定趋同。Tevet 与 Berant 的 NLG 多样性评估研究指出，在其研究设置中，人类对内容多样性的判断优于自动指标；该结论限于论文研究的任务和指标，不提供本例历史数字的复核。

评估观点多样性时，先定义观点轴或原子主张，抽取每个输出的立场，再由盲审人工 rubric 或经过任务校准的评估器检查覆盖和有效性。词面 Jaccard 仍可作为文本差异的一个诊断量，但不能替代语义判定；单个 judge 也可能漏掉观点或产生偏差。

怎么提高获得互补观点的机会？以下是**可测试的设计手段，不是保证**：

**一、给不同的上下文或证据范围。** 让任务明确分工并记录每份输出读过的资料；如果不同切片漏掉共同关键证据，差异也可能来自信息不完整。

**二、给不同的目标或反方约束。** 比如一个 agent 专门找失效条件，另一个检查成本与反例；角色提示只是改变任务输入，不保证模型能力专门化或结论互补。

同一模型、相近上下文和相同问题可能输出相近观点，也可能因采样、模型版本或措辞产生差异。要判断分工是否增加了有用覆盖，需在同一任务集上与单 agent/不同分工方案配对比较，并按预定义 rubric 评分。

## 失败三：错误的级联放大

一种需要检查的风险是：**上游未经验证的主张被下游当成已验证事实继续使用。** 这是可能发生的数据依赖链，不代表所有多 agent 流程都会放大错误。

```text
来源 S1：报表给出退款率 12%（构造示例；已超出业务设定的新鲜度窗口）
主张 C1：把报表值记录为当前退款率
规则 R1：依据 C1 生成风险阈值
动作 A1：将 R1 写入运行策略

风险：下游保留结论，却没有保留可检查的来源与派生关系
```

一种可操作的做法是给来源、提取出的主张和后续派生结果分配稳定 ID，记录数据时间窗口、转换规则版本和 `derived_from` 边。回溯依赖图有助于定位哪些下游结果依赖了可疑主张，但它**不能单独判断原始来源可信、仍然新鲜、解释正确或动作已获授权**。新鲜度必须按业务的数据更新节奏设定；不同字段可能需要不同期限。

执行 trace 和内容 lineage 解决的是相关但不同的问题：trace 可关联模型调用、工具执行、状态与错误，帮助还原「发生了哪些步骤」；它本身不证明某项内容来自可信来源或语义正确。OpenTelemetry 的 GenAI spans 规范目前标注为 development，并提醒 prompt、输入、输出和工具字段可能含敏感信息；内容采集应遵循明确的 opt-in、脱敏与保留策略。

下面的本地示例只检查依赖图的 ID 唯一、引用存在和无环；它不检查来源内容或业务新鲜度。

```python
"""校验构造的来源/派生图结构；不验证事实真假。"""

from collections import defaultdict

RECORDS = [
    {
        "id": "source-report-1",
        "kind": "source",
        "source_ref": "report://refunds/2026-09-30",
        "as_of": "2026-09-30",
    },
    {
        "id": "claim-rate-1",
        "kind": "derived",
        "derived_from": ["source-report-1"],
        "rule_version": "extract-v1",
    },
    {
        "id": "risk-rule-1",
        "kind": "derived",
        "derived_from": ["claim-rate-1"],
        "rule_version": "risk-policy-v3",
    },
]


def lineage_errors(records):
    by_id = {}
    errors = []
    for record in records:
        record_id = record.get("id")
        if not isinstance(record_id, str) or not record_id:
            errors.append("missing record id")
        elif record_id in by_id:
            errors.append(f"duplicate id: {record_id}")
        else:
            by_id[record_id] = record

    parents = defaultdict(list)
    for record_id, record in by_id.items():
        if record.get("kind") == "source":
            if not record.get("source_ref"):
                errors.append(f"source has no source_ref: {record_id}")
            if record.get("derived_from"):
                errors.append(f"source has parents: {record_id}")
            continue
        if record.get("kind") != "derived":
            errors.append(f"unknown kind: {record_id}")
            continue
        refs = record.get("derived_from")
        if not isinstance(refs, list) or not refs:
            errors.append(f"derived record has no parents: {record_id}")
            continue
        for parent_id in refs:
            if not isinstance(parent_id, str) or not parent_id:
                errors.append(f"invalid parent id: {record_id}")
                continue
            if parent_id not in by_id:
                errors.append(f"missing parent: {record_id} -> {parent_id}")
            else:
                parents[record_id].append(parent_id)

    visiting, visited = set(), set()

    def visit(record_id):
        if record_id in visiting:
            errors.append(f"cycle at: {record_id}")
            return
        if record_id in visited:
            return
        visiting.add(record_id)
        for parent_id in parents[record_id]:
            visit(parent_id)
        visiting.remove(record_id)
        visited.add(record_id)

    for record_id in by_id:
        visit(record_id)
    return errors


assert lineage_errors(RECORDS) == []
BROKEN = [
    (
        {**record, "derived_from": ["missing-claim"]}
        if record["id"] == "risk-rule-1"
        else record
    )
    for record in RECORDS
]
assert "missing parent: risk-rule-1 -> missing-claim" in lineage_errors(BROKEN)
assert "duplicate id: source-report-1" in lineage_errors(RECORDS + [RECORDS[0]])
CYCLE = [
    (
        {**record, "derived_from": ["risk-rule-1"]}
        if record["id"] == "claim-rate-1"
        else record
    )
    for record in RECORDS
]
assert any(error.startswith("cycle at:") for error in lineage_errors(CYCLE))
print("valid source and derivation graph: accepted")
print("missing parent fixture: detected")
print("duplicate ID and cycle fixtures: detected")
print("source truth, freshness, semantic correctness and authorization: not evaluated")
```

## 其他可观测的风险线索

下面是补充排查线索，不是已经实测确认的另外三类普遍故障，也没有通用阈值：

**互相扯皮。** 两个 agent 意见不合，各自改对方的产出，来回几轮没有进展。
可监测同一任务/参与者对之间的回合数、重复提案、状态版本是否改变，以及预算/期限消耗。连续对话不等于无进展；先按任务定义什么是有意义的状态变化，再设适合风险和成本的升级策略，不套用固定两轮阈值。必要时由规则、负责人或人工裁决。

**循环失控。** A 让 B 做一件事，B 做完发现还需要 A 确认，A 确认后又要求 B 补充，如此往复。它可能看起来每一步都在推进。检查是否出现环形 handoff、重复动作、没有新增证据的重试，以及是否接近预先设定的步数、时间或费用预算。预算会限制损害范围，但不能证明循环的根因。

**需求漂移。** 下游可能复用上游摘要，却没有重新核对用户目标、约束和证据。可在关键阶段把最终结果对照原始任务 ID、验收条件和来源图检查；人工审核适用于高风险或难以自动验证的部分，但不能假定人工判断必然可靠。

## 怎么防

| 失败 | 判据 | 缓解 |
| --- | --- | --- |
| **并发冲突** | 状态版本冲突、写入覆盖、约束违反或事务重试增加 | 对共享状态使用适配的原子更新/约束/CAS/事务；按实际存储测试 |
| **观点覆盖不足** | 预定义立场/主张类别未覆盖，或输出虽多但新增证据很少 | 明确目标观点轴、任务集和 rubric；与单 agent/不同分工配对比较 |
| **依赖链失真** | 派生结果缺来源、版本或前置主张 | 保存稳定来源 ID、派生边和规则版本；校验引用并回到权威来源复核 |

优先顺序由共享写入风险、任务影响和可观测性决定。并发问题有成熟的数据库/同步原语，但需要按存储、隔离级别和副作用边界验证；观点覆盖与依赖链也需要任务评分和来源复核，不能靠一个通用的「多 agent 成功」指标。

## 小结

- **并发读-改-写可能丢更新**；屏障示例强制 8 个线程先读后写，稳定展示 8 次写入只留下 1
- **这是共享状态的并发问题，不是 agent 专属性质**；数据库原子更新、约束、锁和重试行为要按具体存储验证
- **区分并发与模型非确定性**：查状态版本、冲突日志，并用固定模型输出重放编排
- **词面差异不等于观点覆盖**；定义观点轴，以任务 rubric、人工复核或校准评估器比较
- **不同上下文/目标是可测试的多样性手段，不保证互补结论**
- **来源/派生图帮助定位依赖关系，但不证明来源真实、新鲜或解释正确**
- 监测回合数、状态版本、预算和重复动作；阈值按任务设定，不凭任意固定轮数诊断根因

这些问题可能静默发生，也可能伴随冲突异常、拒绝、超时或预算耗尽。日志无报错不证明业务正确；日志有异常也不自动指出根因。把运行轨迹、版本化状态、来源引用、业务不变量和任务评分放在一起，才有机会定位偏差。
