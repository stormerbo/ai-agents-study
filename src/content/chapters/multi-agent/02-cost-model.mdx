多智能体的成本可以用一个很短的式子估出来。它不精确，但足以让你在动手之前判断这件事值不值。

## 式子

**输入 token 量的粗略估算 = 每份输入的规模 × 它被装载的次数。** 总 token volume 还要加上每次调用的输出；账单则要按各类 token 价格计价。

「装载次数」指的是**同一份内容被送进模型的次数**。这个词是关键 —— 因为多智能体常见的成本来源之一是「同一份内容被装了很多遍」；完整成本还需统计所有阶段的输入、输出与各自计价。

举个具体例子。假设：

- 共享背景 B（团队规范、代码库约定、历史模板）
- 每个工人的私有材料 M
- N 个工人 + 1 个主管

那么：

- **单 agent**：输入约为 B + ΣMᵢ，输出为 Oₛ(single)
- **主管 + N 工人**：输入约为 (N+1)×B + ΣMᵢ + Iₛ（主管汇总工人结果所需的输入），输出为 ΣOᵢ + Oₛ

这里 Iₛ 表示主管实际收到的工人结果及其他汇总输入，Oᵢ 是第 i 个工人的输出。

在同一模型、把输入与输出 token 暂时按相同权重计数时，token-volume 倍数近似为：

```text
倍数 ≈ ((N+1)×B + ΣMᵢ + Iₛ + ΣOᵢ + Oₛ) / (B + ΣMᵢ + Oₛ_single)
```

这个式子给出两个需要用实际调用验证的方向性预期：

**第一，B 越大，重复输入量可能越高。** 只有当请求确实重复包含这份背景时，才会增加对应输入用量；缓存、请求结构和提供商的 usage 口径会影响实际读数与账单。
**第二，活跃工人越多，通常需要统计的调用与输出项越多。** 实际增量取决于调度是否真的调用这些工人、各自请求装入了什么，以及输出是否被重试或截断；不能只凭 N 推出固定倍数。

若 B 相对私有材料很小，重复 B 带来的输入增量可能不显著；但多出来的请求、worker 输出和 supervisor 汇总仍须计入，token-volume 或账单倍数不保证趋近 1。

## 实测：两次不同背景规模下的倍数

我做了这个对照。同一个任务（根据三份材料写技术复盘），同一个模型，只改变共享背景的规模：

| 共享背景 | 单 agent | 主管 + 3 工人 | 倍数 |
|---|---:|---:|---:|
| 小（57 字） | 4,270 | 8,161 | **1.91×** |
| 大（3,489 字） | 9,734 | 19,380 | **1.99×** |

（历史汇总，2026-10-09，登记模型名 `deepseek-flash`。逐次请求/响应、准确端点与模型快照、评分记录和账单未留存，当前无法独立复算；不得视为当前模型的可复现基线。）

**这份历史记录列出的两个倍数是 1.91× 与 1.99×。** 由于没有逐次 usage 轨迹，这些总量既不能证明背景规模对倍数影响很小，也不能解释为什么数值接近；要检验该假设，须逐请求记录输入、输出、重试、停止原因及缓存字段，并说明对照的完整边界。

## 汇总所有调用的输出

还要把所有阶段的输出都计入：

- N 个工人分别生成 Oᵢ，合计为 ΣOᵢ
- 主管再生成 Oₛ；单 agent 则只生成 Oₛ_single

所以更准确的形状是：

```text
token-volume 倍数 = (总输入_multi + ΣOᵢ + Oₛ) / (总输入_single + Oₛ_single)
```

工人输出不能忽略或当作「不乘份数」：输出应累加每个工人及主管的 `output_tokens`。倍数是否接近 N+1，取决于总输入、各工人私有输入、主管汇总输入和全部输出的相对占比；还取决于请求结构，不能只看共享背景 B。

第 3 章另一个实验报告 **8.1 倍**。那是不同任务与对照组的观测，不能只根据本节的公式归因；跨实验比较前应核对统计口径、全部调用的输入/输出和缓存字段。

## 这个模型怎么用

它给出的实际判断是：

**如果共享内容在多个请求中重复、且缓存折扣不足以抵消，输入 token 量会显著增加；如果工人输出或主管汇总输入很大，总 token 量也会增加。** 只有结合所有请求的 usage 才能判断实际量级。

所以设计时应该争取的形状是：**每个工人只装它真正需要的那一小份，而共享的背景尽量少、尽量小。** 具体做法：

- 把共享背景里「其实只有一部分工人需要」的内容拆出去
- 需要全局背景时，可以评估是否生成一份较短的共享摘要再分发。摘要长度、生成模型、是否值得增加一次调用，都没有通用阈值；先用目标任务的代表性样本检查关键信息保留、遗漏风险和端到端总用量，再决定是否替换原背景。
- 工人生成的产出尽量短（结构化字段而不是长文）

三条都旨在减少重复上下文或无用输出；**让 B 变小只是其中一项**，还要控制 worker 输出和 supervisor 汇总输入。

## 一个反直觉的推论

成本模型还解释了一件事：**为什么「工人越多越便宜」并不必然成立。**

一个常见的想法是「拆得越细，每个上下文越小，所以越省」。前半句对，后半句错 —— 因为**拆细的代价是共享内容被装更多遍**。

若暂时只看输入，并假设每个工人私有输入相同为 M，忽略主管汇总输入、所有输出和缓存计价，那么：

```text
输入倍数 ≈ ((N+1)×B + N×M) / (B + N×M)
```

N 增大时分子线性增长，分母里 N×M 也在增长。谁占主导，取决于 B 和 M 的比例。

**结论是：拆分的收益来自「每个工人的私有材料变小」，成本来自「共享背景被装载更多次」。** 所以拆分的正确方向是让每份私有材料**真的不同**，而不是把同一份内容切成很多份 —— 后者只会让 B 的负担变重，M 却没减少。

用一个具体的数字感受一下这个差别：同样是 3 个工人，如果每人装 1/3 的原始材料（M 各 100 字），总输入是 B×4 + 300；如果每人装**全部**材料（M 各 300 字），总输入是 B×4 + 900。前者省下的正是「每个工人不用看别人的那 2/3」。


## 一个更实用的估算办法

上面的简化输入模型只用于形成假设；真实的总 token 和费用来自每次响应的 usage。

**跑单 agent 与多 agent 两种方案，收集每一次请求的 usage。** 先按一致口径汇总总 token volume；再用该模型/提供商当前的各类价格逐次加权，分别得到费用倍数。

然后把多 agent 与单 agent 放进同一套任务和验收标准中，比较端到端质量、完整输入/输出账单、延迟分布、失败与重试成本。只有在任务实际并发、子任务可独立推进且调度器能重叠其执行时，延迟才可能低于串行执行；并发执行也不保证总延迟等于各阶段耗时的最大值。是否值得由业务门槛决定，不存在通用的 2× 或 N× 成本分界线。

这个办法的好处是**它测的是你的真实场景**，而不是套用一个别人的结论。第 3 章那 8.1 倍看起来很吓人，但它是「8 个子 agent 各自装一遍共享背景、输出又很短」这个特定形状下的结果；换成别的形状，数字会完全不同。

最后提醒一句：**不要用一次运行的数字下结论。** 本节留存的成本表只列出 1.91× 和 1.99×；旧正文另有 2.37× 的说法，但没有对应的原始记录或登记数据支持，已撤下。当前无法估计运行间波动，也不能据此声称倍数稳定。

## 和缓存的关系

最后补一个实际会影响账单的细节：有些端点支持缓存输入前缀。

缓存只改变特定端点的计量或定价，不会自动消除多次请求、输出和协调成本。以 Anthropic Messages API 为例，`input_tokens`、`cache_read_input_tokens` 与 `cache_creation_input_tokens` 共同表示输入处理量，且读/写缓存采用各自计价；不能把这个字段约定直接套到兼容端点。DeepSeek 的 Anthropic 格式兼容文档当前把 `cache_control` 标为忽略，因此使用兼容 API 时必须检查该提供商自己的文档与返回 usage。本节历史成本摘要没有缓存读写拆分或账单证据，不能归因于缓存。

若目标端点支持 prompt caching，可将稳定前缀放在适当位置，并通过 usage 验证命中；不要把缓存行为或折扣当作所有模型、厂商都相同的保证。
## 把 usage 拆开，自己复算一遍

公式里的「输入」和「输出」不是估的，它们可从每次响应的 `usage` 中采集；先按目标 endpoint 文档归一化，再分别统计新输入、缓存读取、缓存写入与输出：

```python
import math


USAGE_KEYS = {
    "input": "input_tokens",
    "cache_read": "cache_read_input_tokens",
    "cache_write": "cache_creation_input_tokens",
    "output": "output_tokens",
}


def normalize_usage(raw_usage):
    """把已由 endpoint adapter 校验过的互斥 usage 字段转成统一结构。"""
    normalized = {}
    for category, field in USAGE_KEYS.items():
        value = raw_usage.get(field)
        if type(value) is not int or value < 0:
            raise ValueError(f"usage.{field} 缺失或不是非负整数")
        normalized[category] = value
    return normalized


def token_volume(calls):
    """累加一条方案的所有调用；传入项必须先经 provider-specific adapter 归一化。"""
    return {
        category: sum(call[category] for call in calls)
        for category in USAGE_KEYS
    }


def weighted_cost(calls, rates_per_million):
    """按明确的 endpoint/model 单价，对互斥 usage 字段逐项计价。"""
    if set(rates_per_million) != set(USAGE_KEYS):
        raise ValueError("rates 必须包含 input/cache_read/cache_write/output 四类")
    total = 0.0
    for category, rate in rates_per_million.items():
        if (isinstance(rate, bool) or not isinstance(rate, (int, float))
                or not math.isfinite(rate) or rate < 0):
            raise ValueError(f"{category} 单价必须是非负数")
    for call in calls:
        for category in USAGE_KEYS:
            total += call[category] * rates_per_million[category]
    return total / 1_000_000


sample = normalize_usage({
    "input_tokens": 320,
    "cache_read_input_tokens": 256,
    "cache_creation_input_tokens": 0,
    "output_tokens": 81,
})
assert token_volume([sample]) == {
    "input": 320, "cache_read": 256, "cache_write": 0, "output": 81
}
```

用第 11 章第 1 节那次真跑的两个响应代入（本次实跑，2026-10-12）：新输入 320 + 175 = 495，缓存读取 256，输出 81 + 27 = 108。它们代表两次调用的观测字段，说明应分别累加 usage 类别；不能把其中一类乘上一个想象的「份数」代替统计所有请求。下面的代码假设端点适配器已将 input、cache-read 和 cache-write 归一化成互斥类别。

这些 usage 数字不是本节多智能体成本实验的组成部分，也不足以推出一个统一倍数。复算时应分别收集单 agent 与多 agent 方案的全部请求，先比较 token volume，再按当前价目表和缓存 usage 分项估算账单。

## 完整示例代码

下面的脚本提供单 agent 与 supervisor/worker 的 usage 采集起点，打印每种方案的请求数、输入/输出 token 和本次 token-volume 比值。它**不是**上面历史表的来源；只有在配置好目标 endpoint 的凭据、核对响应语义后实际运行，才能得到新的工作负载样本。

```python
"""Usage 采集骨架。

实跑状态：本轮未调用 provider；旧实验缺少逐次响应，无法复现正文历史表。
本例按顺序调用，不测并行延迟或回答质量；请求不启用 prompt caching。
"""
import json
import os
import urllib.request

BASE_URL = os.environ["ANTHROPIC_BASE_URL"].rstrip("/")
API_KEY = os.environ["ANTHROPIC_AUTH_TOKEN"]
MODEL = os.environ["VERIFY_MODEL"]
BG_SMALL = "团队规范：用简体中文；不编造材料外数字；结论注明来源。"
BG_LARGE = BG_SMALL + "\n" + "\n".join(
    f"约定 {i}：日志带 trace_id；接口设超时；数据库变更走迁移。"
    for i in range(1, 41)
)
DOCS = {
    "D1": "订单服务本周 P99 延迟 820ms，上周 610ms；新增推荐调用占用 34% 时间。",
    "D2": "数据库连接池上限 20；扩容先在预发验证，禁止直接改生产库。",
    "D3": "推荐服务内存从 1.2GB 增至 2.8GB，主要来自无上限缓存。",
}
TASK = "根据材料写技术复盘，指出优先处理的问题并说明依据。"
observed_calls = []  # 每个方案独立清空；即使响应不合格，也先保留本次已返回的 usage。


def nonnegative_int(usage, field):
    value = usage.get(field)
    if type(value) is not int or value < 0:
        raise RuntimeError(f"缺失或无效的 usage.{field}，停止汇总")
    return value


def call(messages, system):
    payload = json.dumps({"model": MODEL, "max_tokens": 4000,
                          "system": system, "messages": messages}).encode()
    request = urllib.request.Request(
        BASE_URL + "/v1/messages", data=payload,
        headers={"content-type": "application/json", "x-api-key": API_KEY,
                 "anthropic-version": "2023-06-01"})
    with urllib.request.urlopen(request, timeout=180) as response:
        body = json.loads(response.read())
    if not isinstance(body, dict):
        raise RuntimeError("响应不是 JSON 对象，usage 未知，停止汇总")
    usage = body.get("usage")
    if not isinstance(usage, dict):
        raise RuntimeError("响应缺少 usage 对象，usage 未知，停止汇总")
    measured = {key: nonnegative_int(usage, key)
                for key in ("input_tokens", "output_tokens")}
    observed_calls.append(measured)
    if body.get("stop_reason") != "end_turn":
        reason = body.get("stop_reason")
        raise RuntimeError(
            f"响应未正常结束；usage 已保留：stop_reason={reason!r}"
        )
    text = "".join(block["text"] for block in body.get("content", [])
                   if isinstance(block, dict) and block.get("type") == "text"
                   and isinstance(block.get("text"), str))
    if not text.strip():
        raise RuntimeError("end_turn 响应没有文本块；需人工检查，不能当作有效答案")
    return text, measured


def run_single(background):
    material = "\n\n".join(f"{key}：{value}" for key, value in DOCS.items())
    text, usage = call(
        [{"role": "user", "content": f"{background}\n\n{material}\n\n{TASK}"}],
        "你是严谨的技术分析助手。")
    return text, [usage]


def run_multi(background):
    calls, partials = [], []
    for key, value in DOCS.items():
        text, usage = call(
            [{"role": "user", "content":
             f"{background}\n\n材料 {key}：{value}\n\n提炼事实、来源和不确定项。"}],
            "你是资料提炼助手，只返回事实、来源与不确定项。")
        calls.append(usage)
        partials.append(f"{key} 工人结果：{text.strip()}")
    merged, usage = call(
        [{"role": "user", "content":
         f"{background}\n\n{TASK}\n\n工人结果：\n" + "\n".join(partials)}],
        "你是严谨的技术分析助手；区分材料事实与推断。")
    calls.append(usage)
    return merged, calls


def totals(calls):
    return {"calls": len(calls),
            "input_tokens": sum(item["input_tokens"] for item in calls),
            "output_tokens": sum(item["output_tokens"] for item in calls)}


if __name__ == "__main__":
    for label, background in (("small", BG_SMALL), ("large", BG_LARGE)):
        observed_calls.clear()
        try:
            _, single_calls = run_single(background)
            _, multi_calls = run_multi(background)
        except RuntimeError as error:
            # Preserve usage already returned before any later failure.
            print(
                f"{label}: incomplete; usage captured so far="
                f"{totals(observed_calls)}; {error}"
            )
            raise
        single, multi = totals(single_calls), totals(multi_calls)
        single_volume = single["input_tokens"] + single["output_tokens"]
        multi_volume = multi["input_tokens"] + multi["output_tokens"]
        print(f"{label} single={single} multi={multi}")
        print(f"{label} observed token-volume ratio="
              f"{multi_volume / single_volume:.2f}x")
```

本例只统计未启用缓存的请求所返回的输入与输出字段。换用带缓存的 endpoint 时，先按该 endpoint 的文档扩展 usage adapter，并分开记录 cache read/write；不能把“缺字段”默认为零。代码先校验并保留每个可解析响应的 input/output usage，再检查 `stop_reason` 与文本；因此 `max_tokens`、tool-use 等未完成响应以及空文本即使不能作为答案，也不会丢掉该响应已返回的 usage。Anthropic [Messages API 响应参考](https://platform.claude.com/docs/en/api/messages/create)明确指出空字符串响应仍可能有非零 `output_tokens`，所以不能先拒绝内容再丢弃计量（核对于 2026-10-22）。缺失或非法 usage 时用量未知，不能填 0；示例只把已收到的计数保存在进程内，并在失败时输出截至当时的部分累计值，生产系统还应逐调用持久化并将未知用量与已知费用分开对账。即使代码跑通，单次串行运行也只得到该次请求的用量样本，不代表质量、延迟或可推广的倍率。

## 常见坑

- **只数「每个上下文多大」，不数「同一份内容装了几遍」。** 重复装载是一个可能的重要成本来源，但还要统计各阶段的新输入、缓存输入、输出、重试与协调开销。
- **以为拆得越细越省。** 私有材料变小是收益，共享背景被多次装载是成本，两者要一起算。
- **用输入公式估总成本。** 所有工人的输出与主管汇总都要加入总 token volume；账单另按 provider/model 计价规则加权。
- **忽略每阶段的输入、输出与缓存 usage。** 同一个架构在不同任务上的 token 与费用倍数都可能不同，需逐次请求测量。
- **为了并行而拆解，却没检查私有材料是否真的不同。** 如果每个工人看到的材料一样，就没有获得上下文隔离收益；独立搜索或冗余核验仍可能有价值，但需在相同任务上测质量、覆盖、延迟与总成本。
