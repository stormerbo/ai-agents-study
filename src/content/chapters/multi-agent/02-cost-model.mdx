多智能体的成本可以用一个很短的式子估出来。它不精确，但足以让你在动手之前判断这件事值不值。

## 式子

**总成本 = 每一份上下文的规模 × 它被装载的次数。**

「装载次数」指的是**同一份内容被送进模型的次数**。这个词是关键 —— 因为多智能体最常见的问题不是「每个上下文很大」，而是「同一份内容被装了很多遍」。

举个具体例子。假设：

- 共享背景 B（团队规范、代码库约定、历史模板）
- 每个工人的私有材料 M
- N 个工人 + 1 个主管

那么：

- **单 agent**：B + N×M 装 1 次
- **主管 + N 工人**：B 装 N+1 次（每个工人一次、主管一次），M 各装 1 次

所以倍数大致是：

```text
倍数 ≈ (B × (N+1) + N×M) / (B + N×M)
```

这个式子立刻给出两条结论：

**第一，B 越大，倍数越高。** 共享背景是唯一被重复装载的东西，它越大，重复的代价越明显。
**第二，N 越大，倍数越高。** 每多一个工人，B 就多装一遍。

而如果 B 很小、M 很大，那么倍数会趋近 1 —— 也就是说，多智能体在这种情况下几乎不额外花钱。**这是拆解做对了的信号。**

## 实测：两次不同背景规模下的倍数

我做了这个对照。同一个任务（根据三份材料写技术复盘），同一个模型，只改变共享背景的规模：

| 共享背景 | 单 agent | 主管 + 3 工人 | 倍数 |
|---|---:|---:|---:|
| 小（57 字） | 4,270 | 8,161 | **1.91×** |
| 大（3,489 字） | 9,734 | 19,380 | **1.99×** |

（实跑数据，2026-10-09，`deepseek-flash`。两次运行分别复测过，倍数在 1.9 到 2.4 之间浮动。）

**两次的倍数很接近，没有随背景变大而明显升高。** 按上面的式子，背景从 57 涨到 3,489（61 倍），倍数本该明显上升 —— 但实测只从 1.91 变到 1.99。

这说明式子里少了一项。**缺的那一项是「输出」。**

## 输出不乘份数

上面那个式子只算输入，但**成本包含输出**，而输出不随上下文份数增长：

- 3 个工人的输出很小（各一段要点）
- 主管的输出与单 agent 相当（一份完整复盘）

所以更准确的形状是：

```text
倍数 = (输入 × 份数 + 输出) / (输入 + 输出)
```

**只有当输入远大于输出时，倍数才趋近「份数」。** 我这次的两个规模都还没到那个区间 —— 一份技术复盘（输出）的字数与共享背景（输入）是同量级的，所以倍数被输出摊平了，稳定在 2 倍左右。

这也是为什么第 3 章那个实验能测出 **8.1 倍**：那一次是 8 个子 agent 各自装一遍共享背景，而每个工人的**输出都很短**（只回一句结论）。输入占绝对主导，于是倍数趋近了份数。

**两种数据的差别不在「哪个更贵」，而在「输出占多大比例」。**

## 这个模型怎么用

它给出的实际判断是：

**如果你的任务里「共享内容」远多于「产出」，那么多智能体的成本会按份数放大；如果产出很多、共享内容很少，那么多智能体的额外成本有限。**

所以设计时应该争取的形状是：**每个工人只装它真正需要的那一小份，而共享的背景尽量少、尽量小。** 具体做法：

- 把共享背景里「其实只有一部分工人需要」的内容拆出去
- 需要全局背景时，先让一个便宜的前置步骤把它压成很短的约定，再分发给工人。压成什么：一份逐条列出、不超过 10 条的清单（每条一行、只写会被反复引用的规则），由一个便宜的小模型跑一次 BG 生成；工人收到的是这份清单，不是原始 BG。代价是一次调用，收益是后面 N+1 次装载都变短。
- 工人生成的产出尽量短（结构化字段而不是长文）

三条都是同一个方向：**让 B（被重复装载的内容）变小。**

## 一个反直觉的推论

成本模型还解释了一件事：**为什么「工人越多越便宜」是错的。**

一个常见的想法是「拆得越细，每个上下文越小，所以越省」。前半句对，后半句错 —— 因为**拆细的代价是共享内容被装更多遍**。

如果拆到每个工人只装一份材料（M 很小），而共享背景 B 不变，那么：

```text
倍数 ≈ (B × (N+1)) / (B + N×M)
```

N 增大时分子线性增长，分母里 N×M 也在增长。谁占主导，取决于 B 和 M 的比例。

**结论是：拆分的收益来自「每个工人的私有材料变小」，成本来自「共享背景被装载更多次」。** 所以拆分的正确方向是让每份私有材料**真的不同**，而不是把同一份内容切成很多份 —— 后者只会让 B 的负担变重，M 却没减少。

用一个具体的数字感受一下这个差别：同样是 3 个工人，如果每人装 1/3 的原始材料（M 各 100 字），总输入是 B×4 + 300；如果每人装**全部**材料（M 各 300 字），总输入是 B×4 + 900。前者省下的正是「每个工人不用看别人的那 2/3」。


## 一个更实用的估算办法

上面的式子是精确的，但你通常不知道 B 和 M 到底占多少 token。有一个更快的估法：

**跑一次单 agent 版本，记下总 token；再跑一次多智能体版本，记下总 token。两者一比就是真实倍数。**

然后拿这个倍数去问一个问题：**这份并行或隔离带来的收益，值不值这个倍数？**

- 如果倍数在 2 附近，而任务能因此并行、延迟从 sum 变成 max —— 值
- 如果倍数接近份数（比如 4 份就是 4 倍），而任务本来就不需要并行 —— 不值

这个办法的好处是**它测的是你的真实场景**，而不是套用一个别人的结论。第 3 章那 8.1 倍看起来很吓人，但它是「8 个子 agent 各自装一遍共享背景、输出又很短」这个特定形状下的结果；换成别的形状，数字会完全不同。

最后提醒一句：**不要用一次运行的数字下结论。** 本次两次运行同一配置得到过 1.91 和 2.37 两个倍数 —— 采样波动不小。要看的是量级（2 倍还是 8 倍），不是小数点。

## 和缓存的关系

最后补一个实际会影响账单的细节：**被重复装载的内容通常是可缓存的。**

第 1 章讲过 prompt caching：前缀不变的部分可以命中缓存，成本大幅下降（实测未缓存输入从 2688 降到 256）。而多智能体里被重复装载的那份共享背景 B，正好符合缓存的条件 —— 它在 N+1 个上下文里是**完全相同的前缀**。

所以真实的账单倍数往往低于按 token 数算出来的倍数。本次实测里，token 倍数在 1.9 到 2.4 之间，而按「份数 4」推算本该更接近 4 —— 差距的一部分就来自缓存。

这也给出一条优化：**把共享背景放在提示的最前面**，不要在后面插入会变的内容，否则缓存前缀被打断，重复装载就得全价付。这条和第 1 章第 5 节讲的「改一个字全部失效」是同一个机制。
## 把 usage 拆开，自己复算一遍

公式里的「输入」和「输出」不是估的，它们就在每次响应的 `usage` 里，而且要分成三类看：

```python
def split_usage(usage):
    """一次响应的 usage 拆成四类。前两类是输入，第三类是缓存，第四类是输出。"""
    return {
        "new_input": usage.get("input_tokens", 0),                        # 新输入
        "cache_read": usage.get("cache_read_input_tokens", 0),            # 命中缓存的前缀
        "cache_creation": usage.get("cache_creation_input_tokens", 0),    # 写入缓存
        "output": usage.get("output_tokens", 0),
    }


def multiplicity(total_input, total_output, copies):
    """倍数的形状：(输入 × 份数 + 输出) / (输入 + 输出)。"""
    return (total_input * copies + total_output) / (total_input + total_output)
```

用第 11 章第 1 节那次真跑的两个响应代入（本次实跑，2026-10-12）：新输入 320 + 175 = 495，缓存读取 256，输出 81 + 27 = 108。套公式算：

```text
输入只算新输入（495），份数 4：  (495×4 + 108) / (495 + 108) = 3.46
输入把缓存读取也算进去（751）：   (751×4 + 108) / (751 + 108) = 3.62
```

**这两个数是公式的预测，不是多智能体实测。** 和本节上面那张表里的实测倍数（1.91 到 1.99）差得不小，差在两处：一是那张表里的任务输出与输入同量级，而上面代入的天气任务输出只占输入的约 18%，所以公式给到 3.4 以上；二是被重复装载的前缀可以命中缓存，`cache_read` 按更低价格计费，实际账单涨得比 token 计数慢。**所以复算的用处不是精确预测账单，而是判断量级：接近 2，还是接近份数。**

## 完整可运行代码

下面这段代码并排跑单 agent 与主管 + 工人两条路线，并打印两种背景规模下的倍数。它就是上面那张表的来源。

```python
"""单 agent vs 主管 + 工人：成本模型与边界信息损失。

设计要点：
  1. 文档 D2 里埋了一条**硬约束**（不要动生产库），看它能不能穿过多层摘要活到最后。
  2. 共享背景做成两种规模 —— 因为成本倍数主要由「共享内容相对单份内容有多大」决定。

实跑状态：2026-10-09，deepseek-flash。
"""
import os
import json, os, urllib.request

BG_SMALL = ("团队规范：所有对外输出用简体中文；数值保留两位小数；"
            "不允许编造未在材料中出现的数字；每条结论必须标注来源文档编号。")

# 大背景：模拟「团队规范 + 代码库约定 + 历史模板」这类真实共享上下文
BG_LARGE = BG_SMALL + "\n\n" + "\n".join(
    "约定 %d：服务命名用 kebab-case；配置项放 config/ 下；日志必须带 trace_id；"
    "所有对外接口要有超时与重试；数据库变更走迁移脚本；异常不得吞掉。" % i
    for i in range(1, 41))

DOCS = {
    "D1": "订单服务本周 P99 延迟 820ms，上周 610ms。排查发现新增的推荐调用占用了 34% 的时间。",
    "D2": "数据库连接池上限为 20。注意：任何扩容操作都必须避开生产库，只能先在预发环境验证。",
    "D3": "推荐服务的内存占用从 1.2GB 增长到 2.8GB，主要来自缓存未设上限。",
}

TASK = "根据三份材料写一份技术复盘，指出三个最需要优先处理的问题，并说明理由。"


def call(messages, system, max_tokens=8000):
    body = json.dumps({"model": os.environ["VERIFY_MODEL"], "max_tokens": max_tokens,
                       "system": system, "messages": messages}).encode()
    req = urllib.request.Request(
        os.environ["ANTHROPIC_BASE_URL"].rstrip("/") + "/v1/messages", data=body,
        headers={"content-type": "application/json",
                 "x-api-key": os.environ["ANTHROPIC_AUTH_TOKEN"],
                 "anthropic-version": "2023-06-01"})
    with urllib.request.urlopen(req, timeout=180) as resp:
        d = json.loads(resp.read())
    u = d.get("usage", {})
    tin = (u.get("input_tokens", 0) + u.get("cache_read_input_tokens", 0)
           + u.get("cache_creation_input_tokens", 0))
    text = "".join(b.get("text", "") for b in d.get("content", []) if b.get("type") == "text")
    if not text.strip() and d.get("stop_reason") == "max_tokens":
        raise RuntimeError("测量故障：空输出 + max_tokens，需调大预算，不是模型失败")
    return text, tin + u.get("output_tokens", 0)


def arm_single(bg):
    """一个 agent 读完三份材料，直接产出复盘。"""
    material = "\n\n".join("%s：%s" % (k, v) for k, v in DOCS.items())
    return call([{"role": "user", "content": bg + "\n\n" + material + "\n\n" + TASK}],
                "你是一个严谨的技术分析助手。")


def arm_multi(bg):
    """三个工人各读一份（每人都要装一遍共享背景），主管汇总。"""
    tok, partials = 0, []
    for k, v in DOCS.items():
        text, t = call([{"role": "user", "content":
                         bg + "\n\n材料 %s：%s\n\n请提炼这份材料里对复盘有用的要点。" % (k, v)}],
                        "你是一个提炼助手，只输出要点。")
        tok += t
        partials.append("%s 的要点：%s" % (k, text.strip()))
    merged, t2 = call([{"role": "user", "content":
                        bg + "\n\n" + TASK + "\n\n各工人的提炼：\n" + "\n".join(partials)}],
                       "你是一个严谨的技术分析助手。")
    tok += t2
    return merged, tok, len(partials)


def run_pair(label, bg):
    single, t1 = arm_single(bg)
    multi, t2, n = arm_multi(bg)
    alive = ("✅" if "生产库" in single else "❌") + " / " + ("✅" if "生产库" in multi else "❌")
    print("%-14s %-10d %-12d %-9.2fx %s" % (label, t1, t2, t2 / t1, alive))
    return single, multi


if __name__ == "__main__":
    print("任务：%s" % TASK)
    print("三份材料共 %d 字" % sum(len(v) for v in DOCS.values()))
    print()
    print("%-14s %-10s %-12s %-10s %s" % ("共享背景", "单 agent", "主管+3 工人", "倍数", "硬约束存活"))
    s1, m1 = run_pair("小（%d 字）" % len(BG_SMALL), BG_SMALL)
    s2, m2 = run_pair("大（%d 字）" % len(BG_LARGE), BG_LARGE)
    print()
    print("看点：两次的倍数很接近（见上表），并没有随背景变大而明显升高。")
    print("机制解释：多智能体只把【输入】乘以份数，【输出】不乘 ——")
    print("  3 个工人的输出很小，主管的输出与单 agent 相当。")
    print("所以背景越大、输入占比越高时，倍数才会趋近「份数」（这里是 4）。")
    print("本次两个规模都还没到那个区间（输出仍与输入同量级），所以看不出差异。")
    print()
    print("=== 大背景下的单 agent 输出（前 400 字）===")
    print(s2.strip()[:400])
```

## 常见坑

- **只数「每个上下文多大」，不数「同一份内容装了几遍」。** 多智能体的成本几乎全部来自后者。
- **以为拆得越细越省。** 私有材料变小是收益，共享背景被多次装载是成本，两者要一起算。
- **用输入公式估总成本。** 输出不随份数增长，在产出很多的任务里会把倍数显著摊平。
- **忽略「产出占比」这个变量。** 同一个架构在不同任务上的倍数可能差好几倍，原因就在这里。
- **为了并行而拆解，却没检查私有材料是否真的不同。** 如果每个工人看到的材料一样，拆解只有成本没有收益。
