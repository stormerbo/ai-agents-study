「工具调用」这个说法容易让人误会。模型自身不会因为生成调用请求就直接执行你的业务代码；对于你定义的 client tool，宿主程序要负责执行与回填。平台托管的 server tool 则可能由服务商基础设施执行，所以“所有工具都由你的代码执行”也不成立。本节只讲 Anthropic Messages API 中由应用执行的 client tool。

一次 client-tool 往返会暴露模型提出的调用请求；它不等于业务操作已经发生，也不等于操作结果已验证。

## 历史响应记录：这次模型提出了什么

`stop_reason` 表示 Anthropic Messages API 本轮为何停止，是处理响应的重要路由字段，但不能把“不是 `tool_use`”都当成正常最终回答。该 API 还区分 `end_turn`、`max_tokens`、`stop_sequence`、`pause_turn`、`refusal` 和 `model_context_window_exceeded`；它们的恢复或展示方式不同。本节示例显式处理 `tool_use`、`end_turn`、`max_tokens` 和 `refusal`；`pause_turn`、上下文溢出及其他未实现状态会返回未完成标记，不会伪装成最终答案。即使 `end_turn` 表示生成回合结束，响应也可能没有可展示的文本；示例会单独报告这种情况，而不把空字符串作为答案。[Anthropic stop reasons 文档](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)。

给模型一个工具定义，问一个需要它的的问题（「100 美元现在能换多少人民币？」）：

```text
HTTP 200   stop_reason=tool_use
usage: {"input_tokens":338, "output_tokens":78}

content 数组：
  [0] thinking   80 字
  [1] tool_use   id=call_00_MuiJDM87LCjrfmnQRkba5824
                 name=get_exchange_rate
                 input={"from":"USD","to":"CNY"}
```

（历史实测记录，`deepseek-flash`，2026-10-08；原始完整响应未归档，当前无法独立复核该响应的全部字段。`thinking` 块与 Anthropic extended thinking 的保留要求依模型和端点而异；Anthropic 要求在相应延续请求中原样带回完整 thinking 块。不要把这一条推广到所有供应商或所有消息类型。[Anthropic thinking 文档](https://platform.claude.com/docs/en/about-claude/models/extended-thinking-models)。）

三件值得注意的事：

**① `stop_reason` 是 `tool_use`，不是 `end_turn`。** 对 Anthropic 的 client tool，这表示要执行一个或多个客户端工具调用并按协议回填。`end_turn` 表示本轮正常结束；`max_tokens` 等状态不能当成完整答案。实际循环要显式区分需要执行、正常完成、拒绝、截断和当前代码不支持的状态。

**② 在这里展示的非流式 Anthropic `tool_use` 响应中，`input` 是对象。** 这不代表可以跳过本地类型、字段和业务规则校验。其他供应商的协议形状不同；流式调用也要按对应事件协议组装，不能套用同一解析假设。

**③ 这次 client-tool 响应本身没有查询汇率。** 模型提出了 USD→CNY 的调用；只有宿主执行查询并把结果回填后，后续回答才可能引用汇率。

1. **识别调用请求** —— 在 Anthropic `content` 中识别应用执行的 `tool_use` 块，并明确拒绝当前循环不支持的服务端工具类型。
2. **执行允许的函数** —— 校验工具名、参数类型和业务权限；schema 合法不代表调用已获授权。
3. **按协议回填结果并继续** —— 用原调用 ID 关联 `tool_result`；再依据新响应的 `stop_reason` 决定完成、恢复或报告未完成。

历史运行摘要声称在第 3 步后得到以下结果；原始逐次响应缺失，本轮未重放，因此这不是可独立核验的模型输出：

```text
HTTP 200   stop_reason=end_turn
最终回答：根据当前汇率，1 美元 = 7.23 人民币，所以 100 美元 ≈ 723 人民币。
          ⚠️ 该汇率为模拟值（由本地函数返回），实际交易时请以银行或外汇平台的实时牌价为准。
```

上述 stdout 摘要还声称模型把本地模拟值 `{"rate": 7.23}` 算成 723 并复述 `note`；原始响应缺失，这部分同样不能独立复核。

## 协议会校验调用与结果的配对

Anthropic 会检查消息序列中的 `tool_use` / `tool_result` 配对；每个 `tool_use.id` 是该调用的唯一标识，结果必须用匹配的 `tool_use_id` 回填。这类校验只证明请求结构符合协议，**不证明宿主真的执行了工具，也不验证返回值真实或正确**。因此示例在执行前会拒绝缺失或重复的调用 ID，避免产生无法可靠配对的业务结果。[Handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)。

### 情况一：把 `tool_use` 追加进历史，但不补 `tool_result`

```json
{
  "error": {
    "message": "messages.2: `tool_use` ids were found without `tool_result` blocks immediately after: call_00_MuiJDM87LCjrfmnQRkba5824. …（下略，原文更长）",
    "type": "invalid_request_error"
  }
}
```

这两条错误来自 2026-10-08 的 DeepSeek Anthropic-compatible endpoint 历史记录；完整原始响应未归档。本节只用它们说明协议配对错误的形状，不能据此声称所有供应商错误码或报文一致。

> 这条 400 只说明请求缺少协议要求的结果块。服务端无法从消息结构判断你的宿主是否真的执行了操作；业务后置条件仍需由应用验证。

### 情况二：`tool_use_id` 写成了一个不存在的 id

```json
{
  "error": {
    "message": "unexpected `messages.2.content.0: tool_use_id` found in `tool_result` blocks: toolu_不存在的ID. …（下略）"
  }
}
```

**`tool_use_id` 是配对标识，不是授权凭证或执行证明。** Anthropic 要求它与待回填的 `tool_use.id` 匹配；实际授权和业务结果核验仍由宿主负责。

## 小样本没有触发工具错误

我原以为会经常遇到模型拿着不完整参数调用工具，然后经历失败与恢复。三次历史尝试里，模型都没有进入“工具报错后再纠正”的路径，因此这组记录**没有测到错误信息对恢复的影响**：

| 设计 | 预期 | 实际 |
|---|---|---|
| 只给 `get_user(user_id)`，问「查用户张三的邮箱」 | 模型拿姓名当 id，撞 404 | 它直接说「需要 user_id」并给出格式示例 |
| 同时给 `get_user` + `list_users` | 靠错误信息才能找到 `list_users` | **它第一次就调了 `list_users`** —— 描述本身就指明了路径 |
| 工具描述含糊、用户没给订单号 | 模型硬编一个参数去调用 | 它先问用户「请提供订单号」 |

（三行历史 stdout 摘要，`deepseek-flash`，2026-10-08；逐次原始响应缺失，无法复核评分过程。）

这三次 `deepseek-flash` 历史观察中，模型在这些特定提示下先追问或选了描述更匹配的工具；原始逐次响应缺失，本轮无法复核，因此它们不能估计“硬编参数”的频率，也不能推广到其他模型。Anthropic 当前文档也明确指出行为因模型而异：Opus 更可能追问缺失参数，Sonnet 也可能推断一个值。工具描述可以帮助选择，但不能替代宿主校验。[Anthropic 工具调用概览](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)。

## 工具结果会影响后续上下文，但仍是有类型的消息

旧记录未能复现格式差异。

设计：让工具返回**同一份数据**，只改格式 —— 一种用晦涩的嵌套 JSON（键名缩写、状态用字母码），一种用清晰文本（带单位、状态可读）。看模型最终回答是否用对了数据。

结果：**两种格式下，模型都完整保住了所有字段和数值，没有差异。**

> 而且第一次跑的时候，我得出了「晦涩格式会让模型丢掉订单号」的结论 —— 直到我发现**是我自己的测试数据里根本没放订单号字段**（我把索引字段 `i` 当成了 id）。这是本次写作里的**第四个测量缺陷**。
>
> 补上字段后重跑，两边都是 4/4 全对。

Anthropic 消息结构保留 `tool_result` 类型与关联 ID；它不等同于普通用户文本，但这也不保证内容可信。网页、邮件、第三方 API 等工具输出可能含有间接 prompt injection，应作为不可信数据处理，限制模型可据此执行的动作，并在宿主端做授权与业务校验。[Anthropic Handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)、[OWASP Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)。

本节这组 4 条记录的历史观察只说明该样本未测出格式差异；原始响应缺失，不能证明格式差异只在更大数据量时出现，也不能量化格式化的收益。让结果可读、有限、可校验是工程建议，不是安全边界。

## 可运行的教学代码骨架

下面的函数是本地常量模拟，不会联网查询汇率；代码也没有实现真实身份认证、租户授权、速率限制、幂等、数据库写入或业务结果校验，不能直接作为生产执行器。

```python
# tool_loop.py
"""一个最小可用的工具调用循环。

没有框架，聚焦一次 client-tool 往返的控制权。这个脚本是教学骨架，不覆盖生产框架常见的状态持久化、并发调度、重试策略、审批、追踪和取消语义。
"""

import json
import os
import re

import anthropic

client = anthropic.Anthropic(
    api_key=(
        os.environ.get("ANTHROPIC_API_KEY")
        or os.environ.get("ANTHROPIC_AUTH_TOKEN")
    ),
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)
MODEL = os.environ["VERIFY_MODEL"]

TOOLS = [
    {
        "name": "get_exchange_rate",
        "description": "查询两种货币之间的当前汇率。",
        "input_schema": {
            "type": "object",
            "properties": {
                "from": {"type": "string", "description": "源货币的三位代码，如 USD"},
                "to": {"type": "string", "description": "目标货币的三位代码，如 CNY"},
            },
            "required": ["from", "to"],
        },
    }
]


def get_exchange_rate(from_currency: str, to_currency: str) -> dict:
    """这段代码和模型完全无关 —— 它就是你自己的业务逻辑。

    真实场景里，它会去查数据库或调第三方接口。
    """
    return {"rate": 7.23, "note": "模拟值，由本地函数返回"}


# ② 执行：工具名 → 真正的函数
IMPL = {"get_exchange_rate": get_exchange_rate}


def run(question: str, max_rounds: int = 8) -> str:
    messages = [{"role": "user", "content": question}]

    for _ in range(max_rounds):          # 本示例只用轮次上限；生产环境还需预算和超时
        response = client.messages.create(
            model=MODEL, max_tokens=4000, tools=TOOLS, messages=messages,
        )

        # ① 按 stop_reason 分流；只有 end_turn 才按完整答案返回
        if response.stop_reason == "end_turn":
            text_blocks = [
                b.text for b in response.content
                if b.type == "text" and isinstance(b.text, str)
            ]
            if not any(text.strip() for text in text_blocks):
                return "已结束，但没有可展示的文本；由调用方按产品策略处理。"
            return "".join(text_blocks)
        if response.stop_reason == "max_tokens":
            return "未完成：模型输出触及 max_tokens，不能当作完整答案。"
        if response.stop_reason == "refusal":
            return "模型拒绝了请求；按产品策略处理，不要继续执行工具。"
        if response.stop_reason != "tool_use":
            return f"未完成：本示例未处理 stop_reason={response.stop_reason!r}。"

        # 本例仅实现应用执行的 client tool；不要静默忽略 server/MCP tool 块
        if any(b.type in ("server_tool_use", "mcp_tool_use") for b in response.content):
            return "未完成：本示例不支持 server-side 或 MCP 工具流程。"
        tool_blocks = [b for b in response.content if b.type == "tool_use"]
        if not tool_blocks:
            return "未完成：响应标记了 tool_use，但没有可处理的 client tool block。"
        tool_ids = [getattr(block, "id", None) for block in tool_blocks]
        if any(not isinstance(tool_id, str) or not tool_id.strip() for tool_id in tool_ids):
            return "未完成：tool_use 缺少有效 ID；没有执行任何工具。"
        if len(set(tool_ids)) != len(tool_ids):
            return "未完成：tool_use ID 重复；没有执行任何工具。"

        # 对需要保留的 Anthropic thinking/tool 块，原样保留完整 assistant content
        messages.append({"role": "assistant", "content": response.content})

        # ② 执行 + ③ 按 Anthropic 协议回填；schema 不等于业务授权
        results = []
        for block in tool_blocks:
            fn = IMPL.get(block.name)
            error = None
            if fn is None:
                error = "unknown_tool"
            elif not isinstance(block.input, dict) or set(block.input) != {"from", "to"}:
                error = "invalid_arguments"
            elif any(
                not isinstance(block.input[key], str)
                or re.fullmatch(r"[A-Z]{3}", block.input[key]) is None
                for key in ("from", "to")
            ):
                error = "invalid_arguments"

            if error:
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,      # 配对 ID，不是授权凭证
                    "is_error": True,
                    "content": json.dumps({"error": error}),
                })
                continue

            try:
                output = fn(
                    from_currency=block.input["from"],
                    to_currency=block.input["to"],
                )
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": json.dumps(output, ensure_ascii=False),
                })
            except Exception:
                # 细节留在受控日志；不要把异常文本、SQL 或密钥回填给模型
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "is_error": True,
                    "content": json.dumps({"error": "tool_execution_failed"}),
                })

        messages.append({"role": "user", "content": results})

    return f"未完成：达到 {max_rounds} 轮上限仍未收到 end_turn"

if __name__ == "__main__":
    print(run("100 美元现在能换多少人民币？"))
```

> **实跑状态**：本文表格与代码块里的**报文和响应结构是实测的**（用直接 HTTP 请求采集）；上面这份 Python 脚本用的是 SDK 写法，字段与采集脚本一致，但**脚本本身未在官方端点验证**。

**这个 Anthropic Messages API 示例在每次请求中都显式传入同一份 `tools` 定义。** 这是本例的接口使用方式，不应当推广为所有 SDK/provider 的持久化规则。若同时使用 prompt caching，缓存命中还取决于缓存断点、前缀布局、端点和策略；单独改一处工具描述不必然导致“整条前缀缓存失效”。具体行为应查相应 API 文档与 usage 字段。

## 常见坑

**把工具执行边界混为一谈。** 用户定义的 client tool 由应用执行；平台托管的 server tool 可能由服务商基础设施执行。模型生成调用请求不等于操作执行，更不等于业务后置条件成立；对应执行方仍需检查结果。

**只把 `text` 块追加进 Anthropic 的工具延续请求。** 对需要延续的 thinking 响应，按相应模型/API 要求保留完整的 assistant content；删掉 `tool_use` 或修改受签名保护的 thinking 块会破坏协议。此要求与其他供应商协议不可互换。

**忘了给循环设上界。** 工具调用是个循环，必须有硬性轮次上限。一个看不懂返回值、或者不断重试的模型会把你的预算烧光。

**把工具内部异常原样回填。** 应用可以用 Anthropic `tool_result` 的 `is_error` 标记报告执行失败，但要先删去密钥、SQL、个人数据等内部细节；模型可能依据错误尝试恢复，但协议不保证它会正确重试。日志应留在受控的宿主侧。

**把工具返回值当作可信指令。** `tool_result` 有自己的消息类型与调用关联，但其中的外部内容仍可能不可信；不要把它拼进 system 指令，也不要让内容绕过宿主授权。
