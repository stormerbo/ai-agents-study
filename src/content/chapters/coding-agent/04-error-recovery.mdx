上一节讲完「怎么把改动写进去」。这一节讲改完之后的事 —— 而这一步才是 coding agent 的分水岭。

因为 agent 和「代码补全」的本质区别不在生成能力，而在**它能不能自己发现错了、并改对**。

## 一、实测：5 个 bug，最多 5 轮

我准备了 5 个有 bug 的函数，每个配一段能真实运行的测试。让模型跑
「看报错 → 改 → 再跑」的循环，最多 5 轮：

```text
fixture     结果      用了几轮
均分        修好        2
去重保序     修好        2
解析时长     修好        2
安全除法     修好        2
截断文本     未修好      5

成功率 4/5 = 80%    平均轮数 2.0（仅统计修好的）
```

两件事值得单独看。

### 修好的四个，全都恰好用了 2 轮

没有一个是 1 轮就对的。这不是巧合：模型第一次只能看到报错**文字**，
它得先从报错反推出「测试到底期望什么」，才发现自己第一次改的方向不对。

举一个具体的：`def average(nums): return sum(nums) / len(nums)`，
测试里有一条 `assert average([]) == 0`。第一次报的是 `ZeroDivisionError`，
模型看到「除零」就加了 `if not nums: return 0` —— 这次对了。
但它第一次的修改是先改成了 `return sum(nums) / max(len(nums), 1)`，
那个写法在空列表上返回 0 但掩盖了真实问题，第二条断言才让它改对。

**所以「一次成型」在 coding agent 上是不现实的。**
这不是模型不够强，而是**任务的信息结构决定的**：报错只提供部分信息，
你必须先做一次尝试，让隐藏的约束暴露出来。这一章后面所有工程手段都建立在这个认识上。

### 那个 5 轮没修好的案例

函数是按长度截断字符串：

```python
def truncate(s, n):
    return s[:n]
```

两条测试：`truncate("hello world", 8) == "hello..."`、`truncate("hi", 8) == "hi"`。

也就是说：**省略号要算在 n 里**。模型前几轮一直走「先按 n 切、再补省略号」的路，
得到 `hello wo...`（11 字符）；后面几轮都在这条路上微调，
**始终没有转向「先减去省略号宽度再切」这个正确方向**。

这个案例说明：**清晰的报错不保证收敛。** 报错说「结果不对」，
但「不对在哪一步」要模型自己反推。而模型倾向于在当前方案上做局部调整，
不是推翻重来 —— 每一轮它看到的都是「上一版代码 + 报错」，很容易在局部最优里打转。

## 二、报错里该放什么，不放什么

既然要循环，那每一轮喂回去的「报错」就是设计对象。三条规则：

**一、给原始报错，不要给它转述。** `AssertionError: assert truncate("hello world", 8) == "hello..."`
比「测试失败了，期望值和实际值不一致」有用得多。前者含有实际期望值，后者只有结论。

**二、加上「已经试过什么」。** 这是最容易被省略、却最能打破打转的一条。
如果第四轮还只给报错，模型很可能再走一遍第二轮的思路。加上一句
「你已经试过 A、B 两种做法，都失败了」会让它更换方向。

**三、别把整个文件塞回去。** 第 3 节的数据说明：给多了不一定是好事，
而且成本高。**给改动点附近的窗口 + 报错 + 已试方案**通常就够。

一个更进一步的规则是**失败计数触发降级**：同一个断言连续失败 2 次，
就把策略从「微调」切到「换实现思路」（在提示里明确要求给出一个完全不同的写法）。
上面那个 `truncate` 案例如果有这条规则，很可能第二轮就跳出来了。

## 三、验证要分层，不能只有「跑测试」

很多 coding agent 只有一层验证：跑测试。但真实项目里，测试通过不等于改对了。
一个分层的验证顺序是这样的：

| 层 | 检查什么 | 成本 | 失败时说明 |
| --- | --- | --- | --- |
| 1. 语法 | 能不能解析 | 极低 | 改动写坏了 |
| 2. 类型 | 类型检查过不过 | 低 | 接口用错了 |
| 3. 单测 | 行为对不对 | 中 | 逻辑错了 |
| 4. **改动范围** | 只改了预期的文件吗 | 极低 | **改多了，引入了无关变更** |
| 5. 端到端 | 整体还跑得通吗 | 高 | 破坏了别的部分 |

第 4 层最容易被漏，但它在 agent 场景里特别重要：**agent 很容易顺手改掉别的东西。**
判据很简单 —— 对比改动的 diff，如果出现了任务没要求的文件，
就应该停下来问，而不是继续往下跑。

第 5 层则要看你的项目有没有这个条件。没有端到端测试时，
至少应该有「改动范围」这一层，因为它是所有层里最便宜、且能拦住最危险情况的。

## 四、代码：一个带跳出机制的修复循环

```python
MAX_TURNS = 6
SAME_FAILURE_LIMIT = 2      # 同一个断言连续失败几次就换方向


def fix_loop(run_tests, ask_model, initial_code):
    code = initial_code
    tried = []              # 记录已经试过的方向
    last_err, same_count = None, 0

    for turn in range(1, MAX_TURNS + 1):
        ok, err = run_tests(code)
        if ok:
            return code, turn, tried

        if err == last_err:
            same_count += 1
        else:
            same_count = 1
            last_err = err

        # 关键：连续卡在同一个错误上，就要求换一个完全不同的实现思路
        if same_count >= SAME_FAILURE_LIMIT:
            hint = ("你已经在同一个错误上卡了 %d 次。请**放弃当前实现**，" % same_count +
                    "给出一个结构上完全不同的写法。之前试过的方向：" + "；".join(tried))
        else:
            hint = "报错：" + err

        new_code = ask_model(code, err, hint, tried)
        tried.append(err[:60])
        if new_code == code:            # 模型没改，再问也是浪费
            return code, turn, tried + ["模型未做改动，提前终止"]
        code = new_code

    return code, MAX_TURNS, tried
```

三个设计点：

**一、`SAME_FAILURE_LIMIT` 是核心。** 它把「多试几轮」换成「换个方向」。
没有它，轮数上限只是一个烧钱的开关。

**二、`tried` 要真的传进提示。** 只记录不喂回去等于没记。

**三、检测「模型没改」并提前终止。** 有时模型会把同样的代码再输出一遍，
这时候继续循环纯属浪费。**这个判断也顺便抓到了一个信号：模型可能已经不会了。**

### 一个真实的报错

我第一版把 `same_count` 的重置写成了：

```python
if err == last_err:
    same_count += 1
else:
    last_err = err          # 错：忘了重置 same_count
```

后果是：只要模型**中途偶然修好了这一段、又在下一段犯同样的错**，
`same_count` 会一直累加，于是循环过早地切换到「换思路」模式 ——
本来正在稳步收敛的任务被强行打断。

这类「计数没有正确重置」的 bug 在循环逻辑里特别常见，
判据是：**任何计数器都要能一眼看出它在哪一行被重置。**
看不出重置位置的计数器，基本都有这个 bug。

## 五、恢复能力的上限由测试覆盖率决定

这一节所有讨论都建立在一个前提上：**测试能发现问题。**
如果测试没覆盖到你改的那部分，那么循环拿到的反馈是「通过」——
于是一个错误的改动会被当成成功的改动，直接进入下一步甚至提交。

这是 coding agent 最危险的失败形态，因为它**看起来完全成功**：
测试全绿、没有报错、agent 报告「已完成」。
而实际情况是它把 `refundable` 的判断条件写反了，只是恰好没有测试覆盖到。

所以对 coding agent 来说，**写测试不是「额外工作」，而是让 agent 能工作的前提**。
这有一个很实际的反直觉推论：

> **测试多的项目，agent 用起来更省力；测试少的项目，agent 反而更贵。**

因为前者能在早期就发现错误并自我修正，后者要靠人来兜底 ——
你最终得逐个 diff 复查，那比自己写还慢。

这也解释了一个现象：同一套 agent 工具，在不同团队里的效果差异极大。
很大程度上不是模型或提示词的差别，而是**被改的那个仓库的可验证性差别**。
所以如果你打算长期用 agent 改代码，最值得的投资是**补齐关键路径的测试**，
而不是继续调提示词。

## 六、小结

- **修好的四个 fixture 全都用了 2 轮** —— 一次成型不现实，循环是必需的
- **报错只提供部分信息**，隐藏约束要靠一次失败的尝试才暴露出来
- **清晰的报错不保证收敛**：实测有一个案例 5 轮都在同一个方向上打转
- **同一错误连续失败就换方向**，这比「再多试几轮」有效得多
- **验证要分层**：语法 → 类型 → 单测 → **改动范围** → 端到端，第 4 层最容易被漏
- **计数器要能一眼看出在哪重置** —— 否则会出现「过早降级」这类隐蔽 bug
