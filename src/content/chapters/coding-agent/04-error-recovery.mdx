上一节讲完「怎么把改动写进去」。这一节讲如何验证改动，以及验证失败后怎样安全地产生下一次尝试。Coding agent 的反馈循环让机器检查参与修复，但“测试变绿”只说明当前检查通过，不能单独证明需求满足、改动安全或任务可以提交。

**实跑状态：** 本节的 AST 检查器和固定 `fake_proposer` 已在本地运行，展示 3 次验证、2 次提案；这不调用 provider，也不执行生成代码。历史 DeepSeek 逐次响应缺失，未复跑，因此历史模型效果仍不可估计。

## 一、先审计一条历史恢复记录

项目在 2026-10-10 记录过五个函数修复摘要，模型标为 `deepseek-flash`，最多五轮；脚本与汇总日志位于忽略目录 `verify-output/coding-recover.py` 和 `verify-output/coding-recover.log`。摘要记了四个 fixture 通过、一个未通过，以及“平均 2 轮”。复查实际脚本后，这组数字**不能支撑原正文的 4/5 模型成功率、模型修复方向或“每个修好的案例都调用模型两次”的结论**：

- “截断文本”fixture 的第二条断言多了右括号，源码无法解析。即使 `truncate` 实现正确，该 fixture 也过不了。因此那条失败不能归因于模型不收敛。
- 脚本从第一轮起就把测试全文放入 prompt；“模型最初只能看报错，隐藏约束要靠失败后才暴露”与脚本不符。
- `turn=2` 表示第二次运行测试时发现通过。对修好的案例，这通常意味着一次候选生成后通过验证；不是两次修复调用。脚本没保存逐次响应和方向，不能重建各轮究竟改了什么。
- API 异常被折叠成“未修好”，汇总日志没有失败分类。它不能区分模型提案无效、接口错误、测试错误或运行环境问题。

所以这批数据应保留为**测试夹具有缺陷、过程不可复核的历史摘要**，不用于估计成功率或比较模型。原始日志如下，只用于展示审计对象：

```text
fixture     日志记录结果  日志记录轮数
均分        修好          2
去重保序     修好          2
解析时长     修好          2
安全除法     修好          2
截断文本     未修好        5

日志汇总：4/5；“平均轮数 2.0”（仅统计修好的）
```

这个例子先说明一件事：**解释模型行为之前，先验证测试、执行器和记录器本身。** 测试失败可能来自代码、测试、依赖、配置或 runner；证据链要把这些情况分开。没有逐次原始输出时，不能用事后猜测填补缺失环节。

为让恢复动作可审计，可以先把结果映射到有限状态。状态记录的是执行器已知的事实，不是模型“觉得修好了”：

| 结果类别 | 证据 | 后续动作 |
|---|---|---|
| `passed` | runner 正常退出且选定断言全通过 | 检查 diff、验收条件和未覆盖风险 |
| `test_failed` | runner 正常执行，至少一条断言失败 | 提供脱敏后的稳定失败 ID 与局部上下文 |
| `runner_error` | 命令未能可靠启动或测试过程崩溃 | 修复/隔离环境；不要消耗模型修复次数 |
| `incomplete` | 超时、取消或结果无法确认 | 保留未知状态，按幂等性决定安全重跑或人工接手 |

同一失败反复出现不一定说明模型“没听懂”：也可能是测试错误、依赖故障、反馈过期或候选改动没有应用。相反，失败签名变化也不自动表示进展，应同时查看实际 diff 和剩余验收项。把这种分类写入协议后，重试策略才能决定是否再次调用模型、重跑测试、修复 runner 或停止。

## 二、失败反馈应该包含什么

修复循环每一轮都要把“系统观察到了什么”转换成下一步可检查的信息。反馈通常包含：失败的测试 ID 和断言位置、预期与实际的安全摘要、受影响的文件/函数、运行器退出状态，以及此前尝试的**改动摘要和验证结果**。仅记录“同一个错误”不够：错误字符串可能包含临时路径或动态值，也可能因实际值变化而改变；最好用稳定测试 ID 或失败签名识别同一个失败。

诊断输出要经过筛选。编译器、测试和被修改仓库中的程序都可能输出密钥、个人信息或带指令的恶意文本。不要把未经审查的完整日志直接拼进 prompt；截取相关片段、脱敏敏感值、标明内容来自不可信的工具输出，并限制长度。必要时给模型完整的局部代码和调用上下文，但不能为了省 token 把决定行为的接口契约、配置或相关测试裁掉。

把“已尝试什么”告诉模型有助于避免重复提案，但它只是提示信息，不能保证模型会换方案。记录应描述**改动了什么**，而不只是重复粘贴失败报错。达到连续失败阈值后要求先解释不同方案的关键假设，再生成另一个候选，是一种可测试的启发式；阈值 2、3 或其它数字要用目标任务评估，不能当作普遍最优值。

修复请求应给出任务目标和验收条件，而不只是测试断言。测试可能没有覆盖需求、误表达预期，甚至本身写错。候选 patch 还要经过文件范围策略、格式/差异检查和人工审查；模型输出不是可信命令。测试应在隔离环境运行，限制文件系统、网络、凭据、资源和时长。此节的循环示例只检查一个玩具 AST，不执行生成代码；真实 coding agent 需要操作系统层的 sandbox。

## 三、验证不是一条固定的五层流水线

语法、类型、单测、差异检查、集成测试和端到端检查各自能发现不同问题。实际运行顺序和成本取决于仓库、依赖关系与风险；改动范围检查也可以在生成 patch 后立即做，而不必排在单测之后。

| 检查 | 可以发现 | 不能单独证明 |
|---|---|---|
| 语法/格式/静态分析 | 解析错误、部分明显接口或风格问题 | 业务行为正确、设计符合需求 |
| 单元测试 | 被覆盖的函数和边界行为是否符合断言 | 断言本身正确，未覆盖场景正确 |
| 类型和构建 | 类型契约、模块集成或编译问题 | 运行期依赖、权限或外部效果正确 |
| diff 与文件范围 | 意外文件、过宽改动、秘密或生成物混入 | 保留文件中的逻辑正确 |
| 集成/端到端/故障测试 | 被执行路径中的组件交互和指定故障 | 生产负载、所有环境和所有故障都已覆盖 |

审查 diff 时，若出现任务未授权修改的文件，应暂停并确认；若任务本来要求跨文件变更，则按预先定义的允许范围检查，不要把“文件多”自动判作错误。测试通过后还要检查需求、边界条件、依赖变更、权限影响和未覆盖风险。代码覆盖率是测试触达范围的一种指标，不是测试质量或正确性的充分条件。

## 四、一个可运行的修复循环控制器

下例不调用模型，也不执行候选 Python。`fake_proposer` 和 `run_demo_check` 只演示控制逻辑：最初的返回值不正确，第一次提出局部改动仍失败；同一稳定测试 ID 连续失败后，控制器请求一个不同方向，最后 AST 检查通过。这个 3 次验证、2 次提案的结果是固定 fixture 的演示，不是 coding agent 的成功率证据。

```python
"""Deterministic repair-loop control demo; never executes model code."""
import ast


def run_demo_check(source):
    """Toy AST check: answer() must return the integer 42."""
    try:
        tree = ast.parse(source)
    except SyntaxError as error:
        return [{"test_id": "python-syntax", "message": error.msg}]

    function = next(
        (node for node in tree.body
         if isinstance(node, ast.FunctionDef) and node.name == "answer"),
        None,
    )
    if function is None or len(function.body) != 1:
        return [{"test_id": "answer-contract", "message": "expected one return"}]
    statement = function.body[0]
    if not isinstance(statement, ast.Return):
        return [{"test_id": "answer-contract", "message": "expected return"}]
    if not isinstance(statement.value, ast.Constant) or statement.value.value != 42:
        return [{"test_id": "answer-contract", "message": "expected integer 42"}]
    return []


def repair_loop(initial_source, run_checks, propose, *, max_repairs=4,
                same_failure_limit=2):
    """Each candidate is checked before it can be returned as passed."""
    source = initial_source
    history = []
    previous_signature = None
    same_failure_count = 0
    proposal_count = 0

    # Initial validation plus at most max_repairs candidate validations.
    for validation_number in range(max_repairs + 1):
        failures = run_checks(source)
        if not failures:
            return {
                "status": "passed", "source": source,
                "validations": validation_number + 1,
                "proposals": proposal_count, "history": history,
            }

        signature = tuple(sorted(item["test_id"] for item in failures))
        if signature == previous_signature:
            same_failure_count += 1
        else:
            previous_signature = signature
            same_failure_count = 1

        if validation_number == max_repairs:
            return {
                "status": "failed_unverified", "source": source,
                "validations": validation_number + 1,
                "proposals": proposal_count, "history": history,
                "failures": failures,
            }

        change_direction = same_failure_count >= same_failure_limit
        candidate, change_summary = propose(
            source=source,
            failures=failures,
            prior_attempts=history.copy(),
            change_direction=change_direction,
        )
        proposal_count += 1
        if candidate == source:
            return {
                "status": "stalled", "source": source,
                "validations": validation_number + 1,
                "proposals": proposal_count, "history": history,
                "failures": failures,
            }
        history.append({
            "change_summary": change_summary,
            "failure_ids": list(signature),
            "requested_new_direction": change_direction,
        })
        source = candidate

    raise AssertionError("unreachable")


def fake_proposer(*, source, failures, prior_attempts, change_direction):
    """Fixed fixture: first local tweak fails; alternate solution passes."""
    assert failures and all(item["test_id"] == "answer-contract" for item in failures)
    if change_direction:
        assert prior_attempts and prior_attempts[-1]["change_summary"] == "try a different constant"
        return "def answer():\n    return 42\n", "return the required value directly"
    return "def answer():\n    return 1\n", "try a different constant"


if __name__ == "__main__":
    result = repair_loop(
        "def answer():\n    return 0\n",
        run_demo_check,
        fake_proposer,
        max_repairs=4,
        same_failure_limit=2,
    )
    assert result["status"] == "passed", result
    assert result["validations"] == 3 and result["proposals"] == 2, result
    assert result["history"][-1]["requested_new_direction"] is True, result
    print({key: result[key] for key in ("status", "validations", "proposals", "history")})
```

这里把“修复提案次数”和“验证次数”分开：初始版本先验证一次，之后每个候选再验证一次，因此最多 `max_repairs + 1` 次验证。达到上限时返回 `failed_unverified` 和最后一次失败；不会在最后一轮生成尚未验证的新代码后，把它伪装成完成。若模型不改代码，状态是 `stalled`，也不能当作成功。

真实 runner 还应分别记录测试基础设施错误、测试失败、测试通过、模型 API 失败、模型输出无法解析和超时。只有测试运行器成功执行且测试断言全部通过，才是 `passed`；runner 崩溃或依赖不可用应是 `incomplete`/`blocked` 等独立状态，而不是模型失败。对于会产生副作用的检查任务，先定义隔离和清理策略。

## 五、恢复能力取决于多条证据链

自动修复能力依赖至少四件事：目标和验收条件足够清楚；检查器能检测目标错误且本身可靠；agent 得到足以定位问题但不过量的反馈；运行环境能安全执行并保存真实结果。任何一处缺失，都可能出现“绿灯但没修好”或“失败却无法归因”。覆盖率只是其中一个诊断指标：即使某行被执行，断言也可能太弱；没有覆盖的行为也不一定在本次改动范围内。

测试数量多不自动意味着 agent 更省钱或更可靠。测试需要稳定、快速、与需求一致，并且能覆盖本次风险；慢而 flaky 的套件会增加迭代时间，脆弱的断言会引导模型追逐错误目标。对测试薄弱的仓库，应先补关键行为规格或加入人工审查/独立验证，而不是无限扩大自动重试。

对每轮修复留存最少的审计记录：任务和基线标识、运行器/依赖版本、测试选择、退出状态、失败 ID、patch 摘要、验证结果、停止原因，以及本次是否修改允许范围外的内容。日志正文按数据分级处理；保存哈希或摘要无法替代必要的脱敏和访问控制。不要把“模型说已完成”当作任何一项机器检查的通过结果。

## 六、小结

- 历史 `coding-recover` 摘要含有语法错误的测试夹具，且无逐次响应；4/5 与“修复需要两轮”的解释不能作为模型效果证据。
- 反馈应包含稳定失败 ID、相关预期/实际摘要、改动摘要和受控代码上下文；日志需脱敏，并视为不可信输入。
- 重复失败后换方向可以作为待评估启发式；需按任务测量，不能从有缺陷的历史样本宣称有效。
- 区分提案次数、验证次数、测试失败、runner/API 故障和未验证状态；最后生成的代码必须再跑检查。
- 结合测试、构建、diff、集成和故障证据判断改动；任何单一绿灯或覆盖率数字都不能代替需求审查。
