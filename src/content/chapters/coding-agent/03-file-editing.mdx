搜索解决「改哪里」，这一节解决「怎么把改动真的写进去」。

文件修改的关键不是选出一种永远正确的格式，而是让模型提出的改动能被执行器明确解析、定位、验证和拒绝。
精确文本替换是一种常见方式，但也有整文件输出、diff、结构化编辑和按行插入等方式；不同工具的能力不同。

**实跑状态：** 下面保留了 2026-10-10 的一次小样本 API 运行日志（模型标记为 `deepseek-flash`）。它只能展示该组 fixture 的观察结果，不能估计一般 coding agent 的编辑成功率：样本分别只有 8、5、5 次，没有重复轮次，也没有保存逐次原始模型响应。脚本与汇总日志在忽略目录 `verify-output/coding-edit.py`、`coding-edit.log`、`coding-edit2.py` 和 `coding-edit2.log`；这些文件不是版本控制中的长期证据。

## 一、第一组：小文件、无重复 —— 8/8 全对

一个 28 行的 Python 文件，8 个编辑任务（改常量、加参数、重命名函数、加字段、改比较符……），
每个任务让模型输出 `old_string` / `new_string`，然后检查两件事：

1. `old_string` 能否在文件里**恰好匹配一次**（0 次或多次都不合格）
2. 替换之后是否是合法 Python

```text
唯一匹配成功：8 / 8 = 100%
替换后语法合法：8 / 8 = 100%
```

这 8 次都唯一匹配且语法可解析，只说明这组简单 fixture 的结果。它不能说明真实仓库中的成功率，也不能与后面的不同 fixture 直接作因果比较。

## 二、第二组：83 行、8 个近乎相同的 handler

换一个 fixture：一个文件里有 8 个结构几乎相同的 `handle_type_N` 函数，
每个都有 `data = req.get("payload")`、`if data is None:`、`total > LIMIT` 这样的行。
任务变成「改第 5 个 handler 的某一处」。

这里测两种条件：

- **A：给模型文件全文**
- **B：只给文件开头 14 行**（模拟真实 coding agent 分片读文件的方式），并告诉它「后面还有 7 个相似函数」

结果：

```text
条件                    唯一匹配       替换后语法合法
A. 给了文件全文           4/5 = 80%      4/5 = 80%
B. 只给了开头片段         0/5 =  0%      0/5 =  0%
```

**B 组这次运行的 5 项都未被记为成功，但汇总输出不足以证明失败原因：**

```text
#1  匹配 0 次        <- 日志只有计数，没有原始 old_string，无法归因
#2  匹配 1879 次     <- 很可能是 old_string 为空；Python 中空字符串会在长度为 N 的文本里计为 N+1 次
#3  JSON 解析失败
#4  JSON 解析失败
#5  匹配 0 次        <- 日志只有计数，没有原始 old_string，无法归因
```

「**匹配 1879 次**」不能按旧解释理解为一个通用代码片段出现近两千次。该 fixture 的文件长度约为 1,878 个字符，而 Python 的 `str.count("")` 返回 `len(text) + 1`；因此这个数字强烈暗示模型返回了空 `old_string`。由于响应没有留存，这只能作为对日志的可检验推断，不能冒充原始输出。执行器应拒绝空字符串、零匹配和多匹配，并分别返回稳定错误类型。

A 组本次为 4/5 唯一匹配，另一次 JSON 解析失败。它提示执行器需要验证输出格式，但 5 次样本不能据此估计格式错误率或认定全文上下文是成功的原因。

`str.count()` 的一个边界：它只统计互不重叠的子串。`"aa"` 在 `"aaa"` 中有两个可能的起点，但 `"aaa".count("aa")` 返回 1。因此，不能直接把 `count(old_string) == 1` 当成唯一定位证明；要按每个字符起点检查候选位置。

### 解析结构化编辑输出

历史日志没有保存原始失败响应，因此不能据此复原围栏、解释文字或其它格式偏差。若工具协议要求 JSON，优先使用 provider 支持的结构化输出；否则先按协议解析，拒绝额外文本和错误字段。不要用正则截取第一个 `{` 到最后一个 `}`：字符串和嵌套对象会让这种提取含糊。

```python
import json


def parse_edit(raw):
    """只接受协议规定的 JSON；调用者应把解析失败作为协议错误处理。"""
    value = json.loads(raw)
    if not isinstance(value, dict):
        raise ValueError("编辑提案必须是 JSON 对象")
    if set(value) != {"old_string", "new_string"}:
        raise ValueError("编辑提案字段不符合协议")
    if not all(isinstance(value[key], str) for key in value):
        raise ValueError("编辑提案字段必须是字符串")
    return value
```

解析失败时不要猜测或自动把响应当作文件内容。可以返回带类型的协议错误，让 agent 在预算内重新提出编辑，改用另一种受支持的 edit format，或停止并交由人处理。整文件重写是另一种编辑策略，不能作为 JSON 解析失败时的通用降级；它也可能遗漏未修改内容、格式错误或产生范围外变化。

## 三、从这两组数据能推出的四件事

**一、编辑提案需要足够的定位依据。** 这组日志里全文条件为 4/5、片段条件为 0/5，
但小样本且未保存原始响应，不能说“唯一变量是全文”，也不能把差异解释成普遍因果规律。
可复用的工程原则是：执行前读取当前文件，并验证编辑目标确实存在且定位满足工具策略。

**二、`old_string` 的唯一性是执行器必须检查的约束。**
一种容易静默造成错位的失败模式是「匹配到多处时静默选了第一处」。
正确的做法是**只在定位唯一时应用编辑；有多处候选就拒绝并报告**（例如：「原文至少匹配两处，可能含重叠位置；请提供更长的上下文」）。这能给下一轮提供明确的修复方向，但不能保证一次提案就能修好。

**三、写入成功不等于行为正确。** 上面还算的是「语法是否合法」，但那只是最低要求。
真正要判的是「**改完之后行为是否还符合预期**」—— 那需要跑测试，
也就是这一章第 5 节要讲的内容。

**四、失败要有可恢复的路径。** 匹配 0 次时，重新读取当前内容并核对目标；多处匹配时，要求更具区分度的上下文；协议错误时，按协议纠正或停止。是否切换为整文件输出应由文件长度、任务范围、输出校验和差异风险决定。

## 四、几种编辑策略的取舍

除了精确匹配替换，还有几种常见策略，各有适用面：

**整文件输出。** 让模型输出完整的新文件。它避免了旧文本定位步骤，但要求输出完整、格式可解析并保留应有内容；完整性、无关差异和 token 成本都需检查。没有通用的“100 行以内”阈值。Aider 当前文档同时列出 whole、diff、udiff 等格式，说明实际工具可以并存多种格式；Anthropic 的 text editor 工具则定义了 `str_replace` 和按行插入命令。参见 [Aider edit formats](https://aider.chat/docs/more/edit-formats.html) 与 [Anthropic text editor tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/text-editor-tool)。

**按行号替换。** 让模型说「把第 42 到 45 行换成……」。优点是省 token；
缺点是**行号会随编辑漂移** —— 同一轮里改了前面一处，后面的行号就全错。
所以它只适合「每轮只改一处、改完立即重算行号」的流程。

**结构化编辑。** 用 AST/CST 或语言服务定位语法节点再修改。AST 可能丢失注释或格式信息；CST/编辑器 API 的保留能力取决于实现。解析器支持、语法版本和格式要求也要纳入选择。

**精确匹配替换。** 需要原文与当前文件精确一致；执行器应明确定义零次、多次和空字符串的行为。不同产品支持不同 edit format：Anthropic text editor 提供 `str_replace` 和行号 `insert`，Aider 文档列出 whole、diff、udiff 等格式；不能据此概括所有工具都采用同一种方式。

策略应依据改动范围、工具保证和验证成本选择。无论使用哪种格式，都记录解析失败、定位失败、应用失败和后续验证失败的不同计数；单一“编辑失败率”会混淆不同故障来源。

### 一个有问题的实现：静默改了第一处

下面这个简化实现展示一种静默改错位置的风险：

```python
def apply_edit(src, old, new):
    if old in src:
        return src.replace(old, new, 1)      # 错
    raise ValueError("原文未找到")
```

两处问题，都很典型：

**一、它只检查「存在」，不检查「唯一」。** 当 `old` 在文件里出现多次时，
`replace(..., 1)` 会**静默地改掉第一处**。程序不报错，测试可能还是过的，
但改的位置完全不对。**这是最危险的一类失败：它看起来成功了。**

**二、它把「未找到」和「找到多处」合并成了一种错误。** 两者的修法完全不同 ——
前者要重新读取当前文件并核对目标，后者要提示模型给更长的上下文。
合并处理会让 agent 收到一条无用的报错，然后原地重试。

可以改成下面这样：

```python
class EditError(ValueError):
    pass


def apply_edit(src, old, new):
    if not old:
        raise EditError("old_string 不能为空")
    matches = 0
    position = 0
    first_match = -1
    while True:
        position = src.find(old, position)
        if position < 0:
            break
        matches += 1
        if matches == 1:
            first_match = position
        if matches > 1:
            raise EditError("原文至少匹配两处（包含重叠位置），请提供更长的上下文")
        position += 1  # 下一字符起点也要检查，不能漏掉重叠候选
    if matches == 0:
        raise EditError("原文在文件中不存在 —— 请重新读取当前文件并核对目标")
    return src[:first_match] + new + src[first_match + len(old):]
```

注意报错文案本身是功能的一部分 —— 它直接告诉模型**下一步该做什么**。
这和第 4 章那条「工具的错误信息要能指导修复」是同一条规则。

## 五、小结

- **历史小样本只描述那几次 fixture 结果**：不能外推成功率，也不能证明全文上下文导致差异
- **`匹配 1879 次` 强烈暗示空 `old_string`**：`str.count("") == len(text) + 1`；缺少原始响应，结论仍是推断
- **执行器应拒绝空字符串，并区分零次、多次和唯一匹配**
- **解析失败、定位失败、应用失败和验证失败要分别报告**，不能自动把错误输出当成文件内容
- **编辑格式按工具、任务和语言能力选择**；所有候选都要检查差异并按风险验证

可以按错误类型跟踪工具调用失败、定位失败、应用失败和验证失败。但这些指标受任务、工具和模型分布影响；只有固定数据集、明确判分规则并重复运行后，才适合比较版本或判断趋势。
