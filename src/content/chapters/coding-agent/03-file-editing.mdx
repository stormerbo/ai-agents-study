搜索解决「改哪里」，这一节解决「怎么把改动真的写进去」。

这件事看起来是纯工程细节，但它是 coding agent 失败率最高的环节之一。原因很简单：
**模型编辑文件普遍用的是「给出一段原文、给出替换后的内容」这种精确匹配方式，
而精确匹配要求它对文件内容有逐字符准确的记忆。**

我做了三组实测，结果差异非常大（实跑数据，模型 deepseek-flash；脚本与逐条输出见 `verify-output/coding-edit.py` 与 `coding-edit2.py`）。

## 一、第一组：小文件、无重复 —— 8/8 全对

一个 28 行的 Python 文件，8 个编辑任务（改常量、加参数、重命名函数、加字段、改比较符……），
每个任务让模型输出 `old_string` / `new_string`，然后检查两件事：

1. `old_string` 能否在文件里**恰好匹配一次**（0 次或多次都不合格）
2. 替换之后是否是合法 Python

```text
唯一匹配成功：8 / 8 = 100%
替换后语法合法：8 / 8 = 100%
```

**全对。** 如果实验停在这里，结论会是「精确匹配不难」。
但真实仓库不是这样 —— 真实仓库里有大量**几乎一样但不一样**的代码。

## 二、第二组：83 行、8 个近乎相同的 handler

换一个 fixture：一个文件里有 8 个结构几乎相同的 `handle_type_N` 函数，
每个都有 `data = req.get("payload")`、`if data is None:`、`total > LIMIT` 这样的行。
任务变成「改第 5 个 handler 的某一处」。

这里测两种条件：

- **A：给模型文件全文**
- **B：只给文件开头 14 行**（模拟真实 coding agent 分片读文件的方式），并告诉它「后面还有 7 个相似函数」

结果：

```text
条件                    唯一匹配       替换后语法合法
A. 给了文件全文           4/5 = 80%      4/5 = 80%
B. 只给了开头片段         0/5 =  0%      0/5 =  0%
```

**B 组全军覆没，而且失败形态非常清楚：**

```text
#1  匹配 0 次        <- 模型凭记忆编造了原文，那段文字文件里根本不存在
#2  匹配 1879 次     <- old_string 太短太通用，在整个文件里命中近两千处
#3  JSON 解析失败
#4  JSON 解析失败
#5  匹配 0 次
```

「**匹配 1879 次**」这个数字值得停一下。模型给出的 `old_string` 大概是
`    data = req.get("payload")` 这样一行 —— 它在 8 个 handler 里各出现一次，
但模型给的可能带上了不同的缩进或拼接方式，于是变成一个能匹配到文件中大量位置的长串。
**执行器面对这样的结果只有两个选择：全改（灾难）或者拒绝（回到起点）。**

A 组的 80% 也有信息量：**即使给了全文，五次里还是有一次失败**。
失败原因是 JSON 解析不出（模型在 JSON 外面加了说明或代码块围栏）。
这意味着**编辑工具不能假设模型输出一定可解析** —— 必须有重试或降级路径。

### 那 20% 失败长什么样（本次复现，2026-10-12）

上面说 A 组五次里失败一次、原因是 JSON 解析失败。**不看原始输出是设计不出解析器的**，所以我用同样的任务重新跑了一轮（模型 deepseek-flash；任务：给 `handle_type_N` 加一个字段或空值判断）。两次的原文分别是：

```text
第一次：整个对象被包在围栏里（为不破坏本文的代码块，这里把三个反引号记作 [FENCE]）
[FENCE]json
{
  "old_string": "def handle_type_3(data):\n    d = data.get(\"payload\")\n    return {\"type\": 3, \"ok\": d is not None}",
  "new_string": "def handle_type_3(data):\n    d = data.get(\"payload\")\n    return {\"type\": 3, \"ok\": d is not None, \"status\": \"ok\"}"
}
[FENCE]

第二次：连围栏都不是 JSON —— 它换成了「字段名 + 缩进块」，末尾还附了一段解释
old_string:
def handle_type_2(data):
    d = data.get("payload")
    return {"type": 2, "ok": d is not None}

new_string:
def handle_type_2(data):
    if not data:
        return {"type": 2, "ok": False}
    ...

在 `data` 参与取值前先做空值判断：若 `data` 为空，直接返回 ok 为 False 的结果……
```

两次用 `json.loads(raw)` 都直接抛 `json.JSONDecodeError`。**本节那个 20% 就是这么来的**：不是模型「不会改」，是**它不按你要求的格式输出** —— 而执行器如果只会 `json.loads`，就会把这两种都记成「模型改错了」。

### 正确的解析方式：先剥壳，再兜底

```python
import json, re


FENCE = chr(96) * 3          # 三个反引号，写成字符拼装是为了不在正则里出现字面围栏


def parse_edit(raw):
    """从模型输出里取 old_string/new_string —— 容忍围栏与前后解释。"""
    m = re.search(FENCE + r"(?:json)?\s*(\{.*?\})\s*" + FENCE, raw, re.S)  # 1 先剥围栏
    text = m.group(1) if m else raw
    start, end = text.find("{"), text.rfind("}")                  # 2 再取最外层对象
    if start == -1 or end <= start:
        raise ValueError("输出里没有 JSON 对象：%r" % raw[:80])
    return json.loads(text[start:end + 1])
```

注意这里仍然有解析不了的情形：**上面第二次那种「块格式」剥壳也救不了** —— 它压根不是 JSON。所以解析要接一个三段式降级：**先按上面的方式解析 → 失败就原样回问一次（明确要求「只输出 JSON，不要围栏」）→ 再失败就改用整文件重写**。降级不是失败，它是「编辑不是原子的」这句话的直接后果，也是下一节恢复循环的入口。

## 三、从这两组数据能推出的四件事

**一、上下文的分片方式直接决定编辑成功率。** A 与 B 的唯一区别是「给不给全文」，
成功率从 80% 掉到 0%。这不是模型能力问题，是**信息可得性**问题。
所以「一次改动需要读多少上下文」不是可省的优化，而是正确性的前提。

**二、`old_string` 的唯一性是执行器必须检查的约束。**
很多编辑工具的失败都源于「匹配到多处时静默选了第一处」。
正确的做法是**匹配数不等于 1 就拒绝，并把匹配数报给模型**（「你给的原文匹配了 1879 次，
请提供更长的上下文」）。这一句反馈往往一轮就能修好。

**三、编辑不是原子的。** 上面还算的是「语法是否合法」，但那只是最低要求。
真正要判的是「**改完之后行为是否还符合预期**」—— 那需要跑测试，
也就是这一章第 5 节要讲的内容。

**四、失败要有可恢复的路径。** 匹配 0 次时，正确的后续动作不是「再试一次同样的方式」，
而是**改变策略**：重新读文件、给出更长的上下文、或者换用「整文件重写」。
这一点和上一章讲故障恢复时的结论一致 —— 循环里需要跳出机制。

## 四、几种编辑策略的取舍

除了精确匹配替换，还有几种常见策略，各有适用面：

**整文件重写。** 让模型输出完整的新文件。优点是永远不会「匹配不上」；
缺点是**模型必须复现它没改的部分**，长文件上极易引入无关改动，而且 token 成本高。
实用做法是只在文件很短（比如 100 行以内）时用它。

**按行号替换。** 让模型说「把第 42 到 45 行换成……」。优点是省 token；
缺点是**行号会随编辑漂移** —— 同一轮里改了前面一处，后面的行号就全错。
所以它只适合「每轮只改一处、改完立即重算行号」的流程。

**结构化编辑。** 用 AST 做替换（比如「把这个函数体换成 X」），
而不是文本替换。它最稳（不受格式和空白影响），但**要求语言有可用的解析器**，
而且对注释、格式这类非语法内容无能为力。

**精确匹配替换。** 就是本节测的这种方式，也是 Claude Code / Aider 这类工具的主流选择。
它省 token、改动最小、diff 直观；代价就是上面那两条失败模式。

一个务实的组合是：**默认用精确匹配替换，匹配失败时降级到整文件重写**（文件小时），
并把每次降级记录下来 —— 降级率本身就是个有用的健康指标。

### 一个真实的报错：静默改了第一处

我第一次实现这个编辑工具时，`replace` 的逻辑是这样写的：

```python
def apply_edit(src, old, new):
    if old in src:
        return src.replace(old, new, 1)      # 错
    raise ValueError("原文未找到")
```

两处问题，都很典型：

**一、它只检查「存在」，不检查「唯一」。** 当 `old` 在文件里出现 1879 次时，
`replace(..., 1)` 会**静默地改掉第一处**。程序不报错，测试可能还是过的，
但改的位置完全不对。**这是最危险的一类失败：它看起来成功了。**

**二、它把「未找到」和「找到多处」合并成了一种错误。** 两者的修法完全不同 ——
前者要重新读文件（说明模型没看到原文），后者要提示模型给更长的上下文。
合并处理会让 agent 收到一条无用的报错，然后原地重试。

改成下面这样之后，上面 B 组那种情况就能被准确诊断：

```python
def apply_edit(src, old, new):
    n = src.count(old)
    if n == 0:
        raise EditError("原文在文件中不存在 —— 你是不是凭记忆写的？请重新读文件")
    if n > 1:
        raise EditError("原文匹配了 %d 处，请提供更长的上下文使其唯一" % n)
    return src.replace(old, new, 1)
```

注意报错文案本身是功能的一部分 —— 它直接告诉模型**下一步该做什么**。
这和第 4 章那条「工具的错误信息要能指导修复」是同一条规则。

## 五、小结

- **小文件无重复时精确匹配几乎不会错**（实测 8/8）
- **同样的任务，只给片段时成功率掉到 0%** —— 从 80% 到 0，差别只在信息可得性
- **`匹配 1879 次` 是真实会发生的**：通用片段在重复代码里命中大量位置
- **执行器必须检查「匹配数恰为 1」**，不满足就拒绝并把实际匹配数告诉模型
- **输出格式不可解析是稳定的失败源**（给全文时仍有 20%），必须有重试与降级
- **编辑策略要按文件大小和语言选**：精确替换为主，整文件重写兜底，行号法只在单处改动时用

还有一个指标建议从一开始就记下来：**编辑失败率**（匹配 0 次 + 匹配多次 + 解析失败的占比）。
它是 coding agent 最灵敏的健康指标之一 —— 一旦它开始上升，通常意味着
**上下文供给出了问题**（读的窗口太小、文件没刷新、或者模型在凭记忆改写），
而这些原因在任务成功率上要过很久才看得出来 —— 那时你已经很难回头定位是哪一次改动引入的了，只能从头重跑一遍评测，而那次评测本身也要花掉不少时间和额度，还未必能复现出来。
