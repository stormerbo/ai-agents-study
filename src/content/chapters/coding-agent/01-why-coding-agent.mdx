前面十四章里，coding agent 被反复提到，但没有单独讲过。这一章补上。

它值得单独一章，不是因为「写代码」这件事天然特殊，而是因为**许多代码任务恰好有可执行的项目检查**。在适配的仓库里，测试、编译和类型检查可以给出低歧义、可重复的部分信号；它们回答的是“当前候选是否满足这些检查”，不能单独回答“需求是否理解正确”或“检查是否覆盖真实风险”。这不是 coding agent 独有的优势：其他 agent 也可能用状态检查、确定性 grader、LLM grader 或人工评审。关键是任务目标能否被可靠地观测和判定。[Anthropic 的 agent 评测指南](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)也建议按任务选择 grader，并指出 coding eval 常用测试，同时仍可按需补充代码质量 rubric。

## 一、它到底特殊在哪

不同 agent 的目标可观测性不同：研究报告的覆盖与论证质量可能需要 rubric 或专家复核；客服任务可以检查工单/退款等最终状态，也可以评估沟通质量；GUI agent 可以检查应用状态。coding agent 的特点不是“别的 agent 没有机器反馈”，而是项目往往已经提供可直接运行的测试、构建或静态检查，**其中一部分约束可以自动判定**。这些检查的有效性取决于规格、断言和执行环境。

代码写完，跑一下就能获得一组关于当前实现的验证信号：

```text
编译 / 语法检查   ->  当前代码能否通过语法与构建检查
单元测试         ->  当前代码能否满足已编码的断言
类型检查         ->  当前代码能否满足静态类型约束
```

这让 coding agent 在部分任务上有几个实用优势，但并不是其它 agent 完全没有机器反馈：

**一、部分反馈可以直接复用。** 对已编码的约束，可以运行测试、构建或类型检查；其他任务也可能有数据库状态断言、grader 或人工评估（第 15 章会讲 LLM-as-judge）。反馈成本和时延取决于检查套件、运行环境及外部依赖，并不总是低或即时。

**二、可以把检查放进有上限的循环。** 当运行器可靠、测试可重复、改动范围受控时，「改一版、跑一遍、再改」可以自动迭代。测试可能 flaky、依赖外部服务或未覆盖需求，所以反馈不总是二值且可复现；循环还要区分测试失败、runner/API 错误和未验证状态，并限制预算、权限与次数。

**先把「agent 循环」这个词说清**，因为它是整章的地基：本书在这里用它指一个常见执行结构 —— 模型提出动作 → 系统执行 → 把执行结果交回模型 → 模型据此决定下一步，直到满足停止条件。具体系统可能合并步骤、跳过额外模型调用，或因错误提前结束；“每个任务必然多次调用”不是定义的一部分。第 11 章从零写过一个循环；本章的恢复节还会给出一个有界控制器。

**三、可以将已编码的约束沉淀为回归检查。** 这能给后续改动提供可重复证据，但一次构建通过或一次测试通过都不能自动成为训练正例或完整能力评估。评测任务、grader、执行环境和真实目标必须对齐；否则分数可能只反映检查器的缺口。

一个最小反例：产品需求是“导出当前用户有权访问的订单”，测试只断言返回结构里有 `orders` 数组。实现若忽略租户过滤，构建与测试仍可全绿，却泄露其他用户订单。此时绿色只证明检查集漏掉了权限要求，不能证明实现正确。

**实跑状态：** 下面的 Python fixture 在本地 Python 3 标准库运行，5 条断言通过；它演示检查器的覆盖差异，不调用模型、不连接数据库，也不验证生产授权。

```python
def export_order_ids(rows, user_id, grants):
    allowed = grants.get(user_id, set())
    return {row["id"] for row in rows if row["id"] in allowed}


rows = [
    {"id": "o-1", "tenant": "A"},
    {"id": "o-2", "tenant": "B"},
]
grants = {"alice": {"o-1"}, "bob": {"o-2"}}

# 过弱的断言只检查响应形状，泄漏实现也能通过。
leaky_result = {"orders": [row["id"] for row in rows]}
assert isinstance(leaky_result.get("orders"), list)

# 更有判别力的断言检查用户可见集合、空授权和未知用户。
assert export_order_ids(rows, "alice", grants) == {"o-1"}
assert export_order_ids(rows, "bob", grants) == {"o-2"}
assert export_order_ids(rows, "guest", grants) == set()
assert "o-2" not in export_order_ids(rows, "alice", grants)
```

这组检查能区分“返回了数组”和“返回了当前用户获准看到的 ID”，却仍只验证一个内存函数的行为。它没有检查 `grants` 是否来自可信身份、查询是否在数据库层隔离租户、权限变更是否即时生效，也没覆盖序列化或分页。把测试补到有判别力，不代表规格已经完整；还需要确认授权来源与线上执行路径。

把一个需求变成机器检查，至少要经历“需求拆分 → 可观察结果 → 判定规则 → 可信执行”四步。需求拆分时，先区分用户可见行为、权限条件、错误处理和副作用；可观察结果可能是返回值、数据库变化、事件记录或外部请求；判定规则需要写出允许集合、拒绝情形和边界值；可信执行则要确保 runner 调用的是本次候选代码，并把依赖、环境变量和退出状态记录下来。少掉任一步，绿灯都可能只说明一个局部假设成立。后端工程师熟悉测试与 CI，但 agent 场景需要额外问：这轮模型看到的失败是不是当前工作树的结果？检查器是否可能执行仓库自带脚本？权限和网络是否被约束？失败后留下的日志是否安全、可重放？把这些问题作为验收条件，才不会把“机器能运行测试”误当成“机器能判断需求”。

## 二、但这个信号有一个前提，很容易被忽略

「有测试就能自动判定」的前提是检查器正确、相关约束被覆盖、runner 成功执行，而且测试结果与产品需求一致。2026-10-10 的历史恢复摘要原来被用来证明“一次失败后会改对”和“截断任务连续五轮打转”；复查发现 `truncate` 的一条固定测试有语法错误，完整测试从第一轮已放进提示，且没有逐次响应。现有证据不足以归因模型成功/失败，也不足以估计 retry 次数。详见 [验证与恢复：报错之后该给它什么](./error-recovery) 的审计说明。

有界循环的结构是：基线验证 → 分类结果 → 最多 N 次候选修改 → 每个候选再次验证 → 返回明确的 passed / failed / stalled / incomplete 状态。最后一个候选必须经过验证；如果命中次数上限，返回未通过状态，不要把未验证代码交付成成功。完整可运行的控制器和 fake proposer 见下一节。真实系统还要隔离执行仓库代码，约束允许修改的路径、工具权限、成本和时长。

## 三、代码不只是产物，也是工具

另一个容易被忽略的维度：在 agent 里，**代码经常不是最终产物，而是手段**。

在需求适合被表达、执行和检查时，代码可以充当中间工具；下面是几种形态，不是“写代码总比直接生成结果可靠”的通用结论：

**代码作为计算工具。** 对能明确写成运算步骤的任务（比如按已给定公式计算分期金额），可以让程序执行算术，减少手算误差；但仍要检查公式、输入和边界条件。它不是把所有推理都变确定，也不证明业务前提正确。

**代码作为业务规则的执行载体。** 如果规则必须在服务端确定性地拦截副作用，可以把它实现为函数并用边界样例测试（例如金额阈值与订单状态组合）。自然语言仍然是需求与评审依据，也可以转化为评测用例；代码测试验证实现是否满足这些用例，不会自动证明规则本身完整或正确。

**代码作为系统适配器。** 当输入/输出契约明确且转换会重复执行时，可以用转换代码固定映射并用样例测试；一次性、含糊或需要判断语义的内容，仍要先解决规格与来源问题。

**代码作为 UI 描述。** 如果产物需要交互、继续编辑或与现有组件集成，可以让模型生成 HTML/图表配置；若目标是固定插图或自由视觉表达，图像可能更合适。可编辑性、复用性与体积取决于具体实现和交付场景。

这些例子共同说明：**在适合程序表达的任务里，模型输出可以成为可执行、可测试或可继续编辑的中间产物。** 这是一种工程选择，不意味着所有 coding agent 都更可靠，也不意味着其他 agent 无法获得机器可检查的结果。

## 四、后端工程师在这里的优势，和三个会失效的直觉

这一章对目标读者尤其划算 —— 你已经会写代码，而 coding agent 的核心动作
（读代码、定位、改、跑测试、提交）全是你熟悉的事。

但有三个直觉会失效：

**直觉一：「代码写对了就行」。** 可验证性是正确性判断的证据来源之一，不能替代对需求和实现的理解。
一段代码即使通过现有检查，也可能遗漏业务约束或安全边界；如果核心行为完全无法观察，交给 agent 迭代的风险会更难控制。
所以要同时问：预期行为是什么？哪些检查能证明它？还有哪些部分仍需要人工或其它证据？

**直觉二：「小改动一定简单」。** 工作量还取决于仓库上下文、依赖关系和验收条件。历史恢复样本里的轮数不可复核，不能用来证明小 bug 普遍需要几轮。
agent 面对的困难常包括**能否取得足够且准确的上下文**，但也可能是规格不完整、测试不可靠或环境无法运行。

（这里把模型可见的 **repo working model** 当作教学简称：它是由当前提示、检索到的文件、工具返回和此前对话等上下文共同形成的工作依据，不是仓库的完整镜像，也不保证每轮都包含最新状态。上下文缺失、陈旧或被摘要压缩时，模型可能对文件、调用关系或改动状态判断错误。）
一个 5 行的改动，如果模型没有取得目标文件的相关片段，可能连精确的 `old_string` 都无法构造（下一节会看到一个局部历史样本及其限制）。

**直觉三：「失败了看报错就行」。** 报错告诉 agent「哪里不对」，但经常不告诉它「为什么」。
前述历史恢复样本无法证明模型在五轮内一直沿同一个方向修改；它的测试夹具有语法错误，逐次响应也未保存。可复用的设计问题是：**失败后提供哪些安全、可定位的反馈，如何判断再次尝试值得，以及如何确认最终候选通过验证。**

## 五、这一章要回答的问题

按一次改动的顺序，这一章回答四个问题：

1. **怎么找到要改的地方**（搜索策略：全文、grep、还是符号索引？）
2. **怎么把改动写进去**（编辑协议、目标定位与失败模式）
3. **改完怎么验证、失败了怎么办**（恢复循环与它的边界）
4. **能执行代码意味着什么**（安全边界）

## 六、小结

- **coding agent 的优势是常有可程序化验证信号**：只覆盖已编码的约束，不代表需求与测试完整
- **但「检查通过」不等于「需求已正确实现」** —— 规格、断言和执行器都可能不完整
- **修复循环必须验证最后一个候选并显式报告未完成**，历史轮数摘要不能替代可靠对照实验
- **代码经常是手段而不是产物**：思考工具、规则载体、系统适配器、生成式 UI
- **验证信号是代理指标，不是正确性的替代品** —— 权限、安全和需求覆盖仍需独立判据
