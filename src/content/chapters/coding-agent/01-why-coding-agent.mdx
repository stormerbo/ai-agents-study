前面十四章里，coding agent 被反复提到，但没有单独讲过。这一章补上。

它值得单独一章，不是因为「写代码」这件事特殊，而是因为**它是唯一一类自带验证信号的 agent**。

## 一、它到底特殊在哪

大多数 agent 的成败要靠外部判断：客服 agent 有没有解决问题要问用户，
研究 agent 的报告好不好要人来读。而 coding agent 面对的是一件罕见的事 ——
**对错可以自动判定。**

代码写完，跑一下就知道对不对：

```text
编译 / 语法检查   ->  通过或失败，二值，无歧义
单元测试         ->  通过或失败，二值，无歧义
类型检查         ->  通过或失败，二值，无歧义
```

这个性质带来三个其他 agent 没有的东西：

**一、反馈便宜且即时。** 不需要人来点评，也不需要另一个模型来打分（第 15 章讲的
LLM-as-judge 在这里几乎用不上 —— 有更硬的信号）。

**二、可以自动重试。** 因为反馈是二值的、可复现的，所以「改一版、跑一遍、再改」
这个循环可以完全自动化。这就是第 11 章那个 **agent 循环**的最自然形态。

**先把「agent 循环」这个词说清**，因为它是整章的地基：它指的是这个结构 —— 模型输出一个动作 → 系统执行它 → 把真实结果作为新消息喂回模型 → 模型再决定下一步，直到满足停止条件。它和普通「一问一答」的区别是：**一次任务里模型被调用多次，每次都看得到上一次的真实结果。** 第 11 章从零写过它；本节末尾会给一个二十行、能跑的最小版本。

**三、可以自动构造训练/评测数据。** 每个能编译通过的提交，都是一个正样本。
这也是为什么 coding 是 agent 能力最先成熟的领域 —— 它有免费的监督信号。

## 二、但这个信号有一个前提，很容易被忽略

「有测试就能自动判定」这句话里藏着一个前提：**测试本身是对的，而且覆盖了你改的那部分。**

我实测过一轮故障恢复：给 5 个有 bug 的函数和一个能真实运行的测试，
让模型「看报错 → 改 → 再跑」，最多 5 轮。

```text
均分        修好   用 2 轮
去重保序     修好   用 2 轮
解析时长     修好   用 2 轮
安全除法     修好   用 2 轮
截断文本     未修好  用 5 轮

成功率 4/5 = 80%     平均轮数 2.0
```

（实跑数据，模型 deepseek-flash；脚本与原始输出见 `verify-output/coding-recover.py`。下面第 4 节会再引用这组数。）

两件事值得看：

**第一，修好的四个都恰好用了 2 轮。** 没有一个是 1 轮就对的。
这不是巧合 —— 模型第一次只能看到报错文字，它得先理解「测试期望什么」，
才发现自己第一次改的方向不对。**所以 coding agent 必须有循环，一次成型是不现实的。**
这也解释了为什么这一章不能只讲「怎么让模型写出代码」——
真正决定成败的是**改完之后怎么验证、验证失败之后怎么重来**。

**第二，那个「5 轮都没修好」的案例。** 测试是对的、报错是清晰的，
但模型五轮都没改对。这说明**有验证信号不等于一定能修好** ——
信号只告诉你「错了」，不告诉你「怎么才对」。
把「能自动判定」误读成「能自动解决」，是这一章最容易犯的错。

### 那个 5 轮没修好的案例，值得展开

出问题的函数是「按长度截断字符串」：

```python
def truncate(s, n):
    return s[:n]
```

测试要求两件事：

```python
assert truncate("hello world", 8) == "hello..."
assert truncate("hi", 8) == "hi"
```

也就是说：**超长时要截断并加省略号，而且省略号占的长度要算在 n 里**，
不超长时原样返回。

模型前几轮的做法是「先按 n 切，再补省略号」，于是 `truncate("hello world", 8)`
得到 `hello wo...`（11 个字符），而不是 `hello...`（8 个字符）。
每次报错都很清楚：

```text
AssertionError: assert truncate("hello world", 8) == "hello..."
```

而它接下来几轮的修改都在这条路上微调（改切片位置、改省略号长度），
**始终没有转向「先减去省略号宽度，再切」这个正确方向**。

这个案例说明三件事：

**一、清晰的报错不保证收敛。** 报错只指出「结果不对」，
而「不对在哪一步」需要模型自己从期望值反推。

**二、失败会强化错误方向。** 模型倾向于在已有方案上做局部调整，
而不是推翻重来。这在人类身上也一样（沉没成本），但 agent 表现得更明显，
因为它每一轮看到的都是「上一版代码 + 报错」，容易在同一个局部最优里打转。

**三、这正是需要工程手段介入的地方。** 如果循环里加一条规则 ——
比如「同一个断言连续失败 2 次就换一个完全不同的实现思路」——
它很可能就跳出来了。**这类规则是 agent 系统的设计内容，不是提示词的润色。**

我在测这个案例时，第 5 轮之后它给出的仍然是 `hello wo...` 一类的答案。
所以这一节留下的结论不是「模型不行」，而是：
**当验证信号反复说「错」而模型反复改同一处时，你需要的是一个跳出机制，而不是更多轮次。**

### 这个循环最小长什么样

前面讲的都是「必须有循环」，下面给一个二十行的正例 —— 它能跑，而且能直接观察到「喂回去的东西决定下一轮」。

```python
def minimal_fix_loop(code, run_tests, ask_model, max_turns=5):
    """最小修复循环：跑测试 → 把原始报错拼进下一轮 → 再跑。

    run_tests(code) -> (ok: bool, err: str)   你接自己的测试
    ask_model(code, prompt) -> str            你接自己的模型调用
    它刻意不含跳出机制/预算/轨迹 —— 那些在第 4、5 节补。
    """
    for turn in range(1, max_turns + 1):
        ok, err = run_tests(code)
        if ok:
            return code, turn, "通过"
        # 关键只有这一行：喂回去的是**原始报错**，不是「测试失败了」这种转述
        prompt = "下面是这次测试的完整报错，请修好代码，只输出新代码：\n\n" + err
        code = ask_model(code, prompt)
    return code, max_turns, "未收敛"
```

三个位置就是这一章后面要展开的全部：`run_tests` 对应第 4 节的验证分层、`ask_model` 里的那段提示对应第 4 节的「报错之后给它什么」、`max_turns` 之外的跳出机制对应第 4 节的 `SAME_FAILURE_LIMIT`。**先有一个能跑的循环，再往里装机制 —— 顺序反了，机制就会变成补丁。**

## 三、代码不只是产物，也是工具

另一个容易被忽略的维度：在 agent 里，**代码经常不是最终产物，而是手段**。

几种常见形态：

**代码作为思考工具。** 一个需要精确计算的任务（比如算一个复杂的分期方案），
让模型「写一段代码然后执行」通常比让它「直接心算」可靠得多。
这不是模型变聪明了，而是**把不确定的推理换成了确定的执行**。

**代码作为业务规则的载体。** 与其在提示词里用自然语言描述一条规则
（「金额超过 100 且状态为 paid 时才退款」），不如写成一段可测试的函数。
区别在于：后者**可以被单元测试覆盖**，前者只能靠人读。

**代码作为系统适配器。** 外部 API 的格式千奇百怪，
让模型写一小段转换代码比让它「理解格式后直接输出」更稳。

**代码作为生成式 UI。** 让模型生成一段 HTML/图表配置，而不是生成一张图片 ——
前者可编辑、可复用、体积小。

这四种形态有一个共同点：**它们把「模型的一次性输出」变成了「可复用的资产」。**
这是 coding agent 相对其他形态最实质的优势。

## 四、后端工程师在这里的优势，和三个会失效的直觉

这一章对目标读者尤其划算 —— 你已经会写代码，而 coding agent 的核心动作
（读代码、定位、改、跑测试、提交）全是你熟悉的事。

但有三个直觉会失效：

**直觉一：「代码写对了就行」。** 在 agent 里，**可验证性比正确性更重要**。
一段正确的代码如果没法被自动验证，它就不适合交给 agent 维护。
所以你写代码时要多想一想：这个改动怎么被自动测到？

**直觉二：「小改动很简单」。** 上面那组数据里，最简单的 bug 也要 2 轮。
agent 面对的困难不在改动本身的复杂度，而在**它必须先从上下文里重建出足够准确的世界图景**。

（**世界图景**指模型对「这段代码现在长什么样」的内部表示：哪些文件存在、函数定义在哪一行、谁调用了谁、当前这版和上一版差在哪。它不来自模型的长期记忆，而是**每一轮从你喂的上下文里现拼出来的** —— 喂得不全，它拼出来的图景就是错的，后面所有判断都建立在那张错图上。）
一个 5 行的改动，如果模型不知道文件长什么样，它连 `old_string` 都拼不出来（下一节会看到数据）。

**直觉三：「失败了看报错就行」。** 报错告诉 agent「哪里不对」，但经常不告诉它「为什么」。
上面那个 5 轮没修好的例子就是：每次报错都清晰，但模型一直在同一个方向上打转。
**真正需要设计的是「失败之后给它什么额外信息」**，而不是「失败之后让它再试一次」。

## 五、这一章要回答的问题

按一次改动的顺序，这一章回答四个问题：

1. **怎么找到要改的地方**（搜索策略：全文、grep、还是符号索引？）
2. **怎么把改动写进去**（精确匹配替换的成功率与失败模式）
3. **改完怎么验证、失败了怎么办**（恢复循环与它的边界）
4. **能执行代码意味着什么**（安全边界）

## 六、小结

- **coding agent 的核心优势是自带验证信号**：编译、测试、类型检查都是二值的
- **但「能自动判定」不等于「能自动解决」** —— 实测里有一个案例 5 轮都没修好
- **修好的四个都用了 2 轮**，说明循环是必需的，一次成型不现实
- **代码经常是手段而不是产物**：思考工具、规则载体、系统适配器、生成式 UI
- **可验证性比正确性更重要** —— 没法自动验证的代码不适合交给 agent 维护
