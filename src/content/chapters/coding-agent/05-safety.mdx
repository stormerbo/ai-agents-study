这一章前面四节都在讲「怎么让它改对」。这一节讲反面：**它能造成的破坏有多大。**

很多人对 coding agent 的安全直觉停留在「它会改我的文件」。这低估了一个量级 ——
**它还会执行代码**，而执行代码这件事的性质完全不同。

## 一、实测：一条完全无害的命令，执行了任意代码

我建了一个最普通的 Python 仓库，只有两个文件：

```text
conftest.py      # 内容是 pathlib.Path("PWNED_MARKER").write_text("conftest.py 被执行了")
test_demo.py     # 内容是一个通过的空测试
```

然后运行一条任何白名单都会放行的命令：**`pytest`**。

```text
$ python3 -m pytest -q
1 passed in 0.01s

$ ls
PWNED_MARKER   __pycache__   conftest.py   test_demo.py
```

**`PWNED_MARKER` 出现了。** 那个文件是 `conftest.py` 里的代码写出来的 ——
而整个过程没有任何异常，测试全绿，命令正常退出。

这个实验的结论很硬：

> **按命令名做白名单，挡不住任何东西。**

因为 `pytest` 会加载仓库里的 `conftest.py`（这是它的正常机制），
`npm test` 会执行 `package.json` 里的 `scripts`，`make` 会执行 `Makefile`，
`cargo test` 会编译并运行 `build.rs`。**这些命令的语义就是「运行这个仓库里的代码」。**

## 二、风险面有三个方向，不只是「删库」

一提到 agent 执行命令，多数人想到的是 `rm -rf /` 这类破坏。
但那只是三个方向里最容易防的一个。

**方向一：破坏。** 删文件、改系统配置、覆盖数据。这个方向最显眼，
所以最容易被规则拦住（比如拒绝含 `rm -rf` 的命令）。
**但正因为显眼，它也最不危险** —— 真正的问题是下面两个。

**方向二：外泄。** agent 能读文件，所以它能读 `.env`、SSH 私钥、云凭据。
而它（或者它运行的代码）还能发起网络请求。**这两件事合起来就是数据外泄。**
注意第 17 章那个实测：7 次提示注入全部**没有**复现 ——
说明让模型「主动泄露」很难；但本节这个实验说明的是另一条路径：
**不需要说服模型，仓库里的一段代码就能做到。**
这两件事的危险性完全不同，因为后者不依赖模型的可欺骗性。

**方向三：供应链。** agent 会安装依赖。`pip install` 一个拼错的包名（typosquatting）、
或者装一个已经被投毒的版本，就把风险带进了你的构建环境。
这一条在人工开发时也存在，但 agent 装包的频率高得多，而且**它不会犹豫**。

## 三、防护的粒度：四条边界

既然命令白名单无效，那有效的做法是什么？答案是**按隔离级别设边界**：

**一、进程边界。** agent 执行命令时，用一个受限的进程（容器、`bubblewrap`、
或者至少一个专用的低权限用户）。它保护的是「命令能碰到宿主机的什么」。
第 16 章讲的分级隔离在这里直接适用 —— 关键是**默认不给宿主机的文件系统**。

**二、文件系统边界。** 只挂载需要改的目录，其余只读或不挂载。
特别地：**凭据目录不进容器**（`~/.ssh`、`~/.aws`、`.env`）。
这是防「外泄」最有效的一层，因为它让可读的东西里根本没有秘密。

**三、网络边界。** 默认不许出网，需要时按域名白名单放行。
这一层专治「外泄」和「供应链」。代价是有些工具（装包、拉依赖）会不 work，
所以通常是「构建阶段允许、运行阶段禁止」。

**四、审批边界。** 对不可逆的动作（删除、推送、发布、花钱）要求人工确认。
第 19 章讲过按可逆性审批的实测：**按可逆性审批 2 次打断、0 漏网；按危险程度审批 1 次打断、1 漏网。**
这个结论在 coding agent 上尤其适用，因为「改文件」可逆、「跑迁移脚本」不可逆，
两者的危险程度可能看起来差不多。

**这四层是叠加的，不是四选一。** 单独任何一层都能被绕过，
合起来才构成有效的边界。这也解释了为什么「给个提示词说不要删文件」这种做法的价值接近零。

## 四、代码：一个按隔离级别配置的执行器

```python
from dataclasses import dataclass, field


@dataclass
class Sandbox:
    """按隔离级别配置 —— 注意没有「允许哪些命令」这个字段。"""
    writable_dirs: list = field(default_factory=list)
    readable_dirs: list = field(default_factory=list)
    allow_network: bool = False
    allow_network_hosts: list = field(default_factory=list)
    max_seconds: int = 120
    max_output_bytes: int = 200_000
    env_denylist: list = field(default_factory=lambda: [
        "SSH_AUTH_SOCK", "AWS_*", "OPENAI_API_KEY", "ANTHROPIC_AUTH_TOKEN",
    ])


def build_policy(level):
    """level 决定边界，而不是决定「允许哪些命令」。"""
    if level == "readonly":
        return Sandbox(readable_dirs=["."])
    if level == "workspace":
        return Sandbox(writable_dirs=["."], readable_dirs=["."])
    if level == "network":
        return Sandbox(writable_dirs=["."], readable_dirs=["."],
                       allow_network=True, allow_network_hosts=["pypi.org", "registry.npmjs.org"])
    raise ValueError("未知隔离级别: %s" % level)
```

这份配置里最值得注意的是**没有的东西**：没有 `allowed_commands`。
这不是省略，而是设计结论 —— **命令名不是安全边界**，
上面那个 `pytest` 实验已经证明了这一点。

`env_denylist` 那一项也值得单独说：**环境变量是最容易被忽略的外泄通道。**
一个 `print(os.environ)` 就能把注入的 API Key 打出来，
而它不需要任何特殊权限。所以隔离环境里要**显式清掉**这些变量，
而不是假设它们不会被读。

### 一个真实的报错

我第一次写这个执行器时，是用 `subprocess.run(cmd, shell=True, cwd=workdir)`，
并认为「工作目录已经限制住了，不会伤到别处」。

这个想法有两个漏洞：

- **`cwd` 不是边界** —— 命令里一句 `cd /` 或者一个绝对路径就能出去
- **`shell=True` 让注入更容易** —— 模型生成的参数里一个分号就能串第二条命令

正确做法是**用容器的挂载做边界**（不挂载的目录它根本看不到），
并且**避免 `shell=True`**（用参数数组调用）。

这里有一个通用原则值得记住：**凡是「用约定限制能力」的做法都要重新检视，
因为它默认了执行方会遵守约定 —— 而 agent 执行的是它自己的代码，不受你的约定约束。**

## 五、一个实用的分级建议

把四层边界组合成三档，覆盖绝大多数场景：

| 档位 | 文件系统 | 网络 | 审批 | 适用 |
| --- | --- | --- | --- | --- |
| **只读** | 全部只读 | 禁止 | 无 | 让它先「读代码、给方案」，不改任何东西 |
| **工作区** | 仅工作区可写 | 禁止 | 不可逆动作 | 日常改代码、跑测试 |
| **联网** | 仅工作区可写 | 按域名放行 | 不可逆动作 | 装依赖、拉包 |

两个实践要点：

**一、默认从只读开始。** 大多数任务的前半步其实是「理解代码」而不是「改代码」。
让它在只读模式下先给出方案，你确认之后再升到工作区 ——
这一步同时解决了两件事：安全，以及**你有了一个复核的机会**。

**二、联网档要短时开启。** 装依赖通常只占任务的一小段。
如果整个任务都开着网络，那前面两层防护的意义会被大幅削弱。
实用做法是**按需临时提权、用完立即降级**，而不是任务一开始就选最高档。

还有一条和成本有关的观察：**隔离程度越高，agent 一次能完成的任务越短**
（因为很多便利手段被禁用了）。所以这不是「越严越好」的单选题，
而是一个按任务风险调整的滑档。**误删一个文件可恢复，泄露一个凭据不可逆** ——
滑档的依据应该是这个，而不是「方便不方便」。

## 六、小结

- **`pytest` 会执行仓库里的 `conftest.py`** —— 实测写出了标记文件，测试还全绿
- **按命令名做白名单无效**：`npm test`、`make`、`cargo test` 都是「运行仓库里的代码」
- **风险有三个方向**：破坏（最显眼）、外泄（最危险）、供应链（最频繁）
- **防护是四层叠加**：进程、文件系统、网络、审批 —— 不是四选一
- **隔离环境要显式清空凭据类环境变量**，一个 `print(os.environ)` 就能外泄
- **「用约定限制能力」的做法都要重新检视** —— agent 执行的是它自己的代码，不受约定约束
