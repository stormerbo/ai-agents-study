这一章前面四节都在讲「怎么让它改对」。这一节讲反面：**它能造成的破坏有多大。**

很多人对 coding agent 的安全直觉停留在「它会改我的文件」。这低估了一个量级 ——
**它还会执行代码**，而执行代码这件事的性质完全不同。

## 一、历史实验：一条看似普通的测试命令触发了仓库代码

历史实验记录描述了一个最小 Python 仓库，只有两个文件：

```text
conftest.py      # 内容是 pathlib.Path("PWNED_MARKER").write_text("conftest.py 被执行了")
test_demo.py     # 内容是一个通过的空测试
```

然后运行通常会被简单命令白名单放行的 **`pytest`**。

```text
$ python3 -m pytest -q
1 passed in 0.01s

$ ls
PWNED_MARKER   __pycache__   conftest.py   test_demo.py
```

**本轮隔离复核**：Python 3.14.7、pytest 8.4.2。在自动清理的临时目录中只放入上述两个文件，运行 `python -m pytest -q`；结果为 `1 passed`，且 `PWNED_MARKER` 内容为 `conftest.py was imported`。这复现了该版本下测试收集会导入 `conftest.py` 的机制；它不是对 2026-10-10 历史运行环境、原始日志或历史完整仓库的重放。

**历史日志报告 `PWNED_MARKER` 出现，且测试通过。** 若该记录可复现，它说明 conftest 中的代码在测试收集时执行；当前证据不能独立确认当时环境与原始输出。

这次观察说明：**对会加载仓库配置/插件/测试模块的命令，命令名白名单无法约束仓库代码的副作用。** 它不是对所有白名单设计的证明；如果白名单绑定的是可信的、不可被仓库内容替换的固定程序，且参数与环境也受约束，它仍可缩小入口，但不能替代隔离。

> **对会加载仓库配置、测试或构建代码的命令，仅按命令名做白名单不足以约束其副作用；边界必须由执行环境实施。**

因为 `pytest` 会加载测试路径上的 `conftest.py`，`npm test` 会执行包脚本，
而 Cargo 会在构建包时编译并运行 `build.rs`。具体行为受配置、版本与运行路径影响，
所以应把这类命令视为可能执行仓库或依赖代码的入口，而不是把每条命令都概括成无条件执行仓库代码。
官方文档分别描述了 [pytest 插件加载](https://docs.pytest.org/en/stable/how-to/writing_plugins.html)、
[npm lifecycle scripts](https://docs.npmjs.com/cli/v11/using-npm/scripts/)
和 [Cargo build scripts](https://doc.rust-lang.org/cargo/reference/build-scripts.html)。

## 二、风险面：先从破坏、外泄和供应链检查

常见威胁建模会先检查破坏、数据外泄和供应链风险；这只是便于检查的分类，不是穷尽列表，也不表示相对频率或严重性排序。

**方向一：破坏。** 删文件、改系统配置、覆盖数据。有些显眼的模式能被简单规则拦截（比如拒绝某些删除命令），但这不意味着其它风险必然更常见或更严重。

**方向二：外泄。** 如果 agent 或其子进程能读取 `.env`、SSH 私钥、云凭据，又能发起网络请求，就存在数据外传路径；具体能否触达取决于进程权限、挂载和网络策略。
注意第 17 章那个实测：7 次提示注入全部**没有**复现 ——
但这只能说明该组提示与配置下没有观察到触发，不能推出攻击普遍很难；本节的安全模型还包括另一条路径：
**如果运行环境允许读取敏感文件并访问网络，仓库代码可以绕过模型的“主动泄露”决策，直接尝试外传。**
后者的触发路径不同：只要仓库代码获得相应文件和网络权限，就不需要先说服模型。

**方向三：供应链。** coding agent 可能在任务中请求或执行依赖安装；是否能安装取决于工具权限和环境策略。攻击面有两种：一种是 **typosquatting（拼写抢注）** —— 攻击者注册一个和常用包只差一两个字符的包名（例如 `reqeusts` 对 `requests`），等你把 `pip install` 打错字时把它装进来；包一旦被安装，安装脚本就能执行任意代码。另一种是装到一个已经被投毒的正常版本。
这一条在人工开发时也存在。对 agent 的控制要落在可审计的依赖变更流程上：锁定版本与哈希、校验来源、尽量使用可信构建产物，并在执行安装/构建脚本时沿用隔离策略。固定镜像只能约束获取位置，不能证明镜像内容安全；人工确认也需要审查包名、版本、来源和变更范围。[pip 官方安全安装文档](https://pip.pypa.io/en/stable/topics/secure-installs/)明确提醒默认安装过程会运行分发包中的任意代码，并介绍哈希校验与拒绝源码分发包等加固方式。

## 三、防护的粒度：四条边界

当命令名白名单不足以约束仓库代码副作用时，应由**实际执行环境实施并验证边界**：

**一、进程边界。** agent 执行不可信命令时，使用受限容器或经评估的 OS sandbox，并限制权限、资源、系统调用与宿主机接口。专用低权限用户能减少权限，但单独使用不等同于文件系统或网络隔离。

容器的隔离效果取决于挂载、能力、命名空间、守护进程与内核边界。[Docker 官方安全文档](https://docs.docker.com/engine/security/)也提醒：挂载宿主目录会把相应访问权交给容器，默认配置可能不足以形成完整隔离。因此“用了容器”不是安全结论；要审查具体配置，并避免挂载 Docker socket、宿主凭据或不必要设备。

**二、文件系统边界。** 只挂载需要改的目录，其余只读或不挂载。
特别地：**凭据目录不进容器**（`~/.ssh`、`~/.aws`、`.env`）。
不给任务不需要的凭据，是减少这类暴露面的直接办法；它仍需和网络控制、身份授权及其它密钥存储边界配合。

**三、网络边界。** 默认禁网；确需访问时通过受控代理实施目的地与协议策略，并评估 DNS 解析、重定向、IP 直连、代理绕过和请求内容。单纯域名 allowlist 不能证明请求安全，也不能阻止向允许站点上传数据。区分依赖获取阶段与执行阶段有帮助，但如果安装/构建脚本执行时仍有网络，它们仍可外传数据。

**四、审批边界。** 对外部副作用（发布、发送、删除远端数据、花钱、权限变更）设计人工审批或独立策略检查。审批应绑定具体主体、动作、目标、参数和有效期，并在执行前再次校验；审批提示本身不是授权机制。第 19 章的有限合成任务记录曾观察到不同审批规则下的打断与漏网差异，但它不能证明 coding agent 场景中的普遍效果，需按该章的样本和证据限制解读。

**这些边界需要组合，并按威胁模型验证。** 单层配置不自动构成有效安全保证；提示词只能表达意图，不能替代 OS 强制的权限、隔离和服务端授权。

## 四、代码：按隔离级别表达策略（不是执行器）

下面是**策略数据结构示意**，不是执行器，也不会创建任何隔离。特别是 `allow_network_hosts` 只是待实现的策略字段；简单 hostname 比较无法覆盖 DNS、重定向、IP 直连与代理绕过。读者不要直接把这段代码用于执行不可信命令。

```python
from dataclasses import dataclass, field


@dataclass
class SandboxPolicy:
    """按隔离级别配置 —— 注意没有「允许哪些命令」这个字段。"""
    writable_dirs: list = field(default_factory=list)
    readable_dirs: list = field(default_factory=list)
    allow_network: bool = False
    # 仅声明策略；必须由外部 sandbox/proxy 实施并验证，不能靠字符串匹配
    allow_network_hosts: list = field(default_factory=list)
    max_seconds: int = 120
    max_output_bytes: int = 200_000
    env_denylist: list = field(default_factory=lambda: [
        "SSH_AUTH_SOCK", "AWS_*", "OPENAI_API_KEY", "ANTHROPIC_AUTH_TOKEN",
    ])


def build_policy(level):
    """level 决定边界，而不是决定「允许哪些命令」。"""
    if level == "readonly":
        return SandboxPolicy(readable_dirs=["."])
    if level == "workspace":
        return SandboxPolicy(writable_dirs=["."], readable_dirs=["."])
    if level == "network":
        return SandboxPolicy(writable_dirs=["."], readable_dirs=["."],
                       allow_network=True, allow_network_hosts=["pypi.org", "registry.npmjs.org"])
    raise ValueError("未知隔离级别: %s" % level)
```

这段代码只是**策略数据模型示意，不会创建容器、限制路径或拦截网络**，不能直接当安全执行器使用。真正的执行器必须把策略映射到 OS/容器配置并验证生效；`readable_dirs`、`writable_dirs`、`allow_network_hosts` 和环境变量 denylist 在这个类里目前都没有执行语义。它表达的设计提醒是：命令 allowlist 单独不足以隔离会解释仓库内容的程序。

`env_denylist` 只是字段，并没有清理环境变量。执行时应从最小的显式环境变量集合开始，避免把宿主凭据注入子进程；如果任务确需凭据，应通过短时、最小权限、可撤销的凭据代理提供，并同时限制网络出口。隐藏变量名或只删几种常见变量都不能代替环境隔离。

### 一个真实的设计错误

我第一次写这个执行器时，是用 `subprocess.run(cmd, shell=True, cwd=workdir)`，
并认为「工作目录已经限制住了，不会伤到别处」。

这个想法有两个漏洞：

- **`cwd` 不是边界** —— 命令里一句 `cd /` 或者一个绝对路径就能出去
- **`shell=True` 让注入更容易** —— 模型生成的参数里一个分号就能串第二条命令

正确做法是**用容器的挂载做边界**（不挂载的目录它根本看不到），
并且**避免 `shell=True`**（用参数数组调用）。

这里要区分输入解析与权限边界：[Python subprocess 文档](https://docs.python.org/3.14/library/subprocess.html#security-considerations)建议避免让 `shell=True` 处理未经转义的输入；`shell=False` 和参数数组能减少 shell 元字符造成的命令拼接风险，但不会限制程序本身访问文件、网络或启动子进程。`cwd` 也只是初始工作目录，不是沙箱。权限必须由执行环境实施。

## 五、一个实用的分级建议

可以把这些策略组合成三档作为讨论起点；具体配置仍取决于平台和威胁模型：

| 档位 | 文件系统 | 网络 | 审批 | 适用 |
| --- | --- | --- | --- | --- |
| **只读** | 仅暴露任务所需目录且只读；宿主其它目录不挂载 | 禁止 | 无 | 让它先「读代码、给方案」，不改任何东西 |
| **工作区** | 仅工作区可写 | 禁止 | 不可逆动作 | 日常改代码、跑测试 |
| **受控联网** | 仅工作区可写，凭据不挂载 | 经代理按用途放行并记录策略 | 外部副作用需审批 | 获取已锁定依赖；安装脚本仍按不可信代码运行 |

两个实践要点：

**一、默认从只读开始。** 大多数任务的前半步其实是「理解代码」而不是「改代码」。
让它在只读模式下先给出方案，你确认之后再升到工作区 ——
这一步同时解决了两件事：安全，以及**你有了一个复核的机会**。

**二、联网档要短时开启。** 只缩短联网时间不能消除执行脚本期间的风险；获取依赖、校验产物、运行安装脚本可以拆开，并在脚本运行时继续使用最小权限与禁网策略。

隔离会改变可用能力与工作流，但不能只按“任务短不短”来调档。应根据数据敏感度、代码可信度、可触达的副作用和恢复能力逐项决定权限，并记录剩余风险；文件修改也可能覆盖唯一副本，外部动作也可能具备补偿机制，不能把可逆性简化成固定二分。

## 六、小结

- pytest、npm 和 Cargo 都可能按其规则加载/执行项目或依赖代码；本节标记文件结果是尚未复现的历史记录
- 单按命令名 allowlist 不能约束这些程序的全部副作用；需由运行时强制资源权限
- 破坏、外泄和供应链是威胁建模入口，不是风险排名
- 进程、文件系统、网络和审批等控制需要按场景组合，并检查实际配置
- 策略对象、提示词与环境变量 denylist 只有在执行器落实后才有相应控制效果
