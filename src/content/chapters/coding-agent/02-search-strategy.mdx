一次改动的第一步不是改，是**找到要改哪里**。这一步做错，后面全错。

而 coding agent 在这上面有一个硬约束：**仓库比上下文窗口大得多**。
一个几十万行的项目不可能整个塞进去，所以「怎么选材」直接决定成败。

## 一、实测：三种上下文组织方式

我造了一个 12 个文件的 fixture 仓库，其中 `compute_total` 定义在 `billing.py`，
被另外两个文件调用。然后问四个「在哪里」的问题，测三种上下文组织方式：

```text
策略              正确率   单次输入 token   上下文大小
A. 全文塞入         4/4        763         2,460 字符
B. grep 命中行      4/4        405         1,012 字符
C. 只给符号索引      3/4        323           717 字符
```

三个数字值得一个一个看：

**B 比 A 省了 47% 的输入 token，正确率一样。** 这是「检索优于全塞」在代码场景的具体证据 ——
和第 3 章讲的即时检索是同一个道理，只是这里的检索手段是 grep 而不是向量。

**C 最省（比 A 省 58%），但正确率掉了一个。** 掉的是哪一题很关键：

```text
q2：有个函数调用了 compute_total 但没有传 with_tax 参数，它是哪个函数？
    正确答案 checkout
    C 的作答：空（符号索引里只有 def 行，没有任何调用信息）
```

**所以「省 token」和「够不够用」是两件事**，取决于你问的是什么类型的问题：

| 问题类型 | 需要什么 | 只用符号索引够吗 |
| --- | --- | --- |
| 这个符号定义在哪 | 定义位置 | 够 |
| 谁调用了它 | 引用关系 | **不够** |
| 它被改了会影响谁 | 反向依赖 | **不够** |
| 这个文件有哪些函数 | 结构 | 够 |

这张表其实就是「检索策略要匹配问题类型」。**先确定问题类型，再决定取什么。**

## 二、grep 的三个边界

上面那张表把 grep 放在很实用的位置，但它有三个明确的边界，
不知道就会踩：

**一、grep 是行级的，不认语法。** 搜 `total` 会命中注释、字符串、以及名字里
恰好含 total 的其它标识符。在真实仓库里，一个短标识符能命中几百处。
缓解办法是**先搜更长的、更独特的字符串**（完整的函数签名而不是函数名）。

**二、grep 找不到「语义相同但写法不同」的东西。** 比如你想找「所有读了这个配置的地方」，
但如果有的地方通过 `getattr(config, KEY)` 读，grep 就找不到。
这类问题需要 AST 级别的分析，或者干脆用 LLM 语义检索（第 6 章讲过的向量检索）。

**三、grep 的结果需要人来判断哪些相关。** 一次 grep 命中 200 行，
你不能全塞给模型（那就退回全文了）。**需要有一个排序或截断策略。**

一个实用的做法是**两级检索**：先 grep 出所有命中的文件，
再按「命中次数」或「是否包含 def/class」排序，只把前几个文件的命中行塞进去。

## 三、符号索引怎么建

符号索引不需要复杂的工具，用语言自带的解析器就够。Python 用 `ast`，
JS/TS 用 tree-sitter（就是 Aider 那个 repo-map 用的东西）。

```python
import ast


def build_index(files):
    """files: {path: source}。返回定义索引与引用索引。"""
    defines, refs = {}, {}
    for path, src in files.items():
        try:
            tree = ast.parse(src)
        except SyntaxError:
            continue                       # 语法错的文件跳过，不要让整个索引崩掉
        for node in ast.walk(tree):
            if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef, ast.ClassDef)):
                defines.setdefault(node.name, []).append((path, node.lineno))
            elif isinstance(node, ast.Call):
                name = None
                if isinstance(node.func, ast.Name):
                    name = node.func.id
                elif isinstance(node.func, ast.Attribute):
                    name = node.func.attr
                if name:
                    refs.setdefault(name, []).append((path, node.lineno))
    return defines, refs


def answer_context(question_symbol, defines, refs):
    """按问题类型决定给什么 —— 这一步就是上面那张表的代码化。"""
    out = []
    if question_symbol in defines:
        out.append("定义：" + ", ".join("%s:%d" % d for d in defines[question_symbol]))
    if question_symbol in refs:
        out.append("调用：" + ", ".join("%s:%d" % r for r in refs[question_symbol]))
    return chr(10).join(out)
```

注意 `build_index` 里那个跳过语法错误文件的分支。真实仓库里总有解析不了的文件
（生成的代码、模板、不支持的语法版本）。**索引器必须能部分成功** ——
一个文件解析失败就让整个搜索失效，是最常见的实现缺陷。

### 一个真实的报错

我第一版 `build_index` 没有那个 `try/except`，直接 `ast.parse`。
结果在一个 fixture 上抛了 `SyntaxError`，整个索引函数崩掉，**搜索退化成「什么也没找到」**。

危险的地方在于**它不报错给用户**：agent 拿到一个空索引，会以为「仓库里没有这个符号」，
于是走上一条完全错误的路径。这和第 5 节那个「环境未重置」是同一种失败形态 ——
**基础设施坏了，但表现得像「查无此物」。**

所以对搜索类工具，有一条通用要求：**区分「找到了 0 条」和「搜索失败了」。**
两者的后续动作完全不同：前者要换关键词，后者要修工具。

## 四、真实 agent 的搜索顺序

把上面三件事组合起来，一个实用的搜索流程是这样的：

**第一步，先用最独特的字符串定位候选文件。** 不要一上来就读文件，也不要一上来就搜
函数名这种泛词。用一个完整的函数签名、一段错误信息、或者一个独特的常量名。
这一轮的目的不是找答案，是**把文件范围从几百个缩到几个**。

**第二步，只读候选文件的相关区域。** 一个 800 行的文件里你通常只需要 30 行。
按行号窗口读（比如命中行前后各 40 行），而不是整个文件。
这一步的收益在真实仓库上比 fixture 上大得多 —— 我那个 fixture 每个文件才 15 行，
但真实文件动辄上千行，**只读窗口能省掉 90% 以上的上下文**。

**第三步，需要改的时候才读完整上下文。** 这直接关系到下一节要讲的事：
精确匹配替换要求模型**逐字符**看到原文。所以「读窗口」够用来理解，
但不够用来生成 `old_string`。这两个目的的读法不同，不能混。

**第四步，改完之后重新搜索一次。** 因为你的改动可能让之前的定位失效 ——
比如你重命名了一个函数，那么所有调用点都变了。**改完不重查，是「第一处改了、
其余地方没改」这类半成品提交的常见来源。**

这四步对应一个常见反模式：**agent 一上来就把几个大文件整个读进来**。
它「看起来很努力」，但结果是上下文被无关内容占满，
而且真正需要精确匹配时又因为内容太多而抓错位置。

还有一个常被忽略的成本：**搜索本身也要花钱**。
一次 grep 不贵，但一个 agent 在一个大任务里可能调用几十次搜索。
第 18 章讲成本时那条「工具定义占 62%」的观察，在这里同样适用 ——
**搜索结果的返回格式**（返回全部命中行还是摘要）直接影响整个任务的开销。
返回全部命中行是省事的做法，但在大仓库里它可能一次就塞进去上万 token。

## 五、小结

- **grep 比全文省约一半 token 且正确率不掉** —— 是代码场景里性价比最高的检索
- **符号索引最省，但只能回答「定义类」问题** —— 问「谁调用」必须补引用信息
- **检索策略要匹配问题类型**：定义 / 引用 / 实现，三者需要的上下文不同
- **grep 是行级的**：短标识符会命中几百处，先搜更独特的字符串
- **索引器必须能部分成功**，且要区分「0 条命中」与「搜索失败」
- **搜索顺序**：先缩范围 → 再读窗口 → 只有要改时才读全文 → 改完重查

最后一条提醒和搜索无关，但经常是搜索失败的原因：**先确认你搜的是最新的代码。**
如果 agent 在一个过期的 checkout 上搜索，它会得到一份「合理的但已经不对」的答案 ——
这和第 5 节那个环境未重置是同一类问题：**基础设施的问题，表现得像内容的问题** —— 而你会在内容上找很久的答案。工程上一条便宜的防线是：**每次搜索前先校验工作区的版本标识**
（commit hash、mtime、或者一个显式的工作区 id），把它一并记进搜索结果的元信息里。
这样当结果可疑时，你至少能立刻排除掉「搜了旧代码」这个可能性。
