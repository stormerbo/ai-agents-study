一次改动的第一步不是改，是**找到要改哪里**。定位错了会让后续修改落在错误目标上，所以结果必须能追溯到当前工作区。

而 coding agent 在这上面有一个硬约束：**仓库比上下文窗口大得多**。
一个几十万行的项目不可能整个塞进去，所以「怎么选材」影响上下文成本和可回答的问题；检索结果仍要核对仓库版本、文件内容和问题判据。

## 一、实测：三种上下文组织方式

我造了一个 11 个文件的 fixture 仓库，其中 `compute_total` 定义在 `billing.py`，
被另外两个文件调用。历史脚本头部写了 12 个文件，但实际构造的是 9 个 module 加 `billing.py` 与 `api.py`，共 11 个。然后问四个「在哪里」的问题，测三种上下文组织方式：

```text
策略                    记录得分   最大单问输入 token   上下文大小
A. 全仓库源码             4/4          763             2,460 字符
B. grep 调用行 + 全部定义  4/4          405             1,012 字符
C. 仅函数定义列表          3/4          323               717 字符
```

**实跑状态：** 这是 2026-10-10 用 `deepseek-flash` 跑的一次四题 API 观察；脚本与摘要在忽略目录 `verify-output/coding-search.py` / `coding-search.log`。日志只保留“期望答案是否为输出子串”和截断后的答案片段，没有逐次完整响应；判分使用子串匹配，不能据此估计模型可靠性。脚本构造的 B 组不是单独的 grep：它把 `compute_total` 命中行与全仓函数定义列表一起提供。因此它只比较这三个具体上下文包，不能支持“grep 相比全文”或“省 token 且正确率不掉”的通则。token 列是四个问题中最大的单问输入值，不是平均值。

三个数字值得一个一个看：

**这次运行中 B 比 A 少用了约 47% 的最大单问输入 token，记录得分同为 4/4。** B 同时含 grep 命中和所有函数定义；这是一个具体 fixture 的观察，不是 grep 优于全文的独立实验或稳定效果估计。

**C 在这次运行里输入最少，但有一道题未通过子串判分。** 日志截取显示：

```text
q2：有个函数调用了 compute_total 但没有传 with_tax 参数，它是哪个函数？
    正确答案 checkout
    C 的作答：空（符号索引里只有 def 行，没有任何调用信息）
```

**所以「上下文短」和「足以回答」是两件事**，需要结合问题类型以及索引实际包含的字段判断：

| 问题类型 | 需要什么 | 只用符号索引够吗 |
| --- | --- | --- |
| 这个符号定义在哪 | 定义记录和路径 | 对本例够用 |
| 谁在源码里调用了它 | 调用点/引用记录 | 只有定义的列表不够；grep 或引用索引可提供候选 |
| 它被改了会影响谁 | 引用记录、导入关系和语义依赖 | 单一符号列表不够；简单 grep/AST 也不是完整影响分析 |
| 这个文件有哪些函数 | 函数定义记录 | 对本例够用 |

这张表其实就是「检索策略要匹配问题类型」。**先确定问题类型，再决定取什么。**

## 二、grep 的三个边界

上面那张表把 grep 放在很实用的位置，但它有三个明确的边界，
不知道就会踩：

**一、grep 是行级的，不认语法。** 搜 `total` 会命中注释、字符串、以及名字里
恰好含 total 的其它标识符。在真实仓库里，一个短标识符能命中几百处。
缓解办法是**先搜更长的、更独特的字符串**（完整的函数签名而不是函数名）。

**二、grep 找不到「写法不同但可能相关」的东西。** 比如你想找「所有读了这个配置的地方」，
有的代码可能通过 `getattr(config, KEY)`、包装函数或反射访问。静态分析、语言服务和语义检索都可以提供候选线索，但都不能仅凭检索命中证明语义等价；需要读调用链、确认变量来源并按需求验证。

**三、grep 的结果需要判断相关性与覆盖。** 一次 grep 命中 200 行，
上下文预算可能不够，但按命中次数截断可能漏掉唯一关键调用点。应优先缩小查询、保留路径和行号、分页查看，并把遗漏范围报告出来。

一个可用的做法是**两级检索**：先 grep 出候选路径，再读相关窗口；按任务线索（符号、调用者、配置引用）排序，并保留剩余候选或可继续读取的游标。按命中次数排行只是一个启发式，不是相关性判断。

**固定窗口示例：** 下面的实现按命中数排序，每个文件最多取 `per_file` 行，并在限额前过滤非整数与越界行号。它只演示有上限的候选采样，不保证选中最相关的命中；生产代码还应制定路径授权与读取失败策略，并提供分页或省略摘要。

```python
import os


def rank_and_truncate(hits, top_k=5, per_file=8):
    """hits: {文件路径: [命中行号, ...]} -> 可直接塞进上下文的行列表。

    两级：先按命中次数给文件排序、取前 top_k 个，再在每个文件里只保留
    前 per_file 行 —— 只排序不截断，"命中很多的单个文件"仍会把上下文占满。
    """
    if type(top_k) is not int or type(per_file) is not int or top_k < 0 or per_file < 0:
        raise ValueError("limits must be non-negative integers")
    ranked = sorted(hits.items(), key=lambda kv: (-len(kv[1]), kv[0]))[:top_k]
    out = []
    for path, lines in ranked:
        with open(path, encoding="utf-8", errors="ignore") as source_file:
            src = source_file.read().splitlines()
        valid_lines = sorted({n for n in lines if type(n) is int and 1 <= n <= len(src)})[:per_file]
        for n in valid_lines:
            out.append("%s:%d: %s" % (path, n, src[n - 1].strip()))
    return out
```

历史记录称，在当时标记为 `langchain_core` 0.3.63 的 checkout 上，对泛查询 `def ` 做过一次本地扫描：

```text
命中                              2070 行 / 157 个文件   84978 字符
rank_and_truncate(top_k=5, per_file=8) 后    40 行 /   5 个文件    2254 字符
```

据该次摘要，输出从 84,978 字符缩到 2,254 字符；它没有保留被选中的源码清单或原始扫描记录，不能证明保留下来的文件对任务相关。另一次摘要称，`model_json_schema` 从 27 行 / 11 个文件截到 21 行 / 5 个文件；由于对应原始执行记录不在仓库中，这组数字只当历史观察。工程判据不是“查询越泛越必须按命中频次截断”，而是：预算不足时要提供可解释的筛选规则、报告未检查部分，并允许检索器继续展开。

## 三、符号索引怎么建

符号索引不需要复杂的工具，用语言自带的解析器就够。

**先把两个词说清。** `AST`（抽象语法树，Abstract Syntax Tree）是解析源码得到的语法结构；Python 标准库的 `ast` 能暴露定义和调用等节点，但这不等于完成名称绑定或跨文件语义解析。这里的示例只建一个**词法级候选索引**：它能列出符合简单语法形态的节点，可能漏掉别名、动态分派和反射，也可能把同名但无关的属性调用混在一起。Python 官方 [ast 文档](https://docs.python.org/3/library/ast.html)说明语法树接口；[Tree-sitter](https://tree-sitter.github.io/tree-sitter/) 是可选的多语言增量解析库，输出 CST；[Aider repo-map 文档](https://aider.chat/docs/repomap.html)介绍其基于代码结构和依赖关系构建仓库地图。不同语言还可使用 compiler API、LSP、索引服务或项目自带解析器；`tree-sitter` 不是唯一选择，安装 parser/grammar 后才能解析对应语言。

```python
import ast


def build_index(files):
    """files: {path: source}。返回定义、词法引用候选和解析诊断。"""
    defines, refs, skipped = {}, {}, {}
    for path, src in files.items():
        try:
            tree = ast.parse(src)
        except SyntaxError as error:
            skipped[path] = error.lineno   # 继续处理，但显式报告未索引路径
            continue
        for node in ast.walk(tree):
            if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef, ast.ClassDef)):
                defines.setdefault(node.name, []).append((path, node.lineno))
            elif isinstance(node, ast.Call):
                name = None
                if isinstance(node.func, ast.Name):
                    name = node.func.id
                elif isinstance(node.func, ast.Attribute):
                    name = node.func.attr
                if name:
                    refs.setdefault(name, []).append((path, node.lineno))
    return defines, refs, skipped


def answer_context(question_symbol, defines, refs, skipped):
    """按问题类型决定给什么 —— 这一步就是上面那张表的代码化。"""
    out = []
    if question_symbol in defines:
        out.append("定义：" + ", ".join("%s:%d" % d for d in defines[question_symbol]))
    if question_symbol in refs:
        out.append("调用：" + ", ".join("%s:%d" % r for r in refs[question_symbol]))
    if skipped:
        out.append("索引不完整，跳过文件：" + ", ".join(sorted(skipped)))
    return chr(10).join(out)
```

`refs` 的 key 是语法节点上的最后一个名字，不是解析后的 symbol identity：例如 `a.save()` 与 `b.save()` 都会落在 `save`，而 `from module import f as g; g()` 只会记为 `g`。它适合生成待人工确认的候选列表，不适合直接声称完整调用图或影响半径。需要更强精度时，优先用能解析项目配置和名称绑定的语言服务/静态分析器，并报告未解析节点。

注意 `build_index` 里跳过语法错误文件时同时保存了 `skipped` 诊断。生成代码、模板或语言版本不匹配都可能让部分文件无法解析。**索引器应允许部分成功，同时明确报告未索引范围**；如果只返回空字典，调用方仍分不清“没有命中”与“文件根本没进入索引”。

**还有上面 Mermaid 里点名的另一个风险：索引会和代码不同步。** 处置办法按成本从低到高：

1. **给索引绑定工作区快照** —— 记录 commit 加脏工作树的 generation 或内容 hash，并把它带进搜索结果。只记 commit 会漏掉未提交修改；mtime 也可能因精度或复制而不足以区分内容。快照不一致就重建或标记 stale。
2. **只在任务开始时建一次**，任务中途不再相信它 —— 每次改完文件，按第 4 节的第四步重新搜索。
3. 可把索引当缓存，读取前用 generation 或内容 hash 校验相关文件；单独依赖 mtime 不一定可靠。

最常见的错误是"建了索引就永久信它"：之后模型改了一个函数，搜索仍然返回旧行号，而**这个错误看起来像"仓库里就是这样"**。每次修改后都应使相关缓存失效或核对文件版本；不确定新鲜度时，直接读取当前文件作为权威来源。

### 一个可复现的失败形态

若索引器对每个文件直接调用 `ast.parse`，一个语法错误就会中断整个批次。若上层再把异常吞掉并返回空索引，agent 会以为“仓库里没有这个符号”。这两步是不同的 bug：解析中断应返回搜索错误；部分索引可以继续，但必须把跳过路径带给调用者。

下面的固定 fixture 展示这两种结果应如何区分：

```python
files = {
    "good.py": "def target():\n    return 1\n",
    "broken.py": "def unfinished(:\n    pass\n",
}
defines, refs, skipped = build_index(files)
assert ("good.py", 1) in defines["target"]
assert skipped == {"broken.py": 1}
context = answer_context("target", defines, refs, skipped)
assert "索引不完整" in context and "broken.py" in context
```

所以对搜索类工具，有一条通用要求：**区分「找到了 0 条」「某些文件未索引」和「搜索失败」。** 零命中可换词或扩大范围；部分索引要核对诊断并决定是否足够；搜索失败则修工具或 runner，不能静默转换成空结果。

## 四、真实 agent 的搜索顺序

把上面三件事组合起来，一个实用的搜索流程是这样的：

**第一步，先用最独特的字符串定位候选文件。** 若需求、风险或架构关系尚不清楚，先读入口文档或目录结构；不要一上来就搜
函数名这种泛词。用一个完整的函数签名、一段错误信息、或者一个独特的常量名。
这一轮的目的不是找答案，是**把文件范围从几百个缩到几个**。

**第二步，按问题读取候选文件。** 如果只需检查一段局部逻辑，可以先读命中行附近的窗口，
例如前后若干行；窗口大小要覆盖函数边界、相关定义和调用上下文。需要理解模块初始化、状态流或跨函数不变量时，再扩展到完整文件或依赖文件。窗口截断也可能删掉关键上下文，因此不存在固定的“只读 30 行”或 90% 节省保证。

**第三步，修改前核对当前文件和编辑锚点。** 精确文本替换需要锚点与当前内容逐字符匹配，
并且按工具规则确认唯一；如果窗口没包含完整锚点或文件刚被改过，就重新读取目标范围。无需把整个仓库或长文件无差别塞进上下文。

**第四步，改完之后重新搜索或检查相关引用。** 因为你的改动可能让之前的定位失效 ——
比如你重命名了一个函数，那么所有调用点都变了。**改完不重查，是「第一处改了、
其余地方没改」这类半成品提交的常见来源。**

这四步对应一个常见反模式：**agent 一上来就把几个大文件整个读进来**。
它「看起来很努力」，但结果是上下文被无关内容占满，
而且真正需要精确匹配时又因为内容太多而抓错位置。

还有一个常被忽略的成本：**搜索本身也会消耗上下文和请求预算**。
一次 grep 不贵，但一个 agent 在一个大任务里可能调用几十次搜索。
第 18 章的 62% 是固定工具数、每轮重复输入与历史 token 假设下的本地模型，不是搜索实验或真实账单观察。**搜索结果的返回格式**（返回全部命中行还是摘要）会改变本次上下文大小；实际成本还取决于模型 tokenizer、缓存与 provider 计费规则。
返回全部命中行是省事的做法，但在大仓库里它可能一次就塞进去上万 token。

## 五、小结

- **本次 fixture 中 grep 命中行加定义列表的上下文比全仓文本短**；这是单次观察，不是通用准确率比较
- **只有定义的索引不包含调用关系**；引用列表也可能是词法候选而非完整调用图
- **检索策略要匹配问题类型**：定义 / 引用 / 实现，三者需要的上下文不同
- **grep 是行级的**：短标识符会命中几百处，先搜更独特的字符串
- **索引器必须能部分成功**，且要区分「0 条命中」与「搜索失败」
- **搜索顺序**：确认工作区 → 按问题检索 → 按需扩展源码上下文 → 编辑前核对锚点 → 改完复查

最后一条提醒和搜索无关，但经常是搜索失败的原因：**先确认你搜的是最新的代码。**
如果 agent 在一个过期的 checkout 上搜索，它会得到一份「合理的但已经不对」的答案 ——
这和第 5 节那个环境未重置是同一类问题：**基础设施的问题，表现得像内容的问题** —— 而你会在内容上找很久的答案。工程上一条便宜的防线是：**每次搜索前先校验工作区的版本标识**
（commit 加脏工作树 hash、索引 generation 或内容 hash），把它一并记进搜索结果的元信息里。
这样当结果可疑时，你至少能立刻排除掉「搜了旧代码」这个可能性。
