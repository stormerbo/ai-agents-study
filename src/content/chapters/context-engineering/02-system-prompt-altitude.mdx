system prompt 该写多具体？这个问题没有标准答案，但有两个方向明确的错误：

- **写太具体** —— 逐条列举每种情况的处理方式
- **写太抽象** —— 只说「你是一个有帮助的助手」

本节不讨论风格偏好，而是把这两种错误都测了一遍。结论是：**太具体的危害比想象中严重得多，而且不是「模型会做错」，是「你无法预测它会怎么做」。**

## 实测：三种具体度，同一组输入

三个 system prompt 处理同一批客服请求（3 个典型 + 1 个触发冲突 + 2 个长尾），每个跑 5 次：

| 写法 | 内容 | 平均输出字数 |
|---|---|---:|
| **抽象** | 「你是一个电商客服助手。」 | 311 |
| **原则式** | 4 条判断原则 + 2 个示例 | 334 |
| **逐条式** | 18 条具体规则 | **81** |

（实测数据，`deepseek-flash`，2026-10-08。逐条式里我放了「回复长度不超过 150 字」，所以字数落差有一部分是这条造成的 —— 但**规则堆叠本身就会长出这类输出形态约束**，这正是问题的一部分。）

字数落差不是重点。真正的问题是下面这个。

## 重点：规则一多，必然自相矛盾

我在那 18 条规则里**故意埋了一对矛盾**：

```
7. 涉及退款问题，一律先致歉并承诺 24 小时内到账
12. 不得对任何请求做出时间承诺
```

第 7 条要求承诺一个具体时间，第 12 条禁止承诺任何时间。同一件事，两条规则给了相反的指令。

然后我问一个正好落在交叉点上的问题：**「我要退款，多久能到账？」**

### 先看单条规则的表现

| 配置 | 承诺 24 小时 |
|---|---|
| 只留第 7 条 | **4/4** 承诺 |
| 只留第 12 条 | **0/4** 承诺 |

单独看，两条规则都是**确定**的 —— 模型严格执行了唯一的那条规则。

### 把两条放一起

| 配置 | 承诺 24 小时 |
|---|---|
| 只留 7 + 12 | 2/4 |
| 7 + 12 + 18（语气热情） | 1/4 |
| 7 + 12 + 18（同一配置，再跑一次） | **4/4** |
| 全部 18 条 | 4/4 |

（实测数据，`deepseek-flash`，2026-10-08。）

**注意第三行和第四行 —— 它们是同一个配置。** 一次 1/4，一次 4/4。

我把这个 prompt 原样跑了 12 次：

```
承诺 承诺 不承诺 承诺 承诺 承诺 承诺 不承诺 承诺 承诺 不承诺 不承诺
→ 承诺 8/12，不承诺 4/12
```

**同一份 prompt，同一个问题，结果是随机的。**

## 为什么这比「做错」更糟

如果模型**稳定地选错**一条规则，你测一次就能发现，然后修 prompt。

但这里不是选错 —— 是**每次的裁决都不同**。这意味着：

- 你测一次通过，不代表上线后也通过
- 出现问题时，你**无法复现**它
- 你甚至不知道「正确行为」是哪一种

**这就是「太具体会失控」的准确含义。** 不是模型变笨了，而是你把行为的决定权交给了一个没有优先级、没有冲突检测的权衡过程。

代码里有两条矛盾的 `if`，编译器或静态检查会告诉你；规则列表里有两句矛盾的话，**没有任何东西会告诉你**。而模型不会拒绝执行 —— 它会挑一条。

## 那该怎么写

从上面的实验能反推出一个可操作的判据：**区分「判断原则」和「输出形态约束」**。

| | 可以多写 | 必须少而明确 |
|---|---|---|
| 内容 | 判断原则（怎么权衡、什么优先、边界在哪） | 输出形态（长度、格式、语气、必含字段） |
| 例子 | 「不要承诺你无法保证的事」 | 「回复长度不超过 150 字」 |
| 冲突后果 | 模型按原则权衡，行为仍可预测 | **互相打架，行为变成随机** |
| 建议 | 3~6 条，覆盖主要判断维度 | 能合并的合并，能删的删 |

原则式那个 prompt 之所以表现最好，就是因为它把**判断**写清楚了，而没有去枚举**情况**：退款场景它不给具体天数（遵循原则 3），但会告诉用户流程和影响因素 —— 这是原则推导出来的行为，不是逐条匹配出来的。

还有一个更狠的自检方法：**把你的规则列表当成需求文档，逐条问「这条会不会和另一条打架」。** 我用 18 条规则做这个自检时，一眼就能看出第 7 条和第 12 条冲突 —— 但如果不做这一步，谁也不会注意到。

## 完整可运行代码

```python
# system_prompt_stability.py
"""测你自己的 system prompt 稳不稳定。

思路：把「同一个输入」跑很多次，看行为是否一致。
不一致 = 规则之间有未被发现的冲突，或者规则与模型的默认行为在打架。

这比「测一次看输出对不对」有用得多 —— 单次通过根本不能说明任何事。
"""

import os
from collections import Counter

import anthropic

client = anthropic.Anthropic(
    api_key=(
        os.environ.get("ANTHROPIC_API_KEY")
        or os.environ.get("ANTHROPIC_AUTH_TOKEN")
    ),
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)
MODEL = os.environ["VERIFY_MODEL"]

SYSTEM = """你是一个电商客服助手。请严格按以下规则处理：

7. 涉及退款问题，一律先致歉并承诺 24 小时内到账
12. 不得对任何请求做出时间承诺
18. 语气必须热情
"""

# 用可机判的特征来归类输出，而不是靠肉眼看
PROBE = "我要退款，多久能到账？"
RUNS = 12


def classify(text: str) -> str:
    """把输出归到一个可比较的类别里。

    换成你自己任务的可判特征 —— 关键是让「行为」变成可统计的东西。
    """
    if any(k in text for k in ("24小时", "24 小时", "一天内", "当天", "1个工作日", "1 个工作日")):
        return "承诺了具体时间"
    if any(k in text for k in ("无法承诺", "以实际为准", "以支付渠道", "取决于")):
        return "拒绝承诺"
    return "其他"


if __name__ == "__main__":
    labels = Counter()
    for i in range(RUNS):
        response = client.messages.create(
            model=MODEL, max_tokens=3000, system=SYSTEM,
            messages=[{"role": "user", "content": PROBE}],
        )
        text = "".join(b.text for b in response.content if b.type == "text")
        labels[classify(text)] += 1
        print(f"  #{i + 1}  {classify(text)}")

    print(f"\n{RUNS} 次运行的行为分布：")
    for label, n in labels.most_common():
        print(f"  {label:<12} {n}/{RUNS}")

    if len(labels) > 1:
        print("\n⚠️  行为不一致 —— 你的规则之间大概率存在冲突。")
        print("   上面表格里 7 与 12 就是一对：一个要求承诺时间，一个禁止承诺时间。")
```

> **实跑状态**：本文表格里的**数据是实测的**（用直接 HTTP 请求采集）；上面这份 Python 脚本用的是 SDK 写法，字段与采集脚本一致，但**脚本本身未在官方端点验证**。

## 上线前怎么发现自相矛盾

本节那个 8/12 的分裂，是在**跑了 12 次之后**才被发现的 —— 这是最贵的发现方式。有没有更早的办法？

有，而且很便宜：**把你的规则集交给模型自己审一遍。**

我拿三条规则做了一次，其中第 1 条与第 2 条在「会改变系统状态」这件事上直接对立：

| 规则 | 内容 |
|---|---|
| 1 | 任何会改变系统状态的操作，都必须先向用户确认 |
| 2 | 不要向用户提问，直接给出并执行最终方案 |
| 3 | 回答要简洁 |

问它「这几条规则里有没有互相冲突的地方」——**4 次全部准确指出了 1 与 2 的冲突，并且说清了触发条件（最终方案会改变系统状态时）**。第 3 条它明确判定为无冲突。

工程含义是：**规则集的内部一致性是可以自动检查的**，不必等线上的行为分裂来告诉你。把它做成一条 CI 检查（每次改 system prompt 就跑一遍），成本是几次调用，换来的是不必「上线两周后才发现」。

两个边界要说清楚。这是**判断辅助，不是证明** —— 模型说「无冲突」不等于真的无冲突。而且它只能发现**文字层面**的对立，发现不了「两条规则单独看都对、合起来才在某个业务场景下冲突」那种情况。所以它替代不了那个「跑 12 次看方差」的实测，只能让你**更早**知道该去测哪里。

## 还有两个更早的探针

除了让模型审规则集，还有两个成本更低的发现手段：

**用行为方差当探针。** 同一份 prompt 跑 8 到 12 次，统计输出的**分裂比例**。分裂本身就说明有规则在互相拉扯 —— 本节那个 8/12 就是这么暴露的。稳定输出不代表规则没冲突（也可能只是某一方始终压过另一方），但**分裂一定是冲突的证据**。

**按类别回查规则集。** 实践中最容易打架的是三类：给默认值的（「默认走只读」）、划权限的（「不允许删除」）、定语气的（「简短回答」）。把它们分开列出来逐类对比，比通读一遍更容易看出对立 —— 因为对立往往不产生在同一类内部，而产生于「权限说可以、默认说不行」这种跨类组合。

**把规则集的冲突留到线上发现。** 8/12 这种分裂要跑 12 次才看得出来，而让模型把规则集审一遍只要几次调用。后者应该进 CI，前者只该作为抽查。

## 常见坑

**以为规则越多越可控。** 实测相反：18 条规则里埋一对矛盾，同一个 prompt 跑 12 次出现 8:4 的分裂，而单条规则时都是 4/4 或 0/4。**规则数量与可控性不是正相关。**

**只测一次的通过率。** 冲突规则下的行为是随机的 —— 单次通过可能只是运气。稳定性必须靠**重复运行 + 统计行为分布**来测。

**把「模型会挑一条执行」当成可接受的行为。** 它挑哪一条是不受控的，而且换一次调用可能就换一条。这意味着你没法复现、没法排查、也没法写回归测试。

**以为长尾情况只能靠枚举覆盖。** 真实输入的组合是无穷的。给判断原则 + 少量典型示例，让模型在原则下自行处理长尾 —— 这正是「原则式」那组的表现来源。
