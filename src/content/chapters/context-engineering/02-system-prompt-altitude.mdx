system prompt 该写多具体？没有一个能脱离任务、模型与风险边界的统一长度。更实用的区分是：哪些要求是模型需要参考的软指引，哪些必须由宿主和程序强制。提示可以表达职责、原则、输出目标与例子；涉及权限、金额、交易或不可逆副作用的保证应放在确定性校验与工作流里。

- **过度枚举** —— 把大量场景逐条写成动作规则，维护成本和冲突风险上升
- **缺少任务约束** —— 只说「你是一个有帮助的助手」，没有交代用户目标、知识边界或验收标准

本节用一组历史客服 prompt 对照讨论这两类风险。现存记录不足以复算，因此它只能提出待验证的设计假设，不能证明“越具体越差”或给出通用 prompt 配方。

## 历史摘要：三种具体度，同一组输入

三个 system prompt 处理同一批客服请求（3 个典型 + 1 个触发冲突 + 2 个长尾），每个跑 5 次：

| 写法 | 内容 | 平均输出字数 |
|---|---|---:|
| **抽象** | 「你是一个电商客服助手。」 | 311 |
| **原则式** | 4 条判断原则 + 2 个示例 | 334 |
| **逐条式** | 18 条具体规则 | **81** |

（2026-10-08 `deepseek-flash` 历史摘要。逐次原始输出、准确 endpoint/model 指纹、采样参数、请求顺序和 scorer 未归档，本轮无法独立复算。逐条式明确含“回复长度不超过 150 字”，因此平均输出字数差异被该输出约束直接混杂；不能据此分离“规则数量”或“具体度”的因果效应。）

字数落差不是重点。真正的问题是下面这个。

## 重点：冲突规则需要显式裁决

历史 prompt 据称**故意包含一对互相矛盾的规则**：

```text
7. 涉及退款问题，一律先致歉并承诺 24 小时内到账
12. 不得对任何请求做出时间承诺
```

第 7 条要求承诺一个具体时间，第 12 条禁止承诺任何时间。两条规则覆盖相同场景却给出相反指令，prompt 没有可执行的优先级定义。更稳妥的做法是先决定业务政策，再让模型表达它；如果承诺必须可保证，就由可信业务状态和宿主逻辑约束。

然后我问一个正好落在交叉点上的问题：**「我要退款，多久能到账？」**

### 先看单条规则的表现

| 配置 | 承诺 24 小时 |
|---|---|
| 只留第 7 条 | **4/4** 承诺 |
| 只留第 12 条 | **0/4** 承诺 |

单独规则的历史摘要分别记录为 4/4 与 0/4；这只是四次输出的分类结果，不能叫作“确定”或稳定性保证。

### 把两条放一起

| 配置 | 承诺 24 小时 |
|---|---|
| 只留 7 + 12 | 2/4 |
| 7 + 12 + 18（语气热情） | 1/4 |
| 7 + 12 + 18（同一配置，再跑一次） | **4/4** |
| 全部 18 条 | 4/4 |

（历史单次摘要，`deepseek-flash`，2026-10-08；原始逐次输出、请求参数、精确模型后端与分类器记录未留存，无法重算。）

历史摘要称第三、四行使用同一配置，结果分别为 1/4 与 4/4；因为没有逐次输出和运行清单，本轮不能确认它们是否真的保持了完全相同的模型、端点、参数和输入。

另一个历史摘要称同一 prompt 与问题重复 12 次，结果分布如下：

```text
承诺 承诺 不承诺 承诺 承诺 承诺 承诺 不承诺 承诺 承诺 不承诺 不承诺
→ 承诺 8/12，不承诺 4/12
```

这份摘要显示了输出类别的变化，但没有原始响应、请求参数、返回模型标识或运行时间，不能归因为“随机”，也无法排除采样参数、服务端模型版本或分类误差。它说明单次试跑不足以证明稳定性；不能据此估计部署中的概率。

## 为什么这比「做错」更糟

如果只看一次输出，你无法知道它是否覆盖冲突边界，也不能判断策略是否稳定。

历史记录看起来存在不同分类结果。若策略规则互相冲突，不能把模型输出当成明确政策裁决；即使一次评估看起来一致，也需要：

- 多次运行覆盖关键边界，并记录模型、端点、参数与原始输出
- 先由产品/业务 owner 定义冲突时的正确行为
- 对硬约束用宿主校验或固定工作流兜底，提示只负责沟通和软性引导

本例能支持的结论范围更窄：**相互矛盾的自然语言指令没有自动形成可靠的优先级规则。** 不能从这个单一历史样本推出“太具体会失控”。

代码中的显式分支可以由测试覆盖；自然语言冲突需要评审和针对性的评测。模型可能折衷、拒答、遵从其中一条或给出其他输出，不能假设它总会挑一条。

## 那该怎么写

从这个例子可以得到一个设计检查：区分政策目标、软性指导与必须强制的约束，并为每类选择合适的实现位置。

| 要求 | 适合的位置 | 验收方法 |
|---|---|---|
| 角色、背景和任务目标 | system prompt 或 developer instruction | 用目标任务集检查相关性与遗漏 |
| 业务政策与优先级 | 明确写出适用范围、例外和冲突时优先级；高风险条件由宿主执行 | 覆盖正例、反例、边界与相互冲突的场景 |
| 输出结构与字段 | 适用时使用结构化输出，再由程序解析和校验 | 非法格式、缺字段、业务约束分别测试 |
| 语气、详略等软性目标 | prompt 指引与正反例 | 用代表性样本做人工或独立评分 |

Anthropic 当前提示指南建议清楚、直接地说明任务和输出要求，并提醒模型专属做法要用自己的评测确认；它不支持固定的“3–6 条原则”上限，也不证明抽象原则一定优于具体规则。本文历史样本的 prompt 数量、原文与完整评分缺失，因此原则式与逐条式的比较只能视为待复验观察。

### 两份 prompt 的原文

历史摘要曾把原则式配置列为表现较好的组，但没有原始评分可复核；下面给出的是可供评测的重写示例，不是那次实验的原始 prompt（构造数据，未实跑）。它保留 4 条原则 + 2 个示例的结构，但逐字原文没有留存：

```text
你是电商客服助手。按下面 4 条原则处理每一轮对话，不要逐条匹配场景。

原则 1（先确认再承诺）：涉及金额、时间、库存的答复，先确认你手上有事实依据；
  没有依据时，说明你会去核实，不要给一个具体的数字。
原则 2（能查就查，查不到就问）：需要订单号、支付渠道、物流单号时，先向用户要，
  或者调用工具去查；两者都不可用时，明确说「我现在无法确认」。
原则 3（不承诺你无法保证的事）：退款到账时间由支付渠道决定，你只说流程和影响因素，
  不要给出具体小时数或天数。
原则 4（该升级就升级）：用户明确要求人工、或提到投诉与法律责任时，不要继续自行处理，
  告诉用户你会转人工，并说明需要哪些信息。

示例 1（正确）：
  用户：我要退款，多久能到账？
  助手：我先帮你确认订单状态。到账时间取决于支付渠道，我无法承诺具体时点 ——
        原路退回通常在渠道审核通过后到账，进度可以在订单详情里看到。
示例 2（错误）：
  用户：我要退款，多久能到账？
  助手：24 小时内到账。
  ← 这违反了原则 3：你在承诺一个你无法保证的时间。
```

对照那 18 条逐条规则（示例：构造数据，未实跑，7 与 12 是原文），一眼就能看出结构差别：

| 编号 | 规则 | 类别 |
|---|---|---|
| 1 | 你是电商客服助手 | 角色设定 |
| 2 | 先判断问题属于退款/物流/商品/账号/投诉哪一类 | 场景枚举 |
| 3~6 | 每一类都要先要一个字段（订单号、物流单号、商品编码、手机号后四位） | 判断原则 |
| 7 | 涉及退款问题，一律先致歉并承诺 24 小时内到账 | 场景枚举（与 12 冲突） |
| 8 | 用户情绪激动时，先安抚再处理 | 判断原则 |
| 9 | 不要主动提及竞品 | 判断原则 |
| 10 | 价格以页面显示为准 | 判断原则 |
| 11 | 超出能力范围时转人工 | 判断原则 |
| 12 | 不得对任何请求做出时间承诺 | 判断原则（与 7 冲突） |
| 13 | 回复中必须包含「还有什么可以帮您」 | 输出形态 |
| 14 | 每段不超过 3 句 | 输出形态 |
| 15 | 回复长度不超过 150 字 | 输出形态 |
| 16 | 语气必须热情 | 输出形态 |
| 17 | 不要复述完整手机号 | 判断原则 |
| 18 | 不确定的信息不要编造 | 判断原则 |

注意 13 / 14 / 15 三条：它们没有直接逻辑冲突，但确有联合满足难度。原始输出与逐次判分没有留存，不能断言它们使输出“随机”。可以把格式、长度和必含字段变成单独的可机判验收项；若约束彼此不可兼容，应先由产品 owner 选择优先级。

### 4 条原则是怎么拆出来的

编写和评估规则可以按以下步骤进行。它们是工作方法，不保证模型一定遵循：

1. **从真实失败与成功案例提炼需求。** 不要只从功能清单枚举场景；检查案例是否覆盖目标读者和实际风险。本文的退款情境是构造示例，不是可复核的线上事故。
2. **把每条要求写成可验收的行为。** “没有订单状态就不承诺到账时间”比“负责任地处理退款”更易测试；具体措辞仍要按任务验证。
3. **定义冲突优先级。** 对不可逆动作、授权、金钱和时限，先定义业务政策并在宿主或工具层强制；不要依赖模型自行裁决硬约束。
4. **列出冲突对和边界输入。** 检查两条要求同时触发时的预期结果，用固定数据集对不同版本运行并保留逐次响应与参数。
5. **用多样的正例和反例评估。** 反例应覆盖边界；评价器需明确标注规则、歧义和人工复核条件，不要把一次格式通过当作事实正确。

自检时把规则列表当成需求文档，逐条问“同一输入会不会触发相反动作”。历史 18 条规则摘要中，第 7 条与第 12 条构成明显冲突；这一结构事实可从文字检查，但模型输出次数和具体变化仍不可独立复核。

## 完整可运行代码

```python
# system_prompt_stability.py
"""对一个固定 probe 做重复评估；词面标签只是人工复核队列，不是正确率。"""

import json
import hashlib
import os
import re
from collections import Counter
from pathlib import Path
import uuid

import anthropic

api_key = os.environ.get("ANTHROPIC_API_KEY") or None
auth_token = os.environ.get("ANTHROPIC_AUTH_TOKEN") or None
if (api_key is None) == (auth_token is None):
    raise RuntimeError("请且仅配置 ANTHROPIC_API_KEY 或 ANTHROPIC_AUTH_TOKEN 其中一个")
client = anthropic.Anthropic(
    api_key=api_key,
    auth_token=auth_token,
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)
MODEL = os.environ["VERIFY_MODEL"]
MAX_TOKENS = int(os.environ.get("MAX_OUTPUT_TOKENS", "512"))
RUNS = int(os.environ.get("PROMPT_EVAL_RUNS", "12"))
RESULTS_PATH = Path(os.environ.get("PROMPT_RESULTS_PATH", "prompt-runs.jsonl"))
SAVE_RAW_RESPONSES = os.environ.get("SAVE_RAW_RESPONSES") == "1"

SYSTEM = """你是一个电商客服助手。请严格按以下规则处理：

7. 涉及退款问题，一律先致歉并承诺 24 小时内到账
12. 不得对任何请求做出时间承诺
18. 语气必须热情
"""
PROBE = "我要退款，多久能到账？"
TIME_HINT = re.compile(r"(?:24\s*小时|当天|次日|\d+\s*个?工作日|\d+\s*天)")
NO_COMMITMENT_HINT = re.compile(r"(?:不|无法|不能|不会|不敢)[^。！？；\n]{0,12}(?:承诺|保证|确定)")


def classify_candidate(text: str) -> str:
    """只筛出需要复核的词面线索，不能替代语义评分。"""
    has_time = bool(TIME_HINT.search(text))
    has_qualifier = bool(NO_COMMITMENT_HINT.search(text))
    if has_time and has_qualifier:
        return "mixed_needs_review"
    if has_time:
        return "time_mention_needs_review"
    if has_qualifier:
        return "no_commitment_mention_needs_review"
    return "other_needs_review"


def usage_record(response) -> dict:
    usage = response.usage
    fields = (
        "input_tokens", "output_tokens", "cache_read_input_tokens",
        "cache_creation_input_tokens",
    )
    return {name: getattr(usage, name, None) for name in fields}


if __name__ == "__main__":
    if RUNS < 1:
        raise ValueError("PROMPT_EVAL_RUNS 必须大于 0")
    run_id = str(uuid.uuid4())
    RESULTS_PATH.parent.mkdir(parents=True, exist_ok=True)
    labels = Counter()
    completed = 0
    with RESULTS_PATH.open("a", encoding="utf-8") as output:
        for i in range(RUNS):
            try:
                response = client.messages.create(
                    model=MODEL, max_tokens=MAX_TOKENS, system=SYSTEM,
                    messages=[{"role": "user", "content": PROBE}],
                )
            except Exception as exc:
                record = {
                    "run_id": run_id, "run": i + 1,
                    "status": "request_error", "error_type": type(exc).__name__,
                }
                output.write(json.dumps(record, ensure_ascii=False) + "\n")
                output.flush()
                print(f"#{i + 1}: request_error ({type(exc).__name__}); stop the run")
                break

            text = "".join(b.text for b in response.content if b.type == "text")
            status = "complete" if response.stop_reason == "end_turn" and text.strip() else "incomplete"
            label = classify_candidate(text) if status == "complete" else "not_scored"
            record = {
                "run_id": run_id,
                "run": i + 1,
                "status": status,
                "requested_model": MODEL,
                "returned_model": getattr(response, "model", None),
                "stop_reason": response.stop_reason,
                "usage": usage_record(response),
                "request_config": {
                    "max_tokens": MAX_TOKENS,
                    "sampling_parameters": "SDK/endpoint default; not pinned",
                    "custom_base_url": bool(os.environ.get("ANTHROPIC_BASE_URL")),
                },
                "candidate_label": label,
                "text_sha256": hashlib.sha256(text.encode("utf-8")).hexdigest(),
            }
            if SAVE_RAW_RESPONSES:
                record["text"] = text
            output.write(json.dumps(record, ensure_ascii=False) + "\n")
            output.flush()
            if status != "complete":
                print(f"#{i + 1}: {status} ({response.stop_reason}); stop the run")
                break
            completed += 1
            labels[label] += 1
            print(f"#{i + 1}: {label}; inspect saved response")

    print(f"\ncompleted calls: {completed}/{RUNS}; candidate labels: {dict(labels)}")
    raw_mode = "raw response text saved" if SAVE_RAW_RESPONSES else "response text omitted; hashes saved"
    print(f"{raw_mode} in {RESULTS_PATH}; protect the file and manually adjudicate before drawing conclusions")
```

> **实跑状态**：本文数字仅为 2026-10-08 的历史摘要，原始响应、逐次请求配置、模型后端指纹和 scorer 未归档，不能复算。上面的代码是新的离线可检查样例，**未在官方端点运行**，也不复刻历史采集脚本。它遇到非 `end_turn`、空输出或请求异常会停止；默认只保存文本哈希、返回模型、停止原因和可用 usage。设置 `SAVE_RAW_RESPONSES=1` 才会保留原文；若 prompt 含真实用户数据，应按组织的数据访问与保留策略保护该文件。候选标签只按词面线索分组，所有输出都需要人工或独立评分器复核，不能直接称为“承诺”或“遵从率”。

## 上线前怎么发现自相矛盾

历史记录里的 8/12 分布来自重复运行摘要；逐次响应和参数未留存，无法确认最早何时会察觉。有没有运行前的辅助办法？

可以让模型协助提出候选冲突，再由负责业务政策的人复核并形成测试；这只是一个启发式检查，不是自动证明。

一个历史摘要描述了三条规则，其中第 1 条与第 2 条在“会改变系统状态”的场景下表面上对立：

| 规则 | 内容 |
|---|---|
| 1 | 任何会改变系统状态的操作，都必须先向用户确认 |
| 2 | 不要向用户提问，直接给出并执行最终方案 |
| 3 | 回答要简洁 |

摘要称模型 4 次都指出了 1 与 2 的冲突，并给出触发条件；但原始输入/输出、模型配置与独立评分均未留存，本轮无法验证“4 次准确”，也不能测出漏报和误报。

工程含义是：模型可以帮助整理候选冲突，最终政策仍要由 owner 定义，再把可判定边界写成测试。不要把未经独立评估的模型自审直接当作 CI 阻断门禁；它的输出适合进入人工复核队列。

### CI 里那句自检提示词

可以用下面的提示收集候选冲突，并要求触发条件。输出仍需由业务 owner 核对：

```text
下面是一份 system prompt 的规则列表。请只做一件事：找出其中互相冲突的规则对。

判定标准：存在一个具体的用户输入，让两条规则给出相反的处理动作。
不要报告「表述含糊」「可以更具体」这类问题 —— 只报真正的对立。

对每一对冲突，输出三行：
  规则 A：<编号与原文>
  规则 B：<编号与原文>
  触发条件：<什么样的用户输入会让它们冲突>

没有冲突就只输出「无」。

规则列表：
<把 system prompt 原文贴在这里>
```

如果要接进 CI，先把它设为非阻断诊断：保存模型与 prompt 版本、采样参数、原始响应和人工裁决；用代表性无冲突/有冲突用例量化漏报、误报和版本漂移后，再决定是否用它触发人工审核。

两个边界要说清楚。这是**候选发现，不是证明** —— 模型说“无冲突”不等于真的无冲突，报告冲突也不代表业务政策必须删除其中一条。语义冲突可能来自实际业务上下文，因此要结合 owner 裁决、确定性约束测试和目标任务评测。重复生成只观察特定设置下的输出差异，不能替代政策审查或质量评测。

## 还有两个更早的探针

除了让模型审规则集，还有两个成本更低的发现手段：

**重复运行作为补充探针。** 在固定任务、模型/端点与生成配置下重复运行，保留每次原始响应并盲审类别。分裂可提示非确定性、歧义、冲突或测量器错误；它本身不能证明提示规则冲突。运行次数应由评估目标和资源预算决定，少量运行只能描述这批输出，不能估计部署概率。

**按类别回查规则集。** 可以把默认行为、权限/禁止项、输出要求分别列出，再检查交叉场景；这是审查清单，不表示冲突更常见于某几类，也不能代替端到端评测。

**不要等线上副作用暴露政策冲突。** 先用 owner 批准的决策表、边界用例和确定性宿主守卫检查硬约束；模型生成评测与重复运行可辅助发现未覆盖行为，但都需要解释其测量范围。

## 常见坑

**把历史小样本当成规则数量定律。** 18 条规则与 8/12 分布只是无法复核的单次历史摘要；它不能证明规则越多就越不可控。审查具体冲突、目标任务质量和宿主强制边界。

**只测一次的通过率。** 一次通过不能证明稳定；重复运行能揭示这一评测设置下的输出变化，但不能单独诊断成因，也不能直接外推到线上。

**把模型输出当作硬政策裁决。** 明确冲突时的业务优先级，并用程序或宿主权限边界落实关键约束；提示语只能作为模型行为指导。

**以为长尾情况只能靠枚举覆盖。** 典型案例可帮助暴露边界，但模型是否能推广原则应在代表性长尾样本上测量；历史原则式 prompt 的表现不可复算，不能把它当作优势证据。
