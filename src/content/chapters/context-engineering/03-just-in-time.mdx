给模型一份资料，有两条路：

- **预加载** —— 把可能用到的资料先全部放进上下文
- **按需取** —— 只给一个目录，让模型需要时自己去读

「按需取更好」常被当作默认答案，但它只是待验证的设计假设。它能减少一次请求里预先加载的正文，却会增加工具往返、调度与失败处理；**成本和答案质量都要在目标任务上测**。

## 历史观测一：资料库越大，按需取越划算？

历史记录称任务需要 60 篇资料里的 2 篇。同一个问题，两条路线各跑一次：

| 资料库 | 路线 | 轮次 | 总 token |
|---:|---|---:|---:|
| 20 篇 | 预加载 | 1 | 2150 |
| 20 篇 | 按需取 | 2 | **1888**（省 12%） |
| 60 篇 | 预加载 | 1 | 6100 |
| 60 篇 | 按需取 | 2 | **3259**（省 47%） |

（历史单次观测摘要，`deepseek-flash`，2026-10-08。逐次请求/响应、模型后端指纹、缓存 usage 原值、任务答案与评分器未归档；本轮无法独立复算。表中 token 口径沿用当时记录，不能据此确认 provider 计费或跨端点 usage 语义。）

在这组历史摘要里，预加载随资料库规模增长，而按需路线只取回少量正文。它是一个可解释的样本，不足以证明线性关系或“几乎不随资料库增长”的普遍规律；目录长度、检索命中、工具轮数、缓存命中和输出长度都会改变结果。

因此不能只按资料库大小选方案；还要测每个任务实际需要多少内容，以及按需路线的额外轮次。

## 历史观测二：需要的比例会影响 token 量，但不能直接当选型阈值

我固定资料库为 40 篇，只改变**任务需要几篇**：

| 需要篇数 | 预加载 token | 按需取 token | 轮次 | 按需 / 预加载 |
|---:|---:|---:|---:|---:|
| 2 / 40 | 3662 | 2329 | 2 | **0.64x** |
| 8 / 40 | 3453 | 3267 | 2 | 0.95x |
| 20 / 40 | 4638 | 11467 | 5 | **2.47x** |
| 40 / 40 | 5059 | 18216 | 5 | **3.60x** |

（历史单次观测摘要，`deepseek-flash`，2026-10-08；逐次轨迹、答案等价性和评分器均未归档，无法独立复算。）

**结论反过来了。**

- 只需要 2 篇时，按需取的历史 token 量少约 36%
- 需要 8 篇（约占 1/5）时，两者**打平**
- 需要 20 篇时，按需取记录的 token 量约为 2.5 倍
- 需要全部时，约为 3.6 倍

预加载两端的历史 token 量接近（3453 与 5059），因为两次都一次性提交 40 篇正文；但实际值仍受输出、任务提示和生成长度影响。按需回填更多正文会增加上下文体量，但该组观测不足以证明其成本随需求线性上涨。

这组点只能说明：在当时这套样本与记账方式下，2/40 的按需记录低于预加载，8/40 接近，20/40 与 40/40 更高。所谓“约 20% 交叉点”只是稀疏单次样本之间的插值，**不是可迁移阈值**；任务质量也没有可复核的等价判分，不能据此声称按需路线更便宜且效果相同。

## 为什么按需取可能增加总 token 量：轮次

看那张表里的一列：**轮次从 2 变成 5**。

按需取不是「读两次就完事」—— 模型每读一批就得把结果发回去，然后进行下一轮。**本节的 Anthropic Messages API 示例由客户端在每次请求中重发对话历史**；其他 API 可能提供不同的服务端状态机制，应按目标 endpoint 核对。

于是当需要读 20 篇时：

```text
第 1 轮：目录 + 问题                      → 读 4 篇
第 2 轮：上面全部 + 4 篇内容               → 再读 5 篇
第 3 轮：上面全部 + 9 篇内容               → 再读 6 篇
...
```

重复发送的历史可能增加累计输入量，但总量取决于每轮新增内容、工具批次、缓存规则和输出。O(N²) 只适用于每轮新增量随已读正文近似线性增长的特定构造；不能仅凭这张表推出一般复杂度。

> 缓存 usage 字段与缓存规则由 provider/endpoint 定义：DeepSeek 当前 API 记录 `prompt_cache_hit_tokens` 与 `prompt_cache_miss_tokens`，Anthropic Messages API 用 `input_tokens`、`cache_read_input_tokens` 和 `cache_creation_input_tokens` 表达输入组成；应按目标端点的官方语义实现并验证计数。缓存可能降低重复前缀的处理成本，但不能把某一端点的规则推广到所有服务，也不能把“请求再次发送”直接等同于缓存命中。测量时应分别记录总输入、缓存读写、输出、账单和延迟，参考 [DeepSeek Context Caching](https://api-docs.deepseek.com/guides/kv_cache/) 与 [Anthropic Prompt Caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。

## 那到底该怎么选

把上面的数据整理成一条判据：

| 你的情况 | 选择 | 理由 |
|---|---|---|
| 资料库小（十几篇以内） | **预加载** | 两者差不多，预加载少一轮往返、也不用建检索 |
| 资料库大，但每次只用到几篇 | **先测按需取** | 正文可能少传，但要把检索命中、轮次、延迟和失败算进去 |
| 资料库大，且每次要用很多 | **比较预加载、筛选与压缩** | 多轮正文回填可能抵消按需收益；历史交叉点不能直接套用 |
| 资料库大，每次用量不定 | **目录 + 按需**（下面这个） | 用目录提供发现能力，再在目标任务上验证答案质量和总成本 |

### 中间形态：只给目录

最后一行值得单独说，因为它是实际系统里最常见的做法，也是两个 checkpoint 里那个「文件路径模式」（本站的 checkpoint 指每节末尾的自检题，不是框架的持久化检查点 —— 后者见第 11 章）：

**把「索引」和「内容」分开。**

- **索引**（标题、路径、摘要）通常比整篇正文短；20 篇约 400 token、60 篇约 1200 token 是构造样例估算，不是 tokenizer 实测。应按目标模型计数，再决定是否常驻
- **内容**只在被选中时加载，可以减少首轮正文，但可能增加后续请求、延迟和工具开销

一份索引长这样（示例：构造数据，未实跑）：

```text
DOC-01  灾备演练规范          ops/dr-drill.md          演练窗口、参与人、演练期间的变更禁令
DOC-02  支付渠道对账流程       billing/reconcile.md     T+1 对账口径、差异分类与处理时限
DOC-03  线上故障分级标准       ops/incident-level.md     P0~P3 的判定条件与响应要求
DOC-04  退款到账时间说明       billing/refund-sla.md    各渠道的到账口径与影响因素
DOC-05  数据导出权限申请       security/export.md       申请流程、审批人、有效期
...（其余 15 条同格式）
```

索引通常需要能定位资源、帮助发现候选的信息；字段与格式应按检索、授权和版本策略设计：

| 字段 | 谁用 | 怎么写 |
|---|---|---|
| 稳定 ID | 宿主定位正文与版本 | 在明确的命名空间内唯一；变更策略与正文版本一起管理 |
| 标题 | 人和模型发现候选 | 尽量保留来源标题，并在索引中记录规范化规则 |
| 摘要 | 帮助筛选候选 | 标明适用范围与来源版本；长度按任务和 token 预算验证 |

**摘要通常适合离线生成并随索引版本化。** 是否要在请求时生成，取决于新鲜度、数据敏感度、更新成本和端到端延迟，不能一概说成多花一轮。摘要应标明来源版本；若它只用于发现正文，写主题与适用范围，并让系统在高风险结论上仍读取权威正文。

模型拿到目录后，「选中」发生在同一次工具调用里 —— 它不需要你额外设计一轮选择对话，目录加问题就是那一轮的输入，它要读哪篇就直接调工具（示例：构造数据，未实跑）：

```text
输入：目录（DOC-01 ~ DOC-20 各一行）+ 问题「灾备演练期间允许改生产配置吗？」
输出：tool_use  read_doc({"id": "DOC-01"})
```

因此索引质量会影响发现效果，但它不是唯一因素；工具检索、候选排序、权限过滤、模型选择和正文新鲜度也会影响结果。摘要太短会漏掉区分条件，摘要写入结论则可能使模型跳过权威正文，应通过目标任务集测量召回、答案正确性与成本。

这个做法顺带解决了另一个问题：**模型不知道自己不知道什么**。先给它一张地图，它才会去问对的问题。本站在做代码检索类任务时用的就是这条路（[aider 的 repo-map](https://aider.chat/docs/repomap.html) 是同一思路的成熟实现）。

## 完整可运行代码

示例使用 Anthropic Python SDK：`ANTHROPIC_API_KEY` 通过 `api_key` 传入，`ANTHROPIC_AUTH_TOKEN` 通过独立的 `auth_token` 传入，不能把两类值合并到 `api_key`。`ANTHROPIC_BASE_URL` 只选择请求端点，不代表兼容服务一定接受相同的认证方式；使用兼容端点时还要核对该端点的认证文档。

```python
# preload_vs_jit.py
"""在你的资料库与任务上，测出那条交叉点在哪。

关键：按需取应**累加所有轮次的输入与输出 token**，并按目标 endpoint 的 usage 语义拆分缓存读写；只看最后一轮会漏掉此前调用。
"""

import json
import os

import anthropic

api_key = os.environ.get("ANTHROPIC_API_KEY") or None
auth_token = os.environ.get("ANTHROPIC_AUTH_TOKEN") or None
if api_key and auth_token:
    raise RuntimeError("请只配置 ANTHROPIC_API_KEY 或 ANTHROPIC_AUTH_TOKEN 其中一个")
client = anthropic.Anthropic(
    api_key=api_key,
    auth_token=auth_token,
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)
MODEL = os.environ["VERIFY_MODEL"]

# 换成你自己的资料库。summary 就是上面那种一句话摘要，索引只用它，不用正文。
DOCS: list[dict] = [...]      # [{"id","title","summary","content"}, ...]
NEEDED_IDS: list[str] = [...] # 这个任务到底需要哪几篇
QUESTION = "..."

TOOL = {
    "name": "read_doc",
    "description": "按编号读取一篇资料全文。只在确定需要时读 —— 每次调用都会增加上下文占用。",
    "input_schema": {
        "type": "object",
        "properties": {"id": {"type": "string"}},
        "required": ["id"],
    },
}


def total_tokens(u) -> int:
    """只适用于 Anthropic Messages usage 字段语义。

    不同 provider/endpoint 的 input/cache 字段可能不同，也可能把缓存 token
    包含在 input_tokens 里。先按目标端点文档实现并测试 adapter，不能盲目相加。
    这里按 Anthropic 定义重建总输入，再加输出 token；这仍是 token 量，不是费用。
    """
    input_tokens = u.input_tokens or 0
    cache_read = getattr(u, "cache_read_input_tokens", None) or 0
    cache_write = getattr(u, "cache_creation_input_tokens", None) or 0
    output_tokens = u.output_tokens or 0
    return input_tokens + cache_read + cache_write + output_tokens


def preload() -> int:
    corpus = "\n\n".join(f"【{d['id']}】{d['title']}\n{d['content']}" for d in DOCS)
    resp = client.messages.create(
        model=MODEL, max_tokens=4000,
        system=f"下面是全部资料。\n\n{corpus}",
        messages=[{"role": "user", "content": QUESTION}],
    )
    if resp.stop_reason != "end_turn":
        raise RuntimeError(
            f"预加载路线未完整结束：stop_reason={resp.stop_reason!r}；"
            "该次结果不能作为可比的已完成样本"
        )
    return total_tokens(resp.usage)


def on_demand() -> int:
    # 目录为候选发现提供线索；摘要不是唯一信号，也不能代替宿主的授权与检索策略。
    catalogue = "\n".join(
        f"{d['id']}  {d['title']}  {d['summary']}" for d in DOCS
    )
    messages = [
        {
            "role": "user",
            "content": (
                f"可查阅以下资料（只给目录，不含正文）：\n\n{catalogue}\n\n"
                f"{QUESTION}\n\n"
                "如果正文是回答所必需的，调用 read_doc 取回它 —— "
                "只在你确定必要时才读，每次读取都会增加一轮往返与上下文占用。"
                "如果目录里没有相关文档，直接说明，不要猜。"
            ),
        }
    ]
    total = 0

    for _ in range(8):                      # 教学样例的硬上界；生产值应由预算与 deadline 决定
        resp = client.messages.create(
            model=MODEL, max_tokens=4000, tools=[TOOL], messages=messages,
        )
        total += total_tokens(resp.usage)   # 累加，不是覆盖

        if resp.stop_reason == "end_turn":
            return total

        if resp.stop_reason != "tool_use":
            raise RuntimeError(
                f"按需路线未完整结束：stop_reason={resp.stop_reason!r}；"
                "该次结果不能作为可比的已完成样本"
            )

        messages.append({"role": "assistant", "content": resp.content})

        results = []
        for b in resp.content:
            if b.type != "tool_use":
                continue
            doc = next((d for d in DOCS if d["id"] == b.input.get("id")), None)
            if doc is None:
                # is_error 是 tool_result 上的一个布尔字段：它告诉模型
                # 「这一条不是结果，是一次失败」。不标它，模型会把错误
                # 当成资料读进去。第 4 章的历史行为摘要缺少原始响应，本例只展示协议字段。
                results.append({
                    "type": "tool_result",
                    "tool_use_id": b.id,
                    "is_error": True,
                    "content": json.dumps({
                        "error": "not_found",
                        "message": f"资料库中没有 {b.input.get('id')} 的正文，"
                                   "索引可能是过期快照。",
                        "retryable": False,
                    }, ensure_ascii=False),
                })
            else:
                results.append({
                    "type": "tool_result",
                    "tool_use_id": b.id,
                    "content": doc["content"],
                })
        if not results:
            raise RuntimeError("收到 tool_use stop_reason，但没有可处理的本地 read_doc 调用")
        messages.append({"role": "user", "content": results})
    raise RuntimeError("按需路线达到工具轮次上限；该次结果未完成，不能当作成功样本")


if __name__ == "__main__":
    pre = preload()
    jit = on_demand()
    print(f"资料库 {len(DOCS)} 篇，任务需要 {len(NEEDED_IDS)} 篇")
    print(f"  预加载：{pre:>7} token")
    print(f"  按需取：{jit:>7} token")
    print(f"  token 量比值：{jit / pre:.2f}x   （<1 表示本次记录 token 更少，不代表费用更低或答案等价）")
```

> **实跑状态**：表格保留的是 2026-10-08 的历史数值摘要，原始请求/响应、完整 usage、逐样本映射与答案判分没有归档，无法独立重放；上面的 Python 脚本未调用 provider。脚本会拒绝把非 `end_turn` 或轮次耗尽的请求记为完成，但只统计 token 量，**不验证两条路线是否给出同等正确答案**。正式对照还需固定任务集、重复运行、校验答案与副作用，并按目标 endpoint 记录 usage、账单和延迟。

## 按需取失败时，模型会怎么办

按需取有一个前面没提的风险：**索引与正文是两份数据。** 索引里列着《灾备演练》，取的时候却可能返回 404 —— 文档被删了、权限变了、索引是过期快照。

于是有一个必答的设计问题：**取不到时，模型会如实说「取不到」，还是编一个答案？**

我构造了一次：索引里列 12 篇文档，问的是其中一篇的频率，而那篇的正文返回 `not_found`。

| 回填方式 | 4 次的结果 |
|---|---|
| 标 `is_error` + 写明「文档库中没有该文档的正文，可能尚未上传」+ `retryable: false` | 历史摘要记录 **4/4** 回答报告取不到；原始响应、样本映射和 scorer 未归档，不能独立复核 |

当时的摘要称回答均报告取不到。由于逐次回答和评分规则未保存，这只能作为待复核观察，不能支持“模型可靠地不会编造”或 4/4 的可复核成功率。

**但别把这读成「模型很诚实」。** 这里的对照组是**错误回填已经做对**的情况 —— 而第 4 章实测过：不标 `is_error`，或者标了 `is_error` 却不说原因，模型的行为完全不同（把错误当成数据写进结果，或者拿同样的参数原地重试）。也就是说：

> **宿主应把「取不到」的状态表达清楚，并自行执行授权、重试上限与数据完整性检查。** 错误回填是协议输入，不是对模型服从或可靠性的保证；具体行为需在目标 provider 与任务上验证。

所以设计按需取时，要像设计接口错误码一样设计「取不到」：文档不存在、暂时不可用、无权访问，需要由宿主映射成不同的受控处理。**权限必须在目录生成和每次读取时由宿主校验**；不要把模型的选择或 `forbidden` 错误提示当作授权机制。对不应暴露存在性的资源，返回结果还要避免泄露其存在。三种回填各长这样（示例：构造数据，未实跑）：

```json
// ① 文档不存在 —— 索引过期了，换一篇或者回来问用户
{
  "error": "not_found",
  "message": "资料库中没有 DOC-07 的正文，索引可能是过期快照。",
  "retryable": false,
  "hint": "换一篇候选，或向用户确认标题后重新检索。"
}
```

```json
// ② 暂时不可用 —— 重试可能成功，但要有次数上限
{
  "error": "unavailable",
  "message": "文档服务本次请求超时，未能取回 DOC-07。",
  "retryable": true,
  "hint": "可以原样重试一次；仍失败就如实说明，并继续其余部分。"
}
```

```json
// ③ 无权限 —— 由宿主拒绝读取，并按系统的资源枚举策略控制错误细节
{
  "error": "forbidden",
  "message": "当前凭据无权读取 DOC-07。",
  "retryable": false,
  "hint": "不要重试，也不要用其它文档替代；向用户说明缺少哪一项权限。"
}
```

映射到动作上就是一张表。不同错误应映射到系统允许的处理动作；模型只接收必要的结果提示。宿主应限制重试次数、检查每次读取授权，并避免把未经验证的工具输出当作事实：

| 回填的 error | 宿主应限制的动作 / 可告知模型的状态 | 宿主必须禁止的行为 |
|---|---|---|
| `not_found` | 换候选，或向用户确认 | 编一个答案；反复读同一篇 |
| `unavailable` | 原样重试一次 | 无限重试；把失败当「没有这篇」 |
| `forbidden` | 停止读取并按策略说明权限不足 | 重试同一请求；绕过宿主授权 |

一个容易忽略的细节：**`retryable` 布尔值不能代替宿主的重试策略**。第 4 章保留的历史摘要称，某次只返回 `retryable: true` 后模型重试了同样参数，但原始响应未归档，不能据此预测模型行为。应由宿主限定尝试次数，并把允许的下一步写清楚；不能由模型提示替代授权与预算控制。

## 让索引不容易过期

索引与正文不一致这件事，有一半是**可以工程化消除**的。

三种工程做法：**给索引带来源版本或内容校验和**，读取时核对目标版本，不一致则拒绝返回过期内容；**按更新策略重建或增量更新索引**，并让宿主检查索引的新鲜度；**让查找工具支持候选发现**，标题不匹配时只返回当前调用者有权查看的候选，再由宿主校验最终读取。模糊匹配结果不能自动授权，也不能绕开对象级权限过滤。

第三条的价值在第 4 章出现过一次：那里把「按路径删」改造成「先列出候选再删」，和这里是同一个思路 —— **不要在信息不足时逼模型猜，给它一个能把问题问清楚的动作。**

## 常见坑

**只看单轮 token 就下结论。** 按需取是多轮的，只看最后一次请求会漏掉前几轮。应累加所有轮次的 usage，并按目标 provider 的字段口径分别记录输入、缓存和输出；token 总量不能直接当成账单。

**以为「按需取一定更省」。** 历史单次摘要记录 2/40 时 token 量较低、20/40 时较高；旧轨迹和质量判分缺失，交叉点不可推广。用目标任务、目标 endpoint 和等价答案判据重新测。

**忽略额外往返的延迟。** 按需取可能增加模型和工具往返；实际时延取决于并行度、工具服务、网络和缓存。对交互式应用应直接测端到端延迟，token 数不能代替时延。

**只给内容不给索引。** 模型不知道自己不知道什么。要让它在需要时去取，得先给它一张地图（目录、路径、摘要）。

**不给循环设上界。** 按需取是个循环，必须有硬性轮次上限 —— 否则一个找不到目标的模型会一直读下去。
