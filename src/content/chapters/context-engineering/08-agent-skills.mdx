这一节讲一个具体的东西：**把领域知识打包成可组合的单元，并让运行时按需暴露。**

它是第 3 节（即时检索）在「指令」上的对应物 —— 那一节讲的是「资料不要预先塞入」，
这一节讲的是「**规则**也不要预先塞入」。但“skill”不是所有产品统一的运行时协议：目录格式、发现方式、加载动作、工具权限和数据生命周期都要看具体宿主。下文把 Anthropic 与 OpenAI 官方实现作为两个例子；“按需加载”是可复用的设计模式，不代表必然省 token、必然需要两次模型调用或保证正确率。

## 一、什么是一个 skill

对读者来说，可以把 skill 理解为一份可版本化的能力包，常见内容包括：

**发现信息**：名字 + 描述，用于让运行时或模型识别适用场景。
**操作说明**：`SKILL.md` 正文或等价指令文件，说明具体流程。
**可选资源**：参考资料、模板、脚本等，可按实现方式再读取或执行。

Anthropic 的 Agent Skills 文档明确采用三级渐进披露：元数据在启动时提供，触发后读取 `SKILL.md`，引用资料或脚本再按需要访问。OpenAI Responses API 的 shell skills 和 Agents API capability directories 也提供 `SKILL.md` 目录发现，但接入形式不同。不要把某一种产品的 system prompt 注入方式、工具调用次数或成本口径当成通用协议。

**指令进入上下文的位置也因 runtime 而异。** Anthropic 的文档示例把 Skill 的 `name` 与 `description` 放进 system prompt；触发后，Claude 再通过 bash 从 filesystem 读取正文。OpenAI Responses API hosted shell 则把 `name`、`description` 和 `path` 放进 user prompt，完整 `SKILL.md` 也是用户提示中的指令，优先级与其他 user 提供的指令相同。OpenAI Agents API 从 sandbox capability directories 发现技能，不能把 hosted shell 的挂载格式直接套用过去。遇到“Skill 指令和系统规则冲突”时，先查目标 runtime 实际如何注入；无论处于哪种消息角色，Skill 内容都不能替代宿主授权和执行时策略。

### 它在磁盘上长什么样

一个常见落地形态是**一个目录 + 一份带元数据的说明文件**。Anthropic Agent Skills 和 OpenAI API Skills 都使用 `SKILL.md`；字段校验、发现位置和宿主执行方式仍按各自文档处理。下面是一个教学用的 `amount-norm` 示例（构造数据，未实跑）：

```markdown
skills/amount-norm/SKILL.md

---
name: amount-norm
description: 把各种来源的金额文本归一化成 {value, currency}。用于解析报表、对账单、订单里的金额字段。
---

# 适用条件
只在输入已经确定是「一个金额」时使用。一段文本里混着多个数字时，先切分再逐项调用。

# 规则
1. 去掉千分位逗号，去掉货币符号前后的空格。
2. 货币符号映射：¥ / ￥ / RMB → CNY；$ → USD；€ → EUR。
   没有符号时，继承上下文里最近出现的币种；仍没有就返回 null，不要猜。
3. 括号表示负数：(1,200.00) → value = -1200。
4. 空单元格、-、N/A 一律返回 value = null，**不要返回 0**。
5. 保留两位小数、四舍五入；负数用前导减号。
6. 只做归一化，不做汇率换算 —— 换算是另一个 skill 的事。

# 输出
{"value": -1200.0, "currency": "CNY"}
```

对应的索引只有一行：

```text
amount-norm    把各种来源的金额文本归一化成 {value, currency}
```

注意这几处设计分别对应下面的四个要点：`description` 写明用途和触发场景；正文给出边界与异常处理；适用条件放在开头；还把汇率换算显式排除。此示例只是文档组织样板，**不构成金额解析器**：例如货币符号歧义、币种继承范围、舍入模式、精度和无效输入策略都需由业务契约定义并由代码验证，不能只靠模型照做。

接下来先审查历史实验能支持什么，再决定是否把它当成优化结论。

## 二、历史摘要：三种组织方式

历史记录列出了 6 个 skill（PDF 表格提取、日期归一化、金额归一化、邮箱校验、去重、重试策略）和三种组织方式：

```text
历史路线（仅摘要）     历史判分记录   token 摘要   记录说明
A. 全文预载              5/5           516       6 个 skill 正文预载
B. 只给技能索引          4/5           148       仅有名称与一句话
C. 两阶段选择/加载       3/3           201       记录称两轮合计
```

（`deepseek-flash`，2026-10-08 的历史汇总。逐次请求/响应、精确 endpoint 与模型版本、usage 原文、题目映射、评分器和聚合口径均未归档，不能独立复算。）

**实跑状态：本节未调用真实模型或平台 runtime。** 文件、技能选择和两阶段流程均为构造示例；离线核对只检查文案边界与官方文档引用。

**这些汇总不能证明“省 61% 且正确率不掉”。** A/B 的分母是 5，C 的分母是 3；无法确认 C 与 A 是否是相同任务集、是否采用同一判分器。516 是单次输入还是聚合值、201 是否准确累加两轮，也缺原始 usage 支持。71% 与 61% 只是旧汇总数字的算术比值，不是可迁移的节省预期。

### B 组错的那一个是重点

B 组的历史摘要把「去重」列为一个失败案例：记录 `[A1, a1 , A2]` 按业务键去重后剩几条，旧记录称模型答 **3**，而预期是 **2**。

旧解释把原因归结为完整指令包含「**大小写与首尾空格不敏感**」，索引描述未包含该规则。但没有原始请求/响应、题目样本和 scorer，无法确认模型确实按字面处理，也无法排除别的输入、实现或判分问题；这是一条待复核的假设，不是已验证的因果结论。

这仍然提示一种值得单独评估的风险：

> **如果任务需要明确业务规则，索引描述不能替代该规则。** 缺少规则时模型可能猜测、给默认值或拒绝作答；具体行为要用目标系统和任务集验证。

索引的职责是帮助发现相关指令，不是承载所有业务约束，也不应让它成为模型凭空补规则的依据。

### 按需读取是一种可选设计

对于“模型先发现候选 skill，再按需读取正文”的实现，可以把过程拆成：

```text
第 1 步  由宿主或 runtime 提供候选技能信息（若需要）
第 2 步  模型或宿主选择一个适用 skill，也允许返回“没有”
第 3 步  按版本和权限加载对应说明/资源
第 4 步  模型遵循指令；宿主验证工具调用与最终业务结果
```

两阶段各自那一轮的输入输出长这样（示例：构造数据，未实跑）：

```text
第 1 阶段 · system：
  可用技能（只给名字与一句话描述）：
    amount-norm   把各种来源的金额文本归一化成 {value, currency}
    date-norm     把各种日期写法归一化成 ISO 8601
    dedupe        按业务键对记录去重（大小写与首尾空格不敏感）

阶段选择结果（示例）：
  {"skill_id": "dedupe"}

宿主检查 `skill_id` 是否属于允许列表、是否适用于当前主体和任务，再读取固定版本的 skill 文件。

后续步骤按具体 runtime 的契约提供 `skills/dedupe/SKILL.md`，其中包含「大小写与首尾空格不敏感」这条规则。
```

这是一个实现模式，不是 Agent Skills 的必需协议。由宿主预先路由、模型通过文件工具读取、运行时自动触发，或先做粗粒度目录再读取具体文件，都可能合适。若用自由文本选标识符，解析器需拒绝未知/多项结果；优先用受约束的结构化输出或宿主白名单映射。正文放在何处、是否影响前缀缓存，由具体运行时和 provider 契约决定。

旧记录称 C 条件 3/3，并记两轮输入 201 token；由于缺少原始材料和可比的 A 组任务结果，不据此断言正确率不降或节省比例。

## 三、和「工具定义」的关系

skill 和工具经常被混在一起，但它们解决的是不同的问题：

| | 工具（tool） | skill |
| --- | --- | --- |
| 描述的是什么 | **能做什么**（能力） | **该怎么做**（规则） |
| 谁执行 | 宿主程序/平台调用能力 | 模型遵循指令；如需工具仍由宿主/平台执行 |
| 典型粒度 | 一次操作 | 一类任务的做法 |
| 加载方式 | 由当前 API/运行时暴露可用工具 | 取决于 skill runtime 的发现和读取方式 |

举个例子：**「查订单」通常是一个工具**（宿主代码去数据库读取），
**「退款金额怎么算」可以是一份 skill 指令**（说明判断步骤和规则）。

它们可以配合：skill 可以指导模型何时请求 `lookup_order`，但授权、参数校验、执行、幂等和业务后置条件仍应由宿主负责。skill 的指令会影响模型规划或工具使用，**不等于授权策略或工作流引擎**；把“应该调用”写进文件，不会自动限制模型或工具。

## 四、写一个 skill 的四个要点

**一、描述要说明用途和触发条件。** Anthropic 的 Agent Skills 文档要求 description 同时说明 skill 做什么、何时使用。可以写出触发场景与不适用情形；描述更清晰有助发现，但不能保证模型选对。

**二、正文写可执行的步骤、输入输出和失败处理。** 反直觉规则值得明确；还需说明前置条件、来源、边界、验证方式和遇到缺失/冲突时该停止还是升级。不要为缩短正文删除任务必需的信息。

**三、把触发和范围放在容易发现的位置。** description 负责发现；正文开头再说明适用范围、排除范围、依赖和风险。对不同运行时，触发动作可能由模型、宿主路由器或平台实现。

**四、规则要有边界值和验证。** 例如金额规则应指定舍入模式、币种缺失、负数与无效输入处理；高风险结果由确定性代码校验。更详细的 skill 不自动更正确，必须用正例、边界例、冲突例和拒绝例评测。

## 五、信任与执行边界

Skill 不只是无害的提示词文本。`SKILL.md` 会影响模型计划与工具使用，目录还可能附带脚本、模板和引用资料。Anthropic 提醒审核整个 skill 包；OpenAI 也把技能内容视为需要开发者检查的特权指令，指出它可能导致提示注入、数据外泄或破坏性操作。

因此，安装前应审查来源、版本、所有文件、脚本行为、外部依赖与网络访问；运行时仍要单独做工具 allowlist、身份/对象授权、路径限制、审批和敏感数据控制。Skill 的描述不是权限声明，模型选中了 skill 也不代表用户有权执行其中的动作。高影响操作要由宿主在真正执行边界重新授权并记录。

## 六、技能变多之后怎么评估

技能库扩大时，不能仅凭数量推断成本或选择准确率；要评估发现、检索、阅读和执行的完整路径：

**一、发现信息也有成本，但成本按实现计量。** 有的运行时把元数据加入模型上下文，有的由宿主查找、以文件工具读取或挂载到沙箱；不能假定每个请求都会携带相同索引。记录目标运行时真实输入 usage、文件读取和工具往返。

**二、检索和路由会出现漏选、误选、多个候选、版本不匹配或读取失败。** 这些错误与技能数、任务分布、描述重叠、路由器和宿主实现相关；不要把工具数实验直接外推成 skill 选择规律。用带金标准的任务集统计召回、精确率、误触发和拒绝率，并保留“无适用 skill”选项。

两层索引的形态（示例：构造数据，未实跑）：

```text
第一层（常驻，只给大类）
  finance   金额、对账、退款相关的计算规则
  ops       演练、发布、故障处理相关的操作规则
  text      日期、编码、去重这类文本归一化规则

第二层（模型选中某个大类后，才把该大类下的具体描述拼进来）
  amount-norm   把各种来源的金额文本归一化成 {value, currency}
  refund-calc   按订单状态与渠道计算应退金额
  reconcile     对账差异分类与处理口径
```

分层目录只是可选的检索策略。是否增加一层取决于召回、延迟、读取量、跨类别任务和维护成本；切换类别是否影响缓存也取决于 provider 与请求结构，不保证缓存一定失效。

显式的“先选再加载”可能增加一次模型往返；runtime 内部文件读取、预路由或工具组合则有不同延迟和 token 形态。比较方案时固定任务集、模型版本、回答判据与温度等参数，分别记录总输入/输出 usage、文件/工具调用、端到端延迟、选择错误率和答案质量；将结果限定到该 harness。

### 一个历史解析问题（无法独立复核）

旧笔记称第一阶段按英文 key（如 `amount-norm`）匹配模型输出时，三个任务里有两个被记为「未选中」。原始请求/响应、解析器版本、题目映射和日志未保存，不能验证该计数或归因。

旧解释认为提示只给了**中文描述**（「金额字段归一化」），解析器却只接受英文 key，因此输出无法匹配。这是合理的排查假设，但缺少原始输出，不能作为已确认根因。

一般原则是：**不要靠自由文本猜技能标识。** 为候选集合定义明确的结构化输出和验证；若运行时支持受约束的枚举输出就用它，否则用严格解析、允许空结果并拒绝未知值。即使标识解析成功，也仍需检查该 skill 是否适用、版本是否可信。

提示格式约束只能改善协议清晰度，不能代替机器可验证的 schema、候选白名单和授权检查。

## 七、小结

- Skill 可包含发现信息、指令及可选资源；分层加载是常见模式，具体机制由 runtime 决定。
- 历史 5/5、4/5、3/3 与 token 数缺少原始材料，任务集分母也不一致，不能证明质量不降或 71%/61% 节省。
- Skill 可能影响工具使用并携带可执行脚本；它既不是授权边界，也不等于工作流引擎。
- 用同一任务集对照预载、索引/路由、按需读取，记录 usage、延迟、漏选/误选、质量和安全结果。
- 可信来源审查、工具授权、审批和数据治理由宿主负责；skill 只表达流程指引。

最后，评估 skill 的价值时要看它是否让流程更可复用、更易维护，并在同一验收集上改善目标行为；token 节省、时延和安全性都需要实测，不能由目录结构本身推出。
