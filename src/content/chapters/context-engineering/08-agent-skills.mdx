这一节讲一个具体的东西：**把领域知识打包成可组合的单元，按需加载。**

它是第 3 节（即时检索）在「指令」上的对应物 —— 那一节讲的是「资料不要预先塞入」，
这一节讲的是「**规则**也不要预先塞入」。

## 一、什么是一个 skill

一个 skill 就是一份自包含的指令包，通常包含两部分：

**元数据**：名字 + 一句话描述（「这个 skill 是干什么的」）。
**正文**：完整的操作规则（「具体怎么做」）。

关键设计在于这两部分是**分开的**：元数据始终可见（成本极低），正文按需加载。
于是模型的能力清单可以很长，而上下文占用可以很小。

### 它在磁盘上长什么样

这一层不落地，读者就不知道 first skill 该写成什么。常见的形态是**一个目录 + 一份带元数据的说明文件**（Anthropic 的 Agent Skills 用 `SKILL.md`，元数据放文件头的 YAML frontmatter，正文是文件其余部分）。下面是本节那 6 个 skill 里的 `amount-norm` 的全文（示例：构造数据，未实跑）：

```markdown
skills/amount-norm/SKILL.md

---
name: amount-norm
description: 把各种来源的金额文本归一化成 {value, currency}。用于解析报表、对账单、订单里的金额字段。
---

# 适用条件
只在输入已经确定是「一个金额」时使用。一段文本里混着多个数字时，先切分再逐项调用。

# 规则
1. 去掉千分位逗号，去掉货币符号前后的空格。
2. 货币符号映射：¥ / ￥ / RMB → CNY；$ → USD；€ → EUR。
   没有符号时，继承上下文里最近出现的币种；仍没有就返回 null，不要猜。
3. 括号表示负数：(1,200.00) → value = -1200。
4. 空单元格、-、N/A 一律返回 value = null，**不要返回 0**。
5. 保留两位小数、四舍五入；负数用前导减号。
6. 只做归一化，不做汇率换算 —— 换算是另一个 skill 的事。

# 输出
{"value": -1200.0, "currency": "CNY"}
```

对应的索引只有一行：

```text
amount-norm    把各种来源的金额文本归一化成 {value, currency}
```

注意这几处设计分别对应下面的四个要点：`description` 里写了「用于解析报表、对账单、订单」，这是**区分**，不是概括；正文只写反直觉的部分（千分位、括号负数、空单元格返回 null 而不是 0），「数字要归一化」这种常识一个字都没有；「# 适用条件」在正文开头；规则 5 给了边界值。整份正文约 110 字。

这听起来像纯粹的优化，但实测下来有一个必须注意的陷阱。

## 二、实测：三种组织方式

我准备了 6 个 skill（PDF 表格提取、日期归一化、金额归一化、邮箱校验、去重、重试策略），
每个的完整指令约 80~120 字。然后测三种方式：

```text
方式              正确率   单次输入 token    说明
A. 全部完整指令预载   5/5        516        6 个 skill 的正文全在 system 里
B. 只给技能索引      4/5        148        只有「名字 + 一句话」，省 71%
C. 两阶段按需加载    3/3        201（两轮）  先给索引选中，再加载该 skill 的正文
```

（实测数据，`deepseek-flash`，2026-10-08。token 为该项请求的输入 token。）

### B 组错的那一个是重点

B 组五个任务错了「去重」：记录 `[A1, a1 , A2]` 按业务键去重后剩几条，
模型答 **3**，正确答案是 **2**。

原因很简单：完整指令里有一条规则是「**大小写与首尾空格不敏感**」，
而索引里的那句话说不到这么细。**模型没有这条规则，就退回了通用直觉** ——
它按字面看 `A1`、`a1 `、`A2` 是三个不同的串。

这是索引模式最容易被低估的代价：

> **缺规则时模型不会停下来问，它会用一个看起来合理的默认值继续做。**
> 而那个默认值通常是错的 —— 因为如果通用直觉够用，你就没必要写这条规则了。

**你写的每一条规则，都是「通用直觉会出错」的证据。** 把它们藏起来，等于把错误放出来。

### C 组才是正确的形态

B 组失败的原因是它只做了一半。真实的 skill 机制是**两阶段**：

```text
第 1 步  system 里只放索引（名字 + 一句话）
第 2 步  模型看完问题，输出「我要用哪个 skill」
第 3 步  把那个 skill 的完整正文加载进来
第 4 步  模型在「有完整规则」的情况下答题
```

两阶段各自那一轮的输入输出长这样（示例：构造数据，未实跑）：

```text
第 1 阶段 · system：
  可用技能（只给名字与一句话描述）：
    amount-norm   把各种来源的金额文本归一化成 {value, currency}
    date-norm     把各种日期写法归一化成 ISO 8601
    dedupe        按业务键对记录去重（大小写与首尾空格不敏感）

第 1 阶段 · 要求输出格式（关键，见下面那个真实报错）：
  只输出标识符本身，例如 amount-norm。不要解释，不要输出描述文字。

第 1 阶段 · 模型返回：
  tool_use  select_skill({"name": "dedupe"})

第 2 阶段 · 把 skills/dedupe/SKILL.md 的正文拼进 system 后重问：
  模型这时才看到「大小写与首尾空格不敏感」这条规则，因此答对
```

**「选中」既可以用一次工具调用，也可以让模型纯文本输出标识符** —— 两种都行。真正的关键是第 1 阶段那句输出格式要求，以及第 2 阶段把正文拼在**稳定前缀**里（原因见第 6、7 节）。

实测 C：3 个任务全部正确，两轮总输入 201 token。
同样的 3 个任务在 A 下是 516 token —— **省 61%，而且正确率不掉**。

## 三、和「工具定义」的关系

skill 和工具经常被混在一起，但它们解决的是不同的问题：

| | 工具（tool） | skill |
| --- | --- | --- |
| 描述的是什么 | **能做什么**（能力） | **该怎么做**（规则） |
| 谁执行 | 你的代码 | 模型自己 |
| 典型粒度 | 一次操作 | 一类任务的做法 |
| 加载方式 | 定义必须在上下文里 | 元数据常驻，正文按需 |

举个例子：**「查订单」是一个工具**（你的代码去数据库拿数据），
**「退款金额怎么算」是一个 skill**（模型按规则决定退多少）。

它们也会配合：一个 skill 里可以写「先调用 `lookup_order`，再按下面规则判断」，
把工具调用顺序也固化下来。**这时候 skill 实际上在承担一部分工作流编排的职责** ——
这是它比「工具描述」更强的地方，也是它更危险的地方（规则写错了它照做）。

## 四、写一个 skill 的四个要点

**一、描述要能区分，不是概括。** 索引里那句「从 PDF 中提取结构化表格」要能让模型判断
「这个任务需要它吗」。如果两个 skill 的描述都能覆盖当前任务，那就是描述写得不够具体。

**二、正文写「反直觉的部分」，不写常识。** 「数字要归一化」不用写，
「千分位要去掉、空单元格用 null 而不是空串」才要写。
这直接减少正文长度 —— 而正文长度决定加载成本。

**三、把触发条件写在正文开头。** 一个 skill 被选中之后，模型要知道「什么情况下适用、
什么情况下不适用」。少了这条，它会把规则套到不该用的任务上。

**四、规则要有边界值。** 「保留两位小数」不如「保留两位小数，四舍五入，
负数用前导减号」—— 后者不会在边界上产生歧义。这和上一节 system prompt 那句
「规则一多必然自相矛盾」是同一个问题的两面。

## 五、技能变多之后会发生什么

上面测的是 6 个 skill。真实系统里可能是 30 个、100 个。这时候两件事会变：

**一、索引本身开始占成本。** 一句话描述比完整正文便宜得多，但它**每个请求都要付**。
别拍一个「每个描述多少 token」的数字 —— 把索引用一次请求发出去，读 `usage` 里的输入 token 即可，方法和第 4 章测工具定义成本完全一样。所以索引也要控制粒度：**描述写「这个 skill 覆盖哪一类任务」，不要写它的做法。** 做法属于正文。

**二、选择本身开始出错。** 6 个里选 1 个不难，100 个里选 1 个就难了 ——
而且失败形态和索引质量直接相关：描述太接近，模型就选错或选多个。
这是第 4 章那条「工具数量与选择准确率」的同一个问题，只是换成了 skill。
缓解办法也一样：**先按大类分组，再在组内选**（两层索引），而不是平铺 100 个。

两层索引的形态（示例：构造数据，未实跑）：

```text
第一层（常驻，只给大类）
  finance   金额、对账、退款相关的计算规则
  ops       演练、发布、故障处理相关的操作规则
  text      日期、编码、去重这类文本归一化规则

第二层（模型选中某个大类后，才把该大类下的具体描述拼进来）
  amount-norm   把各种来源的金额文本归一化成 {value, currency}
  refund-calc   按订单状态与渠道计算应退金额
  reconcile     对账差异分类与处理口径
```

它和第 4 章 4.5 节「工具分组加载」是同一个模式、同一个代价：先选组能省钱，
但**换组会改写前缀、断开缓存**（第 7 节）。所以两层索引适合「一次任务只落在一个大类里」的场景；
任务会在多个大类之间来回跳时，分组反而更贵。

还有一个容易被忽略的成本：**两阶段意味着两轮请求**。
上面 C 组的 201 token 是「两轮加起来」的输入 —— 它比 A 组省，
但**多了一次往返的延迟**。如果你的任务是交互式的、每次都只有一两个 skill 相关，
那这个延迟可能不值得省；如果是批量处理、延迟不敏感，两阶段就很划算。
**省 token 和省时间经常是矛盾的**，这一条在选择实现方式时要一起考虑。

### 一个真实的报错

我第一次实现两阶段加载时，第一阶段问了「你要用哪个 skill」，
然后按 key（`amount-norm` 这样的英文标识）去匹配模型输出。结果三个任务里两个「未选中」。

原因是我在问句里给的是**中文描述**，模型自然也回中文描述
（「金额字段归一化」），而我拿英文 key 去匹配。

这个 bug 的形态值得记：**模型的输出格式取决于你给它的输入格式。**
你在索引里列中文，它回中文；列英文标识，它回英文。
而如果你两边混着用（列中文、按英文匹配），就会得到「模型明明答对了但解析不出来」。

所以选择阶段的解析要**同时接受 key 和描述**，或者干脆在提示里明确要求
「只输出标识符，例如 `amount-norm`」。后者更好 ——
**别让解析器去猜模型会输出什么，要在提示里把输出格式钉死。**

## 六、小结

- **skill = 元数据 + 正文**，元数据常驻、正文按需，这是它能扩展的原因
- **只给索引比全部预载省 71%**，但实测正确率从 5/5 掉到 4/5
- **缺规则时模型不会停下来问**，它会用通用直觉给一个看起来合理的错答案
- **必须两阶段**：索引 → 选中 → 加载正文 → 再答。实测省 61% 且正确率不掉
- **你写的每条规则都是「直觉会出错」的证据**，把它藏起来等于把错误放出来
- **skill 描述「怎么做」，工具描述「能做什么」** —— 前者模型自己执行，后者你的代码执行

最后一句话：**skill 的价值不在于「省 token」，而在于「让规则可以被有选择地应用」。**
省下来的 token 只是副产品；真正的收益是你能为一个系统写下一百条规则，
而每条规则只在它该出现的时候出现。
