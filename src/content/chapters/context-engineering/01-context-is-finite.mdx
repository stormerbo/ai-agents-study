上下文工程里常被引用的两个经验现象是：

1. **Lost in the Middle** —— 在论文所测的模型、任务和上下文长度中，关键信息的位置会影响表现；部分设置呈 U 形
2. **context rot** —— 某些任务与模型中，随着上下文变长，任务表现可能下降

先把词说清楚，否则这两条只是口号。

**注意力机制不是利用率的直接测量。** Transformer 的注意力计算会对表示做加权汇总，但内部注意力权重不能直接等同于模型是否取回、理解或正确使用了一条信息。这里讨论的「利用率」应以具体任务的正确率等外部表现衡量。因而，**一条信息「在不在上下文里」和模型「能否在任务中正确使用它」是两件事**；位置效应是任务表现上的经验结果，不应简化成「token 越多，注意力权重就被稀释」。

**Lost in the Middle 讲的是什么。** 那篇论文在其受测模型、检索任务和长度范围内观察到位置敏感的任务表现，部分设置呈现开头与结尾较好、中间较差的 U 形。它是一个**有适用边界的经验观察**，不是所有模型和任务都必然呈现的规律，也不是已确立的内部机制。所以本节的重点不是「背下 U 形」，而是「在你的模型、任务和语料上测一遍」。

**context rot 不是「窗口满了」。** 窗口超限通常会由接口拒绝或报错；context rot 是对一种可能的性能变化的概括：在特定模型与任务中，即使未达到容量上限，上下文变长也可能使任务表现下降。它不一定报错，也不能从 usage 直接读出；需要控制任务与材料，对比不同上下文规模下的表现。下降幅度、是否出现以及原因都依赖具体设置，不能概括成内容每增加一点、每条信息就必然少被利用一点。

**语义 needle。** needle（针）指在一份长文档里埋一条**全文唯一**的信息（比如某个项目被标为「已停用」），问题要求把它读出来。它与第 0 章那种机械标记的区别是：机械标记靠一个字形奇特的串就能定位，不需要理解；而语义 needle 要求模型真的读懂那一段在说什么，还能和问题对上。

**prompt caching。** 一些服务商会缓存重复请求中的前缀，后续请求复用缓存可减少相应计算或费用；具体匹配边界、缓存断点、保留时间及计费方式由服务商、模型与端点契约决定。某些实现要求缓存前缀对应的 token 序列完全一致，但不能把「逐字不变」当作所有服务商的通用规则。机制见第 1 章第 5 节，它与「前缀」的关系见本章第 7 节。

第 0 章我提过一次：用「机械标记」测位置效应，**没能复现**。当时我说，更接近论文设定的做法是用真实任务而不是机械标记。

这一节就是把那句话兑现 —— 我换了四种更强的设计重测，**结果全都没复现**。而且过程中有一次「失败」其实是我自己的测量 bug，那一段可能是本节最值得读的部分。

## 实测：五次设计，都没复现

任务都要求**真的读懂文档**才能回答（不是照抄一个标记）。设计从弱到强：

| # | 设计 | 文档规模 | 位置扫描 | 容量扫描 |
|---|---|---|---|---:|
| ① | 机械标记（第 0 章做的） | 12k 字符 | 3 位置全遵守 | — |
| ② | 两跳 lookup（先找到设备，再查规格表） | 150 段 ≈ 6.4k token | 5 位置 **15/15** | 10→260 段全对 |
| ③ | 语义 needle（全文只有一段「已停用」） | 150 段 ≈ 5k token | 5 位置 **15/15** | — |
| ④ | 语义 needle，放大到 600 段 | 600 段 ≈ 22.8k token | 5 位置 **15/15** | — |
| ⑤ | 异质段落 + 复合条件 | 400 段 ≈ 15.8k token | 5 位置 **15/15** | 40→400 段全对 |

（实测数据，`deepseek-flash`，2026-10-08。位置扫描取开头 / 前 1/4 / 正中 / 后 1/4 / 结尾五个点，每点 3 次。）

设计 ⑤ 是最接近论文设定的一次，值得展开说：

- 每一条都是**句式不同**的项目条目（400 个项目，各有负责人、阶段、预算、风险等级），不是同一句话复制 400 遍
- 问题要求**同时满足两个条件**才能定位：「风险等级为高」**且**「预算超过 200 万元」
- 文档里有 **134 个**「风险为高」的干扰项、**266 个**「预算超 200 万」的干扰项 —— 只满足一个条件就会被带偏

那三条条目长这样：

```text
（示例：构造数据，未实跑）
P-0271｜负责人：周越｜阶段：已上线｜预算：86万元｜风险等级：高     ← 干扰项①：只满足「风险高」
P-0302｜负责人：李蔓｜阶段：验收中｜预算：240万元｜风险等级：高    ← 正确条目：两条都满足
P-0388｜负责人：陈迟｜阶段：已上线｜预算：310万元｜风险等级：中    ← 干扰项②：只满足「预算超 200 万」
```

**判据：答案必须由两个字段联合推出。** 只看「风险高」会命中 P-0271（以及另外一百多条），只看「预算超 200 万」会命中 P-0388，只有同时读两个字段才能落到 P-0302。如果一个问题靠一个关键字、或者照抄文档里某个标记就能答出来，它测的是字符串匹配，不是「读懂」—— 那类设计会给出漂亮的假象（第 0 章那次没复现就是这个原因）。

**怎么造干扰项。** 先写下你要证明「模型真的读懂了」的那个联合条件（这里是两个字段同时成立），然后**为每个单独条件各造一批只满足它的条目** —— 它们的作用就是让「只匹配一个关键字」的策略失败。句式不能复制粘贴：负责人、阶段、预算、风险四个字段都要变化，否则模型可以靠位置或格式猜出答案。

**结果：无论把答案那条放在开头、正中还是结尾，都是 3/3 全对。**

## 唯一一次「失败」，是我自己的 bug

上面那张表里，设计 ⑤ 在 400 段规模下**一度是 0/3 全错**。我差点把它写成「容量效应复现了」。

先说两个字段：`max_tokens` 是请求里「最多生成多少 token」的上限，`stop_reason` 是响应里「这次为什么停下来」的字段 —— 两者合起来才能判断一次调用是被截断还是正常结束。

但我看了一眼原始输出，是这样：

```text
文档 400 段，max_tokens = 800

#1  stop_reason=max_tokens   输出文本：（空）
#2  stop_reason=max_tokens   输出文本：（空）
#3  stop_reason=max_tokens   输出文本：（空）
```

**输出是空的。** 不是答错，是**什么都没输出**。

原因：这类模型会先思考再回答（第 2 章讲过），而**长上下文会让它思考得更久**。我把 `max_tokens` 设成了 800 —— 思考过程就把输出预算吃光了，模型还没开始写答案就被截断。

把 `max_tokens` 提到 6000，同一份文档、同一个问题：

```text
#1  stop_reason=end_turn   输出：P-0302
#2  stop_reason=end_turn   输出：P-0302
#3  stop_reason=end_turn   输出：P-0302
```

**15/15 全对**（五个位置各 3 次）。

> 这正是第 0 章「截断不报错」那条直觉的实例。注意 `stop_reason` 在这里的价值 —— 如果我只统计「输出里有没有正确答案」，我会得到「模型在长上下文下失败了」这个**完全错误**的结论。
>
> **先怀疑测量方法，再怀疑被测对象。** 这条已经在本站出现过两次了（另一次是第 0 章的缓存污染）。

## 那这两个结论还成立吗

**我的结论只能说这么远：在我测的设计与规模里，没复现。**

不能反过来说「效应不存在」。原因很清楚 —— 我的实验和论文的设定有几处**实质性差异**：

| | 论文的设定 | 我的实验 |
|---|---|---|
| 文档来源 | 真实语料（多篇文档，话题各异，含冗余与噪声） | 我合成的，句式规律 |
| 任务 | 多文档 QA，答案需要**跨文档综合** | 单跳或两跳的定位 |
| 被测模型 | 2023 年的模型 | 2026 年的模型 |
| 规模 | 可达数万 token | 最高 22.8k token |

**第 2 行是关键。** 我的任务无论怎么加强，本质仍是「在文档里找到一个能回答问题的位置」；而论文测的是「读完之后能不能**用**这些信息」。这两件事对注意力的要求不同。

第 4 行也不能忽略 —— 这个结论被引用了三年，模型在长上下文上的能力本身就在快速变化。

> **教学价值不在「我推翻了论文」。** 而在于：**一篇被广泛引用的论文，它的结论在你的场景里未必成立，而验证成本其实很低** —— 上面这些实验加起来不到两小时。这跟第 2 章那六个「未复现」是同一件事。

## 那工程上该怎么做

有意思的地方在这里：**即使效应没复现，克制使用上下文的工程理由一条都没少。**

它们和「模型读不读得到」无关：

**① 成本按轮次重复计费。** 多塞 1000 token 不是一次性的 —— agent 每跑一轮，这 1000 token 都要重新计费一次（第 1 章的 prompt caching 能省一部分，但缓存有失效条件）。一个 20 轮的循环里，这 1000 token 的实际成本是 20000 token。

**② 延迟。** 输入越长，首字节延迟越高。对交互式应用，这是用户直接感知的东西。

**③ 你的真实文档比我的合成文档脏得多。** 我的 400 段句式整齐、无矛盾、无歧义；真实语料里有相互矛盾的说法、有过期信息、有和问题无关的长篇大论。**我在干净数据上看不到效应，不代表你在脏数据上也看不到。**

所以结论不是「随便塞」。而是：**判断依据要放对地方** ——

| 别这么说 | 该这么说 |
|---|---|
| 「中间的信息模型读不到，所以放头尾」 | 「放头尾是零成本的保险；真正决定成本的是 token 总量」 |
| 「窗口够大，全塞进去就行」 | 「每轮都重新计费，塞进去的每一段都要有明确用途」 |
| 「论文说了 U 形，所以按 U 形优化」 | 「先在自己的数据上测一遍，再决定怎么排」 |

最后一行才是这一节真正想教的。下面是可以直接跑的测试脚本。

## 完整可运行代码

```python
# lost_in_middle_test.py
"""在**你自己的文档与问题**上测位置效应。

这是本节唯一重要的交付物 —— 因为「有没有位置效应」依赖模型版本与你的数据类型，
任何别人的结论（包括论文，也包括我上面那张表）都不能直接套用。

用法：把 DOCS 换成你的真实文档，把 QUESTION / ANSWER 换成你的任务。
"""

import os
import random
import re

import anthropic

client = anthropic.Anthropic(
    api_key=(
        os.environ.get("ANTHROPIC_API_KEY")
        or os.environ.get("ANTHROPIC_AUTH_TOKEN")
    ),
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)
MODEL = os.environ["VERIFY_MODEL"]

# ── 语料：先用确定性生成器造一份可跑的；换成真实文档时整段替换 ──
# （示例：构造数据，未实跑。它只保证形状与本节实测那批一致，不是同一批文档。）
NEEDLE_INDEX = 302
ANSWER = "P-0302"
QUESTION = "哪个项目同时满足「风险等级为高」和「预算超过 200 万元」？只回答项目编号。"


def build_corpus(n: int = 400, seed: int = 20261008) -> list[str]:
    """生成 n 条句式不同的项目条目，其中恰好一条同时满足两个条件。

    除正确条目外，每条**只满足一个**条件：
      干扰项① 只满足「风险为高」，干扰项② 只满足「预算超 200 万」。
    这样「只匹配一个关键字」的策略必然被带偏 —— 这是判定「读懂」的前置。
    """
    rng = random.Random(seed)
    people = ["周越", "李蔓", "陈迟", "赵昀", "孙可", "吴攸"]
    stages = ["已立项", "开发中", "验收中", "已上线", "已归档"]
    docs = []
    for i in range(n):
        if i % 3 == 0:                                  # 干扰项①：只满足风险条件
            budget, risk = rng.choice([60, 86, 120, 180]), "高"
        else:                                           # 干扰项②：只满足预算条件
            budget, risk = rng.choice([240, 310, 420]), rng.choice(["低", "中"])
        docs.append(
            f"P-{i:04d}｜负责人：{rng.choice(people)}｜阶段：{rng.choice(stages)}"
            f"｜预算：{budget}万元｜风险等级：{risk}"
        )
    docs[NEEDLE_INDEX] = "P-0302｜负责人：李蔓｜阶段：验收中｜预算：240万元｜风险等级：高"
    return docs


DOCS = build_corpus()


def check_criterion() -> None:
    """先确认题目本身合格：单独匹配任一条件都会命中干扰项。"""
    assert DOCS[NEEDLE_INDEX].startswith(ANSWER), "正确条目不在预期位置"
    high = [d for d in DOCS if "风险等级：高" in d]
    rich = [d for d in DOCS if any(f"预算：{b}万元" in d for b in (240, 310, 420))]
    both = set(high) & set(rich)
    assert both == {DOCS[NEEDLE_INDEX]}, "干扰项与正确条目的联合条件重叠了"

# ⚠️ 关键：给思考留足预算。设小了会得到**空输出 + stop_reason=max_tokens**，
#    让你误判成「模型在长上下文下失败了」（本节就踩过）。
MAX_TOKENS = 6000
TRIALS = 3


def build_doc(needle_pos: int) -> str:
    others = [d for i, d in enumerate(DOCS) if i != NEEDLE_INDEX]
    lines = others.copy()
    lines.insert(needle_pos, DOCS[NEEDLE_INDEX])
    return "\n\n".join(lines)


def ask(doc: str) -> tuple[str, str]:
    """返回 (文本输出, stop_reason)。"""
    response = client.messages.create(
        model=MODEL,
        max_tokens=MAX_TOKENS,
        system="只依据用户提供的文档回答。只给出答案，不要解释。",
        messages=[
            {
                "role": "user",
                "content": f"<document>\n{doc}\n</document>\n\n问题：{QUESTION}",
            }
        ],
    )
    text = "".join(b.text for b in response.content if b.type == "text")
    return text, response.stop_reason


if __name__ == "__main__":
    check_criterion()          # 先确认题目合格，再开始测
    n = len(DOCS)
    positions = {
        "开头": 0, "前 1/4": n // 4, "正中": n // 2,
        "后 1/4": n * 3 // 4, "结尾": n - 1,
    }

    print(f"{'位置':<8} {'正确':>6} {'截断':>6}   模型答的")
    print("-" * 52)

    for label, pos in positions.items():
        doc = build_doc(pos)
        ok = cut = 0
        said = []
        for _ in range(TRIALS):
            text, stop = ask(doc)
            if stop == "max_tokens":
                # 截断不是「答错」—— 必须单独统计，否则结论会完全跑偏
                cut += 1
                said.append("截断")
                continue
            if ANSWER in text:
                ok += 1
            said.append(text.strip()[:12] or "空")

        print(f"{label:<8} {ok}/{TRIALS:>3} {cut}/{TRIALS:>3}   {','.join(said)}")
```

> **实跑状态**：本文表格里的**数据是实测的**（用直接 HTTP 请求采集）；上面这份 Python 脚本用的是 SDK 写法，字段与采集脚本一致，但**脚本本身未在官方端点验证**。

## `max_tokens` 到底该给多少

本节踩的那个坑值得再补一句可操作的做法，因为它每次都会以「模型不行」的面目出现。

**别凭感觉设。** 先用一个明显过大的值（比如 8000）跑一次，读响应里的 `usage.output_tokens` —— 那个数字包含了思考过程，它才是你的真实下限。之后把预算定在它的 2 倍左右：留出思考长度随输入变化的余量，又不至于让一次跑飞的调用烧掉太多。

**并且把「空输出 + `stop_reason=max_tokens`」当成一个独立分支处理**：它不是失败，是**预算不足**。正确的反应是带着更大的预算重试一次，而不是记一条「模型没答出来」的日志 —— 后者会让你在几周后基于一个错误的统计做出架构决策。

**判据只有一条：没确认 `stop_reason` 之前，不要解释任何「模型没答出来」的结果。**

## 常见坑

**把「截断」当成「答错」。** 本节最贵的一课：长上下文会让思考变长，`max_tokens` 不够时返回**空输出**。必须单独统计 `stop_reason == "max_tokens"`。

**因为没复现就断言「效应不存在」。** 我测的是定位类任务，论文测的是多文档综合。规模也差一个量级。**没复现 ≠ 被推翻。**

**以为「窗口还有空间」就等于「可以继续塞」。** 即使模型真的能读全，还有成本和延迟两条硬约束，而且它们随轮次放大。

**拿别人的结论（包括本文的表格）直接套。** 位置效应依赖模型、任务、数据三者的组合。上面的脚本跑一遍你自己的数据，成本不到十分钟。
