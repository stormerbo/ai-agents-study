这一节讲一层平时看不见的东西：**你发出去的消息数组，和模型实际读到的 token 串，不是一回事。**

中间那一步叫 Chat Template —— 它把「role + content」的结构渲染成模型能吃的标记序列。
理解它的存在，能解释好几个反直觉的现象。

## 一、实测：同样的内容，token 差 25%

10 行规则（约 310 字符）加一句问题。两种组织方式，**内容字符数完全相同**：

```text
组织方式                    input token   消息数
合并成一轮 user                  238          1
拆成 10 轮 + 10 条应答            298         21
```

**差 60 token，25%。** 多出来的部分不是内容 —— 内容一个字都没变。
它来自 **20 个角色边界**：每一轮 user 和 assistant 都要用一对特殊标记
（形如 user / assistant 的控制标记）包起来，这些标记也占 token。

这个数字值得记住，因为它是一条很容易踩的成本来源：**对话轮数本身要花钱。**
一个 20 轮的会话，即使每轮只问一句话，光是角色标记就有几百 token。
而且它是**每轮都重发**的（历史消息会被重发，见第 1 章第 4 节）。

### 位置也会改变 token 数

同一段规则块，放在不同位置：

```text
结构                        input token
A. 全部放 system                 234
B. 全部放第一条 user               238    (+4)
C. 一半 system 一半 user           234     (0)
D. 同一句问题问两轮                254    (+20)
```

差别不大（几到几十 token），但它证明了一件事：**位置和角色会影响渲染结果。**
所以「我把同一段文字挪了个位置」在 token 层面**不是一个等价操作**。

## 二、为什么这件事重要

**一、你改的不是文字，是 token 串。** 同一句中文，加一个空格、换一个引号类型
（全角/半角）、把顿号改成逗号，渲染出来的 token 可能完全不同。
这解释了一个常见困惑：「我只改了个标点，为什么 token 数变了那么多？」

**二、跨厂商的渲染不同。** 你的内部表示是「配置 + 历史」两段，
而 OpenAI 把 system 当成 messages 里的第一条 —— 这一层转换就是 Chat Template 的差异。
第 8 章讲适配层时提到的三个结构性差别，本质都是这一层的差别。

**三、它决定了缓存的边界。** 上一节讲的「前缀哈希」不是对你写的 JSON 做哈希，
而是对**渲染后的 token 串**做哈希。所以消息结构变了，缓存就断了 ——
哪怕内容一个字没改。

## 三、三个可操作的推论

**推论一：能用一轮说完的，不要拆成多轮。** 上面的实测是 25% 的差距。
当然这条有边界：把无关内容全塞进一轮会稀释注意力（第 2 节那个 system prompt 高度的实验）。
**判据是：同样的内容如果本来就要一起用，就别拆轮次；如果不相关，就别合并。**

**推论二：别把「结构变化」当成免费操作。** 在长会话里调整消息顺序、
插入一条系统提醒、把某段内容从 system 挪到 user —— 这些都可能在缓存层产生代价。
做这类改动后，值得看一眼 usage 字段。

**推论三：不要手写 token 估算公式。** 因为「字符数 ÷ 4」这类估算对中文、
对结构化标记都不准。要比就实测：用响应里的 input_tokens 字段对比两个版本的差异，
这比任何估算都可靠。

## 四、代码：估算结构成本

```python
def structural_overhead(messages, baseline_tokens, baseline_messages=1):
    """粗略估算角色边界带来的额外 token。"""
    extra = (len(messages) - baseline_messages) * 3      # 每条消息约 3~5 token 的边界标记
    return {"消息数": len(messages), "额外 token 估算": extra,
            "占基准比例": "%.0f%%" % (100.0 * extra / max(baseline_tokens, 1))}


def compare_structures(render_and_count, variants):
    """同一份内容的不同结构各实测一次 token。"""
    out = []
    for name, system, messages in variants:
        out.append((name, render_and_count(system, messages)))
    base = min(t for _, t in out)
    return [(n, t, "%.0f%%" % (100.0 * (t - base) / base)) for n, t in out]
```

第二个函数的用法就是本节做实验的方式：**同一个模型、同一份内容、
几种结构各测一次，看 token 差多少。** 这是唯一可靠的判断方法。

注意上面那个 3 是经验值 —— 不同厂商的模板标记长度不同，
所以它只能用来做量级估算，不能替代实测。**要精确值就实测，不要推算。**

### 一个真实的错误

我在第 18 章做成本实测时，为了「让模型更好地记住早期指令」，
在每个用户回合前面**追加一条很短的系统提醒**（大约 15 个字）。
当时的想法是「15 个字，可以忽略不计」。

跑完之后发现成本涨了明显一截。原因有两层：

- **表面上**：每轮多了一条消息，边界标记 + 那 15 个字，约 20 token
- **真正的大头**：**这条提醒插在中间，破坏了前缀稳定** —— 上一节讲过，
  改开头会导致后面全部失效。而那些「早期指令」本来已经被缓存了

所以真实代价远大于 20 token：**它是「缓存全废」而不是「多几条消息」。**

这个错误很典型：**你以为是加了一点内容，实际是改了一个结构。**
而结构改动在缓存层的代价是内容改动的几十倍。
所以一条实用的规则是：**要加内容，加在末尾。** 除非有明确理由，不要往中间插东西。

## 五、什么时候该关心这一层

这一层大多数时候可以不管 —— 你的请求正常、成本可接受，就没必要去研究模板。
但有四个时刻它值得你花时间：

**一、成本突然涨了而内容没变。** 检查是不是有人加了系统提醒、
改了消息顺序、或者引入了新的消息类型。这一层的变化不会触发任何报错。

**二、跨厂商迁移。** 你要把同一套请求发到两个厂商。这时候「我用的是同一份内容」
这个说法是不成立的 —— 渲染出来的 token 串不同，成本与缓存行为都不同。
第 8 章讲适配层时，这是最容易出错的一层。

**三、缓存命中率不达预期。** 上一节的排查清单里，「序列化是否确定」
和「结构是否稳定」这两条都属于这一层。

**四、你在做提示词的 A/B 对比。** 如果两个版本的**结构**不同（不只是措辞不同），
那么成本差异可能来自结构而不是措辞。**做 A/B 时最好只改一处**，
否则你分不清是哪个改动带来的效果。

还有一个反过来的场景：**当你需要省 token 时，这一层往往有比「删内容」更划算的空间。**
本节那个 25% 的例子说明，光是调整消息组织方式就能省掉四分之一，
而这不需要砍掉任何实质信息。**先看结构，再砍内容。**

## 六、一个具体的例子：同一条规则，两种写法

假设你想让模型「退款前必须确认订单存在」。两种写法：

```text
写法一（放在 system 的规则块里）
  system: ...规则 7：退款前必须先调用 lookup_order 确认订单存在...
  问题:   把订单 A-1001 退了

写法二（在每轮 user 消息前加一句提醒）
  system: ...（没有这条规则）...
  user:   注意：退款前必须先确认订单存在。
          把订单 A-1001 退了
```

从「模型能不能遵守」的角度，两种写法可能都对。但从成本角度：

- **写法一**：规则在 system 里，是稳定前缀的一部分 —— **只付一次，之后命中缓存**
- **写法二**：提醒在 user 消息里，**每轮都不同** —— 前缀从这条消息开始就变了，缓存断掉

而且写法二还有个更隐蔽的问题：**它会随对话轮次累积。**
如果每轮都加一句提醒，20 轮之后历史里有 20 句几乎相同的话，
既占 token 又可能让模型以为这是 20 条独立的约束。

**结论：凡是「每次都适用」的规则，都应该放在稳定前缀里。**
动态提醒只适合「只在这一轮适用」的内容 —— 而且最好也放在末尾。

这个例子的价值在于它很常见：**很多人加提醒的位置是随手选的，
而位置决定了它是「付一次」还是「付每一次」—— 这个差别在长会话里会被放大几十倍。**

## 七、小结

- **Chat Template 是「消息数组 → token 串」的渲染层**，你的输入不等于模型的输入
- **同样的内容，拆成 10 轮比合并成 1 轮多 60 token（25%）** —— 轮数本身要花钱
- **位置与角色会影响渲染结果**，所以「挪个位置」不是等价操作
- **缓存哈希是对渲染后的 token 串做的**，结构变了缓存就断
- **要加内容就加在末尾** —— 往中间插会破坏前缀稳定，代价是几十倍
- **不要手写 token 估算公式**，用响应里的 usage 字段对比两个版本实测
