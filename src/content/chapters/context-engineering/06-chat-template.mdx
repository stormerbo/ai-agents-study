这一节讲一层平时看不见的东西：**应用提交的消息结构、provider 实际计数的输入 token，以及模型内部的序列化格式，不应当混为一谈。**

很多本地推理框架会显式用 chat template 把角色消息渲染成模型专用的控制 token；托管 API 往往只暴露结构化请求和 usage/count-token 接口，不保证把最终模板或精确 token 字符串公开给调用方。工程上应把它当作 provider/model 的实现边界，用目标端点的计数和文档验证，而不是根据 JSON 形状猜内部标记。

## 一、历史观察：消息结构与内容没有被干净地分离

2026-10-08 的历史记录比较了「合并成一条 user」与「10 条 user 规则 + 10 条 assistant 应答 + 最后一条问题」两种请求，并留下 238 与 298 两个输入 token 汇总值。但逐次请求/响应、准确 endpoint/model、usage 原文和评分材料未归档，不能独立复算。更关键的是，正文保留的拆分示例含 10 条额外的“记住了。”assistant 文本，因此两种请求并非只差消息边界，不能把 60 token 归因给 20 个边界标记。

```text
历史路线（仅摘要记录）       input token   消息数
合并版                          238          1
拆分版                          298         21
```

（历史汇总，`deepseek-flash`，2026-10-08；原始 usage 字段和样本缺失。）

这两个历史数值相差 60 token，约为合并版记录值的 25%；但额外 assistant 文本、消息结构、模板实现和缓存口径都可能影响比较。**这不是角色边界的隔离实验，也不能推出每轮固定增加多少 token。**

一般来说，不同角色消息与结构可能带来不同的请求 token 数；实际增量取决于目标模型/provider 的编码、合并规则、工具与多模态块。历史 turn 是否每轮都重新提交，也取决于你使用的有状态 API、引用响应 ID 还是自己重放完整历史。不要把消息数乘以一个通用边界常数来估算。

### 位置也会改变 token 数

同一段规则块，放在不同位置：

```text
结构                        input token
A. 全部放 system                 234
B. 全部放第一条 user               238    (+4)
C. 一半 system 一半 user           234     (0)
D. 同一句问题问两轮                254    (+20)
```

这些历史数值不能证明某个位置造成了多少 token 差异；位置/role 变化可能同时改动请求结构、模型行为和缓存候选前缀。应把它作为目标端点的对照变量测量，而非普遍模板定律。

那「10 行规则 + 一个问题」在数组里到底怎么摆？两种写法（示例：构造数据，未实跑；两份的规则文本逐字相同）：

```json
// 合并成一整轮：1 条 user
[
  {"role": "user", "content": "规则：\n1. …（10 行，约 310 字符）\n\n问题：帮我判断这笔退款该怎么处理。"}
]
```

```json
// 拆成 10 轮 + 10 条应答：21 条消息（这里只列头尾）
[
  {"role": "user",      "content": "规则 1：退款前先确认订单存在。"},
  {"role": "assistant", "content": "记住了。"},
  {"role": "user",      "content": "规则 2：不要承诺你无法保证的时间。"},
  {"role": "assistant", "content": "记住了。"},
  "…（规则 3~9 依此类推，18 条消息）…",
  {"role": "user",      "content": "规则 10：涉及金额的答复必须写明币种。"},
  {"role": "assistant", "content": "记住了。"},
  {"role": "user",      "content": "帮我判断这笔退款该怎么处理。"}
]
```

上面的 JSON 是示意，不是历史请求的逐字复现。它显示拆分版本还新增了 assistant 回答文本，因此不能用这份例子解释 238/298 的差值。若要隔离结构效应，需保存两个实际请求，保证信息、内容和验收规则可比，并用目标模型/token-count 接口记录原始请求与结果；即使这样，结构改变也可能影响行为，不能只以省 token 决策。

## 二、为什么这件事重要

**一、文字与 token 数不是一一对应。** 同一句中文加空格、换标点，tokenizer 可能会给出不同分词；但不能仅凭标点变化预测 token 差值。精确计数要指定模型/provider，并使用其 tokenizer 或 token-count 接口。

**二、跨厂商的请求契约不同。** SDK/适配层可能把统一内部消息转换成 provider-specific 请求；角色、工具调用、多模态块、system/developer 指令和状态延续方式都需按目标 API 文档映射。不能把所有差异都归结为一个公开可见的 Chat Template；多数托管 API 不向应用返回确切的内部序列化串。

**三、输入结构可能影响缓存复用，但规则由 provider 定义。** Anthropic、OpenAI 与 DeepSeek 都提供各自的前缀缓存机制，缓存断点、最小前缀、匹配和 usage 字段并不相同；比如有些变更只影响第一个不匹配位置之后的前缀，也可能仍复用更早的部分。结构调整后检查目标 endpoint 的 cache usage/诊断，不要假设统一的“渲染后 token 哈希”或“缓存全废”。Anthropic 文档允许连续的 user 消息；但其 compaction 场景也说明，同角色消息在特定处理路径中可能合并。因此，不要假设数组中相邻两条 user 消息在每种 API 流程里都保留为两个独立 turn。

## 三、三个可操作的推论

**推论一：按语义和协议表达消息，不为未经验证的 token 假设改结构。** 历史 25% 差异有额外 assistant 文本混杂，不能证明合并总是更省，也不能证明模型表现等价。把多个事实合并或拆分时，需同时验证 token、缓存、输出质量和协议要求。

**推论二：别把「结构变化」当成免费操作，也别预设它一定破坏所有缓存。** 在长会话里调整消息顺序、插入系统提醒或把内容换 role，可能影响输入 token、缓存前缀或语义行为。做这类改动后，用 provider-specific usage 与诊断对比。

**推论三：不要把通用字符公式当精确计数。** 「字符数 ÷ 4」不等同目标 tokenizer。若要在发请求前估算，可用 provider 提供的 token-count API；若要测账单/缓存行为，则比较真实请求的完整 usage 与成本字段。两种口径回答的问题不同。

## 四、代码：按目标 provider 计数

下面使用 Anthropic Messages API 的 token-count 接口，在**不生成回答**的情况下统计输入 token。它只回答该接口口径下请求输入有多少 token，不等同缓存命中、实际账单或其它 provider 的 tokenizer。

**实跑状态：未调用 provider。** 下方 verifier 只用 fake SDK 检查包装函数与差值计算；要得到真实 token 数，需由读者配置自己的目标模型与凭据后运行。

```python
import os

import anthropic

api_key = os.environ.get("ANTHROPIC_API_KEY")
auth_token = os.environ.get("ANTHROPIC_AUTH_TOKEN")
if bool(api_key) == bool(auth_token):
    raise RuntimeError("set exactly one of ANTHROPIC_API_KEY or ANTHROPIC_AUTH_TOKEN")
client = anthropic.Anthropic(api_key=api_key, auth_token=auth_token)
MODEL = os.environ["VERIFY_MODEL"]


def input_tokens(system: str, messages: list[dict]) -> int:
    """Count provider-reported input tokens without generating a model answer."""
    response = client.messages.count_tokens(
        model=MODEL,
        system=system,
        messages=messages,
    )
    return response.input_tokens


def compare_variants(
    variants: list[tuple[str, str, list[dict]]], baseline_name: str,
) -> list[tuple[str, int, int]]:
    """Return (name, input_tokens, delta_vs_baseline); define comparable inputs yourself."""
    names = [name for name, _, _ in variants]
    if len(set(names)) != len(names) or baseline_name not in names:
        raise ValueError("variant names must be unique and include the baseline")

    counts = [(name, input_tokens(system, messages)) for name, system, messages in variants]
    by_name = dict(counts)
    baseline = by_name[baseline_name]
    return [(name, count, count - baseline) for name, count in counts]


if __name__ == "__main__":
    stable_system = "你是退款支持助手。不要编造订单状态。"
    variants = [
        ("single-message", stable_system, [
            {"role": "user", "content": "订单 A-1001：退款前确认订单存在。请先检查状态。"},
        ]),
        ("two-user-messages", stable_system, [
            {"role": "user", "content": "订单 A-1001：退款前确认订单存在。"},
            {"role": "user", "content": "请先检查状态。"},
        ]),
    ]
    # Provider APIs may combine adjacent same-role messages. This compares
    # accepted request inputs; it does not guarantee two distinct user turns.
    print(compare_variants(variants, baseline_name="single-message"))
```

运行前设置 `VERIFY_MODEL`，并按官方 SDK 选择 API key 或 bearer token。示例两组请求只保持事实大致一致，消息结构可能影响模型行为；结果仅比较 Anthropic 当前 token-count 接口的输入 token 差异，**不能把差值归因成纯边界开销、缓存效果、费用差或答案质量等价**。要测缓存需发送实际 Messages 请求并分别记录 `input_tokens`、`cache_read_input_tokens`、`cache_creation_input_tokens`；要测账单还须按当前模型价格与组织配置计算。

没有跨模型通用的“每条消息边界 token”常数。设计阶段可用请求 token-count 接口估量；若该 provider 没有此接口，只能把 tokenizer / 模板估值明确标成近似值，并在运行 usage 上校准。缓存 usage 不能简单当成普通 input tokens 或货币成本。

### 一个排查案例：短提醒为什么可能改变 token 与缓存

历史笔记记载：在每轮前重复加入一条短系统提醒后，观察到成本上升，并把它解释为“消息开销 + 缓存前缀失配”。但逐次请求、usage、价格、endpoint 和缓存诊断均未归档，不能复算，也不能确认这两个因素各自贡献多少。尤其不能据此说缓存“全废”或代价是消息文本的几十倍。

可复现的排查顺序是：保存变更前后的完整请求结构和模型配置；用目标 provider 的 token-count 接口比较输入规模；用真实响应记录完整 usage、缓存读写和实际计价；若 provider 提供 cache diagnostics，定位前缀首次分歧位置。相同请求数、同一模型/区域/工具配置和同一轮次内容下再做对照。每轮重复追加规则会使历史内容累计增长，但规则是否重复、放哪种 role，应先服从 API 语义和授权边界，再看测量结果。

## 五、什么时候该关心这一层

这一层大多数时候可以不管 —— 你的请求正常、成本可接受，就没必要去研究模板。
但有四个时刻它值得你花时间：

**一、成本突然涨了而业务内容看起来没变。** 对比完整请求、工具 schema、模型与 provider 设置、缓存读写及计价口径；调用方 JSON 看似相同也不保证 API 端点渲染/计量一致。

**二、跨厂商迁移。** 为每个 provider 单独验证角色映射、工具/多模态结构、token 计数、状态延续、缓存与 usage 字段。共享领域内容不代表请求契约、计量或行为等价。

**三、缓存命中率不达预期。** 上一节的排查清单里，「序列化是否确定」
和「结构是否稳定」这两条都属于这一层。

**四、你在做提示词的 A/B 对比。** 把提示内容、消息结构、模型参数和缓存状态列为实验变量；若要归因单一因素，固定其它变量并用相同任务集重复测量，单次 token 差异不能证明输出质量等价。

如果要降成本，检查是否重复发送了不必要的历史、工具定义或文档；但是否可删除、摘要或改 role 要按任务质量、API 状态模型、缓存规则与安全语义评测。本节历史 25% 不是可迁移的节省预期。

## 六、一个具体的例子：同一条规则，两种写法

假设你想让模型「退款前必须确认订单存在」。两种写法：

```text
写法一（放在 system 的规则块里）
  system: ...规则 7：退款前必须先调用 lookup_order 确认订单存在...
  问题:   把订单 A-1001 退了

写法二（在每轮 user 消息前加一句提醒）
  system: ...（没有这条规则）...
  user:   注意：退款前必须先确认订单存在。
          把订单 A-1001 退了
```

两种写法会改变请求的语义角色和结构。system/developer 与 user 的区别不只是成本标签；别为了缓存把用户数据或租户策略放进跨用户共享前缀，也别仅凭位置假设模型表现等价。

- **写法一**：如果这是适用于该请求的应用指令，放在 provider 规定的 system/developer 位置；其是否可缓存、缓存多久、如何计费要查当前接口与模型规则。
- **写法二**：若提醒只适用于这一轮，把它放在本轮输入中；若每轮重复追加到持久 transcript，会增加后续请求上下文，但缓存可能仍命中早期稳定前缀，实际结果看 provider 的断点与匹配规则。

而且写法二还有个更隐蔽的问题：**它会随对话轮次累积。**
如果每轮都加一句提醒，20 轮之后历史里有 20 句几乎相同的话，
既占 token 又可能让模型以为这是 20 条独立的约束。

**结论：按语义与权限选择消息角色，按 provider 缓存契约安排稳定前缀。**
共享、稳定且对当前主体适用的说明可考虑放前；用户/租户专属事实、动态内容与逐轮输入需保持正确作用域，不能为了命中缓存越权共享。

缓存只是成本与延迟优化，不是持久状态存储或授权隔离机制；一条稳定前缀也不保证命中，缓存最小长度、断点、TTL、路由和 provider 策略都可能影响结果。

## 七、小结

- Chat template 是模型/provider 的消息序列化机制；托管 API 不一定公开内部模板细节。
- 2026-10-08 的 238/298 token 汇总缺少原始请求；拆分示例还包含额外 assistant 文本，不能归因到消息边界。
- 结构与角色变化可能影响 token、语义和缓存复用；影响范围与计量取决于 provider/model/API。
- 用 provider token-count 接口测输入 token；用真实响应 usage、缓存诊断和价格信息测实际运行成本。
- 保持缓存前缀稳定有助于部分 provider 的复用，但不保证命中；不要牺牲角色语义、租户隔离或安全边界。
