上下文快满时，最直觉的做法是「把之前的对话总结一下」。这一节要说明两件事：

1. **摘要确实会丢东西** —— 而且丢的往往是最不该丢的那一类
2. **压缩不是免费的** —— 它在一次性任务里是净亏损；收益只在你**复用**压缩结果时才出现

## 实测一：压缩比不压缩更贵

场景：一个 32 轮的对话。早期几轮里埋了 3 条具体信息（订单号、金额、某方案被否决的原因），中间 28 轮是与任务无关的问答，最后提一个必须用到那 3 条信息的问题。

三条路线：

| 路线 | 做法 | 全部命中 | 总 token |
|---|---|---:|:--:|---:|
| **A 完整历史** | 什么都不压，全部发过去 | 3/3 | **1952** |
| **B 摘要压缩** | 让模型把历史压成 ≤200 字 | 3/3 | **2272** |
| **C 结构化笔记** | 让模型抽成结构化 JSON | 3/3 | **4246** |

（实测数据，`deepseek-flash`，2026-10-08。token 为**该路线所有调用之和**。）

三条路线**都答对了**。但看最后一列 —— **「压缩」比不压缩更贵，而且贵得多。**

原因不难想，但很容易被忽略：

```
A 完整历史：  1 次调用（输入 = 全部历史）
B 摘要压缩：  2 次调用（第 1 次输入 = 全部历史，第 2 次输入 = 摘要）
                            ↑ 这一次已经把完整历史读了一遍
C 结构化笔记：2 次调用，且压缩产物本身更长（880 字 vs 138 字）
```

**压缩的第一步就是「把没压缩的东西全读一遍」。** 这个成本省不掉 —— 所以压缩只有在**压缩结果被复用很多次**时才划算：压一次、用十次，第一次的开销就被摊薄了。

如果这个上下文只用一次（比如你就问一个问题然后结束），压缩是纯粹的额外开销。

## 实测二：摘要丢掉了那条硬约束

第二个场景更贴近真实压缩的压力：8 条具体信息散在对话里，其中好几条是用「顺便说一句」这类从句带出来的。

| 方式 | 长度 | token | 保住的细节 |
|---|---:|---:|---|
| **摘要** | 138 字 | 812 | **7/8** |
| **结构化笔记** | 880 字 | 2776 | **8/8** |

摘要**唯一丢掉的那条**是：

> 「还有个事，客户强调过**不要动生产库**。」—— 客户的硬约束

（实测数据，`deepseek-flash`，2026-10-08。）

注意它丢掉的是什么：**一条约束**。不是订单号，不是金额，不是报错原文 —— 那些都在。丢掉的是那句听起来像闲聊、但对后续每一步操作都构成限制的话。

这正好印证了 checkpoint 里那条判断：**摘要天然按「重要性」排序，而「结论」和「主线」看起来总比「约束」重要。** 一条约束被单独拎出来时，它看起来只是一句备注；只有当它和后面的动作放在一起时，你才知道它有多关键 —— 而摘要的时候，你还没有后面的动作。

## 那该怎么做：把「状态」从历史里挪出来

结构化笔记之所以更可靠，机制很简单：**它的结构是你定义的，不是模型当场判断的。**

```
摘要：     模型决定什么重要 → 你无法预知它会丢什么 → 丢了也不会报错
结构化笔记：你定义有哪些字段 → 模型只负责填 → 缺字段是可检测的
```

这和你熟悉的一件事是同一个思路：**把状态从「过程」里拆出来。** 对话历史适合承载「我们聊过什么」，笔记适合承载「现在确定了什么」。把状态挪进笔记之后，压缩历史时就不必再小心翼翼 —— 因为该保住的已经不在历史里了。

一个可操作的清单，按「必须结构化保留」排序：

| 类别 | 例子 | 为什么不能交给摘要 |
|---|---|---|
| **约束与禁止项** | 「不要动生产库」 | 单独出现时看起来像备注，实际限制全部后续动作 |
| **标识符** | 订单号、报表编号、文件路径 | 摘要极易把具体值写成「某订单」 |
| **报错原文** | `ERR_POOL_EXHAUSTED` | 模糊化之后就再也查不到了 |
| **否决过的方案及原因** | 「批量接口 —— 不支持幂等」 | 不记原因，下一步会重新提出同一个方案 |
| 数值与日期 | 4820 元、2026-03-15 | 会被四舍五入或写成「约」 |

> 注意最后两行。**「被否决的方案」是最容易被丢的一类** —— 它既不是结论，也不是待办，看起来像已经翻篇的闲聊。但它是唯一能阻止 agent 重新走进同一个坑的东西。

## 完整可运行代码

```python
# compaction_audit.py
"""审计你的压缩策略丢了什么。

做法：先埋一批**已知的**关键信息，压缩一次，再逐条检查它们还在不在。
「丢了多少」必须可机判 —— 靠肉眼读摘要发现不了丢失。
"""

import json
import os

import anthropic

client = anthropic.Anthropic(
    api_key=(
        os.environ.get("ANTHROPIC_API_KEY")
        or os.environ.get("ANTHROPIC_AUTH_TOKEN")
    ),
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)
MODEL = os.environ["VERIFY_MODEL"]

# (值, 类别) —— 这些是"后续一定会用到"的信息，人为埋进对话里
FACTS = [
    ("ORD-88213", "标识符"),
    ("4820", "金额"),
    ("RE-4471", "标识符"),
    ("2026-03-15", "日期"),
    ("不支持幂等", "否决原因"),
    ("不要动生产库", "硬约束"),      # ← 最容易被丢的一类
    ("ERR_POOL_EXHAUSTED", "报错原文"),
    ("张岚", "对接人"),
]

HISTORY = [
    {"role": "user", "content": "处理订单 ORD-88213 的退款，金额 4820 元。上次评审用的报表是 RE-4471。"},
    {"role": "assistant", "content": "好的。建议改用批量接口。我们承诺在 2026-03-15 前完成复检。"},
    {"role": "user", "content": "批量接口先不用，不支持幂等。"},
    {"role": "assistant", "content": "明白。日志里出现过 ERR_POOL_EXHAUSTED，记一下。"},
    # ... 中间是大量与任务无关的轮次 ...
    {"role": "user", "content": "还有个事，客户强调过不要动生产库。对接人是张岚。"},
]

SUMMARY_PROMPT = "把这整段对话压缩成 200 字以内的摘要，保留后续可能用到的信息。只输出摘要。"
NOTES_PROMPT = (
    "把对话里所有具体事实抽成结构化笔记，字段固定为：identifiers / amounts / dates / "
    "rejected_proposals / constraints / error_codes / contacts。用 JSON 输出，不要遗漏任何具体值。"
)


def compress(prompt: str) -> str:
    resp = client.messages.create(
        model=MODEL, max_tokens=3000,
        messages=[*HISTORY, {"role": "user", "content": prompt}],
    )
    return "".join(b.text for b in resp.content if b.type == "text")


def audit(label: str, artifact: str) -> None:
    kept = [f for f, _ in FACTS if f in artifact]
    lost = [(f, kind) for f, kind in FACTS if f not in artifact]
    print(f"\n【{label}】{len(artifact)} 字，保住 {len(kept)}/{len(FACTS)}")
    for value, kind in lost:
        print(f"  ❌ 丢了 [{kind}] {value}")

    if any(kind in ("硬约束", "否决原因") for _, kind in lost):
        print("  ⚠️  丢的是约束/否决原因 —— 这类信息丢了以后，后续步骤会静默跑偏。")


if __name__ == "__main__":
    audit("摘要压缩", compress(SUMMARY_PROMPT))
    audit("结构化笔记", compress(NOTES_PROMPT))
```

> **实跑状态**：本文表格里的**数据是实测的**（用直接 HTTP 请求采集）；上面这份 Python 脚本用的是 SDK 写法，字段与采集脚本一致，但**脚本本身未在官方端点验证**。

## 压缩之后，模型会不会承认自己不知道

本节实测二说「摘要丢掉了那条硬约束」（8 条里丢 1 条，恰好是硬约束）。那么**丢掉之后会发生什么**？

这才是真正的问题。我把它做成了一次对照：先让模型把一份手册压成摘要 —— 摘要**静默**丢掉了「演练期间不得写入生产库」这条约束，但读起来仍像一份完整摘要 —— 然后把原文撤掉，只拿摘要去问一个依赖那条约束的问题。

| system 里有没有限制 | 5 次里直接给结论的比例 |
|---|---|
| 什么都不说 | **5/5** |
| 加一句「只依据摘要回答」 | 0/5（5 次都承认摘要里没有） |
| 再加「缺失要明说」 | 0/5（与上一条无差别） |

第一行最值得警惕。模型不是乱说，它的回答形态是：「不可以。根据该摘要，演练期间仅要求执行常规巡检，**并未授权**写生产库。」—— 它的推理是**摘要里没写，所以不允许**，语气确定，还给出了像模像样的理由。这个结论碰巧是对的，但**推理来源是假的**：换一条真实规则，它同样会从「摘要没提」推出一个确定结论。

第二行说明修复成本极低：**一句「只依据摘要回答」就够了**，额外的「缺失要明说」并没有带来差别。

这件事在压缩场景里格外重要，因为压缩的目的就是把原文移出上下文 —— 于是**模型从此没有任何办法发现自己被喂了残缺信息**。这份信息不对称是**你自己制造**的。所以压缩之后，system 里必须补上那句限定：它不是客套话，是压缩这个操作的必要配套。

## 压缩该在什么时候触发，又必须保住什么

两个操作层面的问题。

**触发时机。** 按 token 占窗口的比例触发（比如超过 70%）比按轮次触发稳，因为每轮增长的量差异很大。但压缩本身要花一次调用，所以别在临界点反复触发 —— 设一个滞后区间（压到 50% 再恢复计数）比单阈值更省。

**必须保住什么。** 从上面的实测看，摘要最容易丢的恰恰是最不该丢的那一类。所以在压缩提示里应该**显式点名**三样：**硬约束**（不许做什么）、**当前目标**（这一轮到底要完成什么）、**已产生的副作用**（已经改了哪些东西）。前两类丢了会让行为跑偏，第三类丢了会导致重复执行 —— 而这三样都不是「流程步骤」，正是常规摘要最容易略过的内容。

## 常见坑

**以为压缩是免费的。** 压缩第一步就要把完整历史读一遍。本节实测：一次性任务里，摘要路线（2272 token）比不做压缩（1952 token）**更贵**。

**以为摘要能保住关键信息。** 实测 8 条里丢 1 条 —— 丢的是「不要动生产库」这样的**硬约束**，因为它单独看起来只像一句备注。

**把「被否决的方案」当成垃圾丢掉。** 它既不是结论也不是待办，看起来已经翻篇 —— 但它是唯一能阻止 agent 重新提出同一个错误方案的东西。**必须连同否决原因一起保留。**

**等上下文快满了才想压缩。** 那时你是在压力下做取舍，而且留给「发现丢了什么」的余量已经没有了。结构化笔记应当在**第一次确认某个事实时**就写下来，而不是事后从历史里回收。

**靠肉眼看摘要判断有没有丢东西。** 丢的那条不会自己举手。要像上面那样，**人为埋入已知信息再逐条核对**。
