上下文快满时，最直觉的做法是「把之前的对话总结一下」。这一节要区分三件事：

1. **摘要是有损表示** —— 有可能遗漏后续恰好需要的信息，遗漏类型要用任务样本测
2. **压缩有成本，也有损失** —— 成本与收益取决于后续请求数、缓存、计费口径和质量要求，不能只看摘要长度
3. **结构化笔记也不是天然可靠** —— 字段固定只让遗漏更容易检测；值仍需来源、冲突处理和业务校验

> **历史实测边界**：下文 2026-10-08 的 token、8 条信息保存率和 5 次问答对照，当前只剩汇总数字；逐次原始请求/响应、准确 endpoint/model、完整 usage 与 scorer 未归档，无法独立复算。`deepseek-flash` 不能唯一识别具体模型版本。这些数字只能作为待复核的历史观察，不能推出摘要必然更贵、摘要更容易丢约束或某提示在一般情况下有效。新项目应先用自己的任务集建立可复现基线。

## 历史样本一：该组记录中摘要路线 token 更多

历史报告把场景描述为一个 32 轮对话：早期埋入 3 条信息，中间有无关问答，最后询问这些信息。逐轮对话已无法取得，因此下表不可重放；下方代码是独立的候选保留探针，不是表格实验的复现输入。

三条路线：

| 路线 | 做法 | 全部命中 | 总 token |
|---|---|---:|:--:|
| **A 完整历史** | 什么都不压，全部发过去 | 3/3 | **1952** |
| **B 摘要压缩** | 让模型把历史压成 ≤200 字 | 3/3 | **2272** |
| **C 结构化笔记** | 让模型抽成结构化 JSON | 3/3 | **4246** |

（2026-10-08 历史汇总，`deepseek-flash`；token 被报告为**该路线所有调用之和**，原始 usage 未归档。）

历史汇总称三条路线**都答对了**，并记录了表中的 token 数；由于缺少原始轨迹和评分器，这些数字目前不可独立复算。它们不证明压缩通常更贵。

原因不难想，但很容易被忽略：

```text
A 完整历史：  1 次调用（输入 = 全部历史）
B 摘要压缩：  2 次调用（第 1 次输入 = 全部历史，第 2 次输入 = 摘要）
                            ↑ 这一次已经把完整历史读了一遍
C 结构化笔记：2 次调用，且压缩产物本身更长（880 字 vs 138 字）
```

**自建摘要通常需要先处理待压缩的历史**，这会增加一次调用；后续能否回本，取决于摘要被复用多少次、每次输入/输出与缓存成本、延迟和任务质量。某些 provider 也提供服务端压缩或上下文编辑，调用与计费语义不同，不能把“先读全量历史”当成所有压缩 API 的统一实现细节。

如果摘要只用于一次后续请求，压缩往往会增加一轮处理成本；但是否净亏仍需按目标 endpoint 的 usage/价格、缓存和答案质量计算。不要仅凭本节单组样本决定是否压缩。

## 历史样本二：摘要记录中遗漏一条硬约束

第二个场景更贴近真实压缩的压力：8 条具体信息散在对话里，其中好几条是用「顺便说一句」这类从句带出来的。

| 方式 | 长度 | token | 保住的细节 |
|---|---:|---:|---|
| **摘要** | 138 字 | 812 | **7/8** |
| **结构化笔记** | 880 字 | 2776 | **8/8** |

摘要**唯一丢掉的那条**是：

> 「还有个事，客户强调过**不要动生产库**。」—— 客户的硬约束

（2026-10-08 历史汇总，`deepseek-flash`；原始对话、摘要、结构化产物与逐条判分未归档。）

历史摘要记录称该次摘要丢了**一条约束**、保留了其余七项。它提醒我们要把约束纳入评估集；单次样本不能证明模型摘要普遍优先丢约束，也不能支撑“摘要天然按重要性排序”的机制结论。

即使摘要看起来连贯，也不能据此推断所有约束都保留了。更稳妥的工程做法是：为目标任务定义需要保真的字段、保存来源与状态，并用已知答案的回归集检查压缩前后的差异。

## 那该怎么做：把「状态」从历史里挪出来

结构化笔记的优势是：**字段由你定义，缺字段和格式错误更容易由程序检查**。它不保证模型填对、填全，也不能代替授权、状态机或数据库事实。

```text
摘要：     模型决定什么重要 → 你无法预知它会丢什么 → 丢了也不会报错
结构化笔记：你定义字段与来源要求 → 模型提出候选值 → 程序校验类型/来源/冲突，必要时回查权威系统
```

这和后端熟悉的状态管理相似：把任务状态持久化到明确的数据结构，而不是把对话 transcript 当作唯一数据库。但笔记仍是派生数据；涉及金额、审批、生产环境限制或已执行副作用时，权威状态应来自宿主应用/业务数据库，模型摘要不能成为唯一记录。

一个可用于设计回归测试的候选字段清单：

| 候选字段 | 例子 | 为什么值得纳入评测 |
|---|---|---|
| **约束与禁止项** | 「不要动生产库」 | 单独出现时看起来像备注，实际限制全部后续动作 |
| **标识符** | 订单号、报表编号、文件路径 | 摘要极易把具体值写成「某订单」 |
| **报错原文** | `ERR_POOL_EXHAUSTED` | 模糊化之后就再也查不到了 |
| **否决过的方案及原因** | 「批量接口 —— 不支持幂等」 | 不记原因，下一步会重新提出同一个方案 |
| 数值与日期 | 4820 元、2026-03-15 | 会被四舍五入或写成「约」 |

> 这些类别是本例的测试设计，不是所有 agent 的固定必填字段。被否决方案可以减少重复讨论，但若需求、接口或约束变化，旧否决未必继续有效；应保存时间、范围、来源与失效/替代状态。

### 一份填好的笔记

字段名只是一半。下面是实测二那 8 条信息填完的样子（示例：构造数据，未实跑）—— 注意每个值是数组还是标量、以及有没有带来源：

```json
{
  "identifiers": [
    {"fact_id": "f-1", "value": "ORD-88213", "what": "订单号", "source": "turn-1"},
    {"fact_id": "f-2", "value": "RE-4471",  "what": "报表编号", "source": "turn-1"}
  ],
  "amounts": [{"fact_id": "f-3", "value": 4820, "unit": "CNY", "what": "退款金额", "source": "turn-1"}],
  "dates":   [{"fact_id": "f-4", "value": "2026-03-15", "what": "复检截止", "source": "turn-2"}],
  "rejected_proposals": [
    {"fact_id": "f-5", "proposal": "改用批量接口", "reason": "不支持幂等", "turn": 3, "source": "turn-3"}
  ],
  "constraints": [
    {"fact_id": "f-6", "text": "不要动生产库", "source": "turn-8", "speaker": "客户", "turn": 8}
  ],
  "error_codes": [{"fact_id": "f-7", "value": "ERR_POOL_EXHAUSTED", "source": "turn-4"}],
  "contacts":    [{"fact_id": "f-8", "name": "张岚", "role": "对接人", "source": "turn-8"}]
}
```

与摘要版的差别在**可检测性**：程序可以断言字段存在、类型正确、值有来源；但“字段非空”并不等于值正确，也不等于覆盖了原文中所有相关事实。评估完整性仍需对照来源或已知答案集。

字段怎么定，三条判据：

1. 会被**程序**拿去比较或拼接的（编号、金额、日期）单独成值，并保留单位、来源与时间；
2. 涉及**副作用**的记录与实际操作账本对齐，笔记只存引用/摘要，不代替幂等键和执行状态；
3. 会限制动作的约束保存来源、生效范围、时间与撤销/替代状态；有冲突时暂停或回查权威来源，不靠“最后一条”自行裁决。

### 笔记放在哪、下一轮谁读回来

笔记是**你**维护的一等对象，不是对话历史的一部分。生命周期有四步：

1. **触发** —— 按任务风险与更新频率选择写入时机；结构性状态变化（审批、承诺、外部副作用）应由宿主在同一事务/可靠事件流程中落账，不依赖模型“检测到”后再记。
2. **存放** —— 放入版本化、带任务/租户范围与访问控制的状态存储。把它放在请求的哪个消息位置由 provider 的协议和缓存规则决定；位置本身不保证缓存命中或更高优先级。Anthropic 当前提供 server-side compaction / context editing；OpenAI Responses API 也提供 compaction 接口。它们是 provider-specific 机制，先核对当前文档、模型支持与保留的状态形态，再决定是否自建摘要。
3. **读回** —— 按需注入经过授权且仍有效的状态；最近对话可以提供语境，但遇到冲突时要按明确来源优先级回查，不能默认笔记正确。
4. **更新** —— 校验 schema、来源、版本与状态迁移；并发更新使用版本号/CAS 或数据库事务，处理冲突时保留审计记录。

消息数组长这样（示例：构造数据，未实跑）：

```text
[
  {"role": "system", "content": "只依据下面的笔记回答；笔记里没有的事实，明说没有。"},
  {"role": "user",   "content": "<notes>\n{…上面那份 JSON…}\n</notes>"},
  {"role": "user",   "content": "本轮问题：退款单 RF-77 用的哪个报表编号？"}
]
```

“只依据笔记回答”可以作为提示，但不能保证模型不补全或不受其它上下文影响。历史 5 次对照缺逐次响应与 scorer，不可复算；缺失关键事实时应由宿主阻止高风险操作、向权威数据源查询或要求用户补充，而非依赖提示语保证安全。

更新与在线检测的伪码：

```python
LIST_FIELDS = {"identifiers", "amounts", "dates", "rejected_proposals",
               "constraints", "error_codes", "contacts"}
REQUIRED_TEXT = {
    "identifiers": ("value", "what"),
    "amounts": ("unit", "what"),
    "dates": ("value", "what"),
    "rejected_proposals": ("proposal", "reason"),
    "constraints": ("text", "speaker"),
    "error_codes": ("value",),
    "contacts": ("name", "role"),
}
INTEGER_FIELDS = {"rejected_proposals": ("turn",), "constraints": ("turn",)}


def validate_notes(notes: dict) -> list[str]:
    """检查本例的字段形状与基础类型；不验证事实真实、完整或授权。"""
    errors = []
    if not isinstance(notes, dict):
        return ["notes: expected object"]
    for key in LIST_FIELDS:
        if key not in notes or not isinstance(notes[key], list):
            errors.append(f"{key}: expected list")
            continue
        for index, item in enumerate(notes[key]):
            where = f"{key}[{index}]"
            if not isinstance(item, dict):
                errors.append(f"{where}: expected object")
                continue
            for field in ("fact_id", "source"):
                value = item.get(field)
                if not isinstance(value, str) or not value.strip():
                    errors.append(f"{where}: missing fact_id or source (invalid {field})")
            for field in REQUIRED_TEXT.get(key, ()):
                value = item.get(field)
                if not isinstance(value, str) or not value.strip():
                    errors.append(f"{where}.{field}: expected nonempty string")
            for field in INTEGER_FIELDS.get(key, ()):
                value = item.get(field)
                if not isinstance(value, int) or isinstance(value, bool) or value < 1:
                    errors.append(f"{where}.{field}: expected positive integer")
            if key == "amounts":
                value = item.get("value")
                if not isinstance(value, (int, float)) or isinstance(value, bool):
                    errors.append(f"{where}.value: expected number")
    return errors


def merge_notes(notes: dict, new_facts: list[dict]) -> dict:
    """示意：按稳定 fact_id 去重；冲突拒绝合并，由调用方持久化候选并交宿主裁决。"""
    merged = {**notes, **{k: list(v) for k, v in notes.items() if isinstance(v, list)}}
    errors = validate_notes(merged)
    if errors:
        raise ValueError(f"invalid existing notes: {errors}")
    for fact in new_facts:
        category = fact["category"]
        if category not in LIST_FIELDS or category not in merged:
            raise ValueError(f"unknown category: {category}")
        if not isinstance(merged[category], list):
            raise TypeError(f"{category} must be a list")
        if not fact.get("fact_id") or not fact.get("source"):
            raise ValueError("new facts require fact_id and source")
        existing = next((x for x in merged[category] if x.get("fact_id") == fact["fact_id"]), None)
        if existing is None:
            merged[category].append(fact)
        elif existing != fact:
            raise ValueError(f"conflicting contents for fact_id={fact['fact_id']}; preserve for host review")
    errors = validate_notes(merged)
    if errors:
        raise ValueError(f"invalid merged notes: {errors}")
    return merged
```

**冲突不要静默覆盖。** 若金额从 4820 改成 4800，helper 应拒绝同一 `fact_id` 的异值合并；调用方需把新旧候选、来源和版本写入冲突记录，再由业务规则或人工确认哪条生效。不能仅凭出现顺序标记新值为真。对于生产环境禁止项、审批状态等约束，模型笔记不能覆盖宿主策略。

**结构校验失败要在使用前拦截。** `validate_notes` 只能发现若干形状/来源问题；它不能证明事实为真或所有必需事实都已抽取。遇到业务关键字段缺失或冲突，由宿主执行查询、拒绝操作或要求澄清；再提示模型“先查证”只是辅助，不能作为唯一控制。

### 别把它和记忆、RAG 混起来

- **笔记** = 本任务的状态，任务结束就作废；
- **记忆** = 跨会话保留（第 7 章给三条判据：还会不会再遇到、写错代价多大、值不值得维护）；
- **RAG**（Retrieval-Augmented Generation，检索增强生成）指的是「从外部知识库检索、再把结果拼进上下文」的一类做法（第 6 章）—— 它是只读知识，既不该写进笔记，也不该指望笔记去回答它。

三者的更新时机不同：笔记每轮都可能更新，记忆按需从笔记晋升，RAG 基本只读。

## 完整可运行代码

```python
# compaction_audit.py
"""审计你的压缩策略丢了什么。

做法：先埋一批**已知的**关键信息，压缩一次，再逐条检查它们还在不在。
「丢了多少」必须可机判 —— 靠肉眼读摘要发现不了丢失。
"""

import json
import os
from pathlib import Path

import anthropic

api_key = os.environ.get("ANTHROPIC_API_KEY")
auth_token = os.environ.get("ANTHROPIC_AUTH_TOKEN")
if bool(api_key) == bool(auth_token):
    raise RuntimeError("set exactly one of ANTHROPIC_API_KEY or ANTHROPIC_AUTH_TOKEN")
client = anthropic.Anthropic(
    api_key=api_key,
    auth_token=auth_token,
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)
MODEL = os.environ["VERIFY_MODEL"]

# (值, 类别) —— 这些是"后续一定会用到"的信息，人为埋进对话里
FACTS = [
    ("ORD-88213", "标识符"),
    ("4820", "金额"),
    ("RE-4471", "标识符"),
    ("2026-03-15", "日期"),
    ("不支持幂等", "否决原因"),
    ("不要动生产库", "硬约束"),      # ← 最容易被丢的一类
    ("ERR_POOL_EXHAUSTED", "报错原文"),
    ("张岚", "对接人"),
]

HISTORY = [
    {"role": "user", "content": "处理订单 ORD-88213 的退款，金额 4820 元。上次评审用的报表是 RE-4471。"},
    {"role": "assistant", "content": "好的。建议改用批量接口。我们承诺在 2026-03-15 前完成复检。"},
    {"role": "user", "content": "批量接口先不用，不支持幂等。"},
    {"role": "assistant", "content": "明白。日志里出现过 ERR_POOL_EXHAUSTED，记一下。"},
    # ... 中间是大量与任务无关的轮次 ...
    {"role": "user", "content": "还有个事，客户强调过不要动生产库。对接人是张岚。"},
]

SUMMARY_PROMPT = "把这整段对话压缩成 200 字以内的摘要，保留后续可能用到的信息。只输出摘要。"
NOTES_PROMPT = (
    "把对话里所有具体事实抽成结构化笔记，字段固定为：identifiers / amounts / dates / "
    "rejected_proposals / constraints / error_codes / contacts。用 JSON 输出，不要遗漏任何具体值。"
)


def compress(prompt: str) -> str:
    resp = client.messages.create(
        model=MODEL, max_tokens=3000,
        messages=[*HISTORY, {"role": "user", "content": prompt}],
    )
    if resp.stop_reason != "end_turn":
        raise RuntimeError(f"incomplete summarization: stop_reason={resp.stop_reason}")
    text = "".join(b.text for b in resp.content if b.type == "text")
    if not text.strip():
        raise RuntimeError("summarizer returned no text")
    return text


def audit(label: str, artifact: str) -> None:
    kept = [f for f, _ in FACTS if f in artifact]
    lost = [(f, kind) for f, kind in FACTS if f not in artifact]
    print(f"\n【{label}】{len(artifact)} 字，保住 {len(kept)}/{len(FACTS)}")
    for value, kind in lost:
        print(f"  ❌ 丢了 [{kind}] {value}")

    if any(kind in ("硬约束", "否决原因") for _, kind in lost):
        print("  ⚠️  丢的是约束/否决原因 —— 这类信息丢了以后，后续步骤会静默跑偏。")


if __name__ == "__main__":
    summary = compress(SUMMARY_PROMPT)
    notes = compress(NOTES_PROMPT)
    audit("摘要压缩", summary)
    audit("结构化笔记", notes)
    # 子串命中只是候选标签，不等于语义完整性或正确性。
    if os.environ.get("SAVE_RAW_RESPONSES") == "1":
        Path("compaction-candidates.json").write_text(
            json.dumps({"summary": summary, "notes": notes}, ensure_ascii=False, indent=2),
            encoding="utf-8",
        )
        print("raw candidates saved; protect the file and manually adjudicate")
```

> **实跑状态**：表格数字是 2026-10-08 的历史记录，但原始请求/响应、模型指纹和评分材料缺失，当前不可复算。上面的 SDK 脚本本轮只做离线检查，未调用 provider；`FACTS` 子串命中只能发现字面缺失，不能判定语义正确、否定、错配或冲突。正式评测需保存脱敏样本、请求参数、provider usage、任务验收规则和裁决结果。

## 压缩之后，模型会不会承认自己不知道

本节实测二说「摘要丢掉了那条硬约束」（8 条里丢 1 条，恰好是硬约束）。那么**丢掉之后会发生什么**？

这才是真正的问题。我把它做成了一次对照：先让模型把一份手册压成摘要 —— 摘要**静默**丢掉了「演练期间不得写入生产库」这条约束，但读起来仍像一份完整摘要 —— 然后把原文撤掉，只拿摘要去问一个依赖那条约束的问题。

| system 里有没有限制 | 5 次里直接给结论的比例 |
|---|---|
| 什么都不说 | **5/5** |
| 加一句「只依据摘要回答」 | 0/5（5 次都承认摘要里没有） |
| 再加「缺失要明说」 | 0/5（与上一条无差别） |

历史记录描述的第一类回答是：「不可以。根据该摘要，演练期间仅要求执行常规巡检，**并未授权**写生产库。」但没有原文、逐次输出或判分记录，不能验证引述或断定该响应模式稳定。摘要未提某约束，不等于该约束不存在；尤其不能用“摘要没写”来推导授权或禁止。

这组 5 次对照的历史摘要不足以证明一句提示就能可靠解决缺失信息问题；即使模型报告“未知”，高风险决策仍须由宿主按权威状态执行 fail closed。

压缩会改变可见证据，因此应在应用层显式记录摘要覆盖范围、来源、时间和待验证项。提示可以要求模型区分“摘要明确记载”与“没有证据”，但不能保证其遵守，也不能把它当作压缩 API 的普遍必要协议。

## 压缩该在什么时候触发，又必须保住什么

两个操作层面的问题。

**触发时机。** 不能把 70%/50% 当通用阈值。按 token/剩余窗口触发比固定轮数更贴近实际容量，但阈值要预留工具结果、输出上限、重试与 provider 侧开销；用目标流量回放测定安全边际。可加滞后区间避免重复压缩，但恢复点应由测量确定，并确保单次压缩不会递归触发。

**必须保住什么。** 不能根据一条历史样本概括摘要的普遍丢失分布。应依据任务威胁模型和恢复要求，把当前目标、有效约束、决策与依据、待办、失败/未决状态、外部副作用引用纳入测试集；真正的副作用状态留在应用账本，摘要只引用其 ID/版本。来源冲突时保留冲突并回查，别让摘要替业务规则裁决。

## 常见坑

**以为压缩是免费的。** 自建摘要一般会增加摘要调用，但总成本取决于后续复用、缓存和质量。本节 2272 vs 1952 是不可复算的单组历史摘要，不是通用成本结论。

**以为摘要能保住关键信息。** 该历史摘要记录为 8 条中保住 7 条，遗漏一条生产库约束；这是一个应加入回归测试的案例，不能推广为摘要的一般错误率。

**把「被否决的方案」当成垃圾丢掉。** 记录方案、理由、来源和适用范围，避免无谓重复；旧决定可能因条件变化而失效，不能把它视为永久禁令。

**等上下文快满了才想压缩。** 那时你是在压力下做取舍，而且留给「发现丢了什么」的余量已经没有了。结构化笔记应当在**第一次确认某个事实时**就写下来，而不是事后从历史里回收。

**靠肉眼看摘要判断有没有丢东西。** 丢的那条不会自己举手。要像上面那样，**人为埋入已知信息再逐条核对**。
