子智能体（subagent）常被讲成「并行提速」的手段。它也可以用于**上下文隔离**：把探索过程留在一个独立运行中，只把需要的结果交回编排者。但隔离不是这个名词自动附带的性质，是否保留历史、转发哪些消息、是否共享状态，都由运行时与宿主配置决定。

先把本节的实现落下，避免把一种编排方式说成通用定义。**这里的子 agent 是由主 agent 调用的独立模型循环**：示例为它新建消息列表、设置 system 与工具循环，最后把摘要作为结果返回。只有当宿主不把子循环的原始历史附回主 agent 时，主上下文才与该段探索过程隔离。框架也可以用 agents-as-tools、handoff 或共享会话等其他形态；例如 OpenAI Agents SDK 的 handoff 默认仍会传递对话历史，可用 input filter 等配置改变接收内容。

并行和隔离是不同的决策。依赖关系、共享状态、副作用与资源上限决定哪些子任务可以并行；创建独立 agent 本身不会自动并发。隔离是否有收益，也要看主任务是否会反复携带探索内容，以及结果压缩有没有丢掉验收所需的证据。

不过「子智能体更贵」这个说法**不是无条件成立的**。本节测了两个方向相反的场景，它们共同指向一条统一的规律。

## 历史观测一：与「把资料留在主上下文」的 token 量对照

任务：在 20 篇文档里找出提到 `legacy_api` 的那几篇，然后连续回答 3 个追问。

| 路线 | 做法 | 记录的总 token | **主 agent 最大请求输入** |
|---|---|---:|---:|
| A 单 agent | 20 篇全文留在主上下文，每轮追问都带着 | 25913 | **6816** |
| B 子智能体 | 子 agent 扫描 20 篇，只回传「哪几篇 + 负责人」 | **9182** | **1258** |

（历史单次观测摘要，`deepseek-flash`，2026-10-08。逐次请求/响应、模型后端指纹、usage 原值、任务映射和答案 scorer 未归档；本轮不能独立复算。总量与峰值的缓存 usage 口径也不能从表格确认。）

**「主 agent 最大请求输入」怎么理解**：原文称其为主流程每次请求的输入 token 数最大值，但没有保存逐次 usage 与 endpoint 字段，无法确认是否包含缓存 token，也不能据它推算账单或准确的窗口占用。若复测，应按目标 endpoint 的 usage 定义重建完整输入，并将 token 体积、费用和上下文容量分开记录。

这份摘要报告 B 的 token 量更低，主 agent 单次请求输入峰值约为 A 的五分之一；由于任务等价性、完成状态和评分过程未归档，不能据此判断两条路线质量相同或普遍更便宜。

一种可能的解释是：A 的主请求反复包含 20 篇原文，而 B 把检索放在子循环，只回传短结果。但旧轨迹没有保存，无法核对实际每轮装载量、缓存读写、工具/输出 token 或答案完整性。架构上可以把原始轨迹留在子运行中，但是否丢弃、归档或提供证据引用应由数据保留、可审计性和主任务需要共同决定。

这提示一个待验证的设计问题：主 agent 需要哪些发现、来源与失败信息才能可靠地完成任务？只回传结论会减少主上下文，但也可能丢失证据、约束或审计路径。探索过程是否保留在主上下文、日志或外部 artifact，应按复核需要决定；原始内容不必全部塞回主 prompt。

## 历史观测二：共享背景重复装载时的 token 量

换个场景，结论就反过来了。

这次有一个 8 项的检查任务，但**每一项都需要一份约 3000 字符的共享背景**（编码规范手册）：

| 路线 | 做法 | 总 token | **共享背景装载次数** |
|---|---|---:|---:|
| A 单 agent | 背景装载 1 次，在同一上下文里逐个检查 8 项 | **8430** | 1 |
| B 子智能体 | 每项一个子 agent，**各自装载背景** | **68548** | 8 |

（历史单次观测摘要，`deepseek-flash`，2026-10-08；逐次请求/响应、精确 endpoint/model、缓存 usage、样本答案与 scorer 均未归档，不能独立复算。）

**摘要中的 token 量比值为 8.1 倍。** 设计上两条路线计划让共享背景分别进入 1 次或 8 次调用；但没有逐次轨迹，不能证明结果差别全部由背景重复装载造成，也不能把 token 比值当成账单比值。

### 这里我又踩了一次同一个坑

第一次跑这个实验时，A 的答案是**空的** —— 我差点得出「单 agent 在复杂检查任务上做不出来」。

历史摘要记为**空文本 + `stop_reason=max_tokens`**。按 Anthropic Messages API 契约，这表示响应触及了输出上限；但当时的逐次响应、usage、模型版本与内容块未保存，无法确认是不是 thinking 消耗了预算，也无法排除其他差异。

后续记录称把上限调到 6000 后两条路线都产生了“合理”的检查结论，但没有保存原始输出、验收规则或逐项评分。因此这不能证明两路均完成了等价任务，也不能支持统一采用 6000 的建议。复测时应依据 endpoint 的 `stop_reason` 与独立任务验收器分类，不能把截断结果当成功或失败率样本。

可复用的教训是：先看 `stop_reason`，再按 endpoint 契约分类；`max_tokens` 说明响应达到生成上限，不单独解释因果，也不能证明任务内容完成。

## 统一规律：重复输入只是总量的一部分

两个历史对照方向相反。对输入 token 的一部分，可以用下面的近似关系帮助列清变量：

> **输入侧的重复内容量，近似取决于内容长度 × 请求中出现次数。**

- 历史观测一的设计中，A 路线计划在多轮中重复携带 20 篇原文，B 路线把扫描放入子循环；具体逐次装载次数无法从留存材料复核
- 历史观测二的设计中，共享背景计划在 A 路线装载 1 次、在 B 路线装载 8 次；逐次请求和实际缓存命中未留存

输入重复量不等于总 token、账单或系统成本。还要计入输出、工具定义和结果、编排调用、重试、并行开销、缓存读写价格、延迟以及任务质量；应在相同任务集和验收规则下对照。

## 一个直接的优化：别让共享背景重复装载

缓存可能降低某些 provider/endpoint 上重复前缀的边际处理价格，但不能预先从 68548 这个历史总量中扣出固定比例。DeepSeek 当前文档描述的是自动、尽力而为缓存和其自身 usage 字段；Anthropic API 则有自己的 cache breakpoint 与 usage 口径。要估缓存后的账单，必须在目标 endpoint 上测实际命中并按对应费率计算；缓存也不减少逻辑上下文中需要提供的内容长度。

缓存不会让「重复装载」在逻辑上消失，也不保证命中或普遍降低上面那组历史 token 数。它是需要单独验证的 endpoint 优化项，不是多 agent 成本结论的替代证据。

另一半可测的优化是**把共享背景收窄**。历史例子里 8 个子 agent 各自携带约 3000 字符的规范手册，其中部分条目与当前检查项无关。按标签裁剪是一个待测方案；减少比例要用目标任务验证，不能从构造代码推断为固定幅度。

## 什么时候该用子智能体

| 情况 | 选择 | 理由 |
|---|---|---|
| 任务需要在大量资料里探索，但交付内容短 | **评估隔离运行** | 可减少主 prompt 中的探索过程；必须保留必要来源和失败信息 |
| 主任务会持续多轮 | **比较不同历史保留策略** | 若每轮重复带入长历史，可能增加输入；缓存、服务端状态和 compaction 会改变结果 |
| 子任务彼此高度依赖或共享可变状态 | **先设计同步与状态边界** | 独立上下文会增加协调、合并与冲突处理，不能把它当成并行收益 |
| 子任务数量多且每项都需要大段共享背景 | **先测背景裁剪与缓存** | 输入重复可能增加，但幅度与账单取决于 endpoint 和实际命中 |
| 任务很短或结果容易直接校验 | **先比较单 agent** | 额外调度、调用和结果验证可能超过隔离收益 |

## 完整可运行代码

```python
# subagent_cost.py
"""比较 Anthropic Messages endpoint 的 token 体积；不代表账单或质量。

运行前需要三个环境变量（第 1 章讲过怎么拿）：
  ANTHROPIC_API_KEY 或 ANTHROPIC_AUTH_TOKEN —— 二选一；前者是 API key，后者是 bearer token
  ANTHROPIC_BASE_URL                         —— 用兼容端点时填，官方端点可留空
  VERIFY_MODEL                               —— 要测的模型名

安装依赖：python -m pip install anthropic
"""

import json
import os

import anthropic

api_key = os.environ.get("ANTHROPIC_API_KEY") or None
auth_token = os.environ.get("ANTHROPIC_AUTH_TOKEN") or None
if (api_key is None) == (auth_token is None):
    raise RuntimeError("请且仅配置 ANTHROPIC_API_KEY 或 ANTHROPIC_AUTH_TOKEN 其中一个")
client = anthropic.Anthropic(
    api_key=api_key,
    auth_token=auth_token,
    base_url=os.environ.get("ANTHROPIC_BASE_URL"),
)
MODEL = os.environ["VERIFY_MODEL"]

# 输出预算应按目标 endpoint 和验收要求设置，没有通用固定值。
MAX_TOKENS = int(os.environ.get("MAX_OUTPUT_TOKENS", "4096"))
MAX_ROUNDS = 4          # 子 agent 自己的轮次上限，与主循环无关

# ── 待检查项与规则（示例：构造数据，未实跑）────────────────────
ITEMS = {
    "ITEM-01": ("io",     "f = open(path)\nlines = f.readlines()"),
    "ITEM-02": ("errors", "try:\n    run()\nexcept Exception:\n    pass"),
    "ITEM-03": ("naming", "def GetUser(ID): ..."),
    "ITEM-04": ("io",     "resp = requests.get(url)"),
}
RULES = {
    "io":     ["文件读写必须显式指定编码", "网络调用必须设超时"],
    "errors": ["不要吞异常", "错误信息必须给出下一步动作"],
    "naming": ["函数名用小写下划线", "常量用全大写"],
}
ALL_RULES = "\n".join(f"- {r}" for rules in RULES.values() for r in rules)
SHARED_BRIEF = (
    "你是代码规范审计员。团队规范手册：\n" + ALL_RULES +
    "\n逐项给出结论：每项要么指出违反的规则，要么写「未发现问题」。"
)

CHECK_TOOL = {
    "name": "check_item",
    "description": "取回一条待检查项的源码，以及适用于它的规则。",
    "input_schema": {
        "type": "object",
        "properties": {
            "item_id": {"type": "string", "description": "形如 ITEM-01"},
        },
        "required": ["item_id"],
    },
}


def check_item(item_id: str) -> tuple[dict, bool]:
    """静态教学目录查询；真实存储层还需分别处理缺失、超时与权限拒绝。"""
    if item_id not in ITEMS:
        return {
            "error": "not_found",
            "message": f"没有 {item_id} 这一项。",
            "retryable": False,
        }, True
    tag, code = ITEMS[item_id]
    return {"code": code, "rules": RULES[tag]}, False


def total_tokens(resp) -> int:
    """按 Anthropic Messages usage 字段汇总；兼容端点须核对字段语义。"""
    u = resp.usage
    # 这是 token 体积口径，不等于费用、质量或所有 provider 的通用口径。
    input_tokens = getattr(u, "input_tokens", None)
    output_tokens = getattr(u, "output_tokens", None)

    def is_count(value) -> bool:
        return (
            isinstance(value, int)
            and not isinstance(value, bool)
            and value >= 0
        )

    if not is_count(input_tokens) or not is_count(output_tokens):
        raise RuntimeError("endpoint 未返回有效的 Anthropic input/output usage")
    optional_usage = (
        getattr(u, "cache_read_input_tokens", 0),
        getattr(u, "cache_creation_input_tokens", 0),
    )
    if any(
        value is not None and not is_count(value)
        for value in optional_usage
    ):
        raise RuntimeError("endpoint 返回了无效的缓存 usage")
    return (
        input_tokens
        + (optional_usage[0] or 0)
        + (optional_usage[1] or 0)
        + output_tokens
    )


def call(system: str, user: str):
    resp = client.messages.create(
        model=MODEL, max_tokens=MAX_TOKENS, system=system,
        messages=[{"role": "user", "content": user}],
    )
    if resp.stop_reason != "end_turn":
        raise RuntimeError(f"响应未正常完成：stop_reason={resp.stop_reason!r}")
    if not any(b.type == "text" and b.text.strip() for b in resp.content):
        raise RuntimeError("响应没有可验收的文本内容")
    return resp


def pick_relevant(item_id: str) -> str:
    """只带这一项真正需要的规则，而不是整本手册。

    真实项目里这一层离线做（按标签切分规则手册）；这里用标签做最小演示。
    """
    return "\n".join(RULES[ITEMS[item_id][0]])


# ── 一个真正的最小 subagent：独立上下文 + 自己的工具循环 + 结构化结论 ──
def run_subagent(task: str, brief: str, expected_ids: set[str]) -> tuple[dict, int]:
    """一次独立的模型调用序列。它与「多调一次模型」的区别有三点：

      1. 有自己的 messages（独立上下文）和自己的工具循环；
      2. 有自己的轮次上限，失败不会把主循环拖进去；
      3. 只回传固定的三个字段，主 agent 因此能区分
         「确实没有」与「查的时候失败了」。
    """
    sub_messages = [{"role": "user", "content": task}]
    used = 0
    not_found: list[str] = []
    failed: list[str] = []
    checked: set[str] = set()
    status = "incomplete"

    for _ in range(MAX_ROUNDS):
        resp = client.messages.create(
            model=MODEL, max_tokens=MAX_TOKENS, system=brief,
            tools=[CHECK_TOOL], messages=sub_messages,
        )
        used += total_tokens(resp)
        if resp.stop_reason == "end_turn":
            status = "complete"
            break
        if resp.stop_reason != "tool_use":
            failed.append(f"unsupported_stop_reason:{resp.stop_reason}")
            break

        calls = [b for b in resp.content if b.type == "tool_use"]
        if not calls:
            failed.append("empty_tool_use")
            break

        # Anthropic correlates every tool_result to a unique tool_use id. Validate
        # the whole batch before dispatch so malformed ids cannot cause ambiguous
        # result routing or let earlier calls run before a later id defect is found.
        tool_use_ids = [getattr(block, "id", None) for block in calls]
        invalid_id = any(
            not isinstance(tool_id, str) or not tool_id.strip()
            for tool_id in tool_use_ids
        )
        if invalid_id or len(set(tool_use_ids)) != len(tool_use_ids):
            failed.append("invalid_tool_use_ids")
            break

        sub_messages.append({"role": "assistant", "content": resp.content})
        results = []
        for b in resp.content:
            if b.type != "tool_use":
                continue
            args = b.input if isinstance(b.input, dict) else {}
            item_id = args.get("item_id")
            valid = (
                b.name == CHECK_TOOL["name"]
                and set(args) == {"item_id"}
                and isinstance(item_id, str)
                and item_id in expected_ids
            )
            if not valid:
                content, is_error = {"error": "invalid_tool_request"}, True
                failed.append(f"invalid_tool_request:{item_id or 'unknown'}")
            else:
                content, is_error = check_item(item_id)
                if is_error:
                    not_found.append(item_id)
                else:
                    checked.add(item_id)
            results.append({
                "type": "tool_result",
                "tool_use_id": b.id,
                "is_error": is_error,
                "content": json.dumps(content, ensure_ascii=False),
            })
        sub_messages.append({"role": "user", "content": results})

    # 轮次耗尽或异常停止时不调用总结模型，也不伪装成完成。
    if status != "complete":
        return {
            "status": status, "did": [], "failed": failed,
            "not_found": not_found,
            "pending": sorted(expected_ids - checked - set(not_found)),
        }, used

    # 总结文本仍需外部验收；状态、失败和缺项由宿主维护。
    final = client.messages.create(
        model=MODEL, max_tokens=MAX_TOKENS,
        system=(
            "只输出 JSON，字段固定为 did。did 是数组，每项包含 item_id 与 finding 两个字符串。"
            "只报告实际检查过的编号；不要报告执行状态或不存在的编号。不要复述过程。"
        ),
        messages=[*sub_messages, {"role": "user", "content": "给出结论。"}],
    )
    used += total_tokens(final)
    if final.stop_reason != "end_turn":
        return {
            "status": "incomplete", "did": [],
            "failed": failed + ["summary_incomplete"], "not_found": not_found,
            "pending": sorted(expected_ids - checked - set(not_found)),
        }, used
    text = "".join(b.text for b in final.content if b.type == "text")
    try:
        summary = json.loads(text)
        if (
            not isinstance(summary, dict)
            or set(summary) != {"did"}
            or not isinstance(summary["did"], list)
            or any(
                not isinstance(item, dict)
                or set(item) != {"item_id", "finding"}
                or not isinstance(item["item_id"], str)
                or not isinstance(item["finding"], str)
                or not item["finding"].strip()
                for item in summary["did"]
            )
        ):
            raise ValueError("summary schema mismatch")
    except (ValueError, json.JSONDecodeError):
        summary = {"did": []}
        failed.append("unparseable_summary")
    did = [item for item in summary["did"] if item["item_id"] in checked]
    reported = {item["item_id"] for item in did}
    pending = sorted(expected_ids - reported - set(not_found))
    return {
        "status": "complete" if not failed and not pending and not not_found else "partial",
        "did": did,
        "failed": sorted(set(failed)),
        "not_found": sorted(set(not_found)),
        "pending": pending,
    }, used


def single_agent() -> int:
    """共享背景装载 1 次，所有子任务在同一上下文里处理。"""
    body = "\n\n".join(f"【{k}】{v[1]}" for k, v in ITEMS.items())
    return total_tokens(call(SHARED_BRIEF, f"逐项检查下面的代码：\n\n{body}"))


def with_subagents(narrow: bool = False) -> int:
    """每个子任务一个独立子 agent —— 共享背景装载 len(ITEMS) 次。"""
    total = 0
    summaries = []
    for item_id in ITEMS:
        brief = pick_relevant(item_id) if narrow else SHARED_BRIEF
        summary, used = run_subagent(
            f"检查 {item_id} 是否符合规范。", brief, expected_ids={item_id}
        )
        total += used
        summaries.append(json.dumps(summary, ensure_ascii=False))

    # 主 agent 只拿三段结论：不装载共享背景，也不接触子 agent 的工具轨迹
    main = call("汇总子智能体的结论。", "\n\n".join(summaries))
    return total + total_tokens(main)


if __name__ == "__main__":
    a = single_agent()
    b = with_subagents(narrow=False)
    c = with_subagents(narrow=True)
    print(f"子任务数：{len(ITEMS)}")
    print(f"  单 agent            : {a:>7} token（共享背景装载 1 次）")
    print(f"  子智能体（原样背景）: {b:>7} token（装载 {len(ITEMS)} 次）")
    print(f"  子智能体（收窄背景）: {c:>7} token（每项只带相关规则）")
    print(f"  比值：{b / a:.2f}x / {c / a:.2f}x")
    print("\n先试着把共享背景收窄到每个子任务真正需要的部分 ——")
    print("上面的 c 用 pick_relevant 演示了这一步。")
```

Anthropic 的每个 `tool_use` 块带有唯一 `id`，宿主用对应的 `tool_result.tool_use_id` 回填结果。示例先对整批 id 做非空和唯一性检查；发现歧义时整批停止，避免错误关联结果或先执行部分调用。这个预检不替代参数校验、授权或结果验收。

`total_tokens` 只接受非负整数；Python 的 `bool` 是 `int` 子类，所以还要显式排除 `True/False`。代码把 Anthropic SDK 中缺省或为 `None` 的可选缓存计数字段按 0 处理；换用兼容端点前，必须确认该端点的 usage 字段和缺省语义相同，否则不要把这项汇总当成完整输入体积。

示例的 `ITEMS` 是进程内构造数据，`check_item` 没有真实数据库、租户隔离或对象授权。生产工具必须在每次读取时按可信调用身份、租户和对象权限检查；模型给出的编号与参数只是请求数据，不能作为授权依据。

### 子 agent 交给主 agent 的那份东西

下面是宿主整理后的返回产物协议示意（构造数据，未实跑；静态示例代码不会产生读取超时）。模型只负责提出 `did` 发现；`status`、`failed`、`not_found` 与 `pending` 由宿主根据工具执行和验收结果维护：

```json
{
  "status": "partial",
  "did": [{"item_id": "ITEM-01", "finding": "未指定编码"}],
  "failed": ["ITEM-02 读取超时"],
  "not_found": [],
  "pending": ["ITEM-02"]
}
```

这些字段各有用途，且不能由模型自行宣布执行状态：

| 字段 | 含义 | 主 agent 该做什么 |
|---|---|---|
| status | 宿主流程状态；`complete` 仅表示预期编号都有非空、格式有效的发现 | 仍需业务/规则验收，不能当作正确性证明 |
| did | 模型给出的检查结论 | 作为待验收的发现；必要时回查代码与规则 |
| failed | 宿主或模型调用流程观察到的失败 | 知道这是**查询失败**，按错误类型决定重试或升级 |
| not_found | 宿主查询确认目标不存在 | 不要把失败伪装成“没有发现问题” |
| pending | 尚无可验收结论的预期编号 | 补查、重试或明确交给调用方 |

主 agent 可以把这份 dict 作为一条消息追加进自己的上下文（如果子 agent 是被工具派出的，就作为那条 `tool_result` 的内容）；只有宿主没有再附回原始轨迹时，才实现了主上下文隔离。保留轨迹、证据引用或审计记录应按复核需求另行设计。

示例用一次独立收尾调用输出 JSON，以便把格式化与工具交互分开；这会增加调用、token 和失败点。它不保证格式正确（仍需解析和校验），也不证明结论正确。是否值得应在任务质量、成本与可审计性上实测。

## 子智能体的失败模式

前面算的都是成本。真要用它，还得知道它会怎么坏 —— 而且**它的坏法和单 agent 不一样**，因为主 agent 拿到的不是原始信息，而是子 agent 的摘要。

**① 摘要可能丢信息，而主 agent 未必察觉。** 上一节的一个历史样本曾记录关键约束丢失；该观察不能推出所有摘要都会如此。子 agent 的摘要若成为主 agent 唯一的信息来源，遗漏就可能不易察觉，因此应按任务要求保留来源、证据或复核入口。

**② 子 agent 的失败可能被误写成「没找到」。** 如果调用失败状态没有进入宿主维护的结果，主 agent 可能把它误读为无相关信息并重复派发。宿主应分别记录工具失败、确认不存在和待检查项，并由重试策略决定是否再执行。

**③ 并行子 agent 之间无法协商。** 它们各自独立工作、各自写摘要，冲突要到主 agent 汇总时才暴露。两个子 agent 给出互相矛盾的结论时，主 agent 手里没有裁决依据，只能再花一次调用去核对。

这些失败模式的共同点是：**边界压缩会隐藏来源或状态。** 让子 agent 返回带编号的结构化发现，并由宿主维护失败、缺项和执行状态；主 agent 收到空结果时要能区分「确实没有」与「查询失败」。发现本身仍要经过规则或业务验收。

## 常见坑

**把子智能体当成天然并行或天然隔离。** 并行取决于依赖与宿主调度；上下文隔离取决于消息传递、会话和状态配置。两者都要检查实现。

**把历史 token 摘要当成可推广的费用结论。** 两个历史摘要方向相反，但缺少逐次 usage、endpoint 与答案评分，不能据此判断当前架构更省或质量相当。比较时同时记录 token、缓存 usage、费用、延迟和独立质量指标。

**让每个子 agent 都带同一份大背景。** 这可能增加输入量；缓存是否命中及其价格依赖 provider/endpoint。先测背景裁剪、缓存命中和端到端费用，再决定是否使用。

**在任务很短时就上子智能体。** 任务短时，隔离带来的上下文收益可能小于额外调度、调用与验收成本；应按实际工作负载比较。

**把空输出归因于思考耗尽预算。** 先按 endpoint 契约检查 `stop_reason`、内容块和 usage；`max_tokens` 表示触及输出上限，单凭它无法证明因果或任务是否完成。
