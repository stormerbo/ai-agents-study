第 1 章第 5 节讲过 prompt caching 怎么用。这一节先用一个 **2026-10-08 的 DeepSeek Anthropic 兼容端点观测**说明前缀变化与缓存命中之间的关系，再区分模型推理时的 KV cache 与厂商提供的跨请求 prompt/context cache。缓存键、前缀匹配、断点、TTL、最小长度和自动/显式缓存策略都是服务实现的一部分，不能从 KV 数学性质直接推成所有 API 的统一规则。Anthropic 的[官方文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)就是一个具有显式断点和 TTL 语义的具体例子。

## 一、先看一组实测数据

这组记录来自 `deepseek-flash` 在 `https://api.deepseek.com/anthropic` 的 Anthropic Messages 兼容端点。实验使用约 2400 字符的 system 提示（约 1800 token），连续问同一个问题四次，第五次只改动前缀里的一个词。用量来自当时保存的表格记录，原始逐次响应未归档，故仅作为历史端点观察：

```text
调用                              input_tokens   cache_read   cache_creation
第 1 次（首次，冷启动）                  1205            0              0
第 2 次（同样前缀）                       181         1024              0
第 3 次（同样前缀，带 cache_control）      181         1024              0
第 4 次（同样前缀，带 cache_control）      181         1024              0
第 5 次（前缀改了一个词）                 1205            0              0
```

以下四点**只描述上述日期、模型标识与端点的观测**，不能直接推广到其他厂商或端点：

**一、这组请求中观察到了自动命中。** 第 2 次没有带 `cache_control`，`cache_read` 为 1024。它只能说明这个端点当时在这组请求中自动返回了缓存命中；其他接口可能要求显式开启缓存，也可能有阈值或其他启用条件。

**二、这次加入的 `cache_control` 没改变返回用量。** 它是 Anthropic Messages API 的缓存控制语义之一，但兼容端点可以忽略、部分实现或采用不同协议。此实验只证明第 2、3、4 次返回的三个用量数字相同，不足以断言该端点普遍忽略 `cache_control`，也不证明所有请求都自动缓存。

**三、改变这组请求的前缀后，本次观测的 `cache_read` 回到 0。** `input` 从 181 回到 1205，约 6.7 倍。这个结果表明被改动的这个请求没有复用原缓存，不足以证明服务没有在更早位置命中其他缓存，也不能得出任何改动都会让整个缓存全部失效。

**四、要按该端点的 usage 定义解释字段。** 本次命中时 `input_tokens` 为 181、`cache_read` 为 1024；没命中时分别为 1205 和 0。要计算这类接口的输入用量需同时检查缓存读/写字段。不同供应商的字段定义可能不同，应以当前 API 文档与实际响应为准。

## 二、为什么是「前缀」而不是「内容」

要理解为什么模型运行时会使用 KV cache，可以看模型内部机制。注意：**运行时 KV cache 的计算性质，不会单独决定供应商跨请求缓存如何建立和失效**；后者还由服务端的缓存键、断点、TTL、阈值、隔离与淘汰策略决定。

**自回归生成**：常见自回归模型按序处理 token；生成后续 token 时会利用前文状态。推理引擎可把这些中间状态留作 KV cache，避免在同一次生成过程中重复计算。实际模型、推理内核和请求 API 的细节各有不同。

**注意力与 Key/Value**：生成每一个 token 时，模型会为上下文里每个已有 token 算三个向量 —— Query（我在找什么）、Key（我是什么）、Value（我携带什么信息）。匹配用的是 Query 与 Key，取回来的是 Value，最后按权重加权求和。每一层都会做这件事。

**KV Cache 就是把这些 Key/Value 留下来。** 它们只和「前面有哪些 token」有关，和后面生成什么无关，所以算过一次就能复用 —— 第 n 个 token 不必重算前 n-1 个。

在常见的自回归 Transformer 推理中，某一层位置的 KV 表示依赖模型配置、该位置 token 及其前序状态；改变序列前部通常意味着后续状态不能直接照搬。但具体能复用到哪里、是否跨请求复用、缓存键包含哪些请求字段，以及何时淘汰，都属于推理服务实现。该机制也不推出「语义相同即可命中」或「任意微小差异都使所有缓存失效」。

这就解释了三层关系（表中的「自回归生成」指上面那个「一次一个 token」的过程）：

| 层 | 在哪 | 由谁控制 | 作用范围 |
| --- | --- | --- | --- |
| **KV Cache** | 模型内部 | 推理引擎 | 单次请求内的自回归生成 |
| **Prompt / Context Cache** | 服务端或推理平台 | 厂商/API 合约 | 可能跨请求复用前缀或相关状态；语义因接口而异 |
| **客户端缓存** | 你的代码 | 你 | 不重复发同样的内容 |

**有些 prompt cache 会跨请求复用模型计算状态或相关表示，但不能把所有产品的 prompt cache 简化成“持久化 KV cache”。** 例如 Anthropic 文档描述了按 `tools → system → messages` 形成前缀、在指定 `cache_control` 断点写入、向前查找已有断点以及默认 5 分钟 TTL；这些是 Anthropic API 的具体合约。DeepSeek 的[Responses API 文档](https://api-docs.deepseek.com/guides/responses_api/)则将 `prompt_cache_key` / `prompt_cache_retention` 标为不支持，并说明缓存由服务自动管理。即使同属前缀缓存，是否要求字节/Token 精确一致、采用什么断点、是否自动缓存、缓存多久和哪些请求参数参与缓存键，都应按对应 provider / endpoint 文档核对。

## 三、把缓存作为有边界的结构优化

前缀稳定性不是模型调用正确性的通用架构约束；在提供前缀缓存的 API 上，它是影响复用率的优化手段。

**建议一：如果当前 API 按前缀缓存，把跨请求稳定且可复用的内容放在可复用区间，把变化内容放在断点之后。** 具体支持方式依 provider 而异：有的服务自动识别前缀，有的要求显式 `cache_control` 断点，也可能根本不提供该缓存接口。时间戳、请求 id 等会降低某些前缀缓存的复用机会，但实际结果应通过 provider 的 usage 字段确认。

**建议二：对采用序列化前缀匹配的 API，保持工具定义及序列化稳定。** 工具顺序变化可能影响该接口的缓存匹配，但它是否进入缓存键、服务如何规范化请求，需要查对应文档并实测。

**建议三：若接口支持增长式消息前缀缓存，只追加历史通常有利于复用此前已写入的前缀。** 改写摘要或替换旧消息可能改变断点之前的内容，从而影响匹配；但断点位置、向前查找范围和缓存刷新行为都是具体服务的语义，压缩是否更贵也需结合真实 usage 与计费验证。

**建议四：不要预设 `effort` 或其他非文本参数必定进入缓存键。** 有些 provider 会将思考配置等渲染到缓存前缀中；另一些接口的参与规则可能不同。Anthropic 对其模型描述了思考配置变化可能使相关断点失效。是否为具体会话固定参数，应依据目标 provider 的文档和 usage 实测决定。

## 四、把这件事换算成钱

上面那些数字看着抽象，换成多轮对话就很具体了。

假设某个支持前缀缓存的 API 确认 system + tools 的 1024 token 前缀符合缓存条件，且后续请求确实报告命中；一次会话问 20 轮：

```text
前缀稳定且接口报告命中：第 1 轮处理/缓存前缀
                         后续轮次复用量以 usage 为准

前缀变化或缓存未命中：每轮可能重新处理该前缀
```

按第 1 章那条记账口径（`input + cache_read + cache_creation`），
若该 API 的 usage 把缓存命中也计入输入总量，两种情况下处理的总输入量可相近；但**计费口径可能不同** —— 命中缓存的部分可能使用单独单价或其他计费规则。具体低多少**因厂商与模型而异，而且会变**，本站不写死这个数字。要知道你自己的比例，去账单里把 `cache_read` 的用量与 `input` 的用量分别拉出来，乘各自的单价算占比（第 1 章第 5 节给过读 usage 的代码）。
因此「20 轮会话」的费用差异必须通过对应模型的价格表与逐次 usage 计算；缓存不改变模型任务成功率这一点也需要在你的应用评测中单独验证。

这组实验展示了一个具体端点上缓存命中与未命中时 usage 字段的差异。它不能单独证明所有 agent 的成本都会相差数倍；要判断自己的成本，应按目标供应商的输入、缓存读写单价和真实 usage 计算，并同时检查任务质量。

顺带说一个推论：**长会话里「省 token」和「省请求」是两件事。**
把更多内容塞进一轮（省请求）通常会破坏前缀稳定或增加单轮成本；
拆成更多轮（省单轮）则要多付几次固定前缀。在目标接口支持且测得有收益时，可尝试让可复用前缀稳定、将变化内容放在合适断点之后；请求拆分仍需同时权衡延迟、任务质量、价格与缓存生命周期。

## 五、一个可操作的检查

```python
import json


def hit_rate(usage) -> float:
    """本次请求的缓存命中率。开发期把它打点，比事后翻账单便宜得多。

    分母是全部输入侧 token（未命中 + 命中 + 新写入）。
    """
    hit = usage.cache_read_input_tokens or 0
    total = (
        (usage.input_tokens or 0)
        + hit
        + (usage.cache_creation_input_tokens or 0)
    )
    return hit / total if total else 0.0


def cache_state(usage) -> dict:
    """当目标 API 暴露缓存 usage 字段时，用它记录该接口实际报告的读写量；其他行为仍需查文档。"""
    read = usage.cache_read_input_tokens or 0
    created = usage.cache_creation_input_tokens or 0
    if read and not created:
        return {"状态": "报告缓存读取且无新写入", "读取": read}
    if read and created:
        return {"状态": "同时报告缓存读取与新写入", "读取": read, "新写入": created}
    return {"状态": "未报告缓存读取", "新写入": created}


def request_fingerprint(req: dict) -> str:
    """把一次请求序列化成确定的字符串，用于两次请求的「同不同」比较。

    它的边界要说清楚：这是「请求文本」的指纹，不是「渲染后 token 串」的指纹。
    它只能比较本地序列化出的请求表示，不能证明 provider 的缓存键相同或不同；接口可能采用规范化、断点和其他请求字段。按对应 API 文档解释 usage。
    """
    parts = [json.dumps(t, sort_keys=True) for t in req.get("tools", [])]
    parts.append(req.get("system", ""))
    for m in req.get("messages", []):
        parts.append(json.dumps(m, sort_keys=True, ensure_ascii=False))
    return "\n".join(parts)
```

怎么在开发期用它们：

1. **如果接口提供缓存用量，每次请求都记录它。** 观察变化有助于定位未命中，但指标下降也可能来自 TTL、缓存阈值、服务配置或请求字段，而不只是有人改了前缀。
2. **发现未命中，先比 `request_fingerprint`。** 两次指纹不同，就去 diff 那两段文本 —— 时间戳、请求 id、字典序都在这里现形。
3. **本地指纹相同但接口未报告读取**，先检查该 API 的缓存开关、TTL、最小前缀长度、断点和 usage 语义；之后再确认请求字段和序列化是否吻合。

### 一个真实的错误

我在第 18 章（成本与延迟）做那个「工具定义占 62%」的实测时，
第一版脚本每次调用都把工具列表**按字典顺序重新序列化**，
而我当时用的是无序的 `dict`。于是两次请求的 tools 顺序可能不同 ——
**前缀从第一个工具就断开了**，缓存命中率接近零。

这个 bug 的隐蔽之处在于：**它不影响正确性。** 本次工具定义顺序对任务理解没有造成可观察差异；但在采用序列化前缀匹配的缓存实现中，顺序变化可能降低复用。只有对照目标接口 usage，才能确认是否造成了额外处理或费用。

对支持序列化前缀匹配的接口，一个可验证的做法是让结构序列化确定（例如稳定排序或有序结构），然后用目标 endpoint 的文档和 usage 检查收益；不要假设不同接口使用相同的序列化或缓存键。

## 六、小结

- **这次 DeepSeek Anthropic 兼容端点观测**：第二次请求返回了 `cache_read=1024`；本次改变前缀后读缓存为 0。它是有日期和范围的观测，不是所有 provider 的保证。
- **按目标 API 文档理解缓存契约**：自动/显式开关、断点、缓存键、最小长度、TTL 与 usage 字段都可能不同。
- **运行时 KV cache 与跨请求 prompt cache 是相关但不同层次的概念**：前者用于模型推理；后者的实现和生命周期由服务决定。
- **稳定可复用的前缀是常见优化方向，不是跨供应商的硬性正确性约束**。用文档和 usage 验证序列化、参数变化、历史改写及缓存成本的影响。

排查缓存未命中时，先核对目标 API 的开关、断点、TTL、最小缓存长度和缓存键规则，再对照请求结构及响应 usage。此实验中的一次未命中只能说明这组请求没有读到缓存；不能把其他 provider 的行为预先归因于客户端前缀结构。
