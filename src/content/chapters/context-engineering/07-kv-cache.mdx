第 1 章第 5 节讲过 prompt caching 怎么用。这一节讲它**为什么长这样** ——
因为不理解机制，你会写出「逻辑上没错、但成本高好几倍」的上下文结构。

## 一、先看一组实测数据

我用一个约 2400 字符的 system 提示（约 1800 token），连续问同一个问题四次，
第五次只改动前缀里的一个词：

```text
调用                              input_tokens   cache_read   cache_creation
第 1 次（首次，冷启动）                  1205            0              0
第 2 次（同样前缀）                       181         1024              0
第 3 次（同样前缀，带 cache_control）      181         1024              0
第 4 次（同样前缀，带 cache_control）      181         1024              0
第 5 次（前缀改了一个词）                 1205            0              0
```

四件事：

**一、缓存确实发生了，而且是自动的。** 第 2 次没有带任何缓存标记，
`cache_read` 已经是 1024。所以「不写 `cache_control` 就没有缓存」是错的。

**二、`cache_control` 在这个端点上被忽略。** 第 2、3、4 次的数字完全一样 ——
带与不带标记没有区别。（第 1 章第 5 节记过这条，这里是独立复现。）

**三、改一个词，缓存全部归零。** input 从 181 涨回 1205，**6.7 倍**。

**四、注意 `input_tokens` 的含义变了。** 命中缓存时它只算「没命中的部分」
（181），没命中时算全部（1205）。**所以看单次的 `input_tokens` 判断不了真实成本**，
必须把 `cache_read` 一起看 —— 这也是第 1 章那条「token 记账要算三项」的原因。

## 二、为什么是「前缀」而不是「内容」

要理解第 3 条，得看模型内部那一层。

语言模型生成时，每一层注意力都会为每个 token 算一对 Key/Value 向量并缓存起来 ——
这就是 **KV Cache**。它让第 n 个 token 不必重算前 n-1 个。

关键性质：**KV Cache 是「按位置累积」的。** 第 i 个 token 的 Key/Value
依赖于它前面所有 token。所以你在**开头**插入一个词，
从这个位置往后的**每一个** token 的 Key/Value 都变了，缓存整体作废。
而你在**末尾**追加内容，前面的部分完全不受影响。

这就解释了三层关系：

| 层 | 在哪 | 由谁控制 | 作用范围 |
| --- | --- | --- | --- |
| **KV Cache** | 模型内部 | 推理引擎 | 单次请求内的自回归生成 |
| **Prompt Cache** | 服务端 | 厂商（你只能「用对结构」） | 跨请求复用同一前缀 |
| **客户端缓存** | 你的代码 | 你 | 不重复发同样的内容 |

**Prompt Cache 本质上是把 KV Cache 跨请求保留下来。** 所以它的约束
（前缀哈希、一字不同全失效）不是实现偷懒，而是 **KV Cache 的性质决定的**。
你没法要求它「按语义判断这段有没有变」—— 它的存储单位就是位置化的 Key/Value。

## 三、它不是一个优化技巧，是一个架构约束

很多人把「前缀稳定」当成一条性能建议。它其实是**结构设计约束**：

**约束一：稳定内容必须在前面，变化内容必须在后面。**
这听起来显然，但实际写法经常反着来。一个典型错误：把当前时间戳、
请求 id、或「本次任务的临时说明」写进 system prompt 的开头。
结果是**每次请求前缀都不同，缓存永远不命中** —— 而请求完全正常，你不会收到任何警告。

**约束二：工具定义顺序要固定。** tools 通常在最前面，
而工具列表的顺序变化同样会改变前缀。如果每次都由一个字典随机序生成，缓存就是零。

**约束三：多轮对话天然缓存友好，前提是「只追加」。**
如果你在每轮里重写历史（比如每轮都重新生成一遍 system，或者压缩后替换掉前面的消息），
那缓存会从被改写的位置断开。**这也解释了一件事：压缩是有缓存代价的** ——
第 4 节讲压缩时提过它更贵，这里是一个更底层的原因。

**约束四：`effort` 这类参数会参与提示渲染。** 第 1 章第 2 节记过：
同一个会话里改变顶层的 `effort`，之前的缓存会失效。
**为了省钱降低 effort，可能因为缓存失效而花更多钱。**

## 四、把这件事换算成钱

上面那些数字看着抽象，换成多轮对话就很具体了。

假设 system + tools 的前缀是 1024 token，一次会话问 20 轮：

```text
前缀稳定：  第 1 轮 付全额（1024 + 用户输入）
            第 2~20 轮 前缀全部命中，只为用户新输入付费

前缀每次都变：每一轮都付全额 1024
```

按第 1 章那条记账口径（`input + cache_read + cache_creation`），
两者**总 token 数是一样的**（都是 20 × 1024 的输入量级），
但**计费口径完全不同** —— 缓存读取的单价通常只有基础输入价的一成左右。
所以「20 轮会话」在两种结构下的实际费用可能差好几倍，而**任务成功率完全一样**。

这就是这一节想说的核心：**同一个逻辑上正确的 agent，因为上下文结构不同，
成本可以是另一个的好几倍。** 而且这个差别不会体现在任何功能指标上，
只体现在账单里。

顺带说一个推论：**长会话里「省 token」和「省请求」是两件事。**
把更多内容塞进一轮（省请求）通常会破坏前缀稳定或增加单轮成本；
拆成更多轮（省单轮）则要多付几次固定前缀。最优解通常是
**让固定前缀尽量大且稳定、让每轮新增尽量小**。

## 五、一个可操作的检查

```python
def diagnose_prefix(prev_request, cur_request):
    """诊断两次请求的前缀稳定性。返回第一个不同的位置。"""
    a = render_prefix(prev_request)      # tools + system，按实际拼装顺序
    b = render_prefix(cur_request)
    for i, (x, y) in enumerate(zip(a, b)):
        if x != y:
            return {
                "稳定前缀长度": i,
                "总长度": min(len(a), len(b)),
                "稳定比例": i / max(len(a), len(b)),
                "第一个差异": repr(a[max(0, i - 20):i + 20]),
            }
    return {"稳定前缀长度": min(len(a), len(b)), "稳定比例": 1.0}


def render_prefix(req):
    """按厂商实际拼装顺序渲染 —— tools 在最前，然后 system。"""
    parts = [json.dumps(t, sort_keys=True) for t in req.get("tools", [])]
    parts.append(req.get("system", ""))
    return chr(10).join(parts)
```

这个函数值得在开发期跑起来：**它能把「缓存为什么没命中」变成一个具体的位置和比例**，
而不是靠猜。稳定比例低于 90% 基本就意味着缓存收益很小。

### 一个真实的错误

我在第 18 章（成本与延迟）做那个「工具定义占 62%」的实测时，
第一版脚本每次调用都把工具列表**按字典顺序重新序列化**，
而我当时用的是无序的 `dict`。于是两次请求的 tools 顺序可能不同 ——
**前缀从第一个工具就断开了**，缓存命中率接近零。

这个 bug 的隐蔽之处在于：**它不影响正确性。** 工具定义顺序对模型理解没有影响，
测试也全过。只有在对比 usage 字段时才会发现「为什么这么贵」。

教训是：**凡是参与前缀拼接的结构，都要保证序列化是确定的。**
具体做法是排序（`sort_keys=True`）或者用有序结构，
而不要依赖语言的默认遍历顺序。

## 六、小结

- **缓存是自动发生的**：实测第 2 次不带任何标记就命中了 1024 token
- **`cache_control` 可能被兼容端点忽略**，但缓存本身照常工作
- **改一个词，input 从 181 涨回 1205（6.7 倍）** —— 这就是前缀哈希的代价
- **`input_tokens` 命中时会变小**，所以判断真实成本必须把 `cache_read` 一起看
- **KV Cache 按位置累积**，Prompt Cache 是它跨请求的延伸 —— 所以「一字不同全失效」是实现不了语义判断，不是偷懒
- **前缀稳定是架构约束不是优化技巧**：稳定在前、变化在后、序列化要确定、压缩有缓存代价

最后提醒一句关于排查顺序的：**缓存没命中时，先检查前缀结构，再看厂商文档。**
我遇到的每一次「缓存怎么没生效」，原因都在我这边 —— 时间戳写进了前缀、
字典序列化顺序不定、压缩替换了历史。**先怀疑自己的上下文结构，成本最低。**
