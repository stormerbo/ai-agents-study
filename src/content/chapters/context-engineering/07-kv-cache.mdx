第 1 章第 5 节讲过 prompt caching 怎么用。这一节先说明一组 **2026-10-08 的 DeepSeek Anthropic 兼容端点历史摘要**能支持什么、不能支持什么，再区分模型推理时的 KV cache 与厂商提供的跨请求 prompt/context cache。缓存键、前缀匹配、断点、TTL、最小长度和自动/显式缓存策略都是服务实现的一部分，不能从 KV 数学性质直接推成所有 API 的统一规则。Anthropic 的[官方文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)就是一个具有显式断点和 TTL 语义的具体例子。

## 一、先看一组历史 usage 摘要

旧表格将这组记录标为 `deepseek-flash`、`https://api.deepseek.com/anthropic`，并称使用约 2400 字符（约 1800 token）的 system 提示。原始逐次响应未归档，当前没有原始请求、token 计数结果或模型快照可供核验；表中首个请求的 `cache_creation=0`，与“冷启动”的解释不相符或至少不足以支持它，且 `input_tokens=1205` 无法与约 1800 token 的估算相互校验。因此下表只转录旧摘要，不把它视为已验证的 provider 行为：

```text
调用                              input_tokens   cache_read   cache_creation
第 1 次（旧记录中的首个请求）             1205            0              0
第 2 次（同样前缀）                       181         1024              0
第 3 次（同样前缀，带 cache_control）      181         1024              0
第 4 次（同样前缀，带 cache_control）      181         1024              0
第 5 次（前缀改了一个词）                 1205            0              0
```

这组摘要最多支持以下有限描述；由于逐次原始响应缺失，表内 `cache_read` 字段是否对应真实缓存读取、字段口径和请求间关联都无法独立核验：

**一、旧摘要将第二至第四次记录为 `cache_read=1024`。** 这只是表格里的字段值；由于响应正文和 usage 原始对象未保存，不能据此确认发生了真实缓存命中、命中由哪次请求建立，或端点是否自动缓存。它也不能作为其他接口需要显式开启缓存或存在特定阈值的证据。

**二、旧摘要中带与不带 `cache_control` 的三项数字相同。** 这不能证明兼容端点忽略了 `cache_control`，因为我们没有可核验的请求/响应，也不能排除请求构造、记录或字段映射问题。Anthropic Messages API 的 `cache_control` 是其自身 API 的缓存控制语义；兼容端点是否支持需另行确认。

**三、旧摘要把改词请求记为 `cache_read=0`。** 如果记录准确，这仅表示该行没有报告缓存读取；它不能证明此前缓存被清除，也不能说明改词导致缓存失效。`input_tokens` 从 181 变为 1205（约 6.7 倍）同样是未经原始 usage 核验的历史字段差异。

**四、不能用这组数字推导 token 总量、命中率、成本或性能。** 缓存读写字段的定义、`input_tokens` 是否排除缓存 token、计费规则都依具体 API 而定，应从当前文档和保存下来的实际响应确认。下文的 Python helper 明确采用 Anthropic Messages 风格字段，仅是本地构造的演示。

## 二、为什么是「前缀」而不是「内容」

要理解为什么模型运行时会使用 KV cache，可以看模型内部机制。注意：**运行时 KV cache 的计算性质，不会单独决定供应商跨请求缓存如何建立和失效**；后者还由服务端的缓存键、断点、TTL、阈值、隔离与淘汰策略决定。

**自回归生成**：常见自回归模型按序处理 token；生成后续 token 时会利用前文状态。推理引擎可把这些中间状态留作 KV cache，避免在同一次生成过程中重复计算。实际模型、推理内核和请求 API 的细节各有不同。

**注意力与 Key/Value**：生成每一个 token 时，模型会为上下文里每个已有 token 算三个向量 —— Query（我在找什么）、Key（我是什么）、Value（我携带什么信息）。匹配用的是 Query 与 Key，取回来的是 Value，最后按权重加权求和。每一层都会做这件事。

**KV Cache 就是把这些 Key/Value 留下来。** 它们只和「前面有哪些 token」有关，和后面生成什么无关，所以算过一次就能复用 —— 第 n 个 token 不必重算前 n-1 个。

在常见的自回归 Transformer 推理中，某一层位置的 KV 表示依赖模型配置、该位置 token 及其前序状态；改变序列前部通常意味着后续状态不能直接照搬。但具体能复用到哪里、是否跨请求复用、缓存键包含哪些请求字段，以及何时淘汰，都属于推理服务实现。该机制也不推出「语义相同即可命中」或「任意微小差异都使所有缓存失效」。

这就解释了三层关系（表中的「自回归生成」指上面那个「一次一个 token」的过程）：

| 层 | 在哪 | 由谁控制 | 作用范围 |
| --- | --- | --- | --- |
| **KV Cache** | 模型内部 | 推理引擎 | 单次请求内的自回归生成 |
| **Prompt / Context Cache** | 服务端或推理平台 | 厂商/API 合约 | 可能跨请求复用前缀或相关状态；语义因接口而异 |
| **客户端缓存** | 你的代码 | 你 | 不重复发同样的内容 |

**有些 prompt cache 会跨请求复用模型计算状态或相关表示，但不能把所有产品的 prompt cache 简化成“持久化 KV cache”。** 例如 Anthropic 文档描述了按 `tools → system → messages` 形成前缀、在指定 `cache_control` 断点写入、向前查找已有断点以及默认 5 分钟 TTL；这些是 Anthropic API 的具体合约。DeepSeek 的[Responses API 文档](https://api-docs.deepseek.com/guides/responses_api/)将 `prompt_cache_key` / `prompt_cache_retention` 标为不支持，并指向服务端自动管理的上下文缓存；这表示该接口不接受这两个客户端控制参数，不表示没有缓存能力。DeepSeek 当前的[Context Caching 文档](https://api-docs.deepseek.com/guides/kv_cache/)进一步描述：缓存前缀按完整持久化单元匹配，系统按固定 token 间隔持久化前缀单元（该规则与其滑动窗口注意力实现有关），usage 暴露 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，且命中属于尽力而为，不保证每次都命中。这个当前文档不能据此反推 2026-10-08 那组 `deepseek-flash` Anthropic 兼容端点请求使用相同模型版本、缓存单位、键或 usage 口径；当时逐次原始响应未归档，历史的 `cache_read` 字段仍只保留为端点观察。即使同属前缀缓存，是否要求字节/Token 精确一致、采用什么断点、是否自动缓存、缓存多久和哪些请求参数参与缓存键，都应按对应 provider / endpoint 文档核对。

## 三、把缓存作为有边界的结构优化

前缀稳定性不是模型调用正确性的通用架构约束；在提供前缀缓存的 API 上，它是影响复用率的优化手段。

**建议一：如果当前 API 按前缀缓存，把跨请求稳定且可复用的内容放在可复用区间，把变化内容放在断点之后。** 具体支持方式依 provider 而异：有的服务自动识别前缀，有的要求显式 `cache_control` 断点，也可能根本不提供该缓存接口。时间戳、请求 id 等会降低某些前缀缓存的复用机会，但实际结果应通过 provider 的 usage 字段确认。

**建议二：对采用序列化前缀匹配的 API，保持工具定义及序列化稳定。** 工具顺序变化可能影响该接口的缓存匹配，但它是否进入缓存键、服务如何规范化请求，需要查对应文档并实测。

**建议三：若接口支持增长式消息前缀缓存，只追加历史通常有利于复用此前已写入的前缀。** 改写摘要或替换旧消息可能改变断点之前的内容，从而影响匹配；但断点位置、向前查找范围和缓存刷新行为都是具体服务的语义，压缩是否更贵也需结合真实 usage 与计费验证。

**建议四：不要预设 `effort` 或其他非文本参数必定进入缓存键。** 有些 provider 会将思考配置等渲染到缓存前缀中；另一些接口的参与规则可能不同。Anthropic 对其模型描述了思考配置变化可能使相关断点失效。是否为具体会话固定参数，应依据目标 provider 的文档和 usage 实测决定。

## 四、把这件事换算成钱

上面那些数字看着抽象，换成多轮对话就很具体了。

假设某个支持前缀缓存的 API 确认 system + tools 的 1024 token 前缀符合缓存条件，且后续请求确实报告命中；一次会话问 20 轮：

```text
前缀稳定且接口报告命中：第 1 轮处理/缓存前缀
                         后续轮次复用量以 usage 为准

前缀变化或缓存未命中：每轮可能重新处理该前缀
```

按第 1 章那条记账口径（`input + cache_read + cache_creation`），
若该 API 的 usage 把缓存命中也计入输入总量，两种情况下处理的总输入量可相近；但**计费口径可能不同** —— 命中缓存的部分可能使用单独单价或其他计费规则。具体低多少**因厂商与模型而异，而且会变**，本站不写死这个数字。要知道你自己的比例，去账单里把 `cache_read` 的用量与 `input` 的用量分别拉出来，乘各自的单价算占比（第 1 章第 5 节给过读 usage 的代码）。
因此「20 轮会话」的费用差异必须通过对应模型的价格表与逐次 usage 计算；缓存不改变模型任务成功率这一点也需要在你的应用评测中单独验证。

这组旧表格摘要不能证明某个端点确实命中或未命中缓存，也不能单独证明 agent 成本会相差数倍；要判断自己的成本，应按目标供应商的输入、缓存读写单价和保存下来的逐次 usage 计算，并同时检查任务质量。

顺带说一个推论：**长会话里「省 token」和「省请求」是两件事。**
把更多内容塞进一轮（省请求）通常会破坏前缀稳定或增加单轮成本；
拆成更多轮（省单轮）则要多付几次固定前缀。在目标接口支持且测得有收益时，可尝试让可复用前缀稳定、将变化内容放在合适断点之后；请求拆分仍需同时权衡延迟、任务质量、价格与缓存生命周期。

## 五、一个可操作的检查

```python
import json
import hashlib
from types import SimpleNamespace as NS


def _token_count(usage, field: str) -> int:
    try:
        value = getattr(usage, field)
    except AttributeError:
        raise ValueError(f"usage does not expose {field}; adapt this helper to the target API") from None
    if isinstance(value, bool) or not isinstance(value, int) or value < 0:
        raise ValueError(f"usage.{field} must be a non-negative integer")
    return value


def hit_rate(usage) -> float:
    """按 Anthropic Messages 风格 usage 计算缓存读取占比；不是通用 provider 公式。

    这里假设 input_tokens 不含 cache read/write；目标 API 字段不同就要改公式。
    """
    input_tokens = _token_count(usage, "input_tokens")
    hit = _token_count(usage, "cache_read_input_tokens")
    created = _token_count(usage, "cache_creation_input_tokens")
    total = (
        input_tokens
        + hit
        + created
    )
    return hit / total if total else 0.0


def cache_state(usage) -> dict:
    """当目标 API 暴露缓存 usage 字段时，用它记录该接口实际报告的读写量；其他行为仍需查文档。"""
    read = _token_count(usage, "cache_read_input_tokens")
    created = _token_count(usage, "cache_creation_input_tokens")
    if read and not created:
        return {"状态": "报告缓存读取且无新写入", "读取": read}
    if read and created:
        return {"状态": "同时报告缓存读取与新写入", "读取": read, "新写入": created}
    return {"状态": "未报告缓存读取", "新写入": created}


def request_fingerprint(req: dict) -> str:
    """计算完整、已脱敏 JSON 请求体的稳定指纹；调用前先移除凭据。

    SHA-256 不是匿名化；不要把原始请求或指纹写入普通日志。相同指纹只表示
    本地 JSON 表示相同，不能证明 provider 的缓存键相同或一定命中。
    """
    canonical = json.dumps(req, sort_keys=True, ensure_ascii=False, separators=(",", ":"))
    return hashlib.sha256(canonical.encode("utf-8")).hexdigest()


if __name__ == "__main__":
    usage = NS(input_tokens=181, cache_read_input_tokens=1024, cache_creation_input_tokens=0)
    first = {"model": "example-model", "system": "stable rules", "messages": []}
    same = {"messages": [], "system": "stable rules", "model": "example-model"}
    changed = {"model": "example-model", "system": "changed rules", "messages": []}
    print(f"cache hit rate: {hit_rate(usage):.1%}")
    print(f"cache state: {cache_state(usage)['状态']}; read={usage.cache_read_input_tokens}")
    print("same payload:", request_fingerprint(first) == request_fingerprint(same))
    print("changed payload:", request_fingerprint(first) != request_fingerprint(changed))
```

```text
cache hit rate: 85.0%
cache state: 报告缓存读取且无新写入; read=1024
same payload: True
changed payload: True
```

> **实跑状态**：以上输出来自本地构造的 Anthropic Messages 风格 usage 对象，不是 provider 响应。`input_tokens` 与缓存读写字段的包含关系因 API 而异；只有确认目标 API 的字段口径后，才能沿用该分母。

怎么在开发期用它们：

1. **如果接口提供缓存用量，每次请求都记录它。** 观察变化有助于定位未命中，但指标下降也可能来自 TTL、缓存阈值、服务配置或请求字段，而不只是有人改了前缀。
2. **发现未命中，先比本地指纹。** 两次不同，就在受控环境比较已脱敏的请求结构；时间戳、请求 id、工具顺序等可能造成差异。不要把原始 prompt 或指纹写入普通日志。
3. **本地指纹相同但接口未报告读取**，先检查该 API 的缓存开关、TTL、最小前缀长度、断点和 usage 语义；之后再确认请求字段和序列化是否吻合。相同的本地 JSON 只能缩小排查范围，不能证明服务端使用相同缓存键。

### 一个历史排查假设

第 18 章（成本与延迟）的旧记录称，当时第一版脚本把工具列表**按字典顺序重新序列化**，而使用了无序的 `dict`，所以两次请求的 tools 顺序可能不同。原始请求、序列化结果和逐次 usage 未归档，无法核实该问题是否实际发生、是否令目标端点的前缀缓存未命中，或是否令命中率接近零；这只能保留为当时的排查假设。

这个假设的价值在于提醒：即使工具顺序变化不影响任务正确性，在采用序列化前缀匹配的缓存实现中也可能降低复用。但是否发生、是否影响当前接口 usage，必须用可核验的请求体和目标端点文档确认。

对支持序列化前缀匹配的接口，一个可验证的做法是让结构序列化确定（例如稳定排序或有序结构），然后用目标 endpoint 的文档和 usage 检查收益；不要假设不同接口使用相同的序列化或缓存键。

## 六、小结

- **DeepSeek Anthropic 兼容端点旧摘要**：记录中的第二至第四次为 `cache_read=1024`、改词请求为 0；原始 usage 缺失且首个请求的 `cache_creation=0`，故不能确认其为真实缓存命中或推导失效原因。
- **按目标 API 文档理解缓存契约**：自动/显式开关、断点、缓存键、最小长度、TTL 与 usage 字段都可能不同。
- **运行时 KV cache 与跨请求 prompt cache 是相关但不同层次的概念**：前者用于模型推理；后者的实现和生命周期由服务决定。
- **稳定可复用的前缀是常见优化方向，不是跨供应商的硬性正确性约束**。用文档和 usage 验证序列化、参数变化、历史改写及缓存成本的影响。

排查缓存未命中时，先核对目标 API 的开关、断点、TTL、最小缓存长度和缓存键规则，再对照请求结构及响应 usage。旧表格的改词行只记有 `cache_read=0`；原始 usage 缺失，不能确认这是一次真实未命中，更不能据此归因于客户端前缀结构或推广到其他 provider。
