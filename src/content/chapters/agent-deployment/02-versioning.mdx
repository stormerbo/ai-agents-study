第 1 节说提示词和工具定义的变更影响可能比代码更大。这一节讲怎么管理这些变更 —— 以及灰度到底能测出什么。

## 什么需要版本号

一个常见的做法是给代码打版本号，而提示词和模型版本散在配置里。这有一个具体的后果：**出问题时你无法回答"当时跑的是哪一版"。**

需要版本化的不是「四个永远足够的资产」，而是所有会改变行为且由你控制的发布输入。至少包括：

| 资产 | 需要记录什么 |
|---|---|
| **应用与编排** | 代码提交、运行时/依赖、路由、预算、重试和终止策略 |
| **提示与上下文组装** | 模板版本及其哈希；不要把含用户数据的渲染结果直接写入公共 manifest |
| **工具** | 工具集合、schema、实现版本和授权策略的引用；仅哈希 schema 不能固定工具行为 |
| **模型请求** | provider、endpoint/API 版本、请求的 model ID、相关参数；响应提供了实际 model ID / fingerprint 时也记入该次 trace |
| **其他行为开关** | 影响安全、检索、路由或输出验收的配置及其版本 |

做法上可把这些输入组织成**不可变发布 manifest**，每次发布生成一个 `release_id`。按规范化、带字段边界的序列化计算各资产哈希，并把构建产物或不可变引用一并记录；只把无分隔符文本拼起来再哈希，不能可靠表示资产边界。所有任务 trace 关联 `release_id`，同时保留此次实际请求的 provider/model 元数据。发布 ID 提供可追踪性，不保证模型输出可逐字复现：模型本身可能随机，托管服务也有各自的版本与退役策略。

这样出问题时你能做一件很关键的事：**把"某次失败"和"当时的配置"直接关联起来** —— 而不是靠时间戳去猜。

## 灰度能测出什么，测不出什么

这是本节的核心。先区分单组比例估计的精度、两版本差异检验和线上停止规则；它们回答不同的问题。下面的公式只作规划近似。

**下面的精度数值只作单组比例的粗略区间宽度参考，不是新旧版本差异的显著性检验，也不能给出统计功效。** 比例型指标（错误率、通过率）会随机抖动：100 个请求里有 2 个失败，再抽 100 个可能是 1 个也可能是 4 个 —— **这个抖动幅度随样本量缩小而变大**。正式比较新旧版本需要明确随机化/配对设计、两组样本量、显著性水平 α、目标功效 (1−β) 和可接受效应量，并用相应的两组比例或配对检验/置信区间；这里不做这些假设。

```text
单组 90% 区间宽度的正态近似 ≈ 2 × z × √( p × (1 - p) / n )
反解规划参考：n ≈ 4 × z² × p × (1 - p) / w²
其中：p = 规划用的基线比例；n = 单组样本量；w = 目标宽度（比例单位）
      z = 90% 置信取 1.6449，95% 取 1.96
```

这是 Wald 正态近似的**规划级量级估算**，不是从已观测数据算出的区间，也不是两版本差异的检验或功效分析。特别是样本少、失败数很少或比例靠近 0/1 时，正态区间可能不准；实际报告比例时应使用适合的区间方法（如 Wilson 或精确二项区间），并按实验设计评估差异。[NIST 对二项比例区间的说明](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)也提醒小样本/少事件下正态近似可能不够准确。

**这里的读法只能是规划级启发：单组区间参考值可以提示小样本不稳定，但不能把观测差异直接判作「噪声」或「显著」。** 第 15 章「净变化 +0.0 但逐条有变化」说明总分会掩盖用例变化；其统计显著性仍需按正确的配对/两组设计评估。

**它是可以自己算的**，不需要任何外部数据 —— 你的 p 和 n 都是自己定的。下面按单组区间宽度公式反解，给出**粗略样本量参考**。它没有纳入两组比较、α、功效、配对相关性或多阶段查看，因此不能用来宣称「每组 n 就足以检出该退步」。

```text
规划用基线错误率 2%，单组 90% 正态近似宽度参考：
宽度阈值 5.0 个百分点 → n≈85
宽度阈值 2.0 个百分点 → n≈531
宽度阈值 1.0 个百分点 → n≈2,122
宽度阈值 0.5 个百分点 → n≈8,486
```

（本地公式计算，2026-10-22；基线比例 p=0.02，z=1.6449。n 是**单组规划参考**，不是实际置信区间保证、两版本检验或功效结果；尤其 5 个百分点这档的期望失败数很少，正态近似只看量级。实际评估需使用合适区间和预先设计的比较方法。）

**这些数字只展示单组比例区间随 n 缩小的量级，不能直接当作灰度检出能力。** 对线上灰度的实际检出能力，需基于两版本的实验设计单独计算。

- **"灰度 100 个请求没发现问题"几乎不说明任何事** —— 这不是可靠检出概率的判断，正式功效需要两组设计计算

- **单组区间参考缩窄到 1 个百分点需要数千个样本** —— 两版本比较所需规模应另按实验设计计算

因此不能把“做了灰度”当成“已具备统计检出能力”。受控暴露可用严重故障 tripwire 保护用户；质量差异是否能被发现，仍取决于指标、样本量、流量分配与实验设计。不要由“小样本精度有限”推出任何固定的灰度能力边界。

## 那质量退化怎么发现

离线评测（第 15 章）通常便于控制条件和扩大样本，但线上灰度可验证真实流量行为；两者应按目标和风险互补。

| 信号 | 在哪里测 | 需要多少样本 |
|---|---|---|
| **严重故障/安全 tripwire** | 受控线上暴露 | 单次严重事件可触发暂停或调查；不能据此估算发生率 |
| **统计退化** | 离线评测或预先设计的线上比较 | 依目标效应、α、功效与设计计算 |
| **主观质量** | 人工校准 | 少但贵 |

这个分工的道理是：**检测与估计是两件事。** 一次严重崩溃或越权行为足以触发预设的暂停/调查规则，但不能估计发生率，也不能单独证明由新版本导致；微小质量差异则需要按效应量、方差、α、功效和实验设计准备样本。离线评测便于控制条件，线上比较能观察真实流量，两者互补。

不要把灰度阶段、流量百分比或单一信号写成通用门槛。每次扩量应按安全护栏、用户影响、观测窗口、样本设计与回滚能力设定；达到预先声明的停止条件就暂停，低严重度指标则不能凭一个百分点差异宣布显著。

## 一次发布的完整顺序

把上面的分工落成一个顺序：

```text
1. 离线回归（第 15 章）—— 按预先声明的评测设计比较候选版本
2. 受控暴露         —— 先保护用户与副作用边界，监测严重故障和服务健康
3. 逐步扩量         —— 每一步按停止条件、观测窗口和样本设计检查业务指标
4. 全量或回退       —— 保留可操作的开关，并确认状态/副作用的恢复方案
```

这里的顺序是决策框架，不是固定流量比例或时间表；每一阶段的流量、窗口和阈值应由服务风险与实验设计确定。

**第 1 步是最重要的，也是最容易跳过的** —— 因为"先上线看看"感觉更快。样本需求取决于目标效应、错误率、α、功效与实验设计；小幅质量退化可能需要很大的样本量。

## 回滚比发布难

最后说一个经常被低估的问题：**回滚不是"把版本号改回去"。**

三类东西改不回去：

**一、已经产生的副作用。** 发出去的邮件、改过的数据 —— 回滚代码不会撤销它们。

**二、已经写进存储的状态。** 如果新版本改了状态的结构，回滚代码之后旧版本读不懂那些状态。

**三、已经对外发生或持久化的行为。** 用户已经看到的输出、已写入的记忆/状态、已发出的通知或已提交的工具动作都不会因切换代码自动消失。通常一次响应不会让托管模型即时改变权重；若系统确实启用了在线学习或外部记忆写入，则还要分别设计其回退/隔离策略。

所以"可回滚"是一个**设计属性**，不是部署属性：

- 状态结构要向后兼容（新版本写的状态，旧版本要能读）
- 不可逆动作要有审计（第 19 章），以便回滚后人工补救
- 对支持补偿的关键动作设计撤销/补偿流程；补偿不等于历史副作用从未发生

## 一个具体的做法：发布单元 id 怎么用

上面说发布 manifest 与 trace 都带 `release_id`。下面是概念示例，不是某家厂商的标准格式：

```json
{
  "release_id": "rel_2026_10_22_a",
  "created_at": "2026-10-22T09:00:00+08:00",
  "parent_release_id": "rel_2026_10_20_b",
  "app_commit": "git:7d91a2f",
  "runtime_image": "sha256:…",
  "orchestrator_hash": "sha256:…",
  "prompt_bundle_hash": "sha256:…",
  "tool_bundle_hash": "sha256:…",
  "runtime_policy_hash": "sha256:…",
  "provider": "example-provider",
  "endpoint": "responses-api",
  "api_version": "2026-01-01",
  "requested_model_id": "provider-model-snapshot"
}
```

（示例：构造数据，未实跑。生产 manifest 应只含非敏感配置或不可变引用；不要把 API key、用户输入或渲染后含个人数据的 prompt 放进去。用规范化的结构化序列化给每项资产计算哈希，并保存对应构建物/引用。模型端实际解析出的版本信息若 API 有返回，放在**单次请求 trace**；不能假设 manifest 中请求的别名就是提供方实际执行的快照。）

各字段回答不同的问题：`app_commit` / `runtime_image` 定位应用制品；各 bundle hash 固定 prompt、工具实现与运行策略；provider/endpoint/API version/requested model ID 说明请求契约；`release_id` 则把这些不可变输入组合成一次发布。`parent_release_id` 帮助理解变更来源，但回滚目标仍应显式选定已验证的 release，并检查状态兼容性。

**为什么工具哈希要覆盖“集合”而不只是“每个工具”。** 工具集合的变化可能改变输入、选择候选与缓存前缀；影响程度依 endpoint、缓存策略、模型和任务而异。历史小样本无法给出通用成本或准确率结论。**加一个工具仍是行为配置的变更**，应进入版本审查并在相关回归集上验证。

（"离线回归"就是下一节那个分工里的第 1 步：**拿一份固定的评测集在新旧两版上各跑一遍，比逐条差异** —— 它不需要真实用户流量，所以叫离线。）

**单次模型请求的 trace 记录发布与实际请求边界：**

```json
{
  "ts": "2026-10-22T10:31:02.184+08:00",
  "task_id": "t_7f21a9",
  "release_id": "rel_2026_10_22_a",
  "provider": "example-provider",
  "endpoint": "responses-api",
  "api_version": "2026-01-01",
  "requested_model_id": "provider-model-alias",
  "response_model_id": "provider-returned-id-or-null",
  "provider_request_id": "req_example",
  "step": 4,
  "tool": "send_email",
  "ok": true,
  "latency_ms": 1840
}
```

（示例：构造数据，未实跑。实际字段按目标 API 响应契约选取；没有返回的 resolved model/fingerprint 应记录为空或“不可得”，不要猜。）

`release_id` 回答“是哪一组不可变发布输入”；每个请求的 provider、endpoint、请求 model ID 和可取得的响应元数据则回答“这次具体调用走了哪条接口路径”。路由可在一项任务中变化，所以模型信息应按 request/step 记；敏感用户输入和秘密不需要为了追踪而写进日志。部署后发现 manifest 与运行配置不一致时，应通过运行时校验或配置审计报告漂移，而不能假设日志里的 release ID 自动证明正在运行的文件哈希一致。

具体用起来能回答四类问题：

```text
1. 这次失败是哪个版本？          → 看日志里的 release id
2. 这个版本上线后变好了吗？       → 按 release 分组看评测通过率
3. 回滚之后问题消失了吗？        → 对比两个 release 的同一指标
4. 首次在哪个版本观察到这个失败？ → 查用例的 first_seen_release（不代表因果）
```

第 4 条能帮你定位**首次观察到失败的版本**，但不能单凭先后关系证明是哪次发布引入了缺陷。要识别回归，还得保留每个评测版本的逐用例结果、评分器版本与评测条件；新旧模型输出有随机性时，应按预设重复策略比较，而不是把一次 pass/fail 当作稳定事实。

`first_seen_release` 记录首次观察到失败时运行的发布，不代表因果归属。单独的 `first_seen_release` 和 `last_pass_release` 也不能推导当前状态；需另存最近一次评测的版本和结果，或查询完整的逐版本结果历史：

```json
{
  "case_id": "C-001",
  "input": "订单 A-1001 为什么没到",
  "expected": "应说明物流状态，不得编造送达时间",
  "first_seen_release": "rel_2026_10_05_a",
  "last_pass_release": "rel_2026_10_10_b",
  "latest_evaluated_release": "rel_2026_10_12_a",
  "latest_result": "fail",
  "evaluator_version": "grader-v3",
  "status": "regression"
}
```

（示例：构造数据，未实跑。）

`status` 应从逐版本的带版本评测结果导出，而不是从两个时间字段猜出来：最新一次 pass 表示当前通过；最新一次 fail 且此前有 pass 才能标记为回归；只有 fail、从未观察到 pass 则是未解决；没有结果则是未评测。对随机模型结果，结果还需带重复次数/聚合规则。离线构造的用例没有“线上首次失败版本”，应保留来源类型并让 `first_seen_release` 为空。

只有 `first_seen_release` 时，你能知道首次观察失败的版本；逐版本结果历史才能告诉你在哪些发布上测过、哪次通过、当前是否回归。这个时间线有助于定位调查范围，但本身不能证明某个发布造成了失败。

## 一个容易被忽略的版本：工具集合

发布单元里，「工具」至少要分别跟踪这些行为输入：

- **单个工具的描述**（改一个字就是变更）
- **工具集合本身**（加一个、删一个也是变更）

第二件容易被忽略，因为「加一个工具」看起来是新增功能，不是「修改」。它可能改变模型候选、请求输入和缓存行为，所以应按配置变更管理。第 2 节的 30 轮/62% 是固定工具数与重复输入假设下的本地计算，不是所有 provider 的账单占比；真实成本要按目标 endpoint 的 usage 与缓存字段核算。

**所以「加一个工具」应该走一次发布流程**，而不是在配置里随手加。它至少要有版本号、要能回滚、而且要在离线回归里跑一遍 —— 因为它可能影响已有工具的选择（第 4 章实测过工具语义重叠时模型会选错）。

## 一个具体的问题：模型版本更新的处理

模型标识与应用代码采用不同的版本契约：有些 endpoint 支持固定 snapshot，有些接受可移动 alias；无论哪种，模型都可能因生命周期策略而退役。

三种情况：

| 情况 | 做法 |
|---|---|
| 目标 endpoint 提供 pinned snapshot | 按其契约固定请求 ID；仍需监控退役并做迁移 |
| 目标 endpoint 接受可移动 alias | 记录请求 ID 与可得响应元数据；用持续评测发现行为变化信号 |
| 自部署模型 | 固定权重、推理栈与配置版本；自行承担验证和升级工作 |

当提供方只接受可移动的别名、或某个请求字段无法锁定实际模型时，定期基线评测可发现**行为变化信号**，但不能单独证明变化由模型造成；输入分布、评测器、运行时、服务侧变更与随机性也会影响结果。应同时记录请求/响应可得的版本元数据、评测集和评分器版本，并保留旧新配置对照。评测频率由变更风险和成本决定，不存在通用的每日门槛。

模型标识的稳定语义因 provider/API 而异：Anthropic 文档区分固定模型 ID 与便利别名，也维护独立退役时间表；OpenAI API 文档建议在一致行为重要时使用 pinned model versions 并持续 eval。部署前按目标 endpoint 查当前契约，并处理退役迁移，不能把“有 ID”当成永不变化或永远可用。[Anthropic model IDs and versions](https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions)；[Anthropic model deprecations](https://platform.claude.com/docs/en/about-claude/model-deprecations)；[OpenAI API overview](https://developers.openai.com/api/reference/overview)。

自部署可以控制权重文件和升级时机，但运行环境、推理引擎、硬件、量化和采样配置仍会影响行为；升级责任也由团队承担。它不是“完全可控”的同义词。

## 一个和「回滚」有关的细节：状态版本

第 2 节说过「状态结构要向后兼容」。具体实现上有一个便宜的技巧：**给持久化的状态加一个 schema 版本号。**

```text
{"schema": 3, "step": 4, "context": [...], ...}
```

这样有两个好处：一是旧版本读到新状态时能明确拒绝（而不是解析出错误的字段），二是排查时你能立刻知道这条状态是哪个版本写的。

它带来的一个额外能力是**渐进迁移**：新版本写入时同时兼容 v2 和 v3 的读法，几个发布周期之后再移除 v2 的代码。这比「一次性切换」安全得多 —— 因为一次性切换期间的回滚会让旧版本读不懂数据，而那正是第 2 节说的「回滚不是改版本号」的具体形态。
## 完整可运行代码

下面代码演示单组区间宽度的规划估算，并给出固定 seed 的两组模拟描述值；它不执行正式灰度检验或功效计算。

```python
"""单组比例精度的规划近似 + 两组模拟描述值（不是显著性检验）。"""
import math
import random

Z_90 = 1.6449


def wald_width_percentage_points(p, n):
    """规划用 Wald 正态近似的单组区间宽度，单位为百分点。"""
    if not 0 < p < 1 or n <= 0:
        raise ValueError("p must be in (0, 1) and n must be positive")
    return 2 * Z_90 * math.sqrt(p * (1 - p) / n) * 100


def planning_n(p, width_percentage_points):
    """反解单组区间宽度近似；不是两组检验的样本量或功效。"""
    if not 0 < p < 1 or width_percentage_points <= 0:
        raise ValueError("invalid planning inputs")
    target = width_percentage_points / 100
    return math.ceil(4 * Z_90**2 * p * (1 - p) / target**2)


def simulate_group_rates(baseline_err, new_err, groups, seed=7):
    """生成固定 seed 的示例比例；只展示数据，不给差异作统计判断。"""
    rng = random.Random(seed)
    results = []
    for label, n in groups:
        base_bad = sum(rng.random() < baseline_err for _ in range(n))
        new_bad = sum(rng.random() < new_err for _ in range(n))
        base_rate = base_bad / n
        new_rate = new_bad / n
        delta = (new_rate - base_rate) * 100
        results.append((label, n, base_rate, new_rate, delta))
    return results


if __name__ == "__main__":
    baseline_err = 0.02
    print("=== 单组 90% Wald 宽度的规划参考（不是发布门槛）===")
    print("规划基线错误率：2%；小样本/少事件时正态近似可能不准。")
    for width in (5, 2, 1, 0.5):
        print("宽度 %.1f 个百分点 -> 单组 n≈%s" % (width, format(planning_n(baseline_err, width), ",")))
    print()
    print("=== 固定 seed 的两组比例示例（仅描述观测，不作显著性判断）===")
    groups = [("A", 200), ("B", 2000), ("C", 10000), ("D", 50000)]
    for label, n, base_rate, new_rate, delta in simulate_group_rates(0.02, 0.04, groups):
        print("组%s n=%-5d 基线=%5.2f%% 新版=%5.2f%% 观测差=%+5.2f 个百分点"
              % (label, n, base_rate * 100, new_rate * 100, delta))
    print()
    print("读法：固定 seed 只让样例可复跑；它不代表真实流量、功效、置信区间或发布决策。")
    print("正式比较需预先定义分流/配对、指标、目标效应、显著性水平、功效、查看规则与回滚护栏。")
```

## 常见坑

- **只给代码打版本。** prompt、上下文、工具实现、运行策略和模型请求也可能改变行为；release manifest 与每次请求 trace 要覆盖各自的变化边界。
- **把单组区间宽度当成两版检验样本量。** 这里的正态近似只给规划量级；灰度比较必须另外设计对照、效应量、α、功效与查看规则。
- **跳过离线回归直接上线。** 这会让候选版本缺少受控对照；线上仍需护栏与回退方案。
- **把回滚当"改版本号"。** 副作用、已写入的状态、累积的行为都改不回去。
- **状态结构不向后兼容。** 那会让回滚之后旧版本读不懂新数据。
- **发布单元不可变。** 如果配置能在运行中被改，你就永远无法回答"当时跑的是哪一版"。
