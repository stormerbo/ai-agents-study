第 1 节说提示词和工具定义的变更影响可能比代码更大。这一节讲怎么管理这些变更 —— 以及灰度到底能测出什么。

## 什么需要版本号

一个常见的做法是给代码打版本号，而提示词和模型版本散在配置里。这有一个具体的后果：**出问题时你无法回答"当时跑的是哪一版"。**

需要版本化的四样：

| 资产 | 为什么 |
|---|---|
| **代码** | 常规 |
| **提示词** | 改一个字可能改变全部行为 |
| **工具定义** | 描述是指令；工具集合变化也是版本变化 |
| **模型版本** | 换版本 = 换执行者，行为会变 |

做法上有一个简单有效的模式：**把这四样打包成一个不可变的"发布单元"，每次上线生成一个 id。** 所有日志、追踪、评测结果都带这个 id。

这样出问题时你能做一件很关键的事：**把"某次失败"和"当时的配置"直接关联起来** —— 而不是靠时间戳去猜。

## 灰度能测出什么，测不出什么

这是本节的核心。计算要用到第 15 节那套**噪声底线** —— 先把它说清楚，否则下面那组数字没法迁移到你的场景。

**下面的噪声数值只作单组比例的粗略区间宽度参考，不是新旧版本差异的显著性检验，也不能给出统计功效。** 比例型指标（错误率、通过率）会随机抖动：100 个请求里有 2 个失败，再抽 100 个可能是 1 个也可能是 4 个 —— **这个抖动幅度随样本量缩小而变大**。正式比较新旧版本需要明确随机化/配对设计、两组样本量、显著性水平 α、目标功效 (1−β) 和可接受效应量，并用相应的两组比例或配对检验/置信区间；这里不做这些假设。

```text
单组 90% 区间半宽参考 ≈ z × √( p × (1 - p) / n )
其中：p = 参考比例（比如错误率 2%），n = 单个版本/单组的样本量
      z = 置信系数：90% 置信取 1.6449，95% 取 1.96
```

**这里的读法只能是规划级启发：单组区间参考值可以提示小样本不稳定，但不能把观测差异直接判作「噪声」或「显著」。** 第 15 章「净变化 +0.0 但逐条有变化」说明总分会掩盖用例变化；其统计显著性仍需按正确的配对/两组设计评估。

**它是可以自己算的**，不需要任何外部数据 —— 你的 p 和 n 都是自己定的。下面这张表是把单组区间宽度公式反解，并按原实验的约定换算出的**粗略样本量参考**。它没有纳入两组比较、α、功效、配对相关性或多阶段查看，因此不能用来宣称「每组 n 就足以检出该退步」。

```text
单组 90% 区间宽度阈值 5.0 个百分点 → n≈170
单组 90% 区间宽度阈值 2.0 个百分点 → n≈1,061
单组 90% 区间宽度阈值 1.0 个百分点 → n≈4,243
单组 90% 区间宽度阈值 0.5 个百分点 → n≈16,971
```

（本地启发式计算，2026-10-09；基线错误率 2%，z=1.6449。n 是单组样本数；所列数值仅来自单组区间宽度阈值，不是新旧版本比较的检验设计或功效结果。）

**这些数字只展示单组比例区间随 n 缩小的量级，不能直接当作灰度检出能力。** 对线上灰度的实际检出能力，需基于两版本的实验设计单独计算。

- **"灰度 100 个请求没发现问题"几乎不说明任何事** —— 这不是可靠检出概率的判断，正式功效需要两组设计计算

- **单组区间参考缩窄到 1 个百分点需要数千个样本** —— 两版本比较所需规模应另按实验设计计算

所以灰度的作用被普遍高估了。小流量灰度更适合观察明显的运营信号（报错、超时、崩溃）；是否能可靠发现某类问题，仍取决于样本量和设计。统计结论不能由「小样本通常看不出细微变化」推成固定能力边界。

## 那质量退化怎么发现

离线评测（第 15 章）通常便于控制条件和扩大样本，但线上灰度可验证真实流量行为；两者应按目标和风险互补。

| 信号 | 在哪里测 | 需要多少样本 |
|---|---|---|
| **灾难性故障** | 线上灰度（1%） | 少 —— 信噪比高 |
| **统计退化** | 离线评测（回归集） | 依目标效应、α、功效与设计计算 |
| **主观质量** | 人工校准 | 少但贵 |

这个分工的道理是：**两类信号的统计性质不同。** 崩溃是一个"要么发生要么不发生"的强信号（一次就够），而"回答质量下降 2%"是一个弱信号（要几千次才能确认）。

**把弱信号拿到线上大流量里去测，是一个昂贵且危险的做法** —— 因为它要求你先放量，而放量本身就扩大了爆炸半径。

## 一次发布的完整顺序

把上面的分工落成一个顺序：

```text
1. 离线回归（第 15 章）—— 按设计检验统计退化，再决定是否进入线上
2. 灰度 1%  —— 只看灾难性指标（报错、超时、崩溃、成本异常）
3. 灰度 20% —— 看业务指标（任务完成率、用户重问率）
4. 全量     —— 同时保留回滚开关
```

**第 1 步是最重要的，也是最容易跳过的** —— 因为"先上线看看"感觉更快。样本需求取决于目标效应、错误率、α、功效与实验设计；小幅质量退化可能需要很大的样本量。

## 回滚比发布难

最后说一个经常被低估的问题：**回滚不是"把版本号改回去"。**

三类东西改不回去：

**一、已经产生的副作用。** 发出去的邮件、改过的数据 —— 回滚代码不会撤销它们。

**二、已经写进存储的状态。** 如果新版本改了状态的结构，回滚代码之后旧版本读不懂那些状态。

**三、已经累积的行为。** 用户看到的输出、模型学到的东西。

所以"可回滚"是一个**设计属性**，不是部署属性：

- 状态结构要向后兼容（新版本写的状态，旧版本要能读）
- 不可逆动作要有审计（第 19 章），以便回滚后人工补救
- 关键动作要有"撤销"能力（第 19 章那条：把不可逆变成可逆）

## 一个具体的做法：发布单元 id 怎么用

上面说"打包成发布单元、日志都带它"。**先说清"打包"是什么形态** —— 最简单也最够用的是**一个不可变文件加一行日志字段**：

```json
{
  "release_id": "rel_2026_10_12_a",
  "prompt_hash": "sha256:3c1f9ab2…",
  "tools_hash": "sha256:77de04c1…",
  "model_id": "deepseek-flash",
  "created_at": "2026-10-12T09:00:00+08:00",
  "parent_release_id": "rel_2026_10_10_b"
}
```

（示例：构造数据，未实跑 —— 它是产物格式的示例。`release_id` 的命名与哈希算法都可以换成你的规范，关键是**它不可变、四个资产都在里面**。）

**五个字段各自固定住什么：**

| 字段 | 它固定住什么 | 怎么生成 |
|---|---|---|
| `release_id` | 这次发布的唯一名字，所有日志与用例都引用它 | 时间戳加序号，或 CI 的运行号 |
| `prompt_hash` | 系统提示与所有模板的逐字内容 | 对所有提示词文本拼接后取哈希 |
| `tools_hash` | **工具集合**，含每个工具的 schema 与 reversible 标注 | 对工具定义列表排序后取哈希 |
| `model_id` | 执行者。托管模型要记**你请求的那个标识** | 配置里的模型名 |
| `parent_release_id` | 从哪一版改过来的 —— 回滚时按它往回走 | 上一次发布填进来 |

**为什么 `tools_hash` 要覆盖"集合"而不只是"每个工具"。** 因为第 4 章实测过：工具数量直接决定每轮输入成本（约 60 token/个），而语义重叠会让模型选错。**加一个工具是一个会影响行为的事件** —— 它应该改哈希、走发布流程，而不是在配置里随手加。

（"离线回归"就是下一节那个分工里的第 1 步：**拿一份固定的评测集在新旧两版上各跑一遍，比逐条差异** —— 它不需要真实用户流量，所以叫离线。）

**一份日志或追踪记录怎么带这个 id：**

```json
{
  "ts": "2026-10-12T10:31:02.184+08:00",
  "task_id": "t_7f21a9",
  "release_id": "rel_2026_10_12_a",
  "prompt_hash": "sha256:3c1f9ab2…",
  "tools_hash": "sha256:77de04c1…",
  "model_id": "deepseek-flash",
  "step": 4,
  "tool": "send_email",
  "ok": true,
  "latency_ms": 1840
}
```

（示例：构造数据，未实跑。）

**注意这里同时写了 `release_id` 和三个哈希。** 看着冗余，但它们回答的问题不同：`release_id` 回答"是哪一次发布"，哈希回答"我实际拿到的这份内容，和那次发布记录的是不是同一份"。**区别在有人手改了线上配置时显现** —— 那时 id 还对，哈希对不上。

具体用起来能回答四类问题：

```text
1. 这次失败是哪个版本？          → 看日志里的 release id
2. 这个版本上线后变好了吗？       → 按 release 分组看评测通过率
3. 回滚之后问题消失了吗？        → 对比两个 release 的同一指标
4. 这条评测用例是哪个版本引入的？  → 用例上带的 first_seen_release
```

第 4 条最有价值，因为它让评测集**带着历史**：一条用例不只是「这个输入会失败」，还有「它是从哪一版开始失败的」。当一个新版本把它修好时，你能明确地说「v14 修好了 v12 引入的问题」。

而这条能力落在一个字段上：**`first_seen_release` 指的是"这条评测用例第一次失败时，线上跑的是哪个发布单元"** —— 它在用例被创建的那一刻写死，之后不再改。配上"最后一次通过"的版本，一条用例的完整形态是：

```json
{
  "case_id": "C-001",
  "input": "订单 A-1001 为什么没到",
  "expected": "应说明物流状态，不得编造送达时间",
  "first_seen_release": "rel_2026_10_05_a",
  "last_pass_release": "rel_2026_10_10_b",
  "status": "regression"
}
```

（示例：构造数据，未实跑。）

**`first_seen_release` 加 `last_pass_release` 就能算出这条用例的年龄与当前状态**：两者相同 → 从没修好过（待修）；`first_seen` 早于 `last_pass` → 曾经修好过又坏了（回归，优先级最高）；没有 `first_seen` → 它来自离线构造，不是线上失败。**三种状态的处置方式完全不同**，而它们只能从这两个字段推出来。

而如果没有这个 id，你只知道「这条用例曾经失败过」—— 无法判断它是老问题还是新引入的回归。**而这个区别决定了你该把它当成「待修」还是「已验证」。**

## 一个容易被忽略的版本：工具集合

上面列了四个要版本化的资产，其中「工具定义」其实包含两件事：

- **单个工具的描述**（改一个字就是变更）
- **工具集合本身**（加一个、删一个也是变更）

第二件容易被忽略，因为「加一个工具」看起来是新增功能，不是「修改」。但它对模型的影响是实打实的：第 4 章实测过工具数量与 token 成本的关系（约 60 token/个，每轮都要付），而第 2 节那个成本模型算出 30 轮时工具定义占输入侧 62%。

**所以「加一个工具」应该走一次发布流程**，而不是在配置里随手加。它至少要有版本号、要能回滚、而且要在离线回归里跑一遍 —— 因为它可能影响已有工具的选择（第 4 章实测过工具语义重叠时模型会选错）。

## 一个具体的问题：模型版本更新的处理

上面把「模型版本」列为要版本化的资产，但它和另外三个有一个关键不同：**你不一定能锁住它。**

三种情况：

| 情况 | 做法 |
|---|---|
| 厂商提供固定版本号 | 锁住，变更时走完整发布流程 |
| 厂商只提供滚动别名（latest） | 锁不住 —— 只能靠监控发现行为变化 |
| 自部署 | 完全可控，但要自己承担升级工作 |

第二种最麻烦，而它很常见。应对方式是**建立一个基线监控**：定期（比如每天）用固定的评测集跑一遍，如果通过率突然变化而你没有发布任何东西，那就是模型变了。

这个监控的价值在于：**它让你能把「模型变了」和「我改坏了」这两个原因分开。** 而如果没有它，一次突然的质量下降会让你去翻自己的 git 历史 —— 翻半天发现代码没动过。

第三种（自部署）有一个反过来的好处：**升级是可计划的。** 你可以先在离线评测上跑新版本，对比之后再决定什么时候上。这是托管模型做不到的 —— 厂商什么时候更新，你说了不算。

## 一个和「回滚」有关的细节：状态版本

第 2 节说过「状态结构要向后兼容」。具体实现上有一个便宜的技巧：**给持久化的状态加一个 schema 版本号。**

```text
{"schema": 3, "step": 4, "context": [...], ...}
```

这样有两个好处：一是旧版本读到新状态时能明确拒绝（而不是解析出错误的字段），二是排查时你能立刻知道这条状态是哪个版本写的。

它带来的一个额外能力是**渐进迁移**：新版本写入时同时兼容 v2 和 v3 的读法，几个发布周期之后再移除 v2 的代码。这比「一次性切换」安全得多 —— 因为一次性切换期间的回滚会让旧版本读不懂数据，而那正是第 2 节说的「回滚不是改版本号」的具体形态。
## 完整可运行代码

下面代码展示一个单组区间阈值对应的样本量参考，并模拟观测差异提示；不是正式灰度检验或功效计算。

```python
"""灰度发布：单组区间参考与观测差异提示（非显著性检验）。

复用第 15 节的单组区间近似作为样本量级参考。正式判断新旧版本差异需要另行设计检验。

纯本地，实跑状态：2026-10-09。
"""
import math, random

Z = 1.6449


def ci_width(p, n):
    return 2 * Z * math.sqrt(p * (1 - p) / n) * 100


def need_n(p, delta):
    """单组 90% 区间宽度的启发式反解；不是两组检验的样本量/功效计算。"""
    n = 1
    while n < 1000000:
        if ci_width(p, n) <= delta / math.sqrt(2):
            return n
        n += 1
    return None


def rollout(baseline_err, new_err, stages, seed=7):
    """模拟观测数据并打印启发式提示；不判断统计显著性或放量。"""
    random.seed(seed)
    log = []
    for pct, n in stages:
        base_bad = sum(1 for _ in range(n) if random.random() < baseline_err)
        new_bad = sum(1 for _ in range(n) if random.random() < new_err)
        base_rate = base_bad / n
        new_rate = new_bad / n
        noise = ci_width(baseline_err, n)
        delta = (new_rate - base_rate) * 100
        # 启发式提示：将两组差异与单组基线区间半宽比较；不是有效的两组显著性检验。
        half = noise / 2
        if abs(delta) <= half:
            verdict = "差异未越过单组参考带；本演示不作结论"
        elif delta > 0:
            verdict = "观测差异超过单组参考带；需正式实验/人工判断（差 %.1f 点 > 参考半宽 %.1f）" % (delta, half)
        else:
            verdict = "观测差异超过单组参考带；不能据此判定改善"
        log.append((pct, n, base_rate, new_rate, delta, noise, verdict))
    return log


if __name__ == "__main__":
    print("=== 一、单组区间宽度阈值对应的样本量参考（非两组检验）===")
    print("  （基线错误率 2%，即大多数请求是好的）")
    print()
    for delta in (5, 2, 1, 0.5):
        print("    单组区间宽度阈值 %.1f 个百分点 → n≈%d" % (delta, need_n(0.02, delta)))
    print()
    print("  这些数仅是单组区间参考的量级，不是两组检验样本量或功效计算。")
    print("  所以「灰度 100 个请求没发现问题」几乎不说明任何事。")
    print()
    print("=== 二、演示观测差异提示（非显著性检验；基线 2%，新版 4%）===")
    stages = [("1%", 200), ("5%", 2000), ("20%", 10000), ("50%", 50000)]
    for pct, n, b, nw, delta, noise, verdict in rollout(0.02, 0.04, stages):
        print("  灰度 %-4s n=%-6d 基线 %.2f%%  新版 %.2f%%  差 %+.2f 点  （单组参考半宽 ±%.1f）→ %s"
              % (pct, n, b * 100, nw * 100, delta, noise / 2, verdict))
    print()
    print("=== 读法 ===")
    print("  上面只是一次固定 seed 的模拟观测；4% 对 2% 的设定差异较大，提示超过参考带，但该次输出本身不是检验结论。")
    print("  真实的新旧版本比较应按预设实验设计计算，而不是把下表当检出能力：")
    print("    单组 90% 区间启发式：1 个点约 4,243 个、0.5 个点约 16,971 个；这些数不是两组比较的功效样本量。")
    print()
    print("  所以「灰度 100 个请求没发现问题」几乎不说明任何事 ——")
    print("  单组区间阈值对应约 170 个样本；不能据此断言两组比较的检出概率。")
    print()
    print("  这只是启发式演示；不得把输出中的‘退步’或‘改善’当成统计显著结论。")
    print("  这就是灰度设计里的核心张力：")
    print("    · 小流量 → 样本少 → 统计精度有限（但爆炸半径小）")
    print("    · 大流量 → 可提高统计精度（但爆炸半径大）")
    print()
    print("  解法不是二选一，而是**分两层**，看两类不同的信号：")
    print("    小流量（1%）：看灾难性故障 —— 报错率、超时率、崩溃，这些信号强、噪声低")
    print("    大流量（20%+）：看统计退化 —— 用第 15 节那套评测，而不是线上错误率")
    print()
    print("  这个分工的道理是：**灾难性故障的信号信噪比高，小样本就够；")
    print("  细微统计退化需要按效应量和功效设计足够样本；离线评测通常更易控制条件，线上灰度用于验证真实流量表现。**")
```

## 常见坑

- **只给代码打版本。** 提示词、工具定义、模型版本都会改变行为，日志里要能查到当时是哪一版。
- **以为灰度能测出质量退化。** 实测：单组 90% 区间启发式参考：1 个点对应约 4,243 个样本；这不是两组灰度检验的样本量。
- **跳过离线回归直接上线。** 那是把弱信号放到最贵、最危险的地方去测。
- **把回滚当"改版本号"。** 副作用、已写入的状态、累积的行为都改不回去。
- **状态结构不向后兼容。** 那会让回滚之后旧版本读不懂新数据。
- **发布单元不可变。** 如果配置能在运行中被改，你就永远无法回答"当时跑的是哪一版"。
