## agent 部署的三个特殊之处

一个 agent 服务看起来就是一个 HTTP 服务。但它有三处和普通服务不同：

**一、它是有状态的，而且状态不在你手里。** 一次任务跨多轮调用，中间状态要存；而它的"输入"里包含模型这个你控制不了的依赖。

**二、它的延迟分布很宽。** 第 18 章实测：一次调用从 1.2 秒到 7.5 秒，取决于输出长度。而一个 agent 任务可能包含几十次这样的调用。

**三、它的失败是"部分成功"。** 一个普通服务要么成功要么失败；agent 常常是"做到第 4 步，第 5 步失败了" —— 而前 4 步的副作用还在。

第三点决定了本章的大部分内容：**agent 的部署要考虑"走到一半"的状态。**

## 三种部署形态

| 形态 | 形态 | 适合 |
|---|---|---|
| **同步请求** | 用户等结果，一次 HTTP 请求返回 | 短任务（几秒内） |
| **异步任务** | 提交后返回任务 id，轮询或推送结果 | 长任务（几十秒到几分钟） |
| **常驻会话** | 一个长连接持续交互 | 需要多轮澄清的任务 |

选择依据主要是**任务时长**，而 agent 的时长有一个特点：**它不可预知。** 第 10 章实测过计划在分支任务上 0/3 —— 步数事先不知道，所以时长也不知道。

这个不可预知性带来一个实用建议：**默认按异步设计，但对短任务走快路径。** 具体说，先同步等 N 秒（比如 20 秒），超时了再转成异步任务并返回 id。这样绝大多数短任务体验最好，而长任务也不会把连接挂死。

第 19 章讲流式时说过同一件事的另一面：**用户能接受等待，但不能接受不知道在等什么。** 所以无论同步还是异步，进度反馈都是必需的。

## 每个请求都是独立的问题

agent 服务有一个容易被忽略的性质：**它的每个请求都要重新组装全部上下文。**

这意味着三件事：

- **请求不能太"轻"。** 一个请求要携带历史状态（或者从存储里读），而读存储是一次额外的往返

- **连接复用很重要。** 第 18 章那个固定开销（0.6 到 0.9 秒）里有相当一部分是建连与 TLS

- **不能靠"粘性会话"省事。** 如果状态存在进程内存里，那么水平扩容会把同一个会话的不同轮次打到不同实例上 —— 而这类 bug 在单实例开发时完全看不出来

第三条是最常见的部署事故。它的表现是"扩容之后偶发丢上下文"，而且**只在并发量上来之后出现** —— 因为它依赖于负载均衡把连续两次请求分到不同实例。

## 配置也是代码

agent 的"代码"不只是 Python 文件，还包括三类运行时资产：

| 资产 | 改它的风险 |
|---|---|
| **提示词** | 高 —— 它就是指令，改一个字可能改变全部行为 |
| **工具定义** | 高 —— 描述同样是指令（第 17 章） |
| **模型版本** | 中到高 —— 换版本等于换了一个执行者 |

三者都不在代码仓库的常规 review 流程里，但它们的变更影响**可能比代码更大**。所以第 2 节要讲版本管理，第 4 节要讲上线后的循环。三者一旦丢失或不一致，表现不是报错，而是「它好像忘了刚才做的事」—— 而这类问题在日志里看不出来，只能靠追踪（第 15 节）才能定位：去看那一步的工具返回值是什么、历史消息里少了哪一轮。没有轨迹时，这个问题几乎无法复现。

一个具体建议：**把提示词和工具定义当代码对待** —— 进 git、走 review、有版本号、可回滚。这不是形式主义，而是因为**它们的变更同样需要灰度**（第 2 节会用数据说明为什么）。


## 一个具体的估算：三种形态各自适合多长

上面那个「总延迟 ≈ 0.8s + 输出/180」的式子可以直接用来判断形态。代进去：

```text
任务              轮数    估算延迟    适合的形态
短任务              1      1.9s      同步
中任务              4     12.1s      同步（接近边界）
长任务             15     49.7s      异步 + 必须进度反馈
```

（本地计算，2026-10-09。）

**注意 20 秒这个边界的来历。** 它不是技术限制，是**用户注意力**的经验值：20 秒以内的等待，用户愿意盯着看；超过之后他就开始做别的事，那时同步返回的体验会变成「我回来发现结果不见了」。

所以混合策略的阈值取 20 秒左右是合理的：**不是「超过 20 秒就做不完」，而是「超过 20 秒用户就走了」。**

而异步形态有一个必须做对的地方：**返回任务 id 之后，结果的取回路径要明确。** 三种做法：轮询（简单，但延迟取决于间隔）、推送（SSE / WebSocket，实时）、通知（邮件或站内信，适合分钟级以上）。长任务用第二种，小时级用第三种。

## 一个容易被忽略的部署细节：超时链

agent 服务有一个容易出事故的地方：**超时是分层的，而各层的值经常配错。**

一次请求会经过好几层超时：

```text
CDN / 网关        60s
负载均衡          60s
应用服务器        30s
上游模型调用      25s          ← 单次调用
整个 agent 循环   300s         ← 多轮累计
```

问题出在最后两行：**单次调用超时（25 秒）和循环总超时（300 秒）不是一回事，而它们必须搭配使用。**

- 只设单次调用超时 → 一个 30 轮的循环可以跑 750 秒，把连接占死
- 只设循环总超时 → 单次调用卡住时，要等到总超时才发现
- **两者都设**，而且循环总超时不能小于单次超时

还有一个跨层的坑：**应用层超时必须小于网关层超时。** 如果应用设 60 秒、网关也设 60 秒，那么应用还差一点没返回时网关先断了 —— 用户看到网关的错误（通常是 502），而日志里应用还在正常跑。这个现象很容易被误判成「偶发网络问题」。

## 一个和「部分成功」有关的设计

第 1 节提到 agent 的失败常常是「部分成功」。部署层面要处理它，有两种做法：

**一、把中间结果持久化。** 每一步完成后写状态，失败时从中断处继续（第 11 章那套）。
**二、把「已完成的部分」返回给用户。** 哪怕整体失败了，前几步的产出也有价值（第 18 章讲预算闸门时说过同一点）。

第一种是机制，第二种是接口设计。两者可以并存，而**第二种的收益常常被低估** —— 用户拿到「我读了三份文档，这是摘要，但第四份打不开」，比拿到「任务失败」有用得多。

实现上它有一个要求：**返回值要能表达「部分完成」这个状态**，而不是二元的成功或失败。这是 agent 接口和普通 REST 接口的一个真实差别。
## 完整可运行代码

下面这段代码模拟三种部署形态在延迟上的表现，并演示"同步等待 N 秒后转异步"的混合策略。

```python
"""三种部署形态的延迟表现，以及混合策略。纯本地。实跑状态：2026-10-09。"""
import time

# 用第 18 章的实测式：总延迟 ≈ 0.8s + 输出/180
def task_latency(turns, out_per_turn):
    per = 0.8 + out_per_turn / 180
    return turns * per


TASKS = [("短任务", 1, 200), ("中任务", 4, 400), ("长任务", 15, 500)]


def sync(task):
    t0 = time.time()
    lat = task_latency(*task[1:])
    time.sleep(min(lat, 0.02))       # 压缩时间，只为演示
    return lat


def hybrid(task, threshold=20.0):
    lat = task_latency(*task[1:])
    if lat <= threshold:
        return "同步返回", lat
    return "转异步（返回任务 id）", lat


if __name__ == "__main__":
    print("任务延迟估算（总延迟 ≈ 0.8s + 输出/180，乘以轮数）")
    print()
    print("  %-10s %-8s %-10s %s" % ("任务", "轮数", "估算延迟", "适合的形态"))
    for name, turns, out in TASKS:
        lat = task_latency(turns, out)
        shape = "同步" if lat <= 20 else ("异步" if lat <= 300 else "异步 + 必须进度反馈")
        print("  %-10s %-8d %-10s %s" % (name, turns, "%.1fs" % lat, shape))
    print()
    print("=== 混合策略：先同步等 20 秒，超时转异步 ===")
    for name, turns, out in TASKS:
        how, lat = hybrid((name, turns, out))
        print("  %-10s 延迟 %6.1fs → %s" % (name, lat, how))
    print()
    print("=== 关键点 ===")
    print("  长任务的延迟是**不可预知**的（第 10 章实测：计划在分支任务上 0/3），")
    print("  所以不能『按任务类型』静态分流，只能按**实际已经跑了多久**分流。")
    print("  这就是混合策略的价值：它不需要预知，只需要一个阈值。")
    print()
    print("  另外：无论同步还是异步，超过 ~1 秒就该有进度反馈 ——")
    print("  用户能接受等待，但不能接受不知道在等什么（第 19 章）。")
```

## 常见坑

- **把 agent 当普通无状态服务部署。** 它的状态跨多轮调用，而且不能存进程内存。
- **用粘性会话省事。** 扩容后会出现"偶发丢上下文"，而这个 bug 在单实例开发时看不出来。
- **假设时长可预知。** 第 10 章实测过计划在分支任务上 0/3 —— 步数事先不知道。
- **只同步或只异步。** 混合策略更好：先同步等 N 秒，超时转异步返回任务 id。
- **把提示词和工具定义当配置改。** 它们是指令，影响可能比代码更大，要进 git、走 review。
- **忽略"部分成功"。** 普通服务要么成功要么失败；agent 常常是做到一半，而前几步的副作用还在。
