## agent 部署的三个特殊之处

agent 服务可以部署在 HTTP 服务之上；与多步骤编排相关的三个设计压力是：

**一、状态跨越多个执行步骤。** 编排状态、任务状态和外部副作用需要由应用按各自契约管理；模型是外部依赖，但这不等于任务状态“不在你手里”。部分 API 可托管对话上下文，例如 [OpenAI Conversations API](https://developers.openai.com/api/docs/guides/conversation-state) 提供跨会话/设备/任务使用的 durable conversation id；这不等于应用的任务 deadline、审批、租户授权、外部副作用账本也由它管理。使用托管会话前仍需核对保留、恢复与删除语义。

**二、端到端延迟由多段关键路径组成。** 模型等待、工具调用、队列、重试与网络都会影响总时长。第 18 章的四行历史数据只有各一条样本，原始 trace、请求标识、精确模型快照与重复样本缺失，不能据此建立延迟分布、输出速率或固定网络开销；详见 [数据限制](../../../docs/DATA.md)。

**三、一次任务可能留下已提交的外部效果。** 例如前几步已写数据库，后续步骤才失败。分布式服务同样会遇到部分提交；agent 的多步骤编排让这种状态更常见，也更需要记录与对账。

因此，本章聚焦于：**任务状态如何持久化、执行如何恢复，以及已经发生的外部效果如何表达和对账。**

## 三种部署形态

| 形态 | 做法 | 适合 |
|---|---|---|
| **同步请求** | 请求内等待并直接返回结果 | 调用方时限足够、允许连接等待且恢复语义清晰的工作 |
| **异步任务** | 持久化提交后返回任务 id，之后查询或接收结果 | 断连后仍需继续、等待人工或超出请求时限的工作 |
| **常驻会话** | 持续交互的会话接口/连接（具体由协议定义） | 需要多轮澄清，且连接成本与恢复契约可接受的任务 |

选择依据包括**任务是否需要跨请求继续、是否要等待人工、结果获取方式、调用方与基础设施的时限，以及恢复/幂等要求**，不只是时长。实际时长会受模型输出、工具、分支、重试与队列影响；第 10 章的历史计划评分 0/3 因原始响应和有效 scorer 缺失，不能证明任务时长不可预测。

对需要断开 HTTP 后继续的任务，一个可审查的方案是：**先持久化任务和可恢复的调度信号，再由 worker 领取；HTTP 可等待同一任务一段时间，超时后返回原 task id。** 超时只结束 HTTP 等待，不会自动取消 worker，也不应重新提交第二份工作。阈值应依据产品体验、端到端 deadline 和基础设施限制配置，不能保证任务会在阈值内完成。

## 任务提交与 HTTP 等待怎么配合

这条建议有三个必须先答的问题：**任务什么时候持久化？由谁执行？客户端拿到 id 后怎么取结果？**

**先看状态机。** 任务先持久化并由唯一的执行机制领取；HTTP 只等待这个任务或返回它的 id。数据库任务表可以直接做小规模队列，也可以与 outbox 配合投递到外部队列：

```text
POST /agent
  ├ 事务：创建 task（status=queued）和可恢复的调度记录
  ├ worker 领取该 task（status=running），执行一次尝试；崩溃、租约过期或重试可能产生后续尝试，外部副作用要由接收端实际执行的幂等键/fencing 契约保护，或由显式对账处理
  ├ HTTP 等待同一个 task，最多 N 秒
  │    ├ task 已完成 → 返回结果
  │    └ 等待超时 → 返回原 task_id 和当前状态；worker 继续
  └ 客户端拿到 task_id → GET /agent/{task_id} 轮询或订阅

GET /agent/{task_id} → { status: queued | running | waiting_approval | partial | done | failed | cancel_requested | cancelled, result?, partial?, event_cursor? }
```

**`event_cursor` 是事件流的续读位置，不等于可直接交付的部分答案。** API 应分别定义事件分页/确认语义、已持久化的部分产物及其完整性；只有经过校验且对用户安全的产物才作为 `partial` 返回。若没有可恢复事件，就不要伪造游标。

**任务的记录长这样**（生产实现应使用持久存储；单进程内存不能承担重启恢复）：

```json
{
  "task_id": "t_7f21a9",
  "tenant_id": "tenant_demo",
  "idempotency_key": "client-request-42",
  "request_ref": "encrypted://task-inputs/t_7f21a9",
  "request_digest": "sha256:…",
  "status": "queued",
  "attempt": 0,
  "execution_epoch": 0,
  "created_at": "2026-10-12T10:31:02+08:00",
  "sync_wait_budget_ms": 20000,
  "task_deadline_at": "2026-10-12T10:36:02+08:00",
  "cancel_requested": false,
  "partial": null,
  "event_cursor": 0,
  "release_id": "rel_2026_10_12_a",
  "error": null
}
```

任务详情、事件和结果接口每次都应按 tenant 与调用方权限检查访问；不可猜的 `task_id` 也不是授权机制。输入引用和轨迹应按数据分级、加密、访问控制和保留期策略处理。

（示例：构造数据，未实跑 —— `tenant_id` / 幂等键唯一索引、payload digest、outbox、lease fencing、敏感输入存储与 TTL 都是实现责任，不是这个 JSON 自动提供的保证。）

| 字段 | 为什么必须有 | 少了它会怎么坏 |
|---|---|---|
| `task_id` | 超时后客户端唯一的寻址键 | 客户端只能重新提交，前半段白跑 |
| `tenant_id` + `idempotency_key` + `request_digest` | 在调用方作用域内识别重试，并拒绝同键不同请求 | 跨租户碰撞或把不同请求静默映射到旧任务 |
| `request_ref` | 让 worker 能取回被保护和保留的原始输入 | 只存 task id 无法从队列恢复执行；原文应按隐私与保留策略存储 |
| `attempt` + `execution_epoch` | 区分重试次数与当前 worker 所有权代次 | 过期 worker 可能覆盖新 owner 的状态或结果；fencing 只有在写入接收端验证 epoch 时才能拦截旧 owner |
| `task_deadline_at` + `cancel_requested` | 区分整个任务 deadline 与 HTTP 等待预算，并表达取消请求 | handler 等待超时可能被错误地当作任务取消 |
| `status` | 区分排队、运行、等待审批、完成、失败和取消 | 客户端无法判断该等还是该取 |
| `partial` / `event_cursor` | 分别表示经过校验的部分产物与事件续读位置 | 把事件偏移当答案可能展示未完成/不安全内容；没有稳定事件 ID 时可能丢失或重复读取 |
| `sync_wait_budget_ms` | 记录本次 HTTP handler 最长等待预算 | 把等待预算和任务 deadline 混为一谈，会错误地取消或超时整项任务 |
| `release_id` | 关联发布单元（第 2 节），出问题时知道是哪一版跑的 | 只能靠时间戳猜版本 |
| `error` | 失败时的原因要能取回，而不是只在日志里 | 客户端只能看到"failed"，不知道能不能重试 |

**服务端的形状（伪代码，重点在顺序）：**

```python
# POST /agent 的处理骨架 —— 伪代码；worker 负责执行，HTTP handler 不执行任务
def handle_agent_request(payload, tenant_id, idempotency_key):
    submission = create_or_get_durable_task(
        tenant_id=tenant_id,
        idempotency_key=idempotency_key,
        request=payload,  # 保存受保护的 request_ref 和规范化 digest
    )  # task 与 outbox/调度记录原子提交；同键异 payload 返回冲突
    task = submission.task
    try:
        return wait_for_task(task.id, timeout_s=20)  # 只观察 worker 创建的同一任务
    except Timeout:
        current = read_task(task.id)
        return {"task_id": task.id, "status": current.status,
                "event_cursor": current.event_cursor}
```

**两条判据，来自这个顺序：**

1. **任务必须先持久化，再由可恢复的调度机制领取。** 队列可能重复投递；worker 崩溃、租约过期后也可能有新尝试。应只允许当前 lease/epoch 更新任务状态，并由接收端支持的幂等键/fencing 契约或显式对账处理外部重复效果。
2. **同步返回与异步查询都观察同一个 task id。** 同步只是 HTTP handler 等待得更久，不是第二套执行路径。
3. **提交请求需要幂等键。** 在租户/调用方作用域内，用稳定键和规范化请求摘要关联已提交任务；同键同 payload 返回原 task id，同键不同 payload 应返回冲突，不能静默复用旧任务。幂等记录与任务创建应在同一事务或等价可靠机制中完成。

较长或存在等待/审批的任务应定义可观察的进度与状态；短任务是否需要细粒度反馈，按产品体验和失败诊断需求决定。不要把模型事件、工具调用意图或尚未校验的中间值直接当成已完成结果。

## 请求上下文与实例状态

如果采用**无状态请求/响应 API**，应用通常需要在每次请求中传入对话历史，或从持久层读取并组装请求；托管会话 API 的状态契约可能不同，必须按目标接口核对。连接复用可减少连接建立开销，但第 18 章四个单次历史样本没有足够证据把 0.6–0.9 秒归因于 TCP/TLS。

负载均衡把请求发往不同实例本身不是错误；风险在于把必须跨请求存在的唯一状态只放在进程内存。只要部署了多个实例且连续请求有机会被路由到不同实例，就可能出现丢状态，不必等到高并发。粘性会话只能影响路由，无法替代持久状态，也不能覆盖重启、重试、扩缩容或路由策略变化。

## 三个后面要用到的词

这一节和下一节会反复提到三样东西，先把它们定义清楚：

**一、前缀（prefix）与 prompt caching。** 请求内容按顺序序列化为 prompt 或消息后，模型提供方可能缓存其中满足其规则的前缀。缓存是否启用、匹配单元、断点、TTL、最小长度、usage 字段与计费折扣都取决于提供方、API 和模型版本；参见 [Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching) 与 [DeepSeek](https://api-docs.deepseek.com/guides/kv_cache/) 文档。不能把通用语义概括为“逐字匹配整个前缀”或保证命中就一定更快/更便宜。第 18 章的 0.0%、9.8%、21.6%、95.1% 是简化分段前缀模型的算术结果，不是 provider 实测命中率；各家的持久单元和匹配规则不同，应该查看目标端点的 usage 并测量实际账单/延迟。

**二、任务记录与轨迹的区别。** **任务记录**是当前状态快照，客户端按 `task_id` 取它；**轨迹（trace）** 会记录一次或多次执行尝试中的事件，用于排查与审计。轨迹不一定完整或不可变，取决于采集与存储系统；前者回答“现在是什么状态”，后者提供“系统记录了哪些过程”。两者应按保留、访问和隐私策略分别设计，避免把无界事件历史塞进单行任务记录。

**三、混合策略里的"快路径"不是另一套实现。** 它是同一个处理函数的两个出口，共用一条任务记录（上面那段伪代码）。把它写成两套逻辑，是这一节最常见的实现错误。

## 配置也是代码

agent 的"代码"不只是 Python 文件，还包括三类运行时资产：

| 资产 | 改它的风险 |
|---|---|
| **提示词** | 高 —— 它就是指令，改一个字可能改变全部行为 |
| **工具定义** | 高 —— 描述同样是指令（第 17 章） |
| **模型版本** | 中到高 —— 换版本等于换了一个执行者 |

三者都不在代码仓库的常规 review 流程里，但它们的变更影响**可能比代码更大**。所以第 2 节要讲版本管理，第 4 节要讲上线后的循环。三者一旦丢失或不一致，表现不是报错，而是「它好像忘了刚才做的事」—— 而这类问题在日志里看不出来，只能靠追踪（第 15 节）才能定位：去看那一步的工具返回值是什么、历史消息里少了哪一轮。没有轨迹时，这个问题几乎无法复现。

一个具体建议：**把提示词和工具定义当代码对待** —— 进 git、走 review、有版本号、可回滚。这不是形式主义，而是因为**它们的变更同样需要灰度**（第 2 节会用数据说明为什么）。

**等待阈值由产品体验、端到端 deadline、HTTP 基础设施与客户端能力共同决定。** 阈值只控制同步等待多久；超时后的处理方式另行定义。客户端可通过带退避的轮询、回调/通知或保持双向连接取结果，选择取决于可达性、时效、可靠性和运维成本，没有“长任务必用推送、小时任务必用通知”的通用分界。

## 一个容易被忽略的部署细节：超时链

一次任务可能经过多个独立的 deadline：客户端、代理、应用请求、单次上游调用和整个任务都各有终止条件。它们应协同配置并向下传递剩余预算。

一次请求会经过好几层超时：

下面数值仅用于说明多个 deadline 的关系，是构造配置，不代表任何 CDN、负载均衡器、应用服务器或模型 API 的默认值：

```text
CDN / 网关              60s
负载均衡                55s
应用请求等待            45s
单次模型调用            25s
agent 任务总 deadline  300s
```

每次模型调用都应服从调用方剩余 deadline，并留出结果持久化、清理和返回的时间；全任务 deadline 可以早于尚未完成的单次调用，并通过取消传播尝试停止其工作。单次 timeout、重试预算和任务总 deadline 应协同配置，不能只把单次时长乘轮数来推算用户等待时间。

应用响应 deadline 通常应早于外层代理 deadline，留出传输和错误映射的余量；具体错误由实际终止请求的那一层和产品决定，代理可能返回 502、504 或其他响应。排查时应关联各层 request ID、deadline 与日志，确定哪一跳终止，而不是预设状态码。

## 一个和「部分成功」有关的设计

第 1 节提到 agent 的失败常常是「部分成功」。部署层面要处理它，有两种做法：

**一、把中间结果持久化。** 每一步完成后写状态，失败时从中断处继续（第 11 章那套）。
**二、把「已完成的部分」返回给用户。** 哪怕整体失败了，前几步的产出也有价值（第 18 章讲预算闸门时说过同一点）。

第一种是机制，第二种是接口设计。恢复时只有已持久化且可安全重放的检查点，才能作为继续执行的起点；有外部副作用的步骤需额外幂等或对账。两者可以并存。部分结果是否适合返回，要看它是否已持久化、通过了必要校验、是否包含敏感数据，以及下游操作失败会不会使它失效。接口可用独立状态表达部分完成，并说明已完成与未完成的范围；事件进度不自动等同于可交付结果。
## 完整可运行代码

下面这段代码只估算不同任务在 HTTP 等待阈值下会呈现的响应形态；它不实现任务调度、唯一执行或持久化恢复。

```python
"""部署情景计算器。纯本地算术，不请求 provider。实跑状态：2026-10-21。"""
# 情景假设：固定开销 0.8s，生成速度 180 token/s；不是 provider 实测
def task_latency(turns, out_per_turn):
    per = 0.8 + out_per_turn / 180
    return turns * per


TASKS = [("短任务", 1, 200), ("中任务", 4, 400), ("长任务", 15, 500)]


def hybrid(task, threshold=20.0):
    lat = task_latency(*task[1:])
    if lat <= threshold:
        return "同步返回", lat
    return "返回原 task id（worker 不变）", lat


if __name__ == "__main__":
    print("情景延迟估算（每轮假设 0.8s + 输出 token / 180 token/s）")
    print()
    print("  %-10s %-8s %-10s %s" % ("任务", "轮数", "情景时长", "示意形态"))
    for name, turns, out in TASKS:
        lat = task_latency(turns, out)
        shape = "同步返回" if lat <= 20 else "返回 task id"
        print("  %-10s %-8d %-10s %s" % (name, turns, "%.1fs" % lat, shape))
    print()
    print("=== 同一持久化任务：HTTP 最多等待 20 秒 ===")
    for name, turns, out in TASKS:
        how, lat = hybrid((name, turns, out))
        print("  %-10s 情景值 %6.1fs → HTTP %s；worker 仍执行原任务" % (name, lat, how))
    print()
    print("=== 关键点 ===")
    print("  以上是情景输入，不是对真实 agent 任务的延迟预测。")
    print("  HTTP 等待阈值只控制同步等待多久，不决定是否重新调度任务。")
    print("  任务始终由持久化任务记录与 worker 管理。")
    print()
    print("  进度反馈形式与频率应按产品、任务风险和可观测性要求设计。")
```

## 常见坑

- **把跨请求状态只放进 worker 进程内存。** 单实例临时运行可以使用内存状态；若任务需要在重启、扩容或请求断开后恢复，就应有 durable state 和重新领取机制。
- **把 sticky session 当持久化。** 它只能影响路由；多实例切换、重启、重试或扩缩容仍可能让进程内状态不可见。
- **把一条历史计划评分当作时延分布证据。** 当前记录缺逐次响应与可复核评分器，不能据此推出任务步数或延迟的可预测性。
- **超时后才重新排队。** worker 可能仍在执行；超时只应结束 HTTP 等待，并返回同一个 task id。相同幂等键若对应不同请求内容，应明确冲突。
- **把提示词和工具定义当配置改。** 它们是指令，影响可能比代码更大，要进 git、走 review。
- **忽略部分提交。** 多步骤 agent 任务可能在后续失败前已完成外部副作用；持久化步骤状态，并为不确定结果设计对账或补偿。
