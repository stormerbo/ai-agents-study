前面十九章是一条线：从理解模型到把它部署出去。这一节讲最后一段 —— **上线不是终点，是循环的开始。**

## 一个闭环

把前面各章的机制串起来，会得到一个闭环：

```text
候选线上事件 → 轨迹与版本 → 脱敏、去重、人工裁决
                              ↓
       进入开发回归集 / 受控留出集 / 不纳入并记录原因
                              ↓
                        离线回归（第 15 章）
                        ↓
                  版本发布（第 2 节）
                        ↓
                  灰度（第 2 节）
                        ↓
                      回到线上
```

**这个闭环从候选线上事件开始，目标是降低已确认问题再次发生的概率。** 没有足够且合规的轨迹，可能无法定位失败；但轨迹本身也不是评测答案，事件需先经过裁决。

第 15 章讲过评测流水线，这里补上它和部署的连接：**进入评测集的用例应记录首次发现时的发布单元 id**（第 2 节），并保留来源、预期行为、评分规则和数据分区，以便追溯它在哪个版本暴露、后续如何处置。

## 上线后需要周期复核的对象

上线后有三类东西可能随业务、流量或依赖变化而逐渐失配；有些漂移不会立刻触发运行时错误，需要用适合该对象的检查发现。

| 对象 | 可能的漂移 | 检查方式 |
|---|---|---|
| **能力评测** | 长期高通过率可能代表题目趋于饱和，也可能是样本过易、评分器过宽或任务范围变化 | 复核任务、评分器和 transcript，再补充经裁决且覆盖新能力的案例 |
| **回归评测集** | 高通过率通常是目标；分数下滑可能提示退化 | 固定已接纳用例持续重放，逐项检查失败和跳过 |
| **提示词假设** | 业务规则、用户表达或上游字段发生变化 | 按风险抽样，并与当前业务规则/来源核对 |
| **工具权限** | 资源或角色变化导致授权范围过宽或不足 | 对照实际调用与当前策略，检查拒绝和越权事件 |

检查可以自动化，也可能需要人工判断；方式取决于对象与风险。高通过率是复核线索，不自动证明评测集失效。

一种**示例阈值**是把能力评测长期接近满分作为复核信号，检查题目是否仍有区分度；例如 95% 只能是团队结合风险与评测集用途自行设定的提示值，不是通用门槛，也不自动意味着要补题。提示词与权限策略的抽样频率和样本量应由风险、变更速度、数据量及审查能力确定。小样本能发现明显漂移，不能证明低频风险不存在。

## 四个值得长期跟踪的指标

前面几章散落着很多指标，这里挑四个作为运维起点：

| 指标 | 建议先写清楚的口径 | 解读边界 |
|---|---|---|
| **任务完成率** | 一个业务任务算成功的条件、统计窗口、分母（符合条件且终态明确的任务） | 别把模型正常结束等同于业务成功；按任务类型与版本分层 |
| **人工介入率** | 发生非预期人工接管的任务数 / 符合统计条件的任务数；另报策略要求的审批 | 必须审批与异常接管含义不同，不能混成一个数 |
| **每任务模型 token** | 窗口内输入/输出 token 总量除以纳入任务数；缺失 usage 单列 | token 是成本代理，不是账单金额；实际费用按 provider usage 与账单口径核对 |
| **回归重放覆盖率** | 最近一次回归中实际执行的已接纳回归用例数 / 当前有效回归用例数 | 同时报失败和跳过；holdout 不应被日常调参反复查看 |

这四项是可落地的一组起点，不是跨任务通用的“最有信息量”排名。指标要配分母、窗口、版本、任务分层和缺失数据处理，否则趋势可能只是流量构成或采集变化。

人工介入率只是运营信号，不能单独证明质量或信任变化。按任务类型区分策略要求的审批、异常接管和用户主动求助，并结合成功、返工/撤销、风险事件及原因分层看。

把线上失败直接变成评测用例也有风险：用户报告不一定代表系统错误，轨迹可能含个人信息，失败标签可能错，重复案例会让回归集失衡。先把它当作 **candidate（候选用例）**：依据保留策略脱敏或最小化数据、去重、由领域负责人确认预期行为与评分规则，再决定是否进入可反复调参的开发/回归集。另设受控的 holdout（留出集）检查泛化；日常开发不要反复查看其逐题结果。所有数据集都保留来源、版本、裁决和处置记录。

## 一个反过来的检查：什么时候该删东西

最后说一个和"加功能"相反的方向。系统运行一段时间后，积累的不只是功能，还有**债**：

- 已经不适用的评测用例（测的是一个不再存在的场景）
- 已经没用的工具（占着 token，还可能被误用）
- 过期的提示词段落（描述了一个旧流程）
- 太严或太松的策略规则（第 16 章：被频繁拒绝是太严的信号）

**这四类东西的代价都可能不明显** —— 评测用例多了会拉长回归时间；工具定义可能增加请求输入并影响缓存，具体成本按目标 endpoint 测；过期提示词可能让模型困惑。

所以运维循环里应有一步是**复核并退役**，而不只是增加资产。可以在相关功能变更时检查是否仍需要旧用例、工具、提示词和规则；保留处置理由、版本及审计记录，遵守数据保留策略，不能把“清理”理解成无条件删除。

## 回到第 15 节那句话

本章和第一部分的内容在这里合上了。第 15 节说过一句：**一份不会被自动跑的评测集等于不存在。**

把这句话扩展一步，就是这一节的全部内容：**一个不会从线上失败学习的系统，会一直犯同样的错。**

Agent 运行通常依赖代码、配置、模型和外部服务；传统软件同样会受数据、配置、依赖和运行环境变化影响。对使用托管模型或外部工具的系统，版本或服务行为可能在应用代码不变时改变，因此需要记录可观测的依赖版本并持续回归。这个循环的目标不是“越用越聪明”，而是让退化更容易被发现和回滚。


## 一个具体的频率建议

上面说要按风险安排检查，这里给出一份**构造的排期示例**：

```text
检查                    频率                工时（构造示例）
评测集高通过率复核       自动提示，人工判断     不估算
提示词假设抽样           按风险安排             每次 15 分钟
策略表 review            按风险安排             每次 30 分钟
工具清单 review          按风险安排             每次 30 分钟
```

若按季度执行前两项、每半年执行后两项，人工工时示例合计约 4 小时/年，实际还要计入准备、复核和跟进。团队应按风险、变更频率与实际工作量调整；任何告警都要绑定 owner、复核动作与升级条件，否则阈值本身不会形成闭环。

## 那四项检查的登记表

"指定 owner"要落到一个能查到的东西上，否则半年后没人知道该找谁。一份够用的登记表长这样：

| 检查项 | owner | 频率 | 上次执行 | 产出 |
|---|---|---|---|---|
| 能力评测饱和复核 | 值班（当周轮值） | 达团队设定的复核条件时处理 | 2026-10-12 | 补了 3 条新用例 |
| 抽样看输出（10 条） | 模型侧负责人 | 每季度 | 2026-10-08 | 发现 1 处提示词描述的是旧流程 |
| 策略表 review | 安全负责人 | 每季度 | 2026-07-15 | 收窄了 2 条过宽的规则 |
| 工具清单 review | 值班 + 模块 owner | 每半年 | 2026-06-30 | 下线 2 个不再使用的工具 |

（示例：构造数据，未实跑 —— 它是登记表格式的示例。）

**注意"产出"这一列。** 一次检查如果什么都没发现，也应该写一句"无变化" —— 因为**只有留下记录，下一次接手的人才能判断"这项检查是否真的在做"**。一张从上季度就没更新过的表，比没有这张表更糟：它给人已经检查过的错觉。

## 跑一次这个循环的真实形状

上面讲的是机制，这里把一次完整的迭代走一遍，让"从失败到改进"有具体的形状：

| 步骤 | 具体动作 | 产出的东西 |
|---|---|---|
| 1 发现 | 从任务结果或指标异常中发现候选问题，避免只靠一条噪声告警 | 候选事件（最小必要 trace 引用与版本） |
| 2 归因 | 检查完整轨迹、工具结果和业务终态，提出可证伪的失败假设 | 失败分类与证据 |
| 3 裁决 | 脱敏、去重，由负责人核对目标行为和 rubric（评分规则）；决定进回归集、留出集或不纳入 | 带来源、预期行为、裁决者、版本和数据分区的用例 |
| 4 改一处 | 记录改动的模型/提示词/工具/编排版本，避免同时改多个变量 | 可回滚的候选发布单元 |
| 5 对照 | 新旧版本使用同一开发回归集；单独报告逐项差异、缺失与失败原因 | 可复核的差异记录 |
| 6 放量 | 通过门槛后小流量观察，按预设规则继续、暂停或回滚 | 灰度记录、负责人、决策与回滚条件 |

**六步里第 2 步和第 4 步最容易偷工。** 第 2 步偷工的表现是"看几条轨迹就改"（没有可验证的假设）；第 4 步偷工的表现是"顺手把工具描述也改了"（一次改多个变量）—— 两者都会让第 5 步失去意义。

## 一个反过来的信号：什么时候该停

最后说一个容易被忽略的方向。运维循环的目标是持续改进，但**它也可能掩盖「这个项目该停了」这个结论**。

三种信号，任何一种持续出现都值得重新评估投入：

- **非预期人工接管率长期偏高。** 先区分任务本身需要判断、审批策略、用户求助、系统退化和操作摩擦，再决定是否缩小自动化范围或改造任务；不能仅凭比率推断任务“不适合 agent”。
- **边际成本收益变小。** 按任务价值、质量风险和资源成本共同复核，平台期本身不证明剩余成本都合理。
- **候选失败长期未裁决或未进入合适分区。** 检查采集、隐私、去重、标注资源和评测设计；单看入库率低无法定位原因，更不能推出是第三方依赖。

第二种最容易被误读：成本不再下降时，团队会继续优化，投入产出比越来越低。而正确的反应可能是「已经到合理水平了，把精力转到别处」。

**这组指标能提示要复核的方向，但单个指标不能代替项目继续/暂停的决策。**

## 一个具体的起点：从零开始建这个循环

上面讲的四类检查、四个指标听起来很多。如果从零开始，建议的顺序是：

**一个可选的四周试行顺序**（不是保证周期，也不适用于所有团队）：

**第 1 周：盘点轨迹。** 先确认允许采集哪些字段、保留多久、谁能看；优先使用 trace 引用和最小必要数据。

**第 2 周：试做候选用例裁决。** 从少量样本开始，完成脱敏、去重、预期行为与评分规则复核，再将合格项加入开发回归集；另行维护留出集。

**第 3 周：定义指标。** 明确任务成功、人工接管、provider usage 的分母与缺失值处理；先离线重算，再决定哪些需要告警。

**第 4 周：落实 owner 与动作。** 为数据集、权限策略和工具目录指定责任人、复核频率、升级和回滚条件。

四周只是一个启动模板；循环是否可用，要看采集合规、用例可复现、评分可信、责任人和发布门禁是否实际运转。

## 完整可运行代码

下面用构造数据演示候选事件如何经过脱敏、去重和人工裁决后才进入开发回归集，以及如何从明确定义的任务记录计算指标。代码不连接线上轨迹、模型或账单；留出集由独立流程维护，不从候选事件自动生成。归档或退役用例时保留来源、版本和处置记录，不能直接删除历史或污染留出集。

```python
"""本地构造示例：候选裁决、回归重放覆盖与任务级指标。"""
from collections import Counter


def format_ratio(numerator, denominator):
    if denominator == 0:
        return f"{numerator}/0 = N/A（分母为 0）"
    return f"{numerator}/{denominator} = {100 * numerator / denominator:.1f}%"


def format_token_mean(total_tokens, task_count):
    if task_count == 0:
        return "N/A（无有效 usage）"
    return f"{total_tokens}/{task_count} = {total_tokens // task_count}"


CANDIDATES = [
    {"id": "F-001", "trace_ref": "trace-demo-1", "input": "订单 A-1001 状态查询失败",
     "first_seen_release": "v12", "sanitized": True, "duplicate": False,
     "reviewer": "support-owner", "expected": "返回订单系统中的当前状态",
     "rubric_version": "support-v1"},
    {"id": "F-002", "trace_ref": "trace-demo-2", "input": "[原始内容未脱敏]",
     "first_seen_release": "v12", "sanitized": False, "duplicate": False,
     "reviewer": None, "expected": None, "rubric_version": None},
    {"id": "F-003", "trace_ref": "trace-demo-3", "input": "与 F-001 重复",
     "first_seen_release": "v13", "sanitized": True, "duplicate": True,
     "reviewer": "support-owner", "expected": None, "rubric_version": None},
    {"id": "F-004", "trace_ref": "trace-demo-4", "input": "地址修改失败（示例）",
     "first_seen_release": "v13", "sanitized": True, "duplicate": False,
     "reviewer": None, "expected": None, "rubric_version": None},
]


def admit_candidate(candidate):
    if not candidate["sanitized"]:
        return None, "隐私待处理"
    if candidate["duplicate"]:
        return None, "重复，保留来源记录"
    if not all(candidate.get(k) for k in ("reviewer", "expected", "rubric_version")):
        return None, "待评审"
    case = {
        "case_id": "C-" + candidate["id"],
        "source_trace_ref": candidate["trace_ref"],
        "input": candidate["input"],
        "first_seen_release": candidate["first_seen_release"],
        "expected_behavior": candidate["expected"],
        "rubric_version": candidate["rubric_version"],
        "reviewer": candidate["reviewer"],
        "split": "development_regression",
    }
    return case, "进入开发回归集"


# 已审核的开发集用例与最近一次回归执行记录；holdout 单独管理。
REGRESSION_CASES = {"C-F-001", "C-BASELINE-002"}
LATEST_RUN = {"C-F-001": False, "C-BASELINE-002": True}
TASKS = [
    {"terminal": True,  "success": True,  "intervention": None,             "input_tokens": 800,  "output_tokens": 400},
    {"terminal": True,  "success": False, "intervention": "exception",      "input_tokens": 1500, "output_tokens": 900},
    {"terminal": True,  "success": True,  "intervention": "policy_required", "input_tokens": 1000, "output_tokens": 800},
    {"terminal": False, "success": None,  "intervention": None,             "input_tokens": None, "output_tokens": None},
]


if __name__ == "__main__":
    decisions = Counter()
    for candidate in CANDIDATES:
        case, decision = admit_candidate(candidate)
        decisions[decision] += 1

    eligible_tasks = [task for task in TASKS if task["terminal"] and type(task["success"]) is bool]
    completed = len(eligible_tasks)
    success_count = sum(task["success"] for task in eligible_tasks)
    unexpected_handoffs = sum(task["intervention"] == "exception" for task in eligible_tasks)
    required_approvals = sum(task["intervention"] == "policy_required" for task in eligible_tasks)
    usage_rows = [task for task in eligible_tasks if task["input_tokens"] is not None and task["output_tokens"] is not None]
    total_tokens = sum(task["input_tokens"] + task["output_tokens"] for task in usage_rows)
    replayed = len(set(LATEST_RUN) & REGRESSION_CASES)
    passed = sum(LATEST_RUN[case_id] for case_id in set(LATEST_RUN) & REGRESSION_CASES)

    print("=== 候选裁决（构造数据）===")
    print("候选 %d 条；进入开发回归集 %d；隐私待处理 %d；重复 %d；待评审 %d" % (
        len(CANDIDATES), decisions["进入开发回归集"], decisions["隐私待处理"],
        decisions["重复，保留来源记录"], decisions["待评审"]))
    print("留出集由独立流程维护，不在本次开发回归中改写。")
    print()
    print("=== 任务级指标（构造数据）===")
    print("任务完成率：" + format_ratio(success_count, completed))
    print("未终态任务 %d 条，不计入任务完成率和人工接管率。" % (len(TASKS) - completed))
    print("非预期人工接管率：" + format_ratio(unexpected_handoffs, completed) +
          "；策略要求审批另报 %d/%d" % (required_approvals, completed))
    print("每任务模型 token：" + format_token_mean(total_tokens, len(usage_rows)) +
          "；usage 缺失 %d 条；不是账单金额" % (completed - len(usage_rows)))
    print("回归重放覆盖率：" + format_ratio(replayed, len(REGRESSION_CASES)) +
          "；通过 %d/%d" % (passed, replayed))
```

## 常见坑

- **把上线当终点。** 没有"线上失败 → 评测用例"这条流水线，系统会一直犯同样的错。
- **评测集不带版本 id。** 那样你只知道"这个输入失败过"，不知道"在哪一版上失败过"。
- **不跟踪人工介入率。** 它是运营诊断信号之一；应结合介入原因和其他质量、体验指标，避免把下降直接解释为信任提升。
- **不清理过期资产。** 过期用例可能拉长回归时间；多余工具定义可能增加输入和缓存成本，需按目标 endpoint 实测。
- **以为评测集会一直有效。** 长期高通过率是复核题目难度、任务覆盖和评分器的线索；补题前先确认新案例已裁决，不能用未核实事件自动扩充。
- **只加不删。** 每次上新功能时顺手问一句"有没有旧东西可以去掉"。
