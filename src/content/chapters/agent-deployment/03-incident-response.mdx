agent 服务出故障时，有一个和普通服务不同的地方：**它往往是"部分坏"，而不是"全坏"。**

一个普通服务的故障形态很干脆：500、超时、连接拒绝。而 agent 的故障更像是：**它还在返回 200，但结果不对、或者慢得离谱、或者偷偷降级了。**

这一节讲怎么识别这些形态，以及怎么降级。

## 四类故障形态

| 形态 | 表现 | 为什么难发现 |
|---|---|---|
| **完全不可用** | 报错、超时 | 最容易——监控能直接看到 |
| **质量退化** | 200 但结果变差 | 需要评测才能发现（第 15 章） |
| **静默降级** | 换了模型/工具，但用户不知道 | 系统"正常工作" |
| **成本或延迟异常** | 能跑通但贵了 10 倍、慢了很多 | 需要专门的指标 |

**第二行和第三行是最危险的。** 因为它们不会触发任何传统的可用性告警 —— 服务健康检查全绿，错误率没变，而实际效果已经变差了。

## 五个必须监控的指标

前四章记录过很多具体的失败形态，它们各自指向一个可监控的指标：

| 指标 | 它揭示什么 | 来自 |
|---|---|---|
| **`stop_reason` 分布** | `max_tokens` 比例上升 = 输出预算不够（第 18 章） | 第 3、7 章踩过 |
| **单次任务 token 的 P99** | 成本失控、循环没停 | 第 1、18 章 |
| **连续失败次数** | 卡住了（第 9 章实测过连点 4 次） | 第 11 章 |
| **工具调用被拒率** | 权限太严，或正在被注入试探（第 16 章） | 第 16 章 |
| **缓存命中率** | 有人往前缀里加了动态内容（第 18 章） | 第 18 章 |

**第一个指标最容易被忽略，而它直接对应一个反复踩过的坑。** 第 3、7、18 章都记录过：模型先思考再回答，输出预算不够时返回**空文本 + `stop_reason` 为 `max_tokens`** —— 看起来像"模型做不到"。如果这个比例在上升，说明上下文变长了或者任务变复杂了，而不是模型变笨了。

第五条也值得说：缓存命中率长期为 0 意味着缓存根本没生效，而它不会报错，只会让账单慢慢变高。

## 降级的四个层次

故障时要降级，而降级有四个层次，从轻到重：

| 层次 | 做法 | 用户感受 |
|---|---|---|
| **换模型** | 切换到更便宜/更快的模型 | 质量下降但可用 |
| **缩功能** | 关掉部分工具或能力 | 任务可能做不完 |
| **转人工** | 转给人工流程 | 慢但可靠 |
| **拒绝** | 明确说"暂时不可用" | 最差，但最诚实 |

**关键是要提前决定用哪一层，而不是故障时临时想。** 故障发生时系统已经在异常状态，那时做决策容易做出更糟的选择（第 18 章讲过同一点）。

一个实用的做法是**按任务类型预设**：关键任务（涉及钱、对外）宁可拒绝也不降级；非关键任务（生成草稿、摘要）可以降到便宜模型。

## 一个反过来的要求：降级要可见

降级之后，用户和运维都应该知道。两种可见性：

**对用户**：明确告知"当前使用了简化处理"（第 19 章那条：用户有权知道他在用哪个版本）。

**对运维**：降级触发要计入监控，而且**降级状态本身是一个指标** —— 如果系统长期处于降级状态，那说明根因没修。

第二条容易被忽略的后果是：**降级变成常态之后就没人管了** —— 系统一直在用便宜模型跑，而所有人都以为那是正常配置。

## 一个具体的排查顺序

出事时按什么顺序查？一个实用的顺序，从"最可能且最容易验证"开始：

```text
1. 看 stop_reason 分布 —— 是不是大量 max_tokens（预算问题，不是能力问题）
2. 看单次任务 token 的 P99 —— 是不是有循环没停（第 11 章）
3. 看失败的轨迹（第 15 章）—— 失败在哪一步，那一步看到了什么
4. 看工具调用被拒率 —— 是不是策略配置错了
5. 最后才怀疑模型 —— 因为前四项都是你能控制的，而模型不是
```

第五行是本节最想强调的：**绝大多数"模型变笨了"其实是前四项里的一项。** 这个项目自己的经历是一个例证 —— 第 3 章那次看起来像"模型在长上下文里失能"的结果，真相是 `max_tokens` 被思考吃光了。


## 一个具体的例子：同一个现象，两种归因

上面那张指标表里，有两个指标的异常都会表现为「成本上升」，但根因和修法完全不同。这个例子值得单独走一遍。

```text
现象：单次任务的 token 从平均 8,000 涨到 20,000

归因 A：输出预算不够
  指标：stop_reason 里 max_tokens 的比例从 1% 涨到 12%
  机制：输出被截断 → 任务没完成 → 用户重试或 agent 重跑
  修法：提高 max_tokens

归因 B：循环没有停
  指标：token_p99 / token_p50 的比值从 2.5 涨到 11
  机制：某类输入让 agent 反复尝试，步数失控
  修法：加最大步数闸门
```

**两个归因的修法互不通用。** 提高 max_tokens 对 B 无效（循环照样跑）；加步数闸门对 A 无效（任务本来就只需要一次调用）。

而如果两个都不看，最常见的反应是「换一个更便宜的模型」—— 那会让 A 更严重（预算更少），也可能让 B 更严重（弱模型更容易绕圈）。

**这就是为什么排查顺序要写在文档里**：不是因为顺序本身有什么魔法，而是因为**在压力下人会跳到最熟悉的那个解释**（「模型不行」），而顺序是抵抗这个倾向的东西。

## 一个反过来的检查：告警太灵敏也是故障

上面讲了四个故障形态，最后补一个方向相反的：**告警疲劳。**

如果一个指标每天告警 20 次，那它实际上不构成告警 —— 团队会在第三天开始忽略它。三种常见形态：

- **阈值太紧。** 比如把「错误率大于 1%」设成告警，而正常情况下就有 0.5% 的波动。
- **没有分级。** 所有告警都发到同一个渠道，P0 和 P3 混在一起。
- **告警不带上下文。** 只说「错误率升高」，不说「哪个版本、哪类请求、从什么时候开始」。

第二条最影响实际响应速度。一个实用的分级是：**P0（完全不可用）走电话；P1（质量退化）走即时消息；P2（成本、缓存异常）走每日汇总。** 而那个「每日汇总」恰恰是本文前面那些指标该去的地方 —— 它们重要，但不紧急。

## 一个具体的演练：降级路径要定期跑

第 18 章说过「降级路径从不测试」是最危险的一类腐烂。这里给出一个可操作的演练方式。

**做法：在测试环境把触发条件调到必然触发，然后走一遍完整流程。**

```text
1. 把熔断阈值调成 1（任何失败都触发）
2. 跑一个正常任务，确认熔断真的打开
3. 确认降级路径生效：用户看到了什么？运维收到了什么？
4. 把阈值调回去，确认系统恢复
```

第二步到第三步之间最容易发现问题：**降级路径本身可能有 bug**，而它平时跑不到。常见的三个：

- 降级逻辑依赖一个在故障时也失效的组件（比如降级后的模型也从同一个挂掉的网关走）
- 降级后的界面没处理「部分结果」，显示成空白
- 降级触发没有告警，所以演练之外没人知道它触发过

第三个最常见。它的后果是：**降级状态可能已经持续了很久，而没人知道** —— 这正是本节前面说的「降级变成常态」。

**这个演练一次花不到半小时，而它验证的是一条平时永远不会被执行的代码路径。** 按性价比算，它是运维里最值得做的一项。
## 完整可运行代码

下面这段代码实现一套故障判定：给定各项指标，输出故障类型与建议的降级层次。

```python
"""故障判定：给定指标，输出故障类型与建议的降级层次。纯本地。实跑状态：2026-10-09。"""
RULES = [
    # (序号, 判据描述, 判据函数, 故障类型, 建议动作)
    ("stop_reason", "max_tokens 比例 > 5%", lambda m: m["max_tokens_ratio"] > 0.05,
     "输出预算不足", "提高 max_tokens，或检查上下文是否变长"),
    ("token_p99", "单次任务 token 的 P99 > 5 倍中位数", lambda m: m["token_p99"] / m["token_p50"] > 5,
     "循环未停", "加最大步数闸门（第 11 章）"),
    ("fail_streak", "连续失败 > 3 次", lambda m: m["fail_streak"] > 3,
     "任务卡住", "熔断并返回已有结果（第 11、18 章）"),
    ("deny_rate", "工具被拒率 > 10%", lambda m: m["deny_rate"] > 0.10,
     "策略太严（或正在被试探）", "review 策略表（第 16 章）"),
    ("cache_hit", "缓存命中率 < 5%", lambda m: m["cache_hit"] < 0.05,
     "缓存没生效", "检查前缀里是否混了动态内容（第 18 章）"),
    ("err_rate", "错误率 > 5%", lambda m: m["err_rate"] > 0.05,
     "完全不可用", "降级或回滚（第 2 节）"),
]

SCENARIOS = [
    ("正常", {"max_tokens_ratio": 0.01, "token_p50": 8000, "token_p99": 20000,
              "fail_streak": 0, "deny_rate": 0.01, "cache_hit": 0.8, "err_rate": 0.005}),
    ("预算不够", {"max_tokens_ratio": 0.12, "token_p50": 8000, "token_p99": 20000,
                  "fail_streak": 0, "deny_rate": 0.01, "cache_hit": 0.8, "err_rate": 0.005}),
    ("循环没停", {"max_tokens_ratio": 0.01, "token_p50": 8000, "token_p99": 90000,
                  "fail_streak": 2, "deny_rate": 0.01, "cache_hit": 0.8, "err_rate": 0.01}),
    ("缓存失效", {"max_tokens_ratio": 0.01, "token_p50": 8000, "token_p99": 20000,
                  "fail_streak": 0, "deny_rate": 0.01, "cache_hit": 0.0, "err_rate": 0.005}),
]


def triage(m):
    hits = [(name, kind, action) for name, _, test, kind, action in RULES if test(m)]
    return hits


if __name__ == "__main__":
    for label, m in SCENARIOS:
        hits = triage(m)
        print("  【%s】" % label)
        if not hits:
            print("      无异常")
        for name, kind, action in hits:
            print("      %-14s → %-22s %s" % (name, kind, action))
        print()
    print("=== 排查顺序为什么重要 ===")
    print("  注意「预算不够」和「循环没停」都会让成本上升，但修法完全不同：")
    print("    预算不够 → 提高 max_tokens")
    print("    循环没停 → 加最大步数闸门")
    print("  如果先怀疑模型（换一个更强的），两个问题都不会被修掉。")
```

## 常见坑

- **只监控可用性。** 质量退化和静默降级都不触发传统告警 —— 服务健康检查全绿而效果已经变差。
- **不看 `stop_reason` 分布。** 第 3、7、18 章都踩过：`max_tokens` 截断看起来像"模型做不到"。
- **降级时临时决定。** 要提前按任务类型预设：关键任务宁拒绝不降级。
- **降级不可见。** 用户和运维都该知道 —— 尤其是运维，因为长期降级意味着根因没修。
- **先怀疑模型。** 排查顺序应该是：预算 → 循环 → 轨迹 → 策略 → 最后才是模型。
- **不监控缓存命中率。** 长期为 0 意味着缓存没生效，而它只让账单变高，不报错。
