你在写「把客服对话整理成工单」的功能。模型输出必须变成程序能消费的数据，于是团队里出现了一句几乎所有人都听过的话：

> 别指望模型。它偶尔会多写一句解释、少一个括号、在字符串里塞一个没转义的引号，所以必须在采样阶段就把 JSON 语法强加上去。

这句话听起来很有道理。作者当时记录了一组实验摘要，但原始数据没有保存在当前工作树里，所以现在**无法独立复核它是否支持该结论**。

> **历史样本边界（2026-10-08）**：下文的 DeepSeek 结果是当时记录的摘要。当前仓库没有这组实验的逐次请求、逐次响应、精确模型快照和可重算评分器，因此本轮无法独立复算。它只能说明作者当时记录了什么，不能证明今天的模型表现，也不能据此估计生产失败率。

动手之前先把这一章会反复出现的四个词定下来 —— 后面所有取舍都建立在它们之上：

- **token**：模型不是按字符也不是按单词处理文本，而是按**词表切分后的片段**。它是计费单位、容量单位，也是延迟来源（第 1 章）。「中文技术文档约两个字符一个 token」是本站实测的经验值。
- **采样**：模型逐 token 生成输出的过程。提示会影响候选 token 的概率分布，但不构成语法保证；某些 endpoint 的约束解码会在受支持的 schema 子集内屏蔽不合规候选（下一节讲）。
- **输出 token 上限**：字段名由 API 决定。本节的 DeepSeek Anthropic 兼容请求用 `max_tokens`；[Anthropic Messages](https://platform.claude.com/docs/en/api/messages/create) 也用这个字段；[OpenAI Chat Completions](https://platform.openai.com/docs/api-reference/chat/object) 推荐 `max_completion_tokens`（旧 `max_tokens` 已弃用），[Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create) 用 `max_output_tokens`。这些字段限制本次响应可生成的 token，不含输入；某些 API/模型会把不可见的推理 token 也计入上限。它不是「模型的知识上限」，只是「这次允许它生成多少」。
- **停止原因字段**：用来说明一次响应为什么停止。字段名和值由 API 决定：[Anthropic Messages](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons) 使用 `stop_reason`，[OpenAI Chat Completions](https://platform.openai.com/docs/api-reference/chat/object) 使用 `finish_reason`；不要把一家的枚举当成通用协议。具体排查时先看目标 endpoint 的响应契约。
- **`thinking`**：这里指 2026-10-08 那次 DeepSeek Anthropic 兼容端点请求里的 provider-specific 参数。下文的 400 只描述当时记录的模型/端点/请求组合，不是所有 DeepSeek 模型或当前端点的永久限制。

> 一个有用的排查步骤是：先看目标 API 的终止状态，再尝试解析。截断、拒绝、工具交接和正常结束是不同状态；字段名及枚举值需按 endpoint 处理。

## 一组无法独立复核的历史对照

同一个任务，三种拿到结构化输出的方式，各跑 8 次（以下均为 2026-10-08 的历史摘要，未能逐次复算）：

| 方案 | 做法 |
|---|---|
| **A** | 把字段要求写进 prompt，末尾加一句「输出 JSON」 |
| **B** | A 的基础上再加「只输出一个 JSON 对象，不要解释，不要代码块包裹」 |
| **C** | 强制工具调用：把 schema 作为工具的 `input_schema`，并指定模型必须调用它 |

两个任务：一个简单（从客服对话里抽 6 个字段），一个麻烦（从采购邮件里抽嵌套明细数组、算出总价、原样保留一段含反引号和引号的备注）。

方案 C 那个工具定义长这样（**构造示例，未实跑** —— 它的形状决定了下面那 325 token 花在哪，但里面的取值是我编的）：

```json
{
  "name": "save_ticket",
  "description": "保存从客服对话中抽取的工单字段。信息缺失时留空，不要编造。",
  "input_schema": {
    "type": "object",
    "properties": {
      "customer_name": {"type": "string", "description": "客户姓名"},
      "phone":         {"type": "string", "description": "联系电话，纯数字"},
      "issue_type":    {"type": "string", "enum": ["refund", "repair", "question", "other"]},
      "order_id":      {"type": "string", "description": "订单号，形如 A-1001"},
      "amount":        {"type": "integer", "description": "涉及金额，单位元"},
      "note":          {"type": "string", "description": "客户原话，原样保留"}
    },
    "required": ["customer_name", "issue_type"]
  }
}
```

三段的分工：`name` 是你要在代码里认领的名字；`description` 是**写给模型看的说明书**；`input_schema` 是**形状声明**。这个构造示例有两个 `required` 字段，不能据此推断六个字段都会出现。普通工具调用和 `tool_choice` 只决定工具调用路径；除非目标 endpoint 明确支持并启用了严格结构约束，否则不能把它当成 schema 校验器。原报告称这份定义约占后文的 325 token，但该历史计数缺少可复核的请求和 usage，不应视为确定的固定开销。

它放进请求之后，完整的最小报文是这样（这是 DeepSeek Anthropic 兼容端点的示意请求；字段和计费口径都按具体 API 契约核对）：

```json
{
  "model": "deepseek-flash",
  "max_tokens": 2000,
  "thinking": {"type": "disabled"},
  "tools": [{ "name": "save_ticket", "description": "...", "input_schema": { "type": "object", "properties": {} } }],
  "tool_choice": {"type": "tool", "name": "save_ticket"},
  "messages": [{"role": "user", "content": "把下面这段对话整理成工单：..."}]
}
```

三个参数不能分开看：`tool_choice` 指定「必须调用这个工具」；当时这组 DeepSeek 请求记录为 `thinking` 与该 `tool_choice` 组合返回 400；`max_tokens` 是该 API 请求的输出上限。工具定义会进入请求，但实际计费、缓存和计数口径依 endpoint 而异；应看目标接口返回的 usage 与账单，不要把 325 token 当成普遍固定成本。

| 任务 | 方案 | 格式成功 | 内容完全正确 |
|---|---|---:|---:|
| 简单 | A | 8/8 | 8/8 |
| 简单 | B | 8/8 | 8/8 |
| 简单 | C | 8/8 | 8/8 |
| 麻烦 | A | 8/8 | 8/8 |
| 麻烦 | B | 7/8 | 7/8 |
| 麻烦 | C | 8/8 | 8/8 |

（历史记录：`deepseek-flash`，2026-10-08。B 的一次响应被记录为 `max_tokens` 截断；原始响应未归档，无法独立确认终态及重算评分。截断不是“格式错误”的同义词，但对要求完整结果的调用仍是一次未完成，需要单独计入端到端失败率。）

历史记录还按**记录条数**分档，每档 3 次：

| 记录条数 | 5 | 10 | 20 | 30 | 60 |
|---|---|---|---|---|---|
| 方案 A（纯提示） | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 |
| 方案 B（提示＋强调） | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 |
| 方案 C（强制工具） | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 |

原报告称每档都要求「一条不能少」，并记录 30 次运行全部通过；但逐次输出与判分器缺失，无法复核“没有漏条/格式非法”。即使接受这条历史摘要，它也只覆盖当时固定的模型别名、请求与数据集，不能外推为其他长度、任务或当前模型的通过率。

**这组未归档的历史样本不足以判断提示式 JSON 在该模型/任务上的失败率。** 更不能据它否定提示式输出在其他模型或任务中的风险。工程选择应基于目标 endpoint、任务风险和可复核的评测；提示可以改善格式倾向，但不构成硬保证。

## 我在这个结论上先错了一次

旧记录称「30 次运行全部正常」，第一版实验则**全部解析失败**；两组原始响应目前都无法独立复核。

差一点就写成「提示式在 30 条记录时会崩」。

旧记录将差异归因为顶层 JSON 数组 `[{...},{...}]` 被只认对象的解析器错误截取。这个诊断与代码机制相符，但由于原始输出和评分记录缺失，本轮无法独立确认它解释了全部失败，也无法复算修复后的 30/30。

这件事值得单独记住，因为它和本项目已经记录的五次测量缺陷是同一个形状：**一个反直觉的结论，看起来像「模型的行为异常」，实际上是「我的测量代码有 bug」。** 每当你准备写下一个反直觉结论时，先问一句：这会不会是我这边的问题？

## 那三种方案真正的差别在哪

这份历史记录没有显示三种方案的格式成功率差异；其请求/响应证据不足以独立复核。工程上的差别通常在 endpoint 能力、约束范围、校验责任、延迟与 token 成本，须逐项实测。

**历史成本摘要**（原文称为同一个工单任务、两个任务合计的 `output_tokens` 中位数；原始响应、usage 与计算脚本未归档，无法复核）：

| 方案 | output_tokens 中位 | 说明 |
|---|---:|---|
| A 纯提示 | 2041 | 模型正常「先想再写」 |
| B 提示＋强调 | 1591 | 强调了一句「不要解释」，省掉了一部分铺垫 |
| C 强制工具 | **223** | 历史记录同时关闭了思考；变量未隔离 |

C 的历史摘要输出 token 较少，但它同时改变了工具调用方式和思考配置；没有逐次数据和受控对照，不能把差异归因于“关掉思考”或“工具调用”。

**当时记录的厂商约束**：`deepseek-flash` 在 2026-10-08 的这个请求组合里，强制工具调用与开启思考被记录为返回 400。此错误未保存为可复核的完整请求/响应，不能视为当前模型的兼容性结论。DeepSeek [当前工具调用文档](https://api-docs.deepseek.com/guides/tool_calls/)称 V3.2 起支持 thinking mode 下的 tool use；[Anthropic 兼容端点说明](https://api-docs.deepseek.com/guides/anthropic_api/)也单独列出 `thinking` 与 `tool_choice` 支持。部署时应按具体 API 格式、模型与当前文档重测，而不是沿用这条历史结论：

```json
{
  "error": {
    "message": "Thinking mode does not support this tool_choice (request_id: ...)",
    "type": "invalid_request_error"
  }
}
```

这只是该历史请求形态观察到的兼容性限制，不能推广到当前 DeepSeek 模型或其他 endpoint。即便工具调用成功，普通 `input_schema` 也不一定被服务端严格执行；应分别确认工具选择、参数约束、思考模式兼容性，并在应用端解析、校验。

**历史 usage 摘要**：原记录称 60 条时方案 B 输入 1280 token、方案 C 输入 1605 token。因未留存逐次响应与 usage 明细，这个差额不能归因成“工具定义恰好 325 token”；输入 token 还可能受消息、模板、缓存及 endpoint 计数规则影响。

| 60 条记录 | input | output | 耗时 |
|---|---:|---:|---:|
| B 提示式 | 1280 | 3219 | 213 ms |
| C 强制工具 | 1605 | 1832 | 394 ms |

原记录的一次计时中 C 比 B 慢（394 ms vs 213 ms）。单次耗时摘要不能归因于协议开销，也不能代表两种方案的延迟分布；不要据此判断工具调用普遍更慢或更快。

## 那到底为什么还需要工程级的保证

即使单次输出在某个测试集上很稳定，也不能直接推出多步系统可靠；这里用一个明确假设的概率模型说明累积效应。

若每次调用独立、成功率相同且没有重试，一个任务要连续通过 N 次调用的概率为 `p^N`。例如假设 `p=0.99`，则：

```text
0.99^10  ≈ 90.4%
0.99^100 ≈ 36.6%      ← 100 次连续调用全部通过的概率
0.999^100 ≈ 90.5%     ← 若要让 100 次链路的通过率约为 90%，单次需假设达到 99.9%
```

这是用来说明累积效应的独立同分布模型，不是服务可靠性预测。真实调用可能相关，任务也会有重试、校验、降级和非模型故障；应以端到端任务定义和生产 trace 计算实际指标。

更关键的一点是：**少量无失败样本无法证明失败率足够低。** 采样可以给出带假设和置信水平的统计界限，但不能证明失败概率为零，也不能代替目标任务上的持续评估。

如果把“30 次全对”当作独立同分布的伯努利样本，零失败时单侧 95% 精确上界约为 9.5%。这远不足以支持“失败率低于 1%”的结论；具体样本量应按要证明的上界、置信水平和数据独立性计算。这里的 30 次本身还是不可复核的历史摘要。

所以正确的推理是：

- **提示式**：影响模型输出倾向，不提供格式或语义保证。
- **受支持的约束输出**：只在 provider 明确支持的 schema 子集和成功响应范围内约束输出；拒绝、截断、网络错误等仍需处理。
- **本地解析与校验**：只有在所有副作用入口都强制经过该门禁时，才能确定性地拒绝不合格结构；它仍不证明内容真实或业务动作获准。

因此选择应看任务风险和接口能力，而不是预设模型“经常失败”或“永不失败”。

## 完整可运行代码：一个带边界说明的解析器示例

这段代码的价值全在注释里标注的那个坑上 —— 它是本节我踩过的那个坑的修复版。

```python
# extract_json.py
"""从模型输出里取出 JSON。

示例展示三种输入形态，但自动截取只是启发式恢复，不是“可信解析”。生产场景优先要求整段是 JSON；若接受代码围栏或截取，必须对解析后的数据再做 schema、业务和来源校验：
  1. 整段就是 JSON（**含顶层数组**，这一点最容易漏）
  2. 被 markdown 代码块包着
  3. JSON 前后混了解释性文字
"""

import json
import re

FENCE = re.compile(r"```(?:json)?\s*(.*?)```", re.S)


def _slice(text: str) -> str | None:
    """从第一个 { 或 [ 截到最后一个 } 或 ]。

    必须同时认 { 和 [。只认 { 的话，模型返回顶层数组时你会截出
    两个元素之间的碎片，然后把它误判成「解析失败」—— 我踩过。
    """
    starts = [i for i in (text.find("{"), text.find("[")) if i != -1]
    if not starts:
        return None
    start = min(starts)
    end = max(text.rfind("}"), text.rfind("]"))
    return text[start : end + 1] if end > start else None


def extract_json(text: str):
    """返回 (值, 取值方式)。全失败时抛 ValueError。"""
    text = text.strip()
    candidates = [("raw", text)]
    candidates += [("fenced", m.group(1).strip()) for m in FENCE.finditer(text)]
    candidates.append(("sliced", _slice(text)))

    for how, candidate in candidates:
        if not candidate:
            continue
        try:
            return json.loads(candidate), how
        except json.JSONDecodeError:
            continue
    # 不要把原始模型输出放进异常、日志或用户可见错误；它可能含个人或敏感数据。
    raise ValueError("输出里找不到可解析的 JSON")


if __name__ == "__main__":
    for sample in [
        '{"a": 1}',
        '[{"a": 1}, {"a": 2}]',            # 顶层数组：第一版就是在这里错的
        '这是我整理的结果：\n{"a": 1}\n希望有帮助。',
        '```json\n{"a": 1}\n```',
    ]:
        value, how = extract_json(sample)
        print(how, "->", value)
```

```text
raw -> {'a': 1}
raw -> [{'a': 1}, {'a': 2}]
sliced -> {'a': 1}
fenced -> {'a': 1}
```

> **实跑状态**：这段代码在本地 Python 3.10 上跑过，上面的输出是真实运行结果。

## 别忘了检查 `stop_reason`

原始响应未归档，因此下面的 18 次/1 次截断仍是不可独立复核的历史摘要。排查时应先依据目标 API 的终止状态分流：截断是未完成；工具交接不是最终 JSON；正常结束后才尝试解析。统计格式错误率时可以单列截断，但端到端交付率必须把未完成纳入。

```python
# read_stop_reason.py
def classify(resp):
    """Anthropic Messages 风格字段的教学例子；其他 API 字段与枚举不同。"""
    reason = resp.stop_reason
    if reason == "max_tokens":
        return "截断：未完成"
    if reason == "end_turn":
        return "最终响应：可以尝试解析"
    if reason == "tool_use":
        return "工具交接：不是最终 JSON"
    if reason == "refusal":
        return "拒绝：不是正常 JSON 响应"
    if reason == "pause_turn":
        return "服务端工具循环暂停：按 API 契约继续"
    if reason == "model_context_window_exceeded":
        return "上下文窗口耗尽：未完成"
    if reason == "stop_sequence":
        return "停止串结束：需按任务契约判断是否完整"
    return "未知取值，单独看"           # 不要默默归进任何一类


if __name__ == "__main__":
    from types import SimpleNamespace as NS
    samples = [
        NS(stop_reason="end_turn"),
        NS(stop_reason="max_tokens"),
        NS(stop_reason="tool_use"),
        NS(stop_reason="stop_sequence"),
        NS(stop_reason="refusal"),
        NS(stop_reason="pause_turn"),
        NS(stop_reason="model_context_window_exceeded"),
    ]
    for r in samples:
        print("stop_reason=%-12s -> %s" % (r.stop_reason, classify(r)))
```

```text
stop_reason=end_turn     -> 最终响应：可以尝试解析
stop_reason=max_tokens   -> 截断：未完成
stop_reason=tool_use     -> 工具交接：不是最终 JSON
stop_reason=stop_sequence -> 停止串结束：需按任务契约判断是否完整
stop_reason=refusal      -> 拒绝：不是正常 JSON 响应
stop_reason=pause_turn   -> 服务端工具循环暂停：按 API 契约继续
stop_reason=model_context_window_exceeded -> 上下文窗口耗尽：未完成
```

（解析器代码曾在本地 Python 3.10 上运行；停止原因例子是本地构造的对象，不是 provider 响应。Anthropic SDK 的 `stop_reason` 是该 API 契约的一部分；其当前文档还列出 `refusal`、`pause_turn` 和 `model_context_window_exceeded` 等状态。字段与枚举会随 API 演进，其他 provider 请按其 SDK/HTTP 响应定义读取；未知值要显式走兜底分支。）

这个坑在本项目的历史写作里曾记录多次。判据是：**解析失败时先检查目标 API 的终止状态与完整性，再分类格式失败、截断、拒绝或工具交接。** 具体字段名和值按 provider 读取；只有确认完整响应后，才有意义讨论是否需要调整任务或预算。

## 常见坑

**把提示式 JSON 的历史摘要当成可靠性证明。** 这组原始数据缺失，不能支持稳定性或失败率判断。即使某次评测格式全对，也不能替代本地解析、schema 校验、业务校验与失败处理。

**解析器只认对象不认数组。** 旧记录称曾遇到顶层数组导致截取错误，但原始输出未归档，无法独立复核。模型可以返回顶层数组；如果输出契约允许数组，解析与 schema 校验也必须接受它。

**把截断从端到端失败率里剔除。** 分析“格式错误率”时可以把截断单列；但完整结果没有交付时，它仍属于端到端未完成。`tool_use` 也表示一次工具交接，不是结构化最终答案已经完成。

**把单次历史计时归因成普遍性能规律。** 394 ms vs 213 ms 缺少重复样本和可比条件，不足以证明协议开销导致变慢。

**把一个 endpoint 的 `strict` 观察推广给所有 provider。** 下一节的历史请求只覆盖该 DeepSeek Anthropic 兼容 endpoint 与请求形态；官方文档已可能随模型/API 更新。先查目标 endpoint 的当前能力，再以边界样例测试，并始终在应用侧校验。
