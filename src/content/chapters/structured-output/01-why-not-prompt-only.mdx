你在写「把客服对话整理成工单」的功能。模型输出必须变成程序能消费的数据，于是团队里出现了一句几乎所有人都听过的话：

> 别指望模型。它偶尔会多写一句解释、少一个括号、在字符串里塞一个没转义的引号，所以必须在采样阶段就把 JSON 语法强加上去。

这句话听起来很有道理。我做了一组实验想验证它，结果**没能复现**。

动手之前先把这一章会反复出现的四个词定下来 —— 后面所有取舍都建立在它们之上：

- **token**：模型不是按字符也不是按单词处理文本，而是按**词表切分后的片段**。它是计费单位、容量单位，也是延迟来源（第 1 章）。「中文技术文档约两个字符一个 token」是本站实测的经验值。
- **采样**：模型逐 token 生成输出的过程。它每一步都从概率分布里挑一个 token —— 所以「提示式 JSON」的语法保证只能靠概率，而「约束解码」是把非法 token 的概率直接压成 0（下一节讲）。
- **`max_tokens`**：你在**请求**里设的一个字段，指的是这一次响应**最多生成多少个 token**，**不含输入**。它不是「模型的知识上限」，只是「这次允许它写多长」。
- **`stop_reason`**：响应里的一个**字段**，指的是**这次生成为什么停下来**。它是你排查一切「解析失败」的第一入口。主要取值：`end_turn` 正常说完、`max_tokens` 撞上了你设的上限（输出被切断）、`tool_use` 模型要求调用工具、`stop_sequence` 撞上了你设的停止串。
- **`thinking`**：请求里的一个开关（`thinking={"type": "disabled"}`），用来关闭模型的「先想再写」。本端点不允许它和强制工具调用同时开（见下文 400 报文）。

> 这就是本节最省事的一条纪律：**任何一次「解析失败」，先看 `stop_reason`，再解释。** 看过之后你才知道这是格式问题，还是你自己把预算设小了。

## 实测一：提示式 JSON 稳得出乎意料

同一个任务，三种拿到结构化输出的方式，各跑 8 次：

| 方案 | 做法 |
|---|---|
| **A** | 把字段要求写进 prompt，末尾加一句「输出 JSON」 |
| **B** | A 的基础上再加「只输出一个 JSON 对象，不要解释，不要代码块包裹」 |
| **C** | 强制工具调用：把 schema 作为工具的 `input_schema`，并指定模型必须调用它 |

两个任务：一个简单（从客服对话里抽 6 个字段），一个麻烦（从采购邮件里抽嵌套明细数组、算出总价、原样保留一段含反引号和引号的备注）。

方案 C 那个工具定义长这样（**构造示例，未实跑** —— 它的形状决定了下面那 325 token 花在哪，但里面的取值是我编的）：

```json
{
  "name": "save_ticket",
  "description": "保存从客服对话中抽取的工单字段。信息缺失时留空，不要编造。",
  "input_schema": {
    "type": "object",
    "properties": {
      "customer_name": {"type": "string", "description": "客户姓名"},
      "phone":         {"type": "string", "description": "联系电话，纯数字"},
      "issue_type":    {"type": "string", "enum": ["refund", "repair", "question", "other"]},
      "order_id":      {"type": "string", "description": "订单号，形如 A-1001"},
      "amount":        {"type": "integer", "description": "涉及金额，单位元"},
      "note":          {"type": "string", "description": "客户原话，原样保留"}
    },
    "required": ["customer_name", "issue_type"]
  }
}
```

三段的分工：`name` 是你要在代码里认领的名字；`description` 是**写给模型看的说明书**（下一节会看到它比 schema 关键字更有用）；`input_schema` 是**形状声明**。上面这 6 个字段、两个 required 的花销大约就是后面那 325 token —— 字段名与类型是小头，`description` 与 `enum` 是大头。

它放进请求之后，完整的最小报文是这样（`messages` 之外的东西都是你每次请求都要固定付的）：

```json
{
  "model": "deepseek-flash",
  "max_tokens": 2000,
  "thinking": {"type": "disabled"},
  "tools": [{ "name": "save_ticket", "description": "...", "input_schema": { "type": "object", "properties": {} } }],
  "tool_choice": {"type": "tool", "name": "save_ticket"},
  "messages": [{"role": "user", "content": "把下面这段对话整理成工单：..."}]
}
```

三个参数不能分开看：`tool_choice` 指定「必须调用这个工具」；`thinking` 在这个端点上**必须同时关掉**，否则直接 400（见下文）；`max_tokens` 管这一次输出的预算。**工具定义是每个请求都付的固定成本**，跟你这一轮有多少条记录无关 —— 所以「要不要为省 token 砍掉 description」这个问题，只有对高频调用才值得算。

| 任务 | 方案 | 格式成功 | 内容完全正确 |
|---|---|---:|---:|
| 简单 | A | 8/8 | 8/8 |
| 简单 | B | 8/8 | 8/8 |
| 简单 | C | 8/8 | 8/8 |
| 麻烦 | A | 8/8 | 8/8 |
| 麻烦 | B | 7/8 | 7/8 |
| 麻烦 | C | 8/8 | 8/8 |

（实测数据，`deepseek-flash`，2026-10-08。B 的那一次失败是输出被 `max_tokens` 截断 —— 不是格式问题，是我给的预算不够，见本节末尾。）

我又按**输出长度**扫了一遍，因为「输出一长就散架」是最常见的说法。每档 3 次：

| 记录条数 | 5 | 10 | 20 | 30 | 60 |
|---|---|---|---|---|---|
| 方案 A（纯提示） | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 |
| 方案 B（提示＋强调） | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 |
| 方案 C（强制工具） | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 |

每一档都要求「一条都不能少」。60 条记录那一次，**30 次运行里没有任何一次漏条、没有任何一次格式非法**。

**所以在这个模型 + 这类任务上，「提示式 JSON 不可靠」这个说法不成立。** 这已经是本项目记录在案的第十一个「未复现」的流行经验。它不是说这条经验在别处也错 —— 而是说：**把它当成前提来设计系统，你会为一个未必存在的风险付出确定性的代价。**

## 我在这个结论上先错了一次

上面那句「30 次运行全部正常」，第一版实验给出的却是**全部解析失败**。

差一点就写成「提示式在 30 条记录时会崩」。

真实原因：模型返回的是**顶层 JSON 数组** `[{...},{...}]`，而我的解析函数只认对象 —— 它用第一个 `{` 和最后一个 `}` 去截取，在一个数组上截出来的是两个元素之间的碎片，当然不是合法 JSON。改掉解析函数之后，30/30 全对。

这件事值得单独记住，因为它和本项目已经记录的五次测量缺陷是同一个形状：**一个反直觉的结论，看起来像「模型的行为异常」，实际上是「我的测量代码有 bug」。** 每当你准备写下一个反直觉结论时，先问一句：这会不会是我这边的问题？

## 那三种方案真正的差别在哪

格式上没差别，差别在成本和厂商约束上。

**成本**（同一个工单任务，两个任务合计的 `output_tokens` 中位数）：

| 方案 | output_tokens 中位 | 说明 |
|---|---:|---|
| A 纯提示 | 2041 | 模型正常「先想再写」 |
| B 提示＋强调 | 1591 | 强调了一句「不要解释」，省掉了一部分铺垫 |
| C 强制工具 | **223** | 因为它**关掉了思考** |

C 为什么能省这么多？不是工具调用的功劳，是**被迫关掉思考的副作用**——原因见下一条。

**厂商约束**：在这个端点上，强制工具调用**必须关闭思考**，否则直接 400：

```json
{
  "error": {
    "message": "Thinking mode does not support this tool_choice (request_id: ...)",
    "type": "invalid_request_error"
  }
}
```

于是出现了一个真实的取舍：**你要协议级的结构保证，就得放弃模型的思考过程。** 实测里关掉思考之后内容正确率没有下降（8/8），但这是「这个任务不需要推理」的结果，换个要做多步推理的任务就不一定成立。

**还有一条容易被忽略的差别**：工具定义本身要占输入 token。60 条记录那次，方案 B 的输入是 1280 token，方案 C 是 1605 —— 多出来的 325 就是那一个工具的定义。

| 60 条记录 | input | output | 耗时 |
|---|---:|---:|---:|
| B 提示式 | 1280 | 3219 | 213 ms |
| C 强制工具 | 1605 | 1832 | 394 ms |

注意耗时：**C 反而更慢**。工具调用的协议开销、以及多出来的输入，在这个规模上盖过了「省掉思考」的收益。所以「用了工具调用就更快」也是一句不能照抄的经验。

## 那到底为什么还需要工程级的保证

因为「单次很稳」和「系统可靠」是两件事。

假设单次请求的格式合格率是 99% —— 这已经是很高的估计。一个 agent 任务平均要调用模型 10 次，那么整条链路全部合格的概率是：

```text
0.99^10  ≈ 90.4%
0.99^100 ≈ 36.6%      ← 一个每天跑上千次的服务，异常分支每天都会被走到
0.999^100 ≈ 90.5%     ← 想守住 100 次，单次得做到 99.9%
```

更关键的一点是：**你没法用采样证明单次合格率有多高。**

我上面跑了 30 次全对。这听起来很稳，但它只说明单次失败率**低于约 9.5%**（30 次全对、95% 置信水平下的上界）—— 连「低于 1%」都证明不了，更不用说「低于 0.1%」。要证明后者，需要跑上千次。

所以正确的推理是：

- **提示式 = 概率性保证（可能很高，但你测不准）**
- **协议/校验层 = 确定性保证（结构上不可能出错）**

这是「工程级约束」的真正理由，不是「提示式会经常失败」。前者是可以在设计文档里写清楚的，后者只是一个关于模型的传言。

## 完整可运行代码：一个不会骗你的解析器

这段代码的价值全在注释里标注的那个坑上 —— 它是本节我踩过的那个坑的修复版。

```python
# extract_json.py
"""从模型输出里取出 JSON。

三种情况都要认，而且顺序不能反：
  1. 整段就是 JSON（**含顶层数组**，这一点最容易漏）
  2. 被 markdown 代码块包着
  3. JSON 前后混了解释性文字
"""

import json
import re

FENCE = re.compile(r"```(?:json)?\s*(.*?)```", re.S)


def _slice(text: str) -> str | None:
    """从第一个 { 或 [ 截到最后一个 } 或 ]。

    必须同时认 { 和 [。只认 { 的话，模型返回顶层数组时你会截出
    两个元素之间的碎片，然后把它误判成「解析失败」—— 我踩过。
    """
    starts = [i for i in (text.find("{"), text.find("[")) if i != -1]
    if not starts:
        return None
    start = min(starts)
    end = max(text.rfind("}"), text.rfind("]"))
    return text[start : end + 1] if end > start else None


def extract_json(text: str):
    """返回 (值, 取值方式)。全失败时抛 ValueError。"""
    text = text.strip()
    candidates = [("raw", text)]
    candidates += [("fenced", m.group(1).strip()) for m in FENCE.finditer(text)]
    candidates.append(("sliced", _slice(text)))

    for how, candidate in candidates:
        if not candidate:
            continue
        try:
            return json.loads(candidate), how
        except json.JSONDecodeError:
            continue
    raise ValueError("输出里找不到可解析的 JSON：" + text[:120])


if __name__ == "__main__":
    for sample in [
        '{"a": 1}',
        '[{"a": 1}, {"a": 2}]',            # 顶层数组：第一版就是在这里错的
        '这是我整理的结果：\n{"a": 1}\n希望有帮助。',
        '```json\n{"a": 1}\n```',
    ]:
        value, how = extract_json(sample)
        print(how, "->", value)
```

```text
raw -> {'a': 1}
raw -> [{'a': 1}, {'a': 2}]
sliced -> {'a': 1}
fenced -> {'a': 1}
```

> **实跑状态**：这段代码在本地 Python 3.10 上跑过，上面的输出是真实运行结果。

## 别忘了检查 `stop_reason`

本节 18 次「麻烦任务」的运行里，有 1 次是**被 `max_tokens` 截断**的。它表现为「输出不是合法 JSON」—— 如果你不检查 `stop_reason`，就会把它记成一次格式失败，然后得出「提示式不可靠」的错误结论。

```python
# read_stop_reason.py
def classify(resp):
    """解析之前先分流。resp 是 SDK 返回的整个响应对象。"""
    reason = resp.stop_reason            # 字符串字段，平铺在响应顶层
    if reason == "max_tokens":
        return "预算不足"               # 输出被切断，不是格式问题
    if reason in ("end_turn", "tool_use", "stop_sequence"):
        return "正常结束"               # 才轮到解析器
    return "未知取值，单独看"           # 不要默默归进任何一类


if __name__ == "__main__":
    from types import SimpleNamespace as NS
    samples = [
        NS(stop_reason="end_turn"),
        NS(stop_reason="max_tokens"),
        NS(stop_reason="tool_use"),
    ]
    for r in samples:
        print("stop_reason=%-12s -> %s" % (r.stop_reason, classify(r)))
```

```text
stop_reason=end_turn     -> 正常结束
stop_reason=max_tokens   -> 预算不足
stop_reason=tool_use     -> 正常结束
```

（本节代码块均在本地 Python 3.10 上跑过，输出为上示真实结果。SDK 里字段名是 `resp.stop_reason`；如果你直接用 HTTP 报文，它在响应的顶层同名位置。）

这个坑在本项目里已经撞过三次。判据很简单：**看到解析失败，先看 `stop_reason` 和 `finish_reason`，再解释。** 越简单越有效 —— 它会立刻把「模型又崩了」这句话拆成两种完全不同的东西：一种要改任务设计，一种只要调大数字。

## 常见坑

**把「模型输出 JSON 不可靠」当成设计前提。** 实测里提示式在 5 到 60 条记录的全部规模上都稳定。用一个测不准的风险，去换一个确定的代价（放弃思考、多付工具定义、跨厂商兼容问题），不划算。

**解析器只认对象不认数组。** 这是本节真实踩到的坑。模型完全可能返回顶层数组，你的截取逻辑必须同时认 `{` 和 `[`。

**不检查 `stop_reason` 就统计失败率。** `max_tokens` 截断会被算进「格式失败」，把测量结果整个污染掉。所以失败率的分母必须先把截断样本剔出去 —— 只统计 `end_turn` / `tool_use` 结尾的那部分。

**以为强制工具调用一定更快。** 实测 60 条记录时它更慢（394 ms vs 213 ms），因为协议开销与工具定义吃掉了省下的思考。

**以为 `strict: true` 会替你强制 schema。** 本节的下一节会给出实测：这个参数被接受（返回 200），但**静默无效**。
