假设一个常见故障：上线两周后，库里出现折扣率为 150% 的记录。代码里的 schema 明明写着：

```json
{ "discount_percent": { "type": "number", "maximum": 100 } }
```

模型也确实调用了工具，返回的 JSON 也通过了你的解析。**问题在于把“请求里带了 schema”误当成“这个 endpoint 一定会强制执行 schema”。** 有些接口只把它作为模型上下文，有些接口提供受支持子集的严格约束；必须按具体 API 格式与 endpoint 确认。无论哪种，都要在副作用入口前做应用侧校验。

这一节会撞上四个名词，先按它们各自管什么分开：

- **token**：模型生成文本时使用的词表单元（第 1 章）。在一种常见的约束解码实现里，系统会根据当前语法状态限制下一步可选 token；具体实现、编译成本和支持范围由服务端决定，不能仅凭“按 token 生成”推断某个 schema 关键字会被强制。
- **`oneOf` / `$ref` / `additionalProperties`**：它们是 JSON Schema 的关键字，可分别表达组合分支、复用定义和额外属性规则。它们的标准语义可迁移；某个 provider 的受限 schema 子集、递归支持和执行方式则不能直接类比成你本地 HTTP 校验器。
- **约束解码**（constrained decoding）：生成过程受语法或 schema 约束的一类方法；具体保证取决于 endpoint 支持的模式和 schema 子集（下一小节展开）。
- **Pydantic**：Python 的数据解析与校验库。模型类可以生成 JSON Schema，但 Pydantic 的运行时校验行为并不与所有 provider 的 schema 子集完全等价；本节用它展示应用侧解析和校验。还要明确类型转换策略：默认 lax 模式可能把 JSON 字符串 `"1200"` 转成整数 `1200`，如果应用要求输入本身满足 JSON 类型，可显式启用 `ConfigDict(strict=True)`；Pydantic 2.9 的 [strict mode 文档](https://docs.pydantic.dev/2.9/concepts/strict_mode/)说明了转换边界。是否转换应由接口契约决定，而不是把解析成功等同于输入类型正确。

## 历史记录摘要：schema 关键字的行为

以下是 2026-10-08 历史记录中的摘要，不是本轮复现结果。当前仓库没有逐次请求/响应、精确模型快照、完整 schema 与可重算 scorer；`deepseek-flash` 也不足以唯一确定当时的模型版本和 API 路由。因此表中每项都是**待核实的历史观察**，不能据此认定关键字失效或推广到其他 endpoint。旧记录称每项强制工具调用 3 次，`additionalProperties` 5 次，并称当时关闭思考；请求形态和评分细节缺失，无法独立确认。

| 关键字 | 旧记录中的输入摘要 | 旧记录中的输出摘要 | 旧报告判断（本轮未复核） |
|---|---|---|---|
| `enum: [low, medium, high]` | 「十万火急」 | `high` | 旧摘要称输出为枚举值；未独立复核 |
| `required: [owner]` | 原文**没提**负责人 | `""` 或 `"未提及"` | 字段存在；schema 不判断内容是否有证据 |
| `type: number` | 「一百九十九元」 | `199`（number） | 类型转换成功 |
| `maximum: 100` | 「折扣力度是 150%」 | `150` | 旧摘要称输出 150；不代表当前 endpoint 能力 |
| `pattern: ^1[0-9]{10}$` | 座机 `010-12345678` | `"01012345678"` | 旧摘要称出现此输出；未独立复核 |
| `additionalProperties: false` | 原文多给了邮箱、手机、公司、职位 | 5/5 只返回 `name` | 这 5 次遵守；小样本不构成保证 |
| `type: integer` | 「买了 2.5 箱」 | `2` 或 `3` | 输出都满足 integer；取整方向是语义选择，不是 Schema 验证结果 |
| `minItems: 3` | 清单里只有 2 项 | 2 项 | 没有，但**没有编造第 3 项** |
| `format: date` | 「下周三交货」 | `"2025-11-19"` 或 `"下周三"` | **没有** |
| `type: ["string","null"]` | 「（没有备注）」 | `"无"` 或 `"null"`（**字符串**） | 端点接受 |
| `oneOf` | — | 正常返回 | 端点接受 |
| 顶层递归 `$ref` | 树形目录 | **HTTP 400** | 端点拒绝 |

这张旧表不能把“字段是否出现”“输出类型是否符合”“业务值是否合理”“内容是否有证据”混为一个 Schema 结果。表中有关缺失字段时生成空字符串或 `"未提及"` 的内容，也只是未复核摘要；不过 [JSON Schema 2020-12 的 `required`](https://json-schema.org/draft/2020-12/json-schema-validation) 标准语义很明确：它要求属性出现，不要求值非空、真实或有来源。`type: integer` 只检查 JSON 类型，不会替业务决定 2.5 箱应如何处理。

**结构合规不能替代业务校验和事实核验。**

## 约束解码是什么，不是什么

**一种常见实现思路**是把语法或 schema 编译成状态机/语法，再在生成时屏蔽当前状态下不合法的 token。不同服务可以采用不同实现；应用通常只看到 API 契约，不应假设自己能取得 provider 的 tokenizer 或掩码。

这解释了两件工程事实：第一，约束保证只覆盖该 endpoint 声明支持的 schema 子集；第二，复杂 schema 可能增加编译成本或被拒绝，但影响取决于具体实现和限制，不能从“schema 更复杂”推出固定的内存、时延或费用规律。结构化最终输出也不等于模型没有内部推理；支持思考模式与严格结构输出的组合能力必须看 provider、API 格式和模型文档。

**按 provider 文档区分接口。** 截至 2026-10-21，DeepSeek 文档把 strict tool-call 模式标为 Beta，要求走 `https://api.deepseek.com/beta` 的 Chat Completions function 形态，并在 `function` 上设置 `strict: true`；其列出的子集包括 `maximum`、字符串 `pattern` 和递归 `$ref`，且说明 V3.2 起支持 thinking mode 下的 tool use。它与下方历史记录里的 Anthropic 风格 `input_schema` 请求不是同一个 API 形态。

[Anthropic strict tool use 文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use)则把 `strict: true` 用于受支持子集内的严格工具输入；[Structured Outputs 文档](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)把 JSON 文本输出 schema 作为单独的 `output_config.format` 功能，并明确列出不支持递归 schema 和数值 `minimum`/`maximum`。这正说明能力必须按 provider、API 格式、模型和 schema 子集分别确认；不能把某个旧 endpoint 的观察当成行业通则。

JSON Schema 可表达字段类型、数值范围、字符串模式、数组约束和一部分依赖/条件关系；标准本身不能替你判断抽取内容是否有证据，也不能一般性地表达任意两个字段之间的大小比较。provider 严格模式只负责文档所列子集，应用仍应在解析后执行本地 schema 与业务校验。

**“严格”也不代表每个响应都一定是符合 schema 的业务结果。** 以 Anthropic 当前 JSON structured outputs 文档为例：安全拒绝可返回 HTTP 200 且 `stop_reason="refusal"`，拒绝文本可能不符合 schema；达到 `max_tokens` 时内容可能被截断；字符串 `enum` / `const` 还存在大小写边界。复杂 schema 也受服务端语法编译复杂度限制，首次编译会增加延迟，超限可能失败。实现时先检查传输/API 状态与 provider 的结束原因，再提取预期内容、解析并在本地校验；不能因 HTTP 200、SDK 返回对象或启用了 `strict` 就跳过这些步骤。工具 strict 约束的是工具名和参数，不自动约束最终文本。上述是 Anthropic 的当前接口例子，不应外推为所有 provider 的统一行为；部署时按实际 endpoint 文档更新处理分支。

旧记录还声称：在 Anthropic 风格的工具定义中加入 `strict: true` 后，该请求仍返回 200 并输出 `150`。原始请求与响应缺失，因此这只是**未能独立复核的历史观察**；而且它不能代表 DeepSeek 现在的 Beta strict Chat Completions 路径。下面保留的是旧记录所示请求形态，不是当前 DeepSeek strict 模式的正确示例：

```json
{
  "name": "save",
  "description": "保存报销单",
  "strict": true,
  "input_schema": {
    "type": "object",
    "properties": { "discount_percent": { "type": "number", "maximum": 100 } },
    "required": ["discount_percent"]
  }
}
```

目前能确定的只有：这条历史摘要没有足够原始证据供本轮复核。不要从它推断 endpoint 接受/忽略字段的现状；部署时按目标接口文档构造正确请求，再测试支持边界，并在应用层执行校验。

三条线要分清楚，因为它们的**处理方式完全不同**：

1. **形状**：字段名、类型、是否对象。应用必须解析并在本地校验；不能只假设模型遵循 schema。
2. **约束**：范围、格式、长度、跨字段关系。JSON Schema 可表达其中许多条件，但要确认目标端点支持并在本地执行校验。
3. **事实依据**：字段内容是否有可信来源，schema 本身无法证明；需保留来源、核对外部事实，或改变任务设计。

## 完整可运行代码：用 Pydantic 把第二层补上

```python
# validated_refund.py
"""Pydantic 在应用侧解析和校验；业务规则另行实现。"""
import json
from datetime import date
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field, ValidationError

class Refund(BaseModel):
    # 让本地输入类型与 JSON Schema 的 JSON 类型边界一致；默认 lax 模式会尝试转换部分输入。
    model_config = ConfigDict(strict=True)

    amount: int = Field(multiple_of=100, description="报销金额，必须是 100 的整数倍")
    issue_type: Literal["refund", "repair"]
    start_date: date
    end_date: date

    def check_business_rules(self) -> list[dict[str, str]]:
        problems = []
        if self.end_date < self.start_date:
            problems.append({"type": "business_rule", "field": "end_date", "msg": "end_date 早于 start_date：区间不可满足"})
        return problems

RAW = """{"amount":1234,"issue_type":"question","start_date":"2026-10-15","end_date":"2026-10-01"}"""
try:
    refund = Refund.model_validate_json(RAW)
    problems = refund.check_business_rules()
except ValidationError as exc:
    # 对下游只暴露字段路径与错误类型/消息；不默认转发原始输入值。
    problems = [{"type": error["type"], "field": ".".join(map(str, error["loc"])), "msg": error["msg"]} for error in exc.errors(include_url=False, include_context=False, include_input=False)]
    refund = None
print("校验结果：", "通过" if refund and not problems else "不通过")
print("问题清单：", json.dumps(problems, ensure_ascii=False))

valid = Refund.model_validate_json("{\"amount\":1200,\"issue_type\":\"refund\",\"start_date\":\"2026-10-01\",\"end_date\":\"2026-10-15\"}")
print("通过时的下游对象：", valid.model_dump_json())
business_case = Refund.model_validate_json("{\"amount\":1200,\"issue_type\":\"refund\",\"start_date\":\"2026-10-15\",\"end_date\":\"2026-10-01\"}")
print("跨字段业务规则问题：", json.dumps(business_case.check_business_rules(), ensure_ascii=False))
```

本地运行输出（Python 3.10 + Pydantic 2.9.2）：

```text
校验结果： 不通过
问题清单： [{"type": "multiple_of", "field": "amount", "msg": "Input should be a multiple of 100"}, {"type": "literal_error", "field": "issue_type", "msg": "Input should be 'refund' or 'repair'"}]
通过时的下游对象： {"amount":1200,"issue_type":"refund","start_date":"2026-10-01","end_date":"2026-10-15"}
跨字段业务规则问题： [{"type": "business_rule", "field": "end_date", "msg": "end_date 早于 start_date：区间不可满足"}]
```

> **实跑状态**：以上示例在本地 Python 3.10 + Pydantic 2.9.2 上运行；没有调用模型 endpoint。历史模型实验未在本轮复现。


**校验通过之后，下游拿到什么？** 失败时得到字段路径、错误类型和可安全展示的消息；成功时得到已解析的数据对象。这个示例刻意不把 `input` 原值放进问题清单，因为输入可能包含个人信息或秘密。Pydantic 的 [`ValidationError.errors()`](https://docs.pydantic.dev/2.9/errors/errors/) 默认可能包含输入值、上下文和文档链接；是否记录这些字段应依据数据分类，而不是无条件打印或发给模型。

跨字段规则是在类型解析后由应用代码执行的。上面的 `business_case` 给出日期先后错误；比较使用 `datetime.date`，避免把任意字符串当日期并依赖字典序。

校验器只报告结果，不应擅自决定重试、人工审核、拒绝还是写入。调用方应结合错误类别、重试预算和业务风险制定策略。下面只展示一个不执行副作用的决策边界：

```python
def decide(refund: Refund | None, problems: list[dict[str, str]]) -> dict:
    if refund is None or problems:
        return {"action": "needs_review", "problems": problems}
    return {"action": "validated", "payload": refund.model_dump(mode="json")}
```

本节后续旧重试表报告过“只给错误原因时 6/6 修正”等数字，但逐次输入/输出、评分器和模型快照需要单独复核；不要把它当成通用修正率。

## 如何解读递归 `$ref` 的旧 400 摘要

旧记录称，一个树形递归 `$ref` 工具 schema 收到 HTTP 400，并摘录了服务端提示根节点 `type` 为 `null`。但原始请求、完整 schema、协议路由和未经截断的响应都没有归档，所以无法判断触发点是根 schema 没有 `type: object`、递归引用不受支持，还是其他格式问题；不能据此得出“这个 endpoint 不支持 `$ref`”或“树形结构必须扁平化”的通用结论。

当前不同 API 的限制也不相同：DeepSeek strict Beta 文档说明支持递归 `$ref`；Anthropic Structured Outputs 文档支持 `$ref`，但不支持递归 schema。应按目标 endpoint 的文档构造 schema，并在应用里做本地校验，而不是从一条缺少请求上下文的 400 推导规则。[DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/) · [Anthropic Structured Outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

## `description` 能引导模型，但不等于硬约束

`description` 会成为工具定义的一部分，可能帮助模型理解字段用途和期望格式；它本身不是验证器。严格模式是否会按某个字段约束输出，要看 endpoint 是否支持该关键字并启用了相应模式。反过来，不能笼统地说 `maximum`、`pattern` 或 `format` 都只是“没人读的注释”：DeepSeek strict 文档明确列出部分 `maximum`、`pattern` 和格式支持，而 Claude Structured Outputs 明确不支持数值边界但支持有限字符串格式与模式。

下面的双语对照是旧记录摘要，未保留逐次请求、响应和 scorer；本轮无法独立复核，因此不作 5/5 成功率或因果结论：

| schema description | 旧记录输入摘要 | 旧记录输出摘要 |
|---|---|---|
| `必须用英文填写公司名` | 「公司叫启明电子」 | `"Qiming Electronics"` |
| `必须是 11 位手机号，纯数字，不要连字符` | 「电话是 010-12345678」 | `"01012345678"` |

第二条即便记录准确，也只说明格式要求可能影响生成，不能把 10 位座机校验成有效 11 位手机。需要硬校验时，在已验证的 strict schema 子集内加约束，并在应用侧执行真实号码规则。

## `enum` 的风险：没有“未知”时，合法值也可能是错值

枚举能把允许的值域写清楚；只有在目标 endpoint 的对应 strict schema 子集确实强制它时，才可依赖其结构保证。无论是否严格，合法枚举值都不代表模型选对了业务含义。若业务确实存在“未知/不适用”状态，应把它建模为明确成员，并在应用层处理；不要机械地给每个枚举追加 `other`，因为这可能不是合法业务状态。

旧记录称 `refund/repair` 两值时 6 次都选错，添加 `other` 后 6 次都选对；原始问题、逐次输出、模型快照和 scorer 未归档。这些数字只保留为待核实历史摘要，不能证明补充 `other` 会带来普遍提升。

## 选型看 endpoint 契约和应用校验

不同产品在 API 格式、strict 开关、受支持的 schema 子集、拒绝方式和响应状态上有差异；版本变化也会改变边界。当前 DeepSeek strict tool calls、Anthropic strict tool use 与 Claude JSON structured outputs 是不同的接口契约，不能把其中一个接口的结果套用到另一个。

工程上按三步处理：查当前官方文档确认模型/API/子集；用边界值测试实际请求和拒绝路径；在写数据库或调用外部工具前执行本地 schema、业务规则与授权检查。历史离线小样本只能说明当时的特定观察，不能替代这三步。

## 常见坑

**把 schema 字段存在请求里，当成 endpoint 一定执行。** 确认使用的 API 格式、模型和 strict 模式，再验证应用实际收到的数据。

**把 `required` 当成事实校验。** 它检查字段是否出现；不能证明值非空、真实或有来源。

**把一个关键字的历史结果推广到所有厂商。** `maximum`、`pattern`、`format`、`$ref` 等的支持范围按 endpoint 文档逐项确认。

**把类型合规当成业务正确。** 整数可能仍是错误的取整；日期格式有效也不代表日期有证据或符合跨字段规则。

**把 Pydantic 异常全文写日志或发回模型。** 错误对象可能包含原始输入；只传递必要、脱敏的字段路径和错误类别。

**只在模型端约束。** 所有副作用入口前都要有应用侧解析、校验和授权边界。
