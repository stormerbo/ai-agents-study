上一节的校验器拦下了一条记录：金额 1234 不是 100 的整数倍。

**接下来发生什么，决定了系统能否安全处理失败。** 校验器提供了具体反馈，模型可以据此尝试修复；但重试不是正确性保证，每一轮结果都必须重新校验，耗尽预算后还要进入明确的失败路径。

## 历史摘要：三种「重试」当时记录了不同结果

设计思路：把一个业务约束放在本地校验器里，用于观察错误反馈能否帮助模型修改输出。但现有仓库没有保存 2026-10-08 的逐次请求/响应、完整 prompt、精确模型版本和评分脚本，因此不能证明各组首轮都按设计失败，也不能重算表中的修正率。

| 策略 | 第二次请求里多了什么 | 首轮不合格 | 两轮内修正 |
|---|---|---:|---:|
| 原样重发 | 什么都没多 | 6/6 | **0/6** |
| 空洞重试 | 「上一次没通过校验，请重新输出」 | 6/6 | **0/6** |
| 带错误信息 | 上次的输出 + 「amount 必须是 100 的整数倍，实际是 1234」 | 6/6 | **6/6** |

旧笔记还保留了以下轨迹摘要；由于原始逐次日志缺失，它不是可独立核查的原始输出：

```text
原样重发   1234 → ✗ , 1234 → ✗ , 1234 → ✗ , 1234 → ✗ , 1234 → ✗ , 1234 → ✗
空洞重试   1234 → ✗ , 1234 → ✗ , 1234 → ✗ , 1234 → ✗ , 1234 → ✗ , 1234 → ✗
带错误信息 1234 → 1200 , 1234 → 1200 , ...（6 次全部修正）
```

（2026-10-08 的历史摘要：每组据称 6 次、`temperature=1`；原始轨迹与 scorer 未归档，数据无法独立复核，不能当作可复现的模型成功率。）

旧记录称各组固定使用 `temperature=1`。控制同一实验中的采样设置有助于减少一个已知混杂因素；但没有原始调用记录，无法确认这个参数在当时 endpoint 上的实际含义或是否每次一致，也不能用温度解释组间差异。不同 provider 对采样参数的支持与行为应按 endpoint 文档确认。

原样重发不会向模型提供新的约束或证据；若每次都重发相同上下文，它只能基于相同条件重新生成。但历史摘要里“6 次相同”无法说明模型为什么输出 1234，也不能证明模型认定该值正确。更稳妥的工程结论是：**如果本地校验器知道具体失败原因，就把经过筛选的错误反馈传回；不要把一次小样本观察写成普遍修正规律。**

## 哪个成分起作用：旧摘要不足以分离因果

历史记录还摘要了三种反馈组合，但没有保留逐次输入、输出或评分规则。下表只能作为不可复核的旧记录，不能用于分离因果：

| 第二次请求里给什么 | 修正率 |
|---|---:|
| 只给上次的输出 | **0/6** |
| 只给错误原因 | **6/6** |
| 两者都给 | 4/6 |

（同一组设置，每组 6 次。）

这组旧摘要与“错误原因可能比重复粘贴旧输出更有用”的假设相容，但不足以证明因果：没有逐次轨迹，且“只给错误原因”与“两者都给”的小样本差异可能来自随机波动或其他未记录因素。工程上应通过可重放的配对评估验证反馈格式，而不是把这张表当成普遍规律。

第三行反而略低于第二行，我没有足够证据解释它（6 次采样、`temperature=1`，噪声完全可能有这个量级）。**不要据此得出「少给更好」的结论** —— 但也不该跳过这个数字不提，它至少说明「信息给得越多越好」也是一句没被验证过的直觉。

## 哪些错误值得重试，哪些不值得

重试不是对所有失败都有效。按失败来源分四类；处理方式也要分层，不能把 API 重试和模型校验重试混为一谈：

| 失败类别 | 例子 | 处理原则 |
|---|---|---|
| 结构/本地约束失败 | 字段缺失、金额不是 100 的倍数 | 可返回脱敏的字段路径与约束类别；每次重试后重新校验 |
| provider 终止状态 | refusal、`max_tokens` 截断、上下文超限 | 先按 `stop_reason` 分流；拒绝通常停止，截断只有在预算策略允许时才增加输出预算 |
| API/传输失败 | 超时、限流或服务端错误 | 使用单独的退避、重试与总预算策略，不当作模型校验错误 |
| 信息缺失 | 原文无负责人且没有可信外部来源 | 重试不能新增证据；询问、补充来源或表达未知 |

本例的 `extract_refund` 只捕获 Pydantic `ValidationError`；`client.messages.create` 抛出的传输异常会向外传播，由调用方的 API/runtime 层按错误码、请求是否可安全重放和总预算处理，不会被误当成 schema 反馈再次喂给模型。第四类（信息缺失）不能靠模型重试补出证据，应改 schema、请求补充材料或查询可信来源。一个必须填、但输入里并不存在的字段，重试不会新增证据；上一节提到的空字符串或 `"未提及"` 只是未复核的历史摘要，不能据此估计模型编造率。信息不足时应允许显式未知状态，再由应用决定是否继续。

判断方法可以浓缩成一句话：**问自己「如果模型足够聪明，它能不能从输入里推出这个值」。** 不能推导出来的，就不是重试能解决的问题。

## 一个反过来的提醒：别把重试当成主要机制

重试是安全网，不是主干。

另一份同日历史摘要声称，把同一条业务规则放在 prompt 或仅放在校验器时，首轮通过率不同；同样缺少请求、原始输出和 scorer，不能据此断言差异幅度或因果：

| 规则放在哪 | 首轮合格率 |
|---|---|
| 写进 prompt | 3/5 ～ 4/5（取决于措辞） |
| 只在校验器里（prompt 不提） | 0/6 |

因此可作为默认设计原则的是两件事一起做，而不是旧成功率本身：

1. **能写进 prompt 的规则就写进 prompt** —— 它可能提高首轮通过率；具体收益需要用同一评估集测量。
2. **写不进去、或不可靠的靠校验器兜** —— 它阻止未通过本地校验的值进入下游，并给模型一次受预算限制的修正机会；校验器不能证明字段内容有事实依据。

只做第一条，你迟早会在某一次没被拦住的输出上出事；只做第二条，可能增加重试成本；应在评估集中同时看首轮通过率、最终通过率、重试次数与端到端成本。

## 这里没有业务副作用，但 Messages API 仍有工具调用协议

本节把一个工具 schema 当作结构化输出通道：模型返回 `tool_use` 后，应用只做本地解析与校验，不调用退款或保存函数。它和真实的业务工具有不同的副作用边界，但仍然是 Messages API 的 client-tool turn。

校验通过时，本例直接结束抽取流程，不再发后续请求，所以无需回填工具结果。**校验失败并准备沿同一段对话重试时，必须把刚才的 assistant `tool_use` 与紧接着的 user `tool_result` 配对**；结果内容可以报告本地校验失败，并设置 `is_error: true`，这表示调用未通过验证，不代表执行过业务副作用。Anthropic 的[工具调用处理文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)要求工具结果紧跟对应的 `tool_use`，并说明可用 `is_error` 返回错误。DeepSeek 或兼容端点也应按各自协议验证，不能默认与 Anthropic 完全一致。

工具强制选择与 thinking 模式还受模型/API 支持范围限制。下面展示的是 Anthropic Messages API 风格的调用形态；选定模型前请核对[强制工具选择限制](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)，本例没有连 provider 实测。若所用端点没有这种能力，应改用其文档支持的 JSON structured-output API，而不要假装工具循环已经验证。

## 完整可运行代码

```python
# retry_with_feedback.py
"""用本地校验反馈修复结构化 tool_use；不执行任何业务副作用。"""

import json
from pydantic import BaseModel, ConfigDict, Field, ValidationError

MAX_ATTEMPTS = 3
TOOL_NAME = "save_refund"


class Refund(BaseModel):
    model_config = ConfigDict(strict=True)
    amount: int = Field(multiple_of=100)
    reason: str


def safe_report(exc: ValidationError) -> list[dict[str, str]]:
    """只返回校验类型、字段路径与标准消息，不回传 input/context/doc URL。"""
    return [
        {
            "type": error["type"],
            "field": ".".join(map(str, error["loc"])),
            "message": error["msg"],
        }
        for error in exc.errors(
            include_url=False,
            include_context=False,
            include_input=False,
        )
    ]


def classify(report: list[dict[str, str]]) -> str:
    kinds = {item["type"] for item in report}
    constraint_errors = {
        "multiple_of", "greater_than", "greater_than_equal",
        "less_than", "less_than_equal", "string_too_short",
        "string_too_long", "string_pattern_mismatch",
    }
    shape_errors = {
        "missing", "int_type", "string_type", "list_type", "dict_type",
        "bool_type", "float_type", "model_type", "tuple_type",
        "extra_forbidden", "int_parsing", "string_parsing",
    }
    if kinds & constraint_errors:
        return "constraint"
    if kinds and kinds <= shape_errors:
        return "shape"
    return "validation_other"


def extraction(
    value: Refund | None,
    attempts: int,
    first_round_ok: bool,
    error_type: str | None = None,
    last_report: list[dict[str, str]] | None = None,
) -> dict:
    return {
        "result": value,
        "attempts": attempts,
        "first_round_ok": first_round_ok,
        "error_type": error_type,
        "last_report": last_report or [],
    }


def extract_refund(client, model: str, ask: str, schema: dict) -> dict:
    """返回真实尝试次数；非 tool_use 终止状态不当成 schema 错误盲目重试。"""
    messages = [{"role": "user", "content": ask}]
    last_report: list[dict[str, str]] = []
    last_error: str | None = None

    for attempt in range(1, MAX_ATTEMPTS + 1):
        response = client.messages.create(
            model=model,
            max_tokens=2000,
            messages=messages,
            tools=[{
                "name": TOOL_NAME,
                "description": "只把报销信息整理为候选对象；不会执行报销或写入操作。",
                "input_schema": schema,
            }],
            tool_choice={"type": "tool", "name": TOOL_NAME},
        )

        if response.stop_reason != "tool_use":
            reason = {
                "refusal": "refusal",
                "max_tokens": "truncated",
                "model_context_window_exceeded": "context_limit",
            }.get(response.stop_reason, "unexpected_stop_reason")
            return extraction(None, attempt, False, reason)

        calls = [block for block in response.content if block.type == "tool_use"]
        if len(calls) != 1 or calls[0].name != TOOL_NAME or not calls[0].id:
            return extraction(None, attempt, False, "unexpected_tool_output")
        block = calls[0]

        try:
            value = Refund.model_validate(block.input)
        except ValidationError as exc:
            last_report = safe_report(exc)
            last_error = classify(last_report)
            if attempt == MAX_ATTEMPTS:
                return extraction(None, attempt, False, last_error, last_report)

            # 复用同一段 Messages API 对话时，工具调用错误也要配对 tool_result。
            feedback = json.dumps(
                {"error": "validation_failed", "issues": last_report},
                ensure_ascii=False,
            )
            messages += [
                {"role": "assistant", "content": response.content},
                {
                    "role": "user",
                    "content": [{
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": feedback,
                        "is_error": True,
                    }],
                },
            ]
            continue

        return extraction(value, attempt, attempt == 1)

    raise AssertionError("MAX_ATTEMPTS must be at least 1")


if __name__ == "__main__":
    try:
        Refund.model_validate({"amount": 1234, "reason": "打车"})
    except ValidationError as exc:
        print("给模型的脱敏问题：")
        print(json.dumps(safe_report(exc), ensure_ascii=False))
```

```text
给模型的脱敏问题：
[{"type": "multiple_of", "field": "amount", "message": "Input should be a multiple of 100"}]
```

> **实跑状态**：以上错误摘要由 Python 3.10 + Pydantic 2.9.2 在本地运行得到，没有调用 provider。真实请求/响应格式、强制工具选择能力以及错误反馈后的模型修正都没有在官方 endpoint 上实测。默认报告不包含 input、context 或文档 URL；若使用自定义 validator，仍须审查其消息是否会泄露敏感值。

## 重试耗尽之后：降级分支与埋点

`extract_refund` 返回实际调用次数、首轮状态、失败类别和脱敏问题列表；调用方仍要决定失败后走哪种业务策略。下面的控制流示例接收一个已绑定 client/model/schema 的抽取函数，并将**观测结果**与**业务降级策略**分开。

先定义这套系统的**产物**，也就是无论成功失败都会产生的那条记录（**构造示例，未实跑**）：

```json
{
  "request_id": "req_8f21",
  "attempts": 3,
  "first_round_ok": false,
  "error_type": "business_rule",
  "action": "human_queue",
  "payload": {
    "case_ref": "case_92ab",
    "last_report": [
      {"type": "business_rule", "field": "end_date", "message": "日期区间无效"}
    ]
  }
}
```

记录包含四项观测：**实际请求次数**（`attempts`）、**首轮是否通过**、**校验问题类别**和**最终动作**。`information` 是应用对“源材料缺少证据”的判断，不是 Pydantic 错误类型；重试器不能仅凭 schema exception 推断它。埋点不含原始请求、模型输出或完整 payload。人工队列通过受控的 `case_ref` 回到授权存储；按数据分级设置访问控制、保留期限和脱敏规则。

```python
# degrade.py
"""将验证结果交给显式的失败策略；指标只记录最少字段。"""

import json
from pydantic import BaseModel, ConfigDict, Field


class Refund(BaseModel):
    model_config = ConfigDict(strict=True)
    amount: int = Field(multiple_of=100)
    reason: str


_MISSING = object()


def emit(event: dict) -> None:
    # 不把原文、模型候选或业务 payload 写入普通指标日志。
    print("[metric] " + json.dumps(event, ensure_ascii=False))


def run(
    ask: str,
    extract,
    *,
    request_id: str,
    fallback_policy: str,
    case_ref: str | None = None,
    default_value=_MISSING,
    split_fields: tuple[str, ...] = (),
    remaining_attempts: int = 0,
) -> dict:
    """extract(ask) 返回上一段的 outcome；策略配置由业务风险决定。"""
    outcome = extract(ask)
    value = outcome["result"]
    attempts = outcome["attempts"]
    first_ok = outcome["first_round_ok"]
    error_type = outcome["error_type"]
    report = outcome["last_report"]

    if value is not None:
        action = "validated"
        payload = value.model_dump(mode="json")
    elif fallback_policy == "human_queue":
        if not case_ref:
            raise ValueError("human_queue requires an ACL-protected case_ref")
        action = "human_queue"
        payload = {"case_ref": case_ref, "last_report": report}
    elif fallback_policy == "conservative_default":
        if default_value is _MISSING:
            raise ValueError("conservative_default requires an explicit default_value")
        action = "conservative_default"
        payload = {"value": default_value, "is_uncertain": True}
    elif fallback_policy == "split_retry":
        if not case_ref or not split_fields or remaining_attempts < 1:
            raise ValueError("split_retry requires case_ref, fields, and remaining budget")
        action = "split_retry"
        # 这是交给有预算限制的字段级 worker 的计划，不在此函数中隐式加轮次。
        payload = {
            "case_ref": case_ref,
            "fields": list(split_fields),
            "remaining_attempts": remaining_attempts,
        }
    else:
        raise ValueError(f"Unsupported fallback policy: {fallback_policy}")

    record = {
        "request_id": request_id,
        "attempts": attempts,
        "first_round_ok": first_ok,
        "error_type": error_type,
        "action": action,
        "payload": payload,
    }
    emit({key: record[key] for key in (
        "request_id", "attempts", "first_round_ok", "error_type", "action"
    )})
    return record


if __name__ == "__main__":
    # 控制流夹具，不调用 provider；实际 requests 是从 outcome 中计数。
    def fake_extract_fixed(ask: str) -> dict:
        return {
            "result": Refund(amount=1200, reason="已脱敏示例"),
            "attempts": 2,
            "first_round_ok": False,
            "error_type": None,
            "last_report": [],
        }

    def fake_extract_failed(ask: str) -> dict:
        return {
            "result": None,
            "attempts": 3,
            "first_round_ok": False,
            "error_type": "business_rule",
            "last_report": [{
                "type": "business_rule",
                "field": "amount",
                "message": "金额与来源规则冲突",
            }],
        }

    cases = [
        ("两轮内修正", fake_extract_fixed, "human_queue", "case_demo", _MISSING, (), 0),
        ("重试耗尽转人工", fake_extract_failed, "human_queue", "case_demo", _MISSING, (), 0),
        ("不确定默认值", fake_extract_failed, "conservative_default", None, None, (), 0),
        ("字段拆分计划", fake_extract_failed, "split_retry", "case_demo", _MISSING, ("amount",), 1),
    ]
    for label, extract, policy, case_ref, default, fields, budget in cases:
        record = run(
            "仅供测试的输入",
            extract,
            request_id="req_demo",
            fallback_policy=policy,
            case_ref=case_ref,
            default_value=default,
            split_fields=fields,
            remaining_attempts=budget,
        )
        print(label, json.dumps({
            "attempts": record["attempts"],
            "first_round_ok": record["first_round_ok"],
            "error_type": record["error_type"],
            "action": record["action"],
            "payload_fields": sorted(record["payload"]),
        }, ensure_ascii=False))
```

> **实跑状态**：以上输出由本地 Fake client 构造，使用 Pydantic 2.9.2，不调用 provider；字段级重试只输出有预算的 dispatch 计划，实际 worker 由调用方实现。

`classify` 只把标准 Pydantic 校验错误映射为约束、形状或其他校验类别；未知错误类型不会被猜成业务规则。真正的 `business_rule` 应来自应用自己的领域校验器；拒绝、截断和传输失败则在 API 响应层另行处理。类别用于诊断，不自动决定业务降级策略：

```text
amount=1234（constraint）        -> constraint
reason 缺失（shape）             -> shape
end_date 早于 start_date（业务）  -> business_rule
```

（分类契约示意：前两行对应上面的 Pydantic 校验错误；第三行必须由应用自己的领域校验器生成，当前代码不把它伪装成 Pydantic 输出。分支动作由调用方显式映射。）

代码把校验错误分类和动作策略拆开：`error_type` 描述失败，业务策略由调用方明确传入。不能让某一种错误类别自动决定是否可写入或走默认值；同一类错误在退款、推荐和数据标注任务中的风险不同。成功与失败都发出同结构的**最小化指标事件**，因此可以计算首轮通过率，而不必把原始数据塞进日志。

**人工处理需要能安全地回到必要上下文。** 这不等于把原文复制进普通队列或日志：只传权限受控的 `case_ref`，由授权页面按需读取原始材料；没有合规存储、访问控制和保留策略时，应拒绝入队或改走其他业务流程。

最后一条纪律：**降级路径也要有测试。** 用 Fake client 返回持续无效的 tool input，耗尽正常的正数重试预算，确认实际尝试次数、脱敏报告与各降级动作都正确；不要把上限设为 0，否则主流程会跳过所有模型调用。

## 重试不是万能的：降级路径必须在设计阶段定

历史摘要把“只给错误原因”记为 6/6，把“错误原因和上次输出都给”记为 4/6；两种反馈形态并不相同，而且都缺少原始轨迹，不能独立复核。**重试可能耗尽。** 下面列出三种示例降级策略，系统也可以选择明确拒绝或中止；具体行为必须在写代码之前定下来，因为临时补的兜底通常既没有测试覆盖也没人知道它存在：

| 降级方式 | 代价 | 适用场景 |
|---|---|---|
| 进人工队列 | 需要有人处理 | 金额、退款、下单这类不可逆动作 |
| 返回保守默认值并标注不确定 | 可能不准 | 推荐位、标签这类可容忍误差的 |
| 拆小重试（先只抽一个字段） | 多一轮成本 | 大 schema 里只有一两个字段过不去 |

不要把内部堆栈、原始输入或 provider 错误原样展示给用户；应返回清楚、可操作且符合业务风险的失败状态，例如请求补充信息、进入人工审核或说明本次无法完成。

## 重试的成本要算进去

每次重试都会增加请求与输出成本。若每轮都把完整历史重新发送，且每轮新增内容规模近似固定，n 轮请求所累计处理的输入长度会按等差数列增长；这是一个特定消息策略下的复杂度模型，不适用于有状态 API、不同缓存计费口径或固定上下文窗口的所有 endpoint。实际费用按 provider 返回的 usage 字段逐次累计。

所以在设计阶段要明确：最大尝试数、可重试错误类型、单次与总预算，以及耗尽后的动作。代码里的 3 次只是示例配置，不是跨 provider 的经验门槛。每个重试都必须受调用次数、时间与费用预算约束；真实业务工具还要另外处理执行结果未知时的幂等与对账。

还有一个无需额外模型调用的收益：**把首轮合格率记下来。**

重试次数的分布是这套系统最有价值的指标之一。首轮通过率偏低是一个诊断信号，但原因也可能是输入分布、模型/API 变更、评估集设计或字段定义不合适；应结合错误类型、分层样本与人工标注排查，不能单凭一个百分比断定 prompt 有问题。只统计最终通过率会掩盖重试成本，因此还应一起记录首轮通过率、最终通过率、尝试次数分布和人工接管率。

## 常见坑

**校验失败就原样重发。** 本节保留的 0/6 是无法复核的历史摘要。相同上下文不会增加新证据；是否会改变输出取决于采样和 endpoint，需在自己的评估集验证。

**只说「没通过校验，请重试」。** 旧摘要记为 0/6，未独立复核。反馈应指出安全可公开的字段路径与约束类别；仅在经过数据分类和脱敏后才附实际值，不要把错误对象中的原始 input 无差别发回。

**把完整异常对象直接发回去。** 它可能包含原始 input、context 或实现细节。先按字段白名单构造错误反馈；机器可读不代表可以安全披露。

**不设重试上限。** 每次重试都是一次完整往返，在模型确实做不到的任务上会持续烧钱。

**没想好降级路径。** 上线后才发现的兜底分支通常不被测试覆盖；而即使失败概率很低，生产流程也应设计并测试失败分支；温度参数本身并不能保证失败必然发生。
