上一节的校验器拦下了一条记录：金额 1234 不是 100 的整数倍。

**接下来发生什么，才是这套系统真正的分水岭。** 大多数第一版实现到这里就把异常往上抛了 —— 而这一节想说的是：抛出去之前，你手里其实有足够的信息让模型自己改对。

## 实测：三种「重试」的差别大到不像同一件事

设计要点：**业务规则不写进 prompt**，只有校验器知道（这样首轮必然不合格，三种策略才有区分度）。

| 策略 | 第二次请求里多了什么 | 首轮不合格 | 两轮内修正 |
|---|---|---:|---:|
| 原样重发 | 什么都没多 | 6/6 | **0/6** |
| 空洞重试 | 「上一次没通过校验，请重新输出」 | 6/6 | **0/6** |
| 带错误信息 | 上次的输出 + 「amount 必须是 100 的整数倍，实际是 1234」 | 6/6 | **6/6** |

三组的轨迹：

```text
原样重发   1234 → ✗ , 1234 → ✗ , 1234 → ✗ , 1234 → ✗ , 1234 → ✗ , 1234 → ✗
空洞重试   1234 → ✗ , 1234 → ✗ , 1234 → ✗ , 1234 → ✗ , 1234 → ✗ , 1234 → ✗
带错误信息 1234 → 1200 , 1234 → 1200 , ...（6 次全部修正）
```

（实测数据，`deepseek-flash`，2026-10-08，每组 6 次，`temperature=1`。）

`temperature` 是采样参数里最常被提到的一个：**它控制每次采样从概率分布里挑 token 时的随机程度** —— 设成 0，模型几乎总是挑概率最高的那个，输出最确定；设成 1，低概率候选也有机会被挑到，输出更发散。本节的实验把它固定为 1，理由不是「1 更好」，而是**让三组策略面对同样的随机性**：如果一组用 0、一组用 1，修正率的差别里就混进了一个与策略无关的变量。这也是后文反复出现「6 次采样、`temperature=1`，噪声完全可能有这个量级」那句话的来源。

「原样重发」为什么是 0？因为**重试这个动作本身不携带任何新信息**。模型面对的是完全相同的输入，它只能重新采样一次 —— 那是在掷骰子，不是在解决问题。而它每一次都掷出了同一个结果，恰恰说明模型认为 1234 就是对的。

## 到底是哪个成分起作用

「跟上次输出」和「说明错在哪」通常是打包在一起的。分开测一次：

| 第二次请求里给什么 | 修正率 |
|---|---:|
| 只给上次的输出 | **0/6** |
| 只给错误原因 | **6/6** |
| 两者都给 | 4/6 |

（同一组设置，每组 6 次。）

结论很干净：**起作用的是「错在哪」，不是「你上次输出了什么」。** 模型自己知道上次输出了什么 —— 那部分信息对它没有增量。

第三行反而略低于第二行，我没有足够证据解释它（6 次采样、`temperature=1`，噪声完全可能有这个量级）。**不要据此得出「少给更好」的结论** —— 但也不该跳过这个数字不提，它至少说明「信息给得越多越好」也是一句没被验证过的直觉。

## 哪些错误值得重试，哪些不值得

重试不是对所有失败都有效。按「错误里有没有可执行的信息」分三类：

| 错误类型 | 例子 | 重试有用吗 |
|---|---|---|
| 形状错误 | 输出里混进说明文字、JSON 被截断 | 有用，但先确认 `stop_reason`；截断要加大预算 |
| 约束越界 | 金额不是 100 的整数倍 | 有用 —— 把越界的值发回去（本节 6/6） |
| 信息缺失 | 原文根本没有负责人，schema 却标了 required | **没用 —— 重试也只能再编一个假值** |

第三类的处理方式与前两类完全不同：它不该重试，该改 schema 或改任务设计。一个必须填、但输入里并不存在的字段，重试多少次都只会得到另一个看起来合规的假值（上一节实测：`""` 或 `"未提及"`）。这类问题的出口只有三个 —— 改成可选、允许 `null`、或者去别处取这个信息。

判断方法可以浓缩成一句话：**问自己「如果模型足够聪明，它能不能从输入里推出这个值」。** 不能推导出来的，就不是重试能解决的问题。

## 一个反过来的提醒：别把重试当成主要机制

重试是安全网，不是主干。

我把同一条业务规则换个地方放，首轮合格率差了一个数量级：

| 规则放在哪 | 首轮合格率 |
|---|---|
| 写进 prompt | 3/5 ～ 4/5（取决于措辞） |
| 只在校验器里（prompt 不提） | 0/6 |

所以正确的做法是两件事一起做：

1. **能写进 prompt 的规则就写进 prompt** —— 它把首轮合格率抬上去，直接省掉重试的钱。
2. **写不进去、或不可靠的靠校验器兜** —— 它保证最终正确，并给模型一次自我修正的机会。

只做第一条，你迟早会在某一次没被拦住的输出上出事；只做第二条，你会把大部分成本花在重试上。

## 先澄清一件事：这里的工具调用没有被执行

本节的代码里出现了 `tools` 和 `tool_choice`，但它和上一章的「工具调用」有一个关键区别：

- 上一章：模型发出调用意图 → **你执行真正的函数** → 回填结果 → 再问一次。
- 本节：模型发出调用意图 → **你只取它的 `input` 当作结构化数据** → 结束。

这里的工具是一个**借用的通道** —— 用来把输出收窄成对象，函数体从头到尾不存在。所以本节不需要回填 `tool_result`，不存在幂等问题，重试也是干净的操作。

`tool_result` 是标准工具调用里的一个消息块，形状大致是 `{"role": "user", "content": [{"type": "tool_result", "tool_use_id": "...", "content": "..."}]}` —— **它的作用是把「你执行函数得到的返回值」送回给模型**。本节没有函数可执行，所以这个块永远不会出现；模型给出 `tool_use` 之后，这次对话就结束了。区分这一点很重要：一旦你把它和真正的工具调用混起来，就会开始怀疑「不回填结果是不是不合规」，而实际上这里根本没有第二个回合。

这个区别值得单独记住，因为两种用法在代码上几乎一模一样，语义上却完全不同：**一个是「让模型动手」，一个是「让模型交一份填好的表」。**

## 完整可运行代码

```python
# retry_with_feedback.py
"""校验失败之后，把错误本身变成下一次的输入。"""

from pydantic import BaseModel, Field, ValidationError

MAX_ATTEMPTS = 3


class Refund(BaseModel):
    amount: int = Field(multiple_of=100)
    reason: str


def extract_refund(client, model: str, ask: str, schema: dict):
    """返回校验过的 Refund；上限内仍失败时返回 None，调用方走降级。"""
    messages = [{"role": "user", "content": ask}]

    for attempt in range(1, MAX_ATTEMPTS + 1):
        resp = client.messages.create(
            model=model,
            max_tokens=2000,
            thinking={"type": "disabled"},   # 强制工具调用的前提，见本章第 1 节
            messages=messages,
            tools=[{
                "name": "save_refund",
                "description": "保存报销单",
                "input_schema": schema,
            }],
            tool_choice={"type": "tool", "name": "save_refund"},
        )
        block = next(b for b in resp.content if b.type == "tool_use")

        try:
            return Refund.model_validate(block.input)
        except ValidationError as exc:
            if attempt == MAX_ATTEMPTS:
                break
            # 两个要点：
            #   1. 把 assistant 的 content 原样带回（消息历史必须完整）
            #   2. 用 exc.json() 而不是 str(exc) —— 前者机器可读，
            #      后者带换行、缩进和 pydantic 文档链接，是给人看的
            messages += [
                {"role": "assistant", "content": resp.content},
                {
                    "role": "user",
                    "content": (
                        "上一次提交被校验器退回了。错误明细（JSON）：\n"
                        + exc.json(include_url=False)
                        + "\n请只修正这些问题，然后重新调用工具。"
                    ),
                },
            ]

    return None   # 重试耗尽，交给降级路径


if __name__ == "__main__":
    # 真实报错原文（Pydantic 2.9）：注意它包含两类信息 ——
    # 机器可读的 loc / msg / input，以及给人看的文档链接
    try:
        Refund.model_validate({"amount": 1234, "reason": "打车"})
    except ValidationError as exc:
        print("str(exc) 给模型看太长：")
        print(str(exc))
        print()
        print("exc.json() 才是该发回去的形式：")
        print(exc.json(include_url=False))
```

```text
str(exc) 给模型看太长：
1 validation error for Refund
amount
  Input should be a multiple of 100 [type=multiple_of, input_value=1234, input_type=int]
    For further information visit https://errors.pydantic.dev/2.9/v/multiple_of

exc.json() 才是该发回去的形式：
[{"type":"multiple_of","loc":["amount"],"msg":"Input should be a multiple of 100","input":1234,"ctx":{"multiple_of":100}}]
```

> **实跑状态**：报错原文与 `exc.json()` 的输出均在本地 Python 3.10 + Pydantic 2.9.2 上实跑得到。上面的 SDK 调用片段与实测采集脚本字段一致，但未在官方端点跑过。

## 重试耗尽之后：降级分支与埋点

上面那个 `extract_refund` 只回答了「怎么重试」，没回答**重试耗尽之后那一步**。而那张降级表的三行选择，落到代码里就是三个不同的返回值 —— 它们必须在写代码之前定下来。

先定义这套系统的**产物**，也就是无论成功失败都会产生的那条记录（**构造示例，未实跑**）：

```json
{
  "request_id": "req_8f21",
  "task": "extract_refund",
  "attempts": 3,
  "first_round_ok": false,
  "error_type": "business_rule",
  "action": "human_queue",
  "payload": {"raw_input": "...", "last_report": [{"type": "business_rule", "field": "end_date", "msg": "end_date 早于 start_date"}]}
}
```

它的字段就是埋点的四件事：**试了几次**（`attempts`）、**首轮是否合格**（`first_round_ok`）、**错在哪一类**（`error_type`）、**最后走去哪**（`action`）。`error_type` 的取值与上面那张表一一对应：`shape` / `constraint` / `information` / `business_rule`。

```python
# degrade.py
"""重试耗尽之后：降级分支 + 埋点。

用假 client 演示控制流：三个字段的埋点、以及三种降级分支各自的载荷。
本地 Python 3.10 + Pydantic 2.9.2 上跑通（未连官方端点）。
"""

import json
import uuid
from typing import Optional

from pydantic import BaseModel, Field, ValidationError


class Refund(BaseModel):
    amount: int = Field(multiple_of=100)
    reason: str


def classify(exc: ValidationError) -> str:
    """把 Pydantic 的错误类型映射到四类之一 —— 分类决定走哪条降级分支。"""
    kinds = {e["type"] for e in exc.errors()}
    if "multiple_of" in kinds or "greater_than" in kinds:
        return "constraint"
    if kinds & {"missing", "string_type", "int_type"}:
        return "shape"
    return "business_rule"


def emit(event: dict) -> None:
    """埋点：每次尝试都落一行。真实系统里这行进日志或时序库。"""
    print("[metric] " + json.dumps(event, ensure_ascii=False))


def run(ask: str, extract) -> dict:
    """包住 extract：负责埋点与降级，extract 只管重试。

    extract 是上一段代码里的函数，返回 (Refund | None, 首轮是否合格, 最后一次的错误类型)。
    """
    request_id = "req_" + uuid.uuid4().hex[:4]
    result, first_ok, error_type = extract(ask)
    attempts = 1 if first_ok else 3          # 简化：没首轮通过就按打满上限记

    if result is not None:
        record = {"request_id": request_id, "attempts": attempts,
                  "first_round_ok": first_ok, "error_type": None,
                  "action": "store", "payload": result.model_dump()}
    else:
        # 三种降级分支：不可逆动作进人工队列，可容忍误差给保守默认值，
        # 大 schema 里只有个别字段过不去就拆小重试。
        action = "human_queue" if error_type in ("business_rule", "information") else "conservative_default"
        record = {"request_id": request_id, "attempts": attempts,
                  "first_round_ok": first_ok, "error_type": error_type,
                  "action": action,
                  "payload": {"raw_input": ask, "last_report": "见上一次尝试的 exc.json()"}}

    # 关键：无论成功失败都发同一条事件，只是 action 不同
    emit({k: record[k] for k in ("request_id", "attempts", "first_round_ok", "error_type", "action")})
    if record["action"] == "human_queue":
        # 入队载荷必须自带原始输入 —— 处理的人不该去翻日志找它
        print("[queue] 入队:", json.dumps(record["payload"], ensure_ascii=False))
    return record


if __name__ == "__main__":
    # 假 client：模拟「首轮越界、第二轮修正」与「三轮都做不到」两种情况
    def fake_extract_fixed(ask: str):
        return Refund(amount=1200, reason=ask), False, None

    def fake_extract_failed(ask: str):
        return None, False, "business_rule"

    for label, extract in (("两轮内修正", fake_extract_fixed),
                           ("重试耗尽", fake_extract_failed)):
        print("==", label)
        print("  ->", json.dumps(run("打车费 1234 元", extract), ensure_ascii=False))
```

`classify` 这个小函数值得单独看一眼 —— 它把「Pydantic 报了什么错」翻译成「走哪条降级分支」：

```text
amount=1234（constraint）        -> constraint
reason 缺失（shape）             -> shape
end_date 早于 start_date（业务）  -> business_rule
```

（分类结果上示：本地 Python 3.10 + Pydantic 2.9.2 实跑得到；分支动作是上表的直接翻译。）

这段代码里有两个设计决定值得单独说：

1. **降级分支由 `error_type` 决定，不由调用方临时判断。** 「信息缺失」与「业务规则冲突」进人工队列，「约束越界」给保守默认值 —— 因为后者还能事后补救，而前者不能。
2. **成功与失败发同一条事件。** 只在失败时埋点，你就永远算不出首轮合格率（分母丢了）。下一小节会说明它是这套系统最有价值的指标。

**入队载荷里必须带原始输入。** 处理队列的人不应该被迫去翻日志、把上下文拼回来 —— 那是把成本从系统转嫁给人，而人工队列的单价是这套链路里最高的。

最后一条纪律：**降级路径也要有测试。** 触发它最简单的方式是把上限设成 0（`MAX_ATTEMPTS = 0`），跑一遍主流程，确认入队载荷与埋点事件都正确 —— 否则这条分支只有在上线后第一次真出事时才会被执行。

## 重试不是万能的：降级路径必须在设计阶段定

上面「带错误信息」那一组是 6/6 —— 但另一组同样设置的运行里是 4/6。**总会有修不好的情况。** 重试耗尽之后只有三种选择，它们必须在写代码之前就定下来，因为临时补的兜底通常既没有测试覆盖也没人知道它存在：

| 降级方式 | 代价 | 适用场景 |
|---|---|---|
| 进人工队列 | 需要有人处理 | 金额、退款、下单这类不可逆动作 |
| 返回保守默认值并标注不确定 | 可能不准 | 推荐位、标签这类可容忍误差的 |
| 拆小重试（先只抽一个字段） | 多一轮成本 | 大 schema 里只有一两个字段过不去 |

最不能选的是第四种：**把异常抛给用户。**

## 重试的成本要算进去

每次重试都是一次完整往返，而且输入更长 —— 它是「原任务 + 上一次的输出 + 错误明细」，比首次请求更贵。第 1 章的算式在这里同样成立：多轮对话的累计输入是 O(N²)，因为每一轮都要把之前的内容重新发一遍。

所以在设计阶段就要定两件事：**上限设几次**（2 到 3 次是常见选择），以及**哪些失败值得重试**（上一小节）。一个没有上限的重试循环，在模型确实做不到的任务上会稳定地把钱烧完 —— 而它在监控面板上看起来只是一直在「努力重试」。

还有一个不花钱的收益：**把首轮合格率记下来。**

重试次数的分布是这套系统最有价值的指标之一。首轮合格率很低（比如 40%），说明你的字段说明或 schema 本身有问题 —— 该去改 prompt，而不是让重试来兜。首轮合格率高、偶发重试，那才是健康状态。只统计「最终成功率」会把这两件事混成一个数字，让你永远看不到前一种问题。

## 常见坑

**校验失败就原样重发。** 实测 0/6 修正。重试动作本身不携带信息，等于再掷一次骰子。

**只说「没通过校验，请重试」。** 同样 0/6。模型需要知道**具体哪个字段、期望什么、实际是什么**。

**把 `str(exc)` 直接发回去。** 它带换行、缩进和文档链接，是给人看的。用 `exc.json()` 这类结构化形式，模型才抓得住重点。

**不设重试上限。** 每次重试都是一次完整往返，在模型确实做不到的任务上会持续烧钱。

**没想好降级路径。** 上线后才发现的兜底分支通常不被测试覆盖；而在 `temperature=1` 下，失败是必然会出现的一类事件，不是异常事件。
