下面三条记录，格式全部合法、全部通过了 JSON 解析、全部通过了 schema 校验：

```json
{"order_id": "A-1001", "status": "处理中"}
{"start_date": "2026-10-15", "end_date": "2026-10-01"}
{"issue_type": "refund"}
```

第一条的状态是编的，第二条是一个时间上不可能的区间，第三条是模型在两个都不对的选项里挑了一个。

**它们的共同点是：没有任何一层会报错。** 这就是这一节要处理的问题 —— schema 能挡住的那类形状错误，恰恰是最容易被发现的一类；而上面这三种会一路流进数据库。

## 实测一：必填字段会逼出幻觉

给一段对话，里面**从头到尾没有出现过订单状态**。然后换三种做法：

| 做法 | schema / 输入 | 5 次输出 |
|---|---|---|
| A 让模型自己判断状态 | `required: [order_id, status]` | `"处理中"` ×5 |
| B 只让它抽取订单号 | `required: [order_id]` | `"A-1001"` ×5 |
| C 代码查库后把事实注入，再让它填 | A 的 schema + 「已知事实：状态是已取消」 | `"已取消"` ×5 |

（实测数据，`deepseek-flash`，2026-10-08。）

A 组值得多看一会儿：模型**没有任何犹豫**，5 次给出同一个「处理中」，语气和它给真实答案时一模一样。你在日志里只看到 `{"status": "处理中"}`，没有任何办法分辨它是真是假。

C 组同样干净：**把事实作为输入给它，它会原样采用。** 所以模型的问题从来不是「不听话」，而是**你在让它回答一个它无从知道的问题**。

## 实测二：跨字段规则，说了就修，不说就照抄

同一份**本身就自相矛盾**的输入：「活动从 2026-10-15 开始，2026-10-01 结束。」

| prompt 里有没有要求归一化 | 5 次输出 |
|---|---|
| 没说 | `2026-10-15 → 2026-10-01` ×5，**区间不可满足** |
| 说了「若结束早于开始请调换」 | `2026-10-01 → 2026-10-15` ×5，已合法 |

（实测数据，`deepseek-flash`，2026-10-08。）

模型两个字段都填对了 —— 它忠实地**照抄**了输入里的矛盾。这不是模型犯的错，是**需求里没写这条规则**。JSON Schema 表达不了「end 必须不早于 start」（跨字段比较不在它的能力范围内），所以这条规则只能在业务层拦，而业务层拦不拦，取决于你有没有想到它。

## 实测三：enum 没有正确答案时

这一条在第 2 节已经量过：`enum: ["refund", "repair"]` 遇到两类都不是的工单，6/6 静默选了错的；补上 `"other"` 之后，6/6 正确。

再加上第 2 节的 `currency` —— 原文里没说币种，schema 里 `enum: ["CNY", "USD"]` 硬要一个，模型就填了「CNY」。**一个带 enum 的必填字段，等于在信息缺失时强制模型编一个。**

**第一条，也是最重要的一条：把事实来源移出模型。** 不要问「这个订单的状态是什么」，而是让它输出 `order_id`，由你的代码去数据库查状态、再拼进最终结果。模型负责它擅长的事（从一段散乱文本里认出标识符），事实负责在它能被验证的地方产生。上面 A 组与 C 组的对照就是这条规则的效果。

**第二条：跨字段与业务规则集中在一处实现。** 解析通过之后立刻跑一遍业务校验（第 2 节的三层防线里的第三层）。放在一处而不是散落各调用点，是因为这类规则最容易在不同代码路径上被漏掉。

**第三条：每个 enum 留一个 `other` 或 `unknown`。** 让「信息不足」这个真实状态有地方落脚。没有出口时，你得到的不是报错，而是一个看起来正常的错误值。

## 完整可运行代码：抽取与事实分离

```python
# extract_then_enrich.py
"""模型只做抽取，事实由代码注入。

反例（本节实测 5/5 编造）：把 status 放进 schema 让模型填。
正例：schema 里根本没有 status 这个字段。
"""

from typing import Type

from pydantic import BaseModel


class Extracted(BaseModel):
    """模型唯一负责的事：从对话里认出订单号。"""

    order_id: str


def call_tool(client, model: str, ask: str, schema_cls: Type[BaseModel], tool_name: str):
    """借工具通道把输出收窄成对象。

    注意：这里**不执行任何业务函数**，只取模型的 input 当数据。
    """
    resp = client.messages.create(
        model=model,
        max_tokens=1000,
        thinking={"type": "disabled"},          # 强制工具调用的前提
        messages=[{"role": "user", "content": ask}],
        tools=[
            {
                "name": tool_name,
                "description": "保存从对话里抽取到的字段",
                "input_schema": schema_cls.model_json_schema(),
            }
        ],
        tool_choice={"type": "tool", "name": tool_name},
    )
    block = next(b for b in resp.content if b.type == "tool_use")
    return schema_cls.model_validate(block.input)


def build_ticket(client, model: str, conversation: str, orders: dict):
    """最终结果 = 模型抽取的字段 + 代码查到的**事实**。"""
    extracted = call_tool(
        client, model, conversation, Extracted, "save_order_id"
    )

    status = orders.get(extracted.order_id)
    if status is None:
        # 查不到就如实说查不到 —— 不要让模型替数据库回答
        return {
            "order_id": extracted.order_id,
            "status": None,
            "status_source": "orders:not_found",
        }

    return {
        "order_id": extracted.order_id,
        "status": status,
        "status_source": "orders",      # 审计用：这条事实从哪来
    }


if __name__ == "__main__":
    # 用假 client 演示结构：模型只被问到 order_id
    print(build_ticket(None, "m", "订单 A-1001 怎么样了", {"A-1001": "已取消"}))
```

```text
{'order_id': 'A-1001', 'status': '已取消', 'status_source': 'orders'}
```

> **实跑状态**：`Extracted.model_json_schema()` 与 `build_ticket` 的拼装逻辑在本地 Python 3.10 + Pydantic 2.9.2 上跑通（用假 client 注入抽取结果）；`client.messages.create` 那一段与实测采集脚本字段一致，未在官方端点跑过。

注意返回结构里那个 `status_source` 字段。它看起来是多余的，但它让「这条状态是查出来的还是编出来的」在数据结构里可分辨 —— **这是把「不确定」显式化，而不是把它藏进一个看起来正常的字符串里。**

## 一个没有报错的「错误案例」

本节最该记住的案例不是一个 400，而是一个**静默通过**的：

```json
{"start_date": "2026-10-15", "end_date": "2026-10-01"}
```

它通过了 `type: string` 校验，通过了 `format: date`（而第 2 节实测 `format` 本来也不生效），通过了必填检查，被顺利写进库。真正发现它的时候，是某个下游报表算出了一个负的时长。

**排查这类问题的方向不该是「怎么让 schema 更严」，而是「这条规则到底该由谁保证」。** 时间区间的关系不该由模型或 schema 保证，它属于业务层 —— 而这正是本节三条修法里第二条的位置。

## 还有一类字段：能算的不要让模型算

「模型不擅长算术」也是一句流传很广的话。在本章的实验里它同样没有复现：第 1 节的采购单任务要求模型自己算总价（`100 × 12.50 + 5 × 899.00 = 5745`），三个方案合计 23 次有效运行里，一次都没算错。

但正确的结论不是「模型算得对，所以可以让它算」，而是：**算术是可验证的，把它委托给一个概率模型没有收益。**

- 让模型算：答案可能对，但除了重算一遍，**你没有别的办法确认它对不对** —— 而重算的成本比让它算更低。
- 让代码算：输入是模型抽出来的原始数字，输出是确定的。

所以字段归属应该按「能不能被验证」来分，而不是按「模型做得好不好」来分：

| 字段类型 | 谁来产生 | 理由 |
|---|---|---|
| 从文本里识别的标识符、日期、人名 | 模型 | 它的强项，且可回原文核对 |
| 数据库里已有的值（状态、余额、库存） | 代码 | 可验证；模型无从知道 |
| 计算与聚合（总价、时长、计数） | 代码 | 可验证；成本更低 |
| 分类、摘要、归一化文本 | 模型 | 本来就没有唯一正确答案 |
| 放行、金额、权限这类不可逆判断 | 代码 + 明确规则 | 出错代价最高，规则必须可审计 |

这张表比任何「模型能力清单」都稳定 —— 因为**它判断的是谁负责保证正确，而不是谁更聪明**，而后者会随模型版本变化。

## 常见坑

**让模型回答它无从知道的事。** 实测 5/5 编造「处理中」，且语气与真实答案无异。这不是模型不可靠，是任务设计的问题。

**以为 schema 校验通过就等于内容可用。** schema 管形状。本节三条记录全部通过了校验，全部是错的。

**把跨字段规则交给 schema。** JSON Schema 表达不了 `end >= start` 这类比较。它能表达的部分（第 2 节实测）也不一定被强制。

**enum 不带 other 出口。** 6/6 静默选错。信息不足时，模型需要一个能被表达的「我不知道」。

**不记录事实来源。** 一旦编造的值和查到的值在库里长得一样，你就永远失去了区分它们的能力。`status_source` 这种字段很便宜，但它决定了你事后能不能审计。
