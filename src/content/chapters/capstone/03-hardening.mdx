骨架跑通了（六条用例全过）。这一节做加固 —— 而加固的正确做法不是"再想想还缺什么"，是**拿一份清单逐条过**。

理由：凭记忆想一定会漏，而漏掉的那些恰好是"平时看不出问题"的那一类（第 15 到 20 章反复出现的主题）。

## 清单从哪来

清单就是第 15 到 20 章各自的收口结论。逐章对照：

| 章 | 检查项 | 这个项目的状态 |
|---|---|---|

| 15 评估 | 用例能否断言结果，轨迹能否定位步骤？ | ✅ 六条 smoke 用例；轨迹记录 step/tool/result，审批字段仍有缺口 |
| 15 评估 | 这六条固定冒烟用例覆盖了哪些可断言行为？ | ⚠️ 现在 6/6 只表示这六个样例通过；不能外推总体能力、覆盖率或上线质量 |

## 这张表怎么读

**右列采用四种项目状态：✅ / ⚠️ / ❌ / SKIP。** 它们描述当前这份教学示例，不是通用产品验收标准；尤其要分清有条件通过、缺口和基于范围跳过。

具体说，评测行的 ⚠️ 是**范围提示**：六条用例全过只能说明当前版本通过了这六个断言；它不能证明用例代表真实输入、覆盖全部失败模式，或足以比较两个版本。若目标是判断一般质量或版本差异，需要定义代表性指标、建立基线，并使用适合该问题的独立/留出样本；不能仅凭 6/6 宣称评测集已经到达能力天花板。

所以加固阶段要做的事，有一类是补实现或补流程（❌），另一类是记录当前证据的边界（⚠️）。边界说明能校准信心，但本身不补控制，也不能代替风险评估。

## 两项明确不在这个教学示例里实现

加固不是把所有 ❌ 都补上。下面两项基于本例当前范围跳过；如果接入真实模型或加入缓存，这个决定就要重审。

| 项 | 为什么不补 |
|---|---|
| 凭证不进上下文 | 本例不调用真实模型，不配置 provider 凭证 |
| 缓存命中率 | 本例没有缓存，当前没有缓存命中可观测 |

示例代码仍缺少 `VERSION`，自动检查会把它报告为缺口；这可以作为教学阶段明确记录的待办，但在形成正式发布单元前需要由负责人决定补齐还是接受风险。**"明确不做"和"忘了做"的区别，是交付文档必须写清楚的事项**（第 4 节）。

## 一个适用于本例的排期草案

以下只是把风险、实现依赖和改动范围放在一起讨论的本地草案，不是普遍优先级，也不是经过对照实验验证的收益排序：

1. **先明确工具调用的主体授权与对象范围**，并把审批目标、影响范围和决策理由展示给审批人；单补一个返回字段不足以构成安全控制。
2. **治理轨迹中的输入/输出数据**，只保留排障所需字段并处理敏感信息；来源标注也要与工具身份、请求和结果关联。
3. **形成发布单元时补版本标识**，让部署、配置和证据能指向同一版本；当前单文件练习尚未实现它。
4. **定义并测试降级行为**，先明确哪些状态算不可用、哪些结果可以安全返回，再改调用流程。

实际顺序应结合最坏影响、暴露面、授权边界、实现依赖、修复成本和验证证据决定；本例没有测量过这些任务的收益或风险下降幅度。

最后补一个方向相反的风险。加固做过头有三种表现：

**一、补了范围外的项目。** 比如这个脚本没有缓存却加缓存命中率监控，会引入当前不存在的复杂度；若将来接入 provider 缓存，再按真实需求补指标。
**二、为不存在的负载优化。** 骨架阶段没有真实流量，性能优化应先有负载假设和测量目标。
**三、为了让通过率低于 100% 而故意加难题。** 这会把分数当成目标。正确做法是先确认评测集代表的用户任务与失败模式，再按目标补充有意义的用例，并把开发集和用于版本比较的留出集区分开。

本例的六条固定 smoke case 全通过是一个有限结果；是否需要更多用例取决于这个练习要支持什么决策。不能为追求"非满分"而改题，也不能拿窄覆盖的 6/6 当作一般能力或发布准备度。

## 一个具体的判断：什么时候算完成了清单审查

上面这张清单有 14 项。逐条登记的价值在于让负责人知道当前状态、证据和剩余风险，不在于让所有项机械变绿。

**以下只定义本节审查完成条件，不构成生产就绪判据：**

1. **每项都有状态和依据**（✅ / ⚠️ / ❌ / SKIP）；自动项有可重复检查，人工项有责任人与复查日期。
2. **每个 ❌ 都有处置决定**（排期、接受风险或限定范围），并注明批准者与条件。
3. **每个 ⚠️ 都写明证据边界**，不能把声明当测试、把样例结果当一般能力。
4. **范围外的 SKIP 有重审触发条件**。

这些条件说明清单审查过程没有悬空项。生产发布还需要按风险建立目标环境验证、权限/数据控制、故障恢复和由风险所有者作出的剩余风险接受。



## 一个反过来的检查：加固是不是在拖延\n\n最后补一个反面。加固清单给了"逐条过"这个动作，而它也可能变成一种逃避 —— **用"还在加固"来推迟交付。**

三个信号说明加固变成了拖延：

- **同一项反复来回**：说明这一项其实需要重做设计，不是在加固
- **补的是范围外的项**：那说明范围表没有约束力
- **没有一个明确的停止条件**：那就是在等"感觉够了"

第三条对治方式就是本节开头那三条判据 —— **它们把"够了"变成一个可检查的状态**，而不是一种感觉。

这也和第 2 节那条"跑通的判据"是同一个思路：**每个阶段都要有一个可以断言的结束条件**，否则阶段之间就没有边界，项目也会失去节奏。
## 完整可运行代码

下面这段代码把上面清单分成三组：能自动检查的读取当前项目值并执行样例，需判断的事项登记为人工声明，当前范围外的项目明确跳过。人工项里的 owner 与复核日期是待填写模板，不是实际负责人或已经排定的日期。跑之前把第 2 节的骨架保存为同目录的 `capstone_agent.py`。

```python
"""加固清单：能自动检查的写成断言，检查不了的保留人工声明并标注复核人。

运行前把第 2 节的骨架保存为同目录的 capstone_agent.py。
实跑状态：2026-10-20；本地合成代码检查，不调用真实模型或服务。
"""
import capstone_agent as agent
from capstone_agent import POLICY, REGISTRY, APPROVALS, TRACE

ALLOWED_TOOLS = {"get_order", "get_policy", "send_reply"}


def case_passes(case):
    try:
        case()
        return True
    except Exception:
        return False


def auto_checks():
    """能自动检查的项 —— 每条是一个 (检查项, 谓词)。

    谓词为真 = 通过；为假或抛异常都算检出。它不是「声明」，是真去读项目里的值。
    """
    # 先跑一条会要求审批的路径：否则 APPROVALS 是空列表，而 all([]) 恒为真 ——
    # 空集合让断言「看起来通过」，这正是自动检查最容易骗自己的地方。
    agent.reset()
    agent.run([("send_reply", {"to": "check@example.com", "body": "probe"})])
    return [
        ("策略对未列入 allowlist 的工具默认拒绝", POLICY["default"] == "deny"),
        ("策略白名单与注册表一致", set(POLICY["allow"]) == set(REGISTRY)),
        ("工具集与范围表一致", set(REGISTRY) == ALLOWED_TOOLS),
        ("轨迹包含步骤和工具定位字段", any("step" in event and "tool" in event for event in TRACE)),
        ("审批请求包含明确目标与影响范围", bool(APPROVALS) and all({"target", "impact_scope"} <= a.keys() for a in APPROVALS)),
        ("有版本号常量", hasattr(agent, "VERSION")),
        ("六条固定冒烟用例通过", all(case_passes(case) for case in agent.CASES)),
        ("任务预算上限会停止超限循环", case_passes(agent.case_5_budget_stops_loop)),
        ("重复批准路径保持幂等", case_passes(agent.case_3_approved_then_duplicate_is_idempotent)),
    ]


# 不能自动检查的项：保留人工声明，但每条必须带 owner 与复核日期
MANUAL = [
    ("15 评估", "评测集代表性与版本差异能力", "warn", "6 条仅覆盖既定断言", "owner=<负责团队>", "review=YYYY-MM-DD"),
    ("17 安全", "真实结果回流的来源/信任边界", "warn", "本例未实现真实模型回合", "owner=<负责团队>", "review=YYYY-MM-DD"),
    ("19 协作", "审批触发策略不只看 reversible", "warn", "需结合授权和影响范围", "owner=<负责团队>", "review=YYYY-MM-DD"),
    ("20 部署", "降级路径", "gap", "未定义不可用状态", "owner=<负责团队>", "review=YYYY-MM-DD"),
    ("15/16 观测", "轨迹敏感字段治理", "gap", "示例记录原始参数/结果", "owner=<负责团队>", "review=YYYY-MM-DD"),
]
SKIP = [
    ("16 沙箱", "凭证不进上下文", "本例不调用真实模型"),
    ("18 成本", "缓存命中率可观测", "本例不使用缓存"),
]


if __name__ == "__main__":
    print("=== 一、自动检查（本地代码与样例）===")
    for name, ok in auto_checks():
        print("  %s %s" % ("✅" if ok else "❌ 缺口", name))
    print()
    print("=== 二、人工待办（登记不等于验证通过）===")
    for ch, item, st, note, owner, review in MANUAL:
        print("  %-5s %-9s %-20s %-14s %s %s" % (st, ch, item, note, owner, review))
    for ch, item, note in SKIP:
        print("  %-5s %-9s %-20s %s" % ("SKIP", ch, item, note))
    print()
    print("  自动检查、人工登记与范围跳过是三类记录；通过本脚本不等于生产就绪。")
    print("  如果某条自动检查必须靠改常量才能变绿，说明清单和代码已经脱钩。")
```


## 三组检查怎么用，以及它们会怎么坏

表格中的 14 项是审查主题数，不等于脚本打印的检查行数：其中「策略默认拒绝且与本例清单一致」这一项被拆成默认值、策略与注册表一致、工具集与范围表一致三条自动断言；另外两条分别是人工声明和范围跳过。因此自动检查 9 条、人工 5 条、跳过 2 条，共 16 条输出记录，对应表格的 14 个主题。

**自动检查也可能被写错。** 本例先执行一个会挂起审批的路径，确保 `APPROVALS` 有样本；谓词还应显式要求列表非空，再逐条检查字段。否则 `all([])` 会返回真，即使审批请求根本没有生成。即便通过，这个检查也只验证字段存在，不证明策略正确、审批人看懂或调用者有权限。

三个自查问题，对应三种坏法：

1. **它读到的是空集合吗？** 断言前先确认被测对象已产生（本节用一次 `run()` 触发审批）。
2. **它是在读常量，还是在读项目？** `CHECKLIST = [("权限默认拒绝", "ok", ...)]` 这种写法里，那个 `"ok"` 是人手写的字符串 —— 代码改了它不会变。真正的检查必须去读 `POLICY["default"]`。
3. **改坏代码它会红吗？** 把 `POLICY["default"]` 手动改成 `"allow"` 再跑一次：自动那一段应该变红。**如果必须改常量才能变绿，说明清单和代码已经脱钩。**

**人工登记的失败形态是「把声明当证据」。** 人工清单打印得再整齐也不是证据 —— 它只记录「谁承诺在什么时候复查」。所以它必须有 `owner` 和 `review` 两个字段，否则一条 gap 会无限期挂在表里，而看起来一切正常。**这正是本节开头那句「纸面清单不会自己更新」的正解：不是让它更新，而是把能自动化的部分真的自动化，剩下的老实标成"人工声明"。**

第一类里最值得自动化的仍然是**默认值** —— 它是结构性的（第 2 节说过），被改掉之后影响面很大，而一条断言的成本只有几行代码。
## 常见坑

- **凭记忆想还缺什么。** 用第 15-20 章的收口结论当清单 —— 凭记忆一定会漏掉"平时看不出问题"的那类。
- **把 ⚠️ 当成 ✅。** 6 条固定断言全过仅覆盖这些场景；不代表一般质量，也不能替代代表性评测。
- **为了消掉 ⚠️ 而硬加难题。** 正确反应是"知道它的含义"，不是改数字。
- **补范围外的项。** 没有缓存的系统加缓存监控，是引入不存在的复杂度。
- **不区分"缺失"和"明确不做"。** 后者要写进交付文档并给出理由。
- **把某一种排序公式当定律。** 应按最坏影响、授权范围、修复依赖和可验证的风险下降来定序；本例草案不是普遍规则。
