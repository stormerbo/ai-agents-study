骨架跑通了（六条用例全过）。这一节做加固 —— 而加固的正确做法不是"再想想还缺什么"，是**拿一份清单逐条过**。

理由：凭记忆想一定会漏，而漏掉的那些恰好是"平时看不出问题"的那一类（第 15 到 20 章反复出现的主题）。

## 清单从哪来

清单就是第 15 到 20 章各自的收口结论。逐章对照：

## 这张表怎么读

**注意右列不是"已完成/未完成"，而是三档：✅ / ⚠️ / ❌。** 中间那一档最容易被当成已完成。

具体说，⚠️ 那一行（评测集通过率 6/6）是一个**陷阱**：六条用例全过看起来很好，但按照第 15 章的结论 —— **全对的评测集测不出改进**。也就是说，如果后面改坏了某一条，你能发现；但如果只是让它变差了一点，这六条测不出来。

所以加固阶段要做的事，有一类是"补充"（❌ 那些），另一类是"意识到它的边界"（⚠️ 那些）。**后者不产生代码，但它决定了你对这个系统的信心该有多少。**

## 三个明确不做加固的项，以及理由

加固不是把所有 ❌ 都补上 —— 因为有些项在**这个项目的范围内**不值得补。

| 项 | 为什么不补 |
|---|---|
| 凭证不进上下文 | 这个项目不调真实模型，没有凭证 |
| 缓存命中率 | 没有缓存 —— 加了反而是复杂度 |
| 版本化单元 | 骨架是单文件脚本，交付时说明这个缺口（第 4 节） |

**"明确不做"和"忘了做"的区别，是交付文档里必须写清楚的第一件事**（第 1 节那张范围表的用法之二）。

## 一个具体的加固顺序

剩下的 ❌ 里，按"改动半径"从小到大排：

1. **审批补上影响范围**（改一个返回值，不动流程）
2. **工具返回值加来源标注**（第 17 章，改工具包装层）
3. **加版本号**（改发布流程，不动代码）
4. **加降级路径**（改调用方流程，半径最大）

顺序的道理是：**先做改动半径小的，因为它们的收益确定、风险低。** 而第四项（降级）半径最大，它值得单独排期 —— 而且它有一个前置条件：得先有"不可用"这个状态的定义。

## 一个反过来的检查：加固也会做过头

最后补一个方向相反的风险。加固做过头有三种表现：

**一、补了范围外的项目。** 比如这个项目没有缓存却加了缓存命中率监控 —— 那是引入了一个不存在的复杂度。
**二、为不存在的负载优化。** 骨架阶段没有真实流量，性能优化都是猜测。
**三、把 ⚠️ 当成 ❌ 去补。** 比如为了"让评测集通过率不是 100%"而故意加难题 —— 那是错的。正确的做法是**意识到它的边界**，然后在范围外的地方补评测（第 2 节那张范围表：多类型任务意味着多套评测，那是明确不做的）。

第三种最容易踩。**"通过率太高"的正确反应是知道它的含义，不是立刻去改数字。** 这个项目只有一类任务，所以六条用例全过是合理的 —— 而它测不出的那部分，应该由"范围表 + 交付文档"来交代，不是靠硬塞几条难题。


## 一个具体的判断：什么时候算"加固够了"

上面那张清单里有 13 项。全做完不现实，而"逐条过"的价值也不在于全做完 —— 在于**你知道哪一条没做、为什么**。

所以"加固够了"的判据是三条：

1. **每一条都有状态**（✅ / ⚠️ / ❌ / ⏭️），没有"没想过"
2. **每一条 ❌ 都有理由**（要么排期，要么明确不做）
3. **每一条 ⚠️ 都被说清楚了边界**

第一条是完备性，第二、三条是**诚实性**。而三条里最容易被跳过的是第三条 —— 因为 ⚠️ 看起来像"已经做了"。

举个具体的：这个项目的"轨迹能定位到具体哪一步"是 ⚠️，因为审批那一环缺影响范围。**写成 ✅ 也不会有人发现** —— 轨迹确实存在、确实能定位。而它的边界是：审批那一步的信息不够，所以事后复盘时你看不出"当时为什么要批这个"。

**把这个边界写出来，比补全它更重要** —— 因为补全会花时间，而写出来只要一行。而它的实际收益是：万一将来出问题，你知道该往哪里看。

## 一个反过来的检查：加固是不是在拖延

最后补一个反面。加固清单给了"逐条过"这个动作，而它也可能变成一种逃避 —— **用"还在加固"来推迟交付。**

三个信号说明加固变成了拖延：

- **同一项反复来回**：说明这一项其实需要重做设计，不是在加固
- **补的是范围外的项**：那说明范围表没有约束力
- **没有一个明确的停止条件**：那就是在等"感觉够了"

第三条对治方式就是本节开头那三条判据 —— **它们把"够了"变成一个可检查的状态**，而不是一种感觉。

这也和第 2 节那条"跑通的判据"是同一个思路：**每个阶段都要有一个可以断言的结束条件**，否则阶段之间就没有边界，项目也会失去节奏。
## 完整可运行代码

下面这段代码把上面那张清单**拆成两段**：能自动检查的真去读项目里的值（不是声明），不能自动检查的保留人工声明，但每条必须带 owner 与复核日期。跑之前把第 2 节的骨架保存为同目录的 `capstone_agent.py`。

```python
"""加固清单：能自动检查的写成断言，检查不了的保留人工声明并标注复核人。

运行前把第 2 节的骨架保存为同目录的 capstone_agent.py。
实跑状态：2026-10-12（重写为真正的自动检查）。
"""
import capstone_agent as agent
from capstone_agent import POLICY, REGISTRY, APPROVALS

ALLOWED_TOOLS = {"get_order", "get_policy", "send_reply"}


def auto_checks():
    """能自动检查的项 —— 每条是一个 (检查项, 谓词)。

    谓词为真 = 通过；为假或抛异常都算检出。它不是「声明」，是真去读项目里的值。
    """
    # 先跑一条会要求审批的路径：否则 APPROVALS 是空列表，而 all([]) 恒为真 ——
    # 空集合让断言「看起来通过」，这正是自动检查最容易骗自己的地方。
    agent.reset()
    agent.run([("send_reply", {"to": "check@example.com", "body": "probe"})])
    return [
        ("权限默认拒绝", POLICY["default"] == "deny"),
        ("策略白名单与注册表一致", set(POLICY["allow"]) == set(REGISTRY)),
        ("工具集与范围表一致", set(REGISTRY) == ALLOWED_TOOLS),
        ("审批记录带影响范围", all("risks" in a for a in APPROVALS)),
        ("有版本号常量", hasattr(agent, "VERSION")),
    ]


# 不能自动检查的项：保留人工声明，但每条必须带 owner 与复核日期
MANUAL = [
    ("15 评估", "评测集会不会失效", "warn", "6/6 已是天花板", "owner=alice", "review=2026-11-01"),
    ("17 安全", "工具返回值标注来源", "gap", "没有做任何标注", "owner=alice", "review=2026-11-01"),
    ("19 协作", "审批展示三样信息", "gap", "只有「为什么」", "owner=bob", "review=2026-11-01"),
    ("20 部署", "版本化单元", "gap", "骨架阶段还没有", "owner=bob", "review=2026-11-01"),
    ("20 部署", "降级路径", "gap", "没有", "owner=bob", "review=2026-11-01"),
]
SKIP = [
    ("16 沙箱", "凭证不进上下文", "本项目不调真实模型，没有凭证"),
    ("18 成本", "缓存命中率可观测", "本项目不用缓存"),
]


if __name__ == "__main__":
    print("=== 一、自动检出（真执行，不是声明）===")
    for name, ok in auto_checks():
        print("  %s %s" % ("✅" if ok else "❌ 缺口", name))
    print()
    print("=== 二、人工声明（不是证据，只记录谁在什么时候复查）===")
    for ch, item, st, note, owner, review in MANUAL:
        print("  %-5s %-9s %-20s %-14s %s %s" % (st, ch, item, note, owner, review))
    for ch, item, note in SKIP:
        print("  %-5s %-9s %-20s %s" % ("SKIP", ch, item, note))
    print()
    print("  两段的区别：上面那段会在代码被改坏时自己变红；下面那段不会。")
    print("  如果某条自动检查必须靠改常量才能变绿，说明清单和代码已经脱钩。")
```


## 两段怎么用，以及它会怎么坏

**第一段的失败形态很隐蔽：它可能在骗你。** 上面代码里有一条注释值得重读 —— 跑检查之前先调了一次 `run()`，因为 `APPROVALS` 缺省是空的。空集合会让 `all(...)` 恒为真，于是「审批记录带影响范围」这条**看起来通过了**，而实际上一条审批记录都还没产生。**这是自动检查最常见的坏法：检查写对了，但检查的对象是空的。**

三个自查问题，对应三种坏法：

1. **它读到的是空集合吗？** 断言前先确认被测对象已产生（本节用一次 `run()` 触发审批）。
2. **它是在读常量，还是在读项目？** `CHECKLIST = [("权限默认拒绝", "ok", ...)]` 这种写法里，那个 `"ok"` 是人手写的字符串 —— 代码改了它不会变。真正的检查必须去读 `POLICY["default"]`。
3. **改坏代码它会红吗？** 把 `POLICY["default"]` 手动改成 `"allow"` 再跑一次：自动那一段应该变红。**如果必须改常量才能变绿，说明清单和代码已经脱钩。**

**第二段的失败形态是「把声明当证据」。** 人工清单打印得再整齐也不是证据 —— 它只记录「谁承诺在什么时候复查」。所以它必须有 `owner` 和 `review` 两个字段，否则一条 gap 会无限期挂在表里，而看起来一切正常。**这正是本节开头那句「纸面清单不会自己更新」的正解：不是让它更新，而是把能自动化的部分真的自动化，剩下的老实标成"人工声明"。**

第一类里最值得自动化的仍然是**默认值** —— 它是结构性的（第 2 节说过），被改掉之后影响面很大，而一条断言的成本只有几行代码。
## 常见坑

- **凭记忆想还缺什么。** 用第 15-20 章的收口结论当清单 —— 凭记忆一定会漏掉"平时看不出问题"的那类。
- **把 ⚠️ 当成 ✅。** 实测：6 条用例全过意味着它测不出细微退化 —— 那是边界，不是成绩。
- **为了消掉 ⚠️ 而硬加难题。** 正确反应是"知道它的含义"，不是改数字。
- **补范围外的项。** 没有缓存的系统加缓存监控，是引入不存在的复杂度。
- **不区分"缺失"和"明确不做"。** 后者要写进交付文档并给出理由。
- **按重要性排序。** 应按**改动半径**从小到大 —— 半径小的收益确定、风险低。
