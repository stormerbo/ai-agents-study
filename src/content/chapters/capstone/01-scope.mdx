这是综合项目的第一步。划范围不是把需求尽量砍小，而是写清楚：**系统负责什么、在哪些数据和权限下负责、用什么证据判断做到了，以及明确不承诺什么。** 没有这些边界，后面的实现、评测和验收就没有共同的判据。

本书综合项目使用一个售后订单场景：对合成订单 `A-1001` 查询订单状态和公开政策；如需通知，模型只提出 `send_notice`，宿主验证权限并等待审批，获批后把通知送到本地合成 sink；系统要保存任务与动作状态，支持中断、恢复和未知投递结果的对账。项目还分别有离线 fixture 与一个预先固定的有界在线 smoke 用例；每个 smoke 任务都有最大模型轮数和单轮输出 token 上限。**在线一次观察只验证这条路径在指定模型/配置下曾运行到什么状态，不等于质量率、生产就绪或真实通知成功。**

项目中的真实对象和非目标应该让读者一眼能分清：合成数据库、固定场景和本地 sink 是教学环境；真实客户数据、真实外部投递和对所有售后请求的普遍能力不在这个边界里。完整项目细节见 `examples/p5-agent-delivery/README.md`、`RUNBOOK.md` 和最终验收节。

## 为什么范围不能只写功能名

「支持订单咨询」还没有构成可验收的范围：哪类订单、读哪些数据、模型能提出哪些动作、谁能批准、失败时什么算未知，都没说。范围表要同时约束**业务目标、数据边界、操作权限和证据强度**。加入一个功能可能引入新输入、风险或运行责任，但代价取决于系统；不能仅凭功能名称断言每项都需要独立评测集或固定审批点。

工具请求输入量可以用测量估算，但要保留样本边界。第 4 章保存的 DeepSeek 兼容端点历史摘要（2026-10-08）报告 8/20/44/86 个候选时请求总 input 分别为 678/1326/2623/4945；它们不是单独的 schema token。两端差约 54.7 input token/新增工具，只描述该历史请求配置，且原始请求、逐次 usage 与缓存字段未归档。8 道选择题每档报告 8/8，也缺少原始题目和 scorer，不能推断其他模型/任务的准确率。第 18 章约 62% 是固定工具数与每轮重复输入假设下的本地计算，不是通用 API 账单占比。你的成本要按目标 endpoint 的 usage、缓存口径和调用轨迹实测。

## 一个具体的范围表

表中的 `in` 是本版必须完成的内容，`out` 是明确排除，`deferred` 是暂不承诺、达到触发条件再重开。它们不是「做/不做」的个人偏好清单：每项都写验收信号或重开条件。

| ID | 状态 | 范围条目 | 验收信号或重开条件 |
|---|---|---|---|
| **S1** | in | 一个固定的合成售后场景：订单 `A-1001` 查询，读取公开政策 | 输入、租户与合成数据版本固定；评测分别核对订单字段、政策依据和缺失数据处理 |
| **S2** | in | `lookup_order`、`search_policy`、`send_notice` 三个明确工具；通知只发往本地合成 sink，且需要宿主审批 | 从真实注册表生成模型可见 schema；未授权、参数变化或资源越界时不投递；回执未知时转对账 |
| **S3** | in | 任务、审批和动作有持久状态；中断/重启后恢复，未知外部效果不自动重试 | 对应单测、数据库集成与故障演练各自留证；不可用 fixture 替代真实数据库路径 |
| **S4** | in | 固定的离线评测与一个预先固定的在线 smoke 用例；每个 smoke 任务受最大模型轮数和单轮输出 token 上限约束，并记录模型、端点、prompt/tool hash、usage 与结论边界 | 离线结果仅证明 scorer/fixture 路径；每份在线报告只描述该次合成任务运行；最终发布还需独立验收 |
| **X1** | out | 真实客户数据、真实外部通知与生产写入 | 若目标环境需要，另行完成隐私、授权、接收端幂等、回执和对账设计后再立项 |
| **X2** | out | 任意售后意图、任意模型可调用工具、自由扩展的工具目录 | 新任务类型先定义身份/数据边界、可判定场景和回归证据；不得只增加 prompt 文案 |
| **X3** | out | 用一次 smoke 或公开 fixture 宣称通用准确率、安全性或生产就绪 | 需要冻结候选、代表性/盲测数据、独立评分和目标环境证据；现有 acceptance gate 未通过则保持未验证 |
| **D1** | deferred | 多区域 HA、大规模并发和跨 provider 的线上质量等价 | 当部署目标要求这些能力时重开范围，设计容量/故障/迁移测试；不能由本地 smoke 推断 |

`send_notice` 是一个有外部影响的动作，之所以纳入，是因为综合项目要演示**受控动作从提议、授权到回执对账**的整条边界；它不是因为“审批点越少越好”。审批要不要人工参与、展示什么、由谁授权，取决于动作影响、主体权限、资源和策略。把真实外部投递排除在本地示例之外，也不等于教学项目可以略过本地的授权与未知结果处理。

## 做范围决策时看什么

用四个维度比较候选项，而不是用单一口号决定做或不做：

1. **用户结果与失败代价**：目标用户要完成哪件事？错误结果影响谁、哪些资源，是否能撤销或补救？影响更大时，需把授权、人工确认、监测和恢复条件一并纳入范围。
2. **数据与身份边界**：输入来自哪里、包含什么敏感级别？系统依据哪个可信身份访问哪个资源？外部文档和工具返回都应作为数据处理；如果当前范围不含来源验证或授权，必须明确排除相关数据与操作。
3. **能力与验收证据**：能否写出可观察的通过、拒绝和未知状态？每个新增任务类型不必强制建设独立评测集，但要在现有数据里覆盖它的关键行为和风险；覆盖不足时，缩小目标或标为未验证。
4. **运行约束与退出条件**：预算、延迟、轮数、外部依赖、人工值守和恢复成本是什么？说明本次不做的理由、代替路径、负责人，以及什么变化会触发重新评估。

应用到本例：如果把本地 `send_notice` 改成真实外部投递，边界就不只是“多一个工具”，还会新增目标端授权、隐私、回执、幂等和未知状态对账，因此要重新评估，而不是从本地演示自动外推。反过来，扩展一个有明确权限且可由既有评测覆盖的只读字段，未必需要独立项目或一套全新数据集。

## 范围表怎么用

范围表不只是需求列表，而是后续实现、评测、交付和复盘共用的约定。每个 `in` 项要有通过条件，每个 `out` 项要说明风险或替代方案，每个 `deferred` 项要有重开条件。这样遇到新增需求时，讨论就不再停留在“看起来简单”，而能问它是否改变目标、数据、主体权限、失败代价或验收证据。

例如，新的请求想让系统“查一下订单后顺便给客户退款”。这不能简单并入 `send_notice`：退款会改变业务状态，授权主体、金额上限、重复请求处理、审批内容、接收方回执和恢复路径都不同。范围表可以先将它列为 out 或 deferred，并写清必须补齐的控制与验收，直到满足条件前不暴露退款工具。相反，如果只增加一种等价只读字段，应先检查现有的字段级授权、schema 和用例是否已经覆盖，不需要因为“新增功能”就假设工作量翻倍。

范围不是一次写定。每次改动前，对照版本化的范围表检查本次变更：新增了什么能力/数据/副作用？现有测试的判定目标变了吗？未覆盖风险是否变大？如有任何答案为“是”，要更新表、对应测试和验收证据，并由范围负责人记录为何接受。只更 prompt、代码或测试中的一处，会让团队对系统能力形成不一致的认识。

## 一个可以检查的范围约定

下面的示例把范围中三个工具的预期模式，与一个工具注册表比较。**示例接收的是运行时代码中的真实注册表**；P5 项目应从 `app/actions.py` 的 `REGISTRY` 生成映射，而不是另维护一份手写 `FOUND_TOOLS`。此脚本检查工具名与动作类别是否一致；它不检查数据访问策略、审批实现、sink 行为或生产授权，这些要由对应测试和运行证据覆盖。

## 范围表的失败形态

范围表最常见的失效，不是忘记了某个 feature，而是**实现已经跨过边界，表和测试却没有更新**。例如新增 `refund_order` 后，代码仍可运行，原有订单查询 fixture 也仍然通过；但授权主体、金额上限、审批语义和未知投递对账都不在原范围内。

应把范围项关联到可检查的来源：tool schema 由运行时注册表生成；权限与副作用有独立测试；任务/评测输入版本化；部署或在线 smoke 记录端点、版本、usage 和运行状态。自动门禁只能检查它实际读取的东西。一个只比较静态样例的脚本不能证明真实模型工具集、数据库访问控制或外部 sink 与范围一致。代码检查发现范围差异后，应要求人工更新范围和证据，不能悄悄自动把新功能列为已批准。

## 完整可运行代码

下面的 Python 例子验证「模型可见工具注册表是否和范围表匹配」，同时拒绝范围缺项、重复 ID、工具遗漏、额外工具和动作类别不一致。样例映射与 P5 项目当前注册表对齐；把它用于项目时，应从 `app/actions.py` 的真实 `REGISTRY` 动态生成 `IMPLEMENTED_TOOL_REGISTRY`，避免两处手写后一起漂移。该检查只看工具名与类别，数据、租户授权、审批持久化及 sink 的行为仍需单独测试。

```python
"""范围契约示例。实跑状态：2026-10-20，Python 3 标准库。"""

SCOPE = [
    {
        "id": "S1", "status": "in",
        "what": "一个合成订单查询与公开政策检索任务",
        "tool_modes": {"lookup_order": "read-only", "search_policy": "read-only"},
        "reason": "固定输入和数据版本，让结果可判定",
        "acceptance": "订单/政策字段按用例返回；缺失数据不伪造",
    },
    {
        "id": "S2", "status": "in",
        "what": "一个审批后发送到本地合成 sink 的通知动作",
        "tool_modes": {"send_notice": "approval-required"},
        "reason": "覆盖提议、审批、投递与未知结果对账",
        "acceptance": "未授权不投递；未知回执不自动重试",
    },
    {
        "id": "S3", "status": "in", "what": "任务持久化、中断恢复与预算/审计边界",
        "tool_modes": {}, "reason": "属于该综合项目的交付目标",
        "acceptance": "对应数据库集成/恢复演练有独立证据",
    },
    {
        "id": "X1", "status": "out", "what": "真实客户数据和真实外部投递",
        "tool_modes": {}, "reason": "教学环境只用合成记录与本地 sink",
        "acceptance": "目标环境具备身份、授权、隐私、幂等和对账设计后再立项",
    },
    {
        "id": "X2", "status": "out", "what": "任意售后任务和自由扩展的工具目录",
        "tool_modes": {}, "reason": "当前证据只覆盖冻结任务与注册表",
        "acceptance": "新增意图需增加风险分析、场景覆盖和回归证据",
    },
    {
        "id": "X3", "status": "out", "what": "基于 fixture 或单次 smoke 宣称通用质量/生产就绪",
        "tool_modes": {}, "reason": "该证据不足以支持该强度的结论",
        "acceptance": "使用代表性盲测、独立评分与目标环境验收",
    },
    {
        "id": "D1", "status": "deferred", "what": "多区域 HA 与跨 provider 线上质量等价",
        "tool_modes": {}, "reason": "不属于本地有界 smoke 的验证范围",
        "acceptance": "部署目标要求时重开，并建立容量/故障/迁移测试",
    },
]

# 独立运行时示例。接入应用时从唯一可信注册表动态生成：
# {name: "approval-required" if needs_approval else "read-only"
#  for name, (_schema, needs_approval) in REGISTRY.items()}
IMPLEMENTED_TOOL_REGISTRY = {
    "lookup_order": "read-only",
    "search_policy": "read-only",
    "send_notice": "approval-required",
}

VALID_STATUSES = {"in", "out", "deferred"}


def validate_scope(scope, tool_registry):
    ids = [item["id"] for item in scope]
    if len(ids) != len(set(ids)):
        raise ValueError("scope IDs must be unique")

    expected_tools = {}
    for item in scope:
        if item["status"] not in VALID_STATUSES:
            raise ValueError(f"{item['id']}: invalid status")
        for field in ("what", "reason", "acceptance"):
            if not item.get(field, "").strip():
                raise ValueError(f"{item['id']}: missing {field}")
        if item["status"] == "in":
            expected_tools.update(item["tool_modes"])
        elif item["tool_modes"]:
            raise ValueError(f"{item['id']}: out-of-scope item declares active tools")

    actual = dict(tool_registry)
    missing = sorted(set(expected_tools) - set(actual))
    extra = sorted(set(actual) - set(expected_tools))
    wrong_mode = sorted(
        name for name in expected_tools.keys() & actual.keys()
        if expected_tools[name] != actual[name]
    )
    if missing or extra or wrong_mode:
        raise ValueError(
            f"scope mismatch: missing={missing}, extra={extra}, mode={wrong_mode}"
        )
    return {"scope_ids": len(ids), "active_tools": sorted(expected_tools)}


if __name__ == "__main__":
    print(validate_scope(SCOPE, IMPLEMENTED_TOOL_REGISTRY))
    drifted = {**IMPLEMENTED_TOOL_REGISTRY, "refund_order": "approval-required"}
    try:
        validate_scope(SCOPE, drifted)
    except ValueError as error:
        print("新增未审批工具被检出:", error)
```

第一条输出证明的是示例注册表与示例范围契约一致；第二条用临时加入 `refund_order` 演示漂移会失败。它仍不能证明注册表从真实运行系统正确加载、权限策略无绕过、或 sink 真正遵守审批。实际项目应让 `tool_registry` 直接从唯一应用注册表生成，再以授权/跨租户/审批恢复/未知回执集成测试证明各自行为。**范围表定义边界，代码门禁定位差异，独立测试验证行为，验收者判断证据是否足够。**

## 范围不是“删功能换成本”

划范围的目的，是建立一份可以被实现、评测和验收共同引用的承诺。明确排除项确实能限制工作量，但不能据此断言某类工作就不需要：即使不支持多类型任务，仍要覆盖本范围内关键输入的通过、拒绝和异常；即使工具数量不变，也要验证权限和副作用；即使暂不支持持久化，也要把这一限制写入交付说明，并判断它是否与目标风险相容。

新增能力的评测工作量取决于它是否改变输入分布、判据、风险、数据权限或运行路径。它可能只需扩展现有测试，也可能需要新的分层数据和独立验收。先做差异分析，再选测试设计；“每个功能都要独立评测集”与“新增功能只增加实现成本”都是没有证据的通用化结论。

本项目把读文件列在范围外，不代表所有 Agent 都应排除文件输入。正确的判断是：若要纳入，就要定义允许的文件来源、解析边界、敏感数据处理、引用/来源保留、注入威胁模型和相应的正反例测试。它们的成本要按实际实现和验证估算，不能使用未经测量的“功能一天、配套两周”作排期依据。

## 一个可带走的判据

有人提出“顺手支持 X”时，先问四个可检查的问题：它改变了哪些用户结果、数据或身份边界、工具副作用和运行约束？当前测试能否判定关键通过与失败状态？风险控制由哪一层执行？新增承诺会把哪些事项从 out/deferred 移入 in？回答后再决定扩展既有用例、新增分层用例、先做原型，还是暂不纳入。

这套问题不要求每个小改动都配一套独立评测集，也不把短期实现估算伪装成普遍规律；它要求新增承诺对应新增证据，并让证据强度匹配风险。
## 常见坑

- **只列"做什么"。** 那不是范围表，是愿望清单 —— 没有边界的项目一定会膨胀。
- **把评测集当作唯一划界标准。** 应同时看用户结果、数据/身份、权限与副作用、证据和运行约束；评测可扩展现有集合，也可能需要独立设计。
- **把它当成技术选型。** 首要原则是**爆炸半径**：这个功能会不会改变"出事之后能造成多大破坏"。
- **"以后可能做"和"明确不做"混在一起。** 前者是洞，后者是有理由的取舍，必须写清楚。
- **排除能力却不检查风险是否仍可接受。** 边界要在交付时明确说明，并与目标场景的可靠性要求相容。
- **范围表写完就不看。** 它的三个用途（防膨胀、交付、复盘）都要求它被反复引用。
