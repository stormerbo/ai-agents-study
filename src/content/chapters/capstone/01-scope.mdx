最后一章要做一个完整的项目。而第一步不是决定做什么 —— 是**决定不做什么**。

## 为什么"不做什么"要写在最前面

第 2 章讲过上下文工程里的一个结论：**放进去不等于读得到。** 项目范围也一样 —— **加进来不等于做得完。**

一个没有边界的 agent 项目会朝三个方向膨胀：

| 膨胀方向 | 表现 |
|---|---|
| **工具越加越多** | 第 4 章实测：约 60 token/个，每轮都要付；第 18 章算过 30 轮时工具定义占输入侧 62% |
| **任务类型越来越杂** | 每一类都要自己的评测集、自己的判据、自己的审批点 |
| **顺手也支持一下** | 每一个"顺手"都是一个要维护的分支 |

三者都有同一个特征：**它们在加的时候看不出代价。** 代价出现在两周后 —— 上下文变长、成本上升、而你说不清是哪一次改动引起的。

## 一个具体的划法

这一章的项目我定的范围是这样的。**这是一份带 id 的表，后面代码里的 `SCOPE` 就是它**（`in` 是 S1–S4，`out` 是 X1–X4）—— 正文和代码引用的是同一份，不是两张各说各的清单。

| id | 类型 | 条目 | 理由 | 若做了会引入什么 |
|---|---|---|---|---|
| **S1** | 做 | 订单咨询这一类任务 | 只做一类，才养得起一套评测集 | —— |
| **S2** | 做 | 三个工具：`get_order` / `get_policy` / `send_reply` | 约 60 token/个且每轮重付（第 4/18 章）；数量本身不影响准确率（8→86 都 8/8） | —— |
| **S3** | 做 | 一个不可逆动作：`send_reply` | 审批点越少越容易验证 | —— |
| **S4** | 做 | 脚本化决策（不接真实模型） | 让整条链路可复现、可断言 | —— |
| **X1** | 不做 | 更多工具 | 成本线性增长且每轮重付（第 4/18 章） | 每个新工具都要重跑选择准确率、更新策略白名单 |
| **X2** | 不做 | 多任务类型 | 每一类都要自己的评测集与判据 | 用例数 × 类型数，审批点翻倍 |
| **X3** | 不做 | 多轮澄清 | 第 19 章已完整讲过机制，重实现不增加新东西 | 一套中断/恢复协议 + 澄清轮的用例 |
| **X4** | 不做 | 持久化存储 | 用内存；交付文档中说明这个缺口 | 状态迁移与向后兼容 |

最后四行（X1–X4）值得单独说：**它们是「明确不做」，不是「没来得及做」。** 区别在于前者有理由、有替代方案（交付时告知使用者），后者只是一个洞。而第五列（若做了会引入什么）就是这两者的分界线 —— 说不出来的那一条，通常过两周就会被推翻。

## 划范围时用的三个判据

**判据一：这个东西要不要自己的评测集？** 要 → 它是一个独立的能力，范围会翻倍。这个判据比"工作量"更可靠，因为评测集的成本容易被低估。

**判据二：它会不会改变"出错的爆炸半径"？** 会 → 它需要自己的审批点和回滚方案。

**判据三：不做它，这个项目还能不能演示它要演示的东西？** 能 → 不做。

第三条是这个项目里最常用的。比如"多轮澄清"—— 第 19 章已经完整讲过了，这个项目再实现一遍**不会增加任何新东西**，只会增加维护面。

## 一个具体的产物：范围表

划范围的产出是一张表，而它必须包含**不做那一列**。只有"做什么"的表不是范围表，是愿望清单。

这张表有三个用途：

1. **防止中途膨胀** —— 有人提"能不能也支持 X"，答案已经在表里
2. **作为交付文档的一部分**（第 4 节）—— 接手的人需要知道边界在哪
3. **作为复盘的依据**（第 5 节）—— 复盘时对照它，看哪些判断错了

第三条特别实际：**没有范围表就没法复盘。** 你只能说"做得不太好"，说不出"我当时判断 X 不重要，结果是错的"。


## 一个具体的问题：范围表的第一稿通常是错的

上面那张范围表看起来干净，但它是**改过两遍**的。第一稿里我写了这些：

```text
第一稿的「做」：
  · 订单咨询
  · 支持读文件（"让 agent 能看文档"）
  · 支持多轮澄清（"不然体验不好"）
  · 接真实模型（"这才像真的"）
```

第二稿把它们全砍了。理由分别是：

| 第一稿 | 砍掉的理由 |
|---|---|
| 支持读文件 | **它引入了"外部内容"这一类新输入** —— 而按第 17 章，那意味着要做来源标注、要做注入防护。范围会翻倍 |
| 支持多轮澄清 | 第 19 章已经完整讲过机制，在这里重实现**不增加任何新东西** |
| 接真实模型 | 会让整条链路不可复现 —— 而这一章要演示的是"机制装进系统"，不是"模型调用" |

**三条砍掉的理由可以归成一句话：它们都不服务于"演示目的"。** 第一条引入了新维度，第二条是重复，第三条损害了可复现性。

这就是划范围的实操形态 —— **它不是"挑最重要的做"，而是"砍掉所有不服务于当前目的的东西"。** 而"当前目的"必须先写下来（这一章的目的是"把全书的生产化机制装进一个能跑的系统"），否则砍无可砍。

## 一个可以自查的问题

范围表写完之后，问一个问题：**表里"不做"那一列，每一条能不能说出一句"如果做了会怎样"。**

说不出来的那一条，通常是"因为觉得不重要"—— 而那个理由不够硬，它会在项目中途被推翻（有人会说"现在时间够了，加上吧"）。

能说出来的那一类，理由是可检验的：

- "做了会引入外部内容这一类输入" → 可检验（确实会）
- "做了不增加新东西" → 可检验（对照第 19 章）
- "做了会让链路不可复现" → 可检验（试一次就知道）

**这条自查的作用是：让范围表在两个月后还能站得住。** 因为两个月后你面对的不是"当时为什么不做"，而是"现在要不要加" —— 而后者需要前者给出一个可检验的理由。

## 范围表的失败形态

范围表不会"报错"，它只有一种坏法：**在第二周被悄悄违反。** 表现是某次提交里多了一个工具、或者"顺手"支持了一类任务，而没有人回来对照这张表 —— 表本身没坏，只是没人读。这类失败之所以危险，是因为**代码仍然能跑、用例仍然全绿**（X2 说的那套评测集，你根本没为它建）。

所以对治方式不是"记得看"，而是**把它变成可断言的东西**：下面那段脚本每次运行都会拿实际工具集与范围表对照，多出来的打 ⚠️。**一份只写在文档里、没有任何检查的范围表，等于没有** —— 这和第 3 节那条「纸面清单不会自己更新」是同一个道理。

## 完整可运行代码

下面这段代码把范围表变成可检查的形式：每个"不做"都带理由，而脚本会检查项目里有没有偷偷做了它。

```python
"""范围表：把「不做」变成可检查的东西。实跑状态：2026-10-09。"""

SCOPE = [
    {"id": "S1", "type": "in", "what": "订单咨询这一类任务",
     "why": "只做一类，才养得起一套评测集", "if_done": "-"},
    {"id": "S2", "type": "in", "what": "三个工具：get_order / get_policy / send_reply",
     "why": "约 60 token/个且每轮重付（第 4/18 章）", "if_done": "-"},
    {"id": "S3", "type": "in", "what": "一个不可逆动作：send_reply",
     "why": "审批点越少越容易验证", "if_done": "-"},
    {"id": "S4", "type": "in", "what": "脚本化决策（不接真实模型）",
     "why": "让整条链路可复现、可断言", "if_done": "-"},
    {"id": "X1", "type": "out", "what": "更多工具",
     "why": "成本线性增长且每轮重付（第 4/18 章）", "if_done": "每个新工具都要重跑选择准确率、更新策略白名单"},
    {"id": "X2", "type": "out", "what": "多任务类型",
     "why": "每一类都要自己的评测集与判据", "if_done": "用例数 × 类型数，审批点翻倍"},
    {"id": "X3", "type": "out", "what": "多轮澄清",
     "why": "第 19 章已完整讲过机制，重实现不增加新东西", "if_done": "一套中断/恢复协议 + 澄清轮的用例"},
    {"id": "X4", "type": "out", "what": "持久化存储",
     "why": "用内存；交付文档中说明这个缺口", "if_done": "状态迁移与向后兼容"},
]

FOUND_TOOLS = ["get_order", "get_policy", "send_reply"]
FOUND_FEATURES = ["in_memory_store"]


if __name__ == "__main__":
    print("=== 范围表 ===")
    print("  做：")
    for x in SCOPE:
        if x["type"] == "in":
            print("    ✅ %-3s %s" % (x["id"], x["what"]))
    print("  明确不做（带理由 + 若做了会引入什么）：")
    for x in SCOPE:
        if x["type"] == "out":
            print("    ❌ %-3s %-14s %s" % (x["id"], x["what"], x["why"]))
            print("         若做了：%s" % x["if_done"])
    print()
    print("=== 检查：有没有偷偷做了不该做的事 ===")
    allowed = {"get_order", "get_policy", "send_reply"}
    extra = [t for t in FOUND_TOOLS if t not in allowed]
    print("  工具：%s" % ("✅ 与范围一致" if not extra else "⚠️ 超出范围：%s" % extra))
    print("  存储：%s" % ("✅ 内存实现（属明确不做，交付时需说明）"
                          if "in_memory_store" in FOUND_FEATURES else "未知"))
    print()
    print("  这张表有三个用途：防中途膨胀 / 交付时告知边界 / 复盘时对照判断。")
```


## 一个和"范围"有关的常见误解

"划范围"听起来像是把大项目砍小，但它其实是**决定这个项目要验证什么**。

上面那张表里，"只做订单咨询这一类任务"看起来是砍功能，实际的效果是：**它让"一类任务的评测集"这件事变得可能。** 如果支持十类任务，那每一类都要自己的判据、自己的用例、自己的审批点 —— 而这些成本加起来会比功能本身大得多。

所以范围表的每一条"不做"，都可以翻译成一句"因此我不需要付的成本"：

```text
不做多类型任务  → 不需要多套评测集与判据
不加更多工具    → 不需要为新增工具重测选择准确率
不做多轮澄清    → 不需要为澄清轮设计中断与恢复
不做持久化      → 不需要管状态迁移与向后兼容
```

**右边那一列才是划范围的真实收益。** 它让"这个项目要花多少维护成本"变成一个可以估算的数字，而不是一个"看情况"。

而第 3 节的加固清单、第 4 节的交付文档，各自都在引用这张表 —— **范围表是整个项目里被引用次数最多的那份材料**，这也是它值得在第一周就写清楚的原因。

## 一个可以带走的判据

如果只记一条关于划范围的东西，记这条：

**问"这个功能要不要自己的评测集"。**

它比"工作量多大"可靠，原因是**评测集的成本容易被系统性地低估**。一个功能写起来可能三天，但它带来的评测集要持续维护：每一类输入要加用例、每个判据要单独写、每次改动都要跑。而这份成本不会出现在任何一份排期表里。

所以当有人问"能不能顺手也支持 X"时，第一个反问不是"要多久"，而是 **它有自己的一类输入吗？** —— 有，那它就是一个独立能力，成本是功能本身的好几倍。

这条判据在这个项目上的应用很直接：支持读文件被砍掉，正是因为它引入了"外部内容"这一类新输入（第 17 章），要配套做来源标注与注入防护 —— **功能是一天，配套是两周。**
## 常见坑

- **只列"做什么"。** 那不是范围表，是愿望清单 —— 没有边界的项目一定会膨胀。
- **按工作量划范围。** 应该按"要不要自己的评测集"来划 —— 评测集的成本更容易被低估。
- **把它当成技术选型。** 首要原则是**爆炸半径**：这个功能会不会改变"出事之后能造成多大破坏"。
- **"以后可能做"和"明确不做"混在一起。** 前者是洞，后者是有理由的取舍，必须写清楚。
- **不做持久化却不说明。** 明确的缺口要在交付时告知使用者，而不是被当成 bug。
- **范围表写完就不看。** 它的三个用途（防膨胀、交付、复盘）都要求它被反复引用。
