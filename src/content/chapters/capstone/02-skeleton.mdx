范围定好之后，第一版代码要形成一条可验证的纵向路径。对本书当前 P5 来说，这条路径是合成任务进入宿主、调用受控 provider、处理工具提议和审批、记录持久状态，并把通知送到本地合成 sink；它不是内存里的一次 `for` 循环。教学样例可以更小，但必须明确哪些机制是模拟的、哪些保证还没实现。

“能跑”只说明路径执行过，不说明状态、权限、外部副作用或崩溃恢复正确。若第一版把模型输出直接当作授权、审批状态只放进进程内存，或把外部投递响应丢失当成失败重试，后续补救会改变存储、状态机和调用方协议。因此骨架阶段要先给这些边界安排清晰位置；具体组件取舍仍应由项目需求决定。

## 一个具体的反面例子

下面是一个**故意不安全的反例**，用于说明调用边界缺失。它与本书 P5 的工具名和实现无关：当前 P5 使用 `lookup_order`、`search_policy` 和需审批的 `send_notice`，写入目标为本地合成 sink。

```python
def send_reply(to, body):
    return {"sent": True, "to": to}

# 循环里：
for step in plan:
    out = TOOLS[step.name](**step.args)     # 直接调，没有策略、没有审批
```

**这段代码能跑通，而且演示效果很好。** 但它把授权决策、审批状态、动作回执与可审计记录全部省略了。即使把工具名放进白名单，也不能单独证明调用者有权操作当前租户和资源。

若系统的目标包含这些保证，却没有统一的宿主执行入口和明确的状态边界，后续改造可能触及多个调用路径；实际改动范围应由代码结构评估，不能预设必然分散或漏检。

因此第一条纵向路径至少要能观察：请求如何被验证、动作如何获得授权、状态如何持久化、未知效果如何停住，以及用什么证据判定完成。对于纯本地、无副作用原型，可暂时省去持久化或人工审批，但要写出省略条件和不能据此声称的能力。

## 骨架要留的五个位置

| 关注点 | 可验证的最小实现 | 边界 |
|---|---|---|
| **工具目录与执行入口** | 由可信注册表生成模型可见 schema，所有调用走同一个宿主入口 | 注册表说明“有哪些能力”，不等于按身份、租户、对象授权 |
| **授权与策略** | 在副作用执行前由宿主检查主体、资源、策略和当前状态 | allowlist 只是能力上限之一，不能代替业务授权 |
| **状态与恢复** | 明确哪些状态需要跨进程保存，并对崩溃/重启做恢复测试 | 单进程变量只适合明确标注的演示，不能叫持久化 |
| **预算与停止** | 在 provider 请求前预留预算，调用后按实际 usage 对账；缺 usage 时保留未知状态 | 单个计数器可做教学闸门，不能代表共享配额或真实费用结算 |
| **观测与审批** | 记录足够定位的事件；有影响的动作使用带主体、目标、参数版本和时效的审批记录 | 轨迹按数据分级最小化；审批不应只看可逆性 |

这些关注点中，策略、状态和副作用边界容易被推迟，因为 happy path 里它们“看不出效果”。它们是否必须进入首个切片，取决于该切片是否会处理真实身份、持久任务或外部副作用；但如果目标承诺包含这些能力，就必须在骨架里能验证：

- 授权要发生在副作用之前 —— 不能只依赖模型 prompt 或前端按钮
- 等待审批、拒绝、过期和重启后的状态需要有明确转换 —— 单纯返回一个 `input_required` 并未实现持久恢复

## 一个具体的结构

下面的顺序是一种教学检查表，不是适用于所有项目的强制架构。当前 P5 的对应实现位于 provider adapter、durable task/action 状态、授权/approval 路径、预算 reservation、事件记录与本地 sink；该实现比单进程样例多出数据库和进程边界。

```text
1. 工具目录（第 11 章）
   trusted registry → provider schema；执行仍由宿主验证

2. 主体/资源授权（第 16 章）
   authenticated principal + tenant + resource + current policy → authorize

3. 状态与预算（第 18 章）
   persist request/reservation → call provider → settle observed usage

4. 事件与审计（第 15 章）
   trace event IDs, decisions, status transitions; minimize sensitive payloads

5. 审批（第 19 章）
   approval binds principal, target, canonical args/version, policy and expiry
```

审批是否适用应结合动作影响、授权主体、目标资源、参数、金额/额度、数据敏感度、可撤销性和组织策略判断。可逆性只是输入之一；不能把“所有不可逆都审批”或某次分组表现直接提升为跨场景政策。

后文的完整可运行程序是一个单进程、内存状态的教学模型。它按 `reversible` 演示挂起与重入，不是当前 P5 实现，也不具备身份认证、租户/资源授权、数据库持久化、审批到期或并发安全。程序中的 `POLICY`/scope 字段只是样例分支，不能作为权限实现；上线系统必须在真实执行路径接入授权与持久化状态机，并测试拒绝、过期、参数/资源变化、崩溃恢复和未知外部结果。

决策由可信宿主在工具执行前作出，不能让模型通过工具参数放宽自己的权限。

**预算必须说明口径。** 程序里的 `BUDGET["max_tokens"]` 是教学用的任务累计阈值，`spend(3000, ...)` 是固定模拟值，不是 provider 实际 usage，也不包括并发任务共享配额、预留竞态或账单金额。provider 请求的输出上限（如 P5 请求中的 `max_tokens: 512`）是单次调用参数，和任务级预算不是一回事。生产实现应使用不同字段名，例如 `max_output_tokens` 与 `task_token_limit`，并记录预留、实际 usage 和未知用量；不能拿固定常数冒充真实成本。

## 骨架跑通的标准

“跑通”需要一个明确判据。以下八条是**后文单进程示例的测试**，覆盖的是它实现的行为，不是完整 P5 的验收标准：

| 用例 | 断言 |
|---|---|
| 正常只读路径 | 两个只读函数返回预期合成字段 |
| 动作进入审批分支 | 示例中标记为不可逆的 `send_reply` 返回 `input_required`；不代表通用审批政策 |
| 挂起停止后续步骤 | 后续计划步骤未执行；仅证明进程内函数返回行为 |
| 显式拒绝 | 返回 `denied` 且停止示例计划 |
| 批准后的重复调用 | 同进程重复调用进入本地 `EXECUTED` 去重分支；不是并发/崩溃/外部 exactly-once 证明 |
| 未注册工具 | 示例策略函数拦截 `delete_all`；不是身份或对象授权测试 |
| 轮次上限 | 第七次循环进入教学停止分支；固定 `3000` 计数不是实际 token usage |
| 事件记录 | 示例 trace 含工具和原始结果，演示定位但不满足生产日志最小化 |

这些测试能作为该教学程序的局部回归集。它们不等同第 15 章某个项目的评测集，更不等同当前 capstone acceptance 的 gate 矩阵；“8/8”只描述本文件固定样例的一次执行。

预算到顶时是否返回已有结果、转入可恢复状态或报告失败，取决于调用方契约和部分结果是否安全可用。不得将未完成结果标记为完整；本程序的 `partial` 只是单进程返回值，无法代表持久化恢复。测试应断言终态、已提交副作用和可恢复信息，而不是只断言“停了”。

### 审批停下之后，谁把它续起来

示例 `ask()` 把请求放进内存 `APPROVALS` 后返回 `input_required`，只演示局部暂停分支。要声称可恢复，宿主还需持久化等待任务和审批请求，并在批准后安全安排恢复；只返回一个标记并没有完成这条链路。

宿主侧需要持久化审批请求，并绑定经认证的审批人、目标资源、规范化参数/版本、策略版本和有效期。下面是**只解释控制方向的伪代码**，不是安全实现：

```python
def host_resume(task_id, approval_request_id, authenticated_approver):
    # 伪代码：读取可信存储并检查审批资格、时效、参数哈希、资源和策略版本。
    request = load_and_validate_approval(
        task_id, approval_request_id, authenticated_approver
    )
    record_approval_decision(request, authenticated_approver)
    return schedule_durable_resume(task_id)
```

三个必须说清的点：

1. **谁在什么时机把 `approved_ids` 传回来**：宿主（UI / CLI / 服务端）在用户批准后，用**同一个 plan、带着 `approved_ids` 再调一次 `run()`**。不是「让 agent 继续」，而是「重放一次，这次带上钥匙」。
2. **`seen` 字段给谁用**：它是 `APPROVALS` 里那条请求的展示状态（用户看没看过），给宿主 UI 用；agent 循环本身不读它。
3. **为什么不能把一次 `run()` 重入叫作安全恢复**：示例的 `approved_ids` 是调用者可构造的集合、`EXECUTED` 是进程内列表；它没有认证批准人、持久化决议、参数/策略版本校验或并发防重。幂等键也不能单独保证外部副作用 exactly-once。当前 P5 通过数据库 approval/action/outbox 状态、worker fencing 与本地 sink 回执对账实现更完整路径，相关边界和 drills 见 `examples/p5-agent-delivery/`；该项目仍不宣称真实生产就绪。

旧版教学程序曾在 2026-10-12 记录过一次 `send_reply` 的内存重入输出。它只能证明当时那份单进程脚本走过对应分支，不能证明授权、跨进程恢复、外部投递或当前 P5 的行为。本书当前 P5 的验收路径把“审批暂停 → durable resume → 本地投递 → 保存回执/未知状态 → 必要时对账”作为独立阶段；完整 PostgreSQL drills 与其报告才是这条路径的本地证据来源。具体是否通过，按运行报告与断言判断，不能从这段历史输出推断。

## 一个容易忽略的细节：骨架阶段不要优化

实现顺序上，可以先保证一条路径可判定，再按真实瓶颈优化；这不是“骨架阶段一律不做性能/成本工作”的普遍规则。

若还没有负载或服务目标，性能优化可能缺少目标函数；但容量约束、请求超时、取消、并发上限和成本闸门可能本来就是需求的一部分，应按运行边界尽早定义。优化是否保留取决于测量结果与维护成本，不能笼统断言早期优化通常会被删。

在本项目范围内，调用轮数和任务/共享预算限制属于可验证的控制条件。第 18 章的 30 轮/单轮约 405 倍，是固定假设下的情景算术结果：23,070 个上下文与工具 schema token 除以单轮无工具上下文的 57 token，约为 405。它不是历史 provider 实测或账单倍率，也不是通用成本曲线；该章另列的情景成本单位使用输出 4 倍权重等假设。系统应使用目标 provider 的实际 usage、预留与费用口径测量。


## 一个具体的顺序：先写用例还是先写实现

上面说骨架要留五个位置。但还有一个顺序问题：**八条冒烟用例是先写还是后写？**

工程上常见的一种做法是先根据需求写可观察的验收断言，再实现；这有助于避免只把现有实现固化成测试。但不能据本节现有材料断言三种方法都经过对照实验并得出“先写”这一普遍结论：

| 做法 | 结果 |
|---|---|
| 先实现，再补测试 | 有把当前行为当成需求的风险；仍可通过独立验收标准来避免 |
| 先写验收条件，再实现 | 先明确可观察结果与失败形态；实现可随后按这些契约迭代 |
| 手动探索后补自动化 | 适合发现未知问题；稳定重复的关键路径仍应固化为可重复检查 |

第一行的差别值得展开：**"照着实现写用例"和"照着需求写用例"看起来产出一样，但它们测的东西不同。**

一个具体的例子。如果我先实现了循环，再补"预算生效"这条用例，我大概率会写成"跑十步，确认它在第六步停下" —— 那是照实现写的。

例如，预算超限时的预期不能预先简化为“返回已有结果”：应先约定是否保留部分结果、任务标为哪种状态、已发生的副作用如何呈现、是否允许恢复，再据此写测试。以需求为先能促使这些问题显式化，但不自动保证测试覆盖充分。

对于这里的八条示例测试，应从期望的外部行为写判据，再检查实现。但仅凭测试先后顺序不能证明测试有效；还要验证失败场景能让测试失败、断言对应需求而非实现细节，并将未覆盖风险明确列出。

## 一个反过来的检查：位置留了但没用

最后说一个常见形态：**五个位置都留了，但有两三个是空壳。**

具体表现：策略表存在但没有对主体/资源进行授权；轨迹函数存在却未在关键状态转换调用；预算字段存在但从未按真实 usage 结算；approval 行存在却能被不同参数或无权用户消费。

这种"留了但没用"比"没留"更糟 —— 因为它给人已经做了的错觉。检验方式很简单：**每个位置问一句"如果我现在删掉它，会不会有测试失败"。**

- 删除某个授权检查 → 对应的未授权主体/越界资源测试应失败
- 删除事件写入 → 状态转换和审计顺序的集成断言应失败
- 删除预算 reservation → 并发任务总额测试应发现超额预留
- 删除 approval 参数绑定 → 修改目标/参数/版本的恢复测试应失败

**测试应触达机制真实执行的边界**，而不只是调用一个看起来像策略的 helper。单元测试、数据库集成、故障演练和线上 smoke 证明的范围不同；合起来也要看它们覆盖了哪些风险。
## 完整可运行代码

下面是一个单进程、内存状态的局部教学实现，以及针对它的八条回归用例。它刻意不实现生产系统的真实授权、持久化和外部投递；不能当作当前 P5 应用或生产骨架。

**实跑状态：2026-10-20**，本地 Python 3 抽取程序运行，固定样例 8/8；这只是该脚本的回归结果，非 provider、PostgreSQL 或生产安全测试。

```python
"""One-process teaching model. This is not the P5 durable application.

It demonstrates a few local branches with scripted decisions. It does not
provide identity/tenant authorization, persistence, concurrency safety,
provider usage accounting, or reliable external delivery.
Historical run date: 2026-10-09; no provider experiment is reproduced here.
"""
import json, time

# ═══════════════ 1. 工具注册表（第 11 章）═══════════════

REGISTRY = {}


def tool(name, *, reversible, scopes=()):
    def deco(fn):
        REGISTRY[name] = {"fn": fn, "reversible": reversible, "scopes": set(scopes)}
        return fn
    return deco


@tool("get_order", reversible=True, scopes={"read:order"})
def get_order(order_id):
    return {"id": order_id, "status": "已发货", "amount": 1288.50}


@tool("get_policy", reversible=True, scopes={"read:policy"})
def get_policy(region):
    return {"region": region, "return_days": 7}


@tool("send_reply", reversible=False, scopes={"send:email"})
def send_reply(to, body):
    return {"sent": True, "to": to}


# ═══════════════ 2. 执行策略（第 16 章）═══════════════

POLICY = {
    "default": "deny",
    "allow": {
        "get_order": {"read:order"},
        "get_policy": {"read:policy"},
        "send_reply": {"send:email"},
    },
}


def check_policy(name):
    if name not in POLICY["allow"]:
        return False, "default=deny：没有规则"
    if name not in REGISTRY:
        return False, "未注册的工具"
    missing = POLICY["allow"][name] - REGISTRY[name]["scopes"]
    if missing:
        return False, "权限不足：%s" % missing
    return True, "ok"


# ═══════════════ 3. 预算与熔断（第 18 章）═══════════════

BUDGET = {"max_turns": 6, "max_tokens": 20000, "breaker_after": 3}
# 注意：这里的 max_tokens 指的是**整个任务的累计 token 预算**（每一步累加），
# 不是单次请求的输出上限 —— 它和第 24 章那个 max_tokens 同名不同义。
STATE = {"tokens": 0, "turn": 0, "fails": 0, "spent": []}


def spend(tokens, what):
    STATE["tokens"] += tokens
    STATE["spent"].append((what, tokens))


def budget_ok():
    if STATE["turn"] >= BUDGET["max_turns"]:
        return False, "步数上限"
    if STATE["tokens"] >= BUDGET["max_tokens"]:
        return False, "预算上限"
    if STATE["fails"] >= BUDGET["breaker_after"]:
        return False, "熔断打开"
    return True, "ok"


# ═══════════════ 4. 轨迹（第 15 章）═══════════════

TRACE = []


def trace(kind, **kw):
    TRACE.append({"step": STATE["turn"], "t": round(time.time() % 1000, 3),
                  "kind": kind, **kw})


# ═══════════════ 5. 审批（第 19 章）═══════════════

APPROVALS = []


def needs_approval(name):
    """为保持示例简短的占位策略；生产策略还需检查主体、资源与影响范围。"""
    # 只演示暂停/恢复，不授予真实主体权限。
    return not REGISTRY[name]["reversible"]


def ask(name, args):
    APPROVALS.append({"action": name, "args": args, "why": "不可逆（发出后无法撤回）",
                      "seen": False})
    return {"result": "input_required", "action": name, "args": args,
            "why": "不可逆（发出后无法撤回）"}


# ═══════════════ 6. 循环 ═══════════════

EXECUTED = []


def call_tool(name, args, approved_ids=(), denied_ids=()):
    ok, why = check_policy(name)
    if not ok:
        trace("deny", tool=name, why=why)
        return {"error": why}
    if needs_approval(name):
        key = "%s:%s" % (name, json.dumps(args, sort_keys=True))
        if key in denied_ids:
            return {"result": "denied", "action": name, "args": args}
        if key not in approved_ids:
            trace("approval_requested", tool=name, args=args)
            return ask(name, args)
        if key in [e["key"] for e in EXECUTED]:          # 幂等（第 11 章）
            trace("idempotent_skip", tool=name)
            return {"skipped": True, "reason": "已执行过"};
    out = REGISTRY[name]["fn"](**args)
    EXECUTED.append({"key": "%s:%s" % (name, json.dumps(args, sort_keys=True)),
                     "action": name, "args": args})
    trace("result", tool=name, result=out)
    return out


def run(plan, approved_ids=(), denied_ids=()):
    """plan 是脚本化的"模型决策"序列 —— 每一步是 (工具名, 参数字典)。"""
    out = None
    for name, args in plan:
        STATE["turn"] += 1
        ok, why = budget_ok()
        if not ok:
            trace("stopped", reason=why)
            return {"stopped": why, "partial": out, "turns": STATE["turn"]}
        spend(3000, name)
        out = call_tool(name, args, approved_ids, denied_ids)
        if "error" in out:
            STATE["fails"] += 1
            return {"ok": False, "status": "failed", "result": out,
                    "partial": None, "turns": STATE["turn"]}
        if out.get("result") == "input_required":
            return {"ok": False, "status": "waiting_approval", "result": out,
                    "partial": None, "turns": STATE["turn"]}
        if out.get("result") == "denied":
            trace("approval_denied", tool=name, args=args)
            return {"ok": False, "status": "denied", "result": out,
                    "partial": None, "turns": STATE["turn"]}
        STATE["fails"] = 0
    return {"ok": True, "status": "completed", "result": out, "turns": STATE["turn"]}


def reset():
    STATE.update({"tokens": 0, "turn": 0, "fails": 0, "spent": []})
    TRACE.clear(); EXECUTED.clear(); APPROVALS.clear()

# ═══════════════ 7. 冒烟评测集（第 15 章）═══════════════
```

## 一个具体的判断：骨架阶段该不该处理错误

最后一个实践问题：骨架阶段要不要写错误处理？

是否需要在首个切片处理某种错误，取决于这条路径是否已包含对应边界。策略拒绝、审批挂起和预算耗尽会影响调用方状态，因此应写进响应/状态契约。若路径已经包含网络调用或外部副作用，就必须定义超时、取消、解析失败、provider 截断、未知响应和恢复行为；它们可能决定是否重复扣费或重复执行动作，不能一概推迟为“实现细节”。纯离线原型可以把它们列为未覆盖项，但不得据此宣称端到端可恢复。

判据不是简单的“是否改变返回值”，而是失败后系统能否判断请求是否发出、状态是否提交、副作用是否发生、下一步能否安全继续？若不能，结果应标记为未知并进入可审查的恢复/对账路径。provider 返回 `is_error` 等结构化错误也要按具体协议处理，不能让错误文本误入业务结果；第 4 章的观测仅支持对应 provider/样本，不代表所有 API 都采用相同结构。
## 常见坑

- **把模型可见工具表当成授权。** schema/registry 告诉模型可提议什么，不证明调用主体有权执行。
- **把日志原样记录参数和返回值。** 轨迹需支持定位，但应按数据分级最小化、脱敏、限制访问和保留期。
- **把单进程测试叫作持久恢复。** 它没有覆盖进程退出、数据库事务、lease takeover 或副作用未知状态。
- **把可逆性当成唯一审批规则。** 它会漏掉可逆但高影响的动作；审批策略还要检查影响范围、敏感度、资源和主体授权。
- **把固定 token 数记成实际 usage。** 调用前预留、调用后结算，并区分单次输出上限、任务预算和共享配额。
- **把局部测试夸成完整验收。** 为每条承诺写可观察断言，同时标明尚未覆盖的阶段。
- **把历史成本倍率当作所有系统的成本曲线。** 用当前 endpoint、usage 与调用轨迹重新测量。
