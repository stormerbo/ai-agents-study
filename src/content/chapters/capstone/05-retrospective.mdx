复盘的核心问题不是「做了什么」，而是：**哪些判断被新证据支持、限制或推翻？** 它把当时的假设、观测记录、测量方法和后来采取的行动放在一起，帮助下一轮决策；它本身不能证明系统可靠，也不能把无法重建的历史记录变成实验证据。

## 为什么必须写这一节

实现检查回答「代码按预期运行了吗」，复盘还要追问「预期是否合理、证据能支持多强的结论、结论适用于什么场景」。这两类检查有交集：测试、故障演练和独立评审也能检验判断。复盘的价值在于把判断与依据连起来，避免只记结果、不记测量条件。

## 这个项目里的三类修正

下面是本课程曾记录的三个例子。它们的证据强度并不相同，不能统称为「三次数据正确、解释错误」。

| 主题 | 可以保留的观察 | 证据边界 |
|---|---|---|
| LangChain 工具 schema | 指定版本和类型声明下，字段 schema 未产生 enum；源码追踪指出 `parse_docstring` 默认关闭，散文描述也不会自动成为类型约束 | 限于记录中的 LangChain 版本、代码和配置；不要外推到所有装饰器或当前版本。见第 13 章与 `verify-output/read-source-tool.py` |
| 多智能体成本 | 历史汇总列出两组成本比 1.91× 与 1.99× | 逐次请求/响应未保存，无法独立复算，也不能判断背景大小是否影响倍数；两组数字不能外推为普遍成本结论。旧文曾写 2.37×，但未找到对应登记原始记录，已撤下（ERR-202）。见第 12 章与 `docs/DATA.md` |
| 提示注入 | 旧汇总写过 0/7，但逐次响应和完整三轮脚本缺失，现存脚本覆盖条件与汇总分母不一致 | 这是不可复核的历史摘要，不能当作模型行为、成功率或防护证据。见 ERR-050 与 `docs/DATA.md` |

复盘时要分别问：**观测有没有可核对的原始记录？测量器是否真的测了目标？解释是否由数据支持？应用范围是否足够窄？** 任一环节不成立，都应降低结论强度；测量或数据有缺陷时，不能只修解释。

这也是本项目的一条具体教训：**先检查观测与测量，再评估解释。** 数据记录可能不完整，评分器可能有假阳性，重复运行也可能波动；把这些可能性显式写出，比笼统地说「数据不会骗你」更有用。

## 一个具体的做法：把预测写下来

若主张可以通过实验检验，事先写下预测会让判定更清楚。第 22 章的源码阅读练习采用了这个方法：读源码前记录预期，再对照实际实现。

这个方法适用于**可检验的假设**：在运行前写下预测、比较对象、判定规则和停止条件。结果出来后先核对观测与规则，再判断差异可能来自机制、样本、实现还是测量。它不适合把所有结论都伪装成可量化预测；对规范事实、设计取舍或不可复现的历史主张，应记录来源、适用范围与不确定性。

这个顺序的差别很实际。如果先看数据再想解释，人会**下意识地找一个能容纳数据的解释** —— 而那个解释往往又符合直觉。反过来先写预测，数据与预测的差异就会立刻显现。

## 这个项目自己的缺口

复盘也要查「漏了什么」，但不能把较早版本的检查结果当成当前实现的完整清单。当前加固章登记了 14 项检查：其中审批目标/影响信息不足与缺少版本标识被检查器检出；示例没有真实模型回合，因此工具结果回流后的来源治理未验证。其他项目按当时范围标为缺口、警告或跳过，不应浓缩成「三项里一项判断错」这样的过期计数。

更稳妥的复盘条目要保留：检查项、检查时的代码版本、结果、判定规则、未覆盖场景和负责人。审批需要展示哪些信息，应结合执行主体、目标资源、影响范围和策略决定；返回值是否可信则要看数据来源与实际传递链路。单文件脚本没有上游服务只能说明该示例没覆盖上游降级，不能证明真实系统不需要降级。

这也解释了为什么要逐项对照清单：清单能减少遗漏，但本身也要有版本、范围和证据；「有一张表」不等于「验证完整」。

## 复盘的时机与全书路径

复盘可在阶段结束时、交付时或发生故障后进行。阶段结束时材料新鲜，适合核对预测与结果；交付时适合汇总跨阶段判断和待办；故障后则聚焦触发条件、影响与恢复。时机按项目节奏决定，不存在适用于所有团队的固定频率。可以在范围表和检查清单旁留下「当时的假设」及版本号，阶段收尾时再补观察和证据引用，减少事后依赖记忆。

综合项目现在有六个环节：划范围、搭骨架、加固、交付、复盘、最终验收。复盘整理判断和依据；验收还要检查运行证据、场景覆盖、恢复演练和独立交接，并由负责人作发布决定。六环节是本教程的练习路径，不是通用组织流程。

| 环节 | 核心问题 | 产物 |
|---|---|---|
| 划范围 | 做什么、不做什么 | 成功判据与排除项 |
| 搭骨架 | 最小流程如何运行 | 可运行切片与边界 |
| 加固 | 哪些风险尚未覆盖 | 有状态的检查清单 |
| 交付 | 别人如何接手 | 运行、验证与限制说明 |
| 复盘 | 判断与证据是否匹配 | 有范围和后续行动的记录 |
| 最终验收 | 有哪些证据支持发布决策 | 场景、运行、恢复、交接和人工决定 |

## 一个具体的产出：带证据边界的复盘表

复盘的产物不是「给项目证据打一个总分」，而是逐条记录主张和它的证据边界。把依据来源、原始产物是否存在、能否重放、当前主张状态分开，避免把「脚本存在」误当成测量有效，也避免把「没有脚本」误写成数据不存在。

```python
"""复盘记录：不把可重放性、证据来源和主张状态混成一个档位。

实跑状态：2026-10-20，Python 3 标准库，无外部依赖。
本表仅演示少数历史记录，不代表全项目证据健康度。
"""

RECORDS = [
    {
        "id": "langchain-schema",
        "claim": "本例的散文描述没有成为 enum 约束",
        "basis": "inferred",
        "provenance": "LangChain 指定版本源码追踪；第 13 章记录",
        "artifact": "local source-trace script recorded; runtime not rerun in this review",
        "replayability": "not-rerun",
        "claim_status": "bounded",
        "scope": "仅限记录的版本、类型声明和配置",
        "next_action": "版本升级时重新核对 schema 与源码",
    },
    {
        "id": "multi-agent-cost",
        "claim": "两组历史成本比为 1.91x 和 1.99x",
        "basis": "unverified",
        "provenance": "docs/DATA.md：历史汇总列出 1.91x 与 1.99x",
        "artifact": "summary only; raw per-run requests and responses were not retained; unsupported 2.37x claim withdrawn",
        "replayability": "unavailable",
        "claim_status": "bounded",
        "scope": "描述性样本，不能证明成本趋势或因果",
        "next_action": "保留离散结果；若需比较则采集新样本并标为新实验",
    },
    {
        "id": "injection-history",
        "claim": "历史摘要称 0/7，但分母和结果不可复算",
        "basis": "unverified",
        "provenance": "ERR-050；逐次 provider 响应和完整三轮脚本缺失",
        "artifact": "incomplete historical summary",
        "replayability": "unavailable",
        "claim_status": "unverified",
        "scope": "不得用于成功率、模型行为或防护效果",
        "next_action": "不补造历史数据；如有需要，另行设计并登记新实验",
    },
]

FIELDS = (
    "id", "claim", "basis", "provenance", "artifact", "replayability",
    "claim_status", "scope", "next_action",
)


def validate(records):
    """检查记录格式；不替人判断证据是否足以支持主张。"""
    for row in records:
        missing = set(FIELDS) - row.keys()
        if missing:
            raise ValueError(f"{row.get('id', '<unknown>')}: missing {sorted(missing)}")
        if row["basis"] not in {"documented", "inferred", "unverified"}:
            raise ValueError(f"{row['id']}: invalid basis")
        if row["claim_status"] not in {"supported", "bounded", "unverified"}:
            raise ValueError(f"{row['id']}: invalid claim status")
        if row["replayability"] not in {"replayed", "not-rerun", "unavailable"}:
            raise ValueError(f"{row['id']}: invalid replayability state")
        if row["claim_status"] == "unverified" and not row["scope"]:
            raise ValueError(f"{row['id']}: explain the verification limit")


def summarize(records):
    """仅汇总这组示例记录，绝不把计数解释成项目健康分。"""
    return {
        "example_records": len(records),
        "historical_runs_replayed": sum(row["replayability"] == "replayed" for row in records),
        "unverified_claims": sum(row["claim_status"] == "unverified" for row in records),
    }


if __name__ == "__main__":
    validate(RECORDS)
    for row in RECORDS:
        print(f"[{row['id']}] {row['claim']}")
        print(f"  basis={row['basis']}; artifact={row['artifact']}")
        print(f"  replayability={row['replayability']}; status={row['claim_status']}")
        print(f"  scope={row['scope']}")
        print(f"  next={row['next_action']}")
    print("示例集计数（不是项目证据健康分）:", summarize(RECORDS))
```

这里的 `basis` 沿用课程中的 `documented / inferred / unverified`，表示主张依据的性质；`artifact` 与 `replayability` 说明历史产物和重放状态；`claim_status` 和 `scope` 说明当前可以说到哪里。它们是不同维度，不能互相替代。比如某主张来自官方文档，仍要写清文档版本和适用条件；一个实验脚本可以重放，也仍可能有错误的评分器或偏差的样本。

这张表有意不设置总分或红黄绿评级，因为评级会掩盖不同的失败模式：没有原始材料、重放环境不一致、评分口径偏差、主张外推过远，需要的后续动作并不相同。一个可复算的脚本也不能替代证据审查；重跑时应先冻结依赖和输入，再对照原始期望，而不是只看脚本是否返回零退出码。判读时至少做四步：先核对来源与版本；再检查原始输入、输出和测量规则；然后判断证据是否覆盖当前主张；最后写清没覆盖什么。若关键产物缺失，就把历史结论保留为不确定；新跑的实验只能回答新运行的问题，不能冒充对旧样本的复现。

## 把复盘变成下一轮决策

以「共享背景变大后，多智能体成本倍数会上升」为例，不能只在复盘表里写「猜错了」。先写原假设的可检验版本：固定模型、工具、任务、输出要求和计费口径，只改变共享背景大小；记录每次模型请求的 input/output/cache usage 和最终费用；事先决定需要多少次重复，以及异常或失败运行如何处理。结束后同时报告原始次数、离散程度与缺失记录，不用两个均值接近就宣称「背景不影响成本」。如果随后发现成本比差异很大，先查请求是否命中缓存、输出长度是否变化、是否有遗漏调用，再决定是否修改成本模型。

这个例子说明复盘不是为过去找一个好听的故事，而是把证据变成下一步行动。行动可以是接受一个有限结论、补充测量、修改实现、收窄适用范围，或明确暂时无法判断。每条行动都要指向可核对的责任人、对象和结束条件；若不值得继续投入，也应记录停止理由。否则复盘表会变成无法闭环的观察清单。

## 复盘的执行顺序

一次可复查的复盘可以按以下顺序完成。第一，冻结时间范围和系统版本，避免把后续修复混进被评估对象。第二，从项目目标、风险登记和阶段决策里挑出会改变架构、成本、权限或上线结论的主张，不必把每个小决定都写进表。第三，为每个主张关联来源、代码版本、原始请求/响应或日志位置；敏感值应通过受控引用定位，不能为了可复查而无限复制到报告。第四，复核判定器与数据集：谁定义了通过、漏掉什么情形、失败样本是否被保留。第五，给主张标注当前状态及边界，写下可以改变决策的下一项证据。

产出应能让未参与项目的人回答三个问题：这条结论依赖什么？它在哪些条件下成立？什么新证据会让团队修改决定？如果回答不出来，就把该项标为未验证或缩小主张。不要拿摘要分数替代逐条判断，也不要把「没有发现问题」等同于「已证明安全」。最后将未完成行动放进交付/验收记录，指定责任人与重新检查的触发条件；否则复盘只保存了认识，没有改变后续执行。

## 常见坑

- **只复盘解释，不复盘测量。** 评分器、样本或日志缺陷会让观测本身不成立；先核原始产物和判定规则，再解释差异。
- **把缺失记录写成失败或成功。** 没有原始响应的历史汇总应标为不可复核，不能把缺证据补成零次成功，也不能用新运行替代旧样本。
- **把脚本存在等同于证据可靠。** 脚本可能复现的是错误判据；还要确认它覆盖目标、样本合适、运行条件匹配。
- **把局部观察变成普遍规律。** 保留版本、配置、任务、比较对象和样本量；不够支持一般结论时就降低措辞强度。
- **只复盘失败。** 成功也可能来自偶然或弱评分；定期抽查成功主张的依据质量，但不要把每个结果强行量化。
- **把复盘写成总结。** 总结记录做了什么；复盘还要记录当时为何这样判断、证据能支持到哪里、以后如何改变决策。
- **只在项目结束时复盘。** 对可检验假设，可在阶段开始时登记预测和判据，阶段结束后对照；规范事实与设计选择则保留出处、范围和理由。
